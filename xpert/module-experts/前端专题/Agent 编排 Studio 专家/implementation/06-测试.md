## 运行命令

> **本轮未实跑**：本次文档会话的可用工具不含 shell（仅只读检索），故下列命令中第 1 条是**调用方给定、本次未能执行**的原始命令，其余为按配置推导的等价/推荐形式。可执行性判定依据见下节与 PROJECT.md 的项目级实测记录。

```bash
# 1) 【调用方给定，本次未实跑】Nx + 单文件过滤

  --testPathPattern="features/xpert/studio/features/types.spec.ts" 2>&1 | tail -40

  --testPathPattern="features/xpert/studio" --skip-nx-cache 2>&1 | tail -60

# 3) 全项目（442 spec，最慢；仅做整体回归时用）
cd /root/xpert && timeout 1800 corepack pnpm nx test cloud 2>&1 | tail -60

# 4) 绕过 Nx 直接跑 jest（最快，免项目图计算）
cd /root/xpert && node node_modules/jest/bin/jest.js \
  --config apps/cloud/jest.config.ts \
  --runTestsByPath apps/cloud/src/app/features/xpert/studio/features/types.spec.ts

# 5) 直跑 jest + 路径正则（"studio" 全集）
cd /root/xpert && corepack pnpm exec jest --config apps/cloud/jest.config.ts \
  --testPathPattern "studio" 2>&1 | tail -40
```

**命令要点**
- 必须用 `corepack pnpm`（仓库 `packageManager: pnpm@10.24.0`，`.npmrc` 固定 `node-linker=hoisted`），裸 `pnpm` 会重建不兼容的 `node_modules`；
- Jest 30 已把 `--testPathPattern` 更名为 `--testPathPatterns`（旧名可用但有弃用提示）；**更稳妥的等价写法是 `--runTestsByPath <绝对/相对文件路径>`**（见第 4 条，不依赖正则转义）；
- 单文件全程约 30–60s 级（Angular/ts-jest 编译占大头）；`nx test` 首跑含项目图计算与 Jest 启动，故用 `timeout 600` 起步、全量用 `timeout 1800`；
- 若环境注入了 `NODE_OPTIONS`/`BASH_ENV`（IDE shim），参考同仓库其他专家资产的做法，用 `env -u NODE_OPTIONS -u BASH_ENV` 前缀剥离后再跑，避免 fs 拦截导致挂起。

## 测试模式要点

读 9 个 spec 归纳出三种模式与四个惯例：

**模式 A｜纯函数/工厂单测（4 个，无 TestBed）**
- `features/types.spec.ts`、`components/context-menu/middleware-groups.spec.ts`、`panel/workflow/middleware/middleware-features.spec.ts`：直接 `import` 被测函数 + 手写 fixture 数组，`toEqual` 断言整体结构（如分组 key 顺序 `['builtin','plugin:@xpert/plugin-b','plugin:@xpert/plugin-a']`）；i18n 以本地 `localize` 桩函数注入，避免引入 TranslateService。
- `header/studio-settings-source.spec.ts`：**用 `signal` 手搓一个 api 桩**（`viewModel: draft`、`saveDraft: jest.fn(() => defer(...))`、`getXpertTeam: jest.fn(() => of(...))`），断言 `source.draft === api.viewModel`（共享同一草稿引用而非拷贝）、discard 只回滚设置项、save 后 discard 以最近一次显式保存为基准，并用 `Subject` 制造「reload 在飞」的时序窗口。

**模式 B｜TestBed 组件测（2 个）**
- `panel/commands/commands.component.spec.ts`：顶层 `jest.mock('../panel.component')`、`jest.mock('../../domain')`（**把重依赖直接换成空类**），`TestBed.configureTestingModule({ imports: [TranslateModule.forRoot()], providers: [...] })` 全部用 `{ provide, useValue }` 提供假服务（`XpertStudioApiService`、`XpertAPIService`、`PromptWorkflowAPIService`、`SkillPackageService`、`ToastrService`），并用 **`TestBed.runInInjectionContext(() => new XxxComponent())` 直接 new 出组件类**（不渲染 DOM），配合 `await Promise.resolve()` 推进微任务；`afterEach(() => TestBed.resetTestingModule())`。
- `header/workbench-initial-layout-settings.component.spec.ts`：**真实渲染**（`imports: [TranslateModule.forRoot(), XpertWorkbenchInitialLayoutSettingsComponent]`——standalone 组件直接进 imports），用 `fixture.nativeElement.querySelectorAll('input[type="radio"]')` 走 DOM 断言，用自写 `settle()`（`detectChanges → await whenStable() → await Promise.resolve() → detectChanges`）等待异步视图流；并直接调 `fixture.componentInstance.setInitialLayout(...)` 验证「无变化不写草稿」。

**模式 C｜模板文本断言（3 个）**
- `studio.component.spec.ts`、`header/header.component.spec.ts`、`header/publish/publish.component.spec.ts`：`readFileSync(join(__dirname, '*.component.html'))` 读模板，用 `toContain` / `indexOf` **顺序与片段存在性**断言（例如发布按钮必须在 `<footer xpDialogFooter>` 之后、不得出现在 `<div xpDialogBody>` 内；市场区 `data-marketplace-section` 必须晚于 `XP.Xpert.VersionHistory`）。**零渲染成本、零依赖 mock**，是覆盖「布局回归」的廉价手段，但无法覆盖组件类逻辑。

**四个惯例**
1. 依赖替换优先「**整模块 mock**」（`jest.mock` 顶层、imports 之后）而非深层 spy；
2. 服务桩一律 `{ provide, useValue }` + `signal()`/`of()`/`BehaviorSubject`，**不引 HttpClientTestingModule**；
3. 断言用**结构等值**（`toEqual` 整个对象/DTO）而非逐字段，便于契约级回归；
4. 无 `beforeAll` 共享状态、无 `snapshot` 文件；`header/*` 的 2 个 TestBed spec 均显式 `TestBed.resetTestingModule()`（与 `test-setup.ts` 的 `destroyAfterEach: false` 配合）。

- **机制**：该 `jest.mock` **未带 `{ virtual: true }`**，Jest 注册 mock 时仍要真实解析模块路径——`jest-resolve/build/index.js:977` 的 `_getAbsolutePath()` 在模块未解析时走 `_getVirtualMockPath()` → `resolveModule()`（第 1002–1005 行），失败即抛 `Cannot find module '@milkdown/crepe' from '.../commands.component.spec.ts'`（同文件 863 行 `_ModuleNotFoundError`）。因此**在加载阶段整文件失败，用例体不执行**。
- **依赖侧的确认**：`@milkdown/crepe` 只在 `apps/cloud/package.json:24` 与 `pnpm-lock.yaml:648`（importer `apps/cloud`）里声明，**未安装到 `node_modules`**；仅 `apps/cloud/src/styles/milkdown.css` 这种本地样式文件存在。亦**无 manual mock 兜底**（`apps/cloud/__mocks__`、`apps/cloud/src/__mocks__`、仓库根 `__mocks__` 均不存在）。
- **本模块可自查的最小复现**：
  ```bash
  cd /root/xpert && timeout 600 corepack pnpm nx test cloud \
    --testPathPattern="features/xpert/studio/panel/commands/commands.component.spec.ts" --skip-nx-cache
  # 或（更快、不走 Nx）
  cd /root/xpert && node node_modules/jest/bin/jest.js --config apps/cloud/jest.config.ts \
    --runTestsByPath apps/cloud/src/app/features/xpert/studio/panel/commands/commands.component.spec.ts
  # 依赖是否落盘的一行判据
  ls /root/xpert/node_modules/@milkdown/crepe 2>/dev/null || echo "MISSING"
  ```
- **修复建议**（择一）：①`corepack pnpm install` 按 `.npmrc` 的 `node-linker=hoisted` 重新落盘；②**优先**——该 mock 疑为从 markdown 编辑器类 spec 复制的**遗留防御**（`studio/panel/commands/commands.component.ts` 已不引用 `@milkdown/crepe`，该目录内仅 spec 命中此字符串），可直接删除这 5 行；③保留 mock 则补 `{ virtual: true }`。
- **待复跑确认的口径差异**：`apps/cloud` 内**另有 17 个 spec** 使用同样未加 `virtual` 的 `jest.mock('@milkdown/crepe', ...)`（`@shared/files/markdown-editor`、knowledgebase wiki 系列、`workspace/prompt-workflows` 系列、`setting/organizations`、`@core/services/tag.service`、`@shared/tag/*`）。按同一机制这些 spec 也应加载失败，**与 PROJECT.md「仅 1 个 spec 失败」的记录不一致**（可能记录时依赖已安装）。复跑后若出现 18 个 spec 的 `Cannot find module '@milkdown/crepe'`，以复跑结果为准并回写 `test/known-failures.md` 的用例计数。

## 缺口与建议

| 优先级 | 缺口 | 为什么值得补 | 建议做法 |
|---|---|---|---|
| 高 | `domain/node/*`、`domain/connection/*`、`domain/xpert/*` handler（约 30 个文件） | 画布编辑语义的**唯一真相层**：创建/移动/删除/替换节点、连接增删、team 展开；改错即画布崩 | 纯函数式 handler（`execute` 入参 request + 内存 draft）**无需 TestBed**，按 `middleware-groups.spec.ts` 模式逐个补 3–5 例 |
| 高 | `domain/layout/layout.ts`、`domain/selection.service.ts` | 选中/重排是交互回归高发区，且是纯逻辑 | 信号桩 + `toEqual` 结构断言 |

**工程建议**
1. **跑前先 `corepack pnpm install`**，消除 `@milkdown/crepe` 类「声明了但没装」的假失败（当前工作区即此状态）。
2. 排查时**永远带 `--skip-nx-cache`**，并在输出里核对「Tests: N passed」的实际数量——`nx.json` 的 `passWithNoTests: true` 会让拼错的 `--testPathPattern` 静默「成功」。

## 结论

Studio 模块自带 **9 个 spec / 23 用例**，Jest 30 + `jest-preset-angular` + Nx 22 的测试链齐备、**无外部服务依赖**，项目级记录为 **✅ 可跑（apps/cloud 442 spec）**。覆盖面集中在「领域判定纯函数 + 草稿保存语义 + 3 处关键布局」，而**画布内核（`domain/` 44 文件）、34 类节点组件（`components/workflow/` 36 文件）、面板与巨型交互组件（`panel/` 56 文件）几乎零覆盖**——这是本模块最大的质量敞口。已知失败仅 1 处且根因是**依赖未安装**（`@milkdown/crepe`），跑前 `corepack pnpm install` 即可解除；本轮未能复跑（会话无 shell），复跑后请以实际输出回写 `test/known-failures.md`。
