## 决策明细 D1–D10

### D1 仅草稿保存（draft-only saves）
- **分类**：架构设计（ki 原记录分类为「数据一致性」，按本表口径归入架构设计）
- **动机（避坑）**：现象——编辑态与发布态若不隔离，画布上的半成品会直接成为运行对象；后果——线上对话/调用消费未完成编排，回滚只能靠再次编辑（该取舍的背景约束为 ki 明写：「发布后的版本是运行时对象（对话/调用按版本运行），编辑态与运行态必须隔离；半成品编辑不应污染已发布版本」）。
- **决策**：编辑先入草稿 `Xpert.draft`，1s 去抖 `POST /api/xpert/:id/draft`；只有发布（publish）把草稿固化为版本；`resume()` 可丢弃草稿回到已发布版本。
- **背景约束**：发布版本是运行时对象；前端唯一真相是内存草稿（无本地持久化）；`pristineDraft` + 哈希比对判定 `unsaved`。
- **被否决方案**：无——ki 记录原文为「无可追溯记录」，本次亦未在代码中找到其它保存策略的痕迹。
- **重新评估触发条件**：需要实时协同编辑，或出现「逐次编辑生成审计版本」的产品需求。
- **关联代码**：`XpertStudioApiService.saveDraft/resume/unsaved/pristineDraft`、`SaveDraftDebounceTime = 1`、`DraftSaveQueue.save`、header `handleCtrlS`。
- **证据来源**：ki 决策记录（明写，含 commit `9c210afd9`）；代码佐证见 [`xpert-api.service.ts`](file://apps/cloud/src/app/features/xpert/studio/domain/xpert-api.service.ts)、[`draft-save-queue.ts`](file://apps/cloud/src/app/@shared/xpert/assistant-settings/draft-save-queue.ts)。
章节来源：[仅草稿保存 draft-only saves.md](file://CodeWikiHub/xpert/memory/决策记录/Xpert%20Studio/仅草稿保存%20draft-only%20saves.md)（关键符号：`决策`、`被否决方案`、`证据来源`）、[xpert-api.service.ts](file://apps/cloud/src/app/features/xpert/studio/domain/xpert-api.service.ts)（关键符号：`saveDraft`、`resume`、`unsaved`、`pristineDraft`、`SaveDraftDebounceTime`）

### D2 [推测] 单 store + Memento 全量快照历史
- **分类**：性能取舍
- **动机（标「避坑」，[推测]）**：现象——多写端点/共享对象引用会让「撤销边界」与「未保存判定」难以对齐；后果——撤销后 `unsaved` 误判、保存与回滚互相覆盖。ki 将该动机记为 [推测]，此处保留标注。
- **决策**：所有编辑经单一 elf store（`createStore({ name: 'xpertStudio' })`），每次写 `structuredClone(state.draft)` 后整体回写；历史由 `elf-state-history`（`comparatorFn: negate(isEqual)` 深比较）保存全量快照。
- **背景约束**：需要可回溯的编辑历史；`calculateHash(JSON.stringify(...))` 是保存判定的唯一输入。
- **被否决方案**：无（ki 未记录，本次亦未找到被否决方案的证据）。
- **重新评估触发条件**：大图（数百节点）下撤销/拖动单次 > 100ms 时重估（ki 原文触发条件）。
- **关联代码**：`XpertStudioApiService.store`、`#stateHistory`、`#updateNode` 的 `structuredClone`、`undo/redo/gotoHistoryIndex`。
- **证据来源**：ki [推测] 条目（保留 `[推测]`）；代码实证：写路径形态与比较器见 [`xpert-api.service.ts`](file://apps/cloud/src/app/features/xpert/studio/domain/xpert-api.service.ts)。
章节来源：[结构暗示的决策集（推测）.md](file://CodeWikiHub/xpert/memory/决策记录/Xpert%20Studio/结构暗示的决策集（推测）.md)（关键符号：`[推测] 单 store + Memento 全量快照历史`）、[xpert-api.service.ts](file://apps/cloud/src/app/features/xpert/studio/domain/xpert-api.service.ts)（关键符号：`store`、`#stateHistory`、`gotoHistoryIndex`）

### D4 执行态走 SSE 事件流（非轮询）
- **分类**：技术选型
- **动机**：流式输出与逐节点执行状态要求「服务端一产生就到达前端」；轮询会产生延迟与无效请求（此动机为 [推测]，代码只体现结论）。
- **决策**：预览与单 Agent 调试都走 `fetch-event-source` 的 SSE（`POST /api/xpert/:id/chat`、`POST /api/xpert-agent/chat`），事件在 `processEvents` 内单点分发；前端不新增执行数据（**[推测]**：执行态零新增数据/纯投影——代码实证为「仅 signal 投影 + `clear()` 清空、刷新即丢」）。
- **背景约束**：流式回复需可中断且不得重复执行；服务端可能重启导致流中断。
- **被否决方案**：无（未找到轮询方案被评估或否决的任何记录）。
- **重新评估触发条件**：出现离线/弱网查看执行历史的需求（ki 原文触发条件）。
- **关联代码**：`injectFetchEventSource`、`RUNTIME_STREAM_INTERRUPTED_EVENT`、`processEvents`、`XpertExecutionService`。
- **证据来源**：ki [推测] 条目（保留 `[推测]`）；代码实证见 [`fetch-event-source.ts`](file://apps/cloud/src/app/@core/services/fetch-event-source.ts)、[`execution.component.ts（Agent 执行面板）`](file://apps/cloud/src/app/features/xpert/studio/panel/agent-execution/execution.component.ts)。

### D5 撤销重做双轨（状态历史 + 语义历史）
- **分类**：架构设计
- **动机（[推测]）**：现象——只用底层快照栈时，UI 只能提供「上一步/下一步」，无法按业务语义命名步骤与直接跳转；后果——用户无法定位「删掉那个节点之前」的状态，可回溯性差。动机为本次推断，标注 [推测]。
- **决策**：底层 `elf-state-history` 负责真实状态回滚（`jumpToPast/jumpToFuture`）；上层 `stateHistories`（`{ reason: EReloadReason; cursor; createdAt }`）负责语义步骤与菜单跳转；`#reload` 流以 `debounceUntilChanged(2000)` 合并高频同类原因。
- **背景约束**：历史必须能随初始化/放弃草稿重置（`initRole` 内 `clear()`）；工具栏需要 `historyHasPast/historyHasFuture` 门控。
- **被否决方案**：无（未找到仅用单轨历史的评审记录）。
- **重新评估触发条件**：出现「跨用户/跨会话共享编辑历史」需求，或语义条目与状态快照出现系统性错位。
- **关联代码**：`XpertStudioApiService.undo/redo/gotoHistoryIndex/clearHistory/stateHistories`、`toolbar.component.ts` 的 `histories`。
- **证据来源**：代码实证（[`xpert-api.service.ts`](file://apps/cloud/src/app/features/xpert/studio/domain/xpert-api.service.ts)、[`toolbar.component.ts`](file://apps/cloud/src/app/features/xpert/studio/toolbar/toolbar.component.ts)）；动机部分为 [推测]。
章节来源：[xpert-api.service.ts](file://apps/cloud/src/app/features/xpert/studio/domain/xpert-api.service.ts)（关键符号：`undo`、`redo`、`gotoHistoryIndex`、`stateHistories`、`TStateHistory`）、[toolbar.component.ts](file://apps/cloud/src/app/features/xpert/studio/toolbar/toolbar.component.ts)（关键符号：`historyHasPast`、`histories`、`onGoToHistory`）

### D6 节点类型静态 `@switch` 分发（唯一注册表是 JSON-Schema widget）
- **分类**：架构设计
- **动机（[推测]）**：现象——节点渲染若走动态注册表，需要运行时解析与错误兜底；静态 `@switch` 编译期即可发现缺失分支。后果（ki 明示）：新增节点类型需**五处同步**（领域类型 / Handler / 节点组件 / 配置面板 / 两处 switch），漏改即不渲染且无报错。
- **决策**：节点渲染走「一条 `@for` + 一个 `@switch(node.type)`」，工作流节点再按 `entity.type` 二次 `@switch`；**节点类型没有动态注册表**（**[推测]**，与代码一致）；模块内唯一的注册表式扩展点是 JSON-Schema widget（`provideJsonSchemaWidgets` / `JsonSchemaWidgetStrategyRegistry`）。
- **背景约束**：34 类节点编辑器数量多且形态各异；`@default` 分支输出 `Unimplement type` / `Not supported yet`。
- **被否决方案**：无（ki 未记录动态注册表被评估与否决）。
- **重新评估触发条件**：出现插件/第三方扩展新增节点类型的需求（ki 原文触发条件）。
- **关联代码**：`components/workflow/workflow.component.html`、`panel/workflow/workflow.component.html`、`panel/panel.component.html`、`studio.component.ts` providers 内的 `provideJsonSchemaWidgets()`。
- **证据来源**：代码实证见 [02-实现.md](file://.module-experts/前端专题/Agent%20编排%20Studio%20专家/implementation/02-实现.md)；「无动态注册表」为 ki [推测]，保留标注。
章节来源：[02-实现.md](file://.module-experts/前端专题/Agent%20编排%20Studio%20专家/implementation/02-实现.md)（关键符号：`@switch (type())`、`JsonSchemaWidgetStrategyRegistry`、`provideJsonSchemaWidgets`）、[studio.component.ts](file://apps/cloud/src/app/features/xpert/studio/studio.component.ts)（关键符号：`providers`、`provideJsonSchemaWidgets`）

### D7 画布复用＝组件级复用 + 组件级 providers

### D8 Copilot 走后端接口，前端不直连模型
- **分类**：安全合规
- **动机（[推测]）**：现象——若前端直连模型供应商，需要在浏览器侧持有渠道凭据并自行过滤可用模型；后果——凭据暴露且无法按 xpert 授权。动机为推断，标注 [推测]。
- **决策**：以 DI 覆盖方式提供 `XpertStudioCopilotServerService.getCopilotModels(type)`，把候选模型收敛到当前 xpert 的后端配置（`getXpertCopilotModels(xpertId, type)`）；助手上下文由 `XpertAssistantFacade.setStudioContext` 经请求上下文传给后端，助手只能通过 `navigate_to_studio` / `refresh_studio` 影响画布，不直接写 draft。
- **背景约束**：模型候选需随切换 xpert 即时变化；非 assistant-shell 环境必须仍可用画布。
- **被否决方案**：无（未找到前端直连模型的实现或评审痕迹）。

### D10 连线 ID 采用 `key + '/' + type` 字符串协议

- **动机（[推测]）**：现象——`@foblex/flow` 的 `fOutputId/fInputId` 是字符串，节点存在多种输出（agent/knowledge/toolset/xpert/workflow 与 `/edge`、`/fail` 分支）；后果——若不约定统一拼接规则，模板与逻辑层无法互认同一根连线。动机为推断，标注 [推测]。
