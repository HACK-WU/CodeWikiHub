## 断言与 mock 风格

- **配置**：`apps/cloud/jest.config.ts`（`displayName: 'cloud'`，`preset: ../../jest.preset.js`，`setupFilesAfterEnv: src/test-setup.ts`）；`moduleNameMapper` 把 `^@xpert-ai/contracts$` 直连 `packages/contracts/src/index.ts`（**仅精确路径**，无需先 build），`environments/environment` 系列统一映射到 `environment.jest.ts`。
- **`transformIgnorePatterns`**：由 `@xpert-ai/chatkit-types` 依赖闭包递归收集 + 静态白名单（`lodash-es`/`nanoid`/`marked`/`echarts`/`zrender`/`@angular/common/locales`）拼成。
- **主流手法**：
  - `HttpClientTestingModule` + `HttpTestingController.expectOne(url)` **断言真实路径**（本域最典型：`/api/auth/request-pass`、`/api/auth/refresh-token`，以及 spec 私有配置下的 `/api/auth/custom/refresh-token`），再 `flush(...)` 假响应。
  - `TestBed.overrideComponent(X, { set: { template: '' } })` 屏蔽模板依赖（login/consent 如此）。
  - 手工替身优先于库：`{ provide: Store, useValue: store }`、`{ provide: AuthService, useValue: authService }`、`{ provide: HttpClient, useValue: { get: jest.fn() } }`、`CookieService`/`TranslateService` 同理。
  - `jest.mock('../../@core', () => ({ getErrorMessage: … }))` 用工厂切断 barrel（onboarding 两个 spec 的共同手法）。
  - `jest.useFakeTimers()` + `jest.advanceTimersByTimeAsync(...)` 驱动登出 5s 超时与 onboarding 轮询/断连窗口。
  - `describe.each(['class','function'])` 对同一守卫的两种实现做参数化（dirty-check）。
- **断言主轴**：请求 URL/方法、`Authorization: Bearer …` 与 `Tenant-Id` 头、副作用是否发生（`store.clear` 调用次数、`store.token` 是否置空）、URL query 到错误文案的映射、守卫/组件决策返回值。

章节来源：[apps/cloud/jest.config.ts](file://apps/cloud/jest.config.ts)（关键符号：`moduleNameMapper`、`transformIgnorePatterns`）、[auth-strategy.service.spec.ts](file://apps/cloud/src/app/@core/auth/auth-strategy.service.spec.ts)（关键符号：`AuthStrategy.logout`）

## 实测结论与失败归因

**ki 归档结论（2026-10-15 基线 `c07bb83d`）**：本域 **14 spec = 13 PASS / 1 FAIL**，失败为**环境级**——`@xpert-ai/store` 未落盘。

| # | 类别 | 机制 | 候选 spec（按静态证据排序） | 置信度 |
|---|---|---|---|---|
| 1 | 环境级：`@xpert-ai/store` | 该包在 `apps/cloud/package.json` 声明为 `"@xpert-ai/store": "3.9.1"`（**非 `catalog:`**）；仓库内**仅 2 处 live 引用**：`app.service.ts` 与 `@core/services/organization-status.service.ts`（`extends ComponentStore`）。任一 spec 的 import 图触及这两者即在**收集阶段**失败 | `apps/cloud/src/app/@core/services/organization-status.service.spec.ts`（**直接** import 上述服务） | 高（若它计入 14 的口径）/ 待复跑确认 |
| 2 | 环境级（间接） | 同上，但经 `@core` barrel：`@core/index.ts → ./services/index → organization-status.service.ts` | `apps/cloud/src/app/@core/auth/auth-strategy.service.spec.ts`、`apps/cloud/src/app/@core/auth/signin-success/sign-in-success.component.spec.ts` | 中，待复跑确认 |
| 3 | 环境级（间接，已部分规避） | onboarding 两个 spec 对 `../../@core` 用了带工厂的 `jest.mock`，**不会**加载真实 barrel；若它们仍失败，则根因在 `@xpert-ai/headless-ui`（`ZardSelectComponent` 等真实渲染）闭包 | `apps/cloud/src/app/onboarding/plugins/setup-plugins.component.spec.ts`、`…/setup-plugin-catalog.component.spec.ts`、`apps/cloud/src/app/@core/guards/dirty-check.guard.spec.ts` | 低，待复跑确认 |

**复跑取真方法**：先 `corepack pnpm install`，再跑 §3 的第 2 条命令，收集输出里 `●` 开头的失败块（`FAIL/PASS` 计数 + spec 路径 + 首条信息），即可把上表逐条结清。注意本会话实测 `node_modules/@xpert-ai` **整个作用域目录不存在**，因此在装依赖之前，14 个 spec **全部**会失败——当前状态无法用于区分「1 个失败」的归档口径。

## 缺口

- **守卫矩阵几乎无自动化覆盖**：`authGuard`、`inviteGuard`、`onboardGuard`、两个 `NoAuthGuard`（含 `accept-invite` 例外）**零 spec**；唯一被测的是 `dirtyCheckGuard`。准入矩阵是纯人工核对点。
- **OIDC 回调路径无覆盖**：consent 只测到组件级（GET/POST 形态与参数），`/auth/consent` 的 `mcpOAuthEnabled` 门控、`XP_API_BASE_URL` 注入、`state/nonce` 全链路均无断言。
- **SSO 绑定页无 spec**：`SsoBindComponent`、`CurrentUserSsoConfirmComponent` 及其 4 个 `/api/auth/sso/bind/*` 端点无覆盖（仅 `register/login` spec 间接断言了 `/api/auth/sso/bind/challenge` 与 `…/register`）。
- **零 spec 的页面**：`accept-invite`（含 `invite.guard` 的邮箱+token 例外）、`forgot-password`、`reset-password`、`verify-email`、`logout`、`sso-bind`、`sso-confirm`、`register-result`、`onboarding/{welcome,tenant-details,unknown}`。
- **双令牌通道不一致无保护**：令牌只写 `Store`，`XpAuthTokenService.onTokenChange` 不反映登录态变化——这一「静默不一致」没有任何 spec 兜底。
- **跨域契约**：`/api/auth/*` 的字段级契约（如登录失败 `200 + null`）只在前端以固定 mock 断言，服务端变更不会让本域 spec 失败。

章节来源：[auth/login/login.component.spec.ts](file://apps/cloud/src/app/auth/login/login.component.spec.ts)（关键符号：`openProvider`）、[sso-bind.component.ts](file://apps/cloud/src/app/auth/sso-bind/sso-bind.component.ts)（关键符号：`SsoBindComponent.submit`）

## 可执行性结论

- **可执行性**：⚠️ 结构上具备（Jest 配置、setup 垫片、`moduleNameMapper` 均已就绪，用例完全离线化），但**当前工作区 `node_modules/@xpert-ai` 整个作用域缺失**，未安装前 14 个 spec 都会在收集阶段失败——这是环境问题而非测试问题。
- **基线口径**：ki 记录 `14 spec = 13 PASS / 1 FAIL`（`2026-10-15`，commit `c07bb83d`），失败归类为环境级 `@xpert-ai/store` 缺依赖；本会话无法复跑，故 §6 的候选清单标注为「静态证据 + 置信度」，**不是结论**。
- **推荐动作**：`corepack pnpm install` → 跑 §3 第 2 条全量 → 用实测 `●` 块替换 §6 第 1 列的行；随后补 `authGuard`/`inviteGuard`/`onboardGuard` 的最小判定单测，把准入矩阵从「人工核对」升级为回归项。
