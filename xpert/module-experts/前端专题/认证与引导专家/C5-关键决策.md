## 决策明细 D1–D11
### D1 策略表驱动认证内核
- **分类**：架构设计。
- **动机**：ki 原文——源自 Nebular auth 体系改造；认证需要「动作名 → 具体实现」可替换，避免每种方式都改页面。
- **决策**：认证动作全部经 `XpAuthService` 按 `strategyName` 分发到 `XpAuthStrategy` 子类；策略在 `XpAuthOptions.strategies` 表注册，由 `nbStrategiesFactory` 实例化（`injector.get(strategyClass)` + `setOptions`）。
- **背景约束**：ki 写的避坑项是「只写策略类不注册表 → 调用静默失败无编译提示」；实测该失败是**运行期同步抛 `TypeError`**（见 D2 约束），故「无编译期保护」成立、「静默」不成立。
- **被否决方案**：无（ki 未记录候选方案）。
- **重新评估触发条件**：ki 未记；本文追加——当非 XHR 语义的认证方式（授权码整页跳转）大量增加、双轨需要收敛时（联动 D3）。
- **关联代码**：`nbStrategiesFactory` / `nbOptionsFactory` / `XpAuthModule.forRoot` / `XpAuthService.getStrategy` / `defaultAuthOptions.strategies`。
- **证据来源**：ki 决策 1（明写）+ 代码实证。
章节来源：[策略表驱动与SSO双轨.md](file://CodeWikiHub/xpert/memory/决策记录/认证与引导/策略表驱动与SSO双轨.md)（关键符号：`决策 1`、`证据来源：auth.options.ts、auth.module.ts:46-52`）、[auth.module.ts（auth）](file://apps/cloud/src/app/auth/auth.module.ts)（关键符号：`nbStrategiesFactory`、`XpAuthModule.forRoot`）

### D2 策略参数化：页面只传 `strategyName`，不碰 HTTP
- **分类**：接口契约。
- **动机（避坑）**：同一套表单结构要能切换到不同登录方式；若页面直连 HTTP，换方式即改页面。
- **决策**：11 个公开方法全部形如 `(strategyName, data?)`（`authenticate/register/logout/requestPassword/resetPassword/refreshToken` + 5 个查询/广播方法）；页面从 `XP_AUTH_OPTIONS` 的 `forms.*.strategy` 取名字（当前全为 `'email'`），只处理「成功/失败 + 跳哪里」。
- **背景约束**：`XpAuthResult` 是唯一返回面（`isSuccess/getRedirect/getErrors/getMessages`）；未注册名字运行期抛错，改表时无类型保护。
- **被否决方案**：无（ki 未记录）。
- **重新评估触发条件**：出现「同一次提交需要横跨多策略」或页面需要读取策略内部状态的需求时。
- **关联代码**：`XpAuthService.authenticate/…/refreshToken`、`getDeepFromObject(this.options, 'forms.login.strategy')`、`XpAuthResult`。
- **证据来源**：代码实证；与 ki 决策 1 同源（策略表驱动的对外形态）。
章节来源：[auth.service.ts（auth）](file://apps/cloud/src/app/auth/services/auth.service.ts)（关键符号：`XpAuthService.getStrategy`、`processResultToken`）、[login.component.ts](file://apps/cloud/src/app/auth/login/login.component.ts)（关键符号：`this.strategy = this.getConfigValue('forms.login.strategy')`）

### D3 SSO/OIDC 不进策略表（双轨现状）
- **分类**：架构设计。
- **动机（避坑，[推测]）**：ki 原文——「SSO 不进策略表（当前仅 email），走独立路由 sso-bind/sso-confirm 与后端 identity 模块——双轨现状」。ki 将该条标为 [推测]，此处保留标注。
- **决策**：SSO/OIDC 由 4 个独立页面直连后端（`/api/auth/sso/*`、`{XP_API_BASE_URL}/oidc/interaction/:id/consent`），不实现 `XpAuthStrategy`；成功一律 `window.location.assign(result.location)` 交还后端。
- **背景约束**：错误文案与准入因此分散在 4 个页面（登录页只做 provider 发现与回跳 query 解析）；consent 路由还受 `environment.mcpOAuthEnabled` 门控（三份环境均为 `false`）。
- **被否决方案**：无（ki 与源码均未记录「把 SSO 做成策略」被评估与否决的痕迹；02-实现 只记录了两条路线的取舍描述，未标注为被否决）。
- **重新评估触发条件**：ki 原文——「SSO 方式增多需统一抽象时」。
- **关联代码**：`auth-routing.module.ts`（`sso-bind` / `sso-confirm` / `consent`）、`SsoBindComponent.loadChallenge/submit`、`CurrentUserSsoConfirmComponent.submit`、`OidcConsentComponent.submitDecision`。
- **证据来源**：ki 决策 2（[推测]，保留标注）+ 代码实证（四页均不经 `XpAuthService`）。
章节来源：[策略表驱动与SSO双轨.md](file://CodeWikiHub/xpert/memory/决策记录/认证与引导/策略表驱动与SSO双轨.md)（关键符号：`决策 2（[推测]）`、`触发条件：SSO 方式增多需统一抽象时`）、[auth-routing.module.ts](file://apps/cloud/src/app/auth/auth-routing.module.ts)（关键符号：`path: 'sso-bind'`、`path: 'sso-confirm'`、`environment.mcpOAuthEnabled`）

### D4 令牌强校验前置（`createToken` failWhenInvalidToken）
- **分类**：安全合规。
- **动机**：ki 原文——「坏令牌入存储会导致全站 401 循环」。
- **决策**：`XpAuthStrategy.createToken(value, failWhenInvalidToken)` 在 `requireValidToken` 为真且 `!token.isValid()` 时抛 `NbAuthIllegalTokenError`，由策略 `handleResponseError` 捕获并转成失败 `XpAuthResult`（错误 message 进 `errors`）。
- **背景约束**：源码注释明写「MUST be intercepted by strategies」；代价是策略必须自带 `requireValidToken` 配置；现役 email 策略不产 token 对象，故该保护在当前生产链路上**不生效**（联动 D5 双轨）。
- **被否决方案**：无（ki 未记录）。
- **重新评估触发条件**：D5 的令牌双轨收敛后，`isValid()` 的时间语义（`NbAuthJWTToken` 的 `exp`）重新成为判据时需复核。
- **关联代码**：`XpAuthStrategy.createToken`、`NbAuthIllegalTokenError`、`XpPasswordAuthStrategy.handleResponseError`、`NbAuthJWTToken.isValid`。
- **证据来源**：ki 决策 3（代码注释明写语义）+ 代码实证。
章节来源：[auth-strategy.ts](file://apps/cloud/src/app/auth/strategies/auth-strategy.ts)（关键符号：`XpAuthStrategy.createToken`、`NbAuthIllegalTokenError`）、[token.ts](file://apps/cloud/src/app/auth/services/token/token.ts)（关键符号：`NbAuthJWTToken.isValid`）

### D5 令牌真源落在 `Store`，注入与 401 刷新统一在 `TokenInterceptor`
- **分类**：架构设计。
- **动机（避坑）**：ki 数据流明写关键约束——「令牌强校验（非法即抛 `NbAuthIllegalTokenError`）；**改令牌结构/刷新语义 = 全站级影响**；公共页免登录是显式白名单」，且令牌的去向是「`@core/auth` 存储 → `http-context` 注入全站请求」。
- **决策**：`AuthStrategy.login/refreshToken` 写 `Store.token/refreshToken`（Akita persist）；`TokenInterceptor.addAuthenticationToken` 统一拼 `Authorization: Bearer`，401 走「单飞 + 等待队列」刷新（`refreshTokenInProgress` + `refreshTokenSubject`，策略侧 `refreshTokenReq` + `shareReplay(1)`），刷新自身 401 → `auth.logout()`。
- **背景约束**：auth 包自带的 `XpTokenLocalStorage`（key `auth_app_token`）在生产链路**无写入方**（`processResultToken` 因 `XpAuthResult` 不带 token 而不触发），故 `XpAuthService.isAuthenticated()` 恒假、`NoAuthGuard` 第二段判据只能放行不能拦截 —— [推测]（implementation/02-实现 已归档同一推断）。
- **被否决方案**：无（ki 未记录「以 auth 包 localStorage 为唯一真源」的评审；现状是双轨并存而非择一）。
- **重新评估触发条件**：任何令牌结构 / 刷新语义改动必须按全站回归（含对话 socket 重连）对待；双轨收敛（二选一、让守卫只读一个源）时应重估本决策。
- **关联代码**：`AuthStrategy.login/refreshToken`、`TokenInterceptor.intercept/addAuthenticationToken/ANONYMOUS_AUTH_PATHS`、`XpAuthTokenService.token$`、`Store.clear`。
- **证据来源**：ki 数据流记录（明写）+ 代码实证。
章节来源：[令牌与准入上下文.md](file://CodeWikiHub/xpert/memory/数据流/认证与引导/令牌与准入上下文.md)（关键符号：`令牌（XpAuthToken）… 去向 @core/auth 存储 → http-context 注入全站请求`、`关键约束`）、[token.interceptor.ts](file://apps/cloud/src/app/@core/interceptors/token.interceptor.ts)（关键符号：`ANONYMOUS_AUTH_PATHS`、`refreshTokenInProgress`）、[auth-strategy.service.ts](file://apps/cloud/src/app/@core/auth/auth-strategy.service.ts)（关键符号：`AuthStrategy.refreshToken`、`refreshTokenReq`）

### D6 守卫族矩阵化：准入 = 判据 + 不通过落点
- **分类**：架构设计。
- **动机（避坑）**：全站准入需要一处权威声明；「未登录 / 已登录 / 未初始化 / 有权限 / 有脏数据」五种状态的落点各不相同，若判据与落点不成对，就会出现「能进页面但接口 401」或白屏。
- **决策**：五入口并存——`authGuard`（同步判 `!!store.token`，失败**先 `await authStrategy.logout()` 清本地**再 `/auth/login?returnUrl=<原 URL>`）；auth 包 `NoAuthGuard`（两段判 + `accept-invite` 的 `email`+`token` 例外）；`onboardGuard`（`TenantService.getOnboard()`：有租户 → `/home/`、探测错 → `/onboarding/unknown`）；`inviteGuard`（`expectedPermissions` 命中 `hasPermission` 且 `selectedOrganization.invitesAllowed`，否则 `/`）；`dirtyCheckGuard` / `DirtyCheckGuard`（`canDeactivate` + 确认框）。
- **背景约束**：`inviteGuard` **全仓无任何路由引用**；`@core/auth` 版 `NoAuthGuard` 也未挂载（跳转目标 `/pages/dashboard` 已不存在）；`xpert/routes.ts` 另有同名不同物、按 `XpertAPIService.getChatApp(name)` 判定的 `authGuard`，检索/评审极易误伤。
- **被否决方案**：无（ki 与源码未记录候选方案）。
- **重新评估触发条件**：新增公共页/新守卫语义；或清理未挂载守卫（`inviteGuard`、`@core` 版 `NoAuthGuard`）时需逐路由重核。
- **关联代码**：`authGuard`、`NoAuthGuard.canActivate/canAccessInviteRoute`、`onboardGuard`、`inviteGuard`、`dirtyCheckGuard`、`features-routing.module.ts` 的挂载面。
- **证据来源**：ki 关联记录（免登录例外清单 + 「改守卫矩阵需逐路由核对」）+ 代码实证。
章节来源：[auth-准入边界-全站.md](file://CodeWikiHub/xpert/memory/关联关系/前端专题/auth-准入边界-全站.md)（关键符号：`authGuard 挂载于全站路由`、`改动风险`）、[auth.guard.ts](file://apps/cloud/src/app/@core/auth/auth.guard.ts)（关键符号：`authGuard`）、[invite.guard.ts](file://apps/cloud/src/app/@core/guards/invite.guard.ts)（关键符号：`inviteGuard`）

### D7 onboarding 三步不可跳步
- **分类**：架构设计。
- **动机（避坑）**：首启必须先拿到「租户 + 默认组织 + 超管」并完成一次自动登录，后续页面才有组织作用域与令牌；跳步会让插件步无凭据、主应用无作用域。
- **决策**：`/onboarding/`（welcome）与 `tenant` 挂 `onboardGuard`、`plugins` 挂 `authGuard`；模板用 `<z-stepper [linear]="true">`；`onboard()` 成功 → `afterOnboard()`（`authStrategy.login()` + `setOrganizationScope`）→ `stepper.next()`；自动登录失败 → `/auth/login?returnUrl=/onboarding/plugins`；安装完成整页 `location.assign('/')` 刷新进程级插件。
- **背景约束**：步骤态不持久化（组件 signal），刷新回守卫判定；`attention` 阶段直接 `return`，无重试按钮文案兜底；`tenant-details` 的 `onStepChange(selectedIndex === 2)` 用路由跳转代替「完成屏」，步骤语义与 URL 不一一对应。
- **被否决方案**：无（未找到「全局步骤机 / 服务端步骤字段」方案的评审痕迹）。
- **重新评估触发条件**：出现「刷新可恢复步骤」「可回退重跑安装」的需求，或 os 安装阶段需要在页面内重试时。
- **关联代码**：`onboarding-routing.module.ts`、`TenantDetailsComponent.onboard/afterOnboard/onStepChange/skipAiModelSetup`、`SetupPluginsComponent.load/monitor/enterOrganization`、`tenant-details.component.html` 的 `z-stepper [linear]`。

### D8 公共页无守卫、准入交后端 + 白名单显式枚举

- **决策**：路由侧白名单——`/sign-in/success`、`/x-chatkit/**`、`/x/**`、`/plugins/marketplace` 顶层无守卫，`/auth/**` 仅 `request-password`/`reset-password`/`accept-invite`/`verify` 挂 `NoAuthGuard`；请求侧白名单——`ANONYMOUS_AUTH_PATHS` 6 条（`/api/auth/login`、`/api/auth/sso/providers`、`/api/auth/sso/bind/{challenge,complete,register}`、`/api/tenant/onboard`）不注入 `Authorization`、不触发刷新。

### D10 登出只清本地、不通知后端
- **分类**：其他（会话生命周期）。

### D11 端点口径以生效面为准（`/api/auth/*`，`/api/auth/custom/*` 不存在）

- **准入轴（D6 + D7 + D8）**：守卫矩阵、引导不可跳步、公共页白名单三者互为条件——改任一项都要同步核对「路由侧白名单 + 请求侧 `ANONYMOUS_AUTH_PATHS`」两处（D8 约束）。
