## 运行方式与实测命令

```bash
# 1) 单文件（最快，绕开 Nx 项目图）——推荐
cd /root/xpert && node node_modules/jest/bin/jest.js \
  --config apps/cloud/jest.config.ts \
  --runTestsByPath apps/cloud/src/app/features/chat/clawxpert/clawxpert.facade.spec.ts

# 2) 三目录全量（本专家口径）
cd /root/xpert && node node_modules/jest/bin/jest.js --config apps/cloud/jest.config.ts \
  --runTestsByPath \
  $(find apps/cloud/src/app/features/chat apps/cloud/src/app/xpert apps/cloud/src/app/features/assistant -name '*.spec.ts')

# 3) Nx 方式（含项目图与缓存；改代码后排查请加 --skip-nx-cache）
cd /root/xpert && corepack pnpm nx test cloud \
  --testPathPattern="features/chat" --skip-nx-cache 2>&1 | tail -60

# 4) 全项目回归
cd /root/xpert && corepack pnpm nx test cloud 2>&1 | tail -60
```

- 必须先按工作区口径（`packages/*` + `catalog:`）安装依赖：`corepack pnpm install`；本仓库 `packageManager: pnpm@10.24.0`，`.npmrc` 固定 `node-linker=hoisted`，裸 `pnpm` 会重建不兼容的 `node_modules`。
- 若环境注入了 `NODE_OPTIONS`/`BASH_ENV`（IDE shim），用 `env -u NODE_OPTIONS -u BASH_ENV` 前缀剥离后再跑。
- `@nx/jest:jest` 默认 `passWithNoTests: true`：**路径写错会「0 用例、退出码 0」**，务必核对输出里的用例数。

章节来源：[project.json](file://apps/cloud/project.json)（关键符号：`targets.test` → `@nx/jest:jest`、`jestConfig`、`webWorkerTsConfig`）、[PROJECT.md](file://.module-experts/PROJECT.md)（关键符号：§5「测试口径与基线」）

## 断言与 mock 风格

- **框架与配置**：Jest 30 + `jest-preset-angular`（`apps/cloud/jest.config.ts`，`displayName: 'cloud'`）；`setupFilesAfterEach: src/test-setup.ts` 提供 `setupZoneTestEnv({ teardown: { destroyAfterEach: false } })` 以及 `structuredClone`、`ReadableStream/WritableStream/TransformStream`、`ResizeObserver` 的 jsdom 补丁。
- **`moduleNameMapper` 关键两条**：`^@xpert-ai/contracts$` → `packages/contracts/src/index.ts`（**仅精确路径**，直连源码、无需先 build）；`environments/environment` 系列 → `src/environments/environment.jest.ts`（避免真实环境注入）。
- **`transformIgnorePatterns`**：放行 `lodash-es`、`nanoid`、`marked`、`echarts`、`zrender`、`@angular/common/locales` 及 `@xpert-ai/chatkit-types` 的依赖闭包（脚本按 package.json 递归收集）。
- **主流 mock 手法**（在巨型 spec 中尤其明显）：`jest.mock('../../../@core', () => ({ … }))` 整个 barrel 替换；`jest.mock('@xpert-ai/chatkit-angular', …)` 用 `jest.requireActual('@angular/core')` 现造壳组件；`jest.requireMock(...)` 回取 mock 以改行为；`HttpTestingController.expectOne((r) => r.url === '…')` 断言真实请求路径并 `flush` 假数据。
- **断言主轴**：HTTP 路径与查询参数（如 `/api/xpert/xpert-1/frequent-questions`）、命令返回码（`unsupported`/`stale_context`/`forbidden`）、信号状态机（`viewState`、`loading`）、以及"拒绝"类负向断言（超大文件不 fetch、跨助手上下文不执行命令）。

章节来源：[apps/cloud/jest.config.ts](file://apps/cloud/jest.config.ts)（关键符号：`moduleNameMapper`、`transformIgnorePatterns`）、[clawxpert-conversation-detail.component.spec.ts](file://apps/cloud/src/app/features/chat/clawxpert/clawxpert-conversation-detail.component.spec.ts)（关键符号：`injectHostedAssistantChatkitControl`（mock 化））

## 实测结论与失败清单

**ki 基线记录（2026-10-15 实测，commit `c07bb83d`）**：本域 **63 spec = 52 PASS / 10 FAIL**（52+10=62，与 63 差 1，疑有 1 个 spec 被 skip/pending 或计数口径差异）；失败**分四类**：**4 环境级 + 1 contracts 产物 + 5 真实断言**。下表为按源码与已知 mock 缺口的**逐条归因**（明确标注置信度）。

| # | 类别 | 候选 spec | 归因 | 置信度 |
|---|---|---|---|---|
| 1 | 环境级（依赖缺失） | `features/chat/clawxpert/clawxpert-conversation-detail.component.spec.ts` | 该 spec 顶层 `jest.mock('@xpert-ai/chatkit-angular', …)` **未传 `{virtual:true}`**，mock 注册仍需真实解析模块路径；`@xpert-ai/chatkit-angular`（`catalog: 0.15.0`）未落盘时套件**加载阶段即失败**，99 个用例全废。与 Studio 域 `@milkdown/crepe` 属同类根因 | 高（静态），**待复跑确认** |
| 2 | 环境级（依赖缺失） | `features/assistant/assistant-chatkit.runtime.spec.ts` | 顶层 `import { createChatKit } from '@xpert-ai/chatkit-angular'`（真实导入） | 中高，**待复跑确认** |
| 3 | 环境级（依赖缺失） | `features/assistant/assistant-composer-client-command.spec.ts` | 同上：`import { createChatKit }` | 中高，**待复跑确认** |
| 4 | 环境级（浏览器/重依赖） | `features/chat/clawxpert/file-change-diff.component.spec.ts`（或 `xpert/canvas/file-preview/file-preview-content.component.spec.ts`） | 二者都依赖重型编辑器/预览依赖（`ngx-monaco-editor`、`monaco-editor`、pdfjs/xlsx 链条），mock 未加 `virtual`；jsdom 下常在校验/渲染阶段炸 | 中，**待复跑确认** |
| 5 | contracts 产物 | 具体 spec **未能静态定位** | `jest.config.ts` 只把**精确路径** `^@xpert-ai/contracts$` 映到源码；任何经子路径/别名的导入会回落到构建产物，`packages/contracts` 未构建时直接 `Cannot find module`。本域三目录内检索 `from '@xpert-ai/contracts/`（子路径）**无命中**，故更可能是"产物过期导致断言/导出缺项"而非子路径导入 | 低，**待复跑确认** |
| 6-10 | 真实断言（5 个） | 候选池（按漂移敏感度排序）：`features/chat/routes.spec.ts`（路由表 22 例，`x/welcome`/`x/common`/Project 段 matcher 均属新近收敛点）、`features/chat/xpert-workbench/xpert-workbench.facade.spec.ts`（Project 采纳/访问 22 例）、`features/chat/clawxpert/clawxpert.facade.spec.ts`（52 例，全量 mock `@core` barrel，导出面漂移即炸）、`xpert/chatkit/public-chatkit.component.spec.ts`（企业 H5/SSO 13 例）、`features/assistant/workbench-navigation-open-client-command.spec.ts`（15 例，target 枚举扩容敏感） | 基线 commit 漂移（`c07bb83d` → `80f5676fd`）导致断言与实现不一致 | 推测；**逐条待复跑确认** |

## 缺口

- **零 spec 的高风险面**：`features/chat` 根目录（socket 客户端 `ChatWebsocketService`、`ChatHomeService`）、`@core/services/chat.service.socket.ts`（ACK 重试 2s、401 刷新重连）、旧 chat 页面（`features/chat/xpert`、`xpert/conversation`、`xpert/chat-input`）均无测试——**实时通道的可靠性语义完全无回归保护**。
- **公共页无守卫的后果**无 spec 覆盖（`/x-chatkit/h5/*` 的 `canActivate` 缺失只被 `chatkit/routes.spec.ts` 断言"不存在"）。
- **跨域契约**：`/api/ai/*` 的字段级契约（threads/messages/search 的响应形状）只在少数 spec 里以 `flush({...})` 假数据固定，后端契约变更不会让前端 spec 失败。
- **i18n**：spec 里普遍用 `TranslateModule.forRoot()` + 默认文案，语言包缺失/键改名不会被捕获。

章节来源：[xpert/chatkit/routes.spec.ts](file://apps/cloud/src/app/xpert/chatkit/routes.spec.ts)（关键符号：`routes`、`authGuard` 缺席断言）、[apps/cloud/jest.config.ts](file://apps/cloud/jest.config.ts)（关键符号：`setupFilesAfterEach`）

## 可执行性结论

- **可执行性**：✅ 具备（Jest 配置、setup 垫片、moduleNameMapper 均已就绪；测试全部离线化）。前提是**依赖已安装**——当前工作区 `node_modules` **缺失**（本会话仅只读检索，未能核实落盘状态），未安装时任何 spec 都会在收集阶段失败，这不是测试本身的问题。
- **基线口径**：ki 记录 `63 spec = 52 PASS / 10 FAIL`（commit `c07bb83d`）；本仓库现为 `80f5676fd`，spec 数已增长到 **66**，**失败清单需复跑重新标定**；上表第 6–10 行的 5 个"真实断言"是**候选池而非结论**。
- **推荐动作**：`corepack pnpm install` → 三目录全量单跑 → 把 §「实测结论与失败清单」的 10 行逐条替换为实测 `●` 块；随后把环境级 3–4 项按 Studio 先例修掉（`jest.mock(..., {virtual:true})` 或补依赖），把 contracts 项用 `nx build contracts` 前置消除。
