## 会话收发链

### 实时通道（socket.io 实现）

`ChatWebsocketServer`（`@core`，`providedIn: 'root'`）：`connect()` 仅在 `!socket || disconnected || !connected` 时建连，`io(${getWebSocketUrl(environment.API_BASE_URL)}/chat, { auth: cb => cb({ token: store.token }) })`；`connect` → `setStatus(true)`，`disconnect` → `setStatus(false)`，`exception` 里 `data.status === 401 && socketId === socket.id` 才 `setStatus(false)` 并（在 `refreshTokening()` 为假时）经 `AuthStrategy.refreshToken()` 重连。`message(data)` 发送前拼上 `organizationId`，并挂 2s 重发定时器；收到 `ChatGatewayEvent.ACK` 即 `clearRetryMessage()`，否则进入 `#response`。`onMessage()` 暴露该 `Subject`，调用方自行 `takeUntilDestroyed`。**实测消费方只有 `features/chat/chat.service.socket.ts` 的 `ChatWebsocketService`，且它本身无其他引用**——这条链当前是保留实现而非活跃路径。

章节来源：[chat.service.socket.ts](file://apps/cloud/src/app/@core/services/chat.service.socket.ts)（关键符号：`ChatWebsocketServer.connect`、`setStatus`、`message`、`resetRetryMessage`、`refreshToken`）、[chat.service.socket.ts](file://apps/cloud/src/app/features/chat/chat.service.socket.ts)（关键符号：`ChatWebsocketService.chatListener`、`answerning`、`cancelMessage`）

### HTTP 控制面与流

活跃链是「一次 POST 拿一条 SSE 流」：`@core` 的 `ChatService.chat(request, options)` 调 `injectFetchEventSource(baseUrl + API_CHAT, JSON.stringify({ request, options }))`（`API_CHAT = API_PREFIX + '/chat'`），另有 `speechToText`（FormData + `file/stt`）与 `synthesize`（GET + query）。在 `src/app/xpert/chat.service.ts` 里该类以别名 `ChatService as ChatServerService` 注入（避免与同文件抽象 `ChatService` 重名）。发送链 `sendMessage()`：本地先 `appendMessage({ role: 'user', ... })`（含 `references` / `attachments` / `thirdPartyMessage`），再构造 `TChatRequest{ action: 'send', clientMessageId, input: {...parametersValue, ...createReferenceHumanInput} }` 交给 `executeChatRequest`；若 `answering()` 为真则转 `enqueueFollowUp`（`PendingFollowUp.mode: 'queue' | 'steer'`）。`chatRequest()` 是唯一被平台/公共页覆写的分叉点（`ChatPlatformService` 无覆写走 `ChatServerService.chat`；`ChatAppService.chatRequest` 改走 `xpertService.chatApp`）。控制面读：`fetchConversation(id)`（`relations: [...]` 含 executions/feedback/task）与 `getFeedbacks(id)`（`feedbackService.getMyAll({ where: { conversationId } })` 归约成 `Record<messageId, feedback>`）；`#conversation = derivedAsync(...)` 把二者 combine 后跑 `filterLatestMessages` 并补 `shortTitle`。`executeChatRequest` 侧的流解析：忽略 `msg.data.startsWith(':')` 的心跳，`JSON.parse` 后 `ChatMessageTypeEnum.MESSAGE` 按 `typeof event.data === 'string'` 分流到 `appendStreamMessage`（追加文本）或 `appendMessageComponent`（结构化块），`ChatMessageTypeEnum.EVENT` 的 `ON_CONVERSATION_START/END` 走 `updateConversation(omit(event.data, 'messages'))`。

章节来源：[chat.service.ts](file://apps/cloud/src/app/@core/services/chat.service.ts)（关键符号：`ChatService.chat`、`speechToText`、`synthesize`）、[chat.service.ts](file://apps/cloud/src/app/xpert/chat.service.ts)（关键符号：`ChatService.sendMessage`、`executeChatRequest`、`chatRequest`、`#conversation`、`getFeedbacks`）、[chat-app.service.ts](file://apps/cloud/src/app/xpert/chat-app.service.ts)（关键符号：`ChatAppService.chatRequest`、`fetchConversation`、`isPublic`）

## 消息渲染

**选择规则**：AI 消息按「步骤类型」分流——文本/推理/执行树走 `ChatAiMessageComponent`（内含 `ChatThoughtComponent` 与执行组件），结构化块（`content[].type === 'component'`）走 `ChatComponentMessageComponent`，Computer 类块可升级到右侧 `ChatCanvasComponent`。`ChatComponentMessageComponent.category` 默认 `'Tool'`（`data.category || 'Tool'`），`openComponentMessage()` 只在 `Computer` 时 `homeService.canvasOpened.set({ opened: true, type: 'Computer', componentId: message()?.id })`，`Tool` 分支当前只 `console.log`。`ChatCanvasComponent` 从 `canvasOpened` 派生 `opened` / `canvasType` / `componentId` 并分发到 Computer / Dashboard / FileViewer。

**数据契约**：`TCopilotChatMessage = IChatMessage & { error?, expanded?, executions?, references? }`；块级为 `TMessageContentComplex`（`TMessageContentReasoning` 为推理文本）；`TMessageComponent` 携带 `category` / `tasks` / `step`（`TMessageComponentStep` 有 `created_date` / `end_date`，组件据此算 `duration`）。执行树纯函数在 `ai-message/agent-run-tree.ts`（`buildAgentRunRenderTree`、`getAgentNodeUnits`、`getAgentRunCounts`、`getAgentRunDuration`、`normalizeRunStatus`、`isRunningRunStatus`、`isFailedRunStatus`）。

**流式增量**：文本走 `appendStreamMessage(content)`，即对最后一条消息 `content = (content ?? '') + content`；Markdown 渲染侧用 `splitStreamingMarkdown(text)` 把文本切成 `frozenBlocks` / `frozenText` / `streaming`——以「行首围栏」为单位冻结已结束块，`getFencedCodeRanges` 保证**不切开代码围栏内部**，只让尾部仍在增长的部分重渲染。去重合并是正确性关键：`filterLatestMessages` 按 `parentId` 建链，每层只保留 `createdAt` 最新（同刻取数组内更靠后者）的孩子，并保持原顺序，被消费方（`ChatService.#conversation`）与 Studio 预览共用。

章节来源：[component-message.component.ts](file://apps/cloud/src/app/xpert/component-message/component-message.component.ts)（关键符号：`ChatComponentMessageComponent.category`、`data`、`openInCanvas`）、[canvas.component.ts](file://apps/cloud/src/app/xpert/canvas/canvas.component.ts)（关键符号：`ChatCanvasComponent.canvasType`、`opened`）、[ai-message.component.ts](file://apps/cloud/src/app/xpert/ai-message/ai-message.component.ts)（关键符号：`ChatAiMessageComponent.message`、`showExecution`、`busy`）、[streaming-markdown.ts](file://apps/cloud/src/app/xpert/ai-message/content/streaming-markdown.ts)（关键符号：`splitStreamingMarkdown`、`getFencedCodeRanges`）、[filter-latest-messages.ts](file://apps/cloud/src/app/@shared/chat/filter-latest-messages.ts)（关键符号：`filterLatestMessages`）、[agent-run-tree.ts](file://apps/cloud/src/app/xpert/ai-message/agent-run-tree.ts)（关键符号：`buildAgentRunRenderTree`、`getAgentRunCounts`）

## 消息反馈

反馈是「按 messageId 索引的一张表 + 两个动作」：`ChatMessageFeedbackService extends OrganizationBaseCrudService<IChatMessageFeedback>`，基址 `API_PREFIX + '/chat-message-feedback'`，仅覆写 `getMyAll` 指向 `/my`。`ChatService.feedbacks` 在读会话时一次性预取并归约成 `Record<messageId, IChatMessageFeedback>`；`ChatAiMessageComponent` 用 `getFeedback(id)` 读、`feedback(message, rating)` 写（`messageFeedbackService.create({ messageId, conversationId, ... })`，成功后 `feedbacks.update(...)` 并 toast）、`cancelFeedback(message, id)` 撤（`delete(id)` 后把该键置 `null`）。展示门控由 `feedbackReady` 决定：只有状态进入终态集合（`XpertAgentExecutionStatusEnum.SUCCESS` 等，`endedStatuses`）才允许评价——避免流式过程中误评。同一服务被 Studio 执行面板复用，属跨域共享契约。

## 群组会话与任务

**群组**：路由层用 `redirectLegacyGroup`（`CanActivateFn`）把 `/chat/groups[/:groupId]` 兼容重定向到「群组会话路由」——有 id 直接取 `groups.conversationRoute(id)`，无 id 取 `groups.list()` 中第一个未归档项，异常回落 `/chat/clawxpert`。群组视图作用域由 `createGroupWorkbenchScope` 解析：以 `[identity, groupId, assistantId]` 为 key，经 `GroupWorkbenchApiService.getContext(groupId)` 拿 `XpertViewRuntimeScopeInput`，并校验返回的 `assistantId` 与 `conversationId` 一致（注释：A group route must never render a personal View while its shared runtime is resolving.）。门面侧群组只暴露 `group?: Signal<{id} | null>`，其存在会改变宿主行为：`chatkitGroup()` 传给 ChatKit、会话 secret 改从 `POST /api/ai/v1/chatkit/sessions` 带 `scope: { kind: 'conversation', conversationId }` 换取，且 `messagePresentation.mode` 强制为 `'bubbles'`。
**任务**：`ChatTasksComponent` 承载 `/chat/tasks[/:id]` 与内嵌两种形态（`embedded` / `xpertId` input）。视图态是「四个集合 + 两条投影」：`currentTasks` / `scheduledTasks` / `pausedTasks` / `archivedTasks`（来自 `XpertTaskService`，`refresh$` 经 `debounceTime(5000)` 抑制抖动），以及 `executionRecords = buildTaskExecutionRecords(tasks)`、`#taskDetail = myRxResource(...)` 拉任务历史。动作分三类：生命周期（`pauseTask` / `scheduleTask` / `archiveTask` / `unarchiveTask` / `deleteTask`）、执行（`runTask`、`openHistoryConversation`、`openExecutionRecord`）、批量（`enterBatchManagement` / `toggleTaskSelection` / `toggleSelectAllVisibleTasks` / `deleteSelectedTasks`）。工作台内另有 `clawxpert-scheduled-tasks` 摘要与门面的 `taskSummary` / `scheduledTaskSummary` / `taskRefreshTick`。

## ChatKit 宿主

**装配**：`injectAssistantChatkitRuntime({ assistantCode, ... })` = 绑定运行时（`injectAssistantBindingRuntimeState`）+ 宿主控制（`injectHostedAssistantChatkitControl`）。绑定运行时把 `assistantBindingService.getEffective(code)` 映射成 `{ config, loading, hasSource, isConfigured, status, refresh }`，`status` 是六态状态机：`loading` / `error`（请求失败或 frame URL 缺失）/ `missing`（无 sourceScope 或配置不完整）/ `disabled`（`config.enabled === false`）/ `ready`。
**iframe 生命周期**：`runtimeKey` 由 `identity:assistantId:groupId:delegatedConversationId:requesterXpertId:frameUrl:apiUrl:token:organizationId` 拼成，`effect` 内比较 key 与 `securityScope` 决定 `createChatKit(options)`（新会话，`sessionKey` 为不透明的 `hosted-session-${revision}`）还是 `currentControl.setOptions(options)`（原地刷新，用于发布变更 `XpertPublicationService.changes$`）；`loading()` 为真时**只在同一认证域内**保留 iframe，否则清空 control。`initialThread` 用 `untracked` 读取，避免切换会话重建全部选项。会话 secret 优先 `HttpClient` POST `/api/ai/v1/chatkit/sessions`（保持平台登录态），无 `HttpClient` 时回落 `store.token`；工具产物预览 `toolOutputAttachments.onRequestPreview` 会校验 artifactId/versionId/sha256 一致后才返回签名链接。

## 热点路径

1. **消息列表的每次更新都是「整数组替换」**：`appendStreamMessage` / `updateLatestMessage` / `appendMessageStep` 均 `messages[messages.length - 1] = {...}` 后 `return [...messages]`，流式长回复下每帧新建数组并触发订阅者重算。
2. **`filterLatestMessages` 每次读会话都全量跑**：对全部消息建三张 Map（`byId` / `indexById` / `childrenByParent`）再按链挑最新孩子，会话越长成本越高，但在读路径执行（非渲染帧）。
3. **`ChatWebsocketService` 的状态更新同样整表重建**，且 `updateMessageStep` 里 `reverse()` → `findIndex` → `reverse()` 就地改数组再复制，长会话下是明显的 O(n) 抖动点。
4. **`ClawXpertConversationDetailComponent` 是 88 KB 单文件**，构造期注册 6 类命令 + 安装对话地图链接 + 多个 `effect`（布局恢复、作用域 host key 对齐、生成产物追踪），任一依赖 signal 变化都会重跑较大范围逻辑。
5. **文件审查的并发批大小是硬编码 4**（`for (let offset = 0; offset < targets.length; offset += 4)`），`conversation` 范围下先整表 `listChanges` 再逐个 `loadReport`，大变更集时请求数线性增长。
6. **任务页 5s 去抖刷新**：`refresh$ = BehaviorSubject → debounceTime(5000)`，与 `taskRefreshTick` 配合，属「按需 + 时间窗」抑制。
7. **宿主 `effect` 的选项重建**：`injectHostedAssistantChatkitControl` 的 `effect` 每次都会重新构造完整 `options` 对象（含 `composer` / `header` / `history` 默认值），只在 `runtimeKey` 变化时才真正重建 iframe，其余走 `setOptions`。
8. **`XpertPublicationService.changes$` → `publicationRevision`**：发布事件经 `filter(organizationId && assistantId)` + `scan` 计数驱动「原地刷新已发布元数据」，避免重建会话。

## 设计维度分析

**维度一：宿主多样性 vs 骨架单一性**——本域用「契约类型 + InjectionToken」把宿主差异一次性收敛：`ClawXpertConversationDetailComponent` 只认 `WorkbenchChatFacade`，三种路由形态（`clawxpert/c/*`、`clawxpert/assistant/*`、`x/:slug[/p/:projectId]/c/*`）各自提供一个实现（含 `XpertWorkbenchFacade` 的项目双阶段字段），因此骨架代码零分支。代价是契约面偏宽（24 个字段 + 6 个方法，其中 7 个可选），一旦可选方法继续增长，就该按「会话运行时 / 项目作用域 / 工作台布局」拆成子契约。优点是**可替换性极强**：新增对话形态只需实现门面并给 `providers` 加一行。

**维度二：能力边界前置 vs 前端兜底**——安全与准入被刻意推到「装配前 + iframe 后」两端：前端只做静态判定（frame URL 白名单 `sanitizeAssistantFrameUrl`、绑定完整性 `hasCompleteAssistantBinding`、附件 50 MiB 上限、`runtimeKey` 不外泄），真正的授权判定交给服务端（ChatKit 会话 secret、iframe 命令回服务器重解析 manifest、`workspace.connector.connect` 由宿主承担授权且凭据不过桥）。这与「公共页 `/x/*`、`/x-chatkit/*` 无路由守卫」是同一套取向：**路由层不设卡，准入由后端兜底**。风险点在于前端判定的失败模式偏「静默」（`missing` / `disabled` 状态只体现在 `status` 上），排查时必须先看 `status` 再怀疑 iframe。

## 结论

- **收发链现状必须按源码记**：活跃路径是「HTTP 控制面（`ChatConversationService` / `ChatMessageFeedbackService`）+ 单流 SSE（`ChatServerService.chat` → `fetchEventSource`，`POST /api/chat`）」；socket.io（`ChatWebsocketServer` + `ChatWebsocketService`）当前是**无消费方的保留实现**（含 401 刷新与 2s 重发语义）。ki 归档口径「socket.io 为唯一实时主通道」与实测不符，改动这条链前先复核。
- **渲染链是一条去重 + 分流管线**：`filterLatestMessages` 定内容 → `ai-message` / `component-message` / `canvas` / `thought` 按类型分流 → 流式增量靠「尾消息追加 + `splitStreamingMarkdown` 冻结已完成块」控制重渲染范围。
- **工作台是「门面 + 子面板」的教科书式组合**：绑定、偏好、触发器、文件审查各自独立组件与独立乐观状态，全部经 `ClawXpertFacade` 读写，触发器用草稿副本 + `dirty` 判定，文件审查用请求序号作废过期批次。
- **ChatKit 宿主承担了本域最重的安全约束**：六态状态机 + `runtimeKey`/`securityScope` 双判 + 会话 secret 换取 + manifest 重解析，6 类 client-command 全部走白名单桥。
- **路由收敛已完成**：入口 `/chat` 经 `redirectToDefaultChatEntry()` 收敛到 `/chat/clawxpert[/c]`，旧 `x/*` 入口全部重定向，`clawxpert` 子树由 `canActivateChild` + `featureGate(..., ['/explore'])` 兜底，壳层还有第二层 `/explore` 回落。
- **优先治理项**：把 `clawxpert-conversation-detail.component.ts`（88 KB）按「ChatKit 装配 / 工作区标签 / 命令注册 / 产物追踪」拆分；为消息数组更新引入不可变增量路径；清理孤立 socket 通道与 `console.log` 残留；把时间常量与并发度集中成具名常量。
