## 门面契约的设计与成员语义

`WorkbenchChatFacade` 是**结构性类型**（`type`，非 `interface`），31 个成员分六组；`WorkbenchChatViewState` 与 `WorkbenchChatDefinition` 是它的两个配套类型。

| 组 | 成员（必需 / 可选） | 语义要点 |
| --- | --- | --- |
| 定义与身份 | `definition`（必需）；`currentXpert?`、`assistantTitle?`、`assistantAvatar?` | `definition.titleKey/defaultTitle` 是骨架的标题兜底；`identity` 是 ChatKit 的挂载身份，**非 `ready` 时必须为 null**，群组用 `chat-group:<id>`、私聊用 `chat-xpert-workbench:<xpertId>` |
| 布局与视图 | `initialLayout`、`defaultViewKey` | 来自 `xpert.options.workbench.{initialLayout,defaultViewKey}`；`initialLayout` 取 `XpertWorkbenchInitialLayoutEnum`（`two-columns` / `overlay-dialog` / `chatkit-maximized` / `workbench-maximized`） |
| 会话绑定 | `threadId`（必需）；`group?` | `threadId` 由 URL 派生；`group` 存在时骨架不加载私有 thread；契约注释明示群组按 conversation id 绑定 |
| ChatKit 宿主面 | `chatkitFrameUrl`（必需）；`chatkitMountProjectId?`、`chatkitProjectSelection?` | `chatkitFrameUrl` 为 `null` 时视图态直接判 `error`；`chatkitMountProjectId` 只用于**初始挂载**，`chatkitProjectSelection` 表达草稿意图 |
| Project 面 | `projectId?`、`projectAccess?`（`TXpertProjectAccessSummary \| null`）；`syncConversationProject?`、`onChatProjectChange?` | `projectAccess` 三态合一（pending / 不可用 / 拒绝均为 `null`，即 fail-closed）；`syncConversationProject` 在运行开始/结束后刷新持久 Project 且**不新开会话** |
| 状态与回调 | `userId`、`assistantId`、`xpertId`、`loading`、`loadingUserPreference`、`viewState`、`suppressAutoResume`、`pendingConversationStartId`、`activeConversation`、`viewErrorMessage()`、`onChatThreadChange()`、`beginPendingConversation()`、`ensureConversationEntry()`、`setActiveConversation()`、`patchActiveConversationStatus()` | `loading` / `loadingUserPreference` 与 `viewState` 三态分离（前者是进度，后者可挂载性）；四个写法方法里 `beginPendingConversation` / `ensureConversationEntry` 接收 `ChatKitControl`，是「宿主驱动 ChatKit」的唯一入口 |

**可选成员的默认实现策略**：契约层不提供任何默认值（纯 type），默认由**两边协商**——宿主侧「不实现即能力缺席」，骨架侧「`?.` 跳过 / 读作 `null`」。因此新增可选成员不会破坏既有宿主（结构性类型 + 可选成员是向后兼容的唯一手段）。

## 骨架组件如何消费门面

骨架 `ClawXpertConversationDetailComponent` 的消费模式有四种：

1. **可选注入 + 兜底**：`readonly #providedFacade = inject(WORKBENCH_CHAT_FACADE, { optional: true })`，`readonly facade: WorkbenchChatFacade = this.#providedFacade ?? inject(ClawXpertFacade)`——无宿主 provider 时整页退回 ClawXpert 私有会话（这是 `/chat/clawxpert/c/*` 形态）。
2. **可选信号的存在性判断**：部分实现需要区分「未声明」与「声明为 null」，用 `getOptionalSignalValue(this.facade, 'projectId')` 与 `getOptionalSignalValue(this.facade, 'currentWorkspaceId')`（`typeof value !== 'function' → null`）；后者说明骨架支持一个**契约类型未声明**的可选键。
3. **可选方法的能力探测**：`hasTaskSummaryRefresh(facade)` 用 `'refreshTaskSummaries' in facade && typeof facade.refreshTaskSummaries === 'function'` 做类型谓词；其余可选用 `?.()` 直接短路（`facade.syncConversationProject?.(threadId)`、`facade.onChatProjectChange?.(...)`）。
4. **就绪门控**：`identity` 传入 ChatKit 前被包一层 `computed(() => this.facade.viewState() === 'ready' ? this.facade.identity() : null)`；启动屏的 `active` 条件是 `viewState() === 'ready' && !chatkitInitialThread() && !chatkitGroup()`，即「无会话 + 非群组」才展示。

骨架零件对门面的依赖是**零**：菜单/账号/加载指示器/启动屏均不注入 token，只通过 inputs 与 `@core` 服务工作，因此可被任何宿主页面在任意位置复用。

章节来源：[clawxpert-conversation-detail.component.ts](file://apps/cloud/src/app/features/chat/clawxpert/clawxpert-conversation-detail.component.ts)（关键符号：`ClawXpertConversationDetailComponent.facade`、`ClawXpertConversationDetailComponent.control`）、[conversation.ts](file://apps/cloud/src/app/features/chat/clawxpert/conversation-detail/chatkit/conversation.ts)（关键符号：`getOptionalSignalValue`、`hasTaskSummaryRefresh`）

## 宿主实现：xpert-workbench 的装配

`ChatXpertWorkbenchComponent` 是整个子域的装配点，全部职责压在三处声明上：`providers: [XpertWorkbenchFacade, { provide: WORKBENCH_CHAT_FACADE, useExisting: XpertWorkbenchFacade }]`、模板一行 `<xp-clawxpert-conversation-detail class="min-h-0 flex-1" />`、`host: { class: 'flex h-full min-h-0 flex-col' }`；`ChangeDetectionStrategy.OnPush`，组件类体为空。**它没有 inputs、没有 outputs、没有任何逻辑**——这是「装配点应尽可能薄」的样板。

`XpertWorkbenchFacade`（`@Injectable()`，无 `providedIn`，只在装配点声明）的内部结构：

| 机制 | 实现 |
| --- | --- |
| 竞态防护 | 三个私有请求序号 `#loadRequestId`、`#projectAccessRequestId`、`#projectNavigationRequestId` + 一个去重键 `#lastConversationEntryKey` |
| 路由派生 | `currentUrl`（`Router.events` 过滤 `NavigationEnd` + `startWith(null)`）→ `slug` / `projectId` / `threadId` 三个纯函数解析；`normalizeWorkbenchPath` 先剥 query、再去尾斜杠 |
| 入口读取 | `#entryResolution = toSignal(this.#route.data.pipe(map(d => d['conversationEntry'])), { initialValue: snapshot })` |
| 状态加载 | `effect(() => { organizationId / slug / groupId })` → `loadState(slug, groupId)`；无组织时清空全部并 `#loadRequestId++` |
| Project 采纳 | `#adoptedProject`（`assistantId + threadId + projectId + mountProjectId + selection` 五元组）+ 一个 `effect` 在 `assistantId/threadId` 变化时自动清空 |
| Project 访问 | `effect(() => { organizationId, projectId })` → `#projectAccessRequestId++` → `loadProjectAccess` + `loadProjectName`（双请求共用同一序号） |
| xpert 归一 | `normalizeXperts(items)` 过滤 `latest === false` 与重复 `id`，兼容数组与 `{ items }` 两种响应形状 |

resolver `resolveConversationEntry` 在路由阶段做三件事：读 `route.paramMap.get('threadId')`、用 `store.organizationId` 拉 `getEntryByThreadId`、按 `entry.purpose !== 'group' && !hasFeatureEnabled(FEATURE_XPERT_CLAWXPERT)` 决定 `RedirectCommand(['/chat'])` 或正常返回 `{ entry, organizationId, error: null }`；`catchError` 把异常转成 `error` 字段（`getErrorMessage(error) || translate.instant('XP.Chat.ClawXpert.LoadFailedDesc')`），**不抛、也不降级**。

## 会话打开、切换与关闭的骨架流程

- **打开**：`xpertWorkbenchConversationMatcher` 消费 `/chat/x/:name[/p/:projectId]/c[/:threadId]` → `resolveConversationEntry` 写入 `data.conversationEntry` → 宿主 `effect` 触发 `loadState` → `getAvailableXperts(USER, CLAWXPERT)` → `currentXpert = availableXperts.find(slug 或 id 命中)` → `viewState` 变 `ready` → 骨架以 `identity() = chat-xpert-workbench:<xpertId>` 挂 ChatKit → 骨架调用 `ensureConversationEntry(control)`：仅当 `isConversationEntryRoute() && xpertId && !threadId() && viewState()==='ready'` 才 `setThreadId(null)` + `focusComposer()`，并按 `${xpertId}:${JSON.stringify(chatkitProjectSelection())}` 去重。
- **切换**：ChatKit 内换线程 → `onChatThreadChange(threadId)` → `handleThreadChange` → `navigateToThread` → `['/chat/x', slug, ('p', projectId,) 'c', threadId]`（`queryParamsHandling: 'preserve'`）→ `NavigationEnd` → `currentUrl` → `threadId` 重新派生。
- **关闭/清空**：`onChatThreadChange(null)` 且当前有 thread → `suppressAutoResume.set(true)` → `navigateToChat()`（去掉 thread 段，`preserve` query）——**`suppressAutoResume` 是「用户主动开新会话」的标记**，防止回来后自动恢复上一线程。
- **首次发消息后归属 Project**：骨架在运行开始/结束调 `syncConversationProject(threadId)` → `getByThreadId` 取服务端 `projectId` → 与路由 Project 不一致则写 `#adoptedProject` 并 `replaceUrl` 导航到 `/chat/x/:slug/p/:savedProjectId/c/:threadId`；期间 `chatkitMountProjectId()` 返回采纳前的挂载值，**ChatKit 不重挂、`identity()` 不变**。
- **切 Project**：`onChatProjectChange(projectId, view?, selection?)` 同项目且无 view/selection 时直接返回 `true`（不导航）；否则 `suppressAutoResume=true`、清 `#adoptedProject` / `activeConversation` / `projectAccess`，再以 `queryParamsHandling: 'merge'` 写 `projectMode` / `view` / `viewSelection` / `viewParameters`；导航返回 `false` 或抛错时 `restore()` 回滚（含 `activeConversation`、`projectAccess`、`suppressAutoResume`、`#adoptedProject`）。

章节来源：[xpert-workbench.facade.ts](file://apps/cloud/src/app/features/chat/xpert-workbench/xpert-workbench.facade.ts)（关键符号：`XpertWorkbenchFacade.ensureConversationEntry`、`XpertWorkbenchFacade.handleThreadChange`、`XpertWorkbenchFacade.onChatProjectChange`、`XpertWorkbenchFacade.restore`）

## 与 ClawXpert 的装配关系

ClawXpert 侧是本子域契约的**第二个（也是默认的）宿主**，两点装配互相不引用：

| 装配点 | provider | 适用路由 | 关键差异 |
| --- | --- | --- | --- |
| [xpert-workbench.component.ts](file://apps/cloud/src/app/features/chat/xpert-workbench/xpert-workbench.component.ts) | `useExisting: XpertWorkbenchFacade` | `/chat/x/:slug[/p/:projectId]/c[/:threadId]` | 公开路由按 `slug|id` 找 xpert；Project 段在 URL 中；群组由 resolver 的 `purpose` 唤起 |
| [clawxpert-conversation-pane.component.ts](file://apps/cloud/src/app/features/chat/clawxpert/clawxpert-conversation-pane.component.ts) | `useExisting: ClawXpertScopedConversationFacade` | `/chat/clawxpert/c/*`、`/chat/clawxpert/assistant/*` | per-scope 适配（`scope: 'task' \| 'assistant'`）、`identity` 追加 `:${scope}`、`threadId` 本地 signal + `nullGuardUntil`、`beginPendingConversation` 额外 `setComposerValue` 清空草稿 |

`ClawXpertScopedConversationFacade` 是「适配器（Adapter）」而非「实现」：它把 21 个必需成员中的 18 个直接转发给 `ClawXpertFacade`（`definition` / `identity` / `userId` / `assistantId` / `xpertId` / `currentXpert` / `assistantTitle` / `assistantAvatar` / `initialLayout` / `defaultViewKey` / `chatkitFrameUrl` / `loading` / `loadingUserPreference` / `viewState`…），只自持 `threadId` / `activeConversation` / `suppressAutoResume` 三个 signal，并把 `activeConversation` 在 `task` scope 下回写共享门面——**契约是这两个宿主唯一的共同语言**。

## 错误态与降级

| 场景 | 触发点 | 表现与兜底 |
| --- | --- | --- |
| 无组织 | `XpertWorkbenchFacade.viewState` | `'organization-required'`；同时清空 `availableXperts` / `activeConversation` / `suppressAutoResume` 并 `#loadRequestId++` |
| 未配置 `CHATKIT_FRAME_URL` | `viewState` + `viewErrorMessage` | `'error'` + `translate.instant('XP.Chat.ClawXpert.FrameMissing')`（`sanitizeAssistantFrameUrl` 把 `DOCKER_` 前缀视为未配置） |
| URL 缺 slug | `loadState(slug=null)` | `errorMessage = 'XP.Chat.XpertWorkbench.MissingSlug'` |
| slug 不在可得 xpert 中 | `loadState` 匹配失败 | `errorMessage = 'XP.Chat.XpertWorkbench.NotFound'`；`xpertId()` 为 `null` |
| `getAvailableXperts` 失败 | `loadState` catch | `getErrorMessage(error) \|\| 'XP.Chat.XpertWorkbench.LoadFailedDesc'` |
| 会话元数据解析失败 | resolver `catchError` | `viewState='error'`、`viewErrorMessage()` 返回该错误；**阻断私聊降级**（避免把无权会话渲染成私有会话） |
| 群组跨组织 | `viewState` 比对 `entryResolution.organizationId === organizationId` | 不一致直接 `'error'`，不挂载 |
| Project 访问被拒（403） | `loadProjectAccess` catch | `projectAccess = null`（与 pending 同形，fail-closed；`null` 语义即「pending / 不可用 / 拒绝」） |
| 常见问题生成失败 | `injectFrequentQuestionsStartScreen` 的 `error:` 分支 | 保留**已配置**启动屏（`configuredStartScreen`），不阻塞会话开始；`active=false` 时整块置 `null` |
| 助手菜单加载失败 | `WorkbenchAssistantMenuComponent.failed` / `groupsFailed` | `role="alert"` + `XP.Chat.WorkbenchPresentation.AssistantsLoadFailed` + Retry（群组单独 Retry 按钮） |
| 快速切换误报加载 | `WorkbenchLoadingIndicatorComponent` | `setTimeout(400ms)` 才 `visible=true`，组件被加载分支 own，快速切换直接销毁定时器 → 不闪 |

`restore()` 是本地降级的关键：`onChatProjectChange` 在导航失败/抛错时把 `activeConversation` / `projectAccess` / `suppressAutoResume` / `#adoptedProject` 全部回滚，并用 `navigationRequestId !== this.#projectNavigationRequestId || this.#router.url !== previous.url` 双重判定避免迟到的回滚覆盖新导航。

## 设计模式与热点路径

### 设计模式

- **依赖倒置（DIP）+ 契约 token 注入**：高层（骨架）不 import 低层（宿主），双方都依赖抽象（`WorkbenchChatFacade`）；抽象的所有权在**消费方一侧的子包**（`workbench-chat/`），这正是「门面契约定义处」放在骨架信封而非实现包的原因。
- **端口—适配器（Ports & Adapters）**：`WorkbenchChatFacade` 是端口，`XpertWorkbenchFacade` 是适配器；`ClawXpertScopedConversationFacade` 是**适配器套适配器**（把 shared 门面裁成 per-scope 端口实现）。
- **Facade（门面）**：宿主用一个对象向骨架暴露 31 个成员，屏蔽 `AssistantBindingService` / `ChatConversationService` / `XpertProjectApiService` / `Router` 四个依赖。
- **状态机（computed）**：`viewState` 是显式四态机（`organization-required | wizard | ready | error`），由 `computed` 单向派生，不存状态。
- **请求序号（generation token）**：三个自增序号 + 一个去重键解决「迟到响应」，模式是「先自增再 await，回来比对」。
- **结构性类型 / 鸭子类型**：`hasTaskSummaryRefresh` 与 `getOptionalSignalValue` 用 `in` 与 `typeof` 探测契约外能力。

### 热点路径

1. **进入 `/chat/x/<slug>/c`（最高频）**：resolver → `loadState` → `viewState='ready'` → 骨架挂 ChatKit → `ensureConversationEntry`。
2. **每次发消息结束**：`syncConversationProject(threadId)`（`getByThreadId` + 可能的 `replaceUrl` 导航）——首条消息后必然发生一次。
3. **`effect(organizationId/projectId)`**：每次进 Project 路由触发 **两个** HTTP（`access` + `get`）。
4. **`onChatProjectChange`**：一次导航 + 一次回滚判定；在 `#workbenchProjectNavigation` 与骨架的 Project 选择器两处都会调用（[xpert-workbench.facade.spec.ts](file://apps/cloud/src/app/features/chat/xpert-workbench/xpert-workbench.facade.spec.ts) 有专门用例断言「打开 Receipt 不改变挂载身份」）。
5. **菜单加载**：`WorkbenchAssistantMenuComponent` 构造即并发 `getAvailableXperts` + `ChatGroupService.list`。

## 设计维度与技术债

### 设计维度

- **维度一：契约稳定性（必需 / 可选 / 契约外）**。21 个必需成员构成「任何宿主都必须回答」的最小面；10 个可选成员承载形态差异（群组、Project、品牌）。**第三层是契约外的鸭子类型**（`refreshTaskSummaries`、`currentWorkspaceId`）——它让骨架能跨版本兼容，但把「谁该实现」变成了口头约定，是本子域最需要收敛的维度。
- **维度二：状态所有权（宿主持有 vs 骨架持有）**。`threadId` / `viewState` / `projectId` 归宿主（源自 URL 与服务端），骨架只读；`control`（ChatKit 句柄）、`overlayDialog`、`startScreen` 归骨架。边界规则是「**可被 URL 表达的状态归宿主**」，因此 Project 采纳必须回写路由（`replaceUrl: true`）而不是只改内存。
- **维度三：装配成本（新增宿主要写多少）**。实测 `/chat/x/:slug` 宿主 = 1 facade + 1 装配组件 + 1 resolver + 1 路由项；若宿主的会话「不由 URL 驱动」（如 per-scope pane），则需额外自持 `threadId` 与 `nullGuardUntil` 类保护——**这是「URL 驱动」与「内存驱动」两种宿主的分水岭**。

## 结论

- **契约只有 65 行，却承担了整个子域的解耦职责**；所有实现复杂度都被推到宿主侧（`XpertWorkbenchFacade` 599 行 + 25 个 `it` 用例）。
- **装配点已经压到极限**：`ChatXpertWorkbenchComponent` 无逻辑、无 inputs/outputs，改宿主形态只需替换 façade 与 `providers`。
- **可选成员策略是「契约无默认值、骨架有兜底」**：契约不提供默认实现，缺失由骨架 `?.` / `null` 化处理，因此新增可选成员是向后兼容的。
- **最值得先修的不是功能而是契约卫生**：把 `refreshTaskSummaries` / `currentWorkspaceId` 收入契约（或明确标注为遗留），并补一个契约级 spec，即可把第 1、3 号技术债一次结清。
- 对外逐成员契约、token 生命周期与复用指南见 `implementation/05-接口.md`；测试现状见 `implementation/06-测试.md`。
