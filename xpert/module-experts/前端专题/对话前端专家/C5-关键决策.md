## 决策明细 D1–D12
### D1 对话入口收敛到 ClawXpert（`/chat` → `/chat/clawxpert`）
- **分类**：兼容处理（ki 原文为 [推测]，按本表口径归入兼容处理）
- **动机（避坑，[推测]）**：现象——`/chat` 下曾并存 `x/welcome`、`x/common`、`x/common/c`、`x/common/c/:id` 等多个入口形态，移动端与旧链接各指一处；后果——入口行为不一致、报障难以归因，路由表也无法清理。ki 将该动机记为 [推测]，此处保留标注。
- **决策**：旧入口全部 `redirectTo: '/chat/clawxpert'`；空路径 `''` 由 `redirectToDefaultChatEntry()` 判定（双特性 → `organizationId` → USER 绑定 → 可用 xpert 命中），命中去 `/chat/clawxpert/c`，否则 `/chat/clawxpert`；`**` → `clawxpert`。
- **背景约束**：入口重定向必须先过父级 `authGuard`（源码注释：Keep the redirect behind the parent auth guard before resolving user bindings.）；`getAvailableXperts` 结果需经 `hasMatchingXpertId` 校验，绑定存在但助手不可用时不得进会话。
- **被否决方案**：无（ki 未记录候选方案，本次亦未在代码或提交信息中找到被否决方案的痕迹）。
- **重新评估触发条件**：ki 原文——「旧入口报障清零且需清理路由表」（即旧入口可安全删除、不再需要兼容层）时重估。
- **关联代码**：`routes.ts` 的 `redirectToDefaultChatEntry`、`path: 'x/welcome'`、`x/common`、`x/common/c`、`path: '**'`、`readAssistantBindingAssistantId`、`hasMatchingXpertId`。
- **证据来源**：ki [推测] 条目（保留标注）；代码实证见 [routes.ts（对话域）](file://apps/cloud/src/app/features/chat/routes.ts)。

### D2 缺特性开关回落 `/explore`（守卫 + 壳层双层）
- **分类**：架构设计
- **动机（避坑）**：现象——ClawXpert 依赖 `FEATURE_XPERT` + `FEATURE_XPERT_CLAWXPERT` 两个特性位，且特性上下文需要异步水合；后果——未开通或水合失败时页面会停在半截骨架（无 iframe、无绑定），用户得不到可行动的解释。ki 记录的触发条件为「旧入口报障清零且需清理路由表」，与 D1 同源，本条是其守卫侧的独立决策。
- **决策**：`clawxpert` 路由 `canActivateChild: [featureGate([FEATURE_XPERT, FEATURE_XPERT_CLAWXPERT], ['/explore'])]`；壳层 `ChatHomeComponent` 在特性上下文 hydrate 完成、URL 属于 `/chat/clawxpert` 且开关缺失时 `navigateByUrl('/explore')`。
- **背景约束**：`featureGate` 内部 `hydrateFeatureContext` 有 **3s 超时**，超时按「未水合」处理并一律回落；回落目标 `/explore` 的路由前缀一变，本配置必须同步（见关联记忆的风险项）；公共页 `/x-chatkit/h5/*` 不经过 `featureGate`。
- **被否决方案**：无（未找到「页面内提示替代回落」或「白屏等待水合」方案的评审记录）。
- **重新评估触发条件**：灰度关停语义变化（例如 ClawXpert 关停后应留在 `/chat` 提示而非跳 `/explore`），或 `/explore` 路由前缀调整。
- **关联代码**：`routes.ts` 的 `canActivateChild` + `featureGate([...], ['/explore'])`、`ChatHomeComponent` 的 `isClawXpertRoute`/`clawxpertEnabled`、`featureGate`/`hydrateFeatureContext`/`FEATURE_HYDRATION_TIMEOUT_MS`。

### D4 实时/控制面双通道分工（socket.io + HTTP），实测口径已修正
- **分类**：技术选型
- **动机（避坑）**：现象——对话需要两类能力：历史/反馈/绑定等「可重放的控制面读取」与「服务端一产生就到前端的增量」；后果——若用一条通道兼做两件事，实时帧会与历史读取互相污染（重复/乱序），且无法按通道独立做鉴权与运维。ki 记录的动机为「socket.io 为唯一实时主通道、HTTP 仅控制面」，此处按其口径保留。
- **决策**：约定分工为「socket.io 走实时、HTTP 走控制面」。**实测修正**：本 commit 的活跃链是 `ChatService@core.chat(request, options)` → `injectFetchEventSource(baseUrl + API_CHAT)` 的**单流 SSE** + HTTP 控制面；`ChatWebsocketServer` 的唯一消费方 `ChatWebsocketService`（`features/chat/chat.service.socket.ts`）在全仓库**无其他引用**，属无路由级消费者的保留实现（含 401 刷新与 2s 重发语义）。
- **背景约束**：socket 客户端未显式配置 `transports`/`reconnection`/`pingInterval`，沿用 socket.io 默认（长轮询起步 + 升级）；多副本部署需要连接粘性；反代需放行 `/socket.io/` 与 `Upgrade`——这些约束在「当前无消费者」的现状下不构成线上依赖。
- **被否决方案**：无（未找到「轮询替代流」或「HTTP 全量替代 socket」方案的评审记录）。
- **重新评估触发条件**：ki 原文——「socket 网关成为部署瓶颈或需无状态横向扩展」；本文追加：若 `@shared/chat/preview` 等外部消费者也被迁移到 SSE，则应直接删除孤立 socket 路径。
- **关联代码**：`chat.service.ts（@core）` 的 `ChatService.chat`/`API_CHAT`、`chat.service.socket.ts（@core）` 的 `ChatWebsocketServer.connect`/`message`/`clearRetryMessage`/`refreshToken`、`chat.service.ts（xpert）` 的 `executeChatRequest`/`startJoinedRunStream`。

### D5 消息去重合并交给共享纯函数 `filterLatestMessages`
- **分类**：接口契约
- **动机（避坑）**：现象——重试/续跑会产生同 `parentId` 的多个子消息，历史补拉与实时增量可能同时落到列表里；后果——不做去重会重复渲染旧分支，做错去重会**丢消息**。该函数同时被对话页与 Studio 预览消费，属跨域共享契约。
- **决策**：按 `parentId` 建链（`byId`/`indexById`/`childrenByParent` 三张表），每层只保留 `createdAt` 最新的孩子（同刻取数组内更靠后者），**保持原顺序返回**；无 `id` 的项不建索引但保留；父不存在视为 root。
- **背景约束**：执行在**读路径**（`ChatService.#conversation` 的 `derivedAsync`），非渲染帧；依赖 `createdAt`——缺失或时区异常时退化为「按原序后位」，无法识别真正的分支覆盖关系；`keep` 为空集时**原样返回输入**（宁可重复不可丢）。
- **被否决方案**：无（未找到「服务端去重」或「按 id 去重」方案的评审记录）。
- **重新评估触发条件**：出现服务端统一去重的消息接口；或长会话下读路径成本成为瓶颈（当前对全部消息建三张 Map）。
- **关联代码**：`filterLatestMessages`/`pickLatest`、`ChatService.#conversation`、对话页与 Studio 预览的 import 点。

### D6 ChatKit 以 iframe 宿主化承载会话 UI
- **分类**：架构设计
- **动机（避坑）**：现象——会话 UI（流式渲染、composer、历史、附件）与平台前端的技术栈与发布节奏不同；后果——若把会话 UI 做成平台内嵌组件，两边的渲染与状态必须同步演进，且会话容器无法独立发布/复用。**说明**：本条动机为本次基于现形态的推断（[推测]），非 ki 记录；「而非内嵌组件」是本表对现有形态的对比描述，**本次未找到内嵌组件方案被评估与否决的任何记录**。

### D12 前端零持久化：投影式状态 + 历史补拉
- **分类**：架构设计
- **动机（避坑）**：现象——执行记录、上下文用量、反馈、绑定等数据后端也在持续写；后果——前端若各自落地一份并独立演进，会与后端形成**双源漂移**（同一会话在两个地方有不同状态）。
- **决策**：前端不做任何本地持久化——消息/会话/执行/反馈/绑定/任务全部是「后端真源 + 前端投影或浅缓存」；实时通道只提供增量视图，**断线重连后以历史补拉为准**；执行记录与上下文用量明确「前端零新增数据（纯投影）」。
- **背景约束**：会话切换按 scope / 组织清理上下文（`contextUsageByAgentKey` 切会话即 `set({})`）；触发器的 `workingItems` 等未保存编辑随组件销毁丢失；`PendingFollowUp`（`queue`/`steer`）与请求上下文是前端独有态，不可回放。
- **被否决方案**：无（未找到「前端本地缓存会话/消息」方案的评审记录）。
- **重新评估触发条件**：出现离线可用 / 弱网查看历史的产品需求；或需要在前端做消息级重放与幂等补偿时。
- **关联代码**：`ChatService.#conversation`（`derivedAsync` + `combineLatest`）、`contextUsageByAgentKey`、`startJoinedRunStream`（1s 重连 + `lastEventId` 续传）、`ClawXpertConfigurationCache`（仅加速首屏且注释明示「缓存永不替代服务端授权」）。

## 决策间关系与重估优先级
- **准入轴（D1 + D2 + D11）**：入口收敛、特性位回落、公共页无守卫同属「路由层不设卡 + 后端兜底」这一取向；改任一项必须同时核对免登录白名单（认证与引导专家）与 `/explore` 前缀（探索广场）。
- **契约轴（D3 + D9）**：门面 token 化决定了项目作用域字段能做成可选（D9 的 `syncConversationProject?` 才有意义）；若 D3 拆子契约，D9 的字段归属需一并重划。
- **通道轴（D4 + D12）**：双通道分工与「后端真源 + 前端投影」互为前提；一旦引入前端本地持久化（D12 重估），D4 的补拉语义与 D5 的去重时机都要重算。
- **宿主轴（D6 + D7 + D8）**：iframe 宿主化带来安全边界前置（D7）与群组/私有的会话作用域差异（D8）；三者共同决定 `runtimeKey`/`securityScope` 的组成。
