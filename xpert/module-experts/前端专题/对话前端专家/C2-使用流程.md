## R1 以 ClawXpert 打开一个会话并收发消息
- **业务目标**：用户访问 `/chat` 即落到「已绑定的 ClawXpert 会话」，能看见历史消息并发出一条新消息、看到流式回复。
- **调用顺序**：`/chat`（空路径）→ `redirectToDefaultChatEntry()`：`hydrateFeatureContext({ skipSessionCache: true })` → `FEATURE_XPERT` 且 `FEATURE_XPERT_CLAWXPERT` → `store.organizationId` → `AssistantBindingService.get(CLAWXPERT, USER)` → `readAssistantBindingAssistantId(binding)` → `getAvailableXperts(USER, CLAWXPERT)` → `hasMatchingXpertId(...)` 命中则 `/chat/clawxpert/c`，否则 `/chat/clawxpert` → `ClawXpertComponent`（壳）按 `mountedScopes()` 常驻挂载 `ClawXpertConversationPaneComponent` → 面板 `providers` 把 `ClawXpertScopedConversationFacade` 绑到 `WORKBENCH_CHAT_FACADE` → `ClawXpertConversationDetailComponent` → `injectHostedAssistantChatkitControl` → `createChatKit(options)` 挂 iframe。发送有两条路径：**(a) iframe 内 composer**（主路径）→ `assistant.chat.send_message` client-command → `registerAssistantChatSendMessageCommand` → `control.sendUserMessage(message)`；**(b) 平台/SDK 路径** → `ChatService.sendMessage` → `appendMessage(humanMessage)` → `chatRequest` → `ChatServerService.chat` → `POST /api/chat` SSE → `executeChatRequest` 归约。
- **时序边界**：用户消息**先落内存后发请求**（乐观）；`clientMessageId = options.id` 是唯一前后端对齐键；ai 占位消息不在发送时创建，而在 `ON_MESSAGE_START` 到达时 `appendMessage({ id: uuid(), role: 'ai', content: '', status: 'thinking' })`；`answering()` 为真时新输入不进请求而进 `enqueueFollowUp`（`mode: 'queue' | 'steer'`）。
- **预期结果**：页面停在 `viewState() === 'ready'`，iframe 加载后 `onReady`；消息列表按 `filterLatestMessages` 单调渲染，回合结束后 `patchActiveConversationStatus('idle')`。
- **错误处理**：`hydrateFeatureContext` 任一环节失败或 catchError 一律回落 `/chat/clawxpert`（入口不会 404/白屏）；`sanitizeAssistantFrameUrl` 返回 `null` 时 `status = 'error'`、**不挂载 iframe**；`registerAssistantChatSendMessageCommand` 在 control 不存在或 `isReady()` 为假时回 `{ success: false, code: 'unsupported' }`，`text`/`content` 双空回 `bad_request`。
- **真实代码示例**：
```ts
// features/chat/routes.ts —— 入口收敛（任何异常都回落到 clawxpert）
return assistantBindingService.get(AssistantCode.CLAWXPERT, AssistantBindingScope.USER).pipe(
  switchMap((binding) => {
    const assistantId = readAssistantBindingAssistantId(binding)
    if (!assistantId) return of(router.createUrlTree(['/chat/clawxpert']))
    return assistantBindingService.getAvailableXperts(AssistantBindingScope.USER, AssistantCode.CLAWXPERT).pipe(
      map((xperts) => (hasMatchingXpertId(xperts, assistantId)
        ? router.createUrlTree(['/chat/clawxpert/c'])
        : router.createUrlTree(['/chat/clawxpert']))),
      catchError(() => of(router.createUrlTree(['/chat/clawxpert'])))) }),
  catchError(() => of(router.createUrlTree(['/chat/clawxpert']))))
```

## R2 断线重连后补拉与消息去重合并
- **业务目标**：socket 掉线、token 过期、或页面重进后，消息列表既不缺消息也不出现重复分支。
- **调用顺序**：① 连接态：`ChatWebsocketServer.connect()` 仅在 `!socket || disconnected || !connected` 时建连；`exception` 报 `401` 时 `setStatus(false)` 并在 `refreshTokening()` 为假时经 `AuthStrategy.refreshToken()` 重连。② 发送可靠性：`message(data)` 发送前拼 `organizationId`，并挂 2s 定时器；收到 `ChatGatewayEvent.ACK` 才 `clearRetryMessage()`，否则原样重发。③ 补拉：重进页面 → `ChatService.#conversation` 的 `derivedAsync` → `fetchConversation(id)`（`relations` 含 executions/feedback/task）+ `getFeedbacks(id)` → **立即** `filterLatestMessages(conversation.messages)`。④ 运行中断线补挂：`effect` → `resolveJoinedRunTarget(conversation)` 选出顶层 `running`/`pending` 执行 → `startJoinedRunStream(threadId, runId, lastEventId)` → `aiThreadService.joinRunStream(threadId, runId, lastEventId)`。
- **时序边界**：**前端无持久化**——补拉的唯一真源是 HTTP 历史；`lastEventId` 只在前端记（`if (message.id) this.joinedRunLastEventId = message.id`），**未在本次核实服务端是否严格不重发**（保留为未确认）。去重是**读路径**纯函数变换，不写回服务端。
- **预期结果**：同一 `parentId` 链上只保留 `createdAt` 最新的子节点（同刻取数组内更靠后者），返回顺序与原数组一致；重试分支的旧消息不再重复渲染。
- **错误处理**：`filterLatestMessages` 在 `keep` 为空集时**原样返回输入**（宁可重复不可丢）；无 `id` 的项不建索引但**仍保留**；父不存在的项视为 root 保留；`joinRunStream` 出错时 1s 后用 `joinedRunLastEventId` 重连，`complete` 才清 `answering`。

## R3 新建会话形态并接入路由（守卫与回落 `/explore`）
- **业务目标**：为一种新宿主（新 URL 形态）复用同一套页面骨架与 ChatKit 宿主，而不改骨架代码；特性未开通时不暴露半截页面。
- **调用顺序（接入 4 步）**：① 实现一个 `WorkbenchChatFacade`（或包装现有门面）——骨架唯一依赖的 30 个成员；② 在形态组件里提供 token：`providers: [{ provide: WORKBENCH_CHAT_FACADE, useExisting: XxxWorkbenchFacade }]`；③ 模板/`imports` 直接复用 `ClawXpertConversationDetailComponent`；④ 路由声明——平台内形态建议 `canActivate`/`canActivateChild: [featureGate([AiFeatureEnum.FEATURE_XPERT, …])]`，回落目标按产品语义给（ClawXpert 段给 `['/explore']`）。现成三种形态的装配为：`ChatXpertWorkbenchComponent`（`/chat/x/:name[/p/:projectId]/c[/:threadId]`）→ `XpertWorkbenchFacade`；`ClawXpertConversationPaneComponent`（`/chat/clawxpert/c*`、`/chat/clawxpert/assistant*`）→ `ClawXpertScopedConversationFacade`；无 provider 时骨架 `inject(WORKBENCH_CHAT_FACADE, { optional: true })` 回退到 `ClawXpertFacade`。
- **时序边界**：`useExisting` 而非 `useClass` ⇒ **同一路由内门面实例唯一**（页面组件与详情组件共享同一份状态）；`featureGate` 内部 `hydrateFeatureContext` 有 **3s 超时**，超时按「未水合」处理并直接回落；门面替换只改「宿主差异」，不改骨架渲染与 ChatKit 生命周期。
- **预期结果**：新形态与 ClawXpert 页面表现一致（同布局、同 iframe、同命令白名单）；可选成员（`projectId?`/`chatkitMountProjectId?`/`syncConversationProject?` 等）由形态按能力决定是否提供，骨架用存在性探测读取。
- **错误处理**：`clawxpert` 子树缺开关时 `canActivateChild: featureGate([...], ['/explore'])` 整棵子树把用户送回 `/explore`；壳层还有第二层兜底——`ChatHomeComponent` 在特性上下文 hydrate 完成、URL 属于 `/chat/clawxpert` 且开关缺失时 `navigateByUrl('/explore')`；`clawxpertConversationMatcher` 与 `xpertWorkbenchConversationMatcher` 未匹配时由 `path: '**'` → `clawxpert` 兜底。

## R4 注册一个新助手（`ASSISTANT_REGISTRY`）并让其可被访问
- **业务目标**：新增一个助手（平台内置或用户自配置），使其出现在注册表、可被门面取到标题、并具备正确的准入特性位。
- **调用顺序**：① 在 `ASSISTANT_REGISTRY` 追加一项，字段为 `code` / `featureKeys` / `management` / `labelKey`+`defaultLabel` / `titleKey`+`defaultTitle` / `descriptionKey`+`defaultDescription`（i18n key 与默认文案双写）；② 若为「用户自配置」类，`management: 'user'` 并确保契约侧 `USER_MANAGED_ASSISTANTS` / `getAssistantManagement` 与本表一致；③ 门面取用：`getAssistantRegistryItem(code)`（`find(...) ?? null`）→ `ClawXpertFacade.definition` 用非空断言取值 → 作为 iframe 标题；④ 准入：`featureKeys` 必须与路由层 `featureGate(...)` 的键一致，用户级助手还需 `AssistantBindingService` 建立 USER 作用域绑定后才可被 `getAvailableXperts` 命中。
- **时序边界**：**新增助手 ≠ 新增路由形态**——注册表只描述助手（`code`/特性位/归属/i18n），页面形态由 `WORKBENCH_CHAT_FACADE` 的 provider 决定（见 R3）；`AssistantCode` / `AiFeatureEnum` 是 `@core` 再导出的契约枚举，注册表只能引用既有枚举值。
- **预期结果**：`ASSISTANT_REGISTRY` 三项（`CHAT_COMMON`/`XPERT_SHARED` 为 `system`、`CLAWXPERT` 为 `user` + 双特性位）之外新增的一项可被 `getAssistantRegistryItem` 命中；对应特性位关闭时相关入口按守卫回落。
- **错误处理**：`getAssistantRegistryItem(code)` 未命中返回 `null`（门面处的 `!` 会把缺失变成运行时错误，新增助手必须同时保证注册表项存在）；`featureKeys` 与实际路由 `featureGate` 不一致时表现为「注册表说可用、路由进不去」，属配置缺口而非代码报错。
- **真实代码示例**：
```ts
// features/assistant/assistant.registry.ts
export const ASSISTANT_REGISTRY: AssistantRegistryItem[] = [
  { code: AssistantCode.CHAT_COMMON, featureKeys: [AiFeatureEnum.FEATURE_XPERT], management: 'system', … },
  { code: AssistantCode.XPERT_SHARED, featureKeys: [AiFeatureEnum.FEATURE_XPERT], management: 'system', … },
  { code: AssistantCode.CLAWXPERT,
    featureKeys: [AiFeatureEnum.FEATURE_XPERT, AiFeatureEnum.FEATURE_XPERT_CLAWXPERT],
    management: 'user', … } ]
export function getAssistantRegistryItem(code: AssistantCode) {
  return ASSISTANT_REGISTRY.find((item) => item.code === code) ?? null }
```

## R5 以 ChatKit 宿主嵌入助手（iframe 握手 + client-command 往返）
- **业务目标**：任意页面用同一个宿主函数把助手 UI（iframe）嵌进来，握手成功后宿主能把会话/项目状态同步进 iframe，iframe 能请求宿主执行受限命令。
- **调用顺序**：① `injectAssistantChatkitRuntime({ assistantCode, … })`（助手 shell 用）= 绑定运行时 + 宿主控制；或直接 `injectHostedAssistantChatkitControl({ identity, assistantId, group?, projectId?, frameUrl, getClientSecret?, … })`（三个宿主：ClawXpert 会话详情、公共页 `PublicChatkitComponent`、项目会话面板）；② 宿主算 `runtimeKey`（identity:assistantId:groupId:delegatedConversationId:requesterXpertId:frameUrl:apiUrl:token:organizationId）与 `securityScope`；③ `newSession = !currentControl || activeRuntimeKey !== key` → `sessionRevision++` → `createChatKit(options)`，否则 `currentControl.setOptions(options)`；④ iframe 侧 `onReady` → 通过宿主 `api.getClientSecret` → 宿主 `POST /api/ai/v1/chatkit/sessions` 换短时 `client_secret`；⑤ 命令下行（宿主→子）：`assistant.chat.send_message` / `assistant.context.set` / `assistant.composer.append_references` / `workbench.browser.open` / `workbench.file.open` / `workbench.navigation.open` / `workspace.connector.connect`；⑥ 命令上行（子→宿主）：`workbench.onClientCommand` → `createChatkitWorkbenchClientCommandHandler` → 校验 → 回服务器重解析 manifest → `commands.execute`。
- **时序边界**：`runtimeKey` 变化才重建 iframe；`loading()` 为真时**只在同一 `securityScope` 内**保留已挂载 iframe，跨安全域立刻清空 control；`initialThread` 用 `untracked` 读取，避免切换会话重建全部选项；`sessionKey` 是**不透明序号** `hosted-session-${revision}`（源码注释明确禁止序列化 `runtimeKey`，其中含登录凭据）。
- **预期结果**：iframe 正常加载并可在其内部完成一轮对话；发布事件（`XpertPublicationService.changes$` → `publicationRevision`）只触发 `setOptions` 原地刷新，**不重建会话**；`workbench.file.open` / `navigation.open` 等命令在宿主内生效。
- **错误处理**：`sanitizeAssistantFrameUrl`（空或 `DOCKER_` 前缀）→ `null` → `status = 'error'` 且不挂载；桥接器 `request.hostType !== 'agent' || request.hostId !== scope.assistantId` → `stale_context`；卡片点击缺会话/未命中服务端历史/manifest 未授权该 key → `forbidden`；`ViewClientCommandRegistry.execute` 无处理器 → `{ success: false, code: 'unsupported' }`；执行前后 `runtimeScope` 变化 → `stale_context`；附件超过 `CHATKIT_ATTACHMENT_MAX_BYTES`（50 MiB）或 `maxCount: 5` 由 composer 直接拦截，不发请求。
- **真实代码示例**：

## R6 处理项目选择与对话上下文绑定
- **业务目标**：让「会话 ↔ 项目」的作用域在首屏挂载、用户切换、运行结束后三个时点都一致，且切换项目不意外新开会话。
- **调用顺序**：① 初始绑定：门面给 `chatkitMountProjectId`（**仅初始**会话绑定的项目）与 `chatkitProjectSelection`（**初始草稿意图**，`ProjectSelection`）；② iframe 内切换：`onProjectChange` → `facade.onChatProjectChange?.(projectId, view?, selection?)`；③ 运行开始/结束：`onThreadLoadEnd` → `facade.syncConversationProject?.(threadId)` 刷新**持久**项目；④ 域内实现（`XpertWorkbenchFacade`）：`#adoptedProject()` 只采纳服务端保存的作用域（`adopted.assistantId === assistantId() && adopted.threadId === threadId()` 才用），随后 `router.navigate(['/chat/x', slug, 'p', savedProjectId, 'c', threadId])`；`chatkitProjectSelection` 在无持久项目时回退 `{ mode: 'existing', projectId }` → 路由 mode → `currentXpert()?.options?.workspaceScope?.onMissing ? - **预期结果**：会话在正确项目下运行；运行结束后 URL 的 `p` 段与持久项目对齐；未支持项目隔离的宿主（不提供可选成员）行为不变。

## R7 消息反馈提交
- **业务目标**：用户对某条 AI 消息点赞/点踩并可撤销，反馈在重进会话后仍然可见（后端为真源）。
- **调用顺序**：① 读取：`ChatService.#conversation`（`derivedAsync`）用 `combineLatest([fetchConversation(id), getFeedbacks(id)])` 把反馈列表归约成 `Record<messageId, IChatMessageFeedback>`，再经 effect 写入 `feedbacks` signal；`getFeedbacks` 调 `feedbackService.getMyAll({ where: { conversationId: id } })`（`ChatMessageFeedbackService extends OrganizationBaseCrudService<IChatMessageFeedback>`，基址 `API_PREFIX + '/chat-message-feedback'`，仅覆写 `getMyAll` 指向 `/my`）；② 提交：`ChatAiMessageComponent.feedback(message, rating)` → `messageFeedbackService.create({ messageId, conversationId, rating })` → 成功后本地 `feedbacks.update(...)` + toastr；③ 撤销：`cancelFeedback(message, id)` → `delete(id)` → 该键置 `null`。
- **时序边界**：反馈是**读写都走后端**的浅缓存（前端只做归约）；展示门控由 `feedbackReady` 决定——只有执行状态进入终态集合（`endedStatuses`，如 `XpertAgentExecutionStatusEnum.SUCCESS`）才允许评价，避免流式过程中误评；反馈与消息的关联键是 `messageId`，不是 `index`。
- **预期结果**：评价后按钮态即时更新（本地 `update`）；重进会话时反馈由 `getMyAll` 重新灌入；同一模式在 `@shared/chat/preview` 与 Studio 执行面板复用（跨域共享契约）。
- **错误处理**：`create`/`delete` 失败经 `getErrorMessage(error)` + `ToastrService.error` 提示，本地不做回滚（下一次读会话会以后端为准）；无会话上下文时 `getFeedbacks` 链失败只表现为反馈区为空。
- **真实代码示例**：
```ts

  this.messageFeedbackService.create({ messageId: message.id, conversationId: …, rating })
    .subscribe({ next: (feedback) => { this.feedbacks.update({ [message.id]: feedback }); … } }) }
cancelFeedback(message: TCopilotChatMessage, id: string) {
  this.messageFeedbackService.delete(id).subscribe({ next: () => this.feedbacks.update({ [message.id]: null }) }) }
```

- **业务目标**：用户进入一个共享群组会话（成员可见、发布可见），群组视图按会话 id 绑定而不混入个人助手线程。

## R9 文件变更审查流程
- **业务目标**：把一次会话（或选中的一批变更）产出的文件改动做成可逐文件 diff 审查的视图，重开时复用同一标签页而不丢端点。
- **调用顺序**：① 标签页：`createFileChangeReviewTab` 生成 `id = 'file-review:' + (threadId ?? conversationId ?? 'current')`（`kind: 'file-review'`），重开走 `upsertFileChangeReviewTab`；② 加载：`FileChangeReviewComponent.load()` —— `scope === 'conversation' && tab.conversationId` 时先 `service.listChanges(conversationId)`（`GET /api/ai/conversations/:id/task-summary/fileChanges`，100 一页循环拉全量），否则直接用标签页携带的 `FileChangeResource | FileChangeSetResource`；③ 批量取报告：`for (let offset = 0; offset < targets.length; offset += 4)` 每批 4 个并发 `service.loadReport(resource)`，并校验 `path === report.workspacePath`；④ 统计与展示：`countFileChangeLines` 汇总增删行，另有 `sideBySide`/`wordWrap`/`showWhitespace`/`showMetadata`/`showFiles`/折叠集等视图态；⑤ 命令入口：`workbench.file.open` 由 `registerWorkbenchFileOpenCommand` 承接（有 `evidence` 开预览对话框，否则开文件产物标签，附件预览上限 1MB）；⑥ 文件本体的读写在 `ClawXpertConversationFilesComponent`，把 load/download/save/upload/saveBinary/delete 适配到 `@shared/files` 工作区桥。
- **时序边界**：并发度 **4 是组件内硬编码**，`conversation` 范围下请求数随变更集线性增长；`request` 自增作为**作废令牌**——每批返回后 `if (request !== this.request) return`，丢弃过期批次；`upsertFileChangeReviewTab` 对已存在的同 id 标签页**只把 `revision + 1`**，不改端点（注释：One review tab per thread; opening another saved range never changes its endpoints.）。
- **预期结果**：逐文件 diff 可读、增删行有统计；缺失证据的文件以 `unavailable: true` 占位而不是整页失败；同一 thread 只有一个审查标签页。
- **错误处理**：单文件 `loadReport` 失败进入 `catch` → `{ key, path, unavailable: true }`（局部降级）；工作区文件刷新由 `WORKSPACE_FILE_REFRESH_DEBOUNCE_MS = 300` 去抖；上传超限由后端 `413` 体现（前端只做附件/预览上限）。
- **真实代码示例**：
```ts
// features/chat/clawxpert/file-change-review.component.ts
const targets = scope === 'conversation' && tab.conversationId
  ? (await this.service.listChanges(tab.conversationId)).map((change) => ({ path: change.workspacePath, … }))
  : …

  const batch = await Promise.all(targets.slice(offset, offset + 4).map(async ({ path, resource }) => {
    const key = resource ? fileReviewKey(resource) : path

    try {
      const report = await this.service.loadReport(resource)

      return { key, path: report.workspacePath, report }
    } catch { return { key, path, unavailable: true } } })) }
```

## R10 排障：消息不刷新 / 重复 / 流式中断 / 宿主握手失败
- **业务目标**：把四类高频故障按「现象 → 判断 → 处置」快速定位到具体通道与代码位点。
- **调用顺序（排查路径）**：

| # | 现象 | 判断与排查点 | 处置 |
| --- | --- | --- | --- |
| 1 | 消息发出去不刷新 | Network 无失败但界面不动：先确认宿主是 **ChatKit 路径**（会话内消息由 iframe 负责）还是 **socket 路径**；socket 路径再查每条 `message` 是否收到 `ack` | 若是 iframe 路径，查 `runtimeKey`/`securityScope` 是否变过（变则重建 iframe）、绑定态 `status` 是否 `ready`；若是平台路径，查 `POST /api/chat` 的 SSE 是否被 `msg.data.startsWith(':')` 心跳分支吞掉、`executeChatRequest` 的 `subscribe.next` 是否走到 |
| 2 | 重复消息 | `ChatWebsocketServer.message()` 挂 2s 定时器，未收到 `ACK` 就**原样重发**（无次数上限、无指数退避）——"日志里看到重复消息"的正常来源；另一来源是历史补拉后未去重 | 核对服务端幂等是否依赖 `clientMessageId`（前端乐观消息的 `id`）；渲染侧确认读路径确实过了 `filterLatestMessages` |
| 3 | 流式中断（回复停在一半） | 会话 `status === 'busy'` 且非本地请求时，`resolveJoinedRunTarget` 选出顶层 `running`/`pending` 执行并 `startJoinedRunStream`；失败 1s 后用 `joinedRunLastEventId` 重连 | 查 `GET /api/ai/threads/:threadId/runs/:runId/stream` 的 `Last-Event-Id` 续传是否成功；**服务端是否严格不重发未在本次核实**（保留为未确认） |
| 4 | 宿主握手失败（无 `onReady`） | Network 里 `POST /api/ai/v1/chatkit/sessions` 失败或跨域被拦；Console 无异常但 iframe 空 | ① `CHATKIT_FRAME_URL` 是否被 `DOCKER_` 哨兵吞掉（→ 不挂载）；② `/chatkit/index.html` 与 `./assets`、`./pets` 是否随构建产出；③ 宿主算出的绝对 `/api/ai` 地址是否被 iframe 访问到；④ 跨域时 iframe 是否允许被 frame |
| + | 打开 ClawXpert 被弹回 `/explore` | — | 特性位 `FEATURE_XPERT` / `FEATURE_XPERT_CLAWXPERT` 未开，或 `hydrateFeatureContext` 超过 3s 超时；灰度关停只改特性位、不发版 |

- **时序边界**：排障前必须先判定「改的是哪条通道」——HTTP 控制面（活跃）、SSE 流（活跃）、socket.io（代码在、**本域无路由级消费者**）、ChatKit 宿主协议（活跃）。同一现象在不同通道下的根因完全不同。
- **预期结果**：能落到具体文件/函数（`ChatWebsocketServer.message`、`filterLatestMessages`、`startJoinedRunStream`、`injectHostedAssistantChatkitControl`、`createChatkitWorkbenchClientCommandHandler`）而非停留在"网络问题"。
- **错误处理**：socket 断线 `disconnect` 只置 `connected$` false，**UI 侧无自动提示**；token 过期走 `refreshToken()` 并 `refreshTokening` 去重；`ChatKitControl` 命令落到无处理器回 `unsupported`，上下文不匹配回 `stale_context`/`forbidden`；附件超限（>50 MiB / >5 个）在 composer 侧直接拦截、不发请求。
