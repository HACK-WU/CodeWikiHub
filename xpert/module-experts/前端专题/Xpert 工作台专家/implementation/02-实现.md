## 助手管理页链（加载 → 编辑 → 保存/发布）

**① 加载**：进入 `/xpert/x/:id` → 路由 `path: ':id'` 命中 `XpertComponent`（`providers: [XpertService]`）→ `XpertService` 构造时 `injectParams('id')` 作为 `paramId`（`linkedModel({ initialValue: null, compute: () => this.#paramId(), update: (v) => v })`），`paramId$ = toObservable(paramId)` → `paramId$` 走 `distinctUntilChanged → filter(nonBlank) → switchMap(#refresh$ → getXpertTeam(id))` → 回调里 `latestXpert.set(value)`、`xpert.set(value.draft?.team ?? value)`。`getXpertTeam` 来自 `injectGetXpertTeam()`，固定 9 项 relations（`agent`、`agent.copilotModel`、`agents`、`agents.copilotModel`、`executors`、`executors.agent`、`executors.copilotModel`、`copilotModel`、`knowledgebase`）。

**② 编辑**：子页面按各自口径读状态——`XpertBasicComponent`（`implements IsDirty`，表单脏态交给对话框框架）与 `XpertHeaderSwitcherComponent`、`XpertAuthorizationComponent` 读草稿优先的 `XpertService.xpert`；`XpertBasicManageComponent`、`XpertMonitorComponent`、`XpertLogsComponent`、`XpertAPIComponent` 读 `XpertComponent.latestXpert`（需要 `versions`/`draft.savedAt` 等已发布态字段）。

**③ 保存/发布**：本域不直接写实体——基础信息对话框、导出、导入、同步模板等动作完成后统一 `xpertComponent.xpertService.refresh()` 重新取团队，从而拿到后端写回的 `draft`；真正的「草稿保存 / 发布 / 版本」在 Studio 侧（`XpertStudioApiService.saveDraft`、`XpertPublishVersionComponent.publish`）。因此管理页是**读侧 + 动作触发侧**，写侧归 Studio。

**④ 动作清单**（`XpertBasicManageComponent`）：`delete()`（确认 → `XpertAPIService.delete` → 跳回 `/xpert/w/:workspaceId`）、`export(isDraft)`（`XpertExportDslComponent` → 关闭后 `refresh()`）、`deleteExportedTemplate()`、`importDsl()`、`syncFromTemplate()`、`duplicate()`（`XpertBasicDialogComponent` → `duplicate(id, { basic, isDraft: true })` → 跳新 id）。`XpertNewBlankComponent`（`blank/`）承载创建向导，由 switcher 的 `createXpert()` 以 `width: 1360px` 对话框打开，返回 `result.xpert.id` 后按类型分流导航。

章节来源：[xpert.service.ts](file://apps/cloud/src/app/features/xpert/xpert/xpert.service.ts)（关键符号：`XpertService.paramId`、`latestXpert`、`xpert`、`refresh`）、[manage.component.ts](file://apps/cloud/src/app/features/xpert/xpert/manage/manage.component.ts)（关键符号：`XpertBasicManageComponent.duplicate`、`export`）、[switcher.component.ts](file://apps/cloud/src/app/features/xpert/xpert/switcher/switcher.component.ts)（关键符号：`XpertHeaderSwitcherComponent.createXpert`、`openXpert`）

## draft 层：buildEditableXpertDraft 的装配与 Studio 复用

`buildEditableXpertDraft(xpert)` 是**纯函数装配器**：`baseTeam = { ...omit(xpert, 'agents'), id: xpert.id }`；若 `xpert.draft` 存在则 `team = { ...baseTeam, ...(draft.team ?? {}), id: draft.team?.id ?? xpert.id }`、`nodes = normalizeMiddlewareNodes(draft.nodes ?? graph.nodes ?? new ToNodeViewModelHandler(xpert).handle().nodes)`、`connections = draft.connections ?? graph.connections ?? new ToConnectionViewModelHandler(xpert).handle()`；否则用 `graph` 或 ViewModel Handler 兜底；两条分支最后都过 `applyChatTriggerInputParametersToDraft`（把 chat 触发器节点上的参数同步进 `team.agentConfig.parameters`，并以 `channelName(triggerKey)` 分组，删除时按组名剔除）。

**Studio 的复用点**：[xpert-api.service.ts](file://apps/cloud/src/app/features/xpert/studio/domain/xpert-api.service.ts) 从 `../../draft/index` 引入 `buildEditableXpertDraft` 与 `deriveChatTriggerInputParametersFromDraft`，在 `XpertStudioApiService` 中把当前 team 与传入 xpert 都转成可编辑草稿（`buildEditableXpertDraft(this.team())` / `buildEditableXpertDraft(xpert)`），同时从 `../../utils` 引入 `genAgentKey`/`genWorkflowKey`/`injectGetXpertTeam`/`injectGetXpertsByWorkspace`。

**触发器编辑半链**：`readTriggerEditorItemsFromDraft(draft, providers)` 抽出非 `chat` 的 trigger 节点（`{ nodeKey, provider, config }`，provider 缺失时用 `name` 兜底）；`upsertTriggerEditorItemsIntoDraft(draft, items)` 先给新节点找主 Agent 节点（`getPrimaryAgentNodeFromDraft` 按 `team.agent.key` 匹配），找不到就 `throw new Error(XPERT_DRAFT_PRIMARY_AGENT_NODE_MISSING)`；随后把新节点按 `TRIGGER_NODE_HORIZONTAL_OFFSET(280)`/`TRIGGER_NODE_VERTICAL_GAP(120)` 定位，并以 `${node.key}/${primaryAgentNode.key}` 去重补边。消费方是 `@core` 的助手设置上下文（`XpertSettingsContextService.triggerEditorItems`）。

章节来源：[editable-draft.util.ts](file://apps/cloud/src/app/features/xpert/draft/editable-draft.util.ts)（关键符号：`buildEditableXpertDraft`）、[xpert-draft-trigger.util.ts](file://apps/cloud/src/app/features/xpert/draft/xpert-draft-trigger.util.ts)（关键符号：`applyChatTriggerInputParametersToDraft`、`upsertTriggerEditorItemsIntoDraft`、`getPrimaryAgentNodeFromDraft`）、[xpert-api.service.ts](file://apps/cloud/src/app/features/xpert/studio/domain/xpert-api.service.ts)（关键符号：`XpertStudioApiService`）

## published$ 发布广播与订阅方

**发布方**（Studio 侧，本域契约的触发点）：`XpertPublishVersionComponent.publish()` 先判断 `studioService.unsaved() ? saveDraft() : of(true)`，再 `xpertAPI.publish(id, newVersion, { environmentId, releaseNotes, businessAreaId, marketplace? })`；成功后依次 `studioService.refresh()` → **`xpertService.published$.next(result)`** → `close()`。注意 `published$` 由 Studio 注入的 `XpertService` 实例发出，而该实例来自路由树中最靠近的 provider。

**订阅方**（本域）：`KnowledgebasePipelineComponent` 构造时 `xpertService.published$.subscribe({ next: () => this.knowledgebaseComponent.refresh() })`；`KnowledgebaseComponent.refresh()` = `this.#knowledgebase.reload()`（重载知识库资源），因此「在流水线页里发布助手 → 知识库立刻重取」。

**实例边界（必记）**：`XpertService` 声明在组件级 `providers`（`XpertComponent`、`XpertStudioComponent`、`KnowledgebasePipelineComponent` 各一份）。所以 ① 广播不跨标签页、不重放；② 若订阅方与发布方不在同一 provider 作用域内，`published$` 静默失效；③ 需要跨页感知时只能靠路由重进 + `refresh()`/后端查询。

章节来源：[publish.component.ts](file://apps/cloud/src/app/features/xpert/studio/header/publish/publish.component.ts)（关键符号：`XpertPublishVersionComponent.publish`、`xpertService.published$`）、[pipeline.component.ts](file://apps/cloud/src/app/features/xpert/knowledge/knowledgebase/pipeline/pipeline.component.ts)（关键符号：`KnowledgebasePipelineComponent.publishedSub`）、[knowledgebase.component.ts](file://apps/cloud/src/app/features/xpert/knowledge/knowledgebase/knowledgebase.component.ts)（关键符号：`KnowledgebaseComponent.refresh`）

## assistant-shell 宿主层实现

`XpertAssistantShellComponent`：`imports: [RouterModule, XpertSharedAssistantComponent]`、模板 `<router-outlet />` + `<xp-shared-assistant />`、`providers: [XpertAssistantFacade]`。因为它是 `features/xpert/routes.ts` 的根组件，**全 `/xpert/**` 共用一个门面**，Studio 才能以可选注入消费到它。

`XpertAssistantFacade` 的实现要点：① `assistantCode = signal(AssistantCode.XPERT_SHARED)`，`runtime = injectAssistantChatkitRuntime({ displayMode: 'pet', pet: SHARED_ASSISTANT_PET, titleKey: 'XP.Xpert.Assistant', onEffect })`；② 路由态用 `#routeState = toSignal(router.events 的 NavigationEnd + startWith(null) → readRouteState())`，`readRouteState()` 用两条正则（`^/xpert/w/([^/]+)`、`^/xpert/x/([^/]+)/agents(?:/|$)`）解析出 workspaceId/xpertId；③ `workspaceId` 三级回退：路由 workspace → 助手缓存（`watchXpertWorkspace` 用 `getTeam(xpertId)` 只取 `workspaceId`，且命中缓存即 `EMPTY`）→ 当前选中工作区；④ `requestContext = buildRequestContext(context, studioRuntimeContext, workbenchRequestContexts)`，把 `env.workspaceId`/`env.xpertId` 与 `targetXpertId`/`unsaved`/`baseDraftHash` 拼进助手请求；⑤ `setStudioContext()` 做三字段幂等（`targetXpertId`/`baseDraftHash`/`unsaved` 全等则不动），`clearStudioContext()` 空检查后置空；⑥ `handleEffect()` 优先处理知识库引用（FAQ/Wiki 直接 `router.navigate(['/xpert/knowledges', ...])`，其余经 `ViewHostEventBus.publish`），再按 `event.name` 分发 `navigate_to_studio` / `refresh_studio` / `refresh_prompt_workflows` / `refresh_workspace_skills`（后者先导航再 `emit*Refresh`，`nonce: Date.now()` 保证同值也能触发）。

`XpertSharedAssistantComponent` 只做渲染与命令注册：`@if (status() === 'ready')` 渲染 `xpert-chatkit`（`[control]="control()"`），构造期注册 5 个客户端命令并在 `destroyRef.onDestroy` 全部注销。

章节来源：[shell.component.ts](file://apps/cloud/src/app/features/xpert/assistant-shell/shell.component.ts)（关键符号：`XpertAssistantShellComponent`）、[assistant.facade.ts](file://apps/cloud/src/app/features/xpert/assistant-shell/assistant.facade.ts)（关键符号：`XpertAssistantFacade.readRouteState`、`watchXpertWorkspace`、`setStudioContext`、`handleEffect`）、[shared-assistant.component.ts](file://apps/cloud/src/app/features/xpert/assistant-shell/shared-assistant.component.ts)（关键符号：`XpertSharedAssistantComponent.control`）

## 知识库与工作区两个子域的接入点

**知识库**：入口 `/xpert/knowledges`（`KnowledgebaseHomeComponent`，权限 `KNOWLEDGEBASE_EDIT`，无权限 `redirectTo: '/settings'`）；`:id` 惰性加载 `knowledgebase/routing.ts`，其子路由里 `xpert/:id → KnowledgebasePipelineComponent`、`xpert → KnowledgebasePipelinesComponent` 是关键接入点（前者即「画布复用 + `published$` 订阅」）；该 routing 亦被 `features/setting/knowledgebase/routing.ts` 复用，`knowledge/` 的组件因此有两个宿主（`/xpert/knowledges/*` 与 `/settings/knowledgebase/*`）。详细能力（文档/切片/FAQ/Wiki/图谱/解析配置）见知识库子专家。

**工作区**：入口 `/xpert/w`（`redirectToSelectedWorkspace` 会按选中工作区改写 URL，并在 `section` 查询参数下分流到 `clawxpert-skills`/`clawxpert-knowledges`/`clawxpert-connectors`/`files`/`settings`）；`/xpert/w/:id` 下 14 个子路由由 `XpertWorkspaceHomeComponent` 承载，其中 `xperts`（助手列表）、`knowledges`、`connectors`、`skills`、`prompt-workflows`（`canDeactivate: confirmLeave`）、`database`、`builtin`/`mcp`/`custom`（工具）各有一号组件。两子域与本域的耦合点是：路由文件、`utils.ts` 注入工厂与 `XpertService`（仅流水线页用到），其余基本解耦。

章节来源：[routing.ts](file://apps/cloud/src/app/features/xpert/knowledge/knowledgebase/routing.ts)（关键符号：`KnowledgebasePipelineComponent`、`KnowledgebasePipelinesComponent`）、[routes.ts](file://apps/cloud/src/app/features/xpert/workspace/routes.ts)（关键符号：`redirectToSelectedWorkspace`）、[home.component.ts](file://apps/cloud/src/app/features/xpert/knowledge/home.component.ts)（关键符号：`KnowledgebaseHomeComponent`）

## 与 Studio 的装配（门面可选注入、画布复用）

**门面可选注入**：`XpertStudioComponent` 里 `readonly #assistantFacade = inject(XpertAssistantFacade, { optional: true })`；构造期注册三个 `effect`：① 把 `injectParams('id')` 写入 `xpertService.paramId.set(...)`（复用方无需自己接线）；② 若 `assistantFacade.xpertId() === 当前 id`，则 `setStudioContext({ targetXpertId, baseDraftHash: calculateHash(JSON.stringify(pristineDraft)), unsaved: apiService.unsaved() })`，否则 `clearStudioContext()`；③ 监听 `assistantFacade.studioRefresh()` 的 `nonce` 事件，匹配 id 后 `apiService.refresh()`。销毁时 `clearStudioContext()` + `subscriptions$.unsubscribe()`。可选注入的语义：Studio 脱离助手壳也能工作，但「助手 → Studio」的上下文与刷新通道失效（静默）。

**画布复用**：`KnowledgebasePipelineComponent` 只写 `imports: [RouterModule, XpertStudioComponent]` + `providers: [XpertService]`，并向内 `inject(KnowledgebaseComponent)` 以调用 `refresh()`；画布自身无 `@Input`/`@Output`，靠 `injectParams('id')` 与 `XpertService` 契约工作，因此复用成本极低、耦合点也就固定在这两处。

章节来源：[studio.component.ts](file://apps/cloud/src/app/features/xpert/studio/studio.component.ts)（关键符号：`XpertStudioComponent.#assistantFacade`、`setStudioContext`、`studioRefresh`）、[pipeline.component.ts](file://apps/cloud/src/app/features/xpert/knowledge/knowledgebase/pipeline/pipeline.component.ts)（关键符号：`KnowledgebasePipelineComponent`）

## 热点路径

1. **打开助手**：`/xpert/x/:id` → `XpertComponent` → `XpertService` 构造 → `getTeam`(9 relations) → `latestXpert`/`xpert` → 子页面渲染；`/agents` 再由 Studio 接管画布（并把 id 写回 `XpertService.paramId`）。
2. **共享助手请求**：任意 `/xpert/**` 页面 → `XpertAssistantFacade.requestContext` 合成（`env.workspaceId`/`env.xpertId`/`targetXpertId`/`unsaved`）→ ChatKit runtime 发送；工作区 id 缺失时触发一次 `getTeam(xpertId)` 补缓存。
3. **DSL 导入**（写路径最重）：`importDsl()` → `uploadYamlFile<TImportedXpertDsl>` → 需要时 `getSandboxProviders()` → `createOverwriteDraftFromDsl(xpert, dsl, sandboxProviders)` + `groupImportedDslMemories` → `toastr.confirm` → `saveDraft(id, draft)` → 有记忆则 `clearMemory` + 逐类型 `bulkCreateMemories` → `refresh()` → 提示「发布后才生效」。
4. **发布后刷新**：Studio `publish()` → `published$.next(result)` → 流水线页 `publishedSub` → `knowledgebaseComponent.refresh()`。
5. **工具集维护**：`/xpert/tool/:id` → `getById(relations: ['tools','createdBy'])` → `tools`/`mcpServer`/`isDirty` → 测试对话框 `XpertToolTestDialogComponent` → `XpertToolsetToolTestComponent`。
6. **助手切换**：`XpertHeaderSwitcherComponent.loadXperts()` → `rxResource` 拉 `getAllByWorkspace(id, { where: { type: Agent, latest: true }, relations: ['knowledgebase'] })` → 按 `type` 三分支导航。

## 技术债与 hack

1. **订阅未随组件销毁退订**：[pipeline.component.ts](file://apps/cloud/src/app/features/xpert/knowledge/knowledgebase/pipeline/pipeline.component.ts) 的 `publishedSub` 只在字段初始化时 `subscribe`，组件无 `OnDestroy` 注销；[xpert.service.ts](file://apps/cloud/src/app/features/xpert/xpert/xpert.service.ts) 的 `xpertSub` 同样在构造器内订阅且无 `takeUntilDestroyed`（[推测] 依赖组件级 provider 随视图销毁被整体回收，但订阅对象本身仍是引用）。
2. **`@core` 反向依赖 features**：[xpert-settings-context.service.ts](file://apps/cloud/src/app/@core/services/xpert-settings-context.service.ts) 从 `../../features/xpert/draft` 引入纯函数与常量。方向倒置，一旦 `draft/` 再引 `@core` 即成环；建议把 `draft/` 纯函数下沉到 `packages/contracts` 或 `@shared`。[推测] 现状可用是因为 `draft/index.ts` 只导出纯函数与常量。
3. **草稿并发无冲突提示**：管理页（basic 对话框等）与 Studio 共享同一后端 draft，前端仅靠 `refresh()` 重取；同一助手两处编辑时后写覆盖先写，无 `savedAt` 比对与提示（ki 数据流已登记「依赖后端 savedAt，前端无冲突提示」）。
4. **DSL 导入非事务**：`saveDraft` 成功后若记忆替换失败，仅 toastr warning（`XP.Xpert.ImportMemoryIncomplete`），留下「草稿已换、记忆半成品」的中间态；且 `importDsl` 会清空现有记忆（`clearMemory`）后才写新记忆。
5. **死代码/占位**：`XpertToolTestComponent.updateTool(id, value)` 是空实现；`XpertComponent.showExtensionSidebar` 被固定为 `signal(false)`（原 computed 被注释）；`basic.component.ts` 里 `injectGetXpertTeam()` 的注入被注释；`develop/` 目录 4 个文件仍在，但 `xpert/routes.ts` 中 `develop` 路由被注释、`copilot` 重定向到 `agents`；模块根 `workspace-home.service.ts` 与 `templates/templates.component.ts` 为空壳。
6. **广播的可见性边界**：`published$` 不跨标签页、不重放（见上节），且实例作用域由 provider 决定——[推测] 若将来把 `XpertService` 提升到路由级 `providers`，`published$` 的语义会变（订阅方与发布方可能互换实例），需同步回归。
7. **测试分布极不均**（实测 spec 93：knowledge 62 / workspace 14 / xpert 13 / tools 2 / draft 1 / assistant-shell 1）：`tools/builtin`（凭据、授权、参数三类面）与 `draft` 的触发器工具仅有 1~2 个测试，`manage`/`monitor`/`memory`/`authorization` 无 spec；ki 记录 2026-10-15 实测 92 spec = 36 PASS / 55 FAIL（53 环境级缺依赖 + 2 真实断言），改动前须按 `test/known-failures.md` 复核。
8. **可选注入的静默降级**：Studio 用 `{ optional: true }` 注入门面，门面缺失时不报错、也不提示，仅上下文/刷新能力消失；[推测] 这就是「Studio 可独立打开」的代价，需要在宿主层保证 provider 存在。

## 设计维度

1. **宿主形态维度**（四种，决定注入什么）：① 管理页独占宿主（`XpertComponent` 提供 `XpertService`）；② 共享壳 + pet 助手（`XpertAssistantShellComponent` 提供门面，覆盖全 `/xpert/**`）；③ 子域嵌入画布（流水线页提供 `XpertService` + 复用 `XpertStudioComponent`）；④ 独立路由配置页（`/xpert/tool/:id` 只注入 `injectParams('id')` 与服务，无助手、无门面）。
2. **状态态维度**（三态并存，读谁要明确）：已发布实体（`latestXpert`，含 `versions`/`exportedTemplate`）、草稿（`xpert` = `draft?.team ?? value`，编辑器与 switcher 用）、本地表单脏态（`IsDirty` / `isDirty` computed，对话框阻止误关闭）。
3. **作用域维度**（四级）：`tenant`（`isTenantXpert = !organizationId`）→ `organization`（授权面板的组织维度）→ `workspace`（`/xpert/w/:id`、`getAllByWorkspace`）→ `xpert`（`paramId`），跨级取数一律经 `@core` 服务而非本域缓存。
4. **耦合强度维度**：强（`XpertService`/`utils.ts`/`draft` 三件套，本域与 Studio 双向）· 中（路由与惰性加载出口）· 弱（`knowledge`/`workspace` 子域与本域仅共享工具与路由）。

## 结论

- **本域的写路径只有一处真源**：草稿（后端 `draft` + 前端 `buildEditableXpertDraft`）；管理页负责触发与重取（`refresh()`），Studio 负责保存与发布（`published$` 广播）。任何「管理页直接改实体」的新代码都会破坏这条不变量。
- **五条链要一起回归**：加载（9 relations）→ 投影（草稿优先）→ 动作（DSL/复制/删除/模板同步）→ 工具集配置（create/builtin/凭据/test）→ 发布广播（pipeline 刷新）；外加门面可选注入与画布复用两处跨域装配。
- **改动优先级**：先看 `utils.ts` 与 `draft/`，再看 `XpertService` 三信号，最后看页面——因为它们被本域、Studio、助手设置三方共同消费。
- **技术债集中在三处**：未退订的订阅、`@core` → `features/xpert/draft` 的反向依赖、以及 tools/draft 面的测试空白；建议按「技术债与 hack」逐条排期。
- 接口清单、数据流与测试口径分别见同目录 `implementation/03-数据流转.md`、`05-接口.md`、`06-测试.md`。
