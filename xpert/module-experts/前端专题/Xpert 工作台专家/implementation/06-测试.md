## 1. 运行方式与实测命令

单文件（绕 Nx 项目图，最快）：

```bash
cd /root/xpert && node node_modules/jest/bin/jest.js --config apps/cloud/jest.config.ts \
  --runTestsByPath apps/cloud/src/app/features/xpert/xpert/xpert.component.spec.ts
```

Nx 方式（走 `apps/cloud/project.json` 的 `test` target，可带缓存控制）：

```bash
cd /root/xpert && corepack pnpm nx test cloud --skip-nx-cache \
  --testPathPattern="features/xpert/(xpert|knowledge|workspace|tools|draft|assistant-shell)" --runInBand
```

- `moduleNameMapper` 已把 `^@xpert-ai/contracts$` 指到 `packages/contracts/src/index.ts`（源码直连，无需先 `nx build contracts`），并把 `environment` 指向 `apps/cloud/src/environments/environment.jest.ts`。
- `transformIgnorePatterns` 对 `@xpert-ai/chatkit-types` 依赖树与 `lodash-es`/`nanoid`/`marked`/`echarts`/`zrender` 做 ESM 转译白名单。

## 3. 断言与 mock 风格

1. **纯函数/工具类**（`draft/xpert-draft-trigger.util.spec.ts`、`manage/import-dsl.util.spec.ts`、`workspace/database/database.component.spec.ts`）：`describe/it` + 结构化 fixture 工厂（`createDraft()`、`createCurrentXpert()`），断言对象深度相等或 `toEqual`，**不需要 TestBed**。
2. **源码文本断言**（`xpert/xpert.component.spec.ts`、`knowledge/new/new.component.*.spec.ts`、`knowledgebase/test/test.component.spec.ts`、`documents/document-progress-column.spec.ts` 等）：`readFileSync` 读 `.html`/`.ts` 字符串，用 `toContain` / `not.toContain` 锁定模板片段与键名。**这类 spec 不依赖 Angular 运行时，是环境最稳的一批**，但断言与模板字符串**逐字**耦合。
3. **TestBed 组件**（`tools/create`、`workspace/knowledges`、`workspace/prompt-workflows`、`knowledge/processing/*`）：`TestBed.configureTestingModule` + `{ provide: Service, useValue: {…jest.fn()} }`；用 `overrideComponent(..., { set: { imports: [Stub], template: '<stub/>' } })` 替换重组件（`tools/create` 用 `forwardRef` + `XpertConfigureToolComponent` 桩）；对话框用 `TestBed.inject(ApplicationRef).tick()` + `document.querySelector` 驱动。
4. **模块 mock**：`jest.mock('../home/home.component', () => ({ XpertWorkspaceHomeComponent: class {} }))` 一类空类替换；重资源库用 `jest.mock('@milkdown/crepe'|'mermaid'|'@xterm/xterm', () => …)`——**均未传 `{ virtual: true }`**，因此仍要求模块真实可解析。
5. **异步流**：`Subject/of/throwError` 手写响应流，`await component.edit(...)`（Promise 化交互）+ `fixture.whenStable()`；错误路径断言 `toastr.error` 被调用、对话框**未**打开。

章节来源：[create.component.spec.ts](file://apps/cloud/src/app/features/xpert/tools/create/create.component.spec.ts)（关键符号：`ConfigureStub`、`XpertStudioCreateToolComponent.createTool`）、[new.component.layout.spec.ts](file://apps/cloud/src/app/features/xpert/knowledge/new/new.component.layout.spec.ts)（关键符号：`readFileSync`、`new.component.ts`）

## 5. 实测结论：92 = 36 PASS / 55 FAIL

**口径**：归档记录 `92 spec = 36 PASS / 55 FAIL`，其中 **53 个环境级缺依赖**、**2 个真实断言失败**（2026-10-15 基线实测；本仓库重建后未复跑）。55 + 36 = 91，与 92 的差额 1 项（skipped/未收集）**待复跑确认**。

### 5.1 环境级缺依赖（53）

- **可静态确证：`@milkdown/crepe`**。该包只在 `apps/cloud/package.json` 声明（`^7.22.1`），本域 **12 个 spec** 显式 `jest.mock('@milkdown/crepe', …)` 且**未带 `{ virtual: true }`** → Jest 注册 mock 时仍需真实解析模块路径，落盘缺失即 `Cannot find module '@milkdown/crepe'`，**套件在加载阶段失败、用例体不执行**。受影响目录：`knowledge/knowledgebase/{wiki,configuration,test,documents/chunk}`、`knowledge/new`（共 10 个）+ `workspace/prompt-workflows`（2 个）。
- **同类机制（同一失败形态）**：`mermaid`、`@xterm/xterm` 在 `knowledge` 的 7 个 spec 中与 milkdown 成组 mock（同样无 `virtual: true`），任一未落盘即整组失败。
- **其余约 41 个**按 ki 归档口径计入「环境级缺依赖」，**逐条模块名待复跑确认**（首要排查 `@xpert-ai/*` 工作区包与 Angular/CDK 依赖树是否完整落盘）。
- **本机现状**：`/root/xpert/node_modules` **不存在**（`ENOENT`，无任何依赖落盘）——在 `corepack pnpm install` 之前，本域任何 spec 都会在收集阶段失败，因此**当前无法复核 55 的明细**。

### 5.2 真实断言失败（2）

- **第 1 条（已确证）**：`apps/cloud/src/app/features/xpert/xpert/xpert.component.spec.ts`，用例 `shows the published version next to the xpert type badge only when a version exists`。断言 `expect(typeBadgeRow).toContain('{{xpert()?.type}}')`，而模板 `xpert.component.html` 实际写法为 `{{ xpert()?.type }}`（插值内含空格）→ 字符串不匹配即失败。该 spec 只 `readFileSync` 模板、不加载 Angular 或第三方模块，属**不依赖环境**的真实断言失败。修复二选一：断言改为 `{{ xpert()?.type }}`，或去掉模板插值内空格（同用例另两条断言 `@if (xpert()?.version)`、`v{{ xpert()?.version }}` 与模板一致）。
- **第 2 条（待复跑确认）**：本机静态核对过 4 个**无需 TestBed**的高风险候选——`knowledge/new/new.component.layout.spec.ts`、`knowledge/new/new.component.faq-type.spec.ts`、`knowledge/knowledgebase/documents/document-progress-column.spec.ts`、`xpert/blank/blank-plugin-resource-error.util.spec.ts`——结论是**倾向 PASS**：`new.component.ts` 只有 `key: 'vector-storage'`/`key: 'retrieval'`（不含 `key: 'vector'`/`key: 'graph'`，`FAQ_SECTION_KEYS` 与断言逐字一致）；`DocumentProgressColumnWidth.fit/update/remove` 的 `Math.max` 语义与全部 5 条期望一致；5 个 i18n 语言文件均含 `TemplatePluginSkills*` 四键。故第 2 条真实失败**更可能落在需要 TestBed 的组件用例**（如 `knowledge/processing/*`、`workspace/prompt-workflows/*`、`tools/create`），具体 spec 与首条失败断言**以复跑输出为准**。

## 7. 缺口与可执行性结论

**缺口**

1. **工具授权/凭据面 0 覆盖**：`tools/api-tool/api-tool.component.ts`、`tools/builtin/authorize/*`（含 `credential.component.ts`）、`builtin/parameters`、`mcp/*`、`openapi/configure`、`odata/configure` 均无 spec（ki 决策记录已标注「工具授权独立成配置面；当前测试覆盖为 0——已知缺口」）。
2. **管理页外围无覆盖**：`xpert/api`、`xpert/app`、`xpert/authorization`、`xpert/memory/*`（store/files/bulk-import）、`xpert/develop/api-key` 无 spec。
3. **跨域契约无覆盖**：`XpertService.paramId/latestXpert/published$` 的消费约定、`utils.ts` 注入工厂（9 项 relations）由 Studio/知识库侧间接覆盖，本域无直接 spec。
4. **文本断言脆弱**：模板字符串断言的 spec 遇任何格式调整即失败（§5.2 第 1 条即此类），建议改为语义断言或快照。
5. **知识库子域**：多数用例锁 UI 片段，**摄取流水线/检索参数**的真实行为无集成级覆盖。

**可执行性结论**：✅ **具备**——`apps/cloud/jest.config.ts` 的 transform、`moduleNameMapper`（contracts 源码直连、environment 替换）、`setupFilesAfterEach` 与 jsdom 垫片齐备，测试全部离线化（HTTP 层用 `useValue` 假服务 / `jest.mock` 空类替换）。**唯一前置是依赖落盘**（`corepack pnpm install`）；本机现状为 `node_modules` 缺失，故 §5 的 PASS/FAIL 计数与 §5.2 第 2 条沿用 ki 归档并标「待复跑确认」。
