### D1 草稿优先投影（`xpert = value.draft?.team ?? value`）
- **分类**：其他（数据一致性——ki 原记录分类为「数据一致性」）
- **动机**：ki 明写背景约束——**编辑态与运行态隔离**；管理页与 Studio 都展示草稿形态（与 Studio draft-only saves 一致），已发布版本经 `versions`/`latestXpert` 另行表达。
- **决策**：订阅回调 `this.latestXpert.set(value)` + `this.xpert.set(value.draft?.team ?? value)`——存在草稿时管理页展示草稿形态。
- **约束**：投影只做一层回落、不深合并；`latestXpert` 必须保留完整响应（含 `draft`/`graph`/`version`）；写后须显式 `refresh()` 才更新；`XpertBasicComponent` 中 Agent 编辑草稿层、其它类型编辑已发布层（代码实证）。
- **被否决方案**：无（ki 未记录候选方案，本次亦未找到被否决痕迹）。
- **重新评估触发条件**：ki 原文——「需要管理页固定展示已发布版 / 跨标签页发布感知时」。
- **关联代码**：`xpert.service.ts` 订阅回调；`basic.component.ts` 的 `draft`/`team` computed 与 `saveDraft`。
- **证据来源**：**明写证据**——ki 决策记录（决策 1）+ 源码逐句核对。

### D3 团队读取固化 9 项 relations 的注入工厂
- **分类**：接口契约
- **动机（避坑，[推测]）**：ki——多页面共享同一聚合形态；避免各页自拼 relations 造成投影口径漂移（管理页、Studio、门面都依赖同一形态）。
- **决策**：`injectGetXpertTeam()` 固定 9 项 relations（`agent`、`agent.copilotModel`、`agents`、`agents.copilotModel`、`executors`、`executors.agent`、`executors.copilotModel`、`copilotModel`、`knowledgebase`），成为全域唯一的团队聚合读取口径；`XpertService.getXpertTeam` 与 Studio 共用。
- **约束**：固定数组、无入参可调；不含 `toolsets`/`userGroups`/`knowledgebases`（各页自行补拉）；增删任一项都会改变下游画布/面板拿到的聚合形态。
- **被否决方案**：无（ki 未记录「按需 relations」方案的评审痕迹）。
- **重新评估触发条件**：ki 原文——「单请求聚合过大导致加载慢时拆按需 relations」。
- **关联代码**：`injectGetXpertTeam`、`XpertService.getXpertTeam`、Studio `xpert-api.service` 的引入点。
- **证据来源**：ki [推测] 条目（保留标注）；代码实证见 [utils.ts](file://apps/cloud/src/app/features/xpert/utils.ts)。

### D7 `buildEditableXpertDraft` 是 Studio draft 的唯一源头（桥 1）
- **分类**：接口契约
- **动机（避坑）**：Studio 画布需要「可编辑草稿」的初始化来源；「草稿覆盖已发布」的合并规则同时固化在契约层（`omitXpertRelations`/`figureOutXpert`），前端与后端执行侧共享同一回落顺序。
- **决策**：`buildEditableXpertDraft(xpert)` 作为唯一装配器：`baseTeam = { ...omit(xpert,'agents'), id: xpert.id }`；有草稿时覆盖 `team`（`id` 回落 `draft.team?.id ?? xpert.id`）、`nodes`（三级回落 + `normalizeMiddlewareNodes`）、`connections`（二级回落）；两条分支末尾必经 `applyChatTriggerInputParametersToDraft`。
- **约束**：输出结构被 Studio（画布初始化）、设置域（触发器编辑）、对话域（触发器草稿）共同消费；改结构=跨域回归；本域、Studio、`@core` 三方共用同一导出。
- **被否决方案**：无（ki 未记录「Studio 自建装配器」方案的评审痕迹）。
- **重新评估触发条件**：需要多草稿/版本并行编辑时；或将 draft 装配下沉至 `packages/contracts` 时（现 `@core` 反向依赖 features 的方向问题见 02-实现技术债）。
- **关联代码**：`editable-draft.util.ts`；Studio `xpert-api.service.ts` 的引入点；`xpert.utils.ts` 的 `omitXpertRelations`/`resolveRuntimeXpert`。

### D8 管理页=读侧+动作触发侧，完整写侧归 Studio
- **分类**：架构设计
- **动机（避坑）**：管理页与 Studio 共享同一后端 draft；若管理页扩散出完整的草稿装配/保存/发布路径，会形成双写源与形态分叉。
- **决策**：管理页承担**读侧 + 动作触发**——删除/复制/导出 DSL/模板同步等动作以「对话框 `closed` + `switchMap` 调接口 + toast + `xpertService.refresh()`」同一节奏收尾；完整草稿的装配（`buildEditableXpertDraft`）、保存（`saveDraft`）与发布（`publish`）在 Studio。基础信息是受控例外：Agent 走 `upadteDraft` 局部更新草稿、其它类型走 `update`。
- **约束**：管理页任何「直接改实体」的新代码都会破坏「草稿是唯一写侧真源」这一不变量；`refresh()` 是唯一收口。
- **被否决方案**：无（未找到把画布/版本管理并入管理页的评审痕迹）。
- **重新评估触发条件**：管理页需要直接编辑画布或版本时（职责边界变化）。
- **关联代码**：`manage.component.ts`（`delete`/`export`/`importDsl`/`syncFromTemplate`/`duplicate`）；`basic.component.ts` 的 `saveDraft` 两分支。

### D9 工具集面与后端工具注册一一对应
- **分类**：接口契约
- **动机（避坑）**：自定义（openapi/odata）、内置（builtin provider）、MCP 三类工具集在 UI 上形态各异，但必须映射到同一后端注册模型，否则「启用/禁用/凭据」语义会分叉。
- **决策**：前端工具集面以 `XpertToolsetService` 对齐后端注册表——`/providers`（目录）、`builtin-provider/:provider/tools` 与 `.../credentials-schema`（内置工具与凭据 schema）、`.../instance`（实例化）、`/:id/credentials`、`provider/openapi|odata/*`（schema 解析）、`POST /api/xpert-tool/test`（调用测试）；启用语义由契约层 `isToolEnabled`（`disabled → enabled → disableToolDefault` 三级）与 `getEnabledTools`（按 `toolPositions` 排序）在前后端共享；写入侧用「按 `name` 合并 + 缺失标 `deletedAt`」表达删除。
- **约束**：仅 `toolsDirty()` 才回写 `tools`；测试接口 `responseType: 'text'` 且错误经 `normalizeToolTestError` 还原；工具集/工具的运行时消费方是后端执行引擎（跨端契约见 ki 登记）。
- **被否决方案**：无（未找到「按工具来源各写一套模型」方案的评审痕迹）。
- **重新评估触发条件**：后端 provider 注册模型/凭据 schema 变更时；或需要工具级批量同步（跨工作区复制工具集）时。

### D10 前端零持久化 + 写后回源（含 draft 无冲突提示）
- **分类**：其他（数据一致性）
- **动机（避坑）**：draft 由管理页与 Studio 双写、发布态由后端维护；前端若自行缓存或比对本，会与后端形成双源漂移。
- **决策**：前端**无 localStorage/IndexedDB 持久化**；所有写操作后统一 `refresh()` 回源；并发编辑依赖后端 `savedAt`（前端不做比对与提示）。
- **约束**：刷新即重拉；`testResult`/`toolsDirty`/`selectedToolIds` 等纯内存态路由切换即丢；`XpertService.#draft` 是声明未用的死槽位（按它做缓存前需先补写入链）。
- **被否决方案**：无（ki 未记录「前端本地草稿缓存」方案的评审痕迹）。
- **重新评估触发条件**：需要离线/草稿保护（未保存提示）时；或后端提供乐观并发控制（ETag/`savedAt` 比对）时。

## 决策间关系与重估优先级
- **数据一致性轴（D1 + D2 + D10）**：草稿优先投影、内存发布广播、零持久化三者互为前提——只要引入前端草稿缓存（D10 重估），D1 的投影口径与 D2 的刷新时机都要重算。
- **跨域轴（D4 + D5 + D7）**：三条桥同源于「本域供给 Studio」——draft 源头（D7）、可选门面（D5）、画布复用（D4）；任一处契约变化必须同时回归 Studio 与本域管理页。
- **契约轴（D3 + D9）**：聚合读取（9 relations）与工具注册面是两条独立契约线；D3 拆按需 relations 或 D9 改 provider 模型都属于跨端回归。
- **边界轴（D6 + D8 + D11）**：授权面独立、写侧归 Studio、子域以路由为界，共同构成「本域不越界」的职责约束。
