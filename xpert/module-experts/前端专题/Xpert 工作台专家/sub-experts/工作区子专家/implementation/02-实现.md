## 工作区列表与详情

**列表**：`XpertWorkspaceHomeComponent.workspaces` 由 `workspaceService.getAllMy({ order: { updatedAt: DESC } }, { purpose: 'authoring' })` 取，映射为 `items` 并 `tap` 关掉 `loading`；模板菜单渲染 `filteredWorkspaces()`（`debouncedSignal(searchWorkspace, 300)` + `name.toLowerCase().includes`）。列表项显示 owner 标记（`me().id === item.ownerId`），点击 `selectWorkspace(ws)` 同时做两件事：`router.navigate(['/xpert/w/', ws.id])` 与 `store.setWorkspace(ws)`——**URL 与 Store 双写**，因为子页面读 Store，守卫读 Store/Persist。

**详情（当前工作区）**：`workspace` 是 `computed(() => workspaces()?.find(_ => _.id === selectedWorkspace()?.id))`，并用自定义 `equal: (a,b) => a?.id === b?.id` 抑制同 id 的重复变更。因此「详情」不是一次单独请求，而是从列表里挑；只有设置对话框才单独 `getOneById(id, { relations: ['owner','members'] })`。

**默认工作区**：`loadDefaultWorkspace()` 用版本号 `#defaultWorkspaceQueryVersion` 丢弃过期响应（`getMyDefault({ purpose: 'authoring' })` 失败即置 `null`）；`setDefaultWorkspace(event, ws)` 先 `stopPropagation`（避免冒泡触发行点击切换），再用 `settingDefaultWorkspaceId` 做「同项进行中」短路，成功后只更新 `defaultWorkspace` 信号并 toast，**不切换选中工作区**。

**概览页**：`XpertWorkspaceSettingsPageComponent` 从宿主注入 `workspace`，用 `forkJoin` 并发 5 个计数（`assistants`(`type: agent, latest: true`)、`skills`、`environments`(`where:{workspaceId}`)、`mcpTools`(`category: mcp`)、`knowledgebases`），每项 `take(1) + catchError(() => of(null))` 单点降级，模板把计数值或 `—` 呈现；`workspaceStatus` 把 `active/deprecated/archived` 映射为中文文案。该页**未被任何路由引用**（见技术债）。

## 设置与可见性变更

**开箱动作**：`openSettings()` 先 `if (!this.canManageWorkspace()) return`，再以 `data: { id: selectedWorkspace()?.id }` 打开 `XpertWorkspaceSettingsComponent`；对话框关闭事件为 `'deleted' | 'archived'` 时，壳层执行 `workspaceService.refresh()` + `router.navigate(['/xpert/w'])`（回到工作区选择面）。

**对话框内部**：`getOneById(id, { relations: ['owner','members'] })` → `derivedAsync`；`selectedMenus` 是 `model<Array<'general'|'members'|'apiKeys'>>(['general'])`，`menu = computed(() => selectedMenus()[0])`；三页签分别是 general / members / `XpertDevelopApiKeyComponent`（`bindingType: ApiKeyBindingType.WORKSPACE`、`bindingId: workspaceId()`）。`workspaceRevision` 信号作为重新取数的开关：`onUpdated(workspace)` 若 `capabilities?.canRead === false` 直接 `close('updated')`，否则 `revision + 1` 重取详情（**能力位驱动对话框自关闭**，是能力位在子域内少见的直接消费点）。

**改名 + 可见性**（`XpertWorkspaceSettingsGeneralComponent`）：`update()` 三重短路（无 id / 无 `canManage` / `loading()`）；仅在 `name()` 变化时 `update(id, { name })`；可见性先由 `shared` 开关 + `isTenantWorkspace()`（`!workspace.organizationId`）推导为 `tenant-shared` / `organization-shared` / `private`，且只在 `canEditVisibility()`（= 有工作区且 `canManage`）且与 `currentVisibility()` 不同时调 `updateVisibility(id, visibility)`；成功后 `workspaceService.refresh()` + `updated.emit(updatedWorkspace)` + toast。失败路径只 toast，**不改 `savedVisibility`**（保证开关回弹到服务端真值）。

**危险区**：`archive()` / `delete()` 都走 `injectConfirmDelete`（要求输入工作区名），分别调 `workspaceService.archive(id)` / `delete(id)`，成功后 `archived` / `deleted` 事件冒泡到壳层收尾。

## 成员管理（含与 UserGroup 的关系）

**取数**：`toObservable(workspaceId).pipe(filter(nonNullable), switchMap(id => workspaceService.getMembers(id)))` 写入 `members: signal<IUser[]>`；`allMembers = computed(() => owner ? [owner, ...members] : members)`，owner 只用于**展示与排除**，不在可删集合里。

**写入是整体覆盖**：`updateMembers(users)` 先本地 `uniqBy([...members, ...users], 'id')`，再 `updateMembers(workspaceId, members().map(u => u.id))`，即 `PUT /api/xpert-workspace/:id/members`（body 为 id 数组）；`removeMember(user)` 同构（本地过滤 + 覆盖提交）。这与后端「成员是整体覆盖语义、无角色列」完全一致，**前端不提供角色/权限列**。

**新增入口**：`openAddUser()` 打开共享 `UserRoleSelectComponent`，`data: { loadOnEmptySearch: true, excludeUserIds: allMembers().map(u => u.id) }`，`closed` 用 `switchMap(result => result ? updateMembers(result.users) : EMPTY)`——空结果不提交。

**与 UserGroup 的关系（后端为准）**：本子域**零 UserGroup 呈现**（`workspace/` 全目录对 `UserGroup` 无任何引用）。后端口径是「UserGroup 只补 `canRun`」，且 `hasPublishedXpertRunAccess` 走原生 SQL 读 `xpert_to_user_group`；因此通过用户组获得运行权的用户**不会**出现在成员列表里，其权限也不经本页可写。结论：成员页**只表达成员资格**，不能用来推断运行权，更不能把「非成员」呈现为「无权限」。

## 文件浏览、上传与下载

**authoring 入口（本子域唯一文件面）**：`XpertWorkspaceFilesComponent` 只做「把 7 个回调绑到服务」——`loadFiles` / `loadFile` / `saveFile` / `saveBinaryFile` / `uploadFile` / `deleteFile` / `downloadFile` 分别对接 `XpertAPIService.getWorkspaceFiles|getWorkspaceFile|saveWorkspaceFile|saveWorkspaceBinaryFile|uploadWorkspaceFileToFolder|deleteWorkspaceFile|downloadWorkspaceFile`，实际路径 `/api/xpert/:id/workspace/*`（后端全部转 `forAuthoring`）。`downloadFile` 先 `firstValueFrom` 取 blob，再按 `item?.hasChildren` 决定文件名加 `.zip`。

**`xpertId` 来源与空态**：`xpertId` 由 `merge(of(null), assistantBindingService.changes$.filter(e => e.code === CLAWXPERT && e.scope === USER)).pipe(switchMap(() => assistantBindingService.get(CLAWXPERT, USER)), map(b => b?.assistantId?.trim() || null), catchError(() => of(null)), startWith(null))` 得到；模板 `@if (xpertId())` 渲染 `<xp-file-workbench layout="library" ...>`，否则渲染「Configure Claw Xpert first.」空态；回调侧 `requireXpertId()` 在缺失时 `throw new Error('Claw Xpert is not configured')`。**注意：本页不读 `:id` 路由参数**。

**runtime 入口（对照，跨子域）**：对话域 `ClawXpertConversationFilesComponent` 用 `AiWorkspaceFilesService`（`/api/ai/assistants/:id/workspace/*`，后端 `forRuntime`），并按 `mode: 'readonly' | 'editable'` 决定是否传入 `fileSaver` / `binaryFileSaver` / `fileDeleter` / `fileUploader`（readonly 时传 `null`）。`projectId` 存在时改走 `ChatConversationService`（Workbench 运行目录）。

**两条入口的呈现差异（小结）**：① 数据源与权限面不同（authoring vs runtime），前端只是分别调用；② 写能力在 workspace 页由**服务端返回码**约束（组件不做本地能力判定），在 runtime 页由**组件 `mode` 输入**做 UI 级只读；③ workspace 页是整页 + `library` 布局，runtime 页是会话侧栏内的面板（`treeSize="sm"`、`referenceable`）。

## 路由入口与守卫

**`/w/*` 与 `/xpert/w/*`**：仓库内唯一注册点是 [features/xpert/routes.ts](file://apps/cloud/src/app/features/xpert/routes.ts)（`path: ''` → `redirectTo: 'w'`；`path: 'w'` → `loadChildren(() => import('./workspace/routes'))`，`data.scopeContext = 'dual-scope'`）。ki 与父级文档把入口写作 `/w/*`，实为 **`/xpert/w/*` 的简写**；全仓未发现顶层 `/w` 路由注册。因此下文统一按 `/xpert/w/*` 表述。

**守卫生成链**：`path: ''` 上挂 `canActivate: [redirectToSelectedWorkspace]`，该内联守卫注入 `Router`/`AppQuery`/`PersistQuery`，取 `appQuery.getValue().selectedWorkspace?.id ?? persistQuery.getValue().workspaceId`，并把 `section` 查询参数映射为子段（`skills→clawxpert-skills`、`knowledges→clawxpert-knowledges`、`connectors→clawxpert-connectors`、`files|settings→同名`），最后 `workspaceId ? router.createUrlTree(['/xpert/w', workspaceId, ...]) : true`（无工作区则放行到宿主空态）。

**`:id` 子路由（14 条）**：`''`(all)、`xperts`、`knowledges`、`clawxpert-knowledges`、`files`、`custom`、`connectors`、`clawxpert-connectors`、`builtin`、`mcp`、`database`、`skills`、`clawxpert-skills`、`settings`（**`redirectTo: '/chat/clawxpert'`, `pathMatch: 'full'`**）、`prompt-workflows`（`canDeactivate: [(c) => c.confirmLeave()]`）。

**子段驱动 UI 的机制**：宿主用 `router.events(NavigationEnd).pipe(startWith(null), map(() => route.snapshot.firstChild?.routeConfig?.path ?? ''))` 得到 `section`，再派生 `type`（`xperts→Agent`、`builtin/mcp/custom→工具类别`、`prompt-workflows→'prompt_workflow'`、其余 `null`）与 `allTags()`（专家标签 / 工具标签 / 提示词标签）。`isAll()`、`isXperts()`、`isTools()`、`isBuiltinTools()` 全部由 `section`/`type` 派生；另有两个正则信号区分「独立工作区路由」（`files|settings|clawxpert-*`）与「市场工作区路由」（`clawxpert-connectors|clawxpert-skills`）。

## 错误态呈现

**现状（读码事实）**：本子域**没有任何 `403`/`404`/`HttpErrorResponse` 字面量或状态码分支**，也没有面级错误页组件。错误一律走三条通道：

1. **toast**：`getErrorMessage(error)` + `ToastrService.error`（改名/可见性失败、归档/删除失败、新建工作区失败、设置默认失败、知识库设置失败等）。
2. **局部降级信号**：`knowledges-page` 的 `loadError`（`'knowledgebases' | 'documents'`）与 `prompt-workflows` 的 `loadError`（直接显示错误文本）；概览页每个计数 `catchError(() => of(null))` 渲染为 `—`。
3. **空态/只读态**：`files` 页的「Configure Claw Xpert first.」、`all/xperts/knowledges/connectors` 的 `@if (canWriteWorkspace())` 隐藏新建入口、connector 卡片的 `zDisabled + definition.unavailable`。

**由此的可见风险**：403（能力不足 / 归档态）与 404（工作区不存在 / 已删）在 UI 上几乎不可区分，用户只会看到一句后端消息或一个空列表；`capabilities.canRead === false` 只在设置对话框里被用来**自动关闭**，宿主层没有「无读权」的专门落点。**这是呈现层缺口，不是鉴权缺口**——后端 `WorkspaceAuthoringGuard`/`WorkspaceOwnerGuard` 仍是唯一闸门。[推测]

| 宿主即上下文（parent-as-context） | `home.component.ts` | 子页面 `inject(XpertWorkspaceHomeComponent)` 读 `workspace`/`canWrite`/`section`/标签信号，避免各自重复取数 |

| 派生信号优先 | `computed` / `toSignal` / `derivedAsync` | 尽量无显式订阅穿透模板 |

## 热点路径

1. **进入 `/xpert/w`** → 守卫读 `AppQuery.selectedWorkspace`/`PersistQuery.workspaceId` → `createUrlTree(['/xpert/w', id, section?])`；无 id 时放行到 `XpertWorkspaceHomeComponent` 空态。
2. **进入 `/xpert/w/:id`** → 宿主 `getAllMy(purpose:'authoring')` + effect 三方同步（路由 id 优先 → `store.setWorkspace`；否则按选中态改写 URL；再否则回落 `workspaces[0]`）。
3. **切子段**（如 `/files`）→ `NavigationEnd` → `section` 派生 `type`/`allTags` + 菜单高亮（含浏览器前进/后退）。
4. **打开设置** → `canManage` 门控 → `getOneById(relations:[owner,members])` → general（改名/可见性）→ `updateVisibility` → `refresh()` → `onUpdated` 重取详情（`canRead===false` 则自动关闭）。
5. **改成员** → `getMembers` → `UserRoleSelect`（排除已有成员）→ `updateMembers(id, ids)` 整体覆盖。
6. **打开文件页** → `AssistantBindingService.get(CLAWXPERT, USER)` → `xpertId` → `getWorkspaceFiles(id, '')` → 树懒加载 → 上传/保存/删除/下载（blob，目录加 `.zip`）。

## 技术债

1. **孤儿页**：`XpertWorkspaceSettingsPageComponent` 全仓仅被自身 spec 引用，`routes.ts` 的 `settings` 段是 `redirectTo: '/chat/clawxpert'`；`XpertWorkspaceModelsComponent` 更彻底（除自身文件外零引用）。[推测] 二者属「已下线/未挂载」页面，建议显式删除或补路由。
2. **错误态无面级呈现**：无 403/404 分支、无错误页组件，403（能力/归档）与 404（不存在）在 UI 上难以区分（见「错误态呈现」）。[推测]
3. **能力位缺省放行**：`canX()` 的 `?? true` 与后端收紧默认相反；若列表/详情未携带 `capabilities`（例如某些投影遗漏），门控会静默放开。[推测]
4. **`files` 页与 `:id` 解耦**：`/xpert/w/:id/files` 只认 ClawXpert 用户绑定，工作区维度事实上**不参与**该页数据选择；多工作区用户看到的是同一份 ClawXpert 卷。[推测] 是否为设计意图待确认。
5. **设置对话框 `getOneById` 与列表投影不共用**：`onUpdated` 依赖 `capabilities.canRead === false` 关闭对话框，但该字段是否总在详情 DTO 中返回未在本子域可验证。
6. **`prompt-workflows` 的 `canDeactivate` 仅覆盖该类**：其它资源页（如 `files` 上传中）没有离开确认。
7. **`section` 参数双实现**：`section → routeSegment` 的映射在 `routes.ts` 与 `home.component.ts`（`syncWorkspaceRoute`）各写一份，改一处漏一处即出现「首跳对、改写不对」的静默偏差。

## 设计维度对照

### 维度一：取数方式（宿主集中取数 vs 页面自取数）

宿主集中取数用于**跨页共享**的工作区实体与选中态（`workspaces`、`workspace`、`canWrite`、`canManage`、`section`、标签源），页面自取数用于**页内资源**（助手列表、知识库、连接器、技能、文件）。判断依据是「该状态是否被两个以上子页面消费」：工作区实体是，资源列表不是。代价是宿主组件体积大（含菜单、搜索、默认工作区、三个对话框入口）。

章节来源：[home.component.ts](file://apps/cloud/src/app/features/xpert/workspace/home/home.component.ts)（关键符号：`workspaces`、`canWriteWorkspace`、`allTags`）

### 维度二：授权呈现（能力位门控 vs 服务端返回码兜底）

本子域**只用能力位做 UI 门控**（隐藏/禁用按钮、关闭对话框），从不把能力位当作「能否成功的判据」；真正的判定与拒绝由后端守卫产生返回码，前端仅 toast / 空态呈现。与之相对，runtime 文件面用的是**组件输入级只读**（`mode`），因为那条路径的授权结果不落到页面实体上。两种呈现方式对应两个不同权限面，**不可互换**。

章节来源：[general.component.ts](file://apps/cloud/src/app/features/xpert/workspace/settings/general/general.component.ts)（关键符号：`canManageWorkspace`、`canEditVisibility`）、[home.component.html](file://apps/cloud/src/app/features/xpert/workspace/home/home.component.html)（关键符号：`canWriteWorkspace`、`canManageWorkspace`）、[clawxpert-conversation-files.component.ts](file://apps/cloud/src/app/features/chat/clawxpert/clawxpert-conversation-files.component.ts)（关键符号：`mode`）、[AGENTS.md](file://AGENTS.md)（关键符号：三元权限面不可互换）

### 维度三：文件面入口（authoring façade vs runtime façade）

同一套 `FileWorkbench*` 回调类型下有两个 façade：workspace 页对接 `/api/xpert/:id/workspace/*`（创作检查，含草稿），对话域对接 `/api/ai/assistants/:id/workspace/*`（运行时准入，只认已发布）。二者由**不同组件、不同服务**承载，前端没有「入口切换」开关——这正是「入口由服务端选定、运行被拒不得回退 authoring」在前端的落地形态。

## 结论

- **实现骨架清晰**：一个宿主（工作区壳）+ 一个设置对话框（三页签）+ 一族资源页 + 一个文件 façade；跨页状态集中在宿主，页内状态各自管理。
- **门控是「呈现」而非「判定」**：`canWrite`/`canManage` 广泛用于隐藏与禁用，但代码层没有任何权限推断；唯一的反向依赖是设置对话框按 `canRead === false` 自我关闭。
- **文件面是两块而不是一块**：`/xpert/w/:id/files` 是 authoring 面且与工作区 id 解耦，runtime 面在对话域；把它们当一个东西改，会同时破坏两处契约。
- **最需要补的三处**：面级 403/404 呈现、孤儿页清理（`settings-page` / `models`）、`section` 映射双实现收敛。
