## 缺口

1. **文件授权回归无前端覆盖（本子域最重要缺口）**：`/xpert/w/:id/files` 的 `XpertWorkspaceFilesComponent` **无 spec**——`xpertId` 的绑定解析（`AssistantBindingService` → `CLAWXPERT/USER`）、缺失时的空态与 `throw`、7 个回调到 authoring 端点的映射、`hasChildren → .zip` 命名、绑定 `changes$` 触发重载，全部无断言。runtime 侧的呈现（`ClawxpertConversationFilesComponent` 的 `readonly/editable`）属对话域，本子域不覆盖，因此**「两条入口不串门」这一硬约束在前端没有回归护栏**。
2. **成员管理零覆盖**：`XpertWorkspaceMembersComponent` 无 spec（整体覆盖语义、owner 排除、空选择不提交、`uniqBy` 去重均无断言）；设置对话框的 `members` / `apiKeys` 两页签只在 `settings.component.spec.ts` 中被 mock 掉。
3. **能力位门控只覆盖两处**：`general.component.spec.ts` 覆盖 `canManage=false`，`custom-connectors-dialog.component.spec.ts` 覆盖 `canManage=false`；`home.component.spec.ts` 用 `canWrite/canManage: jest.fn(() => true)` 全放行，**没有 `canWrite=false` / `canRead=false` / 归档态 / `canRun` 的任何断言**。
4. **错误态无覆盖**：无 403/404 分支断言；`getErrorMessage` + toast 只在 `general`（保存失败）与 `knowledges*`（详情失败）两处被间接覆盖。
5. **孤儿组件被测试固化**：`settings-page.component.spec.ts` 与 `models.component.ts` 对应的页面均无路由消费者，测试覆盖的是「未挂载页面」。
6. **路由守卫无覆盖**：`redirectToSelectedWorkspace` 的 `section → routeSegment` 映射、无工作区时的放行分支无 spec（`home.component.spec.ts` 直接以 `/xpert/w/workspace-1/...` 起手，绕过守卫）。
7. **prompt-workflows 的 `canDeactivate`（`confirmLeave`）无覆盖**。

## 结论

- **可执行性具备、前置是依赖落盘**：配置（contracts 源码直连、environment 替换、jsdom 垫片）齐备，14 个 spec 全部离线；唯一外部前置是 `corepack pnpm install`。父级归档的 53 个「环境级缺依赖」含本子域的 `prompt-workflows` 2 个（`@milkdown/crepe`）。
- **覆盖重心偏「资源页与设置交互」**：连接器（27+3+1）、提示词工作流（12+7+4）、设置面（1+2+5）是三大块；**工作区列表/详情、成员、文件面覆盖薄弱甚至为零**。
- **能力位与权限面在测试里几乎不可见**：现有断言只验「按钮禁用 / 对话框不打开」这类 UI 后果，不验权限面归属；「前端不推断文件权限、两条文件入口不互换」目前**只能靠代码审查**而非测试守护，建议至少补 `files.component` 的绑定解析与端点映射断言，以及 `general` 之外的 `canWrite=false` 断言。
- 文件授权与能力语义的权威口径见后端 [C0-使用总览.md](file://.module-experts/后端专题/Assistant 定义与运行时专家/sub-experts/工作区与文件授权子专家/C0-使用总览.md) 与其 `implementation/06-测试.md`。
