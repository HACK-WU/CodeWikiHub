## Recipe 1 建知识库并上传一批文档（幂等三元组与 `bulk` 语义）

**业务目标**：新建一个作用域内的 KB，并把一批文件一次性登记为文档，能重复调用而不产生重复行。

**调用顺序**
1. `POST /api/knowledgebase`（`CrudController<Knowledgebase>.create`）建 KB，携带 `name`、`vectorStore`、`copilotModelId`、`permission`、`metadataSchema` 等。
2. `POST /api/knowledgebase/:id/file` 上传原件到 KB volume（`UploadFileCommand` 写入 `knowledges` catalog），拿到 `url/filePath/fileUrl/mimeType`。
3. `POST /api/knowledge-document/bulk?process=true` 批量登记；不传 `process` 则只落库不入队。
4. 如需外部源：`POST /api/knowledge-document/connect` 先验证连接，再走 `bulk`。

**事务边界**：`createBulkWithIncrementalSync(documents, manager)` 在调用方传入的 `EntityManager` 事务内完成「复用/新建 + chunk 暂存」；`startProcessing` 的入队发生在事务提交之后，不入事务。`bulk` 状态预置 `WAITING / progress 0 / processMsg null`，由消费者改写。

**预期结果**：返回 `documents` 以及 `createdIds / updatedIds / skippedIds / processableIds` 四组 id；`?process=true` 时 `processableIds` 被投到 `embedding-document`。

**错误处理**
- KB 名重复 → `getQueryFailedErrorCode` 把 PostgreSQL `23505` 翻译成 `BadRequestException`（i18n `xpert.Error.NameExists`）。
- 越权 → `ForbiddenException` + `Error.KnowledgebaseAccessDenied`；KB 处于 `REBUILDING` 时上传/写入被 `assertNotRebuilding` 拒为 400。
- 带非法 `tagIds` → `Error.InvalidDocumentImportTags`。

**幂等三元组语义（核心）**：`sourceKey` + `sourceHash` + `processingHash` 唯一确定「同一文档同一处理配置」。三者全等则复用已有行（`createdIds` 为空、计入 `skippedIds`）；`processingHash` 变化（换了 parser、chunking revision 等）视为需要重切重嵌。

**真实代码示例**
```http
POST /api/knowledge-document/bulk?process=true
[
  { "knowledgebaseId": "<kbId>", "name": "a.pdf", "storageFileId": "<fileId>",
    "sourceType": "local", "sourceKey": "local:default:a.pdf" }
]
```
```ts
// 契约：KnowledgeDocumentService
async createBulkWithIncrementalSync(
    documents: Partial<IKnowledgeDocument>[],
    manager?: EntityManager
): Promise<IncrementalDocumentSyncResult>
// 契约：KnowledgebaseService
async assertNotRebuilding(knowledgebaseId: string)
```

来源：[document.service.ts](file://packages/server-ai/src/knowledge-document/document.service.ts)（`createBulkWithIncrementalSync` / `createOrReuseSourceDocument`）、[knowledgebase.service.ts](file://packages/server-ai/src/knowledgebase/knowledgebase.service.ts)（`getQueryFailedErrorCode` / `assertNotRebuilding`）

## Recipe 2 观察摄取进度与排障「一直处理中」

**业务目标**：把「上传后卡住」定位到具体环节（队列 / 消费者 / 状态列 / 失败写回）。

**调用顺序（排查链）**
1. **队列 → 消费者**：确认 `embedding-document` 有活跃 worker。消费者是 `KnowledgeDocumentConsumer`，`@Process({ concurrency: 5 })`，任务体第一句 `await this.lifecycle.waitUntilReady()`。
2. **就绪门**：若启动后立即投递且队列「有任务无人取」，先怀疑就绪门未放行——`KnowledgeProcessingReadyService` 在 `onApplicationBootstrap` 才 resolve，源码注释：「Bull registers workers in onModuleInit, before CQRS registers its handlers. The explicit CqrsModule dependency orders this gate after CQRS bootstrap.」
3. **状态列**：`GET /api/knowledge-document/status?ids=a,b,c`（只回 `id/status/progress/processMsg`）；或 `GET /api/knowledge-document/:id` 看全量。
4. **失败写回**：`status=ERROR` + `processMsg` + 日志 `Document '<docId>' failed: …`。
5. **停止**：`DELETE /api/knowledge-document/:id/job` 做 `job.discard()` + `moveToFailed('Job stopped by user')`，随后置 `CANCEL`。

**事务边界**：状态推进由消费者逐文档 `catch` 后独立写回，不合并为一个大事务；一篇失败不影响同批其它篇。

**预期结果**：`status` 在 `waiting → validate → running → transformed → splitted → understood → embedding → finish` 之间推进，成功 `progress=100`；取消落 `cancel`，失败落 `error`。

**错误处理**
- 文档 `ERROR` 且 `jobId` 非空 → 不可自愈，需人工重跑 `POST /api/knowledge-document/process`（`ids[]` + `mode`）。
- `mode` 非法 → `Error.InvalidDocumentProcessingMode`。
- Bull 侧无 `attempts`/`backoff`（`embedding-document` 与 `rebuild-knowledgebase-embedding` 均未声明），失败不会自动重试；`knowledge-faq-semantic-prewarm` 例外（`attempts: 3`、指数退避 2000ms、`timeout: 45s`）。
- 「一直处理中」也可能是队列不可用导致派生索引静默滞后：`publish` 对 tags/questions/graph/wiki 逐项 `catch` 后仅 `logger.warn`。

来源：[document.job.ts](file://packages/server-ai/src/knowledge-document/document.job.ts)、[processing-lifecycle.module.ts](file://packages/server-ai/src/knowledge-document/processing-lifecycle.module.ts)、[derived-index-publication.service.ts](file://packages/server-ai/src/knowledge-document/derived-index-publication.service.ts)

## Recipe 3 增量同步（改源文件后 `createBulkWithIncrementalSync` → chunk 级 diff → 中断恢复）

**业务目标**：源文件内容变了只重嵌变化片段，而不是整库重跑。

**调用顺序**
1. KB 侧确认 `incrementalSyncEnabled`（列默认 `false`）。
2. 重新调用 `POST /api/knowledge-document/bulk`（内部走 `createBulkWithIncrementalSync`）或 `POST /api/knowledge-document`（单篇，`createOrReuseSourceDocument`）。
3. 文档级判定后进入 chunk 级：`syncChunksIncrementally(document, vectorStore)`。
4. 变化时 `POST /api/knowledge-document/process` 以 `mode=full` 重新入队；快照可用且只想重切时用 `mode=rechunk`。

**事务边界**：chunk 行先落库，向量在行落库之后写（源码注释：「Chunk rows are saved before vectors. Only a matching published hash proves those rows were indexed.」）——这正是中断恢复要覆盖的窗口。

**预期结果**
- `contentHash = computeKnowledgeDocumentContentHash(incomingChunks)` 与 `document.contentHash` 相等 → `contentChanged=false`、`embeddingChunks=[]`（不重嵌），但仍会 `publish({ contentChanged: false })` 重投 tags/questions 并走 graph 重试分支。
- 不等 → `matchIncrementalChunks` 用 **exact（内容哈希）+ position（顺序）** 两级匹配，产出 `added / changed / unchanged / removed`；未命中行按 `removedChunks` 删除。

**错误处理（中断恢复）**：`recoverInterruptedSync` 的判据是「已有 chunk 行 **且** 现有行重算哈希 ≠ `document.contentHash`」，即「chunk 已写、向量未发布」的中断态；置位后 `unchanged` 一律计为 `updated` 并强制重嵌，`skippedCount` 归 0。

**真实代码示例**
```ts
const recoverInterruptedSync =
    existingChunks.length > 0 &&
    (!document.contentHash ||
        computeKnowledgeDocumentContentHash(sortChunksByDocumentOrder(existingChunks)) !== document.contentHash)
if (!recoverInterruptedSync && document.contentHash && document.contentHash === contentHash) {
    return { chunks: existingChunks, embeddingChunks: [], removedChunks: [], contentHash, contentChanged: false }
}
```

来源：[document.service.ts](file://packages/server-ai/src/knowledge-document/document.service.ts)（`syncChunksIncrementally` / `matchIncrementalChunks` / `recoverInterruptedSync`）、[document-hash.ts](file://packages/server-ai/src/knowledge-document/document-hash.ts)（`computeKnowledgeDocumentContentHash` / `computeKnowledgeDocumentProcessingHash`）

## Recipe 4 检索与调参（三类召回 → RRF 权重 → rerank → 引用投影）

**业务目标**：在不改 Agent 代码的前提下，用 KB 上的 `recall.fusion` 与请求级参数调准召回质量。

**调用顺序**
1. 试跑：`POST /api/knowledgebase/:id/test`，body 支持 `query / k / score / rerankModel / rerankThreshold / filters / variables / retrieval / contentScope`。
2. 生产路径：`KnowledgeRetriever.retrieveDetailed` 组装 `tenantId / organizationId / knowledgebases / query / k / score / rerankThreshold / filters / retrieval / threadId / xpertId` 走 QueryBus → `KnowledgeSearchQueryHandler`。
3. 三路并行候选：`VectorKnowledgeCandidateRetriever` / `KeywordKnowledgeCandidateRetriever`（`content` tsvector、`keyword_vector`、trigram）/ `GraphKnowledgeCandidateRetriever`。
4. 融合：默认 `WeightedRrfFusion`，可切 `LegacyWeightedFusion`（`fusionMode: 'legacy' | 'weighted_rrf'`）。
5. rerank：`KnowledgebaseService.getRerankModel` → `rerankModel.rerank(docs, query, { topN, scoreThreshold })`。
6. 输出投影：`formatKnowledgebaseRetrievalToolOutput` 产出 `chunks`（含 `content`）与去重后的 `citations`。

**事务边界**：整条检索是只读；唯一写操作是 `knowledge_retrieval_log` 的观测行（`filterVersion / fixed|dynamic|request|effectiveFilter / filterHash / filterStatus / candidateChunkCount / vectorLatency / diagnostics`），与检索结果解耦。

**预期结果与调参抓手**
- 权重默认 `DEFAULT_KNOWLEDGE_RRF_WEIGHTS = { vector: 0.65, graph: 0.35, keyword: 0.3 }`，`rankConstant` 默认 60。
- `contentScope === 'wiki'` 或 GraphRAG 未启用时，graph 权重被置 0。
- RRF 要求每条 batch 的权重有限且非负（`validateRrfWeights` 在检索入口先校验），`WeightedRrfFusion` 对 `rankConstant`/rank 抛 `RangeError`。

**错误处理**：rerank 模型缺失/无权限 → `Error.KnowledgeRerankModelUnavailable`；FAQ/图谱不支持的组合 → `Error.KnowledgeFAQGraphUnsupported`。引用投影故意不复述 chunk metadata——源码注释：「Citation summaries deliberately avoid repeating chunk metadata.」

**真实代码示例**
```ts
const citations = chunks.map(({ content, metadata: _metadata, ...citation }) => citation)
return JSON.stringify({ chunks, citations, instructions: KNOWLEDGEBASE_CITATION_MARKDOWN_INSTRUCTION, ...(diagnostics?.length ? { diagnostics } : {}) }, null, 2)
```

来源：[retriever.ts](file://packages/server-ai/src/knowledgebase/retriever.ts)、[citation.ts](file://packages/server-ai/src/knowledgebase/citation.ts)、[weighted-rrf.fusion.ts](file://packages/server-ai/src/knowledgebase/retrieval/weighted-rrf.fusion.ts)、[knowledgebase.model.ts](file://packages/contracts/src/ai/knowledgebase.model.ts)

## Recipe 5 结构化过滤与 `metadataSchema`

**业务目标**：用文档/切片元数据把检索限定在某个业务维度（部门、年度、业务域），并在 Agent 工具层暴露可选项。

**调用顺序**
1. 建库或更新时写 `metadataSchema`（列类型 `jsonb`，默认 `[]`）。每条字段定义形如 `{ key, type, scope: 'document' | 'chunk', enumValues? }`；`scope` 缺省视为 `document`。
2. `createKnowledgeFilterRegistry(knowledgebase)` 构建字段注册表：系统字段 + 按 `scope` 派生前缀 `metadata.<key>`（document）或 `chunk.metadata.<key>`（chunk）。
3. 检索前 `prepareKnowledgeFilter({ knowledgebase, filters, variables })` 编译 → 得到 `fixed / dynamic / request / effective` 四层 filter 与 `filterHash`。
4. 写入侧校验：`KnowledgeDocumentStore` 在 `addKnowledgeChunks` / 更新路径调 `validateFilterMetadata(document.metadata, metadataSchema, 'document')` 与 `validateFilterMetadata(chunk.metadata, …, 'chunk')`。
5. 工具层：`KnowledgeRetriever.toFilterOptionsTool` / `toFolderOptionsTool` / `toGraphExplorerTool` 暴露可选项。

**事务边界**：`metadataSchema` 的读写与 KB 作用域同事务；过滤编译是纯函数，不落库。观测写 `knowledge_retrieval_log`。

**预期结果**：`effectiveFilter` 即为本次实际生效的边界；`filterStatus` 与 `fallbackReason` 说明是否发生回退；`filterHash` 使同一过滤条件可归并统计。

**错误处理**
- 面向 provider 的 schema 故意精简（源码注释：「Keep the provider-facing schema deliberately compact.」）。**精确的字段/操作符/类型校验属于 `KnowledgeFilterCompiler`**：非法动态过滤可安全回退到固定边界，并记为 `invalid_dynamic_filter`。
- 部分 OpenAI 兼容 provider 会把嵌套工具参数序列化成 JSON 文本，schema 因此接受 `string`（`max 32_768`）形式，避免 LangChain 在回退策略生效前直接拒掉整次工具调用。
- 元数据与 schema 不匹配 → 由 `KnowledgeFilterCompiler` 侧拒绝；写入侧由 `validateFilterMetadata` 抛错。

**真实代码示例**
```ts
const registry = createKnowledgeFilterRegistry({ metadataSchema: [
  { key: 'domain', type: 'enum', scope: 'document', enumValues: ['水利', '物流'] },
  { key: 'effectiveYear', type: 'number', scope: 'document' }
]})
// → 字段前缀：metadata.domain / metadata.effectiveYear；chunk 域字段走 chunk.metadata.*
```

来源：[knowledge-filter.ts](file://packages/server-ai/src/knowledgebase/filter/knowledge-filter.ts)、[knowledgebase.entity.ts](file://packages/server-ai/src/knowledgebase/knowledgebase.entity.ts)（`metadataSchema`）、[vector-store.ts](file://packages/server-ai/src/knowledgebase/vector-store.ts)（`validateFilterMetadata`）、[retriever.ts](file://packages/server-ai/src/knowledgebase/retriever.ts)

## Recipe 6 切换 embedding 模型并重建（`assertNotRebuilding` 期间的写阻断与失败处理）

**业务目标**：换 embedding 模型而不破坏旧索引可用性，能够回滚、能够拒绝陈旧任务。

**调用顺序**
1. 更新 KB 的 `copilotModelId`（写 `pendingCopilotModel*`）。
2. `POST /api/knowledgebase/:id/rebuild-embedding` → `startEmbeddingRebuild(id)`：置 `status = REBUILDING`、写 `rebuildTaskId` + `pendingEmbeddingRevision`，投 `rebuild-knowledgebase-embedding`（消费者 `concurrency: 1`）。
3. 消费 `processEmbeddingRebuildJob(data)`：`getPendingVectorStoreForRebuild` 取新 collection → 逐批重嵌所有 chunk（含 question 向量）。
4. `promoteEmbeddingRebuild(knowledgebaseId, rebuildTaskId, pendingEmbeddingRevision)` 原子切换：`pending → active`，`status = READY`，并把 chunk metadata 的 `model` 改为 `getEmbeddingModelName(saved.copilotModel)`。
5. `cleanupEmbeddingCollection(*, oldCopilotModel, oldCollectionName)` 异步清旧 collection（fire-and-forget）。
6. 反悔：`POST /api/knowledgebase/:id/cancel-pending-embedding-model` 清空 `pending*` 回到 `READY`。

**事务边界**：`promoteEmbeddingRebuild` 是唯一的原子切换点（事务内完成 pending→active）；`cleanupEmbeddingCollection` 在切换之后、事务之外执行。**重建期间 `assertNotRebuilding`（`status === REBUILDING` 抛 `Embedding rebuild is running`）阻断写路径**，已确认的调用点包括：文档登记/批量更新/删除/页删除/chunk 写/`process`、KB 文件上传、上传会话（`knowledge-upload-sessions`）、文件夹创建、FAQ 写路径、问题生成、`knowledge-workbench` 写入。这形成「长事务式的全局写锁」，读路径不受影响。

**预期结果**：切换后 active collection 指向新模型；重建期旧 collection 仍在线，**高峰存储约 2×**。

**错误处理**
- 重建失败 → `markEmbeddingRebuildFailed`：`status = REBUILD_FAILED` + 写 `embeddingRebuildError`（该状态仍会阻断写，需立即告警）。
- 陈旧任务 → `assertCurrentRebuildTask` 用 `rebuildTaskId + pendingEmbeddingRevision` 判定，不匹配抛「Embedding rebuild task is stale」；过期 worker 的失败路径只 `logger.warn`，**不覆盖当前状态**。
- 入口错误：400「Embedding rebuild is already running」/「Embedding rebuild is running」/「Pending embedding model is required for rebuild」。
- 跨副本：`assertNotRebuilding` 读 DB 列因此跨副本可见，但它是「先查后写」，检查与写入之间无锁——真正的幂等靠 `rebuildTaskId` + `pendingEmbeddingRevision`，**不要用本地内存缓存替代**。
- 向量表维度不匹配不会被 `synchronize` 修正（向量表非 TypeORM 实体），只能靠重建 + 新 collection 规避。

来源：[knowledgebase.service.ts](file://packages/server-ai/src/knowledgebase/knowledgebase.service.ts)（`startEmbeddingRebuild` / `processEmbeddingRebuildJob` / `promoteEmbeddingRebuild` / `markEmbeddingRebuildFailed` / `assertNotRebuilding` / `assertCurrentRebuildTask`）、[knowledgebase-rebuild-embedding.job.ts](file://packages/server-ai/src/knowledgebase/knowledgebase-rebuild-embedding.job.ts)

## Recipe 7 建 GraphRAG 图谱并查询（重建 / 重试 / 邻域）

**业务目标**：把切片抽成实体-关系图，供检索做图谱候选，并支持人工修正与全库重建。

**调用顺序**
1. 打开 KB 的 `graphRag.enabled`。
2. 触发：文档 durable `FINISH` 后 `KnowledgeDerivedIndexPublicationService.publish` 发 `KnowledgeGraphEnqueueCommand`（`contentChanged` 时）或 `KnowledgeGraphRetryDocumentCommand`（未变时）。
3. `GraphragService.enqueueDocuments` 为每篇建 `KnowledgeGraphIndexJob`（`type`、`sourceContentHash`、`sourcePublicationEpoch`），`dispatchJobs` 入队 `knowledge-graph-index`（入队失败写 `dispatchError`）。
4. `KnowledgeGraphIndexConsumer`（`concurrency: 2`）→ `processIndexJob(graphIndexJobId)`；实体归一调 `KnowledgeIdentityService.resolve / resolveBatch`，结果落在 `knowledge_graph_entity.identityId`。
5. 查询：`GET status` / `GET entities` / `GET relations` / `GET mentions` / `GET entities/:entityId/neighborhood` / `GET entities/:entityId/chunks` / `GET catalog` / `GET visualization`。
6. 手工修正：`POST entities`、`PATCH entities/:entityId`、`DELETE entities/:entityId`（**软隐藏** `hideEntity`，非物理删除）；relation 同构。
7. 重建：`POST /api/knowledgebase/:id/graph/rebuild`。

**事务边界**：job 行与 KB 状态列（`graphStatus` / `graphIndexError`）在各自写回中更新；抽取/写图跨事务，`clearDocument` 失败仅告警。

**预期结果**：`status` 默认 `QUEUED`，终态由 `markJobSuccess`（`SUCCESS`）或 `markJobFailed`（`FAILED`，同时写 KB `graphStatus = FAILED` 与 `graphIndexError`）落定；实体向量写入 `${activeCollectionName}:graph-entities`。

**错误处理**
- 单篇重试：`POST /api/knowledgebase/:id/graph/documents/:documentId/retry`（先 `assertKnowledgebaseWriteAccess`），返回最新进度。
- 批量进度入参非法 → `Error.KnowledgeGraphDocumentStatusBatchInvalid`。
- `graphStatus` 非 `DISABLED` 但 `entities` 为空 → 优先看 `graphIndexError`（`GET status` 以 `error` 暴露），成功路径会清空该列。

**真实代码示例**
```http
POST /api/knowledgebase/<kbId>/graph/documents/status
{ "documentIds": ["<docId>", "<docId2>"] }
GET  /api/knowledgebase/<kbId>/graph/entities/<entityId>/neighborhood
```

来源：[graphrag.controller.ts](file://packages/server-ai/src/graphrag/graphrag.controller.ts)、[graphrag.service.ts](file://packages/server-ai/src/graphrag/graphrag.service.ts)、[graphrag.job.ts](file://packages/server-ai/src/graphrag/graphrag.job.ts)、[derived-index-publication.service.ts](file://packages/server-ai/src/knowledge-document/derived-index-publication.service.ts)

## Recipe 8 建知识 Wiki 并做组织与分类（含 `requiresAdditionalChargeConfirmation` 的人工确认）

**业务目标**：在 KB 之上维护一个由源文档 chunk 派生的 Wiki，并把页面分到目录、跑自动分类。

**调用顺序**
1. `PUT /api/knowledgebase/:knowledgebaseId/wiki/config` 写 `wikiConfig`（触发 `wikiConfigFingerprint` 记录）。
2. `GET /api/knowledgebase/:knowledgebaseId/wiki/status` 读 `wikiStatus` / `wikiAvailability` / `wikiActiveRevision` / `wikiStagedRevision` / `recoveryActions` / `indeterminateInvocationCount` / `canManage`。
3. 生成：源文档 `FINISH` 后 `publish` 发 `KnowledgeWikiEnqueueSourceCommand` → `KnowledgeWikiGenerationService.processJob(jobId)`，按 `job.type` 分派 `classify / source_map / identity_resolve / page_reduce`（先 `lease.acquire(job)`）。
4. 阅读：`GET pages`（`status` 缺省或 `ready` 走 browse，其余走 `listPages`）、`GET pages/:pageId`（附 placement）。
5. 组织：`GET folders`、`POST folders`、`PATCH folders/:folderId`、`DELETE folders/:folderId`（`@HttpCode(204)`）、`PATCH pages/:pageId/placement`、`PATCH taxonomy`。
6. 分类：`POST classification-runs`（`unclassifiedOnly`）→ `GET classification-runs/status` → `GET classification-runs`（返回项含 `requiresAdditionalChargeConfirmation`）→ `POST classification-runs/apply`（`jobIds`）→ `GET graph`。

**事务边界**：Wiki job 通过 `KnowledgeWikiJobLeaseService`（租约）/ `KnowledgeWikiJobFenceService`（栅栏）/ `KnowledgeWikiInvocationBudgetService`（预算）做并发控制；投影由 `KnowledgeWikiProjectionService` 写 `knowledge_wiki_page` / `_page_version` / `_page_link`，投影文档 `sourceKey = 'system:knowledge-wiki'`。

**预期结果**：页面由源文档 chunk 的 evidence 生成（`knowledge_wiki_page_evidence.sourceDocumentIdSnapshot`）；对账由 `KnowledgeWikiReconcilerService.reconcile` 以 `@Interval` 周期执行（退休被取代 job、重派发、回收过期租约、版本升级重算）。

**错误处理（人工确认路径）**
- 非空 Wiki 重建需显式确认计费 → `Error.KnowledgebaseWikiRebuildChargeConfirmationRequired`。
- `POST jobs/:jobId/retry` 仅失败任务可重试 → `Error.KnowledgebaseWikiJobRetryInvalid`；不确定调用需确认 → `Error.KnowledgebaseWikiRetryChargeConfirmationRequired`。
- `requiresAdditionalChargeConfirmation: true` 表示「该模型调用**可能已计费但结果未落地**」，来自 `toRecoveryAction` 的 `canRetry && !notExecuted` 判定与文档进度的 `row.uncertain`——这是不可自动重试的第三态。
- 状态必须可查：`GET status` 的 `indeterminateInvocationCount > 0` 时**不要盲重试**，先人工确认。
- 其它：`Error.KnowledgebaseWikiDisabled` / `Error.KnowledgebaseWikiBudgetExceeded` / `Error.KnowledgebaseWikiStateReadOnly` / `Error.KnowledgebaseWikiFolderNotEmpty` / `Error.KnowledgebaseWikiOrganizationConflict`。
- 组织控制器级 `forbidNonWhitelisted: true`，未知字段直接 400。

## Recipe 9 删除文档与回收（`indeterminate` 的处理路径）

**业务目标**：删除一篇文档并连带清理外部产物（Wiki 证据、向量、图谱），且知道失败时该去哪里看。

**调用顺序（当前可执行路径）**
1. `DELETE /api/knowledge-document/:id`（`version` 必填）或 `DELETE /api/knowledge-document/bulk`（`documents[{id,version}]`）。
2. `deleteResolvedDocument(document, expectedVersion)` → `assertNotRebuilding(document.knowledgebaseId)`。
3. `deleteDocumentArtifacts` 依序：
   - `KnowledgeWikiRetractSourceCommand`，`reason = 'hard_deleted'`；
   - `vectorStore.deleteKnowledgeDocument(...)`；
   - `KnowledgeGraphClearDocumentCommand`（**失败仅告警**）。
4. 物理删 `knowledge_document` 行 → `updateDocumentNumAfterDelete` 回填 `documentNum`。

**事务边界**：跨存储三步不是单一事务；一致性依赖调用顺序与告警日志。关系库删除与向量表删除是两条独立路径。

**预期结果**：删除成功后文档对所有读取接口不可见——读取路径统一追加 `hardDeletePendingAt IS NULL`（`readableDocumentWhere`）；`deletedAt` 仍是 `@DeleteDateColumn`。

**错误处理**
- 软删：`DELETE /api/knowledge-document/:id/soft` 与 `PUT /api/knowledge-document/:id/recover` 路由存在，但 `softRemove` 当前直接抛 `ConflictException`——**软删能力未开放**，不要在生产依赖。
- 版本冲突 → 409（`Knowledge document has been modified. Refresh and try again.`）；缺 `version` → 400「version is required」。
- 重建中 → 400「Embedding rebuild is running」。
- **`indeterminate` 路径（现状）**：三张表 + 一张 source 表构成显式补偿协议——`knowledge_document_deletion_intent.status ∈ prepared | written | promoted | compensated | indeterminate`、`knowledge_document_deletion_cleanup_receipt.status ∈ pending | succeeded | failed | indeterminate`、`knowledge_document_publication_attempt`（`artifacts` 每项带 `idempotencyKey`）、`knowledge_document_publication_attempt_source`。**这四表已在 `KnowledgeDocumentModule` 注册并经 `core/entities/index.ts` 导出，但仓库内未找到写入/消费它们的服务**——即当前不存在删除侧 `indeterminate` 的生产写入路径。
- 因此「`indeterminate` 怎么处理」的**唯一现成入口在 Wiki/Graph 侧**：`GET /api/knowledgebase/:knowledgebaseId/wiki/status` → `recoveryActions[]`（`retry_job` / `full_rebuild`、`failureReason`、`canRetry`、`requiresAdditionalChargeConfirmation`），采取人工补偿，**不可自动重试**。
- 删除后可能出现「向量残留但行已删」（graph 清理失败仅告警）——排查时不要只看关系库。

**真实代码示例**
```http
DELETE /api/knowledge-document/<docId>?version=3
DELETE /api/knowledge-document/bulk
{ "documents": [ { "id": "<docId>", "version": 3 } ] }
```
