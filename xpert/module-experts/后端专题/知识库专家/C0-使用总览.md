## 专家定位

本专家回答「知识怎么进来、以什么代价变成可检索资产、Agent 怎么把它检出来」：以知识库（`Knowledgebase`）为聚合根，向上提供作用域 CRUD、可见性与模型绑定，向内把文档摄取变成一条可幂等、可增量的异步流水线，向 Agent 供给「向量 + 关键词 + 图谱」三路召回与融合/重排/结构化过滤能力，并以派生索引（GraphRAG 图谱、知识 Wiki、自动标签、生成问题、FAQ 语义预热）持续增值。它的核心张力是「主链一次性成功」与「派生索引最终一致」之间的窗口：窗口内的一致性问题被显式记账为可查询、需人工/补偿介入的中间态，而不是被掩盖。

## 何时找这个专家

- 要**建/改/删知识库**，设置可见性（私有 / 组织 / 公开）、绑定 embedding / rerank / chat / vision / wiki 模型，或绑定推理流水线。
- 要**上传文档并看摄取进度**：单篇/批量创建、幂等导入、增量同步、网页抓取与外部源接入。
- 要排查**「文档一直处理中 / 一直失败 / 上传后不见了」**（含待硬删不可见、系统托管文档被列表过滤这类「预期内消失」）。
- 要**调检索与 rerank 参数**：召回模式、topK、相似度阈值、重排阈值、融合策略与权重、内容范围（原文 / Wiki / 全部）。
- 要配 **FAQ、标签、结构化过滤**：FAQ 导入导出与语义匹配、标签手工/自动标注、按元数据字段做候选与过滤。
- 要**建 GraphRAG 图谱并查实体关系**：启停图谱、全库重建、单文档重试、实体/关系手工修正、邻域与可视化。
- 要**建知识 Wiki 并做组织/分类**：启停与配置、重建与重试、页面浏览、目录树、分类运行与应用。
- 要**换 embedding 模型并重建向量**，或处理「重建中其它操作被阻断」「旧/新 collection 并存」。
- 要排查**摄取队列积压**、派生索引静默滞后、`indeterminate` 类中间态，或确认真实鉴权边界（哪些路由有声明式守卫）。

## 边界

**做什么**：知识库作用域与可见性、模型绑定与结构化过滤定义；文档摄取全链（创建、幂等、增量、解析、切片、向量化、删除回收）与网页抓取；向量/关键词/图谱三类召回与融合、重排、过滤候选；派生索引（图谱、Wiki、自动标签、生成问题、FAQ 预热）；向量存储抽象与向量读写唯一入口。

**不做什么**

- **不含 Agent 执行链**：任务调度、工具调用、图编排与运行态归 Agent 执行链专家（批次 4）；本域只把检索器注册给外部并在被调用时执行检索。
- **不含模型访问与计费**：本域只从已建「模型访问与计费专家」取 embedding / rerank / chat / vision / wiki 模型句柄，不实现推理、不判额度、不记账。
- **不含文件与沙箱**：原文件字节、上传会话与卷落盘归文件与沙箱域（后续批次）；本域只持有存储文件引用与卷内相对路径并做归属校验。
- **`xpert-workspace` 只作创作容器引用**：工作区本体及其发布语义属「Assistant 定义与运行时专家」；本域仅继承其作用域基类并在工作区视图下暴露知识库列表。
- 不含文档解析器/切片器/向量库实现本身：这些由插件注册表与 provider 提供，本域只做注册表分派与调用。

## 已知问题与常见坑

1. **绝大多数路由没有 `@UseGuards`**
   - 现象：给账号加了权限点仍能读到某些知识库，或反之以为无鉴权。
   - 触发条件：只有 9 个知识库路由带 `PermissionGuard`、2 个带工作区创作守卫；FAQ/标签/文档/题目/图谱/Wiki 全部零声明式守卫。
   - 正确做法：把 service 断言当作唯一授权边界——知识库写走 `assertKnowledgebaseWriteAccess`，文档读走 `assertDocumentReadAccess` / `readableDocumentWhere`（含 `hardDeletePendingAt` 过滤），列表再叠加系统托管文档过滤；新增查询绕过任一环即产生越权与「读到待硬删文档」风险。
   - 契约来源：`KnowledgebaseController`（守卫分布）、`KnowledgebaseService.assertKnowledgebaseWriteAccess`、`KnowledgeDocumentService.readableDocumentWhere`。
2. **`tag-usage` 与 `:id` 的路径形态**
   - 现象：`GET /api/knowledgebase/tag-usage` 被当作 `:id` 处理并以 UUID 校验失败告终（400）。
   - 触发条件：合法端点是两段的 `/api/knowledgebase/tag-usage/:tagId`；单段 `:id` 通配排在本模块控制器注册序列最前，会兜住任何同层单段请求。
   - 正确做法：不要把 `tag-usage` 当单段路径调用；新增单段控制器（如 `@Get('foo')`）必须注册在知识库主控制器之前，或改用具名前缀，避免与 `:id` 竞争。
   - 契约来源：`KnowledgeTagUsageController`、`KnowledgebaseModule.controllers`。
3. **`graphrag` 与 `wiki` 双挂载 `/knowledgebase` 前缀**
   - 现象：新增图谱/Wiki 子路由后出现的 400 UUID 或落进错误处理器。
   - 触发条件：三个模块共用同一 RouterModule 前缀，仅靠控制器段（`:id/graph` 与 `:knowledgebaseId/wiki`）区分；同层新增单段控制器极易与 `:id` 冲突。
   - 正确做法：图谱/Wiki 新端点一律挂在已有两段控制器段之下；确需新段时先确认注册顺序并做一次真实请求验证。
   - 契约来源：`GraphragModule`、`KnowledgeWikiModule`、`KnowledgebaseModule.controllers`。
4. **派生索引只在源文档 durable FINISH 后派发，且失败静默**
   - 现象：文档已 `finish`，但标签/问题/图谱/Wiki 长时间不更新，日志只有一条 warn。
   - 触发条件：派发点在源文档可靠落库之后；tags / questions / graph / wiki 逐项独立捕获异常，Bull/Redis 不可用时不会影响主摄取，也不会有补偿队列。
   - 正确做法：把这四类索引视为最终一致；排障时按「该文档的派发是否发出 + 目标队列是否有消费者」定位，并对这几条 warn 单独设告警。
   - 契约来源：`KnowledgeDerivedIndexPublicationService.publish`。
5. **`indeterminate` 类中间态需人工/补偿**
   - 现象：Wiki 状态里出现不确定调用计数、重试被要求先确认计费；删除/发布侧存在「结果未知」的记录。
   - 触发条件：模型调用结果未落地但可能已计费；或清理/发布动作在跨存储阶段中断。
   - 正确做法：不要自动重试；按状态接口给出的恢复动作（重试任务 / 全量重建）处理，并预留 `requiresAdditionalChargeConfirmation` 语义的确认步骤。
   - 契约来源：`KnowledgeWikiService.getStatus` / `toRecoveryAction`、删除与发布意图表状态枚举。
6. **幂等三元组 `sourceKey` + `sourceHash` + `processingHash`**
   - 现象：内容没变却整篇重切重嵌，向量与 token 成本重算。
   - 触发条件：任一哈希变化即视为不同版本——`sourceHash` 变化（例如源文件被重新抓取或被重写）会触发重切/重嵌；处理配置（解析器/分块版本等）变化亦然。
   - 正确做法：稳定来源标识与内容哈希；只改「不影响快照有效性」的设置（切片器、图像理解设置被刻意排除在转换指纹之外），避免无谓失效。
   - 契约来源：`computeKnowledgeDocumentProcessingHash` / `computeKnowledgeDocumentTransformFingerprint`、`KnowledgeDocumentService.createBulkWithIncrementalSync`。
7. **重建期间写操作被阻断，且旧/新 collection 并存**
   - 现象：换 embedding 模型后上传、处理、删除等入口报「重建进行中」；存储占用短时接近翻倍。
   - 触发条件：重建态下 `assertNotRebuilding` 生效；重建成功后才提升新 collection 并异步清理旧 collection。
   - 正确做法：把重建当作计划内窗口（低峰执行、按 2× 预留存储）；失败时按错误列与状态定位后用取消 pending 模型回退，不要手工删 collection。
   - 契约来源：`KnowledgebaseService.startEmbeddingRebuild` / `assertNotRebuilding` / `cancelPendingEmbeddingModel`。
8. **`keywordAnalyzer` / `keywordAnalyzerLocked` 普通保存不生效**
   - 现象：改了关键词分析器配置，重启或回读后仍是旧值。
   - 触发条件：这两列声明为不可更新；只有专用设置入口与索引订阅侧的条件更新能写。
   - 正确做法：走知识库更新接口中携带关键词分析器的分支（服务内部转交分析器服务），不要在业务代码里直接保存实体；外部知识库类型会被直接拒绝。
   - 契约来源：`Knowledgebase.entity`、`KnowledgeKeywordAnalyzerService`。
9. **知识库重名判定为唯一键冲突**
   - 现象：创建/改名返回可读的「名称已存在」而非 500。
   - 触发条件：同一租户 + 组织下知识库名唯一。
   - 正确做法：把 23505/1062 视为业务错误处理；跨工作区的同名库仍会冲突，需要改名或复用既有库。
   - 契约来源：`KnowledgebaseService.updateKnowledgebase`（唯一键翻译）。
10. **`rag-web` 两处代码疑点**
    - 现象：Notion 抓取走到 Playwright 的 schema，且 `rag-web/loader.ts` 为空文件。
    - 触发条件：使用网页抓取能力时进入对应 provider。
    - 正确做法：接入 Notion 前先实测其选项与抓取结果，不要假设 schema 为 Notion 定制；不要把空文件当可导入的导出面。
    - 契约来源：`rag-web/provider/index.ts`、`rag-web/loader.ts`。
11. **约 30 个 integration spec 默认 skip**
    - 现象：CI 全绿但数据库相关行为实际没跑。
    - 触发条件：`*.integration.spec.ts` 需要 `KNOWLEDGE_WIKI_PG_E2E` / `KNOWLEDGE_IDENTITY_PG_E2E` / `KNOWLEDGE_GRAPH_PG_E2E` / `KNOWLEDGE_KEYWORD_PG_E2E` / `KNOWLEDGE_TAGGING_PG_URL` / `WIKI_V15_PG_URL` / `BOM_GRAPH_PG` 之一才执行。
    - 正确做法：至少在 CI 注入一组（推荐 Wiki 套件，覆盖面最广）；网页抓取测试还需 ESM 运行旗标。
    - 契约来源：`packages/server-ai/jest.config.ts` 与各 integration spec 的环境判定。
12. **模型依赖硬失败，无降级**
    - 现象：摄取、检索测试或 Wiki 生成直接报「模型未找到 / 不可用」。
    - 触发条件：embedding / rerank / vision / wiki 模型未配置、被下线或无当前用户权限。
    - 正确做法：上线前逐项确认绑定模型可用；把这类失败当作配置问题而非重试问题处理。
    - 契约来源：`KnowledgebaseService.getRerankModel`、`Error.KnowledgeRerankModelUnavailable`。
13. **软删未开放但字段与索引仍在**
    - 现象：调用软删接口返回冲突，而列表里仍有「已删除」痕迹的查询参数。
    - 触发条件：文档软删入口当前直接抛冲突；读路径还需叠加待硬删过滤与系统托管过滤。
    - 正确做法：删除走硬删/批量删除（带版本号）；排查「文档消失」先看待硬删标记与系统托管标记，而不是先怀疑权限。
    - 契约来源：`KnowledgeDocumentService.softRemove`、`document-list-filter.ts`。
14. **向量表不由 ORM 管理，部分索引需运维手工建**
    - 现象：`synchronize` 视角看不到向量表与 trigram/关键词索引，新环境首查报缺表。
    - 触发条件：向量表在运行期按需创建；两个部分索引声明为不随同步生成。
    - 正确做法：新环境预热一次向量化路径；把图结构加性迁移与部分索引列进部署清单，手工执行后再启动新版本。
    - 契约来源：`RagCreateVStoreHandler.createPgVectorStore`、`graphrag/migrations/`。
15. **诊断盲区：默认不返回的列**
    - 现象：按常规查询看不到处理执行标识、标签修订、内容哈希与关键词向量，误判为「没有数据」。
    - 触发条件：若干列默认不参与查询返回。
    - 正确做法：诊断时走服务方法（其内部显式选取），不要以默认查询为空作为「该字段未写入」的证据。
    - 契约来源：`KnowledgeDocument` / `KnowledgeDocumentChunk` 实体列声明。
