## D1 用显式 `CqrsModule` 依赖把就绪门排在 CQRS 引导之后

- **分类**：启动时序 / 避坑
- **动机（避坑）**：**现象** —— Bull 在 `onModuleInit` 注册 worker，早于 CQRS 注册它的 handler；任务一旦在启动窗口被取走，消费者会拿到尚未可用的 `CommandBus`。**后果** —— 摄取主链与派生索引派发在冷启动/滚动升级瞬间失败，且失败原因表现为「命令处理器不存在」，与业务无关，极难定位。
- **决策**：引入 `KnowledgeProcessingLifecycleModule` 作为**启动就绪门**，`imports: [CqrsModule]` 显式声明依赖以强制排序；`KnowledgeProcessingReadyService implements OnApplicationBootstrap` 持有一个 promise，`onApplicationBootstrap()` 时 resolve，消费者在任务体最开始 `await this.lifecycle.waitUntilReady()`。源码顶部逐字：
  > `// Bull registers workers in onModuleInit, before CQRS registers its handlers.`
  > `// The explicit CqrsModule dependency orders this gate after CQRS bootstrap.`
- **背景约束**：Bull worker 的注册时机由 `@Processor` 装饰器驱动，无法在模块内改成 `onApplicationBootstrap`；能改的只有依赖排序 + 任务体内自阻塞。
- **被否决方案**：无（源码未记录曾经尝试过的替代写法）。
- **重新评估触发条件**：升级 Nest/Bull 后 worker 注册时机变为不早于 CQRS 引导；或消费者改为不经 `CommandBus` 的直连服务调用。
- **关联代码**：`KnowledgeProcessingReadyService.waitUntilReady` / `KnowledgeProcessingLifecycleModule`；显式等待方为 `KnowledgeDocumentConsumer`、`KnowledgeAutoTaggingConsumer`、`KnowledgeQuestionsConsumer`；`KnowledgeGraphIndexConsumer`、`KnowledgeWikiGenerationConsumer`、`KnowledgebaseRebuildEmbeddingConsumer`、`FAQSemanticPrewarmProcessor` 的构造器**不含**该服务（未就绪门控）。
- **证据来源**：[processing-lifecycle.module.ts](file://packages/server-ai/src/knowledge-document/processing-lifecycle.module.ts)（文件首两行注释逐字）；[document.job.ts](file://packages/server-ai/src/knowledge-document/document.job.ts)（`await this.lifecycle.waitUntilReady()`）

## D2 队列 payload 让处理模式跨 HTTP / worker 边界持久

- **分类**：异步契约 / 幂等
- **动机（避坑）**：**现象** —— `mode` 若只作为 HTTP 请求参数存在，消费者侧无从得知本次该走 `full` 还是 `rechunk`。**后果** —— 「重新切但复用转换快照」的意图丢失，要么退化成全量重跑（浪费转换器与视觉模型成本），要么错误复用快照。
- **决策**：把 `mode?: KnowledgeDocumentProcessingMode` 放进 job data，由 `startProcessing(ids, kbId, mode)` 显式携带。源码逐字：
  > `/** Queue payload keeps processing mode durable across the HTTP/background-worker boundary. */`
- **背景约束**：Bull 任务体是唯一携带上下文的地方；消费者不持有原 HTTP 请求。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：处理模式改由文档行上的列（而不是 payload）持久化。
- **关联代码**：`type KnowledgeDocumentJobData = { userId; docs; mode? }`；`KnowledgeDocumentService.startProcessing`；`KnowledgeDocumentConsumer`。
- **证据来源**：[document.job.ts](file://packages/server-ai/src/knowledge-document/document.job.ts)（`KnowledgeDocumentJobData` 上方 JSDoc 逐字）

## D3 派生索引只在源文档 durable FINISH 之后派发

- **分类**：一致性策略
- **动机**：派生索引（tags / questions / graph / wiki）都以 chunk 内容为输入；只有源文档已持久化终态，派发才有稳定输入。
- **决策**：把派发收敛到单一入口 `KnowledgeDerivedIndexPublicationService.publish`，并在类上逐字注明：
  > `/** Dispatches optional derived indexes only after the source document is durably FINISH. */`
  派发时以 `contentChanged` 分流：为真发 `KnowledgeGraphEnqueueCommand` / `KnowledgeWikiEnqueueSourceCommand`；为假只发 `KnowledgeGraphRetryDocumentCommand`（保留重试语义而不重跑抽取）。
- **背景约束**：主链（document → chunk → vector）要求 durable，派生侧接受最终一致；二者不能放在同一事务里（派生要调模型与外部队列）。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：需要「主链与派生索引强一致」的业务诉求出现（例如合规要求标签必须与文档同时可见）。
- **关联代码**：`KnowledgeDerivedIndexPublicationService.publish`；派发目标 `KnowledgeAutoTaggingEnqueueCommand` / `KnowledgeQuestionsEnqueueCommand` / `KnowledgeGraphEnqueueCommand` / `KnowledgeGraphRetryDocumentCommand` / `KnowledgeWikiEnqueueSourceCommand`。
- **证据来源**：[derived-index-publication.service.ts](file://packages/server-ai/src/knowledge-document/derived-index-publication.service.ts)（类级 JSDoc 逐字 + `publish` 实现）

## D4 splitter / image-understanding 设置故意不进 transform 快照指纹

- **分类**：缓存失效边界 / 避坑
- **动机（避坑）**：**现象** —— splitter 与 image-understanding 设置都在「切片之前」的配置面上，若纳入快照指纹，动一下切片参数就会让快照失效。**后果** —— 每次调切片策略都退化为重跑转换器（含视觉模型），成本与耗时成倍上升，而转换器的输出其实完全可复用。
- **决策**：`computeKnowledgeDocumentTransformFingerprint` 只捕获「会改变转换器**切片前**输出」的设置（`sourceHash` / `metadata` / `sourceKey` / `sourceType` / `sourceConfig` / `type` / `category` / 文件标识 / `name` 等），splitter 与 image-understanding 设置排除在外。源码逐字：
  > `* Identifies the reusable converter result. Splitter/image-understanding settings are deliberately`
  > `* excluded because changing them must not invalidate a transform snapshot used for rechunking.`
- **背景约束**：快照在「切片前」边界持久化 NDJSON + 完整性 manifest；`rechunk` 模式复用快照、不调用转换器。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：出现某个 splitter 或 image-understanding 设置会改变转换器输出的场景。
- **关联代码**：`computeKnowledgeDocumentTransformFingerprint` / `resolveKnowledgeDocumentTransformerIdentity` / `computeKnowledgeDocumentProcessingHash`。
- **证据来源**：[document-hash.ts](file://packages/server-ai/src/knowledge-document/document-hash.ts)（`computeKnowledgeDocumentTransformFingerprint` 上方 JSDoc 逐字）

## D5 rechunk 遇到非法快照故意失败，而不是静默转换

- **分类**：失败语义 / 避坑
- **动机（避坑）**：**现象** —— 快照缺失/过期/损坏时，最省事的写法是「没快照就现跑一次转换器」。**后果** —— 用户以为在做 `rechunk`（只重切），实际上重跑了转换器与视觉模型，计费与耗时与预期不符，且不可从结果看出差异；同时让 `getReprocessCapabilities` 给出的 `rechunk.available/reason` 失去意义。
- **决策**：`load()` 仅在 `sourceHash` 与转换器 fingerprint 同时匹配时才可用，否则以 `TransformSnapshotUnavailableError` 的 `missing | stale | corrupt` 显式报错，**绝不回退去调用转换器**。源码逐字：
  > `* Restores converter output only when the source and converter fingerprint still match.`
  > `* Rechunk intentionally fails on invalid snapshots rather than silently running conversion.`
- **背景约束**：`rechunk` 的语义契约是「复用不可变快照」；能力探测由 `getReprocessCapabilities`（`POST :id/reprocess-capabilities`）对外暴露，调用方应据此决定是否降级为 `full`。
- **被否决方案**：无（源码未记录替代方案；但 D4 与 D5 共同说明「快照可复用性」是被刻意保护的边界）。
- **重新评估触发条件**：业务愿意接受「rechunk 自动降级为 full 并显式告知」的语义。
- **关联代码**：`KnowledgeDocumentTransformSnapshotService.load` / `getReprocessCapabilities` / `inspect`；`TransformSnapshotUnavailableError`；控制器 `GET :id/reprocess-capabilities`、`POST estimate`（持久化文档优先 `rechunk`，快照不可用才 `full`）。
- **证据来源**：[transform-snapshot.service.ts](file://packages/server-ai/src/knowledge-document/transform-snapshot.service.ts)（`load` 上方 JSDoc 逐字）

## D6 身份归一：语义检索有界且从不授权 merge；域/范围文本是证据不是分类

- **分类**：正确性边界 / 成本
- **动机**：实体归一要同时避免两个错：① 把「语义上像」误当「同一个」而合并掉不同实体；② 用本地字符串规则替 LLM 裁判做分类判断。
- **决策**：两条明写约束。
  1. 有界 + 不授权合并 —— 候选选择里，`identified`（标识符全等）与 `named`（名称/别名命中）**全部**返回（「Names retrieve every ambiguous match」），纯语义相似度只贡献有界的 `index < 8` 名额；语义相似度**仅用于排序**，不构成合并依据。
     > `// Names retrieve every ambiguous match. Semantic retrieval is bounded and never authorizes a merge.`
  2. 域/范围文本只作 LLM 裁判的证据 ——
     > `// Domain/scope text is evidence for the semantic judge, not a locally inferred taxonomy.`
- **背景约束**：LLM 裁判在事务外执行（`KnowledgeIdentityService` 顶部逐字：「`model calls never hold DB locks. Commit under the KB lock only if source and catalogue` …」）；回写前用 catalogue fingerprint 比对，不一致返回 `null` 重试（配 `KnowledgeIdentityBusy`）。观察记录而非任一投影拥有持久身份归属（「Observations, not either projection, own durable identity assignments.」）。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：候选规模增长到有界窗口明显漏召回；或 LLM 裁判延迟成为瓶颈需要更激进的本地预筛。
- **关联代码**：`canMatchIdentity` / `selectIdentityCandidates` / `identityText` / `cosineIdentitySimilarity`；`KnowledgeIdentityService.resolve`/`judge`/`lockSource`/`assertSource`。
- **证据来源**：[knowledge-identity-policy.ts](file://packages/server-ai/src/knowledgebase/identity/knowledge-identity-policy.ts)（两处注释逐字）；[knowledge-identity.service.ts](file://packages/server-ai/src/knowledgebase/identity/knowledge-identity.service.ts)（文件首两行 invariants）

## D7 面向 provider 的工具 schema 与 citation 输出故意精简

- **分类**：对外契约 / 避坑
- **动机（避坑）**：**现象 A** —— 把字段/操作符/类型的精确校验塞进工具 schema，会让模型侧承担本应由编译器承担的校验。**后果 A** —— 一次非法动态过滤会让 LangChain 在回退策略生效前直接拒掉整个工具调用，用户看到的是「工具报错」而非「过滤条件被忽略并回退到固定边界」。
  **现象 B** —— 让引用摘要复述 chunk metadata。**后果 B** —— 每次检索的返回体积随 metadata 膨胀，挤占模型上下文。
- **决策**：
  1. provider schema 保持紧凑，精确校验下放给 `KnowledgeFilterCompiler`，非法动态过滤安全回退到固定边界并记为 `invalid_dynamic_filter`；同时接受 `string`（`max 32_768`）形式以兼容把嵌套工具参数序列化成 JSON 文本的 OpenAI 兼容 provider。源码逐字：
     > `* Keep the provider-facing schema deliberately compact. Exact field/operator/type`
     > `* validation belongs to KnowledgeFilterCompiler, where an invalid dynamic filter`
     > `* can safely fall back to the fixed boundary and be audited as invalid_dynamic_filter.`
  2. 引用摘要剥离 metadata，只保留 Agent 与 citation URL 需要的紧凑 provenance。源码逐字：
     > `// Citation summaries deliberately avoid repeating chunk metadata. The chunk already`
     > `// carries the compact provenance needed by the Agent and citation URL.`
- **背景约束**：工具面由 `KnowledgeRetriever.toFilterOptionsTool` / `toFolderOptionsTool` / `toGraphExplorerTool` 生成；过滤可审计性由 `knowledge_retrieval_log` 的 `filterStatus` / `fallbackReason` 承载。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：接入的 provider 不再出现嵌套参数 JSON 文本序列化，可去掉 `string` 分支；或 citation 体积不再是瓶颈。
- **关联代码**：`createDynamicFilterToolInputSchema` / `resolveKnowledgeFilterOptionKind`；`formatKnowledgebaseRetrievalToolOutput` / `createKnowledgebaseCitationFromDocument` / `KNOWLEDGEBASE_CITATION_MARKDOWN_INSTRUCTION`。
- **证据来源**：[retriever.ts](file://packages/server-ai/src/knowledgebase/retriever.ts)（`createDynamicFilterToolInputSchema` 上方注释逐字）；[citation.ts](file://packages/server-ai/src/knowledgebase/citation.ts)（`formatKnowledgebaseRetrievalToolOutput` 内注释逐字）

## D8 自研 OOXML 处理（DOCX 编号 / PPTX 表格），不依赖现成 loader

- **分类**：解析保真 / 避坑
- **动机（避坑）**：**现象 A（DOCX）** —— Word 把列表与标题编号存在 `numbering.xml` 与 `w:numPr`，而段落文本 `w:t` **不含**这些生成的编号。**后果 A** —— 直接用现成 loader 时，编号后的段落内容丢失条目序号，切片后语义断裂。
  **现象 B（PPTX）** —— `PPTXLoader` 向 officeparser 要纯文本，该 reader 收集每个 `a:p` 却**从不**下探 `a:tbl/a:tr/a:tc`。**后果 B** —— 知识切片只看到段落，chunking 停留在 recursive-character，表格结构彻底丢失。
- **决策**：自研两个 OOXML 处理器。
  1. `docx-numbering.ts` —— 解析 `numbering.xml` + `w:numPr` 还原编号，并明写不变量：`numId 0` 关闭编号；每个 `numId` 独立计数器（新编号实例重新计数）；更浅级别会重置同 `numId` 的更深级别，除非 `lvlRestart` 为 0。
  2. `pptx-slides.ts` —— 走 `presentation.xml` 取幻灯片顺序，把 `graphicFrame` 表格转成 Markdown，输出 `contentFormat = markdown` 以便自动 chunking 能选到结构感知策略；**无表格的 deck 保留旧的纯文本 loader**（渐进增强，不破坏既有行为）。
- **背景约束**：两者都用 `JSZip` + `xmldom` 直读 OOXML 包；`pptx-slides` 返回 `Promise<Document<ChunkMetadata>[] | null>`，`null` 表示「本次不接管」。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：上游 loader（officeparser / LangChain PPTXLoader）开始下探表格或还原编号。
- **关联代码**：`loadDocxNumbering` 系列符号 / `DocxNumPr` / `DocxStyleNumbering`；`loadPptxStructuredMarkdown` / `PptxBlock` / `PackageRelationship`。
- **证据来源**：[docx-numbering.ts](file://packages/server-ai/src/knowledgebase/plugins/transformer-common/docx-numbering.ts)（`Why this exists` + `Invariants` 逐字）；[pptx-slides.ts](file://packages/server-ai/src/knowledgebase/plugins/transformer-common/pptx-slides.ts)（JSDoc 逐字）

## D9 删除/发布用 intent + cleanup receipt + publication attempt 三表（可恢复删除）

- **分类**：一致性策略 / 可运维性
- **动机（避坑）**：**现象** —— 硬删要跨三种存储（关系库行、向量表、Wiki 证据、图谱），任何一步的历史实现都是「先删外部产物、再删行」。**后果** —— 中途崩溃后无法判断某产物是否已删，`indeterminate`（结果未知）只能靠告警与人工，且不可自动重试。`[推测]` —— 把「不确定」升格为可查询的一类状态、而非隐式日志，是该契约设计的动机；源码未写明这一动机。
- **决策**：引入四表协议，状态集合显式包含 `indeterminate`：
  - `knowledge_document_deletion_intent.status ∈ prepared | written | promoted | compensated | indeterminate`，带租约（`lockedAt`/`leaseExpiresAt`）与**部分唯一** `(knowledgebaseId, sourceDocumentIdSnapshot) WHERE status <> 'completed'`；
  - `knowledge_document_deletion_cleanup_receipt.status ∈ pending | succeeded | failed | indeterminate`，唯一 `(intentId, receiptKey)`；
  - `knowledge_document_publication_attempt`（`producerKind` 覆盖 `document | chunk | graph | wiki | embedding_rebuild`，`artifacts` 每项带 `idempotencyKey`，带 `heartbeatAt`）；
  - `knowledge_document_publication_attempt_source`（唯一 `(attemptId, documentIdSnapshot)`）。
- **背景约束**：跨存储没有分布式事务可用；`hardDeletePendingAt` + `publicationEpoch` 构成 fail-closed 资格判断（读取侧统一 `hardDeletePendingAt IS NULL`）。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：编排服务落地（届时 `indeterminate` 有生产路径）；或存储层提供跨表的原子删除。
- **关联代码 / 当前状态（关键落差）**：四表由 `KnowledgeDocumentModule` 的 `TypeOrmModule.forFeature` 注册并经 `core/entities/index.ts` 导出，但**仓库内未找到任何写入/消费它们的服务**——当前硬删仍是 `deleteResolvedDocument` → `deleteDocumentArtifacts`（Wiki 撤回 → 向量删 → graph clear 失败仅告警）→ 物理删行 → `updateDocumentNumAfterDelete` 的顺序路径，**删除侧 `indeterminate` 无生产写入路径**；现成的人工补偿入口仅在 Wiki/Graph 侧（`GET :knowledgebaseId/wiki/status` 的 `recoveryActions`）。
- **证据来源**：[deletion/entities.ts](file://packages/server-ai/src/knowledge-document/deletion/entities.ts)；[document.module.ts](file://packages/server-ai/src/knowledge-document/document.module.ts)；[document.service.ts](file://packages/server-ai/src/knowledge-document/document.service.ts)（`deleteResolvedDocument` / `deleteDocumentArtifacts` / `readableDocumentWhere`）；[knowledge-wiki.service.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki.service.ts)（`getInvocationStatus` / `toRecoveryAction`）

## D10 Wiki 是 KB 上的派生索引，其配置与状态列挤在 `knowledgebase` 表

- **分类**：数据归属 / 演进
- **动机**：无明写依据。可见的结构性事实是：Wiki 配置与状态以 `wikiConfig / wikiStatus / wikiAvailability / wikiActiveRevision / wikiStagedRevision / wikiConfigFingerprint / wikiRebuildRequiredReason / wikiBuildError / wikiGeneratorVersion` 九列直接挂在 `knowledgebase` 行上，而页面内容全部落在 15 张 `knowledge_wiki_*` 表。`[推测]` —— 这样能让「Wiki 是否就绪/是否需要重建」与 KB 的其他状态在同一行内被一次读取，避免为状态机再开一张单行表。
- **决策**：把配置与状态当作 KB 行的一部分（`knowledgebase` 表），把内容与 job 台账当作独立派生面（`knowledge_wiki_*` 15 表）。
- **背景约束**：`KnowledgebaseModule` 与 `KnowledgeWikiModule` 各自 `RouterModule.register({ path: '/knowledgebase' })`，靠 `@Controller(':knowledgebaseId/wiki')` 段区分——状态列与接口同处一个前缀空间。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：`knowledgebase` 表状态列继续增长（例如 GraphRAG / 关键词 / FAQ 也各自堆状态列）导致行宽与写竞争成为问题；或需要按 KB 独立审计 Wiki 状态变更历史。
- **关联代码**：`Knowledgebase.wikiConfig / wikiStatus / wikiAvailability / wikiRevision / wikiActiveRevision / wikiStagedRevision / wikiConfigFingerprint / wikiGeneratorVersion / wikiRebuildRequiredReason / wikiBuildError`；`KnowledgeWikiService.getStatus` / `updateConfiguration`。
- **证据来源**：[knowledgebase.entity.ts](file://packages/server-ai/src/knowledgebase/knowledgebase.entity.ts)（wiki* 列）；[knowledge-wiki.module.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki.module.ts)；[knowledge-wiki.service.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki.service.ts)
