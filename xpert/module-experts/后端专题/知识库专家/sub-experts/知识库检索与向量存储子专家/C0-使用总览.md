## 1 定位

本子专家是知识库域的「资产 + 出口」面：以 `Knowledgebase` 为聚合根管理作用域、可见性、模型绑定与结构化过滤定义；把「向量 + 关键词 + 图谱」三路召回组装成一次可调参、可审计、可重排的检索；并以唯一入口 `KnowledgeDocumentStore` 读写向量，以 `rag-vstore` 抽象具体向量库（PGVector 是当前落地分支）。摄取与切片加工不在本子专家，见子专家②。

## 2 何时找这个子专家

- 要**建 / 改 / 删知识库**，设置可见性（Private / Organization / Public）、绑 embedding / rerank / chat / vision 模型，定义 `metadataSchema` 与默认 `recall`。
- 要**确认某次列表为何看得见 / 看不见**：`my`、`public`、`pagination`、`count`、`by-workspace` 五套口径。
- 要**调检索参数并定位召回质量**：召回模式、`topK`、相似度阈值、重排模型与阈值、融合策略与权重、内容范围、结构化过滤层。
- 要**看检索日志做归因**：`filterStatus` / `fallbackReason` / `candidateChunkCount` / `vectorLatency` / `diagnostics`。
- 要**换 embedding 模型并重建向量**，或处理「重建中写操作被阻断」「新旧 collection 并存」。
- 要**选 / 查向量存储实现**，或排查「新环境首查缺表」「向量表不在 `synchronize` 视野内」。
- 要**用标签做过滤候选**：KB 级标签选中、文档手工打标、标签引用分页。
- 要**取向量读写句柄做二次加工**：`getActiveVectorStore` / `getGraphEntityVectorStore` / `getPendingVectorStoreForRebuild`。

## 4 边界

**做什么**：知识库作用域 / 可见性 / 模型绑定 / 结构化过滤定义；三路召回 + 融合 + 重排 + 引用投影；向量读写唯一入口与向量存储抽象（含 PGVector 分支的运行期建表）；标签选中与引用分页；卷内文件上传与预览；KB 级长任务台账。

**不做什么**
- **摄取与切片不在本子专家**：上传 / 批量 / 增量同步、解析切片、摄取状态机、chunk 增删与重处理归 [子专家②](../文档摄取与流水线子专家/C0-使用总览.md)。
- **图谱与知识身份不在本子专家**：`graphrag/`、`knowledgebase/identity/` 归 [子专家③](../GraphRAG与知识身份子专家/C0-使用总览.md)；本子专家只提供 `getGraphEntityVectorStore` 句柄与图谱召回源装配。
- **Wiki 与知识组织不在本子专家**：`knowledgebase/wiki/` 归 [子专家④](../知识Wiki与知识组织子专家/C0-使用总览.md)。
- **FAQ 端点明细不重复**：`KnowledgeFAQController` / `KnowledgeFAQService` 物理上挂在 `KnowledgebaseModule`，端点口径归父域 C1。
- **不含模型访问与计费**：只取 embedding / rerank / chat / vision 句柄，不实现推理、不判额度。
- **不含文件字节与沙箱**：只持文件引用与卷内相对路径，归属校验委托 `UploadFileCommand` 与文件域。

## 5 已知问题与常见坑

1. **绝大多数路由没有 `@UseGuards`**
   - 现象与触发：`KnowledgebaseController` 仅 9 个路由带 `PermissionGuard` + `KNOWLEDGEBASE_EDIT`（`keyword-analyzers`、`vector-stores`、`findAll`、`count`、`pagination`、`createTask`、`processTask`、`uploadFile`、`statistics/knowledgebases`），2 个带 `WorkspaceAuthoringGuard`（`preview-chunks`、`by-workspace/:workspaceId`）；标签 / FAQ / 文档 / 题目 / 图谱 / Wiki 控制器零声明式守卫。
   - 正确做法：把 service 断言当唯一授权边界（`assertKnowledgebaseWriteAccess` / `assertKnowledgebaseTaskWriteAccess` / `canManageKnowledgebase`）；新增查询绕过断言即产生越权。
   - 契约来源：`KnowledgebaseController`、`KnowledgebaseService.assertKnowledgebaseWriteAccess`。
2. **`tag-usage` 与 `:id` 的路由遮蔽**
   - 现象与触发：`GET /api/knowledgebase/tag-usage` 返回 400（UUID 校验失败）而非 404。合法形态是两段的 `/api/knowledgebase/tag-usage/:tagId`；`KnowledgebaseModule.controllers` 的注册序列为 `[KnowledgebaseController, KnowledgeFAQController, KnowledgeTagController, KnowledgeTagUsageController]`，同层单段的 `@Get(':id')` 在主控制器内且该控制器排最前。
   - 正确做法：不要按单段调用。同控制器内的 `keyword-analyzers` / `vector-stores` 之所以安全，是因为声明在 `:id` 之前——新增单段路由必须确认声明顺序，或改用具名前缀。
   - 契约来源：`KnowledgeTagUsageController`、`KnowledgebaseController`、`KnowledgebaseModule.controllers`。
3. **库级前缀的实际形态是 `/api/knowledgebase/:id/...`**
   - 现象与触发：按 `/api/:knowledgebaseId` 拼路径会 404。知识库主模块 / GraphRAG / Wiki 三个模块各自 `RouterModule.register({ path: '/knowledgebase' })`，库级段靠控制器段（`:knowledgebaseId`、`:id/graph`、`:knowledgebaseId/wiki`）区分。
   - 正确做法：库级资源一律写作 `/api/knowledgebase/<kbId>/...`；三模块共前缀下新增同层单段控制器极易与 `:id` 冲突。
   - 契约来源：`KnowledgebaseModule`、`GraphragModule`、`KnowledgeWikiModule` 的 `RouterModule.register`。
4. **向量表不是 TypeORM 实体（运行期建表）**
   - 现象与触发：`synchronize` 视角看不到 `knowledge_document_vector` / `knowledge_document_collection`，新环境首查报缺表；两表由 `RagCreateVStoreHandler.createPgVectorStore` 运行期 `ensureTableInDatabase()` / `ensureCollectionTableInDatabase()` 创建，写入走 `ON CONFLICT ... DO UPDATE SET`（注释：「Upsert atomically; never delete a published vector before its replacement succeeds.」）。
   - 正确做法：新环境预热一次向量化路径；维度不匹配只能走重建 + 新 collection，不要指望 `synchronize`。
   - 契约来源：`RagCreateVStoreHandler.createPgVectorStore`、`KnowledgePGVectorStore`（`knowledge-pg-vector.store.ts`）。
5. **`assertNotRebuilding` 只在 `REBUILDING` 时阻断**
   - 现象与触发：判据逐字为 `knowledgebase.status === KnowledgebaseStatusEnum.REBUILDING`，`rebuild_failed` **不**被该断言拦截。
   - 正确做法：把 `rebuild_failed` 视为需立即人工介入的状态（pending 模型与错误列仍在），按 `cancelPendingEmbeddingModel` 回退后再恢复写入，不要依赖断言兜底。
   - 契约来源：`KnowledgebaseService.assertNotRebuilding`。
6. **切模型期间新旧 collection 并存**
   - 现象与触发：存储占用短时接近 2×。active = `knowledgebase.embeddingCollectionName ?? knowledgebase.id`；重建期用 `pendingEmbeddingCollectionName`；图谱实体向量是 `` `${activeCollectionName}:graph-entities` ``。
   - 正确做法：按 2× 预留容量；估算时把图谱实体 collection 一并算入，不要按单一 collection 估。
   - 契约来源：`KnowledgebaseService.getActiveVectorStore` / `getGraphEntityVectorStore` / `getPendingVectorStoreForRebuild`。
7. **`vectorStore` 创建后不可变更**
   - 现象与触发：更新知识库时改向量存储类型返回 400。`VectorStoreSettingsService.assertUnchanged` 在 `requested !== (current ?? environment.vectorStore)` 时抛 `Error.KnowledgeVectorStoreImmutable`；`forCreate` 对未注册的 `MILVUS` 抛 `Error.KnowledgeVectorStoreUnavailable`。
   - 正确做法：向量存储类型只在建库时决定；迁移只能新建知识库并重新摄取。
   - 契约来源：`VectorStoreSettingsService`、`KnowledgebaseController.vectorStores`。
8. **`keywordAnalyzer` / `keywordAnalyzerLocked` 普通保存不生效**
   - 现象与触发：改了关键词分析器配置，回读仍是旧值。两列声明为 `update: false`，实体注释逐字：「Conditional SQL owns these fields; ORM saves must not restore stale analyzer state.」。
   - 正确做法：走知识库更新中携带关键词分析器的分支（内部转交 `KnowledgeKeywordAnalyzerService`）；外部知识库类型会被强制置空。
   - 契约来源：`Knowledgebase` 实体、`KnowledgeKeywordAnalyzerService`。
9. **知识库重名是唯一键冲突**
   - 现象与触发：创建 / 改名返回可读的「名称已存在」而非 500；同一租户 + 组织下库名唯一，PostgreSQL `23505` 被翻译为 `BadRequestException`（i18n `xpert.Error.NameExists`）。
   - 正确做法：按业务错误处理；跨工作区同名仍会冲突，需改名或复用既有库。
   - 契约来源：`KnowledgebaseService` 内的 `23505` 翻译逻辑。
10. **融合策略双轨（RRF 默认 / legacy）**
   - 现象与触发：同样的权重在两次检索中表现不一致。默认 `WeightedRrfFusion`，可切 `LegacyWeightedFusion`；`contentScope === 'wiki'` 或图谱未启用时 graph 权重被置 0。
   - 正确做法：入口先做权重校验（有限且非负）；改融合模式时把 `contentScope` 与图谱启停一起纳入回归。
   - 契约来源：`WeightedRrfFusion` / `LegacyWeightedFusion`、`packages/contracts/src/ai/knowledgebase.model.ts`（`defaultRecall`）。
