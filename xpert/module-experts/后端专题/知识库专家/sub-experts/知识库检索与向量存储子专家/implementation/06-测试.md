## 5. 缺口

1. **融合策略双轨的交叉覆盖不足**：`weighted-rrf.fusion.spec.ts` 与 `legacy-weighted.fusion.spec.ts` 各自充分，但 `LegacyWeightedFusion` **只消费 vector / graph 两个 batch**，旧路径下 keyword 分支是否被忽略、以及 `fusion.mode` 从 `weighted_rrf` 切换到 legacy 时的行为差异，未见专门套件（`knowledge-search.handler.spec.ts` 只做了 `fusionMode` 的正/反断言）。
2. **重建链的自动化覆盖偏单元**：`knowledgebase-rebuild-embedding.job.spec.ts` 覆盖消费者，`embedding-state.spec.ts` 覆盖状态机，但 `processEmbeddingRebuildJob` 的**分批写入顺序、FAQ / 问题向量分支、`recordRebuiltQuestionVectors` 回写**与 `promoteEmbeddingRebuild` 的事务内 chunk metadata 批量回写，没有对应 spec；`cleanupEmbeddingCollection` 的 fire-and-forget 容错路径也无断言。
3. **维度 / collection 切换的端到端缺位**：`createCollectionScopedVectorId` 有单元覆盖（`vector-store.spec.ts`），但「换模型 → pending collection 写入 → 提升 → 旧 collection 清理」这条跨 DB + 向量库的链路没有集成测试；维度不匹配的报错面同样无断言。

## 6. 结论

- **覆盖结构**：本子域 89 个套件中 **87 个为纯单测**（无需外部依赖），2 个 PG 门控集成套件 + 1 个 PG 门控的 tag 集成套件构成 DB 行为面；重心明显落在 `KnowledgebaseService`、检索编排（`queries/handlers/` 7 个合计 ~110 KB）与融合器上。
- **可跑性**：配置齐备（`jest.config.ts` + Nx `test` target），单文件与目录级命令均可构造；**本次未执行 jest，「是否通过」未确认**。
- **默认 skip 的 3 个开关**：`KNOWLEDGE_KEYWORD_PG_E2E=1`、`KNOWLEDGE_WIKI_PG_E2E=1`、`KNOWLEDGE_TAGGING_PG_URL`；前两个覆盖本子域最关键的 PG 行为（FTS/trigram 索引、pgvector 幂等 upsert 与结构化检索）。
- **建议的最小回归集**（全为纯单测）：`knowledgebase.controller.spec.ts` + `knowledgebase.service.spec.ts` + `retrieval/weighted-rrf.fusion.spec.ts` + `retrieval/vector-knowledge-candidate.retriever.spec.ts` + `queries/handlers/knowledge-search.handler.spec.ts` + `vector-store.spec.ts` + `rag-vstore/commands/handlers/create.handler.spec.ts`。
- **最高优先补齐项**：① `processEmbeddingRebuildJob` / `promoteEmbeddingRebuild` 的专项单测（可用假 `KnowledgeDocumentStore` + `dataSource.transaction` stub）；② `LegacyWeightedFusion` 路径下 keyword 分支的显式断言；③ `RagCreateVStoreHandler` 的 `UnsupportedVectorStore` 分支。
