## 1. 生成链逐段

### 1.1 map 段
`enqueueSource` 先校验 `wikiConfig.enabled` 与源文档 eligibility：不合格直接转 `RetractionService.enqueue`；合格则按 `lifecycleGeneration+1` 写 `_source_state`，若指纹不一致或处于 `rebuild_required` 只写 `generationPendingReason='full_rebuild_required'` 并返回 null。否则 `invalidateSourcePages` 把该来源的贡献页置为待重建，jobKey 形如 `source:{docId}:{lifecycle}:{revision}:{fingerprint}`，落 `source_map` 任务并把 KB 置 `indexing`。`processSourceMap` 在租约保护下调用 `invokeMapModel` 分批产出候选页，写入 `_source_map_result`（含 `candidateKey`、`normalizedPageKey`、`identity`、`identityEmbedding`、`identityDecision`、`payload`）。

章节来源：[knowledge-wiki-generation.service.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki-generation.service.ts)（关键符号：KnowledgeWikiGenerationService.enqueueSource / KnowledgeWikiGenerationService.processSourceMap）

### 1.2 identity → reduce 段
`KnowledgeWikiPageSchedulerService.completeMap` 在 pipeline 锁内把 map 置 `succeeded`（失败抛 `knowledge_wiki_identity_stale`），rebuild 需等所有 `source_map` 子任务不再非成功，才建 `identity_resolve` 子任务。`schedulePages` 汇总 `normalizedPageKey`（rebuild 额外并入既有 pageKey，增量额外并入旧 contribution 的 pageKey），为每个 key 建 `reduce:{hash(pageKey).slice(0,20)}` 子任务，并建 1 个 `finalize` 子任务（延迟 1000ms 派发）。`KnowledgeWikiPageReduceService.process` 用 `prepareReduceSources` 组合「活跃版本的既有 contribution」与「本次 map 结果合并去重」的载荷，且要求源文档 `eligible`、`lifecycleGeneration` 与 `lastContentHash` 匹配；evidence 由「命中的 chunk 内容 + fact 序号」生成，无 evidence 的源被丢弃。输入指纹变化时旧 `_page_reduce_input` 置 `stale` 且 `generationAttempt+1`，再写 `_page_version`（`building` / `pending`）+ `_page_contribution` + `_page_evidence`。

章节来源：[knowledge-wiki-page-reduce.service.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki-page-reduce.service.ts)（关键符号：KnowledgeWikiPageReduceService.process / KnowledgeWikiPageSchedulerService.schedulePages）

### 1.3 finalize → projection 段
`KnowledgeWikiFinalizeService.process` 等待全部 reduce 子任务成功（未完成则 1500ms 后重新入队）；rebuild 场景额外校验 `maps.length === expectedChildren` 且不允许空发布（`knowledge_wiki_empty_publication`）。随后 `KnowledgeWikiIndexService.prepare` 生成 root 与按类型的索引页及其链接；冲突检测命中 `page.version !== version.expectedPageVersion` 时走 `recoverConflict`（整任务 `generationAttempt+1`、受限的 reduce 子任务重置入队、上限 3 次）。投影在事务外 `ProjectionService.stage`：复用 `sourceKey='system:knowledge-wiki'` 的系统文档，用 `uuidv5` 稳定 chunk id 与 `wikiPageVersionId` 元数据，捕获 23505 竞态，再写向量库；失败仅把版本标 `projectionStatus='failed'` 并抛 `knowledge_wiki_index_failed`。发布事务先锁 KB、按 pageId 排序逐页悲观锁，推进页面指针与 `wikiActiveRevision`，并按需清 `wikiStagedRevision`。

章节来源：[knowledge-wiki-finalize.service.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki-finalize.service.ts)（关键符号：KnowledgeWikiFinalizeService.process / KnowledgeWikiProjectionService.stage）

### 1.4 投影回收与 retraction
`retireSupersededVersions` 找出「已发布但不再 active」的版本并 `retireVersions`（删向量 + 删 chunk + 标 `disabled`），失败只写 `projectionError` 以等待下一轮。`KnowledgeWikiRetractionService.enqueue` 递增 `lifecycleGeneration`、置 `eligible=false` / `cleanupPending=true`、把相关页置 `stale` / `disabled`、创建 `retract` 任务；`process` 校验生命周期与 eligible 后退役该来源的贡献版本；若 wiki 已关闭或需全量重建，则只清 `cleanupPending` 并在启用时置 `generationPendingReason='full_rebuild_required'`；否则建 reduce + finalize 子任务重算页面。

章节来源：[knowledge-wiki-retraction.service.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki-retraction.service.ts)（关键符号：KnowledgeWikiRetractionService.enqueue / KnowledgeWikiProjectionService.retireSupersededVersions）

## 2. 后台自愈与调度
- `KnowledgeWikiReconcilerService.reconcile` 以 `@Interval(30_000)` 触发，单实例串行（`running` 标志），每轮：回收被取代的 job、重派 `dispatchError` 或从未派发的 queued job、把过期租约的 running job 归还 queued 并重派、回收投影、回写 KB 失败状态（区分 `degraded` / `unavailable`、`wikiBuildError` 取最新失败原因）、判定生成器版本升级并写 `rebuild_required` + `generator_upgrade`。
- `KnowledgeWikiRebuildCoordinatorService.scheduleAfterMap` 在最后一个 `source_map` 结束时触发 `scheduleIdentity`。
- 派发侧 `KnowledgeWikiJobDispatcherService.dispatch` 缺计费主体或租户时直接把任务判失败（`missing_billing_principal`），入队异常则记 `dispatchError` 并把 `dispatchAfter` 推迟 30s。
- 任务键与幂等：子任务全部用 `jobKey` 前缀派生（`pipeline.jobKey + ':' + suffix`），`ensureJob` 命中即复用。

章节来源：[knowledge-wiki-reconciler.service.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki-reconciler.service.ts)（关键符号：KnowledgeWikiReconcilerService.reconcile / KnowledgeWikiJobDispatcherService.dispatch）

## 3. 重建与重试
- 重建：`rebuild` 先校验写权限与启用状态，`assertRebuildSources` 校验源可重建；非空 KB 必须 `confirmModelCharges=true`；`revision = max(wikiRevision, wikiActiveRevision) + 1`，jobKey 为 `rebuild:{revision}:{fingerprint}`，并写 `spendEnvelope`（默认 `documents.length × 20` 次调用 / `× 200000` estimatedTokens，上限 10000 与 1e8）；KB 置 `indexing`、`wikiStagedRevision=wikiRevision=revision`。`processRebuild` 为每个合格文档建 `source_map` 子任务。
- 重试：`retry` 只接受 `isCurrent` 且状态为 `failed` 的任务；存在 `indeterminate` 调用时必须 `confirmAdditionalModelCharge=true`；存在 `model_response_invalid` 失败调用时先 `settleFailedResponseBilling`；命中其一则 `generationAttempt+1`，清空错误后重新入队。
- HTTP：`POST rebuild`、`POST jobs/:jobId/retry`；`updateConfiguration` 在配置更新后若处于 `rebuild_required` 且已确认费用，会自动触发重建并就地调整返回对象状态。

章节来源：[knowledge-wiki.controller.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki.controller.ts)（关键符号：KnowledgeWikiController.rebuild / KnowledgeWikiGenerationService.retry / KnowledgeWikiService.updateConfiguration）

## 4. 组织面
- taxonomy 开关：`OrganizationService.configure` 在事务内锁 KB，校验 `revision` 后自增，用于分类任务的版本一致性。
- 目录：`saveFolder` / `deleteFolder` 锁 KB 后校验目录数上限 200、同父级重名（NFKC 小写比较）、环路（`validateWikiFolderMove`），并以 `version` 乐观锁拒绝过期写入；删除前必须无子目录且无页面。
- placement：`movePage` 拒绝 `index` 页，只写 `source='manual'`，以自身 `version` 做乐观锁；分类任务写 `source='automatic'`。
- 分类 run：`start` 要求已开启 taxonomy 且有目录，可 `unclassifiedOnly`，返回 `runId`；`status` 返回活跃任务数；`list` 以 `runId` 聚合结果并标注陈旧；`apply` 按 `jobIds` 将结果落为 placement；`process` 在 REPEATABLE READ 快照取页面与目录、锁 KB 后写 placement 与任务终态。
- 自动分类：发布事务内 `enqueuePublished`；有目录时逐页建分类任务，无目录时按修订号复用/新建 taxonomy 任务（首 100 页 + `pendingPublications` 累积余量）。

章节来源：[knowledge-wiki-organization.service.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki-organization.service.ts)（关键符号：KnowledgeWikiOrganizationService.saveFolder / KnowledgeWikiClassificationService.apply / KnowledgeWikiTaxonomyService.enqueuePublished）

## 5. 浏览面
- 列表分流：控制器 `GET pages` 在 `status` 为空或 `ready` 时走 `KnowledgeWikiBrowseService.list`（可见页过滤 + 目录/搜索/分页），其余状态走 `KnowledgeWikiService.listPages`（诊断路径，需写权限）。
- 详情：`GET pages/:pageId` 组合 `KnowledgeWikiService.getPage`（含 evidence、`sourceAvailable`、反链）与 `KnowledgeWikiBrowseService.placement`。
- 链接：`resolveLinks` 只解析到「ready 且有 activeVersionId」的目标页，返回 `pageId` / `slug` / `title` / `pageType` / `sectionAnchor` / `label`。
- 图谱与目录树：`browse.graph`（REPEATABLE READ，节点限额 + 边过滤）与 `browse.taxonomy`（目录树 + `pageCount` + `unclassifiedCount`）。

## 6. 与身份的对接
`KnowledgeWikiIdentityResolverService` 是身份子域的适配层：`process` 依据 map 结果构建候选（`candidateKey` / `canonicalName` / 别名 / 描述 / facts / embedding），`assertCurrent`（锁 KB + worker CAS）与 `assertSources`（文档与 source state 双重校验）负责并发与来源有效性，`savePage` 在事务内按 `pageKey` / `identityId` 落地规范页并写入计数与投影初值。链接建议阶段通过 `loadIdentityCatalogue` 取身份别名，扩展目标匹配面，再按「唯一匹配」或索引页 key 决定是否落 `_page_link`。

## 7. 清理与状态读取
- `getStatus`：未获管理权限时返回只读视图（`enabled` / `status` / `availability` / `readyPageCount` / `requiresManagement`）；有权限时额外返回 active/staged revision、active/target 指纹、任务分档计数、页面分档计数、`indeterminateInvocationCount`、`billingRecoveryCount`、`cleanupPendingCount`、`cleanupFailedCount` 与 `recoveryActions`。
- `getDocumentStatus`：在 `REPEATABLE READ` 事务内以同一快照计算发布可见性与逐文档进度。
- `getSourceCleanupStatus` / `getInvocationStatus`：分别按 `_source_state` 的清理标志与 `_model_invocation` 的对账状态统计；恢复动作通过 `toRecoveryAction` 归一（是否可重试、是否需要额外费用确认、输入是否仍有效、推荐动作）。
- `getScope` 统一读取 KB 的 wiki 列与模型关系，作为所有读路径的入口。

## 8. 设计模式
- map-reduce：源级 map（`_source_map_result`）→ 页面级 reduce（`_page_version` + evidence），并以 job 树（root / parent / 子 jobKey）表达依赖。
- 投影：wiki 页面被投影为 KB 内部系统文档的 chunk，复用既有向量与检索设施，而非另建索引。
- reconciler：固定周期扫描 + 单实例串行 + 批量上限，把「派发失败 / 租约过期 / 投影残留 / 版本升级」统一收敛。
- 策略与指纹：配置 + 生效模型 → `configFingerprint`，任务与版本都携带指纹，指纹变化即视为需要重建。
- fence/CAS + 锁序：worker 每次推进前 `jobFence.assert`，发布事务固定「KB → page」锁序，指针更新用乐观版本条件，冲突有界重试。
- 乐观锁 + 悲观锁混用：组织面用 `version` 乐观锁 + KB 悲观锁自增 revision。

章节来源：[knowledge-wiki-config.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki-config.ts)（关键符号：createKnowledgeWikiConfigFingerprint / KnowledgeWikiJobFenceService.assert）

## 9. 热点路径
- 模型调用成本：map 按 chunk 分批、reduce 按页聚合，`_model_invocation` 逐次记录 request / 用量 / 计费状态，`spendEnvelope` 提供预算上限，是整条链最贵的部分。
- 页面查询：`_page` 有 3 个唯一索引 + 组合索引，列表默认只取 `ready` 且有 `activeVersionId`，搜索走 `canonicalName` / `slug` 的 ILIKE。
- 反链计数：`LinkService.refreshCounts` 对每个页面各做 2 次 count（入/出），页面数量增长时是典型 N+1 形态，只在发布末尾调用一次。
- 分类：`getStatus` 与 `reconciler` 均有固定批量上限（50），避免单轮扫描放大。

## 11. 技术债
- **KB 表列爆炸**：wiki 的 10 个状态列 + `wikiModelId` 挤在 `Knowledgebase` 上，与「wiki 是派生索引」的定位存在张力，一致性只能靠 `assertNoClientWikiState` 白名单与调用方自觉维持。
- **人工确认路径**：重建非空 KB、重试含 `indeterminate` 调用的任务、变更非空 KB 的生成配置三处都要求显式确认，任何一处缺失都会让任务停在中间态。
- **evidence 快照语义**：`sourceDocumentIdSnapshot` / `sourceChunkIdSnapshot` 是无外键的 UUID 快照，判断来源可用性必须与 `_source_state` 组合，容易被误用为「一定存在的引用」。
- **分类 run 幂等**：`apply` 依赖 `jobIds` + placement `version` 乐观锁，重复应用会以冲突形式失败，需要调用方处理重放。
- **无 KB 外键的三张表**：`_page_reduce_input`、`_page_reduce_input_source`、`_source_map_result` 只有裸 `knowledgebaseId` 列，KB 删除时无 DB 级联。
- **组织面服务不导出**：模块只导出 `KnowledgeWikiService` 与 `KnowledgeWikiGenerationService`，组织/分类能力的外部复用必须另开边界。

## 12. 设计维度
- 一致性维度：发布强一致（单事务 + 锁序 + 乐观版本）vs 派生弱一致（投影回收、分类、计数刷新均可滞后重试）。
- 成本维度：模型调用逐次记账 + 预算信封 + 三处费用确认，把「贵操作」显式暴露给用户而非默认执行。
- 幂等与重放维度：jobKey 派生命名、`inputFingerprint` 复用已付费结果、`generationAttempt` 隔离尝试、`executionAttempt` 做 worker CAS。
- 权限维度：读路径分 `reader` / `management` 两档，诊断类页面查询与非 ready 状态过滤强制写权限。

## 13. 结论
实现的核心思路是「把不可靠的网络与模型调用包在可重放的 job 图里，只在最后一步做一次强一致发布」：map / identity / reduce / finalize 四类任务通过 jobKey 与指纹形成可恢复的 DAG，发布事务负责指针推进与状态归一，reconciler 负责补漏，retraction 负责回收。组织与分类作为发布后的弱一致副作用，用 revision + version 双重乐观锁保证用户手工调整不被自动分类覆盖；成本通过 `_model_invocation` 与预算信封显式管理。主要技术债集中在 KB 表的状态列归属与人工确认路径，属于可维护性而非正确性风险。
