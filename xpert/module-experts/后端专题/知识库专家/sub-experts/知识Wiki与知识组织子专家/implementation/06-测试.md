## 1. 测试布局
- 目录 `packages/server-ai/src/knowledgebase/wiki/` 下共 **33 个 spec 文件**，另加 `entities/knowledge-wiki.entities.spec.ts`，合计 **34 个**。
- 其中 **7 个为集成 spec**（`:knowledge-wiki-document-status.integration.spec.ts`、`:organization.integration.spec.ts`、`:persistence.integration.spec.ts`、`:projection-cleanup.integration.spec.ts`、`:publication-lock.integration.spec.ts`、`:reconciler.integration.spec.ts`、`:recovery.integration.spec.ts`），其余 27 个为纯单元/组件 spec（含实体元数据 spec）。
- 组织方式：服务级 spec 用构造函数手工装配依赖（`new KnowledgeWikiXService(deps as never)`），集成 spec 自建 `DataSource` 并只用 `pg_temp` / 随机 schema 下的夹具实体。

## 2. 单元与组件 spec 覆盖点

### 2.1 生成链
- `knowledge-wiki-generation.service.spec.ts`：写权限、启用校验、费用确认等入口断言（`describe('KnowledgeWikiGenerationService access')`）。
- `knowledge-wiki-generation.stages.spec.ts`：worker 在抽取前后的阶段行为（`describe('Wiki worker stage behavior before and after extraction')`）。

- `knowledge-wiki-page-scheduler.service.spec.ts`：Map → identity → Reduce 调度与子任务命名（`describe('Wiki Map -> identity -> Reduce scheduling')`）。
- `knowledge-wiki-page-reduce.service.spec.ts`：发布冲突后的 reduce 复用、来源材料解析（两个 describe）。

- `knowledge-wiki-identity-resolver.service.spec.ts`：身份解析适配层行为（`describe('Wiki adapter for shared knowledge identity')`）。
- `knowledge-wiki-link.service.spec.ts`：身份解析后的链接落地（`describe('Wiki links after identity resolution')`）。

## 3. 集成 spec（默认 skip）
- 统一模式：文件顶部用 `process.env.KNOWLEDGE_WIKI_PG_E2E === '1' ? describe : describe.skip`；组织面集成改用 `process.env.WIKI_V15_PG_URL ? describe : describe.skip` 并直接把该 URL 传给夹具。

## 4. 运行命令与实测
- 命令来源：`packages/server-ai/project.json` 的 `test` target 使用 `@nx/jest:jest`，`jestConfig` 指向 `packages/server-ai/jest.config.ts`；因此常规命令为 `nx test server-ai`（工作区内也可用 `pnpm nx test server-ai`）。
- 按文件或模式过滤：`nx test server-ai --testPathPattern=knowledgebase/wiki`；单文件：`nx test server-ai --testPathPattern=knowledge-wiki-generation.stages.spec.ts`。
- 开启 PG 集成：在环境中设置 `KNOWLEDGE_WIKI_PG_E2E=1`（组织面用 `WIKI_V15_PG_URL`）后重复上述命令。
- 配置要点：`jest.config.ts` 设定 `displayName: 'server-ai'`、`testEnvironment: 'node'`、`ts-jest`（`tsconfig.spec.json`）+ `moduleNameMapper` 把 `@xpert-ai/server-core` / `@xpert-ai/contracts` 等映射到源码。
- **实测状态**：本轮为只读检索任务，未执行 jest，也没有可引用的运行输出；以上命令与配置均来自仓库文件本身，实际通过/失败结果需在可运行环境复核。

## 6. 缺口
- **生成链端到端缺失**：没有覆盖「enqueueSource → source_map → identity_resolve → page_reduce → finalize → 发布 → 分类入队」全链路的集成用例；跨阶段一致性（job 树收敛、指纹变化触发重建、revision 推进）只能靠单段 spec 与集成片段间接推断。
- **分类 run 的幂等未覆盖**：`classification-runs/apply` 的重复应用、`pendingPublications` 累积、taxonomy revision 变更下的重放均无用例；同时「已发布但未分类」的中间态在读模型上的表现也无断言。
- **清理与撤回链不完整**：`retireSupersededVersions` 失败重试路径（只写 `projectionError` 的降级分支）与 `RetractionService.process` 的「wiki 已关闭 / `rebuild_required`」分支缺少集成验证；`cleanupFailed` 的置位与清除缺少断言。
- **`requiresAdditionalChargeConfirmation` 人工路径**：重试与重建的确认分支只有入口级断言，缺少「存在 indeterminate 调用时未确认必须被拒」的端到端用例。
- **实体覆盖不全**：`knowledge-wiki.entities.spec.ts` 未覆盖 `knowledge_wiki_taxonomy` / `knowledge_wiki_folder` / `knowledge_wiki_placement`，这是本子域表数量口径容易被写成 14 的直接诱因。
- **无 KB 级联的裸列无测试**：`_page_reduce_input`、`_page_reduce_input_source`、`_source_map_result` 在 KB 删除场景下无级联断言。

章节来源：[knowledge-wiki-retraction.service.spec.ts](file://packages/server-ai/src/knowledgebase/wiki/knowledge-wiki-retraction.service.spec.ts)（关键符号：KnowledgeWikiRetractionService.process）+ [knowledge-wiki.entities.spec.ts](file://packages/server-ai/src/knowledgebase/wiki/entities/knowledge-wiki.entities.spec.ts)（关键符号：tableNames 断言）

## 7. 结论
本子域的测试密度高：34 个 spec 覆盖了配置指纹、模型输出边界、调度命名、reduce 复用、发布冲突恢复、撤回、状态读与组织面写入，且把「必须真实 PG 才能验证的部分」（锁序、投影回收、恢复 SQL、组织乐观锁）单独隔离为 7 个默认 skip 的集成 spec。主要不足不在用例数量而在**链路完整性与人工确认路径**：全链端到端、分类 run 幂等、清理/撤回降级分支与实体覆盖（组织三表）是下一轮应优先补齐的四块。
