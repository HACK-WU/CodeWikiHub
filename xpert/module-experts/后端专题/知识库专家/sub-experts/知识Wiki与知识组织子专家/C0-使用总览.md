## 1 定位

本子专家把 Wiki 当作「知识库上的派生索引」：源文档 durable FINISH 后入队，走 `map`（源映射）→ `identity_resolve`（身份归一，复用子专家③）→ `reduce`（多来源归并）→ 投影（写页面与向量）→ 对账（reconciler 周期收敛）→ 撤回（retraction 回收失源页面）的链条；在此之上提供页面浏览、目录树与自动分类。页面内容通过 `KnowledgeWikiProjectionService` 投影成知识库的**系统托管文档**（`sourceKey = 'system:knowledge-wiki'`），因此 Wiki 产物本身也可以被检索消费。

## 2 何时找这个子专家

- 要**启停 Wiki 或改配置**：`PUT /wiki/config`，以及配置指纹变化后触发的重建判定。
- 要**读 Wiki 状态**：`GET /wiki/status`（含不确定调用计数与恢复动作、`canManage`）。
- 要**重建 / 重试**：`POST /wiki/rebuild`（非空 Wiki 需确认计费）、`POST /wiki/jobs/:jobId/retry`（仅失败任务 + 不确定调用需额外确认）。
- 要**浏览页面**：页面列表（`ready` 走 browse 读模型，其他状态走管理视图）、页面详情（附目录归属）、页面版本与证据链接。
- 要**做组织与分类**：目录树增删改、页面移动、taxonomy 启停、分类运行启动 / 查询 / 应用、分类图。
- 要**按文档查 Wiki 处理进度**：`GET /wiki/documents/status`。
- 要**排查「Wiki 一直不生成 / 页面不更新」**：job 租约与栅栏、配置指纹、源状态 `_source_state`、对账器三条线索。
- 要**处理计费不确定态**：`requiresAdditionalChargeConfirmation` / `indeterminateInvocationCount` 的人工确认路径。

## 3 能力清单表

| 能力 | 入口 | 一句话 |
| --- | --- | --- |
| 状态与配置 | `GET /wiki/status`、`PUT /wiki/config`；`KnowledgeWikiService.getStatus` / `updateConfiguration` | 状态含启停后的可用性、可管理判定、不确定调用计数与恢复动作；配置写入后若判定「需重建」且传入 `confirmModelCharges` 则触发重建 |
| 生成链 | `KnowledgeWikiGenerationService.enqueueSource` / `processJob` / `processSourceMap` / `processRebuild` | 按 `job.type` 分派（`source_map` / `identity_resolve` / `page_reduce` / `classify` / 重建）；非当前代或已终态直接跳过；取不到租约即退出 |
| 重建与重试 | `POST /wiki/rebuild`、`POST /wiki/jobs/:jobId/retry`；`rebuild` / `retry` | 先断言写权限；未启用即 400；源非空时必须确认计费；重试先退休被取代的旧任务，仅失败任务可重试 |
| 多来源归并与收尾 | `KnowledgeWikiPageReduceService`、`KnowledgeWikiPageSchedulerService`、`KnowledgeWikiFinalizeService`、`KnowledgeWikiLinkService` | `_page_reduce_input` / `_page_reduce_input_source` 保证归并可重放；收尾发布版本并维护页面链接 |
| 页面投影 | `KnowledgeWikiProjectionService.stage` / `retireVersions` / `retireSupersededVersions` | 把页面版本写成一组 chunk 与向量；投影文档 `sourceKey = 'system:knowledge-wiki'`、`metadata.systemManaged = true`、`systemManagedType = 'knowledge-wiki'` |
| 页面浏览读模型 | `GET /wiki/pages`、`GET /wiki/pages/:pageId`；`KnowledgeWikiBrowseService.list` / `placement` / `taxonomy` / `graph` | `query.status` 缺省或 `ready` 走 browse 读模型，其余状态走 `listPages`（需管理权限） |
| 文档状态 | `GET /wiki/documents/status` | 按文档批量查 Wiki 处理状态（进度 + `uncertain`） |
| 撤回 | `KnowledgeWikiRetractionService.enqueue` / `process` | 源被禁用 / 硬删后回收对应页面与投影 chunk，并维护 `_source_state` 活跃标记 |
| 对账 | `KnowledgeWikiReconcilerService.reconcile`（`@Interval` 周期执行） | 退休被取代 job、重派发、回收过期租约、版本升级重算 |

| 自动分类 | `GET /wiki/classification-runs/status`、`GET /wiki/classification-runs`、`POST /wiki/classification-runs`、`POST /wiki/classification-runs/apply` | `start(unclassifiedOnly)` → 查询（含 `requiresAdditionalChargeConfirmation`）→ `apply(jobIds)` 才落 placement |
| 分类图 | `GET /wiki/graph` | 以页面 / 目录为节点的分类关系图（`KnowledgeWikiBrowseService.graph`） |

## 4 边界

**做什么**：Wiki 配置与状态读写、生成链（map / identity / reduce / 投影 / 收尾 / 链接）、重建与重试、页面与版本浏览、证据与链接、目录树与 placement、taxonomy 与自动分类运行（启动 / 查询 / 应用）、分类图、撤回与周期对账、页面到 KB 系统文档的检索投影。

**不做什么**
- **不含身份归一实现**：`identity_resolve` 阶段复用 [子专家③](../GraphRAG与知识身份子专家/C0-使用总览.md) 的 `KnowledgeIdentityService`，`KnowledgeWikiModule` 以 `forwardRef(() => KnowledgeIdentityModule)` 引入。
- **不含检索与融合**：Wiki 投影只产生 chunk 与向量，召回与重排归 [子专家①](../知识库检索与向量存储子专家/C0-使用总览.md)。
- **不含文档摄取**：源文档登记与切片归 [子专家②](../文档摄取与流水线子专家/C0-使用总览.md)；本子专家只消费其 FINISH 事件。
- **不含模型访问与计费**：模型句柄与 token 计量由模型域提供，本子专家只做预算与「不确定调用」记账。
- **页面不是权威存储**：页面的权威来源是源文档 chunk 的 evidence（`knowledge_wiki_page_evidence.sourceDocumentIdSnapshot`），删源文档会触发撤回而非留下孤儿页。

## 5 已知问题与常见坑

1. **Wiki 状态列挤在 `knowledgebase` 表**
   - 现象与触发：查 Wiki 状态要读 KB 行而不是 Wiki 表；KB 行宽与写竞争随派生索引增多而上升。十列逐字：`wikiConfig`、`wikiStatus`（默认 `'disabled'`）、`wikiAvailability`（默认 `'unavailable'`）、`wikiRevision`、`wikiActiveRevision`、`wikiStagedRevision`、`wikiBuildError`、`wikiRebuildRequiredReason`（类型为 `'generator_upgrade' | null`）、`wikiGeneratorVersion`、`wikiConfigFingerprint`。
   - 正确做法：状态读取走 `GET /wiki/status`（它同时给出恢复动作与不确定调用计数），不要自行拼 KB 行字段。
   - 契约来源：`knowledgebase.entity.ts`、`KnowledgeWikiService.getStatus`。
2. **配置指纹变化触发重建**
   - 现象与触发：只改了配置却导致整库重建 / 计费；`wikiConfigFingerprint` 与 job 行上的 `configFingerprint` 共同决定「配置是否变过」。
   - 正确做法：`updateConfiguration` 的「需重建」判定与 `confirmModelCharges` 是两步；改动前先评估重建成本（非空 Wiki 重建需显式确认计费，否则 `Error.KnowledgebaseWikiRebuildChargeConfirmationRequired`）。
   - 契约来源：`KnowledgeWikiService.updateConfiguration`、`KnowledgeWikiGenerationService.rebuild` / `enqueueSource`（`configFingerprint`）。
3. **页面必须由 source chunk evidence 支撑**
   - 现象与触发：`knowledge_wiki_page_evidence` 的必填列是 `sourceDocumentIdSnapshot` / `sourceChunkIdSnapshot` / `quote` / `ordinal` / `sourceContentHash`（`sectionAnchor` 可空），并建在 `['knowledgebaseId','sourceDocumentIdSnapshot']` 与 `['pageVersionId','ordinal']` 上。
   - 正确做法：诊断「页面内容为何变化」时以 evidence 为准；源文档硬删会经 `KnowledgeWikiRetractionService` 回收页面与投影 chunk，而不是留下无证据页面。
   - 契约来源：`knowledge-wiki-page-evidence.entity.ts`、`knowledge-wiki-retraction.service.ts`。
4. **`requiresAdditionalChargeConfirmation` 需人工确认**
   - 现象与触发：分类运行列表项（`KnowledgeWikiClassificationService.list`）与恢复动作（`toRecoveryAction`）会给出该标记，语义是「模型调用**可能已计费但结果未落地**」——不可自动重试的第三态。
   - 正确做法：`GET /wiki/status` 的 `indeterminateInvocationCount > 0` 时不要盲重试；先人工确认，再带确认参数重试或全量重建。
   - 契约来源：`KnowledgeWikiService.getInvocationStatus` / `toRecoveryAction`、`KnowledgeWikiClassificationService.list`。
5. **分类 run 的幂等与 `apply` 语义**
   - 现象与触发：以为启动分类就会改目录。实际上 `start` 只创建 run / job，`apply(jobIds)` 才写 placement；`process` 内部用「拥有租约 + `executionAttempt` + `isCurrent`」判定归属，过期执行会走 `stale` 分支。
   - 正确做法：把「跑分类」与「应用分类」当两步；应用前用 `GET classification-runs` 复核每条 run 的 `outcome` / `stale` / `requiresAdditionalChargeConfirmation`。
   - 契约来源：`KnowledgeWikiClassificationService.start` / `status` / `list` / `apply` / `process` / `writePlacement` / `stale` / `current`。
6. **投影后可被检索消费，但与用户文档隔离**
   - 现象与触发：Wiki 内容出现在检索结果里，却不在 `GET /api/knowledge-document` 列表里。投影文档以 `sourceKey = 'system:knowledge-wiki'` 创建（`name: 'Wiki'`、`filePath: '.system/wiki'`、`status: FINISH`），普通列表的 `visibleDocumentSql` 只放行 `systemManagedType = 'agent-writer'`。
   - 正确做法：排查「文档不见了」先看 `metadata.systemManagedType`；理解「Wiki 可以被检索」是设计意图（注释逐字：「Filter ordinary HTTP lists, not internal projection storage or retrieval readers.」）。
   - 契约来源：`knowledge-wiki-projection.service.ts`、`knowledge-document/document-list-filter.ts`。
7. **投影版本回收有明确判据**
   - 现象与触发：以为「已发布版本可以再被激活」。`retireSupersededVersions` 的注释逐字：「Published versions cannot become active again: publication advances the page's optimistic version. The committed pointer is the cleanup authority, including retries after a worker crash.」它按 `publishedAt IS NOT NULL` + `projectionStatus <> 'disabled'` + `page.activeVersionId IS DISTINCT FROM version.id` 选取待回收版本，单批不传 KB 时 `take(50)`。
   - 正确做法：回收失败只写 `projectionError` 与 warn，等待下轮重试；不要手工删 `_page_version` 行。
   - 契约来源：`knowledge-wiki-projection.service.ts`（`retireSupersededVersions` / `retireVersions`）。
8. **投影写入用稳定 id 容忍并发**
   - 现象与触发：并发投影同一版本可能撞 `23505`。`stage` 用 `uuidv5(logicalChunkId, uuidv5.URL)` 生成稳定 chunk id，撞键后回读校验 `contentHash` 与 `wikiPageVersionId` 一致才放行，否则原样抛出。
   - 正确做法：把 `23505` 当可容忍的并发信号（仅当回读校验通过）；向量写失败会把 `projectionStatus = 'failed'` 与截断到 4000 字符的 `projectionError` 落到版本行。
   - 契约来源：`knowledge-wiki-projection.service.ts`（`stage`）。
9. **文档状态里存在第三种「不确定」**
   - 现象与触发：`GET /wiki/documents/status` 的进度行带 `uncertain` 语义，与 status 的不确定调用计数呼应；这类状态**不**对应成功或失败。
   - 正确做法：不要把 `uncertain` 当失败重试；回到 `recoveryActions` 走人工确认流程。
   - 契约来源：`knowledge-wiki-document-progress.ts` / `knowledge-wiki-document-progress-query.ts`、`KnowledgeWikiService.getDocumentStatus`。
10. **组织控制器的校验比主控制器更严**
    - 现象与触发：`KnowledgeWikiOrganizationController` 类级 `@UsePipes(new ValidationPipe({ transform: true, whitelist: true, forbidNonWhitelisted: true }))`，未知字段直接 400；而 `KnowledgeWikiController` 只在 `GET pages` / `GET documents/status` 上做 `whitelist`（不带 `forbidNonWhitelisted`）。
    - 正确做法：给组织面加字段前先确认 DTO 已声明，否则客户端多传一个键就整批失败。
    - 契约来源：`knowledge-wiki-organization.controller.ts`、`knowledge-wiki.controller.ts`。
