## 1 定位

本子专家负责「文件怎么变成可检索资产」：单篇 / 批量 / 幂等 / 增量四种登记口径，一条以 Bull 队列 `embedding-document` 为主干的异步流水线（validate → transform → split → understand → embedding → finish），本子域自持的 3 条派生队列（自动标签 / 生成问题 / FAQ 语义预热），chunk 与页面的读写面，原文件预览下载，以及删除回收与重处理能力探测。检索与向量存储不在本子专家，见子专家①。

## 2 何时找这个子专家

- 要**登记文档**：单篇、`bulk`、带标签导入、崩溃安全幂等导入、外部源 `connect` 后的批量落库。
- 要**处理 / 重处理文档**：`POST process` 带 `mode ∈ {full, rechunk}`，或更新时 `?process=true` 顺带启动。
- 要**排查「一直处理中 / 一直失败 / 上传后不见了」**：队列与消费者、就绪门、状态列、失败写回四条线索。
- 要**做增量同步**：改源文件后只重嵌变化片段，或从中断态恢复。
- 要**维护切片**：切片增删改（带版本号）、按条件检索切片、切片树预览。
- 要**预估不落库**：`estimate` / `estimate-table` 试跑解析与切片。
- 要**管原文件**：全量下载、Range 流式预览、多文件打包 zip、分析快照浏览。
- 要**删除或停止**：停止 Bull 任务、按版本硬删单篇 / 批量、软删与恢复的现状。
- 要**接网页抓取**：Playwright / FireCrawl / Notion 三类 provider 的选项与执行。

## 3 能力清单表

| 能力 | 入口 | 一句话 |
| --- | --- | --- |
| 单篇 / 批量登记 | `POST /api/knowledge-document`、`POST|PUT /bulk?process=`；`createDocument` / `createBulk` / `createBulkWithIncrementalSync` | 断言 KB 写权限 + 原文件归属；`bulk` 预置 `WAITING / progress 0 / processMsg null` |
| 幂等导入 | `createBulkIdempotently(documents, key)` | **恰好 1 篇 + `key` ≤160**；`sourceKey = runtime-import:<key>`，事务内 `pg_advisory_xact_lock` 去重；同 key 不同内容 → 400 |
| 带标签导入 | `KnowledgeDocumentImportService.create(documents, tagIds)` | 先锁定 KB，再把文档与手工标签在同一事务内落库（`parseDocumentImport` 校验 tagId 形态与单 KB 约束） |
| 增量同步 | `createDocumentWithIncrementalSync` / `createBulkWithIncrementalSync` → `syncChunksIncrementally` | 返回 `{documents, processableIds, skippedIds, updatedIds, createdIds}`；内容未变即整体跳过 |
| 摄取启动与停止 | `POST /process`、`DELETE /:id/job`；`startProcessing(ids, kbId?, mode='full')` | 过滤运行中文档 → 逐 KB 断言未重建 → 入队携带 `mode` → 置 RUNNING；停止走 `job.discard()` + `moveToFailed` 后落 `CANCEL` |
| 状态与列表 | `GET /status?ids=`、`GET /`、`/pagination`、`/my`、`/count` | 状态只回 `id/status/progress/processMsg`；列表强制单值 `knowledgebaseId` 并叠加系统托管过滤 |
| 切片维护 | `GET|POST /:id/chunk`、`PUT /:docId/chunk/:id`、`DELETE /:docId/chunk/:id?version=` | 删除侧版本号必填；每次切片变更都会重新派发派生索引 |
| 预估与重处理能力 | `POST /estimate`、`POST /estimate-table`、`GET /:id/reprocess-capabilities` | 预估不落库（持久化文档优先 `rechunk`，快照不可用才退 `full`）；能力探测返回 `rechunk.available/reason` |
| 目录与移动 | `POST /folder-child-counts`、`POST /:id/move`、`DELETE /:id/page/:pageId` | 移动需 `knowledgebaseId` + `version`；页删除委托服务 |
| 原文件面 | `GET /:id/original-file/download`、`GET|HEAD /:id/original-file/preview`、`POST /original-files/download` | 单 Range 语义（越界 416）、HEAD 同校验不建流、打包 zip 无文件即 400 |
| 分析快照 | `GET /:id/analysis-preview`、`/pages/:page`、`/pages/:page/raw`、`/assets/:assetId` | 页面与资产流，`Cache-Control: private, no-store` |
| 派生索引派发 | `KnowledgeDerivedIndexPublicationService.publish` | 仅在源文档 durable FINISH 后：Tags / Questions 恒发，GraphRAG 按 `contentChanged` 分流，Wiki 仅内容变化时发 |
| 自动标签队列 | `KnowledgeAutoTaggingConsumer`（`knowledge-automatic-tagging`） | 本子域队列；失败不阻塞主链 |
| 生成问题队列 | `KnowledgeQuestionsConsumer`（`knowledge-questions`）+ `KnowledgeQuestionGenerationController` | 题目读取 / 强制重生成 / 删除 |
| FAQ 语义预热 | `FAQSemanticPrewarmProcessor`（`knowledge-faq-semantic-prewarm`） | 挂在知识库模块的真 Bull 队列，带 `attempts` / 退避（与摄取主链不同） |
| 网页抓取 | `GET /web/:type/options`、`POST /web/:type/load` | `integration.id` 必填，且集成须属本组织或本人创建 |

## 4 边界

**做什么**：文档登记（单篇 / 批量 / 幂等 / 增量）、转换与切片流水线、chunk 与页面读写、摄取状态机与进度、原文件预览下载、删除 / 停止 / 恢复的入口语义、网页抓取 provider 分派、派生索引的派发时点、本子域三条队列的消费者。

**不做什么**
- **检索与向量读写不在本子专家**：三路召回、融合、重排、`KnowledgeDocumentStore` 归 [子专家①](../知识库检索与向量存储子专家/C0-使用总览.md)；本子专家只产出 chunk 行与向量写入请求。
- **图谱与 Wiki 的生成不在本子专家**：`publish` 只负责把命令投出去，落图与页面投影归 [子专家③](../GraphRAG与知识身份子专家/C0-使用总览.md) / [子专家④](../知识Wiki与知识组织子专家/C0-使用总览.md)。
- **向量存储选择与 embedding 模型解析不在本子专家**：归子专家①。
- **解析器 / 切片器 / 理解器实现不在本子专家**：由插件注册表（`DocumentTransformerRegistry`、`TextSplitterRegistry`、`ImageUnderstandingRegistry`、`DocumentSourceRegistry`）提供，本子专家只做分派与调用。
- **不含文件字节与沙箱**：原文件字节由存储文件域提供，本子专家只解析目标路径与字节流语义。

## 5 已知问题与常见坑

1. **就绪门：Bull 注册 worker 早于 CQRS 注册 handler**
   - 现象与触发：冷启动 / 滚动升级瞬间投递的任务「有任务无人取」，失败原因表现为「命令处理器不存在」。`processing-lifecycle.module.ts` 首两行逐字：「Bull registers workers in onModuleInit, before CQRS registers its handlers.」「The explicit CqrsModule dependency orders this gate after CQRS bootstrap.」
   - 正确做法：`KnowledgeProcessingReadyService` 在 `onApplicationBootstrap` 才 resolve；消费者在任务体首句 `await this.lifecycle.waitUntilReady()`（已核实 `KnowledgeDocumentConsumer.process`）。`KnowledgeGraphIndexConsumer` / `knowledgebase-rebuild-embedding` / Wiki / FAQ 预热消费者构造器**不含**该服务，不受该门保护。
   - 契约来源：`processing-lifecycle.module.ts`、`document.job.ts`。
2. **队列 payload 让 `mode` 跨边界持久**
   - 现象与触发：`mode` 若只作 HTTP 参数，消费者无从得知本次走 `full` 还是 `rechunk`，会退化成全量重跑或错误复用快照。JSDoc 逐字：「Queue payload keeps processing mode durable across the HTTP/background-worker boundary.」
   - 正确做法：`KnowledgeDocumentJobData = { userId, docs, mode? }`；由 `startProcessing(ids, kbId, mode)` 写入；`parseProcessingMode` 把非法值拒为 400 `Error.InvalidDocumentProcessingMode`。
   - 契约来源：`document.job.ts`（`KnowledgeDocumentJobData` 上方 JSDoc）、`document.controller.ts`（`parseProcessingMode`）、`document.service.ts`（`startProcessing`）。
3. **派生索引只在 durable FINISH 后派发，且队列不可用时静默滞后**
   - 现象与触发：文档已 `finish` 但标签 / 问题 / 图谱 / Wiki 长时间不更新，日志只有 warn。派发点收敛在 `publish`，四个目标用 `Promise.allSettled` 各自兜异常并只 `logger.warn`，无补偿队列。类级 JSDoc 逐字：「Dispatches optional derived indexes only after the source document is durably FINISH.」
   - 正确做法：把四类索引当最终一致；排障按「该文档的派发是否发出 + 目标队列是否有消费者」定位，并对这几条 warn 单独设告警。
   - 契约来源：`derived-index-publication.service.ts`。
4. **splitter / image 设置故意不进 transform 快照指纹**
   - 现象与触发：动一下切片或图像理解参数就让快照失效，转换器（含视觉模型）成本翻倍。`computeKnowledgeDocumentTransformFingerprint` 只捕获切片前会改变转换器输出的设置。
   - 正确做法：调切片策略走 `rechunk` 复用快照；只有 `sourceKey` / `sourceHash` / 处理配置等真正失效点才触发重转换。
   - 契约来源：`document-hash.ts`（`computeKnowledgeDocumentTransformFingerprint` JSDoc 逐字：「Splitter/image-understanding settings are deliberately excluded because changing them must not invalidate a transform snapshot used for rechunking.」）。
5. **`rechunk` 遇非法快照故意失败，而非静默转换**
   - 现象与触发：快照缺失 / 过期 / 损坏时若回退去调转换器，用户以为只重切却重跑了转换器与视觉模型，计费与耗时都不符预期。
   - 正确做法：`TransformSnapshotUnavailableError` 的 `missing | stale | corrupt` 是显式信号；调用方应先读 `GET :id/reprocess-capabilities` 的 `rechunk.available/reason`，再决定是否降级为 `full`。
   - 契约来源：`transform-snapshot.service.ts`（`load` JSDoc 逐字：「Rechunk intentionally fails on invalid snapshots rather than silently running conversion.」）、`document.controller.ts`（`estimate` / `getReprocessCapabilities`）。
6. **删除侧 `indeterminate` 需人工 / 补偿**
   - 现象与触发：`deletion/entities.ts` 的四表（`knowledge_document_deletion_intent` / `_cleanup_receipt` / `_publication_attempt` / `_publication_attempt_source`）已由 `KnowledgeDocumentModule` 的 `TypeOrmModule.forFeature` 注册，但仓库内未见写入 / 消费它们的服务——**当前不存在删除侧 `indeterminate` 的生产写入路径**。
   - 正确做法：现状硬删走 `deleteResolvedDocument` → Wiki 撤回 → 向量删 → graph clear（失败仅告警）→ 删行；需要「结果未知」的人工补偿入口时走 Wiki 侧 `GET :knowledgebaseId/wiki/status` 的 `recoveryActions`，不可自动重试。
   - 契约来源：`deletion/entities.ts`、`document.module.ts`、`document.service.ts`。
7. **FAQ 导入与批量导入的体积上限**
   - 现象与触发：FAQ 导入被 `KNOWLEDGE_FAQ_IMPORT_MAX_BYTES = 10 * 1024 * 1024` 与 `KNOWLEDGE_FAQ_IMPORT_MAX_ENTRIES = 1000` 双重限制；`bulk` 侧单篇内容合规由 `parseDocumentImport` 把关（tagId 必须是小写 UUID，且 tagIds 存在时所有文档必须同属一个 KB，否则 400 `Error.InvalidDocumentImportTags`）。
   - 正确做法：大体积导入拆批；带标签导入前先确认「单 KB + 合法 UUID 标签」两个前提，否则整批被拒。
   - 契约来源：`knowledgebase/faq/knowledge-faq.controller.ts`、`knowledgebase/faq/knowledge-faq.service.ts`、`knowledge-document/document-import.service.ts`。
8. **`rag-web` 两处源码疑点**
   - 现象与触发：`provider/index.ts` 里 Notion 的 `schema` 实际 `import Notion from './playwright/schema'`（只有 `load` 指向 `./notion/notion`）；`rag-web/loader.ts` 为 **0 字节空文件**。
   - 正确做法：接 Notion 前先实测其选项与抓取结果，不要假设 schema 为 Notion 定制；不要把空文件当可导入的导出面。
   - 契约来源：`rag-web/provider/index.ts`、`rag-web/loader.ts`、`rag-web/provider/notion/schema.ts`。
9. **系统托管文档在普通列表里「消失」是预期内**
   - 现象与触发：Wiki 投影文档与 FAQ 文档不在用户列表；`userDocumentListWhere` 用 `visibleDocumentSql` 过滤 `metadata.systemManaged = true`，仅 `systemManagedType = agent-writer` 放行。
   - 正确做法：排查「文档不见了」先看 `systemManaged` 标记，而不是先怀疑权限或删除了。注释逐字：「Filter ordinary HTTP lists, not internal projection storage or retrieval readers.」
   - 契约来源：`document-list-filter.ts`、`document-management.ts`。
10. **多个 integration spec 默认不执行**
    - 现象与触发：CI 全绿但数据库相关行为实际没跑。`*.integration.spec.ts` 需注入 PostgreSQL 环境变量才执行（仓库内命中 `*_PG_E2E` / `*_PG_URL` / `BOM_GRAPH` 三类命名的文件约 19 个，其中本子域含 `document-list` / `document-publication` / `rag-vstore` 等）。
    - 正确做法：至少在 CI 注入一组；网页抓取测试还需 ESM 运行旗标。
    - 契约来源：`packages/server-ai/jest.config.ts` 与各 integration spec 的环境判定。
