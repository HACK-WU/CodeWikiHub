## 1. 创建与幂等

`createBulkIdempotently(documents, key)` 是「崩溃安全创建收据」：`documents.length !== 1` 或 `key` 为空或 `key.length > 160` 或首篇无 `knowledgebaseId` 时抛 `BadRequestException('Idempotent creation requires one document and a key of at most 160 characters')`；随后 `assertKnowledgebaseWriteAccess`，在事务内先取 `SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`（键 `knowledge-import:${knowledgebaseId}:${key}`），再按 `sourceKey = runtime-import:${key}` 查既有行：命中且 `metadata.sourceHash` 不同 → `BadRequestException('Import key content conflict')`；命中且哈希相同 → 返回 `skippedIds`；未命中 → `createDocument({...doc, sourceKey, metadata._runtimeImportKey})` 并返回 `createdIds + processableIds`。三条路径都返回 `IncrementalDocumentSyncResult`。

`createBulkWithIncrementalSync(documents, manager?)` 是主入口：先 `delete document.processingExecutionId`、`resolveNewDocumentParserConfig(document, true)`（会顺带 `ensureDocumentChunkStructure`）、补齐 `sourceHash` / `sourceKey`；对涉及的知识库并发 `assertNotRebuilding`；再逐篇查 `incrementalSyncEnabled`——开启走 `createOrReuseSourceDocument`，关闭则无条件 `createDocument` + `shouldProcess=true`。结果按 `createdIds / updatedIds / skippedIds / processableIds` 四组返回。

`createOrReuseSourceDocument`（私有）是幂等核心：`completeDocumentSystemAttributes` → `validateDocumentMetadataInput` → 解析 `sourceKey` / `sourceHash` → `findExistingSourceDocument`；未命中则创建（`action: 'created'`）；命中则算 `computeKnowledgeDocumentProcessingHash`，`canSkipProcessedDocument(existing, processingHash)` 为真即 `action: 'skipped'`、`shouldProcess: false`；否则以既有行 id/version 为基底合并变更（保留 `contentHash`、写入新 `processingHash`）。`KnowledgeDocumentImportService.create` 在此之上加了「标签同事务提交」：先逐篇 `resolveNewDocumentParserConfig(document, true)`（注释说明这步必须在持锁前完成，因为解析器解析器用独立连接做一次性更新），再 `tags.lockImportKnowledgebase` → `createBulkWithIncrementalSync(documents, manager)` → `tags.assignImported(manager, ..., tagIds)`。

## 2. 入队与主流水线

`startProcessing(ids, kbId?, mode='full')`：按 `kbId ? {knowledgebaseId, id: In(ids)} : {id: In(ids)}` 取文档，过滤掉 `status === RUNNING`，对每个知识库 `assertNotRebuilding`，`docQueue.add({ userId, docs, mode })`，然后把 `jobId` / `processingExecutionId = null` / `status = RUNNING` / `processMsg = ''` / `progress = 0` 回写并 `save`。

`KnowledgeDocumentConsumer.process` 逐段：
1. `await this.lifecycle.waitUntilReady()`（就绪门，第一句）。
2. `userService.findOne(job.data.userId, { relations: ['role'] })`，用 `captureRequestContext({ user, organizationId, language })` 造上下文——注释说明 embedding 模型创建读 plugin-sdk `RequestContext`，旧 CRUD 路径读 server-core context，「queued work needs both scopes restored」，因此整段包在 `runWithCapturedRequestContext` 里。
3. `processInRequestContext` 取知识库（relations 含 `copilotModel.copilot.modelProvider`、`chatModel.referencedModel`）后进 `_processJob`。`getActiveVectorStore(knowledgebase, true)` 失败时把队列里全部文档置 `ERROR` + `processMsg` 并重抛。
4. 逐篇：`findOne(doc.id, { relations: ['chunks'] })`；native table 文档用 `String(document.jobId) !== String(job.id)` 丢弃过期 job；写 `processBeginAt` / `processingHash` / `sourceHash`。
5. **短路**：`status === FINISH && processingHash 未变 && contentHash 存在`（native table 还需 `tableMetadata.canSkip`）→ 只更新 token 计数与 `lastIncrementalSync.mode = 'skipped'`，然后 `publish({ contentChanged: false })` 并 `continue`。
6. 否则 `commandBus.execute(new KnowledgeDocLoadCommand({ doc, stage: 'prod', mode: job.data.mode ?? 'full' }))`：解析 / `rechunk` 快照载入 / 切片 / image understanding，中途把状态推到 `TRANSFORMED` → `SPLITTED` → `UNDERSTOOD`。
7. `guardEmbeddingInputDocuments(chunks, embeddingContextSize)` 按 `copilotModel.options.context_size` 切分超长输入；native table 走 `tableMetadata.prepare/project/assertIndexCurrent`。
8. `syncChunksIncrementally({...document, chunks}, vectorStore)` → 状态 `EMBEDDING`、`progress 0`、`chunkNum`。
9. 分批 embedding：`batchSize = knowledgebase.parserConfig?.embeddingBatchSize || 10`；每批先算 token（取 `metadata.searchContent ?? pageContent`）、发 `CopilotTokenRecordCommand`（`requestId = knowledge-document:${job.id}:${document.id}:${count}`）、再 `vectorStore.addKnowledgeDocument(document, batch)`；每批后 `checkIfJobCancelled`，为 `CANCEL` 则写 `status=CANCEL` 并 `return`。
10. **FINISH**：`updateDocumentProcessingMetadata(doc.id, { status: FINISH, progress: 100, contentHash: syncResult.contentHash, processingHash, sourceHash, ... }, { tokens, lastIncrementalSync }, syncResult?.contentChanged === true)`；仅当 `contentChanged` 时 `publicationEpoch` 走 `COALESCE("publicationEpoch", 0) + 1`。随后 `publicationService.publish({ ..., contentChanged })`。
11. 单篇异常：`TableMetadataStaleError` 只 debug 后 `continue`（被更新代取代），其余写 `status=ERROR` + `processMsg` 并 `logger.warn('[Job: entity ...] Document ... failed: ...')`，不中断兄弟文档。

## 3. 增量同步与中断恢复

`syncChunksIncrementally(document, vectorStore)` 是 chunk 级幂等的唯一落点，顺序严格：
1. `prepareIncomingChunks`：给每 chunk 补 `metadata.chunkId`（退化 `chunk-${index}`）与 `chunkIndex`，删掉 `questionGeneration / questionGenerationId / questionSourceChunkId / generatedQuestionId` 四个易变键，然后 `contentHash = computeKnowledgeDocumentChunkHash(prepared)`。
2. `contentHash = computeKnowledgeDocumentContentHash(incomingChunks)`（对 `chunks[].contentHash` 求稳定哈希）。
3. 读既有 chunk（`relations: ['parent']`，`order: { createdAt: 'ASC' }`）。`recoverInterruptedSync = existingChunks.length > 0 && (!document.contentHash || computeKnowledgeDocumentContentHash(sortChunksByDocumentOrder(existingChunks)) !== document.contentHash)`——源码注释解释这条不变量：「Chunk rows are saved before vectors. Only a matching published hash proves those rows were indexed.」即「chunk 行已写、向量未发布」的中断态。
4. **整体跳过**：`!recoverInterruptedSync && document.contentHash === contentHash` → 返回 `contentChanged: false`、`embeddingChunks: []`。
5. `matchIncrementalChunks`：两级键匹配 —— exact（自身 contentHash + 父 chunk 内容哈希）优先，未命中退 position（`chunkIndex` + 父 index），产出 `unchanged | changed | added`；未命中既有行归入 `removedChunks`。`recoverInterruptedSync` 为真时把 `unchanged` 一律计入 `updated` 并强制重嵌。
6. 先删向量：`vectorStore.deleteChunks([...removedIds, ...changedIds, ...questionVectorIds(changedAndRemoved)])`——被删/被改 chunk 的**问题向量**一并清掉。
7. 再落行：`chunkService.upsertBulk(chunksToPersist)`，随后 `delete({ id: In(removedIds) })`。
8. `embeddingChunks` 由 `chunkService.findAllEmbeddingNodes(savedChunks)` 再按变更 id 过滤（`findAllEmbeddingNodes` 只保留文本叶子 + 全部媒体 chunk）。

## 4. 派生索引派发

`KnowledgeDerivedIndexPublicationService.publish({ knowledgebase, documentId, userId, contentChanged })` 构造固定 context（`userId / tenantId / organizationId / knowledgebaseId`），组装四条命令：Tags → `KnowledgeAutoTaggingEnqueueCommand`；Questions → `KnowledgeQuestionsEnqueueCommand`；GraphRAG → `contentChanged ? KnowledgeGraphEnqueueCommand({ reason: 'document' }) : KnowledgeGraphRetryDocumentCommand`；Wiki → 仅 `contentChanged` 时才 `KnowledgeWikiEnqueueSourceCommand({ reason: 'document' })`。派发用 `Promise.allSettled(publications.map(({command}) => Promise.resolve().then(() => this.commandBus.execute(command))))`——`Promise.resolve().then` 让同步抛错也变成 rejected promise；`forEach` 对 rejected 项只 `logger.warn('${target} publication failed for document ...')`。源码注释承认该取舍：「Both synchronous dispatch failures and asynchronous queue failures are optional outcomes.」因此 **Bull/Redis 不可用时 tags / questions / graph / wiki 会静默滞后**，主摄取不受影响。下游消费侧：`knowledge-automatic-tagging` 的入队 handler 用确定性 `jobId: ${document.id}-${document.publicationEpoch}-${document.tagRevision}` 做去重、`attempts: 3` + exponential backoff 2000ms；`knowledge-questions` 的入队 handler 用 `attempts: 1`，且在 `parserConfig.questionGeneration` 未配置时**直接 return 不入队**（注释：「No model calls for unconfigured libraries. Explicit opt-out also cleans up an earlier generation.」）。

## 5. 删除回收

**现状路径（可执行）**：`deleteWithVersion(id, expectedVersion)` 先 `findOne` 带 `knowledgebase.documents`（用于回填计数），版本不符抛 `ConflictException('Knowledge document has been modified. Refresh and try again.')`，然后 `deleteResolvedDocument`：`assertNotRebuilding` → `deleteDocumentArtifacts` → `repository.delete({ id, version })`（受影响行数为 0 再抛冲突）或 `super.delete(id)` → `updateDocumentNumAfterDelete`。`deleteBulkWithVersion(documents)` 先 `assertBulkDocumentVersions` 再逐条 `deleteWithVersion`，无事务包裹。`deleteDocumentArtifacts` 的三步是：`KnowledgeWikiRetractSourceCommand({ reason: 'hard_deleted' })` → `vectorStore.deleteKnowledgeDocument(document)` → `KnowledgeGraphClearDocumentCommand`（**包在 try/catch 内，失败仅 warn**，注释/日志为 `Failed to clear GraphRAG data for document '...'`）。`softRemove` 被 override 为抛 `ConflictException(t('server-ai:Error.KnowledgeDocumentSoftDeleteUnavailable'))`。

**设计态四表（已建表、无编排方）**：`deletion_intent`（`status: KnowledgeDeletionStatus`，默认 `'prepared'`；部分唯一索引 `(knowledgebaseId, sourceDocumentIdSnapshot) WHERE "status" <> 'completed'`；含 `manifest` / `failedStage` / `executionAttempt` / `lockedAt` / `leaseExpiresAt` / `@VersionColumn`）→ `cleanup_receipt`（`(intentId, receiptKey)` 唯一，`status: pending | succeeded | failed | indeterminate`，`outcome.ownershipVerified/deleted/alreadyAbsent/providerRequestId`）→ `publication_attempt`（`producerKind: document | chunk | graph | wiki | embedding_rebuild`，`status: prepared | running | published | compensating | compensated | failed | indeterminate`，`artifacts[].status: prepared | written | promoted | compensated | indeterminate` + `idempotencyKey`，租约 `lockedAt/leaseExpiresAt/heartbeatAt`）→ `publication_attempt_source`（`(attemptId, documentIdSnapshot)` 唯一 + `contentHash`）。四表只在 `KnowledgeDocumentModule` 的 `TypeOrmModule.forFeature` 与 `core/entities/index.ts` 出现（另有一个 spec），仓库内**未发现**任何写入或消费它们的服务 —— 人工/补偿路径目前依赖 DB 直查与运维介入。

**注意**：`contracts` 里 `KnowledgeDeletionStatus` 的取值是 `prepared | quiescing | retracting | external_cleanup | finalizing | completed | failed`；**`indeterminate` 不在 intent.status 上**，只出现在 `cleanup_receipt.status`、`publication_attempt.status` 与 `artifacts[].status`（父级文档把 `indeterminate` 记到 `deletion_intent.status` 属口径偏差，以源码为准）。

## 6. rag-web 三 loader 与 web/:type/* 路由

`Providers`（`rag-web/provider/index.ts`）是三路注册表：Playwright → `./playwright/schema` + `./playwright/playwright`；FireCrawl → `./firecrawl/schema` + `./firecrawl/firecrawl`；Notion → **`schema` 复用 `./playwright/schema`**（同文件内 `import Notion from './playwright/schema'`），`load` 取 `./notion/notion`。`rag-web` 根目录 `loader.ts` 是 **0 字节空文件**。三个 loader 的实现成熟度差异极大：`playwright.ts` 用 `CustomPlaywrightWebBaseLoader` + TurndownService，在 `extract` 里抓 `title/description/author` 并生成 `scrapeId: uuidv4()`，在 `evaluate` 里 `document.body.innerHTML` 转 Markdown；`notion.ts` 用 `NotionAPILoader` 但 `id` **硬编码 `"<PAGE_ID>"`**；`firecrawl.ts` 整段 `FireCrawlLoader` 被注释掉，**直接 `return []`**。

调用面：`GET web/:type/options` → `GetRagWebOptionsQuery`；`POST web/:type/load` → 先校验 `body.integration.id`（缺失 400），再 `integrationService.findOneInOrganizationOrTenant(id)`，不满足「属本组织或本人创建」则抛 `knowledgeDocumentAccessDenied()`，最后 `RagWebLoadCommand`。`RagWebLoadHandler` 取 `Providers[type]?.load(webOptions, integration)`，把每个 doc 按 `` `${RagWebLoadCommand.prefix}:${doc.metadata.scrapeId}` `` 缓存 5 分钟（`prefix = 'rag_web'`）；捕获 `playwright install` 类错误后用 `SchedulerRegistry` 加一个名为 `install_playwright` 的 timeout，`spawn(npxCommand, ['playwright','install','--only-shell','chromium'], { shell: true, env: process.env })` 自愈安装，并用缓存键 `rag_web_provider:playwright`（`providerPrefix`）标记 `installing / installed / fail`，配合 i18n `rag.Error.PlaywrightNotInstalled` / `rag.Error.ErrorReinstallPlaywright` / `rag.Error.InstallingPlaywright`。抓取结果由 `KnowledgeDocLoadHandler.loadWeb` 经 `GetRagWebDocCacheQuery` 按 `page.metadata.scrapeId` 取回再切片。

## 7. chunk mutation 与 filter attributes 同步

**chunk 族**（`KnowledgeDocumentChunkService`）：`upsertBulk` 先建 map（key = `metadata.chunkId`），`getOrCreateChunk` 递归先建父行再落子行，带 `entityCache` 去重——闭包表（`@Tree('closure-table')`）的父子关系由 TypeORM 维护；`updateWithVersion(id, entity, expectedVersion)` 用 `repository.update({ id, version }, patch)` 做乐观锁，未命中抛 `ConflictException('Knowledge document chunk has been modified. Refresh and try again.')`；`deleteWithVersion` 同理；`updateMetadataBulk` 逐行 `update({ id }, { metadata, updatedById })`；`findAncestors(id)` 用 `getTreeRepository(...).findAncestors(entity, { depth: 5 })`。

**moveDocument**：校验 `knowledgebaseId` / `documentId` 非空 → `assertNotRebuilding` → 文档必须在目标 KB 内 → 版本比对 → 父节点必须是同 KB 的 `KDocumentSourceType.FOLDER` → 用 `findAncestors(parent.id)` 拒绝「把目录移进自己的后代」。事务内 `treeRepository.save(document)`，若旧前缀/新前缀不同则用**原生 SQL** 按 `folder` 前缀批量重写后代路径并 `"version" = "version" + 1`。事务外收集 `affectedDocumentIds` 后调 `syncMilvusFilterAttributes`。

**syncMilvusFilterAttributes(documentIds)**：`findAll` 带 `knowledgebase` 关系，只保留 `(knowledgebase.vectorStore ?? environment.vectorStore) === VectorTypeEnum.MILVUS` 的文档——**只有 Milvus 需要把文档级属性写进向量库 metadata**；随后按 `documentId` 分组 chunk，每个 KB 取一次 `getActiveVectorStore(knowledgebaseId, true)`，逐文档 `store.partialUpdateFilterAttributes(document, chunks)`。触发点是文档属性白名单 `FILTER_ATTRIBUTE_DOCUMENT_FIELDS`（`name / folder / type / mimeType / category / sourceType / createdAt / updatedAt / disabled / metadata`）经 `hasFilterAttributeChanges` 判定。手工改 chunk 后走 `publishChunkMutation(document)`，它直接以 `contentChanged: true` 调 `publish`，从而自增 `publicationEpoch` 并重派派生索引。

## 8. 设计模式

- **outbox 式删除意图**：`deletion_intent → cleanup_receipt → publication_attempt(+source)` 四表把「要删什么」与「删到哪一步」分离；`manifest.externalArtifacts[].ownership: owned | shared | unknown` 与 `cleanup_receipt.outcome.alreadyAbsent` 是显式为「不确定」留的字段位（当前无写入方）。
- **就绪门（readiness gate）**：`KnowledgeProcessingLifecycleModule` 以 `imports: [CqrsModule]` 排序，`KnowledgeProcessingReadyService` 用 `onApplicationBootstrap` resolve Promise，消费者 `waitUntilReady()` 阻塞——把「Nest 生命周期顺序」这一个隐式约束变成一条可读声明。
- **幂等三元组 + 三级 hash**：文档级 `sourceKey + sourceHash + processingHash`、chunk 级 `contentHash`、发布级 `idempotencyKey`；`createBulkIdempotently` 额外用 `pg_advisory_xact_lock` 把「同 key 并发」在 DB 层串行化。
- **策略注册**：解析侧用 plugin-sdk 的 `DocumentTransformerRegistry` / `TextSplitterRegistry` / `ImageUnderstandingRegistry`；抽取向用 `Providers` 映射 + `Providers[type]?.load` 可选链；两者都靠「注册表 + 运行时查表」避免在业务代码里写 `switch`。
- **确定性 jobId 去重**：自动标签用 `${document.id}-${publicationEpoch}-${tagRevision}` 作 `jobId`，让多副本重复投递自然合并。
- **发布前置收据**：`updateDocumentProcessingMetadata` 先写 FINISH/`publicationEpoch` 再 `publish`，保证「先 durable 后派发」的顺序不依赖调用方自觉。

## 9. 热点路径

1. **主流水线单篇长任务**：`KnowledgeDocLoadCommand`（解析 + 视觉理解 + 切片）与分批 embedding 在**同一个 job 体**内串行；解析阶段有 10 分钟 `cache-manager` 缓存（键前缀 `knowledges:transformer:v2:` / `knowledges:chunker:` / `knowledges:understanding:v4:`），缓存未命中即重新调插件与视觉模型。
2. **大文件**：`transformSnapshotService.save` 用 `fsPromises.open` + 流式写 NDJSON（避免一次性大 JSON 分配），但 `load` 侧 `readFile` 全量读入内存再 `split('\n')`，大文档 rechunk 是内存峰值点。
3. **chunk 批量写**：`matchIncrementalChunks` 是 O(n) 哈希匹配 + `upsertBulk` 逐 chunk 串行 `update`/`create`（含父行递归），大文档的 chunk 数直接放大 DB 往返；`updateSourceTokenCounts` 还会先 `updateChunkMetadataBulk` 再 `findAllEmbeddingNodes` 全量读回算 token。
4. **派发扇出**：每次 FINISH 都发 3~4 条命令；`contentChanged: false` 的短路路径也会重新发 tags/questions 与 graph 重试分支，重复但不阻塞。
5. **`assertNotRebuilding` 的调用面**：`startProcessing` / `createBulkWithIncrementalSync` / `moveDocument` / `deleteResolvedDocument` / `deletePage` / questions 的 `assertCanRegenerate` 与 `isCurrent` 都会查它；embedding 重建期间这些入口全部 400。

## 11. 技术债与 hack

1. **`rag-web` Notion schema 复用疑点 + `loader.ts` 0 字节**：`provider/notion/schema.ts` 确实存在（声明 `TRagNotionParams` / `timeout`），但 `provider/index.ts` 写的是 `import Notion from './playwright/schema'`，即 Notion 选项面板用的是 Playwright 的 schema —— 复制粘贴迹象明确；同时 `rag-web/loader.ts` 是 0 字节空文件。
2. **FireCrawl loader 是桩**：`firecrawl.ts` 的 `FireCrawlLoader` 整段被注释，函数体只剩 `return []`；`notion.ts` 把 `id` 硬编码为 `"<PAGE_ID>"`。两条链目前不可生产使用。
3. **约 30 个 integration spec 默认 skip**：本域可直接影响的有 `document-list.integration.spec.ts`、`document-publication.integration.spec.ts`（均要求 `KNOWLEDGE_WIKI_PG_E2E === '1'`），CI 不注入环境变量等于 DB 回归未跑。`rag-web` 侧的 `*.test.ts` 命名不在 jest `*.spec.ts` 约定内，需要独立执行器；父级文档记录的 `node --experimental-vm-modules` 需求本次未逐行核实。
4. **`indeterminate` 需人工恢复**：四表设计承认「结果未知」，但无自动收敛路径，也无服务写入 —— 当前只能靠 DB 直查 + 运维人工补偿。
5. **FAQ 导入体积上限单列**：`knowledgebase/faq/knowledge-faq.controller.ts` 的 `KNOWLEDGE_FAQ_IMPORT_MAX_BYTES = 10 * 1024 * 1024` 是模块级常量而非 `process.env`（详见 07），与「FAQ 导入不能超过 10MiB」这一运维事实必须分开记录。
6. **派发静默失败**：`publish` 的 `Promise.allSettled` + `logger.warn` 让 Bull/Redis 不可用时的 tags/questions/graph/wiki 滞后**没有告警面**，必须靠日志告警补齐。
7. **`softRemove` 抛错但路由仍在**：`@Delete(':id/soft')` 与 `@Put(':id/recover')` 路由存在，前者必然 409（`Error.KnowledgeDocumentSoftDeleteUnavailable`），实体仍有 `deletedAt` 与 `_kb_disabled` 索引。
8. **`syncMilvusFilterAttributes` 只覆盖 Milvus**：其它向量库（含 PG 内置实现）不做文档级过滤属性同步，`FILTER_ATTRIBUTE_DOCUMENT_FIELDS` 变更对它们无效。
9. **`startProcessing` 无 `attempts`/`backoff`**：`docQueue.add({ userId, docs, mode })` 不带重试选项，`embedding-document` 失败即终态 `ERROR`；`knowledge-questions` 显式 `attempts: 1`，问题生成失败必须靠 `regenerate` 或后续重索引复用已有结果。
10. **`updateDocument` 的类型逃逸**：为规避 TypeORM 递归类型的实例化开销，代码用 `ShallowKnowledgeDocumentUpdater` / `KnowledgeDocumentPublicationWriter` 做窄化断言（注释：「Keep TypeORM's recursive QueryDeepPartialEntity out of concrete call sites」），代价是编译期不再校验更新字段。
11. **`createBulkIdempotently` 只支持单文档**：多篇导入必须退回 `bulk` + 标签导入路径，幂等语义不同。

## 12. 设计维度分析

### 12.1 维度一：可恢复性——「先落行、后落向量」的中断模型

`syncChunksIncrementally` 的顺序是「删旧向量 → 写 chunk 行 → 返回待嵌 chunk」，`document.contentHash` 只在 FINISH 时由 `updateDocumentProcessingMetadata` 写入。于是「chunk 行已存在但 `contentHash` 不匹配」就是唯一的中断指纹，`recoverInterruptedSync` 用它把 `unchanged` 强制升级为 `updated` 并重嵌。这个模型不需要额外的 checkpoint 表，也不需要向量侧可查询状态；代价是**每次中断后的恢复都是全量重嵌**（精度换简单）。与之配套的第二道保险是问题向量：`questionVectorIds(...)` 把被删/被改 chunk 的派生向量一并清理，避免孤儿向量成为检索证据。

章节来源：[packages/server-ai/src/knowledge-document/document.service.ts](file://packages/server-ai/src/knowledge-document/document.service.ts)（关键符号：KnowledgeDocumentService.syncChunksIncrementally / recoverInterruptedSync）；[packages/server-ai/src/knowledge-document/questions/question-vectors.ts](file://packages/server-ai/src/knowledge-document/questions/question-vectors.ts)（关键符号：questionVectorIds / isCurrentQuestionVector）

### 12.2 维度二：新鲜度——三道「陈旧闸门」挡在模型调用之前

系统在**任何付费模型调用之前**布置三道闸门，把「重复付费」压到最低：① 自动标签的 `inputHash`（`sha256({version:1, publicationEpoch, content, config, model, candidates})`）与 `document.autoTaggingInputHash` 比对，相同直接 return；② 问题生成的 `questionInputHash(chunk, context, config)` 支持 `config, 1` 的**上一版 prompt 兼容取值**（注释：「A prompt upgrade must not repeat earlier paid work during automatic jobs or indexing retries.」），并把 `generating` 状态加 15 分钟租约窗口；③ 解析/切片/视觉理解的 10 分钟 `cache-manager` 缓存 + `rechunk` 快照复用。问题生成的顺序还额外做了「先落已付结果再索引」：`saveState(chunk, state)`（含 questions）成功后才 `vectorStore.addKnowledgeDocument(..., { ids: newIds })`，注释写明「an embedding failure never needs another model call」。

### 12.3 维度三：写侧一致性——「显式不确定性」而非原子性

本域没有把「删文档」做成一个跨存储事务，而是承认它跨关系库 / 向量库 / 文件 / 派生索引四个存储：当前实现用 `deleteDocumentArtifacts` 的固定顺序 + graph 失败仅 warn 换取可用性；设计态的 outbox 四表（`deletion_intent` / `cleanup_receipt` / `publication_attempt` / `_source`）把每一步变成可查询的收据，并把 `indeterminate` 提升为**一等状态**（cleanup_receipt 与 publication_attempt 都允许它）。同一思路在派发侧体现为 `Promise.allSettled` + 逐项 warn：失败被记录但不阻塞。代价是「静默滞后」需要靠日志告警补齐，详见 07。

## 13. 结论

实现主线可以概括为「同步侧收口幂等、异步侧承担重活、失败面显式记账」。同步侧的三个入口（`createBulkIdempotently` / `createBulkWithIncrementalSync` / `createOrReuseSourceDocument`）共享同一套 `sourceKey + sourceHash + processingHash` 判定，chunk 级再用 `contentHash` 与 exact/position 匹配收敛到最小写入集；异步侧的 `embedding-document` 消费者把「解析 → 切片 → 视觉理解 → 分批 embedding」放在一个 job 内串行，用 `CANCEL` 检查与 `TableMetadataStaleError` 的静默跳过实现可控中断；收口侧的 `publicationEpoch`（仅在 contentChanged 时自增）+ 就绪门 + 逐项 catch 构成「先 durable、后派发」。可改进优先级：① 补齐 `rag-web` 三个 loader（FireCrawl 桩、Notion 硬编码、`loader.ts` 空文件、Notion schema 复用）；② 为 `publish` 的逐项 warn 建告警；③ 给四表写编排方或明确「废弃」结论，消除 `indeterminate` 的悬空语义；④ 至少在一个 CI 作业里开启本域的 PG integration。
