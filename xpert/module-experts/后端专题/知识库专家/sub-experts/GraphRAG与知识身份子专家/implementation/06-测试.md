## 9. 覆盖缺口

1. **身份归一的语义边界**：`canMatchIdentity` / `selectIdentityCandidates` 无独立 spec。最关键的两条注释式不变量——「concept 一律返回 true，域/范围只作裁判证据」与「identified/named 全留 + 其余取前 8、语义检索不授权 merge」——只有集成测试间接触达，纯函数级边界（候选为空、全 uncertain、多个 same、相似度长度为 0、长度不一致返回 -1）缺少直接断言。`judge` 的「8 个一批 / 多 same → uncertain」分批逻辑也无独立 spec（它依赖注入 `runtime.judge`，本可纯单测）。
2. **图查询的规模路径**：`clampGraphTake` / `clampGraphRetrievalDepth` / `clampGraphEntityChunkTake` / `clampGraphMentionTake` 的边界值（0、负数、超上限）与 `expandEntities` 的 hop 上限、`resolveGraphChunks` 的 `topK` 截断与 `truncated` 标记，没有专门的规模/边界 spec；`listRelations` 的 `total = items.length` 语义也无断言。
3. **`syncEntityVectors` 与向量表一致性**：`clear + addGraphDocuments(ids)` 的全量语义没有 spec 断言（例如「hidden 实体不得出现在向量面」「实体 id = identityId 派生值」）。
4. **重建/清理的保留语义**：`clearKnowledgebase(preservePublications)` 中「manual/curated/hidden 保留、extracted/structured 删除」以及「preserve 时只删无 `publication` 的 job」这类分支，只在 `graphrag.service.spec.ts` 里以 mock 断言删除条件，未在 PG 上验证过真实 SQL 行为（`clearKnowledgebase` 用 QueryBuilder + JSON 路径条件）。
5. **community 表与 `communityTopK`**：表无写入者亦无测试；若后续补实现，需要新增 spec。
6. **env 文档缺口**：三个门控变量未在 `docs/` 中出现，`BOM_GRAPH_PG` 的命名与 `KNOWLEDGE_*` 前缀族不一致，容易在 CI 配置时漏设。
7. **`extractionSnapshot` 的 `select: false`**：漏 select 会静默走错分支，属易回归点；建议补一条「快照已存在时不重复调用模型」的显式断言（`extractOnce` 的注释已声明该意图）。

## 10. 结论

本子域的测试结构是「单元 mock 为主（18/22）+ 默认跳过的 PG 集成（3 文件 + 1 内嵌 suite）」。测试面覆盖了三件最要紧的事：job 生命周期与重试的单飞（`retry-postgres.integration.spec.ts`）、贡献表聚合与结构化写图（`graph-contribution-postgres.integration.spec.ts`）、身份观察表的锁与幂等回放（`knowledge-identity-postgres.integration.spec.ts`）。相较之下，**身份候选筛选纯函数**、**图查询的规模/边界**、**向量同步的全量语义**三块是明显缺口，且它们恰好是本子域最贵、最容易出错的三处。落地建议：① 为 `knowledge-identity-policy` 补纯函数 spec（零依赖、成本最低）；② 为 `clampGraph*` 与 `expandEntities/resolveGraphChunks` 补边界 spec；③ 在 CI 中至少注入 `KNOWLEDGE_GRAPH_PG_E2E=1` 与 `KNOWLEDGE_IDENTITY_PG_E2E=1` 各跑一次，否则「删除保留语义」与「身份锁语义」在回归中完全不可见。
