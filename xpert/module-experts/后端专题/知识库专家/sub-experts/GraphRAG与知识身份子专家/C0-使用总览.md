## 1 定位

本子专家覆盖「知识图谱」与「知识身份」两件事，二者同域的原因写在数据模型里：图谱节点的归一结果直接落在图实体自身的唯一键上——`KnowledgeGraphEntity` 声明 `@Index(['knowledgebaseId', 'identityId'], { unique: true })`，即「同一 KB 内一个身份最多对应一个实体」。图谱侧负责索引链、实体 / 关系的手工修正与清理、邻域与可视化；身份侧负责把候选名归一为稳定身份（`resolve` / `resolveBatch`），并用 LLM 裁判处理歧义。Wiki 与图谱共用同一身份层。

## 2 何时找这个子专家

- 要**启停图谱**、全库重建、单文档重试，或按文档查索引进度。
- 要**查实体 / 关系 / 提及 / 目录 / 可视化**，或展开某实体的邻域与关联切片。
- 要**手工修正图谱**：新建 / 更新实体与关系，或把某实体 / 关系从可见集里摘掉。
- 要**排查「图谱开着但实体为空」**：`error` 列、job 状态、抽取快照三条线索。
- 要**让插件 / 工作台侧的结构化图谱写入落到本域**（`StructuredGraphRuntimeService` 的 publish / status / retract）。
- 要**把候选名归一为稳定身份**（跨 Wiki 与图谱共用），或调身份判定的成本与有界窗口。
- 要**清理**：文档级 `clearDocument`、库级 `clearKnowledgebase`（可保留发布记录语义）。

## 3 能力清单表

| 能力 | 入口 | 一句话 |
| --- | --- | --- |
| 图谱索引链 | `POST /api/knowledgebase/:id/graph/rebuild`；`GraphragService.enqueueDocuments` / `dispatchJobs` / `processIndexJob` | 为每篇文档建 `KnowledgeGraphIndexJob` 并入队 `knowledge-graph-index`；入队失败写 `dispatchError` |
| 启停判定 | `GraphragService.isEnabled` | `knowledgebase.graphRag?.enabled === true` 为唯一开关；未启用时 `enqueueDocuments` 直接返回空数组 |
| 图谱状态与进度 | `GET /graph/status`；`GET /graph/documents/:documentId/status`、`POST /graph/documents/status` | 状态含启停、计数与最近任务，`error` 为空即正常；批量进度入参有数量上限校验 |
| 实体 / 关系 / 提及查询 | `GET /graph/entities`、`/relations`、`/mentions` | 均按 KB 限定范围，`entities` 支持 `search` / `type` / `origin` / `visibility` 等 `where` |
| 手工修正 | `POST /graph/entities`、`PATCH /graph/entities/:entityId`、`DELETE /graph/entities/:entityId`；relations 同构 | `DELETE` 实为 `hideEntity` / `hideRelation`：**软隐藏**，退出可见集但保留数据 |
| 邻域与实体切片 | `GET /graph/entities/:entityId/neighborhood`、`GET /graph/entities/:entityId/chunks` | 邻域返回相连关系与实体集合；`entityChunks` 走 `resolveGraphChunks` |
| 目录与可视化 | `GET /graph/catalog`、`GET /graph/visualization` | 目录可作概览；可视化可由 `query` 限制可见性与规模 |
| 单文档重试 | `POST /graph/documents/:documentId/retry` | 控制器内先 `assertKnowledgebaseWriteAccess`，再发 `KnowledgeGraphRetryDocumentCommand`，返回最新进度 |
| 实体向量同步 | `GraphragService.syncEntityVectors`（私有） | 实体向量写入 active collection 派生的 `:graph-entities` collection |
| 结构化图谱写入面 | `StructuredGraphRuntimeService.publish` / `status` / `retract` / `queryEntities` / `readNeighborhood` | 以 `KnowledgeGraphApi` 运行时能力暴露给插件；写入前校验「托管文档 + 属主 xpert/agent」，快照在 KB/source 悲观锁内预留、提交后派发 |
| 身份归一 | `KnowledgeIdentityService.resolve` / `resolveBatch`；`resolveIdentities`（抽取侧） | 批量入口必须带提取标识；每条候选键必填、≤512 且不可重复；模型调用在事务外 |
| 身份候选选择 | `canMatchIdentity` / `selectIdentityCandidates` / `identityText` / `cosineIdentitySimilarity`（`knowledge-identity-policy.ts`） | 名称类歧义**全量**返回；语义相似度只贡献有界名额且仅用于排序 |
| 清理 | `GraphragService.clearDocument(kbId, documentId)` / `clearKnowledgebase(kbId, preservePublications?)` | 文档级与库级清理；后者可决定是否保留发布记录语义 |
| 抽取内部件 | `KnowledgeGraphExtractionService.extract` / `extractOnce` / `resolveIdentities` / `assertCurrent` / `formatChunksForExtraction` | 批量抽取、快照复用、归一落库、并发护栏 |

## 4 边界

**做什么**：图谱索引 job 的生命周期与派发、抽取与写图、实体 / 关系 / 提及 / 社区 / 目录 / 可视化查询、手工修正与软隐藏、邻域与实体关联切片、实体向量同步、结构化图谱运行时写入面；身份归一（含 LLM 裁判）、观察记录与来源锁定。

**不做什么**
- **不含检索与融合**：图谱只是三路召回中的一路（`GraphKnowledgeCandidateRetriever`），融合与重排归 [子专家①](../知识库检索与向量存储子专家/C0-使用总览.md)。
- **不含 Wiki 页面生成**：Wiki 只复用身份层，页面投影与组织归 [子专家④](../知识Wiki与知识组织子专家/C0-使用总览.md)。
- **不含文档登记与摄取**：入图的输入 chunk 由 [子专家②](../文档摄取与流水线子专家/C0-使用总览.md) 产出；本子专家只在被派发时消费。
- **不含 embedding / chat 模型解析**：由 `CopilotModelModule` 与知识库侧句柄提供；本子专家不判额度、不记账。
- **identity 无独立 HTTP 面**：`KnowledgeIdentityService` 只作为服务被抽取链与 Wiki 调用，端点全部挂在图谱控制器下。

## 5 已知问题与常见坑

1. **唯一 `(knowledgebaseId, identityId)` 是归一底线**
   - 现象与触发：手工建实体与抽取实体「看起来重复」，或归一时报唯一键冲突。`KnowledgeGraphEntity` 的 `@Index(['knowledgebaseId', 'identityId'], { unique: true })` 与部分唯一索引 `IDX_graph_manual_entity_name`（`WHERE "identityId" IS NULL`）共同约束：有身份的实体按身份去重，无身份的手工实体按 `(tenant, org, kb, normalizedName, type)` 去重。
   - 正确做法：想合并两个实体必须走身份归一（让它们落到同一 `identityId`），不要在应用层改 `name`。
   - 契约来源：`knowledge-graph-entity.entity.ts`、`GraphragService.assertNoEntityConflict`。
2. **语义检索有界，且从不授权 merge**
   - 现象与触发：以为「相似度高就会被合并」。候选选择里 `identified`（标识符全等）与 `named`（名称 / 别名命中）**全部**返回，纯语义相似度只贡献有界的 `index < 8` 名额，且排序中位于前两者之后。
   - 正确做法：把语义相似度当排序信号而非判定依据；源码注释逐字：「Names retrieve every ambiguous match. Semantic retrieval is bounded and never authorizes a merge.」
   - 契约来源：`knowledge-identity-policy.ts`（`selectIdentityCandidates`）。
3. **域 / 范围文本是证据，不是本地分类**
   - 现象与触发：担心本地规则替 LLM 裁判做分类判断。`canMatchIdentity` 对 `kind !== 'entity'` 的情形直接返回 `true`（不做本地域判断）。
   - 正确做法：域 / 范围文本只进 `identityText(name, descriptor)` 交给裁判；源码注释逐字：「Domain/scope text is evidence for the semantic judge, not a locally inferred taxonomy.」
   - 契约来源：`knowledge-identity-policy.ts`（`canMatchIdentity`）。
4. **`hide` ≠ 删除**
   - 现象与触发：`DELETE /graph/entities/:entityId` 与 `DELETE /graph/relations/:relationId` 返回成功但数据仍在，重新抽取后可能又出现。
   - 正确做法：`visibility` 是软隐藏语义；要真正移除来源贡献应清理对应文档（`clearDocument`）或走库级重建。
   - 契约来源：`GraphragController.deleteEntity` / `deleteRelation` → `GraphragService.hideEntity` / `hideRelation`。
5. **`_contribution` 的 `sourceDocumentIdSnapshot` 是溯源锚点**
   - 现象与触发：按文档删图或重算实体属性时依赖「哪个文档贡献了什么」。实体与关系各有一张 contribution 表，唯一键含 `sourceDocumentIdSnapshot`，属性由 `recomputeEntityFromContributions` / `recomputeRelationFromContributions` 回算。
   - 正确做法：诊断「实体属性为何回退」先看 contribution 行是否随文档清理被删；`mentionCount` 由 `refreshEntityMentionCounts` 重算，`pruneEntities` 会摘掉无贡献实体。
   - 契约来源：`graphrag.service.ts`（`persistExtraction` / `upsertEntity` / `recomputeEntityFromContributions` / `refreshEntityMentionCounts` / `pruneEntities`）。
6. **索引 job 并发与重试**
   - 现象与触发：同一文档重复入队或旧任务回写覆盖新状态。job 行带 `status` / `revision` / `dispatchError`，消费者 `KnowledgeGraphIndexConsumer` 取任务执行；`assertCurrent` / 抽取快照复用（`extractOnce`）用来避免重复调用模型。
   - 正确做法：单文档重试走 `POST documents/:documentId/retry`（内含写权限断言）；批量进度查询入参非法时错误为 `Error.KnowledgeGraphDocumentStatusBatchInvalid`。
   - 契约来源：`graphrag.controller.ts`、`graphrag.job.ts`、`graph-extraction.service.ts`（`assertCurrent`）。
7. **LLM 裁判是成本中心，且在事务外**
   - 现象与触发：`KnowledgeIdentityService` 文件顶部不变量要求模型调用不持 DB 锁；目录被人并发修改时语义裁判返回 `null` 需重试（配 `KnowledgeIdentityBusy`）。
   - 正确做法：把身份错误族（非法 / 陈旧 / 忙碌）当可重试信号而不是数据错误；批量归一优先走 `resolveBatch` 以摊薄模型调用。
   - 契约来源：`knowledge-identity.service.ts`（`resolveBatch` / `judge` / `catalogue` / `lockSource` / `assertSource`）、`knowledge-identity-error.ts`。
8. **`syncEntityVectors` 存在一致性窗口**
   - 现象与触发：实体刚写库、向量未同步时，图谱召回可能查不到该实体；实体 collection 名是 `` `${activeCollectionName}:graph-entities` ``，换 embedding / 重建会整体切换。
   - 正确做法：把实体向量当最终一致；排障时先确认 `getGraphEntityVectorStore` 是否成功，再怀疑抽取本身。
   - 契约来源：`graphrag.service.ts`（`syncEntityVectors`）、`KnowledgebaseService.getGraphEntityVectorStore`。
9. **图谱未启用时的「静默空数组」**
   - 现象与触发：`enqueueDocuments` 在 `isEnabled` 为假时 `return []`，不报错；`rebuildKnowledgebase` 才走 `ensureGraphEnabled` 报 400。
   - 正确做法：调用方必须显式判断返回长度或先读 `graphRag.enabled`；不要把「返回空」当成「文档没有可抽取内容」。
   - 契约来源：`graphrag.service.ts`（`isEnabled` / `enqueueDocuments` / `ensureGraphEnabled`）。
10. **结构化图谱写入面的授权是复合条件**
    - 现象与触发：`StructuredGraphRuntimeService.authorize` 同时要求：文档可读、KB 可写、`document.metadata.systemManagedType === 'agent-writer'`、`ownerXpertId` 与 `ownerAgentKey` 与调用方一致；`publish` 还会在锁内复查 `graphRag.enabled` / `contentHash` / `disabled` / `hardDeletePendingAt`。
    - 正确做法：不要绕过运行时能力面直接写图；文件顶部不变量逐字：「only the managed document owner can publish. Reserve a complete snapshot under the KB/source locks; dispatch after commit. Retrying a structured publication never invokes a model.」
    - 契约来源：`structured-graph-runtime.service.ts`。
