### 1.3 增量同步与幂等

三元组 `sourceKey` + `sourceHash` + `processingHash` 决定文档是否复用：`computeKnowledgeDocumentProcessingHash` 在 `document-hash.ts` 内聚合 `sourceKey`、`sourceHash` 与 `knowledgeChunkingRevision(textSplitterType)`。入口三处：`createBulkIdempotently`、`createBulkWithIncrementalSync`、`createOrReuseSourceDocument`（私有）。chunk 级用 `contentHash` + exact/position match：`syncChunksIncrementally` 先算 `contentHash`，若未变且非 `recoverInterruptedSync` 则整体跳过；变化时调 `matchIncrementalChunks` 产出 `unchanged | changed | ...` 操作集，再按操作集新增/更新/删除。中断恢复由 `recoverInterruptedSync` 标志驱动——置位后 `unchanged` 也参与写回，保证半途中断的集合被补齐。transform 快照的复用由 `computeKnowledgeDocumentTransformFingerprint` 决定，**故意排除** splitter 与 image-understanding 设置。

### 1.4 检索：三类召回 + RRF + rerank + 结构化过滤

`KnowledgeRetriever.retrieveDetailed` 组装参数（`tenantId / organizationId / knowledgebases / query / k / score / rerankThreshold / filters / retrieval / threadId / xpertId`）投递 QueryBus。三路并行召回：`VectorKnowledgeCandidateRetriever`（向量）、`KeywordKnowledgeCandidateRetriever`（`content tsvector` / `keyword_vector` / trigram 索引，由 `KnowledgeKeywordIndexService` 声明 `KNOWLEDGE_KEYWORD_FTS_INDEX` 等索引名）、`GraphKnowledgeCandidateRetriever`（图谱邻域）。融合默认 `WeightedRrfFusion`（按 `weights` 加权 RRF），可切 `LegacyWeightedFusion`。融合后经 `KnowledgeDocumentStore.rerank`（模型来自 `KnowledgebaseService.getRerankModel`）并按 `rerankThreshold` 截断。结构化过滤：非结构化路径 `similaritySearchWithScore`，结构化路径 `structuredSimilaritySearchWithScore`，二者通过 `createSearchSession(query, reuseUnstructuredQuery)` 复用同一查询构造；候选值由 `countStructuredFilterCandidates` / `listStructuredFilterValueCandidates` / `listStructuredFilterFolderCandidates` / `listStructuredGraphEvidence` 提供，随 `KnowledgeGraphFilterScopeService` 限定图谱过滤范围。

### 1.5 embedding 重建与 collection 切换

`POST /api/knowledgebase/:id/rebuild-embedding` → `KnowledgebaseService.startEmbeddingRebuild(id)` 写入 pending 模型与 pending revision 并投递 `rebuild-knowledgebase-embedding`；`KnowledgebaseRebuildEmbeddingConsumer` 调 `processEmbeddingRebuildJob(data)` 逐批重嵌入到 `getPendingVectorStoreForRebuild` 返回的新 collection，成功则 `promoteEmbeddingRebuild(knowledgebaseId, rebuildTaskId, pendingEmbeddingRevision)` 原子切换 active collection 并把 chunk metadata 的 `model` 改成 `getEmbeddingModelName(saved.copilotModel)`，随后 fire-and-forget 调 `cleanupEmbeddingCollection(promoted, oldCopilotModel, oldCollectionName)` 清旧 collection（内部再 `createVectorStoreForModel` 构造旧 store）。失败走 `markEmbeddingRebuildFailed(data, error)` 写 `embeddingRebuildError`。重建期间 `assertNotRebuilding(knowledgebaseId)` 阻断其它写操作。`cancelPendingEmbeddingModel(id)` 撤销 pending。维度解析由 `resolveEmbeddingDimensions` 完成，模型切换比较由 `resolveEmbeddingModelTargetForComparison` 完成。

## 2. 设计模式及落点

- **CQRS**：写走 `CommandBus`、读走 `QueryBus`。跨子模块联动集中在 `KnowledgeDerivedIndexPublicationService.publish`（一次派发 `KnowledgeAutoTaggingEnqueueCommand` / `KnowledgeQuestionsEnqueueCommand` / `KnowledgeGraphEnqueueCommand` 或 `KnowledgeGraphRetryDocumentCommand` / `KnowledgeWikiEnqueueSourceCommand`）。
- **Bull 消费者**：7 个 `@Processor`，队列名集中在各子模块 `types.ts` 或 command 文件（`JOB_EMBEDDING_DOCUMENT` / `JOB_KNOWLEDGE_AUTO_TAGGING` / `JOB_KNOWLEDGE_QUESTIONS` / `JOB_KNOWLEDGE_GRAPH_INDEX` / `JOB_KNOWLEDGE_WIKI_GENERATION` / `JOB_REBUILD_KNOWLEDGEBASE_EMBEDDING` / `JOB_FAQ_SEMANTIC_PREWARM`）。
- **策略注册**：`VectorStoreRegistry`（plugin-sdk）按 `VectorTypeEnum` 分派；`DocumentSourceRegistry` / `TextSplitterRegistry` / `DocumentTransformerRegistry` / `ImageUnderstandingRegistry` / `KnowledgeStrategyRegistry` / `RetrieverRegistry` / `KeywordAnalyzerRegistry` 同样来自 plugin-sdk；`RagCreateVStoreHandler.execute` 用 `switch` + 注册表兜底，`throw InternalServerErrorException` 时报 `xpert.Error.UnsupportedVectorStore`。
- **就绪门（readiness gate）**：`KnowledgeProcessingReadyService` 用一个受 `OnApplicationBootstrap` resolve 的 Promise，让 Bull worker 等到 CQRS handler 注册完成。
- **幂等三元组**：`sourceKey` + `sourceHash` + `processingHash` 是文档级幂等键；`contentHash` 是 chunk 级幂等键；`publication_attempt.idempotencyKey` 是发布级幂等键。
- **事务外模型调用**：`KnowledgeIdentityService` 顶部注释「model calls never hold DB locks. Commit under the KB lock only if source and catalogue ...」，LLM 裁判在事务外执行，回写前用 catalogue fingerprint 比对，不一致返回 `null` 重试（配合 `knowledge-identity-error.ts` 的 `KnowledgeIdentityBusy`）。

## 3. 热点路径

1. **摄取主链**（最高频、最长耗时）：`createBulk*` → `startProcessing` → `embedding-document`（concurrency 5）→ 解析/切片/embedding/写向量。解析与 embedding 同队列，是超时与内存的主要来源。
2. **检索融合**：每次 Agent 调用都走三路候选召回 + RRF + rerank，`KnowledgeDocumentStore.createSearchSession` 的查询复用是性能关键点。
3. **重授权 / 重建**：`startEmbeddingRebuild` 期间 `assertNotRebuilding` 会阻断同一 KB 的其它写操作，是「长事务式的全局锁」形态。
4. **派发扇出**：文档 FINISH 后的 `publish` 会对 tags / questions / graph / wiki 各发一条命令，`catch` 使 Redis 不可用时的失败静默。

## 5. 技术债与 hack

1. **路由遮蔽**：`KnowledgebaseController.@Get(':id')` 与 `KnowledgeTagUsageController.@Get('tag-usage')` 同为 `/api/knowledgebase/<单段>`；`knowledgebase.module.ts` 的 controllers 顺序为 `[KnowledgebaseController, KnowledgeFAQController, KnowledgeTagController, KnowledgeTagUsageController]`，`tag-usage` 可能先命中 `:id` 并被 UUID 校验拒绝（需实测确认）。修法是把 `tag-usage` 改独立前缀或前置注册。
2. **多数路由无 `@UseGuards`**：仅 3 处 `PermissionGuard`，其余靠全局 `AuthGuard` + service 断言。新增查询方法若绕过 `assertKnowledgebase*Access` 或漏掉 `hardDeletePendingAt` 过滤，即产生越权与「读到待硬删文档」风险。
3. **前缀双挂载**：`GraphragModule` 与 `KnowledgeWikiModule` 都注册 `path: '/knowledgebase'`，与 KB 主模块同前缀，靠 `@Controller` 段区分；新增控制器极易与 `:id` 段冲突。
4. **`indeterminate` 需人工恢复**：删除与发布协议显式承认「结果未知」，无自动收敛路径，必须靠 wiki 的恢复动作暴露给运维。
5. **`keywordAnalyzer` 声明 `update: false`**：普通 `save()` 不生效，只有条件 SQL 能写，极容易「改了不生效」。
6. **`rag-web` 两处疑点**：`provider/index.ts` 中 `import Notion from './playwright/schema'`（Notion 复用 Playwright 的 schema，疑似复制粘贴）；`rag-web/loader.ts` 是 **0 字节空文件**。
7. **派发静默失败**：`KnowledgeDerivedIndexPublicationService.publish` 对每项 `catch`，Bull/Redis 不可用时 graph/wiki/tag 会静默滞后，无告警面。
8. **约 30 个 integration spec 默认 skip**：需 `KNOWLEDGE_WIKI_PG_E2E` / `KNOWLEDGE_IDENTITY_PG_E2E` / `KNOWLEDGE_GRAPH_PG_E2E` / `KNOWLEDGE_KEYWORD_PG_E2E` / `KNOWLEDGE_TAGGING_PG_URL` / `WIKI_V15_PG_URL` / `BOM_GRAPH_PG` 等环境变量开启，CI 不注入等于 DB 回归未跑。`rag-web` 测试还需 `node --experimental-vm-modules`。
9. **wiki 的 `requiresAdditionalChargeConfirmation` 中间态**：由 `KnowledgeWikiService.toRecoveryAction` 与 `knowledge-wiki-document-progress.ts` 的 `row.uncertain` 推出，表示「该模型调用可能已计费但结果未落地」，是不可自动重试的第三个状态。
10. **模型依赖硬失败**：embedding / rerank / vision / wiki / chat 模型未配置或无权限时链路直接抛错（`Embeddings model '...' not found for knowledgebase '...'`），无降级。

## 6. 设计维度分析

### 6.1 维度一：一致性策略——「主链强一致 + 派生索引最终一致」

主链（文档 → chunk → 向量）走「durable FINISH 才放行」的强约束：源文档必须先落库成功，`KnowledgeDerivedIndexPublicationService` 才发出派生命令（源码注释明写）。派生侧则是最终一致：tags / questions / graph / wiki 各自独立队列、独立重试，失败只被 `catch` 吞掉。这一取舍的代价被显式记账——删除与发布引入 `deletion_intent` / `cleanup_receipt` / `publication_attempt` 三表与 `indeterminate` 状态，把「不确定」从隐式变成可查询、需人工介入的第一类状态。相比「全链一个事务」的写法，这里选择了可观测的可补偿性，而不是原子性。

章节来源：[packages/server-ai/src/knowledge-document/derived-index-publication.service.ts](file://packages/server-ai/src/knowledge-document/derived-index-publication.service.ts)（关键符号：KnowledgeDerivedIndexPublicationService.publish）；[packages/server-ai/src/knowledge-document/deletion/entities.ts](file://packages/server-ai/src/knowledge-document/deletion/entities.ts)（关键符号：knowledge_document_deletion_intent / knowledge_document_deletion_cleanup_receipt / knowledge_document_publication_attempt）

### 6.2 维度二：可替换性策略——「向量存储三层抽象」

`rag-vstore` 用「内置 PG 分支 + 注册表插件分支」的双轨把存储差异收敛在一层：`RagCreateVStoreHandler.execute` 先 `switch (vectorStore)`，`VectorTypeEnum.PGVECTOR` 直接 `new KnowledgePGVectorStore(...)` 并 `ensureTableInDatabase()` / `ensureCollectionTableInDatabase()`（表名硬编码 `knowledge_document_vector` + `knowledge_document_collection`），其余类型回落到 `VectorStoreRegistry.get(vectorStore).createStore()`，无匹配则抛 `UnsupportedVectorStore`。上层只认 `KnowledgeDocumentStore` 的接口，因此切换存储不会污染检索或摄取逻辑。代价是 PG 分支的表名与列名硬编码在 handler 内，且 collection 轮换（重建）依赖 `pending*` 字段在应用层协调，存储层不提供原子换名。

### 6.3 维度三：幂等策略——「三元组收敛 + 细粒度匹配」

幂等不是单点开关，而是三级收敛：文档级用 `sourceKey` + `sourceHash` + `processingHash` 判定「同一文档同一处理配置」；chunk 级用 `contentHash` + exact/position match 判定「这个片段是否真的变了」；发布级用 `publication_attempt.idempotencyKey`。这样 `processingHash` 变了（例如换了 parser 或 chunking revision）会触发重切重嵌，而只是 splitter / image 设置变化时 `transformFingerprint` 故意不变以免无谓失效。中断场景由 `recoverInterruptedSync` 显式回补，把「取消后重启」也纳入幂等模型。

## 7. 结论

实现层面的主线是「同步元数据入库 + 异步重活入队 + 显式补偿表」。同步侧集中了幂等判定（三元组）、作用域与权限断言、版本号乐观锁（`updateWithVersion` / `deleteBulkWithVersion` / `updateChunkWithVersion`）；异步侧集中了 7 个队列与就绪门；一致性侧集中了删除/发布四表与 `indeterminate` 人工补偿。可改进优先级：① 修 `tag-usage` 路由遮蔽；② 补齐写路由的显式守卫或断言检查清单；③ 为 `publish` 的逐项 `catch` 增加可观测性；④ 补 `rag-web` 的 `loader.ts` 空文件与 Notion schema 复用；⑤ 在 CI 中至少开启一组 PG integration。
