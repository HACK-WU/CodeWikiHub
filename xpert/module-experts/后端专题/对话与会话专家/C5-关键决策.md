## 决策 ① 取消是协作式（`AbortSignal`），队列查找用扫描而非 Redis 索引

- **分类**：并发与取消语义。
- **动机**：避免为了「停止」而强杀进程或维护一份与队列状态可能不一致的索引。
- **决策**：取消通过 `AbortSignal` 传导，**不强杀同步 CPU 密集代码**；队列查找用逐个队列扫描（`waiting`/`delayed`/`paused`/`active`）而非 Redis 索引键；`waiting`/`delayed`/`paused` 直接 `removeJobs`，`active` 走 `HandoffCancelService.cancelMessages`（本进程 `AbortController.abort()` + Redis pub/sub `ai:handoff:cancel` 跨实例）；结果统一归一为 `dead(canceled:<reason>)`，**不进死信、不重试**。
- **背景约束**：stop 是低频操作；`active` 取消天然对竞态敏感；取消分类必须跨 dispatcher、队列处理器、命令处理器三处一致（`buildCanceledReason`/`isCanceledReason`/`isAbortLikeError`）。
- **被否决方案**：**Redis 索引键**。README 原文："Queue lookup uses scanning instead of Redis index keys."
- **重新评估触发条件**：队列 job 量增长到扫描成本不可接受时（README 明写 "Cost is proportional to current job volume."）；或出现「取消成功率」不达标且无法用 best-effort 竞态解释时。
- **关联代码**：[stop-handoff-message.handler.ts](file://packages/server-ai/src/handoff/commands/handlers/stop-handoff-message.handler.ts)、[handoff-cancel.service.ts](file://packages/server-ai/src/handoff/handoff-cancel.service.ts)、[handoff-queue-gateway.service.ts](file://packages/server-ai/src/handoff/dispatcher/handoff-queue-gateway.service.ts)、[cancel-reason.ts](file://packages/server-ai/src/handoff/cancel-reason.ts)、[message-dispatcher.service.ts](file://packages/server-ai/src/handoff/message-dispatcher.service.ts)
- **证据来源**：[handoff/README.md](file://packages/server-ai/src/handoff/README.md)（"Cancellation is cooperative." / "Canceled results do not go to dead-letter and are not retried." / "Active cancel is best-effort and race-sensitive."）

## 决策 ② inbox/outbox 与 Invocation CAS 同事务

- **分类**：一致性 / 事务边界。
- **动机（避坑）**：**现象** —— 若先把结果写进 Invocation、再单独入队通知，则队列或 Redis 抖动会发生在两次写之间；**后果** —— 已提交的运行时结果永久丢失且无重试入口（Invocation 已是终态，不会再次产生投递意图）。
- **决策**：`appendRuntimeDelivery(manager, invocation)` 必须与 Invocation CAS 在**同一事务**内执行，用 `orIgnore()` 做幂等插入；`RuntimeMessageInboxService.receive` 同样把 `lockInbox`、`input_request` 的 `processed/superseded` 标记、delivery 置 `received` 放在同一事务。
- **背景约束**：事件只由 Invocation 事实派生（终态出 `result`、`waiting` 且有 interaction 出 `input_request`，其余含 progress 不产出）；`messageId = runtime-{invocationId}-{kind}-{revision}` 保证同版本重复提交可被 `orIgnore()` 吞掉。
- **被否决方案**：无（文档未记录被否决方案；此处的架构承诺是单向约束而非方案比选）。
- **重新评估触发条件**：若 CAS 事务的写放大成为瓶颈、需要把 outbox 拆出事务时 —— 届时必须补一套「Invocation 终态 → 补投递意图」的对账扫描，否则不满足本决策的前提。
- **关联代码**：[runtime-message-outbox.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-outbox.ts)、[typeorm-invocation.store.ts](file://packages/server-ai/src/agent-invocation/typeorm-invocation.store.ts)、[runtime-message-inbox.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-inbox.service.ts)
- **证据来源**：`runtime-message-outbox.ts` 逐字注释：`/** Must share the Invocation CAS transaction: a queue outage cannot discard a committed result. */`；[runtime-messaging/README.md](file://packages/server-ai/src/handoff/runtime-messaging/README.md) 第 1 条 "commits the observation and `agent_runtime_delivery` in one transaction."

## 决策 ③ 不从传输成功推断 Task 完成；Invocation 是运行时账本

- **分类**：领域边界 / 事实归属。
- **动机（避坑）**：**现象** —— 队列 ack、enqueue 成功、SSE 收流都可被误当成「任务已完成」；**后果** —— 业务任务被提前判成功，人工/业务侧的验收决策失去依据（本域文档明确 "Final acceptance and `done` decisions belong to stage 4"）。
- **决策**：`Invocation remains the runtime ledger. Project Tasks retain business decisions.` 本域只提供持久 outbox/inbox 与消费认领，**不注册第二个执行器**，也不从传输成功推断 Task 完成；Task 投影只把「实际开始」映到 `in_progress`、成功映 `review`、失败映 `blocked`；`Cancelling an Invocation does not cancel the Task.`
- **背景约束**：自动投影要求「最新实施尝试 + 未变规范 + 捕获到的 task revision」，最终写还用 revision CAS（因为部分 legacy writer 不取 Project 锁）。
- **被否决方案**：**把传输成功当 Task 完成**、**另注册一个执行器**。README 原文："it does not register another executor or infer Task completion from transport success."
- **重新评估触发条件**：若 Task 与 Invocation 的归属被重新划分（例如 Task 下沉到执行链域），或需要让本域直接决定 `done`。
- **关联代码**：[runtime-message-transport.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-transport.service.ts)、[runtime-observation-monitor.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-observation-monitor.service.ts)、[runtime-message.entity.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message.entity.ts)
- **证据来源**：[runtime-messaging/README.md](file://packages/server-ai/src/handoff/runtime-messaging/README.md)（首段 + "Observation and Project projection" 一节）；台账列注释 "投递状态故意与 Task/Invocation 状态解耦"。

## 决策 ④ `consumer_outcome_unknown` 不得重放；本域不是 exactly-once

- **分类**：可靠性语义。
- **动机（避坑）**：**现象** —— 消费进程在「结果已提交、收尾未完成」之间被杀，或 Bull ack 窗口未确认；**后果** —— 系统无法判定模型/CLI 是否真的跑过。若自动重试，就会重复执行模型与 CLI（可能重复扣费、重复产生副作用）。
- **决策**：明确只提供 **可重试投递 + 幂等消费**，即 at-least-once 投递，**不是 exactly-once**（网络与模型执行都做不到）。`recover` 只按 claim 里记录的 executionId 查执行：终态则 `processed`（否则 `consumer_ended_without_success`），非终态一律 `blocked` + `consumer_outcome_unknown`，**不自动重放、不重启 CLI、不分配替代消费者**。
- **背景约束**：`reserved` 消费者可恢复同一 execution ID，`started` 之后只检查该执行；`enqueue` 成功只推后 `nextAttemptAt`（+30s），lost ack 会重发同一 `messageId`，重复由 inbox 唯一键 + `orIgnore()` 兜底。
- **被否决方案**：**自动重放模糊结果**、**重启 CLI**、**分配替代消费者**。README 原文："Neither transport retries nor redrive relaunches the CLI or allocates a replacement consumer."；"ambiguous launches remain unknown and are never replayed."
- **重新评估触发条件**：若上游执行器提供幂等执行契约（例如可携带稳定 execution ID 做去重），才可能允许对 `consumer_outcome_unknown` 自动收敛。
- **关联代码**：[runtime-message-continuation.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-continuation.service.ts)、[runtime-message-inbox.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-inbox.service.ts)、[runtime-message.errors.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message.errors.ts)
- **证据来源**：[runtime-messaging/README.md](file://packages/server-ai/src/handoff/runtime-messaging/README.md)：第 6 条与 "This provides retryable delivery and idempotent consumption, not exactly-once network or model execution."

## 决策 ⑤ 滚动升级：先部署消费者，再部署生产者

- **分类**：发布与兼容性。
- **动机（避坑）**：**现象** —— 新版生产者先上线并开始写新 provenance/新事件字段；**后果** —— 旧宿主在严格命令边界直接拒绝新 `source`/`correlation` 字段，事件已提交但无人能消费（"事件已提交但无人消费"的窗口）。
- **决策**：迁移与宿主启动顺序固定为：先执行 `xpert-project/migrations/20261006-project-task-runtime.sql`，再执行 `packages/server-ai/src/handoff/runtime-messaging/migrations/20261006-runtime-reliable-replies.sql`，**然后启动新版宿主**；滚动时**先部署消费者，再部署生产者**。两份迁移均为加性、`IF NOT EXISTS`、可重复执行。
- **背景约束**：任务书同类约束还有 —— `20260922-conversation-branch.sql` 与 `20261005-message-envelope.sql` 必须**先于**对应能力部署执行；迁移由发布流程手工按序 `psql` 执行（仓库无统一 migration runner）。
- **被否决方案**：**先部署生产者、后部署消费者**（与文档明确要求的顺序相反）。README 原文："Roll out consumers before producers."
- **重新评估触发条件**：若引入严格向后兼容的事件信封与灰度开关（旧宿主可忽略未知字段），才可能放开顺序约束。
- **关联代码**：[20261006-runtime-reliable-replies.sql](file://packages/server-ai/src/handoff/runtime-messaging/migrations/20261006-runtime-reliable-replies.sql)、[20261005-message-envelope.sql](file://packages/server-ai/src/chat-message/migrations/20261005-message-envelope.sql)、[20260922-conversation-branch.sql](file://packages/server-ai/src/chat-conversation/migrations/20260922-conversation-branch.sql)

## 决策 ⑥ 分支=写模型 / 地图=只读无表视图

- **分类**：架构分层（写模型 vs 读投影）。
- **动机（避坑）**：**现象** —— 若把「脉络导航」做成一张持久化表，就要为它承担迁移、回填与并发更新；**后果** —— 每次会话/消息语义变化都要同步改两张表，且地图与真相可能漂移。
- **决策**：**分支是写模型** —— `ConversationBranchService.branch` 在 `dataSource.transaction` 内对源线程 `pessimistic_write` 行锁，复制消息谱系（含 `parentId`/`messageEnvelope`/检查点/`fileAssets` 链接、重算 `messageHash`/`messagePathHash`）并写 `branchSource` 与 `metadata.forkGraphRevision`，`requestId` 幂等。**地图是只读视图** —— `ConversationMapService` 无 entity、无表、无迁移，`scope()` 做 host context 与 `RequestContext` 三重比对后 `read/projectOptions/act`，每次查询重算。分支模块注释原文："Compose domain dependencies here; callers use the command without importing this module."
- **背景约束**：两者共用同一批实体却对「一致性」给出不同答案：分支用事务+行锁+检查点闭包换可独立续跑的历史副本（写放大、长事务）；地图用零表投影换取免迁移与低耦合（读放大、依赖宿主特性开关 `CONVERSATION_MAP_FEATURE` 与 slot `AGENT_WORKBENCH_SLOT`）。
- **被否决方案**：无（文档未记录为地图建表的正式否决记录；`ConversationMapModule` 的 imports/providers 中确实不存在 `TypeOrmModule.forFeature`）。
- **重新评估触发条件**：地图查询规模增长到每次重算不可接受（例如需要跨大量会话分页搜索）时；或宿主不再提供 view-extension Discovery 时。

## 决策 ⑦ envelope 不是命令/授权、不放 prompt 与凭据、分支复制保留原 envelope

- **分类**：契约边界与安全。
- **动机（避坑）**：**现象** —— 若把 envelope 当命令/授权载体，第三方 payload 就能影响 host provenance 或权限判定；**后果** —— 越权与审计失真（一个「只是展示来源」的字段承载了授权语义）。
- **决策**：`TChatMessageEnvelope` 只描述「谁产生了输入、它在会话中如何呈现」，**不是**命令、模型角色、运行时主体、路由请求或权限授予；执行仍归 `XpertChatCommand`、handoff 队列与既有 Agent 调用/任务运行时。公开 mutation 的写白名单**不含**该字段；HTTP 历史、消息查找、递归分页与流式输入确认共用同一 presentation 策略；**分支复制保留原 envelope**（含已审计的目的地与关联）。
- **背景约束**：可信生产者写 `options.messageEnvelope`，命令入口（含队列投递）**只校验一次**（失败 400 `Error.ChatMessageEnvelopeInvalid`）；`version` 当前为字面量 `1`；`presentation='runtime'` 只是「不进入公开历史」，**呈现策略不把输入从模型祖先或重试中移除**（隐藏 ≠ 未参与推理）；非法/未知持久化版本对公开历史隐藏但运行时水合保留。
- **被否决方案**：**让第三方 payload 决定 host provenance/presentation**。MESSAGE-ENVELOPES 原文："Third-party message payloads do not determine host provenance or presentation." 以及 "Do not put prompt text, credentials or authorization claims in the envelope."（**禁止**写入 prompt 文本、凭据或授权声明。）
- **重新评估触发条件**：若引入新的可信生产者需要新的 `source` 判别联合分支，或需要跨版本兼容非 `1` 的 envelope；扩展时"无需新增列（No additional column is needed for this JSONB extension）"这一结论需一并复核。
- **关联代码**：[message-envelope.schema.ts](file://packages/server-ai/src/chat-message/message-envelope.schema.ts)、[upsert.handler.ts（消息）](file://packages/server-ai/src/chat-message/commands/handlers/upsert.handler.ts)、[conversation-branch.service.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/conversation-branch.service.ts)
- **证据来源**：[MESSAGE-ENVELOPES.md](file://packages/server-ai/src/chat-message/MESSAGE-ENVELOPES.md)（首段、"Boundaries and persistence" 一节，含 "Branch copies retain the original envelope, including its audited destination and correlation."）、[20261005-message-envelope.sql](file://packages/server-ai/src/chat-message/migrations/20261005-message-envelope.sql)

## 决策 ⑧ pause 受理 ≠ 检查点完成 + 进程租约 15s/90s + 不重放工具

- **分类**：运行控制与进程生命周期。
- **动机（避坑）**：**现象** —— 客户端把 `202 + pauseId` 当成「已暂停」并据此认为可以安全断线/关机；**后果** —— 检查点尚未落库，恢复时无法重建上下文，或由 staged checkpoint 伪造出一个「已确认暂停」而重复执行工具。
- **决策**：`pause` 是无 body 的控制命令，线程行锁内返回 `202` + execution ID + state + `pauseId`，语义**只是 `pausing`**；Node admission guard 阻止下一步启动；**只有 finalization（检查点与消息持久化之后）才确认 `paused`**；工作流自然结束则转 `idle`。新 run 与 resume claim 在 thread metadata 携带**私有进程租约（每 15s 续约、90s 寿命）**，公开线程 DTO 不含租约元数据；替代进程在一个事务内把未收尾 run 标 `error`、中断执行/消息状态、失效延迟续跑，**不重放工具、不伪造已确认暂停**；无租约的旧 run **不按时长猜死**，只能显式 stop。
- **背景约束**：同一活跃暂停的重复请求返回同一 token，旧执行不能暂停替代它的新 run；`resume` 必须携带 `pauseId`（缺失 400 `Error.PauseTokenRequired`）并重新校验 graph revision 与检查点、恢复加密运行时上下文、新建执行尝试；`releaseDisplayPause`（204）只是旧 SDK 兼容通道。暂停**不撤销**已完成操作，也不中断在途外部动作。
- **被否决方案**：**重放工具**、**由 staged checkpoint 伪造已确认暂停**。thread-run-control.md 原文："It does not replay tools or manufacture a confirmed pause from a staged checkpoint."
- **重新评估触发条件**：若运行时支持真正的中断点续跑工具语义（幂等工具/可补偿动作），才可能放开「不重放」约束；或需要让无租约旧 run 自动回收时。
- **关联代码**：[thread-run-control.service.ts](file://packages/server-ai/src/chat-conversation/thread-run-control.service.ts)、[thread-run-lease.ts](file://packages/server-ai/src/chat-conversation/thread-run-lease.ts)、[chat-execution-admission.service.ts](file://packages/server-ai/src/chat-conversation/chat-execution-admission.service.ts)、[thread.controller.ts](file://packages/server-ai/src/ai/thread.controller.ts)
- **证据来源**：[thread-run-control.md](file://packages/server-ai/src/chat-conversation/thread-run-control.md)（"Request acceptance means `pausing`, not checkpoint completion." / "Process loss" 一节）

## 决策 ⑨ Redrive never changes an Invocation or clears a user stop

- **分类**：运维语义与人工干预边界。
- **动机（避坑）**：**现象** —— 把 redrive（重排传输）当成「重跑一次」的总开关；**后果** —— 用户显式 stop 被绕过、Invocation 账本被篡改、模糊启动被重复执行，审计与业务事实双双失真。
- **决策**：`RuntimeDeliveryController` 的类注释逐字写明 redrive 的边界；`redrive` body 为 strict 空对象 `{}`；经 `RuntimeMessageAccessService.withReply` **重授权原回复目标**后，在事务内只把 `blocked|failed` 的 delivery 复位为 `pending/attempts=0`、把 `blocked|failed` 且 `event->>'kind'='result'` 的 inbox 复位为 `pending/attempts=0`；**保留 claim、phase 与用户 stop 屏障**。
- **背景约束**：`GET /api/agent-invocations/:id/delivery` 是 owner 作用域回执（绑定被撤销但仍具有效组织成员关系的 owner 也能查看传输失败），**不暴露执行结果正文、不授予运行时权限**；对 `consumer_outcome_unknown`，redrive 只检查 claim 中记录的**同一执行身份**；对显式用户 stop，必须改在手工轮次读取结果而不是绕过 stop。
- **被否决方案**：**redrive 时清除用户 stop 屏障**、**用 redrive 绕过显式 stop**。README 原文："For an explicit user stop, read the result in a manual turn rather than bypassing the stop."
- **重新评估触发条件**：若需要「管理侧强制解封」能力，必须新增独立命令并单独审计，而不是放宽 redrive 语义。
- **关联代码**：[runtime-delivery.controller.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-delivery.controller.ts)、[runtime-result-check.handler.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-result-check.handler.ts)、[runtime-message-access.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-access.service.ts)
- **证据来源**：`runtime-delivery.controller.ts` 类注释逐字：`/** Owner-authorized transport operations. Redrive never changes an Invocation or clears a user stop. */`；[runtime-messaging/README.md](file://packages/server-ai/src/handoff/runtime-messaging/README.md)（"Operations" 第 2 条）

## 决策 ⑩ 群组按会话 id 绑定；项目作用域双阶段

- **分类**：身份/作用域绑定契约（跨前后端）。
- **动机（避坑）**：**现象** —— 群会话被当成「加载某个助手私有线程的会话」，或把初始项目选择当成运行中会话的持久项目；**后果** —— 群路由去拉不存在的助手私有线程（越权或 404），以及在运行中切换项目导致 composer/资源校验与已保存会话不一致。
- **决策**：
  1. **群组按会话 id 绑定**：`WorkbenchChatFacade` 契约注释逐字 —— `/** Group sessions are bound by conversation ID; they do not load a private Assistant thread. */`。后端侧对应 `GroupAccessService.authorize` 的凭据约束：群凭据必须 `clientSecretBindingType=USER_CONVERSATION`、`resourceScope.kind='conversation'` 且 `conversationId===groupId`。
  2. **项目作用域双阶段**：契约区分「初始选择」与「持久项目」—— `/** Initial session binding only; ChatKit resolves runtime Project scope from the saved conversation. */`（`chatkitMountProjectId`）、`/** Initial draft intent; distinct from a running conversation's persisted Project. */`（`chatkitProjectSelection`）、`/** Refresh the persisted Project after a run starts or finishes, without starting a new conversation. */`（`syncConversationProject`）。
- **背景约束**：群业务不拥有 HTTP 适配器（群接口全部注册在 `ai/groups/`），本域只提供策略与服务；`GroupWorkswitchGuard`/`GroupWorkbenchGuard` 进一步把群凭据绑到已发布主 Assistant 的私有运行时（`purpose='group_assistant_runtime'`）。
- **被否决方案**：无（文档未记录被否决方案）。
- **重新评估触发条件**：若 ChatKit 不再从已保存会话解析运行时项目作用域，或群会话需要跨会话复用同一运行时线程时。
- **关联代码（后端）**：[group-access.service.ts](file://packages/server-ai/src/chat-group/group-access.service.ts)、[group-members.service.ts](file://packages/server-ai/src/chat-group/group-members.service.ts)、[group-workbench.guard.ts](file://packages/server-ai/src/ai/groups/group-workbench.guard.ts)
- **关联代码（前端契约源）**：[workbench-chat.facade.ts](file://apps/cloud/src/app/features/chat/workbench-chat/workbench-chat.facade.ts)

## 决策 ⑪ `messages.sequence` 由会话行锁分配

- **分类**：排序与写入并发。
- **动机（避坑）**：**现象** —— 若每个写入方各自生成顺序号或依赖 `createdAt` 排序，同一会话的并发写入会出现重复序号或跨域读取方拿到不可比的顺序；**后果** —— 分页游标、未读统计、群快照 `hasMore` 判定全部不可靠。
- **决策**：`sequence` 的分配契约写在会话行上 —— `ChatConversation.lastMessageSequence` 注释逐字：`/** Last allocated message position; allocated under the conversation row lock. */`；消息表以唯一索引 `(conversationId, sequence)` 兜底；群发布路径在群会话行锁内 `locked.lastMessageSequence++` 分配；`sequence` 列**可空**，更新时复用原值。
- **背景约束**：实测当前**唯一推进点是群聊 `publish`**，私有会话消息 `sequence` 常驻 `NULL`；因此普通会话的转录顺序由 `parentId` 父链与 `createdAt` 决定（订阅者 `afterLoad` 按 `createdAt` 排序），群聊顺序由 `sequence` 定义 —— **跨域读取方不能假定 `sequence` 恒存在**；`revision` 是快照版本且会因投递失败推进，**不能**当消息计数或回放游标。
- **被否决方案**：无（文档未记录被否决方案）。
- **重新评估触发条件**：若要让私有会话也支持按 `sequence` 游标翻页，需要（a）新增分配点、（b）对历史 `NULL` 行回填 —— 两者都会改变跨域读取方的假设，必须同步更新文档与读取方。
- **关联代码**：[conversation.entity.ts](file://packages/server-ai/src/chat-conversation/conversation.entity.ts)、[chat-message.entity.ts](file://packages/server-ai/src/chat-message/chat-message.entity.ts)、[group-messages.service.ts](file://packages/server-ai/src/chat-group/group-messages.service.ts)、[upsert.handler.ts（消息）](file://packages/server-ai/src/chat-message/commands/handlers/upsert.handler.ts)
- **证据来源**：`conversation.entity.ts` 实体列注释逐字（"allocated under the conversation row lock"）；[对话与会话专家 · 04-模型](file://.module-experts/后端专题/对话与会话专家/implementation/04-模型.md)（"已知风险与坑" #1）；[tables.md](file://.fe-index/xpert-server/tables.md)（`chat_message` 被 13 个模块引用，跨域读取方众多）
