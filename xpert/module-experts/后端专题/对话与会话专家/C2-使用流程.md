# 对话与会话域 · 使用流程（C2）

> 面向接入方与运维：9 条可执行 Recipe，覆盖会话/消息写入、分支、群聊、运行时投递、取消、暂停恢复、死信 redrive、conversation-map 对接与排障。
> 本文引用的符号、路径、错误码、注释原文均来自源码与设计文档；代码示例是按真实符号组织的调用骨架（非逐字源码摘抄），逐字引用的注释已加引号。

## Recipe 总览

| # | Recipe | 入口符号 | 事务边界关键点 |
|---|---|---|---|
| ① | 创建会话并持续写入消息 | `ChatConversationUpsertCommand` / `ChatMessageUpsertCommand` | 单条 upsert；读状态独立 upsert |
| ② | 从某条消息分支出新会话 | `ConversationBranchCommand` | 源线程行锁 + 全量复制同事务 |
| ③ | 群聊发布并查成员可见投影 | `GroupMessagesService.submit` → `publish` / `snapshot` | 群会话行锁 + 收据 fan-out 同事务 |
| ④ | 消息投递给运行时 | `HandoffQueueService.enqueue*` → 4 个消费者 | 入队不构成回执 |

| ⑨ | 排障：重复/丢失/顺序错乱 | — | 只读诊断，不改状态 |

### Recipe ① 创建会话并持续写入消息（含 sequence 与未读）

**业务目标**：建立一段可读、可续写、未读数正确的会话，并让外部读取方拿到稳定的消息顺序。
**调用顺序**：`POST /api/ai/conversations`（或 `/api/chat-conversation` 侧）→ `ChatConversationUpsertCommand` → `ChatConversationService.create`（容错 `ensureInitialReadState`）→ 逐条 `ChatMessageUpsertCommand` → `ChatMessageUpsertHandler.execute`（`applicationTracing.traceAsync('message.persist')`）→ 可选 `POST /:id/read-state` → `markRead`。
**事务边界**：会话 upsert、消息 upsert 各自独立事务；读状态写入是独立 upsert（唯一索引 `IDX_chat_conversation_read_state_unique(tenantId,organizationId,conversationId,userId)`）；`sequence` 只在群发布路径于群会话行锁内推进，普通会话消息 `sequence` 常驻 `NULL`。
**预期结果**：会话行含 `revision`（公开快照版本）、`lastMessageSequence`（"allocated under the conversation row lock"）、`branchSource` 为空；消息行含 `parentId` 父链与 `messageEnvelope`（可空）；`GET /:id/state` 返回线程态。
**错误处理**：`projectId`/`xpertId` 变更被 `assertImmutableBindings` 拒绝（`Error.ConversationProjectImmutable`、`ConversationXpertImmutable`）；越权统一 `403 Error.ConversationAccessDenied`；`messageEnvelope` 校验失败 400 `Error.ChatMessageEnvelopeInvalid`。
**真实代码示例**：
```ts
// 写入统一经命令（唯一写入口，禁止直查仓库）
await commandBus.execute(new ChatConversationUpsertCommand({ title, xpertId, from: 'platform' }))
await commandBus.execute(new ChatMessageUpsertCommand({ conversationId, role: 'human', content, parentId }))
// 读侧必须经授权入口
const message = await chatMessageService.findOneAuthorized(id, { relations })

章节来源：[upsert.handler.ts（会话）](file://packages/server-ai/src/chat-conversation/commands/handlers/upsert.handler.ts)、[upsert.handler.ts（消息）](file://packages/server-ai/src/chat-message/commands/handlers/upsert.handler.ts)、[conversation.entity.ts](file://packages/server-ai/src/chat-conversation/conversation.entity.ts)、[chat-message.service.ts](file://packages/server-ai/src/chat-message/chat-message.service.ts)、[conversation.controller.ts](file://packages/server-ai/src/chat-conversation/conversation.controller.ts)
```

### Recipe ② 从某条消息分支出新会话（`requestId` 幂等、复制检查点）

**业务目标**：以某条历史消息为锚点，复制出可独立续跑的会话与线程（含检查点、文件链接）。
**调用顺序**：`POST /api/ai/conversations/:conversationId/branch`（`ConversationBranchController`）→ `ConversationBranchCommand` → `ConversationBranchHandler.execute`（仅转发）→ `ConversationBranchService.branch(conversationId, { sourceThreadId, afterMessageId, requestId })`：`assertAccess(contribute)` → `findExistingBranch` 快路径 → `prepareBranch`（`loadBranchPath` 取根→选中消息、校验 `messageBranching().available` 与 `messagePathHash`、校验 `graphRevision`、逐 `fileAssetId` 重授权）→ 事务。
**事务边界**：`dataSource.transaction` 内：源线程 `pessimistic_write` 行锁 → 二次 `findExistingBranch` → 重算 `branchPathSnapshot` 比对 → `allocateBranchTitle`（`pg_advisory_xact_lock` 家族编号）→ `copyBranchCheckpoints`（只复制检查点，**不**复制 pending writes）→ 父先子后插入消息并重算 `messageHash`/`messagePathHash` → 复制 `ConversationFileLink` → 新建线程 `metadata={primary, forkGraphRevision}`。授权读取刻意放在事务**之前**（源码注释：避免连接池饱和导致死锁）。
**预期结果**：返回 `outcome`/`copiedSize`/`durationMs`；新会话 `branchSource` 记录源线程与 `requestId`；同 `requestId` 重试返回同一既有会话（幂等，不重复创建）。
**错误处理**：`requestId` 命中但参数不一致 → `request_conflict`；路径不可分支或 `messagePathHash`/`graphRevision` 不匹配 → 拒绝；越权 `403`。
**真实代码示例**：
```ts
// 幂等键是部分唯一索引：IDX_chat_conversation_branch_request(createdById, branchSource->>'threadId', branchSource->>'requestId')
await commandBus.execute(new ConversationBranchCommand({
    conversationId, sourceThreadId, afterMessageId, requestId  // requestId: UUID
}))
// 调用方不 import ConversationBranchModule（模块注释："callers use the command without importing this module"）

章节来源：[conversation-branch.service.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/conversation-branch.service.ts)、[branch.handler.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/branch.handler.ts)、[branch-checkpoints.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/branch-checkpoints.ts)、[conversation-branch.module.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/conversation-branch.module.ts)、[conversation-branch.controller.ts](file://packages/server-ai/src/ai/conversation-branch.controller.ts)
```

### Recipe ③ 在群聊里发布消息并查成员可见投影

**业务目标**：一条群消息对多个成员（人或助手）产生各自的投递意图，并按收据投影出「谁能看到、谁被唤醒」。
**调用顺序**：`POST /api/ai/groups/:groupId/messages`（`GroupsController.send`）→ `GroupMessagesService.submit`（mention 解析与收件人推导）→ `publish` → 适配器侧再调 `outbox.flush(groupId)` 主动投递；读取用 `GET /api/ai/groups/:groupId` → `snapshot`。
**事务边界**：`publish` 单个 `db.transaction`：锁 `purpose='group'` 群会话行 + 取发送者成员 → 幂等命中比对或原地更新 → 回复链校验 → 反爆炸校验 → 写消息（新建时 `locked.lastMessageSequence++`）→ 逐成员写 `chat_message_recipient`（`wake`/`status`）→ 保存群行 `revision++`。助手工具发布额外锁其运行时线程行并要求 `status==='busy'` 且 `runControl.executionId` 前缀匹配。
**预期结果**：命中 `(conversationId, groupPublicationId)` 时复用同一 `messageId`；`snapshot` 按 `sequence DESC` 取 `limit+1` 判 `hasMore` 后反转，附成员、收据、失败的 `XpertAgentExecution`、运行中线程 run 与 `pending|claimed` 交互。
**错误处理**：内容不一致 → `groupConflict()`（409）；自我投递 409；`hop>=8` 或同根消息 `>=32` 拒绝；成员已被移除 → 收据置 `blocked(member_removed)`；`GroupScopeGuard` 对 JWT 用户直接放行，边界依赖 `GroupAccessService.authorize`。
**真实代码示例**：
```ts
// 幂等键：publicationId ?? `${authorId}:${clientMessageId}`；唯一索引 (conversationId, groupPublicationId)
const message = await messages.submit(groupId, body)   // 强类型入口，sender 恒来自 authorize
await outbox.flush(groupId)
// 私有载荷只在 claim 成功后返回；snapshot 永不输出 executionId/threadId
const snap = await messages.snapshot(groupId, before, limit)

章节来源：[group-messages.service.ts](file://packages/server-ai/src/chat-group/group-messages.service.ts)、[group.controller.ts](file://packages/server-ai/src/ai/groups/group.controller.ts)、[group-outbox.service.ts](file://packages/server-ai/src/chat-group/group-outbox.service.ts)、[group-scope.guard.ts](file://packages/server-ai/src/ai/groups/group-scope.guard.ts)
```

### Recipe ④ 把一条消息投递给运行时（enqueue → 路由 → 消费 → 结果回投）

**业务目标**：把业务意图异步交给运行时执行，并在运行时产出后把结果按原授权目标回投到会话。
**调用顺序**：`HandoffQueueService.enqueue/enqueueMany/enqueueAndWait` → `normalize` → `HandoffRouteResolver.resolve` → `HandoffQueueGatewayService.enqueue`（`add(XPERT_HANDOFF_JOB, msg, { delay, removeOnComplete:true, removeOnFail:false })`）→ 4 个 `dispatch` 消费者 → `MessageDispatcherService.dispatch`（`assertMessage`、`processorRegistry.get(type, organizationId)`、注册 `AbortController`、总/空闲超时）→ 结果分流（`ok` → `enqueueMany(outbound)` + `pendingResults.resolve`）。
**事务边界**：入队**不在**业务事务内；运行时侧唯一的事务耦合点是 `appendRuntimeDelivery(manager, invocation)` —— 源码注释原文："Must share the Invocation CAS transaction: a queue outage cannot discard a committed result."
**预期结果**：队列中 job 名恒为 `dispatch`，默认 `maxAttempts=3`；运行时事件由 Invocation 事实派生（终态出 `result`、`waiting` 且有 interaction 出 `input_request`），`messageId = runtime-{invocationId}-{kind}-{revision}`，`orIgnore()` 保幂等。
**错误处理**：`retry` → `attempt+1` 未超上限则带 `delayMs` 重入队，否则死信；`dead` 非 `canceled:` 才记死信；永久错误（`No handoff processor found`/`Invalid handoff message:`）直接死信；`enqueueAndWait` 仅本进程 best-effort，跨实例只能等 `XPERT_HANDOFF_PENDING_TIMEOUT_MS`（默认 2 分钟）。
**真实代码示例**：
```ts
// 入队三入口；header handoffQueue 优先级最高，busy 线程走 realtime
await queue.enqueue(message)                                     // 无等待
await queue.enqueueAndWait(message, { timeoutMs, onEvent })      // 仅本进程回调
// 运行时消费后：blocked/failed 判定 + 退避，成功仅推后 nextAttemptAt
// 源码注释："Enqueue is not receipt acknowledgement. Resend the same id until inbox commits received."

章节来源：[message-queue.service.ts](file://packages/server-ai/src/handoff/message-queue.service.ts)、[handoff-route-resolver.service.ts](file://packages/server-ai/src/handoff/dispatcher/handoff-route-resolver.service.ts)、[message-dispatcher.service.ts](file://packages/server-ai/src/handoff/message-dispatcher.service.ts)、[runtime-message-outbox.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-outbox.ts)、[runtime-message-transport.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-transport.service.ts)
```

### Recipe ⑤ 取消正在运行的会话/投递（协作式取消 + 不进死信）

**业务目标**：停止一次正在运行的会话或单条投递，且不因「取消」污染失败台账。
**调用顺序**：`POST /api/chat-conversation/:id/cancel`（`contribute`）→ `CancelConversationCommand` → `CancelConversationHandler.execute`：消息置 `aborted`、execution 置 `INTERRUPTED` → `desktopShellOperations.cancelRuns` → `ExecutionCancelService.cancelExecutions` → **best-effort** `StopHandoffMessageCommand({ executionIds, reason: 'Canceled by user' })`（失败仅 `logger.warn`）→ `threadRunControl.cancel` + `CancelTaskWaitsCommand` → 只 `repository.update` 会话状态列（注释：整体 save 会 cascade 覆盖未收尾的消息树）→ 重放一次 execution 状态保证「取消获胜」。handoff 侧 `StopHandoffMessageHandler` 扫描 `waiting/delayed/paused/active` → `removeJobs` → `HandoffCancelService.cancelMessages`（Redis `ai:handoff:cancel` 跨实例）→ `pendingResults.cancel`。
**事务边界**：取消链**没有**跨队列/跨实例事务；只有会话状态列更新与 execution 状态重放是数据库写。
**预期结果**：返回结构化摘要 `requested/matched/removed/aborted/notFound`；消费端把取消归一为 `dead(canceled:<reason>)` 且**不进死信、不重试**。
**错误处理**：取消是协作式（`AbortSignal`），不强杀同步 CPU 密集代码；`active` 取消 best-effort 且对竞态敏感——作业可能在扫描与 abort 之间正常完成；`dead(canceled:...)` 被跳过死信，真实失败可能被降级为「已取消」。
**真实代码示例**：
```ts
// 会话侧：先取消执行，再 best-effort 停 handoff
await commandBus.execute(new CancelConversationCommand({ conversationId }))
// handoff 侧（内部入口）
await commandBus.execute(new StopHandoffMessageCommand({ messageIds, executionIds, reason: 'Canceled by user' }))

章节来源：[cancel-conversation.handler.ts](file://packages/server-ai/src/chat-conversation/commands/handlers/cancel-conversation.handler.ts)、[stop-handoff-message.handler.ts](file://packages/server-ai/src/handoff/commands/handlers/stop-handoff-message.handler.ts)、[handoff/README.md](file://packages/server-ai/src/handoff/README.md)、[handoff-cancel.service.ts](file://packages/server-ai/src/handoff/handoff-cancel.service.ts)
```

### Recipe ⑥ 暂停/恢复一个 thread run（pause 202+pauseId、受理≠检查点完成、租约）

**业务目标**：在一个不可中断的步骤边界暂停运行，并可在校验通过后从检查点恢复。
**调用顺序**：`POST /api/ai/threads/:threadId/runs/:runId/pause`（无 body，返回 `202` + execution ID + state + `pauseId`）→ `ThreadRunControlService.requestPause`：线程行锁内要求 `status==='busy'`，置 `runControl.state='pausing'` + 新 `pauseId`、`thread.status='pausing'`，并清空旧检查点 → `stageCheckpoint`（仅 `pausing` 阶段）→ `finish()` 确认 → `POST /api/ai/threads/:threadId/runs/:runId/resume`（**必须**带 `pauseId`）→ `claimResume` → 新建执行尝试。`DELETE /api/ai/threads/:threadId/display-pause/:pause_id` 是 `204` 的旧 SDK 兼容通道。
**事务边界**：所有状态迁移都在 `locked()`（线程 `pessimistic_write`）内完成；租约写在 `thread.metadata[chatkitRunLease]`（公开 DTO 不含）。
**预期结果**：受理只表示 `pausing`；只有 finalization（检查点与消息已持久化）才确认 `paused`；工作流自然结束则转 `idle`；同一活跃暂停重复请求返回同一 `pauseId`；旧执行无法暂停替代它的新 run；resume 校验 `pauseId` + graph revision + 检查点后回到 `busy`。
**错误处理**：缺 `pauseId` → 400 `Error.PauseTokenRequired`；run 与 thread 不匹配 → 403；进程丢失时由替代进程在一个事务内把未收尾 run 置 `error`、执行置 `INTERRUPTED`、思考中消息置 `aborted`、等待记录置 `stale`；无租约的旧 run **不按时长猜死**，只能显式 stop。
**真实代码示例**：
```ts
// 受理 ≠ 检查点完成（thread-run-control.md 原文："Request acceptance means `pausing`, not checkpoint completion."）
// pause 无 body（旧请求体被忽略），resume 必须携带 pauseId
await threadRunControl.claimResume(threadId, { pauseId, graphRevision })
// 进程租约：每 15s 续约（RUN_LEASE_MS=90_000），跨实例安全依赖该租约
```

### Recipe ⑦ 处理死信与 redrive（语义与禁忌：不改 Invocation、不清 user stop）

**业务目标**：对传输性失败做可审计的人工重驱，且绝不重复模型/CLI 执行。
**调用顺序**：`GET /api/agent-invocations/:id/delivery`（owner 作用域回执：delivery/consumption 的 `messageId`/`event`/`state`/`attempts`/`lastError`/`nextAttemptAt`、inbox 的 `phase`/`claim`）→ 判定是传输失败还是模糊结果 → `POST /api/agent-invocations/:id/delivery/redrive`（body 必须为 `{}`，schema 为 strict）→ `RuntimeMessageAccessService.withReply` 重授权 → 事务内 `resetRuntimeDelivery`：只把 `blocked|failed` 的 delivery 复位为 `pending/attempts=0`，把 `blocked|failed` 且 `event->>'kind'='result'` 的 inbox 复位为 `pending/attempts=0`。
**事务边界**：redrive 的两次复位在同一事务内；不触碰 Invocation、不触碰用户 stop 屏障。
**预期结果**：传输被重新调度；claim/phase 与用户 stop 屏障保留；对 `consumer_outcome_unknown` 只检查 claim 中记录的**同一执行身份**，不分配替代消费者。
**错误处理**：**redrive 禁忌** —— 源码注释原文："Redrive never changes an Invocation or clears a user stop."；不使用 redrive 绕过显式用户 stop（应改在手工轮次读取结果）；队列侧死信**没有台账表**，`HandoffDeadService.record` 只写 `logger.error('Dead letter: type=..., id=..., traceId=..., reason=...')`，只能靠日志检索。
**真实代码示例**：
```ts
// 禁忌清单：不改 Invocation、不清除用户 stop、不重放已消费结果、不重启 CLI、不分配替代消费者
await http.post(`/api/agent-invocations/${id}/delivery/redrive`, {})   // body 必须为空对象
// 队列侧悬挂 job 用取消链显式停，不要直接删 Redis key
await commandBus.execute(new StopHandoffMessageCommand({ messageIds, executionIds }))

章节来源：[runtime-delivery.controller.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-delivery.controller.ts)、[runtime-result-check.handler.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-result-check.handler.ts)、[dead-letter.service.ts](file://packages/server-ai/src/handoff/dead-letter.service.ts)、[runtime-messaging/README.md](file://packages/server-ai/src/handoff/runtime-messaging/README.md)
```

### Recipe ⑧ 对接 conversation-map（view-extension 宿主与槽位）

**业务目标**：以只读视图把会话/分支脉络渲染进助手工作台，并支持 create/rename/side-chat/branch/locate 动作。
**调用顺序**：宿主 Discovery 收集 `@ViewExtensionProvider('platform.conversation-map')` → `getViewManifests(context, slot)`（要求 `hostType==='agent'` 且 `slot===AGENT_WORKBENCH_SLOT`，返回 key `topics`「对话脉络」、`order: 45`、`activation.requiredFeatures=[CONVERSATION_MAP_FEATURE]`、`view.type='remote_component'`/`isolation:'iframe'`/`entry:'conversation-map'`、`dataSource.mode='platform'`、`cache.enabled=false`）→ `getViewData`（`mapQuerySchema` 校验；`parameters.operation==='projects'` 走 `projectOptions`）→ `ConversationMapService.read` → `executeViewAction(key='act')`（`mapActionSchema`）→ `ConversationMapService.act`。
**事务边界**：**无表、无自有事务**；`act.create` 用 `pg_advisory_xact_lock(hashtext('conversation-map:{userId}:{requestId}'))` 加 `requestId` 作会话 ID 实现幂等，再走 `ChatConversationUpsertCommand`；`branch` 转 `ConversationBranchCommand`；`side-chat` 走 `ChatConversationThreadService.copyThread`。
**预期结果**：视图清单只读投影（`turnNodes` 跳过 runtime 消息与非法角色，`humanMessageSummary` 截断 600 字符），动作返回 `target: viewKey 'platform.conversation-map__topics'`；`ConversationMapService.scope()` 先做 host context 与 `RequestContext` 三重比对再读写。
**错误处理**：Zod 校验失败 `400 ConversationMap.InvalidQuery`；scope 比对不一致即拒绝；搜索分页语义特殊 —— 源码注释明写 `page.total` 是扫描范围而非命中数，客户端需配合 `searchOffset`/`nextSearchOffset`；能力暴露完全依赖宿主与服务端一致（runtime 读取 `remote-components/conversation-map/app.js|app.css`）。
**真实代码示例**：
```ts
// 地图是只读视图：无 entity、无迁移、无 controller
const data = await provider.getViewData(context, { key: 'topics', parameters: { operation: 'projects' } })

// target.viewKey === 'platform.conversation-map__topics'
```

### Recipe ⑨ 排障：消息重复 / 丢失 / 顺序错乱

**业务目标**：用有限的只读观测点定位三类高频故障，而不改动状态。
**调用顺序**：① 重复 → 查幂等键是否命中：`(conversationId, groupPublicationId)`、`(conversationId, sequence)`、`agent_runtime_delivery.messageId`、inbox `(tenantId, organizationId, ownerId, consumptionKey)`；② 丢失 → 查 `GET /api/agent-invocations/:id/delivery` 的 `state`/`attempts`/`lastError` 与日志关键字 `Dead letter: type=..., id=..., traceId=..., reason=...`；③ 顺序错乱 → 查消息 `sequence` 是否存在、`createdAt`/`parentId` 父链与 `revision` 是否被误当游标。
**事务边界**：全部只读；不在排障中执行 redrive 或改 `sequence`。
**预期结果**：能明确区分「重复通知（可重试投递的正常现象）」「传输未送达（delivery pending/blocked/failed）」「结果模糊（inbox `blocked` + `consumer_outcome_unknown`）」三类，以及「私有会话 `sequence` 为 NULL」这一预期状态。
**错误处理**：
- **envelope 版本**：`version` 只接受字面量 `1`；非法/未知持久化版本对公开历史隐藏，但运行时水合仍保留用于执行与诊断（隐藏 ≠ 未参与推理）；`readChatMessageEnvelope` 静默吞错，读侧无法区分「无信封」与「损坏信封」。
- **lost ack 重发**：`enqueue` 成功只推后 `nextAttemptAt`（+30s），"Enqueue is not receipt acknowledgement"，同一 `messageId` 会被重发——消费端必须幂等（`orIgnore()` + 唯一键）。
- **`consumer_outcome_unknown`**：模糊结果**不自动重放**，也不重启 CLI；只能按 `GET /delivery` 的同一执行身份人工 redrive。
- **顺序**：`sequence` 由群发布在群会话行锁内分配，私有路径常驻 `NULL`；跨域读取方**不能**假定 `sequence` 恒存在。
