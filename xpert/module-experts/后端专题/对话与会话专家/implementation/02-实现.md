## 核心流程实现位置
### ① 会话与消息写入
`ChatConversationService.create` 调 `super.create` 后容错 `ensureInitialReadState`；`update` 对 `options` 做白名单（`runtimeResources` 保留走 `mergeConversationOptionsSql`）并禁止 `projectId` 迁移；`assertAccess(id, 'read'|'contribute'|'manage')` 统一鉴权（拒绝 `purpose==='group'`、`group_assistant_runtime` 仅 `isGroupRuntime` 放行、Project 会话转 `assertCanRead/assertCanUse`）。消息写入走 `ChatMessageUpsertCommand` → `ChatMessageUpsertHandler.execute`（`message.persist` tracing、有 id 走 `save` 否则 `create`、随后按 `shouldExtractTaskSummary` 抽取 `taskSummary`）。`sequence` 的分配契约写在 `ChatConversation.lastMessageSequence`（会话行锁），实测推进点为群聊 `publish` 的 `locked.lastMessageSequence++`，`ChatMessage.sequence` 可空并受唯一索引 `(conversationId, sequence)` 约束。
章节来源：[conversation.service.ts](file://packages/server-ai/src/chat-conversation/conversation.service.ts)（关键符号：ChatConversationService.assertAccess）、[upsert.handler.ts](file://packages/server-ai/src/chat-message/commands/handlers/upsert.handler.ts)（关键符号：ChatMessageUpsertHandler.execute）、[chat-message.entity.ts](file://packages/server-ai/src/chat-message/chat-message.entity.ts)（关键符号：ChatMessage.sequence）

### ② 分支
`ConversationBranchHandler.execute` 仅转发 `ConversationBranchService.branch(conversationId, input)`（`requestSchema`: `sourceThreadId`/`afterMessageId`/`requestId`）。`branch` 先 `findExistingBranch`（`requestId`+线程幂等），再 `prepareBranch`（校验路径、逐 `fileAssetId` 走 `resolveAuthorizedFileAsset`，拼 `branchPathSnapshot`），随后 `dataSource.transaction`：线程 `pessimistic_write` 行锁 → 复制消息（`parentId`/`role`/`content`/`messageEnvelope`/`inputCheckpoint`/`outputCheckpoint`/`fileAssets`）→ 写 `conversation.branchSource` 与 `metadata.forkGraphRevision` → 返回 `outcome`/`copiedSize`/`durationMs`。`loadBranchPath` 由 head 回溯 ancestors 供只读导航。
章节来源：[conversation-branch.service.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/conversation-branch.service.ts)（关键符号：ConversationBranchService.branch）、[branch.handler.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/branch.handler.ts)（关键符号：ConversationBranchHandler.execute）

### ③ 群聊发布与投递
`GroupMessagesService.send` → `submit`（解析 primary sender 与 recipients/intent）→ `publish`：事务内按 `(conversationId, groupPublicationId)` 命中即复用 messageId（`existing`），否则锁 `purpose='group'` 群会话行、锁运行线程行、`locked.lastMessageSequence++` 分配 `sequence`、写 `messageEnvelope`（`source`/`correlation`/`presentation`）并为每个成员写 `chat_message_recipient`（`wake`/`status`）。`snapshot` 组合 messages + receipts + interactions + runs；`preferences` 用 `readSequence ≤ lastMessageSequence` 落库。投递侧 `GroupOutboxService.deliver` 以 `leaseToken`/`leaseUntil`(60s) + `attempts+1` 原子 claim，成功后 `nextAttemptAt = now+30s`，失败按 `min(300s, 5s*2^n)` 退避、`attempts>=9` 置 `failed`；`route` 校验 receipt（pending+wake）与成员 active，改写为 `AGENT_CHAT_DISPATCH_MESSAGE_TYPE` 并整体复用 handoff 入队（busy 线程走 `realtime`）；`GroupMessageProcessor.process` 只把 `payload.recipientId` 交给 `route`。
章节来源：[group-messages.service.ts](file://packages/server-ai/src/chat-group/group-messages.service.ts)（关键符号：GroupMessagesService.publish）、[group-outbox.service.ts](file://packages/server-ai/src/chat-group/group-outbox.service.ts)（关键符号：GroupOutboxService.deliver）

### ④ handoff 入队到消费
`HandoffQueueService.enqueue/enqueueMany/enqueueAndWait`（`@RequirePermissionOperation('handoff','enqueue'|'wait')`）先 `normalize`（补 id/version/attempt/`maxAttempts`，缺省 `DEFAULT_HANDOFF_MAX_ATTEMPTS=3`）再 `HandoffRouteResolver.resolve`（header `handoffQueue`/`queue` alias > `typePolicy.queue` > 命中规则的 `target.queue` > `defaultQueue`，lane/timeout/idle 同级优先）→ `HandoffQueueGatewayService.enqueue`（`add(XPERT_HANDOFF_JOB, msg, { delay, removeOnComplete: true, removeOnFail: false })`）→ 4 个 `@Processor` 的 `@Process({ name: 'dispatch', concurrency })` → `BaseHandoffQueueProcessor.processMessage`（`runWithHandoffMessageContext`）→ `MessageDispatcherService.dispatch`（`assertMessage` 校验 id/type/tenantId/sessionKey/traceId/businessKey，`processorRegistry.get(type, organizationId)`，注册 `AbortController`，总超时/空闲超时定时器，abort → `dead(canceled:...)`）→ 结果分流：`ok` 时 `enqueueMany(outbound)` 并 resolve waiter；`retry` 时 `attempt+1` 再入队或记死信；`dead` 非 canceled 才记死信。
章节来源：[message-queue.service.ts](file://packages/server-ai/src/handoff/message-queue.service.ts)（关键符号：HandoffQueueService.enqueueAndWait）、[handoff-route-resolver.service.ts](file://packages/server-ai/src/handoff/dispatcher/handoff-route-resolver.service.ts)（关键符号：HandoffRouteResolver.resolve）、[message-dispatcher.service.ts](file://packages/server-ai/src/handoff/message-dispatcher.service.ts)（关键符号：MessageDispatcherService.dispatch）

### ⑤ 运行时消息
`appendRuntimeDelivery(manager, invocation)` 由 `TypeOrmAgentInvocationStore` 在 Invocation CAS 事务内调用（`orIgnore()` 幂等写 `agent_runtime_delivery`）→ `RuntimeMessageTransportService.reconcile`（`@Interval(5000)`、`scanning` 互斥、`take: 20`，末尾串 `HandoffOutboxAdapters.reconcile()`）→ `deliver`（租约 claim → `access.withReply` → enqueue `AGENT_RUNTIME_EVENT_MESSAGE_TYPE`，enqueue 成功仅推后 `nextAttemptAt`，注释明写「Enqueue is not receipt acknowledgement」）→ `RuntimeMessageProcessor` → `RuntimeMessageInboxService.receive`（校验 delivery 存在、`sameInvocationData`、`message.id === agentRuntimeEventMessageId(event)`、sessionKey/conversationId/threadId 与 `replyTo` 一致；事务内 `lockInbox` 后把 `result` 事件覆盖的 `input_request` 置 `processed/superseded`，并置 delivery `received`）与 `lockInbox`（`consumptionKey = agentRuntimeResultConsumptionKey(...)`，`input_request` 追加 `:input:<interactionId>`，insert-orIgnore + `pessimistic_write` 读）、`claimWait`（要求 consumer execution 处于 RUNNING）；续跑由 `RuntimeMessageContinuationService`（`reconcile`→`reserve`→`run`→`recover`→`releaseUnusedReservation`）承担。
章节来源：[typeorm-invocation.store.ts](file://packages/server-ai/src/agent-invocation/typeorm-invocation.store.ts)（关键符号：appendRuntimeDelivery 调用点）、[runtime-message-transport.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-transport.service.ts)（关键符号：RuntimeMessageTransportService.reconcile）、[runtime-message-inbox.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-inbox.service.ts)（关键符号：RuntimeMessageInboxService.receive）

### ⑥ 取消
`CancelConversationHandler.execute`：定位 conversation/thread 与目标消息 → 消息置 `aborted`、execution 置 `INTERRUPTED` → `desktopShellOperations.cancelRuns` → `ExecutionCancelService.cancelExecutions` → **best-effort** `commandBus.execute(new StopHandoffMessageCommand({ executionIds, reason: 'Canceled by user' }))`（失败仅 `logger.warn`，不阻断）→ `threadRunControl.cancel` + `CancelTaskWaitsCommand` → 只 `repository.update` 会话状态列（注释解释：整体 save 会 cascade 覆盖未收尾的消息树）→ 最后重放一次 execution 状态保证「取消获胜」。`StopHandoffMessageHandler` 扫描全部队列（`waiting`/`delayed`/`paused`/`active`）后 `removeJobs`（并 `localTaskService.remove`）、对 active 匹配调 `HandoffCancelService.cancelMessages`（跨实例 Redis pub/sub）、对全部匹配 `pendingResults.cancel`；消费端把取消归一为 `dead(canceled:...)` 且不进死信。
章节来源：[cancel-conversation.handler.ts](file://packages/server-ai/src/chat-conversation/commands/handlers/cancel-conversation.handler.ts)（关键符号：CancelConversationHandler.execute）、[stop-handoff-message.handler.ts](file://packages/server-ai/src/handoff/commands/handlers/stop-handoff-message.handler.ts)（关键符号：StopHandoffMessageHandler.execute）

## 热点路径
1. **单会话消息写**：`ChatMessageUpsertHandler` → `ChatMessageService.create/save`，同一会话写序彼此串行；`ChatMessage.conversation` 为 `onDelete: 'CASCADE'` 并带 `@Tree('closure-table')`。
2. **群 publish 行锁**：`GroupMessagesService.publish` 同时持群会话行锁与运行线程行锁，并做 `(conversationId, groupPublicationId)` 唯一索引兜底；`chainSize >= 32` 直接冲突失败。
3. **inbox 认领**：`lockInbox` 以 `consumptionKey` 唯一索引 insert-orIgnore + 悲观写锁读取，`claimWait` 再校验 consumer execution，故同一 execution 的 wait/follow-up 争用同一行。
4. **扫描器**：transport 每 5s 取 20 条 delivery 并串行调用全部 outbox 适配器；Group outbox 每次取 20 条 pending + 100 条 in-flight 收据。
5. **线程游标**：`ThreadCursorStore` 用 Redis `SET NX`（TTL 30 分钟）发句柄，不含任何 транскрипт 或授权结论。

章节来源：[group-messages.service.ts](file://packages/server-ai/src/chat-group/group-messages.service.ts)（关键符号：GroupMessagesService.publish）、[runtime-message-inbox.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-inbox.service.ts)（关键符号：RuntimeMessageInboxService.lockInbox）、[thread-cursor.store.ts](file://packages/server-ai/src/chat-conversation/thread-cursor.store.ts)（关键符号：ThreadCursorStore.issue）

## 技术债与 hack
1. **无归档字段**：`chat_conversation` 只有 `status`/`error`，无 archived 列；归档语义落在群成员偏好（`pinned`/`archived`）上，会话级归档缺失。
2. **attachments `@deprecated` 双路径**：`ChatConversation.attachments` 与 `ChatMessage.attachments` 均标注 deprecated（新路径 `FileAsset`/`ConversationFileLink`），`filterAuthorizedFileRelations` 仍需并行处理两套关系。
3. **`GroupScopeGuard` 对 JWT 直接放行**：仅当 `principalType` 为 `client_secret`/`api_key` 才收紧，普通登录用户完全依赖下游服务侧断言。
4. **`enqueueAndWait` 跨实例不回调**：注释明写 best-effort，worker/waiter 异实例时调用方只能等超时。
5. **canceled 不进死信**：`dead(canceled:...)` 从死信跳过，失败可见性依赖日志而非死信台账。
6. **僵尸 run**：无租约的旧 run 不按时间猜测回收，需显式 stop。
7. **`sequence` 语义不一致**：行锁分配契约写在 `ChatConversation.lastMessageSequence`，但当前仅群聊 `publish` 推进，私有路径消息 `sequence` 为空。
8. **隐藏 ≠ 未参与推理**：`presentation='runtime'` 不进公开历史但仍可能进入模型祖先/重试。
9. **redrive 边界**：`RuntimeDeliveryController` 明写 redrive 不改 Invocation、不清除用户 stop；模糊结果需人工介入。
10. **装配分散**：`ConversationBranchModule` 不在 `ChatConversationModule` 的 imports 中，分支能力靠调用方单独注册命令处理器。
11. **本域无 `AGENTS.md`**：仓库内 `docs/AGENTS.md` 仅存在于 `plugins/local-shell-sandbox/docs/`，与本域无关。
12. `TChatConversationStatus` 已核实为 `'idle' | 'busy' | 'pausing' | 'paused' | 'interrupted' | 'error'`（此前扫描报告列为未核实项，现关闭）。

## 设计维度分析
**一致性 vs 可用性**：本域选择「先提交，后投递」——outbox 记录与 Invocation CAS 同事务，队列失败由轮询 + 退避 + 死信修复，因此语义是 at-least-once 投递 + 幂等消费，而非 exactly-once；代价是重复通知与需人工 redrive 的模糊结果。
**锁粒度 vs 吞吐**：会话级行锁保证 `sequence`/幂等键的线性化，但把单会话变成写热点（群 `publish` 双锁叠加更甚）；租约 + UPDATE-claim 与 `consumptionKey` 唯一索引把并发控制从锁下推到数据库谓词，交换到的是「重复扫描但至多一次入队」。
**写模型 vs 只读视图**：分支用事务 + 检查点复制换取可导航的谱系（写放大、需行锁），地图用零表投影换取免迁移与低耦合（每次查询重算、依赖 host context 三重比对防越权）。
**边界归属**：逻辑留在本域、适配器分布在 `ai/**` 与 `agent-invocation.module.ts`，使业务可用命令跨越模块边界复用（CQRS 优点），但装配与 API 反查成本上升，需靠模块注释维持可发现性。

## 结论
实现上，本域所有写路径都收敛到少量幂等入口（`ChatMessageUpsertCommand`、`ConversationBranchCommand`、`GroupMessagesService.publish`、`HandoffQueueService.enqueue*`、`appendRuntimeDelivery`），读路径都收敛到授权入口（`assertAccess`、`GroupAccessService.authorize`、`RuntimeMessageAccessService.withReply`）。风险集中在三处：`sequence` 的双语义、取消链路的取消结果不进死信、以及跨域适配器分散造成的装配与审计盲点。新增能力时应坚持「同事务落账、投递可重试、消费幂等」三点，并避免绕开上述入口直查仓库。
