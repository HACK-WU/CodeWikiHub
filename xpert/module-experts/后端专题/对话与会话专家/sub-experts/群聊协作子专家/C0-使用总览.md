# C0 · 使用总览（群聊协作子专家）

> 层级：**契约层（CR1）** ｜ 父专家：后端专题 / 对话与会话专家 ｜ 子专家② 群聊协作
> 资产基线：**2026-10-15 · commit `c07bb83d`**
> 源码范围：`packages/server-ai/src/chat-group/**`（含 `group-project/`）；HTTP 适配器在 `packages/server-ai/src/ai/groups/**`（**目录归属「Assistant 定义与运行时专家」**）

## 0. 契约自足声明

本文是本子专家的对外使用契约：不读实现层即可决定「何时找本子专家、能拿到什么能力、调哪个入口、边界在哪、有哪些已知坑」。算法与表结构细节只给契约级语义与索引。

## 1. 定位

本子专家是**群协作账本的持有者**：群成员模型与准入、公开消息发布幂等、成员可见投影、成员偏好、HITL 交互登记与领取、群内助手运行时准入与收尾、投递收据与 outbox 适配、SSE 观察者流、composer 校验、群任务目标解析。

关键前提：**「群」本身没有独立表**——群就是一行 `chat_conversation`（`purpose='group'`），助手的私有运行时是另一行（`purpose='group_assistant_runtime'`）；本域自有表只有 3 张：`chat_group_participant`、`chat_message_recipient`、`chat_group_interaction`。

## 2. 何时找这个子专家

- 需要建群、加/移除成员、查邀请候选、看群侧边栏摘要：找本子专家。
- 需要以人类身份发送一条群消息（mention 解析、回复原请求）：找 `submit`。
- 需要以助手/程序身份发一条群消息（工具发布、续跑输出投影）：找 `send` / `publish`。
- 需要读取「该调用者可见」的群消息投影（含收据、运行状态、待处理交互）：找 `snapshot`。
- 需要成员个人偏好（已读水位、置顶、归档）：找 `preferences`。
- 需要 HITL 交互（客户端工具请求、审批/编辑决策）的登记、认领与应答：找 `GroupInteractionsService`。
- 需要群内助手的暂停/取消/恢复、撤回单条投递：找 `GroupControlService`。
- 需要群观察者 SSE 流、composer 成员/项目/资源/文件校验、群项目绑定与任务目标：找本子专家。
- 需要异步投递队列本身、取消传播、死信与重驱：**找子专家③**（本域只实现 outbox 适配器与消费策略）。
- 需要会话/消息/线程 CRUD、模型执行本身：**不在本域**。

## 3. 能力清单表

| # | 能力 | 主要入口 | 契约语义 |
|---|---|---|---|
| 1 | 成员模型与准入 | `GroupAccessService.authorize`、`GroupMembersService.create/add/remove` | 建群一次事务写群会话 + owner + 助手运行时会话/线程 + 助手成员；活跃成员上限 32 |
| 2 | 发送 / 提交 / 发布 | `GroupMessagesService.send`、`submit`、`publish` | 单写者：群会话行锁 + `groupPublicationId` 幂等 + 收据 fan-out |

| 4 | 个人偏好 | `GroupMessagesService.preferences` | 只改本人行；`readSequence` 单调且封顶到 `lastMessageSequence` |
| 5 | HITL 交互 | `GroupInteractionsService.register/claim/respond` | `interactionId` 幂等；`claimId` 排除第二个标签页 |
| 6 | SSE 观察者流 | `GroupStreamService.observe` | 加密游标 + 1s 轮询快照 + 挂读私有 run 流；断开不取消模型、不确认工具 |
| 7 | 运行控制 | `GroupControlService.act/cancelDelivery` | pause/cancel/resume + 撤回单条投递 |
| 8 | 群运行时 | `GroupRuntimeService.prepare/finish` | 身份来自持久化绑定；准入事务锁群行 + 线程行 + 收据行 |
| 9 | Composer | `GroupComposerService.member/context/validate/resourceCatalog/capabilities/files` | 项目锁、资源复核、文件必须 `filePath === workspacePath` 且真实存在 |
| 10 | 群项目与任务目标 | `/api/ai/groups/:groupId/project`、`GroupTaskTargetService` | 项目绑定双侧授权；群任务目标解析与投递 |

## 4. 本子专家的持久化对象

| 对象 | 语义 |
|---|---|
| `chat_group_participant` | 谁在群里、以什么身份（`kind` user/assistant、`subjectId`、`role`、`active`）与什么运行时身份（`runtimeConversationId` / `runtimeThreadId` / `principalUserId`）；唯一 `(groupId, kind, subjectId)` |
| `chat_message_recipient` | 投递收据账本：`status`、`wake`、`phase`、`attempts`、`nextAttemptAt`、`leaseToken`/`leaseUntil`、`control`；唯一 `(messageId, participantId)` |
| `chat_group_interaction` | HITL 指派与认领：`interactionId`、`assignedUserId`、`claimedBy`、`claimId`、`payload`（私有）；唯一 `(groupId, interactionId)` |
| `chat_conversation`（复用） | `purpose='group'` 承载公开群；`purpose='group_assistant_runtime'` 承载助手私有运行时；`revision`、`lastMessageSequence` 在群会话行锁内自增 |

## 5. 边界

**HTTP 在别处**：群接口全部注册在 `ai/groups/**`（`GROUP_CONTROLLERS` 聚合进 `ai.module.ts`，`RouterModule` 前缀 `/ai`），归属「Assistant 定义与运行时专家」。适配器只做 Zod 边界校验与转发（`send` → `messages.submit` + `outbox.flush`；`stream` → `streams.observe`）；`chat-group/` 源码**不 import `ai/**`**，依赖方向单向。

**守卫与授权分层**：适配器统一 `@Public()` + `@AllowClientSecretBindings(USER_CONVERSATION)` + `ApiKeyOrClientSecretAuthGuard` + `GroupScopeGuard`（工作台族再加 `GroupWorkbenchGuard`）；`GroupScopeGuard` 只把 conversation grant 收紧到单群路由，**真正的闸门是服务侧 `GroupAccessService.authorize`**。

**投递靠 handoff（子专家③）**：本域实现 `HandoffOutboxAdapter`（模块初始化注册、销毁反注册），由 handoff 的共享扫描 `reconcile` 驱动；队列选择、job 归一化、重试与取消复用 `HandoffQueueService`；消费策略 `@HandoffProcessorStrategy(GROUP_MESSAGE_TYPE)` 注册在本域。

**不负责**：会话/消息/线程 CRUD（子专家①）；handoff 队列实现与取消语义（子专家③）；模型执行本身与助手私有线程的业务正文（本域只读并投影）；群表迁移与 seed（本域无 `migrations/`，表结构规格只由 PostgreSQL 用例承载）。

## 6. 已知坑（9 条）

1. **群 `publish` 在事务内锁 `purpose='group'` 会话 + `groupPublicationId` 幂等 + 收据 fan-out**：单群被串行化；幂等键为 `publicationId ?? "{authorId}:{clientMessageId}"`，命中后逐字段比对（内容/发送者/intent/composer/projectTask/runtimeResult/replyTo），不一致即 409 冲突；消息与全部收据在同一事务写入。
2. **`chat_message_recipient` 增长与 lease**：每条公开消息 × 每个目标成员写一行，且命中幂等时**先删旧收据再重建**（`attempts`/`lease`/`executionId` 历史丢失）；`leaseUntil` 固定 60s 且无心跳，入队成功只把 `nextAttemptAt` 推后 30s——**「Enqueue is not receipt acknowledgement」**，`attempts>=9` 置 `failed` 后只能人工介入。
3. **`GroupScopeGuard` 对 JWT 直接放行**：`canActivate` 只在 `principalType` 为 `client_secret`/`api_key` 时收紧，登录用户 `return true`；**不要用登录态直连群路由做隔离假设**，JWT 路径完全依赖服务侧 `GroupAccessService.authorize`。
4. **outbox 靠轮询 `reconcile` 恢复**：无独立队列、无死信台账；恢复窗口 = 5s 扫描 + 30s 节流 + 最长 300s 退避（`min(300s, 5s*2^n)`），进程崩溃期间只在下一轮扫描被捡起。
5. **`GroupMessageProcessor` 与 Bull ack 边界未确认**：`process` 只把 `route` 的 `{status:'ok'}` 返回给中继，job 完成/失败如何映射为重试在源码与用例中都未描述，跨重启语义不清。
6. **成员 `runtimeConversationId` / `runtimeThreadId` 归属**：一个助手在同一群只有一个私有运行时绑定；`withDeliveryActor`、`GroupRuntimeViewService.get`、`GroupWorkbenchGuard.resolve` 都以该绑定为校验条件——**身份来自绑定而非文本**，HTTP 不接受作者字段。
7. **群内个人视角历史缺失**：`snapshot` 是群级公开投影，`contextSequence`/`readSequence` 只服务运行时上下文与未读统计；没有「以某成员视角」的历史读取接口。
8. **无 FK 级联 + 偏好不可代办**：三张群表与 `branchSource` 均无外键，会话删除不级联收据/交互/成员，遗漏即孤儿行；`preferences` 只能改本人行，owner 无法代成员置顶/归档/修正已读。
9. **反爆炸阈值硬编码且分散**：`hop >= 8`、同一 `rootMessageId` 群消息数 `>= 32`、成员 `>= 32`、自我投递一律 409；另 `interactionId` 的哈希依赖 requests 数组顺序，顺序变化会生成新交互行。
