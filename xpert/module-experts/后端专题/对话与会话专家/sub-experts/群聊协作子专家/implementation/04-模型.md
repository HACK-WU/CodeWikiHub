## 实体基类与群表的存在性
本子域只有 **3 个实体**（`group.entities.ts` 的 `GROUP_ENTITIES = [GroupParticipant, GroupMessageRecipient, GroupInteraction]`），映射 3 张表：`chat_group_participant`、`chat_message_recipient`、`chat_group_interaction`。三表全部继承 `TenantOrganizationBaseEntity`（→ `TenantBaseEntity`），因此都带基类主键 `id`、审计列（`createdAt`/`updatedAt`/`createdById`/`updatedById`）与租户/组织列；`organizationId` 在基类上带 `@Index()`。

**「群」本身没有独立表**（已核实）：群就是一行 `chat_conversation`，用 `purpose='group'` 区分（`ChatConversation.purpose?: 'private' | 'group' | 'group_assistant_runtime'`）；助手的私有运行时是另一行 `purpose='group_assistant_runtime'`。全仓库检索 `chat_group` 字面量只命中 `group.entity.ts`（三张表名）、`group-runtime.postgres.spec.ts`（测试建表 schema）与 `core/entities/index.spec.ts`，**不存在 `chat_group` 表或 `ChatGroup` 实体**。群级字段因此复用会话列：`threadId`（公开群线程）、`revision`（公开快照版本）、`lastMessageSequence`（行锁内分配）、`xpertId`（默认助手）、`projectId`（群项目绑定）。

## chat_group_participant
| 列 | 类型 | 可空 | 默认 | 业务含义 |
|---|---|---|---|---|
| `groupId` | uuid | 否 | — | 群会话 `chat_conversation.id`（应用级关联） |
| `kind` | varchar | 否 | — | `user` / `assistant` |
| `subjectId` | uuid | 否 | — | 人类为 User ID，助手为 Xpert ID（身份与授权只用此列） |
| `name` | varchar | 否 | — | 展示名（群内署名，不参与授权） |
| `role` | varchar | 否 | `member` | `owner`（唯一能改成员） / `member` |
| `active` | boolean | 否 | `true` | 移除后置 false，保留历史署名 |
| `runtimeConversationId` | uuid | 是 | — | 助手私有运行时会话（`purpose='group_assistant_runtime'`） |
| `runtimeThreadId` | uuid | 是 | — | 助手私有运行时线程（与公开群线程分离） |
| `principalUserId` | uuid | 是 | — | 助手技术主体（`XpertPrincipalService.ensurePrincipalUser`） |
| `contextSequence` | int | 否 | `0` | 已投影进模型上下文的公开序号水位 |
| `readSequence` | int | 否 | `0` | 本人已读水位（未读 = `lastMessageSequence > readSequence`） |
| `pinned` / `archived` | boolean | 否 | `false` | 本人侧边栏偏好（非会话级归档） |

**索引与唯一约束**：`@Index(['groupId','kind','subjectId'], { unique: true })` —— 同群同主体只能有一条成员行（`add` 由此做「重入即恢复同一运行时绑定」）。除该复合索引与基类 `organizationId` 索引外无额外索引，按 `groupId` 的查询依赖复合索引前缀。
**关系与级联**：实体未声明任何 `ManyToOne`/外键，故**无数据库级级联**；成员行随群会话清理由应用层负责。
**业务约束**：`active=false` 不等于失联（历史消息仍以其署名）；`remove` 拒绝 `role='owner'` 与默认助手（`subjectId === group.xpertId`）；活跃成员数上限 32；一个助手在同一群只有一个私有运行时（`runtimeConversationId`/`runtimeThreadId` 成对出现）。

## chat_message_recipient
| 列 | 类型 | 可空 | 默认 | 业务含义 |
|---|---|---|---|---|
| `groupId` | uuid | 否 | — | 群会话 ID |
| `messageId` | uuid | 否 | — | 公开消息 ID（`chat_message.id`） |
| `participantId` | uuid | 否 | — | 目标成员 ID |
| `status` | varchar | 否 | `pending` | `pending`/`starting`/`steering`/`consumed`/`blocked`/`canceled`/`failed` |
| `wake` | boolean | 否 | `false` | 是否允许唤醒助手（`pending+wake` 才会入队） |
| `replyMessageId` | uuid | 是 | — | 该收据对应的回复消息（回复认领，防重复完成） |
| `executionId` | uuid | 是 | — | 私有一次运行的执行 ID |
| `inputMessageId` | uuid | 是 | — | 落到私有会话的输入消息（追单消费凭据） |
| `phase` | varchar | 是 | — | `reserved`/`started`/`finalized`（独立于公开状态） |
| `error` | varchar | 是 | — | `transport_unavailable`/`authorization_revoked`/`runtime_blocked`/`member_removed` 等 |
| `attempts` | int | 否 | `0` | 入队重试计数（`deliver` 内 `attempts+1`） |
| `contextSequence` | int | 否 | `0` | 该次投递实际投影到模型的历史水位 |
| `nextAttemptAt` | timestamptz | 否 | `now()` | 下次可扫描时间（+30s 节流 / 退避） |
| `startedAt` | timestamptz | 是 | — | 准入开始时间（配合 120s fail-closed 判定） |
| `leaseToken` | uuid | 是 | — | 租约令牌（每次 `deliver` 新生成） |
| `leaseUntil` | timestamptz | 是 | — | 租约到期（now+60s） |
| `control` | jsonb | 是 | — | 人工决策/暂停恢复指令（`actorId`、`pauseId`、`decision`） |

**索引与唯一约束**：唯一 `(messageId, participantId)`（一人一收据，也是消息幂等的第二道闸）；查询索引 `(status, nextAttemptAt)`（扫描器谓词）。**关系与级联**：无外键声明，`messageId`/`participantId` 为应用级关联、无级联。**业务约束**：收据是投递账本而非执行队列；只有 `wake && status='pending'` 参与入队；`completed?` 由 `finish` 写终态（`consumed`/`failed`/`blocked`/`canceled`）并置 `phase='finalized'`；`control` 在完成时清空。

## chat_group_interaction
| 列 | 类型 | 可空 | 默认 | 业务含义 |
|---|---|---|---|---|
| `groupId` | uuid | 否 | — | 群会话 ID |
| `interactionId` | varchar | 否 | — | `"{executionId}:{sha256(requests)}"`，重放幂等键 |
| `participantId` | uuid | 否 | — | 触发中断的助手成员 |
| `assignedUserId` | uuid | 否 | — | 被指派处理的人类 User ID（因果根人类） |
| `claimedBy` | uuid | 是 | — | 实际认领者（= `assignedUserId` 校验后才写入） |
| `status` | varchar | 否 | `pending` | `pending`/`claimed`/`completed`/`canceled` |
| `recipientId` | uuid | 否 | — | 关联收据（恢复执行时被改写） |
| `runId` | uuid | 否 | — | 对应执行 ID（控制与取消的锚点） |
| `claimId` | uuid | 是 | — | 浏览器生成的认领令牌（排除第二个标签页） |
| `payload` | jsonb | 否 | — | 私有请求体（client_tool / approval），只在下发 `claim` 后返回 |

**索引与唯一约束**：唯一 `(groupId, interactionId)`；实际业务查询按 `groupId + status`、`groupId + participantId + runId`、`assignedUserId` 过滤（无对应二级索引）。**关系与级联**：无外键声明；`recipientId`/`runId` 为应用级关联。**业务约束**：`payload` 永不进入公开投影；`claim` 要求线程 `interrupted` 且交互创建时间晚于 `runtimeContinuationBlockedAt`；`respond` 要求 `claimId`+`claimedBy` 一致、请求与决策逐项匹配、关联收据处于 `blocked`；成员被移除时其交互批量置 `canceled`。

## 关系、外键与级联
- 三表对外只有唯一索引，**没有 `ManyToOne`/外键**，因此不存在数据库级 `ON DELETE CASCADE`；群会话删除后收据/交互/成员行不会被自动清理（需应用层清理），这是本子域最重要的一致性地雷。
- 跨域写入的唯一锚点是 `chat_conversation.id` 与 `chat_message.id`：`publish` 在同一事务里写 `chat_message`（含 `groupCommunication`、`groupPublicationId`、`sequence`）与全部 `chat_message_recipient`，因此「消息可见 ⟺ 收据存在」由事务保证。
- `chat_message` 侧承担两类幂等唯一索引：`(conversationId, sequence)` 与 `(conversationId, groupPublicationId)`；`sequence` 可空，只有群发布路径在群会话行锁内自增分配。
- 私有运行时侧不新增表：`group_assistant_runtime` 会话 + `ChatConversationThread` + `XpertAgentExecution` 承载执行，收据只以 `executionId`/`inputMessageId` 引用它们。

## 迁移与 seed
- **无迁移覆盖群表**：`packages/server-ai/src/chat-group/` 下不存在 `migrations/` 目录（检索无命中）；本域也没有 SQL 文件提及 `chat_group_participant`/`chat_message_recipient`/`chat_group_interaction`。仓库里同族迁移只覆盖会话分支、消息 envelope、运行时可靠回执。
- **唯一可执行的表结构规格**是 `group-runtime.postgres.spec.ts`：它以 `EntitySchema` 显式声明三张群表（含 `indices: [{ columns: ['messageId','participantId'], unique: true }]`、`{ columns: ['groupId','interactionId'], unique: true }`）与 `chat_conversation`/`chat_message`/`chat_conversation_thread`/`xpert_agent_execution` 的最小列集，然后在一次性 PostgreSQL 的隔离 schema 里 `synchronize()`。它由 `GROUP_TEST_DATABASE_URL` 开关（无该变量则整组 `describe.skip`），并显式声明「需要一个全新、可丢弃的 PostgreSQL 数据库；绝不能指向平台库」。
- **seed**：本子域无 seed 文件（检索 `chat_message_recipient` 等表名不命中任何 seed/fixture）。群首行数据由运行时创建流程产生：`GroupMembersService.create` 一次事务写入群会话 + owner 成员 + 助手运行时会话/线程 + 助手成员。
- 无 `chat_group` 表 → 无「群表迁移/群 seed」这一项。

## 校验规则
- **DTO/输入（Zod）**：`groupCreateSchema`（`title` 1–200、`assistantId` uuid，strict）；`groupMemberSchema`（`kind` 枚举 + `subjectId` uuid）；`groupHumanSendSchema`（`clientMessageId` uuid、`text` 1–32000 且去空白非空、`mentions` ≤32、`replyToMessageId` 可选）；`groupSendSchema`（判别联合：`request` 的 `recipientIds` 1–16 去重、`reply` 必须带 `replyToMessageId`、`message` 的 `recipientIds` ≤16）；`groupCommunicationSchema`（strict，`hop` 0–8、`projectTask`/`runtimeResult` 结构、`specificationDigest` 形如 `sha256:<64 位十六进制>`）；`groupHistorySchema`（`before` 正整数、`limit` 1–100 默认 50）；`groupPreferencesSchema`（至少一个键）；`groupJobSchema`（`recipientId` uuid）；`groupControlSchema`（`action` ∈ pause/cancel/resume + `runId`）；`groupClaimSchema`/`groupInteractionResponseSchema`（`claimId` uuid、`decisions`/`toolMessages` ≤32、序列化后 ≤128000）。
- **业务级**：mention 文本切片必须严格等于 `@{name}` 且边界为空白/标点；`reply` 必须命中原请求且原收据未回复、状态不在 `blocked/canceled/failed`；自我投递、`hop>=8`、同根 `>=32`、成员 `>=32` 一律 409；composer 文件必须 `filePath===workspacePath` 且真实存在于项目/助手目录。
- **错误语义**：`groupDenied()` 403、`groupInvalid()` 400、`groupConflict()` 409（三者均为带 i18n key 的标准 Nest 异常）；对外错误正文经 `groupExecutionError` 去凭据 + 截断 2000 字符。
- **授权**：三张表都不做行级过滤式授权，全部走服务入口（`GroupAccessService.authorize` 及其派生上下文）；直查仓库即越权。

## 已知风险
1. **收据表增长速度**：每条公开消息 × 每个目标成员写一行，`publish` 重试命中幂等键时先 `delete` 再重建；加上 `status/nextAttemptAt` 上的高频 UPDATE，`chat_message_recipient` 是本子域最大的写放大表。
2. **lease 过期无续约**：`leaseUntil` 固定 60s 且无心跳，进程崩溃后租约自然失效（下轮扫描可重抢），但 `attempts` 只增不减；`attempts>=9` 置 `failed` 后仅靠 `revision++` 提示 UI，没有复盘入口。
3. **唯一索引与幂等的耦合**：`(messageId, participantId)` 唯一让「同一消息给同一成员」只能存在一行，因此重试必须走「删除重建」而非「更新」；重建会丢掉 `executionId`/`attempts`/`lease` 历史，审计只能依赖消息侧的 `groupPublicationId`。
4. **无 FK → 孤儿行**：群会话/消息删除不级联收据、交互与成员行；`chats_group_*` 类清理只能应用层实现，遗漏即产生悬空 `groupId`/`messageId`。
5. **`sequence` 可空 + 唯一索引**：普通会话消息不分配 `sequence`，群消息才分配；跨域读取方不能假设「按 sequence 必可翻页」。
6. **`preferences` 只能改本人**：`readSequence` 用 `GREATEST` 单调且封顶到 `lastMessageSequence`，但 owner 无法代成员修正，误标已读不可回退。
7. **`interactionId` 哈希依赖请求 JSON 顺序**：requests 数组顺序变化会生成新 interaction 行（旧行仍在），依赖 `orIgnore` 只挡完全相同的重放。

## 结论
本子域的模型只有三张表、零外键、零迁移、零 seed，全部结构事实靠实体类与一次性 PostgreSQL case 承载：`chat_group_participant` 描述「谁在群里、以什么运行时身份存在」，`chat_message_recipient` 描述「谁该看到/该被唤醒、投递到哪一步」，`chat_group_interaction` 描述「哪个人类被指派处理哪次中断」。群本身没有表——它是 `chat_conversation.purpose='group'` 的一行，这一取舍让群可以直接复用会话/线程/消息的既有基础设施，代价是群表与消息/会话之间缺少数据库级完整性约束，需要靠 `publish` 的单事务写入与 `authorize` 的单一授权入口来维持一致性。
