## 运行命令
`project.json` 的 `server-ai.targets.test` 用 `@nx/jest:jest` 执行 `packages/server-ai/jest.config.ts`。实测可用命令（与父级 06 文档一致）：

```bash
# 1) 整包（nx executor；project name = server-ai）
corepack pnpm exec nx run server-ai:test --skipNxCache --runInBand

# 2) 直连 jest，单文件/单目录（本子域最常用）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/chat-group/group-outbox.spec.ts

# 3) 按路径模式跑整个子域
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --testPathPattern 'src/chat-group/'
```

`jest.config.ts` 的 `moduleNameMapper` 把 `@xpert-ai/server-core`、`@xpert-ai/contracts`、`@xpert-ai/plugin-sdk` 指向源码目录，因此跑群 spec 不需要先构建依赖包；`transformIgnorePatterns` 对 `@xpert-ai/chatkit-types` 等 ESM 依赖做了白名单转换（`group-interactions.spec.ts` 依赖其中的 `isHITLRequest`/`isClientToolRequest` 判定函数）。

章节来源：[jest.config.ts](file://packages/server-ai/jest.config.ts)（关键符号：moduleNameMapper / transformIgnorePatterns）、[project.json](file://packages/server-ai/project.json)（关键符号：server-ai.targets.test）

## 需 PostgreSQL 的用例与开启方式
`group-runtime.postgres.spec.ts` 是本子域唯一的真库用例，开启方式是环境变量 `GROUP_TEST_DATABASE_URL`：

- 开关写法：`const databaseUrl = process.env.GROUP_TEST_DATABASE_URL`，`const postgres = databaseUrl ? describe : describe.skip`（未注入变量时整组 skip）。
- 隔离策略：每次运行生成随机 schema `group_runtime_<uuid无连字符>`，先 `CREATE SCHEMA`，再用 `db.synchronize()` 建表；连接以 `synchronize: false` 初始化，避免碰到既有表。
- 结构来源：用 `EntitySchema` 手写 `chat_group_participant`、`chat_message_recipient`、`chat_group_interaction`、`chat_conversation`、`chat_message`、`chat_conversation_thread`、`xpert_agent_execution`、`user`、`xpert`，并合并 `groupResultSchemas`。
- 受控替身：授权（`GroupAccessService`）、运行控制（`ThreadRunControlService`）、工具（`GroupToolsService`）、outbox flush、项目访问都是 mock，**真实的是数据库锁、约束与事务**；测试文件明写「需要一个全新、可丢弃的 PostgreSQL 数据库；绝不能指向平台数据库」。
- 覆盖面（用例标题已核实，19 个 `it` 组）：项目绑定串行化与参与者保留、缺主助手/外部成员的拒绝、群锁下复验 owner、任务串行排队与结果唤醒、Composer 选择进入幂等与转发、单写者准入与 steer、人类输入归属与首次提问决定会话创建者、stop 后不重启旧请求、人类回复重验助手访问、worker 在预留与租约之间消失时 fail-closed、provider 失败持久暴露不重放、父子请求关联、人类发起者归属、单浏览器认领交互并拒绝他人/重复标签页、缺完整收据范围的队列 job 被拒、暂停期新投递被阻断无执行、steer 消费/未消费/失败的三种对账。

章节来源：[group-runtime.postgres.spec.ts](file://packages/server-ai/src/chat-group/group-runtime.postgres.spec.ts)（关键符号：GROUP_TEST_DATABASE_URL / postgres / GroupRuntimeService.prepare / finish）、[group-task-result.postgres.cases.ts](file://packages/server-ai/src/chat-group/group-project/testing/group-task-result.postgres.cases.ts)（关键符号：groupResultSchemas / groupTaskResultCases）

## 断言与 mock 风格
- **纯单元/服务级注入**：大多数 spec 直接 `new Service(mockDb, mockQueue, ...)` 或用 `Test.createTestingModule({ providers: [...] })` 注入 `jest.fn()` 桩；`group-outbox.spec.ts` 用一个 `DataSource` 桩把 `getRepository(entity)` 映射到不同假仓库，并用 `createQueryBuilder()` 链模拟 `deliver` 的 UPDATE-claim（以 `affected` 控制是否抢到租约）。
- **断言形态**：主要断言入队对象的完整形状（`expect(queue.enqueue).toHaveBeenCalledWith(expect.objectContaining({...}))`）、`update()` 的调用序列（含 `leaseToken` 前后一致、`finally` 清空租约）、以及「不变量式」断言（如 `JSON.stringify(projected)` 不含 `'private-'`、SSE 事件里不含 `'private'`）。
- **假定时器**：涉及退避与 `setInterval` 的用例用 `jest.useFakeTimers()` + `jest.advanceTimersByTimeAsync(1000)`（`group-outbox.spec.ts`、`group-stream.spec.ts`）。
- **命令总线断言**：以 `expect.any(CancelConversationCommand)` / `new FinishGroupChatCommand(row.id)` 形式断言跨模块命令调用与顺序（`group-members.spec.ts` 用 `invocationCallOrder` 断言「先撤成员再取消」）。
- **无全局 setup**：共享 fixture 每个 spec 自带，与父级 06 文档结论一致。

章节来源：[group-outbox.spec.ts](file://packages/server-ai/src/chat-group/group-outbox.spec.ts)（关键符号：GroupOutboxService.deliver / flush）、[group-members.spec.ts](file://packages/server-ai/src/chat-group/group-members.spec.ts)（关键符号：GroupMembersService.remove）、[group-stream.spec.ts](file://packages/server-ai/src/chat-group/group-stream.spec.ts)（关键符号：GroupStreamService.observe / publicGroupDelta）

## 覆盖缺口
1. **群发布幂等只被间接覆盖**：`group-messages.spec.ts` 覆盖的是前置拒绝与投影，`groupPublicationId` 命中的两套分支（一致复用 vs `groupConflict`）只在真库 spec 的「Composer 选择进入幂等」用例中被触碰，没有专门的「同键不同内容 → 409」「同键同内容 → 复用 messageId」定向用例。
2. **outbox 恢复语义未闭环**：`reconcile`/`deliver` 的轮转、租约与退避有覆盖，但没有用例验证「进程在 enqueue 成功后崩溃 → 30s 后重扫」与「`leaseUntil` 过期后第二个实例抢到租约」的端到端语义；也没有 Bull worker 级 spec 断言 `GroupMessageProcessor` 的 job 完成/失败如何映射为队列重试（`process` 只返回 `route` 的结果）。
3. **HITL 覆盖偏「单点」**：`group-interactions.spec.ts` 覆盖归属与 schema，真库 spec 覆盖「单浏览器认领 + 拒绝他人/重复标签页」，但 `respond` 的逐项匹配失败矩阵（数量不符、`tool_call_id` 重复、`allowedDecisions` 不含、`edit` 改名）与「完成后重放」缺少系统化用例。
4. **`GroupScopeGuard` 的 JWT 直通分支无断言**：`group-scope.guard.spec.ts` 只覆盖 client_secret 绑定与守卫顺序，`principalType` 非 `client_secret`/`api_key` 时 `return true` 的分支既无用例也不构成失败——这是设计缺陷而非测试遗漏，但两者叠加导致该缺口不可见。
5. **`GroupStreamService` 的 Redis reader 未接真**：现有用例用 `Subject` 替身驱动，`RedisSseStreamService.createSseStream` 的 join/重放/游标续订语义不在覆盖范围。
6. **`GroupCatalogService`/`GroupComposerService` 的真库行为**：侧边栏 `distinctOn` 排序、composer 文件存在性校验都依赖真实 SQL/工作区，现有 spec 以 mock 仓库断言调用，缺少真库断言。
7. **没有端到端脚本**：本子域没有与 `tools/scripts/verify-runtime-recovery.mjs` 对等的「群发布→投递→恢复」验收脚本。

章节来源：[group-messages.spec.ts](file://packages/server-ai/src/chat-group/group-messages.spec.ts)（关键符号：group publication boundaries）、[group-interactions.spec.ts](file://packages/server-ai/src/chat-group/group-interactions.spec.ts)（关键符号：group private interaction ownership）、[group-scope.guard.spec.ts](file://packages/server-ai/src/ai/groups/group-scope.guard.spec.ts)（关键符号：GroupScopeGuard.canActivate）

## 结论
判定：**✅ 可跑**。21 个群 spec 中 20 个无需外部依赖，可直接用上面的命令 1–3 运行；唯一真库用例 `group-runtime.postgres.spec.ts` 通过 `GROUP_TEST_DATABASE_URL` 解锁，自带随机 schema 与一次性库约束，风险可控。覆盖强度呈三层：服务级不变量（发布前置校验、outbox 租约与退避、成员生命周期、SSE 抑制）最扎实；真库层（准入、steer、恢复、HITL、暂停屏障）覆盖了最难的并发语义；最薄弱的是**幂等键的两套分支、outbox 的 ack/恢复闭环、HITL `respond` 的失败矩阵**，以及适配器侧守卫的 JWT 直通分支。补测优先级建议为：先加 `publish` 幂等键的定向用例（`group-messages` 或真库 spec），再补 `GroupMessageProcessor` 的队列边界用例，最后把 `GroupScopeGuard` 的直通行为固化为显式用例（或修掉缺口）。
