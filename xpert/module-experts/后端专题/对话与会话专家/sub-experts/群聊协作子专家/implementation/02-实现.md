## 成员模型与准入
`GroupAccessService.authorize(groupId, manage=false)`：先 `scope()` 从 `RequestContext` 取 tenant/organization/user 且拒绝 API key 上下文（助手凭据永远不是群凭据）；若存在 `currentApiPrincipal()` 则要求 `clientSecretBindingType=USER_CONVERSATION`、`resourceScope.kind='conversation'` 且 `conversationId===groupId`、租户/请求组织一致，过期抛 401；随后 `user()` 要求真实 `UserType.USER` + 活跃 `UserOrganization`；最后并行取 `ChatConversation(purpose='group')` 与活跃人类成员行，`manage` 追加 `role==='owner'`。返回 `{ group, actor, scope }`。`withDeliveryActor` 只在 `withGroupRuntime` 作用域内有效，重验收据状态 `starting|steering` + 助手成员 `runtimeConversationId` 绑定，再用 `groupDeliveryUserId(source)` 建立根用户上下文；`withRootUser` 重验人类成员后写 `capturedRequestContext`（`x-scope-level: organization`）。

`GroupMembersService.create` 单事务写：群会话（`purpose='group'`、`revision=1`、`threadId=randomUUID()`）、owner 人类成员、助手私有运行时会话（`purpose='group_assistant_runtime'`）+ `ChatConversationThread`、助手成员（含 `runtimeConversationId`/`runtimeThreadId`/`principalUserId`）。`add` 先 `authorize(groupId, true)`，事务内锁群行，命中既有成员则直接 `active=true`（重入恢复同一运行时绑定），活跃成员数 `>=32` 抛 409；新建助手时同时建运行时会话与线程。`remove` 拒绝 owner 与默认助手（`subjectId===group.xpertId`），置 `active=false`，把该成员相关或被其发起的未完成收据置 `canceled/member_removed`、交互置 `canceled`，再收集受影响 run 在 `withGroupRuntime` 内派发 `CancelConversationCommand`。

## 发布链
`send` 走内部强类型入口（sender 恒来自 `authorize`）；`submit` 是人类 HTTP 入口：`groupMentionRecipients(text, mentions, members)` 按 mention 区间校验（文本切片必须等于 `@{name}`、边界空白/标点、未声明的 `@` 抛 400、去重后 ≤16），无 mention 时回落到 `group.xpertId` 默认助手；若给出 `replyToMessageId` 且唯一收件人正是原发送者则退化为 `intent='reply'`。

`publish` 的执行顺序：① 前置校验（作者 active 且属本群；`reply` 由原消息 `senderId` 派生收件人；人类作者需逐个校验目标成员 active 与助手可访问；composer 仅允许人类作者、单收件人且 `participantId` 一致，并调 `composer.validate`）。② `db.transaction`：锁 `purpose='group'` 群会话行 + 取回发送者成员；助手工具发布（`publicationId` 以 `tool:` 开头）额外锁其 `runtimeThreadId` 并要求 `status==='busy'` 且 `runControl.executionId` 前缀匹配；幂等键命中时按 `projection`/`intent` 分支比对或原地更新正文（`revision++`）。③ 回复链校验（原消息存在、`intent==='request'`、本发送者收据存在且未回填 `replyMessageId`、状态不在 `blocked/canceled/failed`），`targets=[原发送者]`，继承 `rootMessageId/hop/rootUserId`。④ 反爆炸（自我投递 409、`hop>=8`、同根 `getCount()>=32`）。⑤ 写消息（`sequence` 仅在新建时 `locked.lastMessageSequence++`，`groupCommunication`、`groupPublicationId`、`messageEnvelope.version=1`/`presentation='message'`）。⑥ 收据 fan-out（助手成员在「有 `runtimeResult`」或「非 message 意图且非 projectTask 回复」时 `wake=true/status='pending'`，其余 `consumed`），回填原收据 `replyMessageId`。⑦ 保存群行（`revision++`）并返回 `publicMessage` 投影。

`snapshot` 重新授权后按 `sequence DESC` 取 `limit+1` 再反转，附成员、收据、失败的 `XpertAgentExecution`（legacy `blocked/execution_not_completed` 归一为 failed）、运行中的线程 run、`pending|claimed` 交互与 `hasMore`。`preferences` 只更新本人行，`readSequence` 用 `GREATEST("readSequence", :readSequence)` 且被 `min(group.lastMessageSequence, readSequence)` 封顶。

## outbox 投递链
`onModuleInit` 把自身注册为 `HandoffOutboxAdapter`。`reconcile()`：先取 100 条「`starting|steering` 且 `nextAttemptAt<=now`」或「`canceled+phase='started'`」的活跃收据，逐条把 `nextAttemptAt` 旋到 +5s 并执行 `FinishGroupChatCommand`（用 `allSettled` 隔离单条失败），再取 20 条 `wake=true & status='pending'` 到期的收据执行 `deliver`。`flush(groupId)` 是提交后主动投递入口，`route` 后由 HTTP/运行时调用。

`deliver(row)`：`UPDATE ... SET leaseToken=uuid, leaseUntil=now+60s, attempts=attempts+1 WHERE id AND status='pending' AND (leaseUntil IS NULL OR leaseUntil < now())`，`affected=0` 直接返回；随后 `queue.enqueue(this.message(row))`，成功 → `nextAttemptAt=now+30s`；失败 → `status = attempts>=9 ? 'failed' : 'pending'`、`error='transport_unavailable'`、`nextAttemptAt = now + min(300s, 5s*2^min(attempts,6))`，耗尽时给群会话 `revision++`；`finally` 清空租约。`message(row)` 生成 `id=group:{recipientId}`、`type=GROUP_MESSAGE_TYPE`（`group_message`）、`sessionKey=participantId`、`businessKey=groupId`、`attempt=1/maxAttempts=5`、`traceId=messageId`、`headers.handoffQueue='realtime'`（不含任何凭据）。

消费侧 `GroupMessageProcessor.process` 只做 `groupJobSchema.parse(message.payload)` 后转 `outbox.route(recipientId, message.tenantId)`：重查「本租户 + `pending` + `wake`」收据，缺失即 `{status:'ok'}`；成员已移除则把收据置 `blocked/member_removed`；否则按成员 `runtimeConversationId`/`subjectId` 组装 `AgentChatDispatchPayload`（空输入占位，实际输入由 `prepare` 决定），以 `id=group:dispatch:{recipientId}`、`type=AGENT_CHAT_DISPATCH_MESSAGE_TYPE`、`headers.handoffQueue = thread.status==='busy' ? 'realtime' : 'handoff'`、`policyTimeoutMs='3600000'` 入队。

章节来源：[group-outbox.service.ts](file://packages/server-ai/src/chat-group/group-outbox.service.ts)（关键符号：GroupOutboxService.reconcile / flush / deliver / message / route / GroupMessageProcessor.process）、[group-dispatch.commands.ts](file://packages/server-ai/src/chat-group/group-dispatch.commands.ts)（关键符号：FinishGroupChatCommand / PrepareGroupChatCommand）

## 运行时链
`GroupRuntimeService.prepare(job)`：先确认 `options.groupDeliveryId`、`tenantId`、`headers.organizationId` 齐全（TypeORM 会跳过 `undefined` 条件，注释明写不得放宽查询）；取收据（`pending+wake`）、助手成员、源消息与群行，`initiatorUserId = groupDeliveryUserId(source)`；在 `withRootUser(rootUserId)` 内重验成员助手可访问、发送者成员仍 active（助手发送者再验可访问），在 `withRootUser(initiatorUserId)` 内重验助手、`composer.validate`、项目任务的项目绑定一致性，`receipt.control` 存在时再验控制人类；失败统一把收据置 `blocked/authorization_revoked` 并 `revision++`。

准入事务（锁群行 → 校活跃成员集合包含成员/发送者/根人类/发起人类/控制人类 → 锁目标 `runtimeThreadId` 线程行 → 锁收据行）产出动作：`row.status !== 'pending'` 直接返回；控制分支校验 `pauseId`+`paused` 或 `interrupted`+`operation`+`runtimeContinuationBlockedAt`，置 `starting/phase='started'` 返回 `resume`（无 `pauseId` 时线程回 `busy`+`runControl`）；常规分支在 `pausing|paused`、`operation` 未清、`runtimeContinuationBlockedAt` 越界、`interrupted` 非根请求时置 `blocked/runtime_blocked`；composer 项目冲突置 `blocked/composer_project_changed`；`busy && (projectTask||runtimeResult)` 返回 `null`；`busy !== realtime` 返回 `null`；`executionId = thread.runControl.executionId`（steer）或 `runtimeResult.consumerExecutionId ?? randomUUID()`；新建 run 时首次使用私有运行时会把会话/线程 `createdById` 校正为发起人类，写 `XpertAgentExecution(agentKey='general_agent', status=RUNNING)`。

随后构造提示（`groupModelInput`：成员清单 + `sequence > member.contextSequence` 的背景 40 条 + 寻址输入）并把 `receipt.contextSequence` 推到 `max(member.contextSequence, source.sequence, ...background)`；`resume+pauseId` 走 `GetXpertWorkflowQuery` + `control.claimResume`，`send`/无 pauseId 的 `resume` 走 `control.start`。返回的 dispatch 载荷带 `options.tools=[send_group_message]`、`options.context={groupId, participantId}`、`streamPersistence(redis-stream)` 与 `messageEnvelope.presentation='runtime'`（`correlation.messageId=receipt.id`）。

`finish(recipientId, dispatchFailed, dispatchFinished)`：`dispatchFailed && starting` 时把 run 标错（`control.finish(..., 'error', 'group_dispatch_failed')` + 执行 ERROR）；`steering` 分支按落库输入 `followUpStatus` 决定 `consumed`/`pending`/`blocked`；随后做「预留与租约之间进程丢失」的 fail-closed 判定（线程 busy、同一执行、无 run lease、`startedAt` 超 120s → 线程 `error` + 执行 INTERRUPTED）；执行仍在 RUNNING/PENDING 则返回；未完成且线程 `interrupted` 有 `operation` 时 `interactions.register`；把该执行的可见 AI 输出逐条 `publish`（`publicationId='output:{id}'`、`projection=true`、末条答案走 `intent='reply'`，403/409 记 `publicationBlocked`）；最后写收据终态（`consumed|failed|blocked|canceled` + `phase='finalized'`）、推进成员 `contextSequence`、`revision++`、`outbox.flush`。回复目标由 `automaticReplyTarget`（≤8 跳回溯根请求、跳过已回复/异常/其它未闭合请求）决定。

## HITL 交互
`register` 只在 `isLangGraphInterruptPayload(operation)` 时工作，把 `isClientToolRequest`/`isHITLRequest` 的 interrupt 收集成 `GroupInteractionRequest[]`，以 `interactionId = "{executionId}:{sha256(JSON.stringify(requests))}"` 做 `insert().orIgnore()`，因此重放同一执行不会产生第二行。`claim(groupId, id, claimId)`：授权 → 事务锁群行 + 交互行（`assignedUserId = actor.subjectId`）→ 状态必须 `pending|claimed` 且 `claimId` 未被别的标签页占用 → 成员 active → 线程必须 `interrupted`、有 `operation`、且交互创建时间晚于 `runtimeContinuationBlockedAt` → 写 `claimId/claimedBy/status='claimed'`、`revision++`，此时才返回私有请求体。

`respond`：要求 `claimId` 与 `claimedBy` 都匹配；已完成直接返回；逐项比对 `toolMessages` 与 `clientToolCalls`（数量、`tool_call_id` 唯一、`name` 可选匹配）与 `decisions` 与 `actionRequests`（数量、`reviewConfigs.allowedDecisions`、`edit` 必须同名）；重验线程 `interrupted` 与租约屏障；收据必须是 `blocked`，随后写 `control={actorId, decision:{type:'confirm', payload}}`、`status='pending'`、`phase=null`、`nextAttemptAt=now`，交互置 `completed`、`revision++`，提交后 `outbox.flush(groupId)` 恢复执行。私有载荷永不出现在 `snapshot`，只出现 `id/runId/participantId/assignedUserId/status`。

## SSE 观察者流
`observe(groupId, lastEventId)` 先 `access.authorize`，把游标（加密的 `{version,groupId,viewerId,revision,runs}`，`runs` ≤32）解密并做双重绑定校验：`groupId` 与 `viewerId` 必须与当前请求一致，否则 `resync`；`lastEventId` 超 16000 字符或解析失败同样 `resync`。Observable 内 1s 轮询 `messages.snapshot(groupId, 100)`（每次轮询都隐性重验成员资格），用 `[revision, runs]` 签名去重后发 `snapshot`；对 `busy|pausing` 的 run 通过 `RedisSseStreamService.createSseStream({ threadId: member.runtimeThreadId, runId, mode:'join', requireReplayStart:true, isRunFinished })` 挂读，只在收到 `on_message_start` 拿到 `messageId` 且 `publicGroupDelta` 判定为公开文本时发 `text` 事件；run 结束后退订并清游标。断开只卸载 reader，不取消模型也不确认工具。

## Composer 与草稿
`GroupComposerService.member()` 先授权再要求目标是活跃助手成员并复验助手可访问（客户端 ID 不能建立运行时绑定）；`context()` 返回 `{projectId, locked, busy}`，其中 `locked = 有消息 || 线程非 idle || 群项目与运行时会话一致`。`validate()` 要求 `participantId===member.id`、项目可访问、`locked` 时项目不可切换、`runtimeResources` 经 `runtimeResources.resolve` 复核、`files` 必须 `filePath===workspacePath`、非绝对路径、无 `..`/`.`/反斜杠，且在项目或助手工作区目录清单中真实存在（每个文件一次目录列举）。资源/能力接口统一走 `withResourceActor`（重新授权 + 成员复验 + `withRootUser`），避免把「助手资源 API」当成群授权。`groupComposerSchema` 把 `files` 限 30 条且 `purpose` 只能 `'workspace'`，服务顶部 TODO 明写计划把 Chat 与群的 Composer 操作抽成共享实现。

## 热点路径
1. **群 publish 行锁**：单群串行化（群会话 `pessimistic_write`；助手工具发布再叠运行时线程锁），且 `publish` 每次都要读成员、算收据；继承发布还要按 `groupCommunication->>'rootMessageId'` 做一次 `getCount()`。
2. **收据写入量**：每条消息按目标成员数写 N 行；命中既有消息重试时会 `delete` 全部收据后重建，`attempts`/`lease` 状态随之重置。
3. **outbox 扫描器**：每次扫描 100 条活跃收据（轮转）+ 20 条待投递；`deliver` 逐条 UPDATE-claim + enqueue，失败退避到 300s 上限。
4. **finish 对账**：一次收尾可能触发 8 跳回溯（`automaticReplyTarget`）+ 多条输出 `publish` + `outbox.flush`，是总线上的连锁放大点。
5. **SSE 轮询**：每个观察者 1s 一次 `snapshot(100)`，并为每个活跃 run 建立一条 Redis stream reader。
6. **catalog 侧边栏**：`distinctOn` 取每群最后一条消息 + 全体成员 + 头像解析。

## 技术债与缺口
1. **`GroupScopeGuard` 对 JWT 直接放行**：`canActivate` 在 `principalType` 非 `client_secret`/`api_key` 时 `return true`，登录用户完全依赖下游服务侧断言（`GroupAccessService.authorize`）。
2. **outbox 恢复靠轮询**：无独立队列、无死信台账，恢复窗口 = 5s 扫描 + 30s 节流 + 最长 300s 退避；`attempts>=9` 置 `failed` 后只能人工介入。
3. **`GroupMessageProcessor` 与 Bull ack 边界未确认**：`process` 只返回 `route` 的 `{status:'ok'}`，源码与既有 spec 都未描述 job 完成/失败如何映射为中继重试，跨重启的期间语义不清。
4. **群内个人视角历史缺失**：`snapshot` 是群级公开投影；`contextSequence`/`readSequence` 只服务运行时上下文与未读统计，没有「以某成员视角」的历史读取接口。
5. **收据重建丢状态**：`publish` 命中幂等键时 `delete` 旧收据再重建，`attempts`/`leaseToken`/`executionId` 视为不复用（只保留消息与正文更新路径）。
6. **`preferences` 无管理代理**：只能改本人行（`where id = actor.id`），owner 无法代成员置顶/归档。
7. **Composer 与 Chat 重复**：`GroupComposerService` 顶部 TODO 明写要抽共享实现，当前群侧是「适配器式」复用。
8. **反爆炸阈值硬编码**：`hop>=8`、同根 `>=32`、成员 `>=32` 分散在三处，调整需同时改测试与文档。

## 设计维度
**一致性 vs 可用性**：本域选择「先提交消息与收据，再异步投递」，因此发布是强一致（行锁 + 唯一索引），投递是 at-least-once（enqueue 不等于消费）——代价是重复通知与需要人工修复的 `failed` 收据。
**锁粒度 vs 写放大**：群会话行锁换来 `sequence`/幂等键/回复认领的线性化，但把单群变成写热点（助手工具发布叠加线程锁）；收据 fan-out 把 1 次发布放大成 N 行写入 + N 次可能的入队。
**公开投影 vs 私有运行时**：可见性边界靠「投影函数 + 收据」实现（`publicMessage`/`snapshot` 只出公开字段，私有请求只在 `claim` 成功后返回），代价是投影逻辑与运行时字段强耦合，字段新增需同时改两侧。
**幂等键 vs 唯一索引**：应用层键（`groupPublicationId`、`interactionId`）负责语义复用，数据库唯一索引负责兜底并发；两者必须成对演进，否则重试会退化为 409。

## 结论
实现上，本子域把复杂度压缩到三个收敛点：**一个发布入口**（`publish`：行锁 + 幂等键 + 收据 fan-out）、**一个投递账本**（`chat_message_recipient` + `lease` 抢占 + `route` 改写）、**一对运行时命令**（`PrepareGroupChatCommand`/`FinishGroupChatCommand`，输入输出都是持久化事实）。身份永远来自绑定（`withDeliveryActor`/`withRootUser`/`groupDeliveryUserId`），私有载荷永远不出公开投影。新增能力时应保持「同事务落账、投递可重试、消费幂等」三条底线；最需要补强的是 `GroupScopeGuard` 的 JWT 直通缺口、outbox 的 ack 语义与按成员视角的历史读取。
