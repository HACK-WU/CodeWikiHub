## 核心流程实现位置
### ① 会话 CRUD 与 assertAccess
`ChatConversationService.create` 调 `super.create` 后容错 `ensureInitialReadState`（失败仅 `logger.warn`）；`update` 对 `options` 做白名单合并（`null` → 只保留 `runtimeResources`，`undefined` → 丢弃该字段，对象 → `mergeConversationOptionsSql`）并拒绝 `projectId` 迁移（`Error.ConversationProjectImmutable`）。`assertAccess(id, 'read'|'contribute'|'manage')` 拒绝 `purpose==='group'`、`group_assistant_runtime` 仅 `isGroupRuntime` 放行、Project 会话转 `assertCanRead/assertCanUse`（`manage` 要求本人创建或 `owner/manager`），否则要求 `createdById === 当前用户`，统一 `conversationAccessDenied()`。`markRead` → `resolveLastReadMessage` → `normalizeReadAt` → `saveConversationReadState`（唯一索引 `(tenantId,organizationId,conversationId,userId)`）。
章节来源：[conversation.service.ts](file://packages/server-ai/src/chat-conversation/conversation.service.ts)（关键符号：ChatConversationService.create / update / assertAccess / markRead / ensureInitialReadState）

### ② 消息写入、sequence 与读状态
写入唯一入口是 `ChatMessageUpsertCommand` → `ChatMessageUpsertHandler.execute`：`applicationTracing.traceAsync('message.persist')` 包裹「有 id 走 `save`、否则 `create`」，随后按 `shouldExtractTaskSummary`（新建或触及 content/references/fileAssets/attachments/thirdPartyMessage/taskSummary）重新读取并 `extractChatMessageTaskSummary` 二次 `save`。`sequence` 的分配契约写在 `ChatConversation.lastMessageSequence`（会话行锁），消息表以唯一索引 `(conversationId, sequence)` 约束，私有路径不分配。读侧 `ChatMessageService.findOneAuthorized` 先取轻量行拿到 `conversationId`，再经 `AssertChatConversationAccessQuery` 授权，最后才按 `relations` 二次读取并复核 `conversationId` 一致；`filterAuthorizedFileRelations` 并行处理两条文件路径（legacy `attachments` 经 `GetOwnedStorageFileQuery`、`fileAssets` 经 `ResolveAuthorizedFileAssetQuery`），`ForbiddenException` 静默剔除而非报错。
章节来源：[upsert.handler.ts](file://packages/server-ai/src/chat-message/commands/handlers/upsert.handler.ts)（关键符号：ChatMessageUpsertHandler.execute / shouldExtractTaskSummary）、[chat-message.service.ts](file://packages/server-ai/src/chat-message/chat-message.service.ts)（关键符号：ChatMessageService.findOneAuthorized / filterAuthorizedFileRelations）、[conversation.entity.ts](file://packages/server-ai/src/chat-conversation/conversation.entity.ts)（关键符号：ChatConversation.lastMessageSequence）

### ④ 分支（事务、行锁、谱系复制、幂等）
`ConversationBranchHandler.execute` 只转发 `ConversationBranchService.branch`。`branch` 顺序为：`requestSchema.safeParse`（`sourceThreadId`≤100、`afterMessageId`/`requestId` 为 UUID）→ `RequestContext.currentUserId()` → `assertAccess(contribute)` → 发布版 Xpert 与 Project 运行访问 → `findExistingBranch`（快路径，命中返回既有会话）→ `prepareBranch`（事务外）：`loadBranchPath` 用 `getTreeRepository(ChatMessage).findAncestors` + `messageAncestorPath` 取根→选中消息，校验 `messageBranching(selected).available` 与 `anchor.messagePathHash === branchMessagePathHash(path)`；`GetXpertWorkflowQuery` → `threadGraphRevision(graph) === anchor.graphRevision`；逐消息 `filterAuthorizedFileRelations` 且数量必须相等；逐 `fileAssetId` `resolve(operation:'read')` + `assertCanLinkToConversation`；目标会话 `options` 删除 `sessionWorkspacePath`。事务内：源线程 `pessimistic_write` → 二次 `findExistingBranch` → 重算 `branchPathSnapshot` 比对 → `allocateBranchTitle`（`pg_advisory_xact_lock` 家族编号）→ `copyBranchCheckpoints`（前沿闭包、`rebindCheckpoint`、只复制检查点**不**复制 pending writes）→ 父先子后插入消息并重算 `messageHash`/`messagePathHash` → 复制 `ConversationFileLink` → 新建线程 `metadata={primary, forkGraphRevision}`。命中幂等时返回既有会话，并记录 `applicationMetrics.recordConversationBranch`（`outcome`/`reason`/`durationMs`/`copiedSize`）。
章节来源：[conversation-branch.service.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/conversation-branch.service.ts)（关键符号：ConversationBranchService.branch / prepareBranch / loadBranchPath / findExistingBranch）、[branch-checkpoints.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/branch-checkpoints.ts)（关键符号：copyBranchCheckpoints / rebindCheckpoint）、[branch-title.ts](file://packages/server-ai/src/chat-conversation/conversation-branch/branch-title.ts)（关键符号：allocateBranchTitle）

### ⑤ 地图（provider 注册与投影）
`ConversationMapViewProvider` 以 `@ViewExtensionProvider('platform.conversation-map')` 注册，`supports` 要求 `hostType==='agent'`，仅在 slot `AGENT_WORKBENCH_SLOT` 返回清单：key `topics`（"对话脉络"）、`order: 45`、`activation.requiredFeatures=[CONVERSATION_MAP_FEATURE]`、`workbench.openMode='on-demand'`/`contextScope='conversation'`、`view.type='remote_component'`/`isolation:'iframe'`/`entry:'conversation-map'`、`dataSource.mode='platform'` 且 `cache.enabled=false`、动作 `act`（`actionType:'invoke'`）。`getViewData` 以 Zod 校验（`mapQuerySchema`），`parameters.operation==='projects'` 走 `projectOptions`；`executeViewAction` 要求 `key==='act'` 且 `mapActionSchema` 通过。`presentation.ts` 的 `turnNodes` 跳过 runtime 消息与非 human/ai 角色，人类消息开 turn、AI 消息合并 `answer` 并写入 `branchMessageId`/`branchAvailable`/`branchReason`；`humanMessageSummary` 截断 600 字符并标 `inherited`；搜索只匹配 `title`/`preview`/`answer` 纯文本块。`ConversationMapService.read` 按 `scope()`→`conversation()`→线程或会话页投影，`act` 的 `create` 用 `pg_advisory_xact_lock(hashtext('conversation-map:{userId}:{requestId}'))` 加 `requestId` 作会话 ID 实现幂等，再走 `ChatConversationUpsertCommand`，最后 `target()` 返回 `viewKey: 'platform.conversation-map__topics'`。

### ⑥ 主聊天流（/api/chat）

### ⑦ 运行控制（pause/resume/租约）
`ThreadRunControlService` 所有状态迁移都在 `locked()`（线程 `pessimistic_write`）内完成：`start` 拒绝线程已有其他 execution 并写加密上下文与租约；`requestPause` 要求 `status==='busy'`，置 `pausing` + 新 `pauseId` 并清空旧检查点；`stageCheckpoint` 只在 `pausing` 期间写入；`finish` 先 `recoverExpiredRun` 再判定「`pausing` + 有检查点 + `interrupted` → `paused`」，否则清 `runControl`/`encryptedRunContext`；`claimResume` 校验 `paused` + `pauseId` + `graphRevision` + `CopilotCheckpoint` 存在后回到 `busy`；`cancel` 置 `interrupted` 并写 `runtimeContinuationBlockedAt`。`onModuleInit` 起 15s 定时器续约（`RUN_LEASE_MS=90_000`），`maintainLeases` 同时扫描过期租约线程（`take: 50`）并调 `recoverExpiredRun`，后者在一个事务内：线程置 `error`、清 `runControl`/`encryptedRunContext`/租约、执行置 `INTERRUPTED`、思考中消息置 `aborted`、等待记录置 `stale`、会话置 `error`。`ChatExecutionAdmissionService.lockRuntimeThread` 用 `orIgnore` 补建线程行，`automatic` 续跑要求 `runControl.executionId/state` 与 `status==='busy'` 完全匹配，否则抛 `RuntimeMessageBlocked`。

## 热点路径
1. **单会话消息写热点**：`ChatMessageUpsertHandler` → `ChatMessageService.create/save`，叠加 taskSummary 二次 `save`，且 `ChatMessage` 带 `@Tree('closure-table')`，父链变更会额外维护闭包表。
2. **重授权往返**：`findOneAuthorized` 为「轻量取行 + 授权查询 + 带关系再取」两查一授权；`filterAuthorizedFileRelations` 对每个 attachment/fileAsset 各发一次 `QueryBus`（N+1 型），分支复制会逐消息调用它。
3. **分支事务**：源线程行锁长期持有，事务内逐消息 `save` + 逐检查点 `save` + 逐文件链接查询；`copyBranchCheckpoints` 以前沿栈遍历 checkpoint 父链与 `metadata.parents`。
4. **地图读放大**：无 `conversationId` 时对每个会话调 `threadSummary`（1 次 `requireByThreadId` + 1 次 `findVisibleMessages`）；带 `search` 时对每个线程全量 `findVisibleMessages` + `turnNodes`。
5. **租约续约循环**：每 15s 遍历 `owned` 全部线程并额外扫 50 条过期线程，逐条 `recoverExpiredRun`（每条一个事务）。
6. **未读统计**：`getUnreadByXperts` 为聚合 SQL；`findReadableFamilyConversations` 承担地图首页分页。

## 技术债与 hack
1. **无归档字段**：`chat_conversation` 只有 `status`/`error`，没有 archived 列；侧边栏归档语义由用户偏好承载，会话级归档缺失。
2. **attachments 双路径**：`ChatConversation.attachments` 与 `ChatMessage.attachments` 均标 `@deprecated`，新路径为 `FileAsset`/`ConversationFileLink`，但 `filterAuthorizedFileRelations` 与分支复制必须并行维护两套关系。
3. **地图无表但依赖 view-extension 宿主**：`ConversationMapModule` 没有自有持久化，能力暴露完全依赖宿主 Discovery 收集 provider、`AGENT_WORKBENCH_SLOT` 与 `CONVERSATION_MAP_FEATURE` 特性开关；`getRemoteComponentEntry` 运行时读取 `remote-components/conversation-map/app.js|app.css`。
4. **run 僵尸需显式 stop**：无租约的旧 run 不按时间猜测回收，只能人工 cancel；有租约线程在续约失败时会被直接标 `error`。
5. **`sequence` 双语义**：行锁分配契约写在 `ChatConversation.lastMessageSequence`，但私有会话消息常驻 `NULL`，跨路径读取方不能假定它存在。
6. **装配分散**：`ConversationBranchModule` 不在 `ChatConversationModule.imports`，`ConversationBranchController` 又在 `ai/`，分支能力的注册与反查成本高于同目录能力。
7. **地图搜索分页语义**：`page.total` 是扫描范围而非命中数（源码注释明写），`searchOffset`/`nextSearchOffset` 需要客户端配合。
8. **envelope 读侧静默**：`readChatMessageEnvelope` 吞掉解析异常返回 `undefined`，读侧无法区分「无信封」与「损坏信封」。

## 设计维度分析
**写模型 vs 只读视图**：分支以事务 + 行锁 + 检查点闭包换取「可独立续跑的历史副本」，代价是写放大与长事务；地图以零表投影换取免迁移与低耦合，代价是每次查询重算与读放大。二者共用同一批实体，却对「一致性」给出完全不同的答案。
**授权前置 vs 事务内授权**：分支源码注释明写「服务授权读取在事务之前执行，加锁后一切数据库操作使用同一 manager，避免连接池饱和导致死锁」——这是把授权与并发控制分层，而非在锁内再调外部服务。
**幂等实现的分层**：分支用 `requestId` + 部分唯一索引 + 事务内二次查询；地图 `create` 用 advisory lock + 以 `requestId` 复用为会话 ID；`markRead`/`ensureInitialReadState` 用读写状态唯一索引做 upsert。三种幂等粒度分别对应「一次性写入」「客户端重试创建」「可反复覆盖的读位置」。
**控制面单一写者**：所有既有会话的根式入口都必须经 `ChatExecutionAdmissionService.run` 拿线程写者资格，`automatic` 续跑额外要求与 `runControl` 完全匹配——把「谁能推进线程」与「谁能写消息」解耦，避免运行时的自动续跑绕过人工暂停。

## 结论
本子域的实现特征是「入口极少、闸门极窄、副作用可重放」：消息只有一个写命令、分支只有一个命令、反馈与消息读路径都先过 `assertAccess`、运行控制只有一个写者许可。pause 语义被刻意设计成「受理 ≠ 完成」，租约只证明进程归属而**不**证明检查点或消息已持久化——这两条是全子域最容易被误读的边界。新增能力时最应保持的三点是：不绕开 `assertAccess` 直查仓库、不新增第二个消息写入口、不让 envelope 承担命令或授权语义。
