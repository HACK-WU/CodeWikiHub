## §1 入队契约

入队三入口在 `HandoffQueueService`（`handoff/message-queue.service.ts`，所在模块 `@Global()`）；`enqueue` / `enqueueAndWait` 通过插件权限桥（`HANDOFF_QUEUE_SERVICE_TOKEN`）暴露给插件，权限操作域为 `handoff`。

| 能力 | 方法签名 | 参数与行为语义 | 返回（是否等待结果） | 异常 | 约束 |
|---|---|---|---|---|---|
| 单条入队 | `enqueue(message: HandoffMessage, options?: HandoffEnqueueOptions): Promise<{ id: string }>` | `resolve` → `normalize` → `withRouteHeaders` 写回路由头 → `queueGateway.enqueue`；`options.delayMs` 仅映射为 Bull `delay`（`Math.max(0, delayMs ?? 0)`） | `{ id }`，**不等待**；`id` 为补全后的消息 id | 网关 `add` 失败原样抛出 | `@RequirePermissionOperation('handoff','enqueue')` |
| 批量入队 | `enqueueMany(messages: HandoffMessage[], options?: { delayMs?: number }): Promise<Array<{ id: string }>>` | 逐条 `resolve`/`normalize` 后**串行**入队（网关 `enqueueMany` 内部循环 `add`）；不去重、不聚合 | id 列表，**不等待** | 同上 | 源码**未见**权限注解（内部回投与适配器使用） |
| 入队并等待 | `enqueueAndWait(message: HandoffMessage, options?: HandoffEnqueueAndWaitOptions): Promise<ProcessResult>` | **先**注册本进程 waiter（`waitFor`），**再**入队；`timeoutMs` 缺省 `XPERT_HANDOFF_PENDING_TIMEOUT_MS`（120000）；`onEvent` 接收处理器 `emit` 事件 | `ProcessResult` = `{status:'ok', outbound?}` / `{status:'retry', delayMs, reason?}` / `{status:'dead', reason}`，**等待但仅本进程** | 入队失败时先 `pendingResults.reject(id, error)` 再向上抛；跨实例只会等到超时 | `@RequirePermissionOperation('handoff','wait')`；同一 id 重复 `waitFor` 直接抛错 |
| 本地任务命令 | `EnqueueAgentChatMessageCommand` → `EnqueueAgentChatMessageHandler.execute` | 先 `LocalQueueTaskService.register` 注册进程内闭包并把 `taskId` 放进 `payload`，再 `enqueueAndWait`（显式 `maxAttempts: 1`） | 处理器返回值 | `dead` → 抛 `reason`；`retry` → 抛「unexpected retry result」；失败时 `remove(taskId)` 清理悬挂任务 | 仅在单实例内语义成立 |
| 出站回投 | `BaseHandoffQueueProcessor.handleResult`（`ok` + `outbound`）→ `enqueueMany(result.outbound)` | 消费端把下游消息批量回投，并 `pendingResults.resolve` 兑现等待者 | 无对外返回 | 回投失败走 `handleError` 分流 | 入队**不在**任何业务事务内 |

**`HandoffMessage` 字段语义**（`file://packages/plugin-sdk/src/lib/agent/handoff/types.ts`）：

| 字段 | 语义与约束 |
|---|---|
| `id` | 幂等键与等待键；缺省补 `randomUUID()`；`messageIds` 取消与 `enqueueAndWait` 都按它匹配 |
| `type` | 处理器解析键（`processorRegistry.get(type, organizationId)`），也是路由 `typePolicies` / `match.type` / `match.typePrefix` 的输入 |
| `version` | 信封版本，缺省补 `1` |
| `tenantId` | 必填（`assertMessage` 校验）；决定处理器解析的租户作用域 |
| `sessionKey` | 必填；运行时链路上等于回复目标线程 `threadId` |
| `businessKey` | 必填；业务关联键（运行时链路为 `invocationId`） |
| `attempt` / `maxAttempts` | `attempt` 取 `max(1, attempt ?? 1)`；`maxAttempts` 解析顺序：消息值 → `typePolicies.<type>.retry.maxAttempts` → `3` |
| `enqueuedAt` | 缺省 `Date.now()` |
| `traceId` / `parentMessageId` | `traceId` 必填（日志与取消排障主键）；`parentMessageId` 可选溯源 |
| `payload` | 处理器自定义载荷；`executionIds` 取消匹配 `payload.executionId`，本地任务匹配 `payload.taskId` |
| `headers` | 路由与上下文载体，见下 |

**`headers` 覆盖语义**（`HandoffMessageHeaders`）：`handoffQueue` 是**最高优先级**的队列覆盖（`queue` 为兜底别名，均经别名表归一并在入队时被解析结果写回）；`requestedLane`、`policyTimeoutMs`、`policyIdleTimeoutMs` 为同级覆盖，**显式值不被覆盖**（`withRouteHeaders` 只在缺省时补）；`organizationId` / `userId` / `language` / `conversationId` / `threadId` / `source` / `integrationId` / `sourceAgent` / `targetAgent` 供上下文重建与路由匹配（`rules.match.organizationId` 读 `headers.organizationId`，`match.source` 读 `headers.source`）。

## §2 路由契约

- **队列优先级链**：header `handoffQueue`（`queue` 兜底）> `typePolicies[type].queue` > **首个**命中 `routes[].match` 的 `target.queue` > `defaultQueue`。
- **lane 同级链**：header `requestedLane` > `typePolicy.lane` > `route.target.lane` > `defaultLane`。
- **超时链**：header `policyTimeoutMs` / `policyIdleTimeoutMs` > `typePolicy` > `route.target`（缺省则不写头）。
- **规则匹配字段**（同一规则内全部为「与」关系，`routes` 取首个命中、无优先级字段）：`type`、`typePrefix`（前缀）、`tenantId`、`organizationId`（读 `headers.organizationId`）、`source`（读 `headers.source`）。
- **配置来源**：`HandoffRoutingConfigService` 在 `onModuleInit` 通过 env `HANDOFF_ROUTING_CONFIG_PATH` 加载 YAML 并归一为快照（队列别名表把 YAML 队列名映射到 4 个真实队列名，内置别名含 `handoff`/`default`/`realtime`/`batch`/`integration`；lane 别名含 `high→main`、`low→cron`）；未设置路径时只 `warn` 并使用内置默认快照。

| 消息情形 | 解析结果（队列） | 依据 |
|---|---|---|
| 显式 `headers.handoffQueue = 'realtime'` | `handoff:realtime` | header 优先 + 别名表还原 |
| `type` 命中 `typePolicies` 且配置了 `queue` | 该 typePolicy 的队列 | header 缺省时降级到 typePolicy |
| 无 header / 无 typePolicy，但命中 `routes[].match`（如 `typePrefix: 'agent.chat'`） | `routes[].match.target.queue` | 首个命中规则 |
| 三者皆无 | `defaultQueue`（内置默认 `handoff`） | 最终回落 |
| 运行时事件消息（`runtime_event`） | 由 transport 显式构造并 `enqueue`，未设队列 header → 走 typePolicy/route/default | `RuntimeMessageTransportService.deliver` |

## §3 运行时消息契约

**outbox（appendRuntimeDelivery）**：`appendRuntimeDelivery(manager: EntityManager, invocation: AgentInvocation)` 必须与 Invocation CAS **共享事务**（源注释逐字：`Must share the Invocation CAS transaction: a queue outage cannot discard a committed result.`）；事件只从 Invocation 事实派生——终态出 `kind='result'`（带 `status`）、`status='waiting'` 且有 `interaction` 出 `kind='input_request'`（带 `interactionId`），`progress` 与其余状态**不产出**事件；幂等键 `messageId = runtime-{invocationId}-{kind}-{revision}`（同观测重复提交被 `orIgnore()` 吞掉）；初值 `state='pending'`、`nextAttemptAt=now()`；事件只含引用（`invocationId`/`revision`，可选 project/task 标识）。

| 对象 | 取值与流转 |
|---|---|
| `agent_runtime_delivery.state` | `pending` →（inbox 提交回执）`received`；失败分支 `blocked`（`lastError=access_or_target_changed`）或 `failed`（`attempts>=19`、`lastError=transport_unavailable`）；redrive 把 `blocked|failed` 复位为 `pending`（`attempts=0`） |
| delivery 租约 | claim 为 `UPDATE ... SET leaseToken, leaseUntil=now()+60s, attempts=attempts+1 WHERE state='pending' AND (leaseUntil IS NULL OR leaseUntil < now())`，`affected=0` 即让路 |
| transport 节流与退避 | enqueue 成功后 `nextAttemptAt = now()+30s`（**不是**回执确认）；失败退避 `min(300s, 5s * 2^min(attempts,6))`；扫描 `@Interval(5000)`、`take: 20`、按 `nextAttemptAt ASC` |
| `agent_runtime_inbox.state` | `pending` / `processing` / `processed` / `blocked` / `failed`（`agentRuntimeConsumptionStateSchema`） |
| `agent_runtime_inbox.phase` | `reserved`（已预留 execution / claim，尚未开跑；此阶段可复用同一 execution ID 恢复）或 `started`（已开跑；恢复时**只**查该 execution） |
| `consumptionKey` | `agentRuntimeResultConsumptionKey(invocationId, replyTo)`（JSON 数组：invocationId / conversationId / threadId / agent 目标 / agentKey）；`input_request` 追加 `:input:{interactionId}`，与最终结果**不争抢**；存储唯一键另加 `tenantId/organizationId/ownerId` |
| `claim` | `{ invocationId, resultRevision, recipient, consumer }`，`consumer` 为 `{type:'follow_up', executionId}` 或 `{type:'wait', executionId, callId}` |
| `claimWait(command)` | 逐个 invocation `withReply` 重授权（要求 `sameInvocationData`，含 `parentExecutionId`），仅 `result` 事件参与，要求 consumer 执行仍 `RUNNING` 且 `threadId`/`agentKey`/`createdById` 匹配；同事务 `lockInbox` 后写 `state='processed'` + `claim`；已有 claim 且不一致抛 `Consumed`；返回 `Promise<void>` |

**续跑触发与阻断**：`RuntimeMessageContinuationService.reconcile`（`@Interval(3000)`、`take: 8`、`state IN (pending, processing)`）→ 60s 租约 + 每 15s 心跳 → `withReply` → `reserve` → `phase='started'` → `run`（`ChatCommonCommand` / `XpertChatCommand` 新 `send` 轮次）→ `recover`（只查 claim 记录的 execution）。

| 阻断条件 | 结果 |
|---|---|
| 线程 `runtimeContinuationBlockedAt` 不早于调用创建时间 | `blocked(user_stopped)` |
| 线程 `status ∈ {paused, pausing, interrupted}`、存在 `operation`、或 `runControl.state==='paused'` | `blocked(awaiting_user)`（审批与显式 stop 均属此类） |
| 线程 busy（已有写者） | `blocked(thread_busy)`，`nextAttemptAt = now()+5s` 重试 |
| consumer 执行仍未终态 | `blocked(consumer_outcome_unknown)`，**不自动重放** |
| consumer 已终态但非成功 | `processed` + `lastError=consumer_ended_without_success` |
| `group_assistant_runtime` 会话 | 只预留 claim（`phase` 保持 `reserved`），成员准入归群队列 |

**观测**：`RuntimeObservationMonitorService.reconcile`（`@Interval(5000)`、`take: 20`）以 60s 观察租约（20s 续约）`withActor` 后 `inspect`，**只观察既有句柄、绝不启动**；有 `projectTask` 时发 `ProjectRuntimeObservationCommand`。

## §4 取消与死信契约

- **入参**：`StopHandoffMessageCommand` 接收 `StopHandoffMessageInput = { messageIds?: string[], executionIds?: string[], reason?: string }`；`executionIds` 匹配 `payload.executionId`；两者皆空时**直接返回空摘要、不扫描**。
- **扫描范围**：全部 4 个队列的 `waiting` / `delayed` / `paused` / `active`（`DEFAULT_SCAN_STATES`，逐队列逐状态 `getJobs`）。
- **处置**：`waiting`/`delayed`/`paused` → `removeJobs`（逐个 `job.remove()`，失败仅 `warn`）并对命中 `payload.taskId` 者 `LocalQueueTaskService.remove`；`active` → `HandoffCancelService.cancelMessages(ids, reason)`（先 publish Redis 频道 `ai:handoff:cancel` 通知其他实例，再在本进程记录 reason 并 `AbortController.abort()`）；所有 matched `messageIds` → `pendingResults.cancel(id, 'canceled:...')`。
- **返回**：`StopHandoffMessageResult` = `{ requested, matched, removed.jobs[], aborted.messageIds[], notFound }`；「取消返回成功」不等于「作业已停止」（active 为 best-effort、对竞态敏感）。
- **`dead(canceled:...)` 语义**：取消被归一为 `dead` 且 reason 带 `canceled:` 前缀；该结果会 **resolve 等待者**，但**不进死信、不重试**；`buildCanceledReason` 默认文案 `Canceled by user`，`isCanceledReason` 只看前缀，`isAbortLikeError` 把 abort/cancel 异常映射到取消流（三处分类一致）。
- **死信读出**：`HandoffDeadService.record` 仅 `logger.error('Dead letter: type=..., id=..., traceId=..., reason=...')`，**无台账表、无查询接口**；进入死信只有三条路径——`retry` 超 `maxAttempts`、`dead` 且非 `canceled:`、永久错误（`No handoff processor found` / `Invalid handoff message:` 等）。
- **redrive 的原子性（改什么 / 不改什么）**：`POST .../delivery/redrive` body 为 strict 空对象 `{}`，经 `withReply` 重授权后在**同一事务**执行 `resetRuntimeDelivery`——**改**：`blocked|failed` 的 delivery 复位为 `pending`/`attempts=0`/`nextAttemptAt=now()`/`lastError=null`，`blocked|failed` 且 `event->>'kind'='result'` 的 inbox 做同样复位；**不改**：Invocation 事实、`claim`、`phase`、用户 stop 屏障、已消费结果，也不重启 CLI、不分配替代消费者。命令入口等价于 `RequestRuntimeResultCheckCommand(invocationId, owner)`。

## §5 代码示例（真实调用方代码）

### 例 1 · 入队一条消息并等待（`enqueueAndWait` 的本进程限制）
```ts
// packages/server-ai/src/handoff/commands/handlers/enqueue-agent-chat-message.handler.ts（节选，逐字）
const taskId = this.localTaskService.register(async (ctx) => {
    output = await task(ctx); hasOutput = true; return { status: 'ok' }
})
const result = await this.handoffQueue.enqueueAndWait({
    id: options.id, type: options.messageType ?? AGENT_CHAT_MESSAGE_TYPE, version: 1, tenantId,
    sessionKey: options.sessionKey, businessKey: options.businessKey ?? options.id,
    attempt: 1, maxAttempts: 1, enqueuedAt: Date.now(), traceId: options.traceId ?? options.id,
    payload: { taskId, executionId: options.executionId, integrationId: options.integrationId },
    headers: { handoffQueue: options.queueName ?? XPERT_HANDOFF_QUEUE, requestedLane: options.requestedLane ?? 'main' }
}, { timeoutMs: options.timeoutMs })
assertLocalTaskResult(options.id, result)   // dead → 抛 reason；retry → 抛 unexpected retry result
```
- 语义：`maxAttempts: 1` 表示这条本地桥接消息不重试；失败分支 `remove(taskId)` 清理悬挂闭包；跨实例部署时这条调用只会等到超时。

### 例 2 · 取消一批消息（协作式、不进死信）
```ts
// packages/server-ai/src/handoff/agent-chat-realtime.service.ts（节选，逐字）
void this.commandBus.execute(new StopHandoffMessageCommand({ messageIds: [runId], reason: 'SSE client disconnected' }
))
```
```ts
// 会话侧（CancelConversationHandler）与语音侧（voice-task.service.ts）的一致用法
await commandBus.execute(new StopHandoffMessageCommand({ executionIds, reason: 'Canceled by user' }))
await commands.execute(new StopHandoffMessageCommand({ messageIds: [task.id], reason: 'voice_user_cancel' }))
```
- 语义：`waiting`/`delayed`/`paused` 立即移除；`active` 仅尽力 abort；返回值是**摘要**（`requested/matched/removed/aborted/notFound`），调用方需据此决定后续动作。

### 例 3 · 运行时投递一条结果（与 Invocation CAS 同事务）
```ts
// packages/server-ai/src/agent-invocation/typeorm-invocation.store.ts（replace 事务内，节选，逐字）
const manager = ...                                  // CAS 事务管理器
await manager.getRepository(AgentInvocationEventEntity).createQueryBuilder()
    .insert().values({ /* observation 行 */ }).execute()
await appendRuntimeDelivery(manager, invocation)     // 与 observation 同事务；orIgnore 幂等
// Completion and its durable wake-up are committed together. Polling repairs missed notifications.
```

- 语义：事件只能从 Invocation 事实派生（终态 `result`、`waiting`+interaction `input_request`）；`messageId` 稳定为 `runtime-{invocationId}-{kind}-{revision}`；`progress` 不唤醒父级。

```ts

const owner = this.owner()
return this.access.withReply(id, owner, async () => {
    await this.dataSource.transaction((manager) => resetRuntimeDelivery(manager, id, owner))
    return this.inspect(id)          // 复位后立刻回读 owner 作用域回执
})
// 等价命令入口（项目侧使用）：packages/server-ai/src/xpert-project/runtime/project-task-runtime-read.service.ts
```
