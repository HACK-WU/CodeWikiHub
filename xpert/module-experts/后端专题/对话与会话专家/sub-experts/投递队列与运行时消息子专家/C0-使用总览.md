## 0. 契约自足声明

本文是该子专家的对外使用契约，不依赖阅读实现层即可决定：**何时找它、能得到哪些能力、调哪个入口、边界在哪、有哪些已知坑**。算法、私有方法与数据结构细节一律不在本文展开，只给契约级语义与实现层索引。

## 1. 定位

本子域是「会话 / 群聊 / 执行」三条链共享的**异步投递与运行时回执底座**：它把「已决定要执行的工作」变成可在多副本下安全投递、可重试、可取消、可观测的队列消息（4 个 Bull 队列与 4 个消费者、路由解析、批量入队、扫描式取消、重试耗尽落死信），并在运行时侧维护 `agent_runtime_delivery`（outbox）→ 队列 → `agent_runtime_inbox`（inbox）→ 续跑 / 观测的持久闭环。

## 2. 何时找它

- 需要把一条业务意图**异步交给运行时**执行，且不想自己实现重试、并发与队列：找 `HandoffQueueService.enqueue`。
- 需要一次投递的**最终结果回传**给调用方：找 `enqueueAndWait`（注意「仅本进程」限制）。
- 需要**把不同消息类型 / 租户 / 来源分流到不同队列**，或需要覆盖默认路由：找 `HandoffRouteResolver.resolve` 与 YAML 路由配置。
- 需要**批量投递**（如一次回投多条 `outbound`）：找 `enqueueMany`。
- 需要**取消**已入队 / 正在执行的投递：找 `StopHandoffMessageCommand`（入参 `messageIds` / `executionIds`）。
- 需要排查「运行时结果为什么没回到会话」：先读 owner 级回执 `GET /api/agent-invocations/:id/delivery`。
- 需要**人工重驱一次阻塞 / 失败的传输**：找 `POST /api/agent-invocations/:id/delivery/redrive`（body 必须为 `{}`）。
- 需要「结果自动回到原授权会话」的**可靠回复链**：delivery → transport → inbox → continuation 四段。
- 需要判断**哪些状态会阻断自动续跑**（`paused`/`interrupted`/审批/显式用户 stop）：找 `runtimeReplyBlocked` 语义。
- 需要**观测**长时间运行的 Invocation（只观察、绝不启动），或需要给插件暴露入队能力（`HANDOFF_QUEUE_SERVICE_TOKEN`）。

## 4. 能力清单表

| # | 能力 | 主要入口 | 契约语义 |
|---|---|---|---|
| 1 | 单条入队 | `HandoffQueueService.enqueue` | 补全 `id/version/attempt/maxAttempts/enqueuedAt` 并写回路由头后入队；返回 `{ id }`，不等待 |
| 2 | 批量入队 | `HandoffQueueService.enqueueMany` | 逐条解析 + 串行入队；不做去重与聚合；返回 id 列表 |
| 3 | 入队并等待 | `HandoffQueueService.enqueueAndWait` | 返回 `ProcessResult`（`ok`/`retry`/`dead`）；**仅本进程回调**、best-effort |
| 4 | 路由解析与配置 | `HandoffRouteResolver.resolve`、`HandoffRoutingConfigService` | header > typePolicy > 匹配规则 > default；配置为启动期 YAML 快照 |
| 5 | 4 个队列消费者 | `HandoffQueueProcessor` / `Realtime` / `Batch` / `Integration` | 4 个 `dispatch` 消费者共用 `BaseHandoffQueueProcessor`，只区分队列与并发 |
| 6 | 分发与超时归一 | `MessageDispatcherService.dispatch` | 按 `type + organizationId` 取处理器，注册 `AbortController`，总超时 / 空闲超时，结果归一 `ok`/`retry`/`dead` |
| 7 | 取消 | `StopHandoffMessageCommand` → `StopHandoffMessageHandler` | 扫描 4 队列的 `waiting`/`delayed`/`paused`/`active`；队列 job 移除 + `active` abort（Redis `ai:handoff:cancel`） |
| 8 | 死信记录 | `HandoffDeadService.record` | 仅 `logger.error`：**无台账表、无查询接口** |
| 9 | 运行时投递（outbox） | `appendRuntimeDelivery(manager, invocation)` | 与 Invocation CAS **同事务**、`orIgnore` 幂等写入 `agent_runtime_delivery` |
| 10 | transport 派发 | `RuntimeMessageTransportService.reconcile/deliver` | `@Interval(5000)` 扫描 due 行，60s 租约 claim，重授权后 enqueue（enqueue 不是回执） |
| 11 | inbox 认领 | `RuntimeMessageInboxService.receive/lockInbox/claimWait` | 收据与回执同事务；消费键唯一；`wait` 与 `follow_up` 争同一行 |
| 12 | 续跑 | `RuntimeMessageContinuationService.reconcile/consume` | `reserve → started → run → recover`；阻断态不自动续跑 |
| 13 | 观测 | `RuntimeObservationMonitorService.reconcile` | 独立租约观察既有 Invocation 句柄，**只观察不启动** |
| 14 | 投递回执与重驱 | `RuntimeDeliveryController.inspect/redrive` | owner 作用域回执；redrive 只重排 `blocked`/`failed` 传输 |

## 5. 边界（做什么 / 不做什么 / 适配器在哪）

**本子域拥有**：4 个队列与 4 个消费者的注册与执行、路由解析与路由 YAML 快照、入队三入口、取消与死信记录、`agent_runtime_delivery` / `agent_runtime_inbox` 实体与服务、transport / continuation / observation 三个扫描器，以及 `StopHandoffMessageCommand` 与 `RequestRuntimeResultCheckCommand` 两条命令。

**不做什么**：不注册第二个执行器；不执行模型/CLI；不拥有 Invocation 事实与业务决策（Task 归属与验收在其他域）；不保存结果正文（事件只含引用）；不做恰一次投递；不做 SSE 扇出（`agent-chat-realtime` 只是本域的实时订阅器）。

| 相邻方 | 关系与边界 |
|---|---|
| 群聊 `GroupOutboxService`（`chat-group/group-outbox.service.ts`） | **相邻生产者**：把收据改写为 `agent.chat.dispatch` 后复用本域队列，并通过 `HandoffOutboxAdapters.register` 挂在本域扫描器上；收据账本与成员可见性归群聊子专家 |
| `agent-invocation` + `delivery` HTTP 适配器 | `RuntimeDeliveryController` **物理注册在** `agent-invocation.module.ts` 的 `controllers` 中（按目录归属执行链域）；inbox / delivery 实体与服务仍在本子域源码树——审计与装配需同时看两处 |
| 会话逻辑（`chat-conversation`） | `CancelConversationHandler` 先取消执行、再 **best-effort** 执行 `StopHandoffMessageCommand`（失败仅 warning、不阻断）；续跑侧使用 `lockRuntimeThread`、`ChatCommonCommand` / `XpertChatCommand` 开新一轮 `send` |
| 下游续跑消费者 | `ProjectTaskDispatchRecoveryService`、`DeliverGroupTaskResultCommand` 是续跑链下游，归属各自专家域（避免双计） |

## 6. 已知问题与常见坑（14 条）

1. **`enqueueAndWait` 仅在同一个进程内回调（best-effort）**：worker 或 waiter 分布在不同实例时回调永不到达，调用方只会等到 `XPERT_HANDOFF_PENDING_TIMEOUT_MS`（默认 2 分钟）；跨实例必须改用状态查询 / 轮询。
2. **取消是协作式的（`AbortSignal`）且是扫描式**：不强杀同步 CPU 密集代码；`waiting`/`delayed`/`paused` 直接移除 Bull job，`active` 只尽力 abort，「扫描 → abort」之间已完成的作业可能正常结束。
3. **`dead(canceled:...)` 不进死信、不重试，可能掩盖真实失败**：`isAbortLikeError` 会把任何含 abort/cancel 字样的异常归入取消流；取消成功 ≠ 作业已停止，失败可见性依赖日志与回执。
4. **`consumer_outcome_unknown` 不得自动重放**：结果模糊时只能按回执检查**同一执行身份**（claim 中记录的 executionId），再人工 redrive；传输重试与 redrive 都不重启 CLI、不分配替代消费者。
5. **Redrive never changes an Invocation or clears a user stop**（源注释原文）：redrive 只重排 `blocked`/`failed` 传输，保留 claim、`phase` 与用户 stop 屏障；显式 stop 场景应在手工轮次读取结果，而不是绕过 stop。
6. **不从传输成功推断 Task 完成**：入队 / ack / SSE 收流都不是回执；本域不注册第二个执行器，Task 投影只把「实际开始」映 `in_progress`、成功映 `review`、失败映 `blocked`。
7. **outbox 写入必须与 Invocation CAS 同事务**：否则队列 / Redis 抖动会发生在两次写之间，已提交结果永久丢失且无重试入口（`appendRuntimeDelivery` 的 `orIgnore` 幂等只兜重复，不兜漏写）。
8. **本域不是 exactly-once**：只提供**可重试投递 + 幂等消费**；轮询是持久恢复机制，本地事件与队列投递只是加速。
9. **lost ack 会重发同一通知**：`enqueue` 成功只把 `nextAttemptAt` 推后 30s，同一 `messageId` 会被再次投递，直到 inbox 提交 `received`——消费端必须靠唯一键 + `orIgnore()` 幂等。
10. **`reserved` 可复用同一 execution ID，`started` 之后只查该执行**：已知终态只修复剩余 writer claim，模糊结果置 `blocked(consumer_outcome_unknown)`；不要期待系统自动换一个执行身份重跑。
11. **多副本：租约到期会把「持有租约的未收尾 run」标错**（并把执行/消息状态一并中断）；续约失败只 warn；**无租约的旧 run 不按时长猜死**，只能显式 stop。
12. **滚动升级必须「先部署消费者、再部署生产者」**：新版生产者先写新事件字段会造成「事件已提交但无人能消费」的窗口；迁移为加性、可重复执行，需按固定顺序先应用。
13. **队列并发与 `maxAttempts` 是运维参数**：Bull `add` 固定 `{ removeOnComplete: true, removeOnFail: false }`，**未配置 Bull 级 attempts/backoff**，重试完全由应用层 `message.attempt` + 新 job 承担；并发 env 在模块加载时读取，需重启生效，且应按副本数折算单副本容量。
14. **死信无台账、退避与租约是代码常量**：进入死信只有三路径（重试耗尽 / `dead` 非 `canceled:` / 永久错误），只能靠日志检索；60s 租约、15s/20s 续约、30s 节流、`min(300s, 5s*2^n)`、`attempts>=19` 均不可用环境变量调整；路由 YAML 也只在 `onModuleInit` 读一次。
