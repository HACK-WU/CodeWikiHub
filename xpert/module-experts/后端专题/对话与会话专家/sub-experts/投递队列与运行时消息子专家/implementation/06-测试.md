## 逐文件覆盖点
### 纯单元：归一、路由头与超时
- `cancel-reason.spec.ts`：`buildCanceledReason` 带前缀与默认文案、`isCanceledReason` 前缀判定（`dead:` 不算）、`isAbortLikeError` 对 `This operation was aborted`/`request canceled` 为真、对 `boom` 为假。
- `message-queue.service.spec.ts`：路由头写入（缺省时补 `requestedLane`/`handoffQueue`/`policyTimeoutMs`/`policyIdleTimeoutMs`）与显式头不被覆盖。
- `handoff-routing-config.service.spec.ts`：`typePolicies`/`routes[].target` 的 idleTimeout 解析、header 优先级高于 typePolicy、typePolicy 优先于命中 route、无 typePolicy 时回落到 route target。

章节来源：[cancel-reason.spec.ts](file://packages/server-ai/src/handoff/cancel-reason.spec.ts)、[message-queue.service.spec.ts](file://packages/server-ai/src/handoff/message-queue.service.spec.ts)（关键符号：HandoffQueueService.enqueue）、[handoff-routing-config.service.spec.ts](file://packages/server-ai/src/handoff/dispatcher/handoff-routing-config.service.spec.ts)（关键符号：HandoffRoutingConfigService.onModuleInit）

### 处理器、分发器与死信/取消归一
- `message-queue.processor.spec.ts`：`dead(canceled:...)` 不写死信但仍 resolve 给等待者；`abort` 异常被映射为 `canceled:` 且不重试不入死信；`retry` 在同租户作用域内重新入队（`attempt: 2`、`delayMs` 透传，且处理器与入队两处 `RequestContext` 作用域都被断言）。
- `message-dispatcher.service.spec.ts`：事件转发、按消息 tenant 解析处理器、abort → `dead(canceled:...)`、`policyTimeoutMs` 超时 abort、`policyIdleTimeoutMs` 无心跳时 abort、`heartbeat()` 重置空闲计时、手工取消原因优先于超时原因。

章节来源：[message-queue.processor.spec.ts](file://packages/server-ai/src/handoff/message-queue.processor.spec.ts)（关键符号：HandoffQueueProcessor.process）、[message-dispatcher.service.spec.ts](file://packages/server-ai/src/handoff/message-dispatcher.service.spec.ts)（关键符号：MessageDispatcherService.dispatch）

### 取消链、适配器注册表与实时流
- `stop-handoff-message.handler.spec.ts`：按 messageId/executionId 同时命中 queued 与 active；queued 走 `removeJobs` 且清理本地 task；active 交给 `cancelMessages`；所有 matched 都被 `pendingResults.cancel('canceled:...')`；返回摘要含 `requested/matched/removed/aborted/notFound`。
- `outbox-adapters.service.spec.ts`：同步与异步适配器失败被隔离、dispose 后不再调用；共享扫描不重入（第二次 `reconcile` 不触发查询）、适配器异常后扫描仍可恢复。
- `agent-chat-realtime.service.spec.ts`：先订阅再入队、跨实例 pubsub 载荷转发、error 事件后完成、未订阅完成前取消 handoff 消息、中断信号先于结束、客户端在中断事件上断开不取消后台 job、关机与 Redis 连接竞争时不入队。

章节来源：[stop-handoff-message.handler.spec.ts](file://packages/server-ai/src/handoff/commands/handlers/stop-handoff-message.handler.spec.ts)（关键符号：StopHandoffMessageHandler.execute）、[outbox-adapters.service.spec.ts](file://packages/server-ai/src/handoff/outbox-adapters.service.spec.ts)（关键符号：HandoffOutboxAdapters.reconcile）、[agent-chat-realtime.service.spec.ts](file://packages/server-ai/src/handoff/agent-chat-realtime.service.spec.ts)（关键符号：AgentChatRealtimeService.publish）

### 运行时边界：授权、HTTP 与处理器
- `runtime-message-access.service.spec.ts`：群发起人授权独立于运行时会话创建者、恢复真实作用域 actor 并重载已授权 Invocation、成员关系被撤销在 inspect 前即拒绝、owner/回复 agent/父执行不匹配即拒绝、回复到未注册分支即拒绝。
- `runtime-delivery.controller.spec.ts`：`GET :id/delivery` 返回 owner 作用域回执且不触发运行时（`withReceiptOwner` 被调、`withReply` 未被调）；非法 UUID 在授权前 400；redrive body 含身份/路由字段 400 且不写库；合法红色重驱经 `withReply` 并只把 `state` 复位为 `pending`；未授权 redrive 403 且不修改传输。
- `agent-chat-dispatch.processor.spec.ts`：2 个 describe（`AgentChatDispatchHandoffProcessor` 与 `AgentChatCallbackNoopHandoffProcessor`），覆盖必填载荷缺失即 dead、assistant runtime principal 以目标 xpert 技术用户执行、principal 与 dispatch xpert 不一致时拒绝、legacy header userId 兼容、流事件转回调且 sequence 递增、回调/redis 两条路径的心跳、error 回调、abort 回调携带 dispatcher 原因、命令失败时按发布通道回错、`steer_target_not_running` 机器可读错误码透传。

章节来源：[runtime-message-access.service.spec.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-access.service.spec.ts)（关键符号：RuntimeMessageAccessService.withReply）、[runtime-delivery.controller.spec.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-delivery.controller.spec.ts)（关键符号：RuntimeDeliveryController.inspect / redrive）、[agent-chat-dispatch.processor.spec.ts](file://packages/server-ai/src/handoff/plugins/agent-chat/agent-chat-dispatch.processor.spec.ts)（关键符号：AgentChatDispatchHandoffProcessor）

## 运行命令
Jest 配置位于 `packages/server-ai/jest.config.ts`（`preset: '../../jest.preset.js'`，ts-jest + babel-jest，`moduleNameMapper` 把 `@xpert-ai/*` 指到源码目录），因此可直接用 jest 指定配置与路径运行；仓库根未提供通用 `test` 脚本，`nx.json` 仅为 jest executor 提供缓存配置。
```bash
# 仅本子域（不含真库/真 Redis 用例）
npx jest --config packages/server-ai/jest.config.ts packages/server-ai/src/handoff

# 单个文件
npx jest --config packages/server-ai/jest.config.ts --runTestsByPath \
  packages/server-ai/src/handoff/runtime-messaging/runtime-delivery.controller.spec.ts

# 恢复验收子进程所使用的最小命令形（由父用例自行 spawn）
npx jest --config packages/server-ai/jest.config.ts --runInBand --runTestsByPath \
  packages/server-ai/src/handoff/runtime-messaging/testing/queue-recovery.worker.spec.ts
```
注意 `queue-recovery.worker.spec.ts` 设计为**只能作为子进程**运行（文件头注释：父进程拥有可丢弃的数据库与 Redis，SIGKILL 会跳过清理），单独运行会因缺少 `XPERT_RECOVERY_CHILD` 而整体 skip。

章节来源：[jest.config.ts](file://packages/server-ai/jest.config.ts)（关键符号：displayName / moduleNameMapper）、[queue-recovery.worker.spec.ts](file://packages/server-ai/src/handoff/runtime-messaging/testing/queue-recovery.worker.spec.ts)（关键符号：XPERT_RECOVERY_CHILD / configSchema）

## 需 Redis / PostgreSQL 的用例
**需要 Bull + Redis 的 e2e**：`enqueue-agent-chat-message.handler.e2e.spec.ts` 通过 `describeWithRedis` 受 `REDIS_HOST` 控制；用真实 `BullModule.forRoot`（默认 `localhost`/`6379`/`db=15`）注册 `HandoffQueueModule`，并强制 `HANDOFF_ROUTING_CONFIG_PATH` 指向 `docker/handoff-routing.example.yaml`，同时用测试注册表替换 `HandoffProcessorRegistry`。
**需要真实 PostgreSQL + Redis 的恢复验收**：`queue-recovery.cases.ts`（`queue-recoveryCases`，由 `reliable-return.cases.ts` 引入）要求库名前缀 `xpert_execution_test_` 与 `127.0.0.1` 的 Redis，且容器标签必须为 `runtime-recovery`（否则拒绝重启「无关 Redis」）。它依次跑 `persist`→`send`→`receive-crash`→`receive`→`consume-crash`→`consume` 六个阶段，其中三次 SIGKILL 分别落在「Invocation/outbox 事务提交后」「inbox 事务提交后、Bull 确认前」「consumer 结果提交后、continuation 收尾前」；期间真实重启 Redis 并**等待真实租约过期**（不修改存储 claim 或时钟），最终断言：inbox 仅 1 行、`claim` 不变、线程下 execution 数为 2、CLI `start` 只被调用 1 次、队列 `waiting/active/failed` 均为 0。
**需要真实 PostgreSQL 的跨域集成**：`project-task-dispatch.integration.spec.ts`（`XPERT_EXECUTION_TEST_DATABASE_URL` 控制，同样要求库名前缀 `xpert_execution_test_`）为每次运行创建隔离 schema `task_dispatch_<uuid>`（`CREATE SCHEMA` + `search_path=<schema>,public`，结束时 `DROP SCHEMA ... CASCADE`），并执行 `reliable-return.cases.ts` 中的 27 个用例（含「busy 线程先 pending 后消费」「paused/pausing/interrupted 阻断」「用户 stop 后旧回复仍被阻断」「模糊结果只观察同一执行且永不再次启动」「红色重驱后复用身份」等）。
官方对边界的说明：这些 DB 测试使用真实 PostgreSQL/TypeORM + 隔离 schema + 受控适配器，**不构成 live Redis、部署平台、真实模型或 Computer CLI 的验收测试**；进程/队列级验收需另跑 `node tools/scripts/verify-runtime-recovery.mjs`。

章节来源：[enqueue-agent-chat-message.handler.e2e.spec.ts](file://packages/server-ai/src/handoff/commands/handlers/enqueue-agent-chat-message.handler.e2e.spec.ts)（关键符号：describeWithRedis / fallbackHandoffRoutingPath）、[queue-recovery.cases.ts](file://packages/server-ai/src/handoff/runtime-messaging/testing/queue-recovery.cases.ts)（关键符号：queueRecoveryCases）、[project-task-dispatch.integration.spec.ts](file://packages/server-ai/src/xpert-project/runtime/project-task-dispatch.integration.spec.ts)（关键符号：integration / CREATE SCHEMA）、[runtime-messaging/README.md](file://packages/server-ai/src/handoff/runtime-messaging/README.md)（关键符号：Validation）

## 覆盖缺口
1. **取消是扫描式的、竞态用例缺失**：README 明写「扫描与 abort 之间完成的作业可能正常结束」，但本子域 13 个 spec 中没有任何用例构造「job 在 `findJobs` 之后、`cancelMessages` 之前完成」的时序；`HandoffCancelService` 本身也无 spec（红灯只会出现在 `AgentChatRealtimeService`、`StopHandoffMessageHandler` 的 mock 断言上）。
2. **`consumer_outcome_unknown` 只有真库覆盖，无本子域 spec**：该路径由 `reliable-return.cases.ts`（经 xpert-project 集成 spec、需 `XPERT_EXECUTION_TEST_DATABASE_URL`）断言，日常 CI 若未配置真库即完全不执行；`runtime-message-continuation.service.ts`、`runtime-message-transport.service.ts`、`runtime-message-inbox.service.ts` 三个核心服务在 `handoff/` 目录内**没有自己的 `.spec.ts`**。
3. **死信与 redrive 的队列面未覆盖**：`HandoffDeadService`（仅日志）无断言；`resetRuntimeDelivery` 只被 HTTP 边界 spec 以 mock manager 验证「调用了一次 update」，其 SQL 谓词（只复位 `blocked/failed`、inbox 仅 `kind='result'`）没有真库断言。
4. **`claimWait` 的竞争路径无本子域用例**：只有真库用例覆盖「wait 与 follow-up 竞争同一 claim」「当前轮次认领、普通 inspect 只读」。
5. **升级/迁移验证**：README 称「迁移可重复应用」由真库用例覆盖，但断言的执行体在 `xpert-project` 侧；`handoff/runtime-messaging/migrations/20261006-runtime-reliable-replies.sql` 本身没有被本子域 spec 直接驱动。
6. **观测监控无 spec**：`RuntimeObservationMonitorService` 的租约、`nextObservationAt` 排程（终态 `null`、`unknown` 60s、异常退避）只在真库用例中被间接断言。

## 结论
测试策略是典型的「三层分离」：13 个 `handoff/**` spec 覆盖纯逻辑与边界（归一、路由优先级、超时/取消归一、取消摘要、适配器隔离、HTTP 校验与 redrive 语义），1 个 e2e 覆盖真实 Bull 入队/等待往返，2 个真库用例集覆盖持久化不变量与进程级恢复。空白同样明确：**取消竞态、inbox/continuation/transport 自身的单元测试、死信与 redrive 的 SQL 级断言**都缺少本目录内的独立 spec，关键回归保护依赖可选的真库/真 Redis 路径，日常 CI 若不配置 `XPERT_EXECUTION_TEST_DATABASE_URL` 与 `REDIS_HOST`，这部分能力不会被验证。
