## 入队与路由
`HandoffQueueService.enqueue`（`@RequirePermissionOperation('handoff','enqueue')`）先 `resolve` 再 `normalize`（补 `id`/`version=1`/`attempt≥1`/`maxAttempts`（消息值 → `typePolicy.retry.maxAttempts` → 3）/`enqueuedAt`），然后经 `withRouteHeaders` 写回 `requestedLane`/`handoffQueue` 与 `policyTimeoutMs`/`policyIdleTimeoutMs`（已存在则不覆盖），最后走网关。`enqueueMany` 无权限装饰器，仅批量 `toQueueEnqueueItem` + `enqueueMany`；`enqueueAndWait` 带 `'handoff','wait'`。
`HandoffRouteResolver.resolve` 是纯函数式解析：队列 = header `handoffQueue`（`queue` 作兜底）经别名表 > `typePolicies[type].queue` > 首个命中 `routes[].match` 的 `target.queue` > `defaultQueue`；lane 同级为 header `requestedLane` > typePolicy.lane > route.target.lane > `defaultLane`；timeout/idle 也允许 header 覆盖。匹配条件为 `type`/`typePrefix`/`tenantId`/`organizationId`（读 `headers.organizationId`）/`source`（读 `headers.source`）。
`HandoffRoutingConfigService` 在 `onModuleInit` 通过 `HANDOFF_ROUTING_CONFIG_PATH` 加载 YAML 并归一为快照（别名表把 `handoff/default/realtime/batch/integration` 映射到真实队列名；lane 别名含 `high→main`、`low→cron`）；未设置路径时只 warn 并使用内置默认。

## 四个处理器与消息分发
`HandoffQueueProcessor`、`HandoffQueueRealtimeProcessor`、`HandoffQueueBatchProcessor`、`HandoffQueueIntegrationProcessor` 共用 `@Process({ name: 'dispatch', concurrency })`，分工仅是队列与并发来源不同（基座 `XPERT_HANDOFF_DISPATCHER_CONCURRENCY` 默认 20，实时/批处理/集成分别由 `XPERT_HANDOFF_CONCURRENCY_*` 覆盖），执行路径完全一致。
`MessageDispatcherService.dispatch` 先 `assertMessage`（要求 `id`/`type`/`tenantId`/`sessionKey`/`traceId`/`businessKey`），再从 `HandoffProcessorRegistry.get(type, organizationId)` 取策略；执行前注册 `AbortController`（`runId = message.id`）、起总超时与空闲超时定时器（`heartbeat()` 重置空闲计时），`finally` 里清定时器并注销。abort 或 abort-like 异常统一返回 `dead` 且 reason 为 `canceled:...`（优先取 `HandoffCancelService` 记录的取消原因）。
`handleResult` 分流：`ok` → 若有 `outbound` 则 `enqueueMany` 并 `pendingResults.resolve`；`retry` → `attempt+1` 未超 `maxAttempts` 则带 `delayMs` 重入队，否则记死信并 resolve 为 `dead`；`dead` → 非 `canceled:` 才记死信。`handleError` 分流：canceled/abort-like 一律 resolve 为 `dead(canceled:...)` 且不重试；永久错误（`No handoff processor found`/`Invalid handoff message:`/`Handoff message id is required`）直接死信；其余按 `attempt+1` 重试，耗尽后死信 + reject。

章节来源：[message-queue.processor.ts](file://packages/server-ai/src/handoff/message-queue.processor.ts)（关键符号：BaseHandoffQueueProcessor.handleResult / handleError / isPermanentError）、[message-dispatcher.service.ts](file://packages/server-ai/src/handoff/message-dispatcher.service.ts)（关键符号：MessageDispatcherService.dispatchWithContext / startTimeoutTimers / assertMessage）

## enqueueAndWait 的本进程语义
`enqueueAndWait` 先 `pendingResults.waitFor(id, { timeoutMs, onEvent })`（默认上限 `XPERT_HANDOFF_PENDING_TIMEOUT_MS` = 2 分钟），再入队；入队抛错时 `pendingResults.reject` 并向上抛。等待值随后由消费端 `handleResult`/`handleError` 的 `resolve`/`reject` 兑现，处理器事件经 `emit` → `pendingResults.publish` 回调给 `onEvent`。
源码注释明写这是 **best-effort 且仅进程内**：worker 或 waiter 在另一实例时回调不会到达。`HandoffPendingResultService` 是内存 `Map`，对同一 id 重复 `waitFor` 直接抛错，settle 后删除条目；`clearAll` 可在停机时统一取消。`EnqueueAgentChatMessageHandler` 是典型用法：它先 `LocalQueueTaskService.register` 注册本地闭包，把 `taskId` 放进 payload，再 `enqueueAndWait`，`maxAttempts: 1`，失败时 `remove(taskId)` 清理悬挂任务。

章节来源：[message-queue.service.ts](file://packages/server-ai/src/handoff/message-queue.service.ts)（关键符号：HandoffQueueService.enqueueAndWait）、[pending-result.service.ts](file://packages/server-ai/src/handoff/pending-result.service.ts)（关键符号：HandoffPendingResultService.waitFor / publish / clearAll）、[enqueue-agent-chat-message.handler.ts](file://packages/server-ai/src/handoff/commands/handlers/enqueue-agent-chat-message.handler.ts)（关键符号：EnqueueAgentChatMessageHandler.execute / assertLocalTaskResult）

## 取消链
`StopHandoffMessageHandler.execute` 以 `messageIds` 与/或 `executionIds`（后者匹配 `payload.executionId`）为口径，调用 `HandoffQueueGatewayService.findJobs` 扫描全部 4 个队列的 `waiting`/`delayed`/`paused`/`active`（`DEFAULT_SCAN_STATES`）；`waiting`/`delayed`/`paused` 走 `removeJobs`（逐个 `job.remove()`，失败仅 warn），命中 `payload.taskId` 的额外 `LocalQueueTaskService.remove`；`active` 命中集合交给 `HandoffCancelService.cancelMessages(ids, reason)`；最后对所有 matched messageIds 调 `pendingResults.cancel(id, 'canceled:...')`，返回结构化摘要 `requested/matched/removed/aborted/notFound`。
`HandoffCancelService` 维护 `messageId → AbortController` 与 `messageId → cancelReason` 两个进程内 Map：`cancelMessages` 先 publish 到 Redis 频道 `ai:handoff:cancel`（payload 为 messageIds + reason），再在本进程 `applyCancel`（记录 reason → `AbortController.abort()` → 注销）。消费端 `MessageDispatcherService` 把 abort 归一为 `dead(canceled:...)`，处理器据此**跳过死信、跳过重试**；`cancel-reason.ts` 的 `buildCanceledReason`/`isCanceledReason`/`isAbortLikeError` 保证 dispatcher、处理器、命令处理器三处分类一致。

## 死信与 redrive
`HandoffDeadService.record` 目前只做 `logger.error('Dead letter: type=..., id=..., traceId=..., reason=...')`，源码注释说明 v1 仅记录日志、后续才可能接数据库表或外部告警——**死信没有台账表**。进入死信只有三条路径：`retry` 超 `maxAttempts`、`dead` 且非 `canceled:`、非永久/永久错误在 `handleError` 中的判定。
运行时侧的红驱是另一条链：`RuntimeDeliveryController` 暴露 `GET agent-invocations/:id/delivery`（owner 作用域回执：delivery 与 consumption 的 messageId/event/state/attempts/lastError/nextAttemptAt、inbox 的 phase/claim）与 `POST agent-invocations/:id/delivery/redrive`（body 为 `.strict({})`），后者经 `RuntimeMessageAccessService.withReply` 重授权后在事务内执行 `resetRuntimeDelivery`：只把 `blocked|failed` 的 delivery 复位为 `pending/attempts=0`，把 `blocked|failed` 且 `event->>'kind'='result'` 的 inbox 复位为 `pending/attempts=0`；`RequestRuntimeResultCheckCommand` 是同一逻辑的命令入口。控制器本身**物理注册在 `agent-invocation.module.ts` 的 controllers 中**。

## 运行时 outbox 与 Invocation CAS 同事务
`runtimeObservationEvent(invocation)` 只从 Invocation 事实派生事件：终态（`isAgentInvocationTerminal`）出 `result`（带 `status`），`status==='waiting'` 且有 `interaction` 出 `input_request`（带 `interactionId`），其余（含 progress）返回 `undefined`；引用块带 `invocationId`/`revision`，有 `projectTask` 时附带 project/task/attempt 标识。
`appendRuntimeDelivery(manager, invocation)` 用 `manager.getRepository(AgentRuntimeDelivery)` 原生 insert + `.orIgnore()`，`messageId` 由 `agentRuntimeEventMessageId(event)`（`runtime-{invocationId}-{kind}-{revision}`）派生，初值 `state='pending'`、`nextAttemptAt=now()`。其函数上方注释即架构承诺：「必须与 Invocation CAS 事务共享：队列故障不得丢弃已提交结果」；调用点位于 `TypeOrmAgentInvocationStore.replace`，与 observation 事件插入及 wait 表唤醒同一事务。

## transport 的租约与 enqueue
`RuntimeMessageTransportService.reconcile` 由 `@Interval(5000)` 驱动，用进程内 `scanning` 标志防本进程重入，取 `state='pending' AND nextAttemptAt <= now()` 的前 20 条按 `nextAttemptAt ASC` 并发 `Promise.allSettled(deliver)`，并在 `finally` 里串行调用 `HandoffOutboxAdapters.reconcile()`（`Promise.allSettled` 隔离各适配器失败）。
`deliver` 先做 UPDATE-claim：`set({ leaseToken, leaseUntil: now+60s, attempts: attempts+1 }) WHERE id AND state='pending' AND (leaseUntil IS NULL OR leaseUntil < now())`，`affected=0` 直接返回。成功后解析 `agentRuntimeEventSchema`，经 `access.withReply` 重授权后在回调里构造 `HandoffMessage`（`id=row.messageId`、`type=AGENT_RUNTIME_EVENT_MESSAGE_TYPE`、`sessionKey=replyTo.threadId`、`businessKey=invocationId`、`maxAttempts: 5`、headers 带 organizationId/userId/conversationId/threadId）并 `queue.enqueue`；随后把 `nextAttemptAt` 推后 30 秒（注释：**enqueue 不是回执确认，直到 inbox 提交 received 前都重发同一 id**）。失败时按 `isRuntimeMessageBlocked` 判 `blocked`（`access_or_target_changed`）或 `attempts>=19 ? failed : pending`（`transport_unavailable`），退避 `min(300s, 5s * 2^min(attempts,6))`；`finally` 清空该 leaseToken 的租约列。

章节来源：[runtime-message-transport.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-transport.service.ts)（关键符号：RuntimeMessageTransportService.reconcile / deliver）、[runtime-message-access.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-access.service.ts)（关键符号：RuntimeMessageAccessService.withReply）、[outbox-adapters.service.ts](file://packages/server-ai/src/handoff/outbox-adapters.service.ts)（关键符号：HandoffOutboxAdapters.register / reconcile）

## inbox 认领
`RuntimeMessageInboxService.receive` 的校验顺序是：必需 header（tenantId/organizationId/userId）→ `agentRuntimeEventSchema.safeParse(payload)` → 按 `messageId + tenant/organization/owner` 找 delivery 且 `sameInvocationData(delivery.event, event)` 且 `message.id === agentRuntimeEventMessageId(event)` → `access.withReply(event.invocationId, delivery, ...)` 内再比对 `sessionKey`/`headers.conversationId`/`headers.threadId` 与 `dispatch.replyTo` 一致。通过后在**同一事务**内 `lockInbox`、`result` 事件把同 scope 下 `kind='input_request'` 的既有行标 `processed/superseded`、把 delivery 置 `received`（清租约与 lastError）。
`lockInbox` 用 `orIgnore()` 按唯一键 `(tenantId, organizationId, ownerId, consumptionKey)` 插入，随后 `pessimistic_write` 读回：`consumptionKey = agentRuntimeResultConsumptionKey(invocationId, replyTo)`，`input_request` 追加 `:input:{interactionId}`（输入请求有独立回执，不与最终结果竞争）；插入初值 `result → pending`、`input_request 且已不 waiting/不匹配 → processed(superseded)`、否则 `blocked(awaiting_input)`。
`claimWait` 面向有界等待：逐 invocation `withReply` 校验 `sameInvocationData(original + parentExecutionId, scope)`，要求 consumer 执行仍在 `RUNNING` 且 threadId/agentKey/createdById 匹配，随后同事务 `lockInbox` 并写 `state='processed'` + `claim`（`consumer.type='wait'`）；已有 claim 且不一致则抛 `Consumed`。

## 续跑与观测
`RuntimeMessageContinuationService.reconcile`（`@Interval(3000)`、take 8、`state IN (pending, processing)`）→ `consume`：lease claim（60s）+ 每 15s 心跳续租 → `access.withReply` → `reserve` → 分流。`reserve` 在事务内悲观锁 inbox、校验事件与 Invocation（`status` 与 `revision` 不得超前）、校验既有 claim 一致性；`group_assistant_runtime` 会话只预留 claim（成员准入归群队列）且 `phase` 保持 `reserved`；普通会话先 `lockRuntimeThread` 再判 `runtimeReplyBlocked`（`user_stopped` = 线程 `runtimeContinuationBlockedAt` 不早于调用创建时间；`awaiting_user` = `paused/pausing/interrupted`、存在 `operation` 或 `runControl.state==='paused'`），busy 线程写 `thread_busy` 并 5 秒后重试；通过后以 `previous.consumer.executionId ?? randomUUID()` `orIgnore` 插入 `XpertAgentExecution`，把线程 `runControl={executionId,state:'running'}`/`status='busy'`，`phase='reserved'`。
`consume` 随后把 `phase` 置 `started`，`run` 用 i18n 文案 + `presentation:'runtime'` 的 `messageEnvelope`（correlation 含 messageId/replyToMessageId/invocationId/executionId）调用 `ChatCommonCommand`（project_agent）或 `XpertChatCommand`（xpert），并带 `streamPersistence: { transport: 'redis-stream', threadId, runId }`。`recover` 只按 claim 里的 executionId 查执行：终态则 `processed`（成功清空 lastError，否则 `consumer_ended_without_success`）并在条件匹配时修复线程占用；非终态一律 `blocked` + `consumer_outcome_unknown`。`finally` 的 `releaseUnusedReservation` 只在 `phase='reserved'` 且 `state ∈ {blocked, failed}` 且 consumer 为 `follow_up`、且线程写者仍是该 execution 时释放占位。
`RuntimeObservationMonitorService.reconcile`（`@Interval(5000)`、take 20）只扫描 `nextObservationAt <= now()` 且带 `request.dispatch` 或 `activity` 的 Invocation，用 60s 观察租约（20s 续约）→ `withActor` → `factory.createCapturedApi(scope).inspect(id)`，有 `projectTask` 时发 `ProjectRuntimeObservationCommand`；下一轮时间按终态置 `null`、`unknown` 置 60s、其余 5s，异常写 `observationError='observation_unavailable'` 并退避 60s。

章节来源：[runtime-message-continuation.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-message-continuation.service.ts)（关键符号：RuntimeMessageContinuationService.consume / reserve / run / recover / releaseUnusedReservation / runtimeReplyBlocked）、[runtime-observation-monitor.service.ts](file://packages/server-ai/src/handoff/runtime-messaging/runtime-observation-monitor.service.ts)（关键符号：RuntimeObservationMonitorService.reconcile / observe）

## 设计模式及落点
| 模式 | 落点 |
|---|---|
| Outbox / Inbox | `appendRuntimeDelivery`（与 CAS 同事务、`orIgnore` 幂等）；`RuntimeMessageInboxService.receive / lockInbox`（收据与回执同事务） |
| 租约（lease） | `deliver`、`consume`、`observe` 的 UPDATE-claim（`leaseUntil IS NULL OR < now()`），continuation 额外 15s 心跳 |
| CAS / 乐观并发 | delivery/inbox/observation 的 `where` 条件更新 + `affected` 判定；`reserve` 内校验 `revision`/`status` 不超前 |
| 策略注册 | `@HandoffProcessorStrategy(AGENT_RUNTIME_EVENT_MESSAGE_TYPE, { policy: { lane: 'main' } })` + `HandoffProcessorRegistry.get(type, organizationId)` |
| 适配器注册表 | `HandoffOutboxAdapters.register/reconcile`（`allSettled` 隔离失败，返回 dispose 函数） |
| 幂等键 | `AgentRuntimeDelivery.messageId` 唯一、inbox `(tenant,org,owner,consumptionKey)` 唯一、`GroupMessageRecipient.messageId+participantId`、`enqueueAndWait` 的 `message.id` |

## 热点路径
1. **inbox 认领竞争**：`wait`（`claimWait`）与 `follow_up`（`reserve`）争同一条 `consumptionKey` 行，且 `reserve` 还要抢线程行写者资格（`lockRuntimeThread` + `runControl` 比对），高并发下该行是串行点。
2. **租约续约**：continuation 每 15s、observation 每 20s 各发一次 `UPDATE ... leaseUntil`，续约失败只 warn；扫描器每 3s（inbox）/5s（delivery、observation）各取少量行，吞吐由 `take` 与租约时长共同决定。
3. **重试自环**：`retry` 结果是重新 `enqueue`（新 job），死信与退避都在应用层，多次重试会放大队列写入与扫描量。
4. **等待者回调**：`enqueueAndWait` 的 `pendingResults` 是内存 Map，`emit` 回调在同步路径上抛出只被 warn 吞掉。

## 技术债与 hack
1. **`enqueueAndWait` 跨实例不回调**：进程内 Map + 源码注释明写 best-effort，多副本下 waiter 只能等到 `XPERT_HANDOFF_PENDING_TIMEOUT_MS`（默认 2 分钟）。
2. **canceled 不进死信可能掩盖失败**：`dead(canceled:...)` 被显式跳过死信，而 `isAbortLikeError` 把任何含 abort/cancel 字样的异常也归入取消，真实失败可能被降级为「已取消」。
3. **僵尸 run**：README 与队列恢复验收都指向同一现实——无租约的旧 run 不被时长推断回收，必须显式 stop；`blocked(consumer_outcome_unknown)` 也只能人工 redrive。
4. **Bull ack 边界未确认**：README 的验收脚本描述「接收方在 inbox 事务提交后、Bull 确认 job 前被杀」这一窗口；网关 `add` 未配置 Bull 层 `attempts/backoff`，重试全靠应用层 `message.attempt` 与新 job，因此该窗口完全依赖 inbox 幂等兜底。
5. **死信无台账**：`HandoffDeadService` 只打 `logger.error`，没有表、没有查询接口，运维只能靠日志检索。
6. **退避与租约是代码常量**：60s 租约、15s/20s 续约、30s 节流、`5s*2^n` 上限 300s、`attempts>=19` 全为常量，非环境变量，调整需改代码重发。
7. **transport 用陈旧 attempts 判定**：`deliver` 的 `row.attempts >= 19` 读的是 claim 前的对象值（实际已 +1），失败上界比字面多一轮。
8. **路由配置为启动快照**：`HandoffRoutingConfigService` 只在 `onModuleInit` 读一次 YAML，改配置需重启进程；`routes` 取首个命中，无优先级字段。

## 设计维度分析
**投递语义（至少一次 vs 恰一次）**：选择「先提交后投递」——outbox 与 Invocation CAS 同事务，队列只是可重试的运输工具；代价是同一 `messageId` 会被重发、模糊结果只能人工介入，收益是队列抖动绝不丢弃已提交结果。
**取消语义（协作式扫描 vs 强杀索引）**：`AbortSignal` + 队列扫描换来「不强杀 CPU 密集代码」与「低频 stop 实现简单」，代价是 active 取消 best-effort、成本随 job 量增长、且必须接受扫描与 abort 之间的竞态。
**并发控制（乐观扫描 + 租约 vs 分布式锁/领导者选举）**：delivery/inbox/observation 各自 `UPDATE ... WHERE 租约过期` 认领，多副本无需协调、失败可重复扫描但至多一次入队/一次执行；代价是重复扫描与依赖数据库时钟。
**观测与执行分离（只观察不启动 vs 自动重放）**：`RuntimeObservationMonitorService` 明确只观察既有句柄，`ProjectTaskDispatchRecoveryService` 只重放已提交意图，模糊启动永不重放——用人工介入换「绝不重复执行模型/CLI」。

## 结论
实现上，本子域所有外部可见行为都收敛到 4 个入口：`HandoffQueueService.enqueue*`（入队）、`StopHandoffMessageCommand`（取消）、`appendRuntimeDelivery`（提交即产生投递意图）、`RuntimeDeliveryController`（查询与 redrive）。三条不变量把实现钉死：事件只能由 Invocation 事实派生、收据与回执必须同事务、认领必须经租约或唯一键。风险集中在「失败可见性」（死信只有日志、canceled 被跳过）与「进程内语义」（等待者、本地任务闭包）两处，跨实例与跨进程场景必须依赖 delivery/inbox 的持久状态而非回调。
