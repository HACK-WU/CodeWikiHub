## 取消与恢复操作语义
- **协作式**：取消只发 `AbortSignal`，不强杀同步 CPU 密集代码；`waiting`/`delayed`/`paused` 直接 `job.remove()`，`active` 走 `HandoffCancelService.cancelMessages`（Redis pub/sub `ai:handoff:cancel` 通知其他实例 + 本进程 abort）。
- **结果归一**：取消结果为 `dead(canceled:<reason>)`，**不进死信、不重试**；`buildCanceledReason` 默认文案 `Canceled by user`。
- **best-effort 与竞态**：README 明写 active 取消对竞态敏感——若作业在扫描与 abort 之间完成，它会正常结束；因此「取消返回成功」不等于「该作业已停止」。
- **恢复**：暂停/停止后的续跑由线程准入与 `runtimeReplyBlocked` 决定；`paused`/`pausing`/`interrupted`、存在 `operation`、`runControl.state==='paused'` 都会把 inbox 置 `blocked(awaiting_user)`，`runtimeContinuationBlockedAt` 不早于调用创建时间时置 `blocked(user_stopped)`。
- **僵尸 run**：无租约的旧 run **不按时长猜死**，需显式 stop；`blocked(consumer_outcome_unknown)` 不会自动重放，只能按同一执行身份 redrive 检查。
- **redrive 禁忌**：redrive 只重排传输，**不改 Invocation、不清除用户 stop 屏障、不重放已消费结果、不重启 CLI、不分配替代消费者**；显式用户 stop 必须走手工轮次读取结果。

## 死信处理与人工干预流程
**死信没有台账**：`HandoffDeadService.record` 只写 `logger.error('Dead letter: type=..., id=..., traceId=..., reason=...')`，源码注释说明 v1 仅记录日志。进入死信的只有三类：重试次数耗尽、`dead` 且非 `canceled:`、永久错误（无处理器/消息非法）。
人工干预建议路径：
1. 从日志按 `Dead letter:` 检索 `type`/`id`/`traceId`，或用 `traceId`/`businessKey` 反查业务链路。
2. 运行时链路的失败**不需要靠日志**：`GET /api/agent-invocations/:id/delivery` 返回 delivery 与 consumption 的 `state`/`attempts`/`nextAttemptAt`/`lastError`/`phase`/`claim`；owner 在组织成员关系仍有效时即可查看传输失败（该接口不暴露执行结果正文、不授予运行时权限）。
3. 对 `blocked`/`failed` 且判定为传输性失败的情况，用 `POST /api/agent-invocations/:id/delivery/redrive`（body 必须为空对象 `{}`）复位为 `pending`、`attempts=0`；禁止在 redrive 中携带身份或路由字段（schema 为 strict）。
4. `consumer_outcome_unknown` 只能去检查 claim 中记录的同一 execution；显式用户 stop 必须走手工轮次，不得绕过。
5. 队列侧的悬挂 job 用取消链显式停（`StopHandoffMessageCommand` 的 `messageIds`/`executionIds`），不要直接删 Redis key。

## 观测点与告警
- **派发失败**：`BaseHandoffQueueProcessor` 在 dispatch 异常时 `console.error('Error dispatching handoff message ...')`，错误处理阶段再打 `Error processing handoff message ...`；两者是队列侧唯一强信号。
- **死信**：`HandoffDeadService.record` 的 `logger.error('Dead letter: ...')`，建议按 `reason` 关键字（如 `No handoff processor found`）告警。
- **扫描降级**：transport 扫描异常只 warn `Runtime delivery scan deferred`；continuation 扫描异常 warn `Runtime consumption scan deferred`；租约续约失败 warn `Runtime consumption lease refresh deferred`；取消发布失败 warn `Failed to publish handoff cancel event`；移除 job 失败 warn `Failed to remove handoff queue job ...`。
- **回执字段**：delivery `lastError` 取值 `transport_unavailable`/`access_or_target_changed`；inbox `lastError` 取值 `awaiting_input`/`superseded`/`thread_busy`/`consumer_ended_without_success`/`consumer_outcome_unknown`/`continuation_unavailable`/`access_or_target_changed`/`user_stopped`/`awaiting_user`；Invocation 侧 `observationError='observation_unavailable'`。
- **实时流**：`AgentChatRealtimeService.onModuleDestroy` 输出结构化日志 `runtime.shutdown.agent-streams-interrupting` 与 `runtime.shutdown.agent-streams-closed`（含 pid、streams、redisSubscribers、durationMs），可作停机确认。
- **建议告警阈值**：任一队列 waiting 持续增长、delivery `state='failed'`、inbox `state='blocked'` 且 `lastError='consumer_outcome_unknown'`、inbox `phase='started'` 且 `leaseUntil` 长期过期。

## 多副本注意事项
- **扫描互斥仅本进程**：transport / continuation / observation 的 `scanning` 标志只防同一进程重入；跨进程去重靠数据库租约（60s）与唯一键（`agent_runtime_delivery.messageId`、inbox `(tenant,org,owner,consumptionKey)`）。
- **取消有两条路径**：同实例走内存 `AbortController`，跨实例靠 Redis pub/sub `ai:handoff:cancel`；订阅方在 `onModuleInit` 复制连接并订阅，若 Redis 未注入则该服务静默降级（只 warn 不阻塞）。
- **`enqueueAndWait` 只在同一实例内回调**：worker 与 waiter 分布在不同副本时调用方必须改轮询/状态查询，否则会等到 2 分钟超时。
- **等待者与本地任务都是内存态**：`HandoffPendingResultService` 与 `LocalQueueTaskService` 随进程销毁清空；`AgentChatRealtimeService` 在关机时先向所有流发送中断事件再关连接，避免把 EOF 误当「完成」。
- **队列共享 Redis**：4 个队列同 Redis 实例，`removeOnComplete: true` 让完成 job 立刻消失、`removeOnFail: false` 保留失败 job；并发 env 应按副本数折算单副本 capacity，避免 `并发 × 副本数` 超出下游承载。
- **滚动期间的行为**：先起消费者副本再接生产流量可避免出现「事件已提交但无人消费」的窗口；观察租约未到期时另一副本不会重复观察同一 Invocation。

## 结论
运维要点可压缩成三句话：**队列侧**——4 个同名 `dispatch` job 只区分队列与并发，重试与退避全在应用层，死信只有日志、没有台账；**取消侧**——协作式 + 扫描式，`canceled:` 不进死信，`active` 取消 best-effort，僵尸 run 必须显式 stop；**运行时侧**——Invocation 是账本，delivery/inbox 只有租约与回执，redrive 只重排传输且不清用户 stop，任何恢复都以「先消费者后生产者」与「绝不重放模糊启动」为约束。
