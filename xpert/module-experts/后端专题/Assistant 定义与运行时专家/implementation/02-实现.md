## 1 核心流程实现位置

### 1.1 定义与发布（create / saveDraft / updateDraft / publish / allVersions / duplicate / syncFromTemplate）

- 草稿：`XpertService.saveDraft(id, draft)` 与 `XpertService.updateDraft(id, draft)`，控制器 `@Post(':id/draft')` / `@Put(':id/draft')`。
- 版本：`XpertService.allVersions(id)`、`XpertService.setAsLatest(id)`、`XpertService.createVersionBackup(entity, sourceId)`（注释：版本备份继承源的持久化关联，含已停用 tags）。
- 发布：`XpertController.publish`（`@Post(':id/publish')`）→ `XpertPublishCommand` → `XpertPublishHandler`，落在 `xpert/commands/handlers/publish.handler.ts`。
- 复制：控制器 `duplicate`（`@Post(':id/duplicate')`）实现为 export DSL → import DSL 两步，body 含 `{ basic, isDraft }`。
- 模板同步：`XpertController.syncFromTemplate`（`@Post(':id/sync-template')`）→ `XpertSyncTemplateCommand` → `sync-template.handler.ts`；注释明写"只更新草稿，已发布版本与 Xpert 身份不变"。
- 导入：`XpertController.importDSL`（`@Post('import')`）→ `XpertImportCommand` → `import.handler.ts`（22.97 KB，含 spec 53.75 KB）。

章节来源：[xpert/xpert.controller.ts](file://packages/server-ai/src/xpert/xpert.controller.ts)（关键符号：XpertController.saveDraft、XpertController.duplicate）、[xpert/xpert.service.ts](file://packages/server-ai/src/xpert/xpert.service.ts)（关键符号：XpertService.createVersionBackup）

### 1.2 运行时准入（多受众分支 + assertCurrentUserAccess）

`buildAccessibleQuery` 的分支顺序是实现的骨架：`currentPublicXpertId()` → `buildPublicXpertBoundQuery`；`currentEnterpriseXpertScope() && !resourceParentId` → `buildEnterpriseXpertBoundQuery`；`currentWorkspaceApiKeyWorkspaceId() && !currentRequestedUserId()` → `buildWorkspaceBoundQuery`；否则落到以 `currentAccessUserId()` 为锚的主查询。每个分支尾部统一调用 `applyPublicChatAppFilter` / `applyEnterpriseChatAppFilter` + `applyPublishedFilters` + `applySearchFilter`。单条访问走 `getAccessiblePublishedXpert(id)`：先做 token audience 强制校验，再 `assertCurrentUserAccess(id, xpert)`（后者在资源拥有父级时带 `resourceParentId` 复查一次计数，为 0 即 `ForbiddenException`）。`getAccessiblePublishedXpertForCurrentUser()` 在 `currentUserXpertId()` 存在时额外二次校验。

章节来源：[xpert/published-xpert-access.service.ts](file://packages/server-ai/src/xpert/published-xpert-access.service.ts)（关键符号：PublishedXpertAccessService.buildAccessibleQuery、PublishedXpertAccessService.getAccessiblePublishedXpert）

### 1.3 文件访问（forRuntime / forAuthoring → Command → Handler）

链路三段：`AssistantFilesService.forRuntime(id)` / `.forAuthoring(id)` → `bind(assistantId, entry)` 内的 `authorize(operation)` 每次 `commandBus.execute(new ResolveAssistantFileAccessCommand(assistantId, operation, entry))` → `AssistantFileAccessService.execute()`：

1. 取 `RequestContext.currentTenantId()` / `currentUserId()`，任一缺失即 `denied()`；
2. `entry === 'authoring'`：若 `RequestContext.currentApiPrincipal()` 存在直接 `denied()`，否则 `assertCanAuthorById` + `findOneByIdWithinTenant`；否则走 `published.getAccessiblePublishedXpertForCurrentUser`；
3. 复核 `xpert.tenantId === tenantId`，再 `resolveXpertDataVolumeScope({tenantId, userId, xpertId, workspaceDataScope})` 得出卷范围，返回 `{scope, capabilities}`（共享卷与 `user` 隔离卷都授予全量 CRUD，隔离靠 scope 根而非能力位）。
4. `bind()` 再用 `VOLUME_CLIENT.resolve(scope).ensureRoot()` + `VolumeSubtreeClient(volume, { allowRootWorkspace: true })` 构造卷客户端，`upload()` 另算 `contentSha256` 与 `source: 'platform.workspace.files'` 引用。

章节来源：[xpert/assistant-files/assistant-files.service.ts](file://packages/server-ai/src/xpert/assistant-files/assistant-files.service.ts)（关键符号：AssistantFilesService.forAuthoring）、[xpert/assistant-files/assistant-file-access.service.ts](file://packages/server-ai/src/xpert/assistant-files/assistant-file-access.service.ts)（关键符号：AssistantFileAccessService.execute）

### 1.4 工作区能力（getCapabilities / can / assertCan*）

调用序：`assertCanRead/Run/Write/Author/Manage` → `assertCan(workspaceId, action)` → `getAccess(workspaceId, options)` → `buildAccess(workspace)` → `getCapabilities(workspace, options)`。`getCapabilities` 先判同租户与归档（不满足直接 `emptyCapabilities()`），再叠加成员/可见性与 `hasPublishedXpertRunAccess`（受 `includePublishedRunAccess` 开关控制，批量场景传 `false` 以避免 N+1）；`findAccessibleWorkspaces` 对多工作区批量取能力（`getResourceCapabilities` 配套）。`can(capabilities, action)` 与 `emptyCapabilities()` 是纯函数式判定与兜底。`assertCanAuthor` 复用 `assertCanWrite`（无独立能力位）。

章节来源：[xpert-workspace/workspace-access.service.ts](file://packages/server-ai/src/xpert-workspace/workspace-access.service.ts)（关键符号：XpertWorkspaceAccessService.getAccess、XpertWorkspaceAccessService.can）

### 1.5 触发：编辑期 vs 运行期

- **编辑期** `AssistantTriggerService`（`@Controller(':id/trigger-settings')`）：`list(id)` 只读；`validate(id, mutation)` → `check()` 校验；`mutate(id, mutation)` → `read(id, true)` 后落库，由 `publish-triggers.handler.ts` 在发布时统一实现。
- **运行期** `XpertTriggerConnectionService`（`@Controller(':id/trigger-connections')`，`@UseGuards(XpertGuard)`）：`statuses`、`begin(id, provider)`（QR）、`poll`、`complete`、`cancel`、`disconnect`。所有写路径收敛到私有 `change(id, provider, integrationId)`：`manager.transaction` 内 `repository.findOne({ lock: { mode: 'pessimistic_write' } })` 取行锁，再 `access.assertCanAuthor(xpert.workspaceId)`，随后同步 `graph.connections` 与 `draft`（`previousGraph/providers/strict`）。
- **启动补偿** `XpertTriggerBootstrapRecoveryService implements OnApplicationBootstrap` 负责启动期触发恢复。

章节来源：[xpert/trigger-connection.service.ts](file://packages/server-ai/src/xpert/trigger-connection.service.ts)（关键符号：XpertTriggerConnectionService.change）、[xpert/configuration/assistant-trigger.service.ts](file://packages/server-ai/src/xpert/configuration/assistant-trigger.service.ts)（关键符号：AssistantTriggerService.mutate）

`AssistantBindingService implements OnModuleInit`，`onModuleInit()` 内顺序执行 `backfillLegacySystemBindings()` 与 `backfillLegacyUserBindings()`，依赖 `information_schema` 探测旧 `assistant_config` 表与列后再写绑定；spec 用 `DataSource` + `tableExists/tableHasColumns` 覆盖该行为。

## 3 热点路径

1. **每次运行时文件操作都要重新授权**：`AssistantWorkspaceFilesController` 的每个端点（`capabilities`、`files`、`file`、`file/download`、`file` PUT、`file/upload`、`file/save-binary`、`file` DELETE）都调用 `forRuntime(id)`，从而每次触发一次 `ResolveAssistantFileAccessCommand` → `getAccessiblePublishedXpertForCurrentUser` → 完整多受众查询 + `resolveXpertDataVolumeScope`。**这是有意为之**（"Reauthorize each operation"），代价是文件列表页的 N 次调用 = N 次准入查询。
2. **`accessible` 查询走原生 SQL**：`TENANT_SHARED_WORKSPACE_FILTER` 是字符串常量 `COALESCE((workspace.settings)::jsonb -> 'access' ->> 'visibility', 'private') = 'tenant-shared'`，直接嵌进 QueryBuilder；`getCapabilities` 的批量路径（`findAccessibleWorkspaces` / `getResourceCapabilities`）同样依赖此类 SQL 片段，无法被 TypeORM 类型系统保护。
3. **发布路径重**：`publish.handler.ts` 20 KB、`publish-triggers.handler.ts` 13 KB、`import.handler.ts` 22.97 KB——发布/导入是最大的单文件写路径。
4. **触发写路径串行化**：`change()` 的悲观行锁会把同一 Xpert 的 QR 完成/断开操作串行，`begin`/`poll` 是只读并可并发。

章节来源：[xpert/published-xpert-access.service.ts](file://packages/server-ai/src/xpert/published-xpert-access.service.ts)（关键符号：TENANT_SHARED_WORKSPACE_FILTER）、[ai/assistant-workspace-files.controller.ts](file://packages/server-ai/src/ai/assistant-workspace-files.controller.ts)（关键符号：AssistantWorkspaceFilesController.capabilities）

## 5 技术债与 hack

1. **前缀假象**：`EnterpriseChatkitModule` 无 `RouterModule.register`，靠 `@Controller('xpert')` 自带首段，URL 与 `XpertModule` 的 `/xpert` 同名不同深度；`XpertMarketplaceController` 同样用 `@Controller()` + 方法级 `'xpert-marketplace'` / `'xpert-access-requests'` 拼路径。任何按首段聚合路由白名单的网关都会把 Enterprise H5 的 `@Public()` 端点误判为创作用面。
2. **多受众判定散落两个 service**：`PublishedXpertAccessService` 判 token audience，但 `XpertWorkspaceAccessService` 内部还要按 client-secret 绑定反查 workspace（`currentApiKeyBoundWorkspaceIdForUser` 一类逻辑）；`AssistantsController` 顶层 `@Public()` 全靠 `ApiKeyOrClientSecretAuthGuard` + `AllowClientSecretBindings(ENTERPRISE_XPERT)` 兜底。越权回归集中在"凭证 audience 与目标 assistant 不匹配"。
3. **原生 SQL 与 json 强耦合**：`TENANT_SHARED_WORKSPACE_FILTER` 直读 `workspace.settings->access->visibility`，`COALESCE(..., 'private')` 的失败方向虽是收紧，但字段改名会静默改变可见性语义，且无编译期保护。
4. **路由冲突史**：`ai` 下 `conversations/:id/files` 曾被 FileAsset 与 Workbench 双注册，命中前者返回空附件；现改为 `conversations/:id/workspace/*`，并要求 HTTP 回归测试覆盖两种注册顺序（`workbench-files-routing.http.spec.ts`）。新增 controller 时同类冲突仍无编译期保护。
5. **启动回填并发**：`AssistantBindingService.onModuleInit` 依赖 `information_schema` 探测后写绑定，多实例并发启动存在竞争面（仓库另有 `docs/plans/PLAN_multi_instance_remediation.md`）。
6. **`ensurePrincipalUser` 隐式副作用**：`XpertController` 的 `updateChatApi` / `updateChatApp` 在启用且 `!xpert.userId` 时自动创建 Assistant 的外部服务账号（`XpertPrincipalService.ensurePrincipalUser`），账号生命周期与助手启停状态易不一致；`PUT :id/app` 与公共 App `:identifier/chatkit-session` 共享该账号语义。
7. **匿名 cookie 会话**：公共 App 以 httpOnly cookie `anonymous.id` 作 `fromEndUserId`，换设备/清 cookie 即丢历史；`PUBLIC_XPERT` secret token 默认/上限 TTL 600/3600 s。
8. **草稿与 graph 分叉风险**：`trigger-connection.service.change()` 在事务内同时写 `graph` 与 `draft`（并做行锁）；任何绕过 `change()` 直接改 json 列的写入都可能让草稿与已发布图分叉。
9. **市场授权依赖 UserGroup 生命周期**：`approveRequest` 动态建/复用 `UserGroup` 并回写 `accessGroupId`（`SET NULL` 外键），用户组被删/改名会影响已审批访问，而 `hasRuntimeAccess` 又同时依赖 `userGroups` 与 `workspace.members`。
10. **命名不一致**：同一概念在三处三种名（`WorkspaceAccessService` 文件 / `XpertWorkspaceAccessService` 类；`accessible` vs `xpert-marketplace`；`trigger-settings` vs `trigger-connections`），检索时容易漏。

章节来源：[xpert/enterprise-chatkit-session.service.ts](file://packages/server-ai/src/xpert/enterprise-chatkit-session.service.ts)（关键符号：EnterpriseChatkitSessionService.createSession）、[xpert/xpert-principal.service.ts](file://packages/server-ai/src/xpert/xpert-principal.service.ts)（关键符号：XpertPrincipalService.ensurePrincipalUser）

## 6 设计维度分析

### 6.1 维度 A：权限判定的"入口选择" vs "策略复用"

`ResolveAssistantFileAccessCommand` 是唯一把"选入口"和"判权限"解耦的实现——入口由 `AssistantFilesService` 的两个方法在**服务端代码**里固定，策略由 Handler 内两个分支承担。这带来两个好处：调用方无法通过请求数据越权；策略改动只改一处。代价是**每次操作付一次准入查询**，且"运行时被拒后回退 authoring"这类错误无法在类型层面阻止，只能靠源码注释与 review 约束（"authoring access is explicit and never a fallback after runtime denial"）。对比之下，工作区面用 Guard + Service 双层、准入面用单一查询构造器，两者都没有"入口选择"这一层——因为它们的入口即模块所在。

章节来源：[xpert/assistant-files/resolve-assistant-file-access.command.ts](file://packages/server-ai/src/xpert/assistant-files/resolve-assistant-file-access.command.ts)（关键符号：ResolveAssistantFileAccessCommand.constructor）

### 6.2 维度 B：草稿与已发布态的存储取舍（同表双列 vs 双表）

现方案把 `draft`、`graph`、`version/latest` 全塞进 `xpert` 单表：读取已发布态只需一次 `latest = true` 过滤，`getRuntimeCapabilities(isDraft)` 这类端点也能在同一行上切换视图。代价是写路径必须显式维护"哪一列属于哪个态"——`saveDraft`/`updateDraft` 动 `draft`，`publish` 提升为 `graph` + 新版本行，`change()` 在事务里同时动两者。这正是分叉风险的来源：没有数据库层的约束阻止第三人直接改 json 列。若改为双表，读取路径要 join，但"草稿不影响发布"会由 schema 强制；当前选择偏读取性能与端点简洁。

章节来源：[xpert/xpert.service.ts](file://packages/server-ai/src/xpert/xpert.service.ts)（关键符号：XpertService.saveDraft、XpertService.updateDraft）

### 6.3 维度 C：分发面的授权模型一致性

同一份"某用户能否跑某 Assistant"的判定，在三个分发面上三种落地：准入面查 `published-xpert-access` 多受众查询；市场面在审批时把用户**加进 UserGroup**（`ensureAccessGroup`），运行时再靠 `hasRuntimeAccess` 间接判定；绑定面则完全不判权限，只做槽位映射。三者的收敛点是 UserGroup：市场授权最终变成准入查询里的一条 `userGroups` 命中。这让"同一授权在准入查询里生效"成为可能，但也使授权状态与用户组实体的生命周期绑定（删除/改名即失效）。若要简化，需要把 UserGroup 从"授权载体"降级为"授权索引"。

章节来源：[xpert-marketplace/xpert-marketplace.service.ts](file://packages/server-ai/src/xpert-marketplace/xpert-marketplace.service.ts)（关键符号：XpertMarketplaceService.ensureAccessGroup、XpertMarketplaceService.hasRuntimeAccess）

## 7 结论

实现层面，本域最值得复用的两点是：**(1) 把授权本身建模为 Command**——`ResolveAssistantFileAccessCommand` 让"重授权"变成一次可测试、可替换的调用，而不是散落的 if；**(2) 多受众准入集中到单一查询构造器**——所有受众分支尾部共用 `applyPublishedFilters`，避免"某个分支忘了加 `latest`"这类静默越权。最值得警惕的三点已在技术债中列出：前缀假象导致的网关误判、原生 SQL 与 json 的隐式契约、以及启动期回填在并发下的竞争面。三者都不可能通过读单个文件发现，必须在改动路由 / 改 schema / 改模块初始化时主动检查。
