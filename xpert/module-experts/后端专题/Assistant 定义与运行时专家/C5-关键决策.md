## D1 三元权限面分离：创作 / 运行 / 文件

- **分类**：架构设计
- **动机**：避坑——三套权限判定若共用一个入口，任何一处选错即构成越权；历史上 2026-10-09 的验收修的正是这类问题。
- **决策**：创作侧用 `WorkspaceAuthoringGuard` + `XpertWorkspaceAccessService.assertCanAuthorById`；运行侧用 `PublishedXpertAccessService`；文件侧用 `AssistantFilesService.forRuntime/forAuthoring`。三条面各自独立入口，互不代用。
- **背景约束**：`AGENTS.md` 明写 `XpertWorkspace`（`xpert_workspace`、`xpert.workspaceId`）是 Assistant / 技能 / 连接器的**创作资源容器**，其 `canRead/canRun/canWrite/canManage` **不是** Assistant 文件权限；UserGroup 授权必须在无创作工作区成员资格时也能生效。
- **被否决方案**：用 `XpertService.findOne()`、`XpertWorkspaceService.canAccess()` 或工作区级 `canRun` 充当文件 ACL——`AGENTS.md` 显式禁止。`XpertWorkspaceService.canAccess()` 仍作为公开方法存在，属残留误用面。
- **重新评估触发条件**：出现「同一入口需要同时判创作与运行」的产品需求单（当前无此类需求记录）。
- **关联代码**：`file://packages/server-ai/src/xpert-workspace/workspace-access.service.ts`（`XpertWorkspaceAccessService.can`）、`file://packages/server-ai/src/xpert/published-xpert-access.service.ts`（`PublishedXpertAccessService.buildAccessibleQuery`）、`file://packages/server-ai/src/xpert/assistant-files/assistant-files.service.ts`（`forRuntime` / `forAuthoring`）、`file://packages/server-ai/src/xpert-workspace/guards/workspace-authoring.guard.ts`
- **证据来源**：`file://AGENTS.md`（Authoring workspace versus Assistant file workspace 小节）；`file://.module-experts/后端专题/Assistant 定义与运行时专家/implementation/01-架构.md`；`file://.module-experts/后端专题/Assistant 定义与运行时专家/sub-experts/工作区与文件授权子专家/implementation/02-实现.md`

## D2 绝不接受 HTTP 传入 authoring 模式

- **分类**：安全合规
- **动机**：避坑——文件入口若可由请求数据选择，任何客户端都能把「运行时被拒」改写成「走 Studio 权限」，等价于提权。
- **决策**：`entry`（`runtime` / `authoring`）只能由服务端代码在 `AssistantFilesService.forRuntime()` / `forAuthoring()` 里硬编码选定；`ResolveAssistantFileAccessCommand` 的注释把该约束写进源码：「entry is chosen by trusted server code, never request data」。
- **背景约束**：`assistant-file-access.service.ts` 文件头三条不变量之一为「authoring access is explicit and never a fallback after runtime denial」；`AGENTS.md` 追加「never accept an authoring mode from HTTP data or fall back to authoring after runtime denial」。
- **被否决方案**：把 `entry` 做成查询参数或请求体字段；或在运行时分支 403 之后静默改走 authoring 分支——两者都被源码注释与 `AGENTS.md` 明文禁止。
- **重新评估触发条件**：无（属不可协商的安全不变量）。
- **关联代码**：`file://packages/server-ai/src/xpert/assistant-files/resolve-assistant-file-access.command.ts`（`ResolveAssistantFileAccessCommand` 类型级 JSDoc）、`file://packages/server-ai/src/xpert/assistant-files/assistant-file-access.service.ts`（文件头不变量 + `Delegated credentials cannot select the Studio authority`）
- **证据来源**：`file://AGENTS.md`；源码注释（上列两文件）；`file://.module-experts/后端专题/Assistant 定义与运行时专家/sub-experts/工作区与文件授权子专家/implementation/02-实现.md`

## D3 运行时文件必须经 `ResolveAssistantFileAccessCommand` 且每次操作重授权

- **分类**：安全合规
- **动机**：避坑——授权撤销（被移出 UserGroup、凭证 audience 变更、助手撤回发布）必须在**下一次操作**就生效，而不是等到会话过期或缓存过期。
- **决策**：把「授权」本身建模为一个 Command；文件入口的每个操作都重新派发 `ResolveAssistantFileAccessCommand`，由 `AssistantFileAccessService.execute()` 单点判定，返回 `{ scope, capabilities }`。
- **背景约束**：`AssistantFilesService.bind()` 内注释「Reauthorize each operation, including after a previously successful list or capability lookup.」；`AssistantWorkspaceFilesController` 的 8 个端点（`capabilities` / `files` / `file`(GET) / `file/download` / `file`(PUT) / `file/upload` / `file/save-binary` / `file`(DELETE)）**每个都重新 `forRuntime(id)`**。代价是文件列表页 N 次调用 = N 次准入查询 + N 次 `resolveXpertDataVolumeScope`，属**有意取舍**。
- **被否决方案**：无（源码与文档未记录显式否决过的替代方案）。
- **重新评估触发条件**：文件端点成为可观测的性能瓶颈（判据：准入查询在接口耗时占比显著高于卷 I/O，或列表页出现超时/告警），或引入按会话缓存的授权票据机制后仍要求同等撤销时延。
- **关联代码**：`file://packages/server-ai/src/xpert/assistant-files/assistant-files.service.ts`（`bind`）、`file://packages/server-ai/src/xpert/assistant-files/assistant-file-access.service.ts`（`execute` / `denied`）、`file://packages/server-ai/src/ai/assistant-workspace-files.controller.ts`
- **证据来源**：`file://AGENTS.md`；`file://.module-experts/后端专题/Assistant 定义与运行时专家/implementation/02-实现.md`（热点路径 1）；`file://.module-experts/后端专题/Assistant 定义与运行时专家/sub-experts/工作区与文件授权子专家/implementation/01-架构.md`

## D4 对外出参一律用白名单投影，不序列化实体

- **分类**：安全合规
- **动机**：避坑——实体携带加载关系（`members` / `environments` / `desktopBootstrap` / `agent`）与服务端恢复态，直接序列化会把内部字段与恢复现场泄漏给匿名或低权客户端。
- **决策**：所有对外响应手工构造白名单字段。`XpertProfileController.getProfile` 逐项裁剪 tags/workspace/creator；`XpertAccessController.getAccessiblePublishedXpert` 只回 `{ id, avatar }`；`WorkspacePublicDTO` 用 `@Exclude()` 排除 `members`/`environments`；`EnvironmentPublicDTO` 抹掉 `variables[].value`；`AssistantBinding.desktopBootstrap` 用 `@Exclude({ toPlainOnly: true })`；`BosiBootstrapService.publicProgress()` 只回四字段。
- **背景约束**：`getProfile` 注释原文「Construct a whitelist instead of serializing the entity and its loaded relations.」；`AssistantAppearanceService.save` 注释「Whitelist public identity only」。`@Exclude` 只作用于 `instanceToPlain` 方向——绕过 class-transformer 的序列化路径仍可能泄漏。
- **被否决方案**：无（未见显式否决记录；但「继续序列化实体 + 事后裁剪」这一方向与源码注释直接冲突，不作为可追溯的被否决方案列出）。
- **重新评估触发条件**：无（安全出口约束）。
- **关联代码**：`file://packages/server-ai/src/xpert/xpert-profile.controller.ts`（`getProfile`）、`file://packages/server-ai/src/xpert/xpert-access.controller.ts`、`file://packages/server-ai/src/assistant-binding/assistant-binding.entity.ts`（`desktopBootstrap`）、`file://packages/server-ai/src/assistant-binding/bosi/bosi-bootstrap.service.ts`（`publicProgress`）
- **证据来源**：源码注释（上列文件）；`file://.module-experts/后端专题/Assistant 定义与运行时专家/implementation/06-测试.md` 所列输出白名单校验规则（同见 `04-模型.md` 第 9 节）

## D5 草稿与发布态隔离：统一「仅草稿保存」（draft-only saves）

- **分类**：数据一致性
- **动机**：避坑——发布后的版本是运行时对象（对话与调用按版本运行），半成品编辑若直接落 `graph` 会污染正在跑的版本。
- **决策**：编辑先入 `Xpert.draft`，1s 去抖自动 `POST /api/xpert/:id/draft`；只有 `publish` 才把草稿固化为版本行（`XpertPublishHandler.publish` 写 `graph` 并置 `draft = null`）；前端 `resume()` 可丢弃草稿回到已发布版本。
- **背景约束**：`saveDraft` 与 `updateDraft` 的语义被刻意分开——`PUT :id/draft` 只在 body 命中 `nodes`/`connections` 键时才覆盖图字段，校验时用 `xpert.graph.nodes` 兜底，避免「只改标题」的补丁把已发布图实体化进草稿。已知例外：`POST :id/configuration`（`AssistantConfigurationService.save`）会顺带执行一次 `publish(newVersion = true)`，与整体 draft-only 取向相反。
- **被否决方案**：无可追溯记录（决策记录原文写「无可追溯记录」）。
- **重新评估触发条件**：出现实时协同编辑需求，或出现「逐次编辑生成审计版本」的产品需求。
- **关联代码**：`file://packages/server-ai/src/xpert/xpert.service.ts`（`XpertService.saveDraft` / `updateDraft`）、`file://packages/server-ai/src/xpert/commands/handlers/publish.handler.ts`（`publish` 内 `draft = null`）、`file://packages/server-ai/src/xpert/configuration/assistant-configuration.service.ts`
- **证据来源（跨会话证据）**：`file://CodeWikiHub/xpert/memory/决策记录/Xpert Studio/仅草稿保存 draft-only saves.md`（记录 commit `9c210afd9` feat(studio): unify assistant settings with draft-only saves；代码佐证 `XpertStudioApiService` 的 `saveDraft` / `resume` / `unsaved` / `pristineDraft`）；本仓源码与 `.module-experts/.../sub-experts/助手定义与发布子专家/implementation/02-实现.md` 热点路径 1。**该条为跨会话证据，未在本仓前端源码中二次核验。**

## D6 企业 H5 bootstrap 在身份校验之前，且只暴露白名单字段

- **分类**：接口契约
- **动机**：让未登录的 H5 侧也能先渲染应用壳（名称、头像、starters、features），避免首屏必须两次往返且失败态难表达。
- **决策**：`GET /api/xpert/:identifier/enterprise-h5/:platform/bootstrap` 为 `@Public()`，返回 `EnterpriseH5Xpert`（`id/slug/name/type/description/avatar/title/titleCN/version/publishAt/starters/features/tenantId/organizationId/app`）+ `platform` + `clientConfig`；身份认证推迟到 `POST .../session`，由 `authorization_code` 换身份 → `assertIdentity` 五项全等 → `AccountBindingService.resolveUser` → 签发 `ENTERPRISE_XPERT` client secret（TTL 固定 600 秒）。
- **背景约束**：匿名面靠三条过滤收窄——`publishAt IS NOT NULL`、`organizationId` 非空、`channels[platform].enabled`；源码类型注释原文为「Bootstrap response returned before enterprise identity verification.」。风险面是「任何拿到 slug 的人都能读到助手名/描述/头像/starters/features」。
- **被否决方案**：无（`implementation/02-实现.md` 的维度 C 讨论了「bootstrap 只回 platform 与 clientConfig、xpert 信息放到 session 之后」这一方向与其代价，但**未记录为已否决方案**）。
- **重新评估触发条件**：无（当前无安全事件或需求单记录）；若企业合规要求「匿名阶段不得泄露助手元数据」，则触发重评。
- **关联代码**：`file://packages/server-ai/src/xpert/enterprise-chatkit-session.service.ts`（`EnterpriseH5Xpert` / `EnterpriseH5ChatAppBootstrap` / `getBootstrap` / `createSession` / `assertIdentity`）、`file://packages/server-ai/src/xpert/enterprise-chatkit.controller.ts`

## D7 工作区能力与文件权限解耦：UserGroup 只桥接 `canRun`

- **分类**：安全合规
- **动机**：避坑——被授权的组内用户不是工作区 owner/member，运行智能体时若复用创作态读校验，会报 `Access denied to workspace`，导致「已通过智能体入口 ACL 的用户无法运行目标智能体」；修复方向是只补运行能力，而不是把他变成工作空间成员。
- **决策**：用户组只为工作空间补 `canRun`，**绝不提升 `canRead` / `canWrite` / `canManage`**；不能替代已发布智能体的入口 ACL；运行态查询必须继续保留租户、组织、工作空间数据范围，编辑/保存/发布入口不得走运行态方法绕过创作态校验。
- **背景约束**：判定依赖智能体、用户组与组成员的关联表组合（原生 SQL join `xpert_to_user_group` / `user_group` / `user_group_to_user`，别名必须小写）；托管组元数据只能由平台侧写入（HTTP 入口剥离），防止通过接口伪造组归属。源码注释「A published Xpert grant unlocks execution only; it must not expose workspace authoring resources.」与此一致。
- **被否决方案**：① 把组内用户加入工作空间成员；② 用创作态通用查询承担运行态读取（文档明写会导致二次拒绝）。
- **重新评估触发条件**：用户组被要求授予编辑权，或文件级授权与工作空间能力需要统一（出现「组内用户需要改草稿」的需求单）。
- **关联代码**：`file://packages/server-ai/src/xpert-workspace/workspace-access.service.ts`（`getCapabilities` 的 `canRun` 分支 / `hasPublishedXpertRunAccess`）、`file://packages/server-ai/src/xpert-workspace/workspace.service.ts`（`updateMembers` / `canAccess`）
- **证据来源**：`file://CodeWikiHub/xpert/memory/决策记录/身份与权限/安全合规-UserGroup只桥接canRun.md`（引用 `docs/plans/PLAN_xpert_user_groups_access.md` 与 `docs/zh-Hans/guides/permission.mdx`）；`file://.module-experts/后端专题/Assistant 定义与运行时专家/sub-experts/工作区与文件授权子专家/implementation/02-实现.md`

## D8 市场授权落地为 UserGroup 成员关系

- **分类**：架构设计
- **动机**：`[推测]` 让审批结果立即可被既有准入查询消费，避免为本域新增一套权限子系统与一条新的 join 路径。
- **决策**：`approveRequest` 不再维护独立的授权表，而是 `ensureAccessGroup(xpert)` 建/复用 `UserGroup`（`managedBy = XPERT_MARKETPLACE`、`managedEntityType = XPERT`、`managedEntityId = xpert.id`，名字 `Xpert access - {label}` 截断 100）→ 申请人入 `group.members` → 该组入 `xpert.userGroups` → 回写 `xpert_access_request.accessGroupId`。运行时由 `hasRuntimeAccess` 与准入查询的 `userGroups` join 判定。
- **背景约束**：`xpert_access_request.accessGroupId` 外键为 `SET NULL`，且与 `xpert_to_user_group` 无反向同步——删组或改名后已审批记录仍显示 `approved`，而 `hasRuntimeAccess` 已为 `false`。同意/驳回的审核权由 `assertCanReviewRequest` 判定：有 workspace 时等价 `getCapabilities(workspace).canManage`，无 workspace 时回落 `createdById === 当前用户`。
- **被否决方案**：无（`implementation/02-实现.md` 维度 B 对比了「独立 ACL 表」方向及其代价，但**未记录为已否决方案**）。
- **重新评估触发条件**：出现「UserGroup 删除/改名导致已审批访问与实际权限不一致」的可观测投诉或审计项，或授权与组织架构需要解耦的需求单。
- **关联代码**：`file://packages/server-ai/src/xpert-marketplace/xpert-marketplace.service.ts`（`requestAccess` / `approveRequest` / `rejectRequest` / `ensureAccessGroup` / `hasRuntimeAccess`）、`file://packages/server-ai/src/xpert-marketplace/xpert-access-request.entity.ts`（`accessGroupId`）、`file://packages/server-ai/src/xpert/xpert.entity.ts`（`@JoinTable({ name: 'xpert_to_user_group' })`）
- **证据来源**：`file://.module-experts/后端专题/Assistant 定义与运行时专家/implementation/03-数据流转.md`（§7 市场授权链）；`file://.module-experts/后端专题/Assistant 定义与运行时专家/sub-experts/模板市场绑定与环境子专家/implementation/02-实现.md`（§3 与维度 B）；`file://CodeWikiHub/xpert/memory/决策记录/身份与权限/安全合规-UserGroup只桥接canRun.md`

## D9 路由注册顺序敏感：同方法同 URL 只允许一个 controller

- **分类**：其他（工程纪律）
- **动机**：避坑——两个真实控制器同时注册 `GET /ai/conversations/:conversationId/files` 时，命中前者（FileAsset 附件列表）返回空附件数组，即便同一文件能通过单文件接口读到；现象是「文件存在但列表为空」，后果是功能静默失效且无编译期错误。
- **决策**：约定唯一注册——FileAsset 附件列表继续使用 `/api/ai/conversations/:id/files`，Workbench 运行目录整体迁到 `/api/ai/conversations/:id/workspace/*`，只保留**不冲突**的旧单数路由（`@Get(['workspace/file', 'file'])` 一类）；`xpert-sdk-js` 的 Workbench 客户端同步采用新路径。新增 controller 时必须以「同路径不同 controller」的方式排查冲突。
- **背景约束**：Nest 不做冲突检测，无编译期保护；企业 H5 与创作面的 URL 首段同为 `xpert` 但深度不同（`EnterpriseChatkitModule` 无 `RouterModule.register`，靠 `@Controller('xpert')` 自带首段），任何按首段聚合路由白名单的网关会把 `@Public()` 的企业端点误判为创作用面。
- **被否决方案**：无（验收文档记录的是「修法与保留项」，未记录被否决的其他修法）。
- **重新评估触发条件**：`xpert-sdk-js` 或者外部消费者仍在调用旧路径且无法升级（判据：旧 Workbench 单文件路由出现真实调用量或兼容诉求）。
- **关联代码**：`file://packages/server-ai/src/ai/workbench-files.controller.ts`、`file://packages/server-ai/src/file-understanding/file-understanding.controller.ts`、`file://packages/server-ai/src/ai/workbench-files-routing.http.spec.ts`、`file://packages/server-ai/src/xpert/enterprise-chatkit.module.ts`
- **证据来源**：`file://docs/plans/VERIFY_assistant_file_workspace_access_2026-10-09.md`（「实测发现并修复的额外问题」）；`file://AGENTS.md`（Conversation file APIs 路由区分要求）；`file://.module-experts/后端专题/Assistant 定义与运行时专家/sub-experts/运行时API与准入子专家/implementation/02-实现.md`（§6）

## D10 多副本实例协调：能加锁的加锁，不能加锁的先记缺口

- **分类**：架构设计
- **动机**：线上三个 API 实例同时从数据库加载 `scheduled` 任务、各自建 `CronJob`，同一任务在 09:50 被执行三次并产生三条 `chat_conversation` 记录——单实例假设在多副本下直接变成重复执行。
- **决策**：按「启动副作用是否跨实例互斥」分档处理。**已加锁**：`XpertTriggerBootstrapRecoveryService.onApplicationBootstrap` 用 `RedisLockService` 按 `job:trigger:v2:<xpertId>`（10s）互斥，未抢到只记 `skipped`，可安全多副本启动；`BosiBootstrapService` 的写操作统一包在 `pg_try_advisory_lock(hashtext('bosi-bootstrap'), ...)` 内，抢不到抛 `ConflictException`。**收敛 DDL**：`DB_SCHEMA_SYNC_MODE=external` 让 API 以 `synchronize: false` 启动，DDL 交独立 `schema-sync` 短生命周期进程。**已知未覆盖**：`AssistantBindingService.onModuleInit` 的绑定回填无 Logger、无 advisory lock、无「插入冲突忽略」，多副本同时启动存在重复写入与唯一索引冲突面，`docs/plans/PLAN_multi_instance_remediation.md` 明确记录该计划**并未覆盖**本域绑定回填。
- **背景约束**：模板目录是共享文件系统——启动播种与导出写入同一 `externalRoot`，多副本必须挂共享卷，否则导出模板只在写入副本可见；`AssistantBindingService` 的回填失败以异常冒泡（无日志），只能靠启动失败观测。
- **被否决方案**：无（计划文档记录的是「当前不做的变更」，非被否决方案）。
- **重新评估触发条件**：`AssistantBindingService` 回填在多副本启动中出现唯一索引冲突或重复写（可观测判据：启动异常 / `assistant_binding` 出现违反三条 partial unique 的记录）；或 `bootstrap_recovery_summary` 的 `failed` 计数在多副本下持续 > 0。另：`XPERT_TEMPLATE_DIR` 未落在共享卷时，导出模板跨副本不可见。
