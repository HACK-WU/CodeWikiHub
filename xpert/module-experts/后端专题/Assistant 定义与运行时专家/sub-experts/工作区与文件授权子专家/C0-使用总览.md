## 1 定位与何时找

一句话：**工作区是创作容器，文件是数据卷**，两者在代码上刻意不共享任何判定函数。

**何时必须找本子专家：**

- 建 / 改 / 删 / 归档 / 软删 / 恢复工作区，或改成员列表、改可见性。
- 需要回答「这个用户能不能读 / 跑 / 写 / 管这个工作区」——唯一权威是 `XpertWorkspaceAccessService`。
- 需要让 Assistant 读写文件：Studio 创作侧走 `forAuthoring()`，运行时走 `forRuntime()`。
- 排查 `403 Access denied to workspace`、`WorkspaceIdInvalid`、`WorkspaceFileAccessDenied`、`WorkspaceFileInvalidRequest`、`WorkspaceFileUploadRequired`。
- 需要确认一个文件落在 `xperts`（shared）还是 `user-xperts`（user）目录，或需要文件查看会话 / 票据。

**何时不要找本子专家：**

- Assistant 本体定义、草稿与发布 → 「助手定义与发布子专家」。
- 运行时准入本体（`PublishedXpertAccessService`）→ 「运行时API与准入子专家」；本域只调用它。
- 卷内物理读写、路径包含与符号链接防护 → `shared/volume`（`VolumeSubtreeClient`）。
- 对话附件 `FileAsset` 与 Workbench 会话文件本体 → `ai/file-understanding`、`ChatConversationService`。

## 2 能力清单

| # | 能力 | 入口（符号 / 路由） | 关键语义 |
|---|---|---|---|
| 1 | 工作区 CRUD | `XpertWorkspaceController` `/api/xpert-workspace/*` | create 走 sanitized 边界（不接受客户端身份 / owner / system 字段）；update、成员、可见性、增删走 `WorkspaceOwnerGuard` |
| 2 | 我的工作区集合与默认 | `findAllMy` / `findAllMyEntities` / `findMyDefault` / `setMyDefault` | 只回 `WorkspacePublicDTO` 安全投影；`?purpose` 只接受 `authoring`，其余回落 `runtime` |
| 3 | 成员管理 | `updateMembers` / `ensureMember` / `removeMemberFromOrganizationWorkspaces` | 成员是**整体覆盖**语义且**无角色列**（成员即等价授权）；批量移除显式排除 `user-default` 工作区 |
| 4 | 可见性 | `updateVisibility` / `applyVisibility` | `private`（缺省与未知值回落）｜`tenant-shared`（要求 `organizationId` 为空）｜`organization-shared`（要求非空） |
| 5 | 软删 / 恢复 / 归档 / 硬删 | `softRemoveWorkspace` / `recoverWorkspace` / `archiveWorkspace` / `deleteWorkspace` | `status='archived'` 在 `getCapabilities` 中直接判为无权限；`status` 为 NULL 视为非归档 |
| 6 | 能力四动作 | `XpertWorkspaceAccessService.getCapabilities` → `canRead/canRun/canWrite/canManage` | 另有 `can` / `assertCan` / `assertCanRead|Run|Write|Manage|Author`；能力位是**内存投影**，永不落库 |
| 7 | 用户组运行时准入 | `hasPublishedXpertRunAccess`（原生 SQL 读 `xpert_to_user_group`）与 `getResourceCapabilities` | UserGroup 只补 `canRun`；`isTenantSharedWorkspace` 的合并入口同在此 |
| 8 | 文件 runtime 入口 | `AssistantFilesService.forRuntime(assistantId)` | 只经 `PublishedXpertAccessService.getAccessiblePublishedXpertForCurrentUser` 授权**确切的已发布 Assistant** |
| 9 | 文件 authoring 入口 | `AssistantFilesService.forAuthoring(assistantId)`、`XpertWorkspaceFilesService`（Studio façade） | 保留显式创作检查（含草稿）：`XpertService.assertCanAuthorById` + `findOneByIdWithinTenant` |
| 10 | 文件动作族 | `capabilities` / `list` / `read` / `download` / `save` / `saveBinary` / `uploadToFolder` / `delete` / `upload` | 每次操作重新派发 `ResolveAssistantFileAccessCommand`，不做会话级缓存 |
| 11 | 卷作用域映射 | `resolveXpertDataVolumeScope({ tenantId, userId, xpertId, workspaceDataScope })` | `shared` → `catalog='xperts'`、`isolateByUser:false`；`user` → `catalog='user-xperts'` 且必须绑 `userId`（缺则 `XpertWorkspaceUserRequired`） |
| 12 | 文件查看会话与票据 | `/api/ai/workspace-files/view-sessions`（`WorkspaceFileAccessRuntimeController`） | cookie 会话 + `grants`；票据 URL 只回传 pathname；撤销会话同时清 cookie |

## 3 边界

**做**：`xpert_workspace` 实体与 `xpert_workspace_member` 连接表、能力计算与三档 Workspace 守卫、文件授权解析命令与处理器、Studio 创作 façade、运行时文件 HTTP 面与委派凭证守卫、卷作用域映射。

**不做**：卷内物理读写与穿越 / 符号链接防护（→ `shared/volume`）；Assistant 发布态与多受众准入本体（→ `PublishedXpertAccessService`，仅被调用）；对话附件与 Workbench 会话文件本体（→ `ai/file-understanding`、`ChatConversationService`）。

**一个高频误判**：`XpertWorkspace` 是 Assistant / skills / connectors 的创作资源容器，它的 `canRead/canRun/canWrite/canManage` **不是** Assistant 文件权限。两者共享 "workspace" 这个词，但不是同一个东西。

## 4 已知坑

1. **三元权限面不可互换**。创作面（`XpertWorkspaceAccessService` + 三个 Workspace 守卫，判定对象是 `xpert_workspace`）、运行准入面（`PublishedXpertAccessService`，判定对象是"确切的已发布 Assistant"）、文件面（`ResolveAssistantFileAccessCommand` + `AssistantFileAccessService`，判定对象是 Assistant 数据卷）是三个独立面。把 `XpertService.findOne()`、`XpertWorkspaceService.canAccess()` 或 workspace 级 `canRun` 当文件 ACL 即越权。
2. **绝不接受 HTTP 传入 authoring 模式，且运行被拒不得回退**。入口由可信服务端代码选定（命令注释原文：entry is chosen by trusted server code, never request data）；Studio 用 `forAuthoring()`，运行时被拒后**不得**回退到 authoring。
3. **文件访问永不授予工作区成员资格或编辑权**。共享卷是显式协作（授权用户可读、上传、修改、删除），`user` 隔离卷仅限当前用户自己的卷——两者都不写 `xpert_workspace_member`。
4. **UserGroup 只补 `canRun`**。通过用户组获得的运行时访问只解锁"执行"；`canRead/canWrite/canManage` 保持 false，创作资源不因此可见。
5. **每次操作重新授权**。`AssistantFilesService.bind()` 对 `capabilities/list/read/download/save/saveBinary/uploadToFolder/delete/upload` 每次重新派发命令；不要拿上一次成功的结果替后续操作背书。
6. **`TENANT_SHARED_WORKSPACE_FILTER` 是原生 SQL 与 `settings` json 的强耦合**。`COALESCE((workspace.settings)::jsonb -> 'access' ->> 'visibility', 'private') = 'tenant-shared'` 在 `xpert-marketplace.service.ts` 与 `published-xpert-access.service.ts` 各有一份；改键名或改 `settings` 结构会静默失效且不编译报错。
7. **45 项真机断言的四条硬边界**：① 用户组授权 ≠ 创作工作区成员（B 访问 A 的工作区或 Studio 文件入口 403，但文件能力全 true）；② 未发布草稿对运行接口 404（Studio 侧仍可编辑）；③ 移出用户组后**原 JWT 与原 ChatKit 会话**立即 403，且被拒的写入未改动原文件；④ `..` 路径越界 400。
8. **"workspace" 一词被三处复用**：创作容器 `xpert_workspace`、Assistant 数据卷（Volume 目录）、运行时会话文件目录（Workbench）。`types.ts` 的 `getWorkspaceRoot` 走 `resolveRuntimeVolume({catalog:'workspaces'})`，那是**创作工作区卷**，与 Assistant 数据卷（`xperts` / `user-xperts`）是两套目录。
9. **工作区表几乎没有 DB 约束**：`status` 无默认值与 CHECK（写错枚举被当可用）、`settings.access.visibility` 无 CHECK 且读取侧非法值静默降级为 `private`、`user-default` 无唯一索引、`xpert_workspace_member` 无显式索引且列名由 TypeORM 推导。
10. **路由必须唯一注册**。2026-10-09 验收暴露的真实缺陷：`GET /ai/conversations/:id/files` 被 FileAsset 与 Workbench 双注册，实际命中附件列表；已修正为 FileAsset 保留 `/ai/conversations/:id/files`、运行目录改用 `/ai/conversations/:id/workspace/*`，并要求 SDK 同步交付。
11. **`XpertGuard` 缓存 5 分钟**。创作侧准入结果按 `userXperts:<tenantId>:<userId>_<xpertId>` 缓存；文件面刻意不共享该缓存，这正是"每次操作重新授权"要保住的性质。

## 5 症状定位表

| 症状 | 先看 | 常见根因 |
|---|---|---|
| 403 `Access denied to workspace` | `XpertWorkspaceAccessService.assertCan` | 落在错误的权限面，或 `status='archived'`，或组织作用域下把 `purpose` 当 `authoring` 用 |
| 用户组已授权却拿不到文件 | `AssistantFileAccessService.execute` 的 runtime 分支 | 助手未发布 / 不是 `latest` / 绑定被改；运行时分支只认 `getAccessiblePublishedXpertForCurrentUser` |
| 文件读写 403 但工作区能进 | `AssistantFileAccessGuard` | 凭证受众不匹配（`principalType` / `resourceScope.kind` / 组织 / `host.hostId` 与 `xpertId` 不一致） |
| 草稿能编辑但运行 404 | Studio 与 runtime 两入口 | 这是**预期行为**：authoring 保留草稿检查，runtime 不放开未发布 |
| 移出用户组后老会话仍可用 | 用户组成员关系 + 每次操作重新授权 | 若仍可访问，说明某处引入了会话级缓存或回退路径 |
| 文件落在错误目录 | `resolveXpertDataVolumeScope` | `xpert.workspaceDataScope` 创建后不可改；`user` 缺 `userId` 会抛 `XpertWorkspaceUserRequired` |
| 列表能看但详情 403 | `applyCurrentReadScope` 与 `getCapabilities` 的镜像差异 | 列表 SQL 与点读判定不同源时会出现"看得见进不去" |
| 附件列表返回空但文件明明存在 | 路由双注册 | `/ai/conversations/:id/files`（FileAsset）与 `/ai/conversations/:id/workspace/*`（Volume）必须各归其位 |
| 工作区接口带出环境变量 | `WorkspacePublicDTO` | 该 DTO 显式 `@Exclude()` 掉 `environments` 关系；绕过 DTO 直出实体会泄露 |

## 6 一分钟自查

- 这条文件入口是**谁选的**？HTTP 数据，还是服务端代码？
- 这个卷是**谁的**？tenant + Assistant 身份，还是再绑认证用户？
- 这条路由**是否唯一**？两个控制器是否注册了同一 method + URL？
- 这次判定用的是**哪个权限面**？创作 / 运行准入 / 文件，三者不能互借。
- 这次结论能否**复用**上一次的？不能——每次操作重新授权。
