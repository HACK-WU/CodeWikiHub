## 2 xpert-workspace 的 7 个 spec

**2.1 `workspace-access.service.spec.ts`（`describe('XpertWorkspaceAccessService')`）** —— 覆盖面最广（22 个 it + `it.each`）：租户作用域列表默认只含租户工作区；`includeOrganizationWorkspacesInTenantScope` 跨作用域可见性；组织作用域**默认包含** tenant-shared 而 **`purpose: 'authoring'` 排除**；组织内用户对 tenant-shared 可读可跑但不可写；当前组织成员可创作 organization-shared App 工作区、组织管理员可管理；tenant-private 对组织作用域用户隐藏；`['owner','member','organization-user']` 参数化的可见性；**"通过已发布 xpert 用户组授权获得 runtime-only 工作区访问"**；租户作用域 owner 可管理 tenant-shared；以及一组 api-key / client secret 用例（assistant api key、persisted xpert user 优先、不回退 api key principal user、PUBLIC_XPERT、ENTERPRISE_XPERT 仅限绑定的 H5 工作区、workspace api key、以及多组"不得越界访问其他工作区"的否定用例）。

**2.2 `workspace-base.service.spec.ts`（`describe('XpertWorkspaceBaseService')`）** —— 4 个 it：组织作用域下从目标租户工作区查询租户级记录；`select` 省略作用域字段时 `findOne` 仍可读；`findOneForRuntime` **按 run 而非 read 授权**加载；运行态列表按 run 而非 authoring 授权。

**2.3 `workspace.controller.spec.ts`（`describe('XpertWorkspaceController permission boundaries')`）** —— 6 个 it：所有集合端点都走"成员感知列表"（`findAllMy` 系列）；分页走安全投影（`WorkspacePublicDTO`）；update/delete 端点走 manage 授权的 service 方法；**create 走 sanitized 边界，不接受客户端身份字段**；忽略请求的 `relations` 只回安全投影；成员以 `UserPublicDTO` 返回。

**2.4 `workspace.service.spec.ts`（`describe('XpertWorkspaceService')`）** —— 覆盖：多租户参数化；`findAllMyEntities` 收到 `{ purpose: 'authoring' }`；create 不接受 client identity / owner / system 字段；显式默认工作区可访问时的返回、不可用时的回落、authoring 目的下不可用时的忽略、把可选工作区存为默认、跨组织默认被拒、不可访问默认被拒；可见性更新（保留其他 settings、拒绝对组织工作区设 tenant-shared、拒绝对租户工作区设 organization-shared、`['organization-shared','private']` 参数化）；无管理权限时拒绝可见性更新；只更新可变字段。

**2.5 `guards/workspace-authoring.guard.spec.ts`（`describe('Workspace authoring HTTP boundary')`）** —— 3 个断言组：非法（非 UUID）id 时 `assertCanAuthor` **不被调用**；合法 id 时仍调用 `assertCanAuthor(id)`。

**2.6 `commands/handlers/ensure-personal-default-workspace.handler.spec.ts`（`describe('EnsurePersonalDefaultWorkspaceCommand')`）** —— 通过 `CommandBus.execute(new EnsurePersonalDefaultWorkspaceCommand('Bosi'))` 覆盖幂等/复用/作用域缺失等分支（仓库 mock）。

**2.7 `commands/handlers/ensure-personal-default-workspace.handler.integration.spec.ts`** —— 真 PostgreSQL 版本（见第 5 节）。

## 3 文件访问相关 spec

**3.1 `xpert/assistant-files/assistant-files.service.spec.ts`（`describe('AssistantFilesService storage')`）** —— 4 个 it，真实临时目录（`mkdtemp(path.join(tmpdir(), 'assistant-files-'))`）+ 真实 `VolumeHandle`：上传是内容寻址的原子写入并返回可移植引用；缺失工作区可自动初始化且列表不依赖 conversation；每次上传/读取都绑定当前用户（`user` 隔离卷）；**Studio 权威在上传路径被保留，运行时权威不被静默改变**。

**3.2 `xpert/assistant-files/assistant-files.integration.spec.ts`（`describe('Assistant file authority integration')`）** —— 最具价值的一篇：真实 `XpertWorkspaceAccessService` + `PublishedXpertAccessService` + `XpertService`（仓库 mock，含原生查询桩）与**真实文件系统上的 `VolumeHandle`**，逐条对齐 AGENTS.md 不变量：① 仅用户组用户可协作文件而创作工作区访问被拒（`canRun:true, canRead/canWrite/canManage:false`，且 `xperts.findOne` 抛 Access denied）；② 授权用户共享同一文件、`user` 卷互相隔离；③ 某工作区 `canRun` 不等于该工作区内每个 Assistant 都可访问；④ `read/save/delete` 参数化的跨作用域拒绝；⑤ 创作草稿可用但不静默放开未发布运行访问；⑥ `tenant` / `organization` 参数化的跨域拒绝（且**在打开卷之前**拒绝）；⑦ 委派 secret 背后的用户组被复查；⑧ 授权文件操作仍保留 `..` 穿越防护；⑨ 跨 API 实例共享同一用户卷；⑩ 应用存储按 actor 隔离、拒绝共享工作区与过期绑定；⑪ 撤销后与切换为 shared 模式后重新校验；⑫ 私有文件投影不得被重定向进新近共享的工作区；⑬ **Studio 草稿上传走 authoring 权威，且不从 runtime 回落**。

**3.3 `ai/assistant-files-runtime.http.spec.ts`（`describe('workspace file HTTP authentication')`）** —— 最大的 HTTP 面（20 个 it / `it.each`）：能力查询仅对认证且绑定正确的运行态调用者开放；JWT 与委派读取的 `it.each(routes)` 不触发 401 重试；下载在保留资源/组织/purpose 校验下用 owner JWT；匿名/非法/错误 Assistant/已发布 app 的批量拒绝；域授权拒绝传播；`['fixture-jwt','cs-x-user','cs-x-enterprise']` 参数化的多凭证矩阵；缺失凭证与 Assistant/owner/tenant/organization 错配拒绝；**流式返回前复查被撤销的资源访问、文件身份与作用域**；过期与异会话 grant 拒绝；project scope 变更拒绝；即使 ChatKit 凭证有效也拒绝过期/已撤销会话；未认证/公共/错配的 file-session 管理前置拒绝；委派入口的 DTO 校验仍生效；管理类 file-session 路由要求登录态；授权与撤销按**存储的 Assistant 绑定**校验；列表 `deepth` 强制转换与根路径缺省、拒绝额外/非法字段；写与删除的作用域校验；`upload` / `save-binary` 的 multipart 校验并转发精确字节。

**3.4 `ai/workbench-files-routing.http.spec.ts`** —— 同时挂载 `FileUnderstandingController` 与 `WorkbenchFilesController`，用 `describe.each` 覆盖**两种注册顺序**，断言 `/conversations/:id/files` 仍是附件、`/workspace/files` 是运行目录，且 `workspace/file` 与旧 `file` 单文件路由都能读写删。

**3.5 `ai/workbench-files-auth.guard.spec.ts`（`describe('Workbench files route authorization')`）** —— 4 个 it：先加载持久化对话再放行；拒绝另一 Assistant 的对话（`ForbiddenException`）；公共 client secret 不查对话数据；对话不存在返回 `NotFoundException`。

**3.6 `xpert/xpert.controller.spec.ts`** —— 间接覆盖 Studio 文件面：以 mock 提供 `XpertWorkspaceFilesService` 并断言控制器装配与委派。

## 5 需 DB 的用例

`sensure-personal-default-workspace.handler.integration.spec.ts` 是**唯一**需要真数据库的用例，门槛与形态如下：

- 开关：`const postgres = process.env.PERSONAL_WORKSPACE_PG_E2E === '1' ? describe : describe.skip` —— 未设环境变量时整篇 **skip**（不会因缺库而挂 CI）。
- 连接：`new DataSource({ type: 'postgres', host: DB_HOST ?? '127.0.0.1', port: DB_PORT ?? 5432, username: DB_USER ?? 'postgres', password: DB_PASS, database: DB_NAME ?? 'postgres' })`。
- 隔离手段：用 `EntitySchema`（`PersonalWorkspaceFixture` / `PersonalWorkspaceMemberFixture`）映射到 `CREATE TEMP TABLE personal_workspace_fixture / personal_workspace_user_fixture / personal_workspace_members_fixture`，注释明写 "Connection-local tables exercise real PostgreSQL types without modifying user workspaces."。
- 覆盖点：① 首次调用创建、重试复用同一工作区，且 owner 为 UUID、`settings.system.userId` 以 JSON 文本比较命中；② 忽略不匹配的 JSON 身份，且不把任意 JSON 文本当作 UUID 解析（对应 handler 里 `CAST(:userId AS text)` 的写法）。

## 7 缺口：文件授权回归的自动化覆盖

**已被自动化覆盖**（对照第 3 节逐条）：用户组授权与创作成员资格解耦（组合级 + 工作区级）、跨 Assistant 拒绝、跨 tenant/organization 拒绝（且在打开卷之前）、撤销后复查（服务级与 HTTP 级各一份）、`user` 卷按用户隔离、Studio 草稿与 runtime 不回退、`..` 穿越防护、会话 grant 过期/撤销/异会话、路由分离双注册顺序、委派凭证的 audience 矩阵。

**未被自动化覆盖的缺口**：

1. **端到端多账号流**：45 项验收里的"移出用户组后用**原 JWT / 原 ChatKit 会话**立即 403"依赖真 DB 的用户组成员关系变更 + 真实签发 token 的复用；spec 里对应场景用 mock 的 `getCount()` 桩控制（`groupGrant` 布尔），**不能**证明真实撤销链路。
2. **Cloud 前端与 SDK 客户端**：验收文档明确记录了 Cloud 页面目录打开/编辑/保存 与 `xpert-sdk-js` Workbench 客户端改用新路径（`/ai/conversations/:id/workspace/*`）并要求"发布时同步交付 SDK 更新"；本仓 spec 只覆盖后端控制器，**SDK 侧路径对齐**没有跨仓回归。
3. **文件协作的并发/一致性**：没有针对同一共享文件并发写、`uploads/<sha256>` 内容寻址冲突或卷内大文件（100MB 上传上限）的自动化用例。
4. **`workspaceDataScope` 缺省与不可变**：`resolveXpertDataVolumeScope` 的缺省 `shared` 与 `xpert.workspaceDataScope` 创建后不可改，只在组合级 spec 间接体现，**没有**独立的映射表驱动用例。
5. **`XpertWorkspaceService.canAccess` 的误用防护**：AGENTS.md 把它列为禁止的文件 ACL，但仓库中**没有**断言"文件路径不调用 canAccess / `XpertService.findOne()`"的结构性测试（例如依赖图或 spy 级防护），只能靠 review。
6. **真机验收的可重复性**：如第 6 节所述，45 项断言没有脚本载体，未来要"重跑同一验收"必须重做一遍人工流程。

## 8 结论

本子域的测试策略与它的架构不变量是对齐的：**不 mock 授权服务本身**。`assistant-files.integration.spec.ts` 直接实例化真实的 `XpertWorkspaceAccessService`、`PublishedXpertAccessService`、`XpertService` 与 `AssistantFilesService`，只在持久化与原生活卷解析处打桩，因此"用户组能跑但不能创作"这类判定是**真跑**出来的；`assistant-files-runtime.http.spec.ts` 与 `workbench-files-routing.http.spec.ts` 再用真控制器 + 真路由补上"守卫与路由"这一层——后者专门防的是**单控制器测试无法发现的注册顺序冲突**，这也是 2026-10-09 验收暴露的真实缺陷类型。

主要缺口是"最后一公里"：真机验收里的多账号、真 token 撤销、Cloud 与 SDK 路径对齐都还没有脚本化；`workspace-access.service.spec.ts` 的 22 个用例虽然覆盖了 API-key / client-secret 的多受众矩阵，但仍是 mock 查询。建议的下一步不是增加更多 mock 用例，而是把 45 项断言中**可脚本化**的部分（用户组增删 + 真实 HTTP 请求 + 真实卷目录比对）固化成一条可重复的后端集成测试链，同时保留 Cloud/SDK 的人工验收清单。
