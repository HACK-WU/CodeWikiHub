## 1 表总览

本子域只拥有**一张实体表**（`xpert_workspace`）与**一张由 `@JoinTable` 生成的连接表**（`xpert_workspace_member`）；另有两条**外域关系**从本表出发：`Environment.workspace`（1:N 反向）与 `Xpert.workspace`（`WorkspaceBaseEntity.workspaceId`，1:N 反向）。

| 表 / 连接表 | 类型 | 实体 | 说明 |
|---|---|---|---|
| `xpert_workspace` | 实体表 | `XpertWorkspace`（`TenantOrganizationBaseEntity`） | 创作容器：名称、描述、状态、`settings` json、`ownerId` |
| `xpert_workspace_member` | 连接表 | 无实体类（`@ManyToMany(() => User)` + `@JoinTable({ name: 'xpert_workspace_member' })`） | 成员授权；**无角色列**（成员即等价权限） |
| `environment` | 外域实体表 | `Environment`（`WorkspaceBaseEntity`） | 通过 `XpertWorkspace.environments` 反向声明（字符串关系 `'Environment'`） |
| `xpert` | 外域实体表 | `Xpert`（`WorkspaceBaseEntity`） | 通过 `workspaceId` 归属工作区；不含外键级联声明（继承基类） |

本表**没有**独立的能力列、**没有**成员角色列、**没有** `deletedAt`（软删由基类 CRUD 语义承担时，`TenantOrganizationBaseEntity` 本身不带 `@DeleteDateColumn`）。也**没有** DB 层 CHECK 约束保护 `status` 与 `settings.access.visibility` 的取值集合。

章节来源：[xpert-workspace/workspace.entity.ts](file://packages/server-ai/src/xpert-workspace/workspace.entity.ts)（关键符号：XpertWorkspace / 表 xpert_workspace）、[packages/server-ai/src/environment/environment.entity.ts](file://packages/server-ai/src/environment/environment.entity.ts)（关键符号：Environment.workspace）

## 2 xpert_workspace

| 列 | 类型 / 长度 | 可空 / 默认 | 说明 |
|---|---|---|---|
| `id` | uuid，主键 | NOT NULL（`@PrimaryGeneratedColumn`，基类） | |
| `tenantId` | 基类 | 可空 + `@Index` | 租户隔离 |
| `organizationId` | 基类 | 可空 + `@Index` | **可空即"租户级工作区"**，决定可见性可选值 |
| `name` | varchar（无显式长度） | NOT NULL（`@Column()` + `@IsString`） | 名称 |
| `description` | varchar(500) | 可空 | |
| `status` | varchar | 可空，**无 DB 默认值** | `TXpertWorkspaceStatus = 'active' \| 'deprecated' \| 'archived'`；NULL 视为非归档 |
| `settings` | json（`@Column({ type: 'json' })`） | 可空（`@IsJSON` + `@IsOptional`） | 见第 5 节 |
| `ownerId` | varchar（`@Column({ nullable: true })` + `@RelationId`） | 可空 | 指向 `User`；用于 `isOwner` 判定与个人默认工作区查找 |
| `createdById` / `updatedById` | 基类 | 可空 | |
| `createdAt` / `updatedAt` | timestamptz | 基类管理 | |

**非持久化字段（仅内存投影）**：`capabilities?: TXpertWorkspaceCapabilities`、`isTenantShared?: boolean` —— 由 `XpertWorkspaceAccessService.buildAccess` 在返回前注入，DB 中无对应列。

**索引与唯一约束**：实体装饰器上**没有**声明任何复合唯一索引或 partial index。`tenantId` / `organizationId` 的单列索引来自 `TenantOrganizationBaseEntity`。因此"同一用户在同一组织下不应有多个 `user-default` 工作区"**不是** DB 约束，而是 `EnsurePersonalDefaultWorkspaceHandler` 的查询语义 + 注释里的调用方序列化要求（`EnsurePersonalDefaultWorkspaceCommand` 的 JSDoc："The caller serializes first-time creation for the current tenant / organization / user."）。

**关系与级联**：

| 关系 | 类型 | 级联 / 外键 |
|---|---|---|
| `owner` | `@ManyToOne(() => User)` + `@JoinColumn()` | **无 onDelete 声明** |
| `members` | `@ManyToMany(() => User)` + `@JoinTable({ name: 'xpert_workspace_member' })` | 连接表由 TypeORM 生成列名 |
| `environments` | `@OneToMany<IEnvironment>('Environment', 'workspace')` | `cascade: ['insert','update','remove','soft-remove','recover']` |

**业务约束**（应用层，非 DB）：`createWorkspace` 只接受 `name/description/status/settings.access.visibility`，`ownerId` 强制取自 `RequestContext.currentUserId()`；成员必须是同租户用户、且（组织工作区时）同组织的 `isActive` 成员；`tenant-shared` 要求 `organizationId` 为空、`organization-shared` 要求非空；`archived` 在 `getCapabilities` 中直接判为无权限。

## 3 xpert_workspace_member

连接表由 `@JoinTable({ name: 'xpert_workspace_member' })` 生成；**实体未显式指定 `joinColumn` / `inverseJoinColumn`**，因此列名由 TypeORM 按实体属性名推导（`workspaceId` → `XpertWorkspace.id`，`userId` → `User.id`）。

| 列 | 类型 | 可空 / 默认 | 说明 |
|---|---|---|---|
| `workspaceId` | uuid | 由 TypeORM 生成 | 外键指向 `xpert_workspace.id` |
| `userId` | uuid | 由 TypeORM 生成 | 外键指向 `user.id` |

**索引与唯一约束**：实体装饰器**未声明**任何索引或唯一约束，因此"同一用户在同一工作区只出现一行"依赖 TypeORM 的 M:N 主键/去重行为而非显式业务声明；**该模块无此项**（无显式索引声明）。

**语义**：成员资格是**等价授权**——没有角色列，`getCapabilities` 用 `workspace.members?.some(member => member.id === userId)` 判定 `isMember`，在组织工作区分支中 `isMember` 与 `isOwner` 同为 `canWrite` 的充分条件（`canManage` 仍需 owner 或"组织共享 + 租户管理员"）。成员写路径：`updateMembers`（整体覆盖）、`ensureMember`（幂等追加）、`removeMemberFromOrganizationWorkspaces`（批量移除，排除 `user-default` 工作区）。

**关键边界**：`xpert_workspace_member` **不参与** Assistant 文件授权。AGENTS.md 明写 "UserGroup access must work without authoring workspace membership"，运行时可访问性由 `xpert_to_user_group` + `user_group` + `user_group_to_user`（`hasPublishedXpertRunAccess` 的原生 SQL）决定，与成员表无关。

章节来源：[xpert-workspace/workspace.entity.ts](file://packages/server-ai/src/xpert-workspace/workspace.entity.ts)（关键符号：XpertWorkspace.members / @JoinTable）、[xpert-workspace/workspace-access.service.ts](file://packages/server-ai/src/xpert-workspace/workspace-access.service.ts)（关键符号：XpertWorkspaceAccessService.getCapabilities / hasPublishedXpertRunAccess）

## 4 environment 关联

`XpertWorkspace.environments` 是**字符串关系声明**（`@OneToMany<IEnvironment>('Environment', 'workspace', { cascade: [...] })`），实体侧不在本模块注册：

- `Environment` 实体定义在 `packages/server-ai/src/environment/environment.entity.ts`，是 `WorkspaceBaseEntity` 子类，因此带 `workspaceId` / `publishAt` / `deletedAt`。
- 表由 `EnvironmentModule` 注册；`XpertWorkspaceModule` 的 `TypeOrmModule.forFeature([XpertWorkspace, User, UserOrganization])` **不含** `Environment`，跨模块读取时容易忘记租户过滤。
- 本子域**不**经手 Environment 的写入（另属"模板·市场·绑定·环境"子专家），只在 `WorkspacePublicDTO` 中显式 `@Exclude()` 掉该关系，避免经工作区接口泄露环境变量。

**是否存在 member / environment 的独立关联实体**：该模块无此项 —— 两者都不是本子域定义的实体：成员是 `@JoinTable` 连接表（无类），环境是外域实体（有类但不在本模块）。

章节来源：[xpert-workspace/workspace.entity.ts](file://packages/server-ai/src/xpert-workspace/workspace.entity.ts)（关键符号：XpertWorkspace.environments）、[xpert-workspace/workspace.module.ts](file://packages/server-ai/src/xpert-workspace/workspace.module.ts)（关键符号：TypeOrmModule.forFeature）、[xpert-workspace/dto/public.dto.ts](file://packages/server-ai/src/xpert-workspace/dto/public.dto.ts)（关键符号：WorkspacePublicDTO）

## 5 settings json 与 access.visibility

`TXpertWorkspaceSettings`（contracts）定义两个键：

```ts
access?: { visibility?: TXpertWorkspaceVisibility }
system?: { kind?: 'org-default' | 'tenant-default' | 'user-default' | 'plugin-app'; userId?: string; pluginName?: string; appName?: string }
```

`access.visibility` 取值与语义：

| 取值 | 语义 | 生效前提 | 能力影响 |
|---|---|---|---|
| `private` | 私有（缺省与未知值的回落） | 任意 | 仅 owner / member / 租户管理员可见 |
| `tenant-shared` | 租户级只读共享（无组织维度） | **要求 `organizationId` 为空** | `canRead`/`canRun` 恒 true；`canWrite`/`canManage` 仅租户作用域下的 owner 或租户管理员 |
| `organization-shared` | 组织内共享（不物化成员行） | **要求 `organizationId` 非空** | 当前组织成员 `canRead = canWrite = true`；`canManage` 还需 owner 或（组织共享 + 租户管理员） |

规范化与判定辅助（`packages/contracts/src/ai/xpert-workspace.model.ts`）：`getXpertWorkspaceVisibility()` 只把 `tenant-shared` / `organization-shared` 原样返回，其余一律回落 `'private'`；`isTenantSharedXpertWorkspace()` / `isOrganizationSharedXpertWorkspace()` 是两个布尔包装。**注意**：写入侧（`applyVisibility`）非法值抛 `BadRequestException`，读取侧（`getXpertWorkspaceVisibility`）非法值静默降级为 `private` —— 失败方向是收紧，但两者行为不对称。

`system.kind` 语义（由 SQL 原生片段读取，不在类型里强校验）：`'user-default'` 标记个人默认工作区（配 `system.userId`），`'org-default'` 被 `findOrganizationDefaultWorkspace` 使用，`'plugin-app'` / `'tenant-default'` 只在类型联合中出现。

章节来源：[packages/contracts/src/ai/xpert-workspace.model.ts](file://packages/contracts/src/ai/xpert-workspace.model.ts)（关键符号：TXpertWorkspaceSettings / getXpertWorkspaceVisibility / isTenantSharedXpertWorkspace）、[xpert-workspace/workspace.service.ts](file://packages/server-ai/src/xpert-workspace/workspace.service.ts)（关键符号：XpertWorkspaceService.applyVisibility / findUserDefaultWorkspace）

## 6 迁移与 seed

**迁移**：本子域目录（`packages/server-ai/src/xpert-workspace/migrations/`）**不存在**，`xpert_workspace` 与 `xpert_workspace_member` 没有手写 SQL 迁移文件，建表依赖 TypeORM `synchronize`（与邻域 `assistant-binding/migrations/*.sql` 那类"加可空列"补丁不同）。因此该模块无此项（无迁移脚本）。

**seed / Seeder 实现**：本子域目录内检索不到任何 seed 实现，该模块无此项。

**初始化逻辑的替代形态——`ensure*` handler**：本子域的数据初始化不是 seed 而是**幂等命令**：

- `EnsurePersonalDefaultWorkspaceCommand`（`static readonly type = '[Xpert Workspace] Ensure personal default'`，构造参数为 `name`）→ `EnsurePersonalDefaultWorkspaceHandler.execute()`：先 `ResolveUserOrganizationAccessCommand` 校验组织访问 → 按 `tenantId + organizationId + ownerId + settings.system.kind='user-default' + settings.system.userId` 查候选 → 命中"非归档 + `visibility` 为 `private` + 无成员"即复用 → 否则以 `settings: { access: { visibility: 'private' }, system: { kind: 'user-default', userId } }`、`status: 'active'`、`members: []` 新建 → 建/复用后均执行 `access.assertCanAuthor(workspace.id)`。
- 调用方是 `assistant-binding/bosi/bosi-onboarding.service.ts`（Bosi 首次引导），即"个人 Assistant 不得继承共享工作区的受众或凭证"这条不变量（handler 文件头注释）的落地。
- 另一类"初始化"是运行时的默认工作区回落：`XpertWorkspaceService.findMyDefault` → `UserOrganizationService.getCurrentUserDefaultWorkspaceId()`（显式默认）→ 回落 `findUserDefaultWorkspace`（`system.kind = 'user-default'`）。

章节来源：[xpert-workspace/commands/handlers/ensure-personal-default-workspace.handler.ts](file://packages/server-ai/src/xpert-workspace/commands/handlers/ensure-personal-default-workspace.handler.ts)（关键符号：EnsurePersonalDefaultWorkspaceHandler.execute）、[xpert-workspace/commands/ensure-personal-default-workspace.command.ts](file://packages/server-ai/src/xpert-workspace/commands/ensure-personal-default-workspace.command.ts)（关键符号：EnsurePersonalDefaultWorkspaceCommand）

## 7 已知风险与坑

1. **`status` 无默认值与 CHECK**：`@Column({ type: 'varchar', nullable: true })` 无 DB 默认；能力判定把 NULL 当作非归档（`applyCurrentReadScope` 用 `workspace.status <> 'archived'` OR `IS NULL`），写错枚举值会被当成"可用"而非拒绝。
2. **`settings.access.visibility` 是 SQL 隐式契约**：可见性在多处被原生片段读取（`applyCurrentReadScope`、`TENANT_SHARED_WORKSPACE_FILTER` 类条件），`COALESCE(..., 'private')` 只在**缺键**时收紧；若把键改名或把 `settings` 类型从 json 迁移到 jsonb 语义之外的结构，判定会静默失效而不会编译报错。
3. **`system.kind` / `system.userId` 属未受约束的 json**：`user-default` 的唯一性靠 handler 查询 + 调用方序列化，DB 无从阻止两个 `user-default` 工作区并存；`CAST(:userId AS text)` 的写法也说明 JSON 抽取是 text 比较，注意大小写/类型陷阱。
4. **连接表无显式索引/唯一声明**：`xpert_workspace_member` 的列名由 TypeORM 推导，任何改名（属性名变化）都会连带改列名，而 `getCapabilities` 的 `isMember` 判定依赖 TypeORM 关系加载（不依赖列名），但外部原生 SQL 若引用该表会立即失效。
5. **成员集合是"整体覆盖"语义**：`updateMembers` 直接 `workspace.members = memberIds.map(...)` 后 `save`，并发两次更新会互相覆盖（无版本号、无锁）。
6. **`ownerId` 无 onDelete 声明**：用户删除后工作区可能留下悬挂 owner；`isOwner` 判定会落到 false（对应用户 id 不再匹配），使工作区退化为"仅租户管理员可管理"。
7. **能力位不是持久化状态**：`capabilities` / `isTenantShared` 只存在于返回对象的注入结果中；把它们当列查询（例如写进 SQL 或做索引）会失败，
   这也是"`canRead/canRun` 不是文件权限"在模型层的一个副证。

## 8 结论

模型层极简：**一张实体表 + 一张 M:N 连接表**即可承载"创作容器"的全部语义，权限差异（可见性、成员、租户/组织作用域）全部由 `settings` json 与 `TenantOrganizationBaseEntity` 的两列（`tenantId` / `organizationId`）推导，能力位永不落库。这种设计的最大收益是改动成本低（加一种可见性只需改 `applyVisibility` + 两个判定函数），最大代价是**所有约束都在应用层**：`status` 无 CHECK、`visibility` 无 CHECK、`user-default` 无唯一索引、连接表无显式索引。

对文件授权的模型含义更直接：**文件不在这张表里**。Assistant 文件属于数据卷（`xperts` / `user-xperts` 目录），因此 `xpert_workspace` 的 schema 变更（改名、加列、改可见性语义）**不应该**影响文件权限；反过来说，任何试图"用工作区成员表或可见性列推导文件权限"的实现都是模型层面的越权 —— 这正是 AGENTS.md 与 `AssistantFileAccessService` 文件头共同钉住的边界。
