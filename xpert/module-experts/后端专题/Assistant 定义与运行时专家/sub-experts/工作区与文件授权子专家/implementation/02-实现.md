## 1 工作区能力计算

实际签名是 `getCapabilities(workspace: XpertWorkspace, options?: { includePublishedRunAccess?: boolean })`：**没有** `user` 形参（用户、租户、组织全部来自 `RequestContext.currentUser()` / `getOrganizationId()` / `isTenantScope()`），也**没有** `{ purpose }`——`purpose` 只出现在列表入口 `findAccessibleWorkspaces(orderBy, { purpose })` 与控制器查询参数上。

判定顺序（自上而下短路）：

1. `!sameTenant || workspace.status === 'archived'` → `emptyCapabilities()`（四项全 false）。
2. **api-key 绑定命中**：`currentApiKeyBoundWorkspaceIdForUser(user)` 返回的 workspaceId 等于当前工作区 → `{canRead:true, canRun:true, canWrite:false, canManage:false}`（只读 + 只运行）。该私有方法按 `principalType === 'client_secret'`、`SecretTokenBindingType`（`PUBLIC_XPERT` / `ENTERPRISE_XPERT`）与 `resourceScope.kind`（`workspace` / `assistant`）区分路径，并额外校验 `xpert.publishAt IS NOT NULL`、`app.enabled`、`app.public`、`app.channels[platform].enabled/integrationId`，以及 `xpert.userId` 与当前用户一致。
3. **当前组织工作区**（`workspace.organizationId === RequestContext.getOrganizationId()`）：`canRead = isOrganizationShared || isOwner || isMember`；`canWrite = canRead`；`canRun = canRead || (includePublishedRunAccess !== false && hasPublishedXpertRunAccess(...))`；`canManage = isOwner || (isOrganizationShared && isTenantAdmin)`。此处源码注释明写 "A published Xpert grant unlocks execution only; it must not expose workspace authoring resources."。
4. **租户级工作区 + `tenant-shared`**：`canRead/canRun = true`；`canWrite = isTenantScope && (isOwner || isTenantAdmin)`；`canManage = canWrite`。
5. **租户级工作区 + tenantScope**：`canRead = isOwner || isMember || isTenantAdmin`；`canRun/canWrite = canRead`；`canManage = isOwner || isTenantAdmin`。
6. 其余 → `emptyCapabilities()`。

动作映射在私有 `can(capabilities, action)`：`read/run/write` 各取同名位，**其余动作（含 `manage`）落到 `canManage`**；`assertCanAuthor` 直接复用 `assertCanWrite`（无独立能力位）。批量场景由 `getResourceCapabilities(workspaceIds)` 承担（最多 100 个 id，强制 `includePublishedRunAccess: false` 以避免 N+1）。

`hasPublishedXpertRunAccess` 是一段**原生 SQL**：`xpert` join `xpert_to_user_group` / `user_group` / `user_group_to_user`，要求 `publishAt IS NOT NULL` 且 `user_group.organizationId` 与当前组织一致；注释要求别名保持小写（PostgreSQL 会折叠未加引号标识符，TypeORM 在 join SQL 里复用别名）。这正是"UserGroup 授权在无创作工作区成员资格时也能生效"的实现落点。

章节来源：[xpert-workspace/workspace-access.service.ts](file://packages/server-ai/src/xpert-workspace/workspace-access.service.ts)（关键符号：XpertWorkspaceAccessService.getCapabilities / hasPublishedXpertRunAccess / currentApiKeyBoundWorkspaceIdForUser / can）

## 2 工作区 CRUD 与成员可见性

- **创建**：`createWorkspace(input)` 从 `RequestContext.currentUserId()` 取 `ownerId`（缺失即 `BadRequestException`），`settings` **只保留** `access.visibility`（拒绝客户端身份/系统字段），`status` 默认 `'active'`。
- **列表**：`findAllMyEntities(options, purpose)` = `findAccessibleWorkspaces(order, { purpose })` 后逐个 `buildAccess(item)` 注入 `capabilities` / `isTenantShared`；`findAllMy` 再投影为 `WorkspacePublicDTO`。
- **读**：`findOne(id)` 非字符串分支回落基类；字符串分支走 `assertCanRead(id, { relations })`。控制器 `GET :workspaceId` 与 `GET :workspaceId/members` 由 `WorkspaceAuthoringGuard` 守。
- **成员**：`updateMembers(id, members)` 先 `assertCanManage` → `normalizeMemberIds`（数组校验 + `trim` + 去重）→ `userRepository.find({ id: In(ids), tenantId })` 要求**数量完全命中** → 若工作区有 `organizationId`，再校验 `UserOrganization`（同租户 + 同组织 + `isActive`）→ 覆盖 `workspace.members` 后 `save`。另有 `ensureMember(id, userId)`（幂等加成员，不判定）与 `removeMemberFromOrganizationWorkspaces(tenantId, organizationId, userId)`（用 relation 查询逐条移除，排除 `settings.system.kind = 'user-default'` 的工作区）。
- **可见性**：`updateVisibility(id, visibility)` 与 `updateWorkspace` 都调私有 `applyVisibility`：三值白名单（非法值抛 `t('server-ai:Error.WorkspaceVisibilityInvalid')`）、`tenant-shared` 要求**无** `organizationId`、`organization-shared` 要求**有** `organizationId`；写回时保留 `settings` 其他键（仅覆盖 `access.visibility`）。
- **生命周期**：`archiveWorkspace` = `updateWorkspace(id, { status: 'archived' })`；`softRemoveWorkspace` / `recoverWorkspace` / `deleteWorkspace` 均先 `assertCanManage` 再走基类的软删/恢复/硬删。
- **默认工作区**：`findMyDefault(purpose)` 先问 `UserOrganizationService.getCurrentUserDefaultWorkspaceId()`（不可访问则静默忽略），再回落 `findUserDefaultWorkspace(organizationId, userId)`（原生 SQL 读 `settings.system.kind = 'user-default'` 与 `system.userId`）；`authoring` 目的额外经 `assertCanAuthor`。`setMyDefault` 用 `assertCanAuthor(...).catch(() => null)` 把不可创作转成 404。
- **安全投影**：`WorkspacePublicDTO` 用 `@Exclude()` 排除 `members` / `environments`，`owner` 经 `@Transform` 转 `UserPublicDTO`。
- **幂等创建**：`EnsurePersonalDefaultWorkspaceHandler` 先经 `ResolveUserOrganizationAccessCommand` 校验组织访问，再按 `tenantId + organizationId + ownerId + system.kind='user-default' + system.userId` 查候选，命中"非归档 + private + 无成员"的即复用；否则以 `settings: { access: { visibility: 'private' }, system: { kind: 'user-default', userId } }` 新建，建/复用后都跑一次 `assertCanAuthor`。源码注释点明 `where ownerId makes the shared parameter a UUID; JSON ->> yields text`，故 JSON 侧用 `CAST(:userId AS text)` 比较。

## 3 文件访问解析

`AssistantFileAccessService.execute(command)` 是文件权限的**唯一判定点**，分支如下：

1. 取 `RequestContext.currentTenantId()` 与 `currentUserId()`，任一缺失 → `denied()`（`ForbiddenException`，i18n key `server-ai:Error.WorkspaceFileAccessDenied`）。
2. `entry === 'authoring'`：若 `RequestContext.currentApiPrincipal()` 存在 → 立即 `denied()`（注释："Delegated credentials cannot select the Studio authority, including internal callers."）；否则 `xperts.assertCanAuthorById(command.assistantId)` 后 `findOneByIdWithinTenant`。
3. 否则（runtime 分支）：`published.getAccessiblePublishedXpertForCurrentUser(command.assistantId)` —— 只认"当前用户可访问的已发布 Assistant"，草稿自然 404。
4. 复核 `xpert.tenantId === tenantId`，不等即 `denied()`。
5. `resolveXpertDataVolumeScope({ tenantId, userId, xpertId: xpert.id, workspaceDataScope: xpert.workspaceDataScope })` 得出卷作用域。
6. 返回 `{ scope, capabilities: { canList: true, canRead: true, canWrite: true, canDelete: true } }`：**能力位是显式全开策略**，隔离不靠能力位而靠卷目录根（共享卷 vs `user-xperts/<userId>`）。

`command.operation`（`'read' | 'write' | 'delete' | 'capabilities'`）在 handler 内**不参与分支**——它存在是为了让调用点表达意图并保留未来细粒度策略的位置；当前所有操作都落到同一判定序列。

Zod schema 在 HTTP 边界拦住形状问题：`workspaceFileQuerySchema`（`path` 必填、≤4096）、`workspaceFilesQuerySchema`（`path` 默认 `''`、`deepth` 0..32 强制转型）、`workspaceFileWriteSchema`、`workspaceFileUploadSchema`，全部 `.strict()`；注释明确 "Filesystem containment and symlink checks remain in VolumeSubtreeClient"。真正的越界防护在 `VolumeSubtreeClient.resolveSubtreeRelativePath`：`relative(subtreeRoot, absolutePath)` 以 `..` 开头或是绝对路径即抛 `BadRequestException`（对应验收里 `..` → 400）。

## 4 运行时与创作两条入口

`AssistantFilesService` 只有两个公开入口选择器，且在**服务端代码里硬编码**：

| 入口 | 方法 | 绑定方法返回的动作 |
|---|---|---|
| runtime | `forRuntime(assistantId)` | `capabilities`、`list`、`read`、`download`、`save`、`saveBinary`、`uploadToFolder`、`delete`、`upload` |
| authoring | `forAuthoring(assistantId)` | 同上（Studio 场景） |

两者共同落到私有 `bind(assistantId, entry)`：内部 `authorize(operation)` 每次执行 `commandBus.execute(new ResolveAssistantFileAccessCommand(assistantId, operation, entry))`，`client(operation)` 再 `volumeClient.resolve(scope).ensureRoot()` 并构造 `new VolumeSubtreeClient(volume, { allowRootWorkspace: true })`。文件头注释把不变量写进代码："Reauthorize each operation, including after a previously successful list or capability lookup."；`list/read/download` 用 `'read'`、`save/saveBinary/uploadToFolder` 用 `'write'`、`delete` 用 `'delete'`、`capabilities` 用 `'capabilities'`。

`upload(file)` 单独实现：先 `authorize('write')`，再 `createHash('sha256')` 算 `contentSha256`，写入 `uploads/<sha256>`，返回 `IArtifactWorkspaceFileReference`（`source: 'platform.workspace.files'`、`scopeId: scope.xpertId`、`workspacePath: /workspace/<filePath>`）；注释提醒 "This entry already chose runtime or Studio authority. Do not re-enter runtime ACL for drafts."。

**HTTP 落点**：
- 运行时：`AssistantWorkspaceFilesController`（`@Controller('assistants/:assistantId/workspace')`，`@Public()` + `ApiKeyOrClientSecretAuthGuard` + `AssistantFileAccessGuard` + `@AssistantFileAccess('workspace')`），端点 `GET capabilities`、`GET files`、`GET file`、`GET file/download`、`PUT file`、`DELETE file`、`POST file/upload`、`POST file/save-binary` —— **每个端点都重新 `forRuntime(id)`**。
- Studio：`XpertWorkspaceFilesService`（类注释 "Studio compatibility facade. Runtime routes must use AssistantFilesService.forRuntime()."）把 9 个方法全部转 `forAuthoring(id)`，由 `XpertController` 的 `:id/workspace/*` 端点以 `@UseGuards(XpertGuard)` 暴露（创作准入显式保留）。
- 会话文件：`WorkspaceFileAccessRuntimeController`（`@Controller('workspace-files/view-sessions')`）用 `@AssistantFileAccess('view-session-create' | 'view-session')` 声明 route policy。

章节来源：[xpert/assistant-files/assistant-files.service.ts](file://packages/server-ai/src/xpert/assistant-files/assistant-files.service.ts)（关键符号：AssistantFilesService.forRuntime / forAuthoring / bind / upload）、[xpert/xpert-workspace-files.service.ts](file://packages/server-ai/src/xpert/xpert-workspace-files.service.ts)（关键符号：XpertWorkspaceFilesService.list）、[ai/assistant-workspace-files.controller.ts](file://packages/server-ai/src/ai/assistant-workspace-files.controller.ts)（关键符号：AssistantWorkspaceFilesController.capabilities）

## 5 卷作用域解析

`resolveXpertDataVolumeScope({ tenantId, userId?, xpertId, workspaceDataScope? })` 是"Assistant → 卷目录"的**唯一映射点**，返回 `XpertDataVolumeScope` 两个联合分支之一：

| `workspaceDataScope` | 返回 | 语义 |
|---|---|---|
| `'user'` | `{ tenantId, catalog: 'user-xperts', userId, xpertId }` | 先按 Assistant 隔离、再按用户隔离；缺 `userId` 直接抛错（`server-ai:Error.XpertWorkspaceUserRequired`） |
| 其他 / 缺省 | `{ tenantId, catalog: 'xperts', userId?, isolateByUser: false }` | 共享卷：只按 tenant + Assistant 定位 |

缺省值来自 `DEFAULT_XPERT_WORKSPACE_DATA_SCOPE = 'shared'`（`packages/contracts/src/ai/xpert.model.ts`），因此 `shared` 分支的 `isolateByUser: false` 是常态。`getVolumeSubpath` 对 `catalog: 'xperts'` + `isolateByUser: false` 生成 `/xpert/<xpertId>`（不带 `/user/<userId>` 层级），对 `catalog: 'user-xperts'` 要求 `userId` 并走用户隔离路径；`getVolumePublicBaseUrl` 把 `user-xperts` 与"用户隔离的 xperts"划入私有路由，不使用可直链的公开子路径。

同一子域内还有一条**平行的创作卷入口**：`xpert-workspace/types.ts` 的 `getWorkspaceRoot(tenantId, workspaceId)` 走 `resolveRuntimeVolume({ catalog: 'workspaces', workspaceId })`。它与 Assistant 数据卷是两套 catalog，也**不参与**文件 ACL —— 与 AGENTS.md 的"创作容器不是文件权限"一致。

章节来源：[shared/volume/volume.ts](file://packages/server-ai/src/shared/volume/volume.ts)（关键符号：resolveXpertDataVolumeScope / XpertDataVolumeScope / getVolumePublicBaseUrl）、[xpert-workspace/types.ts](file://packages/server-ai/src/xpert-workspace/types.ts)（关键符号：getWorkspaceRoot）

## 6 守卫选型

| 守卫 | 做判定 | 使用位置（示例） |
|---|---|---|
| `WorkspaceAuthoringGuard` | `isUUID(params.workspaceId)` → `assertCanAuthor(workspaceId)`（= `canWrite`） | `XpertWorkspaceController` 的读端点、`xpert.controller.ts`（`WorkspaceAuthoringGuard`）、`environment.controller.ts`、`prompt-workflow.controller.ts`、`skill-package.controller.ts` |
| `WorkspaceOwnerGuard` | `params.workspaceId` 存在 → `assertCanManage(workspaceId)` | `XpertWorkspaceController` 的全部变更端点、`connector.controller.ts`、`mcp-consumer-oauth.controller.ts` |
| `WorkspaceGuard` | `assertCanRead(workspaceId)` | `connector.controller.ts`、`mcp-consumer-capabilities.controller.ts`、`mcp-consumer-oauth.controller.ts` |
| `AssistantFileAccessGuard` | 认证先行 + route policy（`workspace` / `view-session-create` / `view-session`）解析委派作用域；`workspace` 只接受 `USER_XPERT`，会话类再允许 `ENTERPRISE_XPERT`；登录用户（无 `principalType`）直接放行，交由域服务复查 | `AssistantWorkspaceFilesController`、`WorkspaceFileAccessRuntimeController` |
| `WorkbenchFilesAuthGuard` | 继承 `ApiKeyOrClientSecretAuthGuard`，加 `assertWorkbenchPrincipal(principal, conversation)` 宿主一致性 | `WorkbenchFilesController` |

选型规则：**创作容器**用 Workspace 三档（读/写/管理）；**文件**永远不用 Workspace 守卫，只用 `AssistantFileAccessGuard` + `ResolveAssistantFileAccessCommand` 双层。`AssistantFileAccessGuard` 的文档注释也把边界写清："File/View services retain resource authorization for every entry point."——守卫只做凭证 audience 与宿主一致性，资源授权仍在域服务。

章节来源：[xpert-workspace/guards/workspace-authoring.guard.ts](file://packages/server-ai/src/xpert-workspace/guards/workspace-authoring.guard.ts)（关键符号：WorkspaceAuthoringGuard.canActivate）、[xpert-workspace/guards/workspace-owner.guard.ts](file://packages/server-ai/src/xpert-workspace/guards/workspace-owner.guard.ts)（关键符号：WorkspaceOwnerGuard.canActivate）、[ai/assistant-file-access.guard.ts](file://packages/server-ai/src/ai/assistant-file-access.guard.ts)（关键符号：AssistantFileAccessGuard.canActivate / AssistantFileAccess）

## 7 设计模式及落点

| 模式 | 落点 | 说明 |
|---|---|---|
| CQRS + CommandBus | `ResolveAssistantFileAccessCommand`、`EnsurePersonalDefaultWorkspaceCommand` | 授权与个人工作区引导都被建模为可复用命令 |
| Guard（策略注入） | 三个 Workspace 守卫 + `AssistantFileAccessGuard` | 守卫只做前置判定与参数校验 |
| 装饰器元数据 + Reflector | `@AssistantFileAccess(policy)` + `FILE_ACCESS_POLICY` | 端点声明式标注 route policy，避免守卫内硬编码 URL 分支 |
| 模板方法 + 继承 | `XpertWorkspaceService extends TenantOrganizationAwareCrudService`、`XpertWorkspaceBaseService<T extends WorkspaceBaseEntity>`、`WorkbenchFilesAuthGuard extends ApiKeyOrClientSecretAuthGuard` | 复用租户/组织作用域与认证 |
| 外观（Facade） | `XpertWorkspaceFilesService` | Studio 兼容层，把入口选择固定在 `forAuthoring` |
| 出口白名单 | `WorkspacePublicDTO`（`@Exclude`）、`buildAccess` 注入而非序列化 | 防关系泄露 |
| 幂等引导（ensure*） | `ensureMember`、`EnsurePersonalDefaultWorkspaceHandler` | "已存在即复用" |

## 8 热点路径

1. **每次文件操作重授权**：`AssistantWorkspaceFilesController` 的 8 个端点各自 `forRuntime(id)`，每次触发 `ResolveAssistantFileAccessCommand` → `getAccessiblePublishedXpertForCurrentUser`（多受众查询）→ `resolveXpertDataVolumeScope` → `VOLUME_CLIENT.resolve(scope).ensureRoot()`。列表页 N 次刷新即 N 次准入查询；这是注释明确的有意取舍。
2. **能力计算 + 列表 SQL 双实现**：点读走 `getCapabilities`，列表走 `applyCurrentReadScope`（注释："Mirrors `getCapabilities` in SQL so list results cannot exceed point-read access."），其中 `TENANT_SHARED_WORKSPACE_FILTER` 类条件用原生片段 `COALESCE((workspace.settings)::jsonb -> 'access' ->> 'visibility', 'private')`。
3. **工作区列表 N+1**：`findAllMyEntities` 对每个工作区 `await buildAccess(item)`；组织工作区分支还会对每个工作区跑一次 `hasPublishedXpertRunAccess`（原生 count 查询），批量路径因此显式关掉 `includePublishedRunAccess`。
4. **`currentApiKeyBoundWorkspaceIdForUser`**：在 `getCapabilities` 与 `applyCurrentReadScope` 中都会被调用，内部含 `xpert` 原生查询（按 client secret 类型追加 `publishAt` / `app.enabled` / `app.public` / `app.channels.*` 条件），是委派凭证场景的热点。

## 10 技术债与 hack

1. **三元权限面选错即漏洞**：`XpertService.findOne()` / `XpertWorkspaceService.canAccess()` / workspace `canRun` 都能"看起来通过"文件访问，AGENTS.md 必须显式禁令；`canAccess` 仍作为公开方法存在（内部要求 `userId === RequestContext.currentUserId()` 且 `canRead`），是误用面。
2. **原生 SQL 读 `settings` json**：`TENANT_SHARED_WORKSPACE_FILTER` / `applyCurrentReadScope` / `findOrganizationDefaultWorkspace` / `findUserDefaultWorkspace` / `ensure-personal-default-workspace.handler` 都直接用 `COALESCE((workspace.settings)::jsonb -> ... ->> ...)`。`COALESCE(..., 'private')` 的失败方向是收紧，但**字段改名不会报错**，只会静默改变可见性或默认工作区命中。
3. **`getCapabilities` 缺 `purpose`**：`purpose` 只在列表侧生效（`authoring` 会剔除"跨组织 tenant-shared 只读"支），点读侧没有对应参数，因此"列表能看见但点读被拒"或反之需要靠两边实现同步维护。
4. **`operation` 参数当前不改变判定**：`read/write/delete/capabilities` 在 handler 内等价，能力位恒为全 true；隔离完全依赖卷根，未来若要收紧单个动作，需要在 handler 内新增分支并同步更新调用点语义。
5. **路由冲突史**：`GET /ai/conversations/:conversationId/files` 曾被 FileAsset（附件）与 Workbench（运行目录）双注册，本地命中前者返回空附件数组；现约定 FileAsset 保留原路径、Workbench 改用 `/ai/conversations/:id/workspace/*`，并由 `workbench-files-routing.http.spec.ts` 覆盖两种注册顺序。新增 controller 时同类冲突仍**无编译期保护**。
6. **`canRead` 与文件权限易混**：`WorkspaceAuthoringGuard` 用于读端点、`WorkspaceGuard` 用于 `connector` 读端点，两者名义相近；而文件侧完全没有 Workspace 守卫，排查越权时容易按"workspace"字面搜索到错误的守卫。
7. **`api-key 绑定分支` 与准入面判定重复**：client secret 的 audience 校验在 `PublishedXpertAccessService`、`AssistantFileAccessGuard`、`XpertWorkspaceAccessService.currentApiKeyBoundWorkspaceIdForUser` 三处各写一遍，任一处漏条件即出现"能读工作区但读不到文件"之类的错配。

## 11 设计维度分析

### 11.1 维度 A：入口选择（trusted code）vs 策略判定（handler）

文件授权是**唯一**把"选入口"和"判策略"显式分成两层的实现：入口由 `forRuntime()` / `forAuthoring()` 在服务端代码里固定，策略由 handler 的两个分支承担。好处是调用方**无法**通过请求数据越权（命令里没有来自 HTTP 的 entry），且策略改动只改一处；代价是每次操作付一次准入查询，且"运行时被拒后回退 authoring"这类错误无法在类型层面阻止，只能靠文件头注释与 review 维持。对比工作区面（Guard + Service 双层，无"入口"这一层）与准入面（单一查询构造器），后两者的入口即模块所在，因此不需要该层。

章节来源：[xpert/assistant-files/resolve-assistant-file-access.command.ts](file://packages/server-ai/src/xpert/assistant-files/resolve-assistant-file-access.command.ts)（关键符号：ResolveAssistantFileAccessCommand 注释）、[packages/server-ai/src/xpert/assistant-files/assistant-files.service.ts](file://packages/server-ai/src/xpert/assistant-files/assistant-files.service.ts)（关键符号：AssistantFilesService.bind）

### 11.2 维度 B：能力位显式全开 vs 按动作细粒度

`AssistantFileAccessService` 返回的 `capabilities` 当前恒为四项 true，隔离交给卷根（`xperts` 共享 vs `user-xperts/<userId>`）；而工作区面走了相反路线：四动作能力位逐条计算，甚至 `canRun` 允许在 `canRead = false` 时通过 UserGroup 授权为 true（"runtime-only"）。前者换来"共享即协作"的简单语义与最少的判定分支，代价是能力查询对客户端信息量低（同样返回全 true，无法提示"你只能读别人的文件"）；后者让"能被授权运行但不应编辑容器"成为可表达状态，代价是分支多、需要列表 SQL 镜像。若未来要支持只读共享文件，需要给文件侧引入与工作区侧同构的能力位计算，并同步改 `bind()` 的动作映射。

章节来源：[xpert/assistant-files/assistant-file-access.service.ts](file://packages/server-ai/src/xpert/assistant-files/assistant-file-access.service.ts)（关键符号：AssistantFileAccessService.execute 的 capabilities 返回）、[xpert-workspace/workspace-access.service.ts](file://packages/server-ai/src/xpert-workspace/workspace-access.service.ts)（关键符号：XpertWorkspaceAccessService.getCapabilities 的 canRun 分支）

## 12 结论

实现层面最值得复用的两点：**(1) 把授权本身建模为 Command** —— `ResolveAssistantFileAccessCommand` 让"每次操作重授权"变成一次可测试、可替换的调用，而不是每个控制器各写一遍 if；**(2) 用装饰器把 route policy 与凭证 audience 对齐** —— `@AssistantFileAccess('workspace' | 'view-session-create' | 'view-session')` + `AssistantFileAccessGuard` 让"哪种凭证能进哪类文件端点"集中在守卫一处判定，域服务只负责资源授权。

最值得警惕的三点：一是**入口泄漏**（任何把 `authoring` 变成 HTTP 参数、或在 runtime 403 后回落 Studio 的改动都会直接破坏第 5 节不变量）；二是**原生 JSON 契约**（`settings.access.visibility` 与 `settings.system.kind/userId` 是 SQL 层隐式契约，改名不报错）；三是**路由唯一性**（`/ai/conversations/:id/files` 的历史冲突已修，但同类双注册仍无编译期防护，必须靠 `workbench-files-routing.http.spec.ts` 这类"两个真控制器一起跑"的回归）。
