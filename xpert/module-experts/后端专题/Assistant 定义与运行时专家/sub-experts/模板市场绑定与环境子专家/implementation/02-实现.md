## 1 模板目录与装配链

`getAll` 并行取 `readTemplatesFile()`（externalRoot 的 `templates.json`）与 `getPluginTemplates()`（插件贡献，私有方法），按当前语言取 `recommendedApps`、缺失时回落 `fallbackLanguage`，再 `matchesTemplateQuery` 过滤并按 `getTemplateOrder` 排序。`getCatalog` 直接委托 `paginateTemplateCatalog`：`limit` 默认 48、硬上限 500，且**剥掉 `export_data`、`dslContent`、`targetAppMeta`**——目录响应永不含 DSL。`getTemplateDetail` 先 `parseCapabilityTemplateId` 拆出「模板 id + 能力变体」，再走私有 `getTemplateSourceDetail`（按 `BOSI_TEMPLATE_ID` → `BLANK_ASSISTANT_TEMPLATE_ID` → 插件模板 → `templates.json.details` → 内建描述符 的优先级，最后用 `withTemplateExportData` 从 `templates/<id>.yaml` 补 `export_data`），最终交给 `AssistantCapabilityService.compose` 生成变体模板（`capabilityTemplateId(template.id, selected)` + 重写 `export_data` + 清 `contentHash`）。`getMarketplaceRecommendedTemplates` 另行合并 `templates-market.yaml`、内建 `templates.json` 与插件模板。`getSkillsMarket` 走 `skills-market.yaml`（缓存键 `xpert:skills-market`，TTL 10 秒）并以 `ResolveTemplateSkillRefsCommand` 解析 featured 技能。

## 2 模板安装链

入口是 `XpertTemplateController.installTemplate`（`POST /api/xpert-template/:id/install`）：`parseTemplateInstallInput` 要求 `workspaceId` 非空（缺失 400）、`publish` 必须显式 `=== true`、`workspaceDataScope` 只接受 `shared|user`，然后执行 `PluginTemplateInstallCommand`。该命令的第 8 个参数 `bootstrap`（`resumeXpertId` + `onImported`）注释明写 **never accepted from an HTTP body**——只有 Bosi 服务端可传。`PluginTemplateInstallHandler.execute` 的顺序是：`assertCanAuthor(workspaceId)` → `getTemplateDetail` → `yaml.parse(export_data)` → `normalizeDraft`（把 `workspaceId` 写入 `team`、按可用 sandbox provider 纠正 `features.sandbox.provider`）→ `capabilities.prepareInstallation`（**在导入前重新查询模型授权，注释明写 “Never trust the UI preflight”**）→ `XpertImportCommand` → `resolveTemplateRuntimeDependencyComponents` + `installer.installComponentsForXpert` → 解析模板 toolset 依赖并改写 draft 的工具集节点 → 可选 `XpertPublishCommand` → `XpertTemplateWorkspaceInitializer.initializeByTemplateId`。安装 = **建 Assistant 行 + 工作区内建默认 prompt workflow（+ 可选发布）**，工作区本体不在此创建；非 bootstrap 路径失败时 `rollbackTemplateXpert` 只删 Assistant。

## 3 市场授权链

`requestAccess` 先 `currentOrganizationId()`/`currentUserId()` 强制上下文（缺失分别 403），再 `findDiscoverableXpert`（私有，`buildDiscoverableXpertQuery` = 同 tenant + `publishAt IS NOT NULL` + `latest = true` + `type IN (Agent, Copilot)` + 「tenant-shared 工作区」或「同组织」二选一）；`owned`/`accessible` 直接 400。已有记录若为 `REQUESTED`/`APPROVED` **原样返回**，否则原地重置 `status=requested` 并清空 `response`/`reviewerId`/`reviewedAt`/`accessGroupId`（重申会丢失旧授权指针）。`approveRequest` 三步副作用：`ensureAccessGroup`（先按 `{tenantId, organizationId, managedBy, managedEntityType, managedEntityId}` 查，命中即复用，否则建组，名字 `Xpert access - {label}` 截断 100）→ 把 requester 追进 `group.members` → 把组追进 `xpert.userGroups`；随后写 `status=APPROVED`、`reviewerId`、`response`、`reviewedAt`、`accessGroupId`。`rejectRequest` 不写 `accessGroupId`。运行时侧由 `hasRuntimeAccess`（私有）判定：无组织的 tenant-shared 工作区、工作区 owner/成员、或同 tenant+org 的 `userGroups[].members` 命中。

## 4 系统绑定链

`getEffectiveBinding(code)` 是本域唯一的回落入口：`ensureSystemManagedCode(code)` 拒掉 `clawxpert`；有组织上下文时先查 organization 绑定，命中即 `toResolvedBinding(..., ORGANIZATION)`；否则查 tenant 绑定（`organizationId: null`）；都没有则返回 `sourceScope: NONE` + `enabled: false` 的占位对象（不抛错）。所有查询走私有 `explicitWhere`——tenant 分支强制 `organizationId IS NULL AND userId IS NULL`，organization 分支强制 `userId IS NULL`，user 分支要求 org+user 都非空，从根上避免跨层误命中。`upsertBinding` 分两路：user scope 需 `ensureUserManagedCode` + `getAccessiblePublishedXpert`（并校验 `type === Agent && latest === true`），`enabled` 一律写 `null`；system scope 需 `ensureSystemWriteAccess`（tenant 要 `SUPER_ADMIN`，organization 要 `SUPER_ADMIN|ADMIN`）、`enabled` 必须是 boolean、并经 `ensureSystemAssistantSelectionAllowed`。偏好侧 `upsertBindingPreference` 只在绑定已存在时生效（否则 400），且按 `hasOwnPreferenceField` 逐字段合并——未传字段不清空。启动期 `onModuleInit` → `backfillLegacyBindings` 顺序执行 `backfillLegacySystemBindings`（`to_regclass('public.assistant_config')` 探测后读 `options.assistantId`）与 `backfillLegacyUserBindings`（`information_schema.columns` 五项齐备后读 `assistant_user_preference`），均以「已存在则跳过」写绑定。

章节来源：[assistant-binding.service.ts](file://packages/server-ai/src/assistant-binding/assistant-binding.service.ts)（关键符号：AssistantBindingService.getEffectiveBinding、AssistantBindingService.explicitWhere、AssistantBindingService.onModuleInit、AssistantBindingService.backfillLegacySystemBindings）

## 5 Bosi 桌面引导链

`BosiBootstrapController`（`@Controller('bosi')`）的 8 个端点全部只做 Zod 校验（失败统一 `server-ai:Error.BosiInvalidInput`）后转 `BosiBootstrapService`。服务端所有写操作都包在私有 `locked()` 里：`pg_try_advisory_lock(hashtext('bosi-bootstrap'), hashtext(JSON.stringify([tenantId, organizationId, userId])))`，抢不到锁即 `ConflictException(BosiCreating)`。`scope()` 固定 `code = AssistantCode.CLAWXPERT`、`scope = USER`，并优先取 `currentApiPrincipal().requestedOrganizationId`。`binding()` 先经 `ResolveUserOrganizationAccessCommand` 校验组织成员身份，再读绑定；`enabled === false` 或绑定助手不可访问都转成 403。`setup()` 在已有 `assistantId` 时只回进度（`publicProgress`），否则用 `BOSI_TEMPLATE_ID` 详情 + `capabilities.setup` 给出 `cloud-computer`/`desktop-shell` 两个可选能力探针与默认模型。`create()` 用 `PluginTemplateInstallCommand` 的 `bootstrap` 通道（`resumeXpertId` + `onImported` 写 `progress.draftId`）安装，模板名 `bosi-${binding.id}`、`workspaceDataScope: 'user'`、`publish: true`，完成后 `upsertBinding` 再置 `phase = 'welcome_pending'`。`welcome()` 在 `progress.threadId` 上 `ThreadCreateCommand(if_exists: 'do_nothing')` + `RunCreateStreamCommand`，`reconcileWelcome` 始终以**持久化执行记录**（`XpertAgentExecution`，`parentId IS NULL`）反推 `ready`/`welcome_running`/`welcome_failed`，而非依赖流回调顺序。`BosiOnboardingService` 则用 `EnsurePersonalDefaultWorkspaceCommand('Bosi')` 预留私有工作区（要求 tenant/org/owner 匹配、`members` 为空、`visibility === 'private'`），并在 `binding.assistantId || binding.desktopBootstrap` 已存在时对任何 onboarding 变更抛 `ConflictException(BosiOnboardingFinished)`。

章节来源：[bosi-bootstrap.service.ts](file://packages/server-ai/src/assistant-binding/bosi/bosi-bootstrap.service.ts)（关键符号：BosiBootstrapService.locked、BosiBootstrapService.create、BosiBootstrapService.reconcileWelcome）、[bosi-onboarding.service.ts](file://packages/server-ai/src/assistant-binding/bosi/bosi-onboarding.service.ts)（关键符号：BosiOnboardingService.workspace、BosiOnboardingService.mutable）

## 6 环境变量域

## 8 热点路径

1. **Bosi 每次请求都抢 advisory lock**：`BosiBootstrapController` 的 8 个端点最终都进 `locked()`，包括只读的 `setup`/`onboarding`；同用户并发会被 409 拒绝，桌面端首页因此是串行的。
2. **`findMarketplace` 是内存全量过滤**：`findDiscoverableXperts` 先 `getMany()` 拉全部可发现助手，再在 JS 里 `matchesFilters` + `sortItems` + 切片（`DEFAULT_TAKE = 60`、`MAX_TAKE = 200`），且每项还要 `canReviewXpert` → `XpertWorkspaceAccessService.getCapabilities`，属于典型的 N+1 组合。
3. **`installTemplate` 的副作用面**：一次调用可能触发 §2 的 6 个阶段（导入、插件组件安装、toolset 解析与 draft 改写、发布、工作区初始化）；只有非 bootstrap 路径有一次性 `rollbackTemplateXpert`。
4. **模板目录读取的 10 秒缓存**：`readTemplatesMarketConfig` / `readSkillsMarketCatalog` / `readSkillRepositories` / `readWorkspaceDefaults` / `readTemplates` 全部 `cacheManager.get → 读文件 → set(10s)`，因此改盘后最长 10 秒才生效，`invalidateSkillTemplateCaches` 是唯一主动失效入口。
5. **回填在 `onModuleInit` 同步执行**：`backfillLegacySystemBindings`/`backfillLegacyUserBindings` 逐行 `findOne` + `save`，行数大时直接拖慢启动。

## 10 技术债

1. **市场授权依赖 UserGroup 生命周期**：`xpert_access_request.accessGroupId` 外键为 `SET NULL`，且与 `xpert_to_user_group` 无反向同步；删组或改名后已审批记录仍显示 `approved`，而 `hasRuntimeAccess` 已为 `false`。
2. **启动回填多实例竞争**：`AssistantBindingService.onModuleInit` 探测旧表后逐行「查—写」，无 advisory lock 也无「插入冲突忽略」，多实例同时启动存在重复写入与唯一索引冲突面（仓库另有 `docs/plans/PLAN_multi_instance_remediation.md`）。
3. **模板安装副作用面大**：一次安装包含导入、插件组件安装、toolset 解析、可选发布、工作区初始化五类副作用，回滚只覆盖「删 Assistant」一步；`XpertTemplateWorkspaceInitializer` 失败仅 `logger.warn` 并返回 `status: 'failed'`，调用方不检查该返回值。
4. **`AssistantCode` 槽位与 Xpert 的耦合**：`assistant_binding.assistantId` 是无外键的 `varchar(64)`，助手删除后留下悬挂引用；系统槽位能选哪些助手由 `buildSystemXpertWhere` 的 `type/latest/publishAt/organizationId` 四条件隐式定义，与 `XpertTypeEnum`（含 `deprecated` 的 `copilot`）存在语义漂移风险。
5. **路由前缀拼接**：`XpertMarketplaceController` 无 `RouterModule.register`，同一 controller 用方法级路径产出两个前缀；`EnvironmentController`/`XpertTemplateController` 用空 `@Controller()` 依赖模块前缀——按首段聚合的网关白名单容易误判。
6. **模板内容与计数分家**：内容在文件系统（无事务、无版本、靠 `resolveExternalRelativePath` 拒绝绝对路径与 `..`），`xpert_template` 只存 `key`/`visitCount`/`lastVisitedAt` 且**无唯一索引**，`getMCPTemplate`/`getKnowledgePipeline` 的「先查后建」在并发下可写出重复 `key`。
7. **Bosi 锁与错误语义耦合**：`locked()` 抢不到锁直接 409，客户端必须自行重试；`reconcileWelcome` 靠执行记录状态反推阶段，`XpertAgentExecution` 的写入延迟会直接反映为桌面端进度回退。

## 11 设计维度

### 11.1 维度 A：模板内容放在文件系统还是数据库

`EnsureTemplateDirectoryHandler` 把内建模板「补种」到 externalRoot，其后所有读取（`readTemplatesFile`、`getExternalTemplatePath`）**只认 externalRoot**，DB 里只留访问计数。好处是运维可直接改盘热更新、插件可继续以文件形式贡献模板；代价是**失去事务与唯一约束**：`writeTemplatesFile` 是整文件 `fs.writeFile`，`upsertExportedXpertTemplateCatalog`/`removeExportedXpertTemplateCatalog` 是读—改—整写，多进程并发导出会互相覆盖。若改为 DB 存储，能拿到唯一索引与原子更新，但会丢掉「改盘即生效」与插件目录贡献这两条既有能力。

章节来源：[xpert-template.service.ts](file://packages/server-ai/src/xpert-template/xpert-template.service.ts)（关键符号：XpertTemplateService.writeTemplatesFile、XpertTemplateService.upsertExportedXpertTemplateCatalog）

### 11.2 维度 B：授权载体复用 UserGroup 还是独立 ACL 表

当前用 `UserGroup` 承载市场授权，收益是**运行时不需要新增查询路径**——`xpert_to_user_group` 已被准入与 `hasPublishedXpertRunAccess` 使用，审批结果立刻生效。代价是把「一条申请记录」的语义绑死在「一个可被任意改名的组织实体」上：组名、成员、删除都由 `UserGroup` 侧自由变更，而 `xpert_access_request` 只保存一个 `SET NULL` 指针。若改用独立 ACL 表，授权与组织架构解耦，但需要在准入查询里新增一条 join，且既有 `xpert_to_user_group` 数据需要迁移。

章节来源：[xpert-marketplace.service.ts](file://packages/server-ai/src/xpert-marketplace/xpert-marketplace.service.ts)（关键符号：XpertMarketplaceService.ensureAccessGroup、XpertMarketplaceService.approveRequest）

### 11.3 维度 C：服务端恢复态与客户端进度的分离

`BosiBootstrapService` 把「可恢复的执行现场」放在 `assistant_binding.desktopBootstrap`（`@Exclude({ toPlainOnly: true })`：`phase`/`capabilities`/`modelId`/`threadId`/`welcomeMessageId`/`welcomeRunId`/`draftId`），把「客户端可见进度」单独经 `publicProgress()` 生成。这让 HTTP 合同可以独立演进（客户端只依赖四字段），同时服务端保留重试所需的全部标识。代价是同一份状态有两个表示，任何新增恢复字段都必须同时决定「是否进白名单」，而 `@Exclude` 只作用于 `instanceToPlain` 方向——绕过 class-transformer 的序列化路径仍可能泄漏。

章节来源：[assistant-binding.entity.ts](file://packages/server-ai/src/assistant-binding/assistant-binding.entity.ts)（关键符号：AssistantBinding.desktopBootstrap）、[bosi-bootstrap.service.ts](file://packages/server-ai/src/assistant-binding/bosi/bosi-bootstrap.service.ts)（关键符号：BosiBootstrapService.publicProgress）

## 12 结论

实现层最值得复用的三点：**(1) `explicitWhere` 用三层显式 where 取代「靠调用方传对 scope」**——tenant 强制 `organizationId/userId IS NULL`，组织分支强制 `userId IS NULL`，把分层不变量下沉到查询构造；**(2) 安装前重新校验模型授权**——`prepareInstallation` 注释明写不信任 UI preflight，避免了「预检通过、安装时授权已撤销」的窗口；**(3) 授权复用既有读路径**——审批只写 UserGroup，不新增权限子系统。最值得警惕的三点已在技术债给出：模板内容的无事务整文件写、启动回填的无锁并发、以及 `AssistantBinding.assistantId` 的无外键悬挂引用。
