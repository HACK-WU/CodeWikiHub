## 1 定义 CRUD 与草稿保存

- **创建**：`XpertService.create()` 先 `validateTagAssociations`，再补 `workspaceDataScope`（缺省 `DEFAULT_XPERT_WORKSPACE_DATA_SCOPE`）与 `normalizeXpertAgentConfig(agentConfig)`，交给 `XpertWorkspaceBaseService.create()`；`create` 由 `XpertCreateHandler` 在命令层落地。
- **更新**：`XpertService.update()` 只是 `updateXpert()` 的浅层转发；`updateXpert()` 用 `findOne` 取实体、拦截 `workspaceDataScope` 变更（抛 `XpertWorkspaceDataScopeImmutable`，i18n key `server-ai:Error.XpertWorkspaceDataScopeImmutable`）、`assign(_entity, mutableEntity)`、`validateTagAssociations`、`super.save`。
- **保存草稿**：`saveDraft(id, draft)` 取 `findOne(id)`，若 `draft.team.options.templateSource` 存在则先并入 `xpert.options.templateSource`；随后写 `xpert.draft = { ...draft, nodes: normalizeMiddlewareNodes(draft.nodes), team: { ...draft.team, workspaceDataScope: xpert.workspaceDataScope, updatedAt, updatedById } }`，并把 `validate()` 的 `ChecklistItem[]` 挂到 `draft.checklist`，最后 `super.save(xpert)` 返回草稿。
- **增量改草稿**：`updateDraft(id, draft)` 做 team 浅合并（同样回写 `workspaceDataScope` 与 `updatedAt/updatedById`），仅当 body 含 `nodes`/`connections` 键才覆盖对应字段；校验时用 `nextDraft.nodes ?? xpert.graph.nodes` 兜底，因此「只改 team」的补丁不会把图字段实体化（有专门 spec 断言）。
- **校验**：`validate()` 依次跑 `FreeNodeValidator` 与 `eventEmitter.emitAsync(EventNameXpertValidate, new XpertDraftValidateEvent(draft, context))`，汇总为 `ChecklistItem[]`；`context` 携带 `tenantId/organizationId/xpertId/creatorId`。
- **命名唯一性**：`GET /xpert/validate?name=` → `XpertService.validateName(name)` → `convertToUrlPath` + `slug/latest:true` 计数。
- **删除**：`XpertDeleteCommand` → `XpertDeleteHandler`，服务侧 `deleteXpert(id)` 在行 `latest === true` 时按 `name` 族软删，否则只软删当前行。

## 2 发布链

`POST /xpert/:id/publish` → `XpertService.publish()` → `commandBus.execute(new XpertPublishCommand(id, newVersion, environmentId, notes, marketplace, businessAreaId))` → `XpertPublishHandler.execute()`。

`execute()` 的顺序是硬约束，值得逐段记：

1. 取 `xpert`（带 `agent`、`agents(+copilotModel)`、`knowledgebases`、`toolsets`、`userGroups` 等 relations）；`!xpert.draft` 直接 404。
2. `businessAreaId` 显式传 `null` 表示清空；传值则要求同租户 + 同组织（`organizationId ?? IsNull()`）命中，否则 400 `XpertBusinessAreaScopeMismatch`。
3. 非创建者且 `xpert.userGroups` 为空 → 400「Published xperts must be assigned to at least one user group.」
4. 版本号：同族 = `workspaceId + name`；`newVersion && currentVersion` 时把版本号最后一段 +1，冲突则追加 `.<index>`，否则沿用 `currentVersion || '1'`。
5. `promptWorkflowService.snapshotCommandProfile(workspaceId, commandProfile)` 把命令档案快照进草稿。
6. `validate(draft, context)` + `check(draft)`（游离节点 → 500 "There are free Xpert agents!"；重名节点 → 500 "duplicate names"）。
7. `draft.team.tags != null` 时 `validateTagAssociations({ ...xpert, tags })` —— 注释明写「Reject stale selections before backing up versions or writing agents」。
8. `newVersion && currentVersion` 时 `saveTeamVersion(xpert, version)` 备份旧版本。
9. 写 `releaseNotes`（newVersion 先清空再累加 `notes`）、`environmentId = normalizeEnvironmentId(...)`（空串归 null）、`businessAreaId`。
10. `publish(xpert, version, draft, marketplace)`：
    - `previousGraph = xpert.graph`（供增量触发器下线）；
    - 若 `draft.team.options.modelSelection` 存在，用 `resolveDraftPrimaryCopilotModel` + `normalizeAssistantAllowedModels` 归一允许模型；
    - 遍历 `draft.nodes` 中 `type === 'agent'` 的节点，按 `draft.connections` 收集 `toolset/knowledge/xpert` 关联，对既有 agent 走 `xpertAgentService.update`（新节点走 `create`，多余 agent `delete`）；旧 agent 比草稿新时抛 400 `xpert.Error.AgentOutdated`；
    - 主 agent 未出现在节点里则补 `options.hidden = true`；
    - 回写 `xpert.agents`、`toolsets`、`knowledgebases`、`executors`，并把每个节点的 `position/size` 记到 `options[type][key]`；
    - `xpert.graph = pick(draft, 'nodes', 'connections')`；`draft.team` 字段逐项覆盖 `title/titleCN/description/avatar/starters/tags/copilotModel/agentConfig/memory/summarize/features/commandProfile/options`；
    - `xpert.marketplace = buildXpertMarketplaceProfileSnapshot(marketplace ?? xpert.marketplace, draft)`；
    - `version` 赋值、**`draft = null`**、`publishAt = new Date()`、`active = true`、`agent = undefined`（避免二次更新主 agent 造成 `updatedAt` 不一致），`save`；
    - `ensurePrincipalUser(_xpert)`（仅当 `!xpert.userId` 且有 `xpertPrincipalService`）；
    - `commandBus.execute(new XpertPublishTriggersCommand(_xpert, { strict: true, previousGraph }))`；
    - `eventEmitter.emitAsync(EventName_XpertPublished, _xpert)`。

`graph` 与 `draft` 的关系因此可以一句话概括：**`draft` 是发布输入，`graph` 是发布输出**；发布是唯一把两者同步的官方路径，同事务的例外只有 `trigger-connection.change()` 与 `assistant-trigger.mutate()`。

## 3 版本与回滚

- `GET /xpert/:id/version` → `XpertService.allVersions(id)`：以当前行的 `workspaceId + type + slug` 取同族行，投影 `{ id, version, latest, publishAt, releaseNotes }`。
- `POST /xpert/:id/latest` → `XpertService.setAsLatest(id)`：目标行已是 `latest` 则空操作；否则把族内 `latest = true` 的行全部改 false，再置当前行 true，一次 `repository.save([...xperts, xpert])` 提交。
- `createVersionBackup(entity, sourceId)`：以 `sourceId` 为「源身份」调用 `assertValidTagAssociations(...)`，因此**版本备份继承源的已持久化关联（含已停用 tags）**，随后 `super.create({ ...entity, workspaceDataScope, agentConfig })`；发布链在 `newVersion` 时用它复制旧壳（`saveTeamVersion` 先 `omit(team, 'id','copilotModelId')`，置 `latest=false`、`draft=null`、`agent/agents=null`，再逐个复制 agents）。
- 回滚语义：`setAsLatest` 只切 `latest` 指针，不改 `graph`/`draft`；运行侧读的还是被切中那一行的 `graph`。

## 4 导入导出与复制

- **导出 DSL**：`XpertExportHandler.execute()` 按 `isDraft` 切换 relations；无 `graph` 时 `getInitialDraft()` 用 `createXpertNodes(xpert, {x:0,y:0})` 与 `makeConnections()` 合成初始草稿；`draft.team.agent` 缺失时用 `xpert.agent` 补；输出 `new XpertDraftDslDTO(draft)`，`includeMemory` 时追加 `MemoryDslDTO[]`。控制器把结果 `yaml.stringify(instanceToPlain(xpert))` 包成 `{ data }`。
- **导出为模板**：`XpertExportTemplateHandler.execute()` = 复用 `XpertExportCommand` → `yaml.stringify` → `XpertTemplateService.saveExportedXpertTemplate({ xpert, dslYaml, isDraft, includeMemory })` → 把返回描述符 `updateXpert(id, { exportedTemplate })`。删除走 `XpertDeleteExportedTemplateCommand`。
- **普通导入**：`POST /xpert/import` → `XpertImportHandler.execute()`：先 `normalizeImportedLocalizedText`，`!draft.team` 抛 400；`targetXpertId` 有值走 `overwriteExistingXpertDraft`，否则 `importAsNewXpert`。控制器额外做两件事：校验 `workspaceDataScope ∈ {shared,user}`、带 `templateId` 时调 `XpertTemplateWorkspaceInitializer.initializeByTemplateId`。
- **`importManaged*` 的差异**：只有三个开关差别 —— `normalizeCopilotModels: true`，且 `POST :id/import/managed` 额外带 `targetXpertId`。`true` 时走 `prepareManagedLlmModelSyncContext`（查可用 LLM + 组织主模型 + 主模型兜底）→ `syncImportDraftLlmModels`，把 DSL 里不可用的 `copilotModel` 换成当前组织可用/主模型，再进行落库；不开启则原样保留 DSL 中的模型标识（`dto/xpert-dsl.dto.spec.ts` 断言导出 DSL 保留 copilot 标识）。
- **`importAsNewXpert`**：`validateImportedName(team.name)` → 必含 `team.agent` → `create({ ...omit(team, 'draft','agent','agents','toolsets','knowledgebases', SYSTEM_FIELDS), workspaceDataScope, options: withTemplateSource(...), latest: true, version: null, agent: omit(primaryAgent, ...SYSTEM_FIELDS) })` → `saveDraft(xpert.id, { ...omit(nextDraft, 'memories'), team: xpert })`（可选写入 memories）。
- **`overwriteExistingXpertDraft`**：要求 `draft.team.type === currentXpert.type`、双方都有 `team.agent.key`；`currentTeam` 由现网关系 + 现有草稿合并；nextTeam 用 `omit(draft.team, ...OVERWRITE_PROTECTED_TEAM_FIELDS)` 剥离受保护字段（含 `workspaceId/type/slug/latest/version/publishAt/workspaceDataScope`），`options` 做深合并；最后同样只经 `saveDraft` 落草稿，**不动已发布版本**。
- **模板同步**：`POST :id/sync-template` → `XpertSyncTemplateHandler.execute()`：`resolveXpertTemplateSource(xpert)` 取源（无源 400）→ `getTemplateDetail` → `yaml.parse` → `parsed.team.name = xpert.name` → `preserveInstalledExternalXpertBindings`（保留本实例的 `xpert` 外部绑定节点/边，`xpert.draft ?? xpert.graph` 作为权威）→ 复用 `XpertImportCommand({ targetXpertId, normalizeCopilotModels: true, templateId, sourceTemplateId, templateSource })` → 有 `skills/mcpServers/hooks/apps` 依赖时追加 `PluginTemplateSyncDependenciesCommand`。
- **复制**：`POST :id/duplicate` 是 `XpertExportCommand(id, body.isDraft, false)` → `instanceToPlain` → `XpertImportCommand({ ...dsl, team: { ...dsl.team, ...body.basic } }, { workspaceDataScope: body.basic.workspaceDataScope ?? sourceXpert.workspaceDataScope })`；`workspaceDataScope` 非法值在进入命令前 400。

## 5 配置、外观与能力预览

- **`GET :id/configuration`**：`load()` 要求「有 organizationId + 同租户 + 同组织 + 有 workspaceId」，否则 403 `AssistantConfigurationForbidden`；再 `access.assertCanAuthor(workspaceId)`。`nodes/connections` 取 `saved?.nodes ?? graph?.nodes`；`revision = sha256([xpert.updatedAt, saved, graph])`。草稿缺失时把 `graph` 当可编辑基线（正是「发布清空草稿」的补偿）。缺 `assistantCapabilities` 时尝试从 `templateSource.templateId` 的能力模板回填。
- **`POST :id/configuration`**：`revision` 与 64 位格式在 DTO 解析层校验（`parseAssistantConfiguration`），业务层再比对 revision（不一致 409 `AssistantConfigurationStale`）；随后 `capabilities.compose` → `parseCapabilityTemplateDraft` → `prepareInstallation` → `configureRealtimeVoice` → `updateAssistantPrompt`；**模型/运行时检查后重新 `load` 再比 revision**（防止 await 期间的并发编辑），最后 `xperts.saveDraft(id, draft)` 紧跟 `xperts.publish(id, true, environmentId ?? null, t('server-ai:AssistantConfigurationReleaseNotes'))`；publish 失败抛 422 `AssistantConfigurationPublishFailed`，注释明写「Never pretend a saved draft is already active, or retry publishing implicitly」。
- **`GET :id/configuration/capabilities`** 与 **`POST :id/configuration/capabilities/preview`**：preview 是**纯合成**（注释：the dialog owns draft persistence and the explicit save-and-publish transaction），返回 `TXpertTeamDraft` 但不落库；`sandboxProvider` 可选但在应用前需先 `removeCapabilityState`。
- **外观 `GET/POST :id/appearance`**：控制器用 `UUIDValidationPipe` + `ZodValidationPipe(assistantAppearanceInputSchema)`。`get` 走 `published.getAccessiblePublishedXpert` 后回 `{ canEdit, name, avatar, revision }`（`canEdit` 由 `assertCanAuthor` 试探，Forbidden 时降级 false）；`save` 要求同组织 + `assertCanAuthor`，在 `database.transaction` 内以 `pessimistic_write` 锁行、比对 `revision(title,titleCN,avatar)`，只 `update({ title, titleCN, avatar })`（注释：publishing and Studio drafts are intentionally independent）。

## 6 触发设置

编辑期 **`AssistantTriggerService`**（`@Controller(':id/trigger-settings')` 的 `GET` / `POST validate` / `POST`）：

- `read(id, write)`：先按 `{ id, tenantId, organizationId }` 取行（上下文缺失即 403），`write ? assertCanAuthor : assertCanRead`。
- `list(id)`：`providers()` 过滤掉 `chat` 与 `deprecated`；从 `xpert.graph.nodes` 取 `workflow + WorkflowNodeTypeEnum.TRIGGER` 节点，**只投影 provider schema 中的标量字段**（跳过 `x-ui.component === 'password'`、跳过嵌套/未知字段），附带 `connection` 状态与最近活动时间；`canEdit = canEdit && !!publishAt && !!agent.key`。
- `check()` ↔ `validate()`：`ready()` 要求 `publishAt && agent.key && graph`（否则 400 `TriggerConnectionPublishFirst`），比对 `revision = sha256([graph, draft])` 与 `hasConnectionDraftConflict`（否则 409 `AssistantTriggerStale`），并拒绝同 provider 多节点（409 `AssistantTriggerDuplicate`）；`operation === 'save'` 时再拒 password 字段、用 Ajv（`strict:false, validateSchema:false`）校验 provider schema、检查 `schema.required`、最后调 `registry.get(provider).validate(...)`（非 warning 级错误即拒）。
- `mutate()`：`database.transaction` 内先 `findOne({ lock: { mode: 'pessimistic_write' } })` 锁行，再 `check()`，然后按 `save|toggle|delete` 计算 config 与 node key（`Trigger_<uuid>`），用 `patchConnectionGraph` 同时生成 `graph` 与 `draft`（并写 `savedAt`），以参数化原生 update 落两列，随后 `XpertPublishTriggersCommand(next, { previousGraph, providers:[provider], strict:true })`；命令失败时用 `previous` 反向重放一遍以恢复运行时。

运行期 **`XpertTriggerConnectionService.change(id, provider, integrationId)`**（`/xpert/:id/trigger-connections`，`@UseGuards(XpertGuard)`，`begin/complete` 另需 `INTEGRATION_EDIT`）是同一模式的孪生实现：事务 + `pessimistic_write` 锁 + `assertCanAuthor` + `ready()`（要求已发布且无草稿冲突）+ `patchConnectionGraph` 双列写入 + `XpertPublishTriggersCommand` + 成功后 `status()` 复核，失败则反向重放。启动期由 `XpertTriggerBootstrapRecoveryService` 补偿。

## 7 设计模式及落点

| 模式 | 落点 | 说明 |
|---|---|---|
| CQRS + CommandBus | `commands/*.command.ts` + `commands/handlers/index.ts` | 发布/导入/导出/模板同步/删除全部命令化，控制器不直连写逻辑 |
| 命令重放（补偿） | `XpertPublishTriggersCommand` 在触发写失败后的反向重放 | 「持久化已提交、运行时未起」时用 `previous` 图再打一次，尽力恢复 |
| revision 乐观锁 | `configuration` / `appearance` / `trigger-settings` 三处 `sha256` | 三处 revision 的字段集合各不相同，各自独立 |
| 悲观行锁 | `assistant-trigger.mutate`、`appearance.save`、`trigger-connection.change` | `pessimistic_write` 锁 `xpert` 行，串行化同助手并发写 |
| 白名单 DTO / 投影 | `XpertDraftDslDTO` 家族、`list()` 的 schema 标量投影、`appearance.get` | 只用 `@Expose()` / 显式字段构造，不做实体序列化 |
| 模板方法 + 继承 | `XpertService extends XpertWorkspaceBaseService<Xpert>` | 复用 `findOne/save/softDelete` 与工作区作用域 |

## 8 热点路径

1. **草稿自动保存的频率**：编辑态每次改动都打 `POST/PUT :id/draft`，而 `saveDraft`/`updateDraft` 每次都执行 `findOne` + `validate()`（含 `FreeNodeValidator` + 所有 `EventNameXpertValidate` 监听者）+ `save`。跨会话证据记录了一条前端决策：**编排与助手设置统一「仅草稿保存」（draft-only saves）**，1s 去抖自动 POST `:id/draft`，`resume()` 可丢弃草稿回到已发布版本（证据来源：commit `9c210afd9`）。这意味着 `validate()` 的耗时直接等于自动保存的吞吐上限。
2. **发布时的图校验与 agent 对账**：`check()` 对每个节点做 `connections.some(...)` 线性扫描（O(n·m)），`validate()` 再跑插件校验；`publish()` 对每个 agent 节点重新遍历 `draft.connections` 收集关联，并对每个 agent 触发一次 `xpertAgentService.update/create`。大图（数十节点）的发布是明显的串行重活。
3. **`publish` 的失败原子性缺口**：备份版本与 agent 写入发生在 `publish()` 最终 `save` 之前，中途抛错不会回滚已创建的备份行/agent（只有触发器有反向重放）。
4. **`configuration` 的双重校验**：`save` 与 `preview` 都在 await 之后二次 `load()` 比 revision，即一次保存至少 2~3 次完整加载（`load` 内含 `findOne` + `assertCanAuthor`，能力合成还可能 `getTemplateDetail`）。
5. **触发写路径串行化**：`change()`/`mutate()` 的 `pessimistic_write` 会把同一 Xpert 的写请求排队；`statuses`/`list`/`poll` 是只读并可并发。

## 10 技术债与 hack

1. **`ensurePrincipalUser` 隐式副作用**：`XpertPublishHandler.publish` 与 `XpertController.updateChatApi` / `updateChatApp` / `POST :id/principal-user` 都会在 `!xpert.userId` 时创建外部服务账号；账号生命周期与助手启停状态不绑定，账号一旦创建不会随 `app.enabled=false` 回收。
9. **`API`/`app` 开关的副作用顺序**：`updateChatApi` 先 `updateXpert` 再创建账号；若创建失败，`api` 已落库但 `userId` 为空。
2. **浅层 `update` 的限制**：`updateXpert` 用 `assign` + `super.save`，对 `OneToOne`（如 `copilotModel`）与递归关系不做处理；注释即声明这是为绕开 TypeORM 递归更新类型推断。
3. **草稿与 graph 分叉风险**：`draft` 与 `graph` 是两个独立 json 列，只有 `trigger-connection.change()` 与 `assistant-trigger.mutate()` 在同事务内同时写；任何旁路直写 json 列都会让两者分叉，而 `hasConnectionDraftConflict` 只覆盖「触发节点」这一小块。
4. **发布前无强制校验闸门**：校验是发布流程内部的步骤（`validate` 产出的是 `checklist` 提示，`check` 抛的是 500 而非 400 语义），HTTP 层没有「必须先 validate 通过才能 publish」的开关；`XpertPublishHandler` 的校验失败发生在备份之后的位置也已明确。
5. **`check()` 的错误语义**：游离节点与重名抛 `HttpException(..., 500)`，属于「把用户输入错误报成服务端错误」。
6. **`getMyAll` / `getAllByWorkspace` 的两套过滤**：`countMy`/`getMyAll` 用 `publishAt` 非空 + `createdById` 或工作区集合，`getAllByWorkspace` 用 `version` 非空判「已发布」，两处对「已发布」的定义不一致（`publishAt` vs `version`）。
7. **能力配置的隐式发布**：`POST :id/configuration` 会顺带执行一次 `publish(newVersion=true)`，与「仅草稿保存」的总体取向相反，是唯一由配置页触发的发布入口。
8. **revision 字段集合脆弱**：三处 revision 各自取不同字段（`updatedAt+draft+graph` / `title+titleCN+avatar` / `graph+draft`），任何新增可编辑字段若忘记并入，就会退化为「无锁覆盖」。
9. **`assistant-trigger` 与 `trigger-connection` 的职责交叠**：两者都能改同一批触发节点，靠 `hasConnectionDraftConflict` 与 revision 互相发现，缺少统一的领域服务。
10. **命名不一致**：同一概念在不同层次三种写法（`trigger-settings` 编辑期声明 vs `trigger-connections` 运行期连接；`importManagedDSL` vs `importManagedDSLIntoXpert`），检索时容易漏。

## 11 设计维度分析

### 11.1 维度 A：草稿保存的两种接口（全量 `POST` vs 增量 `PUT`）

`POST :id/draft` 收全量 `TXpertTeamDraft`，`PUT :id/draft` 收 `Partial<TXpertTeamDraft>` 并做 team 浅合并。二者共用一个校验器，但增量路径特意只在 body 命中 `nodes`/`connections` 键时才覆盖图字段，并在校验时用 `xpert.graph` 兜底——这条设计把「只改标题」的补丁与「改结构」的补丁区分开，避免把已发布图误实体化进草稿。代价是两条路径的语义差异只写在代码里（有 spec 保护，但接口文档不体现）。

章节来源：[xpert/xpert.service.ts](file://packages/server-ai/src/xpert/xpert.service.ts)（关键符号：XpertService.updateDraft）

### 11.2 维度 B：校验结果的两种消费方式（`checklist` 提示 vs 抛错阻断）

`validate()` 返回 `ChecklistItem[]` 并挂到 `draft.checklist` —— 是**建议式**校验；`check()` 抛错 —— 是**阻断式**校验。前者在每次草稿保存时执行，后者只在发布时执行。这带来了一个体验事实：编辑期能存下不完整的图（便于分步搭建），发布期才强制「无游离节点、无重名」。风险是两类校验器可能给出不一致的结论（`check()` 的重名规则只看 `type !== 'workflow'` 且有 `name` 的节点）。

章节来源：[xpert/commands/handlers/publish.handler.ts](file://packages/server-ai/src/xpert/commands/handlers/publish.handler.ts)（关键符号：XpertPublishHandler.check）

### 11.3 维度 C：导入的两条口径（保真 vs 托管）

普通 `import` 尽量保真（DSL 里的 `copilotModel` 原样落库），`importManaged*` 则把模型引用换成当前组织可用的主模型。这一分叉让「跨环境搬迁」与「从市场/模板安装」有了不同入口，但也意味着：同一份 DSL 走两条路径会得到不同的可运行性结论（前者可能指向不存在的 copilot）。同步模板选择托管口径，复制选择保真口径 —— 选择依据是「是否需要立刻可运行」。

章节来源：[xpert/commands/handlers/import.handler.ts](file://packages/server-ai/src/xpert/commands/handlers/import.handler.ts)（关键符号：XpertImportHandler.prepareManagedLlmModelSyncContext、XpertImportHandler.syncImportDraftLlmModels）

## 12 结论

实现层面，本子域最值得复用的三点是：**(1) 合成一个命令而不是拼装副作用**——发布/导入/导出/模板同步各自只有一个入口，回滚与补偿点也随之唯一（触发链的双向重放即是此法）；**(2) revision 用「状态哈希」而非版本号**——`sha256([updatedAt, draft, graph])` 天然覆盖所有写入来源，包括绕过本子域的直写；**(3) 白名单 DTO 定义 DSL 边界**——`XpertDraftDslDTO` 决定了什么能跨实例流动，`OVERWRITE_PROTECTED_TEAM_FIELDS` 决定什么不能被覆盖。最需要警惕的是三点已在技术债中列出的结构性缺口：发布失败不回滚已写入的备份/agent、草稿与 `graph` 只能靠少数事务入口维持一致、以及「配置页会顺带发布」这一与 draft-only 取向相反的例外。
