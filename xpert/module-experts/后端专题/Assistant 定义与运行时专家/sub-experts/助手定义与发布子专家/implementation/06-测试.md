## 1 测试框架与运行方式

- 框架：Jest + ts-jest，`displayName: 'server-ai'`、`preset: '../../jest.preset.js'`、`testEnvironment: 'node'`；`moduleNameMapper` 把 `@xpert-ai/server-core`、`@xpert-ai/contracts`、`@xpert-ai/plugin-sdk` 直指源码，因此跑测试**不需要先构建依赖包**。
- nx target：`packages/server-ai/project.json` 的 `test` 目标为 `@nx/jest:jest`，`jestConfig: packages/server-ai/jest.config.ts`。
- 单文件运行：`node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts --runTestsByPath <spec 路径>`。
- 与构建的区分：`pnpm nx build server-ai` 只编译不跑测试。

## 3 逐文件覆盖点

**`xpert.controller.spec.ts`** —— 与创作侧相关的用例：发布时转发合法 `businessArea`、允许无环境绑定发布、发布边界拒绝非法 `businessAreaId`、导入受信模板后初始化工作区 prompt workflow、无 `templateId` 的普通 DSL 导入保持原样、显式 `workspaceDataScope` 透传给创建、导入前拒绝非法 scope、复制时继承源 scope / 使用创建前覆盖值、`update-from-template` 只转发同步命令而不发布、启用 Chat API / Chat App / 按需创建 principal user 三例；另有 `does not expose execution history before authorizing the xpert` 与 `loads runtime capabilities from an unpublished xpert draft`（属邻接运行面）。

**`xpert.service.spec.ts`** —— `tag usage names` 分组（只返回可见关联的名称与版本状态、租户标签查询只用租户范围、无可读工作区时不回退全量、不可用标签先于加载名称被拒、需要登录租户上下文）；标签保存类（拒绝新增已停用标签、更新与版本备份保留已停用标签但新助手拒绝）；`assertCanAuthorById` 三例（目标工作区创作权、解析草稿工作区与持久化工作区不同时二次校验、无工作区时回落创建者 + 同组织）；`publish forwards to XpertPublishCommand` 与空环境绑定转发；`create`/`save` 归一 `agentConfig`、保留/拒绝变更 `workspaceDataScope`、只改 team 的草稿补丁不实体化图字段、草稿保存与更新都覆盖伪造 scope、模板血缘与草稿同次落库；`getTriggerProviders`；用户组授权批量读写。

**`publish.handler.spec.ts`** —— 覆盖 `forwardRef` 场景下参数类型退化为 `Object` 仍能解析 agent provider、原型实例发布、**在备份版本或写 agent 之前拒绝过期标签**、备份时传源身份、租户创建者无用户组可发布、环境绑定 trim、marketplace 快照入发布、组织 businessArea 独立赋值、跨组织 businessArea 被拒、非创建者必须有用户组（含组织级 xpert）、发布前 `ensurePrincipalUser`（含无 schedule trigger 时也执行、已存在时不重建）、版本备份保留 `workspaceDataScope`。

**`import.handler.spec.ts`** —— 覆盖 `XpertImportHandler` 的导入分支与覆盖写分支（用例名未逐一核对，`describe('XpertImportHandler')` 为单顶层分组）。

**`sync-template.handler.spec.ts`** —— 覆盖能力变体模板不被重复加 plugin 前缀、UI 语言变化时保留已安装 prompt 语言、解析 legacy 模板源且只覆盖现有草稿、未命名空间的 legacy 源、替换草稿后对账声明式运行时依赖、跨模板同步保留组织级外部 Xpert 绑定、**以当前草稿而非上次发布为权威**、插件前置条件不算可移植资源、从 `data-xpert` 声明补全旧源、拒绝未关联模板的助手。

**`dto/xpert-dsl.dto.spec.ts`** —— 两例：导出草稿 DSL 保留 copilot 模型标识；**不把本地 `workspaceDataScope` 导出进可移植 DSL**。

**`guards/xpert-workspace-auth.guard.spec.ts`** —— 接受绑定到目标助手的委派用户会话、拒绝绑定到其他助手的会话、API key 同样被限制在绑定助手、拒绝无助手绑定的委派会话。

## 6 缺口与结论

**缺口**：

1. **无「草稿保存」频率/并发实测**：`saveDraft`/`updateDraft` 的 `validate()` 成本、（前端 1s 去抖下的）连续保存冲突面没有任何基准或压测用例；`updateDraft` 的「只带 team 的补丁」有单测保护，但「连续两次不同字段的补丁」这类真实编辑序列没有。
2. **无发布原子性用例**：没有覆盖「备份行已创建但 agent 写入失败」「触发器发布失败后版本已切」这类中途失败的断言，也没有断言失败后版本族的最终形态。
3. **无 `setAsLatest` / `allVersions` 的族内唯一性测试**：服务层这两个方法只有实现，未见到对应 spec 用例（`xpert.service.spec.ts` 的用例名不含版本族场景）。
4. **无端到端创作链**：不存在「创建 → 草稿 → 发布 → 改草稿 → 再发布 → `setAsLatest` 回滚」的整链路用例；HTTP 层的 `XpertController` 也只有行为转发断言。
5. **控制器层缺口**：`XpertTriggerConnectionController` 与 `AssistantTriggerController` 无独立 spec（逻辑由 service spec 覆盖）；`XpertTagUsageController` 无 spec；`assistant-configuration.controller.spec.ts` 仅覆盖入参解析。
6. **`import.handler.spec.ts` 体量最大但用例名未分组归类**：53.75 KB 的单 `describe` 不利于按「新实例导入 / 覆盖草稿 / 托管模型归一」定位回归面。
7. **无并发写用例**：`pessimistic_write` 行锁与 revision 冲突都只有单线程断言（「revision 不匹配即 409」），没有真正的两连接竞争验证。

**结论**：本子域的测试覆盖**集中在服务与命令层的分支正确性**（发布前置校验、标签校验时序、导入/同步的字段保护、配置 revision 冲突），并且用了真实 HTTP 也只覆盖外观契约这一小块。**最大的结构性缺口是「版本族」与「发布原子性」**——恰好是数据模型上最危险、也最难事后补救的两块；其次是缺少针对自动保存节奏的实测数据。建议的最小回归面为：`xpert.service.spec.ts`、`publish.handler.spec.ts`、`import.handler.spec.ts`、`sync-template.handler.spec.ts`、`assistant-configuration.service.spec.ts`、`assistant-trigger.service.spec.ts`、`xpert.controller.spec.ts`。
