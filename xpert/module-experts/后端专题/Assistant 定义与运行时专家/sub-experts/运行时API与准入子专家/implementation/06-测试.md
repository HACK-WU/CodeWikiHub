## 5 运行命令与实测说明

- **命令（来自仓库脚本与 jest 配置，本轮只读调研未执行）**：
  - 单文件：`pnpm nx test server-ai --testFile=src/ai/chatkit-session.http.spec.ts`（Nx + Jest 项目名 `server-ai`，与 `jest.config.ts` 的 `displayName: 'server-ai'` 一致）。
  - 目录/关键字：`pnpm nx test server-ai --testPathPattern=src/ai`。
  - 若使用原生 Jest：`pnpm jest --config packages/server-ai/jest.config.ts src/ai/...`。
- **实测说明（诚实声明）**：本次为**只读**调研任务，未执行任何测试命令，因此本文件不给出通过/失败数字。可核实的**运行前提**来自源码与配置：
  - `testEnvironment: 'node'`，`moduleNameMapper` 把 `@xpert-ai/server-core` / `contracts` / `plugin-sdk` 映射到**源码目录**（`../server/src/index.ts` 等），因此测试无需先构建这些包；
  - `transformIgnorePatterns` 通过递归读取 `node_modules` 内包依赖清单动态放行 `@xpert-ai/chatkit-types`、`lodash-es`、`jose`、`marked` 等 ESM 包，说明这批用例对 `node_modules` 安装状态敏感（依赖缺失时会静默少放行，表现为 ESM 语法报错）；
  - HTTP 用例统一 `app.listen(0, '127.0.0.1')` 取随机端口，**无需外部服务**；
  - 文件类用例用 `mkdtemp(tmpdir())` 建临时工作区并在 `afterAll` 清理。

章节来源：[packages/server-ai/jest.config.ts](file://packages/server-ai/jest.config.ts)（关键符号：testEnvironment、transformIgnorePatterns、moduleNameMapper）、[ai/assistant-files-runtime.http.spec.ts](file://packages/server-ai/src/ai/assistant-files-runtime.http.spec.ts)（关键符号：mkdtemp、app.listen）

## 7 覆盖缺口

1. **准入多受众交叉组合覆盖不足**：`published-xpert-access.service.spec.ts` 覆盖了 public 受众的「同 id 通过 / 异 id 拒绝 / 目录不暴露」，但**没有**覆盖 `ENTERPRISE_XPERT` × `organizationId` 不匹配、`workspace API Key` × `requestedUserId` 同时存在（应走用户分支而非 workspace 分支）这类短路顺序组合；`buildEnterpriseXpertBoundQuery` 的 `applyEnterpriseChatAppFilter` 原生 SQL 参数（platform / integrationId）在 spec 层不可验证。
2. **企业 H5 链路无端到端 spec**：`/api/xpert/:identifier/enterprise-h5/:platform/{bootstrap,session}` 的 `assertIdentity` 五项断言、`account_binding_required` 分支、TTL 固定 600 三项均**没有**对应 spec 文件（`ai/` 与 `xpert/` 下都未检索到）。
3. **公共 App 会话链缺 spec**：`XpertController.createPublicChatkitSession` 与 `getOrSetAnonymousId`（cookie 属性、`x-forwarded-proto` 判定）同样无 spec 覆盖；`anonymous.strategy.ts` 的 cookie 分支也无。
4. **`AIController.proxy` 零覆盖**：`ai/` 下没有 `ai.controller.spec.ts`，流式透传、GET/POST 取凭证不一致、上游错误映射 500 全部无回归。
5. **`StoreController` 与 `ThreadsController` 的 SSE 细节**：Store 无 spec；线程 SSE 只在 `thread.controller.spec.ts` 的 run stream 场景覆盖，`:thread_id/stream` 的 30s 心跳与重复 `ensureThreadAccess` 无专项用例。
6. **保护性断言缺位**：`applyPublishedFilters` 的 `latest` 叠加、`TENANT_SHARED_WORKSPACE_FILTER` 语义均无「字段改名即失败」的护栏测试，与第 7 节外提到的 schema 漂移风险同源。

章节来源：[xpert/published-xpert-access.service.spec.ts](file://packages/server-ai/src/xpert/published-xpert-access.service.spec.ts)（关键符号：does not expose a resource catalog to public assistant sessions）、[ai/thread.controller.spec.ts](file://packages/server-ai/src/ai/thread.controller.spec.ts)（关键符号：run stream HTTP admission with Nest interceptors）

## 8 结论

本子域的测试策略是**分层的、以真实 HTTP 栈为最高置信层**：12 个用例自建 Nest 应用 + 随机端口 + `fetch`，只 mock 凭证、持久化与领域 service，因此能覆盖「守卫顺序」「路由遮蔽」「管道与出参投影」；其余 26 个 spec 承担请求上下文、守卫单独语义与命令/查询处理器。缺口集中在**凭证签发侧**（企业 H5、公共 App 两条链路均无 spec）与**准入组合矩阵**（多受众短路顺序、原生 SQL 参数），这两处恰是本子域风险最高的地方。补测优先级建议：`createPublicChatkitSession` / `EnterpriseChatkitSessionService.createSession` 的 HTTP 用例 > `buildAccessibleQuery` 受众交叉表 > `AIController.proxy` 流式透传。**注意**：任务给出的「7 个真实 HTTP 用例」与源码不符（实际 12 个 `app.listen` 用例、3 个 `.http.spec.ts`），改动测试清单时应以此实测口径为准。
