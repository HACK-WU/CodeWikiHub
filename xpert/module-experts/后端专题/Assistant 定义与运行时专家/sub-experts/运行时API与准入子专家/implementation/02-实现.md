## 1 准入查询构造

`buildAccessibleQuery(options, resourceParentId?)` 是全部可见性的唯一入口，分支顺序即实现骨架：

1. `currentPublicXpertId()` 非空 → `buildPublicXpertBoundQuery(publicXpertId)`：`tenantId` + `publishAt IS NOT NULL` + `id = :publicXpertId`，再叠加 `applyPublicChatAppFilter`（原生 SQL 校验 `app.enabled` 与 `app.public` 为真）。
2. `currentEnterpriseXpertScope()` 非空且 `!resourceParentId` → `buildEnterpriseXpertBoundQuery(scope)`：额外锁 `organizationId`，并叠加 `applyEnterpriseChatAppFilter`（`app.enabled` + `channels[platform].enabled` + `channels[platform].integrationId = :enterpriseH5IntegrationId`，均用 `jsonb_extract_path_text` 原生表达式）。
3. `currentWorkspaceApiKeyWorkspaceId()` 非空且无 `requestedUserId` → `buildWorkspaceBoundQuery(workspaceId)`：锁 `tenantId` + `publishAt` + `workspaceId`。
4. 否则落到主查询：`leftJoin('xpert.workspace','workspace')` + `leftJoin('workspace.members','workspaceMember','workspaceMember.id = :userId')` + `leftJoin('xpert.userGroups','userGroup', ...)` + `leftJoin('userGroup.members','member','member.id = :userId')`；`organizationId` 用 `Brackets` 表达「本组织 OR （无组织的租户共享工作区）」；访问条件为 `createdById = :userId OR workspace.ownerId = :userId OR workspaceMember.id = :userId OR member.id = :userId OR 租户共享`。

四个分支尾部统一调用 `applyPublishedFilters(qb, options?.where)`（可选叠加 `id/slug/workspaceId/type/latest/version/organizationId`）与 `applySearchFilter(qb, options?.search)`（name/title/titleCN/slug/description 的 `LOWER(...) LIKE`）。`resourceParentId` 存在时 `currentUserXpertId()` 被强制置空——这是「资源父级授权」与「凭证受众」互斥的实现点。

## 3 公共 App ChatKit 会话链

`POST /api/xpert/:identifier/chatkit-session`（`@Public()`）实现顺序：

1. `XpertController.createPublicChatkitSession` → `XpertService.findPublicChatAppXpert(identifier)`（必须是已发布且 `app.public` 的公共 App）；
2. `getOrSetAnonymousId(res)`：读 cookie `anonymous.id`，无则生成 uuid 并 `res.cookie(..., { httpOnly: true, maxAge: 365d, sameSite: isSecure ? 'none' : 'lax', secure })`；`isSecure` 由 `req.secure` 或 `x-forwarded-proto` 判定；
3. `UserService.ensureCommunicationUser({ thirdPartyId: 'public-xpert:<xpertId>:anonymous:<anonymousId>' })` 得到匿名通信用户；
4. `SecretTokenService.create({ entityId: xpert.id, type: SecretTokenBindingType.PUBLIC_XPERT, createdById: anonymousUser.id, token: 'cs-x-<64hex>', validUntil })`；
5. 返回 `{ client_secret, expires_at, expires_after, xpertId, assistantId, organizationId }`；TTL 由 `normalizeChatkitSessionExpiresAfter` 决定：非法/缺省 600，上限 3600。

随后的运行时请求全部由 `PublishedXpertAccessService.currentPublicXpertId()` 收口：只允许访问绑定的那一个 xpert，且要求 `app.enabled && app.public`；`findAccessiblePublishedResources` / `getAccessiblePublishedResource` 对公开会话**直接 403**（不暴露资源目录）。会话内的对话访问再由 `assertPublicXpertSessionConversationAccess` 校验 `createdById` 与 `xpertId`（同族放行）。

章节来源：[xpert/xpert.controller.ts](file://packages/server-ai/src/xpert/xpert.controller.ts)（关键符号：XpertController.createPublicChatkitSession、XpertController.getOrSetAnonymousId）、[ai/public-xpert-principal.ts](file://packages/server-ai/src/ai/public-xpert-principal.ts)（关键符号：assertPublicXpertSessionConversationAccess）

## 4 Enterprise H5 链

两段式，且**第一段在身份校验之前**：

1. `GET /api/xpert/:identifier/enterprise-h5/:platform/bootstrap` → `EnterpriseChatkitSessionService.getBootstrap` → `resolveContext`：`findEnterpriseH5Xpert`（原生 QueryBuilder，`identifier` 为 uuid 时按 `id` 否则按 `slug` + `latest = true`，要求 `publishAt IS NOT NULL`、`organizationId` 非空、`app.enabled`、`channels[platform].enabled`、`integrationId` 非空）→ `integrationService.findOneByIdWithinTenant` → 组织一致性校验 → `strategy.meta.enterpriseH5` 的 `platform` 必须匹配 → `strategy.getIdentityBootstrap(integration)`。控制器再用 `toEnterpriseH5PublicXpert` 只输出 12 个白名单字段。
2. `POST .../session` → `requireIdentityGrant`（`grant.type === 'authorization_code'` 且 `code` 非空）→ `strategy.exchangeIdentity` 失败转 401 `EnterpriseH5IdentityVerificationFailed` → `assertIdentity`（provider、`externalOrganizationId`、`subjectId`、`accountBinding.provider`、`accountBinding.subjectId` 五项全等）→ `accountBindingService.resolveUser`：未绑定返回 `{ status: 'account_binding_required', accountBindingProvider }`，绑定成功则 `secretTokenService.create({ type: ENTERPRISE_XPERT, enterpriseH5Scope: { platform, integrationId }, validUntil: now + 600s })`。

凭证被消费时，`currentEnterpriseXpertScope()` 要求 `resourceScope.kind === 'assistant'` 且 `enterpriseH5Scope.platform`、`integrationId` 齐备，否则 403 `EnterpriseAssistantBindingRequired`；`assertEnterpriseChatAppXpert` 再复核 channel 开关与 `integrationId` 完全一致。

章节来源：[xpert/enterprise-chatkit-session.service.ts](file://packages/server-ai/src/xpert/enterprise-chatkit-session.service.ts)（关键符号：EnterpriseChatkitSessionService.getBootstrap、EnterpriseChatkitSessionService.resolveContext、EnterpriseChatkitSessionService.assertIdentity）、[xpert/enterprise-chatkit.controller.ts](file://packages/server-ai/src/xpert/enterprise-chatkit.controller.ts)（关键符号：EnterpriseChatkitController.getBootstrap）

## 5 模型代理与 v1 兼容层

- **`AIController`（`@Controller()` → `/api/ai/proxy/*`）**：`@Get('proxy/:copilotId/:m')` 走 `AiService.getCopilot(copilotId)` 后直接 `fetch('/' + m, { headers: { authorization: 'Bearer ' + copilot.apiKey } })` 并返回 JSON；两个 POST 变体（`proxy/:copilotId/:m`、`proxy/:copilotId/:m/:f`）先经 `GetAiProviderCredentialsQuery(copilot.modelProvider)` 取 `{ baseURL, authorization }`，再 `fetch(baseURL + path)` 并**手工流式透传**：`resp.writeHead(status, {content-type, cache-control, connection, transfer-encoding?, access-control-allow-origin?})` 后递归 `reader.read()` → `resp.write(text)`。凭证解析失败按 403 抛出，上游失败按 500 抛出。注意：GET 版本未走 credentials query（源码里保留了注释掉的 `chatCompletionsUrl`），是两条不一致的取凭证路径。
- **`AIV1Controller`（`@Public()` + `@UseGuards(ApiKeyOrClientSecretAuthGuard)` + `@Controller('v1')`）**：提供 LangGraph Platform 风格的 `POST chat`（`@Sse()` + `ChatCommand`，SSE 头 + 30s keepAlive）、`POST kb` / `PUT|DELETE kb/:id` / `POST kb/:id/bulk|process` / `GET kb/:id/status`（写操作叠加 `KnowledgebaseOwnerGuard` 且服务层再判 `assertKnowledgebaseWriteAccess`）、`POST file`（已标 `@deprecated`，指向 `POST /contexts/file`）、`POST chatkit/sessions`。
- **`createChatkitSession` 的三分支**：`body.scope`（群会话）→ 拒绝任何已存在主体/API Key，要求 `currentUser`+`tenantId`+`organizationId`，先 `GetGroupConversationEntryCommand` 授权再 `createHashed({ type: USER_CONVERSATION, entityId: conversationId })`；`apiKey.id` 存在 → `createHashed({ type: API_KEY, entityId: apiKey.id })` 且不受 3600 上限约束；否则要求 `assistant.id`，按 `project`（`XpertProjectAccessService.assertCanUseXpert`）/`conversation`（`WorkbenchAssistantConversationNavigationService.resolve` 对齐 xpertId 与 projectId）/普通（`getAccessiblePublishedXpert`）三条路径选准入，最后 `createHashed({ type: USER_XPERT, entityId: assistantId, createdById: currentUser.id })`。

章节来源：[ai/ai.controller.ts](file://packages/server-ai/src/ai/ai.controller.ts)（关键符号：AIController.proxyGetModule、AIController.proxy）、[ai/ai-v1.controller.ts](file://packages/server-ai/src/ai/ai-v1.controller.ts)（关键符号：AIV1Controller.chat、AIV1Controller.createChatkitSession）

## 6 路由注册顺序敏感点

`ai/conversations/:conversationId/files` 的冲突史是硬约束：该路径曾同时被 `FileUnderstandingController`（`@Get('conversations/:conversationId/files')`，返回已解析附件 FileAsset）与工作台文件控制器注册，命中顺序决定返回体。修法有两条：

1. 附件列表保留 `/api/ai/conversations/:conversationId/files`，工作台目录整体迁到 `/workspace/*`（`@Controller('conversations/:conversationId')` + `@Get('workspace/files')`），源码注释明写 "Conversation /files belongs to parsed FileAssets. Workspace directories use /workspace/files"；
2. 单文件读/写/删/上传用数组路径保留旧单数路由：`@Get(['workspace/file', 'file'])`、`@Put([...])`、`@Delete([...])`、`@Post(['workspace/file/upload','file/upload'])`——这些「旧路由」之所以安全，是因为它们与 FileAsset 的 `/files` different path。

因此**新增 controller 时必须以「同路径不同 controller」的方式排查冲突，且回归测试要覆盖两种注册顺序**（`workbench-files-routing.http.spec.ts` 用 `describe.each` 显式跑 `assets first` 与 `workspace first` 两种装配）。

章节来源：[ai/workbench-files.controller.ts](file://packages/server-ai/src/ai/workbench-files.controller.ts)（关键符号：WorkbenchFilesController.read、WorkbenchFilesController.upload）、[file-understanding/file-understanding.controller.ts](file://packages/server-ai/src/file-understanding/file-understanding.controller.ts)（关键符号：FileUnderstandingController）

## 8 热点路径

1. **准入查询（最高频）**：`AssistantsController.search/count/getOne` 与所有文件端点每次都触发 `buildAccessibleQuery`；`findAccessiblePublishedXperts` 的做法是「先 `select('xpert.id')` + `distinct` 取 id 列表 → 再 `loadByIds` 并 `enrichWorkspaceAccess`」，即一次准入算两次 DB 往返（其中 `enrichWorkspaceAccess` 还额外调 `XpertWorkspaceAccessService.buildAccess`）。
2. **SSE 流**：`ThreadsController.streamThreadActivity` 每个连接起一个 30s 心跳 `setInterval` 并在 `close`/`finish` 清理，同时 `ensureThreadAccess` 在快照前被调用两次（先准入再取 conversation）；`AIV1Controller.chat` 用 `keepAlive(30000)` + `takeUntilClose(res)`。
3. **proxy 透传**：`AIController.proxy` 用递归 async 读流，无背压处理（`resp.write` 返回值被忽略），上游异常统一 500。
4. **匿名会话创建**：每次 `chatkit-session` 都可能 `ensureCommunicationUser` 建新用户（匿名 cookie 变更即新用户），属低频但会持续累积账号。
5. **群聊路由**：`GroupScopeGuard.canActivate` 对非 client_secret/api_key 主体零成本放行，对凭证请求才查 `GroupAccessService.authorize`。

章节来源：[xpert/published-xpert-access.service.ts](file://packages/server-ai/src/xpert/published-xpert-access.service.ts)（关键符号：PublishedXpertAccessService.findAccessiblePublishedXperts、PublishedXpertAccessService.enrichWorkspaceAccess）、[ai/thread.controller.ts](file://packages/server-ai/src/ai/thread.controller.ts)（关键符号：ThreadsController.streamThreadActivity）

## 10 技术债与 hack

1. **受众判定散落两个 service**：`PublishedXpertAccessService` 判 token audience，但 workspace 绑定同样来自 `resourceScope.kind === 'workspace'`；`AssistantsController` 的类级 `@Public()` 全靠守卫兜底，一旦有人新增方法忘挂 `@AllowClientSecretBindings`，受众面即静默扩大。
2. **原生 SQL 与 json 强耦合**：`TENANT_SHARED_WORKSPACE_FILTER` 与 `applyPublicChatAppFilter` / `applyEnterpriseChatAppFilter` 直读 `workspace.settings->access->visibility`、`xpert.app->>'public'`、`xpert.app->channels->...`；`COALESCE(..., 'private')` / `'false'` 的失败方向是**收紧**（安全），但字段改名会静默改变可见性且无编译期保护。
3. **`@Public()` 面靠守卫**：`AssistantWorkspaceFilesController`、`WorkbenchFilesController`、`SandboxRuntimeController` 等类级 `@Public()` + `@UseGuards(...)`；`AssistantFileAccessGuard` 在缺少 policy 元数据时 `denied()`，是唯一「默认拒绝」的写法，其余守卫默认放行登录用户。
4. **路由冲突无编译期保护**：`conversations/:conversationId/files` 的双注册只能靠 `describe.each` 的 HTTP 用例覆盖两种顺序；Nest 不做冲突检测。
5. **proxy 双路径取凭证**：`proxyGetModule` 用 `copilot.apiKey` 且 `copilotUrl = path`（相对路径，源码注释保留了被注释的 `chatCompletionsUrl`），POST 版用 `GetAiProviderCredentialsQuery` 的 `baseURL`；两者行为不一致。
6. **匿名账号累积**：公共 App 会话用 `thirdPartyId: public-xpert:<id>:anonymous:<uuid>`，清 cookie 即新用户，历史与配额随之分叉。
7. **组织 scope 被请求头劫持式改写**：`applyAssistantScope` 直接写 `request.headers['organization-id']`，与 `RequestContext` 读取路径形成隐式契约，任何绕过该函数的调用都会落到不同的组织 scope。
8. **三处 endpoint 命名不统一**：`assistants/:assistantId/...` 与 `threads/:threadId/...` 与 SDK 风格 `threads/:thread_id`（`AssistantThreadScopeGuard` 不得不同时读 `threadId` 与 `thread_id`）。

## 11 设计维度分析

### 11.1 维度 A：受众判定「集中一个查询构造器」 vs 「一个受众一个守卫」

现方案把四类受众（workspace / public / enterprise / 用户）压进 `buildAccessibleQuery` 的顺序短路，好处是「新增受众只加一个 `build*Query` + 一个分支」，坏处是**判定与查询不可分离**：识别受众的私有方法自身会抛 403，单元测试必须构造 `RequestContext.currentApiPrincipal` 的 mock 才能覆盖，且 `getAccessiblePublishedXpert` 必须再实现一遍同样的分支（单条 vs 列表两条代码路径需同步演进）。若改为「一受众一守卫 + 守卫写入 context」，识别与拒绝会分离，但列表查询会失去「一条 SQL 拿全部可见 id」的能力，代价落在分页与 `distinct` 上。

章节来源：[xpert/published-xpert-access.service.ts](file://packages/server-ai/src/xpert/published-xpert-access.service.ts)（关键符号：PublishedXpertAccessService.currentWorkspaceApiKeyWorkspaceId、PublishedXpertAccessService.getAccessiblePublishedXpertForCurrentUser）

### 11.2 维度 B：把「凭证」当作授权载体 vs 把「用户关系」当作授权载体

本子域用短 TTL client secret（600s / 3600s）承载一切跨进程授权：public 会话携带匿名用户 id，USER_XPERT 携带「助手受众 + 发起人」，ENTERPRISE_XPERT 额外携带 `platform` 与 `integrationId`。这带来两点：凭证即全部上下文（无会话存储、天然可水平扩展）；以及凭证失效即授权失效（不需要吊销逻辑，但 TTL 内无法回收）。替代方案是每次请求回查 `userGroups` / `workspace.members`（准入查询已经这么做了，见主分支），代价是每次交互一次四表 join。当前选择把「受众匹配」放在凭证里、把「成员关系」放在查询里，两者是叠加而非替换关系。

### 11.3 维度 C：Bootstrap 是否应携带业务数据

企业 H5 把 xpert 白名单字段放在**身份校验之前**的 bootstrap 里，换取的是「未登录也能渲染应用壳」；风险是任何拿到 slug 的人都能读到助手名/描述/头像/starters/features。当前边界靠三条过滤守住：`publishAt IS NOT NULL`、`organizationId` 非空、`channels[platform].enabled`。若改为「bootstrap 只回 platform 与 clientConfig，xpert 信息放到 session 之后」，匿名面会收窄，但前端首屏需要两次往返且失败态更难表达。

## 12 结论

实现层面最值得复用的两点：**(1) 准入收敛为单一查询构造器**，所有受众分支尾部共用 `applyPublishedFilters` / `applySearchFilter`，避免「某分支忘了加已发布过滤」；**(2) 把范围约束写进守卫元数据**（`@AssistantFileAccess`），使「策略默认拒绝」可被单文件审计。最值得警惕的三点：`@Public()` 面积大且靠守卫兜底、原生 SQL 直读 json 决定可见性、以及同一前缀下同时存在「准入面」与「领域面」端点导致的归属歧义。**源码校正留档**：`publishAt IS NOT NULL` 由各 `build*Query` 与 `getPublishedXpertInTenant` 硬编码，不在 `applyPublishedFilters` 内；`latest` 过滤仅在调用方把 `latest` 放进 `where` 时生效（`findEnterpriseH5Xpert` 另有 `latest = true`）。
