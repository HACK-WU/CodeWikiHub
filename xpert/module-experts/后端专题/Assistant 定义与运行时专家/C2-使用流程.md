# Assistant 定义与运行时专家 —— C2 使用流程

> 契约层第 2 篇。把本域 9 条主流程写成可照抄的 Recipe：每条给业务目标、调用顺序、事务边界、预期结果、错误处理与真实代码示例。
> 引用一律用 `file://` 相对仓库根，不写行号。符号名、HTTP 路径、错误文案均取自源码或 `.module-experts/` 资产。
> 事务边界一栏区分三种：单次写 / 多步无事务 / 显式事务 + 悲观锁；源码中未见事务包装的一律写「非事务」，不推测。

## Recipe 1 新建并发布一个 Assistant

- **业务目标**：在既有 `XpertWorkspace` 内创建 Assistant 行，反复保存草稿，校验通过后发布为新的版本行并置 `latest`。
- **调用顺序**：① `XpertService.create()` → `validateTagAssociations` → 补 `workspaceDataScope`（缺省 `DEFAULT_XPERT_WORKSPACE_DATA_SCOPE` = `shared`）+ `normalizeXpertAgentConfig` → `XpertWorkspaceBaseService.create()`（`applyWorkspaceScope` 从 workspace 反填 `workspaceId/tenantId/organizationId`，过 `assertWorkspaceWriteAccess`）。② `POST /api/xpert/:id/draft` → `XpertController.saveDraft` → `XpertService.saveDraft(id, draft)`（全量草稿，`draft.checklist` 挂校验项）；增量补丁走 `PUT /api/xpert/:id/draft` → `updateDraft(id, partial)`。③ `GET /api/xpert/validate?name=` → `validateName(name)`。④ `POST /api/xpert/:id/publish?newVersion=true` → `XpertPublishCommand` → `XpertPublishHandler.execute()`。⑤ 读版本 `GET /api/xpert/:id/version` → `allVersions(id)`；回滚 `POST /api/xpert/:id/latest` → `setAsLatest(id)`。
- **事务边界**：`create` / `saveDraft` / `updateDraft` 各为一次 `super.save`，非事务。`publish` 是**多步无事务**（`saveTeamVersion` → agent 增删改 → `toolsets/knowledgebases/executors` 回写 → `graph` 落库 → `draft = null` + `publishAt` + `active` → `ensurePrincipalUser` → `XpertPublishTriggersCommand` → `emitAsync(EventName_XpertPublished)`），中途抛错不回滚已写入的备份行与 agent。`setAsLatest` 用一次 `repository.save([...xperts, xpert])` 批量翻转族内 `latest`。
- **预期结果**：新行 `version` 有值、`latest = true`、`publishAt` 非空、`active = true`、`draft = null`；`newVersion` 时旧行 `latest = false`；`xpert.userId` 由 `ensurePrincipalUser` 补齐为助手自身的外部服务账号。
- **错误处理**：`!xpert.draft` → 404 `No draft found`；`businessAreaId` 跨租户/跨组织 → 400 `XpertBusinessAreaScopeMismatch`；非创建者且 `userGroups` 为空 → 400 `Published xperts must be assigned to at least one user group.`；游离节点 → 500 `There are free Xpert agents!`；节点重名 → 500 duplicate names；旧 agent 比草稿新 → 400 `xpert.Error.AgentOutdated`；`check()` 的用户输入错误被报成 500（已知技术债）。
- **真实代码示例**

```ts
// packages/server-ai/src/xpert/xpert.service.ts
async publish(
    id: string,
    newVersion: boolean,
    environmentId: string | null | undefined,
    notes: string,
    marketplace?: TXpertPublishMarketplaceInput,
    businessAreaId?: string | null
) {
    return await this.commandBus.execute(
        new XpertPublishCommand(id, newVersion, environmentId, notes, marketplace, businessAreaId)
    )
}
```

## Recipe 2 从模板装配新 Assistant 并初始化工作区

- **业务目标**：把模板（含技能 / MCP / hook / app 依赖）安装进既有工作区，得到一个可运行或可继续编辑的 Assistant。
- **调用顺序**：① `POST /api/xpert-template/:id/install` → `XpertTemplateController.installTemplate` → `parseTemplateInstallInput`（`workspaceId` 非空、`publish` 必须显式 `=== true`、`workspaceDataScope ∈ {shared,user}`）。② `PluginTemplateInstallCommand` → `PluginTemplateInstallHandler.execute()`：`assertCanAuthor(workspaceId)` → `getTemplateDetail` → `yaml.parse(export_data)` → `normalizeDraft`（写 `team.workspaceId`、按可用 sandbox provider 纠正 `features.sandbox.provider`）→ `capabilities.prepareInstallation`（**导入前重新查询模型授权**）→ `XpertImportCommand` → `resolveTemplateRuntimeDependencyComponents` + `installer.installComponentsForXpert` → toolset 依赖解析并改写 draft 工具集节点 → 可选 `XpertPublishCommand` → `XpertTemplateWorkspaceInitializer.initializeByTemplateId`。③ 若由 Bosi 桌面端触发，走 `PluginTemplateInstallCommand` 的 `bootstrap` 参数（`resumeXpertId` + `onImported`），该参数**never accepted from an HTTP body**。
- **事务边界**：`initializeByTemplateId` 内部对 prompt workflow 的初始化非事务；整个安装链是**多步无事务**，只有非 bootstrap 路径在失败时执行一次性 `rollbackTemplateXpert`（只删 Assistant）。
- **预期结果**：工作区内新增 `xpert` 行（可选已发布）；该工作区新增默认 prompt workflow；模板声明的技能/MCP/toolset 依赖落盘并注册。**工作区本体不由安装创建**（`workspaceId` 是入参），`XpertTemplateWorkspaceInitializer` 的职责是在既有工作区按模板补默认 prompt workflow，不是创建 Assistant 本体。
- **错误处理**：缺 `workspaceId` → 400；`workspaceDataScope` 非 `shared|user` → `XpertWorkspaceDataScopeInvalid`；`prepareInstallation` 模型授权不足 → `TemplateCapabilityUnavailable`；`initializeByTemplateId` 失败仅 `logger.warn` 并返回 `{ status: 'failed' }`，**不回滚已创建的助手**，且调用方不检查该返回值（已知缺口）。
- **真实代码示例**

```ts
// packages/server-ai/src/xpert/template-workspace-initializer.service.ts（签名，取自实现资产）
XpertTemplateWorkspaceInitializer.initializeByTemplateId(
    templateId: string,
    workspaceId: string,
    language: LanguagesEnum,
    xpertId?: string
)
```

## Recipe 3 导出 / 导入 DSL 与复制助手

- **业务目标**：把 Assistant 的图与配置搬出（YAML/JSON DSL），再在别的租户、组织或工作区还原；或在本实例内快速复制一份。
- **调用顺序**：① 导出 `GET /api/xpert/:id/export?isDraft&includeMemory` → `XpertExportCommand` → `XpertExportHandler.execute()`（按 `isDraft` 切 relations，无 `graph` 时用 `createXpertNodes`/`makeConnections` 合成初始草稿，输出 `XpertDraftDslDTO`，可选追加 `MemoryDslDTO[]`），控制器再 `yaml.stringify(instanceToPlain(xpert))` 包成 `{ data }`。② 导出为模板 `POST /api/xpert/:id/export/template` → `XpertExportTemplateHandler` = 上述 DSL → `yaml.stringify` → `XpertTemplateService.saveExportedXpertTemplate`（落盘 + 目录登记）→ 回写 `xpert.exportedTemplate`。③ 导入 `POST /api/xpert/import?templateId&workspaceDataScope` → `XpertImportHandler.execute()`。④ 复制 `POST /api/xpert/:id/duplicate` body `{ basic, isDraft }`。⑤ 模板同步 `POST /api/xpert/:id/sync-template` → `XpertSyncTemplateCommand`。
- **事务边界**：导出只读。导入的落库动作（`create` 或 `saveDraft`）非事务；模板导出是「写盘 + 写 `templates.json` + 回写 `exportedTemplate`」三步**无事务**，多进程并发整文件写会互相覆盖。`duplicate` = export→import 两个命令串联，同样无外层事务。
- **预期结果**：`importAsNewXpert` 产出 `latest: true`、`version: null` 的新行并把 DSL 落成草稿；`overwriteExistingXpertDraft` **只改 `draft`**，已发布版本与 Xpert 身份不变；`duplicate` 产出与源助手同构但 `team` 被 `body.basic` 覆盖的新助手；`sync-template` 只刷草稿图并保留本实例的 `xpert` 外部绑定节点/边。
- **错误处理**：`workspaceDataScope` 非 `shared|user` → 400 `XpertWorkspaceDataScopeInvalid`；导入缺 `draft.team` → 400；`overwriteExistingXpertDraft` 要求 `draft.team.type === currentXpert.type` 且双方都有 `team.agent.key`；`resolveExternalRelativePath` 拒绝绝对路径与 `..` 越界；导出/导入失败统一包装成 500。
- **真实代码示例**

```ts
// packages/server-ai/src/xpert/xpert.controller.ts
async duplicate(@Param('id') id: string, @Body() body: { basic: Partial<IXpert>; isDraft: boolean }) {
    const sourceXpert = await this.service.findOne(id)
    const xpertDto = await this.commandBus.execute(new XpertExportCommand(id, body.isDraft, false))
    const dsl = instanceToPlain(xpertDto)
    return await this.commandBus.execute(
        new XpertImportCommand(
            { ...dsl, team: { ...dsl.team, ...body.basic } },
            { workspaceDataScope: workspaceDataScope ?? sourceXpert.workspaceDataScope }
        )
    )
}
```

`importManagedDSL` 与普通 `importDSL` 的唯一差别是 `normalizeCopilotModels: true`（走 `prepareManagedLlmModelSyncContext` + `syncImportDraftLlmModels`，把 DSL 里不可用的 `copilotModel` 换成当前组织可用/主模型）；`POST :id/import/managed` 额外带 `targetXpertId`。

## Recipe 4 走运行时 API 跑一次会话

- **业务目标**：以 client secret 或 API-Key 受众面，在「当前用户可访问的已发布 Assistant」上开线程、发消息、拿流式回复。
- **调用顺序**：① `POST /api/ai/assistants/search`（或 `:id` / `:id/runtime-capabilities` / `:id/models`）→ `AssistantsController` → `PublishedXpertAccessService.findAccessiblePublishedXperts` / `getAccessiblePublishedXpert`，再由 `applyAssistantScope(xpert)` 改写请求头 `organization-id` / `x-scope-level`。② `POST /api/ai/threads` → `ThreadsController.createThread` → `ThreadCreateCommand`。③ `POST /api/ai/threads/:thread_id/runs/stream`（或 `runs/wait`）→ 运行控制；长连接侧另有 `GET /api/ai/threads/:thread_id/stream`（SSE，30s 心跳）。④ 取消/暂停走 `runs/:run_id/cancel`、`runs/:run_id/pause`、`runs/:run_id/resume`。
- **事务边界**：运行时链**不引入域内事务**；准入判定每次请求独立执行（受 5 分钟 `userXperts` 守卫缓存影响的是 `XpertGuard`，不是准入查询）。流式回复本身经 `HandoffQueueService` 交接 + `callback.transport = 'redis-pubsub'` 回传，跨进程异步。
- **预期结果**：`search` 只返回 `publishAt IS NOT NULL` 且 `latest` 命中的行；`getOne` 出参经 `transformAssistant` 投影；会话在目标组织 scope 下创建；`userXpertId` 存在时 `getAccessiblePublishedXpertForCurrentUser` 会再二次校验。
- **错误处理**：受众凭证与目标 Assistant 不匹配 → 403 `You do not have access to this assistant.`（`PublishedXpertAccessService` 明文，不退化「查不到」）；`model_id` 缺失/非字符串 → `AssistantModelPreferenceInputRequired` / `AssistantModelPreferenceInputInvalid`；流式游标非法 → `InvalidStreamCursor`；缺 pause token → `PauseTokenRequired`。
- **真实代码示例**：该链无单一可摘录函数，实际装配如下（路径与守卫均来自源码）。

```text
AssistantsController  @Controller('assistants')  →  /api/ai/assistants
  @Public() + ApiKeyOrClientSecretAuthGuard + @AllowClientSecretBindings(ENTERPRISE_XPERT)
ThreadsController     @Controller('threads')     →  /api/ai/threads
  POST ''                                →  ThreadCreateCommand
  POST ':thread_id/runs/stream'          →  运行 + SSE
  GET  ':thread_id/stream'               →  活动快照流（30s 心跳）
```

## Recipe 5 运行时读写 Assistant 文件

- **业务目标**：让「能跑这个 Assistant」的用户在其**数据卷**里列目录、读、写、上传、下载、删除文件——不需要是其创作工作区的成员。
- **调用顺序**：① `GET /api/ai/assistants/:assistantId/workspace/capabilities` → `AssistantWorkspaceFilesController` → `AssistantFilesService.forRuntime(id)` → `bind()` 内 `ResolveAssistantFileAccessCommand`。② 其余 7 个端点（`files` / `file`(GET) / `file/download` / `file`(PUT) / `file/upload` / `file/save-binary` / `file`(DELETE)）**每个都重新 `forRuntime(id)`**。③ 创作侧走 `XpertController` 的 `:id/workspace/*` → `XpertWorkspaceFilesService`（Studio 兼容外观，全部转 `forAuthoring(id)`）。
- **事务边界**：授权与卷访问**无数据库事务**；每次操作独立派发命令并 `VOLUME_CLIENT.resolve(scope).ensureRoot()`，再用 `VolumeSubtreeClient` 做文件操作。上传另算 `contentSha256` 并返回 `IArtifactWorkspaceFileReference`（`source: 'platform.workspace.files'`）。
- **预期结果**：返回的能力位恒为 `{ canList, canRead, canWrite, canDelete }` 全 true；隔离**不靠能力位而靠卷根**——`shared` 映射 `{ catalog: 'xperts', isolateByUser: false }`（tenant + Assistant 身份），`user` 映射 `{ catalog: 'user-xperts', userId, xpertId }`（再按用户隔离）。授权用户对共享卷文件可读可写可删（显式协作语义）；用户隔离卷只在自己的根下可读写。
- **错误处理**：`entry === 'authoring'` 且存在 `RequestContext.currentApiPrincipal()` → 直接 403（`Delegated credentials cannot select the Studio authority`）；缺 tenant/user 上下文 → 403 `WorkspaceFileAccessDenied`；`operation` 当前不改变判定，能力位全开；`..` 越界由 `VolumeSubtreeClient.resolveSubtreeRelativePath` 抛 400；缺文件 → `WorkspaceFileUploadRequired`；shape 非法 → `WorkspaceFileInvalidRequest`；`workspaceDataScope = 'user'` 但缺 `userId` → `XpertWorkspaceUserRequired`。
- **真实代码示例**

```ts
// packages/server-ai/src/xpert/assistant-files/assistant-files.service.ts
forRuntime(assistantId: string) {
    return this.bind(assistantId, 'runtime')
}

forAuthoring(assistantId: string) {
    return this.bind(assistantId, 'authoring')
}

private bind(assistantId: string, entry: AssistantFileEntry) {
    // Reauthorize each operation, including after a previously successful list or capability lookup.
    const authorize = (operation: AssistantFileOperation) =>
        this.commandBus.execute(new ResolveAssistantFileAccessCommand(assistantId, operation, entry))
    const client = async (operation: AssistantFileOperation) => {
        const { scope } = await authorize(operation)
        const volume = await this.volumeClient.resolve(scope).ensureRoot()
        return new VolumeSubtreeClient(volume, { allowRootWorkspace: true })
    }
```

## Recipe 6 发公共分享链接并开 ChatKit 会话

- **业务目标**：把一个已发布且 `app.public` 的 Assistant 作为匿名可用应用分享出去，浏览器侧拿短 TTL client secret 后直接对话。
- **调用顺序**：① `POST /api/xpert/:identifier/chatkit-session`（`@Public()`）→ `XpertController.createPublicChatkitSession`。② `XpertService.findPublicChatAppXpert(identifier)`（必须已发布且 `app.public`）。③ `getOrSetAnonymousId(res)`：读 httpOnly cookie `anonymous.id`，无则生成 uuid 并回写（`maxAge` 365 天，`secure`/`sameSite` 由 `x-forwarded-proto` 决定）。④ `UserService.ensureCommunicationUser({ thirdPartyId: 'public-xpert:<xpertId>:anonymous:<anonymousId>' })`。⑤ `SecretTokenService.create({ type: SecretTokenBindingType.PUBLIC_XPERT, entityId: xpert.id })`。⑥ 客户端携带 secret 打 `/api/ai/ai/v1/chat` 或匿名公共 App 的 `:name/chat-app`(SSE)。
- **事务边界**：无事务。会话创建是「cookie 写回 + 幂等建用户 + 签发令牌」三步独立副作用。
- **预期结果**：返回 `{ client_secret, expires_at, expires_after, xpertId, assistantId, organizationId }`；`expires_after` 非法或缺省归 600、上限 3600。后续请求由 `PublishedXpertAccessService.currentPublicXpertId()` 收口——只放行绑定的那一个 xpert，且要求 `app.enabled && app.public`。
- **错误处理**：identifier 查不到已发布公共 App → 404；应用被 `app.enabled = false` 关闭 → 403；公开会话对 `findAccessiblePublishedResources` / `getAccessiblePublishedResource` **直接 403**（不暴露资源目录）；会话内对话访问由 `assertPublicXpertSessionConversationAccess` 校验 `createdById` 与 `xpertId`（同族放行）。清 cookie / 换设备即丢历史，且每次 cookie 变更会累积新的匿名账号。
- **真实代码示例**

```ts
// packages/server-ai/src/xpert/xpert.controller.ts
async createPublicChatkitSession(
    @Param('identifier') identifier: string,
    @Body() body: { expires_after?: number; currentClientSecret?: string },
    @Res({ passthrough: true }) res: Response
) {
    const xpert = await this.service.findPublicChatAppXpert(identifier)
    const anonymousId = this.getOrSetAnonymousId(res)
    const anonymousUser = await this.userService.ensureCommunicationUser({
        tenantId: xpert.tenantId,
        thirdPartyId: `public-xpert:${xpert.id}:anonymous:${anonymousId}`,
        username: `${xpert.slug || xpert.id}:${anonymousId}`
    })
```

## Recipe 7 企业 H5 接入（bootstrap → session → client secret）

- **业务目标**：把 Assistant 挂到企业微信一类的 H5 平台，用企业身份源换一次性授权码，再换 client secret，最后进 ChatKit 受众面跑会话。
- **调用顺序**：① `GET /api/xpert/:identifier/enterprise-h5/:platform/bootstrap`（`@Public()`）→ `EnterpriseChatkitSessionService.getBootstrap` → `resolveContext`：`findEnterpriseH5Xpert`（原生 QueryBuilder，`identifier` 是 uuid 按 `id` 否则按 `slug` + `latest = true`，要求 `publishAt IS NOT NULL`、`organizationId` 非空、`app.enabled`、`channels[platform].enabled`、`integrationId` 非空）→ 组织一致性校验 → `strategy.meta.enterpriseH5.platform` 匹配 → `strategy.getIdentityBootstrap(integration)`。② `POST .../session`，body `{ grant: { type: 'authorization_code', code } }` → `requireIdentityGrant` → `strategy.exchangeIdentity` → `assertIdentity`（provider / `externalOrganizationId` / `subjectId` / `accountBinding.provider` / `accountBinding.subjectId` 五项全等）→ `AccountBindingService.resolveUser`。③ 拿到 `ENTERPRISE_XPERT` client secret（TTL 固定 600 秒）后打 `/api/ai/assistants` / `/api/ai/threads` 等受众面端点。
- **事务边界**：无事务；身份断言是纯比较，令牌签发由 `SecretTokenService` 落库单行。
- **预期结果**：bootstrap 在**身份校验之前**返回白名单 `EnterpriseH5Xpert`（`id/slug/name/type/description/avatar/title/titleCN/version/publishAt/starters/features/tenantId/organizationId/app`）+ `platform` + `clientConfig`；session 成功时签发 `ENTERPRISE_XPERT` 令牌并带 `enterpriseH5Scope: { platform, integrationId }`；未绑定账号时返回 `{ status: 'account_binding_required', accountBindingProvider }` 而不报错。
- **错误处理**：bootstrap 查不到（未发布 / 无 `organizationId` / channel 未启用）→ 404 `EnterpriseH5XpertNotFound`；集成能力缺失 → 503 `EnterpriseH5BootstrapUnsupported` / `EnterpriseH5IdentityExchangeUnsupported`；换身份失败 → 401 `EnterpriseH5IdentityVerificationFailed`；断言不等 → 401 `EnterpriseH5IdentityMismatch`；凭证被消费时 `currentEnterpriseXpertScope()` 要求 `resourceScope.kind === 'assistant'` 且 `platform`/`integrationId` 齐备，否则 403 `EnterpriseAssistantBindingRequired`。
- **真实代码示例**

```ts
// packages/server-ai/src/xpert/enterprise-chatkit-session.service.ts
/** Published Xpert fields safe to expose through the anonymous H5 bootstrap endpoint. */
export type EnterpriseH5Xpert = Pick<
    IXpert,
    | 'id' | 'slug' | 'name' | 'type' | 'description' | 'avatar'
    | 'title' | 'titleCN' | 'version' | 'publishAt' | 'starters' | 'features'
    | 'tenantId' | 'organizationId' | 'app'
>

/** Bootstrap response returned before enterprise identity verification. */
export type EnterpriseH5ChatAppBootstrap = {
    xpert: EnterpriseH5Xpert
    platform: TEnterpriseH5Platform
    clientConfig: Record<string, unknown>
}
```

## Recipe 8 工作区成员与可见性管理

- **业务目标**：管理创作容器 `XpertWorkspace` 的成员、可见性、软删/归档/恢复，并让列表与点读看到同一套权限结论。
- **调用顺序**：① 创建 `POST /api/xpert-workspace` → `XpertWorkspaceService.createWorkspace`（`ownerId` 取自 `RequestContext.currentUserId()`，`settings` **只保留** `access.visibility`，`status` 默认 `active`）。② 成员覆盖 `PUT /:workspaceId/members` → `updateMembers`（`assertCanManage` → `normalizeMemberIds` → 要求 `In(ids)` 数量**完全命中** → 有 `organizationId` 时校验 `UserOrganization` 同租户同组织且 `isActive` → 覆盖 `members`）。③ 可见性 `POST /:workspaceId/visibility` → `updateVisibility` → 私有 `applyVisibility`。④ 生命周期 `DELETE /:workspaceId/soft`（软删）、`PUT /:workspaceId/recover`、`POST /:workspaceId/archive`、`DELETE /:workspaceId`（硬删），均先 `assertCanManage`。⑤ 默认工作区 `POST /:workspaceId/default` → `setMyDefault`；读取 `GET /my/default?purpose` → `findMyDefault(purpose)`。
- **事务边界**：每次变更一次 `save`，非事务。归档等价于 `updateWorkspace(id, { status: 'archived' })`。
- **预期结果**：`visibility` 三值互斥且与 `organizationId` 绑定——`tenant-shared` 要求**无** `organizationId`、`organization-shared` 要求**有**；写回时保留 `settings` 其他键。`archived`（以及 NULL 视作未归档的补集）在 `getCapabilities` 中直接判为四项全 false。`purpose` 只在**列表入口** `findAccessibleWorkspaces(orderBy, { purpose })` 生效（`authoring` 会剔除「跨组织 tenant-shared 只读」支），点读 `getCapabilities(workspace, { includePublishedRunAccess })` **没有** `purpose` 形参。
- **错误处理**：`workspaceId` 非 UUID → `WorkspaceIdInvalid`（`WorkspaceAuthoringGuard`）；读端点 `WorkspaceAuthoringGuard`（`assertCanAuthor` = `assertCanWrite`），写端点 `WorkspaceOwnerGuard`（`assertCanManage`），无权抛 `Access denied to workspace`；非法 visibility 值 → `WorkspaceVisibilityInvalid`；成员 id 未全部命中 → 400。
- **真实代码示例**

## Recipe 9 市场申请与审批

- **业务目标**：让非创建者通过市场发现 Assistant、提交访问申请、由有审批权的人批准，并在运行时立刻生效。
- **调用顺序**：① 发现 `GET /api/xpert-marketplace` → `XpertMarketplaceService.findMarketplace` → 私有 `buildDiscoverableXpertQuery`（同 tenant + `publishAt IS NOT NULL` + `latest = true` + 允许的 `type`，再 join workspace/businessArea/workspace.members/createdBy/userGroups），每项用 `resolveAccessStatus` 映射到 `not_requested|requested|approved|rejected|accessible|owned`。② 申请 `POST /api/xpert-marketplace/:id/access-requests` → `requestAccess`。③ 审批人看列表 `GET /api/xpert-access-requests/reviewable` → `findReviewableRequests`。④ 批准 `PUT /api/xpert-access-requests/:id/approve` → `approveRequest`；驳回 `.../:id/reject` → `rejectRequest`。
- **事务边界**：`requestAccess` 单行 upsert（唯一键 `(tenantId, organizationId, xpertId, requesterId)`），非事务。`approveRequest` 是**三步无事务副作用**：`ensureAccessGroup`（查/建 UserGroup）→ 申请人加入 `group.members` → 组加入 `xpert.userGroups`；随后写 `status=APPROVED`、`reviewerId`、`response`、`reviewedAt`、`accessGroupId`。任何一步失败都可能留下部分授权。
- **预期结果**：审批通过后 `xpert_access_request.accessGroupId` 指向复用的 UserGroup（`managedBy = XPERT_MARKETPLACE`、`managedEntityType = XPERT`、`managedEntityId = xpert.id`，名字 `Xpert access - {label}` 截断 100）；运行时由 `hasRuntimeAccess`（无组织 tenant-shared 工作区 / 工作区 owner 或成员 / 同 tenant+org 的 `userGroups[].members`）与准入查询里的 `xpert_to_user_group` join 立即生效——即「市场授权 = UserGroup 成员关系」。
- **错误处理**：已 `owned`/`accessible` 再申请 → 400 `XpertMarketplaceAlreadyAccessible`；缺 tenant/org/user 上下文 → 403 `XpertMarketplaceTenantRequired` / `OrganizationRequired` / `UserRequired`；自审 → `XpertMarketplaceSelfReviewForbidden`；无权审 → `XpertMarketplaceReviewForbidden`；申请不存在 → `XpertMarketplaceRequestNotFound`；申请人不存在 → `XpertMarketplaceRequesterNotFound`。**撤销**只能靠删组（外键 `SET NULL`）或从组内移除成员：`accessGroupId` 与 `xpert_to_user_group` 没有反向同步，组被删/改名后记录仍显示 `approved` 而 `hasRuntimeAccess` 已为 false。
- **真实代码示例**

```ts
// packages/server-ai/src/xpert-marketplace/xpert-marketplace.service.ts
async approveRequest(id: string, input?: TXpertAccessRequestDecisionInput): Promise<IXpertAccessRequest> {
    const request = await this.findRequestForDecision(id)
    const xpert = await this.assertCanReviewRequest(request)

    const group = await this.ensureAccessGroup(xpert)
    const requester = await this.userRepository.findOne({
        where: { id: request.requesterId, tenantId: this.currentTenantId() }
    })
    if (!requester) {
        throw new NotFoundException(
            t('server-ai:Error.XpertMarketplaceRequesterNotFound', {
                defaultValue: 'The request user was not found.'
            })
        )
    }
```

## 横向注意点

- **三元权限面不可互换**：创作面（`WorkspaceAuthoringGuard` / `assertCanAuthorById`）、运行面（`PublishedXpertAccessService`）、文件面（`AssistantFilesService.forRuntime/forAuthoring`）各有独立入口；`XpertService.findOne()`、`XpertWorkspaceService.canAccess()`、workspace `canRun` **都不是**文件 ACL。
- **入口由服务端选**：`ResolveAssistantFileAccessCommand` 的 `entry` 来自 `forRuntime`/`forAuthoring` 的硬编码，不来自请求数据；运行时被拒后不得回退 authoring。
- **`@Public()` 不等于匿名可用**：是否放行由该路由附加的 `ApiKeyOrClientSecretAuthGuard` + `@AllowClientSecretBindings(...)` + 领域守卫共同决定。
- **发布是重路径**：`publish.handler.ts`、`publish-triggers.handler.ts`、`import.handler.ts` 是本域最大的单文件写路径，且失败不回滚已完成步骤。
