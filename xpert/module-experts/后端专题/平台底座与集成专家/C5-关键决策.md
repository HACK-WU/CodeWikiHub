## D1 字典族「只读端点 + 种子」而非运行时可写
- **分类**：架构设计
- **动机（避坑）**：现象——若 language/country/currency 开放写端点，改一条译名或加减一个 ISO 代码就变成「多环境手工对账」；下游还按值引用它们（`contact.country` 存 `isoCode` 字符串而非外键、`organization_language` 由 `language` 的 `OneToMany cascade: true` 维护、`is_system` 决定“哪些语言是系统语言”）。后果——字典事实上变成业务表：任何一次删改都会向下游传导出孤儿引用，且无法区分「系统字典项」与「用户自建项」。
- **决策**：三类**全局**字典只提供读端点（`GET /api/languages`、`GET /api/languages/getByName/:name`、`GET /api/country`、`GET /api/currency`，全部 `@Public`）；写路径只有两条——开发/空库种子（`SeedDataService` 基础种子阶段 `createCountries → createCurrencies → createLanguages`、`pnpm seed:module`）与租户侧显式 `LanguageInitCommand → LanguageService.initialize()`；`is_system` 由 `LanguagesEnum` 判定，是系统语言口径的唯一权威。
- **背景约束**：`language.code` 有 `@Unique(['code'])`（整批 `save()` 呈 upsert 语义），country/currency 的 `isoCode` 只有**非唯一** `@Index()`；`createLanguages` 用 `faker.internet.color()` 生成 `color`、每次重跑都会变并把 `description` 重置为空（源码中种子**不可复现**）；唯一约束冲突被 try/catch + `console.log({error})` 吞掉，country/currency 无去重逻辑（重复执行重复插行）。
- **被否决方案**：无（实现层未见对「开放字典写端点」的显式否决记录）。
- **重新评估触发条件**：需要「租户自定义字典项」（自定义国家/货币/语言）或合规要求字典变更可审计可回滚时——须先补唯一约束与幂等 upsert，再开放受控写面。
- **关联代码**：`file://packages/server/src/language/language.controller.ts`、`file://packages/server/src/country/country.controller.ts`、`file://packages/server/src/currency/currency.controller.ts`、`file://packages/server/src/language/language.seed.ts`、`file://packages/server/src/core/seeds/seed-data.service.ts`
- **证据来源**：实现层 [01-架构.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/01-架构.md)「关键不变量」1；[02-实现.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/02-实现.md)「字典族实现」；[07-运维.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/07-运维.md)「字典种子运维」；[04-模型.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/04-模型.md) ③。

## D2 凭据「明文落库 + 出口收窄」而非加密存储
- **分类**：安全合规
- **动机（避坑）**：现象——`data_source_authentication.password` 是普通 text 列（无加密、无 `select:false`、无 `@Exclude`），`data-source.entity.ts` 里 `options` 上方的 `// @Exclude()` **处于注释态**，`prepareDataSource` 在 `authType=BASIC` 时还把当前用户的 `username/password` **回写进 `options`** 并直接交给 runner，`GET /:id` 又直出实体；后果——任何新增读取面（关系展开、导出、日志字段、新的 DTO）都会带出明文连接凭据，而唯一的兜底只剩库级权限。
- **决策**：本域不做应用层加密，改用「**最小暴露面 + 白名单 DTO + 严格代理**」三层——① 出网收窄：只有 `GET /api/data-source`（列表）挂 `ClassSerializerInterceptor` + `DataSourcePublicDTO` 白名单（`id/name/type/typeId/authType/createdAt/updatedAt/createdBy`），`options`/`authentications` 不下发；② 插件侧严格化：唯一出口 `DataSourceRuntimeService.open` 要求 actor 三元组与 `RequestContext` 逐项相等、只放行 `mysql/doris/postgres`、`engineCatalog==='internal'`、逐方法 `check(write)`，并用 `updatedAt` 做 revision 复核，源码逐字「Proxy preserves method receivers and never exposes resolved credentials or the runner.」；③ 集成侧列表用 `IntegrationPublicDTO` 把 `options` `@Exclude()`。
- **背景约束**：**实测本批 14 表无任何加密列**（无 `encrypted*`、无 KMS/信封字段，模块内检索 `encrypt|decrypt|cipher|AES` 0 命中；`core/utils/crypto.ts` 的 AES-256-GCM 工具在注释里明写用于 GitHub token，本域未调用）；`integration.options`（含 `botToken`）无任何隐藏，并会进入 view-extension 的 `hostSnapshot`；个人凭据 30 天硬编码到期（`validUntil = now + 30d`）且**无续期/失效路径**；`authType≠BASIC` 时账号密码由前端写进 `options`，换密必须同时改 `options`。对照工具域 `mcp_api_key.keyHash + encryptedSecret`（`select:false`）与 `mcp_oauth_policy.introspectionClientSecretEncrypted`。
- **被否决方案**：无（未见对「给凭据加列级加密 / 恢复 `@Exclude()`」的显式否决记录）。
- **重新评估触发条件**：新增任何 `options`/`password` 读取面（导出、事件、日志字段、`$relations` 展开），或合规要求「库内不可读」时——须改为列级加密 + `select:false`，并把注释态的 `@Exclude()` 恢复，同时复核 `DataSourcePublicDTO` 白名单与宿主快照。
- **关联代码**：`file://packages/server/src/data-source/data-source.entity.ts`、`file://packages/server/src/data-source/authentication/authentication.entity.ts`、`file://packages/server/src/data-source/dto/public.dto.ts`、`file://packages/server/src/data-source/utils.ts`、`file://packages/server/src/data-source/data-source-runtime.service.ts`
- **证据来源**：[02-实现.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/02-实现.md)「凭据存储与使用 …… 脱敏/加密边界核实结论」；[04-模型.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/04-模型.md)「加密与脱敏边界（凭据类列逐列核实）」；[07-运维.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/07-运维.md) 二/五节；[01-架构.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/01-架构.md)「关键不变量」3。

## D3 xpert-table 物理表激活走 UPGRADE DDL
- **分类**：架构设计
- **动机（避坑）**：现象——Meta 行与外部库物理表必须同时存在才有用，而 `upsertTable` 的 validate →（可选 rename）→ activate 三步**串行且不同事务**，`deleteTable` 也是先 `DROP_TABLE` 再 `softDelete`；后果——激活失败必须区分「新表」与「既有表」两套清理语义，drop 失败会在外部库留下**物理表孤儿**，非 active 改名会让 `physicalTableName` 与 Meta 名脱节。
- **决策**：把「逻辑真相」与「物理真相」拆开——`xpert_table` 只存 Meta（`columns json` / 7 态 `status` / `physicalSchema` / `physicalTableName` / `version` / `activatedAt`），物理结构与数据留在外部库；激活统一走 `DBTableAction.CREATE_TABLE` + `DBCreateTableMode.UPGRADE`（**幂等升级而非重建**），成功后 `active + activatedAt` 并清 `message`，失败 `error + message`；行与 SQL 的入口**刻意不暴露 HTTP**，只经 `@WorkflowNodeStrategy(DB_SQL)`/`(DB_INSERT)` 交给助手工作流，使工作区授权成为唯一执行边界。
- **背景约束**：激活失败时**新表硬删逻辑行、既有表只标 ERROR**（一致性优先于保留现场）；`deleteTable` 的 `DROP_TABLE` 失败仅 `logger.error` 后照常软删；`version` 只是普通 int 列（**不是 `@VersionColumn`**），激活/升降级全靠 `status + version` 手工管理；`validateTableName` 在异常分支对「更新」放行（`return !entity.id`）；7 态中 `ready/needsMigration/deprecated` **未找到写入点**。
- **被否决方案**：无（未见对「DDL 与元数据同事务」或「只做逻辑视图不落物理表」的显式否决记录）。
- **重新评估触发条件**：外部库不支持 `UPGRADE` 语义、或需要「一次提交保证 DDL 与 Meta 同时成功」时——须引入补偿/对账作业，并把 delete 改为两阶段（先标记后 drop）。
- **关联代码**：`file://packages/server-ai/src/xpert-table/xpert-table.service.ts`、`file://packages/server-ai/src/xpert-table/xpert-table.entity.ts`、`file://packages/server-ai/src/xpert-table/plugins/sql/strategy.ts`
- **证据来源**：[01-架构.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/01-架构.md)「关键不变量」4 与「结论」②；[02-实现.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/02-实现.md)「xpert-table 实现」与「技术债与 hack」8；[05-接口.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/05-接口.md) 第五节；[04-模型.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/04-模型.md) ②。

## D4 integration 扫码授权走 Redis 会话状态机
- **分类**：安全合规
- **动机（避坑）**：现象——若让用户在表单里直接粘贴第三方 access token，平台就要长期保管可直接冒用的长期凭据，也无法归并「同一账号多次授权」、无法区分「扫码页 / 触发器」两类来源、无法给出可过期的中间态；后果——令牌泄漏即等于账号被接管，且平台侧没有任何可撤销窗口与重试语义。
- **决策**：把授权拆成「定义 → 会话 → 令牌 → 使用/失效」四段，会话是 **Redis-only 状态机**（`waiting → authorized | expired | denied | failed`）：`begin` 把 `expiresAt` 夹在 30..600s、`intervalSeconds ≥ 2`，并按 `tenant:org:user:provider:purpose` 收敛同键旧会话（先 `cancel`）；`poll` 先写回 `nextPollAt` 再调 provider（防重入）并接受 provider 的退避增量（上限 600s）；`complete` 用**会话 id 作为新集成 id** 换取崩溃重试幂等，命中既有行只合并 `options` 并跑 `onUpdate`（`outcome=reused`），可用策略的 `getQrAuthorizationIdentity` 归并同账号；`cancel` 直删键；全部步骤在 `RedisLockService.runWithLock(key, 60000, fn)` 内串行。
- **背景约束**：源码逐字不变量「QR credentials never leave the server; sessions belong to one user and organization.」「Redis locks serialize polling, completion and cancellation across API instances.」；会话**不落库、无审计表**，Redis 清空即全失效；`complete` 的账号去重依赖策略提供 `getQrAuthorizationIdentity`，缺省时可能重复建 `integration` 行；写入门槛由 `integration.slug` 唯一索引 + 策略 `validateConfig` 提供；`purpose` 由 `context.{xpertId,triggerProvider}` 哈希派生，触发器侧用 `assertContext` 校验归属。
- **被否决方案**：无（未见对「表单直填令牌」的显式否决记录）。
- **重新评估触发条件**：需要授权过程审计、跨实例持久化会话或断点续扫时——须补会话表与审计链，并把 identity 去重从「可选策略」升级为契约必填。
- **关联代码**：`file://packages/server/src/integration/integration-qr.service.ts`、`file://packages/server/src/integration/integration-qr.controller.ts`、`file://packages/server/src/integration/integration.service.ts`、`file://packages/server/src/integration/events/authorized.event.ts`
- **证据来源**：[02-实现.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/02-实现.md)「扫码授权会话」；[05-接口.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/05-接口.md) 第七节；[03-数据流转.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/03-数据流转.md)「链路五 integration 授权链」；[07-运维.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/07-运维.md) 第七节。

## D5 view-extension 走宿主注册表 + 缓存
- **分类**：架构设计
- **动机（避坑）**：现象——宿主（如集成详情页）与视图（插件提供的卡片）若硬编码在服务端，每加一个宿主/视图都要改核心代码并重新发版；反之若完全不缓存，清单读取会按「宿主 × 插件」扇出，每次请求都穿透到全部 provider；后果——扩展点变成发版瓶颈，或热路径被插件扇出拖垮（实现层把 `listSlotViews` 与 `initialization` 作业、desktop-shell 巡检并列为热点路径）。
- **决策**：宿主走**装饰器 + 发现**注册（`@ViewHostDefinition('integration')` → `ViewHostDefinitionRegistry.onModuleInit` 用 `DiscoveryService` + `Reflector` 建表，新增宿主只需新增一个 provider 类）；视图走**插件注册表**（`ViewExtensionProviderRegistry`），解析链固定为 `provider.supports(context) → readProviderViewManifests → normalizeManifest → isManifestActiveForContext → filterVisibleManifests → 按 order 排序`，单 provider 异常只 `logger.warn` 不影响整体；缓存以 `VIEW_EXTENSION_CACHE_SERVICE_TOKEN` 暴露（清单 60s、view data `min(ttlMs, 30s)`），**两条失效链**——实体级 `IntegrationViewHostCacheSubscriber`（insert/update/remove → `invalidateHostIdentity`）与全局 `StrategyBus.events$` → `clearAll()`，清单键并入 `features + hostState` 的 sha1 摘要。
- **背景约束**：控制器类级 `@Public()`，安全完全落在 `ApiKeyOrClientSecretAuthGuard` + `AllowClientSecretBindings(ENTERPRISE_XPERT)` 与宿主 `canRead`/manifest `permissions` 上（文件头逐字「Shared protocol routes; each entry point supplies its own authentication boundary.」）；`hostSnapshot` 会带出 `options.botToken`（仅 `INTEGRATION_VIEW|INTEGRATION_EDIT` 兜底）；注册表是**进程内内存**，插件升级/重装后必须重启宿主；remote component 强约束 `protocolVersion === 1` + `isolation === 'iframe'`，响应 `Cache-Control: no-store`。
- **被否决方案**：无（未见对「硬编码宿主/视图」的显式否决记录）。
- **重新评估触发条件**：出现第二个 `@ViewHostDefinition` 宿主、或要求插件热更新「不重启即生效」时——须把注册表改为可刷新，并复核缓存键与两条失效链是否仍覆盖新宿主。
- **关联代码**：`file://packages/server/src/view-extension/host-definition.registry.ts`、`file://packages/server/src/view-extension/view-extension.service.ts`、`file://packages/server/src/view-extension/view-extension.cache.service.ts`、`file://packages/server/src/view-extension/hosts/integration-view-host.definition.ts`、`file://packages/server/src/view-extension/subscribers/integration-view-host-cache.subscriber.ts`

## D6 desktop-shell 独立 3 表 + 2 个 SQL 迁移
- **分类**：安全合规
- **动机（避坑）**：现象——远程命令执行若把「设备」「授权」「执行」揉进一张表或复用聊天记录，就没有可重放的唯一锚点：一次 `runId+toolCallId` 重试会执行两次；审批过的参数可被改写后复用；设备重连/换机无法作废在途授权。后果——不可幂等、不可撤销、不可审计；同时「pending 授权」与「已批准执行」会被系统混为一谈。
- **决策**：拆成三张表并各给唯一键——`desktop_shell_device`（`UNIQUE(tenantId,organizationId,userId,installationId)`，`credentialHash` sha256 + `credentialExpiresAt` + `connectionEpoch` + `leaseExpiresAt`）、`desktop_shell_grant`（`@Index(deviceId,enabled)`，`operation jsonb` = `{runId,toolCallId,argsHash,decision}`）、`desktop_shell_operation`（`UNIQUE(tenantId,runId,toolCallId)` + `@Index(deviceId,state)`，9 态 `state`、`output`/`seq`/`outputBytes`/`truncated`）；并配**两个显式 SQL 迁移**：`20260924-desktop-shell.sql`（`BEGIN…COMMIT` + `CREATE TABLE IF NOT EXISTS` 建三表、2 个 UNIQUE、2 个索引，additive）与 `20260928-desktop-shell-approval.sql`（单句 `ADD COLUMN IF NOT EXISTS operation jsonb NULL`，为审批链补参数绑定列）。
- **背景约束**：三表真相在 DB，Redis 只做唤起提示（源码逐字「every dispatch rechecks persisted epoch and grant; Redis is only a wake-up hint.」「DB state is authoritative; notification delivery never authorizes a second execution.」）；`grant.operation.decision='pending'` **只路由不执行**（`prepare` 把有效期压到 ≤10 分钟）；`argsHash = sha256([command,cwd,timeoutSec])` 双端一致；`grantId → desktop_shell_grant` **未声明 `ON DELETE`（NO ACTION）**，`assistantId/threadId/runId` 无外键；`LIMITS`（command/chunk 16KiB、output 1MiB、result 64KiB、timeout 60/600s、lease 90s、grant 8h）双端校验；单设备并发靠 `DEVICE_BUSY`，超租约统一标 `unknown/EXECUTION_UNKNOWN`（**明确不重放**）；三表**无 TTL 清理作业**，长期运行需自建归档。
- **被否决方案**：无（未见对「复用聊天/单表建模」的显式否决记录）。
- **重新评估触发条件**：需要多设备并行、或把 `unknown` 改为自动对账/重放时——须先把 1s 巡检改为基于 `deadline` 的查询驱动，并复核 `grantId` 外键与清理作业。
- **关联代码**：`file://packages/server-ai/src/desktop-shell/desktop-shell.entities.ts`、`file://packages/server-ai/src/desktop-shell/migrations/20260924-desktop-shell.sql`、`file://packages/server-ai/src/desktop-shell/migrations/20260928-desktop-shell-approval.sql`、`file://packages/server-ai/src/desktop-shell/desktop-shell-operation.service.ts`
- **证据来源**：[04-模型.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/04-模型.md)「desktop-shell 三表与两个迁移」；[01-架构.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/01-架构.md)「关键不变量」7；[02-实现.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/02-实现.md)「desktop-shell 实现」；[07-运维.md](file://.module-experts/后端专题/平台底座与集成专家/implementation/07-运维.md) 第三/六节。

## D7 initialization 幂等靠稳定 jobId + 出队重查
- **分类**：架构设计
- **动机（避坑）**：现象——组织/租户/用户入组要触发跨 9 个域模块的副作用（工作区、环境、模板导入、技能仓库、ClawXpert、membership）；事件可能重复投递，队列表可能因 Redis 抖动重放，而用户可能在两次重试之间被移出组织。后果——重复建工作区/重复装插件，或**给已离职成员恢复访问**（后者是安全问题而非数据问题）。
- **决策**：把「该不该做」与「做过没有」分开——入队侧 `@OnEvent → queue.add` 只做入队并给**稳定 jobId**（`org-bootstrap:{orgId}`、`tenant-skill-repository-bootstrap:{tenantId}`、`user-org-bootstrap:{orgId}:{userId}`、`user-org-cleanup:{orgId}:{userId}`）实现队列级去重，统一 `attempts:3, backoff:10_000, removeOnComplete:true`（链式 `user-default-skills:{workspaceId}` 为 `attempts:8, backoff:30_000`）；执行侧每个 job **先重查前置条件再动手**（`bootstrapUserInOrganization` 首步 `isActiveOrganizationMember`）；人工恢复入口 `ClawXpertRecoveryService.recover` 对 failed 作业走 `existing.retry()`，否则用同一 jobId `add`。
- **背景约束**：**数据库层没有对应唯一约束兜底**，幂等完全依赖 Bull/Redis 存活与 `removeOnComplete` 语义不变（源码中甚至未出现「幂等」字样，以 jobId 去重表达）；队列内没有 `RequestContext`，靠 `runInOrganizationContext`/`runInTenantContext`/`captureRequestContext` 还原租户、组织与语言；ClawXpert 安装失败只记 `clawXpertError` 并继续（由 processor 抛错触发重试）；`canRecover` 对 `SUPER_ADMIN` 为 false；**bootstrap 无任何 HTTP 面**（只有 ClawXpert 的 2 条恢复端点）。
- **被否决方案**：无（未见对「事件直连同步执行 + DB 唯一约束」的显式否决记录）。
- **重新评估触发条件**：Redis 数据丢失后需要重建入组状态、或需要 bootstrap 可被外部系统按需触发/可查询进度时——须补 DB 侧状态位与唯一约束，并开放受控 HTTP 面。
- **关联代码**：`file://packages/server-ai/src/initialization/bootstrap.processor.ts`、`file://packages/server-ai/src/initialization/bootstrap.service.ts`、`file://packages/server-ai/src/initialization/clawxpert-recovery.service.ts`

## D8 ai-model 与 model-access 的职责切分
- **分类**：架构设计
- **动机（避坑）**：现象——若把「provider 是否存在、凭据是否合法」与「该用户能否用这个模型、用了多少要计费」放在同一模块，进程内的插件注册表就会与租户级授权/账本耦合；后果——模型目录一变就要碰授权与计费代码，provider 目录无法被插件独立扩展，且「凭据校验」会被误解为「已授权」。
- **决策**：`ai-model` 只做**Provider 目录门面 + 凭证 schema 校验**——`AIModelModule` 仅装配 `DiscoveryModule + CqrsModule + RouterModule`（**无 `TypeOrmModule`，0 表**）；`AIProvidersService.getProvider(name, throwError?, organizationId?)` 直查 plugin-sdk 的 `AIModelProviderRegistry`；`providerCredentialsValidate` = 取 `provider_credential_schema` → `ProviderCredentialSchemaValidator.validateAndFilter` → 策略 `validateProviderCredentials` → **只把过滤后的凭据**交回调用方落库；对外 HTTP 仅 `@Public` 的图标端点。授权解析与记账完全在 `model-access`/`model-gateway`/`copilot`（它们注入同一个 `AIProvidersService`，`createModelTarget` 的形参类型即 `ReturnType<AIProvidersService['getProvider']>`）。
- **背景约束**：`getProvider` 默认**不抛**（插件卸载后返回 `undefined`，需 `throwError=true` 才抛 `AIModelProviderNotFoundException`）；本域不存模型、不存密钥、不判授权与配额；凭证校验命令由**邻域 `copilot-provider`** 的 upsert handler 消费，**不在 HTTP 上**；handler 内留有 `// Todo: encrypt secret variables in credentials`，说明加密不在本域（具体落点在消费域 `[推测]`）。
- **被否决方案**：无（未见对「把授权/计费并入 ai-model」的显式否决记录）。
- **重新评估触发条件**：需要把「凭据可用性」做成对外 HTTP 能力、或把计费前移到目录层时——须先定义新的鉴权面与凭据落点归属，**不得**在 `ai-model` 内落表。
- **关联代码**：`file://packages/server-ai/src/ai-model/ai-model.service.ts`、`file://packages/server-ai/src/ai-model/ai-model.module.ts`、`file://packages/server-ai/src/ai-model/commands/handlers/provider-credentials-validate.handler.ts`、`file://packages/server-ai/src/model-access/model-access.service.ts`

## D9 export-import 保留模块但不给 HTTP 面

- **被否决方案**：无（未见对「直接删除该模块」或「补齐导入能力」的显式否决记录）。

## D12 xpert-table 复用 data-source 代理层
- **分类**：架构设计
- **动机（避坑）**：现象——`xpert_table` 的物理表必须建在**外部库**里，而外部库的连接、凭据、引擎白名单已经由 `data-source` 统一持有；若 `xpert-table` 自建一套连接与凭据读取，就会出现第二条出网路径与第二份凭据解析逻辑。后果——凭据注入口径（`authType=BASIC` 的当前用户注入、`options` 合并）被复制多份，任何一处变更都会漏改；且工作区授权无法与数据源作用域校验串成一条链。
- **决策**：`xpert-table.module.ts` **imports `DataSourceModule`**，数据库清单与适配器全部走 data-source 的既有出口——`XpertDatabasesQuery`（handler 注入 `DataSourceService`）提供可激活的目标库，`XpertDatabaseAdapterQuery(database)` 提供适配器并 `finally teardown()`，`getDatabaseSchemas` 直接调 adapter 的 `getCatalogs`；`XpertTableService` 自身只关心「逻辑表授权 + DDL 动作 + 行列操作」，读写前先过 `XpertWorkspaceBaseService` 的 `assertWorkspaceReadAccess`/`assertWorkspaceWriteAccess`。
- **背景约束**：这条复用带来两个后果——① `xpert-table` 的 DDL/DML 与 `data-source` 的查询共享同一 runner 生命周期（**没有连接池、没有 schema 缓存**，代价由外部库决定）；② 装配面出现双向依赖：`xpert-workspace` 以 `forwardRef(() => XpertWorkspaceModule)` 与 `xpert-table` 互为装配，且 `xpert-table.module` 从 server-core 引入**同名但不同实现**的 `DataSourceModule`；另有一个死角：`XpertDatabaseSchemaQuery`（`get-database-schemas.query.ts`）**未注册 handler**，属死 Query 类。
- **被否决方案**：无（未见对「xpert-table 自建连接层」的显式否决记录；实现层「技术债与 hack」9 只记录了死 Query 类）。
- **重新评估触发条件**：需要让自定义表落在与 data-source 不同的引擎/租户隔离维度，或需要为 DDL 单独配连接池与超时时——须显式新增一条受控出口，而不是在 `XpertTableService` 内部另开连接。
