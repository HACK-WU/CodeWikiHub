## 2. integration 侧 spec（逐个）

## 3. view-extension 侧 spec（逐个）

- **`view-extension.service.spec.ts`**（最大）：`createService()` 用**四个手写替身**（假 `providerRegistry`、假 `hostDefinitionRegistry`、假 `permissionService`、假 `cacheService`——后者把 `getOrSet*` 直接透传给 loader 并按需记录 `invalidateView`）直连 `new ViewExtensionService(...)`，不建 Nest 容器。断言覆盖：视图识别在取数之前且区分缓存开关；**缺失/被拒视图绝不用原始 URL 参数打标签**；JSON 与文件两种 transport 下的嵌套视图识别（保留外层视图身份）；缺失/被禁视图/被禁动作三类负例；`listFeatureViewSummaries` 只回权限过滤后的 Feature 关联且不激活视图、不外泄可执行 schema；agent 工作台的统一槽位与旧槽位等价；草稿解析选项贯穿宿主发现与权限检查；按 Feature 交集返回 Project 专家；vue runtime 的远程组件入口；**企业 Xpert 会话被限定到绑定的 agent 宿主**；文件动作路由到解析出的 provider 并失效缓存；动作未声明时的清晰错误；JSON 动作拒绝文件请求；声明的文件访问用途与非法用途各一例。

## 5. 需外部依赖的用例

**结论：本子域 9 个 spec 均可脱离 PG / Redis / 外部 OAuth 运行**，依据逐条实测：

| 依赖 | 是否被 spec 需要 | 实测依据 |
|---|---|---|
| PostgreSQL / 任何关系库 | **否** | `integration-lifecycle.spec.ts` mock 掉 `TenantOrganizationAwareCrudService` 并注入 `getRepositoryToken(Integration)` 为空对象；`connector-app-integration.service.spec.ts` 用假 `{find, findOne, createQueryBuilder}`；`resolve-connector-integration.handler.spec.ts` 用假 `{findOne}` |
| Redis | **否** | `integration-qr.service.spec.ts` 用 `Map` 作假 redis 客户端，`RedisLockService` 被替身直通；断言「跨实例退避」是**在同进程内新建第二个 service 复用同一个假 redis** 模拟，而不是真连 Redis |
| 外部 OAuth / 扫码 provider | **否** | 所有 `beginQrAuthorization` / `pollQrAuthorization` 都是 jest 假实现（含 `intervalIncrementSeconds` 与异常分支） |
| Nest 容器 / HTTP 栈 | 部分 | 两处真建容器：`integration-lifecycle`（`Test.createTestingModule` + `DiscoveryService`/`ModulesContainer`）与 `resolve-connector-integration.handler`（`CqrsModule.forRoot()`）；其余为 `new XxxService(...)` 直连。**不启 HTTP server** |
| i18n 资源文件 | 一处 | `view-extension.utils.spec.ts` 的 `beforeAll` 会在 `i18next` 未初始化时 `initI18next(path.resolve(__dirname, '../../..'))`，即**需要仓库内语言资源可读**（本地文件，无网络） |
| 文件 / 对象存储 | **否** | 文件动作用内存里的 `{buffer, originalname, mimetype, size}` 对象，provider 的 `executeViewFileAction` / `resolveViewFile` 均为假实现 |
| 时间 | 间接 | QR spec 依赖 `Date.now()` 与 `nextPollAt` 的真实推进；`it.each([NaN, Infinity, -5, 0])` 覆盖非法退避增量。**未使用 jest 假定时器**（`[推测]`：因此对系统时钟回拨敏感） |

## 6. 缺口

1. **`IntegrationViewHostDefinition` 无专测**：`hostSnapshot` 里 `botToken` 的摘取、`enabled: true` 硬编码、`status` 兜底 `'unknown'` 全靠 `view-extension.service.spec.ts` 里的**假宿主**绕过——真实宿主行为无断言。父级实测口径（「integration.options 含 botToken 无隐藏」）在本子域**没有任何回归用例**。
2. **缓存服务无 spec**：`view-extension.cache.service.ts`（7.29 KB，键构成、五张台账、三条失效路径、`clearAll`）无独立 spec；`view-extension.service.spec.ts` 把 `cacheService` 整体替身化，因此「TTL 上限 30s」「`key.includes(':slot:')` 的清单键联动失效」「跨实例不失效」都被跳过。
3. **`host-definition.registry.ts` 无 spec**：装饰器扫描与「同 hostType 静默覆盖」的语义未固化；新增第二个宿主时会缺回归保护。
4. **`view-request-metrics.ts` 无独立 spec**：仅通过 `view-extension.service.spec.ts` 的「不用原始 URL 参数打标签」用例间接触达；`VIEW_ROUTES` 白名单（`/api/view-hosts` 与 `/api/ai/groups/:groupId/workbench` × 6 后缀）与 `getViewDataRequestMetricRoute` 别名未逐条断言。
5. **`IntegrationController` 无 spec**：7 个端点的状态码（201/202）、`select-options` 的 JS 侧 features 过滤、`normalizeIntegrationUpdatePayload` 与 `/test` 的 500 包装均无用例；`integration-lifecycle.spec.ts` 只测 handler 不测 controller。
6. **无「详情出口是否剪裁 `options`」的用例**：`IntegrationPublicDTO` 只被列表路径使用，基类 `GET /:id` 的序列化边界没有断言（对应 03 文档的风险 4）。
7. **无跨进程/并发用例**：QR 的 Redis 锁只测「锁被占 → 409」，未测真并发下的 `orIgnore()`/唯一索引冲突分支；`ConnectorAppIntegrationService.create` 的 `orIgnore` 幂等路径在 spec 里未覆盖（源码注释明确提到多副本重试）。
8. **无端到端链路用例**：`IntegrationQrService.complete` → `IntegrationViewHostCacheSubscriber` → `ViewExtensionService.listSlotViews` 的联动（本子域唯一「集成表变更影响视图」的机制）无集成测试，只靠各自的替身覆盖。
9. **契约层用例在邻域**：`packages/contracts/src/integration.spec.ts` 与 `api-key-or-client-secret.guard.spec.ts` 覆盖了部分边界，但归属其它包/模块，本子域文档只能交叉引用。

## 7. 结论

1. **可执行性**：判定为 **✅ 可跑（不实跑，仅给命令与判据）**。9 个 spec 的依赖全是进程内替身（假 Redis `Map`、假 repository、假 provider/host/permission/cache、`Cjsr` 之外无外部服务），唯一「外部资源」是 `view-extension.utils.spec.ts` 需要仓库内 i18n 资源文件可读。命令 1 与命令 3 即可覆盖本子域全部断言面。
2. **测试风格**：`integration` 侧偏「handler/服务级 + 真注册表」（唯一真建 Nest 容器的地方），`view-extension` 侧偏「纯函数 + 手写替身直连」（最小依赖，甚至 controller 用例只读反射元数据）；两者都不做 HTTP 层断言。
3. **覆盖强度的不均匀是最大特征**：授权会话（QR）与视图服务/工具函数覆盖厚实（含负例、并发锁、退避、权限负例），而**三个关键实现文件零专测**——`view-extension.cache.service.ts`、`host-definition.registry.ts`、`view-request-metrics.ts`，恰好是「缓存一致性、宿主注册、凭据快照」这三处风险所在。
4. **补测优先级建议**：① `hostSnapshot.botToken` 的授权与出口回归（对齐 03 文档 §9 风险表）；② 缓存三条失效路径 + TTL 上限；③ 宿主注册表的重复 hostType 语义；④ 详情端点 `options` 剪裁边界；⑤ `IntegrationController` 的 7 端点状态码与 500 包装。
