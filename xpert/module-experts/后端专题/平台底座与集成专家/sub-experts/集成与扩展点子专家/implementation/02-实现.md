**写入链路（`IntegrationUpsertHandler`）**：有 `id` ⇒ `findOne(id)` 取 `previous` → `omit(input,'id')` → `applyStrategyValidation({...previous, ...patch})`（策略 `validateConfig`，返回体经 `pickValidatedIntegrationPatch` **只放行 `name/description/slug/provider/options/features` 六字段**，防止策略越权改租户/权限字段）→ `runStrategyUpdateHook(previous, next)`（**`provider` 变化时改跑 `previous` 的 `onDelete` 后直接返回**）→ `update` → 回读；无 `id` ⇒ 校验后 `create`。**钩子顺序是先校验、再跑钩子、最后落库**，异常统一降级为 `BadRequestException`。

**删除链路（`IntegrationDelHandler`）**：`findOne` → `runStrategyDeleteHook(previous)` → `service.delete(id)`——**钩子失败则行保留**（spec 有对应用例）。

**旁路服务能力**：`IntegrationService` 另提供 `getProviders`、`getIntegrationStrategy`、`readOneById`、`findOneByIdWithinTenant`（租户内强校验）、`ensurePrincipalUser`（为集成补一个 `thirdPartyId = integration:<id>` 的技术主体，供 API Key 绑定；随后把 `userId` 回写）。注意 `applyStrategyValidation` / `runStrategy*Hook` 走的是 `listRegistrations()`（**不带组织过滤**），而 `getIntegrationStrategy` 走的是按组织解析的 `registry.get`——两条取策略路径口径不同。

## 2. 扫码授权全流程（/api/integration/qr 4 端点）

| # | 方法 | 路径 | 关键行为 |
|---|---|---|---|
| 1 | POST | `/api/integration/qr/providers/:provider` | `beginSchema` 校验 `name`(1..100)/`description`(≤10000)/`avatar`；同 `tenant:org:user:provider:purpose` 旧会话先 `cancel`；provider 失败 → **502** `Error.IntegrationQrUnavailable`；返回 `{id, authorizationUrl, expiresAt, intervalSeconds}` |
| 2 | GET | `/api/integration/qr/sessions/:id` | 返回 `{status}`（**绝不含 `deviceCode` / `options`**）；未到 `nextPollAt` 直接回状态；provider 失败 → **502** `Error.IntegrationQrPollFailed` |
| 3 | POST | `/api/integration/qr/sessions/:id/complete` | 要求 `status === 'authorized'`；返回 `{id,name,slug,provider,outcome}` |
| 4 | DELETE | `/api/integration/qr/sessions/:id` | `read(id, true)`（允许缺失）后 `redis.del`，幂等 |

**全流程七步**：① 前端在扫码页调 begin，服务端经 `strategy.meta.setup.qrAuthorization` + `beginQrAuthorization()` 拿 `deviceCode/authorizationUrl/expiresInSeconds/intervalSeconds`（`strategy()` 私有方法在二者缺失时抛 400）；② `expiresAt = now + clamp(30..600)s`、`intervalSeconds = max(2, provider)`、`status='waiting'`、`nextPollAt=0`，以 `integration:qr:session:<id>` 写 Redis（`PX = 剩余 TTL`），并把 id 写入 `integration:qr:active:<tenant>:<org>:<user>:<provider>:<purpose>`；③ 前端按 `intervalSeconds` 轮询 poll，每次轮询把 `nextPollAt` 前移并**先落盘再调 provider**，防多实例并发重复调用；④ provider 回 `authorized` 时把 `options` 暂存进会话；⑤ 前端调 complete，服务端以 **`session.integrationId ?? id`（即会话 id）作为新集成 id** 做崩溃重试幂等；⑥ 若策略提供 `getQrAuthorizationIdentity(options)`，先按 `(provider, tenant, organization)` 拉候选并比对 identity——命中既有行则**只合并 `options`** 并跑 `runStrategyUpdateHook`（`outcome='reused'`），未命中则以 `id = 会话 id` 建行；identity 存在时整个保存动作再套一层 `integration:qr:account:<tenant>:<org>:<provider>:<sha256(identity)>` 锁；⑦ 成功后清空会话的 `deviceCode` 与 `options` 并回写。

**锁与归属**：全部四步都在 `RedisLockService.runWithLock('<key>:lock', 60000, op)` 内串行，`acquired === false` 时抛 409 `{code: 'INTEGRATION_QR_BUSY'}`；`read()` 用 zod 校验后同时校验 `userId/tenantId/organizationId` 三元，任一不符统一 404 `Error.IntegrationQrExpired`（防探测）。**第二入口**：`packages/server-ai/src/xpert/trigger-connection.service.ts` 的 `begin/poll/cancel/complete` 全部先调 `assertContext(session, xpertId, triggerProvider)`——`purpose` 由 `context.{xpertId,triggerProvider}` 的 sha256 派生，触发器维度与集成维度互不干扰。

章节来源：[integration-qr.controller.ts](file://packages/server/src/integration/integration-qr.controller.ts)（关键符号：begin / poll / complete / cancel / Cache-Control no-store）、[integration-qr.service.ts](file://packages/server/src/integration/integration-qr.service.ts)（关键符号：begin / poll / complete / cancel / assertContext / sessionSchema / lock / invalid）、[integration.model.ts](file://packages/contracts/src/integration.model.ts)（关键符号：TIntegrationQrSession / TIntegrationQrStatus / TIntegrationQrErrorCode / TIntegrationQrCompletion）

## 3. 令牌与凭据的落库与使用

**实测结论（照录，不做美化）**：

- `Integration.options` 是 `@Column({ type: 'json', nullable: true })` 的 `any`——**无 `select:false`、无 `@Exclude`、无加密**。`botToken`、`clientSecret` 等键名完全由各 provider 策略决定，实体层不做任何键级约束。
- 唯一的**读取收窄**只有两处：列表中 `IntegrationPublicDTO` 的 `@Exclude() options`；`ConnectorAppIntegrationService.publicOption()` 只回 `{ id, name, organizationId }`。详情/服务层/宿主快照**都直读 `options`**。
- **授权过程中令牌还会短暂以明文驻留 Redis**：`poll` 在 provider 返回 `authorized` 时执行 `session.options = result.options`，随后 `write(session)` 把整份会话（含令牌）序列化进 `integration:qr:session:<id>`，TTL = 授权窗口剩余时间（≤600s + 续写）；`complete` 落库成功后才 `session.options = undefined` 并回写。若 complete 长期不被调用，令牌会在 Redis 中留到会话过期。
- 会话里的 `deviceCode` 同样只在服务端使用（`poll` 时喂给 `pollQrAuthorization`），`cancel` 只删会话键、**不通知 provider 撤销**（`[推测]`：provider 侧 device code 是否自然过期取决于各策略实现）。
- `IntegrationQrService.complete` 合并策略为 `options: { ...existing?.options, ...session.options }`——**是浅合并**，嵌套对象会整体被新值覆盖，且不会清理旧键（`[推测]`：换账号时可能残留上一次的令牌字段）。

**风险清单**：① 库内明文（任何库级读取、备份、慢日志都可拿到）；② 列表白名单是**唯一**的 HTTP 收窄，新增任何 `$relations` 展开或导出面都会带出 `options`；③ `hostSnapshot.botToken` 把凭据以进程内对象形式交给插件 provider（见 §4）；④ 本目录检索 `encrypt|decrypt|cipher|AES` 为 0 命中 ⇒ 应用层零加密。

## 4. 视图宿主注册与解析

**注册（写侧）**：`@ViewHostDefinition(hostType)` 只是 `SetMetadata(VIEW_HOST_DEFINITION, hostType)`；`ViewHostDefinitionRegistry.onModuleInit()` 遍历 `discoveryService.getProviders()`，逐个 `reflector.get(VIEW_HOST_DEFINITION, instance.constructor)`，命中则 `definitions.set(hostType, instance)`。**无排序、无冲突报错、无卸载钩子**。

**宿主契约（`ViewHostDefinitionContract`）**：`hostType` + `slots: XpertViewSlot[]` + `resolve(hostId, options) → { workspaceId?, hostSnapshot?, context? } | null` + `canRead(context, resolution, options) → boolean` + 可选 `prepareFileAction(context, request, file) → request`。

**唯一在用宿主（`IntegrationViewHostDefinition`）**：`hostType = 'integration'`；`slots = [{ key: 'detail.main_tabs', mode: 'tabs', order: 0 }]`；`resolve` 用 `RequestContext.currentTenantId()` 调 `findOneByIdWithinTenant`（找不到直接 `NotFoundException`），并构造 `hostSnapshot`：`id / name / provider / type(=provider) / enabled=true（硬编码常量）/ botToken（读 options）/ status（options.status ?? connectionStatus ?? state ?? 'unknown'）/ workspace / team / botUser / users / lastSyncAt / updatedAt`。`canRead()` 要求 `INTEGRATION_VIEW` 或 `INTEGRATION_EDIT`（`hasAnyPermission([...], false)`）。**`resolve` 忽略 `options.isDraft`**，即集成宿主目前不支持草稿分支。

**解析（读侧，`ViewExtensionService.resolveHostContext`）**：① `assertEnterpriseXpertViewHost(hostType, hostId)`——若当前 API 主体的 `clientSecretBindingType === ENTERPRISE_XPERT`，则强制 `hostType === 'agent'` 且 `resourceScope.kind === 'assistant'` 且 `resourceScope.xpertId === hostId`，否则 403；② `hostDefinitionRegistry.get(hostType)` 为空 → 404 `Unknown view host`；③ `buildBaseViewHostContext` 从 `RequestContext` 取 tenant/org/user/locale，缺 tenant 或 user → 401；④ 运行时 scope：读请求头 `x-xpert-view-project-id` / `x-xpert-view-conversation-id` 组装 `runtimeScope`；⑤ `definition.resolve(hostId, mergedOptions)`，返回 null → 404 `View host '<type>:<id>' was not found`；⑥ `permissionService.assertHostReadable` → 403 `No permission to access this view host`；⑦ 拼 `XpertResolvedViewHostContext`：`...resolution.context` 在前、`baseContext` 覆盖同名键，附 `workspaceId / hostSnapshot / slots`（按 `order` 升序）。

**清单解析（`resolveProviderManifest`）**：`splitPublicViewKey` 以 `__` 拆分 `providerKey__manifestKey`（两段都不得含 `__`）→ `providerRegistry.get(providerKey, organizationId)`（失败 404）→ `provider.supports(context)`（false → 404 `does not support this host`）→ 遍历 `context.slots` 逐个 `readProviderViewManifests` → 命中 `manifest.key === manifestKey` 后 `normalizeManifest` → `isManifestActiveForContext` 不通过则 404。

**槽位与工作台兼容**：`normalizeWorkbenchSlot` 仅对 `hostType === 'agent'` 把 `LEGACY_AGENT_WORKBENCH_SLOTS` 映射到 `AGENT_WORKBENCH_SLOT`；`readProviderViewManifests` 优先用统一槽位声明，仅当返回空数组时回退遍历旧槽位并按 key 去重（`fixed` 声明优先）。

**清单规范化要点（`view-extension.utils.ts`）**：公共键 `providerKey__manifestKey`；`source` 归一为 `{provider, plugin?, version?}`；`dataSource.mode` 强制 `'platform'`；`hostType` / `slot` 必须与上下文一致；`view.type` 必须属于 `stats|table|list|detail|raw_json|remote_component`；`title` 必须有非空 `en_US`；`actions` 默认 `placement='toolbar'`、`transport='json'`；`fileAccess.purposes` 去重且至少一项（仅 `preview|download`）；`hostEvents.subscriptions` 键唯一、`action.type ∈ {refresh, forward, refresh-and-forward}`；`runtime.featureProviders` 由宿主侧按「所有 requiredFeatures 的 provider 交集」重算（**忽略 provider 自报**）。

## 5. 缓存与失效

**两个缓存入口（cache-aside）**：`getOrSetSlotViews(context, slot, 60*1000, loader)` 与 `getOrSetViewData(context, viewKey, query, min(ttlMs, 30*1000), loader)`；数据缓存在 `view-extension.service.ts` 侧受 manifest 的 `dataSource.cache.enabled` 控制，`enabled === false` 时**直连 provider 不读不写缓存**。

**键构成**：`view-extension:<tenant>:<org|tenant>:<userId>:<dataScopeKey | hostType:hostId>:slot:<slot>:<sha1(capabilities.features 排序 + hostState)>` 与 `...:view:<viewKey>:<sha1(归一化 query)>`。三处刻意设计：① 宿主 scope 含 `userId`（不同用户不共享）；② 槽位键并入「激活态摘要」，避免 features/hostState 变化后命中陈旧清单；③ 查询键只取白名单字段（page/pageSize/cursor/search/sortBy/sortDirection/selectionId/filters），`filters` 再做 `{key, operator ?? 'eq', value}` 投影。

**三条失效路径**：① `invalidateView(context, viewKey)`——删该视图的全部 query 变体键，并额外删该宿主身份下的**槽位清单键**（`key.includes(':slot:')`）；② `invalidateHostIdentity(identity)`——按 `tenant:org:dataScopeKey|hostType:hostId` 删该宿主全部键；③ `clearAll()`——`onModuleInit` 订阅 `strategyBus.events$` 后全清，并清空全部键台账。

**触发点**：动作执行返回 `refresh: true` ⇒ `invalidateView`（JSON 与文件动作各一处）；`IntegrationViewHostCacheSubscriber`（构造函数内 `dataSource.subscribers.push(this)`，`listenTo() === Integration`）在 `afterInsert/afterUpdate/afterRemove` 调 `invalidateHostIdentity`（缺 `id` 或 `tenantId` 直接返回）——**这是 `integration` 表变更自动反映到宿主视图的唯一机制**。

**一致性局限（实测）**：键台账（`trackedKeys` / `hostKeys` / `hostIdentityKeys` / `viewKeys` / `viewIdentityKeys`）是进程内 `Map/Set`；`deleteKey` 同时从所有台账摘除。因此失效只对本实例登记过的键生效；多副本部署下兄弟实例不会收到通知，只能等 TTL（60s / ≤30s）自然收敛（`[推测]`：仓库内未见跨实例失效广播或键版本号机制）。

## 6. 动作执行与错误语义

`POST …/views/:viewKey/actions/:actionKey`（`@UseValidationPipe({whitelist, transform})`，body DTO 仅 `targetId? / input? / parameters?`）与 `POST …/actions/:actionKey/file`（`FileInterceptor('file')` + multipart body 解析，缺文件即 400 `file is required`）。

执行次序：宿主解析 → manifest 解析 → `ensureManifestVisible` → 动作存在性 → `ensureActionVisible` → `identifyViewRequest` → transport 校验 → provider 能力校验 → `provider.executeViewAction(context, manifestKey, actionKey, request)`；文件动作额外在 provider 之前插入宿主钩子 `hostDefinition.prepareFileAction(context, request, uploadedFile)`，并对 `file.originalname` 先做 `decodeMultipartFileName`（注释说明「Multer decodes multipart filename bytes as Latin-1」）。成功且 `result.refresh` 为真则失效该视图缓存。

| 场景 | 状态码 | 文案/载荷 |
|---|---|---|
| 未知宿主 / 宿主解析为 null | 404 | `Unknown view host '<type>'` / `View host '<type>:<id>' was not found` |
| 宿主 `canRead` 为假 | 403 | `No permission to access this view host` |
| manifest 不可见 / 权限不足 | 403 | `No permission to access this extension view` |
| 动作未声明 | 404 | `Action '<key>' was not found for view '<view>'` |
| 动作 permission 或 Project 角色不符 | 403 | `No permission to access this extension action` / `The current Project role does not allow this extension action` |
| transport 不匹配 | 400 | `does not support JSON transport` / `does not support file transport` |
| provider 未实现对应方法 | 404 | `is not supported for view '<view>'` |
| 远程组件非 iframe / runtime 不支持 / `protocolVersion !== 1` | 400 | 各自专用文案；入口 key 另做路径穿越校验（拒 `\`、`..`、前导 `/`、`scheme:`） |
| provider 内部异常 | — | **原样冒泡**，无统一包装（与 `integration` 侧「钩子异常降级 400」不同口径） |

## 7. 与前端契约（清单字段）

**路由契约**：前端 `view-extension-api.service.ts` 拼 `${viewHostsPath}/:hostType/:hostId/slots/:slot/views`（`encodeURIComponent(slot)`，`?isDraft=true` 显式开关），`view-extension-route.service.ts` 决定路由族——带 `scope.groupId` 时改走 Project 分组端点，其余走 `/api/view-hosts`；运行时 scope 经 `X-Xpert-View-Project-Id` / `X-Xpert-View-Conversation-Id` 两个头传递（后端 `getRuntimeResolutionOptions` 只取首值并 trim）。移动端 `deployment.viewHostsPath` 恒为 `/api/view-hosts`。

**清单字段（`XpertExtensionViewManifest`）分三组**：

**权限过滤对前端的可见效果**：`listSlotViews` 返回的每条 manifest 已经过 `visible !== false` + `permissions` 过滤，且其 `actions` 已按 action 权限与 Project 角色裁掉——前端拿到的清单即「可渲染集合」；`getViewManifest` 再次过滤 actions 后返回。**`hostSnapshot`（含 `botToken`）不出现在 7 个端点的响应体**（它只进 `XpertResolvedViewHostContext` 交给插件 provider）——但它是凭据暴露面的一部分（见 §3 风险③）。

## 8. 设计模式

1. **策略注册表 + 依赖倒置**：`IntegrationStrategyRegistry` / `ViewExtensionProviderRegistry` 都由插件在进程内注册，宿主只依赖接口（`IntegrationStrategy` / `IXpertViewExtensionProvider`），宿主代码零 provider 分支。
2. **装饰器 + 发现（decorator-driven discovery）**：`@ViewHostDefinition` + `DiscoveryService`/`Reflector`，新增宿主 = 新增一个 provider 类。
3. **CQRS**：写走 `IntegrationUpsertCommand` / `IntegrationDelCommand`，读走 `GetIntegrationQuery`（`IntegrationController` 其余端点直用 service）。
4. **DTO 白名单出口**：`IntegrationPublicDTO`（class-transformer）+ `publicOption` 函数式收窄，两种风格并存。
5. **cache-aside + 双失效链**：TTL 短 + 实体订阅者 + 事件总线全清。
6. **幂等键设计**：会话 id 作集成 id；`integration.slug` 唯一 + `orIgnore()` 回查（connector-app）。
7. **轮询防重入与退避**：`nextPollAt` 先写后调 + `intervalIncrementSeconds` 累计封顶。
8. **权限下推到声明层**：`permissions` 与 `requiredHostAccess` 写在 manifest/action 上，由服务端统一裁决，而不是散落在插件里。

## 9. 热点路径

1. **`listSlotViews`（宿主 × 插件扇出）**：每次未命中缓存要对 `providerRegistry.listEntries(org)` 的每个 provider 依次 `supports` + `getViewManifests`；单 provider 抛错只 `logger.warn` 续跑，因此故障被掩盖但请求仍成功。60s 缓存是主要护城河。
2. **`getViewData`**：TTL 上限 30s；`cache.enabled === false` 的视图每次穿透到 provider。
3. **`IntegrationViewHostDefinition.resolve`**：`integration` 宿主的每次视图请求都要 `findOneByIdWithinTenant` 查一次库（且不带索引之外的限制）——这是最容易被重复触发的 DB 读取。
4. **QR `poll`**：前端按 `intervalSeconds`（下限 2s）轮询，每次一把 Redis 锁 + 一次会话读写；`active` 键与会话键各一次 `SET`。
5. **`ConnectorAppIntegrationService.list`**：按 `(tenantId, organizationId IsNull|org, provider)` 双条件取行后在 JS 侧 `descriptor.fields` 校验「已配置」，行数增长后是线性成本。

## 11. 技术债

1. **`integration.options` 明文落库 + 无隐藏**：列表 DTO 是唯一 HTTP 收窄；任何新增读取面（`$relations`、导出、日志字段）都会带出凭据。`[推测]`：符合父级 D-2「明文落库 + 出口收窄」的既定取舍，而非遗漏。
2. **授权令牌在 Redis 会话中明文驻留**：`poll` 写入 `session.options`，直到 `complete` 才清除；会话无审计表，Redis 清空即全失效。
3. **`IntegrationController` 无显式权限装饰器**：7 个端点只靠全局 `AuthGuard`，而同域的 QR 端点要求 `INTEGRATION_EDIT`；即「读写集成定义（含凭据）」的门槛低于「发起扫码授权」。
4. **`/api/integration/test` 把策略校验失败包成 500**：`InternalServerErrorException(error)` 丢掉了「配置错误 vs 服务端故障」的区分。
5. **`applyStrategyValidation` 与 `getIntegrationStrategy` 取策略口径不一致**：前者用 `listRegistrations()`（无组织过滤），后者按组织解析 ⇒ 组织级策略可能在校验阶段被忽略（`[推测]`：spec 只覆盖了 tenant fallback 与跨租户隔离）。
6. **`ConnectorAppIntegrationService.create` 绕过命令总线**：直用 `createQueryBuilder().insert().orIgnore()`，**不跑 `validateConfig` 与任何策略钩子**，与 CRUD 路径的写入语义分叉。
7. **宿主注册表无冲突检测、无热更新**：同 `hostType` 静默覆盖；插件升级需重启进程。
8. **缓存失效的进程边界**：键台账在内存，多副本下需靠 TTL 收敛；`StrategyBus` 全清是唯一全局兜底且仍按实例执行。
9. **`hostSnapshot` 无条件读 `botToken`**：即使调用方只需要 `id/name`，凭据也会进入 `context` 传给所有 provider；`enabled: true` 是硬编码常量，不反映真实状态。
10. **provider 异常不包装**：视图 provider 抛出什么就冒泡什么，与同子域策略钩子「统一降级 400」的语义不一致。
11. **`IntegrationViewHostDefinition.resolve` 不支持草稿**：`options.isDraft` 被忽略，与协议层 `?isDraft` 能力不匹配。
12. **`features` jsonb 无 CHECK 约束**、`userId` 的 `ManyToOne` 未声明 `onDelete`（`[推测]`：删除用户时的行为依赖数据库默认）。

## 13. 结论

1. **集成侧**的实现特征可以一句话概括：**写路径被 CQRS + 策略钩子收得很紧（校验 → 钩子 → 落库），读路径却很松（详情/服务层/宿主快照都直读 `options`）**。因此本子域的安全边界实际落在 `IntegrationPublicDTO` 与 `ApiKeyOrClientSecretAuthGuard` 两个点上，而不是实体列约束上。
2. **扫码授权**是全子域最精细的一段实现：会话 id 幂等、identity 归并、双锁分级、退避写回、三元归属校验都在代码里逐条落地，且 spec 对「凭据不出服务端」有显式断言；代价是会话不留痕（无表无审计）与令牌在 Redis 的短暂明文窗口。
3. **扩展点侧**的实现特征是「**声明与裁决分离**」：宿主与 provider 只声明（槽位、清单、权限、激活条件），可读性、可见性、动作权限、激活判定与排序全部由 `ViewExtensionService` + `ViewExtensionPermissionService` 统一裁决，这也是同一套路由能被 `/api/view-hosts` 与 Project 分组入口复用的前提。
4. 真正需要盯住的是三处：**凭据出口**（`options` + `hostSnapshot.botToken` + Redis 会话）、**注册表与缓存的进程内属性**（热更新与跨实例失效）、**两条写入路径的语义分叉**（CommandBus vs connector-app 直插）。
