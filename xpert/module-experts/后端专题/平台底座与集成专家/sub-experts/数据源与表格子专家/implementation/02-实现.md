## 1. 数据源 CRUD 与连接测试（16 端点按主题）

`DataSourceController extends CrudController<DataSource>`，类级 `@ApiTags('DataSource') + @ApiBearerAuth() + @Permissions(PermissionsEnum.DATA_SOURCE_EDIT)`；路由前缀由 `RouterModule.register([{ path: '/data-source' }])` 给出。类内**显式声明 16 条**（与父级 C2 的 `/api/data-source`(16) 口径一致）；基类另提供 `GET count`、`GET pagination`、`GET my`、`POST`、`PUT :id`、`DELETE :id`、`DELETE :id/soft`、`PUT :id/recover` 等继承端点（父级口径未计入，实际可用路由**多于 16**）。

**A. 列表与下拉（3 条）**：`GET /`（`findAlls`，`@Permissions(DATA_SOURCE_VIEW)` + `PermissionGuard` + `ClassSerializerInterceptor`，`$query` 经 `ParseJsonPipe` 解出 `{select, relations, order, findInput}`，返回 `IPagination<DataSourcePublicDTO>` —— **全模块唯一脱敏出口**）；`GET /sql-select-options`（`findSqlDataSources()`，`type.protocol = SQL` 的 `{value:id, label:name}`）；`GET /sql-schema-select-options?dataSource=`（无 `dataSource` 直接返回 `[]`，否则 `getCatalogs` 映射成 `{value:name, label:label||name}`）。

**B. 单条 CRUD（2 条显式）**：`GET /:id`（`findOne(id, { relations, ...options })`，`$relations`/`$query` 都经 `ParseJsonPipe`；**直出实体，不带任何 DTO**，`$relations=["authentications"]` 即明文回显凭据）；`PUT /:id`（`dsService.update(id, entity)` 后 `eventBus.publish(new DataSourceUpdatedEvent(id))`，源码内保留 `@todo Updated cqrs event 应该在哪里发出 ?`）。

**C. 连接测试（2 条）**：`POST /ping`（请求体 `IDataSource`，**不落库**，走 `dsService.ping(body)`）；`POST /:id/ping`（`dsService.ping(id, body)`，以库内为底、请求体覆盖）。两条都 `catch` 后抛 `HttpException(err.message, 500)` —— **状态码恒定 500，排障只能看 message**。

**D. 元数据探察（2 条）**：`GET /:id/catalogs`（失败 `500` + `error.message`；而 service 内部对 `runner.getCatalogs()` 的失败会先 `console.error` 再抛 `new Error('配置错误')`，故此处常见 message 是「配置错误」）；`GET /:id/schema?catalog=&table=&statement=`（**三参数都可选**；给了 `statement` 就走 `runner.describe(catalog, statement)` 并包装成单元素 `[{ name: catalog, tables: [tableSchema] }]`，否则 `runner.getSchema(catalog, table)`；**无 `try/catch`，异常直接冒泡**）。

**E. 查询与能力（3 条）**：`POST /:id/query`（body `{ query: string }`，转发 `Accept-Language` 头，失败抛 **400** `err.message`）；`POST /:id/olap`（`@HttpCode(200)`，body `{ query: { id, body }[] }`，`Promise.all` 并发逐个 `olap(...)`，**成功包 `{id, status:200, data}`，失败包 `{id, status: response.status, statusText, data: response.data}`** —— 依赖 axios 错误的 `response` 形状，非 axios 错误会抛 `TypeError`）；`POST /:id/capabilities/query`（`@HttpCode(200)` + `DATA_SOURCE_VIEW`，body `IDataSourceCapabilityQuery`，失败抛 **400**）。

**F. 认证三件套（3 条）**：`GET /:id/authentication`（`getMyAuthentication`，未命中 `NotFoundException(id)`）；`POST /:id/authentication`（`createAuthentication(id, body)`）；`DELETE /:id/authentication`（按 `{tenantId, dataSourceId, userId}` 删）。

**G. 批量导入（1 条）**：`POST /:id/load`（`FileInterceptor('file')`，body 里 `params` 是 `JSON.parse` 出来的 `sheets` 数组，派 `DataLoadCommand`，失败 `500`）。

## 2. 认证与凭据

**实体字段**（`DataSourceAuthentication`，`@Entity('data_source_authentication')`，继承 `TenantBaseEntity`）：`dataSource`（`ManyToOne(DataSource, it => it.authentications, { nullable: true, onDelete: 'CASCADE' })` + `@JoinColumn()` + **关系上 `@Exclude()`**）、`dataSourceId`（`@RelationId` + 真实 `@Column()`）、`userId`（`@Column()`，**无外键、无索引**）、`username`（`@Column()`）、**`password`（`@Column()` 普通 text 列）**、`validUntil`（`@Column({ nullable: true })`）。类注释写的是「语义模型角色」，与实现用途（个人凭据）不符。

**使用链路**：`utils.prepareDataSource(dataSource, userId?)` —— `userId ||= RequestContext.currentUserId()`，当 `dataSource.authType === AuthenticationEnum.BASIC` 时在 `dataSource.authentications` 里按 `userId` 找行，找不到即 `NotFoundException('未找到当前用户认证信息')`，找到则把 `username/password` **回写进 `dataSource.options`**，随后 `options` 原样成为 runner 构造参数。因此 BASIC 模式下 `options` 在内存中是含明文的。

**写路径**（`createAuthentication`）：按 `{tenantId, dataSourceId, userId}` 查已有行，命中则复用（**upsert 语义**），否则 new；然后 `authentication.username = auth.username`、`authentication.password = auth.password`、`authentication.validUntil = addDays(new Date(), 30)` —— **有效期固定 30 天且无续期/过期校验逻辑**（`validUntil` 在 `prepareDataSource` 里从不被读）。`deleteAuthentication` 按同一三元组删除。`ping` 的两式都会把 `authentications[].userId` **强制改写为当前用户**再走 `prepareDataSource`。

**明文风险与建议。** 实测：`password` 无 `select: false`、无 `@Exclude`、无 transformer、无加密；模块内 `encrypt|decrypt|cipher|AES` 0 命中；`data_source.options` 上方的 `// @Exclude()` 处于注释态；`DataSourcePublicDTO` 只用 `@Expose()` 白名单避开 `options`/`authentications`。据此**数据源凭据是明文落库、且存在两条明文出网口**（`GET /:id`（可带 `$relations`）、`GET /:id/authentication`）。建议（按优先级）：① 列级 `@Exclude({ toPlainOnly: true })` 或 `select: false` + 显式 `addSelect`，先堵回显；② 引入对称加密（KMS/环境密钥）改造 `createAuthentication`/`prepareDataSource` 的读写两侧，并给 `options` 里被注入的 `username/password` 做内存期掩码；③ 给 `(tenantId, dataSourceId, userId)` 加**唯一索引**把现在的约定唯一升级为约束；④ `validUntil` 要么实现校验、要么删除，避免给出虚假的安全感。

章节来源：[authentication.entity.ts](file://packages/server/src/data-source/authentication/authentication.entity.ts)（关键符号：DataSourceAuthentication.password / dataSource 的 @Exclude / validUntil）、[data-source.service.ts](file://packages/server/src/data-source/data-source.service.ts)（关键符号：getMyAuthentication / createAuthentication 的 addDays 30 / deleteAuthentication）、[utils.ts](file://packages/server/src/data-source/utils.ts)（关键符号：prepareDataSource 的 AuthenticationEnum.BASIC 分支）、[public.dto.ts](file://packages/server/src/data-source/dto/public.dto.ts)（关键符号：DataSourcePublicDTO 的 @Exclude / 逐字段 @Expose）

## 3. schema 拉取与缓存

**schema 拉取（无缓存）**：`DataSourceService.getCatalogs(id)` / `getSchema(id, catalog?, table?, statement?)` / `queryCapability(id, query)` / `query(id, statement, options?)` / `import(id, body, options)` / `dropTable(id, tableName, options)` 的骨架**完全一致**：`prepareDataSource(id)` → `queryBus.execute(new DataSourceStrategyQuery(type.type, options))` → `try { runner.xxx() } finally { await runner.teardown() }`。源码里 `// const runner = createQueryRunnerByType(...)` 的注释成对出现，说明已从「按类型本地建连」迁移为「插件注册表 + CQRS」，**旧路径注释保留但不可达**。`queryCapability` 在建模**之前**做键名白名单校验：`CAPABILITY_KEY_PATTERN = /^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$/`，`capability ≤ 128`、`operation ≤ 64`，非法即抛（`data-source-capability.spec.ts` 断言此时 `queryBus` 未被调用）；runner 未实现 `queryCapability` 则 fail-closed 并**先 teardown 再抛**。

**OLAP runner 缓存与失效**：`OlapQueryHandler` 在模块作用域持有 `runners[sessionId][dataSourceId] = { runner, expirationTimes }`，`OBJECT_LIFETIME = 1000*60*10`（10 分钟）。命中即复用（**跳过 `prepareDataSource` 与鉴权重算**，用的是首次创建时的凭据快照）；未命中才 `prepareDataSource(dataSource, user?.id)` 后建 runner。回收由 `setInterval(..., 60000*10)` 完成：过期项 `runner.teardown()` 后 `delete`，session 映射空则删 session，`runnerCleanupTimer.unref()` 保证不阻塞进程退出。**失效只有时间维度**：改数据源不清缓存，`DataSourceUpdatedEvent` 又无消费者。

**插件边界的「版本式失效」**（`DataSourceRuntimeService`，本节与 schema 缓存并列的唯一失效机制）：该类 `@RuntimeCapabilityProvider(DataSourceRuntimeCapability)`（capability id `platform.datasource.workbench`），`implements DataSourceRuntimeApi`。`list(actor)` 先 `authorize(actor)`（四项断言：`actor.{tenantId,organizationId,userId}` 全非空 **且** 与 `RequestContext` 的当前值逐项相等，否则 `ForbiddenException('Data source scope mismatch')`；再按 `write` 判 `DATA_SOURCE_EDIT` 或 `DATA_SOURCE_VIEW`），取 `take: 1000` 后**白名单引擎**：`type.type === 'pg' ? 'postgres' : type.type`，只放行 `mysql|doris|postgres`，其余丢弃。`open({actor, dataSourceId, location})` 再判两件事：引擎在允许集内（否则 `Workbench adapter unavailable`）、`location.engineCatalog` 为空或 `'internal'`（否则 `External catalog unavailable`）；随后把 `location.database/schema` 映射进 options（postgres 用 `database`/`catalog`，其余用 `catalog`）；runner 无 `getWorkbenchAdapter` 则 **teardown 后抛 `Database plugin upgrade required`**。返回的是**逐方法包装的 proxy**：每个方法先 `check()`，`check` 里重新鉴权 + 查库比对 `updatedAt`，不一致就 `close()` 并抛 `Data source changed; reopen the connection`；代理**不暴露 runner、不暴露解析后的凭据**（类注释即此意）。写类方法（`query(mode==='write')`、`transaction`、`importRows`）走 `check(true)` 即要求 EDIT 权限。

章节来源：[data-source.service.ts](file://packages/server/src/data-source/data-source.service.ts)（关键符号：getCatalogs / getSchema / queryCapability / CAPABILITY_KEY_PATTERN / isCapabilityKey）、[olap-query.handler.ts](file://packages/server/src/data-source/queries/handlers/olap-query.handler.ts)（关键符号：runners / OBJECT_LIFETIME / runnerCleanupTimer）、[data-source-runtime.service.ts](file://packages/server/src/data-source/data-source-runtime.service.ts)（关键符号：authorize / list / open / sourceRevision / check / 返回的 adapter proxy）

## 4. 查询代理

**请求 → 授权 → 下发 → 结果回流（HTTP 路径）**：`POST /:id/query { query }` → 类级 `DATA_SOURCE_EDIT` → `dsService.query(id, statement, { headers: { 'Accept-Language' } })` → `prepareDataSource(id)`（scope 断言 + BASIC 凭据注入）→ `DataSourceStrategyQuery` → runner → `runner.runQuery(statement, options)` → 结果**原样返回**（无投影、无行数裁剪）。失败 `catch (err) => throw HttpException(err.message, 400)`。

**其他入口的差异**：`GET /:id/schema`（`describe` 走 `statement` 分支，**无 catch**）；`GET /:id/catalogs`（catch 成 500，runner 侧失败被 service 替换为「配置错误」）；`POST /:id/capabilities/query`（catch 成 400，`error instanceof Error ? error.message : 'Data-source capability query failed'`）；`POST /:id/olap`（逐条包装 status，见 §1-E）；CQRS 侧 `QuerySqlHandler`/`ListTablesHandler`/`QuerySchemaHandler`/`DataSourcePingHandler` 都带 `debug: isDev, trace: isDev`（`NODE_ENV === 'development'` 时才开），**HTTP 侧的同名方法不带这两个 flag** —— 同一能力两条路的 runner 配置并不等价。

**错误与超时**：本域内**没有任何超时设置**（源码检索无 `timeout`/`AbortController`/`timeoutMs`）；错误语义是「**转发 message + 固定状态码**」：ping/catalogs 恒 500、query/capabilities 恒 400、olap 恒 200（HTTP 层）。**唯一具备取消/超时能力的是插件协议**：`DatabaseWorkbenchAdapter.query(value, signal)` 收 `AbortSignal`、并有独立 `cancel()`；但它只经 `DataSourceRuntimeService` 暴露给插件，HTTP 代理路径不传 signal。⇒ 面向用户的「查询超时」目前**只能在插件 adapter 侧实现** `[推测]`。

**批量导入路径（`DataLoadCommand` → `utils`）**：`load.handler` 先 `prepareDataSource(id)` 再 `dataLoad(queryBus, dataSource, sheets, file)`；`dataLoad` 以 `{ ...options, debug: isDev, trace: isDev }` 建 runner，调 `importSheetTables`，**finally teardown**。`importSheetTables` 分三叉：`config.catalog` 存在先 `runner.createCatalog(catalog)`；`mimetype` 是 xlsx → `loadFromExcel`（`readExcelWorkSheets` 逐 sheet 转 JSON buffer，`Promise.all` **并发导入**，异常包成 `BadRequestException`，**finally teardown**）；`mimetype` 是 csv 且 runner 满足 `isCsvImportRunner`（`runner.type === 'pg'` 且 `typeof runner.importCsv === 'function'`）→ **流式 `importCsv`，不物化行**（`utils.spec.ts` 断言此时 `readExcelWorkSheets` 未被调用）；否则回落 `readExcelWorkSheets` 再 `runner.import(..., { format: 'json' })`。字段类型 `CsvImportRunner = DBQueryRunner & { importCsv(...) }` 属于**局部鸭子类型**，不在 `plugin-sdk` 契约里。

章节来源：[data-source.controller.ts](file://packages/server/src/data-source/data-source.controller.ts)（关键符号：query / olap / getSchema 的 catch 与状态码）、[data-source.service.ts](file://packages/server/src/data-source/data-source.service.ts)（关键符号：DataSourceService.query / olap / import / dropTable）、[utils.ts](file://packages/server/src/data-source/utils.ts)（关键符号：dataLoad / importSheetTables / isCsvImportRunner / loadFromExcel）、[load.handler.ts](file://packages/server/src/data-source/commands/handlers/load.handler.ts)（关键符号：DataLoadHandler.execute）

## 5. datasource.strategy.handler 的策略选择

`DataSourceStrategyQuery extends Query<DBQueryRunner>`，字段 `name`（类型名，取自 `dataSource.type.type`）、`options`（`AdapterBaseOptions`）、`dataSourceId?`（可选，只有 `XpertDatabaseAdapterQueryHandler` 会传）。

`DataSourceStrategyHandler.execute` 三步：① `this.dataSourceStrategyRegistry.get(name)` —— 抛异常即转 `InternalServerErrorException(\`DataSource strategy not found for type: ${name}\`)`；② `strategy.create(options, dataSourceId)`；③ runner 为空同样抛上述错误，否则返回。**关键语义（有 spec 固化的三条约定）**：runner **只经注册表策略创建**（无 legacy `createQueryRunnerByType` 兜底）、策略缺失**不回落**（`strategy.create` 不会被调用）、策略内部抛出的错误**原样上抛**（`rejects.toBe(error)`）。注册表通过 `@Inject(DataSourceStrategyRegistry)` 注入（来自 `@xpert-ai/plugin-sdk`），非构造函数参数。

**选择键的取值口径**：`name` 一律是 `dataSource.type.type`（字符串），例如 `pg`/`mysql`/`doris`/`xmla`/`sapbw`（spec 用 `sapbw` 与 `postgres` 举例）。`DataSourceRuntimeService` 内部再做一层 `pg → postgres` 归一，**只在这一处**，说明注册表里两种写法可能并存 `[推测]`。`typeId` 列的 `@Index()` + 非空 + `onDelete: 'CASCADE'` 意味着**数据源必须挂类型，类型被删则连带删数据源**——这是策略选择的前置约束。

## 6. xpert-table 实现

**Meta 实体 → 列/行**：`XpertTable extends WorkspaceBaseEntity`（`@Entity('xpert_table')`）。列：`name`（`@Column({ length: 100 })`）、`description`、`database`、`schema`（三者 `nullable: true`）、`columns`（`@Column({ type: 'json', nullable: true })`，`TXpertTableColumn[]`）、`status`（`varchar(30) default 'draft'`，7 态：`draft/ready/pendingActivation/active/needsMigration/deprecated/error`）、`message`、`physicalSchema(100)`、`physicalTableName(150)`、`version`（`int default 1`）、`activatedAt`（`timestamptz`）、`deletedAt`（`@DeleteDateColumn`，**实体上再次声明**，基类已有同名列）。`TXpertTableColumn` 的字段：`name/type/label?/required?/isPrimaryKey?/isUnique?/autoIncrement?/defaultValue?/length?/precision?/scale?/enumValues?/setValues?`。

**物理表激活与 DDL**：`activateTable(tableId)` —— `columns` 为空即 `BadRequestException('Table must have at least one column to activate.')`；先 `update(status = PENDING_ACTIVATION)`；再把每个列**清洗**成 DDL 形状（`name` → `name` + `fieldName`，`isPrimaryKey → isKey`、`isUnique → unique`、`required → required`、`autoIncrement → autoIncrement`，**空字符串 defaultValue 归一为 `undefined`**，透传 `length/precision/scale/enumValues/setValues`）；然后 `adapter.tableOp(DBTableAction.CREATE_TABLE, { schema, table, columns, createMode: DBCreateTableMode.UPGRADE })`；成功 `update({ status: ACTIVE, activatedAt: new Date(), message: null })`，失败 `update({ status: ERROR, message })` 并抛 `BadRequestException`。**`UPGRADE` 是关键词**：对已存在的物理表做结构升级而非新建，⇒ 列增删改直接落外部库，**无审批、无 dry-run、无回滚**。

**读写**：`insertRow(tableId, row)` 硬要求 `status === ACTIVE`，把 `row` 转成 `{ columns: [{name, fieldName, type}], values: {name: value} }` 调 `adapter.tableDataOp(DBTableDataAction.INSERT, ...)`，**`finally adapter.teardown()`**（注意：`tableDataOp` 的 teardown 在 finally，异常直接上抛不包装）。`executeSql(tableId, statement)` 同样要求 `ACTIVE`，直接 `adapter.runQuery(statement, { catalog: table.schema })`，**无任何语句级校验** —— 这是本子域**最宽的写面**，可由工作流节点策略 `WorkflowDBSQLNodeStrategy`（`WorkflowNodeTypeEnum.DB_SQL`，`mustache` 模板渲染 `entity.sqlTemplate` 后调 `executeSql`）间接触达。`WorkflowDBInsertNodeStrategy`（`DB_INSERT`）则从 state 取列值（`value` 或 `get(stateEnv, valueSelector)`）后调 `insertRow`。两者都用 `wrapAgentExecution(...)` 包成 `IXpertAgentExecution`（category `workflow`）。

**改名 / 删除 / 校验**：`upsertTable(entity)` —— 先校验 `name` 与 `database` 必填；`validateTableName` 决定是否放行（`id` 存在且 `name/schema/database` 三者未变 → 直接 `true`；否则查物理表是否存在（`tableOp(GET_TABLE_INFO, ...)`），存在且库内同名记录就是自己 → `true`，其余返回 `!exists`；**异常路径**：更新操作放行、新建操作拒绝）；若改名且旧状态 `ACTIVE` → 先 `tableOp(RENAME_TABLE)`（失败即抛，**不做二次补偿**）；再 `update` 或 `create`；最后**无条件** `activateTable`。激活失败时：新建表 → 回删逻辑行（失败仅记日志），已有表 → 置 `ERROR + message`，随后**统一抛出**以便前端收到错误响应。`deleteTable(tableId)`：`ACTIVE` 时先 `DROP_TABLE`（**失败仅记日志并继续**）再 `softDelete`。`getDatabaseSchemas(databaseId)`：`XpertDatabaseAdapterQuery` → `adapter.getCatalogs()`，异常包 `BadRequestException`。

## 7. subscriber 与事件处理

**定义**：`DataSourceSubscriber implements EntitySubscriberInterface<DataSource>`，`@Injectable()`，构造注入 `Connection` + `EventBus`，构造体内 `connection.subscribers.push(this)`；`listenTo()` 返回 `DataSource`；`afterUpdate(event)` 在 `event.entity?.id` 存在时 `eventBus.publish(new DataSourceUpdatedEvent(event.entity.id))`。类注释自陈：「没有解决 typeorm Subscriber 与注入 nestjs EventBus 的问题」。

**装配实况（关键）**：`DataSourceSubscriber` **从未被实例化** —— 不在 `DataSourceModule.providers`（`[DataSourceService, DataSourceRuntimeService, ...EventHandlers, ...CommandHandlers, ...QueryHandlers]`），不在 `coreSubscribers`（`[StorageFileSubscriber, TagSubscriber, ReferralCodeSubscriber]`），也不在 `data-source/index.ts` 的导出清单（`index.ts` 导出 entity/service/controller/module/authentication/commands/dto/events/queries/utils，**唯独不含 subscriber**）。⇒ 该订阅者当前是**死代码**。

**实际的事件流**：发布方只剩控制器 `PUT /:id` 的显式 `eventBus.publish(new DataSourceUpdatedEvent(id))`；而 `events/handlers/index.ts` 是 `export const EventHandlers = []`（**空数组**，并以 `...EventHandlers` 方式展开进 providers）。⇒ **`DataSourceUpdatedEvent` 既无订阅者（TypeORM 侧）也无 handler（CQRS 侧）**，是一条「悬空事件」。对照影响：§3 的 OLAP runner 缓存与 BAS|C 凭据快照**因此没有任何失效通道**。

**表格侧的「订阅者替代物」**：`xpert-table` 没有 TypeORM subscriber，状态副作用全部写在服务方法里（`status` 流转 + `message`），并以 `@OnEvent(EventNameXpertValidate)` 的两个校验器（`WorkflowDBSqlNodeValidator` / `WorkflowDBInsertNodeValidator`）接入 `XpertDraftValidateEvent` —— 两者都只检查 `entity.tableId` 是否为空，产出 `ruleCode: 'DB_INSERT_TABLE_REQUIRED'` 的 error 项（注意：**两个校验器的 ruleCode 与 message 文本完全相同**，SQL 校验器也报 "Table is required for Database Insert node"，属文案 bug）。`WorkflowDBInsertNodeValidator` 里对 `entity.input` 的检查整段被注释。

## 8. 与前端/仪表盘的契约

**数据源侧（Angular）**：设置页 `features/setting/data-sources/{creation,edit}` 用 `DataSourceConnectionService.ping()` 做「Ping」按钮；表单字段由 `dataSourceType().configuration` 经 `convertConfigurationSchema` 动态生成；`DataSourceProtocolEnum.XMLA` 决定是否展示不同字段。列表数据来自 `GET /api/data-source`（**只拿到 `DataSourcePublicDTO` 白名单：id/name/type/typeId/authType/createdAt/updatedAt/createdBy**）——因此**前端拿不到 `options`**，回显必须靠 `GET /:id`（这也是明文风险的入口）。

**表格侧（Angular）**：`XpertTableService extends OrganizationBaseCrudService<IXpertTable>`，基址 `API_PREFIX + '/xpert-table'`：继承 CRUD 走 `POST`/`PUT`/`GET /:id`；自定义四式 `getDatabases()`（→ `GET /databases`）、`getDatabaseSchemas(databaseId)`（→ `GET /schemas`）、`activateTable(id)`（→ `POST /:id/activate`，**POST 带空 body `{}`**）、`deleteTable(id)`（→ `DELETE /:id`，后端 `@HttpCode(204)`）。契约要点：`POST /` 与 `PUT /:id` **后端都被覆写为 `upsertTable`**（即「保存即激活」），前端不需要额外调 activate，但 activate 仍单独暴露供重试。

**仪表盘/知识库的间接契约**：它们不直连这两张表，而是经 `DataSourceQuery`（`QuerySql|ListTables|TableSchema`，`TableSchema` 会附带 `sample_data`，取自 `SELECT * FROM ${table} LIMIT 10`-equivalent 的取样）与 `DataSourceOlapQuery`（带 `sessionId` 以命中 10 分钟 runner 缓存）。**这两条 query 在仓库内未命中派发点**（除 `DataLoadCommand`），消费方应在插件或邻域 `[推测]` —— 新增消费方必须自带 `sessionId` 否则每次重建连接。

**能力查询契约**：`POST /:id/capabilities/query` 的 body 形状由 `contracts` 固定为 `{ capability, operation, payload? }`，且 capability/operation 必须匹配 `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`（`contracts` 注释明确：**capability 名与 payload schema 由 adapter 及其消费方拥有，平台刻意不建模领域协议**）。

## 11. 技术债

1. **`XpertDatabaseSchemaQuery` 有类无 handler**（`queries/handlers/index.ts` 只导出 `XpertDatabasesQueryHandler` 与 `XpertDatabaseAdapterQueryHandler`）⇒ 契约声明与实现不一致；控制器走的是直调服务，绕过了该 query。
2. **`physicalSchema` / `physicalTableName` / `version` 三列无读写点**，但实体注释把它们描述为生效字段（示例 `xd_ta3f1a_ws9b2_xpd10_cuord_v1`）⇒ 阅读者易误判；`version` 也**不是** `@VersionColumn`，注释所称「字段修改后 +1」无实现。
3. **`XpertTableController` 权限面极薄**：类级只有 `TransformInterceptor`，**仅 `GET databases` 挂 `PermissionGuard + DATA_SOURCE_VIEW`**；`POST /`、`PUT /:id`、`POST /:id/activate`、`DELETE /:id`（含 `DROP TABLE`）都**没有 `@Permissions`**，依赖全局 AuthGuard + `XpertWorkspaceBaseService` 的 workspace 校验 `[推测]`（`XpertWorkspaceBaseService` 实现在 `../xpert-workspace`，不在本子域）。**这是本子域最大的越权面**。
4. **`DataSourceController` 的 `POST /:id/load` 无 `FileInterceptor` 之外的上传校验**（无体积/类型白名单过滤逻辑），`JSON.parse(body.params)` 未包 try/catch 外层语义（在 `try` 内但错误被转成 500 而非 400）。
5. **`olap` 端点的 HTTP 200 恒真**：失败也返回 `{status: 4xx/5xx}` 而不改 HTTP 状态码，前端必须读 body。
6. **`subscriber.ts` 死代码** + **`events/handlers` 空数组**：模块注释 `@todo Updated cqrs event 应该在哪里发出 ?` 长期未解。
7. **明文凭据**（见 §2）+ **两条明文出网口**。
8. **`schema` 未转义即进 `new RegExp`**（`query-schema.handler`、`query.handler`）⇒ ReDoS/构造风险；`SELECT * FROM ${table}` 亦为字符串拼装。
9. **无超时/无行数上限/无 SQL 白名单**（见 §4），HTTP 路径不传 `AbortSignal`。
10. **校验器文案复用 bug**：`WorkflowDBSqlNodeValidator` 产出 `DB_INSERT_TABLE_REQUIRED` 与 "Database Insert node" 文案（应为 SQL）。
11. **`DataSourceService.create` 覆写只为补 `relations: ['type']`**（一次多余回查）；`findSqlDataSources` 用 QueryBuilder 手写 `tenantId/organizationId` 条件，与 `prepareDataSource` 的收敛口径**两套并存**。
12. **`XpertTableModule` 无 `RouterModule`**（与 `DataSourceModule` 不一致）⇒ 前缀完全依赖 `@Controller('xpert-table')`，未来要改前缀只能改字符串。

## 12. 设计维度

**维度一：连接生命周期 —— 「一动作一连接」vs「一会话一连接」。** 元数据/SQL/能力代理是**严格的一次性**（`finally teardown()`，异常也释放），代价是每次请求一次外部库握手；OLAP 是**会话级复用**（`sessionId + dataSourceId` → 10 分钟 TTL），代价是凭据快照陈旧且**改数据源不失效**；插件 workbench 是**版本式失效的租约**（`updatedAt` 比对，变更即强制 `close()`）。三种生命周期在同一模块内并存，选择依据是「调用频次 × 凭据新鲜度要求」，而不是统一抽象——新增能力时必须显式挑一种，不要默认套用。

**维度二：隔离键 —— 三元组并存。** `data_source` 是 **tenant + organization**；`data_source_authentication` 是 **tenant + userId**（无 organization）；`xpert_table` 是 **workspace**（另有 tenant/organization 基列）。校验强度也不同：`prepareDataSource` 是**硬断言 + 查库收敛**，`DataSourceRuntimeService.authorize` 是**硬断言 + 权限位**，而 `xpert_table` 侧只靠 `XpertWorkspaceBaseService` 一层 `[推测]`。⇒ 同一业务动作（例如「表格写一行」）穿过的隔离层数与强度**完全不同**，跨子域复用时要按最严者对齐。

## 13. 结论

实现层的主线是「**薄控制器 + 厚服务 + 单一策略入口**」：`data-source.controller` 的 16 条端点几乎不含业务分支（只做参数转发与错误码归一），全部语义落在 `DataSourceService` 与 `prepareDataSource`；`xpert-table.controller` 的 6 条端点同样薄，但**覆写了基类 POST/PUT 为 `upsertTable`**，把「保存即激活」做成不可绕过的默认行为。所有外部库访问最终收敛到 `DataSourceStrategyHandler` 一行 `strategy.create(options, dataSourceId)`，这是本子域最值得保护的收口。

三个必须优先处理的现实问题：① **`password` 明文 + `options` 的 `@Exclude` 仍是注释 + 两条明文回显口**（列表 DTO 只挡住了最容易看到的那一条）；② **`xpert-table` 写面权限缺失**（`DROP TABLE` 走 `DELETE /:id` 且无 `@Permissions`）；③ **DDL 与查询均无护栏**（`UPGRADE` 直改外部库、`executeSql` 透传任意语句、无超时/无行数上限/HTTP 不传 `AbortSignal`）。扩展时建议：新数据源类型只加策略实现、不新增 runner 构造点；新表格能力一律走 `status` 流转 + `tableOp`/`tableDataOp`，并把 `physicalSchema/physicalTableName/version` 三列要么实现、要么删掉注释以免误导。
