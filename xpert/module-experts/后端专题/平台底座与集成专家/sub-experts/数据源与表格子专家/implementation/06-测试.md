## 2. 运行命令

两套配置的差异（决定了「跑哪个文件就用哪套 config」）：`packages/server/jest.config.ts` 的 `moduleNameMapper` **只**映射 `^@xpert-ai/contracts$ → <rootDir>/../contracts/src/index.ts`；`packages/server-ai/jest.config.ts` 额外映射 `^@xpert-ai/server-core$ → <rootDir>/../server/src/index.ts`、`^@xpert-ai/plugin-sdk$ → <rootDir>/../plugin-sdk/src/index.ts`、`^@xpert-ai/cli-model-profiles$`、`^@xpert-ai/shadcn-ui/brand-icons$`。两者 `transform` 都是 ts-jest（`<rootDir>/tsconfig.spec.json`）+ babel-jest（`babel-jest.config.js`），`testEnvironment: 'node'`，**无全局 setup/setupFiles**（fixture 与 mock 由各 spec 自带）。`server-ai` 的 `transformIgnorePatterns` 还额外放行 `.pnpm/<name>@` 形态。

```bash
# 1) server 侧（本子域的数据源 4 个 spec）
node node_modules/jest/bin/jest.js --config packages/server/jest.config.ts \
  --runTestsByPath packages/server/src/data-source/data-source-capability.spec.ts \
                   packages/server/src/data-source/data-source.config.spec.ts \
                   packages/server/src/data-source/utils.spec.ts \
                   packages/server/src/data-source/queries/handlers/datasource.strategy.handler.spec.ts

# 2) server-ai 侧（本子域的表格 3 个 spec）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/xpert-table/xpert-table.controller.spec.ts \
                   packages/server-ai/src/xpert-table/queries/handlers/xpert-database-adapter.handler.spec.ts \
                   packages/server-ai/src/xpert-table/queries/handlers/xpert-databases.handler.spec.ts

# 3) 整目录（目录过滤）
node node_modules/jest/bin/jest.js --config packages/server/jest.config.ts \
  --testPathPattern 'src/data-source/'
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --testPathPattern 'src/xpert-table/'

# 4) 用例名过滤（-t 匹配 it/describe 标题，小写敏感按标题原文）
node node_modules/jest/bin/jest.js --config packages/server/jest.config.ts \
  --testPathPattern 'src/data-source/' -t 'capability'

node node_modules/jest/bin/jest.js --config packages/server/jest.config.ts \
  --testPathPattern 'src/data-source/' -t 'streams CSV files to postgres'

# 5) Nx（项目名已核实：server / server-ai）
corepack pnpm exec nx run server:test --skipNxCache --runInBand
```

## 3. 需外部依赖的测试

**结论：本子域 7 个 spec 全部是纯单测，零外部依赖**（无真实数据库、无 Redis、无网络）。

- **无 `Test.createTestingModule`**：7 个 spec 都用 `Object.create(XxxService.prototype)` + 手工塞字段（`Object.defineProperty(service, 'queryBus', ...)`、`Reflect.set(handler, 'dataSourceStrategyRegistry', registry)`）或 `new Handler(...)` 直接构造，**没有 Nest DI 容器启动**。
- **无真实外部库**：`DataSourceStrategyRegistry` 全部被替身化（`jest.fn().mockReturnValue(strategy)`，`strategy.create` 为 `jest.fn()`）；`DBQueryRunner` 一律是对象字面量（`{ type: 'pg', importCsv, import, teardown }`），**没有真实数据库连接**——这也意味着 §4 中的查询代理、DDL 路径**在本子域完全没有端到端覆盖**。
- **`jest.mock` 的边界**：`utils.spec.ts` mock `@xpert-ai/server-common`（只保留 `getErrorMessage`/`readExcelWorkSheets` 两个替身）；`xpert-table` 的 3 个 spec 都 mock `@xpert-ai/server-core`（`CrudController`/`TransformInterceptor`/`PermissionGuard` **或** `DataSource`/`DataSourceService`/`DataSourceStrategyQuery`），其中 `xpert-table.controller.spec.ts` 用 `jest.requireActual('../../../server/src/shared/decorators/permissions')` **穿透到 server 源码取真装饰器**，同时 mock `./xpert-table.entity` 与 `./xpert-table.service`——这是「只测元数据、不测行为」的取舍。
- **唯一需要「跨包源码」的测试**：`xpert-table/*.spec.ts` 通过 `moduleNameMapper` 把 `@xpert-ai/server-core` 指到 `packages/server/src/index.ts`，因此**跑表格侧测试会连带编译 server 包的源码**（含 `crud.controller.ts`、`data-source` 导出面）；`data-source.config.spec.ts` 也依赖 server 内的 `feature/default-features.ts` 与 `role-permission/default-role-permissions.ts` 真实常量（**非 mock**），⇒ 改默认权限/默认特性会直接红。
- **若要补外部依赖测试**，需要的最小依赖是：一个可连的 Postgres/MySQL（供 `DBQueryRunner` 实现真实建连）、`DataSourceStrategyRegistry` 的真实注册（即加载数据库插件）、以及 `XpertTableService` 的 `Repository<XpertTable>`（TypeORM 连接）。**当前仓库内无此类 fixture**（0 命中 `testcontainers`/`pg-mem`）`[推测]`。

章节来源：[data-source-capability.spec.ts](file://packages/server/src/data-source/data-source-capability.spec.ts)（关键符号：Object.create(DataSourceService.prototype) / Object.defineProperty(queryBus)）、[datasource.strategy.handler.spec.ts](file://packages/server/src/data-source/queries/handlers/datasource.strategy.handler.spec.ts)（关键符号：Reflect.set(handler, 'dataSourceStrategyRegistry')）、[utils.spec.ts](file://packages/server/src/data-source/utils.spec.ts)（关键符号：jest.mock('@xpert-ai/server-common')）、[xpert-table.controller.spec.ts](file://packages/server-ai/src/xpert-table/xpert-table.controller.spec.ts)（关键符号：jest.requireActual(permissions) / mock xpert-table.entity）、[jest.config.ts（server-ai）](file://packages/server-ai/jest.config.ts)（关键符号：server-core 映射到 ../server/src/index.ts）

## 4. 缺口

按「未覆盖的风险 × 风险等级」排序：

1. **查询代理（`DataSourceService.query/getSchema/getCatalogs/olap`）零覆盖。** 没有任何 spec 断言：`query` 失败必须转 400、`getCatalogs` 失败转 500、`prepareDataSource` 的 `ForbiddenException('Data source scope is required')` 分支、`getSchema` 的 `statement` → `runner.describe` 分支、**`finally teardown()` 在异常路径也执行**（仅 `queryCapability` 有等价断言）。这是全子域最大的覆盖空洞。
2. **DDL 面（`XpertTableService.activateTable` / `upsertTable` / `deleteTable`）零覆盖。** 未测：列清洗（`isPrimaryKey → isKey`、**空字符串 `defaultValue` 归一为 `undefined`**）、`DBCreateTableMode.UPGRADE` 的传参形状、激活失败的 `status = ERROR + message` 落库、**新建表激活失败时回删逻辑行**的补偿分支、改名时 `RENAME_TABLE` 的调用与「失败即抛、不补偿」、`deleteTable` 的 `DROP_TABLE`（含**失败仅记日志仍继续软删**）。
3. **`insertRow` / `executeSql` 零覆盖。** 未测 `status !== ACTIVE` 的 `BadRequestException`、`row → {columns, values}` 的转换形状、`finally adapter.teardown()` 的执行、`executeSql` 的 `catalog: table.schema` 传参。
4. **`prepareDataSource` 的 BASIC 凭据注入零覆盖。** `utils.spec.ts` 只测了 `importSheetTables`，**未测 `prepareDataSource`**（本文件导出的核心函数之一）：`authType === BASIC` 且当前用户无认证行 → `NotFoundException('未找到当前用户认证信息')`、命中则 `options.username/password` 被回写、非 BASIC 完全不改 `options`——这三条都没有断言。
5. **凭据明文风险无回归测试。** 没有任何 spec 断言「`GET /api/data-source` 的响应不含 `options`/`authentications`」或「`GET /:id/authentication` 不回显 `password`」。对照同批 `mobile.service.spec.ts` 有「不泄露密钥」的负例断言——**本子域缺这一条**。
6. **`XpertTableController` 只测了 `getDatabases` 一个端点。** `POST /`、`PUT /:id`、`GET /schemas`、`POST /:id/activate`、`DELETE /:id` 的权限/守卫/覆写语义**全部未断言**——而其中 `DELETE /:id` 会触发 `DROP TABLE`，`POST/PUT` 会被覆写为 `upsertTable`，是权限面的关键缺口。
7. **`DataSourceSubscriber` 与 `DataSourceUpdatedEvent` 零覆盖**（订阅者未装配、`EventHandlers` 为空，故也无从测试）——这本身是「应测而不可测」，需先修装配。
8. **`OlapQueryHandler` 的 runner 缓存零覆盖**：10 分钟 TTL、`setInterval` 回收、`unref()`、**缓存命中时跳过鉴权重算**、`forceRefresh` 入参**在 handler 内未被使用**（`query.input.forceRefresh` 解构后未出现在任何分支）——最后一条是**已读源码可判定但无测试守护**的行为。
9. **`DataSourceQueryHandler` / `QuerySqlHandler` / `QuerySchemaHandler` / `ListTablesHandler` / `DataSourcePingHandler` / `DataLoadHandler` 六个 handler 零覆盖**；其中 `query.handler` 的 `TableSchema` 分支（含 `new RegExp(`^${schema}\\.`)` 未转义与 `SELECT * FROM ${table}` 拼装）风险最高。
10. **无集成/契约测试**：`XpertTableModule` 与 `DataSourceModule` 的 DI 装配（`forwardRef`、`XpertWorkspaceModule` 循环、`@Inject(XpertTableService)` 在策略类中的解析）**没有 `Test.createTestingModule([XpertTableModule])` 级别的测试**；`xpert-table.controller.spec.ts` 反而把 `xpert-table.service` mock 掉了，⇒ **「模块能否启动」这一最基本的事实无人守护**。
11. **无 lint/类型契约测试**：`contracts` 里的 `IDataSource`/`IDataSourceAuthentication`/`IXpertTable` 与实体之间的一致性无编译期测试（`implements` 提供静态保证，但 `TXpertTableColumn` 的 `DatabaseDataType = string` 已放弃类型约束）。
12. **无性能/超时测试**：本域无超时机制，故无「查询超时后 runner 被回收」的断言；`validateTableName` 每次保存都打一次外部库这一 N+1 型行为也无基准。

## 5. 结论

本子域的测试策略是「**只测纯逻辑切面，不测 IO 与装配**」：7 个 spec 覆盖了四类高价值不变式——**runner 必 `teardown`**（`data-source-capability.spec.ts`）、**策略只能来自注册表且无回落**（`datasource.strategy.handler.spec.ts`）、**CSV 流式不物化 / xlsx 异常仍释放**（`utils.spec.ts`）、**权限元数据口径**（`xpert-table.controller.spec.ts` 与 `data-source.config.spec.ts`）——并且刻意用 `Object.create(prototype)` + `Reflect.set` 绕开 Nest DI，因此**跑得极快、依赖为零**。

代价同样清晰：**两条最危险的主干路径无任何测试**——① 外部库查询代理（含 scope 断言、错误码归一、`olap` 缓存命中跳过鉴权）；② `xpert-table` 的 DDL 面（`UPGRADE` 建表、改名、`DROP TABLE`、激活失败补偿）。**且「凭据不明文出网」这一当前明确的安全缺陷也没有负例测试守护**（同批 `mobile.service.spec.ts` 提供了可照抄的写法：在环境/对象里塞入敏感值后断言序列化结果不含）。

补测优先级建议：**P0** `prepareDataSource` + `activateTable`/`upsertTable`/`deleteTable`（补偿与状态机）；**P1** `DataSourceService.query|getSchema|getCatalogs` 的异常与 `teardown`、`XpertTableController` 其余 5 条端点的权限断言（尤其 `DELETE /:id`）、`OlapQueryHandler` 缓存与 `forceRefresh`；**P2** 一条 `Test.createTestingModule([XpertTableModule])` 的装配冒烟测试。**外部依赖**只对「真实 DDL 是否落到外部库」这一类断言必要，其余均可用现有替身风格完成。
