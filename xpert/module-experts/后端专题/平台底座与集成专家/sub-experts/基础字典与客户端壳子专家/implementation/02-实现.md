## 1. 字典族四模块

**种子（写路径）**。三类全局字典共用「常量表 + 逐键构造 + 批量写库」三步：

- **language**：`LanguageService.initialize()` → `createLanguages(connection)`。遍历 `all-languages.ts` 的 182 个条目（默认导出对象，值形如 `{ name, nativeName }`），构造 `Language` 实例：`name = name`、`code = key`、`is_system = LanguagesEnum 值数组.indexOf(key) >= 0`、`description = ''`、`color = faker.internet.color()`；随后 `connection.getRepository(Language).save(languages)` 并返回构造出的数组。**唯一约束冲突被 `try/catch + console.log({error})` 吞掉**，函数仍返回数组——即「重复初始化静默失败」。命令入口是 `LanguageInitCommand`（`static type = '[Language] Init'`，无参构造）→ `LanguageInitHandler.execute` 直接转发 `languageService.initialize()`。
- **country**：`createCountries(connection)` 包在 `new Promise` 里，遍历 `DEFAULT_COUNTRIES`（键为两位 ISO 码）构造 `{ isoCode, country }`，走 `connection.createQueryBuilder().insert().into(Country).values(countries).execute()`（**无去重、无 upsert**）；任何异常 `console.log('Error parsing country:', err)` 后 `reject(null)`。
- **currency**：`createCurrencies(connection)` 同构，常量来自 contracts 的 `DEFAULT_CURRENCIES`（三位 ISO 码 → 名称，含历史币种）。同样无去重。
- 调用顺序在 `SeedDataService` 的「只需 connection 的种子」阶段固定为 `Countries → Currencies → Languages → Features`，另在默认数据库阶段调用 `createDefaultTags` 与 `createTags`。

**读取（读路径）**。`LanguageService extends CrudService<Language>`，`findOneByName(name)` 用 `createQueryBuilder('language').where('"language"."name" = :name')` + `getOne()`——**未命中回 `null`**（不抛）。控制器 `LanguageController` 只挂 `@Get()`（`findAll(query)` 直接转发基类）与 `@Get('getByName/:name')`，两者都加方法级 `@Public()`；`CountryController` / `CurrencyController` 用**类级** `@Public()` 且只有一个 `@Get()`（无分页参数，`findAll()` 走基类默认）。**校验**只发生在实体装饰器层：`Country` / `Currency` 的 `isoCode` / `country` 是 `@IsString() + @IsNotEmpty() + @Column({ nullable: false })`，`Language` 的 `code` / `description` / `is_system` 可空、`name` / `color` 非空——**读端点不做任何 DTO 白名单**。

**语言解析**不在实体层：服务端统一按 `RequestContext.getLanguageCode()` 取当前语言，i18next 以 `fallbackLng: 'en'`（namespace `common`）兜底，`getDefaultOrganizationWorkspaceName()` 与 `AIModelGetIconHandler` 各自实现「`zh_Hans` 优先、`en_US` 兜底」的取值规则。

## 2. contact 的实现与继承面

**实体**：`Contact extends TenantOrganizationBaseEntity`（隔离键 = tenant + organization），13 列（`name` / `firstName` / `lastName` / `country` / `city` / `address` / `address2` / `postcode` / `latitude` / `longitude`(float scale 6) / `regionCode` / `fax` / `fiscalInformation` / `website`）**全部 `nullable: true`**，无唯一索引、无外键；`regionCode` 上有一处重复的 `@Column()` + `@Column({ nullable: true })` 叠加声明（历史遗留）。文件底部三处 `@OneToMany`（`organization_contacts` / `employees` / `candidates`）**整段被注释**——即联系人不再向上聚合任何关系。

**服务**：`ContactService extends TenantAwareCrudService<Contact>`，公开两个写入口——继承自基类的 `create/update/delete/softRemove/softRecover` 与自写的 `saveContact(contactRequest)`（**直接 `repository.save`，无去重、无归属校验**）。命令链 `ContactCreateCommand(input: IContactCreateInput)` → `ContactCreateHandler.execute` → `contactService.create(input)`——注意 handler 走的是**基类 `create`**，而不是 `saveContact`，因此 `saveContact` 在当前代码中**无调用方**（`[推测]`：为外部/历史调用保留）。

**控制器与继承面**：`ContactController extends CrudController<Contact>`，类级 `@UseTagsworn` 实为 `@UseGuards(TenantPermissionGuard)` + `@ApiTags('Contact')`，自身只加一条 `@Get()`（`getAllContact`，参数 `@Query('data', ParseJsonPipe) data`，解构 `{ relations, findInput }` 后调 `contactService.findAll({ where: findInput, relations })`）。**基类提供的 9 条**（`GET count`、`GET pagination`、`GET my`、`GET :id`、`POST /`、`PUT :id`、`DELETE :id`、`DELETE :id/soft`、`PUT :id/recover`；基类内还有一条 `GET /`，被子类同路径覆写）全部继承类级守卫元数据。

**当前不可用（实测）**：`ContactModule` 只在自身文件里声明 `TypeOrmModule.forFeature([Contact]) + CqrsModule + TenantModule`，**既无 `RouterModule.register`，也未被 `server.module.ts` 引入**；全仓 `ContactModule` 的出现点只有它自己与 `server.module.ts` 中的 `OrganizationContactModule`（不同模块）。因此**没有 `/api/contact` 这组路由**，`TenantPermissionGuard` 也不会被实例化。要启用须同时补：模块注册 + 路由前缀 + 对「无唯一键」的写入去重策略。

## 3. desktop-shell 实现

**设备注册与凭据**（`DesktopShellAuthService`）：

1. `register(body)` 严格校验 `installationId`（uuid）、`platform === 'darwin'`、`settings` 三项；`settings` 经 `parseShellBoundary(parseSettings, …)` 归一为 `{ name, shell, cwd, path }`（越界一律 400 `INVALID_MESSAGE`）。`currentShellScope()` 取 `RequestContext` 的 `tenantId / organizationId / userId`，任一非 uuid 即 403 `GRANT_REVOKED`。
2. 同 `(scope, installationId)` 命中已有设备时**先 `disable` 旧设备（连带禁用其 grant 并把在途操作置 `cancel_requested`）**，复用同一 `id` 再写新凭据——即「同机重装」是幂等且会作废旧 token。
3. 明文密钥 `randomBytes(32).toString('base64url')` 只随响应返回一次，形态 `token = ${deviceId}.${secret}`；库里存 `sha256(secret)` hex 与 `credentialExpiresAt = now + LIMITS.grant`，同时把 `connectionEpoch` / `leaseExpiresAt` 清空。
4. `authenticate(token)`：限长 150，按 `.` 切分校验两段，`findOneBy({ id, enabled: true })` 后检查未过期并用 `timingSafeEqual(hash(secret), credentialHash)` 常量时间比较；`refresh(deviceId)` 是唯一轮换路径。
5. `requireDevice(id, scope)` 是三键同入 where 的查库入口（跨租户/组织不探测），失败统一 403。

**授权（grant）**：`issueGrant(deviceId, assistantId, threadId?)` 先 `requireDevice`；带 `threadId` 时先查 `ChatConversationThread`（`threadId + tenantId`），再 `queryBus.execute(new AssertChatConversationAccessQuery({ id }, 'contribute'))` 做会话写权限断言——**校验失败时不落任何 grant**。`expiresAt = min(device.credentialExpiresAt, now + LIMITS.grant)`。`bindForRun(grantId, threadId, assistantId, scope)` 用 `update({ …, threadId: IsNull() }, { threadId })` 实现「**一次绑定**」：只有尚未绑定线程的授权才可被 run 认领。`revokeGrant(id)` 置 `enabled = false` 并把该 grant 下 `pending | running` 的操作置 `cancel_requested`。

**准备与决策（审批链）**：`prepareOperation(deviceId, body)` 先 `parsePreparation` 归一，再 `requireDevice` + `issueGrant`，算 `argsHash = sha256(JSON.stringify([command, cwd, timeoutSec]))`，把 `grant.operation` 写成 `{ runId, toolCallId, argsHash, decision: 'pending' }`，并把有效期压到 `min(grant.expiresAt, now + 10 分钟)`——源码注释逐字「A pending grant routes one operation but cannot authorize execution.」。`decideOperation(id, decision)` 在事务内以 `pessimistic_write` 锁 grant 行，校验 `operation` 存在且未过期、设备仍可用，再判冲突：**已成 `approved` 再拒/再批不同值 → 409 `OPERATION_CONFLICT`**（同值重复决策幂等）。

**执行（台账 + 幂等）**：`DesktopShellOperationService.execute(input, scope)` 的次序是「先验后锁、锁后再验」：`requireGrant(scope.grantId, scope.threadId, scope)` → `cwd` 必须以 `/` 开头、`runId` 为 uuid、`toolCallId` 非空且 ≤255 → 重算 `argsHash` 并比对 `grant.operation` 的 `decision === 'approved'` + `runId` + `toolCallId` + `argsHash` 四项 → 事务内对 `device` 与 `grant` 各加 `pessimistic_write` 再复核一次 → 按 `(tenantId, runId, toolCallId)` 查既有操作（命中则要求 `argsHash` / `grantId` / `userId` 全等，否则 409，**否则直接返回既有行**，这就是重试幂等锚点）→ 设备离线（`leaseExpiresAt` 为空或已过）→ 409 `DEVICE_OFFLINE` → 同设备存在 `pending | running | cancel_requested` → 409 `DEVICE_BUSY`（**单设备串行**）→ 落行（`deadline = now + timeoutSec * 1000`）→ 出事务后 `notify(deviceId)` 向 Redis 频道 `xpert:desktop-shell:dispatch` 发唤醒。

**回执（seq 与终态）**：`receive(deviceId, report)` 在事务内锁操作行：已是终态直接 `true`；`output` 类型要求 `seq` 严格递增（重复回 `true`、跳号回 `false` 触发 `reconcile`），超 `LIMITS.output` 只置 `truncated`；终态报告要求 `seq === op.seq + 1`（跳号回 `false`），`cancel_requested` 状态下忽略非终态回执，`succeeded` 但 `exitCode !== 0` 视为协议错误 400。`wait(id, scope, signal)` 每 200ms 轮询直到 `isFinal(state)` 或超 `LIMITS.wait`，`AbortSignal` 触发时转 `cancel`；`result(op, cursor)` 按 `cursor` 逐 chunk 拼接 stdout/stderr 并以 `LIMITS.result` 截断，返回 `nextCursor` / `truncated` / `error.code`。

**WS 通道**（`DesktopShellGateway`，`namespace = /desktop-shell`，`VERSION = 1`，`maxHttpBufferSize = 65536`）：`handleConnection` 校验 `handshake.auth.version` 与 `token`，签发新的 `connectionEpoch = randomUUID()`、写 `leaseExpiresAt = now + LIMITS.lease`、**主动断开旧 socket**、`emit('ready', { version, connectionEpoch, leaseUntil })` 后立即尝试派发。上行：`ready` / `command`（`exec` 与 `cancel` 两种载荷，含 `connectionEpoch` / `argsHash` / `deadline`）/ `lease` / `ack` / `reconcile` / `revoked`；下行：`heartbeat`（续租约，同时复核 `enabled` + `connectionEpoch` + 凭据未过期，失败 `revoked` + 断连）/ `report`（逐 socket 以 promise 链**串行化**，在途计数 >128 即断连，按 `connectionEpoch` 丢弃陈旧回执）/ `rejected`（只允许把 `pending` 置 `rejected`，注释逐字「Only a never-accepted operation can be rejected.」）。`onModuleInit` 订阅派发频道并起 **1 秒巡检**：遍历在连设备 `dispatch`，同时把 `deadline` 早于 `now - LIMITS.lease - 10s` 的 `pending | running | cancel_requested` 置 `unknown` + `EXECUTION_UNKNOWN`（**不重放**）。`dispatch` 每次都重读设备行比对 `epoch`，逐操作复查 grant 是否存在/过期/`deadline` 已过，把需要撤销的置 `cancel_requested` 并下发 `type: 'cancel'`（`reason: 'timed_out' | 'cancelled'`），对 `pending` 操作下发 `type: 'exec'` 并在 3 秒内不重复下发（`entry.sent` 抑制）。

**审批的两段式 `interrupt`**（`shell-approval.ts`）：`requestShellApproval` 先 `interrupt(ClientToolRequest{ name: 'desktop_shell_prepare' })` 拿宿主准备结果（`kind === 'desktop-shell'`、`cwd` 以 `/` 开头、`expiresAt` 未过期、`decision ∈ {pending, approved}`，否则 403 `GRANT_REVOKED`）；若宿主已返回 `approved`（一次性许可）则跳过交互；否则再 `interrupt(HITLRequest)` 让用户 `approve | reject`，`decisions.length !== 1` 或非 `approve` 一律返回 `null`（中间件侧转为 `status: 'denied'`，并明确要求模型「停止、不要换机器重试」）。

**三张表逐条**：见表组 `desktop-shell` 的实体与迁移口径——`device`（`UNIQUE(tenantId,organizationId,userId,installationId)`；`credentialHash varchar(64)`；`connectionEpoch uuid` 可空；`leaseExpiresAt` 可空）、`grant`（`@Index(deviceId, enabled)`；`threadId` 可空；`operation jsonb`，`ShellOperationAuthorization` = `{runId,toolCallId,argsHash,decision}`）、`operation`（`UNIQUE(tenantId,runId,toolCallId)` + `@Index(deviceId,state)`；9 态 `ShellState`：`pending | running | cancel_requested | succeeded | failed | cancelled | timed_out | rejected | unknown`；`output jsonb` 存 `ShellChunk[]`；`outputBytes` / `seq` / `exitCode` / `signal` / `truncated` / `errorCode(80)`）。

## 5. initialization 的引导与幂等

**执行侧（6 个 `@Process`）**：`handleOrganizationBootstrap` / `handleTenantSkillRepositoryBootstrap` / `handleUserOrganizationBootstrap` / `handleUserDefaultWorkspaceSkillsBootstrap` / `handleUserOrganizationCleanup` / `handleOrganizationSkillRepositorySync`；每个都 `try/catch` 记日志后**重新抛出**（交给 Bull 重试）。`handleUserOrganizationBootstrap` 的特有分支：`bootstrapUserInOrganization` 返回 `{ workspaceId, createdNewUserDefaultWorkspace }` 且**新建**了个人工作区时，追加一个链式 job `user-default-skills:{workspaceId}`（`attempts: 8, backoff: 30_000`）；若返回 `clawXpertError` 则抛错触发重试——即「**先排队补技能，再把 ClawXpert 失败上抛**」。

**幂等实现（`bootstrap.service.ts` + 恢复端点）**：`bootstrapOrganization` / `bootstrapTenantSkillRepositories` / `bootstrapUserInOrganization`（首步 `isActiveOrganizationMember` 重查）/ `bootstrapUserDefaultWorkspaceSkills` / `cleanupUserInOrganization` / `syncSkillRepository` 六个方法都**先重查前置条件再动手**；队列内没有 `RequestContext`，故靠组织/租户上下文还原。`ClawXpertRecoveryService`（`@Controller('initialization/clawxpert')`，2 路由）的 `requireCurrentMember()` 用 `memberships.count({ tenantId, organizationId, userId, isActive: true })` 判活，失败 403；`getStatus()` 并行取 `bindings.getBinding(CLAWXPERT, USER)`、`getAvailableXperts(...)`、`queue.getJob('user-org-bootstrap:{orgId}:{userId}')`，按序判定 `ready`（binding 且候选含该 assistant）/ `dependency_unavailable`（`canRecover === false` 或 `getAvailableClawXpertModel()` 为空）/ `initializing`（job 状态 ∈ active/waiting/delayed/paused）/ `error`（failed）/ `binding_inaccessible` / `missing`；`recover()` 对 `ready | initializing | dependency_unavailable` **原样返回**，对 failed 作业走 `existing.retry()`（并吞掉「已被并发重试」的竞态错误），否则用同一 jobId `add`，返回 `initializing`。`canRecover` 对 `SUPER_ADMIN` 恒 `false`。

## 7. tags 与 export-import

**tags 的 8 条显式端点 + 4 条继承端点**（`TagController extends CrudController<Tag>`，类级 `TenantPermissionGuard`）：`GET directory`（`TagManagementService.directory()`）、`PUT :id`（`write(input, id)`）、`DELETE :id`（`remove(id)`）、`DELETE :id/soft`（**恒 400** `Error.TagUseStatus`「Use tag status to enable or disable a tag.」）、`PUT :id/recover`（**恒 400** 同上）、`GET categories`（`TagService.findAllCategories()`）、`GET /`（`ParseJsonPipe` 解 `data` 后转发基类）、`POST /`（`write(entity)`）；后三条写路径都叠 `PermissionGuard` + `@Permissions(PermissionsEnum.ORG_TAGS_EDIT)`。继承自基类的 4 条为 `GET count` / `GET pagination` / `GET my` / `GET :id`。

**写路径（`TagManagementService.write`）**：① `scope()` 要求 `tenantId` 存在（否则 403），`organizationId ?? IsNull()`；② 权限门；③ zod `inputSchema.safeParse`（`name` trim 后 1..100、`description` ≤500、`label` 仅允许 `{ en_US ≤100, zh_Hans? ≤100 }`、`targets` 必须 ∈ `TAG_TARGETS` 且长度 1..N、`color` ≤2000、`icon` ≤10000、`isActive` 布尔）；④ 事务内 `manager.getRepository('Tenant').findOne({ id, lock: pessimistic_write })` —— **按租户行加锁以串行化目录写入与重名检查**；⑤ 更新时以 `pessimistic_write` 锁标签行，`canEdit()` 要求「有 `ORG_TAGS_EDIT` + `!isSystem` + 组织归属相等」；⑥ 兼容旧客户端：只给 `category` 不给 `targets` 时把 `category` 折成单元素 `targets`（反之由 `targets` 反推 `category`）；⑦ 重名检查 `LOWER(tag.name) = LOWER(:name)` 且限当前组织作用域（无组织时 `organizationId IS NULL`）；⑧ 若此次**移除**了某些 target，先用 `usage(manager, [id], false)` 查用量，任一被移除 target 仍在用即 400 `Error.TagTargetInUse`。

**用量与目录（`usage` / `directory`）**：`directory()` 取「当前组织 + 共享（`organizationId IS NULL`）」的标签，逐条附 `targets`（`getTagTargets`）、`editable`（`canEdit`）与 `usage`。`usage()` 遍历 `manager.connection.entityMetadatas`，挑出**所有 owning 的 M2M 关系**（或反向指向 `Tag` 的关系），对每个 junction 建一条 `innerJoin` 计数查询（用 `driver.escape` 转义列名、`withDeleted()`、按 `tenantId` 过滤、当前组织时再按 `organizationId` 或 `organization.id` 过滤），命中 `usageTargets[resource.tableName]` 才计；**未登记的表名直接 400** `Error.TagUsageUnsupported`（注释逐字「Cannot safely inspect this tag relationship.」）。随后再单独扫 `knowledgebase_tag` / `knowledge_document_tag` 两张**显式关联实体**（它们不是 M2M junction），累加到 `knowledgebase` 目标上。`remove(id)` 也不允许删除在用标签（400 `Error.TagInUse`，提示改为停用）。种子侧另有 `createDefaultTags` / `createTags`（`DEFAULT_GLOBAL_TAGS` 12 项 + `DEFAULT_ORGANIZATION_TAGS` 16 项）与 `TagSubscriber.beforeInsert` 自动补 `tenantId` / `organizationId` / `createdById`。

## 9. 热点路径

1. **桌面派发巡检（每秒 × 在连设备数）**：`setInterval(1000)` 内对每个连接 `dispatch`（各自 1 次设备行读 + 1 次活动操作查询 + 每操作 1 次 grant 查询），并**每次**执行一条跨全表的超期清扫 update（`state IN (...) AND deadline < now - lease - 10s` → `unknown`）。在线设备越多，这条 1Hz 循环与 grant 查询扇出越大。
2. **`/api/tags/directory`**：先取标签集合，再对**每个登记过的 junction** 发一条 `COUNT(*)` 分组查询，最后再补两条显式关联表查询；这是本子域最重的读路径（也是新 junction 未登记即 400 的唯一位置）。
3. **标签写事务**：每次写都先 `pessimistic_write` 锁租户行，再锁标签行，再（可能）跑一次 usage 扫描——**租户级串行**，高并发建标签会排队。
4. **移动端 bootstrap**：`findCurrentUser`（带两个关系）+ 可选的租户全组织查询 + 2 条 assistant binding 解析，均在一次请求内并行/串行混合完成。
5. **初始化引导作业**：由事件驱动（建组织 / 建租户 / 用户入组），单作业内串行执行建工作区、装模板插件、装技能包、绑 ClawXpert 等跨 9 个域的副作用；失败重试靠 Bull（`attempts: 3`）。
6. **图标端点**：`@Public` 且每次读盘（`existsSync` + `readFileSync`）——无缓存；高并发列表渲染会反复打到文件系统。

## 11. 技术债与 hack

1. **`contact` 三处 `@OneToMany` 被整段注释**，且 `regionCode` 上叠了两个 `@Column()`——实体与历史模型已脱节；`saveContact` 无调用方（`[推测]` 为兼容外部调用保留）。
2. **`ContactModule` 未装配**：控制器、服务、种子、命令全在，但既无路由前缀也无人 import；`/api/contact` 不可达，`TenantPermissionGuard` 不会生效。
3. **联系人无唯一键**：`Contact` 无任何 `@Unique`，`saveContact` 直接 `save`——一旦挂载，天然会写入重复联系人（`country` 还只是 isoCode 字符串，无外键约束）。
4. **`contact` 命令文件名拼写错误**：`commands/contact-create.commant.ts`（缺 `d`），仅影响可读性与检索。
5. **字典种子不可复现**：`faker.internet.color()` 每次都变，且会把 `description` 重置为 `''`；`country` / `currency` 无去重，重复执行会产生重复行；`language` 的冲突被 `console.log` 吞掉（无日志级别、无指标）。
6. **`country` / `currency` 的 `isoCode` 只有非唯一索引**：字典一致性完全依赖种子内容，任何直连库的写入都不会被约束拒绝。
7. **`import-history` / `import-record` 是带连字符的字面表名**，与全库 snake_case 命名不一致；且 `import-record.wasCreated` 没有装饰器（非持久列），读代码时极易误判。
8. **`ImportHistory` 不在 `coreEntities` 中而 `ImportRecord` 在**：模块不装配时，两张表的注册来源不一致——迁移/建表路径不对称。
9. **`/api/import` 的 POST 语义已失真**：核心逻辑被注释，成功与失败都只写一条历史记录，调用方无法区分「真导入」与「落盘即成功」。
10. **`desktop_shell_operation.grantId → grant(id)` 未声明 `ON DELETE`**：删除 grant 会被外键拦住（NO ACTION），而 `assistantId` / `threadId` / `runId` 又是无外键的弱引用——删除助手/线程不会级联，靠服务层校验与 `enabled` 位兜底。
11. **`desktop-shell` 的 10 分钟硬上限写在代码里**（`Date.now() + 10 * 60000`）而非 `LIMITS`，与 `LIMITS.grant` / `LIMITS.lease` 并列存在，属可配置口径不统一。
12. **1 秒巡检 + 全表超期清扫**由每个进程实例各自执行（网关间无 leader 选举），`connectionEpoch` 与租约字段是唯一的互斥手段。
13. **移动端无版本协商**：`capabilities` 是布尔位、`deployment` 是自由字符串集合，缺少 `apiVersion` 字段；客户端只能按缺失字段自行降级（`[推测]`：客户端实现未在本次范围内核实）。
14. **`tag-management.usage` 的隐性契约**：依赖全库 `entityMetadatas` 与 `usageTargets` 白名单，任何新 M2M junction 未登记即让 `/api/tags/directory` 400；同时它对 `knowledgebase_tag` / `knowledge_document_tag` 做了硬编码识别。

## 12. 设计维度分析

**维度 A：写入面收敛 vs 写路径复杂度（字典 ≠ 业务表）**。字典族把写能力从运行期移除（只留种子 + `LanguageInitCommand`），代价是「种子不可复现、唯一性只由内容保证」；而唯一的可写字典 `tags` 为了在**无唯一软删**的前提下保证正确性，堆了租户行锁 + 标签行锁 + zod 白名单 + 大小写不敏感重名检查 + target 变更前的用量校验 + 删除前的用量保护。结论：本子域的写复杂度与「写频率」反向——越少写的表越依赖人工流程，越多写的表越依赖数据库锁；`tags` 是全子域最容易成为并发瓶颈的写路径。

**维度 B：真相位置决定可重放性（DB 权威 vs 内存/传输状态）**。`desktop-shell` 明确把三张表当唯一权威、把 Redis 当唤醒提示、把 WS 连接当「可丢的提示通道」：`dispatch` 每次重读设备行与 `connectionEpoch`、`receive` 用 `seq` 判连续性并以 `reconcile` 要求重传、超期统一置 `unknown` 而**永不重放**。这换来「进程重启/多实例/客户端闪断都不会二次执行」的强语义，但代价是：所有状态推进都必须经 DB（1Hz 巡检 + 每操作多次查询），并且必须由客户端诚实上报 `seq`。

**维度 C：幂等的两种实现范式（队列侧去重 vs 数据库唯一键）**。`initialization` 的幂等完全落在 Bull 的稳定 jobId + `removeOnComplete` 语义上（DB 层无对应唯一约束），执行侧再靠「出队先重查前置条件」补一致性；`desktop-shell` 的幂等落在数据库三元组唯一键 + 锁内复核上。前者依赖 Redis 存活与队列语义不变，后者依赖事务与锁；两者对「重放」的防御点不同，排障时应先分清作业是「没跑」还是「跑了两遍」。

**维度 D：门面 vs 实现的所有权切分（ai-model / mobile）**。`ai-model` 把「provider 目录 + 凭证 schema 校验」与「授权/计费」切开，`mobile` 把「投影」与「准入」切开（准入仍在 `PublishedXpertAccessService`），`initialization` 把「该不该做」与「做过没有」切开（入队 vs 出队重查）。三处都是同一手法：**在子域边界上不复制判定逻辑，只暴露窄接口**，避免模型目录、移动端 UI 与队列重试各自演化出第二套授权规则。

## 13. 结论

1. **四个字典模块的代码几乎全是装配与种子**：真正的语义在 `all-languages.ts` / `DEFAULT_COUNTRIES` / `DEFAULT_CURRENCIES` 三份常量与 `LanguagesEnum` 里；读端点零 DTO 白名单，靠实体装饰器兜底。
2. **`contact` 是「写好了但没插上电」的模块**：继承面完整、种子齐备、命令链闭合，缺的只是 `server.module.ts` 的注册与路由前缀；同时它没有任何唯一键，挂载前必须先设计去重策略。
3. **`desktop-shell` 的实现质量集中体现在三处**：`argsHash` 双端一致（准备与执行各算一次）、`pessimistic_write` 下的二次复核、`receive` 的 `seq` 连续性与 `reconcile` 回退；WS 的 `connectionEpoch` 负责换代，Redis 仅唤醒。
4. **`initialization` 与 `ai-model` 是两种极端**：前者把副作用推给队列并靠 jobId 保证幂等（0 HTTP 写面），后者把能力推给插件注册表并保持 0 表；两者都不在本域内做授权判定。
5. **两处未挂载（`/api/contact`、`/api/import`）与一处 400 占位（`tags` 的 `soft` / `recover`）**构成本子域的兼容负债；文档与接口清单必须显式标注，否则会把它们误计为可用能力。
