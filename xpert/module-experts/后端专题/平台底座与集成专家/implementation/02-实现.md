## 字典族实现（language / country / currency）
三个模块结构完全对称：`entity`（`BaseEntity`，**不带租户/组织列**）→ `service extends CrudService` → 只读 `@Controller()` + `@Public()` → `RouterModule.register` 给前缀（`/languages`、`/country`、`/currency`）。
**language**：`@Unique(['code'])` + `name`/`code`/`is_system`（默认 true）/`description`/`color`，另有 `@OneToMany(OrganizationLanguage)`；`createLanguages(connection)` 遍历 `all-languages.ts` 全量字典，`is_system = Object.values(LanguagesEnum).indexOf(key) >= 0`，`color = faker.internet.color()`；整批 `save()` 被 try/catch 包裹并 `console.log({error})` —— 重复初始化时唯一约束冲突会**静默失败**。写路径只有一个 CQRS 入口：`LanguageInitCommand` → `LanguageInitHandler` → `LanguageService.initialize()` → `createLanguages(EntityManager.connection)`，由 tenant 侧调用（树外），HTTP 面无写端点。语言解析：`findOneByName` 用原生条件 `"language"."name" = :name` 查询；排序：控制器与服务均**未声明 order**，`findAll(query)` 直接把 query 交给基类；多语言文案解析发生在别处（`getDefaultOrganizationWorkspaceName` 用 `RequestContext.getLanguageCode()` 选 `zh_Hans/en_US`；`Tag.label` 与 `XpertView*` 用 `resolveI18nText`）。
**country / currency**：`isoCode`（非唯一 `@Index()`）+ `country|currency`，`createCountries`/`createCurrencies` 直接以 `insert().into(...).values(...)` 批量插入 `DEFAULT_COUNTRIES`/`DEFAULT_CURRENCIES`；失败时 `reject(null)`，Promise 语义上会抛 `null`。四者（含 tags）都由 `core/seeds/seed-data.service.ts` 的「基础种子」阶段调用（`Countries`/`Currencies`/`Languages`），因此**同一批种子重复执行必然在其一唯一约束上失败**。校验仅 `@IsString`/`@IsNotEmpty`，无业务校验、无排序保证。
章节来源：[language.seed.ts](file://packages/server/src/language/language.seed.ts)（关键符号：createLanguages）、[language.service.ts](file://packages/server/src/language/language.service.ts)（关键符号：LanguageService.initialize）、[country.seed.ts](file://packages/server/src/country/country.seed.ts)（关键符号：createCountries）

## tags 与 contact：管理面与基类 CRUD
**tags** 是本域唯一「有写语义」的字典：`TagController extends CrudController<Tag>` 覆写 `POST`/`PUT :id`/`DELETE :id` 全部转 `TagManagementService.write/remove`（`PermissionGuard` + `ORG_TAGS_EDIT`），并显式把 `DELETE :id/soft` 与 `PUT :id/recover` 变成 400（文案「Use tag status to enable or disable a tag.」）。`write()` 在事务内先对 `Tenant` 行加悲观写锁（注释「Serialize catalog writes within the tenant, including duplicate-name checks.」），用 zod `inputSchema` 校验（name ≤100、label `{en_US,zh_Hans}`、targets ∈ `TAG_TARGETS`），做**大小写不敏感重名检查**、`targets→category` 兼容回填、并对被移除的 target 做「仍在使用则拒绝」（`Error.TagTargetInUse`）；`remove()` 要求 usage 计数为 0，否则提示改用停用。`usage()` 是全模块最重的一段：**扫描 `connection.entityMetadatas` 找出所有 owning 的 M2M junction**，按 `usageTargets` 白名单映射资源表名，逐表 `COUNT(*)` 聚合（含 `withDeleted`），未登记的 junction 直接 400（`Error.TagUsageUnsupported`）；`knowledgebase_tag`/`knowledge_document_tag` 作为「显式关系实体」单独统计。读取面 `TagService.findAll` 把租户级（`organizationId IS NULL`）与组织级标签**合并返回**，`findAllCategories` 用 `DISTINCT tag.category`。`TagSubscriber.beforeInsert` 回填 `tenantId`/`organizationId`/`createdById`（读上下文兜底）。
**contact**：`ContactController` 只有 `GET /`（`getAllContact` 用 `ParseJsonPipe` 解析 `data`），其余全部继承 `CrudController`；类级 `TenantPermissionGuard` 是唯一准入；`ContactService.saveContact` 只是 `repository.save(request)`，无去重、无唯一键；`createRandomContacts` 用 faker 生成并在 `country` 列写入 `isoCode` 字符串。注意该模块**未被任何模块 import**（见架构篇 §5），因此这些路由在运行时并不存在，只有实体/服务被其它域（`organization-contact`/`invite`）间接引用。
章节来源：[tag-management.service.ts](file://packages/server/src/tags/tag-management.service.ts)（关键符号：TagManagementService.usage）、[tag.controller.ts](file://packages/server/src/tags/tag.controller.ts)（关键符号：TagController.softRemove）、[contact.controller.ts](file://packages/server/src/contact/contact.controller.ts)（关键符号：ContactController.getAllContact）

## data-source 实现
**连接建立**：`DataSourceService.prepareDataSource(id, patch?)` 是全部动作的前置——①要求 `RequestContext.currentTenantId()` 与 `getOrganizationId()` 同时存在，否则 `ForbiddenException('Data source scope is required')`；②按 `{id, tenantId, organizationId}` 查库并 `relations: ['type','authentications']`，未命中抛 i18n 化的 `NotFoundException`；③把入参 `authentications`/`options`（浅合并，非覆盖）与补丁字段合并；④调用工具函数 `prepareDataSource(dataSource)`：当 `authType === AuthenticationEnum.BASIC` 时，从 `authentications` 中**按当前用户**挑一条，未找到即 `NotFoundException('未找到当前用户认证信息')`，找到则把 `username`/`password` **写进 `dataSource.options`**。
**凭据存储与使用**：`data_source_authentication` 只有 `tenantId`（继承）、`dataSourceId`、`userId`、`username`、`password`、`validUntil`；`createAuthentication` 先按 `{tenantId, dataSourceId, userId}` 查、命中即复用该行，写入 `username`/`password` 并把 `validUntil` 固定为 `addDays(new Date(), 30)`；`deleteAuthentication` 直接 delete；`getMyAuthentication` 只按当前用户查。**脱敏/加密边界核实结论**：本模块内不存在任何加解密调用（检索 `encrypt|decrypt|cipher|AES` 0 命中），`password` 列与 `options.password`（非 BASIC 场景由前端写入）均为明文；脱敏仅由 `DataSourcePublicDTO`（白名单 `id/name/type/typeId/authType/createdAt/updatedAt/createdBy`）+ `ClassSerializerInterceptor` 在**列表端点**实现，`GET /:id` 返回实体本身（`options` 会带出）。
**schema 拉取与缓存**：**无缓存**。每次 `getCatalogs`/`getSchema`/`queryCapability`/`query`/`import`/`dropTable`/`ping` 都会新建 runner（`DataSourceStrategyQuery(type, options)` → `DataSourceStrategyHandler` → `DataSourceStrategyRegistry.get(name)` → `strategy.create(options, dataSourceId)`），并在 `finally` 中 `runner.teardown()`；失败路径 `getCatalogs` 会把底层错误替换为中文「配置错误」。`getSchema` 支持 `statement` 直连 `runner.describe(catalog, statement)` 返回单表 schema。
**查询代理**：`query(id, statement, options)` → `runner.runQuery`；`olap(dataSource, body, acceptLanguage)` 在 `type.protocol !== 'xmla'` 时改投 `OLAP_HOST`/`OLAP_PORT`（默认 `localhost:8080/xmla`，`axios` POST XML），否则回落 `query`；`queryCapability` 先做能力键正则校验（`/^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$/`，capability ≤128、operation ≤64），再要求 runner 实现 `runner.queryCapability`，否则明确报「does not support capability queries」。
**认证方式与运行期边界**：`DataSourceRuntimeService` 是插件唯一入口，`authorize(actor, write)` 要求 `tenantId/organizationId/userId` 与 `RequestContext` 逐项相等且持有 `DATA_SOURCE_VIEW|EDIT`；`list` 只回 `{id,name,engine}`（pg→postgres），`open` 限制引擎白名单与 `location.engineCatalog === 'internal'`，用 `source.updatedAt` 做 revision 复核（变更即关闭会话并报「Data source changed; reopen the connection」），返回的代理对象对每个方法都先 `check()`/`check(true)`（写操作要求 EDIT）；注释逐字：「Proxy preserves method receivers and never exposes resolved credentials or the runner.」。
**命令与事件**：命令处理器 5 个（`DataLoadHandler`/`ListTablesHandler`/`QuerySchemaHandler`/`QuerySqlHandler`/`DataSourcePingHandler`），全部与 HTTP 面同套路；`DataLoadHandler` 委托 `dataLoad()`，后者按 `file.mimetype` 选择 Excel（`loadFromExcel`，多 sheet 并发 `runner.import`）或 CSV（pg 优先 `importCsv`，否则 `readExcelWorkSheets` 后走 `runner.import`）。事件面：`DataSourceUpdatedEvent` 在 `subscriber.afterUpdate` 与控制器 PUT 各发一次，而 `EventHandlers = []` —— 事件目前无消费者；`subscriber.ts` 头注「没有解决 typeorm Subscriber 与注入 nestjs EventBus 的问题」，实现上是构造期手动 `connection.subscribers.push(this)`。
章节来源：[data-source.service.ts](file://packages/server/src/data-source/data-source.service.ts)（关键符号：DataSourceService.prepareDataSource）、[utils.ts](file://packages/server/src/data-source/utils.ts)（关键符号：prepareDataSource）、[data-source-runtime.service.ts](file://packages/server/src/data-source/data-source-runtime.service.ts)（关键符号：DataSourceRuntimeService.open）

## data-source 的 16 个端点
1. `GET /`（`findAlls`）：`ClassSerializerInterceptor` + `DataSourcePublicDTO`，**唯一脱敏出口**；2. `GET /sql-select-options`：`findSqlDataSources()`（`type.protocol = SQL` 且限定租户+组织）转 `{value,label}`；3. `GET /sql-schema-select-options?dataSource=`：空参数返回 `[]`，否则 `getCatalogs` 转选项；4. `GET /:id`：返回完整实体（`$relations`/`$query` 可扩展），**不脱敏**；5. `PUT /:id`：直调 `service.update` 并 `eventBus.publish(new DataSourceUpdatedEvent(id))`，函数体内留有 `@todo Updated cqrs event 应该在哪里发出 ?`；6. `GET /:id/catalogs`；7. `GET /:id/schema?catalog&table&statement`；8. `POST /:id/query`（`{query}` + `Accept-Language`，错误统一 400）；9. `POST /:id/olap`（`HttpCode(200)`，逐条 `Promise.all` 并把成功/失败打包成 `{id,status,data|statusText}`）；10. `POST /:id/capabilities/query`（`PermissionGuard` + `DATA_SOURCE_VIEW`）；11. `POST /ping`（未落库的 `IDataSource` 直连测试）；12. `POST /:id/ping`（已落库 + 可选覆盖参数，并把 `authentications[].userId` 覆写成当前用户）；13. `GET /:id/authentication`（当前用户）；14. `POST /:id/authentication`（upsert，`validUntil=+30d`）；15. `DELETE /:id/authentication`；16. `POST /:id/load`（`FileInterceptor('file')` + `params` JSON → `DataLoadCommand`）。类级 `@Permissions(DATA_SOURCE_EDIT)` 覆盖全部方法，方法级再用 `@Permissions(DATA_SOURCE_VIEW)` 放开列表与能力查询；`CrudController` 基类的 `POST /`、`DELETE /:id` 未被覆写，属基类 CRUD 面。
章节来源：[data-source.controller.ts](file://packages/server/src/data-source/data-source.controller.ts)（关键符号：DataSourceController.olap）、[dto/public.dto.ts](file://packages/server/src/data-source/dto/public.dto.ts)（关键符号：DataSourcePublicDTO）

## xpert-table 实现
**Meta 与物理表**：`xpert_table` 是「逻辑表」元数据（`name`/`description`/`database`/`schema`/`columns` json/`status`/`message`/`physicalSchema`/`physicalTableName`/`version`(默认 1)/`activatedAt`/`deletedAt`），继承 `WorkspaceBaseEntity` 与 `XpertWorkspaceBaseService`，因此读写都会先过**工作区授权**（`assertWorkspaceReadAccess`/`assertWorkspaceWriteAccess`，无 `workspaceId` 时回落到租户+组织比对）。
**列/行/视图**：能力面只有「列定义 + 行插入 + 任意 SQL」三件事，`columns` 是自由 json（`TXpertTableColumn`），没有独立视图/公式实体；`insertRow` 要求表已 `ACTIVE`，把 `[{name,value,type}]` 转成 `tableDataOp(DBTableDataAction.INSERT)` 的 columns+values；`executeSql` 同样要求 `ACTIVE`，直接 `adapter.runQuery(statement, { catalog: table.schema })`。
**激活/停用（DDL 风险面）**：`activateTable` 先 `update(status=PENDING_ACTIVATION)`，把 `columns` 清洗成 `{name,fieldName,type,isKey,required,unique,autoIncrement,defaultValue,length,precision,scale,enumValues,setValues}`（空字符串默认值置 undefined），再 `tableOp(CREATE_TABLE, { createMode: UPGRADE })` → 成功置 `ACTIVE` + `activatedAt` + 清 `message`，失败置 `ERROR` + `message` 并抛 `BadRequestException`。`upsertTable` 是「创建/更新 + 自动激活」的组合入口（覆写 `POST /` 与 `PUT /:id`）：先 `validateTableName`（比对物理表是否存在 + 逻辑行 id 是否一致，异常时对更新操作**放行**、对新建**拒绝**），ACTIVE 且改名时先 `RENAME_TABLE`，然后激活；**激活失败时新表执行 `delete`（硬删逻辑行）、旧表只标 ERROR**。`deleteTable`：ACTIVE 时先 `DROP_TABLE`（失败仅 `logger.error`）再 `softDelete` —— 即物理删与逻辑删不保证同时成功。`getDatabaseSchemas` 直接调 adapter 的 `getCatalogs`（配套的 `get-database-schemas.query.ts` 未被 `QueryHandlers` 注册）。
**与助手的接口**：`WorkflowDBSQLNodeStrategy`（`@WorkflowNodeStrategy(WorkflowNodeTypeEnum.DB_SQL)`）用 mustache 把 `entity.sqlTemplate` 套上 state 环境后调 `executeSql`，`WorkflowDBInsertNodeStrategy`（`DB_INSERT`）按 `entity.columns[].valueSelector` 从 state 取值后调 `insertRow`，两者都包在 `wrapAgentExecution` 里落 `IXpertAgentExecution`；validator 监听 `EventNameXpertValidate` 产出 checklist 项（`sql/validator.ts` 的 message/ruleCode 误用 DB_INSERT 文案，`insert/validator.ts` 另有一份）。

## integration 实现
**集成定义**：`integration` 表以 `slug`（唯一索引）+ `provider` + `options` json + `features` jsonb + `userId` + `tags` M2M 描述一个第三方实例。`getProviders()` 把静态 `INTEGRATION_PROVIDERS` 与 `IntegrationStrategyRegistry.list(organizationId)` 的 `strategy.meta` 合并；写路径 **全部走命令**：`IntegrationUpsertCommand` → `IntegrationUpsertHandler`，先 `applyStrategyValidation`（取 `listRegistrations()` 中同 provider 的策略，调 `validateConfig(options, integration)`，成功只把 `name/description/slug/provider/options/features` 这些白名单字段回填 —— 防止策略越权改租户/权限字段），再 `runStrategyUpdateHook`（provider 变了走 `onDelete(previous)`，否则 `onUpdate(previous, current)`），最后落库；`IntegrationDelCommand` 先 `runStrategyDeleteHook` 再 `delete`。`ensurePrincipalUser` 为集成补一个「稳定技术主体」用户（优先 `userId` 命中，否则 `userService.ensureCommunicationUser({thirdPartyId: 'integration:<id>'})` 并回写 `userId`），供 API Key 绑定使用。
**扫码授权会话**：`IntegrationQrService` 是纯 Redis 状态机（无表）。`begin`：zod 校验 `{name,description,avatar}`，owner 取 `RequestContext` 三元组，purpose 为 `integration` 或 `trigger:<sha256(xpertId,triggerProvider)>`，在 `integration:qr:active:{tenant}:{org}:{user}:{provider}:{purpose}` 键上串行——若已存在旧会话先 `cancel`；调 `strategy.beginQrAuthorization()` 拿 `deviceCode/authorizationUrl/expiresInSeconds/intervalSeconds`，把 `expiresAt` 夹在 `[30s, 600s]`、`intervalSeconds ≥ 2`；会话体（含 `deviceCode`、`status: waiting`）整个 JSON 写入 `integration:qr:session:{uuid}`（TTL=expiresAt-now）。`poll`：`nextPollAt` 未到直接返回当前 status，否则**先写回 nextPollAt 再调 provider**（防重入），provider 给出 `intervalIncrementSeconds` 时把间隔上调（上限 600s），`authorized` 时把 provider 返回的 `options` 存入会话。`complete`：仅 `authorized` 可完成，用会话 id（或 `session.integrationId`）作为新集成 id 实现崩溃重试幂等；若策略提供 `getQrAuthorizationIdentity`，先在同 provider/租户/组织的既有集成里按 identity 归并（命中则 `update(options)` + `onUpdate`，未命中则 `create({...input, id})`），归并过程加 `integration:qr:account:...` 锁；完成后清空 `options`/`deviceCode`。所有操作都在 `RedisLockService.runWithLock(key, 60000, fn)` 内，抢锁失败返回 409 `INTEGRATION_QR_BUSY`；`read` 每次都校验 `userId/tenantId/organizationId` 与 TTL，任一不符即 404（对外表现为「过期」）。控制器 `@Controller('qr')` + `INTEGRATION_EDIT`，`begin`/`poll` 显式 `Cache-Control: no-store`。
**与 connector / MCP 的边界**：本模块只暴露「集成实例」概念，不注册 MCP 工具。`ConnectorAppIntegrationService` 给 connector 侧提供受限面：`list/select` 只回 `{id,name,organizationId}`（`publicOption`），`create` 要求 `RolePermissionCheck(INTEGRATION_EDIT)`、按 `slug = connector-{bindingId}-{requestId}` 去重（`insert().orIgnore()` + 回查，注释「The unique slug also deduplicates concurrent retries on different API replicas.」）、并逐字段比对确认未被篡改；`ResolveConnectorIntegrationHandler` 应答插件侧 `ResolveConnectorIntegrationQuery`（按 `{id, provider, tenantId}`，组织维度允许 `IS NULL` 或当前组织）。文件头注释即契约：「Application secrets stay in Integration. Public connector choices contain only identity; retry keys are unique per binding and never update an existing app.」

## desktop-shell 实现
**设备注册/刷新/禁用**：`register` 校验 `installationId`（uuid）、`platform === 'darwin'`、`settings`（zod `parseSettings`）；同一 scope 下同 `installationId` 已存在则先 `disable` 旧设备再复用其 `id`；生成 32 字节 base64url secret，只存 `hash(secret)`（sha256 hex）与 `credentialExpiresAt = now + LIMITS.grant`，返回明文 token `${deviceId}.${secret}`（仅此一次）；`disable` 会级联把该设备所有 grant 置 `enabled=false`，并把 `pending|running` 的 operation 置 `cancel_requested`，随后控制器 `await operations.notify(id)` 唤醒通道。
**授权签发与决定**：`issueGrant` 校验 `assistantId`，若带 `threadId` 则先查 `ChatConversationThread`（租户内）再以 `AssertChatConversationAccessQuery('contribute')` 走对话域准入；grant 的 `expiresAt` 取「设备凭据过期时间」与「now+LIMITS.grant」的较小值。`prepareOperation` 是「准备但**不执行**」的关键：`issueGrant` → 计算 `argsHash = sha256([command, cwd, timeoutSec])` → 把 `{runId, toolCallId, argsHash, decision:'pending'}` 写进 `grant.operation`，并把 grant 有效期压到最多 10 分钟（注释「A pending grant routes one operation but cannot authorize execution.」）。`decideOperation` 在事务里对 grant 行加悲观写锁，只允许 `pending→approved|rejected` 或同值重放，冲突抛 409 `OPERATION_CONFLICT`。
**命令执行**：`execute(input, scope)` 先 `requireGrant`（scope+threadId+assistantId+enabled+未过期），校验 `grant.operation.decision === 'approved'` 且 `runId/toolCallId/argsHash` 三者与本次完全一致，否则 403 `GRANT_REVOKED`；事务内对 device 与 grant 各加悲观写锁复核，按 `(tenantId, runId, toolCallId)` 查重放（命中则比对 `argsHash/grantId/userId`，一致返回原行、不一致 409），设备必须有未过期 lease（否则 409 `DEVICE_OFFLINE`），同设备存在活跃 operation 则 409 `DEVICE_BUSY`，最后写 `state:'pending'` + `deadline = now + timeoutSec`；提交后 `notify(deviceId)` 只做 Redis publish（注释「The gateway also polls its connected devices: a lost notification cannot lose a durable operation.」）。`receive` 在事务内锁 operation 行：output 报告要求 `seq === op.seq + 1`（重复 `<=` 直接 ack，跳号返回 `false` 触发 `reconcile`），累计字节超 `LIMITS.output` 只置 `truncated`；终态报告要求 `seq ≥ op.seq` 且不允许越过缺失 chunk，`cancel_requested` 期间的中间态被忽略，`succeeded && exitCode !== 0` 直接判非法。
**WS 通道与会话生命周期**：`@WebSocketGateway({ namespace: NAMESPACE, transports:['websocket'], maxHttpBufferSize: 65536 })`，握手校验 `credentials.version === VERSION` → `authenticate(token)`（长度 ≤150、`id.secret` 拆分、`enabled=true`、未过期、`timingSafeEqual`）→ 生成新 `connectionEpoch` 与 `leaseExpiresAt`，**踢掉同设备旧 socket**，回 `ready{version,connectionEpoch,leaseUntil}` 并立即 `dispatch`。`heartbeat` 续租前复核 `enabled`/`connectionEpoch`/凭据有效期，不符即 `revoked` + 断开；`report` 用 `entry.received` promise 链把同一 socket 的消息**串行化**（注释「a fast exit cannot overtake its output transaction」），并发报告上限 128 超限断连，成功后回 `ack{operationId,seq,state}`，序列不一致回 `reconcile`；`rejected` 只允许把 `pending` 置 `rejected`（「Only a never-accepted operation can be rejected.」）。`dispatch` 每次重新读设备（epoch/enabled/凭据）与活跃 operation，按 grant 过期/operation deadline 计算 `cancel`，向客户端发 `command`（`exec` 或 `cancel`，带 `argsHash`/`deadline`），同一 operation 3 秒内不重发；模块初始化时订阅 `xpert:desktop-shell:dispatch` 作为唤醒信号，并起一个 `setInterval(1000)` 既遍历重派发、又把超过 `LIMITS.lease + 10s` 未结束的 `pending|running|cancel_requested` 统一置 `unknown` + `EXECUTION_UNKNOWN`（无 `@Interval` 装饰器，属裸定时器）。
**3 表与 2 迁移**：实体见 `desktop-shell.entities.ts`（`desktop_shell_device` 的 `UNIQUE(tenantId,organizationId,userId,installationId)`、`desktop_shell_operation` 的 `UNIQUE(tenantId,runId,toolCallId)` + `(deviceId,state)` 索引、`desktop_shell_grant` 的 `(deviceId,enabled)` 索引与 `operation` jsonb）；`20260924-desktop-shell.sql` 显式建三表并加 FK/UNIQUE/索引，文件头「Apply before enabling Desktop Shell. Additive migration; existing platform data is unchanged.」；`20260928-desktop-shell-approval.sql` 只做 `ALTER TABLE desktop_shell_grant ADD COLUMN IF NOT EXISTS operation jsonb NULL;`。Agent 侧入口 `DesktopShellMiddleware`（`@AgentMiddlewareStrategy('DesktopShell')`，工具名 `desktop_shell`，参数 `action: exec|status|cancel`）：`exec` 先 `requestShellApproval`（`interrupt(ClientToolRequest)` 让客户端准备 → 若未批准再 `interrupt(HITLRequest)`，HITL 里展示 cwd/命令/「Runs as your computer user」提示，只有唯一 `approve` 决策才继续）→ `operations.execute` → 监听 `config.signal` abort 触发 cancel → `operations.wait`；结果通过 `dispatchCustomEvent(ON_TOOL_MESSAGE)` 以 `ChatMessageStepCategory.Program` 回显。

## initialization 的引导与幂等
**入队（时机）**：`ServerAIBootstrapProcessor` 用 4 个 `@OnEvent` 把域事件转成 Bull 作业：`EVENT_ORGANIZATION_CREATED` → `org-bootstrap:{organizationId}`、`EVENT_TENANT_CREATED` → `tenant-skill-repository-bootstrap:{tenantId}`、`EVENT_USER_ORGANIZATION_CREATED` → `user-org-bootstrap:{organizationId}:{userId}`、`EVENT_USER_ORGANIZATION_DELETED` → `user-org-cleanup:{organizationId}:{userId}`；统一 `attempts: 3, backoff: 10_000, removeOnComplete: true`。**幂等机制是「稳定 jobId + 出队时重查」而非数据库唯一约束**。
**执行（6 个 @Process）**：① `bootstrapOrganization`：解析 bootstrap 用户（组织 owner 或租户管理员）→ `membershipService.enqueueOrganizationDefaultMembershipInitialization` → 在组织上下文里 `ensureOrganizationWorkspace` → `ensureDefaultEnvironment` → `preinstallClawXpertTemplatePlugins` → 为全部成员 `workspaceService.ensureMember` → `importDefaultTemplates`；② `bootstrapTenantSkillRepositories`：`templateSkillSyncService.syncCurrentTenantSkillAssets({mode:'full', validateOnly:false, skipLock:true, updateFingerprint:true})`；③ `bootstrapUserInOrganization`：先 `isActiveOrganizationMember`（注释「Queue retries outlive membership removal; never restore access from a stale event.」）→ `ensureTenantDefaultMembership` → 视角色决定是否建个人工作区（`shouldBootstrapPersonalWorkspace`）→ 加入组织默认工作区 → `ensureUserAssignedIfScopeInitialized` → `initializeClawXpertIfModelAvailable`（失败只记 `clawXpertError` 并继续，由 processor 抛错触发重试）；④ processor 在该 job 成功后按 `createdNewUserDefaultWorkspace` 再入队 `user-default-skills:{workspaceId}`（`attempts: 8, backoff: 30_000`）→ `bootstrapUserDefaultWorkspaceSkills`（解析模板默认技能引用、逐条安装、汇总失败原因）；⑤ `cleanupUserInOrganization`；⑥ `syncSkillRepository`。`runInOrganizationContext`/`runInTenantContext`/`runInRequestContext` 用 `RequestContext` 包装器把 `tenantId/organizationId/language` 注入异步执行链，保证下游服务能读到作用域。队列名 `server-ai-bootstrap`（`BullModule.registerQueue` 于模块内注册）。
**ClawXpert 恢复**：`ClawXpertRecoveryController`（`@Controller('initialization/clawxpert')`，`GET` 状态 / `POST` 恢复）→ `ClawXpertRecoveryService`：`requireCurrentMember` 强制当前三元组 + `UserOrganizationService.count({isActive:true})`；`getStatus` 并行取 binding、候选 Xpert、以及 `queue.getJob('user-org-bootstrap:{orgId}:{userId}')`，按优先级给出 `ready / initializing / dependency_unavailable(model_required|personal_workspace_unavailable) / error / binding_inaccessible / missing`（`canRecover` 对 `SUPER_ADMIN` 为 false）；`recover` 时若作业已 `failed` 就 `existing.retry()`（注释「Bull atomically retries only failed jobs, so concurrent clicks cannot enqueue duplicates.」），否则重新 `add` 同一 jobId，并把返回状态置为 `initializing`。

## 热点路径
1. **`prepareDataSource` 是 data-source 全链的必经点**：每个查询/目录/健康检查都先做一次「租户+组织」条件查询并加载 `type`（+可选 `authentications`），随后新建 runner；无连接池、无 schema 缓存，`getSchema`/`getCatalogs` 的代价完全由外部库决定，`finally teardown` 是唯一回收手段。
2. **`xpert-table` 的 DDL 路径**：`upsertTable` = validate（一次物理表探测 + 一次逻辑行查询）+（可选 rename）+ activate（CREATE_TABLE UPGRADE），全部串行且无事务；`executeSql` 是任意 SQL 直通，等于把工作区授权变成唯一的执行边界。
3. **`view-extension` 的清单热路径**：`listSlotViews` 首次命中缓存时遍历**全部** provider 并逐个 `supports` + 读 manifests，随后 `filterVisibleManifests`（每次都读 `RequestContext` 权限）；60s 清单缓存 + 30s 数据缓存上限决定了「插件多、宿主多」时的扇出成本。
4. **`desktop-shell` 的 1 秒巡检**：`setInterval(1000)` 对每个在线连接调用 `dispatch`（重读 device + 查活跃 operation + 逐条查 grant），再执行一次全局 UPDATE 把超期 operation 标 `unknown` —— 连接数与「超期未结束」行数直接决定每秒 DB 负担。
5. **`desktop-shell.receive` 的行锁**：每个 output/report 都在事务内对 operation 行 `pessimistic_write`，长命令的高频输出（`LIMITS.chunk` 粒度）会持续争锁，但 `seq+1` 校验保证了顺序。
6. **`initialization` 的作业串行**：`bootstrapOrganization` 会遍历组织全部成员逐个 `ensureMember`，`bootstrapUserInOrganization` 内还有模板导入与 ClawXpert 安装，均在同一 job 内顺序执行；模板技能同步以 `attempts: 8` 长退避重试。
7. **`TagManagementService.usage` 的全库元数据扫描**：每次 `directory()`（列表页）都会遍历 `connection.entityMetadatas` 的所有 M2M junction 并逐表 `COUNT(*)`。

## 技术债与 hack
1. **凭据明文与序列化口子**：`data-source.entity.ts` 的 `options` 上 `// @Exclude()` 被注释掉、`authentication.entity.ts` 的 `password` 无 `@Exclude()`、`prepareDataSource` 还把凭据写进 `options`；`GET /:id` 直接返回实体。脱敏只覆盖 `GET /` 一条路径，`[推测]` 任何绕过 `DataSourcePublicDTO` 的调用方（含未来的关系展开）都可能读出明文密码。
2. **事件双发且无消费者**：`DataSourceUpdatedEvent` 由 `subscriber.afterUpdate` 与控制器 PUT 各发一次，而 `EventHandlers = []`；PUT 还绕过命令总线，函数体内留着 `@todo Updated cqrs event 应该在哪里发出 ?`。
3. **TypeORM subscriber 的注入 hack**：`data-source/subscriber.ts` 头注「没有解决 typeorm Subscriber 与注入 nestjs EventBus 的问题」，实际靠构造期 `connection.subscribers.push(this)`。
4. **`contact` 模块未装配**：全仓无任何模块 import `ContactModule`，`@Controller()` 下的路由不会注册；同模块也无 `RouterModule.register`，`[推测]` 属于历史迁移遗留（`organization-contact`/`invite` 只引用 `OrganizationContactModule`）。
5. **`export-import` 未装配且逻辑注释**：`ImportAllModule` 未在 `server.module.ts` 注册，`ImportAllService` 与 `unzipAndParse` 全被注释，`POST /import` 只写一条 `import-history` 记录。
6. **字典种子不幂等**：`createLanguages` 唯一约束冲突被 try/catch + `console.log` 吞掉；`createCountries`/`createCurrencies` 失败 `reject(null)`，Promise 语义不友好；触发点是 `seed-data.service` 的「基础种子」阶段。
7. **country/currency 无唯一约束**：`isoCode` 只有非唯一 `@Index()`，重复种子会产生重复行。
8. **`xpert-table` 的 DDL 无事务**：`upsertTable` 的 rename/create/activate 分步执行，激活失败时对**新表**执行硬删逻辑行、对旧表只标 `ERROR`；`deleteTable` 的 `DROP_TABLE` 失败后仍软删逻辑行，物理残留无人清理。
9. **`get-database-schemas.query.ts` 是死代码**：`xpert-table/queries/handlers/index.ts` 只注册 2 个 handler，控制器改调 `service.getDatabaseSchemas`。
10. **validator 文案复制粘贴**：`plugins/sql/validator.ts` 报出 `DB_INSERT_TABLE_REQUIRED` 与「Database Insert node」文案，与节点类型 `DB_SQL` 不符。
11. **`view-extension` 的 `@Public()` 依赖守卫兜底**：控制器自身是 `@Public()`，安全完全落在 `ApiKeyOrClientSecretAuthGuard` + `AllowClientSecretBindings(ENTERPRISE_XPERT)` 与宿主 `canRead`/manifest `permissions` 上；`[推测]` 新增入口若忘记声明守卫边界（文件头已警示「each entry point supplies its own authentication boundary」）会直接裸奔。
12. **使用量扫描的隐性契约**：`TagManagementService.usage` 对未在 `usageTargets` 登记的 M2M junction 直接抛 400，新增任意「可打标签」关系若忘了回填会**让整个标签目录接口失败**。
13. **`desktop-shell` 的裸定时器**：`setInterval(1000)` 同时负责重派发与超期标记，未使用框架调度；`entry.sent` 的 3 秒抑制与 `LIMITS.lease` 的 10 秒宽限是隐式耦合。
14. **`desktop-shell` 输出整行重写**：`output` 为 jsonb 数组，每个 chunk 都 `repository.save(op)` 全量写回；`truncated` 后不再追加但继续更新 `seq`。
15. **`ai-model/README.md` 为 0 字节**：正文只在 `README_CN.md`（6 行）。
16. **`initialization` 幂等依赖队列语义**：去重靠 Bull 的 `jobId` 与 `removeOnComplete`，`[推测]` 一旦 `removeOnComplete` 被改或队列数据被清（Redis 丢失），同一组织/用户可能被重复 bootstrap；数据库层没有对应的唯一约束兜底。

## 设计维度分析
**凭据边界：明文存储 vs 严格代理**。同一条数据源在两条路径上被截然不同的规则约束——HTTP 侧默认把 `options`（可能含用户名/密码）序列化出去，插件侧则由 `DataSourceRuntimeService` 用 actor 三元组比对、引擎白名单、`updatedAt` revision 与逐方法 `check(write)` 层层收紧。这种「内紧外松」的选择把安全责任推给了调用方与 DTO，一旦新增一个直读实体的端点就会破防。
**幂等的两种实现路径**。本域同时存在「表级唯一约束式幂等」（`desktop_shell_operation(tenantId,runId,toolCallId)` + `argsHash` 比对、`integration.slug` + `orIgnore()`、二维码会话 id 预占集成 id）与「队列/状态式幂等」（bootstrap 的稳定 `jobId`、`retry()` 原子性、出队后重查成员有效性与 `_clawXpertError` 延后重试）。前者对数据修复与多实例安全，后者依赖 Redis 队列存活，二者混用时运维面必须同时覆盖 DB 备份与队列持久化。
**双端协议 vs 服务端权威**。`desktop-shell` 把权威完整放在服务端：Redis 只做唤醒提示、客户端只提交报告、所有可执行性判断（epoch、grant、argsHash、lease、deadline、seq 连续性）都在服务端 DB 事务里重做；代价是每次派发都要重读设备与活跃 operation，`receive` 每片输出都要加行锁——正确性优先于吞吐。与之对照，`view-extension` 把权威部分让渡给插件（manifest 由 provider 提供），服务端只保证「宿主解析 + 权限过滤 + 缓存失效」三段，因此插件契约（`supports`/`activation.requiredFeatures`/`permissions`）成为事实上的安全边界。
**只读字典 vs 可写目录**。language/country/currency 完全没有写端点，一致性靠「一次性种子 + 唯一约束」；而 tags 是本域唯一带悲观锁与使用量校验的可写目录。这使 `tags` 的复杂度显著高于其它四个字典：写入要在 Tenant 行锁内做重名与占用检查，读取要跨实体元数据聚合——它们证明「平台字典」并非天然简单。
章节来源：[data-source-runtime.service.ts](file://packages/server/src/data-source/data-source-runtime.service.ts)（关键符号：DataSourceRuntimeService.authorize）、[desktop-shell-operation.service.ts](file://packages/server-ai/src/desktop-shell/desktop-shell-operation.service.ts)（关键符号：DesktopShellOperationService.execute）、[tag-management.service.ts](file://packages/server/src/tags/tag-management.service.ts)（关键符号：TagManagementService.write）

## 结论
实现上，本域把「外部世界」与「平台内部」的接缝集中在三个地方：`DataSourceService.prepareDataSource`（凭据与作用域）、`XpertTableService`（逻辑元数据 ↔ 物理 DDL）、`DesktopShellOperationService`（意图 ↔ 设备执行），三者都采用「先在服务端固化一条可重放的记录，再向外发信号」的同一套路（`options` 注入、`argsHash` 绑定、`seq` 校验）。字典族与 bootstrap 则走另一条路线：字典靠「种子 + 只读端点」把复杂度压到最低；bootstrap 靠「事件入队 + 稳定 jobId + 出队重查」把跨域副作用变成可重试的作业。
需要重点防守四件事：① data-source 的明文凭据，任何新增读取面都必须走白名单 DTO 或显式排除 `options`/`password`；② `xpert-table` 的 DDL 与逻辑行不在同一事务，改动该服务前必须先设计补偿；③ `view-extension` 的每个新入口都要自带鉴权边界（控制器是 `@Public()`）；④ `desktop-shell` 的 `setInterval` 巡检与 `output` 全量写回是容量瓶颈，扩容前应改为基于 deadline 的查询驱动。维护者若要新增平台字典或客户端壳能力，应沿用现有三件套（实体 + 只读/受控服务 + 种子或队列），并避免再出现 `ContactModule`/`ImportAllModule` 这类「存在但未装配」的组件。
