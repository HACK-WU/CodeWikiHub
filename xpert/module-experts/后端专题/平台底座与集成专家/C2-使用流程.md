## Recipe 1 字典种子初始化与读取（含多语言 fallback）
- **业务目标**：把 language/country/currency 三类**全局字典**灌进空库，并让调用方按请求语言取到 `zh_Hans|en_US` 文案。
- **调用顺序**：空库启动 → `serverService.seedDBIfEmpty()`（`SeedDataService` 基础种子阶段按 `createCountries → createCurrencies → createLanguages` 顺序执行）或 `pnpm seed:module --name …`；租户侧要重灌语言走 `LanguageInitCommand` → `LanguageInitHandler` → `LanguageService.initialize()` → `createLanguages(Connection)`；读取用 `GET /api/languages`、`GET /api/languages/getByName/:name`、`GET /api/country`、`GET /api/currency`（全部 `@Public`）。
- **事务-时序边界**：三个种子都是直插（country/currency 走 `insert().values(...)`，language 走整批 `save()`），**没有 upsert 事务**；`createDefaultTags`/`createTags` 另需 tenant 与 organizations，在 `seedDefaultData` 阶段执行，与基础种子不同批。
- **预期结果**：`language.is_system` 由 `LanguagesEnum` 判定（“哪些语言是系统语言”的唯一权威）；country/currency 返回 `isoCode` + 名称；**多语言 fallback 不在字典实体**，而在消费侧的 `Tag.label`、`XpertView*` 的 `resolveI18nText` 与 `getDefaultOrganizationWorkspaceName`（按 `RequestContext.getLanguageCode()` 在 `zh_Hans|en_US` 中二选一）。
- **错误处理**：`createLanguages` 的唯一约束冲突被 try/catch + `console.log({error})` **静默吞掉**；`createCountries`/`createCurrencies` 失败 `reject(null)`；`isoCode` 只有非唯一索引，**重复执行会重复插行**；`faker.internet.color()` 让 `color` 每次重跑都变、`description` 被重置为空——不要把 `color` 当业务字段。
- **真实代码示例**：
```ts
// language.seed.ts（源码事实）
// createLanguages(connection)：is_system = LanguagesEnum 命中；color = faker.internet.color()
// 整批 save() 被 try/catch 包裹并 console.log({error}) —— 重复执行静默失败
// language-init.handler.ts：LanguageInitCommand → LanguageService.initialize() → createLanguages(EntityManager.connection)
```

## Recipe 3 建外部数据源并测试连接（凭据写入与脱敏）
- **业务目标**：登记一个外部库连接（可选“个人认证”），在落库前后各测一次连通性，并确认哪些字段会出网。
- **调用顺序**：`POST /api/data-source`（基类 create，类级 `@Permissions(DATA_SOURCE_EDIT)`，创建后回查 `relations:['type']`）→ `POST /api/data-source/ping`（请求体即完整 `IDataSource`，**不落库**）→ `POST /api/data-source/:id/authentication`（upsert 当前用户凭据）→ `POST /api/data-source/:id/ping`（以库内为底 + 请求体覆盖，`authentications[].userId` 强制改写为当前用户）→ 取列表 `GET /api/data-source`。
- **事务-时序边界**：`prepareDataSource(id, patch?)` 是所有动作的前置——要求 `RequestContext.currentTenantId()` 与 `getOrganizationId()` **同时存在**（否则 403 `Data source scope is required`），按 `{id, tenantId, organizationId}` 查库并带 `type`/`authentications`；`authType === BASIC` 时工具函数把当前用户的 `username/password` **回写进 `options`**，随后 `options` 直接作为 runner 构造参数。认证行按 `(tenantId, dataSourceId, userId)` 复用，`validUntil = now + 30d` 写死。
- **预期结果**：`GET /api/data-source` 返回 `DataSourcePublicDTO` 白名单（`id/name/type/typeId/authType/createdAt/updatedAt/createdBy`，`options` 与 `authentications` 不下发）——这是**全模块唯一脱敏出口**；`POST /:id/authentication` 成功后该用户的凭据即可被后续所有动作注入。
- **错误处理**：连不上 → **500**（`err.message` 原样透传，排障看 message 不看状态码）；`authType=BASIC` 但当前用户无认证行 → **404** `未找到当前用户认证信息`。**加密口径（实测）**：`password` 是无加密 text 列、`data-source.entity.ts` 里 `options` 上的 `// @Exclude()` 处于注释态、`GET /:id` 直出实体（`$relations` 带 `authentications` 时明文 `password` 一并返回）、`GET /:id/authentication` 把当前用户 `password` 明文回给浏览器；模块内检索 `encrypt|decrypt|cipher|AES` **0 命中**。
- **真实代码示例**：
```http
POST /api/data-source/ping                  { "name":"pg","typeId":"<uuid>","authType":"BASIC","options":{ "host":"db","port":5432 } }
POST /api/data-source/<id>/authentication   { "username":"u","password":"p" }   # validUntil = now + 30d
GET  /api/data-source                        # DataSourcePublicDTO：options / authentications 不下发
GET  /api/data-source/<id>?$relations=["authentications"]   # 注意：直出实体，含明文凭据
```
章节来源：[data-source.service.ts](file://packages/server/src/data-source/data-source.service.ts)（关键符号：prepareDataSource / createAuthentication / getMyAuthentication）、[public.dto.ts](file://packages/server/src/data-source/dto/public.dto.ts)（关键符号：DataSourcePublicDTO / Exclude / Expose）、[authentication.entity.ts](file://packages/server/src/data-source/authentication/authentication.entity.ts)（关键符号：password / validUntil）

## Recipe 4 外部数据源 schema 拉取与查询代理（超时/错误）
- **业务目标**：列出可选库/catalog/表结构，并把用户或助手的 SQL 代理到外部库；同时明确超时与失败语义的归属。
- **调用顺序**：`GET /api/data-source/sql-select-options`（`type.protocol = SQL` 且租户+组织双条件）→ `GET /api/data-source/sql-schema-select-options?dataSource=`（空参数回 `[]`）→ `GET /api/data-source/:id/catalogs` → `GET /api/data-source/:id/schema?catalog&table&statement`（带 `statement` 走 `runner.describe`）→ `POST /api/data-source/:id/query`；能力式扩展走 `POST /api/data-source/:id/capabilities/query`（`DATA_SOURCE_VIEW`）；OLAP 走 `POST /api/data-source/:id/olap`；文件装载走 `POST /api/data-source/:id/load`；插件侧走 `DataSourceRuntimeService.open`（无 HTTP）。
- **事务-时序边界**：每个动作都是「`DataSourceStrategyQuery(type, options)` → `DataSourceStrategyRegistry.get(name)` → `strategy.create(...)` → runner → **`finally` 中 `runner.teardown()`**」的同一模板，因此**没有长驻连接**；能力键在**建 runner 之前**校验（正则 `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`，capability ≤128 / operation ≤64）。**本域没有 schema 缓存层**，缓存责任在调用方。
- **预期结果**：`query` 返回 runner 原始结果；`capabilities/query` 返回适配器自有能力结果；OLAP 逐条返回 `{id,status,statusText,data}`（整体仍 200）；插件侧返回**不暴露 runner 与解析后凭据**的方法代理，且 `list` 只回 `{id,name,engine}`。
- **错误处理与超时**：**本域不定义查询超时**——连接池大小与 `statement_timeout` 属插件 adapter（`DBQueryRunner`），超时/取消语义由插件与 HTTP 层决定 `[推测]`；`query` 失败 → **400**（透传 `err.message`）；`catalogs`/`schema`/`ping` 失败 → **500**（`catalogs` 的 message 常退化为 `配置错误`）；capability 非法或适配器未实现 → **400**（`Data source adapter '<type>' does not support capability queries`）；OLAP 在非 `xmla` 协议时改投 `http://${OLAP_HOST|localhost}:${OLAP_PORT|8080}/xmla` 并把失败吞成逐项状态。插件侧在数据源变更后一律 **403** `Data source changed; reopen the connection`（靠 `updatedAt` 做 revision），仅放行 `mysql/doris/postgres` 且要求 `location.engineCatalog === 'internal'`。
- **真实代码示例**：
```http
GET  /api/data-source/<id>/schema?catalog=public&statement=select%201
POST /api/data-source/<id>/query             { "query": "select 1" }
POST /api/data-source/<id>/capabilities/query { "capability": "xmla.metadata", "operation": "discover" }
POST /api/data-source/<id>/olap              [{ "id": "q1", "statement": "..." }]
```
章节来源：[data-source.controller.ts](file://packages/server/src/data-source/data-source.controller.ts)（关键符号：getCatalogs / getSchema / query / olap / queryCapability）、[data-source-runtime.service.ts](file://packages/server/src/data-source/data-source-runtime.service.ts)（关键符号：list / open / authorize / check）、[utils.ts（data-source）](file://packages/server/src/data-source/utils.ts)（关键符号：prepareDataSource / AuthenticationEnum.BASIC）

## Recipe 5 xpert-table 建元数据与激活物理表（DDL）
- **业务目标**：在工作区里定义一张逻辑表，并在选定的外部库中真正建出/升级物理表，随后交给助手工作流读写。
- **调用顺序**：`GET /api/xpert-table/databases`（`XpertDatabasesQuery({protocol:'sql'})`，挂 `DATA_SOURCE_VIEW`）→ `GET /api/xpert-table/schemas?databaseId=` → `POST /api/xpert-table`（覆写基类 create → `upsertTable`，一步完成“建 Meta + 激活”）→ 改列后 `POST /api/xpert-table/:id/activate` 显式重激活 → `PUT /api/xpert-table/:id`（`active` 且改名时先 `RENAME_TABLE`）→ `DELETE /api/xpert-table/:id`（`active` 时先 `DROP_TABLE` 再软删）；行列读写不在 HTTP：`insertRow`/`executeSql` 要求 `status=active`，只经 `@WorkflowNodeStrategy(DB_SQL)` / `(DB_INSERT)` 暴露。
- **事务-时序边界**：`activateTable` 先置 `pendingActivation` → `tableOp(CREATE_TABLE, { createMode: UPGRADE })` → 成功置 `active` + `activatedAt` 并清 `message`，失败置 `error` + `message`；**DDL 与元数据不在同一个事务**（validate → 可选 rename → activate 三步串行）。`columns` 在提交前被清洗为 `{name,fieldName,type,isKey,required,unique,autoIncrement,defaultValue,length,precision,scale,enumValues,setValues}`（空串默认值置 `undefined`）。
- **预期结果**：`xpert_table` 行带 `physicalSchema`（注释示例 `xpert_data`）/`physicalTableName`（例 `xd_ta3f1a_…_v1`）/`version`（默认 1）/`activatedAt`/软删 `deletedAt`；`status` 7 态中**只有** `draft→pendingActivation→active` 与 `→error` 有写入点，`ready/needsMigration/deprecated` 未见写入 `[推测]`。
- **错误处理**：名称冲突 → **400** `Table name <schema>.<name> already exists in the database.`；改名失败 → **400** `Failed to rename physical table: …`；激活失败 → **400** `Table activation failed: …`（行置 `status=error`）；无列 → **400** `Table must have at least one column to activate.`。**风险面**：`validateTableName` 在异常分支对“更新”放行（`return !entity.id`）；激活失败时**新表硬删逻辑行、既有表只标 ERROR**；`deleteTable` 的 `DROP_TABLE` 失败仅 `logger.error` 后照常软删（留下物理表孤儿）；非 `active` 改名会让 `physicalTableName` 与 Meta 名脱节。
- **真实代码示例**：
```http
GET  /api/xpert-table/databases
POST /api/xpert-table          { "name":"orders","database":"<dsId>","schema":"public","columns":[{ "name":"id","type":"int","isKey":true }] }
POST /api/xpert-table/<id>/activate
DELETE /api/xpert-table/<id>   # 204：active 时先 DROP_TABLE（失败仅记日志）再软删逻辑行
```

## Recipe 6 集成扫码授权全流程

## Recipe 8 桌面壳设备授权与命令执行（含 WS 回执）
- **业务目标**：注册一台桌面设备，按会话授权一条命令，并把执行输出与回执收回到 Agent 会话，全程可幂等、可撤销。
- **调用顺序**：`POST /api/desktop-shell/devices`（`installationId` uuid + `platform === 'darwin'` + `parseSettings`；同 scope 同 installationId 先 disable 旧行再复用其 id）→ 桌面端用 `token = <deviceId>.<secret>` 连 `ws(s)://<api-host>/desktop-shell`（握手校验 `credentials.version === 1`）→ `POST /devices/:id/grants`（`assistantId` 必填、`threadId` 可选）→ `POST /devices/:id/prepare`（写 `operation={runId,toolCallId,argsHash,decision:'pending'}`）→ `POST /grants/:id/decision`（`approve|reject`）→ Agent 侧 `desktop_shell` 工具 `execute()` → 设备 `report` → 运维面 `POST /devices/:id/refresh`、`POST /grants/:id/revoke`、`POST /devices/:id/disable`、`POST /operations/:id/cancel`、`GET /operations?deviceId=`。
- **事务-时序边界**：`argsHash = sha256([command, cwd, timeoutSec])`；`prepare` 把 grant 有效期压到**最多 10 分钟**（源码逐字「A pending grant routes one operation but cannot authorize execution.」）；`decision` 在事务内对 grant 行加悲观写锁，只允许 `pending→approved|rejected` 或同值重放；`execute` 在事务内锁 device+grant 并复核 `runId/toolCallId/argsHash` 三者全等，`UNIQUE(tenantId,runId,toolCallId)` 命中即幂等返回（hash/owner 不一致 409），同设备已有活跃操作 409 `DEVICE_BUSY`；提交后 `notify` 只做 Redis publish + 网关每秒轮询兜底（源码逐字「a lost notification cannot lose a durable operation」）。
- **预期结果（含 WS 回执）**：上行帧 `ready/command(type:exec|cancel)/lease/ack/reconcile/revoked`，下行帧 `heartbeat/report/rejected`（`rejected` 只允许把 `pending` 置 `rejected`）；`report` 在同一 socket 内**串行拼 promise 链**（防止「快速退出超过输出事务」），output 分片要求 `seq === op.seq + 1`（重复 `<=` 直接 ack，跳号回 `reconcile`），累计超 `LIMITS.output`(1MiB) 只置 `truncated`，并发报告 >128 直接断连；连接期生成新 `connectionEpoch` 并**踢掉同设备旧 socket**，`leaseExpiresAt = now + 90s` 由 `heartbeat` 续租；每秒巡检把 `deadline < now - (lease + 10s)` 的活跃行统一置 `unknown` + `EXECUTION_UNKNOWN`（**明确不重放**）。
- **错误处理**：`currentShellScope()` 三元组非 UUID 或设备不可用 → **403 `GRANT_REVOKED`**；无未过期 lease → **409 `DEVICE_OFFLINE`**；重复不一致 → **409 `OPERATION_CONFLICT`**；同设备活跃操作 → **409 `DEVICE_BUSY`**；设备凭据过期（`LIMITS.grant = 8h`）→ 401/403，需 `/refresh`；WS 版本不符 → 握手即断 `PROTOCOL_MISMATCH`（文案 `Update Xpert Desktop to connect to this service.`）；反代未放行 websocket upgrade 或 body > 64KiB 会直接连不上。
- **真实代码示例**：
```ts

// prepareOperation()：argsHash = sha256([command, cwd, timeoutSec])，写 grant.operation.decision='pending'
// desktop-shell-operation.service.ts：execute() → requireGrant → decision==='approved' → 三元组全等 → seq 连续校验
// desktop-shell.gateway.ts：setInterval(1000) 重派发 + 超租约置 unknown/EXECUTION_UNKNOWN
```

## Recipe 12 排障入口合集
- **业务目标**：把本域六类高频症状各自收敛到**唯一判据**与**唯一处置动作**，避免按症状猜测。

  1. **连不上外部库**：先 `POST /api/data-source/:id/ping`——**500 + adapter message**；`GET /:id/catalogs` 的 500 常退化为 `配置错误`。判据：`authType=BASIC` 时先查当前用户的 `data_source_authentication` 是否存在、是否超过 30 天；连接池/语句超时**不在本域**，去查插件 adapter 配置。
  2. **扫码授权不回**：看 Redis `integration:qr:session:<id>` 是否还在（TTL 30..600s，过期即 404）；`status` 停在 `waiting` 说明第三方未确认（回第三方后台确认回调与授权人）；`authorized` 后**直接重试 `/complete`**（幂等，返回 `reused`/`created`）；409 `INTEGRATION_QR_BUSY` 是并发轮询过密。
  3. **视图不显示**：用 `GET /api/view-hosts/<hostType>/<hostId>/slots/<slot>/views` 区分三态 404（`Unknown view host` / `View host … was not found` / `View … was not found`）与 403（`canRead`、动作权限、项目角色）；插件视图需确认插件已加载**且宿主进程已重启**（注册表为进程内内存）；集成宿主要求 `INTEGRATION_VIEW|INTEGRATION_EDIT`。
  4. **设备离线/忙**：409 `DEVICE_OFFLINE` = `leaseExpiresAt` 空或过期（>90s 无心跳）；409 `DEVICE_BUSY` = 同设备已有 `pending/running/cancel_requested`；`EXECUTION_UNKNOWN` 是**终态且不自愈**，处置是重新发起新操作而非重放同一 `runId+toolCallId`。
  5. **种子缺失**：先 `SELECT count(*)` 确认缺哪张；country/currency 重灌前按 `isoCode` 去重（无唯一约束会重复插行）；语言用 `LanguageInitCommand` 显式重灌（每次重跑都会刷新 `color` 并清空 `description`）；`/api/contact`、`/api/import` 的 404 属「未挂载」现状而非故障。
  6. **DDL 冲突**：400 `Table name <schema>.<name> already exists in the database.`（同名物理表）/ `Failed to rename physical table: …` / `Table activation failed: …`（行已置 `status=error`，改列后用 `/activate` 重试）/ `Table must have at least one column to activate.`；**删除后停不下来的残留**要靠人工核对「逻辑行已软删但物理表仍在」。
- **事务-时序边界与判据**：本域无自有指标，通用观测只有 `GET /metrics` 与 Swagger `/swg`（`/api/contact`、`/api/import` 缺失属预期）；桌面壳的 Redis 订阅失败只降级告警（`Desktop Shell notification connection unavailable`），仍有每秒轮询兜底。
- **预期结果**：每条症状都能落到「一个 URL + 一个状态码/日志关键字」；排障顺序固定为「先看挂载与否（Swagger）→ 再看鉴权边界 → 最后看数据与缓存」。
- **错误处理**：不在本域归口的症状（模型不可用、文件理解、沙箱）应转「模型访问与计费」「运行时与沙箱」专家域，不要在本域内猜测。
- **真实代码示例**：
```http
POST /api/data-source/<id>/ping                  # 500 + message：网络不通 vs 认证失败
GET  /api/view-hosts/integration/<id>/slots/detail.main_tabs/views
GET  /api/desktop-shell/operations?deviceId=<id> # 含 truncated / error.code(=EXECUTION_UNKNOWN)
POST /api/initialization/clawxpert               # 重试失败的 user-org-bootstrap 作业
```
