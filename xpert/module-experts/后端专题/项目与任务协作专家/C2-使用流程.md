## Recipe 1 创建项目与类型快照固化
- **业务目标**：建一个带初始助手的项目，并把「项目类型身份 + 显示快照」在创建瞬间固化，避免日后类型下线导致历史项目不可解释。
- **调用顺序**：`POST /api/xpert-project`（`XPERT_PROJECT_CREATE`）→ `XpertProjectService.createProject`：`xpertIds` 去重后逐个 `resolveAccessibleCurrentXpert`（可用性与发布校验回落到 `PublishedXpertAccessService`）→ `XpertProjectTypeService.forCreate(input.projectType ?? GENERAL_PROJECT_TYPE)` → `resolve(ref)`（只认当前已加载插件目录里的活体类型）→ `classification(ref)`：解析 `applicationKey`/`projectTypeKey`，按 `pluginName + appName` 反查 `PluginApplicationInstallation` 得 `applicationInstallationId`，固化 `projectTypeSnapshot` → `createProjectWithAssistants` 落库（`bindings.resolveInitialMembers` 规范化助手集合；无 `entity.id` 走 `store.create` + `store.initialize`，有 `entity.id` 在事务内 `insert` + `relation(XpertProject,'xperts').add(...)`）→ 控制器补 `planService.ensureDefaults`（Default plan + Uncategorized）与 `activityService.record({type:'project.created'})`。
- **事务-时序边界**：类型解析与安装校验是落库前的读侧动作；项目行与 M2M 助手关系在同一事务内提交；`ensureDefaults` 与活动记录在**项目创建之后**触发——默认计划是可选语义，缺行必须创建而不是抛错。创建时 `toolsetIds`/`knowledgebaseIds` 被 `void` 剥掉（payload 注释「Deprecated direct capability selections are intentionally ignored.」），故新项目这两个集合恒为空。
- **预期结果**：返回 `XpertProjectDto`；`CK_project_type_identity` 保证 `applicationKey` 与 `projectTypeKey` 同为 NULL 或同非空且非空串；索引 `IDX_project_application_type(tenantId,organizationId,applicationKey,projectTypeKey,status)` 支撑目录查询。
- **错误处理**：binding 为 `entity` 的类型不允许普通创建 → `ProjectApplicationWorkflowRequired`；`insert` 冲突码 `23505` 转类型冲突错误；类型键不合法 → 400。插件/业务侧幂等路径为 `ProjectEnsureCommand` → `ensureManagedProject`，查项目时把 `tenantId`/`organizationId` 一起放进 where（注释：「retries cannot adopt a same-id Project from a different security boundary」）。
- **真实代码示例**：
```ts
// 契约：XpertProjectService.createProject / XpertProjectTypeService.classification
classification(ref) // → { applicationKey, projectTypeKey, applicationInstallationId, projectTypeSnapshot }
// 源码注释（project-type.service.ts）：「display snapshots never authorize app execution.」
```

## Recipe 2 成员管理与 token 邀请
- **业务目标**：增改移除项目成员，并以 token 邀请组织外/外邮箱用户加入，重复邀请不产生重复行。
- **调用顺序**：成员 `POST /:id/members`（`MANAGE`，`{userId, role}`）→ `XpertProjectMembershipService.add`；整体覆盖用 `PUT /:id/members`（兼容桥 `replaceMembers`）；改角色 `PATCH /:id/members/:userId`；移除 `DELETE /:id/members/:userId`。邀请 `POST /:id/invitations`（`{email, role}`）→ `invite`；接受 `POST /api/xpert-project/invitations/accept?token=`、拒绝 `POST /api/xpert-project/invitations/decline`（**该控制器无项目守卫**，靠服务层校验 token 与登录态）。
- **事务-时序边界**：`add` 先 `assertCanManage`，再校验 role 白名单、拒绝把 owner 当普通成员添加、要求目标为「同租户 USER 且同组织 active 成员」，随后 `findOne({withDeleted:true})` 命中软删行则 `restore` 复用同一行（`joinedAt` 重置、`removedAt`/`deletedAt` 清空）。接受在事务内 `pessimistic_write` + `tokenHash` 查询。移除成员时先批量 `pause` 该用户的 `XpertTask`，再 `emitAsync('xpert-project.member-removed')`。
- **预期结果**：`list` 把 owner 与 memberships 合并为 `TXpertProjectMemberSummary`（owner 恒为 `projectRole:'owner'`）；角色口径 `manager|editor|member` + `owner`，`canEdit=[owner,manager,editor]`、`canManage=[owner,manager]`；同项目同邮箱至多一条 pending（部分唯一索引 `IDX_xpert_project_invitation_pending`）。token 为 `randomBytes(32).toString('base64url')`，库内只落 `tokenHash`（`select:false` + `@Exclude`），过期取组织 `inviteExpiryPeriod`（缺省 14 天）。
- **错误处理**：400 `ProjectOrganizationRequired` / `ProjectMemberAlreadyExists`；403 `OrganizationInvitePermissionRequired`（需组织级 `ORG_INVITE_EDIT`）；邀请失效 400 `ProjectInvitationInvalid`、邮箱不匹配 403 `ProjectInvitationEmailMismatch`、撤销非 pending 400 `ProjectInvitationNotPending`；`revoked` 状态未见写入点 `[推测]`。历史成员同步由 60s `@Interval` 重试、退避上限 1h。
- **真实代码示例**：
```ts
const token = randomBytes(32).toString('base64url') // 仅 tokenHash 落库，日志不得出现明文 token
// 同 (projectId, normalizedEmail, pending) 复用同一行并轮换 hash
```
章节来源：[project-membership.service.ts](file://packages/server-ai/src/xpert-project/services/project-membership.service.ts)（关键符号：XpertProjectMembershipService.add / remove）、[project-invitation.service.ts](file://packages/server-ai/src/xpert-project/services/project-invitation.service.ts)（关键符号：XpertProjectInvitationService.invite / accept）、[project-invitation.entity.ts](file://packages/server-ai/src/xpert-project/entities/project-invitation.entity.ts)（关键符号：tokenHash / IDX_xpert_project_invitation_pending）

## Recipe 3 项目资源挂载
- **业务目标**：把助手、工具集、知识库、附件、卷内容与资产索引挂到已建项目上，且不产生重复挂载或越权挂载。
- **调用顺序**：助手 `PUT /:id/xperts/:xpert` 或 `PUT /:id/assistant`（`MANAGE`）→ `addXpert`（要求助手与项目同组织）→ `XpertProjectXpertBindingService.normalize` 把历史版本快照替换为「当前版本」；工具集 `PUT/DELETE /:id/toolsets[/:toolset]`；知识库 `PUT/DELETE /:id/knowledges[/:kb]`；附件 `PUT /:id/attachments`、`DELETE /:id/attachments/:file`；卷内容 `GET/PUT /:id/content/instructions`、`/:id/content/skills`（含 `/install`、`/upload`、`/file`）；资产 `POST/PUT/DELETE /:id/assets[/:assetId]`。
- **事务-时序边界**：附件写入先 diff 现有 id，再对每个新 id 走 `GetOwnedStorageFileQuery`（**拥有权校验**）后整体 `save`；资产以 `(projectId, path)` 唯一键 upsert（`withDeleted` 命中则 recover + 复用）。会话首发另有资源卡通道：`ProjectResourceCardService.attach` 在事务内锁项目行与首条 AI 回复消息行，写 `settings.conversationBootstrap.resourceCards` 并记录 `resourceCardMessageId`，保证「回执与其首条回复原子认领、重放不能重新分配」。
- **预期结果**：助手关系按「家族」而非版本快照比较（`isSameXpertFamily`），加同家族新版本不会重复挂载；受治理路径（`project.md`、`skills/`）不能走普通文件 API，否则 400；技能上传 ZIP ≤ 25MB、工作区文件上传 ≤ 10MB。
- **错误处理**：助手与项目不同组织 → 拒绝；`PATCH :id/content/skills` 缺布尔 `enabled` → 400 `Error.ProjectSkillEnabledRequired`；删除资产/物理 purge 前若关联文件仍在 `uploaded/scanning/parsing/processing/queued` → 400 拦截。
- **真实代码示例**：
```http
PUT /api/xpert-project/<id>/xperts/<xpertId>
PUT /api/xpert-project/<id>/toolsets/<toolsetName>
PUT /api/xpert-project/<id>/attachments   DELETE /api/xpert-project/<id>/attachments/<fileId>
```
章节来源：[project.service.ts](file://packages/server-ai/src/xpert-project/project.service.ts)（关键符号：XpertProjectService.addXpert / addAttachments）、[project-xpert-binding.service.ts](file://packages/server-ai/src/xpert-project/services/project-xpert-binding.service.ts)（关键符号：XpertProjectXpertBindingService.normalize）、[project-resource-card.service.ts](file://packages/server-ai/src/xpert-project/services/project-resource-card.service.ts)（关键符号：ProjectResourceCardService.attach）

## Recipe 4 项目内建任务与依赖表达
- **业务目标**：在项目内建协作任务、维护步骤，并用 `predecessorIds` 与计划字段表达依赖，且不被外部覆盖 provider/投影列。
- **调用顺序**：`POST /:id/tasks` → `createTask`（`validateTaskMode`：simple 只允许固定泳道状态集；`resolveAssigneeXpertId` 强制「执行助手必须是项目成员」）→ `saveAll`；单改 `PUT /:id/tasks/:taskId`、批量 `PUT /:id/tasks/batch`、重排 `PUT /:id/tasks/order`；依赖与计划字段只能经 `PUT /:id/task-graph`（`projectTaskPlanSchema.safeParse` + 必带 `expectedRevision`，仅投影 `parentTaskId/predecessorIds/plannedStartAt/plannedEndAt/estimatedDurationMs`）。
- **事务-时序边界**：`saveAll`/`updateTask`/`updateTaskSteps`/`batchUpdate` 的共同骨架为 `assertOrdinaryTaskInput`（拒绝外部写 13 个 provider 与投影列）→ 事务内 `lockProject`（项目行 `pessimistic_write`，全域名串行化）→ `assertOrdinaryTask`（provider 巡检行不接受通用写）→ `assertBusinessStatus` → 保存；步骤用 `updateTaskSteps` 按 `stepIndex` 就地合并，`notes` 追加而非覆盖。
- **预期结果**：幂等键 `(projectId, providerKey, sourceKey)` 唯一；provider 投影任务 id 由 `projectTaskIdentity(projectId, provider, key)` 的 sha256 派生为稳定 UUID；当且仅当该任务**没有带 `invocationId` 的执行**且所有步骤 `done` 时，任务被隐式推进为 `done`。
- **错误处理**：外部提供 provider/投影列 → `Owned`；已有 Invocation 执行时直接写 `done`/`completed` → `DecisionRequired`（409）；`expectedRevision` 不符 → 409 `Conflict`；zod `.strict()` 多余字段 → 400；任务不存在 → 404 `Project task not found`。注意 `xpert_project_task_log`（`stepId` 级联、`logType ∈ input|output|error`）实体与注册齐备但**未找到写入/读取点**，排障不要依赖该表。
- **真实代码示例**：
```http
PUT /api/xpert-project/<id>/task-graph
{ "expectedRevision": 7, "tasks": [ { "key": "t2", "predecessorIds": ["<taskIdOfT1>"] } ] }
```
章节来源：[project-task.service.ts](file://packages/server-ai/src/xpert-project/services/project-task.service.ts)（关键符号：XpertProjectTaskService.saveAll / updateTaskSteps / lockProject）、[project-task-ownership.ts](file://packages/server-ai/src/xpert-project/services/project-task-ownership.ts)（关键符号：assertOrdinaryTaskInput）、[project-task-graph.service.ts](file://packages/server-ai/src/xpert-project/services/project-task-graph.service.ts)（关键符号：projectTaskIdentity）

## Recipe 5 派发执行并处理回执
- **业务目标**：把任务显式委托给执行器，并在运行时事实回流后正确处理状态，且业务完成只能由显式验收决策确定。
- **调用顺序**：`DispatchProjectTaskCommand`（Agent 侧走工具 `project_dispatch_task`，`requestId` 由 host 从 project/conversation/thread/caller/operation/tool-call ID 派生）→ `ProjectTaskDispatchService.dispatch`：schema 校验 + `target`/`delivery` 互斥 → `ProjectTaskRuntimeContextService.resolve` 还原 `AgentInvocationScope` → `factory.resolveGroupTarget` / `resolveBackgroundTarget` → 事务（锁项目行 → 按 `(projectId, createdById, dispatchRequestId)` 查重放 → `expectedRevision` CAS → 生成 `specificationSnapshot` + digest → 前驱依赖检查 → 在途 Invocation 扫描 → 写执行行）→ `submit` 调 `createCapturedApi(scope).start(intent.request)`，成功后把 `dispatchState` 从 `pending` CAS 成 `submitted`；回执经 `ProjectRuntimeObservationCommand` → `ProjectRuntimeObservationHandler` 投影。
- **事务-时序边界**：注释即契约——「Authorization precedes both reservation and idempotent replay.」「commit the attempt and pinned intent before invoking an adapter.」「Replays keep the original scope; unknown or missing receipts never permit another launch」；`invocationId = agentInvocationId(scope, 'project-task:<requestId>')`，重放**绝不新造 callId**；启动报错但已存在持久记录时返回该记录（「A launch failure can already have a durable unknown receipt. Return that handle, not a retry hint.」）。补偿扫描每 5 秒取 `dispatchState='pending' AND dispatchNextAttemptAt <= now` 前 20 条。
- **预期结果**：`runtimeTaskStatus` 只有三种自动映射 `succeeded→review`、`failed→blocked`、`running && progress.startedAt→in_progress`；仅在「该尝试是最新尝试 + 任务为非 provider 普通任务 + purpose 为 implementation + `projectedTaskRevision === task.revision` + 状态在 `todo/in_progress/review/blocked` 且规格 digest 未变」时用 CAS 推进，随后把 `projectedInvocationRevision` 推到 Invocation 的 revision。业务完成须 `ProjectTaskDecisionService.decide`：accept 时 CAS 成 `done` 并把决策 append 进 `decisions`，否则回 `todo`。
- **错误处理**：运行时错误码统一 `Scope→403`、`NotFound→404`、`Invalid→400`，**其余全部 409**（`Conflict`/`Busy`/`Dependencies`/`State`/`Owned`/`Evidence`/`DecisionRequired`）；前驱未全 `done|completed` → `Dependencies`；同项目存在未终结 Invocation → `Busy`；`dispatch_blocked` 为终态不再重试，`dispatch_unavailable` 60s 后重试。
- **真实代码示例**：
```ts
invocationId = agentInvocationId(scope, `project-task:${requestId}`)  // 重放不新造
dispatchState = 'pending'   // submit 成功后 CAS 成 'submitted'
// 执行行非持久化投影位：invocationStatus / runtimeStartedAt / runtimeCompletedAt
```
章节来源：[project-task-dispatch.service.ts](file://packages/server-ai/src/xpert-project/runtime/project-task-dispatch.service.ts)（关键符号：ProjectTaskDispatchService.dispatch / submit）、[project-runtime-observation.handler.ts](file://packages/server-ai/src/xpert-project/runtime/project-runtime-observation.handler.ts)（关键符号：runtimeTaskStatus）、[project-task-decision.service.ts](file://packages/server-ai/src/xpert-project/runtime/project-task-decision.service.ts)（关键符号：ProjectTaskDecisionService.decide）

## Recipe 6 计划族与执行位约束
- **业务目标**：维护 plan → milestone / plan → sprint → swimlane 四级结构，并用 `wipLimit`/`concurrencyLimit` 表达执行位约束。
- **调用顺序**：`GET/POST /:id/plans` → `PUT/DELETE /:id/plans/:planId` → 里程碑 `POST/PUT/DELETE /:id/plans/:planId/milestones[/:milestoneId]` → 冲刺 `GET/POST /:id/plans/:planId/sprints`、`PUT /:id/sprints/:sprintId` → 泳道 `GET/POST /:id/sprints/:sprintId/swimlanes`、`PUT /:id/sprints/:sprintId/swimlanes/:swimlaneId`；任意入口前若缺默认对象，由 `ensureDefaults(projectId)` 补「Default plan」与「Uncategorized」。
- **事务-时序边界**：四张表由 `XpertProjectPlanService` 统一维护，层级靠显式 FK（无 `@Tree`/闭包表）；`createSprint` 在**同一次调用内**按 `strategyType` 生成默认泳道，并把 `sourceStrategyType` 固化到每条泳道（`updateSprint` 禁改 `strategyType`）。
- **预期结果**：`software_delivery` → `planning/coding/review/release`；`data_analysis` → `research/analysis/visualization`；另加保留 `backlog` 泳道（`kind:'backlog'`、`concurrencyLimit:0`、`wipLimit:0`）。泳道字段承载调度语义：`priority`/`weight`/`concurrencyLimit`/`wipLimit`/`agentRole`/`environmentType`/`sourceStrategyType`；排序字段 `sortOrder`。simple 项目只允许默认计划与默认里程碑。
- **错误处理**：simple 模式加额外计划/里程碑/冲刺 → 400（`Sprints require advanced project mode`）；`createSwimlane` 拒绝 `key==='backlog'`；`updateSwimlane` 拒绝改 backlog 的 `key` 或把它升为 `execution`；计划/里程碑/冲刺/泳道状态均无代码内自动迁移，靠 API 直接赋值。
- **真实代码示例**：
```ts
defaultSwimlanes(strategyType) // backlog(kind:'backlog') + 按策略决定角色泳道，固化 sourceStrategyType
// 泳道空缺默认：concurrencyLimit=1 / wipLimit=0 / environmentType='browser' / agentRole='operator'
```

## Recipe 7 任务与会话链接
- **业务目标**：把任务与一个或多个会话按语义关系关联，供讨论、执行与复核回看，并避免重复行。
- **调用顺序**：`POST /:id/tasks/:taskId/conversations` → `XpertProjectTaskService.linkConversation`（先校验 `conversation.projectId === projectId`，再按四元组 `findOne` 幂等返回）；读回 `GET /:id/tasks/:taskId/relations`（`listTaskRelations`）；项目级会话反查用 `GET /:id/conversations`（`FindChatConversationQuery`）。
- **事务-时序边界**：`@Unique('UQ_project_task_conversation_relation', ['projectId','taskId','conversationId','relationType'])`；会话行由对话域持有，本域只写链接行。派发侧另有一条**弱引用**：执行行保存 `conversationId`（`onDelete: 'SET NULL'`）与 `threadId`——链接表管「任务讨论过哪些会话」，执行行管「这次执行发生在哪个线程」。
- **预期结果**：`relationType ∈ origin|discussion|execution|review`（默认 `discussion`），附 `isPrimary` / `sourceMessageId` / `sourceExecutionId`；重复链接不报错（幂等返回既有行）。注意 `xpert-task` 域反向持有 `ChatConversation.taskId`（同样 `SET NULL`），与本域链接表无关，不要混用两套关联。
- **错误处理**：会话不属于该项目 → 拒绝；关系类型超出四值 → 唯一约束/校验失败；`isPrimary` 不承担唯一约束，业务上需自行保证「一个任务最多一条主链接」。
- **真实代码示例**：
```ts
relationType ∈ { origin, discussion, execution, review }   // 默认 'discussion'
await this.linkConversation(projectId, taskId, conversationId, 'review' as TXpertProjectTaskConversationRelation)
```

## Recipe 8 建周期任务与生命周期
- **业务目标**：建一个可挂项目的定时 Xpert 任务，并走完 schedule → pause → archive → recover 生命周期且清楚哪些步骤会真正重建排程。
- **调用顺序**：`POST /api/xpert-task`（`CreateXpertTaskCommand` → 校验 run-as 必须为本人、Trial 角色上限 10、`agentKey` 合法 → 写 `schedule:null` + `status=SCHEDULED` → 入队 `xpert-task-scheduler`）→ `PUT /:id/schedule`（重解析项目当前助手版本 → 连接器预检 → `rescheduleTask` → `SCHEDULED` 且清 `statusReason`）→ `PUT /:id/pause` / `PUT /:id/archive`（先 `deleteJob` 再写状态）→ `PUT /:id/unarchive`（**落 `PAUSED` 且不排程**）→ `DELETE /:id/soft`（= `pause` + `softRemove`）、`PUT /:id/recover`（只软恢复、**不重建 job**）、`DELETE /:id`（202 硬删，先 `deleteJob` 再 `remove`）。
- **事务-时序边界**：`scheduleCronJob` 用 `CronJob.from({cronTime, timeZone})` + `schedulerRegistry.addCronJob(task.id)`；`SchedulerRegistry` 是**进程内内存**，重启/多副本各存一份。`onModuleInit` 启动期只重建 `status=SCHEDULED` 且 `options || schedule` 存在的任务。执行台账由 `ScheduledTaskExecutionCoordinator.claim(task, buildScheduleOccurrenceKey(task, scheduledAt), scheduledAt)` 承载（`insertIfAbsent` 用 `.orIgnore()`），租约 5 分钟。
- **预期结果**：创建时 `schedule` 被清空（注释「Clear schedule to avoid confusion」）；每次触发把幂等键写进 `runtimeState`（`resolveTaskRuntimeState` + `XPERT_TASK_SCHEDULE_IDEMPOTENCY_KEY`）；`uq_xpert_task_execution_occurrence(taskId, occurrenceKey)` 保证「同一时段至多一次执行」；执行时顺序为 `ChatConversationUpsertCommand` → `XpertAgentExecutionUpsertCommand` → `XpertChatCommand`。
- **错误处理**：`unarchive`、`recover` 之后不执行属**语义**（需再调 `PUT /:id/schedule`）；多副本各自重建同名 cron job，`SchedulerRegistry.getCronJob(taskId)` 只对本副本有效；`QueryXpertTaskHandler` 取不到本地 job 时把返回体 `status` 伪造成 `PAUSED`，与库内 `status` 可能不一致——排障以 DB `status` 与 `xpert_task_execution` 为准。
- **真实代码示例**：
```http
POST   /api/xpert-task                 # 创建：schedule=null, status=SCHEDULED
PUT    /api/xpert-task/<id>/schedule   # 重建排程（唯一真正排程的入口）
PUT    /api/xpert-task/<id>/pause  |  /archive  |  /unarchive
DELETE /api/xpert-task/<id>/soft   ;   PUT /api/xpert-task/<id>/recover
```
章节来源：[xpert-task.service.ts](file://packages/server-ai/src/xpert-task/xpert-task.service.ts)（关键符号：XpertTaskService.scheduleCronJob / onModuleInit / unarchive / softDeleteHttpTask）、[scheduled-task-execution.coordinator.ts](file://packages/server-ai/src/xpert-task/scheduled-task-execution.coordinator.ts)（关键符号：ScheduledTaskExecutionCoordinator.claim / buildScheduleOccurrenceKey）

## Recipe 9 自动任务、模板与便签
- **业务目标**：建仓储式自动任务、自动任务模板、任务模板与日程便签，并清楚扫描方与回写字段。
- **调用顺序**：自动任务 `GET/POST /auto-tasks`、`PUT/DELETE /auto-tasks/:id`；自动任务模板 `GET/POST /auto-task-templates`（内置约 18 条 seed、`builtin:true`）；任务模板 `GET/POST /templates`、`PUT/DELETE /templates/:id`（唯一键 `(source,tenantId,organizationId,createdById,key)`，`source` 区分内置与个人）；便签 `POST/PUT/DELETE /schedule/notes`，读 `GET /schedule/day/:date`、`GET /schedule/overview`；能力视图 `GET /schedule/capabilities/:xpertId`。
- **事务-时序边界**：自动任务由 `@Cron('0 * * * * *') runDueAutoTasks` 扫描，在 Redis 锁 `scheduler:xpert-auto-task`（TTL 5 分钟）下取 `enabled=true AND nextRunAt<=now` 的前 20 条；`executeAutoTask` 结束时算 `nextRunAt`，`frequency==='once'` 置 `enabled=false` 且 `nextRunAt=null`。周期性 XpertTask 则由进程内 cron 主调度，与自动任务扫描互不替代。


## Recipe 10 run-as 提案确认流
- **业务目标**：把定时任务的执行身份换成另一名项目成员，并保证「配置变更即作废授权」且只有被提名人本人能确认。
- **调用顺序**：`POST /:id/run-as/proposal`（`XpertTaskRunAsProposalDTO` + `createXpertTaskRunAsProposalValidationPipe`，`forbidNonWhitelisted`）→ `proposeProjectTaskRunAs`：要求任务有 `projectId` + `xpertId`；发起人若是当前 run-as 用户需 `assertCanUse`，否则需 `assertCanManage`（且目标必须 ≠ 当前 run-as）；校验目标用户为项目可用成员、连接器可用后，写 `pendingRunAsUserId` / `RequestedById` / `RequestedAt` 与 `pendingRunAsConfigurationHash = buildProjectTaskRunAsConfigurationHash(task)`（`xpertId` + 排序后的 connector 绑定集合的 sha256）。确认 `POST /:id/run-as/accept`（仅 `UUIDValidationPipe`）。
- **事务-时序边界**：接受时**只有被提名人本人**可通过（否则 403）；先重算 hash 比对（不一致 → `ProposalChanged`），再用 `update({id, pendingRunAsUserId: actorId, pendingRunAsConfigurationHash: hash}, ...)` 做条件更新，`affected !== 1` 再抛一次 `ProposalChanged`（两步确认 + CAS）；成功后若任务为 `SCHEDULED` 则 `rescheduleTask` 用新 run-as 用户重建 job。`update` 时 `invalidatePendingRunAsProposalForConfigurationChange` 比较哈希，配置变更即清空 pending 四列。
- **预期结果**：执行期身份统一取 `task.runAsUser ?? task.createdBy`；`XpertTask` **没有版本列**，因此该流程靠「配置 hash 条件更新」而非版本号，语义更弱。
- **错误处理**：无提案 400 `Error.ProjectTaskRunAsProposalMissing`；非本人 403 `Error.ProjectTaskRunAsProposalTargetOnly`；hash 变化或 CAS 未命中 400 `Error.ProjectTaskRunAsProposalChanged`；`createdAt` 等非法字段 → 400。
- **真实代码示例**：
```ts
pendingRunAsConfigurationHash = buildProjectTaskRunAsConfigurationHash(task)
await this.update({ id, pendingRunAsUserId: actorId, pendingRunAsConfigurationHash: hash })
// 条件更新未命中 ⇒ Error.ProjectTaskRunAsProposalChanged
```

## Recipe 11 排障入口合集
- **业务目标**：把五类高频症状落到唯一判据与处置动作上，避免按症状猜测。
- **调用顺序（排查链）**：
  1. **任务卡住（定时）**：查 `xpert_task_execution`（`status='running'` 且 `leaseExpiresAt < now()`）→ 下一分钟的 `@Cron('30 * * * * *')` 接管（`attempt+1`）；反复失败看 `lastError`/`failureCode`（类型**仅允许** `LOCAL_RUNTIME_UNAVAILABLE`）。
  2. **派发未回执**：看 `dispatchState` / `dispatchRequestId` / `invocationId` 与 `GET /:id/task-executions/:executionId/target`；有 `invocationId` 而无状态推进 ⇒ 问题在 Invocation/handoff 侧。`dispatchIntent` 为 `select:false`，人工**不得**从任务视图推断意图。
  3. **乐观锁 409**：`PUT /:id/task-graph` 与派发都要求 `expectedRevision`；`task.revision !== expectedRevision` → 409 `Conflict`。观察投影另有 CAS 兜底，拦「没有取项目锁的历史写入者」（源注释：「Some legacy task writers do not take the Project lock. CAS also fences their concurrent decisions.」）。
  4. **邀请失效**：400 `Error.ProjectInvitationInvalid`（非 pending 或已过期）/ 403 `Error.ProjectInvitationEmailMismatch` / 400 `Error.ProjectInvitationNotPending`；同步重试由 60s `@Interval` 驱动、退避上限 1h。
  5. **幂等键冲突**：同 `dispatchRequestId` 但 `input` / `caller` / `replyTo.threadId` / `target` 任一不一致 → 409 `Conflict`（**防护生效而非故障**）；决策 `requestId` 重复但 actor/内容不一致同样 409。
- **事务-时序边界**：项目行悲观锁是全域最粗的串行点（任务写、步骤写、批量更新、派发、决策、观察投影全部排队）；`ProjectTaskRuntimeReadService.get` 对每个带 `invocationId` 的执行逐条取 `AgentInvocationEntity`（N+1，仅用于单任务详情）。
- **预期结果 / 处置要点**：恢复软删任务后必须显式 `PUT /:id/schedule`；`DELETE /:id` 返回 400 说明仍有 `uploaded/scanning/parsing/processing/queued` 文件；升级后启动期 DI 报错优先怀疑 `forwardRef` 两端版本不一致（项目域与任务域需同批发布）。
- **错误处理**：`projectTaskRuntimeError(code)` 统一抛 `HttpException`，文案键为 `server-ai:Error.ProjectTaskRuntime<Code>`；旧版自动化端点返回 410 `GoneException`（预期行为，应改建定时 Xpert 任务）；`PUT /:id/workspace` 恒定 400（项目不再绑定 Workspace）。
- **真实代码示例**：
```http
GET  /api/xpert-project/<id>/task-executions/<executionId>/target
PUT  /api/xpert-project/<id>/task-graph   # 必须带 expectedRevision
PUT  /api/xpert-task/<id>/schedule        # 恢复/归档后的唯一排程入口
```
