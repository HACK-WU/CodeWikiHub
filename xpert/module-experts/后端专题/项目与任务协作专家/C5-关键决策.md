## D1 两套任务体系并存
- **分类**：架构设计
- **动机（避坑）**：现象——用项目内任务图（provider 快照 + `revision` CAS + Invocation 投影）承载周期调度，或用 `xpert_task`（cron + 租约）承载协作任务图；后果——状态机、可见性与权限口径互相污染，且「撤权/删除」的一致性只能靠事件最终送达。
- **决策**：保留两套模型并明确分工——`xpert_project_task` 面向「协作图与执行派发」，`xpert_task` 面向「周期调度与自动化」；两者只通过 `projectId` 外键与 `xpert-project.member-removed` / `xpert-project.xpert-removed` 两个事件耦合。
- **背景约束**：项目内任务有 `@VersionColumn revision`，`XpertTask` **完全没有版本列**，靠条件 UPDATE + 租约表达并发；任务域 6 张表仅 `XpertTask` 有软删。
- **被否决方案**：无（实现层未找到把两者合并的显式否决记录；边界是「分别优化协作图与周期调度两种场景」这一取舍的结果）。
- **重新评估触发条件**：出现跨域统一「任务」概念的硬需求（统一列表、统一权限、统一报表）时，须先收敛两套状态机与可见性口径，再做合并。
- **关联代码**：`file://packages/server-ai/src/xpert-project/entities/project-task.entity.ts`、`file://packages/server-ai/src/xpert-task/xpert-task.entity.ts`、`file://packages/server-ai/src/xpert-project/services/project-membership.service.ts`
- **证据来源**：实现层 [03-数据流转.md](file://.module-experts/后端专题/项目与任务协作专家/implementation/03-数据流转.md)「已知风险」1——「两套任务模型并存……同一『项目任务』概念在两侧状态机、可见性与权限口径完全不同，容易串写」；[02-实现.md](file://.module-experts/后端专题/项目与任务协作专家/implementation/02-实现.md)「设计维度分析」——「两套任务模型……分别优化了『协作图』与『周期调度』两种场景，边界清晰、互不污染」。
章节来源：[project-task.entity.ts](file://packages/server-ai/src/xpert-project/entities/project-task.entity.ts)（关键符号：XpertProjectTask.revision）、[xpert-task.entity.ts](file://packages/server-ai/src/xpert-task/xpert-task.entity.ts)（关键符号：XpertTask 无版本列）

## D2 四层准入设计
- **分类**：安全合规
- **动机（避坑）**：现象——控制器类级挂 `@Public()` 后误以为「已放行」，或只在类级布防而忽略方法级与 `:id` 缺失场景；后果——越权读写项目数据，或反过来把合法调用全部 403。
- **决策**：`@Public()` 只跳过全局 JWT 守卫；真正准入由 `@UseGuards(XpertProjectAuthGuard, XpertProjectFeatureGuard, XpertProjectPermissionGuard)` + `@ProjectPermission(XPERT_PROJECT_VIEW)` 提供，方法级再叠加 `XpertProjectGuard`/`XpertProjectOwnerGuard`；授权唯一业务入口是 `XpertProjectAccessService.resolveAccess/assertCanRead/assertCanUse/assertCanEdit/assertCanManage/assertCanPurge`，插件/运行时侧走 `ProjectAccessRuntimeService`。
- **背景约束**：`XpertProjectPermissionGuard` 在无 `:id` 参数时退化为 `RequestContext.hasPermissions`；`XpertProjectFeatureGuard` 在 feature 未 seed 时**放行**；`XpertProjectAuthGuard` 拒绝 `client_secret` 且非 `USER_XPERT` 绑定的主体；邀请与 `xpert-task` 共 37 条端点**无项目守卫**，全靠服务层断言——绕过 service 直查仓库即越权。
- **被否决方案**：无。
- **重新评估触发条件**：新增非 HTTP 调用面（插件、运行时、后台）时，必须经 `ProjectAccessRuntimeService` 而非自建判定；若收紧「feature 未 seed 即放行」，需同步复核全部类级端点。
- **关联代码**：`file://packages/server-ai/src/xpert-project/project.controller.ts`、`file://packages/server-ai/src/xpert-project/guards/project-permission.guard.ts`、`file://packages/server-ai/src/xpert-project/services/project-access-runtime.service.ts`
- **证据来源**：源码 `project.controller.ts` 类级装饰器逐字：`@Public()` + `@UseGuards(XpertProjectAuthGuard, XpertProjectFeatureGuard, XpertProjectPermissionGuard)` + `@ProjectPermission(AIPermissionsEnum.XPERT_PROJECT_VIEW)`；实现层 [01-架构.md](file://.module-experts/后端专题/项目与任务协作专家/implementation/01-架构.md)「关键不变量」1——「控制器类级 `@Public()` 是『跳过全局 JWT 守卫』而非放行」。
章节来源：[project.controller.ts](file://packages/server-ai/src/xpert-project/project.controller.ts)（关键符号：XpertProjectController 类级装饰器）、[project-permission.guard.ts](file://packages/server-ai/src/xpert-project/guards/project-permission.guard.ts)（关键符号：XpertProjectPermissionGuard.canActivate）、[project-access-runtime.service.ts](file://packages/server-ai/src/xpert-project/services/project-access-runtime.service.ts)（关键符号：listReadable / assertManage / assertEdit）

## D3 任务执行走派发账本
- **分类**：架构设计
- **动机（避坑）**：现象——先启动 Invocation 再落库，或在本域再造一份运行时账本、把派发意图/凭据序列化给任务视图；后果——崩溃后产生孤儿执行与重复启动，且凭据、路由与配置泄漏到读模型。
- **决策**：执行只走 `xpert_project_task_execution` 这一条派发账本——三个唯一索引（`invocationId`、`(projectId,createdById,dispatchRequestId)`、`(taskId,sourceKey)`）+ `dispatchState ∈ pending|submitted`；先固化意图再启动（「commit the attempt and pinned intent before invoking an adapter.」）；`dispatchIntent` 为 `select:false` 的服务端恢复意图；运行时状态一律读投影，不落第二账本。
- **背景约束**：`invocationId` 由 `agentInvocationId(scope, 'project-task:<requestId>')` 预先确定，重放绝不新造 callId；「Replays keep the original scope; unknown or missing receipts never permit another launch」；启动失败但已存在持久记录时返回该记录（「A launch failure can already have a durable unknown receipt. Return that handle, not a retry hint.」）；补偿器 `@Interval(5000)` 只重放 pin 住的意图。
- **被否决方案**：在本域再建一份运行时账本（注释逐字：「Read projection from the associated Invocation, never a second runtime ledger.」）；把 `dispatchIntent` 序列化到任务视图（注释逐字：「Server-only recovery intent; never serialize credentials, routing or configuration to task views.」）。
- **重新评估触发条件**：`dispatchIntent` 的 `select:false` 与补偿扫描强耦合——一旦引入备份/数据修复脚本或更换存储，必须先保证恢复链显式 `addSelect`，否则 intent 解析失败直接归类 `Invalid`。
- **关联代码**：`file://packages/server-ai/src/xpert-project/runtime/project-task-dispatch.service.ts`、`file://packages/server-ai/src/xpert-project/entities/project-task-execution.entity.ts`、`file://packages/server-ai/src/xpert-project/runtime/project-task-dispatch-recovery.service.ts`
- **证据来源**：源码 `project-task-dispatch.service.ts` 不变量注释逐字：「commit the attempt and pinned intent before invoking an adapter.」「Replays keep the original scope; unknown or missing receipts never permit another launch.」；实现层 [02-实现.md](file://.module-experts/后端专题/项目与任务协作专家/implementation/02-实现.md)「执行派发与回执」6 步顺序。
章节来源：[project-task-dispatch.service.ts](file://packages/server-ai/src/xpert-project/runtime/project-task-dispatch.service.ts)（关键符号：dispatch / submit / intent）、[project-task-execution.entity.ts](file://packages/server-ai/src/xpert-project/entities/project-task-execution.entity.ts)（关键符号：dispatchIntent / IDX_project_task_execution_dispatch）

## D4 幂等键 (projectId, providerKey, sourceKey)
- **分类**：接口契约
- **动机（避坑）**：现象——provider 侧快照每次同步都新建任务行，或允许通用写路径提供 provider 身份列；后果——同一来源任务重复落库、依赖边(child/predecessor)指向两张行、图不可重放。
- **决策**：`xpert_project_task` 上以 `@Index(['projectId','providerKey','sourceKey'], { unique: true })` 作为「同一 provider 同一来源键只允许一行」的硬约束；provider 投影任务 id 由 `projectTaskIdentity(projectId, provider, key)` 的 **sha256 派生稳定 UUID**，使跨次快照 id 稳定、图可重放。
- **背景约束**：provider/投影列由 `assertOrdinaryTaskInput` 从通用写路径中逐列拦下（违者抛 `Owned`）；`sourceKey`/`providerKey`/`sourceRevision` 是 provider 侧来源身份；执行行另有 `(taskId, sourceKey)` 唯一索引，形成「任务一次来源一行尝试」的第二重约束。
- **被否决方案**：允许通用写路径（`PUT /:id/tasks/:taskId`）提供 `providerKey`/`sourceKey`/`sourceRevision`/`revision` 等 13 个列——被 `assertOrdinaryTaskInput` 明确拒绝。
- **重新评估触发条件**：provider 契约变化（同一 provider 需要多来源键、或同一来源键需并行多行）时；届时须同步 `projectTaskIdentity` 与两个唯一索引。
- **关联代码**：`file://packages/server-ai/src/xpert-project/entities/project-task.entity.ts`、`file://packages/server-ai/src/xpert-project/services/project-task-graph.service.ts`、`file://packages/server-ai/src/xpert-project/services/project-task-ownership.ts`
- **证据来源**：实现层 [04-模型.md](file://.module-experts/后端专题/项目与任务协作专家/implementation/04-模型.md)「校验规则」——「`xpert_project_task(projectId,providerKey,sourceKey)`」；[03-数据流转.md](file://.module-experts/后端专题/项目与任务协作专家/implementation/03-数据流转.md)「链路四」——「provider 投影任务 id 由 `projectTaskIdentity(...)` 的 sha256 **派生为稳定 UUID**」。

## D5 projectTypeSnapshot 创建时固化
- **分类**：兼容处理
- **动机（避坑）**：现象——项目只存类型 key，类型/插件下线后历史项目无法解释「当初是什么类型」，或反过来用快照去「复活」一个已不可用的类型；后果——历史项目不可读，或对已下线应用放行执行。
- **决策**：创建瞬间由 `classification(ref)` 固化 `applicationKey` / `projectTypeKey` / `applicationInstallationId` / `projectTypeSnapshot`（含 `applicationTitle`、`title`、`binding`）；快照**只用于展示与兼容判定**，可用性一律以 `resolve()` 对「当前已加载插件」重解析为准。
- **背景约束**：`binding` 为 `entity` 的类型不允许普通创建（抛 `ProjectApplicationWorkflowRequired`）；迁移 `20260920-project-types.sql` 的 `CK_project_type_identity` 要求两个类型键同为 NULL 或同非空且非空串；插件幂等路径 `ensureManagedProject` 只做「不重新分类」的校验。
- **被否决方案**：用 `projectTypeSnapshot` 复原一个已下线的类型（实现层明写 `resolve()` 只接受「当前已加载插件目录里的活体类型，快照不能复原一个已下线的类型」）。
- **重新评估触发条件**：插件目录/类型下线策略变化，或需要按历史快照回放执行语义时——届时须先在 `resolve()` 侧定义「快照可授权」的边界，不能只在读侧放开。
- **关联代码**：`file://packages/server-ai/src/xpert-project/services/project-type.service.ts`、`file://packages/server-ai/src/xpert-project/services/project-creation.ts`、`file://packages/server-ai/src/xpert-project/entities/project.entity.ts`

Plugin providers verify persisted business links; **display snapshots never authorize app execution.**」；实现层 [02-实现.md](file://.module-experts/后端专题/项目与任务协作专家/implementation/02-实现.md)「项目创建链」。

## D6 乐观锁只落在任务表一处
- **分类**：性能取舍
- **动机（避坑）**：现象——既有的投影与决策写者与历史写者并发改同一任务行；后果——旧快照/旧观察覆盖新事实，状态被静默回退。
- **决策**：并发控制分两层——**项目行悲观锁**（`lockProject`，`pessimistic_write`）做全域串行化，**任务 `@VersionColumn revision` CAS** 做行级兜底；观察投影与决策提交都带 `revision` 条件。全批只有 `xpert_project_task` 一处有版本列。
- **背景约束**：项目行锁是全域名最粗的一把锁（任务写、步骤写、批量更新、派发、决策、观察投影全部排队），热点项目会成为单点；`project-task-graph.service.ts` 注释「Serialize snapshot acquisition too: an older snapshot cannot overwrite a newer one.」；`project-runtime-observation.handler.ts` 明写「Some legacy task writers do not take the Project lock. CAS also fences their concurrent decisions.」。
- **被否决方案**：无（`XpertTask` 不加版本列是现状而非否决记录；其 run-as 接受改用「配置 hash 条件更新」，语义更弱）。
- **重新评估触发条件**：`XpertTask` 也需要版本语义时（当前 run-as 靠 hash 条件更新）；或出现更多绕过项目锁的写者时（CAS 覆盖面需扩大）。
- **关联代码**：`file://packages/server-ai/src/xpert-project/entities/project-task.entity.ts`、`file://packages/server-ai/src/xpert-project/services/project-task.service.ts`、`file://packages/server-ai/src/xpert-project/runtime/project-runtime-observation.handler.ts`
- **证据来源**：源码 `project-task-graph.service.ts` 注释逐字：「Serialize snapshot acquisition too: an older snapshot cannot overwrite a newer one.」；`project-runtime-observation.handler.ts` 注释逐字：「Some legacy task writers do not take the Project lock. CAS also fences their concurrent decisions.」
章节来源：[project-task.entity.ts](file://packages/server-ai/src/xpert-project/entities/project-task.entity.ts)（关键符号：@VersionColumn revision）、[project-task.service.ts](file://packages/server-ai/src/xpert-project/services/project-task.service.ts)（关键符号：lockProject / assertBusinessStatus）

## D7 任务与会话多关系类型
- **分类**：接口契约
- **动机（避坑）**：现象——把「任务的首发会话」与「执行派生的会话」「复核会话」混为一条链接，用「查重即跳过」处理；后果——派生线程被误判为重复链接而丢失，任务关系图不完整。
- **决策**：用四元组唯一键 `@Unique(projectId,taskId,conversationId,relationType)` 承载四种关系 `origin|discussion|execution|review`（默认 `discussion`），`linkConversation` 先校验 `conversation.projectId === projectId` 再按四元组 `findOne` 幂等返回。
- **背景约束**：会话行由对话域持有，本域只写链接表；派发侧另有弱引用 `xpert_project_task_execution.conversationId`（`onDelete: 'SET NULL'`）与 `threadId`，两者语义不同（链接表管「讨论过哪些会话」，执行行管「这次执行发生在哪个线程」）；`xpert-task` 域反向持有 `ChatConversation.taskId`，与本域链接表无关，**不要混用两套关联**。
- **被否决方案**：无。
- **重新评估触发条件**：新增关系类型，或需要跨项目复用一个会话时——四值枚举与四元组唯一键都需同步演进。

## D9 forwardRef 显式双向依赖
- **分类**：技术选型
- **动机（避坑）**：现象——两个模块互相需要对方的 provider 却又互相 import；后果——Nest 装配期 DI 解析失败（启动直接报错），或事件监听注册缺失导致撤权静默失效。
- **决策**：用 `forwardRef` 把环显式化——`xpert-task.module.ts` 用 `forwardRef(() => XpertProjectModule)`；`project.module.ts` 反向 `forFeature` 引入 `XpertTask` 实体并以 `forwardRef(() => XpertModule/XpertAgentModule/SkillRepositoryModule)` 打破环；跨模块**读**依赖 `XpertProjectAccessModule` 这一薄模块，避免把主模块的装配环放大到 sandbox/对话/文件域。
- **背景约束**：部署含义是两侧必须**同批发布**——旧的 `XpertProjectModule` 与新 `XpertTaskModule` 混跑时，`forwardRef` 解析到的 provider 集合可能缺项；滚动升级建议按「先项目域、后任务域」的同批窗口完成。
- **被否决方案**：无。
- **重新评估触发条件**：拆分模块边界时（例如把 `xpert-task` 对项目的耦合抽成薄模块/独立 command 面），应优先消除环而不是加成更多 `forwardRef`。
- **关联代码**：`file://packages/server-ai/src/xpert-task/xpert-task.module.ts`、`file://packages/server-ai/src/xpert-project/project.module.ts`、`file://packages/server-ai/src/xpert-project/project-access.module.ts`
- **证据来源**：实现层 [07-运维.md](file://.module-experts/后端专题/项目与任务协作专家/implementation/07-运维.md)「跨域依赖与循环引用」——「部署含义：**这两侧必须同批发布**……混合版本时 `forwardRef` 解析到的 provider 集合可能缺项」。

## D10 @OnEvent 作为唯一撤权通道
- **分类**：架构设计
- **动机（避坑）**：现象——项目侧直接删除 `XpertTask` 的内存 cron job；后果——job 注册表在持有方进程内，项目侧无法安全触及，撤权要么失效要么产生跨进程误删。
- **决策**：撤权走「本域先落库、再广播」两段——`XpertProjectMembershipService.remove` 先批量 `pause` 该用户的 `XpertTask`（覆盖 `runAsUserId=userId` 与 `runAsUserId IS NULL AND createdById=userId` 两种归因），再 `emitAsync('xpert-project.member-removed', …)`；`XpertTaskService.pauseProjectTasksForRemovedMember` / `pauseProjectTasksForRemovedXpert` 消费并同步删除内存 cron job；两处都**跳过 `ARCHIVED`**，避免复活已归档任务。
- **背景约束**：事件是跨域撤权的**唯一**通道（`@OnEvent('xpert-project.member-removed')` / `@OnEvent('xpert-project.xpert-removed')`）；撤权/删除的一致性依赖「事件最终送达 + 各侧幂等」，而 `forwardRef` 混版本部署下监听可能缺失。
- **被否决方案**：无。
- **重新评估触发条件**：观测到「事件未生效」（监听端无日志、撤权后任务仍排程）时，通常意味着 `forwardRef` 解析异常或混合版本部署——此时应改为事务内直写 + 补偿扫描，而不是加更多监听。
- **关联代码**：`file://packages/server-ai/src/xpert-project/services/project-membership.service.ts`、`file://packages/server-ai/src/xpert-task/xpert-task.service.ts`
- **证据来源**：源码 `project-membership.service.ts` 逐字：`this.taskRepository.update({ projectId, runAsUserId: userId }, pausedTaskState)` 与 `this.eventEmitter.emitAsync('xpert-project.member-removed', …)`；`xpert-task.service.ts` 逐字：`@OnEvent('xpert-project.member-removed')` / `@OnEvent('xpert-project.xpert-removed')`。

## D11 自动化下线与替代路径
- **分类**：技术选型
- **动机（避坑）**：现象——旧版项目自动化保留写路径与事件触发，而 `triggerEvent` 已不产生任何执行；后果——用户以为自动化生效却静默空转（`triggerEvent()` 返回 `[]`），或出现「两个排程入口」争夺同一项目工作。

## D12 单向投影与显式验收决策
- **分类**：架构设计
- **动机（避坑）**：现象——把 Runtime 运行成功、或「所有步骤都 done」当作业务完成；后果——未经验收的实现被标记为完成，且被旧观察覆盖（陈旧尝试推进新任务）。
- **决策**：运行时事实只允许**单向投影**为三种状态（`succeeded→review`、`failed→blocked`、`running && progress.startedAt→in_progress`），且必须同时满足「该尝试是最新尝试 + 任务为非 provider 普通任务 + purpose 为 implementation + `projectedTaskRevision === task.revision` + 状态在 `todo/in_progress/review/blocked` + 规格 digest 未变」才用 CAS 提交；业务完成必须由 `ProjectTaskDecisionService.decide` 显式决定（accept → `done`，否则回 `todo`），决策与状态变更在同一事务提交、`requestId` 幂等。
- **背景约束**：`projectedInvocationRevision` 用于「旧观察不得覆盖新事实」的比较；`assertBusinessStatus` 在已有 `invocationId` 执行行时拒绝通用写 `done`/`completed`（抛 `DecisionRequired`）；步骤隐式完成仅在「无带 `invocationId` 的执行且全部步骤 done」时成立。
- **被否决方案**：由 Runtime 成功或步骤全完成直接判定业务完成——插件 README 逐字否决：「Runtime success does not automatically complete a business task, and finishing every step does not automatically accept a task with an existing Runtime attempt.」
- **重新评估触发条件**：需要自动验收（例如纯静态任务）时，必须显式新增判定路径与证据校验，**不得**放宽 `runtimeTaskStatus` 的三映射或让它直接产出 `done`。
- **关联代码**：`file://packages/server-ai/src/xpert-project/runtime/project-runtime-observation.handler.ts`、`file://packages/server-ai/src/xpert-project/runtime/project-task-decision.service.ts`、`file://packages/server-ai/src/xpert-project/services/project-task.service.ts`
- **证据来源**：插件 README 逐字：「Automatic task updates require the latest implementation attempt, unchanged requirements, and the expected task revision. Actual execution maps to `in_progress`, success to `review`, and failure to `blocked`.」「The Runtime reports execution facts only.」「Ordinary update tools cannot mark a task with Runtime attempts as complete.」
