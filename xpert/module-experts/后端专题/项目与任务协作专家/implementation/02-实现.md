## 项目创建链
普通 HTTP 路径：`XpertProjectController.create` 先剥掉 `toolsetIds`/`knowledgebaseIds`（`void toolsetIds`，payload 注释明写「Deprecated direct capability selections are intentionally ignored.」），再调 `XpertProjectService.createProject`。后者把 `xpertIds` 去重后逐个 `resolveAccessibleCurrentXpert`，合并 `XpertProjectTypeService.forCreate(input.projectType ?? GENERAL_PROJECT_TYPE)` 的结果，交给 `createWithInitialAssistants`。
`forCreate` → `resolve(ref)`（只接受当前已加载插件目录里的活体类型，快照不能复原一个已下线的类型）→ `classification(ref)`：解析 `applicationKey`/`projectTypeKey`、按 `pluginName + appName` 反查 `PluginApplicationInstallation` 得到 `applicationInstallationId`，并固化 `projectTypeSnapshot = {applicationTitle, title, binding}`。binding 为 `entity` 的类型不允许普通创建（抛 `ProjectApplicationWorkflowRequired`）。
落库由 `createProjectWithAssistants` 完成：先 `bindings.resolveInitialMembers(roots, scope)` 得到规范化后的助手集合；无 `entity.id` 时走 `store.create`（`super.create` + `xperts` 关系）再 `store.initialize`（内容初始化）；有 `entity.id` 时在事务内 `insert` + `queryBuilder().relation(XpertProject,'xperts').add(...)`，冲突码 `23505` 转为类型冲突错误。之后控制器补 `planService.ensureDefaults`（默认计划 + 未分类里程碑）与 `activityService.record({type:'project.created'})`。
插件 / 业务侧（幂等）路径：`ProjectEnsureCommand` → `EnsureXpertProjectHandler` → `XpertProjectService.ensureManagedProject` → `ensureManagedProject(store, input)`，查项目时把 `tenantId`/`organizationId` 一起放进 where（注释：「retries cannot adopt a same-id Project from a different security boundary」），`types.forEnsure` 只做「不重新分类」的校验，已存在项目只回写元数据（显式解构丢掉 `xperts` 关系快照，避免把并发移除的助手复活）。

## 成员与邀请
成员：`XpertProjectMembershipService.add(projectId, userId, role)` —— 先 `assertCanManage`，再校验 `role` 白名单、拒绝把 owner 当普通成员添加、要求目标用户是「同租户 USER 且在同组织的 active 成员」；然后 `findOne({withDeleted:true})`，命中软删记录先 `restore` 再复用同一行（`joinedAt` 重置、`removedAt`/`deletedAt` 清空），最后 `addLegacyMember` 写兼容关系。`list` 把 owner 与 memberships 合并成 `TXpertProjectMemberSummary`（owner 恒为 `projectRole:'owner'`）。
移除：`remove` 禁止移除 owner（要求先转移），置 `removedAt` + `softRemove`，随后**先批量把该用户的 `XpertTask` 置 `PAUSED`**（含 `runAsUserId=userId` 与 `runAsUserId IS NULL AND createdById=userId` 两种归因），再 `emitAsync('xpert-project.member-removed', {...})`，让持有内存 cron job 的一侧自行清理。`replaceMembers` 是旧 `PUT members` 端点的兼容桥，`syncLegacyMembership` 用于历史补偿。
邀请：token 驱动。`XpertProjectInvitationService.invite` 要求 `assertCanManage` + 组织级 `ORG_INVITE_EDIT` 权限 + 项目必须有 Organization；邮箱经 `normalizeProjectInvitationEmail` 归一，`randomBytes(32).toString('base64url')` 生成明文 token、只落 `tokenHash`（列 `select:false`），过期时间取组织的 `inviteExpiryPeriod`（缺省 14 天）；同项目同邮箱已有 pending 邀请时**复用同一行**并轮换 hash（部分唯一索引 `IDX_xpert_project_invitation_pending` 保证「同项目同邮箱至多一条 pending」）。接受/拒绝由 `XpertProjectInvitationController` 暴露（仅 `@ApiBearerAuth`，无项目守卫，靠服务层校验 token 与登录态），成功后被 `XpertProjectMembershipService` 落成正式成员；表内保留 `legacyMembershipSync*` 补偿列，配合 `@Interval(60_000)` 的补偿同步与最长 1 小时退避。
章节来源：[project-membership.service.ts](file://packages/server-ai/src/xpert-project/services/project-membership.service.ts)（关键符号：XpertProjectMembershipService.remove）、[project-invitation.service.ts](file://packages/server-ai/src/xpert-project/services/project-invitation.service.ts)（关键符号：XpertProjectInvitationService.invite）
## 项目资源挂载
项目侧的「资源」是三组不同的东西，不能混谈：① **助手**（M2M `xpert_project_xpert`）：`addXpert` 要求助手与项目同组织，`XpertProjectXpertBindingService.normalize` 把历史版本快照替换为「当前版本」，`contains` 按 `isSameXpertFamily` 判断家族成员，因而加同一家族的新版本不会重复挂载；`getXperts` 读侧也先 `normalize`。② **工具集 / 知识库**（M2M `xpert_project_toolset` / `xpert_project_knowledgebase`）：由 `PUT/DELETE :id/toolsets/:toolset`、`PUT/DELETE :id/knowledges/:kb` 维护，但**创建时不允许直选**，因此新建项目时这两个集合恒为空。③ **附件与文件**：`attachments` M2M 走 `addAttachments`；项目卷内容（`project.md`、`skills/`）由 `XpertProjectContentService.initialize` 建立、`updateInstructions`/`listSkills`/`installSkill` 维护，`isGovernedPath` 标记受管路径；项目资产索引（`xpert_project_asset`，`unique(projectId,path)`）由 `XpertProjectAssetService` 维护，删除前必须确认关联文件不在 `uploaded/scanning/parsing/processing/queued` 状态（`XpertProjectPurgeService.purge` 会以此 400 拦截）。
会话首发场景另有一条「资源卡」通道：`ProjectResourceCardService.attach` 在事务内锁项目行、锁首条 AI 回复消息行，把 `settings.conversationBootstrap.resourceCards` 写进该消息内容并记录 `resourceCardMessageId`，保证「回执与其首条回复原子认领、重放不能重新分配」。
章节来源：[project.service.ts](file://packages/server-ai/src/xpert-project/project.service.ts)（关键符号：XpertProjectService.addXpert）、[project-xpert-binding.service.ts](file://packages/server-ai/src/xpert-project/services/project-xpert-binding.service.ts)（关键符号：XpertProjectXpertBindingService.normalize）、[project-resource-card.service.ts](file://packages/server-ai/src/xpert-project/services/project-resource-card.service.ts)（关键符号：ProjectResourceCardService.attach）

## 项目内任务图
创建与更新：控制器端点（`POST :id/tasks`、`PUT :id/tasks/:taskId`…）最终进 `XpertProjectTaskService`。`createTask` 先 `validateTaskMode`（simple 模式只允许固定泳道状态集）、再用 `resolveAssigneeXpertId` 强制「执行助手必须是项目成员」，然后走 `saveAll`。`saveAll` / `updateTask` / `updateTaskSteps` / `batchUpdate` 的共同骨架是：`assertOrdinaryTaskInput`（禁止外部写入 `providerKey`/`revision`/`predecessorIds`/`decisions` 等 provider 与投影字段）→ 事务内 `lockProject`（项目行 `pessimistic_write`，全域名串行化）→ `assertOrdinaryTask`（provider 任务不接受通用写）→ `assertBusinessStatus`（在已有 Invocation 执行的情况下禁止直接写 `done`/`completed`，抛 `DecisionRequired`）→ 保存。
步骤与日志：步骤用 `updateTaskSteps` 按 `stepIndex` 就地合并（`notes` 追加而非覆盖），当且仅当该任务**没有带 `invocationId` 的执行**且所有步骤 `done` 时，才把任务隐式推进为 `done`；步骤日志走 `xpert_project_task_log`（`stepId` 级联）。`reorder` 只改 `order`/`column`。
依赖与图变更：`predecessorIds` 是 `xpert_project_task` 上的 json 列，通用写入被 `assertOrdinaryTaskInput` 挡掉，只能经 `PUT :id/task-graph`（`ProjectTaskGraphController.change` → `ProjectTaskGraphService.change`，DTO 由 `projectTaskPlanSchema` + `expectedRevision` 校验）；读侧 `GET :id/task-graph` 返回 `ProjectTaskGraph`，其节点 id 由 `projectTaskIdentity(projectId, providerKey, key)` 以 sha256 派生，保证跨次快照稳定，且 `graph` 会调各 provider 的 `snapshot(context)` 并做诊断收集。执行侧还额外校验依赖：`ProjectTaskDispatchService.dispatch` 要求全部前驱状态属于 `done|completed`，否则 `Dependencies`。
章节来源：[project-task.service.ts](file://packages/server-ai/src/xpert-project/services/project-task.service.ts)（关键符号：XpertProjectTaskService.saveAll）、[project-task-graph.service.ts](file://packages/server-ai/src/xpert-project/services/project-task-graph.service.ts)（关键符号：ProjectTaskGraphService.change）、[project-task-ownership.ts](file://packages/server-ai/src/xpert-project/services/project-task-ownership.ts)（关键符号：assertOrdinaryTaskInput）
## 执行派发与回执
派发入口是命令，不是控制器：`DispatchProjectTaskCommand` → `DispatchProjectTaskHandler` → `ProjectTaskDispatchService.dispatch`。关键顺序（源文件注释即契约：「Authorization precedes both reservation and idempotent replay.」「commit the attempt and pinned intent before invoking an adapter.」）：
1. `projectTaskDispatchInputSchema` 校验 + `target`/`delivery` 互斥；`ProjectTaskRuntimeContextService.resolve` 把 caller 还原成 `AgentInvocationScope`（校验会话、线程、执行行、助手与项目关系，群运行时还要走 `AuthorizeGroupTaskCallerCommand`）。
2. 目标解析：`factory.resolveGroupTarget(scope, participantId)` 或 `resolveBackgroundTarget(scope, bindingId)`；`review` 用途强制 evidence-only（provider 必须 `opencode` 且执行环境为 `computer`）。
3. 事务：锁项目行（归档即 `Scope` 拒）→ 按 `(projectId, createdById, dispatchRequestId)` 查重放（命中则比对 intent/scope/replyTo/target，一致即返回原执行行，不一致 `Conflict`）→ 校验 `task.revision === input.expectedRevision` 与任务状态集、`assigneeXpertId === target.reference` → 生成 `specificationSnapshot`（标题/描述/requirements/步骤摘要 + digest）→ 检查前驱依赖 → 遍历同项目全部尝试，只要有未终结的 Invocation 即 `Busy` → 写执行行：`invocationId = agentInvocationId(scope, 'project-task:<requestId>')`、`dispatchState='pending'`、`projectedTaskRevision=task.revision`、`attempt=上一尝试+1`、`dispatchIntent=完整意图（含 prompt 与 replyTo）`。
4. `submit`：重放已保存意图也算「Invocation 预留前崩溃的恢复」，**绝不新造 callId**；若已有同 id Invocation 且未在 `queued`，先比对当前任务规格 digest 是否与意图一致（不一致 `Conflict`），再 `factory.createCapturedApi(scope).start(intent.request)`；启动报错时若已存在「同 request/scope 的持久记录」则返回该记录（注释：「A launch failure can already have a durable unknown receipt. Return that handle, not a retry hint.」），否则抛原错；成功后把 `dispatchState` 从 `pending` CAS 成 `submitted`。
5. 回执投影：`ProjectRuntimeObservationHandler`（消费 handoff 的 `ProjectRuntimeObservationCommand`）在项目行锁内取执行行与最新尝试，`runtimeTaskStatus` 给出唯一三种自动映射 `succeeded→review`、`failed→blocked`、`running && progress.startedAt→in_progress`；只有「该尝试是最新尝试 + 任务为非 provider 的普通任务 + purpose 为 implementation + `projectedTaskRevision === task.revision` + 状态在 `todo/in_progress/review/blocked` 且规格 digest 未变」时才用 CAS（`revision` 为条件）推进状态；随后把 `projectedInvocationRevision` 推到 Invocation 的 revision。业务验收另由 `ProjectTaskDecisionService.decide` 完成（`assertCanEdit` + 项目行锁 + `expectedRevision` + 决策幂等 `requestId` + review 执行与 evidence 校验），accept 时任务 CAS 成 `done` 并把决策 append 进 `decisions`。
6. 派发补偿：`ProjectTaskDispatchRecoveryService` 每 5 秒扫 `dispatchState='pending' AND dispatchNextAttemptAt <= now` 的前 20 条，先用条件 UPDATE 抢（把下次时间推到 60s 后），再以 `RuntimeMessageAccessService.withActor(intent.scope, ...)` 重放 `dispatch`；错误被分类为 `dispatch_blocked`（终态、不再重试）或 `dispatch_unavailable`（60s 后重试）。
配套约束：执行行上 `invocationStatus`/`runtimeStartedAt`/`runtimeCompletedAt` 是**非持久化读投影**；`assertNativeExecutionInput` 禁止 HTTP 侧写 `invocationId`/`dispatchState`/`specificationSnapshot`/`purpose`；`claimExecution` 只认「`status='queued' AND invocationId IS NULL` 且任务无 `providerKey`」的本机执行行。

## xpert-task 独立任务链
**任务 CRUD 与 HTTP 边界**：`XpertTaskController`（`@Controller()` 空前缀 + `RouterModule` 给 `/api/xpert-task`）继承 `CrudController`，35 条端点全部转调 `XpertTaskService` 的 `*HttpTask` 方法（`updateHttpTask`/`scheduleHttpTask`/`pauseHttpTask`/`archiveHttpTask`/`unarchiveHttpTask`/`testHttpTask`/`deleteHttpTask`/`softDeleteHttpTask`/`recoverHttpTask`）。读侧有两套可见性：HTTP 走 `findHttpAccessible`/`findHttpAccessibleById`（做项目成员校验），内部调度器仍用 `findAll`/`findOne`（源文件注释逐字：「HTTP-only query boundary. Internal schedulers deliberately continue to use findAll/findOne so background recovery is not evaluated as the HTTP actor.」）。
**创建**：`CreateXpertTaskCommand` → `CreateXpertTaskHandler`，依次校验 run-as 必须为本人、Trial 角色任务上限 10、`agentKey` 合法性，随后写 `schedule:null` + `status=SCHEDULED`（注释「Clear schedule to avoid confusion」）并入队 `scheduler.add({taskId})`。
**调度（三套并存）**：① Bull 队列 `xpert-task-scheduler`：`TaskSchedulerProcessor`（`@Process({concurrency:5})`）消费后调 `service.schedule(taskId)`；`@Inject(JOB_REF) jobRef` 注入后从未使用（技术债）。② 进程内 cron（主调度）：`scheduleCronJob` 用 `CronJob.from({cronTime, timeZone})` + `schedulerRegistry.addCronJob(task.id, job)`，`frequency===Once` 时设 `runOnce`；`onModuleInit` 在启动期对 `status=SCHEDULED` 且 `options||schedule` 的任务重建 job（`getActiveJobs`）。③ `@Cron` 扫描：`@Cron('30 * * * * *') recoverExpiredScheduledTaskExecutions` 恢复过期租约；`@Cron('0 * * * * *') runDueAutoTasks` 在 Redis 锁 `scheduler:xpert-auto-task`（TTL 5 分钟）下取 `enabled=true AND nextRunAt<=now` 的前 20 条自动任务执行。
**状态迁移**：`schedule`（重解析项目当前助手版本 → 连接器预检 → `rescheduleTask` → `SCHEDULED` + 清 `statusReason`）；`pause`/`archive`（先 `deleteJob` 再写状态）；`unarchive` **落到 `PAUSED` 且不排程**；`softDeleteHttpTask` = `pause` + `softRemove`，`recoverHttpTask` 只软恢复、不重建 job；`updateTask` 若原状态为 `SCHEDULED` 则先清 `statusReason` 再 `rescheduleTask`，否则 `deleteJob`。
**执行与账本**：`scheduleCronJob.onTick` → `resolveScheduledOccurrence` 得到 `scheduledAt` → `ScheduledTaskExecutionCoordinator.claim(task, buildScheduleOccurrenceKey(task, scheduledAt), scheduledAt)`。协调器由 `TypeOrmScheduledTaskExecutionStore`（`insertIfAbsent` 用 `.orIgnore()`、`claimExpired` 用条件 UPDATE 判 `affected===1`）支撑，租约 `SCHEDULED_TASK_LEASE_MS = 5 分钟`，`ownerId = XPERT_INSTANCE_ID || HOSTNAME || randomUUID`；`pending→running→succeeded|failed`，终态不再 claim、未过期租约不可抢、过期则 `attempt+1` 抢租；`markRunning`/`bindRun`/`refreshLease` 都是 owner+status 条件更新，失败抛 `lease was lost`；`finish` 清 `leaseExpiresAt` 并写 `lastError`/`failureCode`（仅 `LOCAL_RUNTIME_UNAVAILABLE`）。随后 `executeTask` → `createPersistedTaskChatRun`：`ChatConversationUpsertCommand({status:'idle', taskId, xpertId, projectId, from:'job'})` → `XpertAgentExecutionUpsertCommand({status:RUNNING, threadId})` → `XpertChatCommand({action:'send', from:'job', taskId, execution:{id}, streamPersistence:{transport:'redis-stream'}})`；本域只持有 `executionId`/`conversationId`，不订阅执行状态。
**模板例行与 OIDC**：`TemplateRoutinesHandler` 把助手模板 manifest 的 routines 落成每用户例行任务，任务 id 用 `uuid v5([tenantId,userId,assistant.id,key])`（注释：「stable per-user IDs make retries recoverable. Import never schedules work」），启用前要求 onboarding 完成 + connectors ready，并用 `pg_advisory_xact_lock` 串行化，且**先以 `PAUSED` 落库再切状态**（保证调度失败可安全重试）；`background-runtime.ts` 对 `offline==='local-only'` 抛 `LOCAL_RUNTIME_UNAVAILABLE`。`scheduled-task-oidc-token.ts` 为无浏览器上下文的定时运行铸造短期 actor token（`act.sub='xpert_task'`，delegated user = `runAsUserId ?? createdById`），仅在 `options.automationContext` 存在且 `context.env.oidc_token` 缺失时注入。
**自动任务 / 模板 / 便签**：`AutoTask`（`frequency: once|daily|weekly`）+ `AutoTaskTemplate`（内置 seed）、`XpertTaskTemplate`（`unique(source,tenantId,organizationId,createdById,key)`，区分内置与个人）、`ScheduleNote`（`type: note|task`、`status: pending|done`）分别由 `auto-tasks*`、`auto-task-templates*`、`templates*`、`schedule/notes*` 端点维护；`executeAutoTask` 结束会算 `nextRunAt`，`frequency==='once'` 时置 `enabled=false`。
**run-as 提案确认流**：`POST :id/run-as/proposal`（DTO `XpertTaskRunAsProposalDTO` + `createXpertTaskRunAsProposalValidationPipe`）→ `proposeProjectTaskRunAs`：要求任务有 `projectId`+`xpertId`；发起人若是当前 run-as 用户需 `assertCanUse`，否则需 `assertCanManage`；校验目标用户为项目可用成员与连接器可用后，写 `pendingRunAsUserId`/`RequestedById`/`RequestedAt` 与 `pendingRunAsConfigurationHash = buildProjectTaskRunAsConfigurationHash(task)`（xpertId + connector 绑定）。`POST :id/run-as/accept` → `acceptProjectTaskRunAs`：**只有被提名人本人**可接受；重算 hash 并比对，最后用 `update({id, pendingRunAsUserId: actorId, pendingRunAsConfigurationHash: hash}, ...)` 条件更新，`affected!==1` 即 `ProposalChanged`；成功后若任务为 `SCHEDULED` 则 `rescheduleTask` 用新 run-as 用户重建 job。配置变更（`invalidatePendingRunAsProposalForConfigurationChange`）会自动作废未确认的提案。

## business-area 字典
`BusinessArea` 是唯一使用 `@Tree('closure-table')` 的实体，字段仅 `type`/`name`/`parentId`，`@Index()` 落在 `name` 上。`BusinessAreaService` 继承 `TenantOrganizationAwareCrudService`，覆盖 `findAll` 默认按 `name ASC`；`createArea`/`updateArea` 用 `requireName` 去空白并拒绝空名；`updateArea` 的父节点校验是**环检测**：拒绝「自己是自己的父」以及「把节点移动到自己的后代之下」（`validateParent` 沿 `parentId` 上溯并记录 `visited`，命中 `id` 即 400）。`deleteArea` 为硬删除，树的级联由 `@TreeParent({onDelete:'CASCADE'})` 承担。

## 热点路径
1. **项目任务写串行化**：`XpertProjectTaskService` 的 `lockProject` 让同一项目的所有任务写、步骤写、批量更新、执行派发、验收决策、观察投影全部排队；这是全域名最粗的一把锁，也是「快照不被旧数据覆盖」的唯一保障（`graph` 注释：「Serialize snapshot acquisition too: an older snapshot cannot overwrite a newer one.」）。
2. **执行派发事务**：`dispatch` 在一个事务里做项目行锁 + 重放查重 + 全量尝试扫描 + Invocation 状态比对，随项目历史增长而线性变重。
3. **任务读投影**：`ProjectTaskRuntimeReadService.get` 对每个带 `invocationId` 的执行逐条取 `AgentInvocationEntity`，属于 N+1 读模式，仅用于单任务详情。
4. **观察投影扫描**：`ProjectRuntimeObservationHandler` 每次回执都要项目行锁 + 最新尝试查询 + 规格 digest 重算。
5. **`xpert-task` 定时热路径**：`scheduleCronJob` 的 `onTick` 每次触发都要在建 Job 上下文（`runWithTaskRequestContext`）中抢租约，`refreshLease` 每 60s 心跳；`runDueAutoTasks` 每分钟在 Redis 锁下取 20 条。
6. **结构订阅者**：`afterLoad` 回填与排序发生在**每次读**，对列表接口是隐性常数开销。

## 技术债与 hack
1. **端点数虚高**：`project.controller.ts` 内 4 条 VCS/GitHub 安装相关路由被注释保留，统计控制器时容易把它们算进真实端点；VCS 能力整体已被 `@deprecated use CodeXpert instead` 取代（`entities/project-vcs.entity.ts`）。
2. **Workspace 绑定被物理拒绝**：`PUT :id/workspace` 直接抛 `BadRequestException('Projects no longer bind to a Workspace')`，实体侧以 `onDelete:'RESTRICT'` 兜底，注释解释项目是要长期存活的交付记录。
3. **旧成员关系无回填**：`XpertProject.members` 标注 `@deprecated Legacy relation`（「no startup backfill is performed」），但 `addLegacyMember`/`removeLegacyMember`/`syncLegacyMembership` 仍在维护它，形成双写面。
4. **`@VersionColumn` 只覆盖一处**：项目任务表有 `revision`，`XpertTask` 完全没有版本列，因此 run-as 接受只能靠「hash 条件更新」而非版本号，语义更弱。
5. **调度三套机制并存**：Bull 一次性入队 + 进程内 cron + `@Cron` 扫描三者的入口不同；`create.handler.ts` 创建后把 `schedule` 置 `null`，而 `onModuleInit` 只重建 `options || schedule` 存在的任务，二者耦合脆弱。
6. **`query.handler.ts` 伪造 `PAUSED`**：`SchedulerRegistry` 是本地内存，多实例或重启后取不到 cron job 就把返回体的 `status` 改成 `PAUSED`，可能与库里状态不一致（属于「读侧纠正」的 hack）。
7. **`scheduler.job.ts` 未使用的注入**：`@Inject(JOB_REF) jobRef` 从未被使用，`@Process({concurrency:5})` 也未命名。
8. **租约时长耦合**：Redis 自动任务锁 TTL 与 `SCHEDULED_TASK_LEASE_MS` 同为 5 分钟，锁过期与租约到期同刻，长批次扫描理论上可重叠。
9. **`template-routines` 依赖 PG 专有锁**：`pg_advisory_xact_lock` 一旦换成非 PG 测试库即失效。
10. **双重删除语义**：`DELETE :id/soft` 与 `DELETE :id` 并存，硬删先 `deleteJob` 再 `delete`，而 `PUT :id/recover` 只恢复软删记录、不重建 job——恢复后任务静默不排程。
11. **`failureCode` 只有一个取值**：`ScheduledTaskExecution.failureCode` 类型仅 `'LOCAL_RUNTIME_UNAVAILABLE' | null`；`finish` 在租约丢失时对 FAILED 还会从 `PENDING` 状态补写一次，终态语义被弱化。
12. **Legacy 自动化成死代码**：实体与两张表保留、扫描器空转、写路径全 `GoneException`，但 `overview` 仍返回 `automations` 字段，用户侧仍能看到历史入口。
13. **`[推测]` 读路径副作用**：`XpertProjectTaskSubscriber.afterLoad` 的就地排序使得「有序 steps」只在经 TypeORM 加载后成立，任何直接构造实体或共享引用的代码路径都可能拿到未排序数组。
14. **`[推测]` `dispatchIntent` 的备份/迁移风险**：`select: false` 使其不出现在常规查询里，备份或数据修复脚本一旦忘记显式 `addSelect`，派发恢复链会因 `intent()` 解析失败而不可用（错误分类为 `Invalid`）。

## 设计维度分析
**一致性 vs 吞吐**：本域选择「项目行级悲观锁 + 任务 `revision` CAS + 幂等键」三件套，换取任务图、验收决策与运行时投影在并发下不会互相覆盖（旧快照无法写入新版本）。代价明确：同一项目的所有任务写与派发被完全串行化，多厂商任务图（provider snapshot）也必须在锁内取，热点项目会成为单点。
**确定性身份 vs 可读 id**：`projectTaskIdentity` 用 sha256 派生 UUID，使 provider 快照可重放、跨次快照 id 稳定，但 id 不可读、不可人工推导，排障必须回查 `providerKey + sourceKey`；同理执行行以 `agentInvocationId(scope, callId)` 预先确定 Invocation id，换来「重放不新造 callId」，却把 Invocation 的身份与项目作用域强绑定。
**两套任务模型的成本**：项目内任务（provider 快照 + CAS + Invocation 投影）与 `xpert-task`（独立表 + 租约 + 会话/执行账本）分别优化了「协作图」与「周期调度」两种场景，边界清晰、互不污染；但用户视角存在两条「任务」概念，跨域只靠 `projectId` 外键与两个 `@OnEvent` 连接，撤权/删除的一致性依赖事件最终送达与各侧幂等。
**授权面的收敛 vs 装配的分散**：授权被收敛成 `XpertProjectAccessService` + `ProjectAccessRuntimeService` 两个入口（含运行时/插件侧），但装配分散在 `XpertProjectAccessModule`（被 sandbox/对话/文件域直接复用）与主模块之间，控制器又用继承（`XpertProjectController extends XpertProjectPlanningController`）合并端点，导致「有哪些路由」必须靠继承链才能看全。

## 结论
实现上，本域把「业务决策」与「执行事实」切得很干净：项目侧的写路径全部收敛到带项目行锁与 `revision` CAS 的少数服务方法，执行侧只通过 `dispatchIntent` 把意图钉死、通过 `specificationSnapshot.digest` 把规格钉死，运行时状态只允许被 `ProjectRuntimeObservationHandler` 单向投影回任务状态，业务完成则必须由 `ProjectTaskDecisionService.decide` 显式确认。`xpert-task` 侧则用 `occurrenceKey` 唯一索引 + 租约换取「同一时段至多一次执行」，用 run-as 提案的配置 hash 换取「配置变更即作废授权」。
需要重点防守三处：① `dispatchIntent` 的 `select:false` 与补偿扫描的耦合（漏选即不可恢复）；② 调度三套机制与 `schedule` 列被清空后的重建耦合；③ Legacy 自动化、VCS、Project File 三处 `@deprecated` 残留仍未迁出模块边界。新增能力时应继续走「命令入口 + 事务内 CAS + 幂等键」的既有骨架，不要绕开 `ProjectTaskOwnership` 的三道断言直接改任务列。
