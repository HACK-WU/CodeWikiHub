## 二、逐文件覆盖点

**根目录**
- `project.controller.spec.ts`（`describe('XpertProjectController collaboration endpoints')`，6 个 `it`）：① 断言 `updateXperts`/`removeXpert` 的 `XPERT_PROJECT_PERMISSION` 元数据均为 `XPERT_PROJECT_MANAGE`；② `create` 把种子交给 `createProject`、**不再调用 `addXpert`**，且 `activityService.record` 的 `payload.xpertCount` 取的是 `project.xperts.length`（3，即归并后的完整初始化成员数）；③ 断言 `createTask` 仍保留 `path: ':id/tasks'` 与 `XPERT_PROJECT_EDIT` 元数据（防止继承链破坏路由）；④ `findAvailable` 的参数归一（`'  xpert-1  '` → `'xpert-1'`、`skip: '-2'` → `0`、`take: '500'` → `100`、`unclassified: false`）；⑤ `getAccess` 对 member 返回 `{canRead:true, canEdit:false, canManage:false, canUse:true}` 并验证 `addMember` 转发为 `add(project, user, 'member')`；⑥ `getInstructions`/`updateInstructions`/`getProjectSkills` 全部转发到 `ContentService`（含 `updateInstructions(id, 'Ship now')` 的字符串参数形态）。
- `project.service.spec.ts`（7 个 `it`）：① `assertRuntimeAccess` 同时要求项目/助手绑定与已发布助手的运行权限；② `findAllMy` 只走 owner 或活跃成员并返回 DB count；③ 传入历史版本时存的是**当前已发布助手**；④ `removeXpert` 会暂停排程任务；⑤ `addAttachments` 经 `GetOwnedStorageFileQuery` 授权；⑥⑦ 硬删/软删项目前先清 Connector 绑定（两个独立 `it`）。
- `project-admin.controller.spec.ts`（3 个 `it`）：`PERMISSIONS_METADATA` 等于 `[ORG_USERS_EDIT, ALL_ORG_EDIT]`；`intervene` 转发 reason；空 reason 在 HTTP 边界被拒。
- `project-managed-provisioning.spec.ts`（`describe('XpertProjectService managed provisioning')`，19 个 `it`，24.35KB）：单助手 ensure 契约保留、创建失败后重试只修内容、会话临时名只替换一次、application 拥有的名字被保留、业务应用首次 provision 前用户改名被保留、请求者与全部直接必需外部助手一次 save 写入、**创建前完成全部校验**、非 root token 不重放、普通 API 创建即种子全部助手（不再调 add-member）、duplicate 展开初始成员、手动移除的成员不被复活、无 expectations 初始化不恢复已移除成员、角色 expectations 不恢复已移除成员、已发布的 External 边移除后仍保留初始化成员、**并发移除不被元数据读快照复活**、身份与成员同事务先于内容初始化落库、初始成员链接失败使创建事务失败、超过一个直接助手的 expectation 被拒。
- `project-module-link.spec.ts`（1 个 `it`）：`XpertModule` 与 `XpertProjectModule` 的 `MODULE_METADATA.IMPORTS` 互为 `forwardRef`（跨子域装配断言）。

**`guards/`**
- `project-auth.guard.spec.ts`（2 个 `it` + `it.each` 3 例）：`USER_XPERT` 绑定放行；`PUBLIC_XPERT`/`ENTERPRISE_XPERT`/`API_KEY` 绑定抛 `ForbiddenException`（用 `TestGuard extends XpertProjectAuthGuard` 覆写 `authenticateClientSecret`）。
- `project-permission.guard.spec.ts`（2 个 `it`）：无 `:id` 时用角色权限集判定（含重复 VIEW 授权仍放行，且**不查库**）；`XPERT_PROJECT_CREATE` 必须「集合权限 + `assertCanRead(projectId)`」双满足，缺权限时 `assertCanRead` 不被调用。

**`dto/`**
- `project-update.dto.spec.ts`（1 个 `it`）：`ProjectUpdateInputDTO` 只接受项目基础配置字段（白名单收窄）。

**`services/`**
- `project-access.service.spec.ts`（14 个 `it`）：manager 可 manage 而 editor 不可；editor 与 owner 均可 edit；member 可读可用已绑助手但项目只读；无活跃成员即拒；**legacy members 不授权也不迁移**；跨租户/组织不探测成员表；`archived` 可读但不可用/不可编辑；运行时使用需要显式助手关系；已链接的发布版本视为同一助手；owner-only 操作保留给 owner。
- `project-access-runtime.service.spec.ts`（2 个 `it`）：`assertEdit` 对合法角色通过、对越权角色抛 `ForbiddenException`。
- `project-membership.service.spec.ts`（4 个 `it`）：直加仅限「同组织活跃真人用户」且不发通知；非活跃组织成员被拒；软删成员时暂停其自动化并 `await` Connector 授权回收；所有权只能转给活跃成员且旧 owner 降为 manager。
- `project-admin-intervention.service.spec.ts`（`describe('XpertProjectMembershipService Organization administrator intervention')`，6 个 `it`）：在同一事务内创建 manager 成员行与「actor + reason」审计活动；复用并把旧成员行提升为 manager；无组织用户管理权限时**在触碰项目前**即拒绝；reason 非空；拒绝当前租户/组织之外的项目；管理员必须是项目组织的活跃成员。
- `project-invitation.service.spec.ts`（8 个 `it`）：只存 hash 且重发时轮换唯一活跃 token；验证用户 email 不匹配即拒；**先落 `expired` 再拒绝**；接受在单事务内完成并对同用户同 token 幂等返回成员行；提交后缓存/兼容工作失败仍返回已提交的接受结果；自动重试持久化的 legacy 兼容工作；manager 只能撤销 pending；匹配的被邀请用户可 decline。
- `project-type.service.spec.ts`（`describe('application Project types')`，17 个 `it`）：内置类型创建普通项目；entity 类型必须走业务创建流程；首发送必须显式 opt-in 且**不为 entity 类型回退**；宿主身份与事务传给 opt-in provider；接受 platform 回执、拒绝把业务 id 当目标；provider 失败回滚首发送；用 loader provenance + 持久化业务链接领取项目；拒绝缺失业务链接与伪造的 desired state；重试时身份与安装 provenance 不变；阻断 legacy 调用者同步已分类项目；保留 chat 创建的通用项目；不把另一 platform 类型当作通用兼容案例；不允许其它插件 provider 冒充类型所有者；不暴露其它组织的插件；已移除应用不能变成平台托管数据；打开 entity 项目需要成员关系 + 显式助手连接；只读 xpert target 的显式类型贡献。
- `project-xpert-binding.service.spec.ts`（4 个 `it`）：用当前助手替换并去重历史版本关系；归一读结果但不回写；当前助手缺失时不解析历史版本；不跨 Workspace / Organization 合并助手。
- `project-initial-assistants.spec.ts`（4 个 `it`）：收录内部 agent 的可选与嵌套边、去重菱形、终止环；只用规范发布版本、**绝不含仅草稿依赖**；支持无组织的租户级图（缺失组织不当通配）；超界时**显式失败**而非持久化部分成员集。
- `project-content.service.spec.ts`（10 个 `it`）：`project.md` 只从 legacy instruction 初始化一次；只有 `project.md` 与 `skills/` 子树被识别为受管内容；初始化时拒绝 symlink 的 skills 根；拒绝含 symlink 目录的 skills 树；只从项目内容发现嵌套 `SKILL.md`；拒绝在 skills 目录之外撰写项目 skill；允许 editor 只在单个项目 skill 路径内撰写/删除；持久化 enabled 状态并卸载已安装 skill；仓库安装先暂存再拷贝校验文件；拒绝返回 staging 目录之外 symlink 的仓库安装。
- `project-workspace-files.service.spec.ts`（4 个 `it`）：读走读权限并返回共享文件模型；受管内容写入路由到 `ContentService`；普通文件用编辑权限编辑；**阻断通用上传/删除绕过项目内容规则**。
- `project-purge.service.spec.ts`（`describe('plugin-owned Project purge')`，5 个 `it`）：非 owner / 活跃项目 / 错误助手绑定在删数据前即拒；应用托管项目在触碰文件前拒绝；文件清理失败在删项目前抛出；删除项目前先移除已理解资产与「仅租户边界内的项目卷」；项目已被移除后的清理重试是安全的。
- `project-resource-card.service.spec.ts`（4 个 `it`）：卡片与其回复一起持久化且不重复；并发首条回复串行化只发一次创建回执；原子附加失败后可恢复 pending 回执；无关会话或手动项目不发。
- `project-list-query.spec.ts`（1 个 `it`，`describe('available project pagination')`）：分页前先应用类型/搜索/组织过滤，且顺序确定（recent-first）。
- `project-automation-scheduler.service.spec.ts`（1 个 `it`）：**不调度 legacy 项目自动化**（下线契约的回归护栏）。
- `conversation-project.service.spec.ts`（`describe('first-send Project creation')`）：首发送项目创建（含会话行锁、`AssertChatConversationAccessQuery`、`conversationBootstrap` 时序）。

## 五、缺口

1. **三个守卫无 spec**：`project.guard.ts`、`project-owner.guard.ts`、`project-feature.guard.ts` **均无对应 spec**。其中 `XpertProjectFeatureGuard` 是最重的一层（每请求 3~4 次查询 + 多分支放行/拒绝），「缺 seed 即放行」「租户级回退组织级」两条分支完全无断言。
2. **`project.guard.ts` 的元数据分派无断言**：`XPERT_PROJECT_MANAGE → assertCanManage / EDIT → assertCanEdit / 默认 → assertCanRead` 的三分支只在 `project-permission.guard.spec.ts` 的同类逻辑上被间接覆盖（同一 guard 的复制实现），`project.guard.ts` 本身未被引用。
3. **`XpertProjectOwnerGuard` 的「不检查 archived」语义无断言**：`PATCH :id/owner` 上「owner 守卫通过、`transferOwnership` 的 `assertIsOwner` 拒绝」这一双护栏次序无 spec 保护，属最容易漂移的语义。
4. **`XpertProjectService` 主路径覆盖薄**：7 个 `it` 只覆盖 `assertRuntimeAccess`/`findAllMy`/`addXpert`（部分）/`removeXpert`/`addAttachments`/`deleteProject`/`softRemoveProject`；**`createProject` 本体、`update`（含 advanced→simple 拒绝）、`archive`、`duplicate`、`exportProject`、`importProject`、`getToolsets`/`addToolset`/`removeToolset`、`getKnowledges`/`addKnowledge`/`removeKnowledgebase`、`delAttachment`、`updateVCS`、`handleIntegrationAuthorizedEvent` 均无直接 spec**（部分由 `project-managed-provisioning.spec.ts` 间接覆盖）。
5. **控制器 HTTP 面几乎无覆盖**：`project.controller.spec.ts` 只有 6 个 `it`，断言的是元数据与转发，**96 条路由无逐条用例**；`uploadFile`/`deleteFile`/`addAttachments`/`removeAttachments`/`listAssets`/`assetTree`/`createAsset`/`updateAsset`/`removeAsset`/`listAutomations`/`runAutomation`/`listAutomationRuns`/`listWorkspaces*`/`inviteMember`/`listInvitations`/`revokeInvitation`/`listActivities`/`getConversations`/`importDsl`/`overview` 均无控制器级断言。
6. **`XpertProjectAssetService` 无 spec**：`(projectId, path)` upsert 的「命中软删行即 recover」语义、`list` 的 `parentId = IsNull()` 根层语义、`take` 夹取 `[1,200]` 全无覆盖——这是① 侧唯一有显式唯一约束的服务。
7. **`XpertProjectActivityService` 无 spec**：`sanitizeActivityPayload` 的递归脱敏（数组 / 嵌套对象 / 正则命中键名的删除）是**全子域的安全不变量**，却无任何单测；`list` 的 `take` 默认值与降序也未被断言。
8. **`XpertProjectAutomationService` 无 spec**：只有 `project-automation-scheduler.service.spec.ts` 的 1 个 `it`（「不调度」）。四个 `GoneException` 写方法、`triggerEvent` 返回空数组、（② 侧的）processor 只写 `failed` 三条契约都无直接断言；`createAutomation`/`updateAutomation`/`removeAutomation`/`run` 的 410 语义回归无护栏。
9. **`XpertProjectPurgeService` 的跨域协作只到 mock 级**：5 个 `it` 覆盖了前置校验与清理次序，但 `FileAssetDeletionService` 与 `VolumeHandle.removePath` 的 `boundaryRoot` 越界拦截、`ENOENT` 吞错两条分支靠 mock，真库/真卷未验。
10. **`project.subscriber.ts` 无 spec**：`ownerId ??= createdById` / `owner ??= createdBy` 的兼容回填是**每次加载**的副作用，无断言；`XpertProjectFile`/`XpertProjectVCS` 与其弃用服务无任何 spec。
11. **`business-area` 覆盖偏薄**：仅 3 个 `it`，`BusinessAreaController` 的 `RoleGuard` + `@Roles(SUPER_ADMIN, ADMIN)` **无守卫级断言**，`@Tree('closure-table')` 的真实级联（删除父节点是否带走后代 + closure 行）在 mock 仓储下完全未验。
12. **邀请的投递与状态补充**：`emailService.inviteUser` 分支、`clientBaseUrl` 回落 `http://localhost:4200`、`organization.inviteExpiryPeriod` 缺省 14 天三条路径未被断言（spec 用空 token/过期 token 覆盖了拒绝侧）。
13. **`[推测]` 无 known-fail / skip 白名单**：① 侧未见 `describe.skip` / `it.skip` 或已知失败清单；`project-module-link.spec.ts` 只断言 `forwardRef` 存在，未断言 `exports`/`providers` 的完整性，因此「新增服务忘记挂进模块」不会被任何 spec 拦住。

## 六、结论

判定：**✅ 可跑（不实跑，仅给命令与判据）**。判据：
1. ① 侧 23 个 `xpert-project` spec 与 1 个 `business-area` spec **不连任何外部服务**：仓储、`EventEmitter2`、`QueryBus`/`CommandBus`、`EmailService`、`ConfigService`、`VolumeClient` 全为 mock 或 `@Optional()` 缺省；命令三与命令二可直接本地执行。
2. `project-content.service.spec.ts` 依赖可写的 `tmpdir`（真实文件系统 + `realpath` + symlink），是① 侧唯一有非内存依赖的 spec；在只读沙箱或禁用 symlink 的环境会失败，属**环境前置**而非代码缺陷。
3. `business-area.service.spec.ts` **必须**切到 `packages/server/jest.config.ts`，否则 `moduleNameMapper` 不解析 `packages/server` 内部路径。
4. 仓库内**未发现** ① 侧的 known-fail / skip 白名单；`project-auth.guard.spec.ts` 用 `it.each` 覆盖三种被拒绑定，属条件参数化而非跳过。
5. 覆盖重心明显偏向**规则型代码**（类型分类、准入判定、邀请状态机、内容受管路径、初始成员 BFS、purge 前置校验），而**聚合写路径与控制器 HTTP 面偏薄**（`XpertProjectService` 主路径、`XpertProjectAssetService`、`XpertProjectActivityService`、三个守卫、96 条路由）。若要为 ① 增加护栏，优先级排序建议为：`XpertProjectFeatureGuard`（含 seed 缺失与 organizationId 回退两条分支）> `sanitizeActivityPayload`（安全不变量）> `XpertProjectAssetService.createAsset` 的 upsert/recover 语义 > `XpertProjectOwnerGuard` 与 `assertCanPurge` 的次序组合 > automation 四个 `GoneException` 的 410 回归 > `XpertProjectService.duplicate`/`importProject`/`exportProject` 的往返一致性。
