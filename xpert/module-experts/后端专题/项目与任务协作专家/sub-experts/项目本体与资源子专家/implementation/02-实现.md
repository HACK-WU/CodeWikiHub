## 1. 项目创建链

HTTP 路径：`XpertProjectController.create` 先解构 `{ xpertIds, toolsetIds, knowledgebaseIds, memberIds, ...projectInput }`，对直选能力做 `void toolsetIds; void knowledgebaseIds`（payload 注释逐字「Deprecated direct capability selections are intentionally ignored.」），把 `status ?? 'active'` 与归一后的 `settings{instruction, mode, managementMode ?? 'simple'}` 交给 `XpertProjectService.createProject`。

`createProject` 分三步：① `xpertIds` 去重去空白后 `Promise.all(map → resolveAccessibleCurrentXpert)`——该方法先 `PublishedXpertAccessService.getAccessiblePublishedXpert(id, { relations: ['agent'] })`，再 `XpertProjectXpertBindingService.resolveCurrent` 换成当前版本；② `XpertProjectTypeService.forCreate(input.projectType ?? GENERAL_PROJECT_TYPE)`——`resolve(ref)` 只在 `catalog()`（`effectiveLoadedPlugins` × `projectApplicationDefinitions`）里查，命中即返回带 `pluginName`/`appName`/`scopeKey` 的注册项，未命中抛 `Error.ProjectTypeUnavailable`；`forCreate` 额外要求 `binding.kind === 'project'`，否则抛 `Error.ProjectApplicationWorkflowRequired`；③ `classification(ref)` 反查 `PluginApplicationInstallation`（`tenantId` + `organizationId ?? IsNull()` + `pluginName` + `appName`）得到 `applicationInstallationId`，并固化 `projectTypeSnapshot = { applicationTitle, title, binding }`。

`createWithInitialAssistants` 把 `createProjectWithAssistants(store, entity, roots)` 接上：`store.bindings.resolveInitialMembers(roots, scope)` → `resolveInitialProjectAssistants` 做 BFS——逐个 `loadCurrent(id)` 校验「同租户、同组织（`?? null` 比较，缺失组织不等于通配）、`publishAt` 非空、`active !== false`、有 `graph`、有 `agent.key`」，不满足抛 `errorCode: 'project_initial_assistant_unavailable'`；超过 256 个抛 `project_initial_assistants_limit`（**不落部分成员集**）；用 `projectExternalAssistantIds(xpert, agentKey)` 从 `graph.connections` 取 `type === 'xpert'` 的边继续下探，`isSameXpertFamily` 去重。

落库两条分支：**无 `entity.id`**（普通创建）走 `store.create`（`super.create` + `xperts` 关系一起写）再 `store.initialize`（`XpertProjectContentService.initialize` 建 `project.md`）；**有 `entity.id`**（插件 provisioning）在事务内 `manager.getRepository(XpertProject).insert(project)` + `queryBuilder().relation(XpertProject, 'xperts').add(ids)`，捕 `error.code === '23505'` 转 `ConflictException(Error.ProjectTypeConflict)`，出事务后再 `initialize`。两侧都用 `omit(entity, ['workspace','workspaceId','xperts','members','memberships','toolsets','knowledges'])` 丢掉不可信关系快照。控制器随后补 `planService.ensureDefaults(project.id)`、逐 `initialMemberIds` 调 `membershipService.add(..., 'member')`、写 `project.created` 活动。

幂等 provisioning 路径：`XpertProjectService.ensureManagedProject` → `ensureManagedProject(store, input)`：`requiredProjectText` 校验三个入参长度，`resolveXpert` 后校验组织一致，`validateProjectExternalAssistants` 校验外部助手；查项目时把 `tenantId` + `organizationId ?? IsNull()` 一并放进 where（注释：「retries cannot adopt a same-id Project from a different security boundary」）；已存在且 `ownerId !== user.id` 抛 `Error.ProjectOwnerSyncRequired`；已存在时显式解构 `const { xperts, ...metadata } = project` 后只 save `metadata`（注释：「Never save a loaded relation snapshot」）；`operation === 'updated'` 时补跑 `initialize` 修复内容初始化。

## 2. 成员与邀请链

**成员**：`XpertProjectMembershipService.add(projectId, userId, role='member')` —— `assertCanManage` → `validateProjectMemberRole(role)`（白名单 `manager|editor|member`）→ 拒绝把 `project.ownerId` 当成员加入（`Error.ProjectOwnerAlreadyMember`）→ `userRepository.findOne({ id, tenantId, type: UserType.USER })` → `userOrganizationRepository.findOne({ tenantId, organizationId ?? IsNull(), userId, isActive: true })`（缺则 `Error.ProjectMemberOrganizationMismatch`）→ `membershipRepository.findOne({ where:{projectId,userId}, withDeleted: true })`，命中软删行先 `restore` 再复用同一行（`joinedAt` 重置、`removedAt`/`deletedAt` 清空）→ `save` → `addLegacyMember(project, user)` 写 `xpert_project_member`。`list` 用 `Promise.all` 取 owner 与 `memberships`（`relations: ['user']`、`order: {joinedAt:'ASC'}`），合并成 `TXpertProjectMemberSummary`（owner 恒 `projectRole: 'owner'`）。

**移除**：`remove` 禁止移除 owner（要求先 `transferOwnership`），置 `removedAt = new Date()` 后 `softRemove`，`removeLegacyMember`，再 `Promise.all` 两条 `XpertTask.update` 把该用户归因的任务置 `ScheduleTaskStatus.PAUSED` 并写 `statusReason`（谓词分别是 `{projectId, runAsUserId: userId}` 与 `{projectId, runAsUserId: IsNull(), createdById: userId}`），最后 `eventEmitter.emitAsync('xpert-project.member-removed', {tenantId, organizationId, projectId, userId, actorId})`。**顺序不可换**：先落库、再暂停、再发事件。

**所有权转移**：`transferOwnership` 在 `management.transaction` 内锁项目行 → 校验新 owner 是活跃成员 → 把新 owner 的成员行 `removedAt` + `softRemove`（owner 不应占成员位）→ 旧 owner 复用/新建成员行并降为 `manager` → 最后写 `lockedProject.ownerId`；出事务后同步 legacy 关系（移除新 owner、加入旧 owner）。

**组织管理员介入**：`interveneAsOrganizationAdministrator(projectId, reason)` 先校验权限（`ORG_USERS_EDIT` 或 `ALL_ORG_EDIT`）与**非空 reason**，事务内 `pessimistic_write` 锁项目行 + 锁成员行，把调用者写成 `role: 'manager'`，并**在事务内直写** `XpertProjectActivity`（`type: 'project.admin-intervened'`，`payload: {actorId, reason, role}`），最后补 legacy 关系。

**邀请**：`invite` 除 `assertCanManage` 外还要求 `RequestContext.hasPermissions([PermissionsEnum.ORG_INVITE_EDIT])` 且项目必须有 `organizationId`（用于取 `organization.inviteExpiryPeriod`，缺省 14 天）；若目标 email 已是同租户 USER 且已是 owner/成员，直接 `Error.ProjectMemberAlreadyExists`；token = `randomBytes(32).toString('base64url')`，库内只存 `hashProjectInvitationToken(token) = sha256 hex`；同 `(projectId, normalizedEmail, status='pending')` 命中则**复用同一行**并轮换 `tokenHash`/`expiresAt`/`lastSentAt`/`role`，未命中才 `create`；随后 `emailService.inviteUser({..., registerUrl: new URL('/project/invitations/accept', clientBaseUrl) + ?token=})`（`emailService` 为 `@Optional()`）。

`accept(token)`：要求 `currentUser.type === UserType.USER && emailVerified`；事务内用 `createQueryBuilder().addSelect('invitation.tokenHash').setLock('pessimistic_write')` 按 `tokenHash + tenantId` 取行；缺失 → `Error.ProjectInvitationInvalid`；`normalizedEmail` 不一致 → `Error.ProjectInvitationEmailMismatch`；`status === 'accepted'` 时是幂等分支（要求 `acceptedById === currentUser.id` 且成员行存在，回既有 `membership`、`organizationMembershipCreated: false`）；`status !== 'pending'` → 无效；`expiresAt <= now` → **先写 `status='expired'` 再返回 `{status:'expired'}`**（事务外统一转 `BadRequestException`）；否则 `userOrganizationService.ensureMembershipInTransaction` + `isActive` 补正，再 upsert `xpert_project_membership`（软删行 `restore`），最后写 `status='accepted'`/`acceptedById`/`acceptedAt`。事务提交后两件事**不阻断主流程**：`runPostAcceptanceStep('organization-membership-completion', …)` 与 `tryLegacyMembershipSync(invitation)`（失败只 `logger.warn`；成功写 `legacyMembershipSyncedAt`，失败按 `60s × 2^(attempts-1)` 指数退避、上限 1 小时写 `legacyMembershipSyncAttempts/LastError/NextAttemptAt`）。

`decline(token)` 要求当前用户 email 与邀请一致且邀请仍 pending、未过期，写 `status='declined'`；`revoke(projectId, invitationId)` 要求 `assertCanManage` 且仅 pending 可撤销，写 `status='revoked'`。补偿扫描 `retryPendingLegacyMembershipSyncs` 由 `@Interval(60_000)` 驱动，取 `status='accepted'` 且 `acceptedById` 非空、`legacyMembershipSyncedAt IS NULL` 且（`NextAttemptAt IS NULL` 或 `<= now`）的前 50 条，异常只 `logger.warn` 并返回 `{scanned:0, synced:0}`。

章节来源：[project-membership.service.ts](file://packages/server-ai/src/xpert-project/services/project-membership.service.ts)（关键符号：XpertProjectMembershipService.add / remove / transferOwnership / interveneAsOrganizationAdministrator / addLegacyMember / validateProjectMemberRole）、[project-invitation.service.ts](file://packages/server-ai/src/xpert-project/services/project-invitation.service.ts)（关键符号：XpertProjectInvitationService.invite / accept / decline / revoke / retryPendingLegacyMembershipSyncs / hashProjectInvitationToken）、[project-invitation.entity.ts](file://packages/server-ai/src/xpert-project/entities/project-invitation.entity.ts)（关键符号：XpertProjectInvitation.tokenHash / IDX_xpert_project_invitation_pending / legacyMembershipSyncAttempts）

## 3. 资源挂载

**助手（M2M `xpert_project_xpert`）**：`XpertProjectService.addXpert` 先 `assertCanManage`，再 `findOne({ where:{id}, relations:['xperts'] })`，`resolveAccessibleCurrentXpert(xpertId)`，校验 `(xpert.organizationId ?? null) === (project.organizationId ?? null)`（否则 `Error.ProjectXpertOrganizationMismatch`）；随后 `xpertBindingService.normalize(withXperts)` **把历史版本关系就地换成当前版本并去重**，`contains(withXperts, xpert)` 为真则 `logger.warn` 后原样返回（幂等），否则 `push` + `repository.save`。`getXperts` 读侧同样先 `normalize`（不持久化）。`removeXpert` 走家族匹配：`removedXpertIds` 由「id 相等 或 `isSameXpert(linkedXpert, currentXpert)`」筛出，移除后把 `XpertTask` 中 `xpertId IN [xpertId, ...removedXpertIds, currentXpert?.id]` 的行批量置 `PAUSED` 并写 `statusReason`。`setAssistant` 标注 `@deprecated`，只是 `addXpert` 的壳。

**工具集 / 知识库（`xpert_project_toolset` / `xpert_project_knowledgebase`）**：`addToolset`/`removeToolset`/`addKnowledge`/`removeKnowledgebase` 均先 `assertCanManage`（部分实现内部再 `assertCanRead`），用 `findIndex` + `splice` 维护数组后整体 `save`。**创建时不允许直选**——`XpertProjectController.create` 丢弃 `toolsetIds`/`knowledgebaseIds`，因此新建项目的这两个集合恒为空，只在后续 `PUT/DELETE :id/toolsets/:toolset`、`PUT/DELETE :id/knowledges/:kb` 中被填充；`getToolsets`/`getKnowledges` 返回 `{items, total}` 投影。

**附件（M2M `xpert_project_attachment`）**：`addAttachments(id, files)` 先 `findOne({relations:['attachments']})`，用 `existingAttachmentIds` 差集过滤出新 id，再对每个新 id `queryBus.execute(new GetOwnedStorageFileQuery(fileId))` 做**拥有权校验**（不是存在性校验），最后整体 `save`。`removeAttachments` 只做数组过滤；`delAttachment(id, fileId)` 额外 `commandBus.execute(new StorageFileDeleteCommand(fileId))`。

**会话首发资源卡（旁路通道）**：`ProjectResourceCardService.attach(conversation, reply)` 在 `projects.manager.transaction` 内先锁 `xpert_project` 行、再锁 `chat_message` 行（`role: 'ai'`），只在 `settings.conversationBootstrap.resourceCards` 非空、`bootstrap.conversationId === conversation.id` 且 `resourceCardMessageId` 未写时才注入，写消息 `content` 后回填 `bootstrap.resourceCardMessageId`——注释逐字：「bootstrap receipts and their first reply are claimed atomically. A crash before attachment leaves the receipt pending; replay cannot reassign it.」

章节来源：[project.service.ts](file://packages/server-ai/src/xpert-project/project.service.ts)（关键符号：XpertProjectService.addXpert / removeXpert / addAttachments / delAttachment / addToolset / addKnowledge）、[project-xpert-binding.service.ts](file://packages/server-ai/src/xpert-project/services/project-xpert-binding.service.ts)（关键符号：XpertProjectXpertBindingService.normalize / contains / resolveCurrentById）、[project-resource-card.service.ts](file://packages/server-ai/src/xpert-project/services/project-resource-card.service.ts)（关键符号：ProjectResourceCardService.attach）

## 4. 文件与资产

**卷内容（`XpertProjectContentService`）**：卷身份 = `volumeClient.resolve({ tenantId, userId: ownerId, catalog: 'projects', projectId })`——**用 ownerId 而非当前用户**，因此跨成员访问同一份卷。`initialize(project)` 调 `initializeProjectContent(volume, project.settings?.instruction)`，把首次内容（`project.md`）落盘；`ProjectContentIntegrityError` 转 `BadRequestException`。受管路径判定是静态方法 `XpertProjectContentService.isGovernedPath(filePath)` → `isProjectGovernedContentPath`（`project.md` 与 `skills/` 子树）。`readInstructions`/`updateInstructions` 分别以 `assertCanRead`/`assertCanEdit` 前置；`listSkills` 用 `realpath(volume.path('skills'))` 后扫描 `SKILL.md` 并与 manifest 合并（`readProjectSkillManifest`），`installSkill` 走 `skillIndexService.findOneInOrganizationOrTenant` + `skillSourceProviderRegistry.get(provider).installSkillPackage` 到 `mkdtemp` 暂存目录后再校验拷贝（防 staging 逃逸）。

**工作区文件（`XpertProjectWorkspaceFilesService`）**：`save` 按路径分流——`project.md` → `contentService.updateInstructions`；`skills/` 前缀 → `contentService.writeSkillFile`；其余走 `createEditClient`（`assertCanEdit`）的 `client.saveFile`。`uploadToFolder` 与 `delete` 先用 `isProjectGovernedContentPath` 拦下受管路径（`uploadToFolder` 抛 `Error.ProjectContentApiRequired`，`delete` 对 `project.md` 抛 `Error.ProjectInstructionsCannotBeDeleted`，对 `skills*` 转发 `contentService.deleteSkillPath`）。`createClient` 每次都先 `contentService.initializeById(projectId)` 再 `new VolumeSubtreeClient(volume, { allowRootWorkspace: true })`；缺 `tenantId`/`ownerId` 直接 `throw new Error(... is missing its storage identity)`。

**资产索引（`XpertProjectAssetService` 与 `xpert_project_asset`）**：`@Index(['projectId','path'], { unique: true })`；`createAsset` 先 `findOne({projectId, path}, withDeleted: true)`，命中则 `Object.assign` 覆盖可变字段 + `repository.recover`（软删行）或直接 `save`，未命中才 `create`——即 **upsert by (projectId, path)**。`list` 固定 `parentId` 语义（未传即 `IsNull()`，只看根层），`take` 夹在 `[1, 200]`；`tree` 按 `path ASC` 全量；`countProjectAssets` 供 `overview` 用；`removeAsset` 是 `softRemove`。控制器 `createAsset` 在返回前 `void activityService.record(...)` 与 `void automationService.triggerEvent(id, 'asset.created', asset.id)`（两者都 fire-and-forget）。

**上传回路（`POST :id/file/upload`）**：`FileInterceptor('file')` → 先 `isGovernedPath(file.originalname)` 拦截 → `commandBus.execute(new UploadFileCommand({ source:{kind:'multipart', file}, targets:[{kind:'volume', catalog:'projects', projectId}] }))` → 用 `getFileAssetDestination(asset, 'volume')` 校验 `destination.status === 'success'`（否则 `Error.ProjectFileUploadFailed`）→ `assetService.createAsset(id, { name: file.originalname, path: file.originalname, kind:'file', mimeType, size, source:'upload', status:'available' })` → `triggerEvent` → 返回 `{url, asset}`。即 **“文件落卷由 file-understanding 的 `UploadFileCommand` 负责，项目侧只写资产索引 + 记录活动”**。

**与 `file-understanding` 的关系（三处）**：① 卷写入走 `UploadFileCommand`（`catalog: 'projects'`，目标 `kind: 'volume'`）；② 附件拥有权校验走 `GetOwnedStorageFileQuery`；③ 物理清理走 `XpertProjectPurgeService.purge` → `FileAssetDeletionService.purgeProjectFile(assetId, projectId)`，逐个删除 `FileAsset` 中 `{tenantId, projectId}` 的行。`purge` 的完整次序：`assertCanPurge`（`role === 'owner' && status === 'archived'`，`NotFoundException` 被吞成「已删除」幂等返回）→ `assertPlatformLifecycle` → 校验 `xperts` 含请求方 `xpertId`（否则 `Error.ProjectPurgeBindingInvalid`）→ 取 `FileAsset` 并**拒绝 `uploaded|scanning|parsing|processing|queued` 任一状态**（`Error.ProjectPurgeBusy`）→ 逐文件删除 → `VolumeHandle.removePath(dirname(serverRoot), basename(serverRoot), { boundaryRoot: volumeClient.resolveRoot(tenantId).serverRoot })`，`ENOENT` 被吞 → `projects.deleteProject(project.id)`。

`XpertProjectFile`（表 `xpert_project_file`）与 `XpertProjectFileService` 已标 `@deprecated`（类注释指向 file volume / FileAsset workspace projection），且**未注册进 `forFeature`**，服务只有 `readFile` 一个方法且无调用方。

## 7. 准入实现

**第 1 层 `XpertProjectAuthGuard`**（判定输入：principal；成本：0 次查询）。继承 `ApiKeyOrClientSecretAuthGuard`，`canActivate` 先 `super.canActivate(context)`（父类完成 API key / client secret 解析与 JWT 校验），`false` 即返回 `false`；再读 `request.user`，当 `principalType === 'client_secret'` 且 `clientSecretBindingType !== SecretTokenBindingType.USER_XPERT` 时抛 `ForbiddenException(Error.ProjectInteractiveSessionRequired)`；失败行为是 403，放行条件是「交互式用户会话」。**注意 `project-auth.guard.ts` 未注册进 `project.module.ts` 的 `providers`**，它由 `XpertProjectController` 的类级 `@UseGuards` 引用，实例化由 Nest 依赖解析完成。

**第 2 层 `XpertProjectFeatureGuard`**（判定输入：`RequestContext.currentTenantId()` + 环境开关 + 两张 feature 表；成本：固定 3~4 次查询/请求）。次序：无 `tenantId` → 403「Tenant context is required」；`Promise.all` 取 `Feature(code: FEATURE_XPERT)` 与 `Feature(code: FEATURE_XPERT_PROJECT)`；`toggleFeatures.FEATURE_XPERT === false` 或 `toggleFeatures.FEATURE_XPERT_PROJECT === false` 或任一 `feature.isEnabled === false` → 403「Xpert Project feature is disabled」；`projectFeature` 不存在时**直接放行**（注释：「A fresh installation may not have completed feature seeding yet. The environment toggle remains the source of the default state.」）；否则先按 `(tenantId, organizationId, feature.id)` innerJoin 查组织级开关，未命中再查 `organizationId IS NULL` 的租户级开关，命中且 `isEnabled === false` → 403。该守卫被 `project.module.ts` 注册为 provider，并被 `XpertProjectAdminController`、`ConversationProjectService` 直接注入复用。

**第 3 层 `XpertProjectPermissionGuard`**（判定输入：`XPERT_PROJECT_PERMISSION` 元数据 + `:id` + `RequestContext`；成本：0~1 次查询）。无 `permission` → 放行；无 `user?.id || !user?.tenantId` → 403；`params.id` 缺失时用 `RequestContext.hasPermissions([permission])`（纯内存判定角色权限集）→ 失败 403 `Error.ProjectPermissionRequired`；有 `id` 时按权限分派——`XPERT_PROJECT_CREATE` 需「`hasPermissions([permission])` 为真」**且** `assertCanRead(projectId)`（即「能在集合上创建」+「能读该项目」，供 duplicate/import 用）；`XPERT_PROJECT_MANAGE` → `assertCanManage`；`XPERT_PROJECT_EDIT` → `assertCanEdit`；其余 → `assertCanRead`。

**第 4 层方法级 `XpertProjectGuard` / `XpertProjectOwnerGuard`**（判定输入：`:id` + 同类元数据；成本：1~2 次查询）。`XpertProjectGuard` 用 `reflector.getAllAndOverride(XPERT_PROJECT_PERMISSION, [getHandler(), getClass()])` 后再分派 `assertCanManage`/`assertCanEdit`/`assertCanRead`（默认 read）；`XpertProjectOwnerGuard` 只做 `assertCanRead` 后判 `access.role !== 'owner'` → 403 `Error.ProjectOwnerRequired`（即它**不检查 archived**，只做 owner 判定）。二者叠用出现在 `DELETE :id`、`DELETE :id/soft`、`PATCH :id/owner`。

**终点 `XpertProjectAccessService`**（判定输入：`tenantId` + `organizationId ?? IsNull()` + `userId`；成本：1~2 次查询 + 可选 `xperts` 关系）。`resolveAccess(projectId, relations = [], actorScope?)` 的语义要点：三键同时入 where（跨租户/组织不探测成员表）；`project.ownerId === userId` 直接返回 `role: 'owner'` 且**不查成员表**；否则查 `xpert_project_membership`（命中即用其 `role`，未命中 403 `Error.ProjectMembershipRequired`）。五个断言的差异：`assertCanRead` 只解析；`assertCanPurge` 要求 `role === 'owner' && status === 'archived'`；`assertCanUse` 只拒 `archived`（**不要求写角色**）；`assertCanEdit` 先拒 `archived` 再要求角色 ∈ `owner|manager|editor`；`assertCanManage` 先拒 `archived` 再要求 `owner|manager`；`assertIsOwner` 先拒 `archived` 再要求 `owner`。`assertCanUseXpert` / `assertCanReadXpert` 在 `relations: ['xperts']` 上额外用 `XpertProjectXpertBindingService.resolveCurrentById` + `contains` 校验家族关系（前者拒 `archived`，后者不拒）。

**运行时/插件入口 `ProjectAccessRuntimeService`**（`implements ProjectAccessApi`，`@RuntimeCapabilityProvider(ProjectAccessRuntimeCapability)`）：以显式 `actor: ProjectAccessActor` 替代 `RequestContext`，`listReadable` 用**单条** query builder（leftJoin 成员行 + `CASE WHEN project.ownerId = :userId THEN 'owner' ELSE membership.role END`）取项目与角色，再用一条 join 查询批量取 `assistantIds`；输出 `archived`/`canManage`（`status !== 'archived' && ['owner','manager'].includes(role)`）。`assertManage` 与 `assertEdit` 都建立在 `listReadable` 之上，因此各多一次全量投影查询。

## 8. business-area 字典面

`BusinessArea` 是① 域内**唯一使用 `@Tree('closure-table')`** 的实体：列只有 `type`（`BusinessType` 枚举，nullable）、`name`（`varchar(255)`，`@Index()`）、`parentId`（uuid，nullable），外加 `@TreeChildren() children` 与 `@TreeParent({ onDelete: 'CASCADE' }) parent`。表名 `business_area`，位于 `packages/server` 而非 `server-ai`，与项目/任务**无任何外键关系**，是平台级字典。

`BusinessAreaService extends TenantOrganizationAwareCrudService<BusinessArea>`：`findAll` 覆写为默认 `order: { name: 'ASC' }`；`createArea` 用 `requireName`（`trim` 后为空即 `BadRequestException(Error.BusinessAreaNameRequired)`）并可选解析 `parentId`；`updateArea` 分别处理 `name` 与 `parentId`；`deleteArea` 先 `findOneByIdString` 存在性校验再**硬删除**（`this.delete(id)`），树的级联由 `@TreeParent({ onDelete: 'CASCADE' })` 与 closure-table 承担。父节点校验 `validateParent(id, parentId)` 是**双向环检测**：先拒绝 `id === parentId`（`Error.BusinessAreaCannotParentSelf`），再沿 `parent.parentId` 上溯并用 `visited` 集合防环，命中 `parent.parentId === id` 即 `Error.BusinessAreaCannotParentDescendant`。

控制器 `BusinessAreaController`（`@Controller()` + `RouterModule.register([{ path: '/business-area', module: BusinessAreaModule }])`）：读端点 `@Get()`/`@Get(':id')`（`UUIDValidationPipe`）开放给所有登录用户；写端点 `@Post()`/`@Put(':id')`/`@Delete(':id')` 一律 `@UseGuards(RoleGuard)` + `@Roles(RolesEnum.SUPER_ADMIN, RolesEnum.ADMIN)`；删除返回 `HttpStatus.ACCEPTED`（202）。模块 `exports: [TypeOrmModule, BusinessAreaService]` 供其它业务域引用。

## 10. 热点路径

1. **`XpertProjectFeatureGuard` 每请求 3~4 次查询**：`ProjectFeatureGuard` 是类级守卫，项目控制器的 96 条路由全部经过；每次都要 `Feature` × 2 + `FeatureOrganization` × 1~2，且 `XpertProjectAdminController` 与 `ConversationProjectService` 又各自复用同一实例（无缓存）。
2. **`assertCanUseXpert` 的 N+1 读**：`resolveAccess(projectId, ['xperts'])` 把 M2M 一次拉全，再对单只 Xpert 走 `resolveCurrentById`（额外一次 `Xpert` 查询 + `resolveCurrent` 可能再查一次）——运行时/插件侧每次工具调用都会命中。
3. **`ProjectAccessRuntimeService.listReadable` 的两次批量查询**：一次项目+角色投影、一次 assistantIds join；`assertManage`/`assertEdit` 都建立在它之上，因此单点授权 = 2 次查询。
4. **`overview` 的 6 路 `Promise.all`**：`planService.list` + `getTasks(take:100)` + `assetService.list(take:100)` + `countProjectAssets` + `activityService.list(20)` + `automationService.list` + `findOne(relations:['owner','members','workspace','xperts','toolsets','knowledges'])`——`relations` 里的 `members` 是弃用 M2M，仍会被 JOIN。
5. **`findAvailableProjects` 的双 EXISTS 子查询**：`linkedXpert` 子查询按 `type + slug + organizationId + workspaceId` 比较（家族级，不是 id 级），叠加 `activeMembershipExists`，在项目量大时是较重的分页查询。
6. **`project.subscriber.ts` 的加载期回填**：发生在**每次** `XpertProject` 加载（含列表），是隐性常数开销。
7. **`XpertProjectPurgeService.purge`**：全量取 `FileAsset` 后**逐条**等待删除再删卷，属长事务外串行操作。

## 12. 技术债与 hack

1. **`xpert_project_member` 双写无回填**：实体注释「Legacy relation. … no startup backfill is performed.」但 `addLegacyMember`/`removeLegacyMember`/`syncLegacyMembership` 仍在维护它；`XpertProject.members` 还被 `overview` 的 `relations` 与 `findOne` 投影反复 JOIN。
2. **端点数虚高**：`project.controller.ts` 有一段被整块注释的 VCS/GitHub 路由（`// @Get(':id/vcs')` 等 4 条），使「装饰器出现次数」大于真实端点数；`project-vcs.entity.ts` 整体标注 `@deprecated use CodeXpert instead` 且未注册 `forFeature`。
3. **Workspace 绑定物理拒绝**：`PUT :id/workspace` 直接 `BadRequestException(Error.ProjectWorkspaceBindingDeprecated)`（「Projects no longer bind to a Workspace」），实体侧靠 `onDelete: 'RESTRICT'` 兜底；但 `ensureManagedProject` 的返回值里仍带 `workspaceId`（注释「Compatibility only」），`XpertProject.workspaceId` 列与 `workspace` 关系仍在。
4. **Legacy 自动化三重残留**：写面 `GoneException`、`triggerEvent` 返空、`@Cron` 扫描空转，但实体、两张表、`XpertProjectAutomationProcessor` 与 `XpertProjectAutomationSchedulerService` 仍留在 `providers` 中；`overview` 仍返回 `automations`。
5. **`XpertProjectFile` / `XpertProjectFileService` 死代码**：类注释指向 file volume / FileAsset 投影，未注册 `forFeature`，`readFile` 无调用方。
6. **`nextScheduleDate` / `PROJECT_AUTOMATION_LOCK_TTL` / `redisLockService` 未使用**：`project-automation-scheduler.service.ts` 内已成死代码，但 `CronTime` 依赖与 Redis 注入仍保留。
7. **`project-auth.guard.ts` 未进 `providers`**：只有 `XpertProjectFeatureGuard`/`XpertProjectOwnerGuard`/`XpertProjectPermissionGuard` 在 `providers` 里；`XpertProjectAuthGuard` 与 `XpertProjectGuard` 依赖 `@UseGuards` 侧实例化——`[推测]` 该差异使 DI 覆盖点不统一，替换授权实现时容易漏改。
8. **`resetAccess` 语义分裂**：`XpertProjectOwnerGuard` 只做 `assertCanRead` + `role === 'owner'`，**不检查 archived**；而 `assertCanManage` 会拒 `archived`。因此「owner + archived」在 `PATCH :id/owner` 上会先通过 owner 守卫、再由控制器内的 `transferOwnership`（`assertIsOwner`）拦下——两道护栏语义不同，靠调用顺序兜底。
9. **`settings` 被 `update` 收窄**：`update` 只保留 `mode` 与 `managementMode`，其余 `settings` 字段（如 `conversationBootstrap`）靠 `...(this.settings ?? {instruction:''})` 展开保住；`advanced → simple` 降级被显式拒绝（`Error.ProjectAdvancedModeDowngradeUnsupported`）。
10. **`addAttachments` 无 `assertCanEdit`**：`XpertProjectService.addAttachments`/`removeAttachments`/`delAttachment` 自身不做授权，完全依赖控制器上的 `XpertProjectGuard` + `XPERT_PROJECT_EDIT`；任何内部直调都绕过授权。
11. **`[推测]` 联接表唯一性未在仓库内声明**：五组 M2M 是 TypeORM 隐式联接表，仓库内看不到显式唯一索引；家族级去重只在服务层。
12. **`[推测]` `featureRepository.findOne({ where: { code } })` 未带租户**：`XpertProjectFeatureGuard` 查 `Feature` 只用 `code`，`Feature` 是否为全局表未在本次范围内证实；若是租户表则存在跨租户取到同一行的风险。
13. **`interveneAsOrganizationAdministrator` 直写活动表**：绕过 `XpertProjectActivityService.record`（因此**没有 `sanitizeActivityPayload` 脱敏**），只有 `reason` 与 `actorId` 被写；这是唯一一处不脱敏的活动写入点。
14. **`ProjectResourceCardService.attach` 抛错语义缺失**：函数内只处理「不该注入」的分支，`message` 用 `findOneOrFail`——消息行缺失时是 `EntityNotFoundError` 而非业务错误。

## 13. 设计维度分析

**维度一：准入放置位置——「控制器声明 + 服务自证」双轨。** 一部分服务在入口自证（`XpertProjectMembershipService.add` 调 `assertCanManage`、`XpertProjectInvitationService.invite` 调 `assertCanManage` + `ORG_INVITE_EDIT`、`XpertProjectWorkspaceFilesService.save` 走 `createEditClient`），另一部分完全依赖控制器守卫（`XpertProjectService.addAttachments`/`removeAttachments`/`delAttachment`、`XpertProjectAssetService.*`、`XpertProjectActivityService.list`）。收益是控制器路径上不会重复查库、内部/插件调用也有护栏；代价是**授权位置不可枚举**——要判断「谁能删附件」必须同时读控制器装饰器与服务实现。这条张力在 `ProjectAccessRuntimeService` 出现后被部分缓解（插件侧走显式 `actor` 而非 `RequestContext`），但 HTTP 侧的两套仍并存。

**维度二：家族关系 vs 版本快照——「当前即关系」。** 项目只存「家族」关系：`xpert_project_xpert` 存的是当前版本，`normalize` 在读/写时把历史版本就地换成当前版本，`contains` 用 `isSameXpertFamily` 比较，`resolveCurrentById` 找不到当前版本时返回 `null`（表示该助手已不可用）。收益是加同一家族的新版本不会重复挂载、助手升级不需要回填项目关系；代价是「项目挂的是哪个版本」这个问题**在项目侧没有答案**——审计与回滚只能靠 Invocation 侧的 `xpertId` 事实，且 `removeXpert` 必须同时按「传入 id + 家族命中的全部 id + 当前 id」三路去归因 `XpertTask` 的暂停。

**维度三：内容真值分裂——卷 vs 表。** 项目里的「文件」有三种落点：① 共享卷（`catalog: 'projects'`，含受管的 `project.md` 与 `skills/`），② `xpert_project_asset`（按 `(projectId, path)` 唯一的索引行，带 `parentId` 自引用形成目录树），③ `xpert_project_attachment`（指向 `StorageFile` 的 M2M，拥有权受 `GetOwnedStorageFileQuery` 校验）。三者的一致性完全靠调用方维持：`uploadFile` 先写卷再写资产行（非事务），`deleteFile` 只删卷目录**不删资产行**，`purge` 只删 `FileAsset` + 卷并让 `xpert_project_asset` 靠 `projectId` 级联删除。收益是上传路径不引入跨域事务；代价是「卷里有文件但资产表没有行」或反之都能长期存在。`[推测]` `deleteFile` 与资产行的不一致是已知缺口，仓库内未见补偿任务。

## 14. 结论

实现层面，① 把「聚合根写入口」「授权入口」「资源挂载入口」三件事分得很开：项目侧的所有改造都经由 `XpertProjectService` 与 4 个专用 service，授权只经 `XpertProjectAccessService`（HTTP）或 `ProjectAccessRuntimeService`（插件），资源挂载则统一落在 `XpertProject` 的五组 M2M 与两个旁挂载体（卷内容、资产索引）上。幂等与一致性靠四种手段组合：软删复用（成员行）、upsert + recover（资产行）、`tokenHash` 轮换 + 部分唯一索引（邀请）、`withDeleted` 差集（附件）。

四处需要重点防守：① **成员事实双轨**——授权读 `xpert_project_membership`，legacy 表只被写不被读，补偿逻辑挂在邀请表上，任何「修成员」的脚本都必须同时考虑两张表；② **守卫链的次序耦合**——`Auth → Feature → Permission → Project/Owner` 中任一层的放行条件（尤其是 FeatureGuard 的「缺 seed 即放行」与 `@Public()`）被改动都会静默放宽全项目 API；③ **弃用面仍在装配**——`XpertProjectFile`/`XpertProjectVCS`/Legacy 自动化三处让「目录有、路由有、功能无」的错觉长期存在；④ **卷与表的内容真值分裂**——`uploadFile`/`deleteFile`/`purge` 三条路径对「文件」的删除语义各不相同，是数据不一致的主要来源。新能力一律走「控制器只转发 + 服务层显式 `assertCan*` + 显式幂等键」的既有骨架。
