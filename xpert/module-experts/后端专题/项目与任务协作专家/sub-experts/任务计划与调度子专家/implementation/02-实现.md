## 1. 项目内任务图 CRUD 与依赖重排

写路径四件套：`createTask`（`validateTaskMode` 校验项目模式 + `resolveAssigneeXpertId` 强制「执行助手必须是项目成员」+ `saveAll`）、`updateTask`、`batchUpdate`、`reorder`。共同骨架是 `assertOrdinaryTaskInput`（拒绝外部写 `providerKey`/`sourceKey`/`revision`/`predecessorIds`/`executions`/`decisions`/`conversations` 等投影列，`progress` 先过 `assertProjectTaskProgress`）→ 事务内 `lockProject`（项目行 `pessimistic_write`）→ `assertOrdinaryTask`（`providerKey` 非空的行拒绝通用写）→ `assertBusinessStatus`（已有带 `invocationId` 的执行行时禁止直接写完成态，抛 `DecisionRequired`）→ 保存。

读与投影：`ProjectTaskGraphService.graph` 在项目行锁内取 provider 快照并落库，`readGraph` 组装 `tasks`/`executions`/`cursor`/`diagnostics` 与展示字段（`assigneeName`/`assigneeAvatar`/`presentation`/`executor`）；`resolveExecution` 把一次 attempt 还原成可导航的 `{projectId, conversationId, threadId, agentExecutionId, xpertId}`。任务类型由 provider 声明，`registeredProjectTaskTypes` 强制「key 必须带 provider 前缀且不重复 + icon 必须来自注册枚举」。

依赖与重排：`predecessorIds`、`parentTaskId`、`plannedStartAt`/`plannedEndAt`/`estimatedDurationMs` 只能经图命令写入，HTTP 侧由 `projectTaskPlanSchema`（zod `.strict()`，含 `taskId`、`expectedRevision`、`predecessorIds`、计划时间与时长）校验后进 `ProjectTaskGraphService.change`；`change` 在事务内锁项目行、锁任务行并按 `id` 逐行重建 `predecessorIds`。`reorder` 只改 `order`/`column`，是看板列内的轻量重排。

## 2. 任务步骤与日志

步骤落在 `xpert_project_task_step`（`taskId` + `stepIndex` + `description` + `notes` + `status ∈ pending|running|done|failed`），日志落在 `xpert_project_task_log`（`stepId` 级联 + `logType ∈ input|output|error` + `content`）。`updateTaskSteps` 在项目锁内按 `stepIndex` 就地合并步骤、`notes` 为追加式拼接，并有两条关键分支：**仅当该任务没有任何带 `invocationId` 的执行行且全部步骤 `done`** 时才把任务隐式推进为 `done`；若调用方显式带 `blocked` 则保留业务状态（`services/project-task.service.spec.ts` 正好覆盖这两条）。

读侧副作用：`XpertProjectTaskSubscriber.afterLoad` 按 `stepIndex` 就地排序 `steps`，因此「有序 steps」只在经 TypeORM 加载后成立。另有 `project-task-step.service.ts` 与 `project-task-runtime-timing.ts` 两个辅助件：前者是步骤侧薄服务，后者把 `XpertAgentExecution` 的 `status`/`createdAt`/`completedAt` 归一为 `runtimeStatus`/`runtimeStartedAt`/`runtimeCompletedAt`（源码注释：「A wall-clock end cannot be reconstructed from elapsed time across pauses or metadata updates.」）。

## 3. 执行派发运行时

**派发（`ProjectTaskDispatchService.dispatch`）**：入口是命令而非控制器（`project-task-dispatch.command.ts` 的 `DispatchProjectTaskCommand`）。顺序为：`projectTaskDispatchInputSchema` 校验 → `ProjectTaskRuntimeContextService` 还原 caller 为 `AgentInvocationScope`（校验会话/线程/执行行/助手与项目关系，群运行时走 `AuthorizeGroupTaskCallerCommand`）→ 解析目标（`factory.resolveGroupTarget`/`resolveBackgroundTarget`）→ 事务内锁项目行 → 按 `(projectId, createdById, dispatchRequestId)` 查重放（命中则比对 intent/scope/replyTo/target，一致返回原执行行，不一致 `Conflict`）→ 校验 `task.revision === expectedRevision`、任务状态集、`assigneeXpertId` 匹配 → 生成 `specificationSnapshot`（`createProjectTaskSpecificationSnapshot`：标题/描述/requirements/按 `stepIndex` 排序的步骤摘要 + `sha256:` digest）→ 校验前驱全部 `done|completed`（否则 `Dependencies`）→ 扫描同项目未终结 Invocation（`Busy`）→ 写执行行（`invocationId = agentInvocationId(scope, 'project-task:<requestId>')`、`dispatchState='pending'`、`projectedTaskRevision=task.revision`、`attempt=上一尝试+1`、`dispatchIntent` 完整意图）。

**提交（`submit`）**：`intent()` 解析持久化意图（schema 明确「no model-supplied identity fields」），重放也复用原 callId；若已有同 id Invocation 且未在 `queued`，先比对当前规格 digest，再 `factory.createCapturedApi(scope).start(intent.request)`；启动报错但已存在同 request/scope 的持久记录时返回该记录，最后把 `dispatchState` 从 `pending` CAS 成 `submitted`。

**`dispatchState` 状态机与回投影**：`pending → submitted` 是唯一持久位；`invocationStatus`/`runtimeStartedAt`/`runtimeCompletedAt` 是**读投影**（`projectTaskInvocationView` 注释：「Read projection only. The legacy attempt status never replaces the full Invocation status.」），投影失败（id 或 scope 不匹配）时降级为 `queued`/`unknown`。回投影由 `ProjectRuntimeObservationHandler` 完成：项目行锁内取执行行与最新尝试，按 `runtimeTaskStatus` 的三种自动映射推进任务状态，且要求 `projectedTaskRevision === task.revision`、规格 digest 未变，最后把 `projectedInvocationRevision` 推到 Invocation revision。业务验收另由 `ProjectTaskDecisionService.decide` 完成（`assertCanEdit` + 项目锁 + `expectedRevision` + 决策 `requestId` 幂等 + review 证据校验，accept 时 CAS 成 `done` 并把决策 append 进 `decisions`）。

**其余 runtime 件**：`project-task-evidence.ts` 提供 `taskSpecification`/`implementationEvidence`/`reviewReport`/`reviewPrompt` 与 `latestImplementationExecutor`（review attempt 不改变实现身份）；`project-task-runtime-read.service.ts` 组装读模型与 `control`（取消）；`project-task-runtime.errors.ts` 统一 10 个错误码 → 400/403/404/409；`project-task-runtime.handlers.ts` 注册 5 个 handler（改计划/决策/派发/读/列执行器）；`project-task-card.provider.ts` 生成资源卡（缺件时给出 `missing`/`unavailable` 原因）；`project-task-dispatch-recovery.service.ts` 每 5 s 扫 `dispatchState='pending' AND dispatchNextAttemptAt <= now` 的前 20 条，先条件 UPDATE 抢占（下次推到 60 s 后）再以 `access.withActor(intent.scope, ...)` 重放，错误分为 `dispatch_blocked`（终态）与 `dispatch_unavailable`（60 s 后重试）。

## 4. 任务与会话链接

链接表 `xpert_project_task_conversation` 用四元组唯一约束表达四种关系：`origin`（任务源自哪次会话）、`discussion`（默认，讨论）、`execution`（执行会话）、`review`（评审会话），并附 `isPrimary`/`sourceMessageId`/`sourceExecutionId`。写入点唯一：`XpertProjectTaskService.linkConversation` 先校验会话属于同项目、再按四元组 `findOne` 幂等返回。读取面 `listTaskRelations` 同时返回该任务的 conversations 与 executions（executions 里会做 Invocation 观察投影）。

与派发侧的差别值得区分：attempt 行上另有**弱引用** `conversationId`（`onDelete:'SET NULL'`）与 `threadId`，语义是「这次执行发生在哪个线程」；链接表语义是「任务被哪些会话讨论过」。`xpert-task` 侧反向持有 `ChatConversation.taskId`（`onDelete:'SET NULL'`），与本链接表无关，不可混用。

## 5. 计划族

四张表由 `XpertProjectPlanService` 统一维护：`XpertProjectPlan`（`status ∈ draft|active|completed|archived`，`view ∈ board|table|gantt|calendar|list`，`order`，`milestones`/`sprints` 级联）→ `XpertProjectMilestone`（`status ∈ planned|in_progress|completed|blocked`、`dueDate`、`order`，`planId` 级联）→ `XpertProjectSprint`（`status ∈ planned|running|review|done`、`strategyType` 默认 `software_delivery`、`goal`/`startAt`/`endAt`/`retrospective`）→ `XpertProjectSwimlane`（`sprintId` 级联）。

`ensureDefaults` 保证「Default plan（active/board/order 0）+ Uncategorized 里程碑」存在；simple 模式只允许这两个默认对象。`createSprint` 在同一次调用内按 `strategyType` 生成默认泳道（`defaultSwimlanes` 工厂），`updateSprint` 拒绝改 `strategyType`。泳道字段承载调度语义：`kind ∈ backlog|execution`、`priority`、`weight`（默认 1）、`concurrencyLimit`、`wipLimit`、`agentRole`（默认 `planner`）、`environmentType`（默认 `browser`）、`sourceStrategyType`、`sortOrder`。层级读取靠显式 FK + `relations`（无 `@Tree`）。

## 6. 独立任务链

**HTTP 边界**：`XpertTaskController` 继承 `CrudController`，35 条端点全部转调 `XpertTaskService` 的 `*HttpTask` 方法（`updateHttpTask`/`scheduleHttpTask`/`pauseHttpTask`/`archiveHttpTask`/`unarchiveHttpTask`/`testHttpTask`/`deleteHttpTask`/`softDeleteHttpTask`/`recoverHttpTask`），读侧 HTTP 走 `findHttpAccessible`/`findHttpAccessibleById`（做项目成员校验），内部调度与恢复继续用 `findAll`/`findOne`（源码注释：「Internal schedulers deliberately continue to use findAll/findOne so background recovery is not evaluated as the HTTP actor.」）。

**CRUD 与生命周期**：创建走 `CreateXpertTaskCommand`（run-as 必须为本人、Trial 上限、`agentKey` 校验、写 `schedule:null` + `status=SCHEDULED` 并入队）；`schedule` 重解析项目当前助手版本 → 连接器预检 → `rescheduleTask` → `SCHEDULED` + 清 `statusReason`；`pause`/`archive` 先 `deleteJob` 再写状态；**`unarchive` 落到 `PAUSED` 且不排程**；`softDeleteHttpTask = pause + softRemove`，`recoverHttpTask` 只软恢复、不重建 job。

**触发与执行**：三套机制并存——① Bull 队列 `xpert-task-scheduler`（`TaskSchedulerProcessor.process` 只做一次性入队后的 `schedule(taskId)`）；② 进程内 cron 主路径 `scheduleCronJob`（`CronJob.from({cronTime, timeZone})` + `schedulerRegistry.addCronJob(task.id, job)`，`taskCronExpression` 优先 `schedule` 否则由 `options` 生成，`TaskFrequency.Once` 置 `runOnce`，`cronMinuteOccurrence` 保证延迟回调仍落在原分钟边界）；③ `@Cron` 扫描（`recoverExpiredScheduledTaskExecutions` 恢复过期租约、`runDueAutoTasks` 在 Redis 锁内处理到期自动任务）。`onModuleInit` 对 `status=SCHEDULED` 且 `options || schedule` 存在的任务重建 job。

**台账与状态回写**：`scheduleCronJob` 的 `onTick` 经 `resolveScheduledOccurrence` + `buildScheduleOccurrenceKey` 得 occurrenceKey 后调 `ScheduledTaskExecutionCoordinator.claim(task, occurrenceKey, scheduledAt)`；协调器由 `TypeOrmScheduledTaskExecutionStore` 支撑（`insertIfAbsent` 用 `orIgnore()`，`claimExpired` 用条件 UPDATE 判 `affected === 1`），租约 5 分钟、`ownerId` 取 `XPERT_INSTANCE_ID || HOSTNAME || randomUUID`，`markRunning`/`bindRun`/`refreshLease` 都是 owner+status 条件更新，失败抛 `lease was lost`，`finish` 清租约并写 `lastError`/`failureCode`。随后 `createPersistedTaskChatRun` 顺序写 `ChatConversationUpsertCommand({status:'idle', taskId, xpertId, projectId, from:'job'})` → `XpertAgentExecutionUpsertCommand({status:RUNNING, threadId})` → `XpertChatCommand({action:'send', from:'job', taskId, streamPersistence})`；本域只持有 `executionId`/`conversationId`，由协调器在完成/失败时写终态，`runtimeState` 里注入幂等键（`resolveTaskRuntimeState` + `XPERT_TASK_SCHEDULE_IDEMPOTENCY_KEY`），**运行不改变 `status`**。无浏览器上下文的运行由 `applyScheduledTaskOidcContext`/`createScheduledTaskOidcToken` 铸造短期 actor token（`act.sub='xpert_task'`，delegated user = `runAsUserId ?? createdById`），仅在 `options.automationContext` 存在且 `context.env.oidc_token` 缺失时注入。

## 9. run-as 提案确认流

两步确认，落库列是 `pendingRunAsUserId`/`pendingRunAsRequestedById`/`pendingRunAsRequestedAt`/`pendingRunAsConfigurationHash`。

**提案（`POST :id/run-as/proposal`）**：DTO `XpertTaskRunAsProposalDTO` + `forbidNonWhitelisted` 管道校验；`proposeProjectTaskRunAs` 要求任务有 `projectId` + `xpertId`，发起人若是当前 run-as 用户需 `assertCanUse`、否则需 `assertCanManage`；目标用户必须是项目可用成员且连接器可用；随后写四列与 `buildProjectTaskRunAsConfigurationHash(task)`（`xpertId` + 排序后的 connector 绑定，sha256）。

**接受（`POST :id/run-as/accept`）**：只有被提名人本人可接受（否则 403）；重算 hash 并比对，不一致即 `ProjectTaskRunAsProposalChanged`；最后用 `update({id, pendingRunAsUserId, pendingRunAsConfigurationHash}, ...)` 条件更新，`affected !== 1` 再抛一次 `ProposalChanged`；成功后若任务为 `SCHEDULED` 则 `rescheduleTask` 用新 run-as 用户重建 job。

**失效**：`invalidatePendingRunAsProposalForConfigurationChange` 在 `updateTask` 时比较配置哈希，配置变更即清空四列（同为条件更新），使「配置变更 = 授权失效」成为硬约束；执行期身份统一取 `task.runAsUser ?? task.createdBy`。

## 12. 热点路径

1. **项目行锁**：任务写、步骤写、批量更新、图快照、派发、决策、回执投影全部在项目行锁内排队；热点项目上「快照/派发/决策/观察」互为瓶颈。
2. **派发事务**：`dispatch` 在单事务内做重放查重 + 全量尝试扫描 + Invocation 状态比对，随项目历史线性变重。
3. **补偿扫描**：每 5 s 一轮 `pending` 行（take 20）先写一次「推迟 60 s」再重放，失败行会持续占用扫描额度。
4. **读投影 N+1**：`ProjectTaskRuntimeReadService.get` 对每个带 `invocationId` 的尝试逐条取 Invocation（`observeProjectTaskInvocations` 用 `In(ids)` 批量），仅适合单任务详情。
5. **回执热路径**：每次回执都要项目行锁 + 最新尝试查询 + 规格 digest 重算。
6. **调度热路径**：`onTick` 每次抢租约 + 60 s 心跳；`runDueAutoTasks` 每分钟锁 Redis 取 20 条；`graph` 每次读都可能触发 provider `snapshot`。

## 14. 技术债与 hack

1. **`scheduler.job.ts` 未使用的注入**：`@Inject(JOB_REF) jobRef` 注入后从未使用，`@Process({concurrency:5})` 也未命名。
2. **创建时清空 `schedule`**：`CreateXpertTaskHandler` 写 `schedule: null`（注释「Clear schedule to avoid confusion」），而 `onModuleInit` 只重建 `options || schedule` 存在的任务，二者耦合脆弱。
3. **`query.handler` 伪造 `PAUSED`**：`SchedulerRegistry` 是本地内存，多实例或重启后取不到 cron job 就把返回体 `status` 改成 `PAUSED`，与库内状态可能不一致。
4. **调度三套机制并存**：Bull 一次性入队 + 进程内 cron + `@Cron` 扫描入口分散，且无 Bull repeatable 统一路径。
5. **`xpert-task` 无版本列**：run-as 接受只能靠「配置哈希 + 条件 UPDATE」，语义弱于 `XpertProjectTask.revision`。
6. **`failureCode` 取值单一**：`ScheduledTaskExecution.failureCode` 仅允许 `LOCAL_RUNTIME_UNAVAILABLE`，`finish` 在租约丢失时还会对 FAILED 从 PENDING 补写一次，终态语义被弱化。
7. **双重删除语义**：`DELETE :id/soft` 与 `DELETE :id` 并存；`PUT :id/recover` 只恢复软删记录、不重建 job，恢复后任务静默不排程。
8. **租约与 Redis 锁 TTL 同值**：`AUTO_TASK_CRON_LOCK_TTL` 与 `SCHEDULED_TASK_LEASE_MS` 同为 5 分钟，长批次扫描理论上可重叠。
9. **`pg_advisory_xact_lock` 依赖 PG 专有锁**：`template-routines` 的串行化在非 PG 测试库上失效。
10. **`dispatchIntent` 的 `select:false` 风险**：备份或数据修复脚本漏加 `addSelect('attempt.dispatchIntent')` 时，恢复链会因 `intent()` 解析失败而不可用。
11. **`[推测]` 读路径副作用**：`XpertProjectTaskSubscriber.afterLoad` 的就地排序使「有序 steps」只在经 TypeORM 加载后成立，任何直接构造实体或共享引用的代码路径都可能拿到未排序数组。
12. **`[推测]` 计划族与任务的连接缺口**：任务行只有裸 `planId`/`milestoneId` 字符串列（无外键、无 `sprintId`/`swimlaneId`），泳道的 `wipLimit`/`concurrencyLimit`/`agentRole` 目前只是配置面，是否被派发或限流逻辑消费需逐调用点确认。

## 15. 设计维度分析

**一致性 vs 吞吐**：项目内任务选择「项目行悲观锁 + `revision` CAS + 幂等键」三件套，代价是同一项目的任务写与派发被完全串行化；独立任务选择「occurrence 唯一索引 + 租约」，代价是多副本需要靠在 Redis 锁与租约超时之间取舍（终态语义弱化并允许过期接管）。两套选择都偏向「先保证不重复、后优化并发」。

**确定性身份 vs 可读 id**：`projectTaskIdentity` 以 sha256 派生 UUID，使 provider 快照可重放且跨次稳定，但 id 不可读、排障必须回查 `providerKey + sourceKey`；执行行同样以 `agentInvocationId(scope, callId)` 预先确定 Invocation id，换来「重放不新造 callId」却把 Invocation 身份与项目作用域强绑定。

**投影单向性 vs 读写便利**：执行状态只有一条单向投影（Invocation → attempt 读投影 → 任务状态 CAS），任何「跳过 digest/版本校验直接写状态」的便利都会破坏可审计性；`assertNativeExecutionInput` 与 `assertOrdinaryTaskInput` 是这条边界的实现手段。

**两套任务模型的边界成本**：项目内任务优化「协作图 + 验收」，独立任务优化「周期调度 + 台账」，边界清晰；但用户视角存在两条「任务」概念，跨域一致性依赖事件最终送达与各侧幂等。

## 16. 结论

实现上，本子域把「业务决策」和「执行事实」切得很干净：任务与步骤写入全部收敛到带项目行锁与 `revision` CAS 的服务方法，执行侧只通过 `dispatchIntent` 钉死意图、通过 `specificationSnapshot.digest` 钉死规格，运行时状态只允许被 `ProjectRuntimeObservationHandler` 单向投影，业务完成必须由 `ProjectTaskDecisionService.decide` 显式确认；`xpert-task` 侧则用 `occurrenceKey` + 租约换「同一时段至多一次执行」，用 run-as 配置哈希换「配置变更即作废授权」。

需要重点防守四处：① `dispatchIntent` 的 `select:false` 与补偿扫描的耦合（漏选即不可恢复）；② 调度三套机制与「创建时清空 `schedule`」的耦合；③ `xpert-task` 无版本列导致的弱 CAS 语义；④ 计划族与任务只有裸字符串列相连，泳道调度字段尚未与派发打通。新增能力应继续走「命令入口 + 事务内 CAS + 幂等键」的既有骨架，不要绕开属主列断言直改任务或执行列。
