  --runTestsByPath packages/server-ai/src/xpert-project/services/project-task.service.spec.ts

## 3. 需 PG / Redis / 外部依赖的用例

## 4. 缺口

1. **派发运行时的闭环未覆盖**：真实 Agent 派发与回执闭环缺失——`project-task-dispatch.integration.spec.ts` 的 adapter（`AgentInvocationFactoryService` 侧策略）仍是桩，`start/inspect/cancel` 为 `jest.fn`；`ProjectRuntimeObservationHandler` 的 CAS 投影与 digest 复算没有独立 spec。
2. **调度 job 无直接 spec**：`scheduler.job.ts`（`TaskSchedulerProcessor`）没有直接用例，`create.handler.ts`/`delete.handler.ts`/`template-routines.handler.ts` 也同样无直接 spec（create 仅被 middleware spec 间接经过）。
3. **run-as 确认流覆盖偏薄**：只有 `dto/run-as.dto.spec.ts` 的管道级用例；`acceptProjectTaskRunAs` 的 hash 重算、`affected !== 1 → ProposalChanged`、配置变更主动失效三条路径仅由 `xpert-task.service.spec.ts` 间接覆盖，无独立 spec。
4. **计划族零 spec**：`XpertProjectPlanService`（plan/milestone/sprint/swimlane、`ensureDefaults`、`defaultSwimlanes`、backlog 保留键与 simple/advanced 模式约束）在 49 个 spec 中**没有对应文件**，泳道 `wipLimit`/`concurrencyLimit`/`agentRole`/`sourceStrategyType` 的语义完全未被测试锁定。
5. **`xpert-task` 无真库覆盖**：`uq_xpert_task_execution_occurrence` 唯一约束与 `(status, leaseExpiresAt)` 索引语义只在内存 store 上验证，coordinator 的条件 UPDATE（`affected === 1`）未在真库取证。
6. **多副本语义无集成验证**：`SchedulerRegistry` 是本地内存，`query.handler.ts` 取不到 cron job 时把返回体 `status` 伪造成 `PAUSED` —— 该分支只有单元级断言，没有多实例/重启场景的集成用例。
7. **属主列断言的负例覆盖不明**：`assertNativeExecutionInput`（拒绝外部写 `invocationId`/`dispatchState`/`dispatchIntent`/`purpose`/`specificationSnapshot`）在本子域 spec 中未见逐列断言，属主列越界写入只能靠 HTTP 边界与集成面间接防守。
8. **补偿扫描的失败分类缺覆盖**：`ProjectTaskDispatchRecoveryService` 的 `dispatch_blocked`（终态）与 `dispatch_unavailable`（60 s 重试）两条分支没有直接 spec。
9. **`dispatchIntent` 漏选风险无常驻守卫**：`select:false` 的正确性依赖恢复链显式 `addSelect`，测试层面缺少「移除 addSelect 即失败」的回归用例。

章节来源：[project-task-dispatch.integration.spec.ts](file://packages/server-ai/src/xpert-project/runtime/project-task-dispatch.integration.spec.ts)、[scheduler.job.ts](file://packages/server-ai/src/xpert-task/scheduler.job.ts)（关键符号：TaskSchedulerProcessor.process）、[project-plan.service.ts](file://packages/server-ai/src/xpert-project/services/project-plan.service.ts)（关键符号：XpertProjectPlanService.ensureDefaults / defaultSwimlanes）

## 5. 结论

判定：**✅ 可跑（不实跑，仅给命令与判据）**。判据：

1. 本子域 30/31 个 spec 不连任何外部服务（Repository、DataSource、RedisLock、Bull queue 全 mock），可直接用第 2 节命令本地执行；任务图/runtime/插件/视图四处均有独立用例；
2. 唯一真库用例 `project-task-dispatch.integration.spec.ts` 默认 `describe.skip`，只有注入以 `/xpert_execution_test_` 开头的库 URL 才解锁，不会污染平台库；
3. `scheduled-task-oidc-token.spec.ts` 需 `JWT_SECRET` 与 `XPERT_TASK_OIDC_TOKEN_*`，未设置属**环境前置**而非代码缺陷；
4. 本子域 spec 全部在 `packages/server-ai/jest.config.ts` 下执行，无需切换配置；仓库内未发现 known-fail / skip 白名单说明，所有 `skip` 均为条件开关。

测试面上的最大风险不是「跑不起来」，而是**覆盖面偏斜**：任务图与派发意图的单元边界测得很密（身份稳定性、投影规则、决策时间戳、类型与展示），而「计划族」「调度 job」「run-as 接受路径」「真实派发—回执闭环」「补偿失败分类」几乎没有直接用例。补充优先级建议：计划族 service spec → `scheduler.job`/create-handler 直测 → run-as 接受与失效三条路径 → 真库 occurrence 约束 → 派发—回执闭环（策略替身 + 真库）。
