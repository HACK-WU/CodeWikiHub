## D1 作用域来源显式化：一律经 `RequestContext`，不信任请求体
- **分类**：架构设计
- **动机**：无此项（实现层只记录为不变量，未记载形成该不变量的事故背景）
- **决策**：租户 / 组织作用域只从 `RequestContext` 派生（登录态与请求头），服务层禁止直接取请求体里的 `tenantId` / `organizationId` 作为作用域；跨作用域访问由守卫与服务层手工校验共同兜底（如 tenant 的 `:id` 三个方法比对当前租户，否则 403）。
- **背景约束**：本域多数表继承 `TenantBaseEntity` / `TenantOrganizationBaseEntity`，`TenantAwareCrudService` 会自动补 `tenantId` 过滤；但 `custom_smtp` / `email_template` 的 `organizationId` 来自调用方传参，因此仍存在「作用域由入参决定」的写入面。
- **被否决方案**：直接采用请求体 / 查询参数中的 `tenantId`、`organizationId` 作为作用域来源（01 篇不变量 1 明写「禁止直接信任请求体」）。
- **重新评估触发条件**：出现跨租户数据可见 / 可写的安全事件，或落地 `PLAN_isolate_tenant_org.md` 中提出的统一 scope-aware 基类（可观测：`findWithInheritance` / `writeToCurrentScope` 等 helper 出现调用点）。
- **关联代码**：`RequestContext.currentTenantId / isTenantScope @ packages/server/src/core/context/request-context.ts`；`ReferralService.getRelations / validateCode @ packages/server/src/referral/referral.service.ts`；`FeatureOrganizationService.updateFeatureOrganization @ packages/server/src/feature/feature-organization.service.ts`
- **证据来源**：`01-架构.md`「关键设计约束与不变量 1」明写；`file://docs/plans/PLAN_isolate_tenant_org.md`（实现层引用的原则来源）；源码事实（非 tenant scope 直接 400）

## D2 `organizationId IS NULL` = 租户默认值
- **分类**：架构设计
- **动机**：无此项（实现层明写为不变量与约束，未记载替代方案的取舍纪要）
- **决策**：`feature_organization`、`custom_smtp`、`email_template` 三张表的「租户默认值」统一以 `organizationId IS NULL` 落库，非空行表示组织级覆盖；读侧一律「组织优先、租户（NULL）兜底」，写侧对是否允许组织级分别约束。
- **背景约束**：三张表共用一套实体基类，`organizationId` 可空；`null` 语义使每个读点都要成对查询（组织级 + NULL 级），也让「未配置」与「配置为空」在数据库层面无法区分。
- **被否决方案**：把 null 语义上浮到业务层自由解释（实现层引用的 `PLAN_isolate_tenant_org.md` 明写该语义「只允许存在于 repository / helper 层」）。
- **重新评估触发条件**：出现「同一租户内组织级配置需要级联到子组织」或多维覆盖（组织 × 用户）需求（可观测：读侧回退链超过两级，或出现按组织树继承的配置单）。
- **关联代码**：`FeatureOrganization @ packages/server/src/feature/feature-organization.entity.ts`；`CustomSmtpService.getSmtpSetting @ packages/server/src/custom-smtp/custom-smtp.service.ts`；`EmailService.getEmailInstance / render @ packages/server/src/email/email.service.ts`
- **证据来源**：`01-架构.md`「关键设计约束与不变量 2」明写；`04-模型.md`（`feature_organization` 业务约束、`email_template`/`custom_smtp` 说明）明写

## D3 退役 feature code 是墓碑，不是「删除即忘」
- **分类**：兼容处理
- **动机**：避坑 —— 现象：feature 定义随版本演进被废弃，但库中已按 code 落了 `feature_organization` 开关行；后果：只删定义会留下无法解释的开关数据并在分组列表露出幽灵条目。因此改为「读侧过滤 + 启动期物理清理」双段处理。
- **决策**：硬编码 `RETIRED_FEATURE_CODES` 集合既用于读侧递归过滤（`getParentFeatures`），也用于启动钩子的物理清理——在**同一事务内先删 `feature_organization` 再删 `feature`**。
- **背景约束**：清理是每次启动都执行的副作用，属于数据面变更；`feature` 自带 `parent → children` 级联，删除顺序错误会留下悬挂开关。
- **被否决方案**：无（未见「立即删除定义、不保留 code 清单」或「只过滤不清理」的取舍记载）
- **重新评估触发条件**：出现「历史开关配置需要保留审计」的合规要求，或退役 code 清单膨胀到需要数据化维护（可观测：`RETIRED_FEATURE_CODES` 条数、每次启动的删除行数）。
- **关联代码**：`RETIRED_FEATURE_CODES / purgeRetiredFeatures / getParentFeatures @ packages/server/src/feature/feature.service.ts`
- **证据来源**：`01-架构.md`「关键设计约束与不变量 6」明写；`03-数据流转.md`（链三）明写「启动时在一个事务内先删 `FeatureOrganization` 再删 `Feature`」

## D4 开关缓存用「版本号失效」而不是删除用户态 key
- **分类**：性能取舍
- **动机**：避坑 —— 现象：用户态开关上下文（`user:me:feature-context`）按用户 × 组织关系集合成键，一次开关写入会影响大量用户；后果：若逐个删 key，则失效成本随用户数放大。改为写一个版本号，让所有旧 key 自然 miss。
- **决策**：任何开关写入后**无条件** bump 租户级版本号（`user:me:feature-context:tenant-version:<tenantId>`，TTL 24h），用户态缓存键内嵌 `v1:<tenantId>:<userId>:<relationsHash>:<version>`；版本变化即整体失效，180s TTL 作兜底。
- **背景约束**：缓存组件不支持按前缀扫描删除；版本计数为进程内 `cache-manager` 值，`@Optional()` 注入，缺失时只有 TTL 生效。
- **被否决方案**：逐个 / 按键删除用户态缓存（02 篇「设计维度一」以「删 N 个用户的 key」对比「写 1 个字节」，明确否定前者）。
- **重新评估触发条件**：缓存后端换成支持前缀扫描并出现「写一个开关要立刻清空」的强一致需求；或版本键与 TTL 的组合被观测到失效窗口不可接受。
- **关联代码**：`touchCurrentUserFeatureTenantCacheVersion / buildCurrentUserFeatureCacheKey @ packages/server/src/user/current-user-feature-cache.ts`；`FeatureOrganizationService.updateFeatureOrganization @ packages/server/src/feature/feature-organization.service.ts`
- **证据来源**：`01-架构.md`「关键设计约束与不变量 4」明写；`02-实现.md`「设计维度一」明写；`07-运维.md`（缓存 TTL 表）明写

## D5 租户设置按请求缓存 5 分钟，且写后不做失效
- **分类**：性能取舍
- **动机**：避坑 —— 现象：每个带 `Authorization` 的请求都会在中间件里读一次租户设置，若不缓存则是「每请求一次 DB `find`」；后果：设置读取成为全站固定开销。用 5 分钟 TTL 换成单次缓存读，代价是写后最长 5 分钟读旧值（实现层明确记为已知缺陷）。
- **决策**：`TenantSettingsMiddleware` 用 `tenantSettings_<tenantId>` 缓存整体设置（TTL 5 分钟，未命中回源），保存设置后**不清除该键**；需要读真值时走 `GET /tenant-setting` 直读接口绕开缓存。
- **背景约束**：缓存键按租户整体缓存（不是按 key），且空结果 `{}` 也会被缓存；中间件异常只 `console.error` 后继续请求；`saveSettngs` 是「查现状 + 一次性 `save`」的 upsert，没有唯一约束保护。
- **被否决方案**：无（未见把「写后立即失效设置缓存」作为取舍项的记载；实现层仅把它列为已知缺陷）
- **重新评估触发条件**：出现因「设置写后 5 分钟仍读旧值」的用户可感知问题（可观测：设置类工单量、中间件缓存命中率、`fileStorageProvider` 切换后生效延迟）。
- **关联代码**：`TenantSettingsMiddleware.use @ packages/server/src/tenant/tenant-setting/tenant-settings.middleware.ts`；`TenantSettingService.getSettings / saveSettngs @ packages/server/src/tenant/tenant-setting/tenant-setting.service.ts`
- **证据来源**：源码事实（TTL 常量与无失效调用点）；`02-实现.md` 技术债 4 明写；`07-运维.md`「缓存 TTL 与失效策略」明写

## D6 出站邮件：传输与模板都走多级回退，失败静默
- **分类**：兼容处理
- **动机**：避坑 —— 现象：部署形态差异大（有的租户配自有 SMTP，有的只配环境变量；模板可能只做英文，也可能只存在于租户级）；后果：任一级缺失就让「注册 / 邀请 / 找回密码」整条业务报错，用户完全无法自助。因此读侧全线回退，代价是错误被吞、投递不可观测。
- **决策**：传输侧按「组织级 `custom_smtp` → 租户级（`organizationId IS NULL`）→ 环境默认（`MAIL_*`）」回退，且每级发送前实时 `verify`；模板侧按「组织级 + 目标语言 → 组织级 + 英文 → 租户级 + 目标语言 → 租户级 + 英文」回退；`send*` 全程 `try/catch + console.error`，失败不冒泡但仍写 `email_sent`；收件人命中 `@example.com` 时跳过真实发送、只写记录。
- **背景约束**：回退链每级都新建连接做 SMTP 握手且**不做缓存**，失败路径的连接开销成倍增长；`createEmailRecord` 反查模板时不带 `tenantId`，可能关联到其他租户的同名模板；发送记录无状态列，成功与失败不可区分。
- **被否决方案**：无（未见「配置缺失即抛错」或「投递失败入队重试」的取舍记载；仓库内队列实现在 `managed-queue/`，本域未引用）
- **重新评估触发条件**：出现「邮件必须可证明送达」的业务 / 合规要求（可观测：投递失败工单、发信耗时分布、`verify` 握手次数）；或环境默认 SMTP 被弃用。
- **关联代码**：`EmailService.getEmailInstance / render / createEmailRecord @ packages/server/src/email/email.service.ts`；`CustomSmtpService.getSmtpSetting / verifyTransporter @ packages/server/src/custom-smtp/custom-smtp.service.ts`
- **证据来源**：源码事实；`02-实现.md`（邮件三级回退、技术债 7/8）明写；`03-数据流转.md`（链四）明写。口径差异提示：实现层 01/03 描述为「任一级验证失败即进入下一级」，源码核实结果只有 `NotFoundException`（未配置）分支会降级，其余异常在外层 catch 中被吞掉——本文以源码为准。

## D7 公开校验接口 fail-closed：限流不可用即拒绝
- **分类**：安全合规
- **动机**：避坑 —— 现象：`GET /referral/validate` 无鉴权、每次都执行一次带 join 的存在性查询；后果：公开端点可被高频调用放大为数据库压力与码枚举面。因此加 Redis 原子计数限流。
- **决策**：公开校验先按「租户 + 客户端 IP 哈希」做 60 秒 / 30 次限流（`INCR` + 首次 `PEXPIRE`），超限 429；**Redis 不可用或返回值非法时抛 500 而不是放行**（fail-closed）；同时要求码所属用户未被软删。
- **背景约束**：限流窗口与上限为模块级常量（不可用环境变量调节）；Redis 成为该公开接口的硬依赖，故障期等于公开校验能力不可用；`REDIS_ENABLED` 在部署样例中出现但未被 Redis 模块读取。
- **被否决方案**：无（未见「限流失败即放行」或「去掉限流」的取舍记载）
- **重新评估触发条件**：公开校验接口的可用性要求高于防滥用要求（可观测：由 Redis 故障引发的 500 率、限流命中率与误伤率）。
- **关联代码**：`ReferralValidationRateLimitService.assertAllowed @ packages/server/src/referral/referral-validation-rate-limit.service.ts`；`ReferralService.validateCode / validatePublicCode @ packages/server/src/referral/referral.service.ts`
- **证据来源**：源码事实（Lua 脚本、常量与抛错分支）；`02-实现.md`「设计维度三」明写「公开返利接口 fail-closed 限流」；`03-数据流转.md`「已知风险与坑」明写

## D8 邀请码字符表与 DB CHECK 双重约束
- **分类**：数据一致性
- **动机**：避坑 —— 现象：邀请码需要被人工转录与口述传递（源码注释与常量即为「去混淆字符表」，剔除 `0/1/I/O`）；后果：若允许全部字母数字，会产生不可分辨的输入错误与反复校验失败。因此生成端限定字符表，数据库端再加 CHECK 兜底。
- **决策**：码固定 10 位、只取 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`；插入用 `orIgnore()` + 最多 10 次重试保证并发幂等；换码在事务内加 `pessimistic_write` 行锁并避开旧值；DB 侧用 `CHK_referral_code_uppercase` 与 `CHK_referral_code_format` 正则二次约束。
- **背景约束**：两条唯一索引（`(tenantId, code)`、`(tenantId, userId)`）与 CHECK 都只在 schema sync / 独立建表流程中生效，仓库内没有迁移文件；用户被物理删除后关系行 `SET NULL` 仍保留。
- **被否决方案**：无（未见「允许更短码」「改用 UUID 形式的码」等取舍记载）
- **重新评估触发条件**：码空间不足或冲突重试率上升（可观测：`referral_code` 行数 / 36^10 的理论空间占比、生成失败错误 `ReferralCodeGenerationFailed` 频次）；或部署切换为 `DB_SCHEMA_SYNC_MODE=external` 后 CHECK 未随建表流程下发。
- **关联代码**：`referral-code.ts`（字母表与重试）；`ReferralCode @ packages/server/src/referral/referral-code.entity.ts`（唯一索引与 CHECK）
- **证据来源**：源码常量与实体的 `@Unique` / `@Check` 声明；`02-实现.md`（邀请码生成、限流）明写；`04-模型.md`「业务约束（DB CHECK）」明写

## D9 购买类开关禁止组织级配置
- **分类**：安全合规

- **关联代码**：`FeatureOrganizationService.updateFeatureOrganization @ packages/server/src/feature/feature-organization.service.ts`；`AiFeatureEnum.FEATURE_MEMBERSHIP_PURCHASE @ packages/contracts`
- **证据来源**：源码事实（分支、i18n key 与默认文案）；`feature-organization.service.spec.ts` 中存在对应的拒绝用例；`03-数据流转.md`「已知风险与坑」明写

## D10 邮件模板以目录约定为准，seed 按事件播种
- **分类**：接口契约
- **动机**：避坑 —— 现象：模板既要有平台内置默认值，又允许租户 / 组织覆盖，还要支持多语言与多用途（html / subject / text）；后果：如果没有固定命名契约，发送侧无法用「名字 + 语言 + 作用域」定位模板。因此把「目录结构 → 数据行」的映射写死在 seed 里。
- **决策**：目录约定 `[template-name]/[language-code]/[template-type].(mjml|hbs)`，入库时 `name = "[template-name]/[type]"`、`languageCode = "[language-code]"`，`.mjml` 编译为 `hbs`、无 `hbs` 的文件被忽略；新租户由 `tenant.created` 事件同步播种；目录按 5 个候选路径探测，全缺失时只 warn 并跳过。
- **背景约束**：`name` 依赖目录结构，改名即改变既有数据语义；`email_template` 无唯一约束，同一 `name + languageCode + scope` 可多行；`createEmailRecord` 反查模板时不带 `tenantId`。
- **被否决方案**：无（未见「改为数据库直填 / 对象存储托管模板」或「模板版本化」的取舍记载）
- **重新评估触发条件**：模板需要版本化或可视化编辑（不再依赖仓库目录），或部署形态无法携带 `default-email-templates` 目录（可观测：seed 的 warn 日志、模板行缺失导致的空内容发送）。
- **关联代码**：`createDefaultEmailTemplates @ packages/server/src/email-template/email-template.seed.ts`；`resolveDefaultEmailTemplateFolder @ packages/server/src/email-template/default-email-template-path.ts`；`EmailTemplateService.handleTenantCreatedEvent @ packages/server/src/email-template/email-template.service.ts`
- **证据来源**：`email-template.seed.ts` 顶部 docstring 明写目录约定与 `template-type` 取值；`07-运维.md`（硬编码常量表：模板目录候选路径、缺失即跳过）明写

## D11 onboarding 把五类数据串成一条链，且不包事务
- **分类**：数据一致性
- **动机**：避坑 —— 现象：一次建租户要写租户行、角色与权限、开关、设置、用户绑定五类数据，还可能建默认组织与播种模板，其中任一步都有可失败的外部条件（例如 `SUPER_ADMIN` 角色查不到）；后果：中途失败会留下半初始化租户（已建角色 / 开关 / 设置，但用户未绑定租户与角色）。当前选择是保持线性编排、把失败面暴露给调用方，而不是引入跨表事务。
- **决策**：`onboardTenant` 以逐步 `await` 的线性顺序完成五类写入（tenant → role/permission → feature toggle → tenant setting → user 绑定 tenant/role），可选建默认组织，最后 `emit(EVENT_TENANT_CREATED)` 触发模板播种；整条链**无事务包裹**，模板播种同步执行且异常自吞。
- **背景约束**：链路依赖多个 CQRS 命令与事件；`POST /tenant/onboard` 的前置判定（`count()>0` 与同名查询）是两次独立查询、非原子；清理半初始化租户没有专门入口，只能走 seed / CLI 或手工修数。
- **被否决方案**：无（未见「把 onboarding 收敛为单事务」或「改为异步作业 + 幂等重试」的取舍记载；实现层只把它列为技术债）
- **重新评估触发条件**：出现半初始化租户的用户可见故障（可观测：存在租户行但无用户绑定 / 无 toggle 的租户数，`onboard` 500 率）；或引入 `DB_SCHEMA_SYNC_MODE=external` 后 DDL 与写入顺序需要显式编排。
- **关联代码**：`TenantService.onboardTenant / prepareTenantCreateInput @ packages/server/src/tenant/tenant.service.ts`；`TenantController.create / onboardDefault @ packages/server/src/tenant/tenant.controller.ts`
- **证据来源**：`02-实现.md`（「整条链路没有事务包裹」与技术债 6）明写；`01-架构.md` 结论与 `03-数据流转.md`「已知风险与坑」明写；`07-运维.md`（Seed 与启动副作用表）明写

## 决策之间的张力（供评审提示）
- D2（`null` 即租户默认）与 D9（购买类开关禁用组织级）共同决定：**配置继承的读侧一致、写侧边界不一致**——新增可继承配置时要单独回答「是否允许组织级写入」。
- D4（版本号失效）与 D5（设置纯 TTL）是本域两种失效哲学的对照：改开关是准实时、改设置要等 5 分钟；排障文档必须同时写清这两条。
- D6（回退 + 静默）与 D7（fail-closed）方向相反且都应保留：邮件属于「尽力送达」路径，公开校验属于「宁可拒绝」路径。
- D11（无事务 onboarding）是所有其他决策的放大器：D3 的启动期清理、D10 的事件播种都可能落在这条链上，评审新建租户流程时需一起看。
