## 概览

本域共 12 个 spec，全部为**纯单元测试**：不使用 `@nestjs/testing`，不连数据库、不连 Redis、不起网络，均以 `new Service(...)` 手工注入普通对象 mock。12 个 spec 已逐文件通读，无 `it.skip` / `xdescribe` / `todo` / `only`，未发现已知失败。

章节来源：[jest.config.ts](file://packages/server/jest.config.ts)（关键符号：displayName/preset/testEnvironment）

## 测试位置与命名惯例

- 位置：spec 与被测源码**同目录同前缀**（如 `tenant/tenant.service.ts` ↔ `tenant/tenant.service.spec.ts`），无独立 `test/` 目录。
- 命名：`<被测文件>.spec.ts`；跨文件的组合场景也沿用被测主体命名（如 `feature/commands/handlers/feature-bulk-create.handler.spec.ts`）。
- 命名粒度：`describe` 用被测类名或场景名（例：`describe('ReferralService registration binding')`），`it` 为完整英文行为句（例：`it('retries when a generated code collides')`）。

章节来源：[tenant.service.spec.ts](file://packages/server/src/tenant/tenant.service.spec.ts)（关键符号：describe('TenantService')）

## 框架与运行方式

- 框架：Jest + ts-jest（`tsconfig.spec.json`），预设 `@nx/jest/preset`，`testEnvironment: node`；`moduleNameMapper` 将 `@xpert-ai/contracts` 映射到 `<rootDir>/../contracts/src/index.ts`（直接测源码，无需先构建 contracts）。
- Nx target：`packages/server/project.json` 的 `test`（`@nx/jest:jest`，jestConfig 指向 `packages/server/jest.config.ts`）。
- 运行（已实测可用，2~5s 量级）：
  - 指定文件：`cd /root/xpert && node node_modules/jest/bin/jest.js --config packages/server/jest.config.ts --runTestsByPath packages/server/src/referral/referral.service.spec.ts`
  - 整域（12 个路径一次传入 `--runTestsByPath`）或整包：`corepack pnpm nx test server`（等价）。
  - 按用例名过滤：追加 `-t "<关键字>"`；覆盖率产物目录 `coverage/packages/server`。

章节来源：[project.json](file://packages/server/project.json)（关键符号：targets.test）

## 断言风格与 mock 模式

- 断言：`expect(...).resolves.toEqual/toMatchObject/rejects.toBeInstanceOf/rejects.toMatchObject`；错误语义优先断言**异常类型**（`BadRequestException`、`NotFoundException`）或 **HTTP 状态**（`status: HttpStatus.TOO_MANY_REQUESTS`），错误文案通过 mock i18next 断言 key。
- 依赖替换：`jest.mock('<相对路径>', () => ({...}))` 用于打断循环依赖与重量级依赖（`../core/context` 的 `RequestContext`、`./default-features`、`./feature.service`、`./feature-organization.entity`、`../../feature.seed`、`i18next` 的 `t`）。
- Repository mock：手写链式 QueryBuilder 桩（`mockReturnThis()` 逐级返回，末端 `execute/getOne/getManyAndCount` 给值），或直接 `jest.spyOn(service, 'findAll')` 桩掉基类方法。
- 时钟/随机：断言邀请码时用正则约束字母表与长度（`/^[23456789ABCDEFGHJKLMNPQRSTUVWXYZ]{10}$/`），不做随机值固定。
- 全局清理：`beforeEach` 中 `jest.clearAllMocks()`；文件级 mock 用 `jest.restoreAllMocks()`。

章节来源：[referral.service.spec.ts](file://packages/server/src/referral/referral.service.spec.ts)（关键符号：ReferralService 的 QueryBuilder 桩）

## 逐文件覆盖点

### tenant（3 个 spec）

- `tenant.service.spec.ts`（2 用例）：断言 `TenantService.onboardTenant` 传给 `OrganizationCreateCommand` 的 `onboardingSuperAdminUserId` 等于首个超级管理员 id；并在无 `defaultOrganization` 时断言**没有**执行 `OrganizationCreateCommand`。
- `anonymous-tenant-resolver.service.spec.ts`（3 用例）：断言 `resolve` 在候选子域查不到时回退 `DEFAULT_TENANT`（`fallbackApplied: true`）并选出默认组织；严格按 `where.subdomain` 命中租户；组织选择优先级为「isActive 的 isDefault → 最早的 isActive」。
- `tenant-subdomain.util.spec.ts`（2 用例）：断言 `normalizeTenantSubdomain` 把空格/下划线/连续连字符折叠为小写 `dtt-saa`；空串、纯符号、`undefined` 返回 `null`。

### feature（3 个 spec）

- `feature.service.spec.ts`（5 用例）：断言 `getParentFeatures` 过滤 `RETIRED_FEATURE_CODES`（含子项）并修正 `total`；`seedDB` 先 `purgeRetiredFeatures`（同一事务内先删 `FeatureOrganization` 再删 `Feature`，且 `In(...)` 值等于退役 id 列表）；`onApplicationBootstrap` 即执行同一清理事务；`seedDB` 为已存在子 feature 回填 `parent/parentId`；清理 legacy 顶层重复行（`repository.delete([legacy.id])`）。
- `feature-organization.service.spec.ts`（7 用例）：断言无 `organizationId` 时按 `{tenantId, featureId, organizationId: IsNull()}` 查询；命中已有租户级开关时原地更新且不触碰组织级；组织级 `FEATURE_MEMBERSHIP_PURCHASE` → 抛 `translated:server-ai:Error.MembershipPurchaseFeatureTenantScopeRequired` 且不落库；组织级 `FEATURE_MEMBERSHIP_PLAN` 允许；开关真实变化时**只 emit 一次** `feature.organization.updated`（载荷字段逐个校验）；`updateTenantFeatureOrganizations` 只为叶子 feature 建开关（跳过含 children 的分组）且 `isEnabled` 取自默认定义。
- `feature-bulk-create.handler.spec.ts`（4 用例）：断言 handler 在默认 feature 保存完成前不 resolve（deferred 控制）；保存失败时 `execute` reject 同一错误对象；已有子 feature 按默认定义重新挂父；清理 legacy 重复行。

### referral（5 个 spec）

- `referral.service.spec.ts`（11 用例）：开关关闭时 `bindRegistration` 完全忽略入参（不查码、不落关系）；开关开启但码无效 → `BadRequestException`；有效码（小写入参）规范化后写入 `{tenantId, referrerUserId, referredUserId, usedCode}`；已有关系不覆盖；`getMyCode` 命中已有码不插入、无码时按需 INSERT + `orIgnore`、碰撞后重试、通信用户 → `NotFoundException`；`regenerateMyCode` 在事务内以 `lock: {mode: 'pessimistic_write'}` 原子换码且不动关系，唯一键冲突（`driverError.code=23505`）重试；`getRelations` 返回已删账号占位视图，非租户 scope → `BadRequestException`。
- `referral.controller.spec.ts`（3 用例）：`GET availability` 用 `RequestContext.getScope().tenantId` 调 `isFeatureEnabled`；`validate` 先 `assertAllowed(tenantId, ip)` 再校验码（IP 取 `request.ip`）；`regenerateMyCode` 委托服务。
- `referral-code.entity.spec.ts`（1 用例）：读 TypeORM 元数据断言存在两条 CHECK：`"code" = UPPER("code")` 与字母表正则 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`。
- `referral-code.subscriber.spec.ts`（3 用例）：普通用户 `afterInsert` 生成一条 10 位大写码（正则校验）且 `execute` 恰一次；`UserType.COMMUNICATION` 不取 repository；插入碰撞（首次查不到）后重试 `execute` 两次。
- `referral-validation-rate-limit.service.spec.ts`（2 用例）：`eval` 脚本含 `redis.call('INCR')`，键为 `referral:validation-rate:tenant-1:<hash>` 且**不含明文 IP**，窗口参数 `'60000'`；计数 31 → 拒绝且状态码 `HttpStatus.TOO_MANY_REQUESTS`。

## 测试可执行性

- 就绪状态：可直接执行，无外部依赖（DB/Redis/网络均被 mock 或未触达）；`@xpert-ai/contracts` 通过 `moduleNameMapper` 直接读源码。
- 环境依赖：Node + 仓库已安装的 `node_modules`（`jest`、`ts-jest`、`@nx/jest`）；不需要先 build。
- 命令：见「框架与运行方式」；实测单文件 2~5s 完成（调用方本轮已验证）。默认 `jest.config.ts` 全量跑 server 包会比本域 12 个文件慢，建议日常用 `--runTestsByPath` 锁定本域。

## 新增测试指引

- 放哪：与源码同目录、同前缀命名，例如 `packages/server/src/tenant/tenant-setting/tenant-setting.service.spec.ts`、`packages/server/src/custom-smtp/custom-smtp.service.spec.ts`。
- 怎么写（照抄现有 mock 模式）：
  1. 纯手工实例化：`const service = new XxxService(repo as never, other as never)`，不引 `Test.createTestingModule`。
  2. 需要 `RequestContext` 时，用 `jest.mock('../core/context', () => ({ RequestContext: { currentTenantId: jest.fn(), currentUserId: jest.fn() } }))`，并在 `beforeEach` 里 `jest.mock` 出来的函数上 `mockReturnValue(...)`（参考 `referral.service.spec.ts`、`feature-organization.service.spec.ts`）。
  3. Repository/QueryBuilder 用链式桩：`insert/into/values/orIgnore` 全部 `mockReturnThis()`，末端断言参数与调用次数；复杂事务用 `manager: { transaction: jest.fn(cb => cb(manager)) }`。
  4. i18next 文案用 `jest.mock('i18next', () => ({ t: (k: string) => \`translated:${k}\` }))`，再断言 `server-ai:Error.*` key（参考 `feature-organization.service.spec.ts` 对 membership-purchase 的断言）。
  5. 错误语义断言类型或 `status`，不比对英文文案。
  6. Controller 测试直接 `new XxxController(serviceMock as never)`，构造 `request` 对象桩（`{ ips: [], ip: '...', socket: {} }`）验证限流/限额参数透传（参考 `referral.controller.spec.ts`）。
- 优先补位顺序建议：`tenant-setting.service`/`save.handler`（设置 upsert 与租户隔离）→ `custom-smtp.service.getSmtpSetting`（回退分支）→ `email-template` PUT/DELETE 的 403 分支 → `tenant.controller` 的 405/403/首租户判定。

章节来源：[referral.controller.spec.ts](file://packages/server/src/referral/referral.controller.spec.ts)（关键符号：ReferralController 构造与 request 桩）
