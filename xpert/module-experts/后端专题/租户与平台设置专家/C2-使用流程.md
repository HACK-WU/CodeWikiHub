**通用前置约定（所有配方共用）**
- 认证全局生效：未标 `@Public()` 的路由需 `Authorization: Bearer <jwt>` 等凭据，否则 401。
- 作用域来源：租户取自 `RequestContext`（登录态与 `tenant-id` 头），组织取自请求头与 scope 级别；服务端不信任请求体里的 `tenantId`。
- 守卫组合：tenant / tenant-setting 用 `TenantPermissionGuard`（+ `RoleGuard` / `@Roles(SUPER_ADMIN)`）；smtp / email / email-template 类级 `TenantPermissionGuard`；feature toggle 追加 `PermissionGuard` + `ALL_ORG_VIEW|ALL_ORG_EDIT`。
- `organizationId` 为空表示「租户级默认值」，非空表示组织级覆盖；读侧一律组织优先、租户兜底。
- 缓存口径三档：`tenantSettings_<tenantId>`、`tenant:default` 为纯 TTL（写侧不失效）；`user:me:feature-context` 为版本号强失效 + 180s 兜底；`referral:validation-rate:*` 为 Redis 计数窗口。

## Recipe 1 新建租户并完成 onboarding（五类数据同链）
- **业务目标**：建出一个可用的租户：租户行、角色与权限矩阵、默认开关、默认设置、创建者绑定五项数据一次到位，并按需建默认组织与默认邮件模板。
- **调用顺序**：
  1. 首租户自举：`POST /tenant/onboard`（`@Public()`，201）→ `count()>0` 或同名租户已存在则 400 → `prepareTenantCreateInput`（子域规范化 + 唯一性）→ `LanguageInitCommand` → `FeatureBulkCreateCommand` → `UserCreateCommand(entity.superAdmin)` → `onboardTenant(prepared, user, { skipSubdomainPreparation: true })`。
  2. 已登录用户自建：`POST /tenant`（仅全局鉴权链；`user.tenantId || user.roleId` 非空即 400）→ `onboardTenant(entity, user)`。
  3. 链路内部副作用顺序：建 `tenant` 行 → `TenantRoleBulkCreateCommand`（角色 + 权限）→ `TenantFeatureOrganizationCreateCommand`（只给叶子 feature 建 toggle，并 bump 该租户开关缓存版本）→ `TenantSettingSaveCommand`（写 `fileStorageProvider=LOCAL`）→ 查 `SUPER_ADMIN` 角色 → 把 `tenantId`/`roleId` 写到用户 → 可选 `OrganizationCreateCommand` → `emit(EVENT_TENANT_CREATED)` → 同步播种默认邮件模板。
  4. 校验：`GET /tenant`（`RoleGuard + TenantPermissionGuard` + `@Roles(SUPER_ADMIN)`，只返回当前租户）；`GET /tenant/onboard`（`@Public()`，按请求 `tenant-domain` 匿名解析，settings 只保留 `name` 以 `tenant` 开头项）。
- **事务边界**：整条链路逐步 `await`，**没有事务包裹**；模板播种由事件监听同步执行且异常自吞，不阻断建租户。
- **预期结果**：`tenant` 一行 + 角色/权限行 + 叶子 `feature_organization` 行 + `tenant_setting(fileStorageProvider=LOCAL)` + 用户 `tenantId/roleId` 已绑定 + `email_template` 默认模板；租户级配置统一以 `organizationId IS NULL` 落库。
- **错误处理**：400 `Tenant already exists`（已有租户或同名）；子域非法或重复 → 400（`Tenant subdomain is invalid` / `Tenant subdomain already exists`）；查不到 `SUPER_ADMIN` 角色 → 500；任一步失败都会留下**半初始化租户**，且重跑时用户名已被占用/子域已存在会被前置校验挡回，需走 seed 或 CLI 补齐。
- **真实代码示例**：

## Recipe 2 读 / 写租户设置（含请求级缓存窗口与直读接口）
- **业务目标**：管理员修改租户级键值设置（如 `fileStorageProvider`），并能判断「为什么改了没生效」。
- **调用顺序**：
  1. 写：`POST /tenant-setting`（`TenantPermissionGuard + RoleGuard` + `@Roles(SUPER_ADMIN)`，body 为任意 name→value 映射）→ `TenantSettingSaveCommand` → `TenantSettingSaveHandler`（用 `RequestContext.currentTenantId() || command.tenantId`）→ `saveSettngs(input, tenantId)` 按 key upsert，返回保存后的映射。
  2. 直读（绕过缓存）：`GET /tenant-setting` → `TenantSettingGetCommand` → `getSettings({ where: { tenantId } })`，行式结果压成 `Record<string, any>`。
  3. 请求级读取（消费方）：`TenantSettingsMiddleware` 对 `forRoutes('*')` 生效，`jwt.decode` 取 `tenantId` → 读 `tenantSettings_<tenantId>`，未命中回源并写 5 分钟 TTL → 挂到 `request['tenantSettings']`；`fileStorageProvider` 等由消费方从该对象读取。
- **事务边界**：保存为「查现状 + 一次性 `save`」，无显式事务；缓存写发生在读路径（中间件），与业务写路径无耦合。
- **预期结果**：表中每个 key 一行；请求级快照在保存后**最长 5 分钟仍为旧值**（写侧不失效）。
- **错误处理**：非 `SUPER_ADMIN` → 403；中间件任何异常只 `console.error` 后 `next()`（请求继续，设置为空对象）；`tenant_setting` 无 `(tenantId, name)` 唯一约束，并发写同 key 可产生重复行且取值顺序不确定，排障以直读接口为准。
- **真实代码示例**：
```ts
// packages/server/src/tenant/tenant-setting/tenant-setting.service.ts
async getSettings(request?: FindManyOptions<TenantSetting>): Promise<Record<string, any>>
async saveSettngs(input: ITenantSetting, tenantId: string): Promise<ITenantSetting>

// packages/server/src/tenant/tenant-setting/tenant-settings.middleware.ts

tenantSettings = await this.cacheManager.get(cacheKey);
const ttl = 5 * 60 * 1000; // Cache TTL: 5 minutes
await this.cacheManager.set(cacheKey, tenantSettings, ttl);
```

## Recipe 3 开通 / 关闭一个开关（含组织级覆盖与版本号失效）
- **业务目标**：为某租户（或某组织）启用 / 停用一个功能开关，并让用户态开关快照尽快刷新。
- **调用顺序**：
  1. 写：`POST /feature/toggle`（`TenantPermissionGuard + PermissionGuard` + `@Permissions(ALL_ORG_EDIT)`），body 为 `CreateFeatureToggleDTO[]`（`featureId`、`isEnabled`、`organizationId?`）；控制器把数组拆成多个 `FeatureToggleUpdateCommand` 并行执行，返回 `boolean[]`。
  2. 单点写入：`updateFeatureOrganization(entity)` → 用 `tenantId + featureId + (organizationId | IsNull())` 查现状并取 `previousIsEnabled` → 无记录新建、有记录更新 → **无条件** `touchCurrentUserFeatureTenantCacheVersion(cacheManager, tenantId)` → 仅当 `previousIsEnabled !== entity.isEnabled` 时 emit `feature.organization.updated`。
  3. 校验：`GET /feature/toggle/organizations`（`ALL_ORG_VIEW`）按 `tenantId? / organizationId?` 分页查开关；定义清单走 `GET /feature/toggle/definition`（`@Public()`）。
  4. 用户态生效：`UserService.findCurrentUserFeatureContext` 组装租户级（`organizationId IS NULL`）+ 当前用户组织集合，缓存键 `user:me:feature-context:v1:<tenantId>:<userId>:<relationsHash>:<version>`。
- **事务边界**：单点写入无事务；版本号 bump 是缓存写（版本键 TTL 24h），不删除任何用户态 key，靠键内版本段变化自然 miss。
- **预期结果**：对应 scope 的 `feature_organization.isEnabled` 更新；用户态快照在下一次读取即重建（版本段变化），最迟 180s 兜底；开关由关→开且 code 命中 `FEATURE_MEMBERSHIP_PLAN` 时，server-ai 侧入队 membership 补数任务。
- **错误处理**：无 `ALL_ORG_EDIT` → 403；父级 feature（含 children）不建 toggle，只作展示分组；`cacheManager` 为 `@Optional()` 注入，缺失时版本号不写、只剩 180s TTL；组织级 `FEATURE_MEMBERSHIP_PURCHASE` 被拒（见 Recipe 8）。
- **真实代码示例**：

## Recipe 4 生成并核对返利码（注册绑定与校验）
- **业务目标**：用户拿到自己的邀请码；新用户在注册时用码绑定邀请关系；外部可校验一个码是否有效。
- **调用顺序**：
  1. 自动发码：用户新增 → `ReferralCodeSubscriber.afterInsert(User)` → `ensureReferralCode`（先查后 `insert().orIgnore()`，最多 10 次，跳过 `UserType.COMMUNICATION`）。
  2. 查询与换码：`GET /referral/me` → `getMyCode()`；`POST /referral/me/regenerate` → `regenerateMyCode()`（事务内 `pessimistic_write` 换码，唯一冲突自动重试）。
  3. 公开核对：`GET /referral/validate?code=`（`@Public()`）→ 先把租户 + 客户端 IP 交给限流器 → `validateCode`（内联 join 码所属用户并要求未软删）→ 布尔。
  4. 绑定：注册事务内 `AuthService.register` 调用 `ReferralService.bindRegistration(manager, { tenantId, referredUserId, referralCode })`：先判租户级 `FEATURE_REFERRAL` 开关 → 已有关系直接返回（幂等）→ 码无效 / 自邀 → 400 → 写 `referral_relation`。开关查询：`GET /referral/availability`（`@Public()`）、关系分页：`GET /referral/relations`（`SUPER_ADMIN|ADMIN` + `REFERRAL_VIEW`，`take` 上限 100）。
- **事务边界**：换码在独立事务内加行锁；绑定**复用调用方（注册）事务的 `EntityManager`**；公开校验只读 + Redis 计数。
- **预期结果**：`referral_code` 每用户一行 10 位码（`[23456789ABCDEFGHJKLMNPQRSTUVWXYZ]`）；`referral_relation` 每个被邀请人在租户内至多一行；`validate` 在开关关闭或无租户上下文时恒为 `false`。
- **错误处理**：限流超 30 次 / 60 秒 → 429 `server-ai:Error.ReferralValidationRateLimited`；Redis 不可用或计数非数值 → 500 `server-ai:Error.ReferralValidationRateLimitUnavailable`（**fail-closed**）；生成失败 → `server-ai:Error.ReferralCodeGenerationFailed`；非租户 scope → 400 `...ReferralTenantScopeRequired`；通信型用户或开关关闭 → 404。
- **真实代码示例**：

## Recipe 5 配自定义 SMTP 并验证发信（回退链）
- **业务目标**：为租户或某个组织配置自有 SMTP，确认能连通，并知道实际会用哪一级配置发信。
- **调用顺序**：
  1. 校验连通性：`POST /smtp/validate`（`TenantPermissionGuard`）用 nodemailer `verify()` 实测，返回布尔（异常吞成 `false`）。
  2. 保存：`POST /smtp` → `CustomSmtpCreateCommand`；`PUT /smtp/:id` → `CustomSmtpUpdateCommand`；作用域由 body 的 `organizationId` 决定（空 = 租户级，`organizationId IS NULL`）。
  3. 读取：`GET /smtp/setting?organizationId=`（空则按 `IsNull()` 取租户级，多条按 `createdAt DESC` 取最新）；查询异常时**回退环境默认配置**（`MAIL_*`，且不含认证）而不是报错。
  4. 发信：`EmailService.getEmailInstance({ organizationId, tenantId })` 按「组织级 → 租户级（`organizationId IS NULL`）→ 环境默认（`SMTPUtils.defaultSMTPTransporter()`）」取配置，每级都先 `verifyTransporter`，成功才构造 `email-templates` 实例（`from = fromAddress || 'service@xpertai.cn'`）；随后 `render` 做模板四级回退并 `Handlebars.compile` 渲染，最后落 `email_sent`。
- **事务边界**：配置为单行写入，无事务；发信链路无事务、无队列、无重试，失败只 `console.error`。
- **预期结果**：`custom_smtp` 一行（可多条，最后写入者胜出）；发信命中回退链上第一个可用级别；收件人命中 `DISALLOW_EMAIL_SERVER_DOMAIN`（`@example.com`）时跳过真实发送但**仍写一条记录**。
- **错误处理**：三级全部 verify 失败 → 500 `Error while retrieving tenant/organization smtp configuration`；**回退只在上一级「查不到配置」（`NotFoundException`）时发生**——上一级配置存在但 verify 不通过会抛出并被外层 catch 吞掉，最终返回 `undefined`，发送端在 `(await getEmailInstance()).send(...)` 处再抛错被吞，表现为「邮件没发出、但 `email_sent` 仍落库」；密钥在出参中永远以打码形态（`secretKey/secretPassword`）出现。
- **真实代码示例**：

## Recipe 6 新增 / 改一封邮件模板（目录约定与 seed）
- **业务目标**：为某租户补一封（或多语言一组）邮件模板，并确认发送链路解析到的是哪一份。
- **调用顺序**：
  1. 目录约定：`...[template-name]/[language-code]/[template-type].mjml|hbs`，`template-type` 可为 `html` / `subject` / `text`；默认模板目录按 5 个候选路径探测，全缺时只 warn 并**跳过 seed**。
  2. 落库：`createDefaultEmailTemplates(connection, tenant)`（由 `seed`/`seedModule` 或 `tenant.created` 事件触发）→ `name = "[template-name]/[type]"`、`languageCode = [language-code]`；`.mjml` 经 `mjml2html` 落为 `hbs`，`.hbs` 直接入库，无 `hbs` 的文件被忽略。
  3. 手工编辑：`POST /email-template/template/save` → `EmailTemplateSaveCommand`；`POST /email-template/template/preview` 生成预览 HTML；`PUT /email-template/:id` 先读记录再比对 `tenantId`（跨租户 403）。
  4. 读取：`GET /email-template/template?data=` 走「组织级 + 目标语言 → 组织级 + 英文 → 租户级 + 目标语言 → 租户级 + 英文」；`GET /email-template` 列出当前租户模板。
- **事务边界**：seed 为批量插入 + 幂等查重；`tenant.created` 监听是同步调用且内部吞异常，不影响租户创建。
- **预期结果**：`email_template` 行落库；`organizationId IS NULL` 表示租户/平台级；发送渲染按同序回退，四级全未命中则以空内容渲染（静默）。
- **错误处理**：`name` 依赖目录结构，文件改名 / 移动会改变既有数据的 `name`；`createEmailRecord` 按 `name + languageCode` 查模板且**不带 `tenantId`**，可能关联到别的租户的模板行（`emailTemplateId` 为非空外键）。

## Recipe 7 排障：设置改了不生效 / 开关不刷新 / 邮件未发出
- **业务目标**：把三类高频工单收敛到既知缓存窗口与失败面，而不是重新怀疑整条链路。
- **调用顺序（排查路径）**：
  1. 设置改了不生效：先用 `GET /tenant-setting` 直读确认库内已是新值 → 若消费方仍读旧值，则是请求级缓存 `tenantSettings_<tenantId>`（TTL 5 分钟、写侧无失效）→ 等待 TTL 过期；仓库内没有该键的清理入口。
  2. 开关不刷新：先确认写入 scope（带 `organizationId` 写的是组织级，租户级需要 `organizationId` 为空）→ 再看用户态缓存键的 `version` 段是否变化（写开关会 bump 租户级版本）→ 若进程 `cacheManager` 缺失（`@Optional()`）则只剩 180s TTL 兜底 → 注意父级 feature 不建 toggle，`ReferralService` 走 DB 直查、不受该缓存影响。
  3. 邮件未发出：先看收件人是否命中 `@example.com`（跳过真实发送但仍写记录）→ 再看组织级配置是否存在但 verify 失败（**不会自动降级**，最终不发信）→ 再看模板是否缺失（四级回退后仍缺则空内容）→ 最后看 `email_sent` 记录里的 `emailTemplateId` 是否关联到了别的租户的同名模板。
- **事务边界**：排障本身不写业务数据；设置类问题只能等 TTL，开关类问题等版本号生效（下一次读取即重建）。
- **预期结果**：结论收敛到四类之一：请求级设置缓存窗口 / 开关 scope 选错或缓存未失效 / SMTP 校验失败 / 模板缺失或错配。
- **错误处理**：本域**没有**手动失效缓存的管理端点；`email_sent` 无发送状态列，成功与失败都落库（失败时 `message` 为空），只能靠日志（`console.error`）判断是否真的发出。
- **真实代码示例**：
```ts
// packages/server/src/tenant/tenant-setting/tenant-settings.middleware.ts
const cacheKey = `tenantSettings_${decodedToken.tenantId}`;   // 5 分钟 TTL，写侧不失效
// packages/server/src/email/email.service.ts
const DISALLOW_EMAIL_SERVER_DOMAIN: string[] = ['@example.com'];  // 命中即跳过真实发送
// 组织级 verify 失败分支（外层 catch 只在 NotFoundException 时降级）：
if (await SMTPUtils.verifyTransporter(transport)) { return this.getEmailConfig(smtpConfig) }
```

## Recipe 8 组织级购买类开关被拒（边界与替代做法）
- **业务目标**：知道「为什么给组织单独开购买类开关会 400」，并知道正确做法。
- **调用顺序**：
  1. 触发：`POST /feature/toggle` body 里带 `organizationId` 且目标 feature 的 `code === FEATURE_MEMBERSHIP_PURCHASE` → `updateFeatureOrganization` 在**查现状/写库之前**先判断并抛 400。
  2. 替代做法：去掉 `organizationId`，在**租户级**（`organizationId IS NULL`）配置同一开关，写入成功。
  3. 校验：`GET /feature/toggle/organizations` 观察该 feature 是否只有租户级行；用户态快照按 Recipe 3 的版本号机制刷新。
  4. 下游联动：该族开关由关→开时（`FEATURE_MEMBERSHIP_PLAN`）server-ai 侧入队 membership 补数任务。
- **事务边界**：拒绝发生在任何写入之前，因此不会产生组织级行；批量提交时数组中各条命令并行执行，**批量内没有回滚语义**，一条被拒即整个请求 400。
- **预期结果**：组织级无新增 / 无变更行；租户级行可正常创建或翻转。
- **错误处理**：400，`message` 为 i18n key `server-ai:Error.MembershipPurchaseFeatureTenantScopeRequired`（默认文案 `Membership purchase can only be configured at tenant scope.`）；若确实需要「按组织差异化」，当前版本没有替代开关，只能在租户级统一配置后用其他机制做业务区分（本域无此能力）。
- **真实代码示例**：
```ts
// packages/server/src/feature/feature-organization.service.ts
if (isNotEmpty(organizationId)) {
  feature = await this._featureService.findOne(featureId)
  if (feature.code === AiFeatureEnum.FEATURE_MEMBERSHIP_PURCHASE) {
    throw new BadRequestException(
      t('server-ai:Error.MembershipPurchaseFeatureTenantScopeRequired', {
        defaultValue: 'Membership purchase can only be configured at tenant scope.'
      })
    )
  }
}
```
