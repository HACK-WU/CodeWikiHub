# C0 使用总览：租户与平台设置专家

> 契约层文档（父专家）｜读者：本域外部调用方（同进程服务调用、HTTP 客户端、其他专家）
> 资产基线：**2026-10-16 · commit `80f5676fd`**（资产原基线 `c07bb83d`）
> 配套：同目录 `C1-能力契约.md`

## 1. 专家定位

租户与平台设置专家回答三个问题：**租户从哪来**（创建 / onboarding / 子域与默认租户解析）、**这个租户或组织开没开某个能力**（feature 开关与组织级覆盖）、**这个租户怎么发信与返利**（自定义 SMTP、邮件模板、出站邮件、邀请码与返利关系）。

- 三段式结构：租户（租户行 + 键值设置 + 请求级设置缓存）→ 可继承配置（开关、SMTP、邮件模板三处统一「组织优先、租户兜底」）→ 出口动作（发信、返利码与注册绑定）。
- 对外契约四类：HTTP 端点；同进程服务方法（`TenantService` / `TenantSettingService` / `FeatureOrganizationService` / `ReferralService` / `CustomSmtpService` / `EmailService` / `EmailTemplateService`）；进程内事件（`tenant.created`、`feature.organization.updated`）；TypeORM subscriber（新用户自动发码）。
- 作用域来源统一是 `RequestContext`（租户 / 组织 / 用户一律从上下文取，不信任请求体）；组织级覆盖由调用方显式传 `organizationId`，**空值即租户默认**（读侧按 `organizationId IS NULL` 命中）。
- 全站横切只有一处：`TenantSettingsMiddleware` 以 `forRoutes('*')` 注册，每个带 Authorization 的请求都会读一次租户设置缓存并挂到 `request['tenantSettings']`。

## 2. 何时找这个专家

- 「我要建租户 / 首租户自举 / 改子域 / 删租户」→ 本专家（`/api/tenant*`、`TenantService.onboardTenant`）。
- 「我要按子域解析当前是哪个租户 / 匿名访问默认落哪个租户」→ 本专家（`GET /api/tenant/onboard`、`AnonymousTenantResolverService.resolve`）。
- 「我要读写租户级键值设置（如 `fileStorageProvider`）」→ 本专家（`/api/tenant-setting`、`TenantSettingService.getSettings` / `saveSettngs`）。
- 「我要在请求上下文中拿租户设置，而不改 controller」→ 本专家（`TenantSettingsMiddleware` + `request['tenantSettings']`）。
- 「我要加/查一个功能开关，或判断某租户是否开了某能力」→ 本专家（`/api/feature/toggle*`、`FeatureOrganizationService`、`ReferralService.isFeatureEnabled`）。
- 「我要同步内置 feature 定义 / 清理退役开关」→ 本专家（`POST /api/feature/upgrade`、`FeatureService.seedDB`、启动期清理）。
- 「我要发邀请码 / 校验邀请码 / 看返利关系」→ 本专家（`/api/referral*`、`ReferralService`）。
- 「我要配自定义 SMTP 并验证连通性」→ 本专家（`/api/smtp*`、`CustomSmtpService`）。
- 「我要发业务邮件（欢迎 / 验证 / 重置密码 / 邀请）或改邮件模板」→ 本专家（`/api/email*`、`/api/email-template*`）。
- 「我要改身份、角色、组织、成员、邀请本体」→ **不找本专家**（见 §6）；模型与计费、插件与技能同理。

## 3. 契约自足声明

- 本文 + `C1-能力契约.md` 构成完整对外契约：`C0` 回答「找谁、走哪个入口、有哪些坑」，`C1` 回答「签名、参数语义、返回、异常、约束」。集成与排障无需先读实现代码。
- 契约粒度为 HTTP 端点与同进程服务方法；出现的类名/方法名均为源码原文签名，**包含源码拼写**（例如设置写入方法原文为 `TenantSettingService.saveSettngs`，非 `saveSettings`）。未能核实处显式标注「未确认」。
- 实现细节（算法、私有方法、表列、缓存键构造）不进契约层，仅在「来源」中作为可追溯锚点出现；逐端点明细见实现层 `05-接口.md`。

## 5. 能力清单

| 能力 | 对外入口（HTTP 或服务方法） | 一句话 |
| --- | --- | --- |
| 租户创建（受保护） | `POST /api/tenant` / `TenantService.onboardTenant` | 已登录且尚无 tenantId/roleId 的用户自建租户并成为 SUPER_ADMIN；否则 400 |
| 首租户自举 | `POST /api/tenant/onboard`（`@Public`） | 仅允许首个租户：先初始化语言与 feature 定义、建 superAdmin 用户，再走同一 onboarding 链路 |
| 匿名租户解析 | `GET /api/tenant/onboard`（`@Public`） | 按请求子域命中租户，未命中回退 `DEFAULT_TENANT`；解析不到返回 `null` |
| 租户读改删 | `GET /api/tenant`、`GET|PUT|DELETE /api/tenant/:id` | 一律只操作「当前租户」，非本租户 403；DELETE 返回 202 |
| 基类接口禁用 | `GET /api/tenant/count`、`/api/tenant/pagination` | 显式 405，勿依赖 |
| 租户设置读写 | `GET|POST /api/tenant-setting`（SUPER_ADMIN） | 键值设置（如 `fileStorageProvider`）读映射、按 key upsert |
| 请求级设置注入 | `TenantSettingsMiddleware`（`forRoutes('*')`） | 每个请求把 `request['tenantSettings']` 填好，TTL 5 分钟 |
| 开关定义查询 | `GET /api/feature/toggle/definition`（`@Public`）、`GET /api/feature/toggle/parent` | 内置开关定义清单；顶层 feature 列表（读侧过滤退役码） |
| 开关读写 | `GET /api/feature/toggle`、`/organizations`（`ALL_ORG_VIEW`）；`POST /api/feature/toggle`（`ALL_ORG_EDIT`） | 组织/租户级开关查询与批量写入（组织级购买类开关被拒） |
| 开关定义同步 | `POST /api/feature/upgrade`（SUPER_ADMIN） | 触发 `FeatureService.seedDB()` 重新同步内置定义 |
| 返利可用性与校验 | `GET /api/referral/availability`、`GET /api/referral/validate`（均 `@Public`） | 租户级 `FEATURE_REFERRAL` 判定 / 带 Redis 限流的码校验 |
| 我的邀请码 | `GET /api/referral/me`、`POST /api/referral/me/regenerate` | 按需发码 / 事务内原子换码（旧关系不变） |
| 返利关系查询 | `GET /api/referral/relations`（SUPER_ADMIN/ADMIN + `REFERRAL_VIEW`） | 租户内关系分页，已删账号返回占位视图 |
| 自定义 SMTP | `GET /api/smtp/setting`、`POST /api/smtp/validate`、`POST|PUT /api/smtp(/:id)` | 配置读写与实测连通性；读取异常静默回退默认配置 |
| 邮件记录 | `GET /api/email`、`PUT /api/email/:id`（+ 基类路由） | 发送记录分页与更新（无发送状态列） |
| 邮件模板 | `GET /api/email-template/template`、`POST .../template/preview`、`POST .../template/save` | 模板解析（多级回退）/ 预览 / 保存 |
| 事件与数据层钩子 | `EVENT_TENANT_CREATED`、`EVENT_FEATURE_ORGANIZATION_UPDATED`、`ReferralCodeSubscriber.afterInsert` | 租户创建后播种模板；开关翻转广播；新用户自动获得邀请码 |

## 6. 边界

**做什么**：

- 租户生命周期（创建 / onboarding / 子域规范化与唯一性 / 默认租户解析 / 租户行读改删）与租户级键值设置及其请求级缓存。
- 功能开关全集：定义同步与退役清理、租户/组织级 toggle 写入与查询、变更事件与缓存失效。
- 通知与返利：自定义 SMTP 配置、邮件模板目录约定与多级回退、出站邮件发送与发送记录、邀请码生成/校验/限流/注册绑定。

**不做什么**：

- **身份、权限、组织、成员、邀请本体**属「身份与权限专家」：本域只在 onboarding 中委派 `TenantRoleBulkCreateCommand`、`OrganizationCreateCommand`、`UserCreateCommand`，自身不实现判权与成员语义。
- **模型与计费**（membership、用量计费）属「模型访问与计费专家」：本域只提供开关位与 `feature.organization.updated` 事件，不消费计费结果。
- **插件与技能市场**属「平台插件与技能专家」：本域不含插件装载、技能仓库生命周期。
- **底层基础设施**属 `core/`：缓存实例、Redis 客户端、实体基类、CRUD 基类与全局前缀均由 `core/` / `bootstrap` 提供，本域只消费。

## 7. 已知问题与常见坑

1. **作用域必须显式化**
   现象：租户维度不写进请求体，一律由 `RequestContext` / `TenantAwareCrudService` 注入；组织级覆盖要调用方显式传 `organizationId`。
   正确做法：**`organizationId` 为空即租户默认**（读侧命中 `organizationId IS NULL`），跨作用域读写必须自己把 scope 说清楚。
   契约来源：`FeatureOrganizationService.updateFeatureOrganization`、`CustomSmtpService.getSmtpSetting`。

2. **开关缓存靠版本号失效，而非逐 key 删除**
   现象：写开关会 bump 租户级版本号，使当前用户的 feature 上下文缓存（`user:me:feature-context`，TTL 180s）立即 miss；`ReferralService.isFeatureEnabled` 走 DB 直查，不看该缓存。
   正确做法：开关变更后立刻重新读取即可；但事务内未提交的变更对直查仍不可见。
   契约来源：`FeatureOrganizationService.updateFeatureOrganization`、`touchCurrentUserFeatureTenantCacheVersion`（[current-user-feature-cache.ts](file://packages/server/src/user/current-user-feature-cache.ts)）、`ReferralService.isFeatureEnabled`。

3. **`tenant_setting` 请求级缓存 TTL 5 分钟且写后不失效**
   现象：`POST /api/tenant-setting` 保存后**不清理** `tenantSettings_<tenantId>`，最长 5 分钟内请求仍读到旧值（空结果 `{}` 也会被缓存）。
   正确做法：改设置后不要假设下一次请求立即生效；对时效敏感的消费方直接查库（`TenantSettingService.getSettings`）。
   契约来源：`TenantSettingsMiddleware.use`（[tenant-settings.middleware.ts](file://packages/server/src/tenant/tenant-setting/tenant-settings.middleware.ts)）、`TenantSettingService.saveSettngs`。

4. **中间件只解码 JWT、不验签**
   现象：`jwt.decode` 取 `tenantId`，无 Authorization 头或 token 无 tenantId 时**不会**挂 `tenantSettings`，且中间件内异常只打日志、不阻断请求。
   正确做法：消费方（如文件存储 provider 解析）必须自带兜底默认值，不要把 `request['tenantSettings']` 当作必然存在。
   契约来源：`TenantSettingsMiddleware.use`、`FileStorage.setProvider`（[file-storage.ts](file://packages/server/src/file/file-storage/file-storage.ts)）。

5. **发信与模板都是多级回退，且每一级都做真实握手**
   现象：SMTP 依次尝试组织级 → 租户级（`organizationId IS NULL`）→ 环境默认，每级都新建连接 `verify()`，全失败才抛 500；模板解析再按「组织+语言 → 组织+英文 → 租户+语言 → 租户+英文」四级回退，全未命中返回**空内容**并继续发送。
   正确做法：排障先看「哪一级 SMTP 生效」；不要以「模板一定渲染出内容」为前提。
   契约来源：`EmailService.getEmailInstance`、`SMTPUtils.verifyTransporter`（[utils.ts](file://packages/server/src/email-send/utils.ts)）、`FindEmailTemplateHandler`。

6. **模板 `name` 由目录约定决定，改目录即改匹配键**
   现象：seed 按 `[模板名]/[语言码]/[类型].mjml|hbs` 落库，`name = "[模板名]/[类型]"`（如 `invite-user/html`），发送记录也按该 `name` 关联模板。
   正确做法：文件重命名/移动会改变既有数据的匹配键，需同步更新既有模板行；无 `hbs` 的文件会被忽略。
   契约来源：`createDefaultEmailTemplates`（[email-template.seed.ts](file://packages/server/src/email-template/email-template.seed.ts)）、`EmailTemplateService.handleTenantCreatedEvent`。

7. **邮件发送失败静默，且仍会写一条记录**
   现象：所有 `send*` 方法异常只 `console.error`，随后仍尝试落 `email_sent`（失败时内容为空），调用方无法从返回值或异常感知。
   正确做法：发信成功与否不能以「没抛错」判定；关键通知需外部对账（记录里没有独立状态列）。
   契约来源：`EmailService.welcomeUser`、`sendVerifyEmailMail`、`requestPassword`、`inviteUser`、`sendAcceptEmailInvitation` 系列。

8. **公开校验端点 fail-closed + 限流**
   现象：`GET /api/referral/validate` 先按租户 + 客户端 IP 限流（60 秒 30 次，超限 429）；Redis 客户端无 `eval` 或计数不可解析时直接 500。
   正确做法：把 500 视为「校验能力整体不可用」而非码无效；该端点无鉴权，禁止在其后挂业务写逻辑。
   契约来源：`ReferralValidationRateLimitService.assertAllowed`（[referral-validation-rate-limit.service.ts](file://packages/server/src/referral/referral-validation-rate-limit.service.ts)）、`ReferralController.validate`。

9. **返利码有硬约束（字符集 + 长度 + DB CHECK）**
   现象：码为 10 位，字符表仅 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`（无 `0/1/I/O`）；实体上有「必须大写」与「必须匹配该字母表」两条 CHECK。
   正确做法：不要自行生成或写入其它形态的码；批量导入数据时先过字母表校验，否则插入必然失败。
   契约来源：`ReferralCode`（[referral-code.entity.ts](file://packages/server/src/referral/referral-code.entity.ts)）、`ensureReferralCode`（[referral-code.ts](file://packages/server/src/referral/referral-code.ts)）。

10. **注册时绑定返利码有严格时序与幂等语义**
    现象：`bindRegistration` 必须由调用方在注册事务内、拿到被邀请人 id 之后调用；开关关闭或无码时静默返回，同一被邀请人已绑定则**不覆盖**，码无效或自邀抛 400。
    正确做法：不要把绑定挪到注册事务之外（会丢一致性），也不要用它做「换绑」——换绑需要另建关系路径。
    契约来源：`ReferralService.bindRegistration`、调用方 `AuthService.register`（[auth.service.ts](file://packages/server/src/auth/auth.service.ts)）。

11. **购买类开关禁止组织级配置**
    现象：带 `organizationId` 写 `FEATURE_MEMBERSHIP_PURCHASE` 直接 400（`server-ai:Error.MembershipPurchaseFeatureTenantScopeRequired`）；`FEATURE_MEMBERSHIP_PLAN` 允许组织级。
    正确做法：购买类能力只在租户级开关上做判定，组织级读写会失败而不是被静默忽略。
    契约来源：`FeatureOrganizationService.updateFeatureOrganization`。

12. **退役 feature 是墓碑，不是「读侧隐藏」**
    现象：`RETIRED_FEATURE_CODES` 既用于读侧过滤，也在启动与 seed 时**物理删除**（同一事务先删开关再删定义）。
    正确做法：配置了退役 code 的历史开关数据不会保留，升级后需按新 code 重建。
    契约来源：`FeatureService.seedDB` / `onApplicationBootstrap` / `getParentFeatures`（[feature.service.ts](file://packages/server/src/feature/feature.service.ts)）。

13. **onboarding 一步失败，整条链断且留半成品**
    现象：建租户 → 建角色权限 → 建开关 → 写默认设置 → 查 SUPER_ADMIN 角色 → 绑定用户 →（可选）建默认组织 → 发事件，五类数据同链且**无事务包裹**；缺 SUPER_ADMIN 角色即 500，前面的数据已落库。
    正确做法：租户创建失败后按「租户 id 是否存在」做补偿清理，不要重试整条链。
    契约来源：`TenantService.onboardTenant`（[tenant.service.ts](file://packages/server/src/tenant/tenant.service.ts)）。

14. **两个 TypeORM subscriber 未注册，`FactoryResetService.reset` 是空实现**
    现象：`FeatureSubscriber` / `EmailTemplateSubscriber` 的 `afterLoad` 计算（`isEnabled`/`imageUrl`/`title`）运行时不会生效（注册表只有 `StorageFileSubscriber`、`TagSubscriber`、`ReferralCodeSubscriber`）；`reset` 方法体整段注释但 HTTP 入口仍暴露，调用成功却什么都不做。
    正确做法：不要依赖上述派生字段；不要用工厂重置接口清理账号数据。
    契约来源：`coreSubscribers`（[subscribers.ts](file://packages/server/src/core/entities/subscribers.ts)）、`FactoryResetService.reset`（[factory-reset.service.ts](file://packages/server/src/user/factory-reset/factory-reset.service.ts)）。
