## 2. 运行命令

两套 jest 配置分别属于两个 package（`preset: '../../jest.preset.js'`、`testEnvironment: 'node'`）：

```bash
# 记忆侧（packages/server-ai）——8 个 spec
pnpm nx test server-ai --testPathPattern="src/file-memory"
# 或直接指定文件
pnpm nx test server-ai --testPathPattern="src/file-memory/file-memory.service.spec.ts"

# 存储侧（packages/server）——1 个 spec
pnpm nx test server --testPathPattern="src/storage-file"

# 按用例名筛选（-t / --testNamePattern）
pnpm nx test server-ai --testPathPattern="src/file-memory" -t "coalesces a new trigger"
pnpm nx test server-ai --testPathPattern="src/file-memory" -t "fail closed"
pnpm nx test server --testPathPattern="src/storage-file" -t "tenant administrators"
```

要点：

- **`server-ai` 配置特殊处**：`transform` 同时挂 `ts-jest`（用 `<rootDir>/tsconfig.spec.json`）与 `babel-jest`；`moduleNameMapper` 把 `@xpert-ai/server-core` → `../server/src/index.ts`、`@xpert-ai/contracts` → `../contracts/src/index.ts`、`@xpert-ai/plugin-sdk` → `../plugin-sdk/src/index.ts`（**源码级映射**，因此记忆测试会连带编译 server/contracts/plugin-sdk 源码）；`transformIgnorePatterns` 通过 `transformSeedPackages` 递归展开白名单（含 `ali-oss`、`nanoid`、`jose` 等）。
- **`server` 配置**：同样双 transform，`moduleNameMapper` 只映射 `@xpert-ai/contracts`；`transformSeedPackages = ['@xpert-ai/plugin-sdk','@xpert-ai/chatkit-types','lodash-es']`。
- **`-t` 的可用锚点**：`file-memory` 侧的 `it` 名是英文长句（如 `coalesces a new trigger when a queued run already exists for the same xpert`、`fails closed when a user-isolated scope has no user id`），`storage-file` 侧同理；中文只在断言数据里出现，不适合做 `-t`。

章节来源：[server-ai/jest.config.ts](file://packages/server-ai/jest.config.ts)（关键符号：displayName server-ai / moduleNameMapper / transformIgnorePatterns）、[server/jest.config.ts](file://packages/server/jest.config.ts)（关键符号：displayName server / transformSeedPackages）

## 3. 需外部依赖

- **PostgreSQL：不需要（已核实）**。两个 package 的 9 个 spec 全部不建 DataSource：记忆侧 `dream.service.spec.ts` 与 `file-memory.service.spec.ts` 用 `os.tmpdir()` + `fsPromises.mkdtemp` 建真实临时目录（`xpert-file-memory-dream-` / `xpert-file-memory-`）后注入沙箱 store 或走本地 fs；`adapters/xpert-conversation-history-reader.spec.ts` 用两个 mock Repository（`find` / `createQueryBuilder`）；`storage-file.service.spec.ts` 直接 `jest.mock` 掉 `../core/crud`、`../core/context`、`./storage-file.entity` 与 `FileStorage`。
- **文件系统：需要，但只限宿主临时目录**。记忆侧会真实 `mkdir`/`writeFile`/`readFile`/`copyFile`（迁移用例会建 `.xpert/memory/xperts/xpert-1/project` 与新根两棵树）；因此需要可写的 `os.tmpdir()` 与 POSIX 路径语义（`path.posix` 参与断言）。
- **对象存储：不需要**。`storage-file` spec 里 `FileStorage` 被替换为只返回 `{ name: 'LOCAL' }` 的类，因此不触碰真实对象存储；`provider.putFile` / `deleteFile` / `Subscriber.afterRemove` 均**不在覆盖范围**。
- **模型 / LLM：不需要**。中间件 spec 与 writeback-runner spec 用 stub `BaseChatModel` 或 `getModel: () => null`（后者断言「模型不可用则跳过」）；未调用真实 provider。
- **沙箱后端：不需要真实后端**。记忆侧通过注入 `runtime.store`（`FileMemoryStore` 假实现，只提供 `listMarkdownFiles/listFiles/readFile/writeFile/getMtimeMs/ensureRoot/rootPath/cacheKey`）绕开 `resolveSandboxBackend`；`assertFileMemorySandboxFeatureEnabled` 只需 `context.xpertFeatures.sandbox.enabled === true`。
- **Nest 运行时：仅 storage-file 侧需要构造实例**（`new StorageFileService(repository)`），不启 HTTP server；因此**没有 HTTP 级端到端测试**（`XpertGuard`、6 个 Dream 端点、3 个存储端点的路由/状态码均未被自动化覆盖）。

章节来源：[file-memory/file-memory.service.spec.ts](file://packages/server-ai/src/file-memory/file-memory.service.spec.ts)（关键符号：mkdtemp / runtime.store 假实现）、[file-memory/adapters/xpert-conversation-history-reader.spec.ts](file://packages/server-ai/src/file-memory/adapters/xpert-conversation-history-reader.spec.ts)（关键符号：createQueryBuilder mock）、[storage-file/storage-file.service.spec.ts](file://packages/server/src/storage-file/storage-file.service.spec.ts)（关键符号：jest.mock('../core/crud') / jest.mock('../file/file-storage/file-storage')）

## 4. 缺口

1. **无 HTTP 端到端**：`FileMemoryController` 6 端点与 `StorageFileController` 3 端点都没有 `.http.spec.ts`/`supertest` 级用例；`XpertGuard`（含 5 分钟缓存键）只在源码中可读，未被测试。
2. **无 `deleteAuthorizedStorageFile` 用例**：跨域删除的「tenantId + organizationId 一致性」断言（以及空值归一）无测试。
3. **无 subscriber 用例**：`afterLoad` 补 `fileUrl`、`afterRemove` 删 `file`/`thumb`（含失败静默）无测试——这正好是「孤儿对象」风险最高的两处。
4. **无 `/api/storage-file/url` 用例**：`axios` 下载 + 名字 latin1→utf8 解码 + `badRequest` 包装无覆盖。
5. **无 `getProviderInstance` 回落用例**：`FileStorage` 的「registry 抛错 → 回落内置 provider」与 `setProvider` 的三级决策链（tenantSettings → environment → LOCAL）只在阅读层可见。
6. **无 `index-validator` 的独立 spec**：`validateFileMemoryIndex` 仅由 `file-memory-core.spec.ts` 覆盖一条正向用例，6 类 issue 中的 `overlong-entry` / `body-like-entry` / `duplicate-target` / `archived-target` 无独立断言。
7. **无 `scoring` / `usage` 边界值用例**：`classifyDreamCandidateScore` 的四档阈值（0.82/0.65/0.45）与 `usefulnessScore` 的负项（correction 罚分）只覆盖单点。
8. **Dream 的并发/锁无真实并发用例**：`acquireLock` 冲突只有「另一 run 已存在」的路径测试，未见两个 run 真并发的时序测试。
9. **legacy 迁移只覆盖「不覆盖新文件」**：跨卷/跨 catalog 迁移、`xperts/` 跳过分支与报告文件内容无断言。
10. **性能/规模无基准**：`readSignals` 全量读、`writeScorecardIndex` 全量重写是热点路径，无规模回归测试。

## 5. 结论

本子域的测试结构是「**核心逻辑高覆盖、边界与 HTTP 面零覆盖**」：记忆的纯函数（路径、frontmatter、usage、scoring、索引校验）与三个状态机/队列（Service IO、Dream、Writeback）都有针对性用例，且大量使用真实临时目录而非全 mock，因此文件语义（相对路径、目录布局、迁移）是被真实验证过的；存储侧则只验证了 service 层的三条删除授权分支与一条创建归一化。

两个最值得补的口子：① **跨域授权与物理副作用**（`deleteAuthorizedStorageFile`、`StorageFileSubscriber`、`getProviderInstance` 回落）——它们是「行删了、对象还在」和「回落导致排障失真」两类问题的唯一防线；② **端点级契约**（9 个端点的状态码、守卫、DTO 投影），当前仅靠源码与父级文档描述，回归风险全在人工。
