## 1. 记忆抽取与写入

**三个触发点**：

1. **显式写入（工具）**：中间件注册 `memory_write`（zod schema：可选 `memoryId` + 必填 `title`/`summary`/`content` + 可选 `type`/`tags`）。执行体调 `FileMemoryService.writeMemory(xpert, {..., conversationId: context.conversationId})`；成功日志 `[XpertFileMemory] memory_write memoryId=… path=… type=… elapsedMs=…`，并置本轮 `explicitWriteOccurred = true`。
2. **隐式 writeback（钩子）**：`afterAgent` 读 state messages → `summarizeMessagesForWriteback` → 若本轮已发生显式写入则 `skipped reason=explicit_write`，摘要为空则 `skipped reason=empty_summary`；否则 `writebackRunner.enqueue({ xpert, messages, conversationId, getModel: createWritebackModel, prompt })`，按 `waitPolicy` 决定是否等待，日志 `afterAgent writeback key=… waitPolicy=… messages=…`。
3. **离线 Dream（HTTP）**：`FileMemoryDreamService.triggerDream` 建 run 后由 dreamer Xpert 直接编辑卷上 markdown（见第 2 节端点 1）。

**写入数据结构**：`FileMemoryDocument = { frontmatter: FileMemoryFrontmatter, body }`；frontmatter 含 `id`（`mem_<uuid>`）、`scopeType:'xpert'`、`scopeId`、`type`（4 类）、`status`（3 态）、`title`、`summary`、`confidence`（新建默认 0.9）、`usage`（8 个计数 + `usefulnessScore`）、`createdAt/updatedAt`、`createdBy/updatedBy`、`source`（`explicit|writeback|dream|imported|manual`）、`sourceRefs`、`tags`。

**去重与覆盖**：`writeMemory` 先按 `memoryId` 找既有记录（`findTopicRecordByMemoryId`，失败吞为 `null`）；命中则**复用 `relativePath` 与 `createdAt`**、若原状态为 `archived` 则复活为 `active`；未命中则 `allocateTopicPath`（`convertToUrlPath(title)` 生成 slug + `memoryId` 去前缀后前 8 位，落到 `<type>/<slug>-<suffix>.md`）。writeback 的软去重在第 1 步之前：`searchMemory(query=对话文本, limit: 6)` 取候选，模型在 `noop|upsert|archive` 中裁决，`upsert` 时复用候选 `memoryId`；决策失败经 `recoverDecision` 从 `llmOutput` 中截取 JSON 再 `FALLBACK_SCHEMA` 校验。

**写后动作固定四步**：`writeTextFile` → `appendSignal(explicit_write)` → `invalidateCaches` → `refreshManagedIndex` + `writeScorecardIndex`。

章节来源：[file-memory/file-memory.service.ts](file://packages/server-ai/src/file-memory/file-memory.service.ts)（关键符号：writeMemory / allocateTopicPath / findTopicRecordByMemoryId / refreshManagedIndex）、[file-memory/file-memory.writeback.ts](file://packages/server-ai/src/file-memory/file-memory.writeback.ts)（关键符号：decideFileMemoryWriteback / normalizeDecision / recoverDecision）、[file-memory/file-memory.middleware.ts](file://packages/server-ai/src/file-memory/file-memory.middleware.ts)（关键符号：memoryWriteSchema / afterAgent / explicitWriteOccurred）

## 2. 记忆读取（6 端点）与消费方

`FileMemoryController`（类级 `@UseGuards(XpertGuard)`，前缀 `xpert/:id/memory`，全局前缀 `api` → `/api/xpert/:id/memory/...`）：

| # | 方法与路径 | 行为 |
|---|---|---|
| 1 | `POST /dream` | body `{ reason?: 'manual'\|'scheduled'\|'signal_threshold' }` → `facade.triggerFileMemoryDream`；同 Xpert 已有 queued run 时**合并**（`coalesced: true`） |
| 2 | `GET /dream/config` | `getDreamConfig`：形如 `{ dreamerXpertId, dreamerAgentKey, gate }`，缺省由环境变量默认值补齐 |
| 3 | `PUT /dream/config` | `saveDreamConfig`：只接受 `dreamerXpertId` / `dreamerAgentKey`（+ gate 归一化），落 `.dream/config.json` |
| 4 | `GET /dream/runs` | 列 `.dream/runs/*` 目录，逐个读 `status.json`，按 `requestedAt` 倒序；读失败静默跳过 |
| 5 | `GET /dream/runs/:runId` | `getRun` → `FileMemoryRunDetail`：summary + `preflight` + `report` + `validation` + **8 个 artifact 描述**（`status`/`request`/`evidence`/`preflight`/`gate`/`dream_report`/`validation`/`changed_files`） |
| 6 | `POST /dream/runs/:runId/cancel` | 仅当 `status === 'queued'` 才写 `cancelled` + `finishedAt`；其他状态原样返回 |

**Agent 侧读取面（真正的消费方）**：`memory_search`（模型筛选 headers，`fallbackOnFailure:false` 时失败返回空）、`memory_get`（按精确 `memoryId` 或 `relativePath` 读正文）、以及 `beforeAgent` → 后台召回 → `wrapModelCall` 用 `buildMemoryContextMessages(recall)` **前置注入**（预算：单轮 20KB / 单会话 60KB、召回超时 3s、最多选 5 条、digest 6 条）。两条路径都会写信号：`memory_search` → `recordRecallHits`；`memory_get` → `getMemory` 内 `detail_read` + `updateTopicUsage`。

**记忆文件 HTTP 面（另在 `xpert.controller.ts`）**：`GET :id/memory/files`、`GET :id/memory/file?path=`、`PUT :id/memory/file`、`POST :id/memory/file/upload`、`DELETE` 侧 `deleteMemoryFile`，全部 `@UseGuards(XpertGuard)`，直连 `XpertService`（`XPERT_MEMORY_WORKSPACE_PATH = '.xpert/memory'`）——与 `FileMemoryFacade` 同名方法**并存**。

## 3. 记忆与向量/模型的交互

- **与向量：无。** `file-memory` 目录对 `embedding|vector|VStore|Knowledgebase|CopilotModel` 检索 **0 命中**；记忆检索是 **header 级关键词打分**（title 0.46 / summary 0.28 / tags 0.14 + exactTitle 0.2 + typeBoost 0.08 + usage 0.2 上限 + recency 0.06/0.03/0.01），中文按 Han 字符 + 2~4 元组切分，无嵌入、无向量库、无 rerank。`[推测]` 记忆规模的实际上限因此由「文件数与 header 扫描成本」而非向量容量决定。
- **与模型（对话模型）：两点强耦合。** ① 召回筛选 `FileMemoryRecallPlanner.selectRecallHeaders`（短名单 = 启发式 top20，模型返回 `selectedIds`，默认 1500ms 超时 → `fallback` 策略）；② 写入决策 `decideFileMemoryWriteback`（`withStructuredOutput(DECISION_SCHEMA)`，取消息尾部 18 条）。两者都用 `metadata: { internal: true }` 标记为内部调用。
- **与模型（Agent）：Dream 复用 `XpertAgentChatCommand`。** `XpertDreamerInvoker.run` 按 `{ id: dreamerXpertId, tenantId }` 查 dreamer Xpert（`relations: ['agent']`），以 `agentKey` 指定 agent，`from: 'job'`、`store: null`，超时 10 分钟（first/each）。
- **无模型时的降级**：`memory_search` 无模型 → 记录 warn 并返回 `[]`；writeback 无模型 → 只记 `writeback_candidate` 信号（`candidate recorded only`）。

章节来源：[file-memory/recall-planner.ts](file://packages/server-ai/src/file-memory/recall-planner.ts)（关键符号：selectRecallHeaders / selectSummaryDigestHeaders / rankHeaders / waitWithin）、[file-memory/file-memory.writeback.ts](file://packages/server-ai/src/file-memory/file-memory.writeback.ts)（关键符号：invokeDecision / trimMessagesForWriteback）、[file-memory/adapters/xpert-dreamer-invoker.ts](file://packages/server-ai/src/file-memory/adapters/xpert-dreamer-invoker.ts)（关键符号：XpertDreamerInvoker.run / XpertAgentChatCommand / DEFAULT_DREAMER_TIMEOUT_MS）

## 4. 存储抽象实现

- **注册与解析**：`FileStorageRegistryBridge` 是静态桥（`OnModuleInit` 时把注入的 `FileStorageProviderRegistry` 存到 static 字段），插件 provider 以 `@FileStorageProvider` 注册。
- **provider 名决策**：`FileStorage.setProvider(name)`——无 name 时读 `RequestContext.currentRequest()['tenantSettings']['fileStorageProvider']`，否则 `environment.fileSystem.name`；两者都经 `normalizeConfiguredProvider` 归一化，空值回落 `FileStorageProviderEnum.LOCAL`。
- **回落语义（逐字引用）**：`getProviderInstance()` 先 `registry.get(name)`，`catch` 内注释为 `// Fall back to built-in providers so bootstrap/tests without Nest context keep working.`，然后返回 `this.providers[name]`；`providers` 来自 `initProvider()` 的 `FALLBACK_PROVIDER_TYPES = [LocalProvider]`（单例缓存，`getInstance()` 优先）。
- **本地 vs 对象存储**：`LocalProvider` 的 `url(filePath)` = `${environment.baseUrl}/public/<path>`，`path(filePath)` 给本地绝对路径，`putFile` 走本地写盘并回填 `file.url`；远端 provider 由插件提供，其 `path()` 是否返回绝对路径**未在仓库内确认**（影响删除链能否清派生目录）。
- **路径解析**：`storage_file.file` 存对象 key；`afterLoad` 用行上的 `storageProvider` new 一个 `FileStorage` 再 `getProviderInstance().url(file)` 补 `fileUrl`（`thumbUrl` 一行被注释掉）。
- **写入口唯一性**：`StorageFileCreateHandler`（CQRS）与 `StorageTargetStrategy.upload`（上传管线）都直接 `createStorageFile`，后者是 controller `POST /` 的实际路径；`StorageFileService.createStorageFile` 内部再做一次 provider 归一化（`storageProvider` 参数 → `new FileStorage().getProvider()?.name` → `LOCAL`），并写 `recordedAt: new Date()`。

章节来源：[file/file-storage/file-storage.ts](file://packages/server/src/file/file-storage/file-storage.ts)（关键符号：getProviderInstance / setProvider / initProvider / normalizeConfiguredProvider）、[file/file-storage/file-storage-registry.bridge.ts](file://packages/server/src/file/file-storage/file-storage-registry.bridge.ts)（关键符号：FileStorageRegistryBridge.onModuleInit / getRegistry）、[storage-file/storage-file.service.ts](file://packages/server/src/storage-file/storage-file.service.ts)（关键符号：createStorageFile / normalizeStorageProvider）、[storage-file/storage-file.subscriber.ts](file://packages/server/src/storage-file/storage-file.subscriber.ts)（关键符号：afterLoad.fileUrl）

## 5. 上传/下载/删除 3 端点

真实前缀 `/api/storage-file`（`RouterModule.register([{ path: '/storage-file' }])` + 全局 `api`）。

| # | 方法与路径 | 实现要点 | 鉴权位置 |
|---|---|---|---|
| 1 | `POST /api/storage-file` | `@UseInterceptors(FileInterceptor('file'))` → `UploadFileCommand({ source: { kind:'multipart', file }, targets: [{ kind:'storage', directory: 'files', prefix: 'files' }] })` → `getStorageFileFromAsset(asset)`；取不到则 400 `Failed to upload storage file`。**注意**：`@Body() entity: StorageFile` 入参只做解析，未参与落库 | **无显式断言**；授权来自 `StorageTargetStrategy` 链上的上下文/租户（`StorageFileService.create` 走 `TenantOrganizationAwareCrudService`） |
| 2 | `POST /api/storage-file/url` | `axios.get(url, { responseType:'arraybuffer' })` → `Buffer.from(response.data)`；`provider = new FileStorage().getProvider()`；`storageFileService.create({...})`，`storageProvider: <NAME 大写>`，原始名经 `Buffer.from(originalname,'latin1').toString('utf8')` 解码；异常统一 400 `Failed to download and store file from URL: …` | **无断言**（服务端主动拉取外链，存在 SSRF 面，见技术债） |
| 3 | `DELETE /api/storage-file/:id` | `@UsePipes(new ValidationPipe())` + `UUIDValidationPipe` → `deleteStorageFile(id)`；service 内 `findOne` 后：`userId = RequestContext.currentUserId()`、`isTenantAdmin = hasRoles([SUPER_ADMIN, ADMIN])`，`if (!userId \|\| (entity.createdById !== userId && !isTenantAdmin)) throw new ForbiddenException()`；`catch` 把任何异常（含找不到）统一转 403，**不区分 404**；成功路径 `repository.remove(entity)`（硬删） | **service 层**（`deleteStorageFile`），controller 不做鉴权 |

**旁路入口**：`deleteAuthorizedStorageFile({ id, tenantId, organizationId })` 供「已由所属域授权」的调用方使用，只比对 `tenantId` 与 `organizationId`（空值用 `?? null` 对齐），**不再校验 owner**。另有 `StorageFileDeleteHandler` / `GetStorageFileHandler`（按 `In(ids)` 批量查）/ `DeployWebappHandler`（zip 解压到 `webapp/<appId>` 并返回 `baseUrl + /webapp/<appId>/index.html`）。

## 6. 卷与文件系统布局

```
<volume root>
└── .xpert/memory/                     # FILE_MEMORY_WORKSPACE_PATH
    ├── MEMORY.md                      # 托管导航索引（FILE_MEMORY_INDEX_FILENAME）
    ├── user/  feedback/  project/  reference/     # 4 类主题目录
    │   └── <slug>-<id8>.md            # frontmatter(document) + body
    └── .dream/                        # FILE_MEMORY_DREAM_DIR
        ├── config.json                # Dream 配置（dreamerXpertId / dreamerAgentKey / gate）
        ├── DREAMS.md                  # dream 日记（appendDreamDiary）
        ├── signals/YYYY-MM-DD.jsonl   # 信号（append 追加）
        ├── scorecards/index.json      # topics + candidates 记分卡
        ├── migrations/<ts>.json       # legacy root 迁移报告
        ├── lock/                      # Dream 互斥锁
        ├── backup/current/            # Dream 前备份（CURRENT_BACKUP_DIR）
        └── runs/<runId>/
            ├── status.json  request.json
            ├── evidence/{memory-manifest.json, signals.json, instructions.md}
            └── output/{preflight-report.md, gate.json, dream-report.json, validation.json, changed-files.json}
```

- **项目卷共享特例**：若 `projectId` 存在，卷作用域切到 `{ tenantId, catalog:'projects', projectId, userId }`，记忆根变为 `.xpert/memory/xperts/<xpertId>`（`getXpertFileMemoryWorkspacePath`）；`createFileMemoryScopeKey` 相应变成 `<tenant>:project:<projectId>:xpert:<id>`。
- **user 隔离**：`workspaceDataScope === 'user'` 时卷 catalog 为 `user-xperts`，且 scope key 追加 `:<userId>`（缺失时字面量 `missing-user`），保证不同用户的 writeback/Dream slot 不串。
- **越界防护**：`normalizeFileMemoryRelativePath` 拒绝 `..`/绝对路径；`resolveAbsolutePath` 要求首段属于 4 类目录或等于 `MEMORY.md` 或以 `.dream/` 开头；卷侧读写在 `VolumeSubtreeClient` + `boundaryRoot` 下进行。
- **沙箱模式**：`XpertSandboxMemoryStore.rootPath` 同样是 `.xpert/memory`（**不带 xpertId 子目录**），写入经 `backend.uploadFiles`，目录创建经 `backend.execute('mkdir -p …')`（参数 `shellQuote`），并为无子目录设计写了对应测试断言。

章节来源：[file-memory/types.ts](file://packages/server-ai/src/file-memory/types.ts)（关键符号：FILE_MEMORY_WORKSPACE_PATH / FILE_MEMORY_INDEX_FILENAME / FILE_MEMORY_DREAM_DIR）、[file-memory/paths.ts](file://packages/server-ai/src/file-memory/paths.ts)（关键符号：getXpertFileMemoryVolumeScope / getXpertFileMemoryWorkspacePath / normalizeFileMemoryRelativePath）、[file-memory/ports.ts](file://packages/server-ai/src/file-memory/ports.ts)（关键符号：createFileMemoryScopeKey）、[file-memory/sandbox-memory.store.ts](file://packages/server-ai/src/file-memory/sandbox-memory.store.ts)（关键符号：XpertSandboxMemoryStore.ensureRoot / resolvePath）

## 7. 生命周期与清理

- **记忆条目**：`active` → `archiveMemory`（`status:'archived'`、`updatedBy:'file_memory_governance'`、可加 `archived` 标签）→ 从 `MEMORY.md` 移除但文件保留；下一次 `writeMemory` 命中同一 `memoryId` 会**复活为 active**。无物理删除入口。
- **信号与记分卡**：`signals/*.jsonl` 只 append；`scorecards/index.json` 每次写后/召回后**全量重写**；`readSignals` 按文件名排序顺序读全部（无按时间裁剪），`MAX_SIGNAL_COUNT = 500` 仅用于 Dream 证据采样的上限。
- **Dream run**：`queued → running → succeeded|partial|failed|cancelled|skipped`；每次运行前 `backupMemoryRoot`，`finally` 里 `cleanupBackup` + `releaseLock`；gate 未过落 `status='skipped'`（写 `dream-report.json` 说明原因，**不是错误**）；另一 run 已持锁 → `partial` + 原因 `Another dream run is already active for this Xpert.`；`cancelRun` 只对 `queued` 生效（`running` 不能被取消）。
- **storage_file**：行删除即硬删，`afterRemove` 删 `file` 与 `thumb` 两个物理对象；`deletedAt` 列存在但无写入点；`afterLoad` 每次加载动态补 `fileUrl`。subscriber 的两个钩子都在 `try/catch` 里 `console.log` 吞异常，不回滚、不告警。
- **legacy 迁移**：`migrateLegacyMemoryRoot` 在 `ensureMemoryRoot` 内惰性触发（每 scope 进程内只跑一次，`migratedLegacyRoots` Set 记录）：从 `.xpert/memory/xperts/<xpertId>` 递归拷贝到新根，跳过 `xperts/` 前缀与已存在目标，写 `.dream/migrations/<ts>.json` 报告。

章节来源：[file-memory/dream.service.ts](file://packages/server-ai/src/file-memory/dream.service.ts)（关键符号：runDream / acquireLock / releaseLock / backupMemoryRoot / cleanupBackup / skipRunByGate）、[file-memory/file-memory.service.ts](file://packages/server-ai/src/file-memory/file-memory.service.ts)（关键符号：archiveMemory / migrateLegacyMemoryRoot / writeScorecardIndex）、[storage-file/storage-file.subscriber.ts](file://packages/server/src/storage-file/storage-file.subscriber.ts)（关键符号：afterRemove / afterLoad）

## 8. 设计模式

1. **端口-适配器（Hexagonal）**：`ports.ts` 定义 3 个抽象类（`FileMemoryConversationHistoryReader` / `FileMemoryDreamerInvoker` / `FileMemoryXpertScopeResolver`），`adapters/` 给默认实现，`file-memory.module.ts` 用 `useClass` 绑定 token——记忆核心因此可脱离 TypeORM/Xpert 运行时测试。
2. **策略 + 名称注册（中间件）**：`@AgentMiddlewareStrategy(XPERT_FILE_MEMORY_MIDDLEWARE_NAME)` 让 Agent 运行时按名装配；工具名 `memory_search|memory_get|memory_write` 是稳定契约。
3. **CQRS（storage-file）**：`CommandHandlers` / `QueryHandlers` 注册在 module，controller 通过 `CommandBus.execute(UploadFileCommand)` 只投命令，不直接编排存储策略。
4. **静态桥 + 回落（provider 解析）**：`FileStorageRegistryBridge`（Nest 依赖 → static）+ `getProviderInstance` 静默回落内置 provider，保证无 Nest 上下文时可用。
5. **Subscriber 钩子（隐式副作用）**：实体加载/删除的物理副作用（补 URL、删对象）挂在 `StorageFileSubscriber`，业务代码不需要显式调用。
6. **队列/槽位串行（Runner）**：`FileMemoryWritebackRunner.slots` 与 `FileMemoryDreamService.slots` 用「按 scope 键的 pending + running」实现单飞；`softDrain(key, timeoutMs)` 提供限时等待（`Promise.race`）。

章节来源：[file-memory/file-memory.module.ts](file://packages/server-ai/src/file-memory/file-memory.module.ts)（关键符号：useClass 绑定 3 个端口）、[storage-file/storage-file.module.ts](file://packages/server/src/storage-file/storage-file.module.ts)（关键符号：CommandHandlers / QueryHandlers / RouterModule）、[file-memory/file-memory.writeback-runner.ts](file://packages/server-ai/src/file-memory/file-memory.writeback-runner.ts)（关键符号：enqueue / softDrain / runSlot）、[file/file-storage/file-storage-registry.bridge.ts](file://packages/server/src/file/file-storage/file-storage-registry.bridge.ts)（关键符号：static registry）

## 9. 热点路径

- **每轮对话的召回读**：`beforeAgent` 起后台 recall（`prepareRecall`）→ `listMemoryHeaders`（mtime 缓存命中则 0 IO）→ `selectSummaryDigestHeaders`（启发式 6 条）→ 可选 `selectRecallHeaders`（模型，≤1500ms）→ `buildDetailBlock`（逐条 `getMemory`，受 20KB/轮 + 60KB/会话预算）→ `wrapModelCall` 注入。**注意** `getMemory` 会写信号并重写该条 frontmatter，因此「读」也是「写」。
- **每轮结束的写回判定**：`afterAgent` → `enqueue` → `recordWritebackCandidate`（写 1 行 jsonl + 重写 `scorecards/index.json`）→ `searchMemory`（全 header 打分）→ LLM 决策 → 可能 `writeMemory`（再触发索引刷新 + 记分卡重写）。
- **`searchMemory` 的成本随记忆数线性增长**：`listTopicRecords` 对 4 个目录逐个 `readdir` + 逐个 `readFile` + `parseFileMemoryMarkdown`；`writeScorecardIndex` 每次又全量 `listTopicRecords` + `readSignals`（读全部 jsonl）。
- **`GET :id/memory/dream/runs`**：读目录并对每个 run 读 `status.json`（N 次文件读），无缓存。
- **`POST /api/storage-file`**：多部分上传 → 策略写盘/写对象 → `createStorageFile` 写行；删除路径额外一次 `findOne`（为触发 `afterRemove` 的 entity 参数）。
- **`/url` 端点**：先 `axios.get` 全量下载到内存（arraybuffer）→ `provider.putFile(url)`，大文件会同时占用网络与内存。

章节来源：[file-memory/file-memory.service.ts](file://packages/server-ai/src/file-memory/file-memory.service.ts)（关键符号：listMemoryHeaders / listTopicRecords / searchMemory / writeScorecardIndex）、[file-memory/file-memory.middleware.ts](file://packages/server-ai/src/file-memory/file-memory.middleware.ts)（关键符号：startBackgroundRecall / consumeCompletedRecall / buildDetailBlock）、[storage-file/storage-file.controller.ts](file://packages/server/src/storage-file/storage-file.controller.ts)（关键符号：createUrl / create）

## 11. 技术债

1. **`/url` 下载后未使用 buffer**：端点把响应转成 `Buffer` 后并未传入存储，而是 `provider.putFile(url)`（把 URL 当内容参数）。`[推测]` 属实现遗留，且该端点无内容类型/大小校验（SSRF + 大文件风险）。
2. **记忆检索是纯关键词**：无嵌入、无 rerank，长记忆库下 recall 精度与成本都随文件数线性退化（见第 9 节）。
3. **`getMemory` 有读副作用**：读取会重写 frontmatter 并 append 信号，令「纯读」不可幂等；`searchMemory` 亦如此。
4. **信号文件无裁剪**：`signals/*.jsonl` 只追加、无轮转/压缩，`readSignals` 每次全量读，`MAX_SIGNAL_COUNT` 只作用于 Dream 证据。
5. **`storage_file.deletedAt` 死列**：有列无写入点，删除是硬删；「软删/回收站」语义缺失。
6. **`deleteStorageFile` 吞异常**：`catch {}` 把找不到与无权统一成 403，调用方无法区分 404 与越权。
7. **subscriber 静默失败**：`afterRemove`/`afterLoad` 用 `console.log` 吞错，物理对象可能残留而 DB 已删（孤儿对象）。
8. **记忆文件 CRUD 双实现**：`FileMemoryFacade` 与 `XpertService` 各一份；后者硬编码 `.xpert/memory`，不随项目卷切换，`[推测]` 会让「项目内 xpert 记忆」在文件面板里看不到。
9. **Dream 无调度装饰器**：目录内无 `@Cron/@Interval/@Processor`；`reason: 'scheduled'` 由谁触发**未在仓库内确认**（外部调度器或调用方）。
10. **`POST /api/storage-file` 的 `@Body() entity: StorageFile` 未使用**，且该端点无显式鉴权断言（依赖上传策略与 Crud 基类）。

## 12. 设计维度

**维度一：记忆介质抽象层级（卷文件系统 ⇄ 沙箱后端）**。同一个 `FileMemoryService` 有两套 IO 实现：`runtime.store` 存在时全走 `XpertSandboxMemoryStore`（`globInfo/downloadFiles/uploadFiles/lsInfo/execute`），否则退化为本机 `fsPromises` + `VolumeClient.resolve().path()`。好处是沙箱与宿主共用一套记忆语义；代价是两套实现的路径语义不同（沙箱根**不带** `xpertId`，卷路径在项目模式下**带** `xperts/<xpertId>`），且 `resolveAbsolutePath` 的类型/目录白名单校验在沙箱分支**不生效**（沙箱分支只经 `normalizeFileMemoryRelativePath`）。

**维度二：判定用 LLM ⇄ 启发式回落（可观测的降级面）**。召回筛选显式建模 `strategy: 'model' | 'fallback' | 'disabled'`（默认超时 1500ms、短名单 20、`fallbackOnFailure:false` 直接返回空）；写入决策在结构化输出失败时先尝试从 `llmOutput` 里抠 JSON，再无解才 `noop`；Dream gate 在阈值不足时把 run 标 `skipped` 而非失败。三者共同构成「模型不可用/超时也不阻塞对话」的一致性策略。

**维度三：provider 解析时点（写时固化 ⇄ 读时解析）**。`storageProvider` 在行落库瞬间固化（大写），读取永远按行上的值解析；因此「租户改默认 provider」不会让历史行迁移，但会让「同一批文件分属不同后端」成为常态；`getProviderInstance` 的静默回落则让这一分布对调用方不可见。

章节来源：[file-memory/sandbox-memory.store.ts](file://packages/server-ai/src/file-memory/sandbox-memory.store.ts)（关键符号：resolveSandboxMemoryStore / FileMemoryStore）、[file-memory/recall-planner.ts](file://packages/server-ai/src/file-memory/recall-planner.ts)（关键符号：FileMemoryRecallSelectionResult.strategy）、[file-memory/dream.service.ts](file://packages/server-ai/src/file-memory/dream.service.ts)（关键符号：evaluateDreamGate / skipRunByGate）、[storage-file/storage-file.service.ts](file://packages/server/src/storage-file/storage-file.service.ts)（关键符号：normalizeStorageProvider）

## 13. 结论

实现层面的主线是「**无表记忆 + 有表存储索引**」。记忆侧用 `FileMemoryService`（唯一事实源 = 卷上 markdown/JSON）承载三种写入入口与两层召回（digest + 工具），Dream 作为离线治理回路完成 gate 判定、备份、证据与报告；存储侧用 `StorageFileService` + `FileStorage` provider 抽象 + subscriber 收尾，把「字节 key → 可访问 URL → 物理删除」收敛成一条链路。

工程上最值得注意的是三点：① **记忆的可观测性依赖文件信号**（`signals/*.jsonl` → `usage` → `usefulnessScore` → 召回打分），因此信号读取性能直接决定召回性能；② **降级路径被显式建模**（`strategy` 三态、决策 `noop`、run `skipped`），这是本子域最成熟的设计；③ **存储 provider 的静默回落**与 **记忆文件 CRUD 双实现** 是两处最容易在排障时误导人的地方。
