## 2. 按主题分组

**A. 授权与访问边界（域服务组，6 个）** —— 本域最重的测试主题，因为授权是唯一收口。
- `file-asset-access.service.spec.ts`（30.7KB）：手工 `new FileAssetAccessService(...)` 注入假仓储/假服务（`conversationFileLinkRepository`、`storageFileService.findOneInOrganizationOrTenant`、`projectAccessService.assertCan*`、`publishedXpertAccessService`），`jest.requireActual` 保留真 `server-core` 只换掉 `RequestContext`；覆盖 locator 双形态、current-owner 与 conversation 两条 authority、`attach` 时的项目编辑边界前置、跨 Project 复用 409、user-isolated Xpert 的 fail-closed 分支、项目回收夹具（`purgeFixture`）。
- `technical-principal-attachment-access.spec.ts`（9.5KB）：用真实 `PublishedXpertAccessService` + 假 query builder，同时 spy `@xpert-ai/server-core` 与 `@xpert-ai/plugin-sdk` 两个 `RequestContext`，验证技术主体（`UserType.COMMUNICATION` / `api_key` principal，`ownerUserId` 与 `apiKeyUserId` 分离）走 `CreateWorkspaceFileAssetCommand` 的 attachment 授权路径。
- `file-asset-deletion.service.spec.ts` + `file-understanding.controller.spec.ts`：后者 `jest.mock` 掉 `server-core` 的装饰器与 guard 类，用 `it.each` 逐 operation 断言 `resolve` 入参（read / parse / delete），并断言拒权时 `queryBus.execute` **从未被调用**；公共 Xpert 会话分支用 `jest.Mock` 切换 `getPublicXpertSessionConversationScope`。

**B. 写链 handler（6 个）** —— 每条链的幂等与状态回写。
- `create-file-asset.handler.spec.ts`（12.7KB）：`storageFileId` 缺失 400、按 `(storageFileId, tenantId)` 复用不新建行、`sha256` 落列、`conversation_file_link` upsert、metadata 三次合并。

- `parse-file-asset.handler.spec.ts`（12.7KB）与 `index-file-chunks.handler.spec.ts`：解析成功/失败/授权拒绝（`forbidden-file` → `ForbiddenException`）分支、`replaceArtifacts` 顺序、切块与锚点重建。

**C. 读链 query handler（9 个）** —— 检索、预览、可见性。

## 4. 断言与 mock 风格

- **纯手工构造 + 全 mock（主流）**：域服务与 handler 几乎都直接 `new XxxHandler(repo, ...)` 并注入 fake 仓储；只有 `RequestContext` 用 `jest.spyOn` / `jest.requireActual` 组合替换，避免污染真 `server-core` 行为。
- **控制器级「授权先于执行」**：`file-understanding.controller.spec.ts` 用 `jest.mock('@xpert-ai/server-core')` 桩掉装饰器与 guard 类，再逐 operation 断言 `resolve` 入参，并断言拒权时下游 `queryBus.execute` **零调用**——这是「授权是唯一入口」这条不变量的可执行形式。
- **真实类 + 假仓储**：`technical-principal-attachment-access.spec.ts` 用真 `PublishedXpertAccessService` + 假 query builder，验证技术主体（api_key principal）与人类 owner 的分离语义。
- **真实文件系统**：`file-workspace-projection.service.spec.ts`（28.8KB）mock `@xpert-ai/server-config` 的 `environment`，用 `fsPromises` + `os.tmpdir()` 真读写并断言投影字节与冲突路径；`technical-principal-attachment-access.spec.ts` 亦用 `os.tmpdir()` 构造卷目录。
- **解析器：mock loader + 子类桩**：`pdf.parser.spec.ts` mock `PDFLoader` 并**继承覆写** `createPdfToImageDocument` / `getStorageProvider`；`office.parser.spec.ts` mock loader 与 `createRequire`。
- **契约精确列表**：`file-understanding.middleware.spec.ts` 与 `file-understanding.tools.spec.ts` 断言工具名**精确数组**（含负例：不得出现旧 `file_*` / `workspace_*` 名），任何工具改名都会红灯。
- **向量服务：构造期反射注入**：`file-understanding-vector.service.spec.ts` 用 `Reflect.construct(FileUnderstandingVectorService, [fileEmbeddingRepository, ...])` 注入假账本仓储、假 `CommandBus`（`RagCreateVStoreCommand` → 假 vectorStore）与假 `QueryBus`（`CopilotOneByRoleQuery` → 假 copilot、`CopilotModelGetEmbeddingsQuery` → 假 embeddings），并显式设置 `dimensions: 3` 以验证指纹与维度校验路径。

章节来源：[file-understanding-vector.service.spec.ts](file://packages/server-ai/src/file-understanding/file-understanding-vector.service.spec.ts)（关键符号：createService / Reflect.construct / 假 vectorStore）；[file-workspace-projection.service.spec.ts](file://packages/server-ai/src/file-understanding/file-workspace-projection.service.spec.ts)（关键符号：os.tmpdir 真文件系统）；[middlewares/file-understanding.middleware.spec.ts](file://packages/server-ai/src/file-understanding/middlewares/file-understanding.middleware.spec.ts)（关键符号：tools 名精确断言 / ListProjectFilesQuery 分支）

## 5. 外部依赖

**结论：29 个 spec 均为单元/组件级，不需要 PG / Redis / 对象存储 / 解析器二进制。** 逐项说明：

| 依赖 | 是否需要 | 依据 |
|---|---|---|
| PostgreSQL / TypeORM 真实连接 | **不需要** | 所有仓储均为手工 fake（`find/findOne/save/delete` 手写实现）或 `jest.mock` |
| Redis / Bull 队列 | **不需要** | 本域**未注册任何队列**，解析走 `setImmediate` + `CommandBus`（`EnqueueFileParseHandler`），测试直接注入假 `CommandBus` |
| RagVStore（向量库） | **不需要** | `RagCreateVStoreCommand` 被假 `CommandBus` 截获并返回假 `vectorStore`（`addDocuments/similaritySearchWithScore/delete` 皆 `jest.Mock`） |
| Embedding 模型 / 网络 | **不需要** | `CopilotOneByRoleQuery` → 假 copilot，`CopilotModelGetEmbeddingsQuery` → 假 embeddings（`embedQuery` 返回定长数组） |
| 解析器外部二进制 | **不需要** | `PDFLoader` 被 mock 且 `pdf-to-img` 入口被**子类覆写**；`unzipper`/`xlsx`/`sharp` 均为纯 JS/WASM 依赖；`word-extractor` 由 `createRequire` 被 mock |
| 对象存储（S3/OSS） | **不需要** | `FileStorage().getProvider()` 在 pdf/projection/technical-principal 三类 spec 中被桩成假 provider（`putFile/getFile/deleteFile/path`） |
| 可写临时目录 + `HOME` | **需要（环境前置）** | `file-workspace-projection.service.spec.ts`、`technical-principal-attachment-access.spec.ts` 用 `os.tmpdir()` 真读写；卷布局默认取用户目录，故需可写 `HOME` |
| 时间/随机 | **不需要 mock** | `parseRunId = randomUUID()`、`projectedAt` 等只做存在性断言，不比对固定值 |

章节来源：[file-understanding-vector.service.spec.ts](file://packages/server-ai/src/file-understanding/file-understanding-vector.service.spec.ts)（关键符号：假 commandBus 截获 RagCreateVStoreCommand）；[enqueue-file-parse.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/enqueue-file-parse.handler.ts)（关键符号：无队列、setImmediate）；[implementation/06-测试.md](file://.module-experts/后端专题/文件理解与记忆专家/implementation/06-测试.md)（关键符号：六、可执行性结论 / 不连 PG、Redis、S3）

## 6. 覆盖缺口

1. **无端到端链路 spec**：上传 → 解析 → 切块 → 向量 → 工具读取的**串联**没有被任何一个 spec 覆盖，全部是分段单测；上传入口契约的测试落在 `ai/context.controller.spec.ts` 与 `ai/workbench-files-routing.http.spec.ts`（本域 29 个之外）。
2. **`CreateWorkspaceFileAssetHandler` 的卷路径与目录错误文案**只由 handler spec 断言，没有针对真实 `VolumeClient` 的集成验证。`[推测]` 卷 provider 差异（本地 vs 沙箱）可能导致行为偏差未被测出。
3. **`FileAssetDeletionService.purgeProjectFile`**：`delete-file-asset.handler.spec.ts` 极薄（491B），`purgeProjectFile` 的 `assertCanPurge` + 归属比对分支在本域 spec 中**没有被断言**；调用方 `xpert-project/services/project-purge.service.spec.ts` 反而是 `jest.mock` 掉整个 `FileAssetDeletionService`。
4. **重试路径**：`RetryFileParseHandler` 是纯转发、无 spec；平台侧门禁（`retryUnderstanding` 只允许 failed / unavailable）的测试在 `RuntimeCapabilityModule` 的 spec 中，不在本域。`[推测]`
5. **并发与竞态无覆盖**：`(storageFileId, tenantId)` 去重、跨 Project 409、`IndexFileChunks` 删-建窗口都只做了顺序断言，没有并发用例（与 02-实现.md §12 的技术债同源）。
6. **失败清理无覆盖**：`cleanup` 的静默 `catch(() => undefined)`、远端 provider 下跳过 `fs.rm` 的分支、`deleteStalePageImages` 的失败分支均无断言。
7. **`create-file-artifacts.handler`** 无 spec（与它「无生产调用方」现状一致）。
8. **`parsers/binary-content.spec.ts` 与实现文件命名脱节**（`parsers/` 下无 `binary-content.ts`），`[推测]` 其断言实际落在 `text-file.ts` 的二进制嗅探路径上，新增解析类型时容易误判覆盖范围。
9. **XML/`spreadsheet`/`archive`/`image` 四个解析器无独立 spec**：`spreadsheet.parser.ts`、`archive.parser.ts`、`image.parser.ts` 目前只被间接覆盖（或完全不覆盖），与 `pdf`/`office`/`text` 三个「有 spec 的解析器」不对等。

## 7. 结论

- **可跑**：29 个 spec 全部是单元/组件级，命令覆盖「目录 / 单文件 / `-t` 用例名 / Nx」四种粒度；唯一环境前置是**可写 `os.tmpdir()` 与 `HOME`**（卷布局），无 PG / Redis / S3 / 解析器二进制需求。
- **覆盖质量呈两极**：授权（`file-asset-access.service.spec.ts`、`file-understanding.controller.spec.ts`、`technical-principal-attachment-access.spec.ts`）与投影（`file-workspace-projection.service.spec.ts`）是**厚覆盖**，且断言的是不变量本身（resolve 入参、拒权时下游零调用）；而删除旁路（`purgeProjectFile`）、重试、并发、失败清理是**薄覆盖或零覆盖**。
- **判据建议**：本子域改动若要「跑得放心」，至少应同时跑 `-t 'FileAssetAccessService'`、`-t 'FileUnderstandingController'`、`-t 'CreateFileAssetHandler'`、`-t 'ParseFileAssetHandler'`、`-t 'exposes file understanding tools'` 五组；改动解析器时追加对应 `-t 'PdfFileParser'` 等。
- **优先补齐**：① `purgeProjectFile` 的权限与归属分支；② 去重与跨 Project 409 的并发用例；③ 上传→解析→检索 的最小端到端；④ `spreadsheet/archive/image` 三个解析器的 `supports`/产物断言。
