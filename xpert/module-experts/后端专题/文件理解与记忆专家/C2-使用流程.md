## R1 上传并启动理解

**业务目标**：把本地字节变成平台可授权、可解析、可引用的 `FileAsset` 句柄，并让理解链开始跑。
**调用顺序**：① `POST /api/ai/contexts/file`（multipart：`file` + `target`/`purpose`/`parseMode`/`conversationId`/`threadId`/`projectId`/`xpertId`）→ ② `resolveExternalStorageUploadTarget` 解析 target（默认 `{kind:'storage',directory:'contexts',prefix:'files'}`）→ ③ `resolveConversationReferences` 用会话覆盖 `projectId`/`xpertId`，`workspacePath` 被强制清空 → ④ 授权（无会话 `assertUploadScope`；有会话 `assertCanCreateConversationAsset(...,'upload')`）→ ⑤ `UploadFileCommand` → `StorageTargetStrategy.upload`（key 必须落在 `contexts/<tenantId>/` 内）→ `createStorageFile` 落 `storage_file` → ⑥ `CreateFileAssetCommand` 建/复用 `file_asset`（有会话时 upsert `conversation_file_link`）→ ⑦ `EnqueueFileParseCommand`。
**时序边界**：字节与 `storage_file` 行先于 `file_asset` 建行；`parseMode==='none'` 时 enqueue 只置 `ready` 不做解析；`options.runInline` 为真则同请求内同步跑完整条解析链，否则 `setImmediate` 后台执行（上传响应已先返回）。
**预期结果**：返回 `AgentFile`（`id == fileId == FileAsset.id`，`storageFileId` 仅作兼容桥）；资产状态停在 `parsing`（后台）或已是 `ready|partial|failed`（同步）。
**错误处理**：400 `Error.ExternalUploadTargetInvalid`（改动 `directory`/`prefix` 或携带额外键）、上传失败 400；403（项目编辑权不足、助手不可见、公共会话下非 storage target 或带 `projectId`）；同 `storageFileId` 重复上传**原地更新**而不新建行。
**真实代码示例**
```http
POST /api/ai/contexts/file        # multipart
file=@a.pdf & purpose=chat_attachment & parseMode=auto & conversationId=<conversationId>
```
```ts
// 链路（命令名即投递点）
UploadFileCommand → CreateFileAssetCommand → EnqueueFileParseCommand({ fileAssetId })
```

## R2 读解析状态与重试

**业务目标**：判断一个文件解析到哪一步、失败原因是什么，并在失败面内安全重放。
**调用顺序**：① `GET /api/ai/files/:fileId/status` → `GetFileParseStatusQuery`，返回 `{fileId, status, error, parsedAt}` → ② 读状态机 `uploaded|scanning|parsing|ready|partial|failed` → ③ 需要更细的索引进度时走运行时 `GetFileUnderstandingStatusQuery`（`vectorIndexStatus` 为派生值：`failed` 状态→`failed`；`uploaded|scanning|parsing`→`pending`；`chunkCount>0 && indexedChunkCount>=chunkCount`→`ready`；否则 `unavailable`）→ ④ 重试二选一：HTTP `POST /api/ai/files/:fileId/parse/retry`（`operation:'parse'`，**无状态门禁**）或运行时 `retryUnderstanding`（门禁：仅 `status==='failed'` 或 `vectorIndexStatus ∈ {failed,unavailable}`）。
**时序边界**：HTTP 重试直接转发 `ParseFileAssetCommand`，**不经过** `EnqueueFileParseHandler`，因此不预置 `status`、不读 `runInline`；运行时门禁在投递 `EnqueueFileParseCommand` 前判定，并在通过后叠加 `assertUnderstandingAssetVisible('parse')`。
**预期结果**：重试重新走「置 `parsing` 并清 `error` → 选源 → 解析器 → `replaceArtifacts` → 切块索引 → 回写 `status/capabilities/metadata/parsedAt`」；失败终态写 `error` + `failedAt` + `metadata.understandingErrorCode`。
**错误处理**：403 `FileAssetAccessDenied`；404（仅 status 端点，授权通过后）`File asset "…" not found`；400 `Only failed or unavailable file understanding can be retried`；解析异常不冒泡到 HTTP，被 handler 吞成 `status='failed'`。
**真实代码示例**
```http
GET  /api/ai/files/<fileId>/status
POST /api/ai/files/<fileId>/parse/retry
```
章节来源：[get-file-parse-status.handler.ts](file://packages/server-ai/src/file-understanding/queries/handlers/get-file-parse-status.handler.ts)（关键符号：GetFileParseStatusHandler.execute）、[workspace-files-runtime-capability.service.ts](file://packages/server-ai/src/shared/runtime/workspace-files-runtime-capability.service.ts)（关键符号：retryUnderstanding / getUnderstandingStatus）、[retry-file-parse.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/retry-file-parse.handler.ts)（关键符号：RetryFileParseHandler.execute）

## R3 读取与预览

**业务目标**：在授权边界内取「摘要 / 正文 / 检索结果」三种不同粒度，且不越权、不放大返回体积。
**调用顺序**：① `GET /api/ai/files/:fileId/preview`（紧凑预览：`file.summary` 截断 900 字、`compactMetadata` 只留 parser/chunkCount/fileCount/pdfPageImages、artifact ≤12 且排除 `summary`、chunk ≤8 且仅 `chunkId/orderNo/anchor/tokenCount`，页图附 `createPageImagePreviewFile`）→ ② `POST /api/ai/files/:fileId/search`（**有 query**：向量召回 + 关键词 `ILIKE` 经倒数排名融合 `1/(60+rank)`；**无 query**：按 `orderNo` 顺序列举；`limit ≤30` 或 `≤101`）→ ③ `POST /api/ai/files/:fileId/read`（`chunkId` 或 `orderNo`，默认 0）→ ④ 会话维度列举 `GET /api/ai/conversations/:conversationId/files`（`assertConversationAccess` + 公共会话断言 + `ListConversationFilesQuery`）。
**时序边界**：三者都是只读；preview 固定三次查询（asset + artifacts + chunks）；search 是「读 `file_embedding` 账本做 collection 交叉过滤 → 查向量库」两跳；read 以 `fileAssetId` 绑定作用域。Agent 侧还有一层可见性：工具 `listVisibleFiles` 有可信 `projectId` 时走 `ListProjectFilesQuery`，否则走 `ListConversationFilesQuery`。
**预期结果**：preview 不返回 artifacts/chunks 正文；search 返回融合后的 chunk 序列；read 命中返回块内容，未命中返回 `null`（工具描述明确「缺块是终态 not-found，禁止按 `orderNo` 枚举扫描」）。
**错误处理**：403 `FileAssetAccessDenied`（**不存在与无权限不区分**，防枚举）；asset 不存在时 preview 返回 `null`（HTTP 200，不是 404）；`ConversationFileLink` 是读权限边界，未 attach 的文件在会话工具面不可见。
**真实代码示例**
```http
GET  /api/ai/files/<fileId>/preview
POST /api/ai/files/<fileId>/search   { "query": "违约条款", "limit": 8 }
POST /api/ai/files/<fileId>/read     { "orderNo": 0 }
GET  /api/ai/conversations/<conversationId>/files
```
章节来源：[file-understanding.controller.ts](file://packages/server-ai/src/file-understanding/file-understanding.controller.ts)（关键符号：getPreview / searchFile / readFile / listConversationFiles）、[get-file-preview.handler.ts](file://packages/server-ai/src/file-understanding/queries/handlers/get-file-preview.handler.ts)（关键符号：GetFilePreviewHandler.execute）、[tools/file-understanding.tools.ts](file://packages/server-ai/src/file-understanding/tools/file-understanding.tools.ts)（关键符号：createFileUnderstandingTools / SEARCH_RESULT_LIMIT）

## R4 大文件、内联与不支持类型

**业务目标**：知道哪些体积/形态会走内联、哪些走后台、哪些必然落到 `failed`，避免「上传成功但 Agent 读不到」被误判。
**调用顺序**：① 会话内联 `data:` 文件受 `MAX_DATA_URL_BYTES = 25MB` 与 base64 校验约束 → ② 内联字节超过 `MAX_INLINE_PARSE_BYTES = 2_000_000` 时转后台 → ③ 解析分流 `shouldRunParseInline`：`fast` 恒真、`deep` 恒假、其余按 `size <= 2_000_000` → ④ 解析阶段 `FileParserRegistry.getParser(source)` 按固定顺序匹配 pdf → spreadsheet → office → image → archive → text。
**时序边界**：体积与模式判定发生在请求内，只决定「同步或后台」，不影响是否建资产；类型判定发生在解析阶段——后台分支的失败只进 `logger.warn` 与资产 `error`，客户端看不到即时错误。
**预期结果**：图片 → `status='partial'`、`capabilities` 含 `preview/read/vision/ocr`、metadata 标 `ocrPending/visionPending`；PDF → 每页文本 + 页图（scale 2），页数超过 `FILE_UNDERSTANDING_PDF_RENDER_MAX_PAGES`（默认 300）或被截断/报错时 `partial` + metadata `renderError`；压缩包 → 前 500 项清单 + 前 80 个文本类条目正文（≤200KB/条），其余仅清单。
**错误处理**：六解析器全不匹配 → `UnsupportedFileContentError`，在 handler 内被吞成 `status='failed'` + `understandingErrorCode='file_understanding_parse_failed'`；`deep` 模式无可用 Embedding → `file_understanding_embedding_unavailable`；向量索引/检索异常 → `file_understanding_vector_index_failed`；超 25MB 内联 → 400 `Chat request file is too large`。
**真实代码示例**
```http
POST /api/ai/contexts/file   # 大文件请走 multipart，不要用 data: 内联
file=@big.pdf & parseMode=auto
```
章节来源：[chat-file-assets.ts](file://packages/server-ai/src/xpert/commands/handlers/chat-file-assets.ts)（关键符号：MAX_DATA_URL_BYTES / MAX_INLINE_PARSE_BYTES / normalizeChatRequestFiles）、[file-parser.registry.ts](file://packages/server-ai/src/file-understanding/parsers/file-parser.registry.ts)（关键符号：FileParserRegistry.getParser / UnsupportedFileContentError）、[context.controller.ts](file://packages/server-ai/src/ai/context.controller.ts)（关键符号：ContextsController.shouldRunParseInline）

## R5 删除与回收（含 `DeleteFileAssetCommand` 入边）

**业务目标**：删掉一个资产并把连带产物清干净；同时明确哪些清不干净、去哪里看残留。
**调用顺序（HTTP 入边）**：① `DELETE /api/ai/files/:fileId` → `authorizeFile(...,'delete')` → `DeleteFileAssetCommand`；② `DELETE /api/ai/contexts/file/:id`（`:id` 是 **storageFileId**）：有 `FileAsset` 时先 `resolve({locator:{fileAssetId,storageFileId}, operation:'delete'})` + `DeleteFileAssetCommand`，随后 `deleteAuthorizedStorageFile`；无 `FileAsset` 时走 `assertStorageFileOwner(id)`（**严格 owner，无管理员豁免**）。
**事件入边的实际效果**：`DeleteFileAssetHandler.execute` 只有一句 `await this.deletion.delete(command.fileAssetId)`；`FileAssetDeletionService.delete` 先以 `operation:'delete'` 授权，再 `cleanup` 按固定顺序硬删：向量（`deleteFileVectors`）→ `file_citation_anchor` → `file_embedding` → `file_chunk` → `file_artifact` → `conversation_file_link` → `file_asset` 行 → 页图对象 → 派生目录。项目回收是**独立入口** `purgeProjectFile`（先 `assertCanPurge`，再比对 `asset.projectId === project.id && asset.tenantId === project.tenantId`），由 `ProjectPurgeService` 逐资产调用。
**时序边界**：**无软删**——`file_asset` 连 `deletedAt` 都没有；`storage_file` 有 `deletedAt` 列但删除路径走 `repository.remove`（注释明写是为触发 `afterRemove` 的 entity 参数）。派生目录 `fsPromises.rm` **仅在 `provider.path()` 返回绝对路径（本地 provider）** 时执行；向量删除与页图/目录删除失败一律静默。
**预期结果**：资产行、产物、块、锚点、向量账本、会话链接全部消失，本地 provider 下派生目录被清；远端 provider 下 `contexts/<tenantId>/file-understanding/<assetId>/**` 可能残留为孤儿对象。
**错误处理**：403 `FileAssetAccessDenied`；`contexts/file/:id` 无 storageFile 时抛**空消息** `ForbiddenException`；项目忙（存在 `uploaded|scanning|parsing|processing|queued` 资产）→ 400 `ProjectPurgeBusy`；项目归属不符 → 403 `Error.ProjectPurgeFileMismatch`。
**真实代码示例**
```ts
// commands/handlers/delete-file-asset.handler.ts
async execute(command: DeleteFileAssetCommand): Promise<void> {
    await this.deletion.delete(command.fileAssetId)
}
```
章节来源：[delete-file-asset.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/delete-file-asset.handler.ts)（关键符号：DeleteFileAssetHandler.execute）、[file-asset-deletion.service.ts](file://packages/server-ai/src/file-understanding/file-asset-deletion.service.ts)（关键符号：FileAssetDeletionService.delete / cleanup / purgeProjectFile / deleteDerivedRootIfLocal）、[storage-file.service.ts](file://packages/server/src/storage-file/storage-file.service.ts)（关键符号：deleteAuthorizedStorageFile / deleteStorageFile）

## R6 写入文件记忆并在下一轮消费

**业务目标**：让 Agent 把「值得跨会话保留的事实」写进卷上记忆，并在后续轮次被自动召回，而不落任何本域表。
**调用顺序**：① **显式**：模型调 `memory_write` → `FileMemoryService.writeMemory`（frontmatter `source:'explicit'`）→ ② **隐式**：轮次结束 `afterAgent` → `FileMemoryWritebackRunner.enqueue(snapshot)`，按 `createFileMemoryScopeKey`（含 tenant/project/user）串行，`softDrain` 可限时等待；`processSnapshot` 先 `recordWritebackCandidate`，再 `searchMemory`，由 `decideFileMemoryWriteback` 决策 `upsert`/`archive`，落 `source:'writeback'` → ③ **离线**：`POST /api/xpert/:id/memory/dream` → `FileMemoryDreamService.triggerDream`（gate 默认 `minIntervalMinutes:30`）经 `XpertAgentChatCommand` 调 dreamer 助手 → ④ **消费**：`beforeAgent` 起后台召回，`wrapModelCall` 用 `buildMemoryContextMessages(recall)` 前置注入（预算 20KB/轮、60KB/会话、召回超时 3s），工具面 `memory_search`/`memory_get`/`memory_write`。
**时序边界**：写入与消费都发生在 Agent 中间件钩子里，不经 DB 事务；记忆介质是卷上 markdown/JSON，路径为 `.xpert/memory`（项目共享卷下为 `.xpert/memory/xperts/<xpertId>`），路径归一化拒绝 `..` 与绝对路径。记忆域与理解域**零代码依赖**。
**预期结果**：生成 `MEMORY.md` 索引 + `user|feedback|project|reference` 四类目录文件，`status ∈ active|archived|conflict` 写在 frontmatter；Dream 运行证据落 `.dream/runs/<runId>`（gate 未过落 `status='skipped'`，**不是错误**）。
**错误处理**：同轮已发生 `memory_write` 时 `afterAgent` 直接 `skipped reason=explicit_write`（避免双写）；模型不可用时只留候选并 warn；xpert 未启用 sandbox feature → `XpertFileMemoryMiddleware requires the xpert sandbox feature to be enabled.`；同 scope 已有运行 → 返回 `{...pending, coalesced:true}`；backend 不可用 → `Sandbox backend is unavailable for file memory runtime.`
**真实代码示例**
```http
POST /api/xpert/<xpertId>/memory/dream      { "reason": "manual" }
GET  /api/xpert/<xpertId>/memory/dream/runs/<runId>
```
章节来源：[file-memory.middleware.ts](file://packages/server-ai/src/file-memory/file-memory.middleware.ts)（关键符号：XpertFileMemoryMiddleware.beforeAgent / wrapModelCall / afterAgent）、[file-memory.writeback-runner.ts](file://packages/server-ai/src/file-memory/file-memory.writeback-runner.ts)（关键符号：FileMemoryWritebackRunner.enqueue / softDrain / processSnapshot）、[file-memory/dream.service.ts](file://packages/server-ai/src/file-memory/dream.service.ts)（关键符号：FileMemoryDreamService.triggerDream / DEFAULT_DREAM_GATE_CONFIG）

## R7 存储抽象切换与新增存储后端

**业务目标**：把对象存储从 LOCAL 换到外部后端（或新增一个后端）之后，历史文件仍可读，且知道哪些能力会退化。
**调用顺序**：① provider 名解析顺序 = 请求 `tenantSettings['fileStorageProvider']` → `environment.fileSystem.name` → `LOCAL`；落库时统一大写（`normalizeStorageProvider`）→ ② 新增后端：以 `@FileStorageProvider` 注册进 registry（`FileStorageRegistryBridge`）→ ③ 读取侧按**行上的 provider** 解析：`new FileStorage().getProvider(storageFile.storageProvider).path(storageFile.file)` → ④ 切换后旧对象必须保持可读，历史行不改写。
**时序边界**：provider 名在 `storage_file` 行落库瞬间固化，不随租户设置变化；`storage_file.storageProvider` 带 `@Exclude({toPlainOnly:true})` 不对外序列化；加载时 `afterLoad` 动态补 `fileUrl`。
**预期结果**：新写入行带新 provider 值、旧行仍按旧 provider 读取；`FileStorage.getProvider()` 先查注册表，失败**静默回落**内置 provider（注释逐字「Fall back to built-in providers so bootstrap/tests without Nest context keep working.」）。
**错误处理**：走 `storage()` 路径且 provider 未注册 → `Provider "…" is not registered`；`getProviderInstance` 的静默回落意味着**排障时不能据返回值判断真实 provider**；远端 provider 的 `path()` 若不返回绝对路径，删除链的派生目录清理不生效（孤儿对象）。
**真实代码示例**
```ts
// packages/server/src/file/file-storage/file-storage.ts
const registry = FileStorageRegistryBridge.getRegistry()
if (registry) { try { return registry.get(`${this.config.provider}`) } catch { /* 静默回落 */ } }
return this.providers[this.config.provider]   // 内置（LOCAL）
```
章节来源：[file-storage.ts](file://packages/server/src/file/file-storage/file-storage.ts)（关键符号：FileStorage.setProvider / getProviderInstance）、[storage-file.service.ts](file://packages/server/src/storage-file/storage-file.service.ts)（关键符号：StorageFileService.createStorageFile / normalizeStorageProvider）、[storage-file.subscriber.ts](file://packages/server/src/storage-file/storage-file.subscriber.ts)（关键符号：StorageFileSubscriber.afterLoad）

## R8 跨域：从对话附件走归一化

**业务目标**：把聊天请求里的三种文件形态统一成 `FileAsset`，让工具面（`parsed_file_*`）与消息组装都能看到它。
**调用顺序**：① `XpertModule` 调 `normalizeChatRequestFiles` → ② 三形态归一：data URL（校验 base64 + 25MB）、老式 `storageFileId`（`GetOwnedStorageFileQuery`）、`workspacePath`（工作区卷）→ ③ `AssertFileUploadScopeQuery` 断言上传作用域 → ④ `CreateFileAssetCommand` / `CreateWorkspaceFileAssetCommand` 建句柄 → ⑤ `EnqueueFileParseCommand` 启动理解 → ⑥ 需要挂到会话时 `AttachFileToConversationCommand`。
**时序边界**：归一化在聊天请求内完成；≤2MB 内联字节走同步解析、其余后台；attach 由 `AttachFileToConversationHandler` 做 `ConversationFileLink` 先查后写（唯一索引兜底）并 best-effort 触发 `projectFileAsset` 投影。
**预期结果**：同一 `storageFileId` 复用同一 `file_asset` 行；会话侧出现 link，此后该文件在该会话的工具面可读/可检索。
**错误处理**：400 `Chat request file is too large` / `Invalid chat request file data URL`；跨项目复用同一 `file_asset` 的链接 → 409 `This file is already shared with another Project`；403 上传作用域或助手可见性不符。
**真实代码示例**
```ts
// xpert/commands/handlers/chat-file-assets.ts
normalizeChatRequestFile(...) → resolveOrCreateFileAssetForStorageFile(...) → attachChatFileAssetsToConversation(...)
```
章节来源：[chat-file-assets.ts](file://packages/server-ai/src/xpert/commands/handlers/chat-file-assets.ts)（关键符号：normalizeChatRequestFile / resolveOrCreateFileAssetForStorageFile / attachChatFileAssetsToConversation）、[attach-file-to-conversation.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/attach-file-to-conversation.handler.ts)（关键符号：AttachFileToConversationHandler.execute）

## R9 跨域：知识库摄取取源文件句柄

**业务目标**：知识库只把本域的对象存储行当作**源文件句柄**，自己走转换/切片/向量链，不共享解析结果。
**调用顺序**：① `knowledge-document` 侧以 `document.storageFileId` 投 `GetOwnedStorageFileQuery` → ② 拿到 `StorageFile`（key/url/size/mimetype/provider）→ ③ 用自己的转换器与向量存储处理，写知识库侧的表。
**时序边界**：知识库仅在摄取时读一次句柄，**不读** `file_asset`，因此不继承 `parseMode`/解析状态，也不受本域解析失败影响；反向依赖为 0（本域不 import 知识库）。
**预期结果**：知识库文档行与 `storage_file` 行形成引用；同一文件可同时被理解域建 `file_asset`、被知识库建文档。
**错误处理**：句柄不属于当前 tenant/organization 时查询返回空（由所属方判定）；「知识库侧是否容忍句柄缺失」**未确认**（本域只提供查询，如何处置在对方域）。
**真实代码示例**
```ts
// knowledge-document/document.service.ts（跨域只读依赖，共三处调用）
queryBus.execute(new GetOwnedStorageFileQuery(document.storageFileId))
```

## R10 跨域：项目卷挂载与随项目回收

**业务目标**：把会话附件挂到项目、让项目维度能列举文件，并在项目永久删除时把文件与卷一起回收。
**调用顺序**：① 会话绑定项目：`conversation-project.service.ts` 用 `AttachFileToConversationCommand` 挂载附件；项目侧拥有权校验用 `GetOwnedStorageFileQuery` → ② `FileAssetAccessService.assertCanEdit` **先于** link 查询（注释逐字：读权限成员不得借既有 link 绕过项目编辑边界）→ ③ 永久删除：`ProjectPurgeService.purge` 先做「处理中不许删」忙判 → 逐资产 `purgeProjectFile`（校验 `projectId`/`tenantId`）→ `VolumeHandle.removePath(..., {boundaryRoot})` 删项目卷根目录。
**时序边界**：attach 的授权先于链接读取；purge 的忙判先于逐资产清理，卷删除发生在资产清理之后；个人 Xpert 卷**不因**项目会话自动公开，须显式 attach 后由 `ConversationFileLink` 成为共享授权。
**预期结果**：`conversation_file_link` 新增或复用一行；项目维度可用 `file_asset` 的 `@Index(['tenantId','organizationId','projectId'])` 列举文件；项目删除后资产行、产物与项目卷均被清理。
**错误处理**：403 `Error.ProjectPurgeFileMismatch`（资产与项目不一致）、403 无 `assertCanPurge` 权限、400 `ProjectPurgeBusy`、409 跨项目复用同一资产；项目侧 `project-file.entity.ts` 已标注弃用（改走 FileAsset 工作区投影）。
**真实代码示例**
```ts
// xpert-project/services/project-purge.service.ts（跨域调用本域专用入口）
queryBus/commandBus → purgeProjectFile(project, asset) → VolumeHandle.removePath(root, { boundaryRoot })
```
章节来源：[file-asset-deletion.service.ts](file://packages/server-ai/src/file-understanding/file-asset-deletion.service.ts)（关键符号：FileAssetDeletionService.purgeProjectFile）、[conversation-project.service.ts](file://packages/server-ai/src/xpert-project/services/conversation-project.service.ts)（关键符号：AttachFileToConversationCommand）、[project-purge.service.ts](file://packages/server-ai/src/xpert-project/services/project-purge.service.ts)（关键符号：ProjectPurgeService.purge）

## R11 排障：解析卡住 / 预览 404 / 记忆不生成 / 回收未清 / 跨域 403

**业务目标**：把五个高频症状各自定位到唯一观测点，避免在错误层（DB / provider / 授权）上反复试。
**调用顺序（按症状各一条链）**：① **解析卡住** → 查 `file_asset.status='parsing'` 存量 + 日志 `Failed to parse file asset <id>: <msg>`（warn）→ 处置用 `POST /api/ai/files/:id/parse/retry`；② **预览为空/404** → 先用 `GET /api/ai/files/:id/status` 确认资产存在与 `capabilities`，再核对 provider 与派生目录（**preview 查不到 asset 时返回 `null` + HTTP 200**，真正的 404 只在 status 端点）；③ **记忆不生成** → 取 `POST /api/xpert/:id/memory/dream` 返回的 runId → `GET …/dream/runs/:runId`，读 `output/gate.json` 与 `status='skipped'`，看日志 `File memory dream skipped for <xpert>/<runId>: …`；④ **回收未清** → 判断 `provider.path(derivedRoot)` 是否绝对路径，远端 provider 只删 DB 行，subscriber 异常被 `console.log` 吞掉，须查对象存储控制台；⑤ **跨域 403** → 逐层核对鉴权矩阵（`FileAssetAccessDenied` / 公共会话主体与 owner 不一致 / client_secret 绑定非 ENTERPRISE_XPERT / 项目场景未 attach）。
**时序边界**：① 的根因是「无持久队列」——后台解析用 `setImmediate`，进程重启即丢任务，状态可能**永久停在 `parsing``；③ 的 `skipped` 与 `coalesced:true` 都不是错误（前者 gate 未过，后者同 scope 已有运行）；④ 的残留是「DB 已删、对象仍在」的时序差。
**预期结果**：每类症状都能落到一个可复现的判据：状态列 + `metadata.understandingErrorCode`（`file_understanding_embedding_unavailable` / `file_understanding_vector_index_failed` / `file_understanding_parse_failed`）、`[FILE_VECTOR_DEBUG]` 日志、dream run 目录、provider 返回值。
**错误处理**：若 |`parsing` 长期不降，先确认是否多实例/重启导致丢任务，再决定是否引入持久队列（当前不存在）；若 403 来自 `resolve`，注意它**不区分**「不存在」与「无权限」，需用 tenant/organization/owner 逐项比对；跨域删除失败一律转 403，不要据状态码推断业务原因。
**真实代码示例**
```bash
# ① 积压排查
SELECT status, count(*) FROM file_asset GROUP BY status;
# ② 失败原因
SELECT metadata->>'understandingErrorCode' FROM file_asset WHERE status = 'failed';
```
