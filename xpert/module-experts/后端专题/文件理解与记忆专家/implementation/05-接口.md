## 一、总览：前缀、端点数与控制器分工

全局前缀 `api`（`setGlobalPrefix('api', { exclude: ['a','a/(.*)','.well-known/oauth-protected-resource/(.*)'] })`），另注册全局守卫 `AuthGuard + PluginScopeGuard`。模块前缀由 `RouterModule.register` 或控制器自身路径给出。

|---|---|---|---|---|
| `FileUnderstandingController` | `@Controller()`（空前缀）＋ `RouterModule { path: '/ai' }` | `/api/ai/*` | **8** | `@Public()` ＋ `@AllowClientSecretBindings(ENTERPRISE_XPERT)` ＋ `ApiKeyOrClientSecretAuthGuard` |
| `FileMemoryController` | `@Controller('xpert/:id/memory')`，无独立 RouterModule（父模块装载） | `/api/xpert/:id/memory/*` | **6** | `@UseGuards(XpertGuard)` |
| `StorageFileController` | `@Controller()` ＋ `RouterModule { path: '/storage-file' }` | `/api/storage-file/*` | **3** | **无控制器守卫**，鉴权在 service |

| `WorkbenchFilesController`（邻域） | `@Controller('conversations/:conversationId')` ＋ `/ai` | `/api/ai/conversations/:id/workspace/*` | 6 | `@Public()` ＋ `WorkbenchFilesAuthGuard` |

## 二、上传入口与路径校正

**路径校正**：`ContextsController` 的装饰器写作 `@Controller('contexts')` ＋ `@Post('file')` / `@Delete('file/:id')`，但它注册在 `AIModule` 的 `controllers` 中，而 `AIModule` 由 `RouterModule.register([{ path: '/ai', module: AIModule }])` 装载 —— 因此真实路径是 **`POST /api/ai/contexts/file`** 与 **`DELETE /api/ai/contexts/file/:id`**（旧代码注释与部分文档写的 `POST /contexts/file` 缺 `/ai` 段，勿直接照抄）。

| 方法 | 真实路径 | 用途与关键行为 | 主要错误 |
|---|---|---|---|
| POST | `/api/ai/contexts/file` | multipart 上传 → `UploadFileCommand`（target 默认 `{kind:'storage',directory:'contexts',prefix:'files'}`）→ `CreateFileAssetCommand` → `EnqueueFileParseCommand`；返回 `AgentFile`（`withFileUnderstanding` 合并解析态） | 400 `ExternalUploadTargetInvalid` / `Failed to upload context file…`；403（公共 Xpert 会话下非 storage target 或带 projectId、xpertId 不匹配） |
| DELETE | `/api/ai/contexts/file/:id` | `:id` 是 **storageFileId**：若有 FileAsset → `resolve({locator:{fileAssetId,storageFileId}, authority:current-owner, operation:'delete'})` → `DeleteFileAssetCommand` → `deleteAuthorizedStorageFile`；若无 FileAsset → `assertStorageFileOwner(id)`（**严格 owner，无管理员豁免**） | 403（`FileAssetAccessDenied`；`!storageFile` 时抛空 `ForbiddenException`） |

上传体参数：`file`（multipart）、`target`（JSON，仅允许 `kind:'storage'` 且 `directory`/`prefix` 必须与默认值一致，多余键即 400）、`purpose`（默认 `chat_attachment`）、`parseMode`（`auto|fast|deep|none`，默认 auto）、`conversationId`/`threadId`/`projectId`/`xpertId`（若 conversationId/threadId 能解析到会话则以会话字段覆盖），**`workspacePath` 被显式忽略**（源码 `workspacePath = undefined`）。是否同步解析由 `shouldRunParseInline(file, parseMode)` 决定（小文件内联，否则 `setImmediate` 后台）。

**它为何是文件理解的实际入口**：`FileUnderstandingController` 只提供句柄/检索/删除类端点，不含 multipart 上传；`FileAsset` 的创建与解析入队只发生在 `contexts/file`（及 xpert 域 `chat-file-assets.ts` 的会话文件归一化路径）。旧入口 `POST /api/ai/v1/file`（`AIV1Controller`，`@Controller('v1')` ＋ `/ai`）源码注释逐字标注「@deprecated Use POST /contexts/file. The context endpoint returns an AgentFile/FileAsset handle and starts the file-understanding parse flow.」——迁移语义即：旧入口只落 `StorageFile`/destination、**不建 FileAsset、不触发解析**；新入口返回 FileAsset 句柄并启动理解链。

章节来源：[context.controller.ts](file://packages/server-ai/src/ai/context.controller.ts)（关键符号：ContextsController.create / delete / resolveExternalStorageUploadTarget / withFileUnderstanding），[ai.module.ts](file://packages/server-ai/src/ai/ai.module.ts)（关键符号：RouterModule.register / controllers），[ai-v1.controller.ts](file://packages/server-ai/src/ai/ai-v1.controller.ts)（关键符号：AIV1Controller.create / @deprecated），[external-upload-target.ts](file://packages/server-ai/src/ai/external-upload-target.ts)（关键符号：EXTERNAL_STORAGE_TARGET_KEYS / invalidExternalUploadTarget），[chat-file-assets.ts](file://packages/server-ai/src/xpert/commands/handlers/chat-file-assets.ts)（关键符号：DEFAULT_UPLOAD_TARGET / normalizeChatRequestFile）

## 三、FileUnderstandingController：8 条端点

类级三件套：`@Public()`（放开全局 `AuthGuard`）、`@AllowClientSecretBindings(SecretTokenBindingType.ENTERPRISE_XPERT)`、`@UseGuards(ApiKeyOrClientSecretAuthGuard)`；每个方法先经 `authorizeFile(fileId, operation)` → `FileAssetAccessService.resolve({authority:'current-owner'})`，再叠加公共 Xpert 会话 scope 校验（`getPublicXpertSessionConversationScope()` 命中时要求 `fileAsset.userId === scope.createdById`，否则空 `ForbiddenException`）。

| 方法 | 路径 | 用途 | operation | 主要错误 | 消费方 |
|---|---|---|---|---|---|
| GET | `/api/ai/files/:fileId` | 返回授权后的 FileAsset 句柄 | `read` | 403 `FileAssetAccessDenied` | ChatKit/前端附件面板 |
| GET | `/api/ai/files/:fileId/status` | `GetFileParseStatusQuery` → `{fileId,status,error,parsedAt}` | `read` | 403；404 `File asset "…" not found` | 前端轮询、排障 |
| POST | `/api/ai/files/:fileId/parse/retry` | `RetryFileParseCommand` → 转 `ParseFileAssetCommand`（**无状态门禁**） | `parse` | 403；解析异常被 handler 吞并写 `status='failed'` | 前端重试按钮 |
| POST | `/api/ai/files/:fileId/search` | `SearchFileChunksQuery({fileId,query,limit})`：有 query 走向量＋关键词 RRF 融合；无 query 按 `orderNo` 列举 | `read` | 403 | Agent 工具、LoadFileHandler、runtime capability |
| GET | `/api/ai/files/:fileId/preview` | `GetFilePreviewQuery`：紧凑预览（去掉审计字段与 artifact 正文） | `read` | 403；asset 不存在时 handler 返回 `null`（HTTP 200） | shared/agent 消息组装、Agent 工具 |
| POST | `/api/ai/files/:fileId/read` | `ReadFileChunkQuery({chunkId|orderNo})`；按 `orderNo` 缺省 0 | `read` | 403；chunk 缺失返回 `null` | Agent 工具（`parsed_file_read` 约定缺失即终态 not-found） |
| GET | `/api/ai/conversations/:conversationId/files` | 先 `assertConversationAccess({kind:'conversation'},'read')`，再 `ListConversationFilesQuery` | 会话读 | 403（会话不可读/会话与资产组织不一致） | Agent 工具 `parsed_file_list`、ChatKit |
| DELETE | `/api/ai/files/:fileId` | `DeleteFileAssetCommand` → `FileAssetDeletionService.delete` 全链路清理 | `delete` | 403 | 前端删除 |

`GET /api/ai/conversations/:conversationId/files` 与邻域 `GET /api/ai/conversations/:conversationId/workspace/files` 是两条不同路由，`ai/workbench-files-routing.http.spec.ts` 以两种控制器注册顺序断言二者不互相遮蔽。

## 四、FileMemoryController：6 条端点

`@UseGuards(XpertGuard)` ＋ `@Controller('xpert/:id/memory')`；`:id` 统一走 `UUIDValidationPipe`。`XpertGuard` 判定：`xpert.createdById === user.id` 或 `workspaceService.canAccess(xpert.workspaceId, user.id)`，失败抛 `ForbiddenException('Access denied')`，命中后缓存 5 分钟（`userXperts:<tenantId>:<userId>_<xpertId>`）。全部方法经 `FileMemoryFacade` → `FileMemoryDreamService`（记忆体的**文件 CRUD 不在此控制器**，见第六节）。

| 方法 | 路径 | 用途与关键行为 | 主要错误 |
|---|---|---|---|
| POST | `/api/xpert/:id/memory/dream` | `triggerDream(xpert,{reason})`；`reason` 可取 `manual|scheduled|signal_threshold`；若同 scope 已有 pending 运行，直接返回 `{...pending, coalesced:true}`；否则写 `queued` 并异步启动 | 403；gate 未过时**不报错**，落 `status='skipped'` 并写 `output/gate.json` |
| GET | `/api/xpert/:id/memory/dream/config` | 返回磁盘 `config.json` ＋ `defaults`（env 派生） | 403 |
| PUT | `/api/xpert/:id/memory/dream/config` | 归一化 `dreamerXpertId`/`dreamerAgentKey` 后写回并回读（**`gate{…}` 不经 DTO 白名单**，仅由 service 侧归一化） | 403；解析 dreamer 缺项时错误文案 `FileMemory Dreamer config requires dreamerXpertId and dreamerAgentKey.` |
| GET | `/api/xpert/:id/memory/dream/runs` | 扫描 `.dream/runs/*` 目录，按 `requestedAt` 倒序返回运行摘要；目录缺失返回 `[]` | 403 |
| GET | `/api/xpert/:id/memory/dream/runs/:runId` | 运行详情：summary ＋ preflight ＋ report ＋ validation ＋ artifacts 清单 | 403 |
| POST | `/api/xpert/:id/memory/dream/runs/:runId/cancel` | 仅当状态为 `queued` 时置 `cancelled` 并写 `finishedAt`；其他状态原样返回 | 403 |

## 五、StorageFileController：3 条端点

模块路由 `/storage-file`，控制器 `@Controller()`，**无类级守卫/无 `@Public()`** —— 因此只受全局 `AuthGuard` 与 service 断言约束。

| 方法 | 路径 | 用途与关键行为 | 主要错误 |
|---|---|---|---|
| POST | `/api/storage-file` | `FileInterceptor('file')` → `UploadFileCommand`（target `{kind:'storage',directory:'files',prefix:'files'}`）→ `getStorageFileFromAsset` | 400 `Failed to upload storage file`（destination 非 success） |
| POST | `/api/storage-file/url` | `axios.get(url,{responseType:'arraybuffer'})` 拉取后 `provider.putFile(url)` 落盘，`originalname` 按 latin1→utf8 纠正，再 `createStorageFile` | 400 `Failed to download and store file from URL: <msg>` |
| DELETE | `/api/storage-file/:id` | `UUIDValidationPipe` ＋ `service.deleteStorageFile(id)` | 403（**catch-all**：任何异常一律转 `ForbiddenException`）；404 语义不单独返回 |

**鉴权在 service 的断言位置**（`storage-file.service.ts`）：
1. `deleteStorageFile(id)`：先 `findOne(id)`（注释逐字「为了正确触发 StorageFileSubscriber 的 afterRemove 事件参数中的 entity」），再取 `RequestContext.currentUserId()` 与 `hasRoles([SUPER_ADMIN, ADMIN])`；`!userId || (entity.createdById !== userId && !isTenantAdmin)` → 403；方法体整体 `try/catch` 把任意失败（含找不到行）都转成 403。
2. `deleteAuthorizedStorageFile({id,tenantId,organizationId})`：供**已由属主域授权**的跨域调用使用（如 `contexts/file/:id` 删除链），校验 `entity.tenantId === storageFile.tenantId` 且 `(entity.organizationId ?? null)` 一致，否则 403。
3. `createStorageFile`：无鉴权，仅归一化 provider（`normalizeStorageProvider` → 大写，缺省回落 `LOCAL`）——它是 `StorageTargetStrategy` 的落库点。

邻域说明：仓库内**真正的通用上传口**是 `POST /api/files`（`FileUploadModule` 注册 `/files`，imports `StorageFileModule`）；`StorageTargetStrategy`（`@FileUploadTargetStrategy('storage')`）是 `storage_file` 的唯一写入点之一：key 形如 `<directory>/<tenantId>/<fileName>`，并断言 key 不得越出租户目录。

章节来源：[storage-file.controller.ts](file://packages/server/src/storage-file/storage-file.controller.ts)（关键符号：create / createUrl / delete），[storage-file.service.ts](file://packages/server/src/storage-file/storage-file.service.ts)（关键符号：createStorageFile / deleteStorageFile / deleteAuthorizedStorageFile / removeStorageFile），[file-upload.module.ts](file://packages/server/src/file/file-upload/file-upload.module.ts)（关键符号：RouterModule.register / FileUploadModule），[storage-target.strategy.ts](file://packages/server/src/file/file-upload/strategies/storage-target.strategy.ts)（关键符号：StorageTargetStrategy.upload / assertContainedInTenantDirectory）

## 六、其他相关入口

- **记忆文件 CRUD（xpert 域，非本控制器）**：`XpertController`（`/api/xpert`）提供 `GET :id/memory/files`、`GET :id/memory/file`、`PUT :id/memory/file`、`POST :id/memory/file/upload`、`DELETE :id/memory/file`（均 `XpertGuard`，转 `XpertService` 的 memory 方法）；另 `GET :id/memory`（旧记忆列举）与 `POST :id/memory/bulk`。它们与 `FileMemoryFacade.getMemoryFiles/getMemoryFile/saveMemoryFile/uploadMemoryFile/deleteMemoryFile` 同源——**校验与路径语义在本域 facade/paths 中**。
- **工作区文件（邻域）**：`WorkbenchFilesController`（`/api/ai/conversations/:conversationId/workspace/file[s]`，含 `file` 单数别名、`download`、上传 100MB 限制）与 `XpertController` 的 `:id/workspace/file(s)` 系列。

## 七、鉴权矩阵与「看似无守卫」的解释

| 层 | 机制 | 覆盖范围 | 判定要点 |
|---|---|---|---|
| L0 全局 | `AuthGuard` ＋ `PluginScopeGuard`（bootstrap 注册） | 所有路由 | 缺省要求已认证用户；`@Public()` 标注显式放开 |
| L1 公共 AI 端点 | `ApiKeyOrClientSecretAuthGuard` ＋ `@AllowClientSecretBindings(ENTERPRISE_XPERT)` | `FileUnderstandingController`、`ContextsController` | 允许 API Key 或 **ENTERPRISE_XPERT 类型**的 client secret 绑定 |
| L2 助手作用域 | `XpertGuard` | `FileMemoryController`（及 xpert 域记忆/工作区文件） | owner 或 workspace 可访问；命中后缓存 5 分钟 |
| L3 服务断言 | `FileAssetAccessService`、`StorageFileService`、`FileAssetDeletionService` | 全部文件端点 | 见下 |

**为何多个文件端点看似无守卫**：两件事叠加。
1. `FileUnderstandingController` 类级标记 `@Public()`（放开 L0），文件级边界完全由 L1 守卫 + `FileAssetAccessService.resolve` 承担 —— 而 `resolve` 的判定是**隐式**的：`fileAssetRepository.findOne({id, tenantId: actor.tenantId})` 查不到与组织不可见、locator 不一致一样，统一抛 `FileAssetAccessDenied`（403），因此从控制器签名上看不到任何鉴权痕迹。
2. `StorageFileController` 既无守卫也无装饰器，删除授权内联在 `StorageFileService.deleteStorageFile/deleteAuthorizedStorageFile` 里，且**所有异常被 catch 成 403**；上传/URL 抓取则完全不设用户边界（依赖 L0 全局登录）。所以「无守卫」≠「无鉴权」，但也确实意味着**绕过 service 直查仓储即越权**。

```mermaid
flowchart TD
    R[HTTP 请求] --> G0[全局 AuthGuard + PluginScopeGuard]
    G0 -->|@Public 放开| G1[ApiKeyOrClientSecretAuthGuard<br/>ENTERPRISE_XPERT client_secret 绑定]
    G0 -->|默认| U[用户会话]
    G1 --> FA[FileAssetAccessService.resolve<br/>tenantId 过滤 + 组织可见 + locator 一致]
    U --> XG[XpertGuard<br/>owner 或 workspace 可访问]
    XG --> FM[FileMemoryFacade 记忆卷]
    U --> SF[StorageFileService<br/>owner 或 SUPER_ADMIN/ADMIN]
    FA --> OP[按 operation 分支<br/>read/attach/parse/write/delete → project/conversation/xpert 边界]
    SF --> RM[repository.remove → Subscriber 删物理对象]
```

## 八、错误语义

- **文件不存在**：`FileAssetAccessService.resolve` 对「不存在」与「无权限」**不区分**，统一 403 `Error.FileAssetAccessDenied`（默认文案 `You do not have access to this file`，i18n key `server-ai:Error.FileAssetAccessDenied`）——防枚举。仅 `GET /files/:fileId/status` 在授权通过后会额外 404（`File asset "…" not found`）。
- **类型不支持**：`FileParserRegistry.getParser` 六解析器全不匹配 → `UnsupportedFileContentError`；该异常在 `parse-file-asset.handler` 的 catch 中落为 `status='failed'`（HTTP 不抛错），`metadata.understandingErrorCode='file_understanding_parse_failed'`。
- **解析失败**：`status='failed'` ＋ `error`（异常 message）＋ `failedAt`；错误码三态：`file_understanding_embedding_unavailable`（deep 模式缺可用 Embedding 模型）、`file_understanding_vector_index_failed`（向量索引/检索不可用）、`file_understanding_parse_failed`（其余）。
- **重试不可用**：HTTP `POST /files/:fileId/parse/retry` **本身无门禁**（直接 Enqueue→Parse）；门禁只在 runtime capability：非 `failed` 且 `vectorIndexStatus` 非 `failed/unavailable` → 400 `Only failed or unavailable file understanding can be retried`。
- **越权访问**：403 家族 —— 资产级 `FileAssetAccessDenied`；公共 Xpert 会话 scope 不匹配抛**空消息** `ForbiddenException`；`contexts/file/:id` 无 storageFile 时同样空 403；跨项目复用同一 FileAsset 的 link → **409** `This file is already shared with another Project`；项目 purview 不符 → 403 `Error.ProjectPurgeFileMismatch`。
- **存储不可用**：解析时既无 `storageFileId` 又无 workspace 卷源 → `File asset "…" does not have a readable storage or workspace source`（同落 failed）；provider 未注册时 `FileStorage.storage()` 抛 `Provider "…" is not registered`；`storage_file` 行找不到时 `deleteStorageFile/deleteAuthorizedStorageFile` 一律 403。
- **体积超限与入参非法**：会话内联 `data:` 文件超过 `MAX_DATA_URL_BYTES`（25MB）→ 400 `Chat request file is too large`；data URL 非 base64 → 400 `Invalid chat request file data URL`；外部 upload target 非 `storage` 或携带额外键/改动 `directory`/`prefix` → 400 `Error.ExternalUploadTargetInvalid`（文案 `External uploads only support the server-managed storage target`）。≤ `MAX_INLINE_PARSE_BYTES`（2,000,000）的内联字节走同步解析，其余后台。
