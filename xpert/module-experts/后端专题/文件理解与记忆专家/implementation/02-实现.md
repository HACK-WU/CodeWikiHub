## 上传与落地
入口是 `ContextsController.create`（`POST /api/ai/contexts/file`，multipart）：`resolveExternalStorageUploadTarget(targetValue, {kind:'storage', directory:'contexts', prefix:'files'})` 解析可选 JSON target；`workspacePath` 被强制清空；`resolveConversationReferences` 用 `conversationId`/`threadId` 反查会话并**用会话覆盖** `projectId`/`xpertId`；公共会话（`getPublicXpertSessionConversationScope`）只允许 storage target 且 xpert 必须匹配；否则调 `assertUploadScope`（项目编辑权 + 可用助手，或已发布助手可见性），有会话时再 `assertCanCreateConversationAsset`。随后 `UploadFileCommand` 落对象存储，`getFileAssetDestination` 校验 `status === 'success'`，`getStorageFileFromAsset` 取登记行，`CreateFileAssetCommand` 建/更新 `FileAsset`（`purpose` 默认 `chat_attachment`，`parseMode` 经 `resolveParseMode` 白名单校验），最后 `EnqueueFileParseCommand`。大小/类型策略集中在两点：`shouldRunParseInline` 决定同步/后台（`fast` 恒真、`deep` 恒假、其余按 `size <= 2_000_000`）；聊天请求内联文件受 `MAX_DATA_URL_BYTES = 25MB`、内联解析受 `MAX_INLINE_PARSE_BYTES = 2MB` 约束（`normalizeChatRequestFiles`）。落地细节由 `StorageTargetStrategy` 完成：key 必须是 `directory/<tenantId>/<fileName>`（`assertContainedInTenantDirectory` 拒绝越界），文件名 `files-<ts>-<hex>.<ext>`，再 `createStorageFile` 写行。
章节来源：[context.controller.ts](file://packages/server-ai/src/ai/context.controller.ts)（关键符号：ContextsController.create）、[create-file-asset.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/create-file-asset.handler.ts)（关键符号：CreateFileAssetHandler.execute）、[storage-target.strategy.ts](file://packages/server/src/file/file-upload/strategies/storage-target.strategy.ts)（关键符号：StorageTargetStrategy.upload）

## 理解与解析链
`EnqueueFileParseHandler.execute` 先取资产：`status = parseMode === 'none' ? 'ready' : 'parsing'`、清 `error` 并保存；`none` 直接返回；`runInline` 走同步 `ParseFileAssetCommand`，否则 `setImmediate` 后台执行且失败仅 `logger.warn`。`ParseFileAssetHandler.execute` 是核心：① `fileAssetAccessService.resolve(operation:'parse')`；`parseMode==='none'` 时补 `parsedAt` 返回；② 置 `parsing` 并清错；③ 源解析——有 `storageFile` 用 `new FileStorage().getProvider(storageFile.storageProvider).path(storageFile.file)`，否则用 `resolveFileAssetWorkspaceVolumeScope` + `createVolumeFileSnapshot` 取工作区快照，两者皆无则抛「does not have a readable storage or workspace source」；④ `parserRegistry.getParser(source)` → `parser.parse(source)`；⑤ `replaceArtifacts`（先 delete 后 save）并触发 `IndexFileChunksCommand`；⑥ 成功写 `status = parsed.status ?? 'ready'`、`capabilities` 并入 `preview`/`read`、`metadata{parser, chunkCount}`、`parsedAt`，再投影页图并清理旧 run 的页图；⑦ 失败写 `status='failed'`、`error`、`failedAt` 与 `metadata.understandingErrorCode`（`file_understanding_embedding_unavailable` / `file_understanding_vector_index_failed` / `file_understanding_parse_failed`）；⑧ `finally` 释放快照。派生目录为 `contexts/<tenantId>/file-understanding/<assetId>/<parseRunId>`。`retry` 语义极简：`RetryFileParseHandler.execute` 直接转发 `ParseFileAssetCommand`（不预置状态，仅由受控入口 `workspace-files-runtime-capability` 限定为 failed/unavailable 才允许）。
章节来源：[enqueue-file-parse.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/enqueue-file-parse.handler.ts)（关键符号：EnqueueFileParseHandler.execute）、[parse-file-asset.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/parse-file-asset.handler.ts)（关键符号：ParseFileAssetHandler.resolveDerivedStorageDirectory）、[retry-file-parse.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/retry-file-parse.handler.ts)（关键符号：RetryFileParseHandler.execute）

## 读取与搜索
控制器 8 端点按「先授权、后执行」排列：`GET /files/:fileId` 返回授权后的资产；`GET /files/:fileId/status` → `GetFileParseStatusQuery`；`POST /files/:fileId/parse/retry`；`POST /files/:fileId/search` → `SearchFileChunksQuery({fileId, query, limit})`；`GET /files/:fileId/preview` → `GetFilePreviewQuery`；`POST /files/:fileId/read` → `ReadFileChunkQuery({fileId, chunkId|orderNo})`；`GET /conversations/:conversationId/files` → `assertConversationAccess` + 公共会话断言 + `ListConversationFilesQuery`；`DELETE /files/:fileId` → `DeleteFileAssetCommand`。返回形态上 `GetFilePreviewHandler` 只选安全字段（不含 artifacts/chunks 正文）：`file`（含 `summary` 截断 900 字、`compactMetadata` 只留 parser/chunkCount/fileCount/pdfPageImages）+ `artifacts`（排除 `summary`，最多 12 条，页图附 `createPageImagePreviewFile`）+ `chunks`（最多 8 条，仅 `chunkId/orderNo/anchor/tokenCount`）。搜索侧 `FileUnderstandingVectorService.searchChunkIds` 走 `similaritySearchWithScore` + `filter{tenantId, organizationId, fileAssetId, enabled:true}`，再用 `file_embedding` 记录里的 collection 名交叉过滤。工具层（`createFileUnderstandingTools`）再叠一层可见性：`listVisibleFiles` 在可信 `projectId` 存在时用 `ListProjectFilesQuery`，否则用 `ListConversationFilesQuery`，`resolveFileIds` 拒绝不可见 id；8 个工具为 `parsed_file_search`、`parsed_file_read`、`parsed_file_preview`、`parsed_file_page_images`、`parsed_file_table_query`、`parsed_file_list`、`parsed_file_read_by_path`、`parsed_file_search_all`，上限 `SEARCH_RESULT_LIMIT=8`、片段 800 字、正文 4000 字。
章节来源：[file-understanding.controller.ts](file://packages/server-ai/src/file-understanding/file-understanding.controller.ts)（关键符号：FileUnderstandingController.getPreview）、[get-file-preview.handler.ts](file://packages/server-ai/src/file-understanding/queries/handlers/get-file-preview.handler.ts)（关键符号：GetFilePreviewHandler.execute）、[tools/file-understanding.tools.ts](file://packages/server-ai/src/file-understanding/tools/file-understanding.tools.ts)（关键符号：createFileUnderstandingTools）

## 状态与清理
状态枚举 `FileAssetStatus = uploaded|scanning|parsing|ready|partial|failed`；`GetFileParseStatusHandler` 返回 `{fileId, status, error, parsedAt}`。清理是硬删链：`DeleteFileAssetCommand` → `FileAssetDeletionService.delete`（先以 `operation:'delete'` 授权）→ `cleanup` 顺序为「删向量（`deleteFileVectors`）→ 删 `file_citation_anchor` → 删 `file_embedding` → 删 `file_chunk` → 删 `file_artifact` → 删 `conversation_file_link` → 删 `file_asset` 行 → `provider.deleteFile` 删页图对象 → 删派生目录」；派生目录删除只在 `provider.path()` 返回绝对路径（本地 provider）时执行 `fsPromises.rm(..., {recursive:true, force:true})`。项目回收是独立入口：`purgeProjectFile` 先 `projectAccessService.assertCanPurge(projectId)`，再校验 `asset.projectId === project.id && asset.tenantId === project.tenantId`（注释：「never trusts the supplied project ID as authority」），随后复用 `cleanup`；上层 `ProjectPurgeService` 遍历 `FileAsset where {tenantId, projectId}` 逐个调用，并 `VolumeHandle.removePath(..., {boundaryRoot})` 删除项目卷。`storage_file` 侧不存在软删路径：`deleteStorageFile` 先 `findOne` 再 `repository.remove`（注释：为了正确触发 `StorageFileSubscriber` 的 `afterRemove` 事件参数中的 entity）。
章节来源：[file-asset-deletion.service.ts](file://packages/server-ai/src/file-understanding/file-asset-deletion.service.ts)（关键符号：FileAssetDeletionService.purgeProjectFile）、[get-file-parse-status.handler.ts](file://packages/server-ai/src/file-understanding/queries/handlers/get-file-parse-status.handler.ts)（关键符号：GetFileParseStatusHandler.execute）、[storage-file.service.ts](file://packages/server/src/storage-file/storage-file.service.ts)（关键符号：StorageFileService.deleteStorageFile）

## 文件记忆链
**抽取**：`memory_write` 工具 → `FileMemoryService.writeMemory`（frontmatter `source: 'explicit'`）；轮次结束 `afterAgent` → `FileMemoryWritebackRunner.enqueue`（按 `createFileMemoryScopeKey` 串行，`softDrain` 可限时等待），`processSnapshot` 先 `recordWritebackCandidate`，再 `searchMemory` 取候选，由 `decideFileMemoryWriteback` 决策 `upsert`/`archive`，落 `source: 'writeback'`；离线 `FileMemoryDreamService.triggerDream` 受 gate 约束（`DEFAULT_DREAM_GATE_CONFIG` 默认 `minIntervalMinutes: 30`、会话信号门槛），经 `FileMemoryDreamerInvoker`（`XpertDreamerInvoker`）以 `XpertAgentChatCommand` 调 dreamer 助手（默认 env `FILE_MEMORY_DREAMER_AGENT_KEY = 'FileMemoryDreamer'`），运行证据写在 `.dream/`（signals.json 等）。**存储**：卷上 `.xpert/memory`，索引文件 `MEMORY.md`，四类目录 `user|feedback|project|reference`，状态 `active|archived|conflict`，信号 6 类（recall_hit/detail_read/explicit_write/writeback_candidate/user_correction/index_issue）。**消费**：`beforeAgent`/`wrapModelCall` 触发后台召回，`wrapModelCall` 用 `...buildMemoryContextMessages(recall)` 前置注入消息并附记忆系统策略（预算 `MAX_DETAIL_BYTES_PER_TURN=20KB` / `PER_SESSION=60KB`），工具面 `memory_search`/`memory_get`/`memory_write`。**与理解结果的关系**：**无代码依赖**——记忆域不读 `FileAsset`/`file_chunk`，只共享卷基础设施与 `chat_conversation`/`chat_message`/`xpert` 三张外部表（`FileMemoryConversationHistoryReader` 取证、`FileMemoryXpertScopeResolver` 解析作用域）。
章节来源：[file-memory.service.ts](file://packages/server-ai/src/file-memory/file-memory.service.ts)（关键符号：FileMemoryService.writeMemory）、[file-memory.writeback-runner.ts](file://packages/server-ai/src/file-memory/file-memory.writeback-runner.ts)（关键符号：FileMemoryWritebackRunner.processSnapshot）、[dream.service.ts](file://packages/server-ai/src/file-memory/dream.service.ts)（关键符号：FileMemoryDreamService.triggerDream）、[paths.ts](file://packages/server-ai/src/file-memory/paths.ts)（关键符号：getXpertFileMemoryWorkspacePath）

## 存储抽象与卷
抽象入口是 `FileStorage`：`getProvider(providerName)` 先走插件注册表，失败**静默回落内置 provider**（注释：「Fall back to built-in providers so bootstrap/tests without Nest context keep working.」）；provider 名来自租户设置或环境配置，写行时统一大写保存。仓库内只有 LOCAL 实现：`LocalProvider` 以 `assetOptions.assetPublicPath` 为 `rootPath`、`environment.baseUrl + '/public'` 为 `baseUrl`，`file` 列存相对 key。`storage_file` 行的生命周期：上传（`POST /api/storage-file` 经 `UploadFileCommand` → `StorageTargetStrategy.upload` → `StorageFileService.createStorageFile`；`POST /api/storage-file/url` 直连 `provider.putFile(url)`；`StorageFileCreateCommand` 走 `files/<tenantId>/file-<ts>-<n>.<ext>`）→ 加载补 `fileUrl`（subscriber `afterLoad`）→ 删除 `repository.remove` 触发 `afterRemove` 删物理对象与 thumb。卷与路径约束：`FileAssetDeletionService` 与 `ParseFileAssetHandler` 共用 `normalizeRelativePath('contexts', tenantId, 'file-understanding', id, parseRunId)`；工作区源/投影走 `resolveFileAssetWorkspaceVolumeScope`（识别 `environment/projects/xperts/user-xperts/users` 目录，项目/xpert/user 的 scopeId 不匹配即返回 null 并回落到推断）；记忆域 `VolumeSubtreeClient(..., {allowRootWorkspace:true})` + `normalizeFileMemoryRelativePath` 双重防逃逸。**去重语义**：`FileAsset` 去重键是 `storageFileId`（非 `sha256`），重复上传原地更新。
章节来源：[file-asset-deletion.service.ts](file://packages/server-ai/src/file-understanding/file-asset-deletion.service.ts)（关键符号：FileAssetDeletionService.deleteDerivedRootIfLocal）、[domain/workspace-file.ts](file://packages/server-ai/src/file-understanding/domain/workspace-file.ts)（关键符号：resolveFileAssetWorkspaceVolumeScope）、[storage-file.subscriber.ts](file://packages/server/src/storage-file/storage-file.subscriber.ts)（关键符号：StorageFileSubscriber.afterRemove）、[storage-file-create.handler.ts](file://packages/server/src/storage-file/commands/handlers/storage-file-create.handler.ts)（关键符号：StorageFileCreateHandler.execute）

## 解析器实现细节
`FileParserRegistry.getParser` 的**匹配顺序即优先级**：pdf → spreadsheet → office → image → archive → text，全部不匹配抛 `UnsupportedFileContentError`。逐类要点：① **PDF**（`PdfFileParser`）：`PDFLoader` 抽每页文本成 `page_text` 锚 `{page}`，再经 `pdf-to-img`（scale 2）渲染页图为 `page_image` 并写入派生产物目录 `pages/page-0001.png`；页数上限 `FILE_UNDERSTANDING_PDF_RENDER_MAX_PAGES`（默认 300），渲染被截断或报错则 `status='partial'` 并把 `renderError` 落 metadata；文本与页图按页交错排序。② **Office**（`OfficeFileParser`）：`doc/docx/ppt/pptx`；`docx` 先做 compound 签名（`d0cf11e0a1b11ae1`）探测以兼容「WPS 存成 .docx 的二进制 Word」，命中走 `word-extractor`，否则 `DocxLoader`/`PPTXLoader`，ppt 产物 kind 为 `slide` 且锚 `{slide}`。③ **表格**（`SpreadsheetFileParser`）：`csv/tsv` 直接文本读成 `table`（metadata 记 delimiter），`xlsx/xls` 用 `XLSX.readFile({cellDates:true})` 逐 sheet 生成 `sheet` 产物（含 rowCount/headers/前 30 行样本），capabilities 含 `table_query`。④ **图片**（`ImageFileParser`）：`image/*` 或扩展名白名单，`sharp.metadata()` 出 `image_metadata`，capabilities `preview/read/vision/ocr`，`status='partial'` 且 metadata 标 `ocrPending/visionPending`。⑤ **压缩包**（`ArchiveFileParser`）：`unzipper` 列前 500 项成 `file_manifest` + `code_tree`，再对前 80 个文本类条目（≤200KB）解码为 `text`（锚 `{path}`），其余仅留清单。⑥ **文本**（`TextFileParser`）：`supportsTextFile` 判定 + `readTextFile` 解码（含二进制内容拒绝），产物 `text` 锚 `{path}`；三者共用 `summarizeText`/`estimateTokenCount` 与 `getFileExtension`/`isZipFile` 契约。

## 热点路径
1. **上传→解析（同步路径）**：`fast` 模式或 ≤2MB 文件会**同步**跑完整解析（含 PDF 页渲染与向量索引），直接占用请求线程，是慢请求主因。
2. **后台解析**：`setImmediate` 无队列、无 lease，进程重启即丢任务，状态会永久停在 `parsing`；失败只写 `warn` 与资产 `error`。
3. **解析内串行链**：`ParseFileAssetHandler` 内串行做「读源 → 解析 → 删旧产物 → 落新产物 → 切块 → 向量索引」，单文件大 PDF 会长时间持锁式占用工作区快照。
4. **向量索引/检索**：`FileUnderstandingVectorService` 每批 12k 字符调 embedding，检索时先读 `file_embedding` 做 collection 交叉过滤再查向量库，两跳。
5. **预览读**：`GetFilePreviewHandler` 固定三次查询（资产 + artifacts + chunks），带 take 上限，属常量级开销。
6. **记忆 recall 注入**：每次 `wrapModelCall` 都可能新建/消费后台召回并前置注入消息，注入体积受 20KB/60KB 预算与 `DEFAULT_RECALL_TIMEOUT_MS=3000` 约束。
7. **存储删除**：`StorageFileService.deleteStorageFile` 先读后删，物理对象删除发生在数据库提交后的订阅者里（best-effort，失败仅 `console.log`）。

## 技术债与 hack
1. **无持久队列**：解析靠 `setImmediate` + `logger.warn`，无重试调度；重试仅靠 `RetryFileParseCommand`，崩溃即丢任务、状态可能停在 `parsing`。
2. **无迁移 DDL**：本域三目录无 `migrations/`、无 `.sql`，但**默认部署由启动期 schema sync 依据实体元数据对齐 DDL**（`apps/api/src/schema-sync.ts` 在启动期执行 `dataSource.synchronize()`）；仅外部托管模式（`XPERT_SCHEMA_SYNC=external`）才 `synchronize:false`、建表在仓库外。**反向风险**：实体收窄也可能被自动改表。
3. **`sha256` 形同虚设**：列被写入但无唯一索引、无去重查询；真正去重键是 `storageFileId`，跨存储对象的内容级去重未实现。
4. **`deletedAt` 与硬删并存**：`storage_file.deletedAt` 列存在，但删除路径是 `repository.remove`；`FileAsset` 连软删列都没有，回收不可回滚。
5. **远端 provider 孤儿对象**：派生目录清理仅对「`provider.path()` 返回绝对路径」的本地 provider 生效；对象存储下派生页图与目录只能依赖逐键删除，缺目录级回收。
6. **组织维度用 `IsNull()` 兜底**：链接查询/比较多处 `organizationId ?? IsNull()`，语义上「无组织 = 租户共享」，与「空值 = 可见」的判定叠加后容易被误读。
7. **排障靠日志**：`[FILE_VECTOR_DEBUG]` 前缀日志散落在索引/检索链，无 metrics/tracing 指标。
8. **`dream.service.ts` 是 god service**（近 50KB）：gate、证据、prompt、运行台账、写盘与适配器调用混在一个类里。
9. **两子域无共享抽象**：记忆域与理解域各自处理「卷作用域 + 路径归一化 + 中间件挂载」，同名概念（workspacePath/volume scope）存在两套实现。
10. **路径契约靠工具描述维持**：`parsed_file_page_images` 要求把 `workspacePath` 原样传给 `view_image`（POSIX 相对路径、不得拼主机前缀），属于跨工具隐式契约。
11. **`parsed_file_read` 反枚举约束**：描述明确禁止按 `orderNo` 递增扫描（缺失块是终态错误），说明历史上出现过探测式调用。
12. **`[推测]` 多实例语义**：`setImmediate` 与 `FileMemoryWritebackRunner` 的内存 `slots` 都只在单进程内有效，多实例下既无互斥也无接力（未见分布式锁）。
13. **`[推测]` 上传入口分散**：`/api/contexts/file`、`/api/storage-file`、`/api/files`、`/api/ai/conversations/:id/file/upload` 四条上传路径并存，旧 `/ai` 上传入口仅以注释标注 `@deprecated`，容易被新代码误用。
14. **`[推测]` 公共会话分支**：`getPublicXpertSessionConversationScope` 分支里对 `assertPublicXpertSessionConversationAccess` 做了类型断言强转，签名一旦变化不会在编译期暴露。

## 设计维度分析
**同步理解 vs 后台理解**：`shouldRunParseInline` 用「模式 + 2MB 阈值」在延迟与吞吐之间取舍——小文件/`fast` 让同一轮对话立刻拿到 preview/vision 元数据，大文件或 `deep` 转后台但**没有队列兜底**，可用性建立在「进程不重启」假设上。
**文件句柄 vs 对象行**：`FileAsset` 与 `StorageFile` 双记录（前者面向 Agent 与解析状态，后者面向对象存储兼容），换来 ChatKit/历史客户端的兼容与「解析状态可原地更新」，代价是同一次上传要写两行并保持 `storageFileId` 强一致，且删除必须两域协作（`deleteAuthorizedStorageFile`）。
**授权内聚 vs 鉴权分层**：文件侧把全部判定收进单一 `resolve`（含 attach 前先 `assertCanEdit` 的次序设计），存储侧却把鉴权放进 service（控制器无守卫），记忆侧用 `XpertGuard`——三种风格并存使「谁在什么层拒绝」必须在三处分别确认。
**记忆的「文件」语义**：用卷上 markdown + frontmatter 取代记忆表，换来人类可读、可 diff、可被 Agent 工具直接读写，代价是索引一致性（`MEMORY.md` 与 topic 文件）与并发写必须自行处理（writeback 串行槽 + Dream gate）。

## 结论
实现上，本域把「字节 → 理解 → 可引用」拆成四段可独立重放的步骤（资产登记、解析产物替换、切块与锚点、向量账本），每段都以「先删后建 + 幂等键」自证可重放；授权则收敛到 `FileAssetAccessService.resolve` 与 `XpertGuard`/service 断言三条线，删除链与项目回收各自带专用入口与归属校验。记忆子域刻意选择「卷上文件而非表」，把写入与消费挂在 Agent 中间件的 `afterAgent`/`wrapModelCall` 上，与理解域零代码耦合。需要重点防守三处：① 无队列的 `setImmediate` 解析（状态可能永久停在 `parsing`）；② 远端 provider 下的派生对象回收（孤儿对象）；③ `sha256` 存在却未用于内容级去重，若后续要接去重/秒传必须同时补唯一约束与写入路径。
