## D1 上传入口放在跨域的 `ai/context`

- **分类**：兼容处理
- **动机（避坑）**：**现象** —— 仓库里并存四条上传路径（`/api/ai/contexts/file`、`/api/ai/v1/file`、`/api/storage-file`、`/api/files`），旧入口只落 `StorageFile`/destination。**后果** —— 新代码误用旧入口时，文件只有字节行、没有 `FileAsset` 句柄、也不会启动理解链，表现为「上传成功但 Agent 永远读不到」，而工具面与 `AgentFile` 契约都不会报错。
- **决策**：把「上传 + 建句柄 + 启动理解」定在 `ContextsController.create`（`@Controller('contexts')` 注册于挂 `/ai` 的 `AIModule`，真实路径 `POST /api/ai/contexts/file`）；本域控制器只提供句柄/检索/删除类 8 个端点，**不含 multipart**；旧入口源码注释逐字：
  > `@deprecated Use POST /contexts/file. The context endpoint returns an AgentFile/FileAsset handle and starts the file-understanding parse flow.`
- **背景约束**：上传体里 `workspacePath` 被显式置空；`target` 只允许服务端管理的 storage target（改 `directory`/`prefix` 或加键即 400）；`conversationId`/`threadId` 能解析到会话时**以会话字段覆盖** `projectId`/`xpertId`。
- **被否决方案**：无（源码未记录否决记录；旧入口的 `@deprecated` 注释即迁移口径：旧入口「只落 storage/destination」vs 新入口「返回句柄并启动解析」）。
- **重新评估触发条件**：若要把上传收敛回本域控制器，必须同时迁移 `AgentFile` 响应契约、upload-target 校验与 `assertUploadScope`/`assertCanCreateConversationAsset` 前置断言。

## D2 资产 → 解析 → 记忆三层解耦

- **分类**：架构设计
- **动机（避坑）**：**现象** —— 记忆若以「解析产物」为输入、或直接读 `file_asset`/`file_chunk`，记忆链就被解析状态机与向量可用性绑架。**后果** —— 一次解析失败或向量库不可用会连带记忆不可用；两个子域互相持有实体后，依赖图出现环，任何一侧改表都要联动另一侧。
- **决策**：三条独立链并行：① 字节句柄（`FileAsset` + `storage_file`）；② 理解链（命令 → `FileParserRegistry` → `file_artifact` → `file_chunk`/`file_citation_anchor` → `file_embedding` 账本）；③ 记忆链（卷上 markdown，中间件消费）。记忆子域对理解子域**零代码依赖**，只共享卷基础设施与 `chat_conversation`/`chat_message`/`xpert` 三张只读表。
- **背景约束**：两者各自实现一个 `@AgentMiddlewareStrategy`（`FileUnderstandingMiddleware` / `XpertFileMemoryMiddleware`），代码上互不 import；理解域入边 10 组、出边 0；记忆域唯一出站是 Dream 的 `XpertAgentChatCommand`。
- **被否决方案**：无（源码未记录）。
- **重新评估触发条件**：出现「用解析产物喂记忆」的产品需求（如把 PDF 摘要自动写成 memory）时，必须新增显式跨域读接口，而不是让记忆域直连 `file_asset`。

- **证据来源**：实现层 03-数据流转.md「链路六 文件记忆链」——「与 `file-understanding` 无代码依赖，只共享卷基础设施与对话/助手表」；实现层 02-实现.md「文件记忆链」——「**与理解结果的关系**：**无代码依赖**」。

## D3 幂等与去重键的选择

- **分类**：一致性策略
- **动机（避坑）**：**现象** —— 一次上传会同时产生 `storage_file` 行与 `file_asset` 行，且上传入口有多条、解析可被重放。**后果** —— 若按内容或时间建行，重复上传/重试会散出多行资产、多份向量与多个会话链接，配额、引用口径与「同一个文件」的判断全部漂移。
- **决策**：① `file_asset` 以 `storageFileId` + tenantId 为去重键，`CreateFileAssetHandler` 先查后原地更新（`status` 沿用旧值）；② `conversation_file_link` 用 `@Index(['conversationId','fileAssetId'],{unique:true})`，handler 先 `findOne` 再 save 做幂等 upsert；③ 解析/索引重放前先删旧数据（`replaceArtifacts` 先 delete 后 save；`IndexFileChunksHandler` 开头删 anchors/embeddings/chunks）。
- **背景约束**：`sha256` 列被写入（`createHash('sha256').update(buffer)`）但**仅有普通索引、无唯一约束、无查重查询** ⇒ 内容级去重未实现；`file_citation_anchor.anchorKey` 无唯一约束，重放安全完全靠「先删后建」。
- **被否决方案**：无（源码未记录「用 `sha256` 去重」的否决记录；实现层把它列为技术债 3「`sha256` 形同虚设」的现状）。
- **重新评估触发条件**：要上「秒传/去重」必须**同时**补唯一约束与写入路径（含 buffer 缺失场景），否则会落成「列存在但不生效」的误判。
- **关联代码**：[create-file-asset.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/create-file-asset.handler.ts)、[attach-file-to-conversation.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/attach-file-to-conversation.handler.ts)、[conversation-file-link.entity.ts](file://packages/server-ai/src/file-understanding/entities/conversation-file-link.entity.ts)
- **证据来源**：实现层 04-模型.md「校验规则」——「**file-understanding 其余 6 张表全部无唯一约束**，重复写入靠应用层『先删后写』与幂等键（`storageFileId`）」；实现层 02-实现.md「存储抽象与卷」——「**去重语义**：`FileAsset` 去重键是 `storageFileId`（非 `sha256`）」。
章节来源：[create-file-asset.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/create-file-asset.handler.ts)（关键符号：CreateFileAssetHandler.execute / sha256 / 幂等复用）、[conversation-file-link.entity.ts](file://packages/server-ai/src/file-understanding/entities/conversation-file-link.entity.ts)（关键符号：unique @Index(conversationId,fileAssetId)）

## D4 删除走硬删 + 分步回收

- **分类**：架构设计
- **动机（避坑）**：**现象** —— 一次删除要跨五种存储（关系行、向量库、对象字节、派生目录、会话链接），没有任何跨表事务；若改软删，读路径还要到处补过滤。**后果** —— 软删会让「已删资产」继续占向量与对象、并让每个查询都要记得过滤；而硬删中途崩溃会留下孤儿对象，排障时「DB 已删、对象还在」极易被误判为已回收。
- **决策**：`FileAsset` **不设软删**，`FileAssetDeletionService.cleanup` 固定顺序硬删：向量（`deleteFileVectors`）→ `file_citation_anchor` → `file_embedding` → `file_chunk` → `file_artifact` → `conversation_file_link` → `file_asset` 行 → 页图对象 → 派生目录；`storage_file` 有 `deletedAt` 列但删除路径仍走 `repository.remove`（源码注释逐字说明是为触发 `StorageFileSubscriber.afterRemove` 的 entity 参数）；项目删除走**专用入口** `purgeProjectFile`（注释逐字「Dedicated project lifecycle entry; never trusts the supplied project ID as authority.」）。
- **背景约束**：派生目录 `fsPromises.rm` **仅当 `provider.path()` 返回绝对路径（本地 provider）** 时执行，远端 provider 只剩 DB 删除 ⇒ 孤儿对象；页图与目录删除失败一律 `catch(()=>undefined)`；本域无 TTL/补偿任务（`@Cron`/`@Interval`/`@Processor` 检索 0）。
- **被否决方案**：无（实现层记录的是「`deletedAt` 与硬删并存」的现状落差，未记录曾采用软删）。
- **重新评估触发条件**：需要「可回滚删除」「删除审计」，或要求在远端 provider 上做目录级回收时——届时必须给 provider 补目录语义或引入清理任务。
- **关联代码**：[file-asset-deletion.service.ts](file://packages/server-ai/src/file-understanding/file-asset-deletion.service.ts)、[storage-file.service.ts](file://packages/server/src/storage-file/storage-file.service.ts)、[project-purge.service.ts](file://packages/server-ai/src/xpert-project/services/project-purge.service.ts)
- **证据来源**：实现层 03-数据流转.md「链路五 删除与回收链」——「**无软删**：`file-understanding` 全域检索 `softRemove|softDelete|@DeleteDateColumn` **0 命中**」；实现层 02-实现.md「状态与清理」——「`storage_file` 侧不存在软删路径」。
章节来源：[file-asset-deletion.service.ts](file://packages/server-ai/src/file-understanding/file-asset-deletion.service.ts)（关键符号：cleanup / purgeProjectFile / deleteDerivedRootIfLocal）、[storage-file.subscriber.ts](file://packages/server/src/storage-file/storage-file.subscriber.ts)（关键符号：StorageFileSubscriber.afterRemove）

## D5 存储抽象与卷路径约定的取舍

- **分类**：技术选型
- **动机（避坑）**：**现象** —— 租户可配不同对象存储，且 provider 名在行上固化后不可改写；key 由调用方传入。**后果** —— 若按「当前配置」而不是「行上的 provider」解析对象，切换后端后历史文件会**全部读不到**；若 key 不做租户目录约束，会出现跨租户越界写/越权读。
- **决策**：① 读路径一律 `new FileStorage().getProvider(storageFile.storageProvider)`（先查 `FileStorageRegistryBridge`，失败**静默回落**内置 provider）；② 上传 key 强制 `<directory>/<tenantId>/<fileName>`，由 `assertContainedInTenantDirectory` 断言不越界；③ 解析派生物统一 `contexts/<tenantId>/file-understanding/<assetId>/<parseRunId>`（`normalizeRelativePath`）；④ 记忆路径由 `normalizeFileMemoryRelativePath` 拒绝 `..`、绝对路径与空路径，子域根读取需显式 `{ allowRootWorkspace: true }`。
- **背景约束**：仓库内只有 LOCAL 实现（`assetOptions.assetPublicPath` 为 rootPath、`environment.baseUrl + '/public'` 为 baseUrl）；S3/对象存储经 `@FileStorageProvider` 外部插件注册；`storageProvider` 列 `@Exclude({toPlainOnly:true})` 不对外序列化。
- **被否决方案**：无（源码未记录；静默回落注释只说明「为让无 Nest 上下文的 bootstrap/测试能跑」）。
- **重新评估触发条件**：引入第二个内置 provider，或要求「派生对象可被目录级回收」时——需要先把 `path()` 的绝对路径语义升级为 provider 契约的一部分。
- **关联代码**：[file-storage.ts](file://packages/server/src/file/file-storage/file-storage.ts)、[storage-target.strategy.ts](file://packages/server/src/file/file-upload/strategies/storage-target.strategy.ts)、[paths.ts](file://packages/server-ai/src/file-memory/paths.ts)、[domain/workspace-file.ts](file://packages/server-ai/src/file-understanding/domain/workspace-file.ts)
- **证据来源**：源码 `file-storage.ts` 注释逐字「Fall back to built-in providers so bootstrap/tests without Nest context keep working.」；实现层 01-架构.md「关键不变量」5——「对象读写一律 `new FileStorage().getProvider(storageFile.storageProvider)`（先注册表、失败回落内置 provider）」。
章节来源：[file-storage.ts](file://packages/server/src/file/file-storage/file-storage.ts)（关键符号：FileStorage.getProviderInstance / normalizeConfiguredProvider）、[paths.ts](file://packages/server-ai/src/file-memory/paths.ts)（关键符号：normalizeFileMemoryRelativePath）

## D6 命令/查询入边驱动，本域零出边

- **分类**：架构设计
- **动机（避坑）**：**现象** —— 同一批文件资产被对话、消息、项目、知识库、运行时、消息组装六类调用方同时需要。**后果** —— 若让每个调用方直连本域实体或自建查询，租户/组织过滤与 `resolve` 授权会被复制并迅速发散（绕过 `resolve` 直查仓储即越权），删表/改列的影响面也不可枚举。
- **决策**：入向统一为命令/查询（共 10 组：`CreateFileAssetCommand`、`EnqueueFileParseCommand`、`CreateWorkspaceFileAssetCommand`、`AttachFileToConversationCommand`、`DeleteFileAssetCommand`、`GetFileAssetByStorageFileQuery`、`GetOwnedStorageFileQuery`、`ResolveAuthorizedFileAssetQuery`、`GetFilePreviewQuery`、`GetFileUnderstandingStatusQuery`、`SearchFileChunksQuery`、`ValidateFileUnderstandingReferencesQuery` 等）；本域**不发事件**（无 `.publish(`/`@EventsHandler`）；记忆域唯一出站是 Dream 的 `XpertAgentChatCommand`。
- **背景约束**：依赖方向单向（会话/项目/知识库/运行时 → 本域）；跨域只读表 4 张（`xpert_project` + 记忆侧三表），本域不写它们；文件删除必须两域协作（`deleteAuthorizedStorageFile`）。
- **被否决方案**：无（源码未记录；但 `domain/types.ts` 的 `AgentFile` 契约（`id == fileId == FileAsset.id`）与 `storageFileId` 兼容桥说明对外只暴露句柄而非实体）。
- **重新评估触发条件**：需要「本域主动通知下游」（例如资产删除后通知知识库重索引）时，必须先定义事件契约，否则下游只能轮询或依赖已知缺口。

## D7 记忆的存储形态与消费时机

- **分类**：数据归属
- **动机（避坑）**：**现象** —— 长期记忆若落库，就要自带索引、清洗、审计、人工修正入口与迁移节奏；若只做 session 摘要，则会随会话结束而丢。**后果** —— 前者让记忆与对话内容争抢同一套 DB 权限与发布窗口且不可人读/人改；后者让「跨会话事实」根本不存在。
- **决策**：记忆以**卷上 markdown/JSON** 承载（`.xpert/memory` + `MEMORY.md` 索引 + `user|feedback|project|reference` 四类目录，frontmatter 承载 id/scope/type/status/usage/confidence/source）；消费挂在 Agent 中间件：`beforeAgent` 起后台召回，`wrapModelCall` 用 `[...buildMemoryContextMessages(recall), ...request.messages]` **前置注入**（预算 20KB/轮、60KB/会话、召回超时 3s），并暴露 `memory_search`/`memory_get`/`memory_write` 三工具。
- **背景约束**：写入三入口（显式工具 / `afterAgent` writeback / Dream 离线整理）；writeback 按 `createFileMemoryScopeKey`（tenant/project/user）串行、`softDrain` 可限时等待；middleware 入口先 `assertFileMemorySandboxFeatureEnabled`，未启用直接抛错；项目共享卷按 xpert 隔离为 `.xpert/memory/xperts/<xpertId>`。
- **被否决方案**：无（源码未记录；实现层把「文件语义」描述为取舍结果而非否决记录）。
- **重新评估触发条件**：需要跨助手共享记忆、或对记忆做检索级性能优化、或需要记忆变更审计时，「卷上文件」的一致性（`MEMORY.md` 与 topic 文件）与并发写将成为约束。
- **关联代码**：[file-memory.middleware.ts](file://packages/server-ai/src/file-memory/file-memory.middleware.ts)、[file-memory.service.ts](file://packages/server-ai/src/file-memory/file-memory.service.ts)、[paths.ts](file://packages/server-ai/src/file-memory/paths.ts)、[sandbox-memory.store.ts](file://packages/server-ai/src/file-memory/sandbox-memory.store.ts)
- **证据来源**：实现层 02-实现.md「设计维度分析」——「**记忆的『文件』语义**：用卷上 markdown + frontmatter 取代记忆表，换来人类可读、可 diff、可被 Agent 工具直接读写」；实现层 03-数据流转.md「链路六」——「记忆介质：卷上的 markdown/JSON……**不是向量库、不落本域表**」。

## D8 访问授权放在 service 断言

- **分类**：安全合规
- **动机（避坑）**：**现象** —— 本域端点同时被用户会话、API Key、ENTERPRISE_XPERT client secret、平台 runtime、Agent 工具与命令投递方调用，身份形态不统一。**后果** —— 判定若写在控制器装饰器里：(a) 非 HTTP 调用面（runtime capability / 工具 / 命令投递方）完全不被保护；(b) 要为每种身份各写一份守卫；(c) 控制器签名会暴露「资源是否存在」，可被枚举；反之若只在控制器布防，绕过 service 直查仓储即越权。
- **决策**：文件侧唯一授权入口是 `FileAssetAccessService.resolve({ locator, authority, operation })`（`operation ∈ read/attach/parse/write/delete`），在 service 内做 `tenantId` 过滤 + 组织可见性 + locator 一致性 + 会话/项目/助手边界断言；**「不存在」与「无权限」统一抛 `FileAssetAccessDenied`（403，防枚举）**；存储侧鉴权在 `StorageFileService`（owner 或 `SUPER_ADMIN/ADMIN`；跨域删除走 `deleteAuthorizedStorageFile` 比对 `tenantId`/`organizationId`）；记忆侧用 `XpertGuard`。
- **背景约束**：`FileUnderstandingController` 类级 `@Public()` + `@AllowClientSecretBindings(ENTERPRISE_XPERT)` + `ApiKeyOrClientSecretAuthGuard`；`StorageFileController` **无控制器守卫**且 `deleteStorageFile` 把任何异常 catch 成 403；`attach` 到项目**先** `assertCanEdit` **再**查 link（注释逐字：读权限成员不得借既有 link 绕过项目编辑边界）；个人 Xpert 卷不因项目会话自动公开。
- **被否决方案**：无（未被表述为一次方案否决；但源码注释明确否定了「先看 link 再授权」的次序）。
- **重新评估触发条件**：新增任何非 HTTP 调用面时必须经 service 断言或 `FileRuntimeService`，不得直查仓储；三套风格（`resolve` / service / `XpertGuard`）并存意味着改一处需同步核对另外两处。
- **关联代码**：[file-asset-access.service.ts](file://packages/server-ai/src/file-understanding/file-asset-access.service.ts)、[storage-file.service.ts](file://packages/server/src/storage-file/storage-file.service.ts)、[xpert.guard.ts](file://packages/server-ai/src/xpert/guards/xpert.guard.ts)
- **证据来源**：实现层 05-接口.md「鉴权矩阵与『看似无守卫』的解释」——「`resolve` 的判定是**隐式**的……统一抛 `FileAssetAccessDenied`（403），因此从控制器签名上看不到任何鉴权痕迹」；实现层 01-架构.md「关键不变量」4。

## D9 解析器注册表与类型支持策略

- **分类**：技术选型
- **动机（避坑）**：**现象** —— 文件类型要可扩展，但同一扩展名下内容可能不同构（例如「WPS 存成 .docx 的二进制 Word」，其扩展名与真实容器不符）。**后果** —— 靠扩展名直连某个 loader 时，部分文件会产出**空内容而不报错**，下游表现为「索引 0 块 / 预览为空」而不是失败，排障会误判为存储或向量问题。
- **决策**：用 `FileParser` 契约 + `FileParserRegistry.getParser(source)` **顺序匹配（顺序即优先级）** pdf → spreadsheet → office → image → archive → text，全部不匹配抛 `UnsupportedFileContentError`；解析器以静态数组 `FileParsers` 注册进模块 `providers`（`...FileParsers`）；office 侧先做 compound 签名 `d0cf11e0a1b11ae1` 探测，命中走 `word-extractor`，否则走 `DocxLoader`/`PPTXLoader`。
- **背景约束**：注册表**非插件化**（`FileParsers` 是静态数组）⇒ 升级解析行为等于发布新宿主；解析异常在 `parse-file-asset.handler` 内被吞成 `status='failed'` + `metadata.understandingErrorCode='file_understanding_parse_failed'`（HTTP 不抛）。
- **被否决方案**：无（源码未记录替代方案）。
- **重新评估触发条件**：需要租户级/插件级自定义解析器，或需要在运行时按 MIME 动态扩展时，必须把静态数组改成可注册注册表，并同步「新增类型必须进 `FileParsers`」这条约束。
- **关联代码**：[parsers/file-parser.registry.ts](file://packages/server-ai/src/file-understanding/parsers/file-parser.registry.ts)、[parsers/office.parser.ts](file://packages/server-ai/src/file-understanding/parsers/office.parser.ts)、[file-understanding.module.ts](file://packages/server-ai/src/file-understanding/file-understanding.module.ts)
- **证据来源**：实现层 02-实现.md「解析器实现细节」——「`FileParserRegistry.getParser` 的**匹配顺序即优先级**……全部不匹配抛 `UnsupportedFileContentError`」；实现层 01-架构.md「关键不变量」6——「新增类型必须同时进 `FileParsers` provider 数组，否则运行时不可解析」。

## D10 同步/后台解析的二分取舍

- **分类**：性能取舍
- **动机（避坑）**：**现象** —— 解析包含 PDF 页渲染与向量索引，属长耗时任务。**后果** —— 一律同步会让上传与对话首轮变慢（PDF 页图 + embedding 都在请求线程里）；一律异步又会让小文件在下一轮对话前拿不到 preview/vision 元数据，用户体验成「刚传完就要等」。
- **决策**：用「模式 + 阈值」二分——`shouldRunParseInline`：`fast` 恒同步、`deep` 恒假、其余按 `size <= 2_000_000`；`runInline` 为真走同步 `ParseFileAssetCommand`，否则 `setImmediate` 后台执行且失败仅 `logger.warn`；两种路径都先把 `status` 写成 `parsing` 以便观测。
- **背景约束**：**无持久队列、无 lease、无重试调度**（本域 `@Processor`/`@Cron`/`@Interval` 检索 0），进程重启即丢任务，状态可能**永久停在 `parsing``；重试只有显式命令（HTTP `parse/retry` 或 runtime `retryUnderstanding`），且 HTTP 重试无门禁。
- **被否决方案**：无（源码未记录「为何不引入队列」；实现层将其列为技术债 1「无持久队列」而非决策记录）。
- **重新评估触发条件**：多实例部署、或出现「解析必达」的业务要求时，必须引入持久队列/租约；否则需接受「人工重试」的运行口径。
- **关联代码**：[enqueue-file-parse.handler.ts](file://packages/server-ai/src/file-understanding/commands/handlers/enqueue-file-parse.handler.ts)、[context.controller.ts](file://packages/server-ai/src/ai/context.controller.ts)、[workspace-files-runtime-capability.service.ts](file://packages/server-ai/src/shared/runtime/workspace-files-runtime-capability.service.ts)
- **证据来源**：实现层 02-实现.md「热点路径」1/2——「`fast` 模式或 ≤2MB 文件会**同步**跑完整解析……直接占用请求线程，是慢请求主因」「后台解析用 `setImmediate`，无队列、无 lease，进程重启即丢任务」。

## D11 记忆写入的显式优先与 writeback 分工

- **分类**：一致性策略
- **动机（避坑）**：**现象** —— 同一轮里模型既可能调 `memory_write`（显式），又会在轮次结束触发 `afterAgent` writeback。**后果** —— 同一内容被写两遍，记忆库出现重复条目与互相矛盾的 `source`（`explicit` vs `writeback`），并使 writeback 的模型调用产生无谓计费与决策噪声。
- **决策**：`afterAgent` 检测 `explicitWriteOccurred`，为真则直接 `skipped reason=explicit_write` 并复位标志；writeback 走「先记候选（`recordWritebackCandidate`，`sourceRef = conversation:<id>`）→ `searchMemory(limit 6)` 取候选 → `decideFileMemoryWriteback` 决策 `upsert`/`archive` → 落 `source:'writeback'`」；模型不可用时只留候选并 warn，不落半成品记忆。
- **背景约束**：writeback 按 `createFileMemoryScopeKey` 串行（后到覆盖 `pending`），`softDrain` 超时返回 false 表示未等待完成；Dream 是第三入口，受 gate（默认 `minIntervalMinutes:30`、`minNewOrUpdatedMemories:1`、`minConversationCount:1`）约束，gate 未过落 `status='skipped'`（不是错误）。
- **被否决方案**：无（源码未记录；实现层亦未记录把显式写入也并入 writeback 决策的方案）。
- **重新评估触发条件**：若要改成「显式写入也走 writeback 决策」，必须先解决重复与冲突判定（当前策略是直接跳过）。

- **证据来源**：源码 `file-memory.middleware.ts` 的 `afterAgent` 分支日志逐字 `afterAgent skipped reason=explicit_write`；实现层 03-数据流转.md「链路六」——「写入时机：`afterAgent` 入队 → …… 先记候选（`sourceRef = conversation:<id>`），再取模型决策 upsert/archive，模型缺失时只留候选并 warn」。
