## 闸门评估
`EvolutionEvaluationExecutor.run(operation, target, manager)` 文件头注释逐字：`// Each evaluator runs against the same frozen candidate; an omitted assessment is never a passing test.`。它按 `change.strategy.definition.evaluations` 逐步分派：`kind === 'golden_replay'` 走内置 `replay()`，其余走 `target.checkEvaluator!.evaluate(...)`；每步返回后立即 `validateChangeEvaluation(change, result, step.requiredChecks)`（不合法即 `inconsistent_evaluation_gate`）。多步时每步各自 `saveEvaluation`（`strategyHash` 绑定、`assessment: 'tested'`），单步时不额外落「公共评估」；聚合结果的 `assessment = results.length ? 'tested' : 'not_applicable'`（**无评估步骤时不得被当作通过**），`passed = results.every(result => result.passed)`，`checkId` 单步保持原值、多步加 `<step.key>:` 前缀，`datasetHash` 单步用 provider 原生值、多步改为对每步 `{runId, datasetHash}` 的规范哈希。
`replay()` 是全域最重的一段：① 取 `change.datasetSnapshotIds[step.key]`，缺失即 `evaluation_dataset_required`；② 校验快照 `targetId` 与 `sameScope(scope)`（`evaluation_snapshot_mismatch`）；③ 校验基线版本 `artifact.hash === change.baseline.hash`（`candidate_baseline_mismatch`）；④ 为基线与候选各建一个 `executionMode: 'replay'` 的能力束（`bundleHash = hashEvolutionValue(items)`）并落 `capability_bundle`；⑤ 逐 case 调 `runReplayCase` + `evaluateResult`（`randomSeed: 42`、`repeatIndex: 0`，保证可复现）；⑥ `aggregateMetrics` 后交 `reviewGoldenReplay` 出闸门结论，落一条**原生** `EvaluationRun`（`status = gate.passed ? 'passed' : 'failed'`，含 `gate` 与全量 `caseResults`）；⑦ 再返回一条 `ASSESS-<runId>` 公共评估（`checks` 只含一条阻塞性 `replay-gate`、`datasetHash` 用快照哈希）——注释逐字：`The common assessment has its own immutable record; replay evidence retains its native metrics.`

## 审批与质量治理
`reviewGoldenReplay(cases, metrics)` 是纯函数，五项判据逐条收集 `blockingReasons`：`metrics.totalCases < 50` → `golden_dataset_below_50_cases`；affected 切片（`slice === 'affected' | startsWith('affected:') | startsWith('affected_')`）`< 20` → `affected_slice_below_20_cases`；`risk === 'high'` 计数 `< 10` → `high_risk_slice_below_10_cases`；`metrics.severeErrors > 0` → `severe_errors_present`；`metrics.accuracyDelta <= 0` → `candidate_does_not_improve_baseline`。返回 `{passed, decision: 'reject'|'promote', blockingReasons}`。
`requiredHumanApprovals(riskLevel)` = `R3|R4 → 3`、其余 `2`；`reviewHumanApprovals(riskLevel, approvals)` 先筛 `decision === 'approved'`，若存在 `approvalAuthority === 'administrator'` 的批准则 `requiredApprovals = 1` 且 `passed = true`（**运维逃生门**），否则要求 `distinct actorId` 与 `distinct actorRole` **双达标**——同一人用两个角色投两票无效。服务端决定是否凑齐配额，前端只做展示。

## 发布执行
`EvolutionPublicationExecutor.package(manager, operation)` 注释逐字：`// Staged publication allocates its version and package in the caller's transaction.`——它**不自行开事务**，接收调用方 `EntityManager`。顺序：① `identity = changeIdentity({tenantId, organizationId})`，`releasePackageId = PUB-<changeId>`，`findOneBy` 命中即返回旧值（发布幂等）；② 前置断言「有候选 + 有评估 + `change.approval?.decision === 'approved'`」，否则 `human_approval_required`；③ 取该候选全部审批行，`gatePolicy = gates.snapshot()`，若 `profile === 'manual_test'` 且 `change.approval.approvalAuthority !== 'administrator'` 即 `manual_test_administrator_required`；④ 分配 `CapabilityVersion`：`versionId = <targetId>:<changeId>`、`sequence = max(sequence)+1`、`semanticVersion = 1.${sequence-1}.0`、`artifact = candidate.artifact`、`sourceCandidateId = changeId`；⑤ 落 `ReleasePackage`：`publicationKind: 'staged_rollout'`、`status: 'approved'`、`targetVersionId`、`rollbackVersionId = change.baseline.resourceId`、`evaluationRunId`、`gatePolicy` + `shadowMinimumSamples`、`canaryPercent: 0`、`approvalIds` 只收「decision approved + `candidateHash` + `evaluationRunId` + `strategyHash` 三元组全对齐」的批准。另两条发布路径不在本执行器：`version_write` 走 `target.versionPublisher.publish` 并校验回执三元组（`write_receipt_mismatch`）；一致性夹具走 `AgentEvolutionService.createRelease`，包名 `RP-<simulationId>`（**与 `PUB-` 命名不同，口径需区分**）。

## 金丝雀
**首档与升档**：`startCanary` 只接受 `5|25|50`。从 `shadow`（或 `paused` 且最新部署渠道为 `shadow`）进入时**必须 5%**，且最新 shadow 行满足 `sampleCount ≥ gatePolicy.shadowMinimumSamples`、`severeErrors === 0`、`minimumElapsed(startedAt, shadowMinimumDurationHours)`，否则 `AgentEvolutionShadowGateNotSatisfied`（文案带 `hours`/`samples` 插值）。从 `canary`（或 `paused` 且最新渠道 `canary`）扩档时 `expectedNext = 5 → 25 → 50`，`expectedNext` 必须严格等于本次 `percent**（跳档即 400），且满足 `canaryMinimumSamples` / `severeErrors === 0` / `canaryMinimumDurationHours`，否则 `AgentEvolutionCanaryGateNotSatisfied`。两条分支都不匹配时 `Canary can start only after Shadow or resume from paused`。
**一次性覆盖的四连门**（`createCanaryTestOverride`）：① `requireHuman` + `approvalAuthority === 'administrator'`（否则 `AgentEvolutionCanaryTestOverrideRequiresAdministrator`）；② release 的 `gatePolicy.profile === 'manual_test'` **且**当前进程 `manualTestProfileEnabled()`（否则 `…RequiresManualTestProfile`）；③ `release.status === 'canary'`；④ 存在 `channel:'canary' && status:'canary' && !completedAt` 的活跃部署。参数：`subjectKey ≤ 200`、`reason ≤ 500`、`expiresInMinutes ∈ [1,120]`（缺省 **30**），同部署同主体已有 `pending` 即 `…AlreadyPending`。写入走 `EvolutionRuntimeStore.createCanaryTestOverride`（同事务建覆盖 + 审计 `canary.manual_test_override_created`）。
**一次性语义与指标口径**：`activeKey = sha256(tenant:org:deploymentId:subjectKey)` 建唯一索引；创建时命中**未过期**活跃行直接返回旧值（不续期），已过期则就地翻 `expired` + 清 `activeKey` 后新建。消费在 `resolveExecutionPlan` 内：只对「canary 渠道 + release 为 canary + 部署未完成」的部署尝试；命中则分配项带 `selectionReason: 'manual_test_override'` 与 `manualTestOverrideId`，响应另出 `manualTestOverrides[]`。**覆盖消费后同一 `subjectKey` 回落**到确定性路由 `deterministicPercent = sha256(deploymentId:subjectKey).readUInt32BE(0) / 2^32 * 100 < deployment.canaryPercent`。惰性过期：`listCanaryTestOverrides` 与 `getDashboard` 会把「pending 且已过 `expiresAt`」的行就地翻 `expired`（**读路径写库**，翻转不写审计）。
章节来源：[governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts)（关键符号：startCanary、createCanaryTestOverride）、[evolution-runtime.store.ts](file://packages/server-ai/src/agent-evolution/application/evolution-runtime.store.ts)（关键符号：createCanaryTestOverride、consumeCanaryTestOverride）、[agent-evolution-runtime.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-runtime.service.ts)（关键符号：resolveExecutionPlan、deterministicPercent）、[evolution-store.helpers.ts](file://packages/server-ai/src/agent-evolution/application/evolution-store.helpers.ts)（关键符号：canaryTestOverrideActiveKey）、[agent-evolution.store.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution.store.ts)（关键符号：listCanaryTestOverrides）

## 运行时服务
`resolveExecutionPlan` 是「发布如何影响运行」的唯一落点：① 校验 `targetIds` 非空、`subjectKey.trim()` 非空、scope 合法；② 对每个去重 targetId **先取 `channel:'production'` 指针，缺失即 404**（硬前置）；③ 取该目标全部部署（`listDeploymentsForTarget`，按 `createdAt DESC`）逐条与 release 联查，`release` 缺失或为 `paused|rolled_back` 直接跳过；④ `shadow` 渠道且 release 为 `shadow` → 记入 `shadowAssignments` 并 `break`；⑤ `canary` 渠道且 release 为 `canary` 且 `!completedAt` → 先消费覆盖、再判确定性百分比，`!consumedOverride && !deterministicSelection` 则 `continue`，命中才把 `productionVersionId` 换成 `release.targetVersionId` 并标 `canarySelected`；⑥ 未命中任何候选时回落「按指针的生产分配」，若 `pointer.value.releasePackageId` 有值则再找活跃生产部署补 `deploymentId`；⑦ `createBundle` 为每个分配 `findVersion` 取 `artifactHash/providerKey/providerVersion`，`bundleHash = hashEvolutionValue(items)`，`bundleId = BND-<uuid>`，**每次解析都新增一行** `capability_bundle`。响应的 `executionMode` 依次取 `canary > shadow > production`，影子另出 `shadowBundle` + `shadowAssignments`。
与 `active_pointer` 的关系是「**指针定基准、部署改覆盖**」：指针恒定提供 `productionVersionId` 的初值，只有 canary 分支会临时替换它并把 `selectionReason` 标出来；`paused`/`rolled_back` 的 release 不参与任何选路。`recordRuntimeObservation` 只做 `observationId` 补全（缺省 `OBS-<uuid>`）与 `validateScope` 后转 `EvolutionRuntimeStore`；`getCapabilityBundle` / `getCapabilityVersion` 是只读兜底，未命中一律 404。

## 观测与经验
`saveRuntimeObservation` 在一个事务内完成四件事：① 按 `observationId` 查重（命中即返回旧值，不重复累加）；② 落 `runtime_observation`（`deploymentId` 可空，**为空时只入观测表、不累加统计**并静默返回）；③ 对 `release_deployment` 加 `pessimistic_write` 累加：`sampleCount = prev + 1`、`candidateAccuracy = (prevAvg * prevCount + success) / sampleCount`、`severeErrors += severeError`、`p95LatencyMs = max(上一次观测的 p95, 本次 latencyMs)`（单调不减）、`averageCost = (上一次观测的均值 * prevCount + cost) / sampleCount`，并把单条 `runtimeObservation` append 进 `observations[]`；④ `severeError === true` 且 release `isStagedRelease` 且 `status ∈ {shadow, canary}` 时 `assertReleaseTransition(status, 'paused')` 后自动暂停，审计 `deployment.auto_paused`（主体 `agent-evolution-runtime` / `system_safety_guard`）。**这是本子域唯一由数据触发状态迁移的路径**；`active` 不会被自动降级。
经验沉淀：`createExperience` 要求 `requireHuman` + release `active` + 冻结 `gatePolicy` 存在 + 存在 `channel:'production' && status:'active'` 部署且 `sampleCount ≥ experienceMinimumSamples`、`severeErrors === 0`、时长 ≥ `experienceMinimumDurationHours`，并回查 `change.evaluation.passed && evaluation.runId === release.evaluationRunId`（否则 `Release strategy assessment does not match`）；产出 `EvolutionExperience{experienceId: EXP-<uuid>, status:'active', evidence:{productionObservationCount, severeErrors, stableDays: hours/24, evaluationRunId}}`，**不改变任何指针**。学习事件侧：`ingestLearningEvent` 校验 scope、confidential 必须 `redacted`、目标必须 `active`，落 `learning_event`（`reviewStatus` 强制 `pending`）——它是闭环的入口，但**「经验 → 下一轮学习事件」在本仓没有写入点**。

## 队列与 job
`AgentEvolutionQueueService` 的顺序是「**先落账本再投递**」：`if (!this.queue) throw ServiceUnavailableException('Managed Queue is unavailable')` → 构造 `jobId = EVOJOB-<uuid>`、`job: EvolutionJob{jobType, resourceId, status:'queued', createdAt}` → `store.saveJob` → `queue.enqueue({pluginName: '@xpert-ai/platform', queueName: 'agent-evolution', jobName: jobType, payload:{jobId, context, ...}, tenantId, organizationId, userId, jobId, attempts: 3, backoffMs: 1000})` → `updateJobStatus('queued', {queueJobId})`；`catch` 分支写 `failed` + `errorCode: 'queue_enqueue_failed'` + `completedAt` 后**重抛**（HTTP 500，任务未进队列）。`enqueueReleaseOperation` 对 `canary` 会补默认 `request = {}`；`GET /jobs/:jobId` 直读账本（未命中返回 `null` 而非 404）。
`AgentEvolutionQueueProcessor` 同时挂五个 `@PluginJobProcessor`（`evaluation 2`、`install 1`、`shadow 2`、`canary 1`、`rollback 1`），`handle` 先 `updateJobStatus('running', {startedAt})`，再 `switch(payload.operation)` 分派到 `governance.{evaluateCandidate, installRelease, startShadow, startCanary, rollbackProduction}`；成功 `completed`（`completedAt`），异常写 `failed` + `errorCode: 'evolution_job_failed'` + `errorMessage` 后**重抛**交给队列重试。**无调度器**：`@Cron`/`@Interval`/`@Timeout` 零命中；也**不订阅跨域事件**（`@OnEvent` 零命中）。

## 热点路径
1. **`resolveExecutionPlan`（每次执行一次）**：同步循环「每目标 → 取指针 → 列部署（含 release 联查）→ 可能消费覆盖 → 建能力束（逐分配 `findVersion`）」，且 `createBundle` **为每次解析新增一行 `capability_bundle`**；该表只有 `bundleHash` 普通索引、无 TTL 与清理路径。
2. **`saveRuntimeObservation`（每次运行一次）**：单事务「观测去重插入 + 部署行 `pessimistic_write` 累加 + `observations[]` append」，同一部署的并发观测被行锁串行化，是观测侧吞吐上限。
3. **`replay()`（评估）**：逐 case 串行 `runReplayCase` + `evaluateResult`，`totalCases ≥ 50` 是硬闸门，单次评估至少 50 次 provider 往返，`caseResults` 全量落 `EvaluationRun.value`。
4. **`decide()`（审批，① 侧写路径）**：每次评审都取该候选全部历史审批做三元组过滤；本子域的 `reviewHumanApprovals` 只做内存计算，风险在「历史行随重试增长」。
5. **`inspect()`（基线面板）**：每次调用都真调 `previewBaseline`（可能读外部源）+ 读指针/版本；前端每次 scope 变化都会触发。
6. **`createCanaryTestOverride` 与 `listCanaryTestOverrides`**：创建要连查 release + 部署列表 + 覆盖列表；list 带**读路径写库**的过期翻转，高并发下产生写竞争。

## 技术债
1. **`job.status` 口径漂移**：契约 `EvolutionJobStatus` 无 `pending`，① 的 `change.service.process` 补偿分支仍判断 `['pending','queued','running']`——本子域处理器只写 `running/completed/failed`，该分支很可能是死分支。
2. **`cancelled` 无写入点**：契约有该状态，但 48 个端点中没有「取消 job」入口，只能直接改 `agent_evolution_job` 账本；`job` 表**无 TTL、无清理任务**。
3. **`saveRelease` 绕过状态机**：`startCanary` 用 `store.saveRelease({...release, status:'canary', canaryPercent})` 直接覆盖 `status`，未过 `assertReleaseTransition`；`transitionRelease` 与 `saveRelease` 两条写口并存。
4. **`observations[]` 无界增长**：观测逐条 append 进部署行 json 列，长跑部署会把单个 json 单元格撑大；`p95LatencyMs` 用 `max` 合并，**只增不减**，无法反映延迟改善。
5. **观测均值口径**：`averageCost` 用「上一次观测的均值 × 上一轮样本数」续算，而非读部署行上的累计值——`[推测]` 若历史行被外部修改，该口径会漂移。
6. **`capability_bundle` 写入放大**：每次 `resolveExecutionPlan` 新增一行且无清理路径；`[推测]` 高 QPS 下该表可能成为最大表（未在测试中验证）。
7. **指针冲突是 500 而非 409**：CAS 失败抛普通 `Error('Active Pointer CAS conflict')`，前端无法据状态码做重试语义。
8. **回滚不可逆**：`rolled_back` 在迁移表中是终态，回滚后 release 状态与指针 `revision` 同时前推，**回不到原 canary 档**，只能重走 install。
9. **`paused` 恢复路径依赖「最新部署渠道」**：`startCanary` 从 `paused` 恢复时用 `deployments[0]?.value` 判断可走 shadow 还是 canary，**部署历史顺序因此成为隐式状态**。
10. **覆盖残留与单列唯一索引**：`@Index(['activeKey'], {unique:true})` 是全域唯一**不带 tenant/organization** 的唯一索引（值本身含哈希）；已消费行不删除，`[推测]` 多轮部署后「已消费重试」分支按 `createdAt DESC` 可能匹配到旧行。
11. **读路径写库**：`listCanaryTestOverrides` 与 `getDashboard` 会把过期 `pending` 就地翻 `expired`（清 `activeKey`），**翻转不写审计**，只读端点产生写竞争与审计缺口。
12. **基线 `inspect` 无缓存**：每次调用都真调 `previewBaseline`；`[推测]` 若 provider 为远程读，前端 scope 切换会放大为外部 QPS。
13. **无 SQL 迁移**：本子域 11 表（乃至全模块 19 表）DDL 的唯一事实来源是实体注解，目录内无 `migrations/`、全仓 `*.sql` 中 `agent_evolution` 零命中。
14. **`@VersionColumn` 全域缺失**：唯一乐观锁是手写的 `active_pointer.revision`；其余表依赖条件更新或行锁。

## 设计维度
**「同步硬闸门」 vs 「队列化动作」**：`pause`/`activate` 同步返回（HTTP 报错即业务拒绝，调用方立刻知道放量结果），`install|shadow|canary|rollback|evaluation` 入队返回 `EvolutionJob`（HTTP 200 **不代表动作成功**，失败只能靠 `GET /jobs/:jobId` 的 `errorCode` 观察）。取舍得当之处在于：改指针的语义必须同步确认，不改指针的 provider 调用可以异步重试（`attempts: 3`）。代价是前端必须实现轮询，且「入队失败」与「作业失败」是两个不同的错误码（`queue_enqueue_failed` vs `evolution_job_failed`）。
**「冻结阈值」 vs 「可调 env」**：六项阈值只在**建包时**经 `snapshot()` 读取一次并写进 `ReleasePackage.gatePolicy`，此后全部读 `forRelease`。这让「改配置影响在途发布」在结构上不可能，也使闸门判据完全可复现（审计只需一条发布包行）。代价是调阈值必须重新建包，而 `PUB-<changeId>` 已是幂等固定 id，**无法对同一变更改阈值**。
**「覆盖一次性」 vs 「路由可解释」**：金丝雀覆盖刻意做成一次性 + 逐次消费，使「管理员临时放行」不会永久改变路由；回落逻辑用 `sha256(deploymentId:subjectKey)` 而非随机，保证同一主体在覆盖消费后仍可复现地落回同一 bucket。代价是排查时必须同时看 `canary_test_override`（是否消费）、部署的 `canaryPercent` 与 `active_pointer.revision` 三者，任一缺失都会把「为什么这次走旧版本」解释错。
**「读侧薄」 vs 「多表关联」**：`resolveExecutionPlan` 不落任何「解析结果」表，只落 bundle；`inspect` 的状态是读时派生。好处是无中间态需要维护，代价是每次解析都要做「部署 → release → 版本」三段查询，且 `capability_bundle` 必须写库才能让调用方拿到不可变引用。

## 结论
实现骨架可概括为「**四层冻结 + 一道 CAS + 一条回流**」：策略快照（① 侧）与 `gatePolicy`、审批三元组、覆盖 `activeKey` 分别在提交/建包/评审/覆盖创建时冻结；真正让版本生效的只有 `ActiveCapabilityPointer` 的一次条件更新；观测回流是唯一能自动改写发布状态的通道（`severeError → paused`）。扩展时应继续沿用既有骨架：阈值判据写进两个纯函数服务、部署动作走 `AgentEvolutionGovernanceService` 的显式前置链、运行时写入只经 `EvolutionRuntimeStore`（事务 + 行锁 + 审计三件套）、跨阶段绑定量一律用 `hashEvolutionValue`。三处必须长期防守：**阈值只能读 `forRelease`**、**覆盖必须写 `activeKey`**、**`pause`/`activate` 之外的部署动作不得直改指针**。需要重点盯的风险是 `job.status` 的 `pending` 死分支、`saveRelease` 绕过状态机、以及 `capability_bundle` / `observations[]` 两条无界增长路径。
