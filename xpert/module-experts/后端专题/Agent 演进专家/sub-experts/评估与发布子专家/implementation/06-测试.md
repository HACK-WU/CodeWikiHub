## 五、缺口
1. **回滚路径无独立用例**：`rollbackProduction` / `rollbackPointerCas` 没有专门 spec；真库用例的终态是「发布包 `active`」，**没有走到回滚**。因此「回滚后 release 为 `rolled_back`、指针 revision 前推、无法回到原 canary 档」只有结构推断，无测试取证。
2. **队列处理器无任何行为验证**：`AgentEvolutionQueueProcessor.handle` 的状态推进（`running → completed|failed`）、五个 `@PluginJobProcessor` 的并发声明（2/1/2/1/1）、`attempts: 3` / `backoffMs: 1000` 的失败语义**没有打到真实队列**；入队失败置 `queue_enqueue_failed` 与 worker 失败置 `evolution_job_failed` 两条分支无用例。
3. **指针切换的端到端缺失**：`activateProduction` 的「指针前置校验 → provider.activate → CAS」在 mock 语境下未形成断链；`Active Pointer CAS conflict` 的失败语义（`affected !== 1`）无用例，冲突时抛 500 而非 409 的口径也无回归护栏。
4. **`EvolutionRuntimeStore` 无 store 级 spec**：覆盖的悲观锁消费与「同 executionId 重试返回已消费结果」、观测累加（`sampleCount/severeErrors/candidateAccuracy/p95LatencyMs/averageCost`）、`severeError → 自动 pause` 与对应审计**全部没有直接断言**（模块内无 `*.store.spec.ts`）。
5. **部署阶梯的拒绝路径不全**：跳档（5%→50%）、首轮非 5%、shadow/canary 门槛不足、`pause` 非法状态、`rollback` 的 agent 主体与「不是当前生产版本」三条前置**未见过滤用例**。
6. **基线端点的 HTTP 层无用例**：`controllers/` 下 0 个 spec，`GET /baselines/:targetId` 的**三权限位并列**与 `canManage` 返回体靠人工核对。
7. **`cancelled` 与 `pending` 两个状态无用例**：job 取消无 HTTP 入口（只能改库），① 侧 `['pending','queued','running']` 死分支也无过滤用例。
8. **夹具门禁 404 无断言**：`assertConformanceEnabled` / 生产 `manual_test` 闸门的相关分支在本子域 spec 中无直接用例（策略侧只覆盖到「生产忽略 manual_test」）。
9. **无 e2e / 无前端联调**：本仓未见针对 `/api/agent-evolution/*`（含鉴权失败、夹具 404）的端到端测试，前端 spec 属 `apps/cloud` 另配配置，与后端接口契约无自动比对。
章节来源：[agent-evolution-governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts)（关键符号：rollbackProduction、startCanary 阶梯校验、pauseRelease）、[evolution-runtime.store.ts](file://packages/server-ai/src/agent-evolution/application/evolution-runtime.store.ts)（关键符号：activatePointerCas、consumeCanaryTestOverride、saveRuntimeObservation）、[agent-evolution-queue.processor.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-queue.processor.ts)（关键符号：@PluginJobProcessor 并发声明 / handle）、[agent-evolution-runtime.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-runtime.service.ts)（关键符号：resolveExecutionPlan）

## 六、结论
判定：**✅ 结论上可跑，但本次不实跑**（只给命令与判据，未执行 jest）。
1. **可跑性依据（结构事实）**：本子域相关 spec 全部落在 `packages/server-ai/jest.config.ts` 的 `testMatch` 覆盖范围内；`moduleNameMapper` 直指源码，**无需先 `nx build` 依赖包**；除真库用例外均无外部依赖，单文件命令可直接执行。
2. **覆盖强度排序**：**强**——闸门策略（含生产忽略 manual_test 的 env 门禁）、质量治理 quorum、基线 inspect/publish（8 条，含 `revision_changed` / `managed_release` / 双点 `source_changed`）、金丝雀覆盖的创建门与一次性回落、conformance 端到端与指针终态；**弱**——队列、回滚、指针 CAS 冲突、观测累加副作用、HTTP 层权限。
3. **唯一环境前置**：真库 spec 默认 `describe.skip`，只有显式注入 `AGENT_EVOLUTION_PERSISTENCE_E2E=1` + 可达 PostgreSQL 才解锁；解锁后它在目标库内创建并删除自己的 schema，仍建议指向测试库。
4. **建议的验证顺序**：`quality-governance` → `release-gate-policy` → `runtime.service` → `governance.service` → `evolution-baseline` → `agent-evolution.service` → 最后单独跑 integration；任一步失败先确认 `moduleNameMapper` 是否命中源码路径。
5. **不实跑与不声明结论的原因**：本轮为只读检索任务，未执行 jest；本仓亦未见针对 agent-evolution 的「已复跑」记录，因此**不声明本子域任何 PASS/FAIL**。本域无 known-fail 白名单，唯一的 `skip` 是条件开关（`AGENT_EVOLUTION_PERSISTENCE_E2E`），不属「已知失败」。
