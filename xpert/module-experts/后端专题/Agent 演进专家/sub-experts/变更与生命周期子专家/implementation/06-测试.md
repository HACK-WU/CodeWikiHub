## 2. 逐 spec 覆盖点

**`changes/change.service.spec.ts`（16 条，也是 ① 的唯一「全路径」护栏）**：`it` 覆盖七类语义——① 只用规范生命周期实体、无聚合快照与伪造 replay 指标；② 必须精确人工审批 + 并发发布回调去重；③ 持久化 publishing 意图并在 receipt 保存失败后恢复；④ 拒绝被否决 / 陈旧策略 / 陈旧来源 / 跨组织请求；⑤ provider 拒绝发布授权时**不改发布状态**；⑥ 冻结请求一次后按 feedback 构建与评估、且不含 document/product 字段；⑦ 不覆盖已冻结评估；⑧ plugin presentation 不可用时审计数据仍可读；⑨ 必须为当前 provider 契约显式声明策略；⑩ 策略修订后仍可读历史 presentation 但不许在该修订下发布；⑪ human proposal 跳过学习与质量测试但仍需精确人工决策；⑫ 目标不允许时调用方不能选 human 捷径；⑬ 真实学习闸门 + target draft + 领域检查 + 直接版本发布的组合；⑭ 在 provider 工作完成前持久化 draft 与评估进度；⑮ 往返执行上下文并在 provider 工作前暴露会话；⑯ 会话持久化不可用时**模型检查与审批门不变**。

**`changes/change.validation.spec.ts`（3 条）**：接受 target 自定义的非 BOM 策略并评估真实模板输出；要求声明的证据种类与作用域身份；拒绝「缺必需覆盖 / 假 pass / 重复 check / 快照变更」。

**`changes/execution-conversation.service.spec.ts`（7 条，顶层 `it`，无 `describe`）**：作用域会话 + 真实 draft 与失败检查的 ChatKit 流；一变更一会话且队列重试流与消息互不干扰；项目或助手访问被拒时**不建记录**；记录生成失败并关闭同一执行流；对更早或非会话型目标**不改动任何东西**；初始流事件发布失败时仍保留可终结的 session；写入树形父关系使 ChatKit 能加载完整消息祖先（含队列重试）。

**`changes/lifecycle.projection.spec.ts`（2 条）**：发布与「显式采纳」相互独立（`phase:'publication'` + `effectStatus:'pending'` vs presentation 给出 `effect.status:'active'` 后转 `effective`）；已完整激活的 rollout 归入 published，同时保留 Canary 作为部署阶段（`status:'canary'` → `publicationStatus:'publishing'` + `effectStatus:'partial'`）。

**`changes/lifecycle.service.spec.ts`（1 条）**：`decide` 之后送给发布实体的 where **恰好只有 `organizationId`/`releasePackageId`/`tenantId` 三个键**——即 `changeIdentity()` 不得把 `actorId`/`actorType`/`actorRole` 混进实体查询。这是本子域唯一一条「上下文卫生」护栏。

**`changes/strategy.service.spec.ts`（3 条）**：手工输入 + 分阶段发布 与 学习输入 + 直接发布 两条组合各自独立成立；仅对要求学习的策略保留「受信多主体学习闸门」；拒绝歧义的评估者身份（不覆盖结果）。

**`domain/evolution-hash.spec.ts`（1 条）**：哈希前规范化对象键（规范 JSON）。
**`domain/evolution-state.spec.ts`（2 条）**：接受受治理的正常路径迁移；拒绝绕过评估或安装的捷径。
**`application/evolution-proposal-persistence.spec.ts`（1 条）**：更新已准备的 proposal 行时**不丢失请求身份**（断言 `findOne` 只按 `tenantId/organizationId/proposalId/revision` 查、且返回行保留 `id`/`requestId` 与原 `title` 覆盖结果）。
**`agent-evolution.module.spec.ts`（2 条）**：`imports` 含 `CqrsModule`；真实模块上下文可解析 `PermissionGuard`（唯一一条「守卫依赖 CommandBus」的装配护栏）。

## 5. mock 与断言风格

## 6. 缺口

1. **8 条端点零 HTTP 用例**：`changes/lifecycle.controller.ts` **无 spec**，因此「路径拼写、`@Get('records')` 必须先于 `@Get(':id')` 的声明顺序、`@Permissions` 的 `EVOLUTION_VIEW | XPERT_EDIT` 或语义、`POST /changes` 的 400 分支」全靠人工核对。这是本子域**最大的回归风险面**。
2. **`submission.schema.ts` 无直接用例**：`.strict()` 拒绝多余字段、`input ≤ 100000`、`evidence ≤ 100`、`candidateInput` 值域等边界**未被断言**；`change.validation.spec.ts` 走的是手写 `validateChangeInput`，不经过 zod。
3. **`change.processor.ts` 与队列语义无用例**：`@PluginJobProcessor({concurrency: 2})`、`invalid_job_identity` 分支、`attempts: 3 / backoffMs: 1500` 只由常量存在，重试与重复消费的行为语义**未被测试取证**（`process()` 的「残留 job 收尾」分支亦然）。
4. **夹具 provider 与夹具端点无用例**：`ConformanceTemplateProvider` 的 `authorizeScope`/`fixtureInput` 自举基线/`validateCurrent` 的「恰 1 条 feedback」硬口径、以及 `assertTemplateConformanceEnabled()` 的生产 404 门禁**均无断言**；`POST /changes/conformance-template` 亦然。
5. **`change_not_found` 的 400 语义无用例**：`changeError` 恒抛 `BadRequestException`，跨组织/不存在/无权限在 HTTP 上不可区分——这一口径既无测试也无文档化契约。
6. **两套摘要算法无交叉用例**：`digest`/`changeDigest`（`JSON.stringify`，顺序敏感）与 `hashEvolutionValue`（键排序）**没有被放在同一个用例里比对过**；`evidence` 重排即 `immutable_request_changed` 这一行为属源码推断。
7. **`decide()` 的并发路径无用例**：实体无 `(candidateId, actorId)` 唯一索引，且 `records.read` 在 `decide` 中未启用 `pessimistic_write`；「同 actor 改判」只有串行用例，**没有并发取证**。
8. **`awaitingDataset` 的静默停留无用例**：「缺 `golden_replay` 数据集 → `process()` return、`status` 停在 `testing`、job 已 `completed`」这一组合态**无可执行判据**延续到 04/05 文档。

1. **可跑性依据**：11 个 ① 相关 spec 全部落在 `packages/server-ai/jest.config.ts` 的 testMatch 覆盖内；`moduleNameMapper` 直指源码，**无需先 `nx build`**；其中 10 个无外部依赖（DB/Redis/队列全部 mock 或 `@Optional()` 未注入即走无队列分支），单文件命令可直接执行；仅 `agent-evolution.persistence.integration.spec.ts` 需显式开关 + 可达 PostgreSQL。
2. **覆盖强度分布极不均**：`change.service.spec.ts` 一个文件占本子域 16/39 条（≈41%），而 `change.processor`/`submission.schema`/`lifecycle.controller`/`conformance-template.provider` 四个文件**覆盖率为零**——即「同步协调路径」被反复回归，「异步与入口层」几乎没有护栏。
3. **建议的验证顺序**：`domain/*` → `changes/{strategy,change.validation}` → `changes/lifecycle.projection` → `changes/lifecycle.service` → `changes/execution-conversation.service` → `changes/change.service` → `agent-evolution.module` → `application/evolution-proposal-persistence` → 最后单独开 `AGENT_EVOLUTION_PERSISTENCE_E2E=1` 跑真库用例。
4. **最高优先补齐项**（按风险排序）：① `changes/lifecycle.controller.ts` 的路由顺序与权限位；② `submission.schema.ts` 的严格边界；③ `ConformanceTemplateProvider` 的 scope 校验与生产门禁；④ `digest` vs `hashEvolutionValue` 的等价性交叉用例；⑤ `decide()` 的并发改判。
5. **skip 语义**：本子域**无 known-fail 白名单**，唯一的 `skip` 是条件开关（`AGENT_EVOLUTION_PERSISTENCE_E2E`），不属「已知失败」。
