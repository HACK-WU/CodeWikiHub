## 1. 提交入口与校验（8 条 changes 端点）

类级 `@Controller('changes')` + `@UseGuards(PermissionGuard)`；最终路径前缀 `/api/agent-evolution/changes`。**逐端点**：

| # | 方法 + 路径 | 处理函数 | 权限 | 校验与转发 |
|---|---|---|---|---|
| 1 | `POST /changes` | `submit` | `EVOLUTION_MANAGE` | `evolutionSubmissionSchema.safeParse(body)` 失败即 `invalid_strategy_submission`；成功后 `{...parsed.data, ...identity()}` → `changes.prepare()` |
| 2 | `POST /changes/conformance-template` | `conformance` | `EVOLUTION_MANAGE` | `assertTemplateConformanceEnabled()` 门禁；body 仅 `{requestId, strategyId}`（**无 schema 校验**）；`fixture.fixtureInput(...)` 装配输入；`sourceKind = strategyId === 'human_proposal' ? 'manual' : 'business_evidence'` → `prepare()` |
| 3 | `GET /changes` | `list` | `EVOLUTION_VIEW \| XPERT_EDIT` | `lifecycle.list(identity(), query)` → 投影 + 过滤 + 分页 |
| 4 | `GET /changes/records` | `records` | `EVOLUTION_VIEW \| XPERT_EDIT` | `@Query('targetId')` → `changes.list()`（**契约原文，非投影**） |
| 5 | `GET /changes/:id` | `get` | `EVOLUTION_VIEW \| XPERT_EDIT` | `lifecycle.get(identity(), id)` → 单条投影 |
| 6 | `POST /changes/:id/evaluations` | `evaluate` | `EVOLUTION_MANAGE` | body `{datasetSnapshotIds?}` → `lifecycle.evaluate(context(), id, ...)` |
| 7 | `POST /changes/:id/decisions` | `decide` | `EVOLUTION_MANAGE` | body `{candidateHash, evaluationRunId, decision, reason}` → `lifecycle.decide(context(), id, body)` |
| 8 | `POST /changes/:id/publication` | `publish` | `EVOLUTION_MANAGE` | 无 body → `lifecycle.publish(context(), id)` |

**路由顺序**：`@Get('records')` 声明在 `@Get(':id')` **之前**，因此 `/changes/records` 不会被 `:id` 吞掉——这是本控制器唯一的顺序敏感点，且**无 spec 守护**（`controllers/` 与 `changes/lifecycle.controller.ts` 均无用例）。

**上下文归一**：`identity()` 只返回 `{tenantId, organizationId}`（**只含两个键**，被 `lifecycle.service.spec.ts` 断言为「不把 actor 字段透传给实体查询」）；`context()` 在此之上加 `actorId`/`actorRole`（缺省 `'human_operator'`）/`actorRoleName`/`approvalAuthority`（`role.name ∈ {SUPER_ADMIN, ADMIN}` → `'administrator'`，否则 `'standard'`）/`actorType: 'human'`。`agent-evolution.controller.ts` 的 `requestScope()`/`commandContext()` 是同一套口径的孪生实现（两个文件各写一份，未抽公共函数）。

**错误出口**：`changeError(code)` 恒抛 `BadRequestException`（i18n `server-ai:Error.EvolutionChange`），因此**包括 `change_not_found`、`identity_mismatch` 在内的全部业务失败都是 400**，不存在 404/409 语义——与父域其他模块（如基线发布的 409）口径不同。

## 2. change.store 的落库与去重

文件头注释逐字：`// Invariants: one Proposal owns request identity; Candidate, Evaluation, Approval and Release` / `// are authoritative for their own stage. EvolutionChange is assembled, never persisted whole.`——这是本子域最重要的读侧约束。

**写侧 `save()` 的五段**（注释逐字 `Saves each stage in its canonical table. Call under the Proposal row lock.`）：
1. **proposal**：先 `findOneBy`，若已有 `isEvidenceProposal` 行则**保留原叙事字段**（`title`/`problemStatement`/`rootCause`/`changeHypothesis`/`riskLevel`）再覆写；变前再校验 `changeDigest(evidence)`/`evidenceHash`/`baseline`/`strategy.hash` 未变，否则 `immutable_request_changed`。
2. **candidate**：`prior.artifactHash !== artifact.hash` 或 `definition` digest 变化 → `immutable_candidate_changed`；构造 `PreparedEvolutionCandidate`（`proposalId: PROP-<changeId>`、`proposalRevision: 1`、`baseVersionId`、`buildInputsHash = change.evidenceHash`、`evaluationRunId`、`status: toCandidateStatus(...)`），实体列写 `artifactHash`/`status`。
3. **evaluation**：转交 `saveEvaluation()`。
4. **approval**：同 `approvalId` 已存在且 digest 不同 → `immutable_approval_changed`；不存在才插入（列含 `candidateHash`、`decision`）。
5. **release_package（仅 `version_write` 路径）**：`PUB-<changeId>`，`prior.candidateHash` 不符或已 `published` 但 receipt 变了 → `immutable_receipt_changed`；`approvalIds` 由**四元组全对齐**过滤（`decision === 'approved'` + `candidateHash` + `evaluationRunId` + `strategyHash`）；状态在 `published`（有 receipt）/ `publishing` / `approved` 三态间取值。

**`saveEvaluation()`**：同 `runId` 不同 digest、或 `candidateId` 不符、或行不是 `isProviderEvaluation` → `immutable_evaluation_changed`；写 `status = result.passed ? 'passed' : 'failed'`、布尔判据列 `gatePassed = result.passed`、`evaluatorKind: 'strategy_checks'`、**`startedAt: change.createdAt`**（复用变更创建时间，不是评估真实开始时间）。

**读侧 `assemble()` 跨五表拼装**：proposal → candidate（`isPreparedCandidate` 否则 `candidate_snapshot_mismatch`）→ evaluation_run（按 `candidate.evaluationRunId`，否则 `evaluation_snapshot_mismatch`）→ approval（取 `evaluationRunId` + `candidateHash` 双匹配的最近一条）→ release_package（`PUB-<candidateId>`，`version_write` 路径下类型不符即 `publication_snapshot_mismatch`）。`status` 由**五级优先级链**派生：`staged 发布行（active→published，其余→publishing）` > `receipt.status` > `approval.decision==='rejected'` > `approval && candidate.status==='approved'` > `proposal.preparation==='failed'` > `fromCandidateStatus(candidate.status)` > `'preparing'`。

**去重三口径**：① DB 唯一索引 `UX_evolution_proposal_request(tenant, organizationId, targetId, requestId)`（`create()` 靠 `insert().orIgnore()` 命中）；② 应用层 7 字段 `changeDigest` 对账（见 `01-架构.md §6-②`）；③ `prepare()` 用 `record.changeId === changeId` 判「是否首次」。`read(manager, input, id, lock)` 的定位键是 `proposalId: PROP-<id>` + `revision: 1`，`lock` 时加 `pessimistic_write`，命中失败即 `change_not_found`。

章节来源：[change.store.ts](file://packages/server-ai/src/agent-evolution/changes/change.store.ts)（关键符号：EvolutionChangeStore.create / read / assemble / save / saveEvaluation / proposal / changeIdentity）、[entities/evolution.entities.ts](file://packages/server-ai/src/agent-evolution/entities/evolution.entities.ts)（关键符号：ImprovementProposalEntity 的 UQ、EvaluationRunEntity.gatePassed）

## 3. change.processor 的异步执行与重试

**处理器**：`@PluginJobProcessor({ ...CHANGE_QUEUE, concurrency: 2 })`；`handle(job, context)` 先校验 `context.tenantId && context.organizationId && typeof job.data?.changeId === 'string'`（否则 `invalid_job_identity`），再调 `changes.process({tenantId, organizationId, changeId})`。**无本地重试逻辑**——重试完全交给队列（`attempts: 3, backoffMs: 1500`）。

**`process()` 的八段（源码顺序）**：
1. `get()` 读变更；状态不在 `{preparing, testing, failed}` → 收尾残留 job（`['pending','queued','running']` → `completed`）并 return。
2. `updateJobStatus(running, {startedAt})`。
3. `recordConversation(() => conversations.start(initial))`：成功后**独立事务**写 `change.executionConversation = session.reference`。
4. **事务 A**：`setStage(candidate, 'running')` + `save`——注释逐字 `Commit progress before slow provider calls so readers can observe the running stage.`
5. **事务 B**：`strategies.current()` 复核策略快照未漂移 → `buildDraft()`（`target_draft` 走 `draftBuilder.prepare`，否则 `findVersion(baseline)` 校验哈希后 `candidateBuilder.buildCandidate({idempotencyKey: '<changeId>:build'})` + `validateCandidate`）→ 三项校验（基线 digest、`artifact.uri`/`hash` 非空、`schemaVersion` 对齐）→ `setStage(candidate, 'passed')` → `status = 'testing'` → 若 `awaitingDataset`（存在 `golden_replay` 步骤且缺 `datasetSnapshotIds[step.key]`）则**不**置 evaluation running。
6. `recordConversation(() => conversations.drafted(...))`。
7. **事务 C**：再判一次 `awaitingDataset`（命中即 return，评估不跑、状态停在 `testing`）→ `assertCurrent()` → `evaluations.run(operation, target, manager)`（② 的执行器；已有 `change.evaluation` 则复用）→ 清空 `failureReasons`、写 `evaluation`、`status = passed ? 'pending_approval' : 'test_failed'`、`setStage(evaluation, assessment==='not_applicable' ? 'not_applicable' : passed ? 'passed' : 'failed', [runId])`、`audit('candidate_assessed')`。
8. `updateJobStatus(completed)` + `recordConversation(() => conversations.finish(...))`。

**失败路径**：`catch` 内单事务写 `status='failed'` + `failureReasons=[message]` + `setStage(candidate ? 'evaluation' : 'candidate', 'failed')`；job 写 `failed` + `errorCode: 'change_preparation_failed'` + `completedAt`；`conversations.finish(..., message)` 自身失败被 `logger.warn` 吞掉；最后 **`throw error`** 让队列重试。

**重入安全**：`process()` 的三个事务块各自再判 `['preparing','testing','failed'].includes(change.status)`，因此并发或重试时只有第一个观察者推进；`build()`/`evaluate()` 是 HTTP 直连的「改输入 + 触发 `process`」，`evaluate()` 另有 `if (change.approval || change.receipt) changeError('approved_candidate_immutable')`。

章节来源：[change.processor.ts](file://packages/server-ai/src/agent-evolution/changes/change.processor.ts)（关键符号：EvolutionChangeProcessor.handle）、[change.service.ts](file://packages/server-ai/src/agent-evolution/changes/change.service.ts)（关键符号：EvolutionChangeService.process、buildDraft、assertCurrent、build、evaluate、enqueue、CHANGE_QUEUE）

## 4. 生命周期读取与投影

**`GET /changes`（投影读）**：`EvolutionLifecycleService.list` 分三步——① `changes.list({...identity, targetId})` 取全部变更；② 按 `changeIdentity(identity)`（**仅 tenant/org**）`find` 全部 `ReleasePackageEntity`，过滤 `isStagedRelease` 后按 `release.candidateId === change.changeId` 匹配；③ 逐条 `lifecycleRecord(change, release)`，再按 `publicationStatus === query.status` 与 `title + targetId` 的 `toLowerCase().includes` 过滤，按 `createdAt DESC` + `id ASC` 排序后内存分页（`page ≥ 1`、`pageSize = min(200, max(1, ...))`）。**全量加载 + 内存分页**是本子域最直接的扩容瓶颈。

**`GET /changes/:id`（单条投影）**：`changes.get()` + 按 `PUB-<id>` 单行读发布包，同样 `isStagedRelease` 收窄后交给 `lifecycleRecord`。三动作（`evaluate`/`decide`/`publish`）执行完都**复用 `this.get(context, id)`** 返回同形投影，因此前端三动作的响应体与详情页一致。

**`GET /changes/records`（契约原文）**：绕过投影，直接 `EvolutionChangeService.list` → `records.list` → `assemble`。因此该端点的 `status` 是变更状态机词表（`preparing|testing|test_failed|...`），而 `/changes` 的 `status` 在同一字段名上可能是**发布包状态**（`release?.status ?? change.status`）——**同名不同义，前端必须按端点区分**。

**投影细节**（`lifecycle.projection.ts`，纯函数）：`publicationStatus` 优先级 `closed(rejected|rolled_back|superseded) > blocked(failed|stale|test_failed|paused) > published > publishing > review > preparing`；`effectStatus` 三态 `active|partial|pending`；`phase` 六态 `closed|blocked|effective|publication|review|evaluation|preparation`；`stages` 中 `publication`（published 时强制 `passed`）与 `effect`（按 `effectStatus` 映射 `passed|running|pending`）会被重写；`capabilities` 四个建议位。

**分页口径漂移**：`lifecycle.service` 上限 **200**／默认 20，`evolution-store.helpers.normalizePage` 上限 **100**／默认 20——同一个 UI 在两个端点上会拿到不同深度的页。

章节来源：[lifecycle.service.ts](file://packages/server-ai/src/agent-evolution/changes/lifecycle.service.ts)（关键符号：EvolutionLifecycleService.list / get / evaluate / decide / publish）、[lifecycle.projection.ts](file://packages/server-ai/src/agent-evolution/changes/lifecycle.projection.ts)（关键符号：lifecycleRecord）、[evolution-store.helpers.ts](file://packages/server-ai/src/agent-evolution/application/evolution-store.helpers.ts)（关键符号：normalizePage）

## 5. 三动作在本子域的职责边界

| 动作 | ① 的职责（记录与投影） | ② 的职责（执行与判据） |
|---|---|---|
| `POST /changes/:id/evaluations` | 事务内冻结 `datasetSnapshotIds`（已有评估且映射变化 → `evaluation_snapshot_mismatch`）、无评估则推 `status='testing'`、已审批禁止再评（`approved_candidate_immutable`）；触发 `process()`；落 `EvaluationRun`（经 `saveEvaluation`，`immutable_evaluation_changed` 兜底）；把 `status` 写成 `pending_approval`/`test_failed` 并 `setStage('evaluation', ...)` | `EvolutionEvaluationExecutor.run`：逐步评估、golden replay、`validateChangeEvaluation`、阈值判定（`reviewGoldenReplay`） |
| `POST /changes/:id/decisions` | **全部校验与落库**：三元组绑定（`candidate.artifact.hash`/`evaluation.runId`/`evaluation.strategyHash === strategy.hash`，任一不符 `review_snapshot_mismatch`）、历史审批按三元组过滤、同 actor 幂等/改判拒绝、状态只能 `pending_approval\|test_failed`、批准需 `evaluation.passed` 且 `assertCurrent`、写 `ApprovalDecision`（含 `approvalAuthority`/`actorRoleName`）、用 `gate.passed` 决定 `approved` 或仍 `pending_approval`、`audit('candidate_approved\|rejected')` | `reviewHumanApprovals(riskLevel, approvals)` 提供 quorum 判据（R3/R4 → 3 人，否则 2 人；管理员单票放行） |
| `POST /changes/:id/publication` | 状态机（只有 `approved\|publishing` + 审批通过 + 双 `strategyHash` 对齐 + `evaluation.passed` 才放行，否则 `human_approval_required`）、先推 `publishing` + `setStage('publication','running')`，再第二个事务真正发货；`version_write` 路径校验回执三元组（`changeId`/`candidateHash`/`approvalId`，否则 `write_receipt_mismatch`）；写 `release_package` 行 + `audit('version_publication')`；**已有 `receipt` 直接 return（幂等）** | `EvolutionPublicationExecutor.package()` 分配 `CapabilityVersion` + `PUB-<changeId>` 并冻结 `gatePolicy`；发布族队列、部署阶梯、指针 |

**一句话边界**：① 决定「**能不能**做、记录什么」，② 决定「**怎么**做、用哪个阈值」。两侧的接口都很窄：`evaluations.run()`、`publication.package()`、`quality.reviewHumanApprovals()`，**没有反向调用**。

章节来源：[change.service.ts](file://packages/server-ai/src/agent-evolution/changes/change.service.ts)（关键符号：evaluate、decide、publish、assertCurrent）、[lifecycle.service.ts](file://packages/server-ai/src/agent-evolution/changes/lifecycle.service.ts)（关键符号：evaluate / decide / publish 的转发与回投影）、[change.store.ts](file://packages/server-ai/src/agent-evolution/changes/change.store.ts)（关键符号：EvolutionChangeStore.saveEvaluation）

## 6. 夹具 provider 的授权与 scope

**两道门禁，同一个判据**：`assertTemplateConformanceEnabled()`（provider 内）与 `assertConformanceEnabled()`（`agent-evolution.controller.ts` 内）都是 `environment.production && process.env.AGENT_EVOLUTION_ENABLE_CONFORMANCE !== 'true'` → `NotFoundException`——**与「资源不存在」在 HTTP 上不可区分**，这是刻意的隐藏式下线。

**第二道 scope 校验**：`authorizeScope(context)` 在**每个对外方法首行**调用（`fixtureInput`/`describe`/`prepare`/`evaluate`/`validateCurrent`/`authorizePublication`/`publish`），判据是 `context.targetId === CONFORMANCE_TEMPLATE_TARGET && context.scope.type === 'organization' && context.scope.key === context.organizationId`，任一不符即 `identity_mismatch`。`publish` 先走 `authorizePublication`，那里再加**人主体校验**（`actor.actorType !== 'human'` → `human_approval_required`）。

**descriptor 口径**：`targetType: 'test_fixture'`、`riskLevel: 'R1'`、`providerVersion: '1.0.0'`、`artifactSchemaVersion: '1'`、`supportedScopes: ['organization']`、`capabilities` 仅 `candidateBuild: true`（`replay/shadow/canary/install/rollback` 全 false）；`strategies` 两项：`evidenceDrivenStrategy({version:'template/2', effect:'activation', evidenceKinds:['feedback'], requiredChecks:[render, boundary]})` 与 `structuredClone(HUMAN_PROPOSAL_STRATEGY)`；`draftBuilder`/`checkEvaluator`/`versionPublisher`/`presenter` 四者为同一个 `this`。

**写库点（易被忽略）**：`fixtureInput()` 会 **`saveVersion('CONFORMANCE-TEMPLATE-BASE', sequence 1)`** 自举基线（仅当该目标还没有版本时）——即夹具入口不只是造输入，它会落一条能力版本。`publish()` 产出 `CONFORMANCE-<changeId>` 版本 + `RECEIPT-<changeId>` 回执（`receiptId/changeId/candidateHash/approvalId/resource/completedAt`），并在版本已存在时校验 `version.value.artifact.hash === change.candidate.artifact.hash`，否则 `write_receipt_mismatch`。

**夹具口径不等于通用规则**：`validateCurrent()` 除基线与哈希外，额外要求 `evidence.length === 1 && kind === 'feedback' && uri === 'conformance-feedback://greeting/1' && hash === hashEvolutionValue(feedback)`；`evaluate()` 还把候选 artifact 与本地 `artifactFor(template)` 逐字段比对，不同即 `immutable_candidate_changed`。任何把该 provider 当参照实现的下游都会踩空。

## 8. 热点路径

1. **`GET /changes`（每次打开工作台一次）**：`changes.list` 全量取变更 + 全量取该租户/组织下**所有** `ReleasePackageEntity`，再在内存里逐条 `lifecycleRecord` 与过滤、排序、分页。数据量随变更数 × 发布包数线性放大，且 `filter(isStagedRelease)` 说明其中相当一部分行在内存里被丢弃。
2. **`assemble()`（每次读变更一次）**：单次读变更最多 **6 次查询**（proposal → candidate → evaluation_run → approval 列表 → release_package + `read` 内的 proposal 复读），`list` 路径下是 **N×6**。
3. **`decide()`（每次评审一次）**：取该候选**全部历史审批**再做三元组过滤；实体只有 `candidateId` 维度索引、**无 `(candidateId, actorId)`**，高风险 R3/R4 攒 3 人时要重复扫 3 遍。
4. **`process()`（每次推进一次）**：八段里 **4 次独立事务 + 4 段会话副作用 + 1 段 provider 构建**；外部 provider 调用**不持锁**（注释明示先提交 running 段），因此同变更并发推进靠状态判断而非锁。
5. **`save()`（每次写入一次）**：单次最多写 5 张表，其中 release 段还要**再查一次该候选的全部审批**做 `approvalIds` 过滤——与 `decide()` 的历史扫描是同一张表的第二次全扫。
6. **`prepare()` 的 feedback 对账**：`findLearningEvents` 取全量事件后逐个算 `digest(value)` 并与入参 evidence **逐条**比对（两次排序 + 两次哈希），证据上限 100 条时是 100 次 sha256。

## 10. 技术债与 hack

1. **`change_not_found` 是 400**：`changeError` 恒抛 `BadRequestException`，因此「变更不存在」「租户不符」「跨组织」在 HTTP 上全部是 400，前端无法区分「没权限」与「不存在」——与父域基线发布的 409 语义不一致。
2. **两套摘要算法并存**：`digest`/`changeDigest`（`JSON.stringify`，**键不排序、数组顺序敏感**）vs `hashEvolutionValue`（键排序的规范 JSON）。`evidenceHash` 用前者、夹具与阈值判据用后者；等价性依赖调用方保持字段顺序。
3. **`job.status` 的 `'pending'` 分支**：`process()` 判断残留作业时用了 `['pending','queued','running']`，而契约 `EvolutionJobStatus` 无 `pending`（只有 `queued|running|completed|failed|cancelled`）——该分支在当前实现下不可能命中，属**死条件**；但 `updateJobStatus` 的类型参数是 `EvolutionJobStatus`，故 `'pending'` 只能出现在只读判断里。
4. **分页上限不一致**：`lifecycle.service` 200 / `store.normalizePage` 100，同一资源两个深度。
5. **`saveEvaluation` 的 `startedAt` 复用 `change.createdAt`**：评估记录的开始时间不是真实开始时间，用它算评估耗时会得到「变更创建 → 评估完成」的端到端时长。
6. **`GET /changes` 与 `/changes/records` 的 `status` 同名不同义**：前者是投影（可能为发布包状态），后者是变更状态机词表，无字段区分。
7. **候选迁移表形同文档**：`save()` 用 `toCandidateStatus` 直接赋值，`assertCandidateTransition` 在 ① 内无调用点；任何依赖「非法迁移必被拒」的假设都不成立。
8. **`approval` 无 `(candidateId, actorId)` 唯一索引**：「同 actor 不可改判」只靠 `decide()` 读历史比对，并发两个请求可同时通过检查（`decide` 在事务内但**未加 `pessimistic_write`**，`read` 的 `lock` 参数未被 `decide` 打开）。
9. **`conformance-template` 端点无 schema 校验**：body 仅按 TS 类型取 `requestId`/`strategyId`，`strategyId` 直接决定 `sourceKind`，非法值会走到 `strategy_not_allowed` 而非 400 参数错误。
10. **`identity()`/`context()` 在控制器与 `agent-evolution.controller.ts` 各写一份**（`requestScope`/`commandContext`），改动需双改。
11. **`[推测]` `finish()` 的非幂等性**：失败路径里 `conversations.finish(...)` 抛错只 `logger.warn`，随后队列重试会**再次** `start()`（新 `executionId`）并再写一轮消息；注释说明这是「retry 是独立 run」的设计意图，但会话数会随重试线性增长。
12. **`[推测]` `awaitingDataset` 的静默停留**：缺 `golden_replay` 数据集时 `process()` 直接 return，`job` 已被置 `completed`、`status` 停在 `testing`；此时没有超时告警，前端只能看到「卡在评估中」。
13. **`[推测]` 内存分页的规模风险**：`GET /changes` 每次全量加载租户/组织下全部变更与发布包，未在测试中验证过万级规模的表现。

## 11. 设计维度分析

**「记录不可变」 vs 「状态可覆写」**：① 对证据、基线、候选 artifact、评估结果、审批内容都设了不可变闸（`immutable_request_changed` / `immutable_candidate_changed` / `immutable_evaluation_changed` / `immutable_approval_changed`），但**状态列本身是可覆写的**——`save()` 直接写 `status`，`toCandidateStatus`/`fromCandidateStatus` 双向翻译。结果是「事实字段只增不改、状态字段随写随变」，读侧必须同时看状态与 stages（`stage` 是第二套进度表达）。

**「异步推进」 vs 「同步可见性」**：推进被放进队列（可重试、并发 2），但为了让读侧看到进度，`process()` 刻意把 running 阶段**先提交再调外部 provider**，并额外写一条 `executionConversation` 引用。代价是一次推进变成 4 次事务提交，换来「卡在哪一步」这件事在库里可读。

**「投影层薄」 vs 「词表三套」**：投影是纯函数、不落库，但承载了 candidate / release / change 三套状态词表的归一与 `capabilities` 建议位。这是一个**把复杂度留在读侧、把可维护性让给写侧**的选择：写侧可以自由演进各阶段状态，代价是任何新状态都必须在 `lifecycleRecord` 的优先级链里显式落位，否则会掉进 `preparing` 兜底。

**「会话真实」 vs 「结论可靠」**：转录走真实 ChatKit（CommandBus 写 `ChatConversation`/`ChatMessage`/`XpertAgentExecution`），但整条链路用 `recordConversation` 包住并吞异常。这是明确的取舍：**可观测性不参与正确性**，代价是「会话完整」不能当作「状态已推进」的证据。

## 12. 结论

实现上，本子域可以概括为「**一个协调器 + 一张分表映射 + 一个纯投影 + 一条尽力而为的转录**」。`EvolutionChangeService` 独占阶段推进，且每次推进都在事务内重读状态后再决定是否继续；`EvolutionChangeStore` 把契约对象拆进 5 张表（proposal 承载请求身份，candidate/evaluation/approval/release 各自权威），用「行守卫 + 不可变闸 + 三层去重」把重复提交与内容篡改挡在写侧；`lifecycleRecord` 把三套状态词表压成 `phase`/`publicationStatus`/`effectStatus` 三个可读字段；转录链路的全部异常都被吞掉，明确声明不参与正确性判定。

新增能力时应继续沿用这套骨架：提交一律经 `prepare`（不要绕过 schema 与策略冻结直写 proposal）、阶段推进一律经 `process`（不要在事务外自行写 candidate/evaluation）、读侧一律经 `lifecycleRecord`（不要在控制器里手拼状态）。需要重点防守四处：**两套摘要算法**（`digest` vs `hashEvolutionValue` 不可互换）、**`changeError` 的 400 语义**（缺 404/409 会导致前端无法区分失败类型）、**`decide()` 未加行锁**（应用层「同 actor 不可改判」在并发下不封闭）、以及 **`GET /changes` 的全量内存分页**（变更与发布包增长后是最先劣化的读路径）。
