## §1 HTTP 入口索引

全局前缀 `api`；本子专家真实路由＝`EvolutionLifecycleController`（`@Controller('changes')` ＋ 类级 `@UseGuards(PermissionGuard)`），最终前缀 `/api/agent-evolution/changes`。**8 条逐条**：

| # | 方法 | 路径 | 权限位 | 用途 | 同步 / 入队 |
|---|---|---|---|---|---|
| 1 | POST | `/changes` | `EVOLUTION_MANAGE` | `evolutionSubmissionSchema.safeParse` 失败即 `invalid_strategy_submission`；成功后 `{...parsed.data, ...identity()}` → `changes.prepare()` | **入队型**（写 `proposal` ＋ 投递 `change_preparation`，返回变更记录） |
| 2 | POST | `/changes/conformance-template` | `EVOLUTION_MANAGE` ＋ 夹具门禁 | body 仅 `{requestId, strategyId}`（无 schema 校验）；`fixture.fixtureInput()` 装配输入后复用 `prepare()` | **入队型**（同上） |
| 3 | GET | `/changes` | `EVOLUTION_VIEW｜XPERT_EDIT` | `lifecycle.list()`：投影 ＋ `publicationStatus`/`search` 过滤 ＋ 内存分页 | 同步读 |
| 4 | GET | `/changes/records` | `EVOLUTION_VIEW｜XPERT_EDIT` | `@Query('targetId')` → `changes.list()`（**契约原文，绕过投影**） | 同步读 |
| 5 | GET | `/changes/:id` | `EVOLUTION_VIEW｜XPERT_EDIT` | `lifecycle.get()`：单条投影（读 `PUB-<id>` 单行发布包） | 同步读 |
| 6 | POST | `/changes/:id/evaluations` | `EVOLUTION_MANAGE` | body `{datasetSnapshotIds?}` → `lifecycle.evaluate()`：冻结映射 ＋ 触发 `process()`（评估执行在 ②） | **同步返回投影**（内部同步跑 provider） |
| 7 | POST | `/changes/:id/decisions` | `EVOLUTION_MANAGE` | body `{candidateHash, evaluationRunId, decision, reason}` → 三元组绑定 ＋ 写审批 | 同步 |
| 8 | POST | `/changes/:id/publication` | `EVOLUTION_MANAGE` | 无 body → 状态机前置 ＋ 第二事务发货（`staged_rollout` 转 ② 的 `package()`） | 同步（返回投影；部署仍由 ② 的队列承载） |

**路由顺序敏感点**：`@Get('records')` 必须声明在 `@Get(':id')` **之前**，否则 `/changes/records` 会被 `:id` 吞掉——该控制器**无 spec 守护**。**上下文归一**：`identity()` 只返回 `{tenantId, organizationId}`（**只含两个键**，不得把 actor 字段透传给实体查询）；`context()` 追加 `actorId`/`actorRole`（缺省 `'human_operator'`）/`actorRoleName`/`approvalAuthority`/`actorType: 'human'`。

**记录侧关联端点（入口位于 `AgentEvolutionController`，语义归本子专家的 8 张表）**：

| 方法 | 路径 | 权限位 | 用途 |

| PATCH | `/learning-events/:eventId/review` | `EVOLUTION_MANAGE` | 唯一人工分类入口（`pending｜ignored｜golden`） |

| GET / POST | `/candidates` | 读两位 / 写 `EVOLUTION_MANAGE` | 候选分页 / 构建（依赖 `proposalRevision`） |

## §2 服务契约

| 服务 / 关键方法 | 用途 | 参数行为语义 · 异常 |
|---|---|---|
| `EvolutionChangeService.prepare(input, options?)` | 变更提交（**唯一入口**） | `checkIdentity` → `strategies.freeze()`；feedback 模式对学习事件做「数量/主体/`sameScope`/`qualifiesLearning`」四重门并重算 evidence **逐条对账**；写 `Proposal`（`proposalId = PROP-<changeId>`、`revision: 1`）＋ `job`；400 `invalid_strategy_submission` / `strategy_not_allowed` / `learning_evidence_gate_failed` / `learning_evidence_snapshot_mismatch` |
| `EvolutionChangeService.build(input)` · `evaluate(input)` · `process(input)` | 候选构建 / 评估触发 / 幂等推进 | `build` 已存在候选即做 digest 比对（`immutable_candidate_changed`）；`evaluate` 已审批或已有回执即拒（`approved_candidate_immutable`）＋`evaluation_snapshot_mismatch`；`process` 非可推进状态即收尾残留 job 并返回，推进时**先提交 running 阶段再调外部 provider** |
| `EvolutionChangeService.decide(input)` | 人工审批 | 必须人主体 ＋ `reason` 非空；候选哈希 / `evaluationRunId` / `strategyHash` 三绑定；同 actor 同判返回原变更、改判拒；400 `review_snapshot_mismatch` / `immutable_approval_changed` / `review_reason_required` / `not_reviewable` |
| `EvolutionChangeService.publish(input)` | 发布意图 | 先推 `publishing` 再第二事务发货；`staged_rollout` → ② 的 `package()`；`version_write` → `versionPublisher.publish` 并校验回执三元组；已有 `receipt` 直接 return；400 `publication_not_in_strategy` / `publication_snapshot_mismatch` / `write_receipt_mismatch` / `identity_mismatch` |
| `EvolutionChangeStore.create / read / assemble / save / saveEvaluation / proposal / changeIdentity` | 分表双向映射与去重 | `create` 用 `insert().orIgnore()` 命中 `UX_evolution_proposal_request` 后复读 ＋ 7 字段 `changeDigest` 比对；`assemble` 跨五表拼装（**从不整表持久化**）；`save` 五段各自带不可变闸；`read(..., lock)` 可加 `pessimistic_write`，命中失败 `change_not_found` |
| `EvolutionChangeProcessor.handle(job, context)` | 异步推进消费者 | `@PluginJobProcessor({...CHANGE_QUEUE, concurrency: 2})`；先校验 `context.tenantId/organizationId` ＋ `job.data.changeId` 否则 `invalid_job_identity`；**无本地重试**，异常 `change_preparation_failed` 后重抛交队列 |
| `change.validation.validateChangeInput / validateChangeEvaluation` | 业务不变量校验 | 提交层：scope key 与租户/组织一致、`evidence` 非空且种类在白名单、`strategy.inputs` 含 `sourceKind`；评估层：快照绑定与 check 唯一性，违规 `inconsistent_evaluation_gate` |
| `submission.schema.evolutionSubmissionSchema` | 提交的**结构**边界（`zod/v3`） | 全对象 `.strict()`；`executionContext.input ≤ 100000`、`title/requestId ≤ 200`、`evidence/learningEventIds ≤ 100`、`scope.type ∈ {tenant, organization, workspace, project}`；服务层只复用 `executionContext` 子 schema |
| `EvolutionStrategyService.freeze / current / validateStrategy / qualifiesLearning / initialStages / setStage` | 策略快照与阶段 | `freeze` 出 `EvolutionStrategySnapshot` ＋ `hash`（`structuredClone`）；`current()` 做陈旧检测（漂移即 `strategy_snapshot_stale`）；`qualifiesLearning` 决定 event_cluster 是否 `proposal_ready` |
| `EvolutionLifecycleService.list / get / evaluate / decide / publish` | HTTP 投影层 | 读一律经 `lifecycleRecord()`；写代理 `EvolutionChangeService` 后**回读投影**；`pageSize` 上限 200、默认 20；`GET /changes` 为**全量加载 ＋ 内存分页** |
| `lifecycleRecord(change, release?)` | 纯函数投影（不落库） | `release.status` **优先**于 `change.status`；派生 `phase` / `publicationStatus` / `effectStatus` / `stages` 重写 / `capabilities` 四位；`release` 存在时 `capabilities.publish` 恒 false |
| `EvolutionExecutionConversationService.validate / start / drafted / finish` | 会话与执行账本联动 | `validate` 经 `ModuleRef` 取 `PublishedXpertAccessService` 与 `XpertProjectAccessService.assertCanUseXpert`，失败即抛且**不建任何记录**；`conversationId/threadId` 由 `sha256('evolution-chat:<changeId>:<part>')` 确定派生，`executionId` 每次 `randomUUID()` |
| `changeError(code: string)` | 变更域统一错误信道 | 恒抛 `BadRequestException`（i18n `server-ai:Error.EvolutionChange`，`defaultValue = 'Evolution cannot proceed: {{code}}'`）；**调用方应按 code 解析** |

**与 ② 的窄接口（唯三）**：`EvolutionEvaluationExecutor.run(operation, target, manager)`、`EvolutionPublicationExecutor.package(manager, operation)`、`AgentEvolutionQualityGovernanceService.reviewHumanApprovals(riskLevel, approvals)`；**② 不反向调用 `changes/*`**。

## §3 投影读模型契约

**`EvolutionLifecycleRecord`（`GET /changes`、`GET /changes/:id` 与三动作响应同形）**：

| 字段 | 取值 / 派生规则 |
|---|---|
| `status` | `release?.status ?? change.status`——**发布包状态优先**；变更词表为 `preparing｜testing｜test_failed｜pending_approval｜approved｜publishing｜published｜rejected｜stale｜failed` |
| `publicationStatus` | 优先级链 `closed(rejected/rolled_back/superseded) > blocked(failed/stale/test_failed/paused) > published > publishing > review > preparing` |
| `effectStatus` | 三态 `active｜partial｜pending`；`release.active → active`、`release.canary → partial`，否则取 `change.presentation?.effect?.status` 或按 `published && effect === 'activation'` 推导 |
| `phase` | 六态 `closed｜blocked｜effective｜publication｜review｜evaluation｜preparation` |
| `stages` | `publication` 在 published 时被**强制改写**为 `passed`；`effect` 按 `effectStatus` 映射 `passed｜running｜pending`；`evaluation` 阶段值可为 `not_applicable`（**不等于通过**） |
| `capabilities` | `{stagedRollout, evaluate, decide, publish}`——**建议位不是权限位**；`release` 存在时 `publish` 恒 false |

**分页与过滤**：`page ≥ 1`、`pageSize = min(200, max(1, pageSize))`（默认 20）；先按 `publicationStatus === query.status` 与 `title + targetId` 的 `toLowerCase().includes` 过滤，再按 `createdAt DESC` ＋ `id ASC` 排序后**内存分页**。

**`GET /changes/records`（契约原文读模型，绕过投影）**：`EvolutionChangeService.list()` → `assemble()`，`status` 为变更状态机词表（**与投影同名不同义**）；入参 `targetId`（控制器 `@Query`）＋ 标准分页（`normalizePage`：上限 **100**、默认 20、`sort ∈ createdAt|updatedAt|status`）。

**不可变与幂等（读侧可见的约束）**：`candidate` 的 `artifactHash` 与 definition digest 改动即 `immutable_candidate_changed`；`evaluation_run` 同 `runId` 内容不同即 `immutable_evaluation_changed`；`approval` 同 `approvalId` digest 不同即 `immutable_approval_changed`；`proposal` 命中 `requestId` 但 7 字段指纹不同即 `immutable_request_changed`。

章节来源：[lifecycle.projection.ts](file://packages/server-ai/src/agent-evolution/changes/lifecycle.projection.ts)（关键符号：lifecycleRecord / phase / publicationStatus / effectStatus / capabilities）、[lifecycle.service.ts](file://packages/server-ai/src/agent-evolution/changes/lifecycle.service.ts)（关键符号：EvolutionLifecycleService.list / get）、[evolution-store.helpers.ts](file://packages/server-ai/src/agent-evolution/application/evolution-store.helpers.ts)（关键符号：normalizePage）

## §4 示例

### ① 提交一个变更并读投影

```ts
// lifecycle.controller.ts（剪裁）：POST /changes → prepare；GET /changes → lifecycle.list
submit(@Body() body: unknown) {
    const parsed = evolutionSubmissionSchema.safeParse(body)
    if (!parsed.success) changeError('invalid_strategy_submission')
    return this.changes.prepare({ ...(parsed.data as Omit<SubmitEvolutionChange, 'tenantId' | 'organizationId'>), ...identity() })
}
list(@Query() query: EvolutionPageQuery) {
    return this.lifecycle.list(identity(), query)   // → { items, total, page, pageSize }
}
```

要点：`prepare()` 先 `strategies.freeze()` 冻结策略快照，feedback 模式还要重算 evidence 与入参**逐条对账**；只有本次真新建 `Proposal` 行时才会写 `job`（`EVOJOB-<changeId>`）并入队，重复提交复用同一作业标识重投递。推进后经 `GET /changes` 读投影即可看到 `phase` / `publicationStatus`。

### ② 提一个候选并审批

```ts
// governance 侧写入点最终收敛到 ① 的两个方法（剪裁）
await this.changes.build({ ...command })       // 候选 artifact 与 definition 双不可变
await this.changes.decide({ candidateHash, evaluationRunId, decision, reason })

// change.service.ts（剪裁）：三绑定 + 同 actor 语义
if (change.candidate.artifact.hash !== input.candidateHash) changeError('review_snapshot_mismatch')
if (change.evaluation.runId !== input.evaluationRunId) changeError('review_snapshot_mismatch')
if (change.evaluation.strategyHash !== strategy.hash) changeError('review_snapshot_mismatch')
```

要点：审批是**精确人工决策**——三元组任一不符即 `review_snapshot_mismatch`；同 actor 同判直接返回原变更（不写第二行），改判 `immutable_approval_changed`；终态由 ② 的 quorum 决定，「批准一次」不必然是终态（可能仍停在 `pending_approval`）。

### ③ 触发一次评估并读 job

```ts
// ① 的记录侧入口：POST /changes/:id/evaluations（同步返回投影）
await this.lifecycle.evaluate(context(), id, datasetSnapshotIds)
// ② 的入队型入口：POST /api/agent-evolution/evaluations（返回 EvolutionJob，不是评估结果）
@Permissions(AIPermissionsEnum.EVOLUTION_MANAGE)
enqueueEvaluation(@Body() body: EvaluateCandidateCommand) {
    return this.queue.enqueueEvaluation(commandContext(), body)
}

// 读 job 账本：GET /api/agent-evolution/jobs/:jobId（未命中返回 null 而非 404）
```

要点：两条路径语义不同——`/changes/:id/evaluations` 在 ① 侧**冻结 `datasetSnapshotIds` 并同步触发 `process()`**，返回生命周期投影；`/evaluations` 是**入队型**，HTTP 200 只代表受理，成败看 `GET /jobs/:jobId`（判据是 `queueJobId` 是否为 `null`，`errorCode` 是 `queue_enqueue_failed` 还是 `evolution_job_failed`）。评估执行器、闸门阈值与 `candidate_bundle` 落库属 ②。
