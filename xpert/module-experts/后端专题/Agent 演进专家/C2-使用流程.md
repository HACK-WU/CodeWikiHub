# C2 使用流程（Agent 演进专家）

> 面向调用方的 Recipe 手册。范围：`agent-evolution`（**44 非 spec `.ts` / 19 表 / 48 HTTP 端点**，HTTP 前缀 `/api/agent-evolution`；三个控制器 `AgentEvolutionController` 39 · `EvolutionLifecycleController` 8 · `EvolutionBaselineController` 1）。子域：① 变更与生命周期 ② 评估与发布。
> 准入口径：读 `EVOLUTION_VIEW | XPERT_EDIT`（**或**语义）、写 `EVOLUTION_MANAGE`、基线只读端点三位任一；服务层另有 `requireHuman`（`actorType==='agent'` 直接拒）与 `approvalAuthority==='administrator'`（角色名 `SUPER_ADMIN`/`ADMIN`）两层。
> **跨全篇最关键的一条口径：入队型端点返回 `EvolutionJob`，不是结果。** `install|shadow|canary|rollback` 与 `POST /evaluations` 的 HTTP 200 只代表「已受理」，成败要看 `GET /jobs/:jobId`；只有 `pause` 与 `activate` 是同步返回（发布包 / 新指针）。未被实现层证实处标 `[推测]`。

## Recipe 1 提交变更并读生命周期记录
- **业务目标**：提交一条变更（预算是「把能力/策略版本推进一格」），并在任何阶段用同一个读模型确认它到了哪一步。
- **调用顺序**：`POST /api/agent-evolution/changes`（`EVOLUTION_MANAGE`，body 经 `evolutionSubmissionSchema` 校验）→ `EvolutionChangeService.prepare`：`checkIdentity` → `strategies.freeze()` 冻结策略快照与 `hash` → 校验 `supportedScopes` 与 `validateChangeInput` → `executionContext` 存在时经 `ExecutionConversationService.validate` 做 xpert/项目准入 → 生成 `changeId = EVO-<uuid>`、`jobId = EVOJOB-<changeId>`、`evidenceHash`、`stages = initialStages(strategy.definition)` → 写 Proposal 行（`proposalId = PROP-<changeId>`、`revision: 1`）+ `job change_preparation` → 非 defer 时入队。读：`GET /changes`（`lifecycleRecord` 投影，`{items,total}`）、`GET /changes/records`（富变更）、`GET /changes/:id`（单条）。
- **时序边界**：`prepare` **只落 Proposal + job**，候选与评估由队列内的系统主体（`actorType: 'system'`）在后续阶段落库；`EvolutionChange` **永远不整表持久化**（文件头逐字：`EvolutionChange is assembled, never persisted whole.`），读变更必须跨 `proposal/candidate/evaluation_run/approval/release_package` 拼装。`/changes/records` 与 `/changes/:id` 的路由顺序由装饰器声明序决定（`records` 先声明），新增子路径必须放在 `/:id` 之前。
- **预期结果**：HTTP 返回 `EvolutionLifecycleRecord`（`phase` / `publicationStatus` / `effectStatus` 由投影派生，`release.status` 优先于 `change.status`），其中 `capabilities.{stagedRollout,evaluate,decide,publish}` 告知该变更此刻允许哪些下一步动作。
- **错误处理**：`.strict()` 契约下多余字段直接 400 `invalid_strategy_submission`；同 `requestId` 重放但内容不同 → `immutable_request_changed`；feedback 模式下学习事件数量/主体/新鲜度/脱敏四重门失败 → `learning_evidence_gate_failed`；事件重算 evidence 与输入对账不符 → `learning_evidence_snapshot_mismatch`；策略未命中目标描述符 → `strategy_not_allowed`；查询单条未命中 → `changeError('change_not_found')`。
- **真实代码示例**：
```http
POST /api/agent-evolution/changes
{ "strategyId": "...", "sourceKind": "learning_events", "scope": { "type": "organization", "key": "<orgId>" },
  "baseline": { "resourceId": "...", "version": "...", "hash": "..." }, "learningEventIds": ["EVT-..."],
  "candidateInput": { ... }, "datasetSnapshotIds": { "replay": "DSS-..." } }
GET  /api/agent-evolution/changes?page=1&pageSize=20
```

## Recipe 2 诊断与聚类看趋势
- **业务目标**：把散落的执行/反馈信号聚成「同一根因」的簇，判断哪些簇已具备提提案资格。
- **调用顺序**：外部运行时经 `ingestLearningEvent` 入账（`UQ(idempotencyKey)` 幂等）→ `PATCH /learning-events/:eventId/review` 做人工分类（`reviewStatus ∈ pending|ignored|golden`）→ `POST /diagnoses`（`EVOLUTION_MANAGE`，body 为事件 id 列表）→ `AgentEvolutionAnalystService.diagnose` 落 `EvolutionDiagnosis` + `EvolutionEventCluster` → 读 `GET /diagnoses`、`GET /clusters` 看趋势。
- **时序边界**：`diagnose` 先对入参事件 id **去重后按租户取行，数量不等即 400**；再次拒绝未脱敏的 confidential；按 `correctionSignature = hashEvolutionValue({targetId, scopeType, scopeKey, dimensions, decisionPoint, reasonCodes(sorted)})` 分组，每组产出一条诊断与一条簇（`caseCount = distinct subjectRef`）。同签名重入会**复用 `clusterId`**：并集 `eventIds`、`caseCount` 取 `max`——因此「簇」是累积对象，不是每次诊断的新行。
- **预期结果**：簇状态 `status = qualifiesLearning(...) ? 'proposal_ready' : 'collecting'`；**是否「可提提案」由策略阈值决定，不由事件数量单独决定**；`rootCause` 为 `repeated_correction_signature:<reasons>` 或 `unclassified_repeated_correction`，`confidence` 为组内均值。
- **错误处理**：空列表 → 400 `At least one Learning Event is required for diagnosis`；跨租户 → 400 `One or more Learning Events were not found in the current tenant scope`；未脱敏 confidential → 400 `Confidential Learning Events must be redacted before analysis`；策略不允许 → `strategy_not_allowed`；confidential 事件入账阶段即被拒（`Confidential learning events must be redacted before ingestion`）。
- **真实代码示例**：
```http
PATCH /api/agent-evolution/learning-events/EVT-123/review   { "reviewStatus": "golden" }
POST  /api/agent-evolution/diagnoses   { "learningEventIds": ["EVT-123","EVT-456"] }
GET   /api/agent-evolution/clusters?pageSize=50            # status=proposal_ready 才值得提提案
```
章节来源：[agent-evolution-analyst.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-analyst.service.ts)（关键符号：diagnose / correctionSignature / listClusters）、[agent-evolution-runtime.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-runtime.service.ts)（关键符号：ingestLearningEvent）、[strategy.service.ts](file://packages/server-ai/src/agent-evolution/changes/strategy.service.ts)（关键符号：qualifiesLearning）

## Recipe 3 从提案到候选与审批
- **业务目标**：把「业务侧改进意图」固化成提案，构建隔离候选，再收集人工审批票。
- **调用顺序**：`POST /proposals`（`governance.createProposal`，`requestId` 幂等）→ `POST /candidates`（`governance.buildCandidate`，依赖提案的 `proposalRevision`）→ `POST /candidates/:candidateId/approvals`（`governance.decideApproval`，单条人工审批）。读：`GET /proposals`（只认 `sourceKind='learning_events'`）、`GET /candidates`（可按策略 hash 过滤）。
- **时序边界**：候选一经存在**即不可换**——`decide`/`publish` 都以 `artifact.hash` 与调用方入参比对；跨版本重放 `POST /candidates` 会命中 `candidate_snapshot_mismatch`。审批写入前先按三元组过滤（`candidateHash` + `evaluationRunId` + `strategyHash`），**同 actor 改判即 `immutable_approval_changed`**（同 actor 同判则原样返回，天然幂等）。`POST /diagnoses`/`POST /proposals` 不互为替代：诊断只产出簇，提案必须显式调用。
- **预期结果**：提案行 `revision` 恒为 1（重复 `requestId` 走 `.orIgnore()` 后复读比对）；候选 `artifact.hash` 即后续全链的 `candidateHash`；审批行记录 `approvalAuthority`（administrator/standard）与 `actorRoleName`，是否凑齐 quorum 由 `reviewHumanApprovals` 决定（R3/R4 → 3 票，其余 2 票；**有 1 名管理员审批即直接放行**）。
- **错误处理**：agent 主体提 R4 → `agent_proposal_risk_forbidden`；无生产基线 → `production_baseline_required`；基线不符 → `candidate_baseline_mismatch`；变更不存在 → `change_not_found`；候选已存在且内容不同 → `immutable_candidate_changed`；agent 提交审批 → 400 `Agent identity cannot satisfy a human approval decision`。
- **真实代码示例**：
```http
POST /api/agent-evolution/proposals   { "targetId": "...", "requestId": "REQ-001", "proposalRevision": 1, ... }
POST /api/agent-evolution/candidates  { "changeId": "EVO-...", "proposalRevision": 1 }
POST /api/agent-evolution/candidates/<candidateId>/approvals  { "decision": "approved", "evaluationRunId": "ASSESS-..." }
```
章节来源：[agent-evolution-governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts)（关键符号：createProposal / buildCandidate / decideApproval）、[change.service.ts](file://packages/server-ai/src/agent-evolution/changes/change.service.ts)（关键符号：EvolutionChangeService.decide）、[agent-evolution-quality-governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-quality-governance.service.ts)（关键符号：requiredHumanApprovals / reviewHumanApprovals）

## Recipe 4 数据集快照与评估运行
- **业务目标**：为 golden replay 准备可用例集快照，跑评估并读懂 `gatePassed`。
- **调用顺序**：`POST /datasets`（`governance.createDatasetSnapshot`：要求 provider 具备 `replayEvaluator` + `capabilities.replay`、scope 受支持、用例 `(caseId, revision)` 唯一）→ `POST /changes/:id/evaluations`（`lifecycle.evaluate`，可带 `datasetSnapshotIds`，用于**冻结数据集映射**）或 `POST /evaluations`（队列化，返回 `EvolutionJob`）→ 读 `GET /evaluations`（含 `gatePassed`）。
- **时序边界**：`evaluate` 在事务内冻结数据集映射，已存在评估且映射变化即 `evaluation_snapshot_mismatch`；无评估则把状态推 `testing`。`golden_replay` 走内置 `replay()`（基线与候选各建一个 `executionMode:'replay'` 的能力束，逐 case `randomSeed: 42`/`repeatIndex: 0` 保证可复现），其余步骤走 `target.checkEvaluator.evaluate`。落库侧 `saveEvaluation` 以「同 runId 同内容」幂等，**写后不可改**。**审批后不可再评估**：`evaluate` 前置发现已审批即拒绝。
- **预期结果**：`evaluation_run.status` 只有 `passed|failed`；`gatePassed` 是实体上的**冗余布尔列**，恒等于 `value.gate.passed`（staged 路径）或 `value.result.passed`（version_write 路径），供 SQL 侧直接筛。replay 路径另返回一条 `ASSESS-<runId>` 的公共评估记录（`checks` 只含一条阻塞性 `replay-gate`）。**无评估步骤时 `assessment='not_applicable'`，绝不可当通过**（源码逐字：`an omitted assessment is never a passing test`）。
- **错误处理**：缺快照 → `evaluation_dataset_required`；快照 `targetId`/scope 不一致 → `evaluation_snapshot_mismatch`；基线哈希不符 → `candidate_baseline_mismatch`；步骤不在策略内 → `evaluation_not_in_strategy`；内容不同重放 → `immutable_evaluation_changed`；用例问题 → 400 `Golden Dataset must contain at least one case` / `Golden Dataset contains duplicate cases` / `Target '<id>' does not support Golden Replay`；队列不可用 → 503 `Managed Queue is unavailable`。
- **真实代码示例**：
```http
POST /api/agent-evolution/datasets   { "targetId": "...", "cases": [ { "caseId": "c1", "revision": 1, "evidenceRef": "..." } ], ... }
POST /api/agent-evolution/changes/EVO-.../evaluations   { "datasetSnapshotIds": { "replay": "DSS-..." } }
GET  /api/agent-evolution/evaluations?pageSize=50        # 只看 gatePassed=true 的 run 才可继续
```
章节来源：[evaluation-executor.service.ts](file://packages/server-ai/src/agent-evolution/changes/evaluation-executor.service.ts)（关键符号：EvolutionEvaluationExecutor.run / replay / not_applicable）、[change.service.ts](file://packages/server-ai/src/agent-evolution/changes/change.service.ts)（关键符号：EvolutionChangeService.evaluate）、[agent-evolution-governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts)（关键符号：createDatasetSnapshot）

## Recipe 5 闸门策略与人工审批门
- **业务目标**：知道「为什么这道闸门过不去」，并能区分「数据没到」与「人没到」两类阻塞。
- **阈值来源与 env**：数值来源**不是运行时配置**，而是一张写死的表 —— `STANDARD_GATE_POLICY` = shadow `100 样本/72h`、canary `30/24h`、productionCanary `30/24h`、experience `100/168h`。仅在**非生产**且 `AGENT_EVOLUTION_GATE_PROFILE=manual_test`（trim + 忽略大小写）时切 `manual_test` 档，六个阈值可被 `AGENT_EVOLUTION_TEST_{SHADOW,CANARY,PRODUCTION,EXPERIENCE}_MIN_{SAMPLES,HOURS}` 覆盖（缺省 `1 / 0`）。生产环境该变量**被静默忽略**；`requestedShadowMinimumSamples` 只能**抬高**（`Math.max(STANDARD, requested)`）。注意生产判定口径：闸门策略用 `environment.production || process.env.NODE_ENV === 'production'`，而夹具门禁用 `environment.production` 单条件。
- **调用顺序与边界**：阈值在**建模发布包时冻结**——`EvolutionPublicationExecutor.package()` 调用 `snapshot()` 把 `gatePolicy` 写入 `ReleasePackage`；此后所有判定走 `forRelease(release)` 只读冻结值，缺失即抛 `Release gate policy was not frozen`。人工审批门由 `decide` 串联：先判 `evaluation.passed`（否则 `tests_must_pass`），再 `reviewHumanApprovals(riskLevel, [...历史, 本次])` 决定终态是 `approved` 还是继续 `pending_approval`；通过条件是 `hasAdministratorApproval` **直接放行**，否则 `distinct actorId` 与 `distinct actorRole` **双达标**（同一人用两个角色投两票无效）。
- **预期结果**：数据闸门给出 `decision: 'reject' | 'promote'` 与逐条 `blockingReasons`（`golden_dataset_below_50_cases` / `affected_slice_below_20_cases` / `high_risk_slice_below_10_cases` / `severe_errors_present` / `candidate_does_not_improve_baseline`）；审批门给出「还差几票」。两层职责分离：低层只判数据、高层只判人。
- **错误处理**：`AgentEvolutionShadowGateNotSatisfied` / `AgentEvolutionCanaryGateNotSatisfied` / `AgentEvolutionProductionGateNotSatisfied` / `AgentEvolutionExperienceGate*`（均带 `hours`/`samples` 插值）；`manual_test` 档下审批人非 administrator → `manual_test_administrator_required`。**改 env 不影响已建的发布包**——这是结构性的，不是策略。
- **真实代码示例**：
```ts
// 冻结（建包时一次性）
gatePolicy = releaseGatePolicy.snapshot(requestedShadowMinimumSamples)
// 判定（之后永远读冻结值）
const policy = this.releaseGatePolicy.forRelease(release)   // 未冻结 → 'Release gate policy was not frozen'
```
章节来源：[agent-evolution-release-gate-policy.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-release-gate-policy.service.ts)（关键符号：STANDARD_GATE_POLICY / MANUAL_TEST_DEFAULTS / resolveEvolutionReleaseGatePolicy / forRelease）、[quality-governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-quality-governance.service.ts)（关键符号：reviewGoldenReplay / reviewHumanApprovals）、[publication-executor.service.ts](file://packages/server-ai/src/agent-evolution/changes/publication-executor.service.ts)（关键符号：EvolutionPublicationExecutor.package / gatePolicy 冻结）

## Recipe 6 发布包与部署阶梯
- **业务目标**：把已审批的候选变成发布包，再按不可跳档的阶梯放量到生产。
- **调用顺序**：`POST /release-packages`（`governance.createReleasePackage`，冻结 `gatePolicy` 并产出 `PUB-<changeId>`）→ `POST /releases/:id/install` → `POST /releases/:id/shadow` → `POST /releases/:id/canary`（body `StartDeploymentRequest`，`canaryPercent ∈ {5,25,50}`）→ `POST /releases/:id/activate`。可选 `POST /releases/:id/pause`。
- **时序边界**：**四级硬前置**——`install` 要求 `release.status === 'approved'`；`shadow` 只允许 `installed | paused`；`canary` 首档必须 5%（`The first Canary stage must be 5%`），扩档由 `latest.canaryPercent` 推导 `expectedNext`（5→25→50，**跳档即 400**），且从 shadow 起需过影子门槛、扩档需过金丝雀门槛；`activate` 要求 `canaryPercent === 50` + 生产阈值 + **指针仍等于 `release.rollbackVersionId`**。队列化边界：`install|shadow|canary|rollback` 入队返回 `EvolutionJob`，`pause|activate` 同步返回（发布包 / 新指针）。
- **预期结果**：`release_package.status` 沿 `draft → pending_approval → approved → installed → shadow → canary → active` 前进（`paused` 是唯一可双向的中间态）；`activate` 成功后 `activatePointerCas` 切指针并建 `channel:'production'`（100%）部署行；每步动作都会写入 `agent_evolution_audit_event`。
- **错误处理**：作业内 400 `Only an approved Release Package can be installed` / `Target does not support Shadow` / `Shadow can start only from installed or paused` / `Canary percent must be 5, 25 or 50` / `Canary can start only after Shadow or resume from paused` / `AgentEvolutionShadowGateNotSatisfied` / `AgentEvolutionCanaryGateNotSatisfied`；激活侧 `Production activation requires Canary` / `AgentEvolutionProductionGateNotSatisfied` / `Production pointer no longer matches the approved rollback version`；建包侧 `publication_not_in_strategy` / `publication_snapshot_mismatch` / `identity_mismatch`；**HTTP 200 不代表动作成功**——失败要先经 `errorCode='queue_enqueue_failed'` 或 worker 侧 `errorCode='evolution_job_failed'` 暴露。
- **真实代码示例**：
```http
POST /api/agent-evolution/release-packages          # → PUB-<changeId>，gatePolicy 冻结
POST /api/agent-evolution/releases/PUB-.../install  # → EvolutionJob
POST /api/agent-evolution/releases/PUB-.../shadow   # → EvolutionJob
POST /api/agent-evolution/releases/PUB-.../canary   { "canaryPercent": 5 }   # 5 → 25 → 50
POST /api/agent-evolution/releases/PUB-.../activate # 同步 → 新 ActiveCapabilityPointer
```

## Recipe 7 金丝雀一次性覆盖与回落
- **业务目标**：在生产放量前，让某个指定主体（`subjectKey`）**只被强制路由一次**到候选版本，用于人工验收；之后自动回到确定性路由。
- **调用顺序**：`POST /releases/:releasePackageId/canary-test-overrides`（`EVOLUTION_MANAGE`）→ `governance.createCanaryTestOverride`（写 `activeKey`）→ 消费方调用 `POST /capability-executions/resolve` → `resolveExecutionPlan` 内 `consumeCanaryTestOverride` → 读 `GET /releases/:id/canary-test-overrides` 审计。
- **时序边界（四个 AND 才可创建）**：① 调用者是人（`requireHuman`）；② `approvalAuthority === 'administrator'`；③ 发布包冻结的 `gatePolicy.profile === 'manual_test'` **且**当前进程 `manualTestProfileEnabled()`；④ release 处于 `canary` 且存在 `channel:'canary' && status:'canary' && !completedAt` 的活跃部署。参数：`subjectKey ≤ 200`、`reason ≤ 500`、`expiresInMinutes ∈ [1,120]`（缺省 **30**）。消费在单事务内：先按 `status:'consumed'` 查重试，`consumedByExecutionId === executionId` 即返回旧结果；否则 `pessimistic_write` 锁 pending 行，过期翻 `expired` 返回 null，有效则翻 `consumed` + 记 `consumedAt`/`consumedByExecutionId` + 追加审计。
- **预期结果（一次性与回落）**：一次性由 `UQ(activeKey)`（`sha256(tenant:org:deploymentId:subjectKey)`）物理保证——同主体同部署至多一条活跃覆盖，且**发现活跃覆盖直接返回旧值、不续期**。回落判据源码逐字：`!consumedOverride && !deterministicSelection → continue`，即覆盖只对「该 `executionId` 的那一次解析」生效，之后同一 `subjectKey` 回落到 `deterministicPercent = sha256(deploymentId:subjectKey) → [0,100)` 与 `canaryPercent` 的比较。命中覆盖时分配项带 `selectionReason: 'manual_test_override'` 与 `manualTestOverrideId`，响应体另有 `manualTestOverrides[]` 供消费方审计。**指标口径**：覆盖是**在线路由强插**，与 golden replay（评估阶段的离线复现，同 seed、同 bundle）**互不相关**，两者不可互相解释。
- **错误处理**：404 `Release Package was not found`；400 `AgentEvolutionCanaryTestOverrideRequiresAdministrator` / `…RequiresManualTestProfile` / `…RequiresCanary` / `…InvalidSubject` / `…InvalidReason` / `…InvalidExpiry` / `…AlreadyPending`。注意 `listCanaryTestOverrides` 与 `getDashboard` 会**在读路径把过期 pending 就地翻 `expired`**（读路径写库，且该翻转不写审计）。
- **真实代码示例**：
```http
POST /api/agent-evolution/releases/PUB-.../canary-test-overrides
{ "subjectKey": "user-42", "reason": "manual acceptance", "expiresInMinutes": 30 }
POST /api/agent-evolution/capability-executions/resolve
{ "targetIds": ["..."], "subjectKey": "user-42", "executionId": "EXE-..." }   # 本次强制命中；下次回落
```

## Recipe 8 回滚
- **业务目标**：把生产指针从当前候选版本退回该发布包的 `rollbackVersionId`（通常是基线版本）。
- **调用顺序**：`POST /releases/:id/rollback`（`EVOLUTION_MANAGE`，入队）→ `AgentEvolutionGovernanceService.rollbackProduction`：拒绝 agent 主体 → `releaseOperationContext(...)` 取 release/provider → 校验 `capabilities.rollback` → 校验**指针 `activeVersionId === release.targetVersionId`** → `releaseProvider.rollback` → `rollbackPointerCas` → 审计。
- **时序边界**：`rollbackPointerCas` 在一个事务内以 `revision + activeVersionId` 为条件 UPDATE，`affected !== 1` 即抛 `Active Pointer CAS conflict`（普通 `Error`，表现为 5xx 而非 409）；成功后 release 状态与指针 `revision` **同时前推**。`rolled_back` 在迁移表中是**终态**（`rolled_back: []`）——**回不到原 canary 档，只能重新走 `install`**；`paused → shadow|canary` 是唯一可回退的中间态路径。
- **预期结果**：指针 `activeVersionId` 翻回 `rollbackVersionId`，release 落 `rolled_back`，审计 `action` 记录 CAS 结果；`GET /active-pointers` 可核对最终指针。
- **错误处理**：agent 主体 → 400 `Agents cannot initiate Production rollback`；provider 无能力 → `Target does not support rollback`；该发布包不是当前生产版本 → `Release is not the active Production version`；指针并发 → `Active Pointer CAS conflict`；非法迁移 → `Illegal release transition: <from> -> <to>`。
- **真实代码示例**：
```http
GET  /api/agent-evolution/active-pointers?pageSize=20     # 先确认 activeVersionId == release.targetVersionId
POST /api/agent-evolution/releases/PUB-.../rollback       # → EvolutionJob
```
章节来源：[agent-evolution-governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts)（关键符号：rollbackProduction / releaseOperationContext）、[evolution-runtime.store.ts](file://packages/server-ai/src/agent-evolution/application/evolution-runtime.store.ts)（关键符号：rollbackPointerCas / Active Pointer CAS conflict）、[evolution-state.ts](file://packages/server-ai/src/agent-evolution/domain/evolution-state.ts)（关键符号：RELEASE_TRANSITIONS 的 `rolled_back: []`）

## Recipe 9 观测回流与经验沉淀
- **业务目标**：把生产/影子/金丝雀的真实运行结果送回闸门，并在稳定达标后沉淀一条可检索的经验。
- **调用顺序**：**观测入账没有 HTTP 端点**——由外部运行时经运行时能力 `recordRuntimeObservation` 回流（`observationId` 缺省 `OBS-<uuid>`）；本域只提供只读 `GET /runtime-observations`。经验由人触发：`POST /experiences`（`EVOLUTION_MANAGE`）→ `governance.createExperience`；读 `GET /experiences`。
- **时序边界**：`saveRuntimeObservation` 单事务内两步——按 `observationId` 去重（重复直接返回旧值，不重复累加）→ 对 deployments 行加 `pessimistic_write` 锁，累加 `sampleCount`、滚动 `candidateAccuracy`、`severeErrors`、`p95LatencyMs = max(prev, latencyMs)`（**单调不减**）、`averageCost` 按样本数加权，并把单条观测追加进 `observations[]`。**`severeError === true` 且 release 处于 `shadow|canary` 时自动暂停**（`assertReleaseTransition(status,'paused')` 通过则翻 `paused`，审计 `deployment.auto_paused`，主体为系统 `actorId: 'agent-evolution-runtime'`/`actorRole: 'system_safety_guard'`）——这是 shadow/canary **唯一由数据触发的状态迁移**，`active` 不会被自动降级。
- **预期结果**：经验行的前置 = 人主体 + release 为 `active` + 冻结 `gatePolicy` 存在 + 存在 `channel:'production' && status:'active'` 部署且 `sampleCount ≥ experienceMinimumSamples`、`severeErrors === 0`、时长达 `experienceMinimumDurationHours`，并回查 `change.evaluation.runId === release.evaluationRunId` 且 `passed`。产出 `experienceId = EXP-<uuid>`、`status: 'active'`，`evidence` 内含生产观测数与稳定天数——**它只是「已稳定」的留档，不改变任何指针**。闭环在本仓**只有数据形状**：`experience` 与 `learning_event` 之间无代码连线（`[推测]`：回流到下一轮学习需由外部域实现）。
- **错误处理**：观测阶段——`deploymentId` 为空时**只入观测表、不累加统计**（静默跳过）；闸门失败时生产闸门错误（`EvolutionExperienceGate*`）；评估不一致 → `Release strategy assessment does not match`；解析侧 404 `Production pointer for '<targetId>' was not found`（无生产指针即无解析结果）。
- **真实代码示例**：
```ts
// 外部运行时（运行时能力 token，非 HTTP）
await runtime.recordRuntimeObservation({ observationId: 'OBS-...', targetId, deploymentId,
  executionId: 'EXE-...', severeError: false, latencyMs: 820, cost: 0.013, success: true })
```

## Recipe 10 job 轮询与取消
- **业务目标**：正确判断一个异步动作到底成没成，并知道「取消」在这个域里意味着什么。
- **调用顺序**：入队型端点返回 `EvolutionJob`（`jobId = EVOJOB-<uuid>`）→ 轮询 `GET /jobs/:jobId`（`EVOLUTION_VIEW | XPERT_EDIT`，读 `agent_evolution_job` 账本，只回 `value` JSON 全量，含 `status`/`queueJobId`/`errorCode`/`startedAt`/`completedAt`）。
- **时序边界**：入队顺序是「**先落 job 账本再投递**」——写 `EvolutionJob{status:'queued'}` → `queue.enqueue({attempts: 3, backoffMs: 1000, ...})` → 回写 `queueJobId`；投递失败则把 job 直接置 `failed` 并写 `errorCode: 'queue_enqueue_failed'` 后抛出。worker 侧 `handle` 先推 `running`（记 `startedAt`），成功 `completed`（记 `completedAt`），异常写 `errorCode: 'evolution_job_failed'` + `errorMessage` 后**重抛**交给队列做 3 次重试。**未命中返回 `null`（HTTP 200）而不是 404** ——「查不到」与「已删除」必须区分。
- **预期结果**：契约 `EvolutionJobStatus = 'queued' | 'running' | 'completed' | 'failed' | 'cancelled'`；实写路径为 `queued → running → completed | failed`。**没有任何「取消 job」的 HTTP 入口**：`cancelled` 只能由运维直接改账本产生。轮询窗口与应用超时无关——前端 `waitForJob` 为 60×1s（`[推测]`：该数字来自实现层对前端行为的转述）。
- **错误处理**：503 `Managed Queue is unavailable`（未注入 `MANAGED_QUEUE_SERVICE_TOKEN`）；`MANAGED_QUEUE_AUTORUN=false` 或 `MANAGED_QUEUE_PREFIX` 两侧不一致时，端点仍返回 job 但**永远停在 `queued`**；`queueJobId` 为 `null` 说明入队即失败。**`job.status` 口径提醒**：`change.service.process` 的补偿分支判断 `['pending','queued','running']`，而契约**不存在 `pending`**（死分支/跨实现漂移）——合法状态以契约枚举为准。
- **真实代码示例**：
```http
GET /api/agent-evolution/jobs/EVOJOB-0f7c...      # → EvolutionJob | null（HTTP 200）
# 判读顺序：status → queueJobId → errorCode（queue_enqueue_failed / evolution_job_failed）
```
章节来源：[agent-evolution-queue.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-queue.service.ts)（关键符号：enqueue / getJob / queue_enqueue_failed）、[agent-evolution-queue.processor.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-queue.processor.ts)（关键符号：handle / evolution_job_failed）、[governance.ts](file://packages/contracts/src/ai/evolution/governance.ts)（关键符号：EvolutionJobStatus）

## Recipe 11 排障合集
- **业务目标**：五类高频症状各落到**唯一判据**与处置动作，避免按症状猜测。
- **调用顺序（排查链）**：
  1. **闸门恒不过**：判据是发布包内**冻结**的 `gatePolicy` 与 `ReleaseDeployment` 上的 `sampleCount`/`severeErrors`/`startedAt`；改 env 无效（`manual_test` 只在非生产生效）。处置：生产只能等真实样本/时长；测试环境**重建发布包**后再放开 `AGENT_EVOLUTION_GATE_PROFILE=manual_test`。
  2. **回滚被拒**：四条各查其一 —— agent 主体、provider `capabilities.rollback=false`、`Release is not the active Production version`（指针 `activeVersionId ≠ release.targetVersionId`）、`Active Pointer CAS conflict`。处置：先比对 `GET /active-pointers` 与 `GET /releases`；注意 `rolled_back` 是终态，只能重新 `install`。
  3. **job 卡 running**：worker 在 `updateJobStatus('running')` 之后崩溃（账本无补偿写入）。处置：依赖 `attempts: 3` 重试；长期悬挂需人工把账本置 `failed`（**无取消端点**）。
  4. **覆盖未回落**：确认 `expiresAt`（默认 30 分钟、上限 120）与 `status`；确认消费侧 `subjectKey` 与创建时一致；过期行**不会被删除**，只在读路径被翻 `expired`。若「永久命中」，先查是否有同 `activeKey` 的活跃行（创建时返回旧值、不续期）。
  5. **夹具 404**：`POST /simulations/conformance`、`POST /examples/conformance-field-mapping/run`、`POST /changes/conformance-template` 在生产且未设 `AGENT_EVOLUTION_ENABLE_CONFORMANCE=true` 时**抛 `NotFoundException`（与「不存在」不可区分）**——这是**预期行为**，不是路由缺失。
- **时序边界**：观测回流未发生则四道闸门**永远无法满足**（模块内 `@Cron`/`@Interval` **零命中**，无超时或补齐机制）；`/jobs/:jobId` 与 `/runtime-observations` 都是「无 TTL、无清理」的账本，历史行会长期存在。
- **预期结果 / 处置要点**：升级后「表不存在」优先怀疑 schema 同步（本域**无 SQL 迁移**，建表依赖实体同步或插件 schema 预检，`DB_SCHEMA_SYNC_MODE=external` 时 API 侧 `synchronize:false`）；转录/SSE 失败是**静默降级**（`logger.warn`），「前端没动画」不等于状态没变。
- **错误处理**：`changeError(code)` 恒抛 400，文案为 `Evolution cannot proceed: {{code}}`——**按 code 解析，不要匹配整句**；`*_snapshot_mismatch` 系列的语义统一是「读到的快照与你手上的不一致，请重载」。
- **真实代码示例**：
```http
GET /api/agent-evolution/active-pointers        # 回滚/激活类冲突的唯一事实
GET /api/agent-evolution/jobs/EVOJOB-...        # errorCode 决定是入队失败还是执行失败
GET /api/agent-evolution/audit-events           # 治理动作是否真的落过痕
```
