## 三、运行方式

```bash
# 1) 单文件（最常用；--runTestsByPath 要求路径精确）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/agent-evolution/changes/change.service.spec.ts

# 2) 多文件（一次导入同一个 jest 配置，避免重复启动成本）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/agent-evolution/application/agent-evolution.service.spec.ts \
                   packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.spec.ts

# 3) 整个域（按路径正则过滤）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --testPathPattern 'src/agent-evolution/'

# 4) 按用例名过滤（-t 命中 describe/it 标题，适合回归单个语义）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/agent-evolution/changes/change.service.spec.ts \
  -t 'freezes a request once'

node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/agent-evolution/application/agent-evolution-runtime.service.spec.ts \
  -t 'one-time Candidate override'

# 5) Nx 方式（project.json 的 test target 用 @nx/jest:jest）
corepack pnpm exec nx run server-ai:test --skipNxCache --runInBand
corepack pnpm exec nx run server-ai:test --testPathPattern 'agent-evolution'
```

注意事项：① `--runTestsByPath` **不做模式匹配**，路径写错会直接报「未找到测试」；② `server-ai` 项目名已核实（`packages/server-ai/project.json` 的 `name`），`nx run server-ai:test` 会跑**整个包**（2000+ 用例），本域建议始终带 `--testPathPattern 'agent-evolution'`；③ 本包**无全局 setup/setupFiles**，环境变量必须在命令行前缀注入（见第五节）。

章节来源：[jest.config.ts](file://packages/server-ai/jest.config.ts)（关键符号：preset / moduleNameMapper / transform / coverageDirectory），[project.json](file://packages/server-ai/project.json)（关键符号：targets.test.executor / options.jestConfig）

## 四、断言与 mock 风格

- **手工 new 服务 ＋ 全 mock（本域主流）**：`change.service.spec.ts` 在文件头 `jest.mock` 掉 `execution-conversation` 与 `plugin-sdk`，再手工构造 `EvolutionChangeService` 及其依赖（`DataSource`、provider registry、store 全为假实现），因此**不需要 PG/Redis**。
- **Nest 集成（无库）**：`agent-evolution.module.spec.ts` 用 `Test.createTestingModule` 导入真实 `AgentEvolutionModule` ＋ 假 `DataSource`/`StrategyBus`，断言 `PermissionGuard` 可解析——这是「守卫依赖 `CommandBus`」这一装配约束的**唯一**回归护栏。
- **provider 桩的行为断言**：`change.service.spec.ts` 用 `h.provider.describe.mockRejectedValue(...)` 等构造降级分支（presentation 不可用时审计数据仍可读）。
- **数据驱动/语义断言为主**：`evolution-state.spec.ts` 直接喂合法/非法迁移对；`change.validation.spec.ts` 喂缺覆盖、假 pass、重复 check 等非法输入；断言集中在**抛出与拒绝**，而非日志。
- **真库用例单独一档**：仅 `persistence.integration.spec.ts` 用 `TypeOrmModule.forRoot` ＋ 真实 `DataSource`（`synchronize: true`，见下节）。

章节来源：[agent-evolution.module.spec.ts](file://packages/server-ai/src/agent-evolution/agent-evolution.module.spec.ts)（关键符号：Test.createTestingModule / PermissionGuard / CqrsModule），[change.service.spec.ts](file://packages/server-ai/src/agent-evolution/changes/change.service.spec.ts)（关键符号：jest.mock / provider 桩 / 降级断言），[change.validation.spec.ts](file://packages/server-ai/src/agent-evolution/changes/change.validation.spec.ts)（关键符号：validateChangeInput / 非法输入矩阵）

## 六、缺口

1. **48 个端点没有 HTTP 层用例**：`controllers/` 下 **0 个 spec**，`changes/lifecycle.controller.ts` 也无 spec。因此「路径拼写、路由声明顺序（`/changes/records` 必须先于 `/changes/:id`）、`@Permissions` 位组合、401/403 行为」全靠人工核对。这是本域**最大的回归风险面**。
2. **夹具端点的 404 门禁无断言**：`assertConformanceEnabled()`（控制器）与 `assertTemplateConformanceEnabled()`（provider）的 `production && AGENT_EVOLUTION_ENABLE_CONFORMANCE !== 'true' → 404` 分支在本包 spec 中**未发现直接用例**；`providers/conformance-field-mapping.provider.spec.ts` 只覆盖 provider 本体。`POST /changes/conformance-template` 同样无用例。
3. **回滚路径无独立 spec**：`rollbackProduction` / `rollbackPointerCas` 没有专门用例；真库用例的终态是「release = `active`、部署 2 条」，**没有走到回滚**。因此「回滚后 release 终态为 `rolled_back`、指针 revision 前推、无法回到原 canary 档」只有结构推断，没有测试取证。
4. **运行时观测的副作用无 spec**：`EvolutionRuntimeStore.saveRuntimeObservation` 的 `severeErrors → 自动 pause` 与样本累加（`sampleCount/severeErrors/candidateAccuracy/p95LatencyMs/averageCost`）**没有 store 级 spec**（模块内无 `*.store.spec.ts`）。
5. **无真实队列证据**：没有任何 spec 打到真实 BullMQ/Redis；「attempts=3 / backoffMs=1000 / concurrency 2/1」只由常量断言（若有）而非行为验证，job 卡死与重试语义**未被测试覆盖**。
6. **`cancelled` 与 `pending` 两个状态无用例**：job 取消无 HTTP 入口（见 05 第九节），`change.service` 中 `['pending','queued','running']` 分支也未见过滤用例。
7. **无 e2e / 无前端联调用例**：本仓未见针对 `/api/agent-evolution/*` 的端到端（含鉴权失败、夹具 404）测试；前端侧的 spec 属 `apps/cloud`（另配 jest 配置），与后端接口契约无自动比对。

## 七、可执行性结论

判定：**✅ 结论上可跑，但本次不实跑**（只给命令与判据，未执行 jest）。

1. **可跑性依据（结构事实）**：19 个 spec 全部落在 `packages/server-ai/jest.config.ts` 的 `testMatch` 覆盖范围内；`moduleNameMapper` 直指源码，**无需先 `nx build` 依赖包**；18 个 spec 无外部依赖（DB/Redis/队列均 mock 或可选注入），单文件命令可直接执行。
2. **唯一环境前置**：第 10 个 spec 默认 `describe.skip`，只有显式注入 `AGENT_EVOLUTION_PERSISTENCE_E2E=1` ＋ 可达的 PostgreSQL（`DB_*`）才解锁；解锁后它会**在目标库内创建并删除自己的 schema**，不会污染业务 schema——但仍建议指向测试库。
3. **不实跑的原因（如实记录）**：本轮为只读检索任务，未执行 jest；本仓亦未见针对 agent-evolution 的「已复跑」记录（前端同专题资产在 `test/known-failures.md` 中标注「重建后未复跑」），因此**不声明本域任何 PASS/FAIL 结论**。
4. **建议的验证顺序**：`domain/*` → `providers/*` → `changes/*` → `application/*`（除 integration）→ 最后单独跑 integration；任一步失败先看 `moduleNameMapper` 是否命中源码路径。
5. **skip 语义**：本域无 known-fail 白名单；唯一的 `skip` 是条件开关（`AGENT_EVOLUTION_PERSISTENCE_E2E`），不属「已知失败」。

章节来源：[jest.config.ts](file://packages/server-ai/jest.config.ts)（关键符号：moduleNameMapper / transform / testEnvironment），[agent-evolution.persistence.integration.spec.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution.persistence.integration.spec.ts)（关键符号：persistenceDescribe / describe.skip），[project.json](file://packages/server-ai/project.json)（关键符号：targets.test）
