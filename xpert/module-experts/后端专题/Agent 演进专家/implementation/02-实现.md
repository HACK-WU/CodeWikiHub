## 学习事件与诊断链
入账侧由 `AgentEvolutionRuntimeService.ingestLearningEvent` 承担（它是 `EvolutionRuntimeCapability` 的实现）：先 `validateScope`（scope key 非空；`organization` 型 scope 必须等于请求组织），**confidential 事件必须 `redactionStatus === 'redacted'`**（否则 400 `Confidential learning events must be redacted before ingestion`），再要求目标存在且 `status === 'active'`（否则 404），补 `eventId`（缺省 `EVT-<uuid>`）与 `reviewStatus: 'pending'`，经 `store.saveLearningEvent` 落 `agent_evolution_learning_event`（`UQ(idempotencyKey)` 保证重复投递幂等）。
复核与诊断：`PATCH /learning-events/:id/review` 把 `reviewStatus` 写成 `pending|ignored|golden`（契约 `learning-event.ts`），是唯一的学习事件人工分类入口。`POST /diagnoses` 走 `AgentEvolutionAnalystService.diagnose`：事件 id 去重后按租户取行，**数量不等即 400**；再次拒绝未脱敏的 confidential；按 `correctionSignature = hashEvolutionValue({targetId, scopeType, scopeKey, dimensions, decisionPoint, reasonCodes(sorted)})` 分组，每组产出一条 `EvolutionDiagnosis`（`rootCause` 为 `repeated_correction_signature:<reasons>` 或 `unclassified_repeated_correction`，`confidence` 为组内均值）与一条 `EvolutionEventCluster`（`caseCount = distinct subjectRef`，`status = qualifiesLearning(...) ? 'proposal_ready' : 'collecting'`）。策略侧要求 `request.strategyId` 命中目标描述符且 `learning.mode === 'feedback'`，否则 `strategy_not_allowed`——**聚类是否「可提提案」由策略阈值决定，不由事件数量单独决定**。

## 提案与候选链
**提交入口**在校验层被 `submission.schema.ts` 提前收窄：`evolutionSubmissionSchema` 是严格 Zod 契约（`executionContext` UUID + `input ≤ 100000`、`strategyId`/`sourceKind∈{learning_events,business_evidence,manual}`、`scope.type∈{tenant,organization,workspace,project}`、`baseline.{resourceId,version,hash}`、`evidence[≤100]` 且 `locator` 严格、`learningEventIds[≤100]`、`candidateInput` 为标量/字符串数组、`datasetSnapshotIds` 记录），全对象 `.strict()`——**多余字段直接 400**（`invalid_strategy_submission`）。
**prepare**：`EvolutionChangeService.prepare` 先 `checkIdentity`，`strategies.freeze()` 冻结策略快照 + `hash`，校验 `supportedScopes` 含 scope 类型与 `validateChangeInput`，`executionContext` 存在时经 `conversations.validate` 做 xpert/项目可用性校验，`sourceKind === 'manual'` 时要求人主体；feedback 模式下把学习事件重算成 evidence 与输入逐条 `digest` 对账。随后生成 `changeId = EVO-<uuid>`、`jobId = EVOJOB-<changeId>`、`evidenceHash`、`stages = initialStages(strategy.definition)`，写 **Proposal 行**（`proposalId = PROP-<changeId>`，`revision: 1`，`UQ(tenant,org,targetId,requestId)` 幂等，`UQ(…,revision)`）与 `job change_preparation`，非 defer 时入队。
**build/process**：`build()` 在事务内加锁读变更，写入 `candidateInput`（已存在候选则比对 digest，不同即 `immutable_candidate_changed`），再交 `process()`；`process()` 按策略 `candidate.builder` 分派——`target_draft` 走 `draftBuilder.prepare`，否则要求基线版本哈希与 `change.baseline.hash` 一致后调 `candidateBuilder.buildCandidate`（`idempotencyKey = <changeId>:build`）+ `validateCandidate`，产出 `EvolutionCandidate`（`artifact.hash` 即后续全链的 `candidateHash`）。**候选一经存在即不可换**：`decide`/`publish` 都以 `artifact.hash` 与调用方入参比对。
章节来源：[submission.schema.ts](file://packages/server-ai/src/agent-evolution/changes/submission.schema.ts)（关键符号：evolutionSubmissionSchema）、[change.validation.ts](file://packages/server-ai/src/agent-evolution/changes/change.validation.ts)（关键符号：validateChangeInput）、[change.service.ts](file://packages/server-ai/src/agent-evolution/changes/change.service.ts)（关键符号：EvolutionChangeService.prepare、build、buildDraft）、[change.store.ts](file://packages/server-ai/src/agent-evolution/changes/change.store.ts)（关键符号：EvolutionChangeStore 的 proposal 映射、changeIdentity）

## 策略服务
`EvolutionStrategyService` 文件头注释逐字：`// Invariants: the target allowlist selects a versioned plan. Callers cannot weaken a frozen plan.`。`freeze(targetId, organizationId, strategyId, sourceKind)` 从 `EvolutionTargetProviderRegistry.get(targetId, organizationId)` 取描述符，要求 `descriptor.status === 'active'`、策略存在且 `inputs.includes(sourceKind)`（否则 `strategy_not_allowed`），再 `validateStrategy`，最后 `structuredClone` 出 `{definition, riskLevel, providerKey, providerVersion}` 并算 `hash = sha256(JSON.stringify(snapshot))`——**快照里的四个字段任一变化都会使 hash 变化**，从而让后续 `current()` 抛出 `strategy_snapshot_stale`。
`validateStrategy` 是策略的「合法性 + 能力可用性」双检：`id`/`version`/`inputs`/`approval === 'human'` 必填；评估步骤 `key` 不得重复；`learning.mode === 'feedback'` 时 `minimumEvents ≥ 1`、`minimumSubjects ≥ 1`、`maximumAgeDays ≥ 1`、`trustLevels` 非空；`candidate.builder === 'target_draft'` 需 `draftBuilder`、否则需 `candidateBuilder`；评估步骤按 `kind` 需 `replayEvaluator` 或 `checkEvaluator`；发布按 `mode` 需 `releaseProvider + capabilities.install`（`staged_rollout`）或 `versionPublisher`（`version_write`），且 `staged_rollout` 的 `effect` 必须是 `activation`。策略来源是契约包的三个工厂：`evidenceDrivenStrategy`、`FEEDBACK_LEARNING_STRATEGY`、`HUMAN_PROPOSAL_STRATEGY`（夹具 `conformance.template_version` 同时挂后两者）。`initialStages` 把六阶段（learning/candidate/evaluation/approval/publication/effect）初始化成 `passed|pending|not_applicable`——**learning 模式为 `none` 时直接 `passed` 并给出 `strategy_does_not_require_learning`**，评估步骤为空时 `not_applicable`（Human 判定）。
章节来源：[strategy.service.ts](file://packages/server-ai/src/agent-evolution/changes/strategy.service.ts)（关键符号：EvolutionStrategyService.freeze、current、validateStrategy、initialStages、setStage）

## 评估链
`POST /changes/:id/evaluations` → `EvolutionLifecycleService.evaluate` → `EvolutionChangeService.evaluate`（先事务内冻结 `datasetSnapshotIds`：已存在评估且数据集映射变化即 `evaluation_snapshot_mismatch`；无评估则把状态推 `testing`）→ `process()` → `EvolutionEvaluationExecutor.run`。执行器对策略的每个评估步骤依 `kind` 分派：`golden_replay` 走内置 `replay()`，其余走 `target.checkEvaluator.evaluate`；每步返回后立刻 `validateChangeEvaluation`，最后 `results.every(r => r.passed)` 决定整体 `passed`。
`replay()` 是全域最重的一段：① 取 `change.datasetSnapshotIds[step.key]`，缺失即 `evaluation_dataset_required`；② 校验快照 `targetId` 与 `sameScope(scope)` 一致（`evaluation_snapshot_mismatch`）；③ 校验基线版本 `artifact.hash === change.baseline.hash`（`candidate_baseline_mismatch`）；④ 为基线与候选各建一个 `executionMode: 'replay'` 的能力束（`bundleHash` 由 items 规范哈希得出）；⑤ 逐条 case 调 `replayEvaluator.runReplayCase` + `evaluateResult`（`randomSeed: 42`、`repeatIndex: 0`，保证可复现）；⑥ `aggregateMetrics` 后交质量治理 `reviewGoldenReplay` 出闸门结论，落一条 **原生** `EvaluationRun`（`status = gate.passed ? 'passed' : 'failed'`，含 `caseResults`）；⑦ 再用 `ASSESS-<runId>` 返回一条「公共评估」记录（`checks` 只含一条阻塞性 `replay-gate`，`datasetHash` 用快照哈希）——注释逐字：`The common assessment has its own immutable record; replay evidence retains its native metrics.`
多步骤时的 `datasetHash` 是**合成值**（对每步 `{runId, datasetHash}` 做规范哈希），单步时用原生值；`checkId` 在单步时保持原值、多步时加 `<step.key>:` 前缀。落库侧 `EvolutionChangeStore.saveEvaluation` 以「同 runId 同内容」幂等，内容不同即 `immutable_evaluation_changed`；`gatePassed` 是实体上的**布尔判据列**，供 SQL 侧直接筛。
章节来源：[evaluation-executor.service.ts](file://packages/server-ai/src/agent-evolution/changes/evaluation-executor.service.ts)（关键符号：EvolutionEvaluationExecutor.run、replay）、[change.validation.ts](file://packages/server-ai/src/agent-evolution/changes/change.validation.ts)（关键符号：validateChangeEvaluation）、[change.service.ts](file://packages/server-ai/src/agent-evolution/changes/change.service.ts)（关键符号：EvolutionChangeService.evaluate）、[change.store.ts](file://packages/server-ai/src/agent-evolution/changes/change.store.ts)（关键符号：EvolutionChangeStore.saveEvaluation、isProviderEvaluation）

## 闸门策略
**质量闸门**（`AgentEvolutionQualityGovernanceService`，纯函数）：`reviewGoldenReplay` 对 `totalCases ≥ 50`、`affected*` 切片 `≥ 20`、`risk === 'high'` 切片 `≥ 10`、`severeErrors === 0`、`accuracyDelta > 0` 五项逐条判定，收集 `blockingReasons`（`golden_dataset_below_50_cases`/`affected_slice_below_20_cases`/`high_risk_slice_below_10_cases`/`severe_errors_present`/`candidate_does_not_improve_baseline`）并给出 `decision: 'reject' | 'promote'`。`requiredHumanApprovals(R3|R4) = 3`、其余 `2`；`reviewHumanApprovals` 的通过条件是 **`hasAdministratorApproval` 直接放行**，否则 `distinct actorId` 与 `distinct actorRole` **双达标**（两个集合各自 ≥ 要求人数）——所以同一人用两个角色投两票无效。
**发布闸门**（`AgentEvolutionReleaseGatePolicyService`）：`STANDARD_GATE_POLICY` 为 `shadow 100 样本/72h`、`canary 30/24h`、`productionCanary 30/24h`、`experience 100/168h`；`resolveEvolutionReleaseGatePolicy` 只在 **非生产** 且 `AGENT_EVOLUTION_GATE_PROFILE=manual_test` 时给出 `manual_test` профиль（六个阈值均可用 `AGENT_EVOLUTION_TEST_*` env 覆盖，缺省 sample=1、hours=0）；生产恒为 `standard`，且 `requestedShadowMinimumSamples` 只能**抬高**不能降低（`Math.max(STANDARD, requested)`）。`forRelease` 只读发布包内冻结值，缺失即 `Release gate policy was not frozen`；`manualTestProfileEnabled()` 供控制器/治理侧判断当前进程是否允许一次性覆盖。冻结动作发生在 `package()` 与每次 `releaseOperationContext(...)` 之后（`freezeReleaseGatePolicy`），并要求 `manual_test` 时调用者必须是 administrator。
章节来源：[quality-governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-quality-governance.service.ts)（关键符号：AgentEvolutionQualityGovernanceService.reviewGoldenReplay、reviewHumanApprovals）、[release-gate-policy.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-release-gate-policy.service.ts)（关键符号：STANDARD_GATE_POLICY、MANUAL_TEST_DEFAULTS、resolveEvolutionReleaseGatePolicy、forRelease）、[governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts)（关键符号：AgentEvolutionGovernanceService.freezeReleaseGatePolicy、requireGatePolicyAuthority）

## 发布与部署链
**审批（decide）**：`EvolutionChangeService.decide` 先在事务内校验「候选哈希 = 入参 `candidateHash`」「评估 `runId` = 入参 `evaluationRunId`」「`evaluation.strategyHash` = `strategy.hash`」，任一不符即 `review_snapshot_mismatch`；再从 `agent_evolution_approval` 取该候选的历史审批并按三元组过滤，**同 actor 改判即 `immutable_approval_changed`**（同 actor 同判则原样返回，天然幂等）；状态必须属于 `pending_approval|test_failed`（否则 `not_reviewable`）；批准时要求 `evaluation.passed` 并调 `assertCurrent` 复核目标快照。写入的 `ApprovalDecision` 同时记录 `approvalAuthority`（administrator/standard）与 `actorRoleName`，随后 `reviewHumanApprovals` 决定 `approved` 还是继续 `pending_approval`。
**发布（publish）**：状态机不允许跨级——先事务内把状态推 `publishing` + `publication: running`，再第二个事务真正发货：`staged_rollout` 走 `EvolutionPublicationExecutor.package()`（注释：`// Staged publication allocates its version and package in the caller's transaction.`）分配 `PUB-<changeId>` 与 `CapabilityVersion`（`sequence = max+1`、`artifactHash = candidate.artifact.hash`、`rollbackVersionId = baseline.resourceId`、`gatePolicy` 冻结、`canaryPercent: 0`，`approvalIds` 只收哈希/runId/strategyHash 全对齐的批准）；`version_write` 走 `target.versionPublisher.publish`，并且要校验回执三元组（`changeId`/`candidateHash`/`approvalId`）否则 `write_receipt_mismatch`。
**部署阶梯**（`AgentEvolutionGovernanceService`）：`install` 校验目标支持 `capabilities.install` 后调 `releaseProvider.install` 并把 release 推 `installed`；`shadow` 只允许从 `installed|paused` 起；`canary` 只接受 `5|25|50`，首档必须 5%，扩档由 `expectedNext = (5→25→50)` 推导，跳档 400；`activateProduction` 要求 `canaryPercent === 50` + 生产阈值 + 指针仍等于 `rollbackVersionId`，成功后 `activatePointerCas` 切指针并建 `channel: 'production'` 的部署；`rollback` 先校验目标支持 `capabilities.rollback`、release 就是当前生产版本，再 `releaseProvider.rollback` + `rollbackPointerCas` 指回 `rollbackVersionId`。`pause` 只允许 `shadow|canary`。队列化边界：`install|shadow|canary|rollback` 走队列返回 `EvolutionJob`，`pause|activate` 同步返回（`ReleasePackage` / `ActiveCapabilityPointer`）——与前端 `C1-能力契约.md` 的返回语义一致。
章节来源：[change.service.ts](file://packages/server-ai/src/agent-evolution/changes/change.service.ts)（关键符号：EvolutionChangeService.decide、publish）、[publication-executor.service.ts](file://packages/server-ai/src/agent-evolution/changes/publication-executor.service.ts)（关键符号：EvolutionPublicationExecutor.package）、[governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts)（关键符号：installRelease、startShadow、startCanary、pauseRelease、activateProduction、rollbackProduction）、[evolution-state.ts](file://packages/server-ai/src/agent-evolution/domain/evolution-state.ts)（关键符号：RELEASE_TRANSITIONS）

## 金丝雀与覆盖
**一次性覆盖的创建条件（四个 AND）**：调用者是人；`approvalAuthority === 'administrator'`（否则 `AgentEvolutionCanaryTestOverrideRequiresAdministrator`）；**发布包冻结的 `gatePolicy.profile === 'manual_test'` 且当前进程 `manualTestProfileEnabled()`**；release 状态为 `canary` 且存在 `channel:'canary' && status:'canary' && !completedAt` 的活跃部署。参数校验：`subjectKey ≤ 200`、`reason ≤ 500`、`expiresInMinutes ∈ [1,120]`（缺省 **30**）；同部署同主体已有 pending 覆盖即 `AgentEvolutionCanaryTestOverrideAlreadyPending`。
**只生效一次**：实体以 `activeKey = sha256(tenant:org:deploymentId:subjectKey)` 建唯一索引；`EvolutionRuntimeStore.createCanaryTestOverride` 发现活跃覆盖**直接返回旧值**（不续期），已过期则翻 `expired` 并清 `activeKey` 后新建。消费侧 `consumeCanaryTestOverride` 在一个事务内：先按 `status:'consumed'` 查重试，`consumedByExecutionId === executionId` 即返回旧结果；否则 `pessimistic_write` 锁 pending 行，过期翻 `expired` 返回 null，有效则写 `status:'consumed'` + `consumedAt` + `consumedByExecutionId`，并追加一条审计。
**指标口径与回落**：`resolveExecutionPlan` 对 canary 部署先尝试消费覆盖——`!consumedOverride && !deterministicSelection → continue`，即**覆盖只对「该 executionId 的那一次解析」生效，之后同一 subjectKey 回落到确定性路由** `deterministicPercent = sha256(deploymentId:subjectKey) → [0,100)` 与 `canaryPercent` 比较。命中覆盖时分配项带 `selectionReason: 'manual_test_override'` 与 `manualTestOverrideId`，响应体另有 `manualTestOverrides[]` 数组供消费方审计。golden replay 与覆盖**互不相关**：前者是评估阶段的离线复现（同 seed、同 bundle），后者是生产阶段的在线路由强插。

## 运行时与观测
**解析（读侧）**：`resolveExecutionPlan(request)` 要求 `targetIds` 非空、`subjectKey` 非空；对每个去重后的 targetId **先取 `channel:'production'` 指针，缺失即 404**（这是硬前置：没有生产指针就没有解析结果）。随后遍历该目标全部部署，按优先级选路：`shadow` 且 release 为 `shadow` → 记入影子分配并 `break`；`canary` 且 release 为 `canary` 且部署未完成 → 先消费覆盖，再判确定性百分比，命中才把 `productionVersionId` 换成候选版本并标 `canarySelected`；否则回落 `channel:'production'`（有 `pointer.releasePackageId` 时再找活跃生产部署补 `deploymentId`）。最后用 `createBundle` 生成**能力束**（items 含 targetId/versionId/artifactHash/providerKey/providerVersion，`bundleHash = hashEvolutionValue(items)`），`executionMode` 依次取 `canary > shadow > production`，影子另出 `shadowBundle` + `shadowAssignments`。
**回流（写侧）**：`recordRuntimeObservation` 生成 `observationId`（缺省 `OBS-<uuid>`）后交给 `EvolutionRuntimeStore.saveRuntimeObservation`：按 `observationId` 去重（重复直接返回旧值）；有 `deploymentId` 时对该部署行加 `pessimistic_write` 锁，累加 `sampleCount`、滚动 `candidateAccuracy`、`severeErrors`、`p95LatencyMs = max(prev, latencyMs)`（**单调不减**）、`averageCost` 按样本数加权，并把单条 `runtimeObservation` 追加进 `observations[]`；`severeError === true` 且 release 处于 `shadow|canary` 时，`assertReleaseTransition(status,'paused')` 通过则**自动暂停**并写审计（`action: 'deployment.auto_paused'`，主体为系统）。**该自动暂停是 shadow/canary 唯一由数据触发的状态迁移**；`active` 不会被自动降级，回滚必须由人（或非 agent 主体）显式发起。

## 质量治理与经验
**审批门的两段式**：低层 `reviewGoldenReplay` 只判「数据是否达标」（可拒绝发布），高层 `reviewHumanApprovals` 只判「人是否到位」（可继续挂起）。`decide()` 把两层串起来：先 `evaluation.passed`（否则 `tests_must_pass`），批准后由 `reviewHumanApprovals(riskLevel, [...历史, 本次])` 决定终态是 `approved` 还是 `pending_approval`；管理员单票即放行（`hasAdministratorApproval` 分支），是刻意的运维逃生门，也是**审计上最需要盯的一条路径**。前端侧同口径只做展示（`evolutionApprovalGatePresentation`），注释明示「服务端决定是否凑齐所需人工审批」。
**经验沉淀**：`createExperience` 要求人主体 + release 为 `active` + 冻结 `gatePolicy` 存在 + 存在 `channel:'production' && status:'active'` 部署且 `sampleCount ≥ experienceMinimumSamples`、`severeErrors === 0`、时长达 `experienceMinimumDurationHours`；并回查变更的 `evaluation.runId === release.evaluationRunId` 且 `evaluation.passed`（否则 `Release strategy assessment does not match`）。产出 `EvolutionExperience`（`experienceId = EXP-<uuid>`、`status: 'active'`、`evidence` 内含生产观测数与稳定天数 `hours/24`）——**它是「已稳定」的留档，不改变任何指针**。

## 队列与作业
**队列恒定在 `agent-evolution`**（`AGENT_EVOLUTION_QUEUE`），owner 为 `@xpert-ai/platform`；作业类型两族：发布族 `evaluation | install | shadow | canary | rollback`（`@PluginJobProcessor` 并发依次 2/1/2/1/1），变更族 `change_preparation`（`CHANGE_QUEUE`，并发 2，消费者 `EvolutionChangeProcessor`）。`AgentEvolutionQueueService.enqueue` 的顺序是「**先落 job 账本再投递**」：写 `EvolutionJob{status:'queued'}`（`jobId = EVOJOB-<uuid>`）→ `queue.enqueue({attempts: 3, backoffMs: 1000, tenantId, organizationId, userId, jobId})` → 把 `queueJobId` 回写 job；投递失败则把 job 直接置 `failed` 并写 `errorCode: 'queue_enqueue_failed'` 再抛出。`Managed Queue` 未注入时是 `ServiceUnavailableException`（`@Optional()` 注入，模块可在无队列环境装配）。
**作业状态与查询**：`EvolutionJobStatus = 'queued' | 'running' | 'completed' | 'failed' | 'cancelled'`（契约 `governance.ts`）；`AgentEvolutionQueueProcessor.handle` 把 job 推 `running`（记 `startedAt`）→ 按 `operation` 分派到治理服务 → 成功 `completed`（记 `completedAt`）、异常写 `errorCode: 'evolution_job_failed'` + `errorMessage` 后**重新抛出**（让队列做 3 次重试）。`GET /jobs/:jobId` 直接读 job 账本（`ResourceId` 指向候选或发布包）；前端据此轮询（`waitForJob` 60×1s，超时窗口不等于作业超时）。**无调度器**：模块内 `@Cron`/`@Interval`/`@Timeout` 零命中，全部 HTTP 或队列驱动；也**不订阅跨域事件**（`@OnEvent` 零命中）。

## 热点路径
1. **`resolveExecutionPlan`（每次执行一次）**：同步循环「每目标 → 取指针 → 列部署 → 取每个部署对应的 release → 可能消费覆盖 → 建能力束（逐版本 `findVersion`）」，且 `createBundle` 会**为每次解析新增一条 `capability_bundle` 行**——解析频率越高，`agent_evolution_capability_bundle` 增长越快（该表只有 `bundleHash` 索引，无 TTL/清理路径）。
2. **`saveRuntimeObservation`（每次运行一次）**：单事务内「观测去重插入 + 部署行 `pessimistic_write` 累加 + 追加 `observations[]` 数组」，`observations` 随样本线性增长，**同一部署的并发观测被行锁串行化**，是观测侧的吞吐上限。
3. **`process()`（变更推进）**：一次调用内多次独立事务 + 外部 provider 调用 + ChatKit 会话写入；读侧只在每次事务重读变更，**外部调用不持锁**（注释说明先提交 running 阶段以便观察）。
4. **`replay()`（评估）**：逐 case 串行调 `runReplayCase`/`evaluateResult`，`caseResults` 全量落 `EvaluationRun.value`；`totalCases ≥ 50` 是硬闸门，单次评估至少 50 次 provider 往返。
5. **`decide()`（审批）**：每次评审都把该候选**全部历史审批**取出做三元组过滤（无 `candidateId + actorId` 复合索引，只有 `candidateId` 维度），高风险 R3/R4 需 3 人时最坏要重复扫 3 遍。
6. **`inspect()`（基线面板）**：每次调用都真调 provider 的 `previewBaseline`（可能读外部源）+ 读指针/版本；前端 `EvolutionBaselinePanelComponent` 每次 scope 变化都会触发。

## 技术债与 hack
1. **无 SQL 迁移**：`agent-evolution` 目录无 `migrations/`，全仓 `*.sql` 内 `agent_evolution` 零命中；19 表 DDL 的唯一事实来源是实体注记，集成测试自建 schema（`agent_evolution_test_<pid>`）。上线/回滚都没有可执行 DDL。
2. **`job.status` 口径漂移**：`process()` 里判断残留作业时用了契约**不存在**的 `'pending'`（`EvolutionJobStatus` 只有 `queued|running|completed|failed|cancelled`），而前端 `C1-能力契约.md` 把 `pending` 写进了 job 状态清单——**三处口径不一致**，该分支很可能是死分支。
3. **变更无整表**：`change.store.ts` 注释明示「assembled, never persisted whole」，因此任何读变更都要跨 4~5 张表拼装；「写一半」的中间态由 `status` + `stages` 双份表达，读侧必须同时看两者。
4. **指针回滚不可逆**：`rolled_back` 是终态且回滚后 release 状态与指针 revision 同时前推，`paused → shadow|canary` 是唯一回退路径；误回滚只能重走 `install`。
5. **`paused` 恢复路径依赖「最新部署渠道」**：`startCanary` 从 `paused` 恢复时要求 `latest.channel` 匹配 shadow（只准 5%）或 canary（只准下一档），因此**部署历史顺序**成了隐式状态。
6. **`@VersionColumn` 全域缺失**：19 表无 TypeORM 版本列，唯一乐观锁是 `ActiveCapabilityPointer.revision`（手工维护）；其余表依赖条件更新或行锁。
7. **无软删**：模块内无 `DeleteDateColumn`，基类也没有——历史行只能靠归档语义（状态）而非删除语义处理。
8. **`observations[]` 无界增长**：观测按条 append 进部署行的 json 列，长跑部署会把单个 json 单元格撑大；`p95LatencyMs` 用 `max` 合并，**只增不减**，无法反映延迟改善。
9. **执行账本与部署统计无对账**：`xpert-agent-execution` 只被单向写，`runtime_observation` 与执行记录之间没有关联校验，重复观测只能靠 `observationId` 幂等。
10. **SSE 失败静默**：转录发布失败被 `logger.warn` 吞掉（注释：`Persisted messages and runtime state remain authoritative when live delivery fails.`）——排障时「前端没动画」不等于状态没变。
11. **夹具口径易被误当通用规则**：`ConformanceTemplateProvider.validateCurrent` 要求 evidence 恰为 1 条 feedback，且 `capabilities` 近乎全 false；任何把它当参照实现的下游都会踩空。
12. **`[推测]` 单步评估 `datasetHash` 是合成值**：单步时沿用 provider 返回值、多步时改为对 `{runId, datasetHash}` 的规范哈希，语义不一致；下游若按「datasetHash 即数据集指纹」做缓存或比对，可能在步骤数变化时失效。
13. **`[推测]` 基线 `inspect` 的外呼成本**：每次调用都真调 `previewBaseline`，若 provider 实现为远程读，前端 scope 切换会放大为外部 QPS；模块内无缓存层。
14. **`[推测]` `createBundle` 的写入放大**：每次 `resolveExecutionPlan` 都新增 bundle 行且无清理路径，高 QPS 场景下 `agent_evolution_capability_bundle` 可能成为最大表（该推论未在测试中验证）。

## 设计维度分析
**「一键发布」 vs 「不可跳过的人工闸门」**：本域把自动化做到队列化（`install|shadow|canary|rollback` 全是作业），但把**升级与放量**做成同步硬校验：档位只能 5→25→50，激活前必须 50% 且指针未被人动过，回滚入口拒绝 agent 主体。代价是运维必须多轮触发（每档都要重新 POST `/canary` 并满足时长阈值），换来「任何一次放量都留下一条审计 + 一个部署行」。
**「冻结快照」 vs 「可调阈值」**：策略快照、`gatePolicy`、审批三元组都被冻结进各自的不可变记录；env 只在**建包时**生效。这使「改配置影响在途发布」在结构上不可能，但也意味着调阈值必须重新建包（`PUB-<changeId>` 已是幂等的固定 id，无法改）。
**「单一哈希口径」 vs 「多处独立摘要」**：`hashEvolutionValue` 统一了候选/基线/证据/策略/覆盖的组合哈希，使跨阶段绑定校验（`review_snapshot_mismatch`/`evaluation_snapshot_mismatch`/`immutable_approval_changed`）全部可读；但策略快照的 hash 用的是裸 `sha256(JSON.stringify(snapshot))` 而非规范哈希，**两套摘要算法并存**，跨实现的等价性只能靠「字段顺序稳定」这一隐含前提。
**「记录与投影分离」 vs 「双份状态口径」**：候选状态机与发布状态机各自独立，再通过 `fromCandidateStatus`/`toCandidateStatus` 双向映射到「变更状态」这一第三套词表（`expired↔stale`、`packaged↔publishing`、`evaluation_failed↔test_failed`）。好处是各阶段可独立演化，代价是同一事实有三种字符串表达，前端必须靠 `lifecycleRecord()` 的投影才不至于读错。

## 结论
实现上的骨架可以概括为「**四层冻结 + 一道 CAS**」：策略在提交时冻结、数据集映射在评估时冻结、闸门阈值在建模发布包时冻结、审批三元组在评审时冻结；真正让版本生效的只有 `ActiveCapabilityPointer` 的一次条件更新（`revision + activeVersionId`），失败的语义被显式命名为 `Active Pointer CAS conflict`。读侧则刻意保持「薄」——`GET /changes` 返回的是 `lifecycleRecord()` 投影而不是实体，前端因此不需要理解 19 张表。新增能力时应继续沿用既有骨架：写路径走 `EvolutionRuntimeStore`（事务 + 行锁 + 审计三件套）、跨阶段绑定量一律用 `hashEvolutionValue`、放量与回滚必须落在状态机白名单内，不要绕开 `decide`/`publish` 直接改 `ReleasePackage`。需要重点防守的三处是：**19 表无 SQL 迁移**（DDL 只在实体注解里）、**`job.status` 的 `pending` 死分支与前端清单不一致**、以及**`capability_bundle` / `observations[]` 两条无界增长路径**。
