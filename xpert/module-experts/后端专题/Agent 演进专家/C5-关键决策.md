## D1 能力版本不可变
- **分类**：架构设计
- **动机（避坑）**：现象——把「同一目标第 N 版能力」实现为可改写的行（就地覆盖 `artifactHash` 或 `sequence`）；后果——已激活的生产指针会指向一个内容被悄悄替换的版本，历史审计、金丝雀对比与回滚目标同时失真，且任何哈希绑定校验都失去意义。
- **决策**：`CapabilityVersionEntity` 以 `UQ(tenant, organization, targetId, sequence)` + `artifactHash` 列把「第 N 版」固化：`versionId = \`${targetId}:${changeId}\``、`sequence = max(sequence)+1`、`semanticVersion = \`1.${sequence-1}.0\``；版本一旦落库**只被指针引用，不被改写**。基线的「精确重放」也只**返回旧行**。
- **背景约束**：列与 `value` JSON 的重复字段（`artifactHash`/`sequence`）是查询副本，一致性由服务端同时赋值保证，**数据库层无约束**；`sourceCandidateId` 可空（基线初版无候选）。
- **被否决方案**：无显式否决记录；边界以文件注释形式明写——`// An exact replay after success is harmless; never overwrite a different version on retry.`
- **重新评估触发条件**：出现「同版本号修补」（hotpatch 同一 `sequence`）的硬需求时，须先定义「修补」版本号语义与指针失效规则，**不得**直接放开 `saveVersion` 的 hash 校验。
- **关联代码**：`file://packages/server-ai/src/agent-evolution/entities/evolution.entities.ts`、`file://packages/server-ai/src/agent-evolution/changes/publication-executor.service.ts`、`file://packages/server-ai/src/agent-evolution/application/evolution-baseline.service.ts`
- **证据来源**：实现层 [01-架构.md](file://.module-experts/后端专题/Agent 演进专家/implementation/01-架构.md)「关键不变量」3——「版本一旦落库只被指针引用，不被改写」；源码 `evolution-baseline.service.ts` 逐字：`// An exact replay after success is harmless; never overwrite a different version on retry.`
章节来源：[evolution.entities.ts](file://packages/server-ai/src/agent-evolution/entities/evolution.entities.ts)（关键符号：CapabilityVersionEntity / UQ(targetId, sequence) / artifactHash）、[publication-executor.service.ts](file://packages/server-ai/src/agent-evolution/changes/publication-executor.service.ts)（关键符号：EvolutionPublicationExecutor.package）

## D2 发布包冻结 gatePolicy
- **分类**：接口契约
- **动机（避坑）**：现象——闸门阈值直接从 `process.env` 现读现用；后果——发布进行到一半有人改了阈值，同一个发布包在不同档位被不同标准判定，历史结论不可复现，且「谁在什么时候放宽了闸门」无从追查。
- **决策**：阈值在**建模发布包时一次性冻结**——`EvolutionPublicationExecutor.package()` 调用 `snapshot()` 把 `gatePolicy`（`profile` + 六个样本/时长阈值）写入 `ReleasePackage.value`；此后 `forRelease(release)` **只读冻结值**，缺失即抛 `BadRequestException('Release gate policy was not frozen')`。
- **背景约束**：`STANDARD_GATE_POLICY` 写死 shadow `100/72h`、canary `30/24h`、productionCanary `30/24h`、experience `100/168h`；`manual_test` 档仅在**非生产**且 `AGENT_EVOLUTION_GATE_PROFILE=manual_test` 时生效，六个阈值可被 `AGENT_EVOLUTION_TEST_*` 覆盖（缺省 1/0）；生产**恒为 standard**；`requestedShadowMinimumSamples` 只能抬高（`Math.max`）。发布包 id 固定 `PUB-<changeId>`（幂等：已存在直接返回旧值），**无法改**。
- **被否决方案**：「靠改 env 调整在途发布的阈值」——被结构上排除（实现层明写「改配置影响在途发布在结构上不可能」）。
- **重新评估触发条件**：需要「灰度放宽」某一道闸门时，只能在**建新包**路径上做（新 `gatePolicy`），或新增显式的「闸门修订」记录类型；**不得**让 `forRelease` 读环境变量。
- **关联代码**：`file://packages/server-ai/src/agent-evolution/application/agent-evolution-release-gate-policy.service.ts`、`file://packages/server-ai/src/agent-evolution/changes/publication-executor.service.ts`、`file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts`
- **证据来源**：源码 `agent-evolution-release-gate-policy.service.ts` 逐字：`if (!release.gatePolicy) throw new BadRequestException('Release gate policy was not frozen')`、`shadowMinimumSamples: Math.max(STANDARD_GATE_POLICY.shadowMinimumSamples, …)`；实现层 [02-实现.md](file://.module-experts/后端专题/Agent 演进专家/implementation/02-实现.md)「设计维度分析」——「『改配置影响在途发布』在结构上不可能」。

## D3 金丝雀覆盖只生效一次
- **分类**：安全合规
- **动机（避坑）**：现象——为了「验收方便」让管理员创建的强制路由长期有效（或可反复续期）；后果——**永久覆盖**事故：某个主体被无声地钉在候选版本上，绕过了确定性百分比路由，指标被污染且没人知道它还在生效。
- **决策**：一次性语义由三层物理机制共同保证——① `EvolutionCanaryTestOverrideEntity` 的 `UQ(activeKey)`（`activeKey = sha256(tenant:org:deploymentId:subjectKey)`）保证「同主体同部署至多一条活跃覆盖」；② 消费即 `status: 'consumed'` + 记录 `consumedByExecutionId` + 清空 `activeKey`（让位给后续创建）；③ `expiresAt` 到期由读路径惰性翻 `expired`。消费后 `resolveExecutionPlan` 的判据是 `!consumedOverride && !deterministicSelection → continue`，即**同一主体回落到** `deterministicPercent = sha256(deploymentId:subjectKey)` 的确定性路由。
- **背景约束**：创建需四个 AND（人 / administrator / 发布包 `gatePolicy.profile === 'manual_test'` 且当前进程 `manualTestProfileEnabled()` / release 处于 `canary` 且有活跃 canary 部署），参数上限 `subjectKey ≤ 200`、`reason ≤ 500`、`expiresInMinutes ∈ [1,120]`（缺省 **30**）；同一 `executionId` 重试**返回已消费结果**（幂等重试不会被当成「再给一次机会」）。
- **被否决方案**：「为同一主体重复创建覆盖以续期」——实现为发现活跃覆盖**直接返回旧值、不续期**（源码：`if (existing && existing.expiresAt.getTime() > Date.now()) return existing.value`）。
- **重新评估触发条件**：需要「长时间观测某主体」时，应新增显式的**观测模式**（且与闸门样本隔离），**不得**把一次性覆盖改成可续期；同时注意 `activeKey` 唯一索引**不带租户维度**（值本身含 tenant/org 哈希），若未来改为不含租户的 key，必须同步加租户维度。
- **关联代码**：`file://packages/server-ai/src/agent-evolution/application/evolution-runtime.store.ts`、`file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts`、`file://packages/server-ai/src/agent-evolution/application/agent-evolution-runtime.service.ts`、`file://packages/server-ai/src/agent-evolution/application/evolution-store.helpers.ts`
- **证据来源**：源码 `evolution-runtime.store.ts` 逐字：`if (existing && existing.expiresAt.getTime() > Date.now()) return existing.value`（不续期）、`if (retried?.value.consumedByExecutionId === input.executionId) return retried.value`；实现层 [02-实现.md](file://.module-experts/后端专题/Agent 演进专家/implementation/02-实现.md)「金丝雀与覆盖」。
章节来源：[evolution-runtime.store.ts](file://packages/server-ai/src/agent-evolution/application/evolution-runtime.store.ts)（关键符号：createCanaryTestOverride / consumeCanaryTestOverride）、[evolution-store.helpers.ts](file://packages/server-ai/src/agent-evolution/application/evolution-store.helpers.ts)（关键符号：canaryTestOverrideActiveKey）、[agent-evolution-runtime.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-runtime.service.ts)（关键符号：deterministicPercent）

## D4 指针切换是唯一生效点
- **分类**：架构设计
- **动机（避坑）**：现象——把「发布成功」等同于「线上换版本」（在发布包里写 `currentVersionId`，或由控制器/治理服务直接更新指针行）；后果——多入口并发写同一指针，最后一次写覆盖前一次，激活与回滚互相踩踏，且没有任何冲突信号。
- **决策**：所有「生效」收敛为 `ActiveCapabilityPointer` 的**一次条件更新**——`activatePointerCas` / `rollbackPointerCas` 以 `revision + activeVersionId` 为条件，`affected !== 1` 即抛 `Error('Active Pointer CAS conflict')`；写入被 `EvolutionRuntimeStore` **独占**（文件头逐字：`// Invariants: runtime rollout mutations keep their original CAS, locks and safety gates.`）。
- **背景约束**：激活前必须校验指针仍等于 `release.rollbackVersionId`（被别人前推就拒绝，报 `Production pointer no longer matches the approved rollback version`）；回滚前必须校验指针仍等于 `release.targetVersionId`；`revision` 是手写应用层版本列（19 表无 `@VersionColumn`）。**发布不改任何 Agent 运行时行为**——真正切换发生在消费方调用 `resolveExecutionPlan` 时，因此「发布成功」≠「线上已换版本」。
- **被否决方案**：「由控制器或治理服务直写 `active_pointer` 实体行」——被「运行时写入唯一（`EvolutionRuntimeStore` 独占状态迁移、指针 CAS 与审计）」这一约束排除（实现层 [01-架构.md](file://.module-experts/后端专题/Agent 演进专家/implementation/01-架构.md) 结论）。
- **重新评估触发条件**：出现多目标/多 scope 批量切换需求时，仍应**逐指针 CAS**（或新增批量 CAS 原语），不得改为无条件 UPDATE；若消费方要求 409 语义，需要把 CAS 冲突从普通 `Error` 改为显式 HTTP 冲突。
- **关联代码**：`file://packages/server-ai/src/agent-evolution/application/evolution-runtime.store.ts`、`file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts`
- **证据来源**：源码 `evolution-runtime.store.ts` 逐字：`throw new Error('Active Pointer CAS conflict')`、审计 `action: 'active_pointer.cas_activated'`、`auditId: \`AUD-${input.releasePackageId}-activate\``；实现层 [07-运维.md](file://.module-experts/后端专题/Agent 演进专家/implementation/07-运维.md)「指针切换的影响面」——「发布**不改任何 Agent 运行时行为**」。
章节来源：[evolution-runtime.store.ts](file://packages/server-ai/src/agent-evolution/application/evolution-runtime.store.ts)（关键符号：activatePointerCas / rollbackPointerCas / Active Pointer CAS conflict）、[agent-evolution-governance.service.ts](file://packages/server-ai/src/agent-evolution/application/agent-evolution-governance.service.ts)（关键符号：activateProduction / rollbackProduction）

## D5 双 store 与持久化自证
- **分类**：架构设计
- **动机（避坑）**：现象——让业务读路径（列表、dashboard）也承担指针 CAS、覆盖消费、观测累加这类锁写；后果——只读端点在高并发下产生写竞争（且读路径翻转过期覆盖**不写审计**），更严重的是「读接口顺手改了状态」无法在评审中被发现。
- **决策**：持久化层按**写意图**一分为二——`AgentEvolutionStore` 是 19 表的业务读写门面（目标/版本/事件/提案/候选/数据集/评估/发布/部署/经验/作业），`EvolutionRuntimeStore` 是**运行时侧独占写入者**（发布状态迁移、指针 CAS、金丝雀覆盖、观测累加与自动暂停、审计落地）；store 内的包装方法惰性 `new EvolutionRuntimeStore(dataSource)` 转发。另设**持久化自证** `verifyEvolutionPersistence`，配合需 `AGENT_EVOLUTION_PERSISTENCE_E2E=1` 才跑的集成用例。
- **背景约束**：自证只核对 **13 张表**（target / capability_version / capability_bundle / active_pointer / learning_event / proposal / candidate / dataset_snapshot / evaluation_run / approval / release_package / release_deployment / audit_event），**未覆盖** diagnosis / event_cluster / experience / canary_test_override / runtime_observation / job ——是「约定式探针」而非表级完备校验；`getDashboard` 与 `listCanaryTestOverrides` 的惰性过期翻转属已知的**读路径写库**。
- **被否决方案**：无。
- **重新评估触发条件**：新增写路径时若需要锁或状态迁移，**必须落在 `EvolutionRuntimeStore`**；若要把自证扩为全表覆盖，需同时补齐六张表的引用清单（否则 `verified` 会给出虚假安全感）。

## D6 队列加 job 账本承载异步
- **分类**：技术选型
- **动机（避坑）**：现象——评估与发布在 HTTP 请求内同步执行（golden replay 逐 case 串行、install/rollback 调外部 provider）；后果——请求超时后调用方无法判断动作是否已发生，重试可能重复放量，且没有任何可查询的中间状态。
- **决策**：把耗时与外部调用全部队列化，并**先落账本再投递**：`AgentEvolutionQueueService.enqueue` 写 `EvolutionJob{status:'queued'}`（`jobId = EVOJOB-<uuid>`）→ `queue.enqueue({attempts: 3, backoffMs: 1000, ...})` → 回写 `queueJobId`；投递失败把 job 直接置 `failed` + `errorCode: 'queue_enqueue_failed'` 并抛出。worker 侧 `handle` 推 `running`（记 `startedAt`）→ 分派治理服务 → 成功 `completed`（记 `completedAt`）、异常写 `errorCode: 'evolution_job_failed'` 后**重抛**交给队列重试。状态由 `GET /jobs/:jobId` 可查。
- **背景约束**：队列恒定在 `agent-evolution`（owner `@xpert-ai/platform`），六个 job 类型并发依次 `change_preparation` 2 / `evaluation` 2 / `install` 1 / `shadow` 2 / `canary` 1 / `rollback` 1；`install|shadow|canary|rollback` 入队、`pause|activate` 同步——**前端必须按返回类型区分**。`GET /jobs/:jobId` **未命中返回 `null`（HTTP 200）而不是 404**。
- **被否决方案**：无（未找到显式否决记录）；现状的两处缺口属**未实现而非否决**——「取消 job」无 HTTP 入口（`cancelled` 只能改库），以及 `job.status` 判断里存在契约不存在的 `'pending'` 死分支。
- **重新评估触发条件**：需要「取消入队任务」或「按 resourceId 反查 job」时，须新增端点并同时清理 `pending` 死分支；若引入调度类动作，应复用同一账本而不是另建状态表。

## D7 权限位三分与夹具生产门禁
- **分类**：安全合规
- **动机（避坑）**：现象——用一个粗粒度权限位同时管读写；或让一致性夹具（`test_fixture` provider）在生产可写。后果——只读巡检者获得治理写权，或演练夹具在生产造出带 `RP-<simulationId>` 命名、`capabilities` 近乎全 false 的假发布包，污染指针对照表。

## D9 与执行账本只写不读
- **分类**：架构设计
- **动机（避坑）**：现象——为了让「部署样本」更可信，把 `xpert-agent-execution` 执行账本 join 进闸门统计（或用执行记录反查观测是否漏报）；后果——两个域的写入节奏被绑死、本域读到一个自己无法保证一致性的账本，闸门结论会因账本延迟/回填而抖动，且「观测」与「执行」的重复计数无法界定唯一来源。
- **决策**：本域与执行/会话面**单向解耦**——评估与候选阶段经 `CommandBus` 写**真实 ChatKit 会话与执行账本**（`ChatConversationUpsertCommand`/`ChatMessageUpsertCommand`/`XpertAgentExecutionUpsertCommand`，RUNNING → SUCCESS/ERROR），但**从不读取、不订阅**执行账本与 `agent-invocation`（模块内两域引用 0 命中，`@OnEvent` 0 命中）；闸门只认 `ReleaseDeployment` 上的观测累加值，观测重复只靠 `observationId` 幂等。
- **背景约束**：**口径校订（必读）**：任务书措辞为「本域不写执行账本」，与实现层事实不符——本域**确实会单向写**执行账本行（只写不读）。因此本决策的准确表述是「**只写不读、无关联校验**」：`xpert-agent-execution` 是单向出边，不是读依赖。转录可用性也**不影响结论**（源码逐字：`Transcript availability must never change evaluation, approval or publication outcomes.`），SSE 失败被 `logger.warn` 静默吞掉（注释：`Persisted messages and runtime state remain authoritative when live delivery fails.`）。
- **被否决方案**：无显式否决记录；边界以「不读执行账本」的方向性约束明写（实现层 [01-架构.md](file://.module-experts/后端专题/Agent 演进专家/implementation/01-架构.md)——「**不读执行账本**，对 `xpert-agent-execution` 是单向写」）。
- **重新评估触发条件**：若确实需要账本↔观测对账，必须新增显式关联列与幂等规则（当前**无关联列、无校验**），且对账只能在离线侧做，不得进入闸门判据。
- **关联代码**：`file://packages/server-ai/src/agent-evolution/changes/execution-conversation.service.ts`、`file://packages/server-ai/src/agent-evolution/application/agent-evolution-runtime.service.ts`、`file://packages/server-ai/src/agent-evolution/application/evolution-runtime.store.ts`

## D10 变更不整表加三套状态词表
- **分类**：接口契约
- **动机（避坑）**：现象——把「变更」做成一张宽表（同时存 request/candidate/evaluation/approval/release 字段）并就地更新；后果——阶段不可独立演进（改候选字段要动变更表结构）、无法表达「同一变更不同阶段各自权威」，而且「写一半」的中间态会以看似终态的值被读出。
- **决策**：`EvolutionChange` **永远不整表持久化**（文件头逐字：`// Invariants: one Proposal owns request identity; Candidate, Evaluation, Approval and Release` / `// are authoritative for their own stage. EvolutionChange is assembled, never persisted whole.`），由 `EvolutionChangeStore.assemble` 从 proposal / candidate / evaluation_run / approval / release_package **五表拼装**；变更阶段入口唯一收敛在 `EvolutionChangeService`（`prepare → build → evaluate → process → decide → publish`）。
- **背景约束**：代价是**三套状态词表并存**——候选状态机、发布状态机各自独立，再经 `fromCandidateStatus`/`toCandidateStatus` 双向映射到「变更状态」（`expired↔stale`、`packaged↔publishing`、`evaluation_failed↔test_failed`）；任何读变更都要跨 4~5 张表，且「写一半」的中间态由 `status` + `stages` 双份表达（读侧必须同时看两者）。`process()` 是幂等 worker：非可推进状态时把残留的 `pending|queued|running` job 收尾成 `completed`，推进时**先提交 running 阶段再调外部 provider**，让读侧能看到进度。
- **被否决方案**：「把 `EvolutionChange` 整表持久化」——被文件头不变量注释直接排除（`assembled, never persisted whole.`）。
- **重新评估触发条件**：若读侧出现高频跨表拼装的性能问题，应加**只读投影**（或物化视图）而不是让变更落成宽表；投影必须可重建，且不得成为写路径的事实来源。

## D11 回滚单向前推
- **分类**：兼容处理
- **动机（避坑）**：现象——把回滚实现成「撤销激活」（状态回到 `canary`、指针 revision 回退）；后果——历史被改写、审计链断裂，且下一个人无法从数据判断「曾经激活过又退回来了」，误回滚可被反复掩盖。
- **决策**：回滚只**前推**——`rollbackPointerCas` 成功后 release 落 `rolled_back`、指针 `revision` **+1**（不回退），并在迁移表中把 `rolled_back` 设为**终态**（`RELEASE_TRANSITIONS.rolled_back = []`）；`paused` 是唯一可双向的中间态（`paused → shadow|canary|rolled_back`），因此「回退一档」只能经 `pause` 表达。
- **背景约束**：代价是**误回滚不可逆**——回不到原 canary 档，只能重新走 `install → shadow → canary`；且 `startCanary` 从 `paused` 恢复时依赖 `latest.channel`（shadow 只准 5%、canary 只准下一档），**部署历史顺序成了隐式状态**。CAS 冲突抛普通 `Error`（表现为 5xx 而非 409），前端无法据此做重试语义。
- **被否决方案**：`rolled_back → canary` 的迁移——被迁移白名单物理排除（该状态的目标数组为空数组，`assertReleaseTransition` 直接抛 `Illegal release transition: rolled_back -> canary`）。
- **重新评估触发条件**：需要「快速回切再重放」时，应新增一个显式状态（例如 `superseded` 已用于被新版本取代的场景）并定义其迁移，**不得**把 `rolled_back` 改回可迁移；同时若消费方需要重试语义，应把 CAS 冲突改为显式冲突响应。

- **证据来源**：源码 `evolution-state.ts` 逐字：`rolled_back: []`、`paused: ['shadow', 'canary', 'rolled_back']`、`throw new BadRequestException(\`Illegal release transition: ${from} -> ${to}\`)`；实现层 [02-实现.md](file://.module-experts/后端专题/Agent 演进专家/implementation/02-实现.md)「技术债与 hack」4——「误回滚只能重走 `install`」。

## D12 无 SQL 迁移
- **分类**：技术选型
- **动机（避坑）**：现象——为一个仍在快速演进的 19 表域引入手写、需人工排序的 DDL 迁移；后果——在「表结构事实来源」上引入第二份真相（迁移文件 vs 实体注解），实体改了而迁移没补的情况会在运行期以「列不存在」暴露。
- **决策**：**不引入 SQL 迁移**——`agent-evolution` 目录无 `migrations/`，全仓 `*.sql` 内 `agent_evolution` 零命中；19 表 DDL 的**唯一事实来源是实体注解**（`AGENT_EVOLUTION_ENTITIES`），建表/改表由 TypeORM 实体同步或插件 schema 预检（`PluginSchemaSyncService.synchronize`）承担。
- **背景约束**：部署含义是硬性的——`DB_SCHEMA_SYNC_MODE=external` 时数据源被强加 `synchronize: false`，必须确保 schema-sync 作业在**新版本 API 开始服务前**已同步这 19 张表，否则表现为运行期「表不存在」而不是启动失败；**回滚应用版本不会回退表结构**，新增列/索引会残留在库中。集成测试自建 schema（`agent_evolution_test_<pid>`）。
- **被否决方案**：无显式否决记录（现状是「依赖实体同步建表」的事实选择，实现层以**技术债/风险**而非「否决方案」的形式记录）。
- **重新评估触发条件**：当本域需要「可审计、可回滚的 DDL」时（多实例灰度、正式合规审计、需要回退列级变更），应改为版本化迁移并把实体同步降为校验；届时必须一次性补齐 19 表的历史 DDL 基线。
