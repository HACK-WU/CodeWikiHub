# C5 关键决策（模型访问与计费专家）

> 每条含：分类（单选）/ 动机 / 决策 / 背景约束 / 被否决方案 / 重新评估触发条件 / 关联代码 / 证据来源。优先收录有文档或源码证据的决策；「被否决方案」无记录即写「无」，不编造。本组 9 条均有证据，无 `[推测]` 条目。

## D1 grant 只服务一次执行，且授权快照只会更严

- **分类**：架构设计
- **动机**：避坑。现象：若凭据等同于「用户级通用模型密钥」，同一容器内的多次执行会共享预算与授权；后果：撤销一次执行无法止损，付款人归属与单次执行台账被抹平，事后无法按执行维度对账。
- **决策**：`ModelExecutionGrant` 绑定一次 CLI 会话 / Agent Invocation / Shell 子执行，签发时快照 tenant、runtime organization、用户、Assistant 与已发布版本、会话、环境实例或 binding revision、工具与精确版本；`validate`/`revalidate` 每次请求重查账号、组织访问、发布态与模型权限，并且只允许收紧（`tightenExecutionLimits`）；放宽策略不会给已签发 grant 增加模型、协议或预算；默认模型被移除即拒绝继续使用。
- **背景约束**：执行可能长时间运行、容器可能被替换；模型删除/Provider 替换/访问撤销必须即时失效；`assistant-default` 必须映射签发时固定的默认模型。
- **被否决方案**：无（文档未记录候选方案）。
- **重新评估触发条件**：出现「跨执行复用凭据」或「长生命周期凭据」的业务要求时；grant 快照字段与租户策略 schema 出现漂移时。
- **关联代码**：[execution-grant.service.ts](file://packages/server-ai/src/model-execution/execution-grant.service.ts)、[execution-policy.defaults.ts](file://packages/server-ai/src/model-execution/execution-policy.defaults.ts)、[execution.entity.ts](file://packages/server-ai/src/model-execution/execution.entity.ts)
- **证据来源**：[docs/model-execution.md](file://docs/model-execution.md)（Authorization Scope of an Execution：`It applies to that execution; it is not a general-purpose model key`、`Existing authorization snapshots can only become more restrictive`）

## D2 预算无隐式默认，且「未知费用 ≠ 免费」

- **分类**：接口契约
- **动机**：避坑。现象：给 `tokenBudget`/`userTokenBudget` 设一个隐性默认值，会让未配置租户表现成「有上限」；后果：真实成本超限时无告警可归因，且估算值被误读为事实（未知消费被当作 0 消费）。
- **决策**：`tokenBudget` / `userTokenBudget` 均为可选，未配置时不参与准入，仅显式保存的额度生效；准入用「估算输入 + 请求输出长度（缺省取 catalog 输出上限）」做预占，估算**不**注入额外 `max_tokens`，不作为用量事实；未知结果一律保留预占并进入 `settlement_pending`，由权威证据或人工核对释放。
- **背景约束**：单笔在途请求无法给出严格金额上界；`pricingStatus` 存在 `priced`/`free`/`unpriced`（查询侧还有未解析的 `pending`）三态；`unpriced` 与「免费」必须可区分。
- **被否决方案**：按存量策略/授权里的 `maxInputTokens` / `maxOutputTokens` 做每请求硬上限——这两个字段被读入后丢弃、不做数据迁移（文档明写 legacy 字段 accepted then discarded）。
- **重新评估触发条件**：业务提出「严格货币预算/硬性成本上限」要求时（文档明确 token budget 不保证资金上界）；需要把 `unpriced` 自动折算为 0 时（目前禁止）。
- **关联代码**：[execution-admission.service.ts](file://packages/server-ai/src/model-execution/execution-admission.service.ts)、[execution-usage-schema.ts](file://packages/server-ai/src/model-execution/execution-usage-schema.ts)、[execution-policy.defaults.ts](file://packages/server-ai/src/model-execution/execution-policy.defaults.ts)
- **证据来源**：[docs/model-execution.md](file://docs/model-execution.md)（Budget Admission and Metering：`Token budgets have no implicit defaults`、`an unknown charge must remain distinct from a free call`、四态结算表）

## D3 usage fact 先落库、再投递（outbox 式），按 attempt 幂等

- **分类**：架构设计
- **动机**：避坑。现象：把账本写入放在上游调用返回的同一路径上；后果：投递失败即丢费，重试又可能重复扣费，且无法区分「调用失败」与「已产生用量」。
- **决策**：`ModelGatewayCall.usageFact` 作为不可变事实先落库（`isDeepStrictEqual` 拒绝同一 attempt 的第二份不同事实），再由 `CopilotTokenRecordCommand` 投递，`ModelUsageDeliveryReceipt` 记录回执；捕获 `ExceedingLimitException` 时必须查到回执 `status='completed'` 才算已投递；`@Interval(30_000)` 补投递 + `recoverAbandonedExecutionCalls`（未派发→`failed` 释放预占，已派发→`settlement_pending` 保留预占）。
- **背景约束**：投递通道可能部分失败；父 Assistant 与子 Invocation 会分别展示，但一次模型调用只能扣一次费；事实与估算必须物理隔离。
- **被否决方案**：以估算（`estimatedUsage`）补记一笔消费——估算被隔离在 `executionUsageEstimateSchema`，永不进入事实 schema；对账 `no_usage` 也不允许伪造实际用量行。
- **重新评估触发条件**：出现「投递成功但事实缺失」的可复现案例时；30 秒轮询延迟成为业务瓶颈时。
- **关联代码**：[execution-metering.service.ts](file://packages/server-ai/src/model-execution/execution-metering.service.ts)、[execution-recovery.ts](file://packages/server-ai/src/model-execution/execution-recovery.ts)、[model-usage-delivery-receipt.entity.ts](file://packages/server-ai/src/copilot-usage/model-usage/model-usage-delivery-receipt.entity.ts)
- **证据来源**：[docs/model-execution.md](file://docs/model-execution.md)（`Usage facts are persisted before delivery to the ledger`、结算行为表）、[docs/operations/model-execution-runbook.md](file://docs/operations/model-execution-runbook.md)

## D4 积分集中在单一账本，唯一索引是幂等底线

- **分类**：架构设计
- **决策**：所有扣减与调整都写 `membership_point_ledger`（事实行 `source='model_usage'` 与扣减行共表，靠 `source` 区分；个人积分行以 `:personal` 后缀区分），幂等由 `IDX_membership_ledger_source_reference`（UNIQUE）与 `UQ_membership_ledger_model_usage_request_metric_revision`（UNIQUE）在数据库层兜底；`recordUsage`/`recordGatewayUsage` 在事务内先取锁再查重，命中即返回既有结果。
- **动机**：避坑。现象：多个扣费来源（copilot-usage 事实、model-execution 投递、model-gateway 结算与留存归档）各写各表；后果：重复扣费无法在数据库层拦截，对账口径分裂。
- **背景约束**：三/四个模块共享该表；`pointsDelta numeric(28,10)` 支持小额与负值；读模型用反连接避免事实行与扣减行双计；`excessPoints > 0`（已知未扣满）与 `unpriced`（未知）必须分开呈现。
- **被否决方案**：无（未记录候选方案）。
- **重新评估触发条件**：列语义变更导致四方口径互相牵制时；`model-usage-charge:` 与 `:personal` 硬编码前缀需要收敛时。
- **关联代码**：[membership-point-ledger.entity.ts](file://packages/server-ai/src/membership/membership-point-ledger.entity.ts)、[membership.service.ts](file://packages/server-ai/src/membership/membership.service.ts)、[model-usage-ledger.service.ts](file://packages/server-ai/src/copilot-usage/model-usage/model-usage-ledger.service.ts)、[model-gateway-call-retention.ts](file://packages/server-ai/src/model-gateway/model-gateway-call-retention.ts)
- **证据来源**：[membership-point-ledger.entity.ts](file://packages/server-ai/src/membership/membership-point-ledger.entity.ts) 索引定义、[.module-experts/会员与积分账本子专家 03-数据流转](file://.module-experts/后端专题/模型访问与计费专家/sub-experts/会员与积分账本子专家/implementation/03-数据流转.md)

## D5 网关独立于执行，且客户端 scope header 不选择租户/组织

- **分类**：安全合规
- **动机**：避坑。现象：让客户端通过请求头/请求体声明租户、组织或付款人；后果：可跨租户冒用额度，凭据作用域与执行作用域错位，事后无法判定付款主体。
- **决策**：`/api/openai/v1`（API key）与 `/api/model-execution/*`（execution credential）是两套独立入口与两套凭据；API key scope 只用于解析访问，执行发生在 publication scope；execution grant 的 scope 只来自平台身份与自有会话；`assistant-default` 只存在于执行侧；平台侧查询/会话/管理端点显式拒绝 API principal 并要求 tenant/organization/user 三重相等。
- **背景约束**：两套入口均为 `@Public()`（无 `@Permissions`），安全性完全依赖各自 `authenticate` 与 scope 校验；错误体与模型别名也随之分化。
- **被否决方案**：无（未记录候选方案；文档强调不得复用登录态或 ChatKit client secret）。
- **重新评估触发条件**：出现「合并两套 OpenAI 兼容入口」的提案时（当前已被列为技术债，合并需同时改两套错误映射与 scope 解析）；任何新增 `@Public()` 入口时。
- **关联代码**：[openai.controller.ts](file://packages/server-ai/src/model-gateway/openai.controller.ts)（首行 Invariants 注释）、[execution-openai.controller.ts](file://packages/server-ai/src/model-execution/execution-openai.controller.ts)、[execution-query.controller.ts](file://packages/server-ai/src/model-execution/execution-query.controller.ts)
- **证据来源**：[openai.controller.ts](file://packages/server-ai/src/model-gateway/openai.controller.ts)（`client scope headers do not select the gateway's tenant or organization`）、[docs/model-execution.md](file://docs/model-execution.md)（API and Identity Boundaries）

## D6 native 协议默认关闭，必须由 catalog 显式声明

- **分类**：兼容处理
- **决策**：`nativeProtocols`（`openai_responses`、`anthropic_messages`）默认关闭，需租户策略与模型 catalog 的 `protocols` 双声明；未声明时走版本受限的 `chatBridgeProtocols` 转换，快照分别记为 `openai_responses_chat` / `anthropic_messages_chat`；传输在签发时固定，两条路径都可用时 native 优先；无法等价转换的字段（native thinking、加密推理、多媒体、hosted tools、嵌套 namespace、严格 JSON schema 等）在调用 provider 前拒绝。
- **动机**：避坑。现象：按 Provider 名称推断协议兼容性或对未知字段做静默丢弃；后果：请求语义被悄悄改变、上游报错不可归因，且 CLI 与模型的真实兼容性无法验证。
- **背景约束**：native 能力因 provider/模型而异；`Responses` 强制 `store:false` 并拒绝 background 与服务端会话引用；输入端仅支持内联文本与客户端工具。
- **被否决方案**：native 失败后自动改走 Chat 重试或扩大授权——文档明确排除（`A native failure does not trigger a retry through Chat or expand authorization`）。
- **重新评估触发条件**：新增 native 协议或新增 CLI 版本需要进入兼容清单时（必须复核请求形状、多轮工具调用、取消与逐次计量）；多媒体/文件引用能力开放时。
- **关联代码**：[execution-native.controller.ts](file://packages/server-ai/src/model-execution/execution-native.controller.ts)、[execution-native-protocol.ts](file://packages/server-ai/src/model-execution/execution-native-protocol.ts)、[execution-chat-bridge-request.ts](file://packages/server-ai/src/model-execution/execution-chat-bridge-request.ts)、[execution-policy.defaults.ts](file://packages/server-ai/src/model-execution/execution-policy.defaults.ts)
- **证据来源**：[docs/model-execution.md](file://docs/model-execution.md)（Model Protocols 表与 Chat 转换边界段）

## D7 self-audit 阻断：申请人不得同时是该范围的管理者

- **分类**：安全合规
- **动机**：避坑。现象：同一用户既能提交模型访问申请、又持有该范围的审批权限；后果：可自批自用，`model_access_event` 的审批留痕失去互证价值，授权台账不再有独立复核环节。
- **决策**：`createRequest` 在写库前调用 `assertRequesterIsNotManager`：`canManageTargetScope` 命中（作用域匹配且持有 `COPILOT_EDIT` / `MEMBERSHIP_EDIT` / `MODEL_ACCESS_REQUEST_EDIT` 之一）即抛 403，错误文案固定为「Users who manage this scope cannot request personal model access」。
- **背景约束**：管理员对特权用户存在自动批准的旁路（内部调用 `approveRequest`），因此个人申请入口必须单独阻断；审批侧仍需人工理由与有效期。
- **被否决方案**：无（未记录候选方案）。
- **重新评估触发条件**：出现「管理员也必须走个人申请流程」的业务需求时；权限点集合调整时需同步更新 `canManageTargetScope`。
- **关联代码**：[model-access.service.ts](file://packages/server-ai/src/model-access/model-access.service.ts)（`createRequest` → `assertRequesterIsNotManager` → `canManageTargetScope`）
- **证据来源**：源码方法体（i18n key `Error.ModelAccessManagerCannotRequest`）、[.module-experts/模型访问与执行子专家 02-实现](file://.module-experts/后端专题/模型访问与计费专家/sub-experts/模型访问与执行子专家/implementation/02-实现.md)

## D8 `select:false` 敏感列的读取约定：必须显式 addSelect

- **分类**：安全合规
- **决策**：`model_execution_grant.credentialHash`、`model_gateway_api_key.tokenHash`/`encryptedSecret`、`model_gateway_call.usageFact`/`settlementContext`/`encryptedRequest`/`encryptedResponse` 一律声明 `select: false`，默认不参与查询；鉴权加 `tokenHash`、个人 Key 列表加 `encryptedSecret`、结算重试加 `settlementContext`、执行用量投递加 `usageFact`、管理取证加 `encryptedRequest`+`encryptedResponse`；明文只在签发/创建响应出现一次。
- **动机**：避坑。现象：敏感列随默认查询进入日志、序列化体或宽表返回；后果：凭据哈希与密文泄漏面扩大（`@Exclude` 只保护序列化，不保护查询层）。反向代价同样明确：漏写 `addSelect` 不报错，只静默拿到 `undefined` 并跳过投递。
- **背景约束**：`encryptedSecret` / 调用体密文受 `SECRETS_ENCRYPTION_KEY` 保护，轮换前必须确认既有密文仍可解密；`tokenHash` / `credentialHash` 为 sha256，不受该密钥影响。
- **被否决方案**：无（未记录候选方案）。
- **重新评估触发条件**：出现「事实已落库但未投递」的静默跳过案例时（优先怀疑 `addSelect` 漏写）；`SECRETS_ENCRYPTION_KEY` 轮换或密钥派生方式变更时。
- **关联代码**：[execution.entity.ts](file://packages/server-ai/src/model-execution/execution.entity.ts)、[model-gateway-api-key.entity.ts](file://packages/server-ai/src/model-gateway/model-gateway-api-key.entity.ts)、[model-gateway-call.entity.ts](file://packages/server-ai/src/model-gateway/model-gateway-call.entity.ts)、[execution-metering.service.ts](file://packages/server-ai/src/model-execution/execution-metering.service.ts)（`deliver`）
- **证据来源**：[.module-experts/模型访问与计费专家 07-运维](file://.module-experts/后端专题/模型访问与计费专家/implementation/07-运维.md)（安全运维段）、[.module-experts/模型访问与计费专家 04-模型](file://.module-experts/后端专题/模型访问与计费专家/implementation/04-模型.md)（已知风险）

## D9 多副本下的幂等定时任务：进程内 Interval + Redis 锁 / cursor / advisory lock

- **分类**：架构设计
- **决策**：需要「同 tick 只跑一次」的任务用 Redis 锁（`scheduler:model-access-lifecycle`、`scheduler:membership-period-settlement`，TTL 5 分钟）+ CACHE_MANAGER cursor（`model-access:lifecycle-cursor:v1`，TTL 24 小时）或 PG 会话级 `pg_try_advisory_lock`（检查点留存）；纯重放型维护任务（网关 5 个 `@Interval`、metering/reconciliation 的 30 秒重试）不加锁，改为按状态过滤小批量 + 唯一索引幂等 + `FOR UPDATE OF c SKIP LOCKED`；积压指标明示为进程本地量、多副本不可相加。
- **动机**：避坑。现象：`@Cron`/`@Interval` 随每个 API 副本各自注册；后果：多副本并跑导致重复结算、重复失效与重复告警（正确性靠唯一索引兜底，但产生写放大与噪声指标）。
- **背景约束**：部署为多 API 副本共享同一数据库，没有集中式调度器；锁获取失败即跳过本轮、仅降级为日志；游标丢失则从头扫描。
- **被否决方案**：无（未记录候选方案；未引入集中式 scheduler）。
- **重新评估触发条件**：引入集中式调度/单副本 worker 时；把积压指标改为分布式聚合时（当前按实例展示或取 max）。
- **关联代码**：[model-access-scheduler.service.ts](file://packages/server-ai/src/model-access/model-access-scheduler.service.ts)、[membership-period-scheduler.service.ts](file://packages/server-ai/src/membership/membership-period-scheduler.service.ts)、[retention.service.ts](file://packages/server-ai/src/copilot-checkpoint/retention.service.ts)、[model-gateway.service.ts](file://packages/server-ai/src/model-gateway/model-gateway.service.ts)
- **证据来源**：[docs/operations/model-execution-runbook.md](file://docs/operations/model-execution-runbook.md)（指标多副本口径）、[docs/operations/model-execution-alerts.yml](file://docs/operations/model-execution-alerts.yml)、[.module-experts/模型访问与计费专家 07-运维](file://.module-experts/后端专题/模型访问与计费专家/implementation/07-运维.md)（定时任务与队列表）
