## 核心流程实现位置

### ① 模型访问审批与 grant 生命周期

- 申请：`ModelAccessService.createRequest` 先 `assertRequesterIsNotManager`，再校验目标模型与范围，写 `ModelAccessRequest` 并 `writeEvent` 记录 `ModelAccessEventTypeEnum` 迁移。
- 审批：`approveRequest` 生成 `UserModelGrant`（含有效期与来源），`rejectRequest` 关闭申请；`extendGrant`/`revokeGrant` 调整授权；管理员入口带 `@Permissions(AIPermissionsEnum.MODEL_ACCESS_REQUEST_EDIT)`。
- 执行凭据：`ModelExecutionGrantService.issue` 在 policy 校验工具版本后签发，凭据明文只在签发响应出现，库中仅 `credentialHash`；`authenticate`/`validate`/`revalidate` 每次请求重查账号、组织、Assistant 发布态与模型权限。
- 生命周期：`processDueGrants` 处理到期，`reconcileLifecycleBatch` 按 cursor 批量协调，`handleCopilotStateChanged` 处理 Copilot 启停；`ModelAccessSchedulerService` 以 `@Cron('0 * * * * *')` 与 Redis cursor `model-access:lifecycle-cursor:v1` 驱动增量批次。

章节来源：[packages/server-ai/src/model-access/model-access.service.ts](file://packages/server-ai/src/model-access/model-access.service.ts)（关键符号：ModelAccessService.reconcileLifecycleBatch）

### ② 执行准入预占与 usage fact 投递

- 准入：`ModelExecutionAdmissionService.begin` 先 `pg_advisory_xact_lock`（`model-execution:{tenantId}:{ownerId}`）再悲观锁 grant，按 `grant.limits.tokenBudget`、`userTokenBudget`、`maxConcurrentRequests`、`requestsPerMinute` 及 shell 父执行聚合预算判定，落 `ModelGatewayCall`（`status=started`、`reservedTokens`）。
- 派发：`dispatch` 在事务内二次确认状态与预算并写 `dispatchedAt` 一次性标记（"A crash after this point retains the reservation"）。
- 落账事实：`ModelExecutionMeteringService.finish` 事务内锁读调用，`isDeepStrictEqual` 校验 fact 一致性，落不可变 `usageFact` 与 `settlementContext`，实际用量即释放 `reservedTokens`。
- 投递：`deliver` 发 `CopilotTokenRecordCommand`，投递回执由 `ModelUsageDeliveryReceipt` 承载；`@Interval(30_000)` 补投递 + `ModelExecutionReconciliationService`（同频）重试未完成对账，`@Interval(30_000)` 之外无隐式重发。

章节来源：[packages/server-ai/src/model-execution/execution-admission.service.ts](file://packages/server-ai/src/model-execution/execution-admission.service.ts)（关键符号：ModelExecutionAdmissionService.dispatch）

### ③ 网关 startCall/finishCall 与结算重试

- 认证与目录：`ModelGatewayService.authenticate(authorization)` → `listAccessiblePublications`（`/api/openai/v1/models` 返回 `{object:'list', data:[{id, object:'model', owned_by:'xpert'}]}`）。
- 准入：`startCall` 事务内 `lockedUser` 悲观锁用户行，`GatewayAdmissionPolicy.getAdmissionLimits` 读 `TenantSetting`，超限抛 `ModelGatewayRequestLimitException`（携带 `retryAfterSeconds`）。
- 执行：`executeGatewayChat` 复用同一协议执行器，`finishCall` 统一结算；`recordSettlementFailure` 把调用置回 `settlement_pending`。
- 重试与留存：`retryPendingSettlements`（`GATEWAY_MAINTENANCE_INTERVAL_MS = 5 * 60 * 1000`）重放 `source='external_api'` 的待结算调用；另有 body 清理、调用留存清理、key 过期、stale call 失败化共 5 个 `@Interval`。

### ④ 积分记账与周期结算

- 记账入口：`MembershipService.recordUsage`（按 `sourceReference`）与 `recordGatewayUsage`（按 `gatewayRequestId`）都在 `dataSource.transaction` 内先取锁再查重，命中即返回既有账本。
- 金额与积分：`resolveTenantCnyPerPoint` + `calculatePointsFromCny` 折算，`model-billing.ts` 的 `settleChargeToCny` 统一币种；`pointsDelta` 以 `numeric(28,10)` 存储，超额部分记 `excessPoints`。
- 校验面：`findModelAccessWithOrganizationSelfHeal` 解析会员+模型访问（含组织自愈写），`hasConsumableBalance`、`assertCanUse`、`assertRateLimits` 在调用前拦截。
- 周期结算与回填：`MembershipPeriodSchedulerService.settleDueMembershipPeriods` 以 `@Cron('0 * * * * *')` + Redis 锁调用 `processDueMembershipPeriods`；默认会员回填走 `MEMBERSHIP_MAINTENANCE_QUEUE`（`MembershipBackfillQueueService`，`attempts: 5`）。

## 设计模式及落点

- **CQRS**：配置与解析面全量走 `CommandBus`/`QueryBus`——`copilot-model` 的 `CopilotModelGetChatModelQuery`/`CreateModelClientCommand`、`copilot` 的 `CopilotOneByRoleQuery`、`copilot-usage` 的台账查询、`ai-model` 的 `AIModelGetIconQuery`。
- **Outbox（先落事实后投递）**：`ModelGatewayCall.usageFact` + `ModelUsageDeliveryReceipt` 构成执行侧 outbox，`CopilotTokenRecordCommand` 为投递通道，`attemptId`/`requestId` 为幂等键。
- **分布式锁**：DB 层 `pg_advisory_xact_lock`（准入）与 Redis 锁（`scheduler:membership-period-settlement`、`model-access:lifecycle-cursor:v1`）、PG advisory 锁（checkpoint 留存 `RETENTION_CRON_LOCK_KEY`）三层并用。
- **策略/声明式能力**：`GatewayAdmissionPolicy` 决定网关限额；`nativeProtocols`/`chatBridgeProtocols` 由 catalog 声明，native 默认关闭；`CliModelProfilesCapability` 决定 CLI 工具与版本可用性。
- **模板方法/共享执行器**：`executeGatewayChat` 让 API key 与 execution 两条链路共用同一 stream/settle 生命周期。
- **幂等表 + 唯一索引**：`membership_point_ledger` 用 `IDX_membership_ledger_source_reference` 与 `UQ_membership_ledger_model_usage_request_metric_revision` 兜底重复投递。

## 热点路径

- **每次模型调用的准入 + 记账**：`begin`（advisory lock + 悲观锁 + 聚合查询）→ `dispatch` → provider 调用 → `finish`（事务 + fact 落库）→ `deliver`（命令 + 回执），是延迟最敏感的串行段。
- **网关限流**：`startCall` 内每分钟窗口计数与并发计数各一次查询 + `getAdmissionLimits` 读 `TenantSetting`，属于每请求固定成本。
- **会员解析**：`findModelAccessWithOrganizationSelfHeal` 在 `recordUsage`/`recordGatewayUsage`/`assertCanUse` 中重复调用，可能触发隐式写入。
- **对账与补投递轮询**：metering 与 reconciliation 的 `@Interval(30_000)`、gateway 的 5 分钟维护循环，均按状态过滤小批量扫描。

## 技术债与 hack

- **两个 OpenAI 兼容入口并存易混**：`/api/openai/v1`（API key + publication）与 `/api/model-execution/openai/v1`（execution credential + grant）语义不同，错误体也不同（`rate_limit_error` vs `code:'model_execution_failed'`）；`assistant-default` 只存在于后者。
- **`@Public()` 控制器靠凭据自证**：`ModelExecutionOpenAIController`/`ModelExecutionNativeController`/`ModelGatewayOpenAIController` 无 `@Permissions`，安全性完全依赖 `authenticate` 与 grant 校验，边界脆弱。
- **Query/Session controller 无 `@Permissions`**：`ModelExecutionQueryController.options|list` 靠 `tenantId/organizationId/userId` 三重相等 + `currentApiPrincipal()` 判空拒绝；漏改一处即越权。
- **GET 有副作用**：`ModelGatewayService.getSettings` 内部调用 `getOrCreateSettings`，读接口会写 `ModelGatewaySettings` 行。
- **`copilot_store_vectors` 的 `@Entity` 被注释**：`copilot-store/vectors/vectors.entity.ts` 中实体装饰器处于注释状态，向量表只经 `store.ts` 原生 SQL 使用，ORM 层与表结构存在漂移风险。
- **TIMER 多副本并发**：所有 `@Cron`/`@Interval` 在多副本部署下都会并跑，仅靠 Redis/PG 锁去重，锁过期或未加锁的循环（如 gateway 维护）可能重复执行。
- **`findModelAccessWithOrganizationSelfHeal` 隐式写**：查询路径带自愈写入，读接口可能在会员数据缺失时修改状态，审计与复现困难。
- **对账禁忌写入运行手册**：不得以估算补单、直接改库或手动减预占（[docs/operations/model-execution-runbook.md](file://docs/operations/model-execution-runbook.md)）。

## 设计维度分析

**维度一：一致性与幂等。** 三层防线互相补位——DB 唯一索引（`IDX_membership_ledger_source_reference`、`UQ_membership_ledger_model_usage_request_metric_revision`）保证账本不会双扣；`usageFact` 不可变 + `isDeepStrictEqual` 校验保证同一 attempt 重试不产生新证据；`dispatchedAt` 一次性标记保证同一 attempt 不会二次派发。代价是"未知结果"必须长期占用预占，需靠人工对账收敛。

**维度二：信任边界与凭据最小化。** 客户端 scope header 不参与租户/组织选择，scope 只从自有会话与 API key 解析；凭据仅存 hash 且授权快照只允许更严；管理端点（`/api/model-execution/admin/*`）与用户端点分离，`reconcile` 显式拒绝 API principal。代价是执行期每次请求都要重查账号/组织/发布态，带来额外读放大。

**维度三：失败可观测与人工闭环。** 用量事实与投递状态分离（`usageDeliveredAt`、`delivered`），指标 `applicationMetrics.recordModelExecution('admitted'|'provider_usage'|'usage_pending')` 与 alert 规则配套，`applied` 不等于投递成功这一区分被写进文档，避免把对账应用误读为已扣费。

## 结论

实现层面四条主流程各自闭环：授权/审批以事件流留痕，执行准入以 DB 串行化 + 预占保序，网关以 API key 面复用同一执行器并保留结算重试，积分账本以唯一索引为幂等底线。演进建议集中在三处：合并或强区分两套 OpenAI 兼容入口、给 Query/Session 类控制器补权限声明、把 `getSettings` 与自愈读取的写副作用移出读路径。测试覆盖约 71 个 spec（model-execution 24、membership 7、copilot-usage 6、copilot 6、model-access 5、model-gateway 5、copilot-model 5、copilot-user 5、copilot-provider 4、copilot-checkpoint 4），PG 集成用例受 `XPERT_EXECUTION_TEST_DATABASE_URL` 门控（库名前缀 `xpert_execution_test_`），无 PG 时自动 skip；`copilot-organization`/`copilot-knowledge`/`copilot-store`/`ai-model` 无 spec（仅 `copilot-store` 有 2 个 `.test.ts`）。
