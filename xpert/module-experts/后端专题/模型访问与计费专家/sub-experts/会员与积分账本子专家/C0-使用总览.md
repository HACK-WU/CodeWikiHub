## 定位与何时找

一句话：**上游决定「这笔消费是多少」，本子域决定「记在谁头上、以什么额度扣、什么时候换期」**。它是模型调用的唯一扣费出口，也是唯一持有积分账本写权限的地方。

找这个子专家的场景：

- 要写入或排查一笔模型消费的积分扣减（谁被扣、扣了多少、为什么没扣）。
- 要判断某用户此刻能不能用会员/积分调用模型；调用被拦下时定位是限流、额度还是白名单。
- 要调整会员额度或个人积分（人工补分、纠错、赠送）。
- 要管理会员套餐（额度、周期、允许模型、倍率、限流规则）与分配/续费/暂停/恢复/撤销。
- 要处理周期结算、外部履约追加期次、未来期次退款与单期撤销。
- 要做用量读侧（个人会员总览、本期消费、按小时/模型/渠道的汇总与审计）。
- 要开通某租户/组织的默认会员（默认套餐 + 默认会员初始化与批量回填）。

不要找这个子专家的场景：模型调用与网关协议、provider 凭据、Copilot 配置（见子专家③）；授权台账与执行准入（见子专家①）；对话与会话本体（不在本专家域内）。

## 边界

**做什么**

- 积分账本的唯一写通道（`recordUsage` / `recordGatewayUsage`）与全部人工/系统调整入口。
- 会员资格、额度、模型白名单、倍率、限流的判定与调用前拦截。
- 会员计划、会员分配、期次状态机、周期结算、续费与退款。
- 默认套餐/默认会员的初始化与批量回填（含 `EVENT_FEATURE_ORGANIZATION_UPDATED` 订阅）。
- 面向本域表的读模型组装（会员概览、用量分页、审计、管理员列表）。

**不做什么**

- **不管模型调用与网关**：不创建模型客户端、不做协议转换、不写网关调用记录、不签 API key、不释放预占；`recordGatewayUsage` 只接收网关已算好的金额。
- **不管 copilot 配置**：`copilot` / `copilot_model` / `copilot_provider(_model)` 的 CRUD、provider 凭据与模型发现属于子专家③。
- 不生成定价与用量事实：本域只消费调用方传入的 `settlementAmount` / `settlementCurrency` / `pricingStatus` / `exchangeRate`；`source='model_usage'` 事实行由 copilot-usage 写入。
- 不管理授权凭据：`user_model_grant` / `model_execution_grant` / `model_gateway_api_key` 属于 model-access 与 model-gateway。
- 不为未知消费编造扣费：`unpriced`、缺金额、非 CNY/RMB/USD 币种、USD 缺汇率一律折算为 `null`，绝不退化为 0。

## 已知坑（12 条）

1. **账本唯一索引是「一次调用只计一次」的底线**
   - 现象：绕过服务层直写账本后出现重复扣费或漏扣，且难以回滚。
   - 触发条件：以仓储或原生语句直接写 `membership_point_ledger`，或自行拼装 `sourceReference`。
   - 正确做法：只经 `recordUsage` / `recordGatewayUsage`；调用方必须提供稳定幂等键（调用路径为 `model-usage-charge:<事实ID>`，个人积分行由服务补 `:personal`）。兜底索引为 `IDX_membership_ledger_source_reference` 与 `UQ_membership_ledger_model_usage_request_metric_revision`。
   - 契约来源：`MembershipService.recordUsage`、`membership-point-ledger.entity.ts`。
2. **资格解析路径带隐式写（self-heal）**
   - 现象：一次 GET 查询后会员/组织范围数据发生变化，复现与审计困难。
   - 触发条件：`findModelAccessWithOrganizationSelfHeal` 命中「请求的组织范围与 Copilot 组织范围一致」且访问的组织不匹配。
   - 正确做法：把这类查询视为可能写库（会开户：建默认套餐 + 默认会员）；需要严格控制副作用时先显式 `ensureScopeInitialized`，再走只读查询。
   - 契约来源：`MembershipService.findModelAccessWithOrganizationSelfHeal` / `MembershipService.findUsableMembership`。
3. **锁的失败语义不显式（8 个 advisory 锁 + 1 个 Redis 调度锁）**
   - 现象：并发下表现为长尾延迟或等待超时，而不是「拿不到锁请重试」这类返回值。
   - 触发条件：8 个 `acquire*Lock` 全部是 `pg_advisory_xact_lock`（阻塞等待 + 事务级自动释放）；连接类型不是 postgres 时**静默跳过加锁**；调度侧 Redis 锁 `scheduler:membership-period-settlement`（TTL 5 分钟）未获取则整轮跳过。
   - 正确做法：把锁等待纳入超时与延迟观测；测试环境（非 postgres）不具备生产并发语义，不能据此判断并发安全。
   - 契约来源：`MembershipService.acquireUsageSourceLock` 等 8 个 `acquire*Lock`、`MembershipPeriodSchedulerService.settleDueMembershipPeriods`。
4. **定时任务是进程内调度，多副本会并跑**
   - 现象：多副本下同一批数据被处理两次，日志重复。
   - 触发条件：`@Cron('0 * * * * *')` 的周期结算与 Bull `MEMBERSHIP_MAINTENANCE_QUEUE` 回填在多副本同时运行。
   - 正确做法：视为「设计为幂等、允许并跑」；Redis 锁 TTL 5 分钟与批 100 条不构成互斥保证，Bull job 无 `jobId` 去重，重复入队会产生重叠批次（由账本幂等键兜底）。账本类指标属进程本地量，跨副本不可相加。
   - 契约来源：`membership-period-scheduler.service.ts`、`membership-backfill.queue.ts`。
5. **`pointsDelta numeric(28,10)` 的精度与舍入**
   - 现象：极小消费被前端显示成 0，或核对时发现末位不一致。
   - 触发条件：`pointsFromCny` 按 10 位小数四舍五入；读侧若对结果二次取整会与账本不符。
   - 正确做法：扣减判定与展示都基于账本原值；`excessPoints > 0` 才是「已知但未扣满」，不要用显示值判断。
   - 契约来源：`model-billing.ts`、`membership-point-ledger.entity.ts`。
6. **定价态决定读侧返回 0 还是 `null`，与 `reconciled_no_usage` 不是同一件事**
   - 现象：前端把「未知」渲染成「0 消费」。
   - 触发条件：读模型对 `pricingStatus='unpriced'`、缺金额、缺汇率返回 `NULL`；只有 `free` 才返回 0。
   - 正确做法：`NULL`（未知）、`0`（免费）、`excessPoints > 0`（已知未扣满）三种口径分开；对账侧 `errorCode='reconciled_no_usage'` 表示**没有权威用量事实**、不写账本。
   - 契约来源：`membership-usage-points.ts`、`docs/operations/model-execution-runbook.md`。
7. **runbook 三禁忌**
   - 现象：人工「修补」后账本与账实更不一致。
   - 触发条件：以估算补单、直接改库、手动减去预占。
   - 正确做法：只用管理端待核对列表 + `retry-delivery` 或 `reconcile` 提交权威证据；`reconcile` 返回 `applied` 也不代表账本已投递。
   - 契约来源：`docs/operations/model-execution-runbook.md`（待核对消费 / 禁忌）。
8. **`recordUsage` 可能静默返回「无账本」**
   - 现象：调用成功但查不到账本行，调用方以为落账失败。
   - 触发条件：金额为 0 或缺失、`modelAccess.accessSource = direct`、该范围未启用会员计划。
   - 正确做法：显式判断返回值是否为 `null`，并区分「免费」「未纳管」「未投递」。
   - 契约来源：`MembershipService.recordUsage` / `MembershipService.recordGatewayUsage`。
9. **`:personal` 后缀与 `model-usage-charge:` 前缀是三处硬编码**
   - 现象：改一处造成统计口径分裂（同一笔消费被计两次或不计）。
   - 触发条件：`model-usage-ledger.service.ts`、`membership-usage-points.ts`、`execution-metering.service.ts` 不同步修改。
   - 正确做法：把来源键当成对外契约的一部分评审；读模型 SQL 里硬编码了前缀与 `('', ':personal')` 两个后缀。
   - 契约来源：`membership-usage-points.ts`（`USAGE_POINTS_SQL` / `USAGE_POINTS_PREDICATE`）。
10. **同一次调用会解析两次会员**
    - 现象：事务内外的会员口径可能不同，出现「precheck 通过但记账时余额已变」。
    - 触发条件：`assertCanUse` 与紧随其后的 `recordUsage` 各自跑一遍 self-heal 与权限查询（只有事务内那次带 `forUpdate`）。
    - 正确做法：不要假设校验与记账之间状态不变；跨进程/跨副本场景下以记账事务结果为准。
    - 契约来源：`MembershipService.assertCanUse` / `MembershipService.recordUsage`。
11. **套餐快照双写，新增字段要同步多处**
    - 现象：给套餐加字段后，激活的历史期次丢失该字段或读到 `undefined`。
    - 触发条件：`createPlanSnapshot` / `copyPlanSnapshot` / `planFromSnapshot`（读取侧另有 `hydrateMembershipPlanSnapshot`）未同步。
    - 正确做法：把 `planSnapshot` 视为「套餐版本随期冻结」，套餐改动不回溯已签发期次。
    - 契约来源：`MembershipService.createPlanSnapshot` / `MembershipService.planFromSnapshot`。
12. **无限额度 ≠ 额度为 0**
    - 现象：对无限额度会员调用调整接口被拒，或界面 `pointsRemaining` 显示为空。
    - 触发条件：`pointsGranted === null` 时 `pointsRemaining` 返回 `null`（不算额度），`adjustUserPoints` 对无限会员直接拒绝。
    - 正确做法：先判 `null` 再判数量；无限额度下 `hasConsumableBalance` 视为可用。
    - 契约来源：`MembershipService.pointsRemaining` / `MembershipService.hasConsumableBalance`。
