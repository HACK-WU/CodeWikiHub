## 流程① 记账幂等事务

- 入口一 `recordUsage(RecordUsageInput)`：先做三道短路——`nonNegativeBillingAmount` 为 0（金额缺失/非正）返回 `null`、`modelAccess.accessSource === Direct` 返回 `null`、`isMembershipAccessEnabled` 为假返回 `null`。随后 `resolveTenantCnyPerPoint` 取租户换算率，再进 `dataSource.transaction`。
- 事务内顺序：`acquireUsageSourceLock`（有 `sourceReference` 时）→ 按 `(tenantId, sourceReference)` 查重命中即直接返回既有账本 → `findModelAccessWithOrganizationSelfHeal(..., manager, true)`（`forUpdate=true`）→ `assertCopilotScopeMatches` + `assertModelAllowed`（`accessSource` 非 Grant 时）→ 结算金额乘倍率 `applySettlementMultiplier` → `calculatePointsFromCny` → 落账。
- 落账分档：`personalPointsOnly` 时只写一条 `personal_usage` 行（`pointsDelta = -min(pointsUsed, 个人积分余额)`，超出部分进 `excessPoints`）；否则先扣会员额度（`pointsUsed += min(pointsUsed, pointsRemaining)`，无限额度时全额），`save(user_membership)` 后调 `synchronizeCurrentPeriodProjection`，再写 `usage` 行，最后若还有余额缺口则 `acquirePersonalPointsLock` + 个人积分余额二次裁剪 + 一条 `sourceReference='<ref>:personal'` 的 `personal_usage` 行。
- 超额处理：`exceeded` 在事务内累积（个人积分不足、`pointsUsed > pointsGranted`），**账本照记**，事务提交后抛 `ExceedingLimitException`。
- 入口二 `recordGatewayUsage(RecordGatewayUsageInput)`：`sourceReference` 由本方法自造为 ``model-gateway:${gatewayRequestId}``，`acquireGatewayRequestLock` 锁 `gatewayRequestId`；无会员访问时写一条 `pointsDelta: 0` 但 `excessPoints = pointsUsed` 的"超额证据行"后返回 `{chargedPoints: 0, excessPoints, ledger}`；有访问时沿用与 `recordUsage` 同构的 会员额度→个人积分 两段扣减，返回 `{chargedPoints, excessPoints, ledger}`。

章节来源：[membership.service.ts](file://packages/server-ai/src/membership/membership.service.ts)（关键符号：MembershipService.recordUsage / MembershipService.recordGatewayUsage / MembershipService.createLedger）

## 流程② 资格与配额判定（含 self-heal 隐式写）

- 开关判定：`isMembershipAccessEnabled` = 组织级 `FEATURE_MEMBERSHIP_PLAN` 开启，或（组织未开启时）租户级开启；`isMembershipPlanEnabledForScope` 是唯一真值来源，`hasActiveMembershipPlan` 额外把 catalog 派生套餐计入。
- 访问解析：`findModelAccess` 先要求至少一个 scope 开关开启，再 `resolveBillableUserId`（xpert 计费付款人设为 RuntimeUser 时用调用者）与 `hasMembershipUsePermission`，然后 组织会员 → （组织有 active plan 时）个人积分 → 租户会员 → 租户个人积分 的回落顺序；`findUsableMembership` 在解析过程中即可能改变状态（见流程③）。
- 个人积分访问：`findPersonalPointsAccess` 在个人积分为 0 时返回 `null`，否则以 `findDefaultPlan` + 合成 `fallbackMembership`（`personalPointsOnly: true`、`pointsGranted: 0`）构造访问对象，周期区间由 `resolveFallbackPeriod` 推导。
- 调用前拦截：`assertCanUse` 对 `Direct` 访问与开关关闭直接放行；无访问抛 `ExceedingLimitException('MembershipPlanRequired')`；`pointsRemaining <= 0` 且个人积分也为 0 时抛 `MembershipPointsLimitExceeded`；最后 `assertRateLimits`。
- 限流：`assertRateLimits` 用套餐 `rateLimits` 中 provider/model 匹配的规则（支持 `'*'`），窗口起点由 `rateLimitStart(period, currentPeriodStart)` 给出（`hour`/`day`/`week`/`cycle` 四态），`SUM(ABS(pointsDelta))` 只统计 `usage` 与 `personal_usage` 两个 source，达到 `pointLimit` 抛 `ExceedingLimitException`。
- **self-heal 隐式写**：`findModelAccessWithOrganizationSelfHeal` 仅在「请求的组织范围与 Copilot 组织范围一致」且「access 的组织不匹配」时触发；若查不到访问会先做 `hasMembershipUsePermission` 判定，随后 `ensureScopeInitialized` 开户（建默认套餐 + 默认会员），再重查一次访问。该路径被 `recordUsage` / `recordGatewayUsage` / `assertCanUse` 反复调用——**读调用也可能落库**。

章节来源：[membership.service.ts](file://packages/server-ai/src/membership/membership.service.ts)（关键符号：MembershipService.findModelAccessWithOrganizationSelfHeal / MembershipService.assertCanUse / MembershipService.assertRateLimits）

## 流程③ 周期结算、续费与退款

- 定时结算：`MembershipPeriodSchedulerService.settleDueMembershipPeriods`（`@Cron('0 * * * * *')`）在 Redis 锁 `scheduler:membership-period-settlement`（TTL 5 分钟）内调 `processDueMembershipPeriods()`；异常只 `logger.error`，不回抛；有量时输出 `scanned/settled/skipped/failed` 日志。
- 批处理：`processDueMembershipPeriods(limit = 100)` 取 `status=Active` 且 `currentPeriodEnd <= now` 且套餐 `status=Active` 的会员（`take = min(batch*5, 1000)`），逐个在事务内 `acquireMembershipAssignmentLock` + `findMembershipForUpdate` 复核，再调 `findUsableMembership(forUpdate=true)` 触发换期；每条的失败只累加 `failed`。
- 到期后的两条分支：`activateScheduledPeriod` 找到 `Scheduled` 且已到 start 的期次则激活（旧期置 `Completed` 并落 `pointsUsed`，会员行改 `planId/planSnapshot/currentPeriodStart/End/pointsGranted`，写一条 `source=renew` 的赠分账本）；无可用期次且 `renewalMode=Manual` 时置 `status=Expired` + `createMembershipStatusLedger`，`Auto` 则走 `renewMembership`（`pointsUsed` 归零、结转 `pointsTotalUsed`、`pointsGranted = plan.includedPoints`、新建 `sourceReference: null` 的当前期、写 `renew` 账本）。
- 追加期次：`appendMembershipPeriods` 仅为事务包装，实体逻辑在 `appendMembershipPeriodsInTransaction`——`count` 限 1~120；`source=external` 必须给 `sourceReference`；同 `sourceReference` 重复请求按 `userId/organizationId/planSnapshot.planId/count` 全等校验后原样返回（幂等）；首期必须立即开始。
- 退款两阶段：`reserveFutureMembershipPeriodsForRefund` 要求 `sourceReference` 非空，`pessimistic_write` 锁住该来源的期次；已存在 `refund_pending` 直接返回；只取 `Scheduled` 且 `periodStart > now` 的期次，并校验其必须是同 membership 的**连续尾段**（否则抛 `MembershipRefundTailRequired`），再统一置 `RefundPending`。`finalizeFutureMembershipPeriodsRefund` 把 `RefundPending` 置 `Cancelled` 并写一条 `source=status_change`、`pointsDelta: 0` 的说明账本。
- 单期撤销：`cancelScheduledMembershipPeriod` 只允许撤销最后一个 `Scheduled` 期次（否则 `MembershipPeriodCancellationOrder`）；外部管理的期次必须由调用方传入一致的 `sourceReference`（否则 `ExternalMembershipPeriodCancellationRequired`），成功后写 `status_change` 账本。

## 流程④ 并发控制与锁策略

- 全部 8 个 advisory 锁都是 `SELECT pg_advisory_xact_lock(hashtext($1), hashtext($2))`，用 `tenantId` 作第一维、语义化字符串作第二维：`tenant-default-membership-plan`、`organization-default-membership-plan:<orgId>`、`tenant-default-membership:<userId>`、`organization-membership:<orgId>:<userId>`、`personal-membership-points:<userId>`、`personal-membership-points-source:<ref>`、`membership-usage-source:<ref>`、`model-gateway-request:<requestId>`。
- 语义是**阻塞等待 + 事务级自动释放**（不是 `try` 版本），因此失败表现为等待超时/连接错误，而非"拿不到锁请重试"的返回值；非 postgres 连接直接跳过加锁（方法首行类型判断）。
- 锁粒度与业务对齐：账本按"来源"（usage source / gateway request），额度按"付款人"（personal points），周期按"会员分配"（membership assignment，组织为空时复用租户默认锁）。
- 读取路径的锁：`findMembershipForUpdate` / `findActiveMembershipForUpdate` 走 `pessimistic_write`；退款与追加期次在 query builder 上显式 `setLock('pessimistic_write', undefined, ['period'])`。
- 跨进程去重：scheduler 用 `RedisLockService.runWithLock`；队列 job 不设 `jobId` 去重，改为「每批处理后按 `nextCursor` 入队下一批」的链式推进（`removeOnComplete: true`、`attempts: 5`、`backoff: 10_000`）。

章节来源：[membership.service.ts](file://packages/server-ai/src/membership/membership.service.ts)（关键符号：MembershipService.acquireMembershipAssignmentLock / MembershipService.acquireGatewayRequestLock）、[membership-backfill.queue.ts](file://packages/server-ai/src/membership/membership-backfill.queue.ts)（关键符号：MembershipBackfillQueueService.enqueueTenantDefaultMembershipBackfill）

## 设计模式及落点

- **幂等 outbox/投递**：copilot-usage 先 `insert().orIgnore()` 落 `source='model_usage'` 事实行（靠 `UQ_membership_ledger_model_usage_request_metric_revision` 去重），再对每条事实调 `recordUsage({ sourceReference: 'model-usage-charge:<factId>' })` 产生扣减行；model-execution 交付后再 UPDATE 扣减行补齐 `usageChannel` / `executionContext` / `actorId` 并写 `usageDeliveredAt`。
- **分布式锁**：DB 层 8 个 advisory 锁 + 悲观行锁（会员/期次），进程层 Redis 调度锁，队列层 Bull 重试。
- **快照式周期**：`createPlanSnapshot` / `copyPlanSnapshot` / `planFromSnapshot` / `hydrateMembershipPlanSnapshot` 四点闭环，周期切换时以 `planSnapshot` 还原 `plan` 对象，等价于"套餐版本随期冻结"。
- **策略/规则匹配**：`allowedModels` / `modelMultipliers` / `rateLimits` 三组 JSON 规则共用"provider/model 匹配 + `'*'` 通配"的判定风格（`isModelAllowed`、`resolveModelMultiplier`、`assertRateLimits`）。
- **门面式 service**：controller 只做权限与参数转发，全部规则内聚在 `MembershipService`；`findUsableMembership` 承担"读取即修复"的事实上的领域命令职责。

## 热点路径

- **每次调用的记账**：`recordUsage` 一次事务内最多 2 个 advisory 锁 + 1 次来源查重 + `findModelAccessWithOrganizationSelfHeal`（可能再做 `resolveBillableUserId`、权限查询、开户写入）+ `user_membership.save` + `synchronizeCurrentPeriodProjection` + 1~2 条账本 insert。这是计费链路上最重的单点。
- **每次调用的资格判定**：`assertCanUse` 会重复走一遍访问解析（含 self-heal），再加 `getPersonalPointsBalance` 与 `assertRateLimits` 的聚合查询；与随后的 `recordUsage` 形成"同一次调用解析两次会员"的读放大。
- **限流聚合**：`assertRateLimits` 逐条规则发一次 `SUM(ABS(pointsDelta))`，规则多时线性增长。
- **周期结算**：每分钟一次全表条件扫描（`currentPeriodEnd <= now`，`take <= 1000`）+ 每条一次事务，多副本时靠 Redis 锁压成单副本。
- **读模型**：`readPeriodConsumedPoints` / `findUserUsageSummaries` / `getOverview` 依赖 `USAGE_POINTS_SQL` 的子查询，脚本注释明确"避免对每条历史扣减行做全表反连接"。

## 技术债与 hack

- **单文件巨型 service**：`membership.service.ts` 约 218 KB，把账本、资格、周期、退款、读模型、锁、DTO 归一、i18n 包装全部内聚；`synchronizeAssignedPlanPoints`（套餐改额度后回填 `pointsGranted`，仅对无 `planSnapshot` 的旧会员生效）这类一次性迁移逻辑也留在其中。
- **读路径的隐式写**：`findModelAccessWithOrganizationSelfHeal` / `findUsableMembership` 在"解析访问"时会开户、换期、续费、把 Manual 会员置 `Expired`——GET 类读接口（`getMe`、`getPersonalPoints`）的后台可能落库，审计与复现困难。
- **同一次调用解析两次会员**：`assertCanUse` 与紧随其后的 `recordUsage` 各自跑一遍 self-heal 与权限查询，事务内外口径可能不同（事务内那次才带 `forUpdate`）。
- **锁失败语义不显式**：`pg_advisory_xact_lock` 无返回值，调用方无法区分"拿到锁"与"等了很久"；非 postgres 连接静默跳过加锁，测试环境与生产的并发行为不同。
- **静默不记账**：`recordUsage` 在金额为 0、`Direct` 访问或开关关闭时返回 `null`，调用方若忽略返回值会表现为"调用成功但无账本"。
- **`:personal` 后缀约定**：个人积分行靠 `sourceReference + ':personal'` 字符串约定与主扣减行配对，读模型 SQL 里硬编码了 `'model-usage-charge:'` 前缀与 `('', ':personal')` 两个后缀，三处必须同步修改。
- **多副本**：`@Cron` 靠 Redis 锁去重，锁 TTL 5 分钟而结算批 100 条；Bull job 无 `jobId` 去重，重复入队会产生重叠批次（由幂等键兜底）。

## 设计维度分析

**维度一：一致性优先于可用性。** 三件套把"重复扣费"这个最贵的事故彻底堵死——来源级 advisory 锁串行化同来源并发，事务内查重返回既有行，唯一索引 `IDX_membership_ledger_source_reference` / `UQ_membership_ledger_model_usage_request_metric_revision` 兜底。代价是热点付款人的所有调用被同一把 `personal-membership-points:<userId>` 锁排队，且锁等待表现为长尾延迟而不是显式拒绝。

**维度二：额度语义分层。** "会员额度（`pointsGranted`，null = 无限）→ 个人积分（`personal_usage` 独立账）→ 超额（`excessPoints` + 抛异常）"三层，把"扣不到"拆成"记多少"和"是否拒绝"两个独立决策：账本永远记录真实消费额（`chargedPoints` + `excessPoints`），是否中断由 `ExceedingLimitException` 表达。这与 `docs/model-execution.md` 的"未知费用必须区别于免费调用"同源：`excessPoints > 0` 是"已知但未扣"的证据，`settlementAmount = null` 才是"未知"。

**维度三：快照式不可变历史。** `planSnapshot` 让套餐改价/改倍率不会污染历史期次；`appendMembershipPeriodsInTransaction` 对外部履约按 `sourceReference` 全等校验后幂等返回；退款只允许动"连续尾段"。代价是 `plan` 与 `planSnapshot` 双写，任何新增套餐字段都要同步 `createPlanSnapshot` / `copyPlanSnapshot` / `planFromSnapshot` 三处。

## 结论

实现层面四条流程各自闭环：记账以"锁 + 查重 + 唯一索引"实现幂等且永不双扣；资格判定把开关、白名单、倍率、限流、余额收敛为一个 `assertCanUse`，但把修复动作埋进了解析路径；周期以 `findUsableMembership` 为唯一推进点（定时结算与实时调用共用）；退款与撤销只允许动尾部期次。演进建议集中在四件事：把 self-heal 从读路径移到显式初始化命令、给 `assertCanUse` 与 `recordUsage` 合并一次访问解析、把 `MembershipService` 按账本/周期/读模型拆包、以及为锁等待补齐可观测性（等待时长与超时计数）。
