## 逐文件覆盖点

### membership.service.spec.ts

覆盖面最广：`assertCanUse` 被反复调用（含会员缺失、额度耗尽、Grant/Direct 访问、Copilot 组织不匹配、限流等分支）；`recordUsage` 覆盖正常扣减、`Direct` 短路、金额为空短路、自愈开户路径；`recordGatewayUsage` 覆盖网关扣减分支；`applyPersonalPointsAdjustment`（spec 内 7 处引用）覆盖个人积分调整与幂等校验；退款与周期方法（`reserveFutureMembershipPeriodsForRefund`、`cancelScheduledMembershipPeriod*`、`processDueMembershipPeriods`、`appendMembershipPeriods`）在 spec 中合计 17 处引用；锁方法（`acquireUsageSourceLock` / `acquireGatewayRequestLock` / `acquirePersonalPointsLock` / `acquireMembershipAssignmentLock`）4 处引用，其中 `pg_advisory_xact_lock` 仅 1 处出现，说明锁**发射**被断言，锁**竞争/等待**未被模拟。

章节来源：[membership-usage-points.spec.ts](file://packages/server-ai/src/membership/membership-usage-points.spec.ts)（关键符号：USAGE_POINTS_SQL / USAGE_POINTS_PREDICATE）

## PG 依赖用例的开启方式

- `membership-usage-points.spec.ts` 顶部为 `const url = process.env.XPERT_USAGE_READ_TEST_DATABASE_URL` 与 `const integration = url ? describe : describe.skip`：**未设置该环境变量时整组用例被 skip**（不会失败）。
- 准备方式：设置 `XPERT_USAGE_READ_TEST_DATABASE_URL` 指向一个可连接的 PostgreSQL，并确保连接以只读事务运行（spec 自带 `-c default_transaction_read_only=on`，且全部数据由 `jsonb_to_recordset` 内存构造，不依赖任何业务表或迁移）。
- 其余 6 个 spec 不读取数据库环境变量，仅靠 mock 与元数据断言，因此在无数据库环境下也能完整执行。

章节来源：[membership-usage-points.spec.ts](file://packages/server-ai/src/membership/membership-usage-points.spec.ts)（关键符号：XPERT_USAGE_READ_TEST_DATABASE_URL / read_only）

## 覆盖缺口

- **退款终态化未覆盖**：`finalizeFutureMembershipPeriodsRefund` 在 membership 目录的 spec 中零引用（仅 `membership.service.ts` 出现 1 处），退款两阶段的"连续尾段"约束（`MembershipRefundTailRequired`）与 `finalize` 后的 `Cancelled` + `status_change` 账本缺少回归保护。
- **套餐额度回填未覆盖**：`synchronizeAssignedPlanPoints`（改套餐额度后回填无快照的旧会员）在 spec 中零引用。
- **锁语义未覆盖**：`pg_advisory_xact_lock` 仅 1 处出现在 spec 中，且 8 个 `acquire*Lock` 在 service 侧共 24 处调用——锁的阻塞、非 postgres 跳过、超时与死锁路径均无测试；`acquirePersonalPointsSourceLock` 的幂等配对（与 `applyPersonalPointsAdjustment`）依靠间接用例覆盖。
- **周期推进的端到端未覆盖**：`MembershipPeriodSchedulerService` 只验证"是否调用"与锁参数，`processDueMembershipPeriods` 的批上限/跳过开关（`isMembershipPlanEnabledForScope` 为假时 `skipped++`）与 `failed` 计数没有直接断言用例。
- **对账与运维流程无 spec**：`reconciled_no_usage`、`retry-delivery`、`admin/calls/:id/*` 属 model-execution 测试面；本子域没有任何针对"账本与投递回执不一致"的测试。
- **HTTP 权限面覆盖偏薄**：`membership.controller.spec.ts` 只校验 6 个 `me*` 方法的权限元数据，`admin/*` 与 `plans/*` 路由的权限声明未断言。
- **多副本并发**：无任何跨进程/并发测试覆盖 Redis 锁与 Bull 队列在多副本下的重叠执行。

章节来源：[membership.service.spec.ts](file://packages/server-ai/src/membership/membership.service.spec.ts)（关键符号：MembershipServiceTestAccess）、[membership.service.ts](file://packages/server-ai/src/membership/membership.service.ts)（关键符号：MembershipService.finalizeFutureMembershipPeriodsRefund / MembershipService.synchronizeAssignedPlanPoints）

## 可执行性结论

7 个 spec 中 6 个可在无数据库环境直接运行（纯 mock + 元数据断言），1 个（`membership-usage-points.spec.ts`）需要只读 PostgreSQL 连接并由 `XPERT_USAGE_READ_TEST_DATABASE_URL` 门控；所有 spec 均通过 `packages/server-ai/jest.config.ts` 可被单文件定位执行，无额外构建前置。风险点在于：计费最关键的"锁竞争、退款尾段、额度回填、对账一致性"四条路径目前**没有**对应用例，任何一次 `membership.service.ts` 重构都需要先补这四类回归测试，才能把唯一索引与 advisory 锁的保护面从"代码事实"升级为"可验证事实"。
