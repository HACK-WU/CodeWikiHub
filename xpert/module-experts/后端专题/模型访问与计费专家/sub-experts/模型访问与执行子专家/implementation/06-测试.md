## model-access spec 逐文件覆盖点

- `model-access.service.spec.ts`（14 个顶层 describe）：组织模型配置、Xpert 计费归属、模型解析（`resolveModelAccess`）、目录（`getCatalog`）、审批幂等（重复 `approveRequest` 不产生第二条授权）、管理端作用域隔离、请求作用域解析、请求并发（同范围唯一索引冲突回退）、组织清理、生命周期批次（`reconcileLifecycleBatch` 游标）、请求生命周期、grant 生命周期（`processDueGrants` / `revokeGrant` / `extendGrant`）、过期日期计算、Provider 目录同步。
- `model-access.controller.spec.ts`（`ModelAccessController`）：路由到服务的委派与方法名一致性，保证控制器不引入额外业务分支。
- `model-access-scheduler.service.spec.ts`（`ModelAccessSchedulerService`）：`@Cron('0 * * * * *')` 任务在 Redis 锁内串起 `processAllDueGrants` 与 `reconcileLifecycleBatch`，游标读写与异常吞掉后不重抛。
- `model-access-credentials.spec.ts`（`ModelAccessService model credentials`）：凭据/可见性解析相关边界，与审批链共享同一 `resolveModelAccessWithContext` 口径。
- `dto/model-access.dto.spec.ts`（`model access DTO validation`）：`ModelAccessRequestCreateDto` 必填与长度、`validUntil` 的 `YYYY-MM-DD` 正则、理由必填类 DTO 的校验行为。

## env-gated 集成用例

- **门控变量**：`XPERT_EXECUTION_TEST_DATABASE_URL`。四个文件使用同一模式 `const integration = url ? describe : describe.skip`，未设置时整段静默跳过：`execution-admission.integration.spec.ts`、`execution-operations.integration.spec.ts`、`execution-migration.integration.spec.ts`、`execution-grant.lifecycle.spec.ts`（`execution lease renewal / PostgreSQL`）。
- **建库要求**：四个文件都在 `beforeAll` 里校验 `new URL(url).pathname.startsWith('/xpert_execution_test_')`，否则抛 `Error('Dedicated test database required')`；数据库名必须以 `xpert_execution_test_` 开头（`docs/model-execution.md` 同样要求库名以该前缀开头且不得指向应用库）。
- **隔离方式**：每个文件自建随机 schema（`execution_admission_<uuid>`、`execution_operations_<uuid>`、`execution_migration_<uuid>`、`execution_lease_<uuid>`），用 `new DataSource({type:'postgres', url})` 初始化后 `CREATE SCHEMA`，因此可并行运行；`execution-migration.integration.spec.ts` 还会重复执行 `20261003-shell-launcher.sql` 以断言迁移可重复。
- **无关变量**：`XPERT_USAGE_READ_TEST_DATABASE_URL`（会员积分只读投影）与 `MODEL_USAGE_TEST_DATABASE_URL`（网关用量台账集成）属于其他模块，本 34 个 spec 不使用。

## 覆盖缺口

- **无 PG 时的静默跳过**：CI 未设置 `XPERT_EXECUTION_TEST_DATABASE_URL` 时，准入串行化、`recoverAbandonedExecutionCalls` 两条 SQL、查询投影与迁移可重复性**完全没有覆盖**，这些正是本子域最关键的不变量（预占保留、只允许更严、迁移幂等）。建议把该变量作为流水线必需项。
- **`model-execution` 无独立 spec 的源文件**：`model-execution.module.ts`（装配）、`execution-entities`（`execution-reconciliation.entity.ts` 仅经集成用例间接覆盖）、`invocation-model-source.ts` 之外的 `execution-openai.controller.ts` 与 `execution-chat.service.ts` 只有 `execution-input-context.spec.ts` 一处间接覆盖；`execution-chat-bridge-writer.ts` / `execution-chat-bridge-request.ts` 由 `execution-chat-bridge.spec.ts` 覆盖但不能替代真实 SSE 输出回归。
- **`model-gateway` 缺口**：`gateway-admission-policy.ts` 与 `model-gateway-call-retention.ts` 没有独立 spec，仅被 `model-gateway.service.spec.ts` 间接引用（后者还被 `jest.spyOn` 打桩，等于绕过真实 SQL）；`model-gateway-client.ts`、`chat-writer.ts`、`model-gateway.i18n.ts`、`model-gateway-usage.ts` 无专门用例。
- **`model-access` 缺口**：`model-access-event.entity.ts` 的幂等唯一索引冲突路径、`processAllDueGrants` 的多租户分发、`handleCopilotStateChanged` / `handleConfiguredModelDeleted` 两个配置联动入口没有独立 describe；`model-access.module.ts` 无装配测试。
- **端到端缺口**：三目录无 HTTP 级 e2e（没有 supertest 风格用例），`@Public()` 入口的错误体、`Retry-After` 头与 SSE 分帧只在控制器单测层面验证；16 MB 上限、`anthropic-*` 头透传、native 桥接降级均无真实上游回归用例。

章节来源：[packages/server-ai/src/model-gateway/model-gateway.service.spec.ts](file://packages/server-ai/src/model-gateway/model-gateway.service.spec.ts)（关键符号：purgeModelGatewayCallBatch）

## 可执行性结论

- **可执行**：34 个 spec 文件齐全，`jest.config.ts` 与 `project.json` 的 `test` 目标可直接驱动；单文件命令 `node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts --runTestsByPath <spec>` 对三个目录均适用。
- **默认结果**：31 个纯单元 spec 无需外部依赖即可运行；4 段 PG 集成（3 个整文件 + 1 个 describe）在未配置 `XPERT_EXECUTION_TEST_DATABASE_URL` 时按 `describe.skip` 跳过，因此「全绿」不等于准入/恢复/迁移逻辑被验证过。
- **建议门槛**：CI 至少两条流水线——一条跑全部 34 个 spec（无 PG），一条以 `xpert_execution_test_` 前缀库为条件开启四段 PG 集成；并在变更 `model_gateway_call` 相关 SQL、`usageFact` schema 或迁移脚本时强制后者。
