## 流程一：审批与 grant 生命周期

- **申请**：`createRequest` 顺序执行 `requireTenant` / `requireUser` / `requireNormalUser` → `requireVisibleEnabledTarget`（目标必须可见且启用）→ `assertRequestFeatureEnabled` → `assertRequesterIsNotManager`；后者用 `canManageTargetScope` 判定「作用域匹配 且 持有 `COPILOT_EDIT`/`MEMBERSHIP_EDIT`/`MODEL_ACCESS_REQUEST_EDIT` 之一」，命中即抛 `ForbiddenException`，**自审在入口被阻断**。理由缺失抛 `ModelAccessRequestReasonRequired`，套餐已含该模型抛 `ModelAccessPlanIncluded`。
- **去重**：先 `processDueGrants` 清过期，再 `findActiveGrant`（已授权 → `ModelAccessAlreadyGranted`）与 `findPendingRequest`（已有 pending → 直接回读并 `attachEventsToRequest`）；插入阶段的唯一冲突也回退到 `findPendingRequest`，靠部分唯一索引（`status='requested'` 且区分 `organizationId` 是否为 NULL）保证同范围仅一条。
- **审批**：`approveRequest` 在单事务内 `findRequestForAdminUpdate` → 幂等短路（已 `approved` 直接回读 grant）→ 渠道特性开关校验（ExternalApi 走 `assertModelGatewayFeatureEnabled` 并 `ensureAutomaticPublications` 写 `gatewayPublicationId`/`externalModelId`）→ `normalizeValidUntil` → `assertRequestStatus` → 目标消失则 `closeRequestForSystem(ModelDeleted)` 返回 `null` → 已有 active grant 则只推进请求状态 → 否则写 `user_model_grant`（`approvedAt`/`approvedById/Name`/`ownershipScope`/`modelSnapshot`），并 `writeEvent` 写 `Approved` 与 `GrantActivated` 两条事件。
- **撤回/驳回/延期/撤销**：`withdrawRequest` 只允许本人且仅在 `requested` 态；`rejectRequest` 强制理由（`ModelAccessRejectionReasonRequired`）；`extendGrant` 只允许 `active`（否则 `ModelAccessGrantNotActive`）、不允许永久后再改（`ModelAccessGrantAlreadyPermanent`）、不允许缩短（`ModelAccessGrantCannotShorten`）；`revokeGrant` 先跑一次 `processDueGrants` 再置 `revoked` 并写 `revokedAt/ById/Name/revokeReason`。
- **到期与协调**：`processDueGrants` 事务内 `pessimistic_write` 锁 `validUntil < now` 的 active 授权（`take(500)`）逐条转 `expired`，事件 `idempotencyKey = grant:{id}:expired`；`processAllDueGrants` 先取 DISTINCT tenantId 再分发。`reconcileLifecycleBatch` 用 `requestAfterId` / `grantAfterId` 游标分别批处理 `reconcilePendingRequest` 与 `reconcileGrantAvailability`，返回 `nextRequestAfterId` / `nextGrantAfterId`；`ModelAccessSchedulerService.expireDueGrants` 每分钟在 Redis 锁 `scheduler:model-access-lifecycle`（TTL 5 分钟）内串起两者，游标存 CACHE_MANAGER（TTL 24 小时），异常只 `logger.error`。
- **配置联动**：`handleCopilotStateChanged` 按 `copilotId` 重跑 active 授权的可用性协调；`handleConfiguredModelDeleted` 关闭 pending 申请并 `revokeGrantForDeletedModel` 撤销对应授权；`closeOrganizationAccessForRemovedUser` 关闭申请并撤销该组织内授权，事件键 `grant:{id}:user-left-organization`。

## 流程二：执行准入与预占

- **签发**：`issue` 先 `policy.require(tenantId)` 校验 `tool.id + tool.version` 命中策略（否则 `Invalid`），再 `user`/`resolveForExecution`/`resolve` 解析助手与默认模型，`executionToolModels` 求交；`shell_execution` 必须 `prepare=true`（否则 `Denied`），非 shell 不允许 `prepare`。随后 `sources.assertCurrent` 与 `ModelExecutionEnvironmentCapability.assertCurrent` 双重校验，生成 `xpert-exec-${randomBytes(32).toString('base64url')}`，库中只写 `hashExecutionCredential(secret)`（sha256）；`status = prepare ? 'pending' : 'active'`，`expiresAt = min(deadline, now + leaseSeconds)`，`absoluteExpiresAt = deadline`（`maxDurationSeconds` 封顶）。
- **校验**：`authenticate` 用正则 `/^Bearer (xpert-exec-[A-Za-z0-9_-]{43})$/` 取 secret 并反查 `credentialHash`；`validate` 逐项比对上下文与行内列（tenant/org/actor/billable 四项不等即 `Denied`）、`assertActive`、工具仍在策略中、`tightenExecutionLimits` 只收紧、`sources.assertCurrent` 与环境能力校验，最后把已存 `models` 与「当前权限可见模型」按 `id/copilotId/model/modelType/provider/providerScopeId/providerOrganizationId` 求交并裁剪能力/协议，默认模型被移除抛 `Model`。
- **两阶段**：`activate` 只接受 `pending` + `shell_execution`，UPDATE 谓词带 `clock_timestamp()` 比较 `expiresAt` 与 `absoluteExpiresAt`，`affected !== 1` 即 `Denied`；**注释明确「不重置准备租约，也不复活已过期凭证」**。`renew` 在事务内先 `pessimistic_write` 锁行（注释说明 UPDATE 谓词可能先于行锁等待执行），再用 `expiresAt > clock_timestamp()`、`absoluteExpiresAt > clock_timestamp()`、`createdAt + maxDurationSeconds > clock_timestamp()` 三重谓词续租。`watch` 每 5 秒 `revalidate`，失败即 `abort.abort()`。
- **串行化与预占**：`begin` 单事务内 `lockGrant` 先 `SELECT pg_advisory_xact_lock(hashtextextended('model-execution:{tenantId}:{ownerId}', 0))`，再对 `status='active'` 行 `pessimistic_write` 并 `tightenExecutionLimits`；`reservation = estimatedInputTokens + outputLimit`（输出未指定时取 `model.outputTokenLimit ?? 0`），对 `grantId` 维度与付款人维度（`grantId IS NULL`，`used` 取 24 小时内 `totalTokens`、`reserved` 取 `reservedTokens`）各跑一次 `aggregate`，`assertExecutionAdmission` 校验预算与并发/速率（`Budget` / `RateLimit`）；`shell_execution` 额外经 `parentTotals` 与同父执行兄弟取最小已签发预算。最后插入 `model_gateway_call`（`source='execution_grant'`、`status='started'`、`reservedTokens`、新 `requestId`/`callId`），并 `applicationMetrics.recordModelExecution('admitted')`。
- **派发栅栏**：`dispatch` 在事务内同序取锁后 `pessimistic_write` 读回 `status='started'` 的尝试，`!attempt || attempt.dispatchedAt` 即 `Denied`；重新按 grant 级、付款人级与父执行级校验预算后写 `dispatchedAt`。注释明写「A crash after this point retains the reservation」。
- **请求生命周期**：`executionRequestLifetime(grant, abort)` 用 `requestIdleSeconds ?? 600` 做静默超时，另加 `absoluteExpiresAt` 绝对截止；`ModelExecutionChatService.execute` 在 `beforeDispatch` 里重跑 `revalidate` + `assertRequestCapabilities` + `assistants.authorize` + `admission.dispatch`，并强制 `client.caller = new AsyncCaller({ maxRetries: 0 })` 关闭提供方默认重试。

## 流程三：usage fact 投递与重试

- **落事实**：`finish` 只在 `usage.source === provider && totalTokens > 0` 时构造 `ExecutionUsageFact`；价格态推导为 `unpriced` / `free`（金额 0）/ `priced`。事务内以 `addSelect(['call.usageFact','call.settlementContext'])` + `pessimistic_write` 读回：已有事实与新事实 `isDeepStrictEqual` 不符即 `Invalid`；`errorCode='reconciled_no_usage'` 拒写；已有事实或已投递直接返回。
- **状态写入**：`status = settlement_pending`、`completedAt`/`durationMs`、`usageSource`；估算仅经 `executionUsageEstimateSchema` 写入 `estimatedUsage`（永不进事实 schema）；有事实则 `reservedTokens = 0`；无事实且 `!dispatchedAt` 转 `failed` + `execution_preflight_failed` 并清预占；`error` 存在时置 `execution_interrupted`。随后 `recordModelExecution(fact ? 'provider_usage' : 'usage_pending')`，有事实即同步 `deliver(call.id)`。
- **投递**：`deliver` 再 `addSelect` 取 `usageFact` 与 `settlementContext`，缺 grant/model/settlementContext 抛 `Invalid`；派发 `CopilotTokenRecordCommand`（`requestId`、`billableUserId`、`runtimeOrganizationId`、`xpertId`、`threadId`、`copilotId`、`model`、`modelAccess`、token 三元组、价格与 `pricingStatus`、`execution`、`executionModel`、`tokenDetails`）。
- **回执语义**：捕获 `ExceedingLimitException` 时必须查到 `ModelUsageDeliveryReceipt.status='completed'` 才算已投递（注释：「Only a durable receipt proves the latter」），否则记 `delivery_retry` 指标并保持 pending。成功后用一条原生 SQL 把账本行（`sourceReference IN ('model-usage-charge:<factId>', 'model-usage-charge:<factId>:personal')`）补齐 `usageChannel` / `executionContext` / `actorId`，再写 `usageDeliveredAt` 与终态（有 `errorCode` → `failed`，否则 `succeeded`）。
- **后台循环**：`@Interval(30_000) retry` 先 `recoverAbandonedExecutionCalls`（`startedAt` 超 15 分钟且不存在 active 且未过期的 grant：未派发 → `failed` + 清零预占，已派发 → `settlement_pending` 保留预占，`errorCode='worker_lost'`），再刷新 `xpert_model_execution_pending{attempts|reserved_tokens|oldest_seconds}`，最后重投最旧 100 条「`settlement_pending` 且 `usageFact IS NOT NULL`」。
- **人工闭环**：`ModelExecutionReconciliationService.pending` 分页返回 `id`（数据库 UUID）/`attemptId`/`callId`；`reconcile` 以 `insert` 追加审计（重复 `operationId` 不覆盖，23505 → `Invalid`），`apply` 对 `no_usage` 释放预占并置 `reconciled_no_usage`，对 `provider_usage` 复用 `finish` 走同一投递路径；`retryDelivery` 返回 `delivered` 布尔；`@Interval(30_000) retry` 重放 `appliedAt IS NULL` 的 100 条审计。

## 流程四：网关 startCall / finishCall 与结算重试

- **认证与可见性**：`authenticate` 用 `readBearerToken` 取 Bearer，`hashToken` 查 `tokenHash`（显式 `addSelect`），过期即就地置 `Expired`，非 active 抛 `ModelGatewayApiKeyInvalid`，属主缺失抛 `ModelGatewayApiKeyOwnerMissing`，命中后刷新 `lastUsedAt`。`listAccessiblePublications` 按 Key 的 tenant/organization 过滤 publication 后逐个 `resolveExternalModelAccess`，只保留 `grantId` 且（allowed 或 `QuotaExhausted`）的项；`requireCallablePublication` 找不到 model 抛 404 `ModelGatewayModelNotFound`，`QuotaExhausted`/`MembershipRequired` 抛 429 `ModelGatewayNoRemainingPoints`，其余不可用抛 403 `ModelGatewayModelNotCallable`。
- **准入**：`startCall` 先 `getOrCreateSettings` 与 `GatewayAdmissionPolicy.getAdmissionLimits(tenantId)`（读 `TenantSetting` 的 `MODEL_GATEWAY_REQUESTS_PER_MINUTE_SETTING` / `MODEL_GATEWAY_MAX_CONCURRENT_REQUESTS_SETTING`，越界回退默认）；事务内对 Key 属主 `User` 行 `pessimistic_write`（`lockedUser`）后再统计窗口（60 秒）内 `source='external_api'` 计数与 `started` 并发数，超限抛 `ModelGatewayRequestLimitException`（`openAICode='rate_limit_exceeded'`，`retryAfterSeconds` 分别为 60 与 1）；最后插入 `model_gateway_call`（必带 `apiKeyId` + `publicationId`，`settlementContext` 存访问解析结果，仅 `storeBodies` 为真才写 `encryptedRequest` 与 `bodyExpiresAt`）。
- **结算**：`finishCall` 只接受 `started` 或 `settlement_pending`；先用 `settleChargeToCny` 把价格折算为 CNY（`unpriced → null`、`free → 0`），再调 `MembershipService.recordGatewayUsage`（`sourceReference = model-gateway:<requestId>`，按 `gatewayRequestId` 去重），回写 `chargedPoints` / `excessPoints` / token 三元组、清空 `settlementContext`、按需加密响应体。OpenAI 控制器对 `finishCall` 做一次立即重试（`settleCall` 两次尝试），仍失败才 `recordSettlementFailure`。
- **失败与重试**：`recordSettlementFailure` 只在行仍为 `started` 时置 `settlement_pending` 并保留 token/价格快照，写库异常时返回 `null`；`@Interval(GATEWAY_MAINTENANCE_INTERVAL_MS = 5 分钟) retryPendingSettlements` 每次 `addSelect('call.settlementContext')` 取最旧 100 条 `external_api` + `settlement_pending`，缺 context 时重新 `resolveExternalModelAccess` 再重放 `finishCall`。
- **维护循环**：`purgeExpiredBodies`（1 小时，清空过期密文体）、`purgeExpiredCalls`（1 小时，`purgeModelGatewayCallBatch` 批 1000、最多 20 批，`FOR UPDATE OF c SKIP LOCKED`，先把用量归档进账本再删行）、`expireDueApiKeys`（5 分钟，可定向 tenantId）、`failStaleCalls`（5 分钟，超 30 分钟未完成置 `failed` + `gateway_interrupted`）；`MODEL_GATEWAY_UPSTREAM_TIMEOUT_MS = 30 分钟 - 60 秒` 用于控制器侧中止。

## 设计模式及落点

- **Outbox（先落事实后投递）**：`model_gateway_call.usageFact`（不可变、`select:false`）+ `ModelUsageDeliveryReceipt` 构成执行侧 outbox，`CopilotTokenRecordCommand` 是投递通道，`attemptId`（即 `call.requestId`）是幂等键；`usageDeliveredAt` 与 `appliedAt` 把「事实存在」与「投递完成」分离。
- **悲观锁 + 数据库串行化**：`pg_advisory_xact_lock('model-execution:{tenantId}:{ownerId}')`（付款人级）、`pessimistic_write`（grant 行、尝试行、用户行、审计行）、`FOR UPDATE ... SKIP LOCKED`（留存清理）三层并用；`renew` 与 `dispatch` 都刻意「先锁行再判时钟」，注释说明 UPDATE 谓词可能先于行锁等待执行。
- **状态机**：`model_execution_grant.status`（`pending → active → revoked`，DB CHECK）、`model_gateway_call.status`（`started → succeeded|failed|settlement_pending`）、申请/授权/事件三表各自终态不可回退，迁移方向统一为「只允许更严」。
- **策略与声明式能力**：`GatewayAdmissionPolicy` 从 `TenantSetting` 读限额；`nativeProtocols` / `chatBridgeProtocols` 由租户策略与模型 `protocols` 双声明，native 默认关闭；`CliModelProfilesCapability` 决定 CLI 工具与精确版本可用性。
- **模板方法/共享执行器**：`executeGatewayChat` 用 `GatewayChatLifecycle`（`capabilities` / `begin` / `beforeDispatch?` / `createModel` / `settle`）把 API key 链路与 execution 链路统一到同一 stream/settle 生命周期；`settled` 标志位保证一次尝试只结算一次。
- **CQRS 出向**：`model-execution` 只用 `CommandBus.execute(new CopilotTokenRecordCommand(...))` 出向，不注册 handler；配置与解析能力由其他模块的 query/command 承担。

## 热点路径

- **每次执行的串行段**：`begin`（advisory lock + 悲观锁 + 2~3 次聚合查询）→ `dispatch`（重取锁 + 再次聚合）→ 提供方调用 → `finish`（事务 + fact 落库）→ `deliver`（命令 + 账本 UPDATE），是延迟最敏感的路径，且 `beforeDispatch` 会再跑一次完整 `revalidate`（含组织访问与模型求交）。
- **网关每请求固定成本**：`startCall` 的两次 `count`（窗口内计数、并发计数）+ `getAdmissionLimits` 读 `TenantSetting` + `getOrCreateSettings`，全部在请求前置路径上。
- **列表与查询**：`ModelExecutionQueryController.list` 除主查询外还要 `grants.findBy`、`createMembershipUsageQuery` 按 `executionContext->>'attemptId'` 分组聚合积分，并对每条 call 做 grant 归属断言。
- **轮询批次**：metering/reconciliation 的 `@Interval(30_000)`（各 100 条）、gateway 的 5 分钟结算重试（100 条）与 1 小时留存清理（批 1000 × 最多 20 批）。

## 技术债与 hack

- **两个 OpenAI 兼容入口语义不同**：`/api/openai/v1`（API key + publication，错误体带 `type`/`param`/`code`）与 `/api/model-execution/openai/v1`（execution credential + grant，错误体固定 `code:'model_execution_failed'`）；虚拟模型 `assistant-default` 只存在于执行侧，客户端容易串用。
- **`@Public()` + 自证式鉴权**：两个 OpenAI 入口与 native 入口无 `@Permissions`，安全性完全落在 `authenticate` 与 grant 校验上；`ModelExecutionQuery/SessionController` 无任何权限装饰器，靠 `RequestContext.currentApiPrincipal()` 判空 + 租户/组织/用户三重相等，漏改一处即越权。
- **读接口有写副作用**：`ModelGatewayService.getSettings` 内部 `getOrCreateSettings` 会建行；`ModelAccessService.getCatalog` / `findMyRequests` 内联 `reconcileGrantAvailability` / `reconcilePendingRequest` 会改状态；`listMyKeys` / `listAdminKeys` 会顺带 `expireDueApiKeys`。
- **`select:false` 静默 undefined**：`usageFact` / `settlementContext` / `encryptedRequest` / `encryptedResponse` / `tokenHash` / `encryptedSecret` 漏写 `addSelect` 不报错，只静默跳过投递或返回空。
- **无分布式锁的定时任务**：gateway 的 5 个 `@Interval` 全部无锁，多副本会并跑；`ModelExecutionMeteringService.retry` 与 `ModelExecutionReconciliationService.retry` 同样无锁，仅依赖幂等。
- **指标不可相加**：积压快照是进程本地量，多副本重复暴露；`reserved_tokens` 只是未知消费占用，不等于实际 token 或金额。
- **人工闭环的禁忌**：`docs/operations/model-execution-runbook.md` 明确禁止以估算补单、直接改库、手动减预占；`reconcile` 返回 `applied` 只证明证据已应用，不等于投递完成。

## 设计维度分析

**维度一：一致性与幂等。** 三层防线互补——DB 唯一索引（`model_gateway_call.requestId`、`ModelAccessEvent` 幂等键、账本 `sourceReference`）挡住重复写入；`usageFact` 不可变 + `isDeepStrictEqual` 校验挡住同一 attempt 的第二次不同事实；`dispatchedAt` 一次性栅栏挡住二次派发；投递侧用 `ModelUsageDeliveryReceipt` 与 `usageDeliveredAt` 区分「事实」与「已入账」。代价是「未知结果」必须长期占用预占，只能靠人工对账收敛。

**维度二：信任边界与凭据最小化。** 客户端 scope header 不参与租户/组织选择；执行凭据与 API Key 只存哈希（API Key 另有可解密密文用于个人列表回显，受 `SECRETS_ENCRYPTION_KEY` 保护）；授权在签发时快照、在每次请求（以及每 5 秒 `watch`）重新校验且只允许收紧。代价是执行期读放大：每个请求都要重查账号、组织访问、助手发布态与模型权限。

**维度三：失败可观测与人工闭环。** 用量事实、投递状态、审计应用三态分离（`usageFact` / `usageDeliveredAt` / `appliedAt`），指标 `recordModelExecution('admitted'|'provider_usage'|'usage_pending'|'delivery_retry')` 与 `setModelExecutionPending` 配套告警阈值（`oldest_seconds > 900`、`attempts > 20`、`delivery_retry` 增量 > 5）。代价是运维需要人工把权威证据转化为结构化请求。

## 结论

四条主流程各自闭环：审批链以「入口阻断自审 + 事件幂等键 + 部分唯一索引」保证授权口径唯一；准入链以「advisory lock → 悲观锁 → 聚合判定 → 一次性派发」保证同一付款人串行且未知消费不释放；计量链以「事实先落、幂等投递、30 秒补投递 + 人工对账」保证不重复扣费也不静默丢费；网关链以「Key 哈希 + publication 可见性 + 租户限流 + 结算重试」把外部调用收敛到同一执行器与同一账本出口。演进建议集中在三处：合并或强区分两套 OpenAI 兼容入口、给 Query/Session 类控制器补权限声明、把定时任务与读路径的写副作用收敛到可观测的显式作业。
