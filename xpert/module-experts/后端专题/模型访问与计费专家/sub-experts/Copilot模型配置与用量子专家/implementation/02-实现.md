## 1. 核心流程实现位置

### ① 角色化模型选择与可见范围计算

- 角色枚举 `AiProviderRole` 的优先级常量 `ProviderRolePriority = [Embedding, Secondary, Primary, Reasoning]` 定义在 `copilot.service.ts` 顶部。
- `CopilotService.findAllAvailablesCopilots(tenantId, organizationId, where, relations)`：并行取三个布尔量（租户级 membership 是否启用、组织级是否启用、组织是否配置了自己的模型），据此算出 `membershipEnabled` 与 `membershipAllowedScopes` 集合；`relations` 被 `mergeCopilotRelations` 强制并入 `modelProvider`；`find` 用 `organizationId IS NULL` 与具体 org 两支 OR 查询后，再按集合二次过滤；最后 `hydrateVisibleModelProviders` 用 `CopilotProviderService.findVisibleByCopilotIds` 覆盖 `modelProvider`（组织级优先）。
- 兜底路径：不在集合内的 Copilot 只有在「非 `MEMBERSHIP_EDIT` 用户」且 `usesOrganizationCredentials(copilot, organizationId)` 或 `ModelAccessService.hasOrganizationModelCredentials(...)` 为真时才保留。
- 角色取值：`CopilotOneByRoleHandler.execute` 先走 `findAllAvailablesCopilots({ role })`；为空时要求请求上下文身份与查询的 tenant/organization 完全一致，再用 `FindCopilotModelsQuery`（`CopilotModelCatalogMode.Available`）过滤 `findAllEnabledCopilotsWithoutMembership` 的候选。

### ② provider 凭据解析与组织级覆盖

- 写入：`CopilotProviderController.create/update` 走 `CopilotProviderUpsertCommand`；`CopilotProviderUpsertHandler` 先用 `providersService.getProvider(providerName, true)` 确认策略存在，再用 `AiProviderCredentialsValidateCommand` 让插件按 `provider_credential_schema` 过滤并校验凭据，最后 create/update —— 校验不通过则一行都不落库。
- 读取与覆盖：`findVisibleByCopilotIds` 返回 `Map<copilotId, CopilotProvider>`，`organizationId` 存在时查两支 where，按 `organizationId` 非空的那条覆盖租户级。
- 自定义模型：`CopilotProviderModelService.upsertModel` 强制 `modelName`，创建时必须给 `modelProperties`；`model_configuration` 走 `modelConfigurationSchema.safeParse` 且类型必须等于 `modelType`；写入时把 `configuration_source` 固定成 `manual`，并保留/删除 `discovery_model_id`；改名前会用 `modelManager.validateCredentials(modelName, {...provider.credentials, ...modelProperties})` 校验；改名或换类型会调 `ModelAccessService.handleConfiguredModelDeleted` 关闭历史授权。
- 发现与导入：`ModelDiscoveryService.discover` 比对 `discovery_model_id` / `modelName` 标记 `configured`；`importModels` 在事务内 `pessimistic_write` 锁 provider 行，只追加不更新已存在行，并原子写回 `provider.options.modelDiscovery = { mode: 'configured', syncedAt, availableModelIds }`。

### ③ 运行时创建模型客户端

- `CopilotModelGetChatModelHandler.execute` 的固定顺序：定位 `copilotModel` → 缺 `copilot` 时用 `CopilotGetOneQuery` 补 `modelProvider` 关系 → `CopilotCheckLimitCommand` 拿 `modelAccess`（并回调 `modelAccessCallback`）→ `GetCopilotProviderModelQuery` 取自定义模型（用作 `modelProperties`）→ `AIModelGetProviderQuery` 解析策略 → `ensureCopilotModelContextSize` 归一化 `context_size` → `resolveModelParameterOptions` 合并参数规则 → `getModelInstance(modelType, {...copilotModel, copilot}, { verbose, modelProperties, resolveUsagePricingSnapshot, handleModelUsage, handleLLMTokens })` → `setModelVisionSupport`。
- token 记账埋点在 `handleLLMTokens`：先调外部 `usageCallback`，`usage.type === 'estimated'` 直接返回，缺 `model` 只记 error 日志，其余构造 `CopilotTokenRecordCommand`（补 `requestId = input.requestId ?? randomUUID()`、`usageHour` 由下游计算）。
- `CopilotModelGetEmbeddingsHandler` 只校验 `modelType === TEXT_EMBEDDING`，然后复用同一 ChatModel 查询；`CopilotModelGetRerankHandler` 是独立实现（校验 `modelType === RERANK`，走 `CopilotCheckLimitCommand` + `CopilotModelUsageRecordCommand`，不接 `handleLLMTokens`）。

### ④ 限额校验、用量聚合与投递

- 校验：`CopilotCheckLimitHandler` 先 `ModelAccessService.assertCanUseModel` 得到 `billableUserId`，再分别用 `CopilotUserService.getUsageSummary`（userId + provider + model + orgId）与 `CopilotOrganizationService.getUsageSummary`（provider + model）比 `tokenLimit`，超限抛 `ExceedingLimitException`（i18n key 分用户/组织两套）。
- 聚合写：`CopilotTokenUsageDeliveryService.deliver` 在单事务内 `orIgnore` 插回执 → `pessimistic_write` 读回执 → 校验 `payloadFingerprint` → `status === 'completed'` 短路 → `CopilotUserService.upsert`（按 tenant/org/orgId/xpertId/threadId/userId/provider/model/usageHour）→ 有 `organizationId` 时 `CopilotOrganizationService.upsert` → 回写 `userRollupDeliveredAt` / `organizationRollupDeliveredAt` / 两个 `*TokenLimitExceeded` / `completedAt`。
- 账本事实：`ModelUsageLedgerService.recordTokenUsage` 要求 `totalTokens > 0`，`pricingStatus` 由 `priced/free/unpriced` 与 `priceAmount` 推导，`settleChargeToCny` 折算结算币种，`insert().orIgnore()` 落 `membership_point_ledger`（`source = ModelUsage`、`revision: 1`、`metricKey: 'token'`），随后对 `settlementAmount > 0` 的行调 `membership.recordUsage`。
- 读侧：`CopilotUsageService` 把 `ledger*` 全部委托 `ModelUsageLedgerService`（`findPage` / `findAccountPage` / `findBreakdownPage` / `totals`，底层 `createModelUsageReadQuery` 直查 `membership_point_ledger` 并叠加 `LEGACY_USAGE_SOURCES` 兼容谓词）；`summary` 按 dimension 分派 user/model/organization 三种聚合；`quota/adjust|renew` 走 `findQuotaRecords` + `saveQuotaRecords`；`repair-organization-usage` 需要 `RolesEnum.SUPER_ADMIN`。

### ⑤ 向量存储与 checkpoint

- `CopilotMemoryStore`：`ensureTableInDatabase(dimensions)` 用 `CREATE_VECTOR_TABLE.replace('$1', 'vector(N)')` 建表；写入用 `INSERT ... ON CONFLICT (prefix, key, field_name) DO UPDATE`；检索用 `copilot_store s JOIN copilot_store_vectors sv` 加打分排序；`PutOperation` 走 `batchPutOps`。
- `CopilotKnowledgeService`：`getVectorStore(tenantId, organizationId, role)` 以 `(organizationId || tenantId) + ':' + (role || 'default')` 作 collectionName（租户级 embedding Copilot 时退化为 tenant 维度），拿不到 embedding Copilot 直接 `throw new Error('No embedding copilot found')`；`create` / `update` / `delete` / `createBulk` 全部同步 PGVectorStore 并回写 `provider` 与 `vector: true`；`similaritySearch` 在指定 role 命中为空时回退默认 role，并按 `1 - score > (score ?? 0.7)` 过滤。

## 2. 设计模式及落点

- **CQRS（全量）**：写走 `CommandBus`（`CopilotProviderUpsertCommand`、`GeneratePromptCommand`、`CopilotTokenRecordCommand`、`CopilotModelUsageRecordCommand`、`CopilotCheckLimitCommand`、`CreateModelClientCommand`），读走 `QueryBus`（`CopilotOneByRoleQuery`、`FindCopilotModelsQuery`、`GetCopilotProviderModelQuery`、`AIModelGetProviderQuery`、`AIModelGetIconQuery`）。
- **注册表 + 策略**：`AIProvidersService.getProvider` 从 `AIModelProviderRegistry` 取 `IAIModelProviderStrategy`，provider 语义（模型清单、参数规则、凭据 schema、定价快照）全部外置到插件。
- **DTO 脱敏**：`CopilotProviderPublicDto` 用 class-transformer 的 `@Exclude()` 屏蔽 `credentials`，`CopilotUserController` 用 `PublicCopilotUserDto` + `UserPublicDTO` / `OrganizationPublicDTO` 收敛返回字段。
- **幂等回执（Outbox 变体）**：`ModelUsageDeliveryReceipt` 的「唯一索引 + `orIgnore` 插入 + 悲观锁读回 + fingerprint 比对 + `completed` 短路」是标准四段式。
- **TypeORM subscriber 补上下文**：`CopilotModelSubscriber.beforeInsert` 在实体层统一回填 tenant/org，避免各调用点重复传参。
- **运行期 DDL**：`CopilotMemoryStore.ensureTableInDatabase` 与 `PGVectorStore.ensureTableInDatabase/ensureCollectionTableInDatabase` 在首次使用时建向量表，绕开迁移体系。
- **凭据判定交给 schema**：`usesOrganizationCredentials` 不看具体 key 名，只看 `credential_form_schemas` 中 `type === SECRET_INPUT` 且 `show_on` 条件成立的字段是否有值。

章节来源：[packages/server-ai/src/copilot/utils.ts](file://packages/server-ai/src/copilot/utils.ts)（关键符号：usesOrganizationCredentials）

## 3. 热点路径

- **每次对话的模型选择**：`CopilotOneByRoleQuery` → `findAllAvailablesCopilots`（3 个并行探测 + OR 查询 + `findVisibleByCopilotIds` 再查一次 provider）→ `CopilotCheckLimitCommand`（2 次 SUM 聚合）→ `getModelInstance`。这条链在每轮对话都会执行一次，且 `getUsageSummary` 的两个聚合都无缓存。
- **role 兜底查询**：`findAllAvailablesCopilots` 为空时会再执行一次 `FindCopilotModelsQuery`（在 `copilot-model-find.handler.ts` 内对每个 Copilot 叠加 provider 内置模型 + 自定义模型 + schema 查询），成本显著高于首次查询。
- **记账写路径**：`CopilotTokenRecordCommand` → `recordTokenUsage`（`insert().orIgnore()` + 回读 `find`）→ 逐行 `membership.recordUsage`；随后 `deliver` 再开一个事务（回执 + 两个 upsert），单轮对话的 token 记账至少产生两次事务边界。
- **读侧聚合**：`ledger` 系列每个端点都跑「分页键聚合 + `COUNT(DISTINCT ...)` 总数字」两条查询；`findAccountPage` 还要再补一次 metrics 聚合与一次用户表 `find`。
- **checkpoint 读写**：`getTuple` 在未给 `checkpoint_id` 时按 `checkpoint_id DESC take 1` 取最新行，再拉全部 pending writes 并逐条 `serde.loadsTyped`。

## 5. 技术债与 hack

- **无权限的读入口**：`CopilotController.findAllCopilots` / `getOne` 没有任何 `@Permissions`，靠 `CrudController` 的登录态即返回全部 Copilot 配置；`CopilotProviderController` 的 `:providerId/model`、`:providerId/model/:id`、`model-parameter-rules`、`POST|PUT|DELETE :providerId/model[/:id]` 同样无权限装饰器。
- **凭据明文**：`CopilotProvider.credentials` 是普通 `json` 列，无加密 transformer；「组织内读租户级 provider 用 `CopilotProviderPublicDto` 遮住 credentials」是唯一防线，任何新增的直出路径都会泄漏密钥。
- **`copilot_store_vectors` 实体被注释**：DDL 在 `CopilotMemoryStore.ensureTableInDatabase` 里以字符串 replace 生成（`dimensions` 为空时列类型退化为 `vector`），ORM 与表结构、索引、外键均不在同一处维护。
- **聚合列的读-改-写**：`CopilotOrganizationService.upsert` 与 `CopilotUserService.upsert` 都是「findOne → 累加 → save」，没有行锁、也没有唯一索引兜底；并发投递同一 key 时存在丢失更新与重复插入的可能。
- **`copilot_user` 的唯一性只写在注释里**：实体注释「Unique index: user, provider, model」，实际只有 3 个普通 `@Index`，没有 `unique: true`。
- **两条模型创建入口并存**：`CopilotModelGetChatModelQuery` 已标 `@deprecated` 指向 `CreateModelClientCommand`，而后者又委托 `AgentMiddlewareRuntimeService`，调用方需自行判断走哪条。
- **`primary/verify` 会真实消耗额度**：`PrimaryModelSmokeService.infer` 用 `max_tokens: 16` 真调模型，`usageCallback` 传空实现但 `handleLLMTokens` 仍会发出 `CopilotTokenRecordCommand`，因此该自检会留下真实用量与账本行（超时 20 秒不阻断已发生的调用）。
- **`PageSize` 型硬上限**：`findDetails` 固定 `DETAIL_LIMIT = 200`；`CopilotUsageService` 的 `overview` 走 `DATE_TRUNC('day')` 全表分组，没有时间下限时可能扫全表。
- **历史残留**：`copilot.service.ts` 保留了注释掉的 `findOneByRole` 与旧版可见性过滤；`copilot-store/tests/store.test.ts` 直连本机 PG（`DB_USER`/`DB_PASS`/`DB_NAME`）且无 `describe.skip` 门控。

## 6. 设计维度分析

**维度一：可见性即授权。** 本子域没有自己的授权表，而是把「membership 计划范围」与「model-access 判定」乘积成 `queryScopes`，再叠加「组织级凭据直连」特例。优点是不引入第二套授权真源、配置改动即时生效；代价是 `findAllAvailablesCopilots` 的分支矩阵（4 种 scope 组合 × 直连例外）只能靠单测覆盖，生产上很难从现象反推命中哪条分支；同时组织级 provider 覆盖租户级 provider 与「组织未配置模型时允许用租户 Copilot」两条规则叠加，使「为什么这个 Copilot 可见」需要同时读三处代码。

**维度二：配置真源双轨。** 模型信息分散在 `copilot_model`（选中的模型）与 `copilot_provider_model`（自定义模型及其 `modelProperties`）两处，运行时由 `get-chat-model.handler.ts` 合并（自定义模型优先提供 `modelProperties`，参数规则由插件补）。好处是自定义模型可以独立于 Copilot 生命周期演进（甚至有 `referencedModel` 自引用）；代价是判断「Vision 是否支持」「context_size 取谁」要在三处取值（`options.context_size` → `model_configuration.contextSize` → provider 内置 `model_properties`），`resolveModelVisionSupport` 与 `ensureCopilotModelContextSize` 就是这个优先级链的固化实现。

**维度三：账本事实与配额聚合分离。** `copilot-usage` 只读 `membership_point_ledger`，配额却落在 `copilot_user` / `copilot_organization` 两张聚合表。这个设计让读模型不需要新表，也让配额重置（`renew`）与账本永不互相污染；代价是同一笔用量在两处有不同投影，聚合表一旦丢更新，只能靠 `repair-organization-usage`（SUPER_ADMIN 限定）从 `copilot_user` 反推重建组织行。

章节来源：[packages/server-ai/src/copilot-model/model-capabilities.ts](file://packages/server-ai/src/copilot-model/model-capabilities.ts)（关键符号：resolveModelVisionSupport）、[packages/server-ai/src/copilot-model/utils/context-size.ts](file://packages/server-ai/src/copilot-model/utils/context-size.ts)（关键符号：ensureCopilotModelContextSize）

## 7. 结论

实现层面五条流程各自闭环：配置侧「provider 先验凭据、模型先验 schema、发现导入锁 provider 行」；运行侧「限额 → 参数归一 → `getModelInstance` → token 记账」集中在 `get-chat-model.handler.ts` 一处，可读性好；用量侧「回执幂等 + 两个聚合 upsert」把重复投递挡在事务内；账本事实用 `orIgnore` 与 `revision` 兜底；存储侧 checkpoint 清理有 advisory 锁与分支钉住逻辑。演进优先级建议为：给 `CopilotController` / `CopilotProviderController` 的读端点补权限声明，把 provider 凭据改为加密列或至少收敛直出路径，给 `copilot_user` / `copilot_organization` 补唯一索引 + 行锁或 `ON CONFLICT DO UPDATE` 原子累加，并把 `copilot_store_vectors` 的 DDL 与实体重新对齐。
