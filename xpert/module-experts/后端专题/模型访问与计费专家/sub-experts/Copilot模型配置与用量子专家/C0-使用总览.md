## 定位与何时找

一句话：本子域是「**配置面 + 用量读侧**」的聚合边界——它决定「用哪个 provider 的哪个模型」，把配置装配成可用的模型客户端，并对外提供用量与配额的读写视图；账本本身的写权限不在这里。

找这个子专家的场景：

- 要新增/修改 provider 与凭据（组织级或租户级），或排查「凭据配置了但模型不可用」。
- 要发现远端模型并导入为自定义模型，或排查导入后 `configured` 标记不更新。
- 要按角色（Primary / Secondary / Reasoning / Embedding）取当前用户可用的 Copilot。
- 要写「用某个 Copilot 的某个模型创建客户端」的代码，并确保额度校验与 token 记账被接上。
- 要查/运维用量与配额（账本分页、账户与模型/供应商维度分解、总量、概览、配额调整与重置、组织用量修复）。
- 要读写会话检查点、做保留清理，或维护 few-shot 知识库与其向量检索。
- 要维护 LangGraph BaseStore（`copilot_store` 与运行期向量表）。

## 边界

**做什么**

- `copilot` / `copilot_model` / `copilot_provider` / `copilot_provider_model` 四张配置表的读写与其可见性计算。
- provider 凭据落库前的 schema 校验、组织级覆盖租户级的解析、模型发现与导入。
- 按角色解析可用 Copilot，并把配置装配为可用的模型客户端（含限额校验与 token 回调埋点）。
- 用量事实落库（`model_usage` 事实行）与用量/配额读侧统计；组织级用量修复。
- checkpoint / writes 存取与保留清理；`copilot_store` 与向量表；`copilot_knowledge` 与向量库同步。
- provider/model 元数据与插件策略解析（`ai-model`，本子域上游）。

**不做什么**

- **不管授权与账本写入**：`user_model_grant` / `model_access_request` 属 `model-access`；积分扣减只经 `MembershipService.recordUsage`，本子域只写 `pointsDelta: 0` 的事实行（`copilot-usage` 负责事实行）。执行期准入与预占（grant / admission）属父域另一子专家，本子域不读取其表。
- **不管对话与会话**：会话、消息、线程本体不在本专家域内；checkpoint 端点只做访问断言后落盘，不实现会话语义。
- 不实现供应商协议与定价：模型客户端、参数规则、凭据 schema、定价快照全部来自 Provider 插件的策略实现。
- 不做对外 HTTP 模型兼容层：`/api/openai/v1` 与 `/api/model-execution/*` 不属于本子域。
- 不做平台身份与权限点定义：租户/组织/用户与权限点由其他批次专家提供（本子域只消费）。

## 已知坑（12 条）

1. **部分 Copilot 读端点没有权限点**
   - 现象：登录后即可列出全部 Copilot 配置。
   - 触发条件：`CopilotController` 的 `GET /api/copilot`、`GET /api/copilot/:copilotId`，以及 `availables*` / `providers` / `models` / `model-select-options` / `generate-prompt` 只有登录态。
   - 正确做法：不要把这两个端点当管理端点使用；需要收敛时在网关层或前端按角色过滤，新增端点必须显式补 `@Permissions` 并加反射断言测试。
   - 契约来源：`CopilotController.findAllCopilots` / `CopilotController.getOne`。
2. **provider 凭据不是加密列**
   - 现象：预期读不到明文，实际 `credentials` 就是普通 `json` 内容。
   - 触发条件：`CopilotProvider.credentials` 声明为普通 `json` 列，无 transformer；唯一遮蔽是组织内读租户级 provider 时返回的 `CopilotProviderPublicDto`（`@Exclude()`）。
   - 正确做法：任何新增直出路径、日志打印或前端序列化都要重新评估泄漏面；不要把它当「加密列」设计。
   - 契约来源：`CopilotProviderController.findOneById`、`CopilotProvider`。
3. **`copilot_store_vectors` 的 `@Entity` 被整块注释**
   - 现象：ORM 视角看不到向量表，但检索可用；索引与外键无统一维护点。
   - 触发条件：表由 `CopilotMemoryStore` 在 `ensureTableInDatabase` 时以原生 SQL 建（`PK(prefix, key, field_name)` + 外键到 `copilot_store ON DELETE CASCADE`）。
   - 正确做法：向量表结构以存储实现为准，不要依赖实体同步；新增维度前先确认已有表定义。
   - 契约来源：`copilot-store/vectors/vectors.entity.ts`（整文件注释）、`CopilotMemoryStore.ensureTableInDatabase`。
4. **组织级覆盖租户级的判定很窄**
   - 现象：期望「组织配置生效」但实际仍走租户级，或反之。
   - 触发条件：`findVisibleByCopilotIds` 同时查 `organizationId = :organizationId` 与 `organizationId IS NULL`，仅当「已存在的那条 `organizationId` 为空、新命中的那条非空」才替换。
   - 正确做法：判断「为什么这个 Copilot 用了这份凭据」时必须同时核对两支查询与替换条件，不要只看 provider 表里的行数。
   - 契约来源：`CopilotProviderService.findVisibleByCopilotIds`。
5. **可见性是「会员范围 × 授权目录」的乘积，还有直连例外**
   - 现象：同一用户在不同组织下可见集合不同，或模型对某用户不可见却对另一用户可见。
   - 触发条件：`findAllAvailablesCopilots` 先算 `membershipAllowedScopes`；不在集合内的 Copilot 仅当「非 `MEMBERSHIP_EDIT` 用户」且使用组织级凭据（`usesOrganizationCredentials` / `hasOrganizationModelCredentials`）时才保留。
   - 正确做法：排查可见性问题按「四个 scope 组合 + 直连例外」五个分支逐一排除，不要用单表查询推断。
   - 契约来源：`CopilotService.findAllAvailablesCopilots`、`copilot/utils.ts`（`usesOrganizationCredentials`）。
6. **`GetChatModelQuery` 等是创建 LangChain 客户端的唯一入口**
   - 现象：自己 `new` provider SDK 客户端，结果没有限额校验、也没有用量与账本。
   - 触发条件：绕过 `CopilotModelGetChatModelQuery` / `GetEmbeddingsQuery` / `GetRerankQuery` 直接构造客户端。
   - 正确做法：一律走这三个查询处理器（或它们的 `CreateModelClientCommand` 替代入口），并接上 `usageCallback` / `modelUsageCallback`；注意 `GetChatModelQuery` 类注释已标 `@deprecated use CreateModelClientCommand instead`，两条路径目前并存，调用方需明确选一条。
   - 契约来源：`CopilotModelGetChatModelQuery`、`CopilotModelGetEmbeddingsQuery`、`CopilotModelGetRerankQuery`、`CreateModelClientHandler`。
7. **GET 有写副作用的入口要分清楚属于谁**
   - 现象：一次读取后数据量变化。
   - 触发条件：本子域内 `CopilotController` 的读端点、`CopilotProviderController` 的模型读取端点与 `CopilotUsageController` 的读端点**都不写库**；「GET 写默认设置」属 `model-gateway` 的 `ModelGatewayService.getSettings`（父专家 C0 第 3 条已收录），不在本子域。
   - 正确做法：本子域真正要警惕的写副作用在写路径上——`CopilotService.enableRole(Primary)` 会进一步触发组织会员初始化（写组织默认会员）。
   - 契约来源：`CopilotService.enableRole`、`ModelGatewayService.getSettings`（不在本子域）。
8. **`primary/verify` 会真实消耗额度**
   - 现象：做一次模型自检后用量中心出现真实消耗与账本行。
   - 触发条件：`PrimaryModelSmokeService.verify` 真实调用 Primary LLM（20 秒截止），`usageCallback` 传空实现但 token 回调仍会发出记账命令。
   - 正确做法：把它当「真实调用」纳入用量预期与告警；超时 20 秒**不阻断**已经发生的调用。
   - 契约来源：`CopilotController.verifyPrimaryModel`、`PrimaryModelSmokeService.verify`。
9. **聚合列是读-改-写，没有行锁也没有唯一索引**
   - 现象：并发投递同一 key 时出现丢失更新或重复聚合行。
   - 触发条件：`CopilotUserService.upsert` / `CopilotOrganizationService.upsert` 都是 `findOne → 累加 → save`；`copilot_user` 实体注释里承诺的唯一键**没有落到 DDL**。
   - 正确做法：把聚合行视为「可能被稀释的估算视图」，权威口径以账本为准；组织行丢更新时用 `repairOrganizationUsage`（限 SUPER_ADMIN）从用户聚合反推重建。
   - 契约来源：`CopilotUserService.upsert`、`CopilotOrganizationService.upsert`。
10. **checkpoint 清理窗口与保留边界**
    - 现象：以为清理干净了，实测仍有大量历史行。
    - 触发条件：只 `@Cron('0 0 3 * * *')` 跑一次，单轮上限 `batchSize(1000) × maxBatchesPerRun(20)`；被消息输出检查点引用链锚定的祖先、仍有运行控制的线程、仍被输入检查点引用的行会**永久保留**；未开启保留开关的租户不清理。
    - 正确做法：对账「预期删除量」时按上述四条排除项计算；多副本下靠 `pg_try_advisory_lock` 去重，拿不到锁的那一 tick 直接跳过。
    - 契约来源：`CopilotCheckpointRetentionService.execute` / `runScheduledCleanup`。
11. **凭据判定不看具体 key 名**
    - 现象：按猜想的字段名判断「是否组织级凭据」而得错。
    - 触发条件：`usesOrganizationCredentials` 依据 provider 的 `credential_form_schemas` 中 `type === SECRET_INPUT` 且 `show_on` 条件成立的字段是否有值。
    - 正确做法：沿用该函数而不是自己读 `credentials` 的字段名；provider 插件改 schema 时该判定会随之变化。
    - 契约来源：`copilot/utils.ts`。
12. **存储侧的两个外溢约束**
    - 现象：跨租户写入冲突，或删用户被外键拒绝。
    - 触发条件：`copilot_store` 的 `key_in_namespace` 唯一索引**不带租户维度**（全库 `(prefix, key)` 唯一）；`createdBy` 关系为 `ON DELETE: RESTRICT`。
    - 正确做法：`prefix` 里带上租户/组织隔离维度；删除创建过 store 项的用户前先清理其 store 行。
    - 契约来源：`copilot-store/copilot-store.entity.ts`。
