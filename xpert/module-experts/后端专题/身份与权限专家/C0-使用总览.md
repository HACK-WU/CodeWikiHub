# C0 使用总览：身份与权限专家（父专家）

> 契约层文档（父专家）｜读者：本域外部调用方（同进程服务调用、HTTP 客户端、其他专家）
> 资产基线：**2026-10-15 · commit `c07bb83d`**｜覆盖 3 个子专家
> 配套：同目录 `C1-能力契约.md`

## 1. 专家定位

身份与权限专家回答两个问题：**请求是谁**（凭据 → principal）与**这个人能做什么**（角色 → 权限位），并维护「人—租户—组织」的归属关系。

- 三段式结构：凭据（登录 JWT/refresh、API key、secret token、actor token、外部身份绑定）→ 归属（用户、组织、成员关系、用户组、邀请）→ 判权（角色 + 权限位 + guard）。
- 对外契约有三类：HTTP 端点、同进程服务方法（NestJS provider）、判权装饰器与 guard（`@Permissions` / `@Roles` / `@Public()`）。
- 运行时判权只有一条真实路径：`@Permissions` + `PermissionGuard`（或 `@Roles` + `RoleGuard`）。CASL 能力工厂存在但**未接线**（`CaslAbilityFactory.createForUser` 全仓无调用者，见 [casl-ability.factory.ts](file://packages/server/src/core/casl/casl-ability.factory.ts)）。
- 凭据解析结果统一落在请求上下文：`RequestContext.currentUser()` / `currentUserId()` / `currentTenantId()` / `currentRoleId()` / `getOrganizationId()`（见 [request-context.ts](file://packages/server/src/core/context/request-context.ts)）。

## 2. 何时找这个专家

- 「我要登录 / 注册 / 刷新令牌 / 重置密码 / 验证邮箱」→ 认证与凭据子专家。
- 「我要 SSO / 社交登录 / 把第三方账号绑到已有用户」→ 认证与凭据子专家（`auth/sso/`、`packages/auth` 社交策略、`account-binding/`）。
- 「我要签发或校验 API key、client secret、内部服务间 actor token」→ 认证与凭据子专家。
- 「我要把人加进组织 / 建组织 / 改成员默认组织 / 建用户组 / 发邀请 / 管员工」→ 组织与成员子专家。
- 「我要定义角色、维护权限位、给接口加权限拦截、排查 403」→ 角色与权限子专家。
- 「我要读当前用户、按邮箱查用户、判断活跃成员、删除用户」→ 组织与成员子专家（`UserService`）。该模块被大量外部模块依赖：调研口径 36 个模块依赖 `user`，实测 18 个旁路模块显式 import `UserModule`。

## 3. 契约自足声明

- 本文 + `C1-能力契约.md` 构成完整对外契约：`C0` 回答「找谁、走哪个入口、有哪些坑」，`C1` 回答「签名、参数语义、返回、异常、约束」。集成与排障无需先读实现代码。
- 契约粒度为 HTTP 端点与同进程服务方法；出现的类名/方法名均为源码原文签名，未能核实处显式标注「未确认」。
- 父专家只给「域级入口索引 + 服务契约主体」；端点明细与字段级约定以各子专家 `05-接口` 为准（见 §9）。

## 6. 能力清单

| 能力 | 对外入口（HTTP 或服务方法） | 一句话 |
| --- | --- | --- |
| 密码登录 | `POST /api/login`（`@Public`） | 邮箱 + 密码校验后签发 access/refresh 并落库 refresh |
| 免费注册 | `POST /api/signup`（`@Public`） | 建用户（邮箱待验证）+ 发验证邮件 |
| 通用注册 | `AuthService.register` / `POST /api/register` | 注册、加入组织、受邀接受、代客创建共用同一入口 |
| 令牌刷新 | `GET /api/refresh` / `AuthService.refreshTokens` | 校验 refresh 后轮换，旧 refresh 立即失效 |
| 令牌有效性 / 角色断言 | `GET /api/authenticated`、`GET /api/role` | 只读断言，不签发新令牌 |
| 密码重置 | `POST /api/request-password`、`POST /api/reset-password`（均 `@Public`） | 邮件链接带 token；重置失败统一 400 + code |
| 邮箱验证 | `GET /api/verify`、`POST /api/resend-verification` | 验证令牌有效期 2 天 |
| SSO 与社交登录 | `/api/sso/providers`、`/api/sso/bind/*`；`packages/auth` 各 provider 回调 | 绑定成功后统一走 `AuthService.issueTokensForUser` |
| 外部身份绑定 | `GET|DELETE /api/me/:provider`、`AccountBindingService.*` | 第三方身份 ↔ 用户绑定，冲突显式报错 |
| API key | `x-api-key` 头（`ApiKeyStrategy`）；`ApiKeyController` 仅 CRUD 基类路由 | 校验记录有效性并生成 principal |
| secret token / client secret | `x-client-secret` 头或 `Authorization: Bearer cs-x-...` | 按绑定类型分派 principal 并决定组织/租户作用域 |
| 出站 actor token | `OutboundActorTokenProvider.mint`（无 HTTP 入口） | 无状态短时委派令牌（默认 TTL 900s 封顶） |
| 用户与个人设置 | `GET /api/me`、`PUT /api/me`、`PUT /api/preferred-language/:id`、`GET /api/user/email/:email` | 读当前用户视图 / 自更新资料与偏好 |
| 组织与成员 | `/api/organization*`、`/api/user-organization*` | 组织 CRUD、成员关系与「默认/活跃」不变量 |
| 用户组 | `/api/user-group*`（含 `/api/user-group/:id/members`） | 组织内成员分组，用于运行授权增量 |
| 员工 | `/api/employee/user/:userId` | 员工记录查询（本域现存最薄入口） |
| 邀请三路径 | `POST /api/invite/emails`、`GET /api/invite/validate`、`POST /api/invite/user|employee|contact`、`POST /api/invite/resend` | 批量创建、公开接受（用户 / 员工 / 组织联系人） |
| 角色与权限判定 | `@Permissions`+`PermissionGuard`、`@Roles`+`RoleGuard`、`RolePermissionService.checkRolePermission` | 角色权限行存在性判定（含短时缓存） |

## 7. 边界

### 7.1 做什么

- 身份生命周期：注册、登录、令牌签发/刷新、密码重置、邮箱验证。
- 凭据全生命周期：JWT/refresh、API key、secret token、actor token 的签发与校验，外部身份绑定。
- 归属建模与维护：组织、成员关系、默认/活跃不变量、用户组、邀请、员工、联系人。
- 判权基础设施：角色、角色权限位、`@Permissions`/`@Roles`/`@Public()` 拦截语义。

### 7.2 不做什么

- **不含租户生命周期本身**：`tenant/` 属邻近模块；本域只在邀请接受（组织联系人路径）中调用 `TenantService` 与租户角色批量创建。
- **不做业务域资源授权决策**：工作台/Xpert/知识库的资源级语义由消费方（如 server-ai 的工作台访问层）落实；本域只提供 principal、角色、权限位与 guard。
- **不提供 CASL 运行时判权**：`CaslAbilityFactory.createForUser` 无调用者，不要按 CASL 语义编写集成。
- **不做插件/业务模块的市场与生命周期**（属 plugin 域）。

## 8. 已知问题与常见坑

1. **guard 无注解即放行**
   现象：未声明 `@Permissions`/`@Roles` 的接口对任何已登录用户开放。
   触发：新建 controller/方法时漏写判权注解。正确做法：把注解清单纳入评审基线，逐接口核对。
   契约来源：`PermissionGuard.canActivate`（[permission.guard.ts](file://packages/server/src/shared/guards/permission.guard.ts)）、`RoleGuard.canActivate`。
2. **CASL 未接线**
   现象：按 CASL 能力模型设计的判权不会生效。
   触发：集成时以为有「能力-主题」授权层。正确做法：只用 `@Permissions`+`PermissionGuard`。
   契约来源：`CaslAbilityFactory.createForUser`（无调用者）。
3. **租户权限 guard 只剩骨架**
   现象：`TenantPermissionGuard` 只做基类校验与 `SUPER_ADMIN` 短路，不会按租户权限集判权。
   触发：期望它拦截非超管的租户级操作。正确做法：额外叠加 `@Permissions` + `PermissionGuard`。
   契约来源：`TenantPermissionGuard.canActivate`。
4. **邀请接受端点完全公开**
   现象：`POST /api/invite/user|employee|contact` 无鉴权却会建用户/组织/租户。
   触发：泄漏或猜测 invite token 与邮箱。正确做法：视为高危公开写入口，邮件侧与 token 唯一性是唯一防线，勿在这些端点挂内部逻辑。
   契约来源：`InviteController.acceptUserInvite` / `acceptEmployeeInvite` / `acceptOrganizationContactInvite`。
5. **`invite/employee` 与文档不符**
   现象：接受员工邀请实际不创建员工记录，只把邀请置为已接受。
   触发：依赖该端点同步员工数据。正确做法：不要以该端点作为员工创建入口（结果以 `InviteService.update` 为准）。
   契约来源：`InviteAcceptEmployeeHandler.execute`。
6. **`PUT /api/invite` 行为异常**
   现象：该路由未声明路径参数，却要求 `id`，等同不可用。
   触发：按 REST 习惯调用。正确做法：用 `POST /api/invite/resend`、`POST /api/invite/emails` 或 `PUT /api/invite/organization-contact/:id`。
   契约来源：`InviteController.update`（未确认是否为有意保留）。
7. **同一邮箱只能有一条有效邀请**
   现象：跨租户邀请同一邮箱会互相阻塞（被跳过的邮箱计入 `ignored`）。
   触发：同一邮箱已在「邀请中」或已是租户用户。正确做法：先处理既有邀请或用 `resendEmail`，并检查返回的 `ignored`。
   契约来源：`InviteService.createBulk`。
8. **判权结果有约 5 分钟授权残留**
   现象：回收角色权限后，最长 5 分钟内旧授权仍可能通过。
   触发：权限变更后立即做验证。正确做法：变更后等待缓存过期或走变更后重新登录/重启路径；不要以「改权限即时生效」做安全假设。
   契约来源：`PermissionGuard.canActivate`。
9. **判权语义是「任一权限命中即通过」且默认忽略角色**
   现象：只要求传 `permissions` 时，租户内任意角色命中即返回 `true`。
   触发：直接调用判权服务且未开启角色维度。正确做法：以角色维度判定时必须显式开启角色条件（guard 走的就是该分支）。
   契约来源：`RolePermissionService.checkRolePermission`。
10. **密码重置是跨租户语义且窗口极短**
    现象：重置记录不携带租户维度，有效期固定（10 分钟内）；失败统一为 400「Password Reset Failed (code: 1|2|3)」。
    触发：延迟点击邮件链接、跨租户同邮箱场景。正确做法：失败提示按 code 分类处理，不要把 400 当成「密码错误」。
    契约来源：`AuthService.resetPassword`、`PasswordReset`。
11. **`validateUser` 只在邮箱已验证时命中**
    现象：未验证邮箱的用户走该校验会被判为「不存在」（401）。
    触发：复用 `AuthService.validateUser` 做自研登录入口。正确做法：明确该入口的前置条件是邮箱已验证，否则先用登录主链路或 `resetPassword` 之后的验证置位。
    契约来源：`AuthService.validateUser`。
12. **超管不建成员关系**
    现象：`SUPER_ADMIN` 调用加组织成员时返回空数组，不产生成员关系。
    触发：按成员关系判断超管归属或组织可见性。正确做法：判定组织可见性时把超管作为特殊分支（`UserService.isActiveMemberOfOrganization` 即如此）。
    契约来源：`UserOrganizationService.addUserToOrganization`。
13. **成员不变量会拒绝「看起来正常」的写入**
    现象：置 `isActive=false` 或删除最后一条成员关系会抛错；直接置默认组织会顺带把其它默认降级。
    触发：脚本化修改成员关系。正确做法：删除最后一条须显式传参放行；置默认前明确期望「至多一个默认」。
    契约来源：`UserOrganizationService.update` / `delete`。
14. **跨模块读当前用户不要读半成品上下文**
    现象：只传 id 构造的用户对象缺少角色/员工/组织装配，权限位为空。
    触发：自行拼 `Partial<User>` 或跳过当前用户读取方法。正确做法：用 `UserService.findCurrentUser` / `getIfExists`，或用 `RequestContext.currentUser()`。
    契约来源：`UserService.findCurrentUser`、`AuthService.createToken`（缺角色时 payload 的 `role`/`permissions` 为 null）。
15. **删除用户必须走守卫入口**
    现象：直连删除会残留成员关系与外部身份绑定，且可能删掉最后一个管理员。
    触发：绕过 `deleteWithGuards` 调 CRUD 删除。正确做法：统一走 `UserService.deleteWithGuards`（含成员清理与绑定清理），物理删除仅在管理后台显式使用。
    契约来源：`UserService.deleteWithGuards`、`UserService.deleteHardWithGuards`。
