## 配置来源与装配

- 环境对象由 `@xpert-ai/server-config` 暴露（`environment` / `environment.prod`），`AuthService` 同时注入 `ConfigService<IEnvironment>` 读 `JWT_SECRET`、`jwtExpiresIn`、`JWT_REFRESH_SECRET`、`jwtRefreshExpiresIn`。
- actor token 不走 `ConfigService`，直接读 `process.env`（`XPERT_OUTBOUND_ACTOR_TOKEN_AUDIENCE`、`XPERT_OUTBOUND_ACTOR_TOKEN_TTL_SECONDS`、`JWT_SECRET`），所以**它可以在运行时被 env 覆盖而无需重启进程级别的配置变更**（仍受 `Math.min(...,900)` 限制）。
- 社交策略在实例化时用 `configService.get('<provider>Config')` 读取；缺 clientId/secret 时回退字符串 `'disabled'`，即“未配置”不会报错但 OAuth 流程必然失败——排查时应先看这些配置项而非日志。
- `AuthModule` 通过 `SocialAuthModule.registerAsync({ useExisting: AuthService })` 装配社交模块，运维上这意味着社交登录与账号密码登录**共用同一个 AuthService 实例与同一份 JWT 配置**。

## 部署相关

1. **回调地址必须在 provider 侧登记**，并与代码拼接一致：`GithubStrategy.config()` 等默认 `${baseUrl}/api/auth/<provider>/callback`；`baseUrl` 来自 `API_BASE_URL`，因此在反向代理/多域名部署下**必须把 `API_BASE_URL` 设为外部可达地址**，否则 OAuth 回调会指向内网地址。
2. **Auth0 与 Facebook 是两处已知偏差**：Auth0 默认回调缺 `api` 段（`${baseUrl}/auth/auth0/callback`），Facebook 缺省回落到 Google 的 callback。启用这两个 provider 时必须显式配置 `AUTH0_*` 对应的回调与 `oauthRedirectUri`，否则会串台。
3. **SSO discovery 依赖请求侧的 baseUrl**：`resolveRequestBaseUrl(request)` 优先读 `x-forwarded-proto`，再由 `resolveRequestHost` 取 host；网关若不透传 `x-forwarded-proto`/`Host`，provider 描述里的回调地址会变成 `http://<内部 host>`。
4. **Redis 是 SSO 绑定的硬依赖**：`PendingSsoBindingChallengeService.set` 需要 `setEx`，`consume` 需要 `getDel`；不支持会直接抛 `InternalServerErrorException`。多副本部署必须共用同一 Redis。
5. **邮件可用性是密码重置/邮箱验证的前置条件**：`EmailService.requestPassword` 与 `sendVerifyEmailMail` 失败会被 `AuthService` 吞成通用异常（`code: 1/2/3`），SMTP 故障表现为“重置失败”而非明确错误。

章节来源：[packages/server/src/auth/sso/request-base-url.ts](file://packages/server/src/auth/sso/request-base-url.ts)（关键符号：resolveRequestBaseUrl）、[packages/server/src/auth/sso/pending-sso-binding-challenge.service.ts](file://packages/server/src/auth/sso/pending-sso-binding-challenge.service.ts)（关键符号：PendingSsoBindingChallengeService.set、PendingSsoBindingChallengeService.consume）

## 日志与监控

可观测锚点（按排查价值排序）：

1. `ApiKey.lastUsedAt` 每次验证都会被刷新（`UseApiKeyQuery` 与 `SecretTokenStrategy.validateToken` 都会 `update(lastUsedAt)`），可用于判断密钥是否仍在被使用、能否安全吊销。
2. `SecretToken.validUntil` + `clientSecretExpiresAt`：principal 上带绝对过期时间，供长连接在初始认证后重新复核。
3. `AuthRegisterTrialHandler` 有 `logger.debug` 逐步日志（“Create trial user …”“Found TRIAL role …”“Created organization …”“Signup user …”），是注册问题最佳追踪点。
4. `AuthService` 持 `Logger` 实例（`validateOAuthLoginMobile` 会 `logger.debug` OAuth 输入）。
5. 反模式告警：`AuthService.requestPassword`/`resetPassword` 用 `console.log(error)` 后统一抛错，`JwtStrategy`/`WsJwtStrategy` 失败路径用 `console.error`——这些**不进结构化日志**，建议后续替换为 `Logger` 并附 `error.name`。
6. 审计事件：注册成功会发 `EVENT_ORGANIZATION_CREATED`，试用建号发 `trial_user.created`，可用于关联“谁在什么时候被创建”。
7. 建议监控指标：登录失败率（注意失败返回 `null` 而不是 4xx，需按响应体判定）、refresh 失败率（`Access Denied`）、`client-secret` 绑定类型分布、SSO challenge 过期率（`SSO binding session has expired`）、`Token expired`/`ApiKey expired` 计数。

| 表/字段 | 过期/唯一性语义 | 运维含义 |
| --- | --- | --- |
| `api_key.validUntil` | 可空；`@AfterLoad` 仅在有值时计算 `expired` | **为空 = 永不过期**，需要定期巡检空的长期密钥 |

## 安全运维注意

1. **轮换 `JWT_SECRET` 是“双影响面”操作**：它同时用于登录态 JWT 和出站 actor token 的 HS256 签名（`readSigningSecret()` 读同一个 `JWT_SECRET`）。轮换后：所有用户登录态失效、所有下游/插件已完成验签的 actor token 在 900s 内自然失效，且**必须与外部受信方同步密钥**，否则出站调用会被拒。
2. **轮换 `JWT_REFRESH_SECRET`** 会立即让所有 refresh token 失效（用户需重新登录），但不会影响 api key / client secret。
3. **api key / client secret 的吊销粒度是“行级”**：删除 `api_key` 行或让 `validUntil` 到期即可；`secret_token` 吊销同理。注意 `SecretTokenStrategy` 对 `API_KEY` 类型会级联检查其绑定的 api key 是否过期。
4. **无全局撤销/黑名单**：没有 logout 端点、JWT 无版本号或 `jti` 撤销表，因此“立刻踢人”只能靠轮换密钥或重置密码；涉及账号盗用的应急处置预案应写进 runbook。
5. **digest 边界**：`SecretTokenService.findBySecret` 显式拒绝以 `sha256:` 开头的输入，避免“库内摘要被当作 bearer 使用”；同时数据库导出物仍可能含历史明文密钥，导出/备份需按密钥对待。
6. **审计边界要写清**：`UserType.COMMUNICATION` 技术用户（`thirdPartyId = client:<code>` 等）与真人用户在同一个 `user` 表；`IApiPrincipal.resourceScope` 只是 audience 而非权限，任何“按 scope 放行”的运维脚本/网关策略都必须再叠加租户与成员校验。
7. **委托会话的复核要求**：`USER_XPERT` 委托会话在资源访问时要重新检查当前用户授权（含独立 Assistant 文件卷场景），不能以“凭据仍有效”作为继续访问的依据。
8. **登录无速率限制的证据缺口**：`AuthLoginHandler` 与 `AuthService.validateUser` 均未实现失败计数/锁定，暴力破解防护应放在网关/WAF 层，并监控登录失败率。

## 结论

- 上线前必须明确的四件事：`API_BASE_URL` 必须是外部可达地址（回调拼接依赖它）、Redis 必须可用（SSO 绑定硬依赖）、`JWT_SECRET`/`JWT_REFRESH_SECRET` 必须显式注入、每个启用的 provider 都要在控制台登记与源码一致的 callback。
- 轮换密钥的影响面大于直觉：`JWT_SECRET` 同时是登录态与出站 actor token 的签名密钥，需把外部消费方纳入变更窗口。
- 日常巡检重点：`api_key.validUntil` 为空的长命密钥、`secret_token.token` 中非 `sha256:` 的残余明文、SSO challenge 过期率、以及登录失败（注意其返回 200 + null）。
- 故障排查口诀：登录问题看 `AuthLoginHandler` 日志与 `tenant-id` 头；密钥问题区分 `api-key` 与 `client-secret` 两条链；SSO 问题先查 Redis，再查 `x-forwarded-proto`，最后查 binding 唯一约束冲突。
