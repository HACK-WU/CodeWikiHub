## 登录 / 刷新 / 登出链

**登录**：`POST /api/auth/login`（`@Public`）→ `AuthLoginCommand` → `AuthLoginHandler.execute`：

1. 从 `tenant-id` 头取租户（`getLoginTenantId`）拼 `tenantFilter`；若未命中且租户是 `DEFAULT_TENANT`，回退到不带头部的查询（`isDefaultTenantId`）。
2. `buildLoginUserOptions` 支持 `email + emailVerified` 或 `username` 两种标识，关联 `role/role.rolePermissions/employee`。
3. `bcrypt.compare(password, user.hash)` 失败直接 `return null`（**注意：不是抛 401**）。
4. 成功则 `AuthService.createToken(user)` + `AuthService.updateRefreshToken(user.id, refreshToken)`。

`AuthService.validateUser` 是 Basic 策略用的另一条口径：只按 `email + emailVerified=true` 查，失败抛 `UnauthorizedException`。

**刷新**：`GET /api/auth/refresh`（`@Public` + `AuthGuard('jwt-refresh')`）→ `RefreshTokenStrategy.validate` 从 `Authorization` 头取原始 refresh token 回填 payload → `AuthService.refreshTokens(userId, refreshToken)`：`user.refreshToken` 缺失或 `bcrypt.compare` 不匹配都抛 `ForbiddenException('Access Denied')`，成功后重新 `createToken` 并轮换 `updateRefreshToken`（旧 refresh 立即失效）。

**登出**：`packages/server/src/auth` 下没有 `logout` 端点（源码检索 0 命中），前端 `apps/cloud` 的 `/api/auth/logout` 调用在服务端无对应实现；登出语义只能靠 refresh token 轮换/过期实现，见“技术债”。

章节来源：[packages/server/src/auth/commands/handlers/auth.login.handler.ts](file://packages/server/src/auth/commands/handlers/auth.login.handler.ts)（关键符号：AuthLoginHandler.execute、AuthLoginHandler.getLoginTenantId）、[packages/server/src/auth/auth.service.ts](file://packages/server/src/auth/auth.service.ts)（关键符号：AuthService.refreshTokens、AuthService.updateRefreshToken）

## 注册链

- `POST /api/auth/signup`（`@Public`）：`deploymentTarget === 'customer-onprem'` 时直接抛 `ForbiddenException`，否则执行 `AuthTrialCommand`；`AuthRegisterTrialHandler` 在默认租户下复用/重建用户，创建组织后调用 `AuthService.signup`。
- `AuthService.signup` 生成 `nanoid()` 邮箱验证 token，`createRegisteredUser` 时写入 `emailVerification.validUntil = now + 2 天`，再发 `sendVerifyEmailMail`。
- `POST /api/auth/register`（需登录）：`AuthRegisterCommand` → `AuthRegisterHandler.execute`；若目标是 `SUPER_ADMIN` 角色则强制要求 `createdById` 且创建者本身是 SUPER_ADMIN，否则 400/401。
- `AuthService.register` 用 `createdById` 的租户覆盖输入租户，调 `createRegisteredUser` 后按 `organizationId ?? 默认组织` 发欢迎邮件。
- `createRegisteredUser` 的事务要点：`lockTenantRegistrationScope`（对 `Tenant` 行加 `pessimistic_write` 锁）→ 邮箱/用户名重复检测（`core.User.Error.AccountAlreadyExists` i18n）→ 落库 → 重新 hydrate（`role/tenant`）→ `ensureMembershipInTransaction` → `referralService.bindRegistration`。

## 密码重置链

1. `POST /api/auth/request-password`（`@Public`，`ResetPasswordRequestDTO`）→ `AuthService.requestResetPassword(email, languageCode, origin)`。
2. `fetchUsers(email)` 按小写邮箱取全部租户用户；为每个用户 `createToken(user)` 生成 JWT（用 `JWT_SECRET` 签），执行 `PasswordResetCreateCommand` 落 `password_reset`，再用 `generateResetLink(clientBaseUrl + '/auth/reset-password', token, email, tenantId)` 拼链接发信。
3. 单用户场景走 `AuthService.requestPassword` 变体（额外带 `organizationId` 发信）；`resetPassword` 独立在 `POST /api/auth/reset-password`（`@Public`，`ChangePasswordRequestDTO`）。
4. `AuthService.resetPassword`：`PasswordResetGetCommand` 查最新记录 → `record.expired` 为真抛 `BadRequestException('Password Reset Failed (code: 1).')` → `verify(token, JWT_SECRET)` 取 `id/tenantId`（未做强过期校验）→ `changePassword` 后顺带 `emailVerified = true`。
5. 过期语义来自实体：`password_reset` 继承 `BaseEntity`（**无 tenantId**），`@AfterLoad` 计算 `expired = now - createdAt > 10 分钟`；字段为 `token`（历史上拼写应为 `oken`，现名已修正）。

## 外部身份绑定链

- `AccountBindingService`：`bindUser` 在事务中处理 4 种分支（同 user 复用 / 他人占用但可回收 / 本 user 换 subject / 新建），随后调用 `syncLegacyUserIdentityForProvider`（仅 `lark`）同步 `User.thirdPartyId`；`unbindUser` 反向清理 `thirdPartyId`。
- 回收判定：`canReclaimLarkIdentity` 允许回收“无 hash 的 ghost user”或 `UserType.COMMUNICATION` 占用的 lark 身份；`isGhostUser` 以 `hash` 是否为空判定。
- `AuthService.resolveOrBindVerifiedEmail`：事务内先按 `(tenantId, provider, subjectId)` 找 binding；未命中则锁租户、按“同租户 + 邮箱（不区分大小写）”匹配用户（命中 >1 抛 `ConflictException`），把 `emailVerified` 置真并 `createStrictVerifiedIdentityBinding`。
- `AuthService.registerVerifiedExternalIdentity`：校验密码长度/一致性 → 事务内查/建用户（`UserType.USER` + TRIAL 角色 + `emailVerified: true`）→ 自动建组织 → `ensureMembershipInTransaction` → `referralService.bindRegistration` → 严格绑定外部身份；事务外发出 `OrganizationCreatedEvent` 并 `welcomeUser`。
- 唯一约束 `23505` 被 `rethrowVerifiedIdentityConflict` 统一翻译成 `ConflictException`（并发下的兜底语义）。

## OIDC / SSO 链

- **发现**：`GET /api/auth/sso/providers`（`@Public`）→ `AuthSsoDiscoveryService.discover`：先取匿名租户解析结果（`ANONYMOUS_TENANT_RESOLUTION_REQUEST_KEY` 或 `AnonymousTenantResolverService.resolve`），再用 `resolveRequestBaseUrl(request)`（尊重 `x-forwarded-proto`）逐条 `strategy.describe(...)`，按 `order` + `displayName` 排序。
- **挑战存储**：`PendingSsoBindingChallengeService` 用 Redis，key 前缀 `auth:sso:bind:challenge:`，TTL 600 秒；`create`（公共绑定）、`createVerifiedEmailSignup`（校验 `returnTo` 必须是同源路径）、`get`、`consume`（要求 Redis 支持 `getDel`，否则 500）。
- **完成绑定**：`AuthSsoBindingService.getChallenge` / `getCurrentUserChallenge`（后者校验当前登录用户与 `challenge.tenantId` 一致）→ `completeBinding`（用户名/密码 `bcrypt.compare` 后 `bindUserToChallenge` → `issueTokensForUser` → 删除 challenge）→ 返回 `location`（`/sign-in/success?jwt=...&refreshToken=...&userId=...&returnTo=`）。
- **注册并绑定**：`registerAndBind` 分两条路：`flow === 'verified_email_signup'` 走 `registerVerifiedEmailIdentity`（校验提交邮箱等于验证邮箱 → `registerVerifiedExternalIdentity` → `consume` 校验 provider/subject/tenant 一致 → 发令牌）；否则走 `AuthService.register` 新建用户再绑定。
- 冲突翻译：绑定冲突按错误文本匹配（`already bound to another user` / `already occupied by another user`）转成面向用户的 `ConflictException`。

章节来源：[packages/server/src/auth/sso/auth-sso-binding.service.ts](file://packages/server/src/auth/sso/auth-sso-binding.service.ts)（关键符号：AuthSsoBindingService.completeBinding、AuthSsoBindingService.registerVerifiedEmailIdentity、AuthSsoBindingService.bindUserToChallenge）、[packages/server/src/auth/sso/auth-sso-discovery.service.ts](file://packages/server/src/auth/sso/auth-sso-discovery.service.ts)（关键符号：AuthSsoDiscoveryService.discover）

## 热点路径

1. **每个已认证请求**：`JwtStrategy.validate` 都要查一次 `UserService.getIfExists/getIfExistsThirdParty` 并把 `payload.permissions` 展开成 `rolePermissions` 数组（覆盖数据库中的 role 关系）——权限变更在 token 有效期内**不会即时生效**，且这是每请求的数据库查询。
2. **API key 请求**：`ApiKeyStrategy.authenticate` → `UseApiKeyQuery`（按 `token` 精确查 + `update(lastUsedAt)` + 关联 `createdBy/user`）→ `ApiKeyService.resolvePrincipal`（必要时再查 `user` 或 `integration`，`client` 类型会 `ensureCommunicationUser`）。即每请求至少 2 次写/读。
3. **client secret 请求**：`SecretTokenStrategy.validateToken` 优先按 `sha256:` digest 查（兼容明文），`API_KEY` 类型还会查一次 api key 并刷新其 `lastUsedAt`；`ENTERPRISE_XPERT` 额外执行 `assertEnterpriseXpertScope` 的 PostgreSQL `jsonb_extract_path_text` 查询（发布状态 + `app.channels.<platform>.integrationId` 匹配）。
4. **头部改写**：`applyRequestedOrganizationScopeHeaders` 会用持久化的 `requestedOrganizationId` 覆写 `organization-id` 并把 `x-scope-level` 设为 ORGANIZATION；`USER_CONVERSATION` 路径会 `delete req.headers['x-principal-user-id']` 并强制 `tenant-id`。
5. **SSO 绑定挑战**：`consume` 走 Redis 原子 `getDel`，避免同一 ticket 被并发消费两次。

## 技术债

1. **digest 与明文并存**：`findBySecret` 同时查 `sha256:<digest>` 与明文，历史明文密钥在其生命周期内仍可被拖库直接复用；迁移完成前无法强制“只存 digest”。
2. **无黑名单 / 无 token 版本号**：JWT 无 `jti` 撤销表（仅 actor token 带随机 `jwtid`），登出没有服务端端点，无法单点失效已签发的 access token。
3. **`validUntil` 语义不统一**：`api_key.validUntil` 为空表示**永不过期**（`@AfterLoad` 只在有值时判过期）；`secret_token` 则相反，`SecretTokenStrategy.validateToken` 遇到空 `validUntil` 直接判 `Token expired`。运维必须知道这个差异。
4. **`x-principal-user-id` 缺少开关/白名单**：任意合法 api key 都能在同租户内切换到其他业务用户；`thirdPartyId` 也还没有租户内唯一约束（并发 `ensureCommunicationUser` 可能产生重复技术用户）。
5. **`USER_XPERT` 委托会话残留**：principal 只恢复 audience，资源读取仍需复核当前用户授权，否则从 UserGroup 移出的用户可继续用旧会话访问。
6. **策略代码与启用状态不一致**：`keycloak`/`microsoft`/`dingtalk` 的策略与 guard 仍在仓库（`dingtalk.strategy.ts` 整体被注释），但 `internal.ts` 不注册；容易误判“已支持”。
7. **遗留回调拼接不一致**：社交策略默认回调统一形如 `${baseUrl}/api/auth/<provider>/callback`，但 `Auth0Strategy` 写死 `${baseUrl}/auth/auth0/callback`（缺 `api` 段），`FacebookStrategy` 默认回落到 `${baseUrl}/api/auth/google/callback`（复制粘贴遗留）。
8. **密码重置链条不透明**：多处 `catch` 里 `console.log(error)` 后统一抛通用错误码（`code: 1/2/3`），排障依赖人工复现；`password_reset` 无 `tenantId`，多租户同名邮箱只靠 `createdAt DESC + token` 区分。
9. **SSO 冲突靠字符串匹配**：`AuthSsoBindingService.bindUserToChallenge` 依赖错误消息文本判断冲突，消息一改就失效，应改为错误码/类型判定。

## 设计维度分析

**维度一：身份恢复 vs 资源授权（信任边界的切割）**

- 实现上刻意把“能证明你是谁”和“你能看到什么”分离：strategy 产出 `IApiPrincipal.resourceScope`（`{kind:'assistant'|'workspace'}`、或 `clientSecretBindingType = USER_CONVERSATION` + `entityId`），契约注释明确写了“这不是权限授予，租户/组织/成员/操作检查仍然适用”。
- 代价是调用方必须记得二次校验，因此 `docs/zh-Hans/guides/permission.mdx` 把 `USER_XPERT` 委托会话单独列出复核要求；优点是凭据轮换/绑定变更不会隐式放宽任何业务资源。

**维度二：凭据形态演进与向后兼容**

- 演进方向是“只存不可逆表示”：`SecretTokenService.createHashed` 写 `sha256:<hex>`，读取侧同时兼容明文；`findBySecret` 用 `startsWith('sha256:')` 拒绝把库内 digest 当 bearer。
- 这类兼容策略的收益是零停机迁移，成本是“旧数据仍是弱形态”，并且必须在运维上明确“何时可以清掉明文分支”。

**维度三：装配收敛（单例复用与循环依赖）**

- `SocialAuthModule.registerAsync({ useExisting: AuthService })` 让 `SocialAuthService` 令牌指向 `AuthService` 实例，避免同进程出现两套认证逻辑与两份状态；`AuthService extends SocialAuthService` 让抽象在 `packages/auth`、实现在 `packages/server`，因此必须用 `forwardRef` 打破模块循环。
- 代价是模块图更难读：`AuthModule` 同时承担“被注册到 `/auth` 前缀”“注册社交子模块”“暴露 AuthService”三件事，改动时需同时考虑三处。

## 结论

- 所有入站凭据最终都收敛为两种对象：交互用户 `User`（jwt/refresh/ws-jwt/社交）与 `IApiPrincipal`（api-key/client-secret），这种“两出口”设计让下游 context（`RequestContext.currentUser/currentApiPrincipal`）实现简单，但也意味着**任何** audience 语义都必须在 principal 构造处一次说清。
- 最值得优先偿还的债是“无撤销能力”（登出端点缺失 + JWT 无版本号）与“`validUntil` 语义分叉”；二者都是线上事故的直接来源。
- 实现层最大的隐性成本在热点路径：JWT 每请求查库、API key 每请求写 `lastUsedAt`、ENTERPRISE_XPERT 每请求跑 JSONB 查询；若 QPS 上升，应优先在 `ApiKeyStrategy`/`SecretTokenStrategy` 上做缓存与写合并，而不是改动业务授权逻辑。
