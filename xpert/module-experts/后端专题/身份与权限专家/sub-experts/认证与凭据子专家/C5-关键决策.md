# C5 · 关键决策（认证与凭据子专家）

## D1 · 用「凭据类型 × 显式绑定类型」表达授权语义

- **分类**：架构设计
- **动机**：凭据创建者信息无法区分「API key 授予」「被委托的用户会话」「公开助手会话」，若按创建者推断会让不同强度的凭据获得同一套解释。
- **决策**：入站凭据统一收敛为两种主体（交互用户、`IApiPrincipal`），并用显式持久化的绑定类型（`API_KEY` / `USER_XPERT` / `PUBLIC_XPERT` / `ENTERPRISE_XPERT` / `USER_CONVERSATION`）决定 `entityId` 的解释方式与 audience；不按创建者字段反推。
- **背景约束**：同一张凭据表被多种业务场景复用（API 调用、被委托会话、公开助手、企业内嵌、共享会话），且都需要短期有效。
- **被否决方案**：按 `createdById` 推断授权语义；为每类场景各建一张凭据表。
- **重新评估触发条件**：出现无法用现有五种绑定类型表达的授权形态，或同一 `entityId` 需要承载多种解释。
- **关联代码**：`SecretTokenBindingType`、`SecretTokenStrategy.authenticate`、`buildApiKeyPrincipal`。
- **证据来源**：[secret-token.model.ts](file://packages/contracts/src/secret-token.model.ts)（「createdById alone does not distinguish an API-key grant, a delegated user session, or a public assistant session」）。

## D2 · 资源 audience 用 `resourceScope` 表达，并弃用 key 上的 type/entityId 做业务判定

- **分类**：接口契约
- **动机**：认证是唯一能一次性说清「这条凭据代表哪个资源」的位置，下游若各自回读 key 字段会产生不一致的授权解释。
- **决策**：认证阶段把 key 绑定归一化为 `resourceScope`（assistant / workspace / conversation）；业务侧只消费该值，`apiKey.type`/`entityId` 仅作为技术身份判别保留。
- **背景约束**：历史 key 未补充绑定信息，需要兼容兜底；同时不允许用请求参数放宽 audience。
- **被否决方案**：在业务代码中直接读取 `apiKey.type`/`entityId` 推导可访问资源；让请求参数参与 audience 计算。
- **重新评估触发条件**：`resourceScope` 无法覆盖新的资源粒度，或契约注释声明的知识库向后兼容解析长期未落地而与实际产出持续不一致。
- **关联代码**：`ApiPrincipalResourceScope`、`resourceScopeFromApiKey`、`IApiKey.type`、`IApiKey.entityId`。
- **证据来源**：[api-key.model.ts](file://packages/contracts/src/api-key.model.ts)（`resourceScope` 不是权限授予、只由显式持久化绑定产生、`type`/`entityId` 已标记废弃）、[PLAN_api_principal_identity.md](file://docs/plans/PLAN_api_principal_identity.md)。

## D3 · 出站委托凭据做成无状态、单向、短时的 actor token

- **分类**：安全合规
- **决策**：出站委托使用独立载荷形态的签名令牌（`typ: actor`、随机标识、被委托用户/租户/组织/角色声明），只提供铸造与可用性判断，**不入库、不提供入站校验策略**，并强制 TTL 上限。
- **动机**：[推测] 让出站委托不引入新的凭据生命周期管理面（无表、无撤销状态、无入站信任面），从而把爆炸半径限制在短时间窗内。
- **背景约束**：无请求上下文的后台任务（如计划任务）仍需代表某个业务用户访问外部受信资源，且外部受信方需要独立验签。
- **被否决方案**：为出站委托复用登录态 JWT；为 actor token 建立持久化表并支持撤销。
- **重新评估触发条件**：出现「必须单点撤销已签发 actor token」或「TTL 上限不足」的明确需求；或存在多个互不信任的外部受众需要差异化授权。
- **关联代码**：`OutboundActorTokenProvider.mint`、`OutboundActorTokenProvider.isAvailable`、`buildAct`。
- **证据来源**：[outbound-actor-token.provider.ts](file://packages/server/src/actor-token/outbound-actor-token.provider.ts)（TTL 默认与上限同值、audience 缺省、无入站策略注册）。

## D4 · 短期凭据只存不可逆表示，但仍兼容历史明文

- **分类**：兼容处理
- **决策**：新签发的 client secret 以摘要形式落库，同时保留对既有明文的读取兼容；查找入口显式拒绝「把库内摘要当 bearer 使用」的输入。
- **动机**：在不制造停机窗口的前提下逐步消除明文密钥的拖库风险。
- **背景约束**：历史上已签发的凭据仍在其有效期内，无法一次性失效；运维需要能统计残余明文规模。
- **被否决方案**：一次性强制摘要化（会让所有存量凭据立即失效）；继续全量存明文。
- **重新评估触发条件**：存量非摘要记录清零后，可移除明文读取分支。
- **关联代码**：`SecretTokenService.createHashed`、`SecretTokenService.findBySecret`、`ISecretToken.token`。
- **证据来源**：[secret-token.model.ts](file://packages/contracts/src/secret-token.model.ts)（「Never send a digest as a bearer secret」）。

## D5 · SSO/social 走双轨：启用清单驱动的社交登录 + 独立 SSO 绑定路由

- **分类**：技术选型
- **决策**：社交登录由注册清单决定启用哪些 provider（策略与控制器成对注册，未列入即无路由）；企业 SSO 的发现、一次性绑定挑战与绑定完成走独立的路由族，并复用同一份账号与绑定服务。
- **动机**：[推测] 社交登录是既有形态（保持向后兼容），而企业 SSO 需要「先登录/后绑定」的中间态与一次性票据，语义差异不足以合并。
- **背景约束**：禁用某 provider 时不能留下半可用路由；绑定流程必须在未登录、已登录、注册中三种状态下都可用。
- **被否决方案**：把所有 provider 统一走一条绑定流程；靠配置文件逐个禁用策略而保留路由。
- **重新评估触发条件**：未启用但仍留在仓库中的 provider 策略被误认为已支持并投入对接；或绑定流程的状态机需要新增分支。
- **关联代码**：`Strategies`、`Controllers`、`AuthSsoDiscoveryService.discover`、`AuthSsoBindingService.completeBinding`、`AuthSsoBindingService.registerAndBind`。
- **证据来源**：[internal.ts](file://packages/auth/src/internal.ts)（Keycloak / Microsoft / Dingtalk 被注释）、[auth-sso.controller.ts](file://packages/server/src/auth/sso/auth-sso.controller.ts)（SSO 路由挂在 `/auth` 之下）。

## D6 · 密码重置保持 10 分钟窗口与「无租户列」的记录形态

- **分类**：接口契约
- **决策**：重置记录按邮箱与 token 定位，过期判定为创建后十分钟；重置成功后顺带把邮箱置为已验证。
- **动机**：[推测] 以固定短窗口降低重置链接被转发的风险，同时避免为重置记录引入租户上下文。
- **背景约束**：同一邮箱可能存在于多个租户，而重置入口是公开端点；窗口与租户字段都未提供配置项。
- **被否决方案**：为重置记录增加租户列并按租户分别过期；把窗口做成可配置项。
- **重新评估触发条件**：出现「多租户同名邮箱无法区分」的线上问题；或需要按租户调整有效期。
- **关联代码**：`PasswordReset.afterLoadEntity`、`AuthService.resetPassword`、`AuthService.requestResetPassword`、`PasswordResetGetCommand`。
- **证据来源**：[password-reset.entity.ts](file://packages/server/src/password-reset/password-reset.entity.ts)。

## D7 · 复用既有技术用户类型承载第三方技术身份

- **分类**：架构设计
- **动机**：技术身份与真人用户共用同表时，审计、上下文恢复与既有权限关系可以零改造复用。
- **决策**：第三方/集成/客户端的技术主体复用现有的通信用户类型与稳定外部标识，不新增独立的主体实体；显式传头才允许代表某个业务用户，且只从请求头读取。
- **背景约束**：历史密钥可能没有稳定绑定信息，需要创建者兜底；外部标识当前没有租户内唯一约束。
- **被否决方案**：新增独立的 API 消费者实体；从请求体/查询参数推断被代表的业务用户。
- **重新评估触发条件**：`x-principal-user-id` 获得显式开关/白名单策略，或外部标识补上租户内唯一约束（两者均已被列为后续建议）。
- **关联代码**：`resolvePrincipal`、`resolveApiKeyPrincipalUser`、`API_PRINCIPAL_USER_ID_HEADER`、`buildApiKeyPrincipal`。
- **证据来源**：[PLAN_api_principal_identity.md](file://docs/plans/PLAN_api_principal_identity.md)（复用通信用户、只从 header 读取业务用户、后续建议两条）。

## 结论

- 决策主线是「把不确定的解释收口到认证边界」：audience 只由持久化绑定产生，头部只能收窄。
- 风险最集中的两条是 D3（无撤销面）与 D6（固定窗口、无租户列）：它们都是有意的取舍，而不是遗漏，因此重新评估应基于可观测事件而非审计偏好。
- 与相邻子专家的分工在 D2 上体现得最明显：本子专家产出 audience，是否放行由角色/权限与组织成员专家决定。
