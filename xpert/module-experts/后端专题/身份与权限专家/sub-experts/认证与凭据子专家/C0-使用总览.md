# C0 · 使用总览（认证与凭据子专家）

**覆盖范围**：`packages/server/src/{auth,account-binding,api-key,secret-token,actor-token,password-reset}/**` 与 `packages/auth/src/**` 中「把一次请求或一次出站调用解析成可信身份」的对外契约。

## 1. 子专家定位与何时找它

本子专家只回答**「你是谁」**：校验凭据、产出主体（交互用户或 `IApiPrincipal`），以及账号身份的生命周期（注册、邮箱验证、密码重置、外部身份绑定、SSO 绑定）。它不回答「你能做什么」。

| 场景 | 归属 |
| --- | --- |
| 校验登录态 / API key / client secret / 出站委托凭据，恢复请求主体 | 本子专家 |
| 注册、邮箱验证、密码重置、SSO 登录与绑定、社交登录回调 | 本子专家 |
| 外部身份（provider + subjectId）与 Xpert 用户的绑定关系维护 | 本子专家 |
| 角色、权限、`@Permissions` 判定，token 内权限与数据库权限的取舍 | 角色与权限子专家 |
| 组织成员增删、组织级授权边界 | 组织与成员子专家 |
| 租户识别、租户生命周期、域名/匿名租户判定 | 租户与域名子专家 |
| 各 SSO/OIDC provider 插件本体 | 插件/集成子专家（本子专家只提供发现、挑战与回调落点） |

## 2. 能力清单

| 能力 | 入口（HTTP 或服务方法） | 一句话 |
| --- | --- | --- |
| 登录 | `POST /api/auth/login`（公开） | 校验邮箱/用户名 + 密码，签发 access token 并轮换 refresh token |
| 刷新登录态 | `GET /api/auth/refresh`（公开 + `jwt-refresh`） | 用 refresh token 换新 access token，并立即轮换旧 refresh |
| 登出 | 无此项（服务端无端点） | 只能依赖 refresh 轮换/过期实现失效 |
| 登录态探活 / 角色探测 | `GET /api/auth/authenticated`（公开）、`GET /api/auth/alive`、`GET /api/auth/role` | 判断当前 token 是否可用、是否命中指定角色 |
| 自助试用注册 | `POST /api/auth/signup`（公开） | 默认租户建号 + 建组织 + 发验证邮件 |
| 受控建号 | `POST /api/auth/register`（需登录） | 在创建者租户下建号，含超级管理员越权防护 |
| 申请密码重置 | `POST /api/auth/request-password`（公开） | 生成重置链接并发信，链接 10 分钟内有效 |
| 执行密码重置 | `POST /api/auth/reset-password`（公开） | 用重置 token 改密，并顺带把邮箱标记为已验证 |
| 邮箱验证 | `GET /api/auth/verify?token=`（公开）、`POST /api/auth/resend-verification`（需登录） | 消费/重发邮箱验证 token（默认 2 天有效） |
| SSO 发现 | `GET /api/auth/sso/providers`（公开） | 列出当前租户可用 SSO provider 及其回调描述 |
| SSO 绑定挑战 | `GET /api/auth/sso/bind/challenge`、`GET /api/auth/sso/bind/current-user/challenge` | 读取一次性绑定票据对应的挑战视图 |
| SSO 完成绑定 | `POST /api/auth/sso/bind/complete`（公开）、`POST /api/auth/sso/bind/current-user/complete` | 用已有账号确认绑定，随后签发登录态 |
| SSO 注册并绑定 | `POST /api/auth/sso/bind/register`（公开） | 新账号注册并绑定外部身份（含已验证邮箱注册流程） |
| 社交登录 | `GET /api/auth/<provider>` 与 `GET /api/auth/<provider>/callback` | OAuth 回调后重定向到前端成功页并携带 token |
| 外部身份绑定查询/解绑 | `GET /api/account-binding/me/:provider`、`DELETE /api/account-binding/me/:provider` | 查看/解除当前用户与某 provider 的绑定 |
| API key 管理 | `/api/api-key/*`（CRUD 统一端点，需登录） | 创建、轮换、吊销长期密钥（默认形态 `sk-x-…`） |
| API key 认证 | `ApiKeyStrategy('api-key')`，凭据取 `x-api-key` 或 `Bearer <token>` | 产出 `IApiPrincipal`，并按 key 绑定归一化资源 audience |
| Secret token / client secret 认证 | `SecretTokenStrategy('client-secret')`，凭据取 `x-client-secret` 或 `Bearer cs-x-…` | 按 5 种绑定类型产出不同 audience 的 `IApiPrincipal` |
| Secret token 签发 | `SecretTokenService.createHashed(...)` | 只存不可逆表示，签发方保留明文 |
| 出站委托凭据 | `OutboundActorTokenProvider.mint(...)` / `isAvailable()` | 为出站调用铸造短时 actor token（无入站校验、无持久化） |
| 密码重置记录 | `PasswordResetCreateCommand` / `PasswordResetGetCommand` | 记录重置请求，`expired` 由 10 分钟窗口派生 |

## 3. 边界（不做的事）

| 不做 | 归属 |
| --- | --- |
| 角色/权限判定、`@Permissions` 语义、token 权限与库内权限的优先级 | 角色与权限子专家 |
| 组织成员关系、组织级数据范围判定 | 组织与成员子专家 |
| 租户生命周期（创建/停用）与租户解析策略 | 租户专家 |
| SSO/OIDC provider 插件实现（策略内部协议细节） | 插件/集成子专家 |

## 4. 已知问题与常见坑

1. **登录失败返回 `200 + null`**
   - 现象与触发：`POST /api/auth/login` 传入错误凭据时接口仍是 200，响应体为 `null`，不返回 401。
   - 正确做法：按响应体判空，不要只依赖状态码；失败率监控不能用 4xx 统计。
   - 契约来源：`AuthController.login`、`AuthLoginHandler.execute`。

2. **`validUntil` 语义在两处相反**
   - 现象与触发：`api_key.validUntil` 为空表示**永不过期**；`secret_token.validUntil` 为空则立即判 `Token expired`。
   - 正确做法：巡检长期密钥时把「空 validUntil」当作风险项；签发 secret token 时必须显式给有效期。
   - 契约来源：`ApiKey.afterLoadEntity`、`SecretTokenStrategy.validateToken`。

3. **没有撤销通道**
   - 现象与触发：服务端没有登出端点，登录态 JWT 没有黑名单/版本号；已签发的 access token 在有效期内无法单点失效。
   - 正确做法：应急处置（账号盗用）走轮换签名密钥或重置密码，并把「影响面」写进 runbook。
   - 契约来源：`AuthService.createToken`、`AuthService.refreshTokens`、`AuthService.resetPassword`。

4. **`x-principal-user-id` 可覆盖同租户业务用户且缺白名单**
   - 现象与触发：任何合法 API key 都能通过该头把请求主体切换为同租户内其他用户；当前无显式开关或白名单策略。
   - 正确做法：面向第三方开放 API key 时按调用方隔离，并把该头视为高风险能力；不要用它做权限推导。
   - 契约来源：`API_PRINCIPAL_USER_ID_HEADER`、`ApiKeyStrategy.authenticate`、`ApiKeyService.resolvePrincipal`。

5. **`password_reset` 无租户列且过期硬编码 10 分钟**
   - 现象与触发：多租户同名邮箱的记录只能靠 token 唯一定位；过期窗口不可配置。
   - 正确做法：依赖 token 定位而不是邮箱；调整窗口必须改代码而非配置。
   - 契约来源：`PasswordReset.afterLoadEntity`、`AuthService.resetPassword`。

6. **部分 provider 策略被注释但代码仍在仓库**
   - 现象与触发：Keycloak / Microsoft / Dingtalk 的策略与配置项仍存在，但未注册，因此**没有可用路由**。
   - 正确做法：以「是否出现在启用清单」判断支持能力，而不是以策略文件存在判断。
   - 契约来源：`Strategies`、`Controllers`（`packages/auth/src/internal.ts`）。

7. **库内 digest 不可当 bearer 使用**
   - 现象与触发：任何以 `sha256:` 开头的输入都会直接被拒（401），即使它与库内记录完全一致。
   - 正确做法：导出/备份中的 digest 不能当作可用凭据；补数据时不要回填 digest 去「恢复」密钥。
   - 契约来源：`SecretTokenService.findBySecret`、`ISecretToken.token`（契约注释）。

8. **「记忆中的路径」多数不存在**
   - 现象与触发：`/api/auth/custom/*`、`/api/sso`、`/api/bosi`、`/api/{provider}/{id}/login` 均不是本子专家的路由；刷新也不是 `refresh-token`。
   - 正确做法：以 `/api/auth/*`（含 `sso/*`）、`/api/account-binding/*`、`/api/api-key/*` 为唯一事实来源。
   - 契约来源：`AuthController`、`AuthSsoController`、`AccountBindingController`。

9. **`resourceScope` 不是权限授予，且并非所有 key 都能得到**
   - 现象与触发：只有绑定为 `assistant`（或 `workspace`）的 key 才产出 `resourceScope`；`integration`/`client` 绑定不产出，且该值越权不得由请求参数放宽。
   - 正确做法：以 `resourceScope` 作为资源 audience 判据，业务授权仍需叠加租户/成员/操作检查；不要回读 `apiKey.type`/`entityId` 做业务判定。
   - 契约来源：`ApiPrincipalResourceScope`、`resourceScopeFromApiKey`、`IApiKey.type`（废弃说明）。

10. **企业内嵌与共享会话凭据默认被拒**
    - 现象与触发：`ENTERPRISE_XPERT` 与 `USER_CONVERSATION` 凭据访问未显式声明的路由时直接 403。
    - 正确做法：需要放行的控制器必须显式声明允许的绑定类型，否则不要用它对接。
    - 契约来源：`ApiKeyOrClientSecretAuthGuard.assertClientSecretBindingAllowed`、`AllowClientSecretBindings`。

11. **两处回调路径与默认值有偏差**
    - 现象与触发：Auth0 默认回调缺少 `api` 段；Facebook 未配置重定向地址时会回落到 Google 的回调。
    - 正确做法：启用这两个 provider 时显式配置回调地址，并与 provider 控制台登记值逐字对齐。
    - 契约来源：`Auth0Strategy.config`、`FacebookStrategy.config`。

12. **刷新接口形态与前端默认拼装不一致**
    - 现象与触发：服务端是 `GET /api/auth/refresh` 且只需 `Authorization: Bearer <refreshToken>`；前端默认配置会拼出 `refresh-token`、`logout` 等不存在的端点。
    - 正确做法：对接方按本契约实现刷新与登出，不要复用前端默认路径模板。
    - 契约来源：`AuthController.refreshToken`、`RefreshTokenStrategy.validate`。

## 6. 结论

- 对外真正暴露的 HTTP 面很小：`/api/auth/*`（含 `sso/*`）、`/api/account-binding/*`、`/api/api-key/*` 与社交 provider 回调；其余凭据是策略/服务级接口。
- 所有入站凭据最终收敛为两个出口：交互用户与 `IApiPrincipal`；两者的差别只在「audience 表达能力」，不在「权限」。
- 对接方最容易踩的三类坑：错误语义（200 + null）、路径记忆偏差、以及把 audience 误当权限。
