## 一、子专家定位与何时找它

一句话：本子专家回答「**某个角色能做什么**」——角色行、角色与权限点的绑定、以及接口上的判权声明方式。

找它的情况：

- 要新增 / 调整角色，或判断某个角色为什么删不掉、改不了名。
- 要给某个角色开启或关闭一个权限点，或要为新权限点补默认授予。
- 要在新接口上加权限校验，或排查「接口本该 403 却返回 200」。
- 要判断「撤销权限后多久生效」「换角色后多久生效」。

不找它的情况见第三节边界。

定位依据：[docs/zh-Hans/guides/permission.mdx](file://docs/zh-Hans/guides/permission.mdx)（明写：角色是租户级角色、一个用户只挂一个 `roleId`、后端通过守卫与装饰器落实最终授权）。

## 二、能力清单

| 能力 | 入口（HTTP 或判权注解） | 一句话 |
| --- | --- | --- |
| 角色查询（列表 / 单条 / 分页 / 计数） | `GET /api/roles`、`GET /api/roles/find`、`GET /api/roles/count`、`GET /api/roles/pagination`、`GET /api/roles/:id` | 只过租户一致性守卫，**不校验权限点** |
| 角色创建 | `POST /api/roles` + `@Permissions('CHANGE_ROLES_PERMISSIONS')` + `PermissionGuard` | 新角色一律 `isSystem=false` |
| 角色改名 / 更新 | `PUT /api/roles/:id` + 同上 | 系统角色不可改名、`isSystem` 不可改 |
| 角色删除 | `DELETE /api/roles/:id` + 同上 | 系统角色、被用户或待接受邀请引用的角色不可删 |
| 角色软删 / 恢复 | `DELETE /api/roles/:id/soft`、`PUT /api/roles/:id/recover` + 同上 | 走基类路径，**不经过**角色的系统/引用校验 |
| 默认角色与租户开通建角色 | 非 HTTP：租户开通与邀请接受流程编排；种子流程 | 每个租户按 `RolesEnum` 建全套角色行 |
| 权限点查询 | `GET /api/role-permissions`（类级要求 `CHANGE_ROLES_PERMISSIONS`） | 按 `findInput` 分页查询权限开关 |
| 权限点开启 / 关闭 | `PUT /api/role-permissions/:id`（body 通常为 `{ enabled }`） | `SUPER_ADMIN` 的权限行不可改 |
| 权限点新增 / 删除 | `POST /api/role-permissions`、`DELETE /api/role-permissions/:id` | `SUPER_ADMIN` 的权限行不可删 |
| 默认权限矩阵增量同步 | `POST /api/role-permissions/sync-defaults` | 按预置矩阵补齐缺失权限点，返回统计 |
| 启动期权限点清理与改名 | 非 HTTP：应用启动钩子 | 删除退役权限点、重命名历史权限点 |
| 权限点判定（注解式） | `@Permissions('XXX')` + `PermissionGuard` | 角色是否拥有权限点，结果缓存 5 分钟 |
| 角色白名单判定 | `@Roles(RolesEnum.X)` + `RoleGuard` | 纯角色名白名单，不查权限点 |
| 公开路由 | `@Public()` | 仅跳过鉴权守卫，**不跳过判权** |
| 租户一致性 | `TenantPermissionGuard` / `TenantBaseGuard` | 请求租户与当前用户租户必须一致 |
| 组织级判权 | `OrganizationPermissionGuard` | 存在但当前未接线，勿依赖 |
| 服务层 / CQRS 主动判权 | `RolePermissionService.checkRolePermission(...)`、`CheckRolePermissionCommand` | 非 HTTP 的判权查询入口 |
| CASL 策略层 | `core/casl/` | **未接线，勿依赖** |

## 三、边界

| 不负责 | 交接对象 |
| --- | --- |
| 凭据签发与解析（JWT / API Key / Client Secret 的生成、校验、主体映射），401 类问题 | 认证与凭据子专家 |
| 用户、员工、组织、邀请归属关系的维护，以及用户能切换到哪些组织 | 组织与成员子专家 |
| 功能开关与套餐能力（Feature 层） | 功能开关方向；权限通过不等于入口可见 |
| 插件声明式能力（service permission 等） | 插件方向 |

判定口径：改动若改变「某个角色可见/可操作的接口集合」属本范围；若改变「请求代表谁」或「用户归属哪个组织」则不属于。

## 四、已知问题与常见坑

| # | 现象 | 触发条件 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 以为存在 ABAC / 资源级策略层 | 看到 `core/casl/` 目录与 `@casl/ability` 依赖 | **CASL 未接线**：后端策略工厂无任何调用方、模块无任何导入；前端另有一套独立的 CASL 用法，与后端无关。判权只由 Guard 链承担，勿依赖 `Ability` / `AppAbility` |
| 2 | 新接口没写任何权限校验却返回 200 | 只写了 `@Permissions(...)` 却没挂 `PermissionGuard`；或两者都没写 | **Guard 元数据为空即放行（fail-open）**：`PermissionGuard`、`RoleGuard` 在元数据为空时直接放行，`OrganizationPermissionGuard` 无权限元数据时也放行。逐 controller 注解是唯一护栏，漏注解 ≈ 公开接口 |
| 3 | 撤销权限、换角色后接口仍能访问 | 权限变更后 5 分钟内重复请求同一端点 | **权限判定结果缓存 5 分钟**，且「不允许」结果同样被缓存；仓内没有权限缓存的主动失效调用点。需要即时生效只能等 TTL 或由运维清缓存 |
| 4 | 以为 `TenantPermissionGuard` 会校验权限点 | 读到它读取 `permissions` 元数据 | 该守卫内的**租户权限查询整段被注释**，读到的权限仅用于日志；实际等价于「`TenantBaseGuard` + 超管环境开关旁路」。它只保证租户一致，不代表权限校验 |
| 5 | 以为存在组织级权限点判定 | 使用 `OrganizationPermissionGuard` | 它用 `employee.organization[权限点]` 的旧列判权，与权限点体系并行；且仓内唯一引用处已被注释，当前实际未接线 |
| 6 | `@Public()` 后仍被 403 | 在带 `@Permissions` 的方法上加 `@Public()`，且请求缺用户/租户/角色上下文 | **`@Public()` 只被 `AuthGuard` / `WsAuthGuard` 读取**（跳过鉴权），`PermissionGuard` / `RoleGuard` / `TenantPermissionGuard` / `OrganizationPermissionGuard` 都不读它。公开且需判权时要显式设计 |
| 7 | 把 `checkRolePermission` 第 4 个参数当成 `enabled` | 按参数名直觉传参 | 真实第 4 参是 `includeRole`（默认 `false`）：`true` 时把查询限定到该 `roleId`；`false` 时**不限定角色**，只要该租户下任意角色启用了该权限点即返回 `true`。`enabled = true` 是硬编码条件 |
| 8 | 传多个权限点却被「只有一个」放行 | `@Permissions(A, B)` 或 `checkRolePermission(..., [A, B])` | 多权限点是**或**语义（命中任一即通过），不是「必须全部拥有」。若需全部拥有，需拆成多次判定 |
| 9 | 任意租户成员能读到角色清单 | 直接 `GET /api/roles` / `GET /api/roles/find` | 角色读接口不校验权限点，只过租户守卫；若需限制读取，要自行补判权注解 |
| 10 | 软删「系统角色」成功 | 调用 `DELETE /api/roles/:id/soft` | 软删/恢复走基类路径，绕过角色的系统角色与引用校验；需要强约束时应避免暴露该入口或在前置检查中介入 |
| 11 | 按文档写权限点 / 预置角色对不上 | 参考设计文档列出的角色清单 | 文档中的角色清单（含已不存在的角色）已过期；真实角色枚举只有 5 个。且「角色枚举 / 默认权限矩阵 / 是否系统角色」三处口径不一致，`isSystem` 也并非所有创建路径都会置位 |
| 12 | 请求被 403 但用户权限看着没问题 | 未携带 `Tenant-Id` 头，也未在 query/body 中等价提供 | 租户守卫要求显式提供租户标识：读删除类请求看 `Tenant-Id` 头或 query（含 `data.findInput.tenantId`），写请求看 `body.tenantId` 或 `body.tenant.id`；都缺失即拒绝 |

## 五、结论

本子专家的可依赖面是：两张表（角色行、角色-权限点行）+ 注解式 Guard 链 + 5 分钟结果缓存 + 一个增量同步接口。使用时的两条铁律：**每个受保护端点必须显式挂判权守卫并写元数据**（否则放行），**权限变更的生效延迟由 5 分钟缓存决定**。CASL、组织级守卫、以及名字里带 permission 的租户守卫都不构成可依赖的额外保障。
