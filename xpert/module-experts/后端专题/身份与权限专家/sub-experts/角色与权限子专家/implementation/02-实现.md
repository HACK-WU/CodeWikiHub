## 一、权限判定链

1. 装饰器 `@Permissions(...)` 以 `SetMetadata(PERMISSIONS_METADATA, permissions)` 写入元数据（键值 `'permissions'`，常量来自 `@xpert-ai/server-common`）。
2. `PermissionGuard.canActivate` 用 `getAllAndOverride(PERMISSIONS_METADATA, [handler, class])` 取权限并 `removeDuplicates`；`isEmpty(permissions)` 时**直接 `return true`**。
3. 上下文取自 `RequestContext`：`currentUser()`（即 `request.user`）、`currentTenantId()`（`user.tenantId`）、`currentRoleId()`（`user.roleId`）；任一为空则 `logger.warn` 并 `return false`。
4. 缓存键：`userPermissions:${tenantId}_${roleId}_${permissions.join('_')}`；`cacheManager.get` 返回 `null` 才回源，回源后 `cacheManager.set(key, value, 5 * 60 * 1000)`。注意判断条件是 `fromCache == null`，因此 `false` 会被负缓存。
5. 回源走 CQRS：`CommandBus.execute(new CheckRolePermissionCommand(tenantId, roleId, permissions, true))`（第 4 参数 `includeRole = true`）。命令与 handler 位于 `role-permission/commands/` 与 `role-permission/commands/handlers/`，handler 仅转发给 `RolePermissionService.checkRolePermission`。
6. 查询语义：`createQueryBuilder('rp')` → `rp.tenantId = :tenantId` → 若 `includeRole` 追加 `rp.roleId = :roleId` → `rp.permission IN (:...permissions)` → `rp.enabled = true` → `getCount() > 0`。
7. 返回 `false` 时 Nest 抛 `ForbiddenException`（403），日志记录 userId、角色、租户与检查的权限列表。

章节来源：[packages/server/src/shared/guards/permission.guard.ts](file://packages/server/src/shared/guards/permission.guard.ts)（关键符号：PermissionGuard.canActivate）

## 二、角色 CRUD 与种子

### 2.1 RoleService 的不变量

`RoleService extends TenantAwareCrudService<Role>`，注入 `Role`/`User`/`Invite` 三个仓库；`currentTenantId()` 在无租户上下文时抛 `BadRequestException('Tenant context is required for role access.')`。`create` 强制写入 `isSystem: false`；`update` 拒绝重命名系统角色（`System roles cannot be renamed.`）与改写 `isSystem`（`System role flags cannot be modified.`）；`delete` 先按当前租户定位角色（找不到抛 `The requested role was not found in the current tenant.`），再拒绝系统角色、拒绝仍有用户绑定的角色（`Cannot delete a role that is assigned to users.`）、拒绝仍被待接受邀请引用的角色（`Cannot delete a role that is referenced by pending invites.`）。基类 `TenantAwareCrudService.findOneByWhereOptions` 会按当前用户附加租户过滤，是删除/改名前定位的统一入口。

章节来源：[packages/server/src/role/role.service.ts](file://packages/server/src/role/role.service.ts)（关键符号：RoleService.findRoleForMutation）

### 2.2 种子与默认矩阵

`role.seed.ts` 的 `createRoles` 对每个租户 × `Object.values(RolesEnum)` 建行，并用 `defaultRoles.includes(name)` 置 `isSystem`；`default-role.ts` 的 `defaultRoles = DEFAULT_SYSTEM_ROLES`（`SUPER_ADMIN`、`ADMIN`、`TRIAL`、`AI_BUILDER`、`VIEWER`）。`role-permission.seed.ts` 的 `createRolePermissions` 依 `DEFAULT_ROLE_PERMISSIONS` 逐租户建 `role_permission` 行（`enabled = true`），并在 DEMO 模式过滤 `ACCESS_DELETE_ACCOUNT`/`ACCESS_DELETE_ALL_DATA`；`cleanUpRolePermissions` 反向清理。两者由 `core/seeds/seed-data.service.ts` 调用。

章节来源：[packages/server/src/role-permission/role-permission.seed.ts](file://packages/server/src/role-permission/role-permission.seed.ts)（关键符号：createRolePermissions）

### 2.3 onboarding 中的角色

`TenantService.onboardTenant` 第 2 步 `CommandBus.execute(new TenantRoleBulkCreateCommand([tenant]))` → `TenantRoleBulkCreateHandler` 先 `roleService.createBulk(tenants)`（为每个租户建全部 `RolesEnum` 角色行，**不设置 `isSystem`**，与种子不同），再 `CommandBus.execute(new TenantRolePermissionBulkCreateCommand(tenants))` → `TenantRolePermissionBulkCreateHandler` 调 `rolePermissionService.updateRolesAndPermissions(tenants)`；第 4/5 步回查 `SUPER_ADMIN` 角色并把 `tenant`+`role` 绑到新建用户。邀请接受流程 `invite.accept-organization-contact.handler.ts` 也复用同一条 `TenantRoleBulkCreateCommand`。

章节来源：[packages/server/src/tenant/tenant.service.ts](file://packages/server/src/tenant/tenant.service.ts)（关键符号：TenantService.onboardTenant）

## 三、权限点同步与迁移

| 方法 | 用途 | 触发时机 | 关键细节 |
| --- | --- | --- | --- |
| `updateRolesAndPermissions(tenants)` | 为新建租户批量落默认权限 | onboarding / 邀请接受流程（经 `TenantRolePermissionBulkCreateHandler`） | 先 `purgeRetiredAnalyticsPermissions`；DEMO 模式跳过两个高危权限；`save` 批量写入 |
| `syncDefaultRolePermissions()` | 当前租户**增量**对齐默认矩阵 | `POST /api/role-permissions/sync-defaults`（前端 `RolePermissionsService.syncDefaults`） | 只插缺失权限；对 `SUPER_ADMIN` 额外把已存在但 `enabled=false` 的默认权限回补为 true；返回 `{tenantId, inserted, enabled, roles[]}` 统计 |
| `purgeRetiredAnalyticsPermissions(tenantIds)` | 清理退役权限点 | 私有方法，被上面两者调用 | 删除 `RETIRED_ANALYTICS_PERMISSION_CODES`（`MODELS_*`、`STORIES_*`、`INDICATOR_*`、`DATA_FACTORY_*`、`SUBSCRIPTION_*`、`CERTIFICATION_EDIT`、`NOTIFICATION_DESTINATION_*`、`BUSINESS_AREA_EDIT`、`PERMISSION_APPROVAL_*`） |
| `onApplicationBootstrap()` | 应用启动期全表清理与重命名 | Nest 生命周期启动钩子 | 无租户过滤地删除退役权限；把 `MEMBERSHIP_PURCHASE` 更新为 `AIPermissionsEnum.MEMBERSHIP_USE` |
| `migratePermissions()` | 只读导出当前租户权限行 | **当前无调用者**（配套的 `migrateImportRecord` 已整段注释） | 返回 `IRolePermissionMigrateInput[]`（含 `sourceId`/`role` 名称） |
| `updateRoles(tenant, role)` | 按单角色写入默认权限 | **当前无调用者** | 依赖 `role.name` 命中 `DEFAULT_ROLE_PERMISSIONS`，否则解构 `undefined` 会抛错 |
| `updatePermission` / `deletePermission` | 单行启用/禁用与删除 | 控制器 `PUT`/`DELETE` 路由 | 行关联 `role.name === SUPER_ADMIN` 时抛 `NotAcceptableException`，并统一被 `catch` 包成 `BadRequestException` |

## 四、Guard 族逐个说明

| Guard | 读取的元数据 | 元数据缺失行为 | 失败结果 | 备注 |
| --- | --- | --- | --- | --- |
| `PermissionGuard` | `PERMISSIONS_METADATA`（handler + class） | `return true`（放行） | `false` → 403 | 上下文缺失时 warn + `false` |
| `RoleGuard` | `ROLES_METADATA`（`'roles'`） | `isEmpty(roles)` → `true` | `false` → 403 | 比对 `RequestContext.hasRoles(roles)` |
| `TenantBaseGuard` | 无元数据 | 不适用 | `false` → 403 | `user.tenantId` 缺失即 false；GET/DELETE 查 header `tenant-id`、query `tenantId`、`query.data.findInput.tenantId`；POST/PUT/PATCH 查 `body.tenantId` 或 `body.tenant.id` |
| `TenantPermissionGuard` | 名义读 `'permissions'`（handler） | 不适用 | 同 `TenantBaseGuard` | 先调 `super.canActivate`；`env.allowSuperAdminRole` 且 `SUPER_ADMIN` 直接放行；**真正的租户权限查询整段被注释**，读到的 `permissions` 只出现在日志里 |
| `OrganizationPermissionGuard` | `'permissions'`（handler） | 无 `permissions` → `true` | `false` → 403 | `SUPER_ADMIN` 旁路；否则按 `employeeId`/`userId` 查 `Employee`（`relations: ['organization']`），用 `employee.organization[p]` 旧列判断 |
| `ApiKeyOrClientSecretAuthGuard` | `ALLOWED_CLIENT_SECRET_BINDINGS_METADATA` | 非 `ENTERPRISE_XPERT`/`USER_CONVERSATION` 绑定不受限 | 抛 `ForbiddenException` | 识别 `x-client-secret` 头或 `Bearer cs-x-`；否则 api-key 失败后回退 `CoreAuthGuard`（jwt/basic） |
| `AuthGuard`（全局） | `'isPublic'`（handler + class） | 无 `isPublic` → 走 passport `jwt`/`basic` | 401 | 在 bootstrap 中 `useGlobalGuards` 注册 |
| `PluginScopeGuard`（全局） | 插件作用域元数据键 | 作用域为系统全局 → 放行 | 抛 `ForbiddenException` | 按租户/组织作用域比对 |
| `ApiKeyAuthGuard` / `CoreAuthGuard` | 不读 `isPublic` | 不适用 | 401 | 前者仅 `api-key`，后者 `jwt`/`basic` |

章节来源：[packages/server/src/shared/guards/tenant-permission.guard.ts](file://packages/server/src/shared/guards/tenant-permission.guard.ts)（关键符号：TenantPermissionGuard.canActivate）

## 五、CASL 现状与未接线证据

`core/casl/` 只有 3 个实现文件：`action.ts` 定义 `Action`（`manage`/`create`/`read`/`update`/`delete`），`casl-ability.factory.ts` 的 `CaslAbilityFactory.createForUser(user)` 中「有 user 即 `can(Action.Manage, 'all')`，否则 `can(Action.Read, 'all')`」，另加 `can(Action.Update, Organization, { createdById: user.id })` 与 `cannot(Action.Delete, Organization, { isActive: true })`（注意 `user` 为 null 分支仍访问 `user.id`），`casl.module.ts` 仅 providers/exports 该工厂。未接线的实测证据：

1. 全仓检索 `createForUser`/`CaslAbilityFactory`，命中仅为定义文件与 `casl.module.ts`，**无任何调用者**。
2. `CaslModule` 未被任何模块 `imports`。
3. 提到 casl 的文件仅 3 个（含 `packages/server/package.json` 的 `@casl/ability` 依赖）。
4. 前端另有**独立**的 CASL 用法：`apps/cloud/src/app/@core/services/app-init-service.ts` 的 `updateAbility(user)` 自行 `new AbilityBuilder(Ability)` 并按角色 `can(AbilityActions.Manage, 'all')`，与后端 `CaslAbilityFactory` 无调用关系。

结论：当前判权完全由 Guard 链承担，CASL 是占位/死代码，容易让人误以为存在 ABAC 策略层。

章节来源：[packages/server/src/core/casl/casl-ability.factory.ts](file://packages/server/src/core/casl/casl-ability.factory.ts)（关键符号：CaslAbilityFactory.createForUser）

## 七、热点路径

- 每个带 `@Permissions` 的请求都执行：反射取元数据 → `cacheManager.get` → 未命中时一次 `role_permission` `getCount()` 加一次 CQRS 调用 → `cacheManager.set`。
- 缓存粒度是「权限组合」而非角色：键里含 `permissions.join('_')`，同一角色的不同端点各占一个键，注解权限越多键空间越大；同一端点不同权限组合之间不共享结果。
- 撤权/换角色后最长 5 分钟内旧结果（含负缓存）仍会命中；代码中不存在权限缓存失效调用点（`cacheManager.del` 仅出现在 `view-extension.cache.service.ts`）。
- `TenantBaseGuard` 每请求解析 header/query/body，GET/DELETE 分支还会对 `query.data` 做 `isJSON` + `JSON.parse`。
- `PermissionGuard` 的 `logger.verbose` 在授予/拒绝路径上都会调用（verbose 关闭时开销可忽略）。

## 九、技术债

1. **CASL 未接线**：有工厂、有模块、有依赖，但零调用者、零 imports，属死代码，误导读者的「策略层」预期。
2. **`TenantPermissionGuard` 的权限查询整段被注释**：名字暗示权限判定，实际等价于 `TenantBaseGuard` + `env.allowSuperAdminRole` 旁路 + 日志，是最容易误读的命名债。
3. **`OrganizationPermissionGuard` 用 `employee.organization[p]` 旧列判权**：与权限点体系并行，两套语义，且依赖 `Employee` 上的历史字段。
4. **撤销权限的 5 分钟窗口**：权限缓存无失效钩子；`syncDefaultRolePermissions`、`updatePermission`、`deletePermission` 之后旧判定仍可能命中。
5. **预置角色定义未收口**：`RolesEnum`（contracts，仅 `SUPER_ADMIN/ADMIN/AI_BUILDER/VIEWER/TRIAL`）、`DEFAULT_SYSTEM_ROLES`、`DEFAULT_ROLE_PERMISSIONS`（5 个角色）、种子 `isSystem` 判定、以及文档 `permission.mdx` §2 列出的 8 个角色，五处口径不一致；`RoleService.createBulk` 建角色时不设 `isSystem`。
6. **fail-open 无护栏**：漏注解即放行，仓内无 lint 规则，只能靠 spec 断言 `PERMISSIONS_METADATA`（server-ai 多个 `*.controller.spec.ts` 已是事实范式）。
7. **测试覆盖不均**：`role-permission/` 有 service 与默认矩阵 spec、`api-key-or-client-secret.guard.spec.ts` 与 `plugin-scope.guard.spec.ts`；而 `role/`、`core/casl/`、`permission.guard.ts`、`role.guard.ts`、`tenant-permission.guard.ts`、`organization-permission.guard.ts` 均无 spec。

## 十、设计维度分析

**维度一：判定位置——注解式 Guard 判定 vs 资源级 ABAC。** 注解式 Guard 的优点是自描述、低开销、可用 spec 断言元数据；代价是判权只到「角色能做什么」，数据级规则（只读自己创建的 Xpert、知识库 `organization`/`public` 可见性等）散落在各业务 service 中，没有统一策略层。CASL 未接线意味着 ABAC 无处落地，若要引入资源级判定，需要同时补一个读 `AppAbility` 的守卫和 `CaslAbilityFactory` 的调用点（当前 `createForUser` 的逻辑也必须先按 `rolePermissions` 重写，否则「有 user 即 manage all」等效于放行）。

**维度二：缓存粒度与一致性——按权限组合 vs 按角色。** 当前键为 `userPermissions:{tenantId}_{roleId}_{permissions}`，命中判定简单但键空间随注解组合膨胀，且同一角色的多个端点不共享结果；TTL 5 分钟是「最终一致」的折中。若调整为按 `(tenantId, roleId)` 缓存权限集合、请求内做集合包含判断，可显著减少键数量并为「权限变更后主动失效」提供单点删除入口（`cache-manager` 无 scan，前缀删除不可行，需要版本号键或单键集合）。

**维度三：fail-open vs fail-closed。** 空元数据放行是可用性优先的设计；对「新增 controller 忘注解」是直接放行风险。改为 fail-closed 需要先给所有开放接口显式声明权限或维护白名单，属于破坏性变更，建议以「lint 规则 + controller spec 断言 + 评审清单」渐进加固。

## 十一、结论

实现完整且可用：角色行与权限行两层数据 + 注解式 Guard 链 + CQRS 判权查询 + 结果缓存，构成一条端到端可验证的判权路径；服务层对系统角色与 `SUPER_ADMIN` 的保护、启动期退役权限清理、默认矩阵增量同步都已具备。主要风险集中在「漏注解即放行」「撤销权限有 5 分钟窗口」「两套并行语义（权限点 vs 组织旧列 vs 未接线的 CASL）」三处；建议优先做元数据断言护栏、缓存失效策略与预置角色口径收口。
