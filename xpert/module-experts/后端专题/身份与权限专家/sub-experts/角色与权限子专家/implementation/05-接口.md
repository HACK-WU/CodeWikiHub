## 一、路径与守卫归属

- 全局前缀为 `api`：bootstrap 中 `app.setGlobalPrefix('api', { exclude: [...] })`。
- `RoleModule` 的 `RouterModule.register([{ path: '/roles', module: RoleModule }])`（带前导斜杠）；`RolePermissionModule` 的 `RouterModule.register([{ path: 'role-permissions', module: RolePermissionModule }])`（**无前导斜杠**）。两种写法在 Nest 拼接路由时都会归一化，实际前缀分别为 `/api/roles` 与 `/api/role-permissions`——这一点由前端调用证实：`RolePermissionsService` 请求 `${API_PREFIX}/role-permissions`、`${API_PREFIX}/role-permissions/${id}`、`${API_PREFIX}/role-permissions/sync-defaults`（`API_PREFIX = '/api'`），`RoleService` 请求 `${API_PREFIX}/roles`、`/roles/find`、`/roles/${id}`。
- 鉴权是**全局**的：bootstrap 中 `app.useGlobalGuards(new AuthGuard(reflector), new PluginScopeGuard(reflector))`，因此两个控制器无需自己声明认证守卫；未标 `@Public()` 的路由一律要求 `Authorization: Bearer <jwt>`、Basic 或 `x-api-key`（`JwtStrategy` 支持从 `x-api-key` 头取 token），否则 401。
- 判权是**控制器级**的：`RolePermissionController` 在类上同时声明 `@UseGuards(TenantPermissionGuard, PermissionGuard)` 与 `@Permissions(PermissionsEnum.CHANGE_ROLES_PERMISSIONS)`（对该控制器所有路由生效）；`RoleController` 类上只声明 `@UseGuards(TenantPermissionGuard)`，仅在 create/update/delete/softRemove/softRecover 上追加 `@UseGuards(PermissionGuard)` + `@Permissions(PermissionsEnum.CHANGE_ROLES_PERMISSIONS)`——**读路由（`GET /find`、`GET /` 及继承来的 GET）不校验权限点**。
- 两个控制器都继承 `CrudController<T>`，因此除自身声明的路由外，还继承了 `GET count`、`GET pagination`、`GET my`、`GET :id`、`POST`、`PUT :id`、`DELETE :id`、`DELETE :id/soft`、`PUT :id/recover` 等路由。

## 二、/api/roles 端点明细

| 方法与路径 | 守卫/注解 | 参数 | 职责 | 主要错误 |
| --- | --- | --- | --- | --- |
| `GET /api/roles` | 类级 `TenantPermissionGuard` | 无 | `RoleService.findAll()` 列出当前租户角色 | 401（未认证）、403（`Tenant-Id` 与 `user.tenantId` 不一致或缺失） |
| `GET /api/roles/find?data={"findInput":{...}}` | `TenantPermissionGuard` | `data`（JSON 字符串，`ParseJsonPipe`） | `RoleService.findOne({ where: findInput })` 查单个角色 | 403、404（`CrudService.findOneByWhereOptions` 未命中抛 `NotFoundException`） |
| `GET /api/roles/count`、`/pagination`、`/my`、`/:id` | 继承自 `CrudController`，仅 `TenantPermissionGuard` | `$where`/`$relations`/`$select`（`ParseJsonPipe`）、`:id`（`UUIDValidationPipe`） | 计数、分页、我的、按 id 查询 | 403、404 |
| `POST /api/roles` | `TenantPermissionGuard` + `PermissionGuard` + `@Permissions(CHANGE_ROLES_PERMISSIONS)` | body：`Partial<Role>`（`name`、`tenantId` 或 `tenant.id`） | 创建角色，服务层强制 `isSystem: false`；HTTP 201 | 403（缺权限点或租户不一致）、400（租户上下文缺失） |
| `PUT /api/roles/:id` | 同上 | `:id` UUID、body `Partial<Role>` | 更新角色；HTTP 202 | 400 `System roles cannot be renamed.`、`System role flags cannot be modified.`、`The requested role was not found in the current tenant.`、403 |
| `DELETE /api/roles/:id` | 同上 | `:id` UUID | 删除角色；HTTP 202 | 400 `System roles cannot be deleted.`、`Cannot delete a role that is assigned to users.`、`Cannot delete a role that is referenced by pending invites.`、403 |
| `DELETE /api/roles/:id/soft` | 同上 | `:id` UUID | 软删除角色；HTTP 202 | 403、404（基类 `softRemove`，**不经过** `RoleService.delete` 的系统角色/引用校验） |
| `PUT /api/roles/:id/recover` | 同上 | `:id` UUID | 恢复软删除角色；HTTP 202 | 403、404 |

实体字段：`Role.name`（`RolesEnum` 字符串、`@Index`）、`Role.isSystem`（默认 false）、`Role.rolePermissions`（1:N，`cascade: true`）、`Role.users`（1:N）。

## 三、/api/role-permissions 端点明细

该类级已带 `@Permissions(PermissionsEnum.CHANGE_ROLES_PERMISSIONS)`，因此下列**所有**路由都要求调用者当前角色拥有该权限点。

| 方法与路径 | 参数 | 职责 | 主要错误 |
| --- | --- | --- | --- |
| `GET /api/role-permissions?data={"findInput":{...}}` | `data`（JSON 字符串，`ParseJsonPipe`） | 按 `findInput` 分页查询权限行 | 401、403 |
| `POST /api/role-permissions` | body：`IRolePermissionCreateInput` | 新增一条权限开关；HTTP 201 | 400（校验）、403 |
| `POST /api/role-permissions/sync-defaults` | body 可空 | 当前租户增量同步默认权限矩阵，返回 `{tenantId, inserted, enabled, roles[]}`；HTTP 202 | 400 `Tenant context is required for role permission sync.`、403 |
| `PUT /api/role-permissions/:id` | `:id` UUID、body `RolePermission`（通常 `{ enabled }`） | 启用/禁用某权限点（`updatePermission`）；HTTP 202 | 400（`Cannot modify Permissions for Super Admin` 被包装为 `BadRequestException`）、403、404 |
| `DELETE /api/role-permissions/:id` | `:id` UUID | 删除权限行（`deletePermission`）；HTTP 202 | 400（`Cannot delete Permissions for Super Admin` 同理包装）、403 |
| `GET /api/role-permissions/count`、`/pagination`、`/my`、`/:id` | 继承自 `CrudController`（`UUIDValidationPipe`/`ParseJsonPipe`） | 计数、分页、我的、按 id 查询 | 403、404 |
| `DELETE /api/role-permissions/:id/soft`、`PUT /api/role-permissions/:id/recover` | `:id` UUID | 继承自 `CrudController` 的软删/恢复 | 403、404 |

实体字段：`RolePermission.permission`（`PermissionsEnum` 字符串、`@Index`）、`enabled`（可空，默认 false）、`roleId`（`@Index`，`@ManyToOne` → `Role`，`onDelete: 'CASCADE'`）。

## 四、判权约定

### 4.1 `@Permissions('xxx')` 常见取值

`@Permissions` 只是 `SetMetadata('permissions', [...])`；要真正生效必须同时挂 `PermissionGuard`（类级或方法级），方法级元数据优先于类级。

| 权限点（实测出现处） | 语义 | 典型落点 |
| --- | --- | --- |
| `PermissionsEnum.CHANGE_ROLES_PERMISSIONS` | 管理角色与权限 | role.controller（5 处）、role-permission.controller（类级） |
| `PermissionsEnum.ORG_USERS_VIEW` / `ORG_USERS_EDIT` | 查看/管理租户用户 | user-group.controller |
| `PermissionsEnum.ALL_ORG_VIEW` / `ALL_ORG_EDIT` | 查看/编辑全部组织 | feature-toggle.controller、organization.controller、user.controller |
| `PermissionsEnum.ORG_INVITE_VIEW` / `ORG_INVITE_EDIT` | 邀请查看/发起 | invite.controller、organization-contact.controller |
| `PermissionsEnum.ORG_EMPLOYEES_EDIT` / `ORG_TAGS_EDIT` | 员工、标签编辑 | organization-contact.controller、tag.controller |
| `PermissionsEnum.DATA_SOURCE_VIEW` / `DATA_SOURCE_EDIT` | 数据源能力 | data-source.controller |
| `PermissionsEnum.INTEGRATION_EDIT`、`REFERRAL_VIEW`、`ACCESS_DELETE_ALL_DATA` | 集成、推荐、高危删除 | integration-qr.controller、referral.controller、user.controller |
| `AIPermissionsEnum.*`（如 `COPILOT_EDIT`、`MEMBERSHIP_USE`、`KNOWLEDGEBASE_EDIT`） | AI 侧权限点 | `packages/server-ai` 各控制器（copilot、membership、knowledgebase 等） |

权限组合会被拼进缓存键（`permissions.join('_')`），因此新增组合等于新增缓存条目。

章节来源：[packages/server/src/shared/decorators/permissions.ts](file://packages/server/src/shared/decorators/permissions.ts)（关键符号：Permissions）

### 4.2 `@Roles(RolesEnum.*)` 常见取值

`@Roles` 写 `'roles'` 元数据，只由 `RoleGuard` 读取；`RoleGuard` 不查 `role_permission`，是纯角色白名单（角色名取自 `user.role.name`）。

| 取值 | 语义 | 实测落点 |
| --- | --- | --- |
| `RolesEnum.SUPER_ADMIN` | 租户超级管理员独占 | tenant.controller、tenant-setting.controller、runtime-control.controller、setup-plugins.controller、feature.controller、packages/server-ai 的 plugin-resource / copilot-organization / mcp-publication-management |
| `RolesEnum` 全量取值 | 仅 5 个：`SUPER_ADMIN`、`ADMIN`、`AI_BUILDER`、`VIEWER`、`TRIAL` | contracts 的 `RolesEnum`（文档 `permission.mdx` §2 仍写 8 个角色，属过期描述） |

注意：`TenantPermissionGuard` 内的 `env.allowSuperAdminRole === true && 角色为 SUPER_ADMIN` 会直接放行，与 `@Roles` 白名单是两条独立通道。

章节来源：[packages/server/src/shared/guards/role.guard.ts](file://packages/server/src/shared/guards/role.guard.ts)（关键符号：RoleGuard.canActivate）

### 4.3 `@Public()` 的语义

- 实现：`SetMetadata('isPublic', true)`，只有方法级/类级两处元数据。
- 唯一读取者是 `AuthGuard`（全局守卫）与 `WsAuthGuard`：命中 `isPublic` 时直接 `return true`，不再调用 passport；`ApiKeyAuthGuard`、`CoreAuthGuard` 不读。
- `PermissionGuard`、`RoleGuard`、`TenantPermissionGuard`、`OrganizationPermissionGuard`、`PluginScopeGuard` 均**不读** `isPublic`。因此 `@Public()` 只跳过鉴权，不跳过判权：`@Public()` + 无 `@Permissions` 时 `PermissionGuard` 因元数据为空而放行；`@Public()` + 有 `@Permissions` 时若上下文缺失用户则返回 false（403）。
- 仓内范式：`user.controller` 的 `GET /user/me` 用 `@Public()` + `@UseGuards(ApiKeyOrClientSecretAuthGuard)`，由守卫自行完成认证（对应 spec 断言 `isPublic` 元数据与守卫列表）。

章节来源：[packages/server/src/shared/decorators/public.decorator.ts](file://packages/server/src/shared/decorators/public.decorator.ts)（关键符号：Public）

## 五、新增一个受保护端点的正确做法

1. 定义权限点：在 `packages/contracts` 的 `PermissionsEnum`（或 AI 侧枚举）新增字符串常量，避免直接写裸字符串——服务端查询是 `permission IN (...)` 的字符串比对。
2. 决定是否默认授予：把新权限点加入 `DEFAULT_ROLE_PERMISSIONS` 对应角色的 `defaultEnabledPermissions`；否则预置角色不会自动获得该行，需要靠 `POST /api/role-permissions/sync-defaults` 增量补齐。
3. 注解组合（最小可用）：
   - 权限点方式：`@UseGuards(TenantPermissionGuard, PermissionGuard)` + `@Permissions(PermissionsEnum.XXX)`（可放类级，方法级会覆盖类级）。
   - 角色白名单方式：`@UseGuards(TenantPermissionGuard, RoleGuard)` + `@Roles(RolesEnum.SUPER_ADMIN)`；须知它绕开 `role_permission`，无法被细粒度授予。
   - 若控制器需要非 JWT 凭据（API Key / Client Secret），额外挂 `ApiKeyOrClientSecretAuthGuard`；`ENTERPRISE_XPERT`/`USER_CONVERSATION` 绑定还需 `@AllowClientSecretBindings(...)`，否则 403。
4. 不要用 `@Public()` 代替判权：它只影响全局 `AuthGuard`/`WsAuthGuard`。
5. 补一条断言 spec：`expect(Reflect.getMetadata(PERMISSIONS_METADATA, handler)).toEqual([...])`（server-ai 多个 controller spec 已是仓内范式），这是目前防「漏注解即放行」的唯一自动化护栏。
6. 缓存影响：新权限组合会产生新的 `userPermissions:{tenantId}_{roleId}_{permissions}` 键，首次请求回源一次 DB；调整角色权限后旧缓存最长 5 分钟内继续生效，仓内没有权限缓存失效调用点，需要即时生效时应主动清除缓存（或等待 TTL）。

章节来源：[packages/server/src/shared/guards/permission.guard.ts](file://packages/server/src/shared/guards/permission.guard.ts)（关键符号：PermissionGuard.canActivate）

## 六、结论

`role` 与 `role-permission` 两套接口形态一致：都继承 `CrudController` 的 CRUD 路由，都由 `TenantPermissionGuard` 保证租户一致性，差别在权限面上——`role-permissions` 是类级统一要求 `CHANGE_ROLES_PERMISSIONS`，`roles` 只在写操作上要求该权限点（读操作仅过租户守卫）。路径前缀按 `api` + RouterModule 声明拼接为 `/api/roles` 与 `/api/role-permissions`（后者声明无前导斜杠，前端已按该前缀调用）。新增端点时必须显式挂上判权守卫与元数据，并同步考虑默认权限矩阵与 5 分钟缓存的行为。
