# C0 使用总览（组织与成员子专家）

> 隶属「身份与权限专家」；对外可依赖的行为细节见 [C1-能力契约.md](./C1-能力契约.md)，实现层描述见 `implementation/`。

## 1 子专家定位与何时找它

**定位**：本子专家是「身份 / 组织 / 成员 / 邀请 / 用户组」五件事的写路径负责人，覆盖 `user`、`user-organization`、`user-group`、`organization`、`organization-language`、`organization-contact`、`employee`、`invite` 以及事实上的死模块 `contact` 共九个模块。

**何时找它**：

- 需要读取「当前登录用户」及其可见组织（含按组织裁剪、feature context 组装）。
- 需要新增 / 更新 / 删除用户，修改密码，更新本人资料或首选语言。
- 需要建组织、改组织、删组织，或维护组织语言与外部联系人。
- 需要建立 / 更新 / 删除成员关系（`user_organization`），设置默认组织、默认工作区、入口引导偏好。
- 需要创建、重发、公开校验邀请，或走完三条接受邀请路径（用户 / 员工 / 组织联系人）。
- 需要维护组织内用户组及其成员（含平台托管的智能体访问组）。
- 需要读写员工档案（`employee`）。

## 2 能力清单

| 能力 | 入口（HTTP 或服务方法） | 一句话 |
| --- | --- | --- |
| 当前用户读取 | `GET /api/user/me`；`UserService.findCurrentUser` | 唯一「当前用户」读取入口，按 relations / options 在三个分支中选择装配方式 |
| bootstrap 组织裁剪 | `GET /api/user/me`（`data.limitOrganizations`）；`UserService.findCurrentUser` 的裁剪分支 | 响应里 `user.organizations` 只返回 1 条成员（currentOrganizationId → 默认组织 → id 升序） |
| feature context | `GET /api/user/me`（relations 命中白名单） | 回填租户级与组织级 `featureOrganizations`，结果按用户/租户版本缓存 |
| 用户 CRUD | `/api/user` 的 POST / PUT / GET / DELETE；`UserService.createOne`、`updateProfile` | 建、改、查、软删用户；列表默认排除技术用户 |
| 用户删除护栏 | `DELETE /api/user/:id`；`UserService.deleteWithGuards`、`deleteHardWithGuards` | 禁止删自己、技术用户、最后一个租户管理员；软删前先收敛成员关系 |
| 密码修改 | `POST /api/user/:id/password`；`UserService.resetPassword`、`changePassword` | 本人需校验旧密码；管理路径需 `ALL_ORG_EDIT` 或 `SUPER_ADMIN_EDIT` |
| 组织 CRUD | `/api/organization`；`OrganizationService.create/update/delete/findByPublicLink` | 组织主数据、公开资料链接、删除前置校验与成员收敛 |
| 成员身份 | `POST/PUT/DELETE /api/user-organization`；`UserOrganizationService.ensureMembership`、`update`、`delete` | 成员真相表；创建幂等、默认组织唯一、活跃成员兜底 |
| 默认组织 | `POST /api/user-organization`（`isDefault`）、`PUT /api/user-organization/:id` | 同一租户内至多一条 `isDefault`；删除时自动补位 |
| 默认工作区与引导 | `UserOrganizationService.get/setCurrentUserDefaultWorkspaceId`、`markCurrentUserEntryGuideAutoShown`；`PUT /api/user-organization/me/preferences/entry-guides/:guide/auto-shown` | 成员级偏好，写在同一成员的 `preferences` 上 |
| 用户组 | `/api/user-groups`；`UserGroupService.findAllByOrganizationId`、`updateMembers` | 组织内分组与覆盖式成员维护，全部要求组织范围 |
| 托管组 | 平台侧直写仓储（如 Xpert 市场访问组）；`UserGroupService` 只做剥离 | HTTP 输入无法设置 `managed*`，托管元数据只由平台写入 |
| 员工 | `/api/employee`；`EmployeeService.createBulk`、`findWorkingEmployees`、`search` | 与 `user` 1:1 的档案；专项查询与搜索 |
| 邀请创建与重发 | `POST /api/invite/emails`、`POST /api/invite/resend`；`InviteService.createBulk`、`resendEmail` | 批量建邀请、失效重发（改写同一行刷新 token / 过期时间） |
| 邀请接受（三路径） | `POST /api/invite/user`、`/api/invite/employee`、`/api/invite/contact` | 用户 / 员工 / 组织联系人；均为 `@Public()` |
| 邀请公开校验 | `GET /api/invite/validate`；`InviteService.validateByToken` | JWT 验签 + email 匹配 + status 与过期时间校验 |
| 组织语言 | `/api/organization-languages` | 组织语言配置（仅有租户级守卫，无细粒度权限） |
| 组织联系人 | `/api/organization-contact`；`OrganizationContactService.findByEmployee`、`findAllOrganizationContacts` | 外部联系人及其 `inviteStatus` |
| 遗留 contact | 无对外 HTTP 入口 | `contact/` 未挂载路由，仅为遗留实体 |

## 3 边界（不做这些）

- **不做登录与凭据**：token 签发、SSO / 第三方登录、API key、账号绑定归「认证与凭据子专家」；本子专家只提供注册落库、`changePassword`、`resetPassword`、`verifyEmail` 这类原语。
- **不做角色权限判定**：权限矩阵与 CASL 规则归「角色与权限子专家」；本子专家只读取 `roleId` / `role.name` 做删除与邀请护栏，不定义权限语义。
- **不做租户基础设施**：tenant 解析与配置归「租户专家」，本子专家只在既有 tenant 范围内读写。
- **不做项目 / 工作空间成员**：项目与工作空间协作成员归「项目协作专家」；用户组只作为运行授权输入，最终 `canRun` 判定在 AI 侧。
- **不替代智能体授权**：用户组授权只对已发布智能体生效，不能当作文件 ACL 或智能体入口 ACL 使用。

## 4 已知问题与常见坑

1. **`invite.email` 全局唯一，查重只按租户**。现象：跨租户对同一邮箱发邀请会直接撞数据库唯一约束，而不是返回业务 400。触发条件：被过滤逻辑放行（`createBulk` 只在当前 `tenantId` 内比对有效邀请与已存在用户）。正确做法：邀请前自行确认全局未被占用，或复用同一行（`resendEmail` 的做法）。
2. **员工邀请的接受路径已退化**。现象：文档声称「注册用户 → 建 employee → 置 ACCEPTED」，实现只做注册 + 置 ACCEPTED；`updateEmployeeMemberships` 是空实现，EMPLOYEE 类型邀请也不发信。触发条件：调用 `POST /api/invite/employee`。正确做法：不要依赖该端点产出 `employee`，改用员工创建 / 导入链路。
3. **`invite_organization_contact` 是 M2M，语义未定（源码带 TODO）**。现象：接受联系人邀请时只更新 `invite.organizationContact[0]`，建邀请时也只写单元素数组。触发条件：同一邀请挂多个联系人。正确做法：按「一邀请一联系人」使用，不要依赖顺序之外的关系。
4. **成员不变量禁止绕过 service 直写仓储**。现象：直接改 `user_organization` 仓库会破坏「唯一默认组织」「至少一个活跃成员」「最后一条成员关系不可删」「删除后默认组织补位」,并不会刷新当前用户 feature 缓存版本、也不会发出成员创建 / 删除事件。正确做法：所有成员写操作走 `UserOrganizationService`。
5. **超级管理员不是组织成员**。现象：`POST /api/user-organization` 对超管返回 400（"Super admin users are not organization members."）；查询 / 更新 / 删除命中超管成员时同样 400。正确做法：超管的组织可见性由角色推导（`isActiveMemberOfOrganization` 对超管直接放行），不要为其建成员关系。
6. **托管组元数据在 HTTP 路径被静默剥离**。现象：请求体带 `managedBy` / `managedEntityType` / `managedEntityId` 不报错但不生效。触发条件：`POST/PUT /api/user-groups`。正确做法：托管组只由平台侧直写仓储创建（三列同时非空时受部分唯一索引约束）。
7. **用户组只补 `canRun`**。现象：把用户加入访问组后，其工作空间 `canRead` / `canWrite` / `canManage` 不会提升，未发布智能体也不产生 `canRun`，且不能绕过智能体入口 ACL。正确做法：不要把用户组当成组织权限的替代品。
8. **`organization` 自身没有 `organizationId`**。现象：组织是租户级实体；而 `user_organization` / `invite` / `user_group` / `employee` / `organization_contact` 的 `organizationId` 全部可空，数据库不阻止「无组织」数据产生。正确做法：组织维度过滤必须由调用方显式带上。
9. **删组织有前置条件且会批量收敛成员**。现象：仍有 `INVITED` 邀请或有 user_group 时返回 400；通过校验后会删除该组织全部成员关系并为受影响用户重选默认组织。触发条件：`DELETE /api/organization/:id`。正确做法：先清邀请与用户组，确认影响面后再删。
10. **公开组织资料链接无唯一保证**。现象：`GET /api/organization/profile/...` 是 `@Public()` 且跨租户，而 `profile_link` 没有唯一索引，重复链接时命中不确定。正确做法：把 `profile_link` 当业务侧唯一值维护。
11. **软删用户需要占位展示**。现象：`DELETE /api/user/:id` 只写 `deletedAt`，默认查询会排除该用户，`GET /api/user` 需 `data.withDeleted` 才能列出；历史引用（如推荐关系）会拿到 id 但取不到用户，需要占位（现有做法是返回 `{ deleted: true, name: null, email: null }`）。触发条件：先软删用户，再读引用它的数据。
12. **守卫与路由存在缺口**。现象：`employee` 控制器没有类级守卫与 `@Permissions`（仅 `GET /api/employee/user/:userId` 单加租户守卫），员工 CRUD 只靠全局认证兜底；`contact/` 模块未注册故无任何路由；`PUT /api/invite` 是恒返回 400 的占位路由；`POST /api/invite/resend` 失败时把错误对象当返回值返回，调用方无法用状态码区分成功与失败。正确做法：不要把这些端点纳入权限设计假设，重发失败需按返回值判断。
