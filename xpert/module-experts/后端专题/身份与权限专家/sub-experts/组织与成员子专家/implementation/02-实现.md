## 1 用户读取链

入口是 `GET /user/me`：`UserController.findMe` 读 `RequestContext.currentUserId()`，把 `data.relations` 与 `CurrentUserFindOptions`（`currentOrganizationId`、`limitOrganizations`、`select`）整体交给 `UserService.findCurrentUser`。

`findCurrentUser` 有三个分支，互斥且按顺序判断：

1. **feature context 分支**：请求的 relations 恰好覆盖 `CURRENT_USER_FEATURE_RELATIONS`（tenant/organization 的 featureOrganizations 及其 feature）且全部在允许集合内，且注入了 `FeatureOrganization` 仓储时，走 `findCurrentUserFeatureContext`。
2. **组织裁剪分支**：调用方显式传 `limitOrganizations`，且请求的 organization 相关 relations 只落在 `organizations` / `organizations.organization` 白名单内时，走 `findCurrentUserWithLimitedOrganizations`。
3. **兜底分支**：`findOne`，relations 固定合并 `CURRENT_USER_CORE_RELATIONS`（`employee`、`role`、`role.rolePermissions`、`tenant`）。

**frobenius 裁剪**实际由 `findCurrentUserBootstrapOrganizations` 完成：以 `userId + tenantId + isActive: true`、并要求 `organization.isActive = true`，最多取 1 条成员记录，优先级为"传入的 currentOrganizationId → `isDefault = true` → `id ASC`"，因此响应里 `user.organizations` 永远只有一条。

**feature context 组装**（`findCurrentUserFeatureContext` + `loadCurrentUserFeatureContext`）：先取基础用户，再按 tenant 查 `organizationId IS NULL` 的租户级 feature，按 membership 的 organizationId 集合查组织级 feature，然后回填 `user.tenant.featureOrganizations` 与每个 `membership.organization.featureOrganizations`。结果缓存在 `user:me:feature-context:v1:{tenant}:{user}:{relationsHash}:{version}`，TTL 180 秒，version 由租户级与用户级版本键拼成；任何 membership 写操作都会 `touchCurrentUserFeatureUserCacheVersion` 使缓存失效。

## 2 邀请链

**创建**：`POST /invite/emails` → `InviteService.createBulk`。它先归一化 email，再过滤两类"已占用"地址：同 tenant 下状态为 `INVITED` 且未过期的邀请、同 tenant 已存在的用户；被过滤部分只计入返回值的 `ignored`。邀请角色为 `SUPER_ADMIN` 时，邀请人自身必须是 `SUPER_ADMIN`，否则抛 `UnauthorizedException`。`expireDate` 规则：`InvitationExpirationEnum.NEVER` → `null`，否则用显式周期，缺省取 `organization.inviteExpiryPeriod` 或 `DEFAULT_INVITE_EXPIRY_PERIOD`。每条邀请的 `token = createToken(email)`（JWT 签 email），注册链接为 `clientBaseUrl + /auth/accept-invite?email=…&token=…`。发信只对 `InvitationTypeEnum.USER` 生效，EMPLOYEE 分支整段被注释。

**校验**：`GET /invite/validate` → `validateByToken`：验签 → payload.email 必须与入参 email 一致 → 只接受 `status = INVITED` 且（`expireDate >= now` 或 `expireDate IS NULL`）的记录；任何失败统一抛 `BadRequestException`。

**接受路径 A（`InviteAcceptUserHandler`）**：docstring 写"注册 user → 建 user_organization → invite 置 ACCEPTED"。真实实现只做三件事：按 `input.organization.id` 取组织（含 tenant）→ `AuthService.register({...input, organizationId})` → `inviteService.update(inviteId, { status: ACCEPTED })`。中间的成员关系是 `AuthService.register` 内部在事务里用 `ensureMembershipInTransaction` 建的（`SUPER_ADMIN` 跳过），提交后再由 `completeMembershipCreation` 补发事件、刷缓存版本——**步骤等价，位置不同**。

**接受路径 B（`InviteAcceptEmployeeHandler`）**：docstring 写"注册 user → 为组织建 employee → ACCEPTED"，但实现只 register + 置 ACCEPTED；`employeeService.create(...)`、`updateEmployeeMemberships(...)`、`sendAcceptInvitationEmail(...)` 三段均被注释掉，且 `updateEmployeeMemberships` 本体只剩空函数体。补充证据：`EmployeeService` 没有自定义 `create`（只有 `createBulk`、`findAllActive`、`findWorkingEmployees` 等，`createBulk` 内部用的是基类 `this.create(emp)`）。结论：**文档与实现不一致，该路径实际不再产出 employee**。该 handler 还额外读取 projects/departments/organizationContact 关系并校验 `organization.invitesAllowed`，前者已无消费方。

**接受路径 C（`InviteAcceptOrganizationContactHandler`）**：注释里编号 1–8：新建 tenant → `TenantRoleBulkCreateCommand` → `TenantFeatureOrganizationCreateCommand` → 建 organization →（报表步骤已注释）→ "创建联系人"这一步实际是再次 `organizationService.create({...organization})`，contact 字段被注释 → 查 `SUPER_ADMIN` 角色 → `authService.register` →（第二个编号"8"）读 `invite.organizationContact[0].id`，调 `organizationContactService.update(inviteStatus: ACCEPTED)` 并置 invite 为 ACCEPTED。代码里保留 `TODO Make invite and contact as one to one`，说明当前 M2M 关系的用法是**约定式的**。

## 3 组织成员链

**建组织**：`OrganizationCreateHandler.execute` → `organizationService.create`（补 `show_*` 默认值）→ 再 `create` 一次（历史遗留，原 contact 合并逻辑已注释）→ 导入场景写 import record → 若带 `onboardingSuperAdminUserId` 则 `userOrganizationService.ensureMembership` → 发 `EVENT_ORGANIZATION_CREATED`。

**建成员**：`POST /user-organization` → `UserOrganizationCreateHandler` → `addUserToOrganization`（`SUPER_ADMIN` 直接返回 `[]`，不建成员）→ `ensureMembership`（已存在即返回原记录，幂等）。底座 `create` 先过 `prepareCreateEntity`：用户/组织必填；同一 `userId + organizationId + tenantId` 重复则 400；`isActive` 缺省 true 且**首条成员必须活跃**；`isDefault` 缺省等于"是否首条"，为 true 时调 `ensureUniqueDefault` 把其他成员置为非默认。

**默认组织唯一性维护**：`update` 里 `isDefault === true` 先 `ensureUniqueDefault(exclude self)`；`isActive === false` 先 `ensureActiveMembershipRemains`（删/停到 0 个活跃成员直接 400）。`delete` 时若删掉的是默认成员，或剩余成员已没有默认成员，则 `pickNextDefaultMembership`（优先 `isActive`，否则第一条）补位。

**删组织的成员收敛**：`OrganizationService.delete` 先做两个前置拒绝（存在 `INVITED` 邀请 → 400；存在 user_group → 400），再调 `UserOrganizationService.deleteByOrganizationForOrganizationRemoval`：取该 tenant/organization 全部成员 → 记录其中拥有默认组织的 userId → 按条件批量删除 → 对这批用户在剩余成员中补默认组织 → 逐用户刷新 feature 缓存版本 → 为每条被删成员发 `EVENT_USER_ORGANIZATION_DELETED` → 最后才 `super.delete`。

**成员删除的服务口径**：`user-organization.delete.handler` 调 `userOrganizationService.delete(id, { allowDeletingLastMembership: true })`，即用户级删除不适用"最后一成员"限制，仅组织级 API 适用。

## 4 用户组链

**入口与权限**：`UserGroupController`（`/user-groups`）列表与详情需要 `ORG_USERS_VIEW`，创建/更新/改成员/删除需要 `ORG_USERS_EDIT`；列表支持 `?organizationId`，有则走 `findAllByOrganizationId`，无则走 `findAll`（两者都要求组织上下文）。

**成员增删**：`PUT /user-groups/:id/members` → `updateMembers`：先按 `id + tenantId` 取组（含 members），再解析可访问组织并要求 `group.organizationId` 与之一致（否则 403），随后 `validateMemberIds` 校验——所有 id 必须属于当前 tenant，且必须是该组织的**活跃成员**，否则 400——最后整体覆盖 `group.members`。

**组织范围解析**：`resolveAccessibleOrganizationId` = 无入参时 `RequestContext.requireOrganizationScope()`；有入参时 `assertAccessibleOrganizationId`：组织必须属于当前 tenant（否则 404）；若请求已绑定组织则必须相同（否则 403）；若请求处于 tenant scope 且有 `ALL_ORG_VIEW` / `ALL_ORG_EDIT` 则放行；否则要求当前用户是该组织活跃成员。`findAll/findOne/create/update/delete` 全部先 `requireOrganizationScope()`。

**托管组元数据**：`stripManagedMetadata` 在 create/update 时删除 `managedBy` / `managedEntityType` / `managedEntityId`，保证这三个字段只能由平台侧（如 Xpert 发布时绑定访问组）写入；三者同时非空时受部分唯一索引 `IDX_user_group_managed_entity_unique` 约束。

**授权边界**：用户组只补已发布智能体的工作空间 `canRun`，不提升 `canRead` / `canWrite` / `canManage`；未发布智能体不产生 `canRun`，且该能力不能绕过智能体入口 ACL。

## 5 用户删除护栏

`DELETE /user/:id` → `UserDeleteCommand` → `UserService.deleteWithGuards`，分三段：

1. `ensureDeleteWithGuards`：不能删除自己；`UserType.COMMUNICATION` 技术用户禁止（走用户管理删除）；用户必须有 role；目标角色为 `SUPER_ADMIN` 时要求请求者具备 `SUPER_ADMIN_EDIT`；目标是 `SUPER_ADMIN` 或 `ADMIN` 时，按 tenant 统计**其他**管理员数量，为 0 抛"不能删除最后一个租户管理员"。
2. `deleteUserOrganizations`：逐条 `userOrganizationService.delete(id, { allowDeletingLastMembership: true })`，并逐条发 `EVENT_USER_ORGANIZATION_DELETED`。
3. 事务内：删该用户的 `ExternalIdentityBinding`，再对 `user` 做 `softDelete({ id, tenantId })`，即写 `deletedAt`。

`deleteHardWithGuards` 则只跑第 1 段护栏后直接 `delete(id)` 物理删除，**不先清成员关系**、不发成员事件——两条删除路径在成员收敛上不对称。

成员侧的护栏在 `UserOrganizationDeleteHandler`：删除对象是 `SUPER_ADMIN` 成员时，要求请求者角色也是 `SUPER_ADMIN`，且同租户该角色用户数必须 > 1，否则抛错（`CANNOT_DELETE_ALL_SUPER_ADMINS`）。

## 6 热点路径

| 路径 | 成本特征 | 说明 |
| --- | --- | --- |
| `GET /user/me` | 每前端启动/切组织一次，多 join | 默认合并 `employee`、`role`、`role.rolePermissions`、`tenant`；feature 聚合有 180s 缓存，键含 relationsHash 与租户/用户版本 |
| `GET /user/me`（limitOrganizations） | 1 次基础查询 + 1 次"取 1 条成员"查询 | `take: 1` 且要求 `organization.isActive = true`，是唯一会裁剪组织列表的分支 |
| `GET /user/search` | 大表模糊匹配 | `TRIAL` 角色只返回自己；`membership=non-members` 时排除超管并 `take(20)` |
| `POST /invite/emails` | 写放大 | 单次批量插入 N 条邀请 + N 封邮件；先用两次查询收敛 blocked 邮箱 |
| 成员写路径 | 全表扫描该用户成员 | `ensureUniqueDefault` / `ensureActiveMembershipRemains` 都对该 `userId` 的成员集合做全量 `find` 并逐条 update |
| 删除组织 | 批量 + 每用户重算 | 一次批量 delete 后，对每个曾拥有默认组织的用户再查一次剩余成员并补默认 |
| `PUT /user-groups/:id/members` | 覆盖式写 | 成员 id 需两次集合校验（tenant 内存在 + 该组织活跃成员），随后整体替换 M2M 集合 |

## 8 技术债

- `contact/` 的 `ContactController` 是 `@Controller()`（无前缀）且 `ContactModule` 未在 `ServerAppModule` 注册，属事实上的死模块。
- `invite.accept-employee` 的 docstring 与实现不一致：employee 创建、成员同步、接受通知三段注释，`updateEmployeeMemberships` 为空函数；`EmployeeService` 亦无自定义 `create`。
- `OrganizationCreateHandler` 与 `InviteAcceptOrganizationContactHandler` 都存在"连续两次 `organizationService.create`"的历史写法，第二次调用基本是空转。
- `InviteService.createBulk` 中 EMPLOYEE 发信分支被注释；`createOrganizationContactInvite` 的邮件发送整段被注释，邀请只在库里落地。
- `InviteService.resendEmail` 的 catch 分支 `return error` 而非抛出，调用方无法区分成功与失败，也没有返回值类型约定。
- `invite.email` 全局唯一索引与"同一 email 可再次受邀请"的业务诉求冲突，靠"删旧建新/改同一行"绕开，缺少显式约束说明。
- `deleteHardWithGuards` 与 `deleteWithGuards` 的成员收敛不对称（硬删不清 `user_organization`）。
- `employee/`、`invite/`、`contact/`、`organization-contact/`、`organization-language/`、`user-group/` 六个目录均无 spec 文件；`user/`、`user-organization/`、`organization/` 有 spec，其中 `organization.service.spec.ts` 覆盖"先收敛成员再删组织"的顺序。
- `InviteAcceptOrganizationContactHandler` 里 `invite.organizationContact[0]` 的取值依赖 M2M 顺序，代码自带 `TODO` 要求改成 1:1。

## 9 结论

三条主链的真实行为可概括为：读取链是"按需裁剪 + 版本化缓存"，成员链是"幂等创建 + 默认组织唯一性 + 删除时补位"，邀请链是"库内状态机完整、邮件与员工落地被削减"。最需要警惕的是文档与实现的漂移（员工接受路径）、遗留的空转调用（重复 create）与无人守护的模块（6 个目录零测试）；最需要遵守的边界是不让用户组、成员关系越过权限矩阵去替代角色与工作空间授权。
