## D1 入站凭据固定为五种，各自独立生命周期
- **分类**：技术选型
- **动机**：无此项（未检索到统一论证五种凭据取舍的设计文档）
- **决策**：入站凭据按用途拆分为五类并各自维护入口：① 登录 JWT + refresh（`jwt` / `jwt-refresh` / `ws-jwt` / `basic`）；② `x-api-key` 长期 API key；③ `x-client-secret` 或 `Bearer cs-x-` 的短期 client secret（按绑定类型分派）；④ 出站 actor token（`typ:'actor'`，TTL 封顶）；⑤ 外部身份绑定。所有入站凭据最终归一为 `User` 或 `IApiPrincipal` 两种主体。
- **背景约束**：既有浏览器会话、第三方长期调用、短时委托会话与无用户上下文的出站归因；`createdById` 单字段无法区分「API-key 授权 / 委托用户会话 / 公开助手会话」（docstring 明写）。
- **被否决方案**：无
- **重新评估触发条件**：出现新的凭据形态需求（如标准 OAuth2 客户端凭据流），或下游重新出现直接读 `apiKey.type` / `entityId` 做资源判定的代码（可观测：代码扫描命中数回升）。
- **关联代码**：`IApiPrincipal @ packages/contracts/src/api-key.model.ts`；`SecretTokenBindingType @ packages/contracts/src/secret-token.model.ts`；`SecretTokenStrategy.authenticate @ packages/server/src/secret-token/secret-token.strategy.ts`；`LocalOutboundActorTokenProvider.mint @ packages/server/src/actor-token/outbound-actor-token.provider.ts`
- **证据来源**：contracts docstring 明写；`file://docs/plans/PLAN_api_principal_identity.md` 明写

## D2 client secret 只落摘要，读取期兼容历史明文
- **分类**：兼容处理
- **动机**：避坑 —— 现象：已签发的 `secret_token` 是明文存储，若立即改为只存摘要，所有存量密钥同时失效；后果：已上线的嵌入/集成调用集体中断。因此采用「新写入摘要化 + 旧明文在其既有有效期内继续可兑付」的过渡策略。
- **决策**：新写入一律为单向摘要（`sha256:<hex>`），读取侧同时接受摘要与历史明文，并显式拒绝把库内摘要当 bearer 提交。
- **背景约束**：迁移需要零停机；摘要与明文在同一列共存，无法用列约束区分形态。
- **被否决方案**：无（文档中未见「一次性切换为只存摘要」的评估记载）
- **重新评估触发条件**：存量非摘要行占比归零（可观测：`token NOT LIKE 'sha256:%'` 统计为 0），或发生一次明文导出导致的密钥泄露事件。
- **关联代码**：`SecretTokenService.createHashed` / `SecretTokenService.findBySecret @ packages/server/src/secret-token/secret-token.service.ts`
- **证据来源**：`secret-token.service.ts` docstring 明写（单向表示、签发端点唯一返回原文、兼容期读取）；`secret-token.model.ts` 明写（never send a digest as a bearer secret）

## D3 技术身份复用 `COMMUNICATION` 型用户，业务用户只能显式声明
- **分类**：架构设计
- **动机**：避坑 —— 现象：此前存在「按 apiKey 临时创建 communication user」与「把 request user 猜成某个 end user」两类做法；后果：同一外部调用方可能产生多个技术用户，且请求代表的业务用户不可解释，审计与授权失真。
- **决策**：技术身份统一使用现有 `UserType.COMMUNICATION` 用户，不新增独立的技术主体实体；技术身份用稳定标识绑定（`xpert:<id>` / `integration:<id>` / `client:<code>`）；本次请求代表的业务用户只能由 `x-principal-user-id` 头显式指定，且限定同租户。
- **背景约束**：`user` 表已同时容纳真人与技术用户，默认用户列表排除 `COMMUNICATION`；secret 策略要求会话型凭据的 acting user 必须是真人用户。
- **被否决方案**：新增 `ApiConsumer` 之类的技术主体实体；从 body/query 或上下文推断业务用户。
- **重新评估触发条件**：出现技术身份与真人身份需要在数据库层面强隔离的需求（可观测：审计或合规要求「技术用户不得出现在用户管理/成员列表」的强制项）。
- **关联代码**：`ApiKeyService.resolvePrincipal @ packages/server/src/api-key/api-key.service.ts`；`buildApiKeyPrincipal @ packages/server/src/api-key/api-key-principal.ts`；`API_PRINCIPAL_USER_ID_HEADER @ packages/contracts/src/api-key.model.ts`
- **证据来源**：`file://docs/plans/PLAN_api_principal_identity.md` 明写；`api-key.model.ts` docstring 明写（`resourceScope` 不是权限授予、`requestedUserId` 语义）

## D4 角色是租户级，一个用户同一时刻只有一个角色
- **分类**：架构设计
- **动机**：无此项
- **决策**：角色在租户维度维护；一个用户只挂一个 `roleId`，不随组织切换而改变；授权结果以「角色 + 权限点 + enabled」的记录形式存储。
- **背景约束**：`user` 表只有一个角色列；组织切换改变的是工作上下文与数据范围，不改变角色；组织级权限只保留了少量旧列场景。
- **被否决方案**：组织级角色（文档明确当前不支持，仅列为未来可能）
- **重新评估触发条件**：出现「同一用户在不同组织需拥有不同能力」的明确需求（可观测：变更单要求成员关系携带角色字段，或出现按组织授予权限的接口需求）。
- **关联代码**：`User.role @ packages/server/src/user/user.entity.ts`；`RoleService.create` / `RoleService.findRoleForMutation @ packages/server/src/role/role.service.ts`；`RolePermissionService.checkRolePermission @ packages/server/src/role-permission/role-permission.service.ts`
- **证据来源**：`file://docs/zh-Hans/guides/permission.mdx` 明写（租户级角色、一人一角色、组织切换不换角色）

## D5 判权由 Guard 链承担，CASL 保留为未接线的占位
- **分类**：技术选型
- **动机**：无此项
- **决策**：实际授权由注解式 Guard 链完成 —— `@Permissions` + `PermissionGuard`、`@Roles` + `RoleGuard`、租户一致性守卫，以及少量组织属性权限场景；资源级 ABAC 工厂保留在代码库中但无调用方，不参与判定。
- **背景约束**：数据级规则（如「只读自己创建的资源」「已发布资源的可见性」）分散在各业务服务中，没有统一策略层；后端被明确定位为「最终裁决」方。
- **被否决方案**：无（未见「引入 CASL 做统一判定」的决策记录，也未见其被否决的记载）
- **重新评估触发条件**：出现跨资源的统一数据级规则需求，或 ABAC 工厂被某模块 imports / 出现 `createForUser` 调用点（可观测：调用点数量从 0 变为非 0）。
- **关联代码**：`PermissionGuard.canActivate @ packages/server/src/shared/guards/permission.guard.ts`；`RoleGuard.canActivate @ packages/server/src/shared/guards/role.guard.ts`；`CaslAbilityFactory.createForUser @ packages/server/src/core/casl/casl-ability.factory.ts`
- **证据来源**：`file://docs/zh-Hans/guides/permission.mdx` 明写后端裁决机制清单；`CaslAbilityFactory` 零调用者（代码扫描）

## D6 Guard 无元数据即放行（fail-open）
- **分类**：安全合规
- **动机**：无此项
- **决策**：判权守卫在未读到权限/角色元数据时直接放行；判权正确性因此外包给「注解覆盖率」，漏注解的控制器等价于不做授权判定。
- **背景约束**：所有路由默认经全局认证守卫，但认证与判权分离；`@Public()` 只跳过认证、不跳过判权，因此「公开端点 + 有权限注解」仍可能被拒绝。
- **被否决方案**：无（仓库内没有 lint 规则或 CI 检查拦「忘注解」，也未见切换为 fail-closed 的决策记载）
- **重新评估触发条件**：出现一次「新增控制器漏注解导致未授权访问」的事件，或团队引入元数据断言/静态检查（可观测：带权限注解的控制器 spec 中断言元数据的比例）。
- **关联代码**：`PermissionGuard.canActivate @ packages/server/src/shared/guards/permission.guard.ts`；`RoleGuard.canActivate @ packages/server/src/shared/guards/role.guard.ts`；`OrganizationPermissionGuard.canActivate @ packages/server/src/shared/guards/organization-permission.guard.ts`
- **证据来源**：代码事实（三处元数据为空即 `true`）；子专家技术债清单记载

## D7 UserGroup 只桥接工作空间 `canRun`，不提升读写与管理能力
- **分类**：安全合规
- **动机**：避坑 —— 现象：被授权的组内用户不是工作空间 owner/member，运行智能体时因复用创作态读校验而报 `Access denied to workspace`；后果：已经通过智能体入口 ACL 的用户无法运行目标智能体。修复方向是只补运行能力，而不是把他变成工作空间成员。
- **决策**：用户组只为工作空间补 `canRun`，绝不提升 `canRead` / `canWrite` / `canManage`；不能替代已发布智能体的入口 ACL；运行态查询必须继续保留租户、组织、工作空间数据范围，编辑/保存/发布入口不得走运行态方法绕过创作态校验。
- **背景约束**：判定依赖智能体、用户组与组成员的关联表组合；托管组元数据只能由平台侧写入（HTTP 入口会剥离），防止通过接口伪造组归属。
- **被否决方案**：把组内用户加入工作空间成员；用创作态通用查询承担运行态读取（文档明写会导致二次拒绝）。
- **重新评估触发条件**：用户组被要求授予编辑权，或文件级授权与工作空间能力需要统一（可观测：出现「组内用户需要改草稿」的需求单，或工作区权限与文件卷权限混用的工单量）。
- **关联代码**：`UserGroupService.updateMembers` / `UserGroupService.assertAccessibleOrganizationId @ packages/server/src/user-group/user-group.service.ts`；`XpertWorkspaceAccessService.hasPublishedXpertRunAccess`（`xpert-workspace` 模块）
- **证据来源**：`file://docs/plans/PLAN_xpert_user_groups_access.md` 明写；`file://docs/zh-Hans/guides/permission.mdx` 明写安全不变量

## D8 邀请接受拆三条公开路径，创建侧受权限点保护
- **分类**：接口契约
- **动机**：无此项
- **决策**：邀请接受提供三条独立公开入口（用户 / 员工 / 组织联系人），仅凭邀请 token + 邮箱即可完成；创建、重发、删除、联系人邀请均在受权限点保护的入口下。三路都以邀请状态置为已接受收尾。
- **背景约束**：外部联系人没有既有租户，需要一条能同时建立租户、组织与用户主体的路径；邀请只有「已邀请 / 已接受」两态，过期不落状态、只体现为过期时间与查询过滤，因此过期靠时间字段而非状态位。
- **被否决方案**：无（未见合并三路或改为统一受保护入口的决策记载）
- **重新评估触发条件**：出现邀请 token 被重放或滥用的安全事件，或需要为「已存在用户接受邀请」补齐显式分支（可观测：相关工单或 issue 反复出现）。
- **关联代码**：`InviteController.acceptUserInvite` / `acceptEmployeeInvite` / `acceptOrganizationContactInvite @ packages/server/src/invite/invite.controller.ts`；`InviteAcceptUserHandler.execute` / `InviteAcceptOrganizationContactHandler.execute @ packages/server/src/invite/commands/handlers/`；`InviteService.createBulk` / `validateByToken @ packages/server/src/invite/invite.service.ts`
- **证据来源**：controller 的 `@Public()` 明写；handlers docstring 与 TODO 明写（含 `accept-organization-contact` 里「邀请与联系人应改为一对一」的 TODO；`accept-employee` 的 docstring 与实际产出一致性存在漂移）

## D9 判权结果按「角色 + 权限组合」缓存 5 分钟
- **分类**：性能取舍
- **动机**：避坑 —— 现象：每个带权限注解的请求都要回源一次角色权限计数查询；后果：判权会成为请求量的放大器（尤其注解组合多、命中率低时）。用 TTL 缓存换取判权不查库。
- **决策**：判权结果以「租户 + 角色 + 权限组合」为键缓存 5 分钟，未命中才回源，且缓存包含否定结果（负缓存）；不设置主动失效钩子。
- **背景约束**：缓存键包含权限组合，同一角色的不同端点各占一个键，键空间随注解组合增长；缓存组件不支持按前缀扫描删除，因此无法按角色整体失效；撤权存在最长 5 分钟残留窗口。
- **被否决方案**：无（「按角色缓存权限集合并做集合包含判断」仅作为改进方向出现在子专家分析中，未见决策记载）
- **重新评估触发条件**：撤权残留窗口被业务或合规判定不可接受，或缓存键数量/回源率不可控（可观测：权限相关缓存键总量、未命中率、撤权类工单量）。
- **关联代码**：`PermissionGuard.canActivate @ packages/server/src/shared/guards/permission.guard.ts`；`CheckRolePermissionHandler.execute @ packages/server/src/role-permission/commands/handlers/check-role-permission.handler.ts`；`RolePermissionService.checkRolePermission @ packages/server/src/role-permission/role-permission.service.ts`
- **证据来源**：代码事实（缓存键形态与 5 分钟 TTL、无失效调用点）；子专家技术债清单记载

## 决策之间的张力（供评审提示）
- D5（Guard 链）与 D6（默认放行）共同决定：安全正确性 = 注解覆盖率，二者需一起评审新增端点。
- D4（一人一角色）与 D7（用户组只补 `canRun`）共同决定：批量授权只能走用户组，且只能补运行能力，不能自定义能力组合。
- D2（摘要化兼容期）与 D9（5 分钟缓存）都是「最终一致」型折中，其可观测判据即为各自的重新评估触发条件。
- D8 的公开接受入口与 D6 的默认放行叠加时，邀请链是权限面最大的公开写路径，评审优先级最高。
