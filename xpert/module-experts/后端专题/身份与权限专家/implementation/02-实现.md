## 注册与登录实现位置
- `AuthService.register`：通用注册（注册/加入组织/受邀接受共用），解析 `tenant` 后调用私有 `createRegisteredUser`，再以 `resolveDefaultOrganizationId` 兜底组织并发欢迎邮件（`EmailService.welcomeUser`）。
- `AuthService.signup`：免费注册专用，`createRegisteredUser` 时置 `emailVerified=false` 并写入 `emailVerificationToken`（nanoid），随后 `sendVerifyEmailMail`。
- `AuthService.createRegisteredUser`（私有）：单事务内 `lockTenantRegistrationScope`（tenant 行 `pessimistic_write` 锁）→ 按 `tenantId+email`/`tenantId+username` 查重（允许「待验证注册」幂等更新）→ 保存 `User`（bcrypt 哈希）→ hydrate `role`/`tenant` → 解析组织 → `ensureMembershipInTransaction`（`SUPER_ADMIN` 跳过）→ `ReferralService.bindRegistration`；事务外补 `completeMembershipCreation`（事件 + 特性缓存版本）。
- 登录：`AuthController` → `AuthLoginCommand` → `AuthLoginHandler.execute`（`UserService.findOneByOptions` + `bcrypt.compare` + 租户校验 → `AuthService.createToken` → `updateRefreshToken`）；另有 `AuthService.validateUser`（强制 `emailVerified: true`）供其他入口复用。
- 令牌：`AuthService.createToken` 组装 payload（`id`、`tenantId`、`employeeId`、`role.name`、启用权限位），分别用 `JWT_SECRET`/`JWT_REFRESH_SECRET` 与 `jwtExpiresIn`/`jwtRefreshExpiresIn` 签发；`refreshTokens` 以 bcrypt 比对 `user.refreshToken` 后轮换；`issueTokensForUser` 为 SSO 回调用例（签发 + 落库哈希）。
- SSO：`AuthSsoBindingService.registerAndBind`/`registerVerifiedEmailIdentity` 依赖 `AccountBindingService` 与 `PendingSsoBindingChallengeService`，成功后统一 `issueTokensForUser`。
章节来源：[auth.service.ts](file://packages/server/src/auth/auth.service.ts)（关键符号：AuthService.register、createRegisteredUser、createToken、refreshTokens、resolveDefaultOrganizationId）

## 邀请接受三条路径
- 入口：`InviteController` 的 `POST invite/user`、`POST invite/employee`、`POST invite/contact`，三者均 `@Public()`，分别派发 `InviteAcceptUserCommand`/`InviteAcceptEmployeeCommand`/`InviteAcceptOrganizationContactCommand`。
- `accept-user`：校验组织 → 补默认头像 → `AuthService.register`（tenant 取自组织，`organizationId` 传入，内部建 `user_organization`）→ invite 置 `ACCEPTED`。
- `accept-employee`：文档注释声称「register user 后创建 employee 记录」，实现中 employee 创建与成员关系同步整段被注释（仅保留 `InviteService.update` 置 `ACCEPTED`）；`updateEmployeeMemberships` 回调也是空实现——文档与实现不符。
- `accept-organization-contact`（8 步）：`TenantService.create` 新租户 → `TenantRoleBulkCreateCommand`（建角色+权限）→ `TenantFeatureOrganizationCreateCommand` → `OrganizationService.create` → 组织落库 → 取 `SUPER_ADMIN` 角色 → `AuthService.register`（用户绑定该角色）→ `OrganizationContactService.update` 置 `ContactOrganizationInviteStatus.ACCEPTED` → invite 置 `ACCEPTED`。
- 邀请创建侧：`InviteService.createBulk` 规范化邮箱、按 `tenantId+email+status=INVITED` 与既有租户用户去重（`blockedEmails`），`expireDate` 由 `organization.inviteExpiryPeriod`/`DEFAULT_INVITE_EXPIRY_PERIOD` 或 `InvitationExpirationEnum.NEVER`（null）决定；`InviteOrganizationContactHandler` 以 `VIEWER` 角色向组织联系人发邀请并把联系人状态置 `INVITED`。
章节来源：[invite.accept-organization-contact.handler.ts](file://packages/server/src/invite/commands/handlers/invite.accept-organization-contact.handler.ts)（关键符号：InviteAcceptOrganizationContactHandler.execute）

## 组织成员建立与默认成员不变量
- `UserOrganizationService.prepareCreateEntity`：要求 userId+organizationId，同组织重复成员直接报错；首条成员强制 `isActive`，`isDefault` 缺省等于「首条成员」；若为默认则先 `ensureUniqueDefault`。
- `ensureUniqueDefault`：查询该用户在同租户的全部成员关系，把（除自己外）仍为默认的记录逐一降级，保证「至多一个默认组织」。
- `ensureActiveMembershipRemains`：把「除被排除项外」的成员关系过滤出活跃集合，为空则抛错「User must have at least one active organization membership.」——保证「至少一个活跃成员」。
- 删除路径（`delete` override）：`resolveRemainingMemberships` 拒删最后一条（除非 `allowDeletingLastMembership`）→ 若删的是默认或剩余集合无默认，则 `pickNextDefaultMembership`（优先 active，否则第一条）并回写默认。
- 组织级收敛（`deleteByOrganizationForOrganizationRemoval`）：删除组织前批量删该组织全部成员关系，并按 `defaultUserIds` 为受影响用户重新指派默认组织，最后逐条发 `EVENT_USER_ORGANIZATION_DELETED`；调用方为 `OrganizationService.delete`（前置校验：存在待处理邀请或用户组时禁止删除）。
- 建组织侧：`OrganizationCreateHandler` 创建后调用 `ensureMembership` 并发出 `EVENT_ORGANIZATION_CREATED`。
章节来源：[user-organization.services.ts](file://packages/server/src/user-organization/user-organization.services.ts)（关键符号：UserOrganizationService.prepareCreateEntity、deleteByOrganizationForOrganizationRemoval、pickNextDefaultMembership）

## 权限判定链
- `PermissionGuard.canActivate`：读取 `PERMISSIONS_METADATA`（handler+class 合并）→ 为空直接放行 → 取 `RequestContext.currentUser()`、`currentTenantId()`、`currentRoleId()`，任一缺失即拒绝 → 计算缓存 key `userPermissions:{tenantId}_{roleId}_{permissions}` → 命中则用缓存布尔值，未命中则 `commandBus.execute(new CheckRolePermissionCommand(tenantId, roleId, permissions, true))` 并按 **5 分钟** TTL 回填。
- `CheckRolePermissionHandler.execute` 透传到 `RolePermissionService.checkRolePermission`：QueryBuilder 按 `tenantId` + `roleId`（includeRole）+ `permission IN (...)` + `enabled=true` 计数，`count > 0` 即通过——即权限是「角色-权限行」的存在性判定。
- `RoleGuard.canActivate`：读取 `ROLES_METADATA`，空即通过，否则 `RequestContext.hasRoles(roles)`。
- `TenantPermissionGuard`：先 `TenantBaseGuard` 校验，再在 `allowSuperAdminRole` 时短路 `SUPER_ADMIN`；真正的「租户权限查询」分支（`tenantService` 注入与 `tenantPermissions` 匹配）被注释——只保留骨架。
- `OrganizationPermissionGuard`：以 `Employee` + `organization` 关系取组织，用 `permissions.filter((p) => employee.organization[p])` 判定（依赖组织实体上的旧布尔列）。
章节来源：[permission.guard.ts](file://packages/server/src/shared/guards/permission.guard.ts)（关键符号：PermissionGuard.canActivate、userPermissions 缓存键）

## 五种身份凭据的签发与校验入口
1. **登录 JWT/refresh**：签发 `AuthService.createToken`（payload 含 role/permissions/employeeId），校验由 `JwtStrategy`/`WsJwtStrategy`/`RefreshTokenStrategy`（`auth/strategies`）与 `AuthService.isAuthenticated`/`hasRole` 完成，刷新走 `refreshTokens`。
2. **API key（`x-api-key`）**：`ApiKeyStrategy` 校验 `ApiKey` 记录（`validUntil`/`expired`/`lastUsedAt`），`UseApiKeyHandler` 记录使用时间；principal 由 `buildApiKeyPrincipal` 生成（`ownerUserId`/`apiKeyUserId`/`requestedUserId`/`resourceScope`）。
3. **secret token / client secret（`x-client-secret` 或 Bearer `cs-x-`）**：`ApiKeyOrClientSecretAuthGuard` 识别 `cs-x-` 前缀或头存在即走 `client-secret` 策略；`SecretTokenStrategy.authenticate` 读取 token → `SecretTokenService.findBySecret`（摘要或历史明文，`validUntil` 未过期）→ 按 `SecretTokenBindingType` 分派 `resolveConversationPrincipal`/`resolveUserXpertPrincipal`/`resolvePublicXpertPrincipal`/`resolveEnterpriseXpertPrincipal`，否则落到 API key 绑定并 `ApiKeyService.resolvePrincipal`。
4. **actor token**：`LocalOutboundActorTokenProvider.mint` 以 `JWT_SECRET` 签名，claim 含 `typ:'actor'`、`id`、`tenantId`、`act`（含 `principal_type`/`client_secret_binding_type`/`requested_user_id`），`audience` 可配置，TTL 默认 900s 且 `Math.min` 封顶。
5. **外部身份绑定**：`AccountBindingService.bindUser` 在事务内解析 `tenantId+provider+subjectId` 与 `tenantId+provider+userId` 双唯一索引，冲突抛 `ConflictException`（仅 `lark` 允许回收 `UserType.COMMUNICATION` 旧身份）。
章节来源：[secret-token.strategy.ts](file://packages/server/src/secret-token/secret-token.strategy.ts)（关键符号：SecretTokenStrategy.authenticate、resolveUserXpertPrincipal、resolveEnterpriseXpertPrincipal）

## 设计模式及落点
- **策略（Strategy）+ Passport**：`SecretTokenStrategy`（`'client-secret'`）与 `api-key`、`jwt`、`ws-jwt`、`jwt-refresh` 策略名，用于「同端点多凭据」；`ApiKeyOrClientSecretAuthGuard` 以 `PassportAuthGaurd('client-secret')` 动态实例化实现策略复用。
- **Guard + 元数据反射**：`@Permissions`/`@Roles` 元数据 + 反射器组合，`ApiKeyOrClientSecretAuthGuard` 再叠加 `ALLOWED_CLIENT_SECRET_BINDINGS_METADATA` 白名单（`ENTERPRISE_XPERT`/`USER_CONVERSATION` 必须显式声明才放行）。
- **CQRS（CommandBus/QueryBus）**：注册/登录（AuthLoginCommand、AuthRegisterCommand）、邀请接受、角色批量创建、权限判定（CheckRolePermissionCommand）、组织创建、API key 使用（UseApiKeyQuery）。
- **工厂/合成 principal**：`buildApiKeyPrincipal` 与 `OutboundActorTokenProvider`（抽象类 + `LocalOutboundActorTokenProvider` 本地实现）把「凭据 → principal/令牌」集中一处。
- **模板方法 + 服务基类**：`TenantAwareCrudService`/`TenantOrganizationAwareCrudService` 承载租户/组织作用域，`UserOrganizationService`、`OrganizationService`、`RoleService`、`UserGroupService` 通过 override `create/update/delete` 注入不变量。
章节来源：[api-key-or-client-secret.guard.ts](file://packages/server/src/shared/guards/api-key-or-client-secret.guard.ts)（关键符号：ApiKeyOrClientSecretAuthGuard.canActivate、assertClientSecretBindingAllowed）

## 热点路径
- **每请求判权**：`PermissionGuard` 每个带权限注解的请求都要拼缓存 key 并访问 `CACHE_MANAGER`；角色权限变更后 5 分钟内可能读到旧授权（无主动失效）。
- **登录签发**：`createToken` 在 `role`/`employee` 缺失时回查 `UserService.findOne(relations: role.rolePermissions, employee)`——登录热路径上的一次关联读取。
- **成员写入**：`prepareCreateEntity` 每次创建都会 `find` 该用户在同租户的全部成员关系（默认唯一性 + 首条判定），成员数增长时是 O(n) 读放大。
- **邀请接受**：`accept-organization-contact` 一次请求内串行 8 步（含建租户、建角色+权限、建组织、建用户），是全域最重的写路径。
章节来源：[role-permission.service.ts](file://packages/server/src/role-permission/role-permission.service.ts)（关键符号：RolePermissionService.checkRolePermission）、[auth.service.ts](file://packages/server/src/auth/auth.service.ts)（关键符号：AuthService.createToken）

## 技术债清单
- **CASL 未接线**：`CaslAbilityFactory.createForUser` 无任何调用者（仅 `core/casl` 两文件出现），实际判权只走 `@Permissions`+`PermissionGuard`/`@Roles`+`RoleGuard`。
- **TenantPermissionGuard 权限查询被注释**：`TenantService` 注入与租户权限匹配整段注释，只剩基类校验与超级管理员短路。
- **guard 元数据为空即放行**：`PermissionGuard`/`RoleGuard`/`OrganizationPermissionGuard` 三处默认 `true`，缺少注解的 controller 等价于无鉴权。
- **`x-principal-user-id` 缺全局白名单**：API key 分支按该头解析 `requestedUserId`，仅在 `USER_CONVERSATION` 分支显式删除伪造头，其余分支未见集中校验。
- **USER_XPERT 委托会话残留**：`resolveUserXpertPrincipal`/`resolvePublicXpertPrincipal`/`resolveEnterpriseXpertPrincipal` 仍在构造 `@deprecated` 合成 `apiKey`（仅保留凭据元数据兼容）。
- **invite.accept-employee 文档与实现不符**：handler 注释声称创建 employee，实际 employee 创建与成员同步整段注释。
- **password_reset 无 tenantId 且过期硬编码 10 分钟**：`PasswordReset` 继承 `BaseEntity`，`afterLoadEntity` 以 `expiredAt.diff(createdAt,'minutes') > 10` 判定。
- **invite.email 全局唯一索引**：与 token 同为 `@Index({ unique: true })`，跨租户同一邮箱无法并存两条邀请。
- **OrganizationPermissionGuard 用 employee 旧列**：以 `employee.organization[p]` 布尔列判权，与组织权限模型演进脱节。
章节来源：[casl-ability.factory.ts](file://packages/server/src/core/casl/casl-ability.factory.ts)（关键符号：CaslAbilityFactory.createForUser）、[password-reset.entity.ts](file://packages/server/src/password-reset/password-reset.entity.ts)（关键符号：PasswordReset.afterLoadEntity）

## 设计维度分析
- **维度一：凭据归一 vs 租户隔离**。5 种凭据最终都归一为 `IApiPrincipal`/`RequestContext`，但只有会话型凭据（`USER_CONVERSATION`）强制把 `tenant-id` 写回头部并删除客户端伪造的 `x-principal-user-id`；API key 分支仍信任 `requestedUserId` 头，说明「隔离强度随凭据类型递减」，审计须按凭据分类。
- **维度二：一处判权 vs 注解覆盖**。判权算法集中在 `RolePermissionService.checkRolePermission`（存在性判定 + 5 分钟缓存），但触发点分散在每个 controller 注解上，「默认放行」把安全正确性外包给注解覆盖率——这是一致性的最大结构性风险。
- **维度三：宽入口 + 严出口**。邀请接受端点 `@Public()`（无鉴权）却做最重的写操作（建租户/组织/用户），而凭据侧采取摘要存储、`validUntil`、enterprise scope 复核等严出口策略；两端的安全投入不对等。
章节来源：[permission.guard.ts](file://packages/server/src/shared/guards/permission.guard.ts)（关键符号：PermissionGuard.canActivate）、[invite.accept-employee.handler.ts](file://packages/server/src/invite/commands/handlers/invite.accept-employee.handler.ts)（关键符号：InviteAcceptEmployeeHandler.execute）

## 结论
实现层面的主链路是清晰的：注册集中在 `AuthService.createRegisteredUser` 的单事务里（含租户锁、查重、成员关系、推荐绑定），邀请接受三路各自封闭，判权被收敛到一条「guard → 命令 → 服务查询」的链路上，5 种凭据都有明确的签发/校验入口。工程化短板同样明确：默认放行的 guard、被注释的租户权限查询、未接线的 CASL、以及 `accept-employee` 的文档-实现漂移，使得「读代码得出的安全语义」与「运行时真实语义」存在偏差，需要在测试与评审中以 controller 注解清单为基准逐项核对。
