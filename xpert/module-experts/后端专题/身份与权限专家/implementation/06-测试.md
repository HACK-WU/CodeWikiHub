## spec 位置与命名惯例
- 与被测源文件同目录同名前缀：`<module>/<name>.service.spec.ts`、`*.controller.spec.ts`、`*.handler.spec.ts`、`*.strategy.spec.ts`、`*.provider.spec.ts`、`*.entity.spec.ts`；CQRS handler 的 spec 放在 `commands/handlers/`、`queries/handlers/` 内（如 `api-key/queries/handlers/api-key.use.handler.spec.ts`、`user-organization/commands/handlers/*.spec.ts`）。
- 顶层 `describe` 常用「被测单元名」或行为句（如 `describe('shared ChatKit credential storage'`、`describe('default role permissions'`、`describe('user organization seed helpers'`）。
- 按目录口径实测：本域（`user/`…`password-reset/` 等 17 个模块目录）共 **24 个 spec**；若把判权直接相关的 `shared/guards/` 2 个 spec 计入则为 26 个。调研清单口径 27 个的差异来自是否把 `shared/`、`core/` 邻近 spec 计入，本文件按目录逐文件列明以便复核。
章节来源：[user-organization/user-organization.services.spec.ts](file://packages/server/src/user-organization/user-organization.services.spec.ts)（关键符号：describe('UserOrganizationService')）

## 框架与运行方式
- 框架：Jest + ts-jest（配置 `packages/server/jest.config.ts`），仅用 `@nestjs/testing` 的 `Test.createTestingModule` 构造依赖，不做真实 HTTP/E2E。
- 运行单个 spec（已实测可用）：
  `cd /root/xpert && node node_modules/jest/bin/jest.js --config packages/server/jest.config.ts --runTestsByPath packages/server/src/auth/auth.service.spec.ts`
- 运行整个目录示例：把 `--runTestsByPath` 换成 `packages/server/src/user-organization` 或直接用路径匹配模式（`--testPathPattern`）。
- 无数据库、无 Redis 依赖：仓储用 `{ find, findOne, delete, update, save, create }` 形态的 `jest.fn()` 替身；Redis 用 `{ setEx, get, del, getDel }` 内存替身。
章节来源：[api-key/api-key.use.handler.spec.ts](file://packages/server/src/api-key/queries/handlers/api-key.use.handler.spec.ts)（关键符号：UseApiKeyHandler、getRepositoryToken(ApiKey)）

## 断言风格与 mock 模式
- **手工装配 + jest.fn()**：多数 spec 直接 `new XService(repository as unknown as Repository<T>, ...)`，避免 Nest 容器开销（`UserOrganizationService`、`OrganizationService`、`RolePermissionService`、`SecretTokenStrategy`、`AuthLoginHandler`）。
- **jest.mock 打断循环依赖**：`user.service.spec.ts` 在 import 之前 `jest.mock('../core/context')`、`jest.mock('../core/crud')`、`jest.mock('./user.entity')`、`jest.mock('../feature/feature-organization.entity')`、`jest.mock('../account-binding/external-identity-binding.entity')`；`auth.service.spec.ts` mock `@xpert-ai/server-auth`、`@xpert-ai/server-config`、`../referral`、`../organization` 等，`auth-sso-*`、`account-binding.controller`、`auth.login.handler` 亦同。
- **mock 后 require 加载被测模块**：`jest.mock(...)` 之后用 `const { X } = require('./x.service')` 取模块，保证 mock 生效（`organization.service.spec.ts`、`account-binding.controller.spec.ts`、`auth.login.handler.spec.ts`）。
- **mock QueryBuilder / 仓储细粒度断言**：`RolePermissionService.checkRolePermission` 相关测试断言 `createQueryBuilder` 链式参数，权限迁移测试直接检查 `repository.delete` 的 criteria（`criteria.permission.value` / `criteria.tenantId.value`）。
- **mock Redis 与 Challenge**：`pending-sso-binding-challenge.service.spec.ts` 断言 `setEx('auth:sso:bind:challenge:<ticket>', 600, expect.stringContaining('"flow":"anonymous_bind"'))`，并覆盖 `get`/`getDel`/`del`。
- **环境变量快照-恢复**：`outbound-actor-token.provider.spec.ts` 保存/恢复 `JWT_SECRET`、`XPERT_OUTBOUND_ACTOR_TOKEN_AUDIENCE`、`XPERT_OUTBOUND_ACTOR_TOKEN_TTL_SECONDS`，用 `decode`/`verify` 校验 claim 与签名。
- **元数据断言**：`Reflect.getMetadata` 检查 `@Public`、`__guards__`、`HTTP_CODE_METADATA`（`user.controller.spec.ts`、`account-binding.controller.spec.ts`）。
- **Nest Test 模块**：`api-key.use.handler.spec.ts` 与 `resolve-user-organization-access.handler.spec.ts` 用 `Test.createTestingModule` + `getRepositoryToken`，后者还构造 `CqrsModule` 消费方验证命令总线派发。
章节来源：[user.service.spec.ts](file://packages/server/src/user/user.service.spec.ts)（关键符号：jest.mock('../core/crud')、jest.mock('./user.entity')）

## 无测试模块与缺口
- 完全无 spec 的目录（读代码时风险最高）：`role/`、`employee/`、`invite/`、`contact/`、`organization-contact/`、`organization-language/`、`user-group/`、`password-reset/`。
- 具体缺口：邀请接受三路（含被注释的 accept-employee）无测试；`PermissionGuard` 本身无 spec（判权缓存 key 与 TTL、空元数据放行仅能靠代码阅读确认）；`RoleGuard`/`TenantPermissionGuard`/`OrganizationPermissionGuard` 无 spec；`CaslAbilityFactory` 无 spec 也无调用者；`AuthSsoController`、`UserGroupService`、`RoleService.createBulk` 无直接测试。
- 建议优先级：① `InviteAccept*Handler` 三 handler（公开端点写路径）② `PermissionGuard`（缓存与默认放行）③ `UserGroupService` 作用域校验 ④ `RoleService`/`TenantRoleBulkCreateHandler`。
章节来源：[permission.guard.ts](file://packages/server/src/shared/guards/permission.guard.ts)（关键符号：PermissionGuard.canActivate）

## 测试可执行性
- ✅ 可跑：本域全部 24 个 spec 均可在无 DB/Redis/网络的纯 Node 环境执行；已实测命令见 `## 框架与运行方式`。
- ✅ 无外部依赖：数据库访问被替身化，Redis 用内存替身，社交登录/配置包被 `jest.mock`，环境变量用快照-恢复（未写入真实 secret）。
- 本域未见 skip/todo：检索 `describe.skip(`/`it.skip(`/`test.skip(` 在本域 spec 中为空。
- 全仓另有 skip 标记位于非本域目录：`plugin/` 的若干 spec（如 `organization-plugin.store.spec.ts`、`plugin-startup-watchdog.spec.ts`、`plugin-schema-scope.integration.spec.ts`、`marketplace/plugin-marketplace-shared.integration.spec.ts`）与 `core/redis/redis-ephemeral.service.spec.ts` 等，归属 plugin/core，不属本专家域范围。
- 注意：包含 `Test.createTestingModule` 的 spec 依赖 Nest 反射元数据，若后续重构构造函数签名（新增依赖）需同步更新这些测试；`jest.mock` 打断依赖图的 spec 对 mock 路径敏感，移动目录会导致 mock 失效。
章节来源：[pending-sso-binding-challenge.service.spec.ts](file://packages/server/src/auth/sso/pending-sso-binding-challenge.service.spec.ts)（关键符号：PendingSsoBindingChallengeService）

## 结论
本域测试呈现出「服务层与凭据/principal 逻辑覆盖较好、判权与邀请写路径偏弱」的形态：24 个本域 spec 集中在 AuthService、UserOrganizationService、secret/api-key principal 与 SSO 绑定，另有 12 个邻近 spec 守住上下文与基础设施；而邀请接受、Guard 默认放行、用户组作用域这些高风险的「边界语义」缺少测试护栏。补齐这三类缺口，比继续增加服务层单测更能降低身份与权限域的回归风险。
