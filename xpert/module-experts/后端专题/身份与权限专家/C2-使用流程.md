**通用前置约定（所有配方共用）**
- 认证全局生效：未标 `@Public()` 的路由需 `Authorization: Bearer <jwt>`、Basic 或 `x-api-key`，否则 401。
- 判权按注解生效：`@Permissions` 必须同时挂 `PermissionGuard`，`@Roles` 必须同时挂 `RoleGuard`；两者元数据为空即放行。
- 上下文来源：租户由 `tenant-id` 头与登录态 `user.tenantId` 决定；组织由 `organization-id` 头与 `x-scope-level` 决定。
- 已认证请求的权限快照写在 token 内，撤权不会即时生效（见 Recipe 7）。

## Recipe 1 邀请用户加入组织
- **业务目标**：管理员按邮箱批量邀请，被邀请人通过邮件链接加入当前组织的租户，落成用户 + 成员关系。
- **调用顺序**：
  1. 发起：`POST /api/invite/emails`（`TenantPermissionGuard` + `PermissionGuard` + `@Permissions(ORG_INVITE_EDIT)`，201）→ `InviteBulkCreateCommand` → `InviteService.createBulk(emailInvites, languageCode)`。
  2. 校验链接（可选）：`GET /api/invite/validate`（`@Public()`），参数为 `data` JSON 中的 `email` + `token` → `InviteService.validateByToken(...)`。
  3. 接受（三选一，均 `@Public()`）：`POST /api/invite/user`（加入既有组织）、`POST /api/invite/employee`、`POST /api/invite/contact`（外部联系人，可新建租户与组织）。
  4. 三条路径都以 `InviteService.update(inviteId, { status: InviteStatusEnum.ACCEPTED })` 收尾。
- **事务边界**：创建阶段逐条邀请写入，不跨邮箱共享事务；接受阶段 `AuthService.register` 自带单事务（租户行锁 → 查重 → 写用户 → 建成员关系 → 推荐绑定），邀请状态更新在 `register` 返回之后调用，属独立写，两者不同事务。
- **预期结果**：`invite.status` 由 `INVITED` 变 `ACCEPTED`；新增 `user` 行与 `user_organization` 行；`contact` 路径还会新建 `organization`（并可新建 tenant）。
- **错误处理**：邀请 `SUPER_ADMIN` 角色而邀请人不是 `SUPER_ADMIN` → `UnauthorizedException`；目标邮箱已是本租户用户或已有未过期邀请 → 计入返回值的 `ignored`（不报错）；`invite.email` 为全局唯一索引，跨租户同邮箱会直接撞库约束；token 过期、邮箱不匹配或已接受 → 统一 `BadRequestException`。
- **真实代码示例**：
```ts
// packages/server/src/invite/invite.controller.ts
@Post('/emails')
@HttpCode(HttpStatus.CREATED)
@UseGuards(TenantPermissionGuard, PermissionGuard)
@Permissions(PermissionsEnum.ORG_INVITE_EDIT)
async createManyWithEmailsId(
  @Body() entity: CreateInviteDTO,
  @LanguageDecorator() languageCode: LanguagesEnum
): Promise<ICreateEmailInvitesOutput>

// packages/server/src/invite/invite.service.ts
async createBulk(emailInvites: ICreateEmailInvitesInput, languageCode: LanguagesEnum): Promise<ICreateEmailInvitesOutput>
async validateByToken(where: Pick<FindOptionsWhere<Invite>, 'email' | 'token'>, relations: string[] = []): Promise<IInvite>
```

## Recipe 2 用户注册并绑定默认组织
- **业务目标**：新用户落库并获得一个组织归属；自助注册额外发邮箱验证信。
- **调用顺序**：
  1. 自助注册：`POST /api/auth/signup`（`@Public()`，`deploymentTarget === 'customer-onprem'` 时 403）→ `AuthTrialCommand` → `AuthService.signup(input, languageCode)`。
  2. 代客创建：`POST /api/auth/register`（需登录，`RegisterUserDTO`）→ `AuthRegisterCommand` → `AuthRegisterHandler.execute` → `AuthService.register(input, languageCode)`。
  3. 邀请接受路径复用同一条 `AuthService.register`（见 Recipe 1）。
  4. 组织归属：优先 `input.organizationId`，否则取该租户 `isDefault = true && isActive = true` 的组织。
- **事务边界**：`register` → `createRegisteredUser` 单事务内完成：租户注册范围行锁（`pessimistic_write`）→ `(tenantId,email)`/`(tenantId,username)` 查重 → 写 `user` → 重建 `role`/`tenant` 关联 → 建成员关系（`SUPER_ADMIN` 跳过）→ 推荐注册绑定；提交后补发成员事件与欢迎邮件。
- **预期结果**：新增 `user`（bcrypt 哈希、`roleId` 已绑定）；signup 额外写 `email_verification`（唯一 token，有效期 2 天）；非 `SUPER_ADMIN` 用户获得 `user_organization` 首条成员记录（强制活跃且默认）。
- **错误处理**：同租户邮箱或用户名已存在 → `BadRequestException`（i18n `core.User.Error.AccountAlreadyExists`）；目标角色为 `SUPER_ADMIN` 但创建者不是 `SUPER_ADMIN` → 400/401；未解析到租户 → i18n `server-ai:Error.RegistrationTenantRequired`。
- **真实代码示例**：
```ts
// packages/server/src/auth/auth.service.ts
async signup(input: IUserRegistrationInput, languageCode: LanguagesEnum)
async register(input: IUserRegistrationInput, languageCode: LanguagesEnum): Promise<User>
// 事务内的成员绑定（组织为默认兜底）：
await this.userOrganizationService.ensureMembershipInTransaction(manager, {
  organizationId, tenantId, userId: String(hydratedUser.id)
})
```

## Recipe 3 登录与刷新令牌（含 socket 重连复用 refresh）
- **业务目标**：前端取得 access + refresh 令牌；access 过期后轮换；WebSocket 断线或 401 时复用同一刷新流程重连。
- **调用顺序**：
  1. 登录：`POST /api/auth/login`（`@Public()`）→ `AuthLoginCommand` → `AuthLoginHandler.execute` → `AuthService.createToken(user)` → `AuthService.updateRefreshToken(user.id, refreshToken)`。
  2. 刷新：`GET /api/auth/refresh`（`@Public()` + `AuthGuard('jwt-refresh')`，Authorization 头带 refresh token）→ `AuthService.refreshTokens(userId, refreshToken)`。
  3. WebSocket：握手凭据取 `auth.token`（`ws-jwt` 策略）；收到 401 时前端调用 `refreshToken()`，成功后 `connect()` 复用新令牌建连。
  4. 查询当前状态：`GET /api/auth/authenticated`（`@Public()`）、`GET /api/auth/role?roles=`（需登录）。
- **事务边界**：无显式事务；登录与刷新各含一次 `user.refreshToken` 覆盖写。轮换语义为「读旧哈希 → 比对 → 覆盖新哈希」，无锁。
- **预期结果**：客户端得到 `{ token, refreshToken }`；服务端只存 refresh 的 bcrypt 哈希且不回传；旧 refresh token 立即失效（轮换）。
- **错误处理**：账号或密码错误时登录返回 `null`（HTTP 200，**不是 401**），排障需按响应体判断；刷新失败统一 `ForbiddenException('Access Denied')`；服务端**没有 logout 端点**，登出只能靠令牌过期或轮换。
- **真实代码示例**：
```ts
// packages/server/src/auth/auth.service.ts
async createToken(user: Partial<User>): Promise<{ token: string; refreshToken: string }>
async refreshTokens(userId: string, refreshToken: string)
async updateRefreshToken(userId: string, refreshToken: string)
async issueTokensForUser(userId: string): Promise<{ jwt: string; refreshToken: string; userId: string }>

// apps/cloud/src/app/@core/services/chat.service.socket.ts
this.socket.on('exception', (data) => {
  if (data.status === 401 && socketId === this.socket.id) {
    this.setStatus(false)
    if (!this.refreshTokening()) this.refreshToken()
  }
})
refreshToken() { this.#auth.refreshToken().subscribe(() => { this.connect() }) }
```

## Recipe 4 密码重置与邮箱验证
- **业务目标**：用户自助找回密码；用户完成邮箱验证或要求重发验证信。
- **调用顺序**：
  1. 申请重置：`POST /api/auth/request-password`（`@Public()`）→ `AuthService.requestResetPassword(request, languageCode, originUrl?)`：按小写邮箱取该邮箱下的全部用户 → 逐个签发重置 token → 写 `password_reset` → 拼 `clientBaseUrl + '/auth/reset-password'` 链接发信。
  2. 执行重置：`POST /api/auth/reset-password`（`@Public()`）→ `AuthService.resetPassword(request)`（`ChangePasswordRequestDTO`：`token`/`password`/`confirmPassword`）。
  3. 邮箱验证：`GET /api/auth/verify?token=`（`@Public()`）→ `AuthService.verifyEmail(token)`。
  4. 重发验证信：`POST /api/auth/resend-verification`（需登录）→ `AuthService.resendVerificationMail(user, languageCode)`。
- **事务边界**：重置为「先落 `password_reset` 行、再发信」两步，发信失败不回滚记录；改密与置 `emailVerified = true` 在同一次改密调用内完成。
- **预期结果**：`password_reset` 新增一行（仅 `email` + `token`，**无 tenantId**），10 分钟内有效；`email_verification` 重发会覆盖 token，旧链接立即失效。
- **错误处理**：重置失败统一 `BadRequestException('Password Reset Failed (code: 1|2|3).')`；单用户变体在用户不存在时抛 `NotFoundException('Email is not correct, please try again.')`；SMTP 故障被吞成通用错误码，表现为「重置失败」而非明确错误。
- **真实代码示例**：
```ts
// packages/server/src/auth/auth.service.ts
async requestResetPassword(request: IResetPasswordRequest, languageCode: LanguagesEnum, originUrl?: string): Promise<boolean | BadRequestException>
async requestPassword(request: FindOptionsWhere<User>, languageCode: LanguagesEnum, originUrl?: string): Promise<boolean | BadRequestException>
async resetPassword(request: IChangePasswordRequest)
async verifyEmail(token: string): Promise<void>
async resendVerificationMail(user: User, languageCode: LanguagesEnum)
```

## Recipe 5 新增一个受保护端点（注解 + 缓存影响 + 审校清单）
- **业务目标**：新增端点具备租户一致性检查与权限点判权，且不落入「漏注解即放行」。
- **调用顺序**：
  1. 在 contracts 的 `PermissionsEnum` 新增权限点（不要写裸字符串，判权是字符串比对）。
  2. 若预置角色应默认获得，则加入 `DEFAULT_ROLE_PERMISSIONS`；否则需靠 `POST /api/role-permissions/sync-defaults` 增量补齐。
  3. 挂守卫：`@UseGuards(TenantPermissionGuard, PermissionGuard)` + `@Permissions(PermissionsEnum.XXX)`（方法级覆盖类级）；角色白名单则 `@UseGuards(TenantPermissionGuard, RoleGuard)` + `@Roles(RolesEnum.SUPER_ADMIN)`。
  4. 如需 API Key / Client Secret 访问：追加 `ApiKeyOrClientSecretAuthGuard`；`ENTERPRISE_XPERT` / `USER_CONVERSATION` 绑定还需 `@AllowClientSecretBindings(...)` 显式声明，否则 403。
  5. 审校清单：`@Public()` 只跳过认证不跳过判权，不能替代 `@Permissions`；补一条元数据断言 spec（`Reflect.getMetadata(PERMISSIONS_METADATA, handler)`）。
- **事务边界**：判权在请求入口（守卫阶段）完成，不参与业务事务；命中的是缓存值或一次 `role_permission` 计数查询。
- **预期结果**：无权限者 403；有权限者首次请求回源一次并写入缓存，后续命中缓存。
- **错误处理**：上下文缺 `user`/`tenantId`/`roleId` → 拒绝并 403；**元数据为空 → 直接放行**（这是新增端点最大的风险点）；`@Roles` 通道绕开 `role_permission`，无法细粒度授予。
- **缓存影响（必读）**：新权限组合产生新键 `userPermissions:{tenantId}_{roleId}_{permissions}`，TTL 5 分钟；角色权限变更后旧值最长 5 分钟继续生效，且仓库内没有权限缓存失效调用点。
- **真实代码示例**：
```ts
// packages/server/src/user-organization/user-organization.controller.ts（仓内范式）
@UseGuards(PermissionGuard)
@Permissions(PermissionsEnum.ORG_USERS_EDIT, PermissionsEnum.ALL_ORG_EDIT)
@Delete(':id')
async delete(@Param('id', UUIDValidationPipe) id: string, ...)

// packages/server/src/shared/decorators/allowed-client-secret-bindings.decorator.ts
export const AllowClientSecretBindings = (...bindings: SecretTokenBindingType[]) =>
  SetMetadata(ALLOWED_CLIENT_SECRET_BINDINGS_METADATA, bindings)
```

## Recipe 6 第三方登录与 SSO 身份绑定
- **业务目标**：用户经社交 provider 或 SSO 登录；已登录用户把外部身份绑定到既有账号，或解绑。
- **调用顺序**：
  1. 社交登录：`GET /api/auth/<provider>` → 回调 `GET /api/auth/<provider>/callback` → 回调内签发令牌（可用 provider：github/google/facebook/linkedin/twitter/auth0/feishu；keycloak/microsoft/dingtalk 策略存在但未注册，无路由）。
  2. SSO 发现：`GET /api/auth/sso/providers`（`@Public()`）→ 返回当前租户可用 provider 列表。
  3. 绑定挑战：`GET /api/auth/sso/bind/challenge?ticket=`（`@Public()`）；当前登录用户确认用 `GET /api/auth/sso/bind/current-user/challenge?ticket=`（需登录）。
  4. 完成绑定：`POST /api/auth/sso/bind/complete`（`@Public()`，body `{ ticket, userName, password }`）、`POST /api/auth/sso/bind/current-user/complete`（需登录）、`POST /api/auth/sso/bind/register`（`@Public()`，注册并绑定，支持 `verified_email_signup` 流程）。
  5. 账号绑定查询/解绑：`GET /api/account-binding/me/:provider`、`DELETE /api/account-binding/me/:provider`（均需登录）。
- **事务边界**：绑定挑战存于 Redis（前缀 `auth:sso:bind:challenge:`，TTL 600 秒，消费为原子取删）；身份绑定在数据库事务内处理双唯一索引冲突（`(tenant,provider,subject)` 与 `(tenant,provider,user)`）。
- **预期结果**：`external_identity_binding` 新增或更新一行；成功响应统一为 `{ location: '/sign-in/success?jwt=...&refreshToken=...&userId=...' }`；解绑成功 204。
- **错误处理**：ticket 过期 → 400 `'SSO binding session has expired. Please sign in again.'`；账号或口令错误 → 401 `'Incorrect account or password.'`；身份已被占用 → 409；Redis 不支持原子取删 → 500（Redis 是 SSO 绑定硬依赖）。
- **真实代码示例**：
```ts
// packages/server/src/auth/sso/auth-sso.controller.ts
@Public() @Get('providers')            async getProviders(@Req() request: Request)
@Public() @Get('bind/challenge')       async getBindChallenge(@Query('ticket') ticket?: string)
@Public() @Post('bind/complete')       async completeBinding(@Body() body: { ticket?: string; userName?: string; password?: string })
@Post('bind/current-user/complete')    async completeCurrentUserBinding(@Body() body: { ticket?: string })
@Public() @Post('bind/register')       async registerAndCompleteBinding(@Body() body: {...})

// packages/server/src/account-binding/account-binding.service.ts
async bindUser(input: BindUserInput): Promise<ExternalIdentityBinding>
async resolveUser(input: ResolveUserInput): Promise<User | null>
async unbindUser(input: UnbindUserInput): Promise<void>
```

## Recipe 7 排障：撤销权限后仍可访问 / 邀请邮件收不到
- **业务目标**：把两类高频工单定位到既知已知坑，而不是重新怀疑整条鉴权链。
- **调用顺序（排查路径）**：
  1. 撤权后仍可访问：先确认是否仍在用旧 access token（权限快照写在 token 内，有效期内的旧权限继续生效）→ 再确认是否命中 5 分钟判权缓存（含负缓存）→ 再核对目标控制器是否确实挂了 `@Permissions`/`PermissionGuard`（元数据为空即放行）→ 最后检查是否走了 `TenantPermissionGuard` 的 `SUPER_ADMIN` 旁路或 `OrganizationPermissionGuard` 的组织旧列判定。
  2. 邀请邮件收不到：确认是否被创建侧静默忽略（目标邮箱已是本租户用户，或存在同租户未过期的 `INVITED` 邀请 → 计入 `ignored`）→ 检查是否撞 `invite.email` 全局唯一约束（跨租户同邮箱）→ 检查邀请类型（EMPLOYEE 发信分支已注释）与「组织联系人邀请」路径（其邮件发送整段已注释，邀请只在库里落地）→ 最后查 SMTP（`request-password` 在 SMTP 故障时仍返回成功）。
- **事务边界**：排障本身不写数据。若确认为缓存导致，等待 TTL（≤5 分钟）或清理 `userPermissions:*` 键（仓库内无自动失效调用点）。
- **预期结果**：结论收敛到四类之一：token 内权限快照 / 5 分钟判权缓存 / 注解缺失放行 / 邮件侧未发送或被去重。
- **错误处理**：需要「立刻失效所有已签发令牌」时只能轮换 `JWT_SECRET`（会同时使激活中的出站 actor token 失效）或逐用户重置密码；无 logout 端点、无 JWT 撤销表。
- **真实代码示例**：
```ts

async createOrganizationContactInvite(inviteInput: ICreateOrganizationContactInviteInput): Promise<Invite>
// 判权缓存键（角色与权限组合参与哈希）：
// userPermissions:{tenantId}_{roleId}_{permissions}，TTL 5 分钟
```
