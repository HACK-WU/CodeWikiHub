## 三、运行方式

`server-ai` 的 jest 配置：`preset: '../../jest.preset.js'`、`testEnvironment: 'node'`、TS 走 `ts-jest`（`tsconfig.spec.json`）、JS/MJS 走 `babel-jest`；`moduleNameMapper` 把 `@xpert-ai/server-core`、`@xpert-ai/contracts`、`@xpert-ai/plugin-sdk` 直指源码目录（**无需先构建依赖包**）；**无全局 setup/setupFiles**，fixture 各 spec 自带。

```bash
# 1) 单文件 / 多文件（本域全部 spec 都用 server-ai 配置）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/mcp-publication/mcp-publication.service.spec.ts \
                   packages/server-ai/src/xpert-toolset/xpert-toolset.service.spec.ts

# 2) 按目录整批
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --testPathPattern 'src/(xpert-toolset|xpert-tool|mcp-publication|agent-plugin)/'

# 3) 按用例名过滤（-t）——适合单条断言级复现
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/mcp-publication/mcp-task.service.spec.ts \
  -t 'idempot'

# 4) Nx 方式（项目名 server-ai 已核实）
corepack pnpm exec nx run server-ai:test --runInBand \
  --testPathPattern 'src/mcp-publication/'
```

注意：`mcp` 模块 0 spec，任何"跑 MCP 协议端点"的期望都要落到 `mcp-publication` 的协议 spec 上；本域**不涉及 `packages/server/jest.config.ts`**（该配置属 server 包）。

章节来源：[jest.config.ts](file://packages/server-ai/jest.config.ts)（关键符号：preset / transform / moduleNameMapper），[project.json](file://packages/server-ai/project.json)（关键符号：server-ai.targets.test）

## 四、断言与 mock 风格

- **纯手工构造 + 全 mock 为绝对主流**：服务类 spec 直接 `new XxxService(fakeRepo, fakeBus, ...)` 或以 `Test.createTestingModule({ providers: [...] }).compile()` 注入 `jest.fn()`，`getRepositoryToken()` 提供假仓库；无 `pg-mem`、无内存 PG 替身。
- **控制器 spec 直接 `new Controller(...)` 后 `controller.x.call(controller, input)`**：`mcp-publication-management.controller.spec.ts` 即此风格（断言 `publications.create` 收到原样入参、`connection-info` 用可信 baseUrl 而非请求 Host）。
- **环境开关断言**：`environment.mcpOAuthEnabled` 在 `beforeEach` 置 `true`、`afterEach` 还原，专门覆盖"OSS 发行版拒绝 OAuth"分支；`process.env.XPERT_MCP_STDIO_RUNTIME_ENABLED` 同理（先 `delete` 断言 fail-closed，再置 `'true'` 断言审计事件）。
- **结构断言替代集成**：`mcp-module-wiring.spec.ts` 用 `Reflect.getMetadata(MODULE_METADATA.IMPORTS, …)` 断言 `RedisModule` 在 `imports` 里、用 `design:paramtypes` 断言 `McpConsumerCapabilitiesService` 依赖 `ToolRuntimeService`—这是**编译期装配契约**，不代表运行时真的连上了 Redis。
- **假定时器驱动生命周期**：stdio 审计 spec 用 `jest.useFakeTimers()` + `advanceTimersByTimeAsync` 断言 idle/`max-lifetime` 超时关闭与 `closeReason`。
- **真 HTTP（进程内）**：`mcp-files.controller.spec.ts` 起真实 Nest app（`app.listen(0)` + `fetch`），是少数"真网络栈"用例，但仍是同进程、无外部服务。
- **data-driven**：协议 spec 用递增请求号（第 3 参）+ `request(...)` 辅助函数铺开方法矩阵；`protocol.spec.ts` 里 `at least 40+` 个 `it` 级别的协议分支（文件 59.8KB）。

章节来源：[mcp-publication-management.controller.spec.ts](file://packages/server-ai/src/mcp-publication/mcp-publication-management.controller.spec.ts)（关键符号：connectionInfo / environment.mcpOAuthEnabled），[mcp-module-wiring.spec.ts](file://packages/server-ai/src/mcp-publication/mcp-module-wiring.spec.ts)（关键符号：MODULE_METADATA / design:paramtypes），[mcp-stdio-runtime.audit.spec.ts](file://packages/server-ai/src/xpert-toolset/provider/mcp/mcp-stdio-runtime.audit.spec.ts)（关键符号：prepareServer / closeClient）

## 六、缺口

- **MCP 协议端到端缺失**：`mcp` 模块 0 spec，`/mcp/sse`、`/mcp/messages` 无任何断言；且该模块**未被注册**（见 05 第七节），所以连"端到端"的宿主接法都还不存在。
- **stdio 运行时无进程级覆盖**：`mcp-stdio-runner.js`（142 行，含 `detached` 进程组、SIGTERM→3s SIGKILL、startup-timeout、max-lifetime、stdin close 终止）**没有对应 spec**；host 侧只覆盖到"准备/审计/超时关闭"，`runnerPid`/`childPid` 解析（`CHILD_PID_MARKER`）与僵尸进程回收未验证。
- **发布审核流覆盖偏弱**：`reviewStatus='required'` 的"审核后转 current" 路径没有独立 spec（`enable` 只断言拒绝分支）；`markPublicationCapabilitiesCurrent`、`replaceCapabilitiesWithCatalog` 的 catalog 变更分类（新增/删除/hash 变化）在协议 spec 里被 mock 掉，真库上的唯一索引冲突（`publicName` 重名）无集成用例。
- **准入矩阵无守卫级断言**：`ToolsetGuard`、`WorkspaceAuthoringGuard`、`RoleGuard+@Roles(SUPER_ADMIN)`、`McpRuntimeController.assertSuperAdmin` 都**没有 spec 文件**（`xpert-toolset/guards/*.spec.ts` 不存在）。
- **`xpert-toolset.controller.ts` 无控制器 spec**：18 个端点（含 `@Sse` 流）无逐条用例，前端契约只能靠 `xpert-toolset.service.spec.ts` 间接保障。
- **`agent-plugin` 控制器 HTTP 覆盖不一致**：`runtime-resource.controller.spec.ts`、`agent-plugin-maintenance.controller.spec.ts`、`default-agent-plugins.controller.spec.ts` 有；**`agent-plugin.controller.ts`（12 端点，含 git/zip 导入与 bindings）无同名 spec**，仅有前端侧 `agent-plugins.component.spec.ts` 断言它调了哪些 URL。

## 七、可执行性结论

判定：**✅ 可跑（本报告不实跑，只给命令与判据）**。判据：

1. 72/73 个 spec（除 integration 一份）**不连任何外部服务**：Repository/QueryBuilder/Bull/Redis/metrics 全为 mock，可直接用第三节命令 1/2 本地执行；
2. 唯一的真库用例 `package-maintenance.integration.spec.ts` **默认 `describe.skip`**，只有注入 `AGENT_PLUGIN_TEST_DATABASE_URL` 才解锁，且只碰自带 schema 与临时目录，不会污染平台库；
3. `moduleNameMapper` 已把 `@xpert-ai/server-core`/`contracts`/`plugin-sdk` 指到源码，**本域测试不依赖先构建 workspace 包**；但反过来说，`@modelcontextprotocol/*` 等第三方依赖需要 `node_modules` 就位（`transformIgnorePatterns` 已为若干 ESM 包放行）；
4. 依赖环境变量的用例（`mcpOAuthEnabled`、`XPERT_MCP_STDIO_RUNTIME_ENABLED`、`NODE_ENV`）都在 spec 内自设并还原，**不是环境前置**；
5. 仓库内**未发现本域的 known-fail / skip 白名单**，所有 `skip` 均为条件开关；`mcp` 模块 0 spec 属覆盖缺口而非执行失败。
