## 工具集 CRUD 与类型
HTTP 入口 `XpertToolsetController extends CrudController<XpertToolset>`：`GET /` 与 `GET by-workspace/:workspaceId` 都经 `service.afterLoad()` 后再包成 `ToolsetPublicDTO`（`afterLoad` 负责内置 tag 回填 + `hydrateBuiltinToolSchemas` 用 provider 最新 schema 覆盖工具）；`GET :toolsetId/tools` 以 `relations: ['tools']` 取子工具；`GET :id/credentials` 是唯一凭据出口，`@UseGuards(ToolsetGuard)` 前置；`GET :id/avatar` 与 `GET builtin-provider/:name/icon` 走 `@Public()`（前者用 `toolset:avatar:${tenantId}:${id}` 缓存 5 分钟，MCP 类别回落内置 SVG）。类型枚举以契约为准：`XpertToolsetCategoryEnum = builtin | api | mcp | workflow`（`workflow` 标 `@deprecated`）；实体列 `category` 额外允许 `'command'`（`varchar(10)`），`schema`/`schemaType` 承载 OpenAPI 原文（`openapi_json | openapi_yaml`）。工具侧 `xpert_tool` 以 `@ManyToOne(toolset, { onDelete: 'CASCADE' })` + 冗余 `toolsetId` 列关联，`enabled` 已标 `@deprecated use disabled`。

## 工具集 provider 体系
`provider/index.ts` 导出四件实现，各自负责「工具发现 + schema 生成」：
- **builtin**：`BUILTIN_TOOLSET_REPOSITORY` 是静态注册表（Planning、Tavily、SearchAPI、Email、Bing、DingTalk、Slack、Discord、Serper），`createBuiltinToolset(provider, toolset, params)` 命中即 `new providerTypeClass(...)`；**未命中时回落 `CreateToolsetCommand` 由平台插件提供实现**，仍失败才抛 `ToolProviderNotFoundError`。`XpertToolsetService.createBuiltinToolset` 额外注入 `env`（`EnvStateQuery`）与 `modelRuntime`（`agentMiddlewareRuntime.createScopedApi({tenantId, organizationId})`），并先跑 `toolproviderController.validateCredentials(entity.credentials)`。
- **openapi**：`OpenAPIToolset extends BaseToolset<OpenAPITool>`，构造时把 `toolset.tools` 过滤（`isEnableTool`）后逐条生成动态子类（`static lc_name() => item.name`）。schema 生成走两条端点：`POST provider/openapi/remote`（`GetOpenAPIRemoteSchemaQuery` 拉远端）、`POST provider/openapi/schema`（`ParserOpenAPISchemaCommand` 解析文本）。
- **odata**：`ODataToolset` 同构，配套 `POST provider/odata/remote`（`GetODataRemoteMetadataQuery`）与 `POST provider/odata/schema`（`ParserODataSchemaCommand`）。
- **mcp**：不生成 schema，而是**连远端探测**——`POST provider/mcp/tools` 标 `@Sse()`（注释逐字：「@Post @Sse There is a priority order.」），body 为 `Partial<IXpertToolset>`，内部派 `MCPToolsBySchemaCommand` → `MCPToolsBySchemaHandler` 建客户端 `getTools()` → 返回 `{ tools, logs }`；流用 `keepAlive(30000)` + `takeUntilClose(res)` 保活。plugin-managed 工具集在探测前会强制回库校验 `pluginName`/`componentKey` 一致（`resolveToolset`），否则 400。
- **测试链路**：`POST /xpert-toolset/provider/openapi/test` 直接派 `TestOpenAPICommand`；`POST /xpert-tool/test` 走 `XpertToolService.testTool` → `ToolInvokeCommand`。
章节来源：[provider/builtin/index.ts](file://packages/server-ai/src/xpert-toolset/provider/builtin/index.ts)（关键符号：createBuiltinToolset）、[openapi-toolset.ts](file://packages/server-ai/src/xpert-toolset/provider/openapi/openapi-toolset.ts)（关键符号：OpenAPIToolset.getTools）、[xpert-toolset.service.ts](file://packages/server-ai/src/xpert-toolset/xpert-toolset.service.ts)（关键符号：XpertToolsetService.createBuiltinToolset）、[mcp-tools-schema.handler.ts](file://packages/server-ai/src/xpert-toolset/commands/handlers/mcp-tools-schema.handler.ts)（关键符号：MCPToolsBySchemaHandler.execute）

## 工具执行面 tool-runtime
`ToolRuntimeService` 是唯一执行出口，被三处调用：`ToolInvokeHandler`（HTTP 测试与 API 调用）、Agent 运行时（`subgraph.handler` 装配后由 LangChain 直接调工具）、发布运行时（MCP 发布侧经 `tool-runtime` 执行远端能力）。
- **寻址**：`loadToolsets({principal, toolsetIds, toolsetSnapshots?, ...})` 先 `resolveToolsets`（`persistedToolsetWhere` + `resolveToolRuntimeScope` 约束 workspace），空列表直接返回 `[]`；`executeTool({toolsetId, toolName, arguments, executionId, requestId})` 先 `loadToolsets` 取回单个 toolset，找不到抛 `ToolNotFoundError`，再组装 `ToolExecutionContext`。
- **环境边界**：`ToolRuntimeEnvironment` 的注释逐字写明宿主所有权——`mcpRuntime?: McpPublicationRuntimeConfiguration` 是「Validated Publication configuration supplied by the host, never tool arguments.」，`workspaceDataScope` 是「Persisted Xpert storage policy; derived catalog fields are never accepted from callers.」，`toolsetSnapshots` 是「Trusted API preview snapshots. Persisted Agent and MCP execution must not use this escape hatch.」。
- **能力面**：`describeCapabilities` 从 `McpCapabilityCatalog` 读 `enabled: true` 的 descriptor；`executeMcpCapability`/`executeMcpResource`/`executeMcpPrompt`/`completeMcpCapability` 统一走 `withCapabilityToolset`：`MCPToolset` 直连 `callMcpTool`/`readMcpResource`/`getMcpPrompt`/`completeMcpCapability`，其它 provider 经 `requireCapabilityProvider(toolset).getMcpCapabilityDefinitions()` 取声明实现（`toolset.ts` 的 `_BaseToolset` 提供 `initTools`/`getTool`/`getVariables`/`close` 契约）。
- **用量与错误**：`loadToolsets` 在有 `executionId` 时用 `createExecutionModelUsageRecorder` + `XpertAgentExecutionRecordUsageCommand` 记账；`ToolInvokeHandler` 捕获 `error.name === 'ToolException'` 转成 `ToolInvokeError`（注释逐字：「The MCP adapter identifies tool failures by name but does not export its error class.」）。
章节来源：[tool-runtime.service.ts](file://packages/server-ai/src/tool-runtime/tool-runtime.service.ts)（关键符号：ToolRuntimeService.executeTool）、[tool-invoke.handler.ts](file://packages/server-ai/src/xpert-tool/commands/handlers/tool-invoke.handler.ts)（关键符号：ToolInvokeHandler.execute）、[toolset.ts](file://packages/server-ai/src/shared/tools/toolset.ts)（关键符号：_BaseToolset.initTools）

## MCP 客户端
客户端实现全在 `xpert-toolset/provider/mcp/`，与 `mcp-consumer/**` 组合成两层：**传输层**（`createMCPClient`/`createProMCPClient`）与**协议层**（`McpConsumer`）。
- **传输选择**：`createMCPClient` 遍历 `schema.servers ?? schema.mcpServers`，按 `server.type` 或字段特征分流：`http` 走 `transport:'http'` + `resolveRemoteHeaders` + `resolveMcpConsumerAuthProvider`（支持 oauth/connector 认证提供者）；`sse`（或无 type 但有 url）走 `useNodeEventSource: true`，且明确禁止 oauth/connector（「MCP OAuth requires Streamable HTTP」）；`stdio`（或无 type 但有 command）先 `mcpStdioRuntimeManager.assertInitScriptsAllowed`，再按需 `runScript(initScripts)`（带 10 分钟超时）并派发 `ON_CHAT_EVENT` 进度。
- **stdio 运行时**：`mcp-stdio-runtime.ts` 定义 `McpRuntimeStatus = starting|running|closing|closed|failed`、`McpRuntimeOrigin = agent-toolset|mcp-app-host`、`McpStdioRuntimeHandle`（含 `runnerPid`/`childPid`/`stderrTail`）与单例 `mcpStdioRuntimeManager`（`list`/`touchClient`/`isClientRuntimeUsable`/`closeRuntime(runtimeId, reason)`/`killByFilter(filter, reason)`）；策略由 `TMcpStdioRuntimePolicy` 收敛（`provider`、`startupTimeoutMs`、`idleTimeoutMs`、`maxLifetimeMs`、`allowedCommands`），服务端会按平台与租户安全设置收紧。
- **协议层能力**：`MCPToolset` 持有 `client: MultiServerMCPClient` + `consumer: McpConsumer` + `destroy`；`initTools()` 产出 `DynamicStructuredTool`（全部 `verboseParsingErrors = true`），`wrapMCPTool` 每次调用都 `mcpStdioRuntimeManager.touchClient(client)` 并按结果注册 MCP App 实例（`registerMcpAppInstance` + `waitForMcpAppInstancePersistence` + `ON_TOOL_MESSAGE`）；长任务走 `callMcpTaskTool`（`timeout`/`tasks.start`/`wait(onStatus)`/`result`），elicitation 经 `input.request` 转 `ToolInputRequest`（仅接受 `elicitation/create`，`mode` 只能 `url|form`）；`close()` 先 detach App 实例，再 `forceCloseMCPClientTransports` 强关 SSE，最后 `destroy?.()`。
- **App 兼容层**：`app-support.ts`/`meta-artifact-bridge.ts` 是 `_meta` 桥接，按 `mcp/README.md` 注释属临时兼容层；`pro.ts` 仅切换 Pro 客户端实现；`mcp-tool-filter.ts` 负责按 `toolset.tools` 与 `options` 过滤远端工具。
章节来源：[types.ts](file://packages/server-ai/src/xpert-toolset/provider/mcp/types.ts)（关键符号：createMCPClient）、[mcp-stdio-runtime.ts](file://packages/server-ai/src/xpert-toolset/provider/mcp/mcp-stdio-runtime.ts)（关键符号：McpStdioRuntimeManager.closeRuntime）、[mcp-toolset.ts](file://packages/server-ai/src/xpert-toolset/provider/mcp/mcp-toolset.ts)（关键符号：MCPToolset.callMcpTaskTool）

## MCP 服务端封装
`packages/server-ai/src/mcp/**` 是通用 **MCP Server** 封装，不持久化任何表：
- **模块**：`MCPModule.register(options)`/`registerAsync(options)` 返回 `global: true` 动态模块，providers 由 `useFactory` 手工实例化 `new MCPService(options, discoveryService, metadataScanner, reflector)`，exports 仅 `MCPService`。**全仓搜索 `MCPModule` 只命中 `mcp.module.ts` 自身**——当前无装配点（`[推测]` 后果：`mcp/sse` 与 `mcp/messages` 未挂进任何运行中的应用）。
- **协议装配**：`onModuleInit` 先 `scanAndRegisterProviders()`（遍历 `DiscoveryService.getProviders()`，用 `MetadataScanner.getAllFilteredMethodNames` + `Reflector` 读 `MetadataKey.MCP_RESOURCE|MCP_TOOL|MCP_PROMPT`），随后构造 `NestSSEAdapter`（默认端点 `mcp/messages`、`mcp/sse`），最后按 `options.enableStdio` 决定是否挂 `StdioServerTransport`。
- **注册语义**：resource 用 `` new ResourceTemplate(`${name}://{id}`) ``；tool 的参数表经 `convertParametersToZod` 转 zod（`string|number|boolean|array|object`，已是 zod 则直用，兜底 `z.any()`）；prompt 支持方法返回动态参数再合并。
- **会话与端点**：`BaseMCPController` 类级 `@Public()` + `@Controller()`（空前缀），`@Get('mcp/sse')` → `handleSSEConnection`（每个连接新建 transport 并 `server.connect(transport)`），`@Post('mcp/messages')` → `handleMessages`（转发给 adapter）。全局前缀 `api` 意味着实际路径为 `/api/mcp/sse` 与 `/api/mcp/messages`。
章节来源：[mcp.service.ts](file://packages/server-ai/src/mcp/mcp.service.ts)（关键符号：MCPService.scanAndRegisterProviders）、[base-mcp.controller.ts](file://packages/server-ai/src/mcp/controllers/base-mcp.controller.ts)（关键符号：BaseMCPController.sseHandler）

## MCP 发布链
链路上每一步都有独立的表与准入：**草稿 → 能力快照 → 审核 → 凭据 → 调用审计 → 长任务**。
1. **草稿**：`McpPublicationManagementController`（类级 `RoleGuard` + `@Roles(SUPER_ADMIN)` + 严格 `ValidationPipe`）`POST mcp-publications` → `McpPublicationService.create`：`assertNameAndSlug` → `assertSlugAvailable` → 落 `status:'draft'`、`authMethods`（默认 `['api_key']`）、`runtime: parseMcpRuntimeConfiguration(input.runtime)`、`protocolVersion: MCP_PROTOCOL_VERSION`、`reviewStatus:'current'`（注释契约：`Host-owned execution configuration. Tool arguments cannot override these bindings.`）。
2. **能力快照**：`McpCapabilityCatalogService.discoverAndReplaceMcpToolset(toolsetId)` 发现并整体替换 catalog（≤1000 条，`bindCapability` 绑定 toolset 身份，`assertValidMcpCapabilityDescriptor` 校验，`hashMcpCapabilityDescriptor` 生成 `char(64)` 哈希）；绑定侧 `PUT mcp-publications/:id/capabilities` → `McpPublicationService.replaceCapabilities`（事务内 delete + save + `markPublicationCapabilitiesCurrent`），`replaceCapabilitiesWithCatalog` 则是「catalog 快照 + bindings」原子替换版本。
3. **审核**：`resolveRuntimeCapabilities` 逐条比对 `binding.descriptorHash === item.descriptorHash`；不同则 `compareMcpCapabilityDescriptors(binding.descriptorSnapshot, item.descriptor)`，**只有 breaking 变更才把 `publication.reviewStatus` 置 `'required'` 并记 `reviewReason`**（注释：`Required to classify descriptor changes instead of treating every hash change as breaking.`）；`assertCanEnable` 在 enable 时拒绝 `reviewStatus === 'required'`。
4. **凭据**：`McpApiKeyService`（`POST mcp-publications/:id/api-keys`、`list`、`revoke`、`rotate`）与 `McpOAuthService`（`GET|PUT mcp-publications/:id/oauth-policy`、`.../oauth-policy/test`）。OAuth 三个入口都先 `assertMcpOAuthEnabled()`（Pro 特性，非 Pro 抛 `McpOAuthProOnly`）。组织级共享发布另走 `McpPublicationAccessService`（`enable`/`disable`/`isEnabled`/`assertEnabled`，唯一键 `(publicationId, organizationId)`，写后 `subscriptions.publishAccessInvalidated`）。
5. **调用与审计**：`McpPublicationController` 类级 `@Public()` + `@Controller('mcp/p')` + `@All(':slug')` → `McpPublicationRuntimeService.handle(slug, req, res, body)`：`findActiveBySlug` → 认证/授权/限流 → 每个请求 `createMcpHandler(() => this.createServer(...), { legacy: 'stateless', responseMode: 'auto', bus: this.subscriptions.bus(publication.id) })` + `toNodeHandler`，并在 `runWithCapturedRequestContext` 内只恢复本次调用验证过的用户（注释：文件/产物能力要读 `RequestContext`，服务账号不得继承管理员）。能力注册由 `mcp-runtime-registration.ts` 的 `registerTool`/`registerResource`/`registerResourceTemplate`/`registerPrompt`/`registerApp` 完成。审计由 `McpInvocationAuditService.start` → `succeeded`/`failed` 两段写（`requestId` 唯一，`argumentSummary` 只存 key 列表与字节数，且列 `select: false`），`failed` 时 `ForbiddenException` 记 `denied`、其余记 `failed`。清单/测试端点：`GET mcp-publications/:id/audit`、`POST mcp-publications/:id/test`（返回 `reply/rateLimit/review/policy` 检查项）、`GET mcp-publications/:id/connection-info`（`transport:'streamable-http'` + `/api/mcp/p/{slug}`）。文件能力单独走 `McpFilesController`（`@Public` + `McpFilesGuard`，`POST|GET mcp/p/:slug/files`）。
6. **长任务**：`McpTaskService.create` 先算 `idempotencyKey = hashText(publication\0subjectType\0subjectId\0requestId\0rpcRequestId 类型\0值\0publicName)` 与 `inputHash = hashJson(arguments)`，`findByIdempotency` 命中即 `assertIdempotentReplay`（比对 subject 与 inputHash，不一致抛 `-32602`）；未命中则校验队列健康度后落 `status:'working'`，再用 try/catch 兜并发竞争（catch 里重查一次）。`get` 对过期未终态任务补写 `MCP_TASK_EXPIRED`，`update` 只接受 `status === 'input_required'` 的补充输入，`cancel` 会先 `managedQueue.cancel({jobId, executionPool:'default'})`。执行由 `McpTaskProcessor`（`@PluginJobProcessor({ pluginName:'@xpert-ai/platform', queueName:'mcp-publication', jobName:'execute-tool', concurrency:4 })`）消费 → `process(payload)`。审批字段 `approvalGranted` 注释逐字：「Server-obtained approval for this queued invocation; never supplied by tool arguments.」。

## 热点路径
1. **`McpPublicationRuntimeService.handle`**：每个 MCP 请求都要 `findActiveBySlug` → 认证/授权/限流 → `createMcpHandler` + `toNodeHandler` + `createServer`，无跨请求复用（`legacy: 'stateless'`），是发布域最重的单请求路径。
2. **`resolveRuntimeCapabilities`**：读路径逐条比对 catalog 与 binding，并对 breaking 变更回写 `reviewStatus`，随发布能力数线性增长。
3. **`McpCapabilityCatalogService.replacePreparedToolsetCapabilities`**：事务内 delete + save 全量 catalog，且每次替换前先 `bindingRepository.find({ where: { toolsetId } })` 找受影响发布并逐个发事件。
4. **`ToolRuntimeService.loadToolsets`**：每次执行/装配都要按 toolsetIds 查库 + 解析 scope + 按需建连；MCP stdio 连接成本尤高（受 `startupTimeoutMs`/`idleTimeoutMs` 约束）。
5. **`MCPToolset.wrapMCPTool` 的每次工具调用**：`touchClient` + App 实例注册 + `waitForMcpAppInstancePersistence`（仅当返回 App 数据时才 await），是工具调用的固定开销。
6. **`XpertToolsetService.afterLoad`**：列表读路径为每个内置 provider 再查一次 `ListBuiltinToolsQuery` 并覆盖工具 schema（每次列表都是 N 次批量查询）。
7. **Agent 插件 `resolve`/`catalog`**：动态资源解析涉及 binding 可见性、connector 认证与 toolset 校验，且要在执行前完成。

## 技术债与 hack
1. **凭据加密被注释掉**：`XpertToolsetService.createBuiltinToolset` 内逐字保留 `// encrypt credentials` 与 `// credentials = tool_configuration.encrypt_tool_credentials(credentials)`，即当前 `credentials` 以明文 json 落库，仅靠 `@Exclude` + 守卫控制「不返回」。
2. **`ToolsetGuard` 只缓存允许结果且无失效通道**：命中即放行，5 分钟内被移出工作区/被转交的工具集仍可继续用凭据端点；缓存键含 tenant 与 userId，但**没有任何主动清除调用点**。
3. **`MCPModule` 未接线**：`global: true` 的动态模块全仓无装配点，`MCPService` 的 `mcp/sse`/`mcp/messages` 实际不可达（`[推测]`：该封装为插件/宿主二次集成预留）。
4. **`xpert-toolset` 模块吞邻域资产**：controllers 含 `mcp-consumer` 的两个控制器，forFeature 含 `mcp-publication`/`mcp-app-runtime`/`mcp-consumer`/`plugin-resource` 的表，`[推测]` 这是为了绕开循环依赖而把「谁提供 repository」集中在一处，代价是模块边界与子域边界不一致。
5. **`XpertToolsetService` 的遗留命令表**：`registerCommand`/`executeCommand` 与私有 `commands: Map` 均标 `@deprecated`，仍在类上保留。
6. **`xpert_tool.enabled` 与 `disabled` 双列并存**：`enabled` 标 `@deprecated use disabled`，两列都可空，判定工具可用性时需要同时考虑（`isEnableTool` 归一）。
7. **MCP `_meta` 桥接是临时层**：`meta-artifact-bridge.ts`/`app-support.ts` 属 `mcp/README.md` 描述的 temporary compatibility layer，上游暴露 `_meta` 后应删除。
8. **工具失败靠错误名识别**：`ToolInvokeHandler` 用 `error.name === 'ToolException'` 判定，注释逐字：「The MCP adapter identifies tool failures by name but does not export its error class.」——上游改类名即静默降级。
9. **`descriptorSnapshot` 的读路径副作用**：漂移审核发生在 `resolveRuntimeCapabilities`（读），也就是「不读就不审核」，`[推测]` 长期不访问的发布可能带着过期能力快照持 active 状态。
10. **`mcp_task.revision` 不是 `@VersionColumn`**：只是 `@Column({type:'int', default:0})`，并发状态推进依赖 `revision` 的读取-写入约定而非数据库 CAS 语义（`[推测]` 并发输入补充存在丢写窗口）。
11. **OAuth 属 Pro**：`assertMcpOAuthEnabled()` 非 Pro 直接 403，OAuth policy 的读写与测试三个端点全部门控，开源部署下该能力不可用。
12. **发布域无 `RouterModule`**：管理端点用 `@Controller()` 空前缀并自行携带 `mcp-publications`/`mcp-api-keys`/`mcp-capability-catalog` 等路径段，与运行时端点 `mcp/p` 同处 `mcp` 命名空间，路由全景需逐个控制器读装饰器。
13. **`xpert-toolset` 与 `xpert-tool` 无迁移文件**：五个模块中仅 `agent-plugin` 有 `migrations/*.sql`，其余表结构完全由实体驱动，`[推测]` 生产库的列变更依赖 TypeORM synchronize 或外部迁移工具。

## 设计维度分析
**声明式快照 vs 实时发现**：发布域刻意把「插件/工具集声明了什么」固化为 `mcp_capability_catalog`（含 `descriptorHash` + `descriptor`），把「发布承诺了什么」固化为 `mcp_publication_capability`（含 `descriptorSnapshot`），再在运行时读路径做二级比价。好处是能力变更可被**分类**（`compareMcpCapabilityDescriptors` 区分 breaking 与否）而不是一律当破坏性变更；代价是读路径承担审核副作用，且删掉源工具集后绑定仍保留（注释：`The concrete toolset identity is retained even if that toolset is later deleted.`），必须靠 catalog 缺失去关闸。
**凭据的「只写不回」边界**：三个层次同时作用——实体 `@Exclude({toPlainOnly:true})` 保证序列化不泄；`select: false` 保证默认查询不取列（`keyHash`/`encryptedSecret`/`introspectionClientSecretEncrypted`）；守卫保证端点级准入（`ToolsetGuard` 之于 `/credentials`，`RoleGuard`+SUPER_ADMIN 之于管理面）。反面是凭据以明文存储这一缺口（加密步骤仍为注释），因此该边界目前保护的是**回显**而非**存储**。
**两个 MCP 方向、两套技术栈的对称性**：客户端用 `MultiServerMCPClient` + `McpConsumer`（LangChain 适配），服务端用 `McpServer` + `createMcpHandler`（原生 SDK）。二者共享协议契约（`MCP_PROTOCOL_VERSION = '2026-07-28'`、`MCP_HTTP_CORS_REQUEST_HEADERS` 白名单），但**能力模型不同**：客户端以远端工具表为准（`filterMcpTools`），服务端以本域 descriptor 为准（`registerTool` 读 `descriptorSnapshot`）。`[推测]` 这种不对称是「发布先于标准」的历史结果，新增能力时应优先在 descriptor 侧建模。
**三种插件的统一落点 vs 分治准入**：平台插件、Agent 插件、MCP 发布最终都写 `XpertToolset`/`XpertTool`，但准入分治（平台插件走 `LOADED_PLUGINS` + 管理面、Agent 插件走 `requireResourceAdmin` + 组织 scope、MCP 发布走 SUPER_ADMIN + 组织准入表），并用 `options` 上的 `pluginManaged`/`runtimeSource` 标记来源。好处是执行面只需认一个类型；风险是**来源标记是 json 字段上的字符串约定**，任何绕过安装器直接建工具集的代码都会落进「无来源」灰区。

## 结论
实现上，本域把「能力」抽象成了一条可审计、可分类、可替换的流水线：远端/插件声明 → `mcp_capability_catalog`（带 `descriptorHash`）→ 发布绑定 `mcp_publication_capability`（带 `descriptorSnapshot` + `policy`）→ 运行时 `createServer` 注册 → 调用落 `mcp_invocation_audit` → 长任务落 `mcp_task`（`idempotencyKey` + `inputHash` 双保险）。执行侧则把信任边界钉在 `ToolRuntimeService` 的参数契约上——环境、存储策略与 Publication 配置一律由宿主提供，工具参数永远不能越权注入；stdio 运行时另有一层实例审计与 SUPER_ADMIN 停机阀。Agent 插件走的是「声明在包里、安装才落库」的路线，与平台插件的「bundle 已加载再投影」路线在 `PluginResourceInstallerService` 交汇。
需要重点防守四处：① `credentials` 明文落库 + 5 分钟守卫缓存构成的撤权窗口；② `descriptorSnapshot` 的漂移只在读路径触发；③ `XpertToolsetModule` 吞噬邻域资产带来的装配耦合；④ `MCPModule` 未接线与 `@deprecated` 命令表/双列 `enabled` 等历史残留。新增工具集能力时应继续走「provider 实现 + descriptor 声明 + catalog 刷新 + 绑定快照」的既有骨架，不要绕过 `ToolRuntimeService` 与安装器直接写 `xpert_toolset`。
