## D1 工具集 provider 化（四实现统一抽象）
- **分类**：架构设计
- **动机（避坑）**：现象——每种工具来源（内置、OpenAPI、OData、MCP）各建一套工具模型与执行分支，助手挂载、Agent 装配、MCP 发布各自按来源 switch；后果——执行面扩散成多条路径，新增来源要改所有下游，且「能力声明」无处收敛。
- **决策**：`provider/{builtin,openapi,odata,mcp}` 四实现统一承担「工具发现 + schema 生成」，落点统一为 `XpertToolset`/`XpertTool`，执行统一经 `ToolRuntimeService`（`loadToolsets`/`executeTool`），能力统一经 `_BaseToolset` 的 `initTools`/`getTool`/`getVariables`/`close` 契约暴露；服务端执行侧只用一个类型判断（`instanceof MCPToolset`）决定「直连」还是「走声明」。
- **背景约束**：`loadToolsets` 按 `category`+`type` 分派——`builtin → createBuiltinToolset`、`api + openapi → OpenAPIToolset`、`api + odata → ODataToolset`、`mcp → MCPToolset`，其它抛 `ToolProviderNotFoundError`；内置注册表未命中时回落 `CreateToolsetCommand`（由平台插件提供实现）；只有 `source === 'api'` 允许使用 `toolsetSnapshots` 快照通道。
- **被否决方案**：无（实现层未找到对「按来源分治多套执行面」的显式否决记录；这条边界是「统一落点 + 统一执行面」这一取舍的结果）。
- **重新评估触发条件**：新增第五类 provider（例如远程 A2A/HTTP 插件工具）时，须同时补齐 `provider/` 实现、`category` 分派、能力声明与 catalog 刷新四处，**不得**在 `ToolRuntimeService` 之外新开执行入口。
- **关联代码**：`file://packages/server-ai/src/xpert-toolset/provider/index.ts`、`file://packages/server-ai/src/tool-runtime/tool-runtime.service.ts`、`file://packages/server-ai/src/shared/tools/toolset.ts`
- **证据来源**：实现层 [02-实现.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/02-实现.md)「工具集 provider 体系」与「设计模式及落点」（策略 / 提供者注册表两行）；[03-数据流转.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/03-数据流转.md)「链路一」按 `category` 分派清单。

## D2 凭据脱敏的边界（按列分层）
- **分类**：安全合规
- **动机（避坑）**：现象——只靠 DTO 过滤（新增字段忘走 DTO 即泄漏）或只靠端点守卫（任何绕过端点的序列化、日志、导出都会带出凭据）；后果——凭据在回显面泄漏，且泄漏点随新功能扩散。
- **决策**：分两层且**按列不同**——① 序列化层：实体 `@Exclude({ toPlainOnly: true })` + 控制器 `TransformInterceptor`（`instanceToPlain`）保证出网即剔除；② 端点级准入：守卫保证 `GET /:id/credentials` 与发布管理面各自的门（`ToolsetGuard` / `RoleGuard` + `@Roles(SUPER_ADMIN)`）。**注意 `xpert_toolset.credentials` 没有列级 `select:false`**——默认查询会取列（`GET /:id/credentials` 正是靠此直接返回）；`select:false` 只用于 `mcp_api_key.keyHash`/`encryptedSecret`、`mcp_oauth_policy.introspectionClientSecretEncrypted`、`mcp_invocation_audit.argumentSummary`、`mcp_task` 的 payload 类列（`ToolsetGuard` 之于 `GET /:id/credentials`，`RoleGuard` + `@Roles(SUPER_ADMIN)` 之于发布管理面）。另配布尔位 `introspectionClientSecretConfigured`，让 UI 在不读密文的前提下判断「是否已配置」。
- **背景约束**：`xpert_toolset.credentials` **库内是明文 json**（`createBuiltinToolset` 里 `// encrypt credentials` 仍为注释），因此这一层保护的是**回显**而非**存储**；`mcp_api_key.keyHash`/`encryptedSecret` 与 `mcp_oauth_policy.introspectionClientSecretEncrypted` 才是「加密 + 隐藏」；`mcp_invocation_audit.argumentSummary`（只存 key 列表与字节数）与 `mcp_task` 的 payload 类列同为 `select:false`。
- **被否决方案**：无（未见对「只用 DTO 或不加隐藏列」的显式否决记录；三层各自对应一种已存在的泄漏路径）。
- **重新评估触发条件**：启用凭据加密、或新增任何凭据字段/导出面（CSV、事件、日志字段）时——须同步决定该字段落在三层中的哪几层，并复核 `ToolsetPublicDTO` 白名单。
- **关联代码**：`file://packages/server-ai/src/xpert-toolset/xpert-toolset.entity.ts`、`file://packages/server-ai/src/mcp-publication/entities/mcp-api-key.entity.ts`、`file://packages/server-ai/src/mcp-publication/entities/mcp-oauth-policy.entity.ts`、`file://packages/server-ai/src/xpert-toolset/guards/toolset.guard.ts`
- **证据来源**：实现层 [03-数据流转.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/03-数据流转.md)「建模边界：快照、台账与密钥材料」（三层脱敏）与「已知风险」1；[07-运维.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/07-运维.md)「密钥与凭据运维」表格逐行口径。

## D3 ToolsetGuard 的 5 分钟允许缓存
- **分类**：性能取舍
- **动机（避坑）**：现象——`GET /:id/credentials` 每个请求都要做 `createdById` 判定 + `workspaceService.canAccess` 查询；后果——凭据读端点成为高频 DB 放大点。反过来，若把拒绝结果也缓存或做永久缓存，则会出现「授权后被拒」与「撤权后仍可读凭据」两类错误。
- **决策**：只缓存**允许**结果——`cacheKey = userToolset_${tenantId}_${user.id}_${toolsetId}`，命中即直接返回；未命中才走 `createdById === user.id || workspaceService.canAccess(toolset.workspaceId, user.id)`，且仅当 `isAuthorized` 时 `cacheManager.set(..., 5 * 60 * 1000)`；拒绝路径**不写缓存**（每次穿透并每次抛 403 `Access denied`）。
- **背景约束**：**没有任何主动清除调用点**——缓存键含 tenant 与 userId，但 5 分钟内被移出工作区/被转交的工具集仍可继续读凭据，即撤权存在最长 5 分钟窗口；同时凭据本身库内明文，两者叠加构成主要风险面。
- **被否决方案**：无（未见对「缓存拒绝结果」或「不缓存」的显式否决记录）。
- **重新评估触发条件**：出现「权限回收必须立即生效」的合规要求，或需要给缓存加显式失效通道（成员移除/工作区变更事件）时——届时应改为「允许缓存 + 主动失效」或降为极短 TTL。
- **关联代码**：`file://packages/server-ai/src/xpert-toolset/guards/toolset.guard.ts`、`file://packages/server-ai/src/xpert-toolset/xpert-toolset.controller.ts`
- **证据来源**：实现层 [01-架构.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/01-架构.md)「关键不变量」1 与「技术债与 hack」2；[05-接口.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/05-接口.md)「鉴权与准入矩阵」`ToolsetGuard` 行。

## D4 MCP 客户端走 stdio 子进程 + 运行时审计
- **分类**：安全合规
- **动机（避坑）**：现象——允许用户配置的 `command` 直接在 API 进程内 spawn，且只留内存态句柄；后果——任意命令执行没有准入与上限，进程泄漏成黑盒，运维既不能定位 PID 也不能回收整个进程组。
- **决策**：stdio 走**两级子进程 + 策略钳制 + 持久审计 + 停机阀**——宿主 `spawn` runner（`mcp-stdio-runner.js`，spec 经 `XPERT_MCP_STDIO_RUNNER_SPEC` 传 base64 JSON），runner 再 `spawn` 真实 MCP server（`detached: true`、`shell: false`）；策略由 `TMcpStdioRuntimePolicy` 收敛（`provider`/`startupTimeoutMs`/`idleTimeoutMs`/`maxLifetimeMs`/`allowedCommands`）并由服务端按平台与租户安全设置收紧；生命周期经 `setAuditSink` 写 `mcp_runtime_instance`（`commandLabel` 内建脱敏、`commandHash` sha256、`policySnapshot` 白名单、`stderrTail` 16KB、`runnerPid`/`childPid`）；终止走 `POST operations/mcp-runtimes/:runtimeId/stop`（`admin-stop`）与 `/kill`（`admin-kill`），两者都先 `assertSuperAdmin()`。
- **背景约束**：`XPERT_MCP_STDIO_RUNTIME_ENABLED` **默认关闭、fail closed**（关闭时抛 `MCP stdio runtime is disabled. Set XPERT_MCP_STDIO_RUNTIME_ENABLED=true to allow stdio MCP servers.`）；`initScripts` 默认 `!environment.production`；生产环境必须命中 `XPERT_MCP_STDIO_ALLOWED_COMMANDS` 白名单；单租户并发默认 10；宿主重启时残留 `starting|running|closing` 由 `onApplicationBootstrap` 统一收尾为 `closed` + `host-restart-or-lost`。
- **被否决方案**：无（实现层未见对替代实现的显式否决记录）。`[推测]` 双层 runner 的动因是让真实 MCP server 落在独立进程组，从而用 `process.kill(-child.pid, SIGTERM)`（3 秒后补 SIGKILL）整组回收。
- **重新评估触发条件**：需要支持远程/共享 MCP 运行时（而非本机子进程）、或需放宽任一 `*_TIMEOUT_MS` 与命令白名单时——须同时复核审计字段与 kill 语义是否仍成立。
- **关联代码**：`file://packages/server-ai/src/xpert-toolset/provider/mcp/mcp-stdio-runtime.ts`、`file://packages/server-ai/src/xpert-toolset/provider/mcp/mcp-stdio-runner.js`、`file://packages/server-ai/src/xpert-toolset/mcp-runtime-audit.service.ts`、`file://packages/server-ai/src/xpert-toolset/mcp-runtime.controller.ts`
- **证据来源**：[07-运维.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/07-运维.md)「子进程 / stdio 运行时运维」「环境变量与门禁」；[04-模型.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/04-模型.md) `mcp_runtime_instance` 行与 `commandLabel`/`commandHash` 说明。

## D5 mcp 模块只做 SDK 封装、不持久化
- **分类**：架构设计
- **动机（避坑）**：现象——把「通用 MCP Server 封装」与「对外发布运行时」合成一个模块，会话状态（内存 transport Map）被当成可持久状态，发布域又需要 8 张表与 SUPER_ADMIN 准入；后果——权限口径与生命周期混在一起，且服务端封装无法被插件/宿主独立复用。
- **决策**：`mcp/**` 只做**通用 MCP Server SDK 封装**——`MCPModule.register/registerAsync` 返回 `global: true` 动态模块，`MCPService` 在 `onModuleInit` 用 `DiscoveryService` + `MetadataScanner` + `Reflector` 扫描带 `@Tool/@Resource/@Prompt` 的方法注册进 `McpServer`，端点仅 `mcp/sse` 与 `mcp/messages`；**0 实体、0 表**，会话只存 `NestSSEAdapter.activeTransports` 内存 Map。对外发布完全独立在 `mcp-publication/**`（8 表 + 管理面 SUPER_ADMIN + `@All('mcp/p/:slug')` 运行面）。
- **背景约束**：`MCPModule` 虽声明 `global: true`，但**全仓检索只命中 `mcp.module.ts` 自身**，即当前无装配点——`[推测]` 该封装为插件/宿主二次集成预留，`mcp/sse`/`mcp/messages` 在当前组装下未挂载。协议版本常量也不在 `mcp` 模块，而由发布域契约 `MCP_PROTOCOL_VERSION` 持有。
- **被否决方案**：无。
- **重新评估触发条件**：若宿主改为 `MCPModule.register(...)` 装配，则需同步确认全局 `api` 前缀与 `.well-known` exclude 列表的交互，并核对会话与鉴权口径（`@Public()` 类级）是否满足要求。
- **关联代码**：`file://packages/server-ai/src/mcp/mcp.module.ts`、`file://packages/server-ai/src/mcp/mcp.service.ts`、`file://packages/server-ai/src/mcp/controllers/base-mcp.controller.ts`

## D6 能力台账双表 + descriptorHash 分类
- **分类**：接口契约
- **动机（避坑）**：现象——只存一份能力表，把「工具集当前声明了什么」与「已发布承诺了什么」混为一体；后果——工具集改一个 schema 就静默改掉对外契约（无审核环节），或反过来一改就全量判为破坏性变更需人工逐个复核。
- **决策**：两级投影 + 指纹分类——`mcp_capability_catalog` 存「当前声明」（唯一 `(toolsetId, capabilityType, capabilityKey)`，事务内 delete + save 整体替换）；`mcp_publication_capability` 存「对外承诺」（唯一 `(publicationId, publicName)` 与 `(publicationId, toolsetId, capabilityType, capabilityKey)`，含 `descriptorSnapshot` + `descriptorHash char(64)`，**二者成对固化，不可只写哈希**）；运行时读路径 `resolveRuntimeCapabilities` 逐条比对哈希，不同则 `compareMcpCapabilityDescriptors(binding.descriptorSnapshot, item.descriptor)` 分类，**只有 breaking 变更**才置 `reviewStatus='required'` + `reviewReason`，并由 `assertCanEnable` 阻止上架。
- **背景约束**：唯一索引即幂等键（重复 discover/绑定在同一键上收敛为同一行）；`toolsetId` 两侧**故意不建外键**（注释 `intentionally not a FK so broken bindings stay diagnosable`），工具集删除后绑定仍在、执行期才失败；漂移审核发生在**读路径**，即「不读就不审核」；`replacePreparedToolsetCapabilities` 抢在事务内 replace，但 catalog 无 `@VersionColumn`，并发 discover 与绑定变更之间后写覆盖前写。
- **被否决方案**：把任何哈希变化一律当破坏性变更——被注释逐字否决：「Required to classify descriptor changes instead of treating every hash change as breaking.」
- **重新评估触发条件**：给 catalog 增加版本列或把漂移审核移出读路径时；以及需要「先审核后自动冻结对外契约」时——须同步改 `assertCanEnable` 与订阅通知（`publishCatalogChanged`）。

## D7 发布认证双模（API Key + OAuth policy）
- **分类**：安全合规
- **动机（避坑）**：现象——对外 MCP Server 只支持一种认证（或把两种混在同一个开关里）；后果——机器对机器场景要长期共享静态密钥，企业场景又无法接入既有 IdP，且「能签发」与「能校验」的口径容易分离。
- **决策**：`authMethods ⊆ {api_key, oauth}`（可并存，默认 `['api_key']`），两条链各自独立建模——API Key 走 `xpert_mcp_` 前缀 + ≥24 字符 + `keyPrefix` 命中 + `timingSafeEqual(sha256)`，落 `mcp_api_key`；OAuth 走与 publication **一对一唯一**的 `mcp_oauth_policy`（`issuer`/`audience`/`requiredScopes`/`subjectMapping`/`introspection*`），并暴露 `.well-known/oauth-protected-resource` 元数据。运行时由 `McpAuthenticationService.authenticate` 统一分流：`xpert_mcp_` 前缀走 Key，否则 `assertMcpOAuthEnabled()` 后走 OAuth；`enable` 时若 `authMethods` 含 oauth 却无 enabled 策略 → 400 `RequiresOAuthPolicy`。
- **背景约束**：OAuth 是 **Pro 门控**——`mcp-oauth-feature.ts` 文案明写「available only in Xpert Pro」，且本仓库 `packages/config` 的 `environment.ts` 与 `environment.prod.ts` **均把 `mcpOAuthEnabled` 硬编码为 `false`**，开源部署下 OAuth 端点全 403 `Error.McpOAuthProOnly`；`introspectionClientSecretEncrypted` 仅 `select:false`（无 `@Exclude`），配布尔位 `introspectionClientSecretConfigured`；内省/发现默认拒绝私网地址（`XPERT_MCP_OAUTH_PRIVATE_HOST_ALLOWLIST` 才放行）。Key 侧 `rotate` = 旧键撤销 + 新键只回显一次，`revoke` 不删行。
- **被否决方案**：无（未见对「单模认证」或「合并两链」的显式否决记录）。
- **重新评估触发条件**：开源版需要 OAuth、或需要新增第三种认证方式（mTLS/签名）时——须同时改 `authMethods` 枚举、`authenticate` 分流、challenge 分支与 `enable` 前置校验四处。
- **关联代码**：`file://packages/server-ai/src/mcp-publication/mcp-api-key.service.ts`、`file://packages/server-ai/src/mcp-publication/mcp-oauth-feature.ts`、`file://packages/server-ai/src/mcp-publication/mcp-publication.service.ts`、`file://packages/config/src/environments/environment.prod.ts`
- **证据来源**：[05-接口.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/05-接口.md)「鉴权与准入矩阵」与「错误语义」；[07-运维.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/07-运维.md)「环境变量与门禁」「密钥与凭据运维」。

## D8 长任务幂等（idempotencyKey + inputHash）
- **分类**：接口契约
- **动机（避坑）**：现象——MCP 长任务客户端会按 `tasks/get` 轮询并在超时后重发同一请求；若无幂等键，同一逻辑任务会产生多行 `mcp_task` 并重复执行工具；后果——重复副作用（重复发信、重复写库）与账实不符，且无法判断「同键不同入参」是重试还是新意图。
- **决策**：**双指纹 + 唯一索引**——`idempotencyKey = sha256(publicationId \0 subjectType \0 subjectId \0 requestId \0 typeof rpcRequestId \0 String(rpcRequestId) \0 capability.publicName)` 与 `inputHash = hashJson(arguments)`；唯一索引 `(publicationId, idempotencyKey)`，命中即 `assertIdempotentReplay`（比对 `subjectType`/`subjectId`/`inputHash`，**同键异指纹抛 `-32602` 协议错误**），并发插入冲突在 catch 里重查一次兜底。`revision` 只在 `input_required → working` 的补充输入路径 `+1`，用于让客户端识别状态推进。
- **背景约束**：`mcp_task.revision` 是**普通 int 列，不是 `@VersionColumn`**——真正的并发保护来自唯一索引 + 单 worker（`concurrency: 4`）；`requestPayload`/`inputRequests`/`inputResponses` 均 `select:false` 但**以 json 明文持久化**（单条上限 2 MiB）；`lifetime` 默认 1h、上限 24h 写 `expiresAt`；`get` 对过期非终态就地判 `failed` + `MCP_TASK_EXPIRED`；审批字段注释逐字：「Server-obtained approval for this queued invocation; never supplied by tool arguments.」；**没有 REST 形式的轮询/取消端点**，只有协议 `tasks/get|update|cancel`。
- **被否决方案**：无（未见对其他幂等口径的显式否决记录）。`[推测]` 并发输入补充存在丢写窗口（`revision` 非 CAS）。
- **重新评估触发条件**：长任务并发提升（多 worker）或需要把 `tasks/*` 暴露为 REST 时——须先把 `revision` 换成真正的 CAS 语义（`@VersionColumn` 或条件 UPDATE），再放开并发。
- **关联代码**：`file://packages/server-ai/src/mcp-publication/mcp-task.service.ts`、`file://packages/server-ai/src/mcp-publication/entities/mcp-task.entity.ts`、`file://packages/server-ai/src/mcp-publication/mcp-task.processor.ts`
- **证据来源**：[02-实现.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/02-实现.md)「MCP 发布链」第 6 步与「技术债与 hack」10；[04-模型.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/04-模型.md) `mcp_task` 行与「幂等键口径」；[05-接口.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/05-接口.md)「错误语义」任务段。

## D9 Agent 插件按 digest 幂等 + PortablePlugin
- **分类**：兼容处理
- **动机（避坑）**：现象——git/zip 重导入（修复/更新）若无稳定包身份，会新增重复包行与重复绑定，动态资源解析出现同一插件多版本；后果——专家版本与安装结果漂移，且「重导入」会把已选模板的引用关系一起改写。
- **决策**：**包身份 = (scope, digest)**——digest 由 `portablePackageDigest(root)` 计算；入库统一在一个事务 + `lockPackageScope` 内，先 `findOne({ ...scope, digest })` 去重，命中且 `packageIntact` 时**复用原 `rootPath` 只更新 `descriptor`**；解析边界由 `PortablePlugin` 承担（Ajv 2020 + zod v3 双校验，`realpath` + `relative` 白名单，任何真实路径必须落在包根内）。绑定侧 `version = sha256(JSON.stringify({ ...input, expertVersions, digest }))`，修订冲突用 `supersededById` 串成版本链，`enabled=false` 的旧绑定保留供审计。
- **背景约束**：`@Index(['tenantId','organizationId','digest'])` **非唯一**，去重必须由应用层完成，**DB 不兜底**（并发导入理论上可产生重复包 `[推测]`）；`definitionHash = pkg.digest` 会被透传进插件组件（skills 与 `mcp.json`），因此「同 digest 视为不可变包」是整条链的隐含前提；`cleanupEligible` 决定能否被目录清理回收（注释逐字：「Only automatic catalog defaults may be collected; selecting a template reserves the reference.」）；解析边界由文件首行注释划定：「Portable discovery is intentionally separate from the native Xpert module loader.」
- **被否决方案**：在修复/重导入时重写包身份、创建时间或绑定——被注释逐字否决：「Never rewrite package identity, creation time or bindings during repair/reimport.」
- **重新评估触发条件**：需要「同 digest 但内容可变」的包（例如本地开发覆盖），或需要并发导入强一致时——应先把 `(tenantId, organizationId, digest)` 升级为唯一索引并把冲突处理显式化。

- **证据来源**：[03-数据流转.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/03-数据流转.md)「链路七」；[04-模型.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/04-模型.md)「③ Agent 插件子域」与「校验规则」；[01-架构.md](file://.module-experts/后端专题/工具与 MCP 专家/implementation/01-架构.md)「关键不变量」6。

## D10 四模块无 migrations，表结构由实体驱动
- **分类**：技术选型
- **动机（避坑）**：现象——五个模块中只有 `agent-plugin` 自带 SQL，其余四模块的表结构完全由 TypeORM 实体驱动、索引名在装饰器里显式命名；后果——宿主关闭 `synchronize` 时 `mcp_runtime_instance`、`mcp_publication*` 这批表不会自动出现，升级后表现为启动期关系缺失/查询报错，而仓库内**没有基线 DDL 可对照**。
- **决策**：不自带 DDL 的四个模块（`xpert-toolset`/`xpert-tool`/`mcp`/`mcp-publication`）把建表责任交给宿主的同步策略或平台统一迁移线；`agent-plugin` 因要**先放宽组织维度约束再创建租户安装**，保留 3 份顺序化 SQL（`20260921` 建两表 + `ALTER TABLE skill_package ... runtimeResourceOnly`；`20261012` `organizationId DROP NOT NULL`；`20261015` `cleanupEligible`），并在 README 逐字要求「部署前应用」。
- **背景约束**：`20260921` 首行注释要求 `-- Apply in a transaction before enabling composer.resources.`；`mcp` 模块 0 实体 0 表，天然不需要 DDL；实体与库的漂移在仓库内无对照物，`[推测]` 生产环境列变更依赖外部迁移工具或一次性基线。
- **被否决方案**：无（未见对「把 DDL 纳入仓库」或「全量迁移化」的显式否决记录）。
- **重新评估触发条件**：宿主关闭 `synchronize`、或需要对已上线库做列级审计时——须补齐四模块的基线 DDL，并保证索引名与实体装饰器中的 `IDX_*` 一致。

## D11 邻域控制器与实体由本模块注册
- **分类**：架构设计
- **动机（避坑）**：现象——让每个子域各自 import 对方模块换取 repository provider，会形成 `xpert-toolset ↔ mcp-publication ↔ mcp-consumer ↔ plugin-resource` 的环；后果——Nest 装配期 DI 解析失败（启动直接报错），或被迫到处加 `forwardRef` 使装配顺序脆弱。
- **决策**：把「谁提供 repository」集中到 `XpertToolsetModule` 这一处（本域 DI 图的**单点重装配**）——其 `controllers` 含 `McpConsumerOAuthController`/`McpConsumerCapabilitiesController`；`forFeature` 含 MCP 发布侧的 `McpCapabilityCatalog`/`McpPublicationCapability`、MCP App 的 `McpAppAudit`/`McpAppHistory`、平台插件域的 `PluginResourceInstallation`、消费侧的 `McpConsumerOAuthCredential`/`McpConsumerOAuthSession`；`providers` 含 `McpSubscriptionService` 与执行面的 `ToolRuntimeService`。同时 `MCPModule` 声明 `global: true`，保证 `MCPService` 在被任一模块 import 后全局可注入，不必重复 import。
- **背景约束**：代价是**模块边界与子域边界不一致**——`/api/xpert-toolset/*` 的实际端点包含 mcp-consumer 的子路径，路由全景必须逐个控制器读装饰器；同时 `ToolRuntimeService` 无自有 Nest 模块，由 `XpertToolsetModule` 提供并导出。
- **被否决方案**：无显式否决记录。`[推测]` 该装配是为绕开循环依赖（实现层「技术债与 hack」4 亦标为 `[推测]`）。
- **重新评估触发条件**：需要按子域独立部署/测试、或要把工具集域拆成更薄的模块时——应先抽出「共享 repository 薄模块」再删控制器，而不是继续往本模块堆邻域资产。
