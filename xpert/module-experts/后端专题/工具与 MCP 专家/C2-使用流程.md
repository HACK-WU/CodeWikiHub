## Recipe 1 建工具集与 provider 选择
- **业务目标**：为工作区建一个可被助手挂载的工具集，明确 `category`/`type` 与 provider 身份，并把运行时选项写进 `options`、凭据写进 `credentials`。
- **调用顺序**：`GET /api/xpert-toolset/providers`（`ListBuiltinToolProvidersQuery`）挑 provider → `GET /api/xpert-toolset/provider/:name` 读元数据 → `GET /api/xpert-toolset/builtin-provider/:name/credentials-schema` 取凭据表单 → `POST /api/xpert-toolset/builtin-provider/:name/instance`（先 `validateCredentials` 再 `createBuiltinToolset`，强制 `category=BUILTIN`、`type=provider`）。api 类先 `POST provider/openapi/remote` 或 `POST provider/odata/remote` 取 schema，再走 `CrudController` 的 create（`schema`/`schemaType` 装 `openapi_json|openapi_yaml` 原文）；mcp 类先 `POST provider/mcp/tools` 探测再 create。
- **事务-时序边界**：凭据校验是落库前的读侧动作；`create`/`save` 双入口统一先 `assertValidTagAssociations(..., TagCategoryEnum.TOOLSET)`（标签 M2M 由 `@JoinTable` 级联维护）；`update` 被显式收窄到 `updateToolset`，不暴露 TypeORM 递归更新类型；读侧 `afterLoad` 只做回填（`??=` 语义，**不覆盖库里已有值**），不写库。
- **预期结果**：`category ∈ builtin|api|mcp|workflow(@deprecated)`，实体列另允许 `command`；响应统一 `ToolsetPublicDTO`，`credentials` 因 `@Exclude({toPlainOnly:true})` 不出网；工具集随后可被助手侧以只读 `ToolsetCatalogItem` 引用。
- **错误处理**：provider 不存在 → 404 `ToolProviderNotFoundError`；凭据不合法 → 400 `ToolProviderCredentialValidationError` 家族；但 `POST builtin-provider/:name/instance` 会把**任何**异常包成 500 `InternalServerErrorException(err.message)`——排障看 message，不看状态码。`createBuiltinToolset` 内 `// encrypt credentials` 仍是注释，**凭据以明文 json 落库**。
- **真实代码示例**：
```ts
// 契约：XpertToolsetService.createBuiltinToolset
// 1) toolproviderController.validateCredentials(entity.credentials) 通过后才 create
// 2) category 强制 BUILTIN、type = provider
// 3) 源码逐字保留：// encrypt credentials
```

## Recipe 2 工具发现与 schema 生成
- **业务目标**：按 provider 拿到「工具清单 + JSON Schema」，供表单预览与后续落库。
- **调用顺序（四路）**：① builtin — `GET /builtin-provider/:name/tools`、`GET /providers`、`GET /provider/:name`，命中 `BUILTIN_TOOLSET_REPOSITORY` 静态注册表（Planning、Tavily、SearchAPI、Email、Bing、DingTalk、Slack、Discord、Serper）；② openapi — `POST /provider/openapi/remote`（`GetOpenAPIRemoteSchemaQuery`）与 `POST /provider/openapi/schema`（`ParserOpenAPISchemaCommand`）；③ odata — `POST /provider/odata/remote`（`GetODataRemoteMetadataQuery`）与 `POST /provider/odata/schema`（`ParserODataSchemaCommand`）；④ mcp — `POST /provider/mcp/tools`（**`@Sse` 长连**，`keepAlive(30000)` + `takeUntilClose(res)`）。
- **事务-时序边界**：schema 生成全程是读（本地解析或远端拉取），**不落库**；工具行只在工具集 create/update 时由 `XpertToolset.tools` 的级联写入。mcp 探测若解析出「插件托管 MCP」选项，必须先回库校验 `pluginName`/`componentKey` 与已安装实体逐字一致（`resolveToolset`），否则 400——防止用未安装配置探测运行时。
- **预期结果**：builtin 返回候选工具定义，供 `hydrateBuiltinToolSchemas` 在列表读路径补齐 `label/description/schema`；openapi/odata 返回工具 JSON Schema 与可保存的 schema 原文；mcp 返回 `{ tools, logs }`，工具元数据经 `getMcpToolAppMeta` 投影为 `{ mcp: {...}, _meta }`。
- **错误处理**：provider 未命中静态注册表时回落 `CreateToolsetCommand`（由平台插件提供实现），仍失败才抛 `ToolProviderNotFoundError`；openapi/odata 解析失败抛 `ToolApiSchemaError` 家族（控制器不兜底）；mcp 失败**走 SSE 流内 error 事件**，不是 4xx/5xx JSON 体。单条工具试跑另有 `POST /provider/openapi/test`（内部派 `TestOpenAPICommand`）。
- **真实代码示例**：
```ts
// controller（源码注释逐字）：@Post @Sse There is a priority order.
// handler：MCPToolsBySchemaCommand → client.getTools() → { tools, logs }
// plugin-managed 探测前置：BadRequestException('Plugin-managed MCP discovery must use the installed plugin component')
```
章节来源：[xpert-toolset.controller.ts](file://packages/server-ai/src/xpert-toolset/xpert-toolset.controller.ts)（关键符号：getMCPTools / getOpenAPISchema / parseODataSchema）、[mcp-tools-schema.handler.ts](file://packages/server-ai/src/xpert-toolset/commands/handlers/mcp-tools-schema.handler.ts)（关键符号：MCPToolsBySchemaHandler.execute / resolveToolset）、[provider/builtin/index.ts](file://packages/server-ai/src/xpert-toolset/provider/builtin/index.ts)（关键符号：BUILTIN_TOOLSET_REPOSITORY）

## Recipe 3 工具执行（tool-runtime 唯一出口）
- **业务目标**：任何一次工具调用都经同一执行面完成，并保证环境、存储策略与发布配置只能由宿主提供。
- **调用顺序**：调用方三类——`ToolInvokeHandler`（HTTP 测试/API 调用）、Agent 运行时（`subgraph.handler` 装配后由 LangChain 直接调工具）、发布运行时（`mcp/p/:slug` 侧）。统一路径：`ToolsetGetToolsCommand` → `ToolRuntimeService.loadToolsets` → 逐工具 `initTools()` + `getVariables()` → `executeTool({toolsetId, toolName, arguments, executionId, requestId})`。**寻址三分支**：① 声明式工具 → `executeDeclaredTool`；② `MCPToolset` 且同时给出 `serverName` + `remoteName` → 按 `remoteTaskMode` 走 `callMcpTaskTool` 或 `callMcpTool`；③ 其余 → `toolset.getTool(toolName)` 后 `invoke(arguments, { configurable: {...executionContext, tool_call_id: requestId, toolExecutionContext} })`。
- **事务-时序边界**：`loadToolsets` 先 `resolveToolsets`（`persistedToolsetWhere` + `resolveToolRuntimeScope` 约束 workspace；空列表直接返回 `[]`）；`toolsetSnapshots` 仅当 `source === 'api'` 可用，否则抛 `McpToolsetSnapshotApiOnly`；无论成败 `finally toolset.close()`。
- **预期结果**：成功经 `normalizeToolResult` 归一；有 `executionId` 时创建 `createExecutionModelUsageRecorder`，用量经 `XpertAgentExecutionRecordUsageCommand` 写入 Agent 执行账本（跨域写）。
- **错误处理**：工具不存在 → `ToolNotFoundError`；provider 不可解析 → `ToolProviderNotFoundError`，两者原样上抛；`ToolInvokeHandler` 仅当 `error.name === 'ToolException'` 时转 `ToolInvokeError`（源码注释逐字：「The MCP adapter identifies tool failures by name but does not export its error class.」——上游改类名即静默降级）。
- **真实代码示例**：
```ts
// ToolRuntimeEnvironment（注释逐字）：
// mcpRuntime?:        'Validated Publication configuration supplied by the host, never tool arguments.'
// workspaceDataScope:'Persisted Xpert storage policy; derived catalog fields are never accepted from callers.'
// toolsetSnapshots:   'Trusted API preview snapshots. Persisted Agent and MCP execution must not use this escape hatch.'
```
章节来源：[tool-runtime.service.ts](file://packages/server-ai/src/tool-runtime/tool-runtime.service.ts)（关键符号：loadToolsets / executeTool / resolveToolsets / normalizeToolResult）、[tool-invoke.handler.ts](file://packages/server-ai/src/xpert-tool/commands/handlers/tool-invoke.handler.ts)（关键符号：ToolInvokeHandler.execute）、[subgraph.handler.ts](file://packages/server-ai/src/xpert-agent/commands/handlers/subgraph.handler.ts)（关键符号：ToolsetGetToolsCommand / dynamicResources.toolsetIds）

## Recipe 4 工具测试与参数 faker
- **业务目标**：在不影响业务的条件下试跑单条工具，并由 schema 生成可直接填入表单的参数样例。
- **调用顺序**：`POST /api/xpert-tool/test` → `XpertToolService.testTool(body)`：按 `body.toolsetId` / `body.id` 分别取工具集与工具行，浅合并后交 `ToolInvokeCommand`；OpenAPI 专用入口 `POST /api/xpert-toolset/provider/openapi/test` 只是 `TestOpenAPICommandHandler` 转一次 `ToolInvokeCommand`，**两条入口共用同一 handler**。参数 faker：`GET /api/xpert-tool/:id/faker` → `getParamsFaker`。
- **事务-时序边界**：`ToolInvokeHandler` 前置断言 `!toolset || !tenantId || !toolset.workspaceId` → 400 `server-ai:Error.McpToolInvocationScopeRequired`，即**测试链也要求显式租户与工作区**；随后构造快照 `Object.assign(new XpertToolset(), toolset, { id, tenantId, organizationId, workspaceId, tools: [tool] })` 作为 `toolsetSnapshots` 传入——这是 tool-runtime 中唯一允许快照的 `source:'api'` 通道。
- **预期结果**：返回 `events.length ? { events, result } : result`；`principal` 为登录用户，否则退化 `{ type:'service_account', id:'api-tool-invoke' }`，`executionId = requestId = randomUUID()`。faker 路径：内置类目走 `ToolSchemaParser.parseZodToJsonSchema` + `JSONSchemaFaker.generate`；非内置走 `ToolsetGetToolsCommand` → `initTools()` → `lc_kwargs.schema ?? parseZodToJsonSchema`，`finally close()`（**同样经 tool-runtime，不是并行实现**）。
- **错误处理**：工具不存在 404、参数非法 400、调用失败 400；参数按 `tool.schema.parameters` 分 `form`/`llm` 两桶并用 `ApiBasedToolSchemaParser.convertPropertyValueType` 转类型，无 schema 时回落 `{ llm: tool.parameters ?? {}, form: {} }`；`UUIDValidationPipe` 失败 400。
- **真实代码示例**：
```http
POST /api/xpert-tool/test        { "toolsetId": "<id>", "id": "<toolId>", "arguments": { } }
GET  /api/xpert-tool/<toolId>/faker
POST /api/xpert-toolset/provider/openapi/test
```

## Recipe 5 MCP 客户端接入与 stdio 运行时审计
- **业务目标**：把一个远端 MCP Server 接成本域工具集，枚举其工具并在 stdio 场景留下可核对的运行时审计行。
- **调用顺序**：建 `category=mcp` 工具集（`schema` 为含 `servers`/`mcpServers` 的 JSON 字符串）→ `POST /api/xpert-toolset/provider/mcp/tools`（`@Sse`）枚举工具（可无 `id`；插件托管必须有 `id` 且 `pluginName`/`componentKey` 与已安装实体一致）→ 运行时装配产出 `MCPToolset` → `initTools()` 按 `isPro()` 择 `createProMCPClient`/`createMCPClient` → `new McpConsumer(new LangChainMcpConnection(client))` 包装 → 工具经 `filterMcpTools` 过滤 + `wrapMCPTool` 包一层。
- **stdio 分支与审计**：`createMCPClient` 按 `server.type` 或字段特征分流 `http`/`sse`/`stdio`；stdio 先 `mcpStdioRuntimeManager.assertInitScriptsAllowed`，再按需 `runScript(initScripts)`（10 分钟超时）并派发 `ON_CHAT_EVENT` 进度。运行期经 `setAuditSink` 把 `McpRuntimeAuditService` 挂到生命周期：`recordStarting`（首插，写 `commandLabel`/`commandHash = sha256(command+args)`/`policySnapshot`）→ `recordRunning`（`readyAt`/`startupDurationMs`/`runnerPid`/`childPid`/`stderrTail`）→ `recordClosed`（`closedAt`/`closeReason`/`durationMs`）→ `recordAppInstance`（仅 `appInstanceId IS NULL` 时补写）。
- **事务-时序边界**：stdio 是**两级子进程**（宿主 spawn runner，runner 再 spawn 真实 server）；策略由 `TMcpStdioRuntimePolicy` 收敛并被服务端按平台/租户收紧；工具调用每次 `touchClient(client)` 并在返回 App 数据时 `registerMcpAppInstance` + `waitForMcpAppInstancePersistence`。
- **预期结果**：`mcp_runtime_instance` 出现可核对行（`status ∈ starting|running|closing|closed|failed`、`origin ∈ agent-toolset|mcp-app-host`）；停止入口 `POST /api/xpert-toolset/operations/mcp-runtimes/:runtimeId/stop`（`admin-stop`）与 `POST .../kill`（`admin-kill`），`GET` 合并库内历史与内存活体快照（默认窗口 180 天）。
- **错误处理**：`XPERT_MCP_STDIO_RUNTIME_ENABLED` **默认关闭（fail closed）**，关闭时抛 `MCP stdio runtime is disabled. Set XPERT_MCP_STDIO_RUNTIME_ENABLED=true to allow stdio MCP servers.`；插件托管契约在插件清单里缺失时直接抛 `not available in the current plugin manifest`（表现为「工具发现为空」）；运维端点未过 SUPER_ADMIN 一律 403。
- **真实代码示例**：
```ts
// provider/mcp/types.ts：stdio 先校验再执行
// mcpStdioRuntimeManager.assertInitScriptsAllowed(schema) → runScript(initScripts, { timeout: 10 * 60_000 })
// wrapMCPTool：mcpStdioRuntimeManager.touchClient(client)  →  registerMcpAppInstance(...)
```
章节来源：[mcp-toolset.ts](file://packages/server-ai/src/xpert-toolset/provider/mcp/mcp-toolset.ts)（关键符号：initTools / wrapMCPTool / callMcpTaskTool）、[mcp-stdio-runtime.ts](file://packages/server-ai/src/xpert-toolset/provider/mcp/mcp-stdio-runtime.ts)（关键符号：McpStdioRuntimeManager / resolvePolicy）、[mcp-runtime-audit.service.ts](file://packages/server-ai/src/xpert-toolset/mcp-runtime-audit.service.ts)（关键符号：recordStarting / recordRunning / recordClosed）、[mcp-runtime.controller.ts](file://packages/server-ai/src/xpert-toolset/mcp-runtime.controller.ts)（关键符号：assertSuperAdmin / stop / kill）

## Recipe 6 MCP 服务端会话（mcp/sse + mcp/messages）
- **业务目标**：用本域自带的 MCP Server 封装对外提供 SSE 会话式协议端点，并把宿主 provider 上带注解的方法自动注册成 MCP 原语。
- **调用顺序**：客户端 `GET /api/mcp/sse` → `MCPService.handleSSEConnection` → `NestSSEAdapter.handleSSE(req,res)` → `createTransport(res)` 以 `${globalApiPrefix}/${messagesEndpoint}` 构造 `SSEServerTransport`，把 `_sessionId` 存入 `activeTransports` 并监听 `res.on('close')` 删会话；随后客户端 `POST /api/mcp/messages?sessionId=…` → `handleMessages` → `transport.handlePostMessage(req, res, req.body)`。

## Recipe 7 MCP 发布全流程
- **业务目标**：把工具集能力反向发布为对外 MCP Server，并保证「能力变更需评审、发布可准入、调用可审计、长任务可重放」。
- **调用顺序**：
  1. **草稿** `POST /api/mcp-publications`（类级 `RoleGuard` + `@Roles(SUPER_ADMIN)` + 严格 `ValidationPipe`）→ `assertNameAndSlug` → `assertSlugAvailable` → 落 `status:'draft'`、`authMethods` 默认 `['api_key']`、`runtime: parseMcpRuntimeConfiguration`、`protocolVersion: MCP_PROTOCOL_VERSION`、`reviewStatus:'current'`。
  2. **能力快照** `POST /api/mcp-capability-catalog/toolsets/:toolsetId/discover` → `discoverAndReplaceMcpToolset`（≤1000 条、`assertValidMcpCapabilityDescriptor`、`hashMcpCapabilityDescriptor` 生成 `char(64)` 哈希，事务内整体 replace）。
  3. **绑定** `PUT /api/mcp-publications/:id/capabilities` → `replaceCapabilities`（事务内 delete + save + `markPublicationCapabilitiesCurrent`），写 `descriptorHash` + `descriptorSnapshot`。
  4. **审核** `resolveRuntimeCapabilities` 逐条比对 `binding.descriptorHash === item.descriptorHash`，不同则 `compareMcpCapabilityDescriptors(binding.descriptorSnapshot, item.descriptor)`，**只有 breaking 变更**才置 `reviewStatus='required'` + `reviewReason`；`POST :id/enable` 走 `assertCanEnable` 三重前置（required 拒 / 无 enabled 能力拒 / `authMethods` 含 oauth 但无 enabled 策略拒）。
  5. **访问授权**：`mcp_publication_access` 组织级 `enable`/`disable`（唯一 `(publicationId, organizationId)`，写后广播 `publishAccessInvalidated`）；**该面没有 HTTP 端点**，由 `McpPublicationService.findCurrentScopeById`、`McpPublicationAuthorizationService.assertCanRun`、`PluginMcpServerService` 在服务层调用——排查「某组织看不到发布」要走服务层。
  6. **凭据**：`POST :id/api-keys`（`xpert_mcp_` + base64url(32B)）；OAuth `GET|PUT :id/oauth-policy`（先 `assertMcpOAuthEnabled()`）。
  7. **调用**：`ALL /api/mcp/p/:slug` → `findActiveBySlug` → 认证/授权/限流 → 每请求 `createMcpHandler(() => createServer(...), { legacy:'stateless', responseMode:'auto', bus })` + `toNodeHandler`；审计 `McpInvocationAuditService.start` → `succeeded`/`failed`（`ForbiddenException` 记 `denied`）。
  8. **长任务**：协议方法 `tasks/get|update|cancel`（**没有 REST 轮询/取消端点**），执行由 `@PluginJobProcessor({ queueName:'mcp-publication', jobName:'execute-tool', concurrency:4 })` 消费并最终回到 `toolRuntime`。
- **事务-时序边界**：草稿的 `runtime` 是宿主侧执行配置（契约注释逐字：「Host-owned execution configuration. Tool arguments cannot override these bindings.」）；绑定是整体替换（重复 body 幂等）；审计 `requestId` 唯一 ⇒ 一次调用恰一条；运行时在 `runWithCapturedRequestContext` 内**只恢复本次调用验证过的用户**（服务账号不得继承管理员）。
- **预期结果**：`GET :id/connection-info` 返回 `protocolVersion`、`transport:'streamable-http'`、`endpoint = <baseUrl>/api/mcp/p/<slug>`、`authorization:'Bearer'`；`POST :id/test` 返回协议版本/能力数/启用状态/评审状态四项 checks。
- **错误处理**：非当前 scope 的 `:id` → **404**（避免探测存在性）；运行时主体不匹配 → 403 `Error.McpPublicationAccessDenied`；OAuth 三端点非 Pro → 403 `Error.McpOAuthProOnly`（本仓库 `packages/config` 两套 environment 均把 `mcpOAuthEnabled` 固定为 `false`）；「发布建好却调不通」基本收敛到 enable 的三条前置。
- **真实代码示例**：
```http

POST /api/mcp-capability-catalog/toolsets/<id>/discover # 能力快照
PUT  /api/mcp-publications/<id>/capabilities            # 绑定（整体替换）
POST /api/mcp-publications/<id>/enable | /disable | /test | /connection-info
ALL  /api/mcp/p/<slug>                                  # 对外运行时（Bearer 自校验）
```

## Recipe 8 API Key 签发、轮换与撤销
- **业务目标**：给外部客户端发一把可检索、可轮换、可追溯的调用凭据，且密钥材料默认不出网。
- **调用顺序**：签发 `POST /api/mcp-publications/:id/api-keys` → `secret = 'xpert_mcp_' + base64url(32B)`，落 `keyPrefix`（存储前缀长度 24）+ `keyHash`（sha256，`char(64)`）+ `encryptedSecret`（仅「可回显」路径写入）；列表 `GET :id/api-keys`（`keyHash`/`encryptedSecret` 为 `select:false` 且 `@Exclude`）；轮换 `POST /api/mcp-api-keys/:keyId/rotate` = **先撤销旧 Key，再按同 name/subject/scopes/expiresAt 新建**（新 secret 只返回一次）；撤销 `POST /api/mcp-api-keys/:keyId/revoke` 写 `revokedAt`/`revokedById`（**不删行**）。
- **事务-时序边界**：`rotate` 与 `revoke` 都广播 access 失效（`publishAccessInvalidated`），客户端需在过渡窗口内完成换 Key；`lastUsedAt` 只在鉴权成功路径回写；有效判定为 `revokedAt IS NULL AND (expiresAt IS NULL OR expiresAt > now())`。
- **预期结果**：调用侧 `McpApiKeyService.authenticate` 先看 `publication.authMethods` 必含 `api_key`，再要求 Bearer 以 `xpert_mcp_` 开头且 ≥24 字符，按 `keyPrefix` 命中未撤销行并 `timingSafeEqual` 比对 sha256，过期即拒。密文读取必须显式 `.addSelect('apiKey.encryptedSecret')`，且 `getOrCreateRevealableCredential` 仅当前用户 + 同组织可解一次。
- **错误处理**：调用侧 401 统一 `Error.McpApiKeyUnauthorized`，覆盖「缺失 / 前缀不合法 / 前缀未命中 / 已撤销 / 已过期 / hash 不匹配」六类并回 `WWW-Authenticate` 挑战；管理侧操作未知 Key 是 **400** `Error.McpApiKeyNotFound`（不是 404）。运维要点：`SECRETS_ENCRYPTION_KEY` 必须显式设置且跨副本一致，换 key 前必须先轮换/重建 Key，否则旧密文不可解。
- **真实代码示例**：
```http
POST /api/mcp-publications/<id>/api-keys        # 返回一次 secret: xpert_mcp_…
POST /api/mcp-api-keys/<keyId>/rotate           # 旧键撤销 + 新键只回显一次
POST /api/mcp-api-keys/<keyId>/revoke           # 写 revokedAt / revokedById，不删行
```
章节来源：[mcp-api-key.service.ts](file://packages/server-ai/src/mcp-publication/mcp-api-key.service.ts)（关键符号：createForPublication / rotate / revoke / authenticate / getOrCreateRevealableCredential）、[mcp-api-key.entity.ts](file://packages/server-ai/src/mcp-publication/entities/mcp-api-key.entity.ts)（关键符号：keyPrefix / keyHash / encryptedSecret）、[mcp-publication-management.controller.ts](file://packages/server-ai/src/mcp-publication/mcp-publication-management.controller.ts)（关键符号：createApiKey / rotateApiKey / revokeApiKey）

## Recipe 10 排障入口合集
- **业务目标**：把本域五类高频症状落到唯一判据与处置动作上，避免按症状猜测。
- **调用顺序（排查链）**：
  1. **工具发现为空**：① `XPERT_MCP_STDIO_RUNTIME_ENABLED` 未开 → 直接抛 disabled；② 插件托管契约在插件清单里找不到 → 抛 `not available in the current plugin manifest`；③ 能力目录从未 discover。先核对 env 与 launch 日志，再校验插件 bundle 的 MCP 组件，最后管理侧调 `POST mcp-capability-catalog/toolsets/:toolsetId/discover`。
  2. **provider 报错 500 但没细节**：`POST builtin-provider/:name/instance` 把所有异常包成 `InternalServerErrorException(err.message)`——看响应 message 与宿主日志；凭据类失败本身是 400 `ToolProviderCredentialValidationError`。
  3. **MCP 握手失败**：协议版本/会话不匹配（对齐 `MCP_PROTOCOL_VERSION`，旧客户端走 legacy 兼容层）、`authMethods` 未含所用方式、OAuth 内省主机落私网被拒（`XPERT_MCP_OAUTH_PRIVATE_HOST_ALLOWLIST` 显式放行）。
  4. **Key 失效（401）**：按下节六类逐项核对，用 `GET mcp-publications/:id/api-keys` 看 `revokedAt`/`expiresAt`，`rotate` 换新并把新 secret 一次性发给客户端。
  5. **任务卡住或重复**：查 `mcp_task.status/expiresAt/revision`，队列 `mcp-publication/execute-tool` 堆积；同 `idempotencyKey` 不同入参会被协议拒绝（`-32602`）——那是防护生效而非故障；客户端按 `tasks/get` 轮询、`tasks/cancel` 取消（**均无 REST 端点**）。
- **事务-时序边界与判据**：① 运行时：`mcp_runtime_instance` 的 `status`/`runnerPid`/`childPid`/`stderrTail`/`closeReason`；`host-restart-or-lost` 是启动收敛的**预期**结果（`onApplicationBootstrap` 把 `starting|running|closing` 批量收尾），不要按这些行告警；`idle-timeout`/`max-lifetime-timeout` 由策略触发，`admin-stop`/`admin-kill` 是人工操作。② 调用：`event='mcp.request'` JSON 日志 + `mcp_invocation_audit.requestId`（一次调用一条，`argumentSummary` 默认查不出）。③ 发布自检：`GET connection-info` 确认版本/端点 → `POST :id/test` 看四项 checks。
- **错误处理**：`reviewStatus='required'` / 无 enabled 能力 / 缺 OAuth 策略 → `enable` 400，或跨 scope 查询得到 404；升级后表不存在要确认宿主迁移线是否覆盖 `xpert-toolset`/`mcp-publication` 这批实体（这两个模块**无 SQL 迁移文件**），而 `agent-plugin` 的三份 SQL 必须按序先执行。
