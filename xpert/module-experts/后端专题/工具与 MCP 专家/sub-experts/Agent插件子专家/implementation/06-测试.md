## 缺口
1. **`AgentPluginService` 与 `AgentPluginController` 无同名 spec**：`agent-plugin.service.ts`（27KB，含 `importGit`/`importZip`/`importStagedDirectory`/`createBinding`/`addToWorkspace`/`setEnabled`）与 `agent-plugin.controller.ts`（12 端点，含 git/zip 导入与 bindings）都没有直接用例；导入主链只被 `workspace-plugin.service.spec.ts`、`defaults/*.spec.ts`、G 组集成 spec 间接覆盖。`importStagedDirectory` 的 `existing`/`repaired` 分支中最关键的分支（同 digest 命中 + 磁盘损坏）只在集成 spec（默认 skip）里真跑。
2. **`AgentPluginCleanupService` 无单元 spec**：`preview`/`cleanup` 的 `reason` 归类只在集成 spec 覆盖；`referencedPackages` 的 LIKE 扫描语义（含"宁可多留"的保守行为）没有独立断言。
3. **`agent-plugin-connector.service` 的 `provider()` 无专测**：运行期凭据解析的六重校验（runtimeScope 一致性、工具集 owner、有效目录、URL/schema 全等）只靠 `agent-plugin-connector-*` 两个 spec 间接覆盖，`[推测]` 拒绝分支覆盖不完整。
4. **zip 来源端到端缺失**：`importZip` 的下钻单层目录逻辑与 `POST agent-plugins/zip` 的 100MB/1 文件限制没有 HTTP 级用例（`extractPortableZip` 自身有 A 组覆盖）。
5. **迁移与 DDL 无验证**：三份 `migrations/*.sql`（含 `organizationId DROP NOT NULL`、`cleanupEligible`、`runtimeResourceOnly`）没有 spec 或迁移断言；`[推测]` schema 漂移只能靠集成 spec 的真库 smoke 暴露。
6. **`RuntimeResourceController` 只有 query 校验**：6 个端点中 `commands`/`validate`/`authorize`/`update` 的入参与鉴权形状没有控制器级用例（业务在 service spec 覆盖）。
7. **模块装配断言只有间接一处**：`chat-group.module.spec.ts` 断言 `AgentPluginModule` exports 含 `RuntimeResourceService`，但 `AgentPluginModule` 自身的 providers/imports（含 `PluginResourceModule`、`ConnectorModule`）没有 wiring spec；`RuntimeResourceController` 由 `ai.module.ts` 装载这一点也无人断言。
8. **无端到端「导入→选择→执行」链路**：五条链各自有覆盖，但「git/zip 导入 → 目录 → 会话选择 → resolve → prepare → 工具集装配」的贯通用例不存在（`[推测]` 属于刻意把成本留在集成 spec 的设计）。

## 结论
判定：**可跑，且本子域的自动化程度在五个模块中最高**（30 个 spec 覆盖解析、文件系统、锁、收据、运行时授权与模板锁）。判据：
1. 29/30 个 spec 不连任何外部服务（Repository/ModuleRef/registry/安装器全为 mock），可直接用第三节命令 1/2 本地执行；唯一真库用例 `package-maintenance.integration.spec.ts` **默认 `describe.skip`**，只有注入 `AGENT_PLUGIN_TEST_DATABASE_URL` 才解锁，且只碰自带 schema 与临时目录。
2. 本子域 spec **不需要真 git、不需要网络、不需要 Redis/Bull**：`stagePortableGit` 在单元 spec 中只被覆盖「调用前校验」，在更新与集成 spec 中均被 mock/spy 替换；`pg_advisory_*` 在单元层只做调用断言。
3. 依赖环境变量的用例（`XPERT_AGENT_PLUGIN_PATH`、`AGENT_PLUGIN_TEST_DATABASE_URL`）都在 spec 内自设并 `afterEach`/`afterAll` 还原，不是环境前置；夹具依赖 `archiver` 由 `node_modules` 提供。
4. 覆盖重心合理：风险最高的三处（digest/路径遏制、`installations` 写锁、模板依赖锁）都有对应文件（A 组、C/D 组、H 组），但**导入主链（`AgentPluginService`）与清理归类（`AgentPluginCleanupService`）缺少单元级防线**，是新增改动最应优先补的两处。
