## 1. MCP 客户端链

`MCPToolset extends _BaseToolset`，`providerName = 'mcp'`、`providerType = XpertToolsetCategoryEnum.MCP`。`initTools()` 按 `environment.pro` 二选一分叉：Pro 走 `createProMCPClient(toolset, signal, commandBus, schema, env, xpertId, params)`，开源走 `createMCPClient(toolset, schema, env, xpertId, params)`——**`pro.ts` 当前是桩实现**，直接返回 `{ client: null, destroy: null, logs: null }` 并 `void _runtimeContext`。随后 `this.consumer = new McpConsumer(new LangChainMcpConnection(client))`，工具经 `filterMcpTools` 过滤后逐个 `wrapMCPTool` 包装，并统一 `verboseParsingErrors = true`。

`createMCPClient` 的装配序列（`types.ts`）：
1. `resolvePluginManagedMcpSchema` 解析插件托管 schema；遍历 `servers ?? mcpServers`，按 `server.type` 分三支：`HTTP` → 渲染 headers + `resolveMcpConsumerAuthProvider(...)` 生成 `authProvider` 并以 `transport: 'http'` 入列；`SSE`（或仅有 `url`）→ **`auth.type` 为 `oauth`/`connector` 时直接抛错**（`MCP OAuth requires Streamable HTTP; server '...' uses legacy SSE`），否则 `useNodeEventSource: true`；`STDIO`（或仅有 `command`）→ `mcpStdioRuntimeManager.assertInitScriptsAllowed` → 发 `ON_CHAT_EVENT` 起始事件 → 执行 `initScripts`（`runScript`，超时 10 分钟，`safeEnv: environment.production`）→ 用 `PromptTemplate(mustache)` 渲染 `args` 与 `env` → `prepareServer` 产出受管 server + runtime 句柄。
2. 构造 `MultiServerMCPClient({ throwOnLoadError: true, prefixToolNameWithServerName: false, additionalToolNamePrefix, outputHandling: { resource: 'artifact' } })`。
3. 装两处桥接：`installMcpMetaArtifactBridge(client)`（`_meta` artifact 桥，README 定位为 `temporary compatibility layer`）与 `installMcpToolAppMetadataBridge(client)`、`installMcpUiClientCapabilitiesBridge()`。
4. `new LangChainMcpConnection(client)` → `negotiateHttpProtocols()` → 对 `usesModernHttp(serverName) === false` 的 server 显式 `client.getTools(...)` → `mcpStdioRuntimeManager.attachClient(client, stdioRuntimes)`；失败即 `failRuntimes(...)` + `client.close()` 后重抛。

**stdio 运行时**：`McpStdioRuntimeManager` 是单例（`mcpStdioRuntimeManager`）。`prepareServer` 从 toolset options 与 server 级 policy 收敛出 `ResolvedMcpStdioRuntimePolicy`（`provider` / `startupTimeoutMs` / `idleTimeoutMs` / `maxLifetimeMs` / `allowedCommands`），把 spec base64 编码后经 `XPERT_MCP_STDIO_RUNNER_SPEC` 环境变量交给 `mcp-stdio-runner.js`；runner 用 `spawn(..., { stdio:['pipe','pipe','pipe'], detached: platform!=='win32', shell:false })` 拉起真实子进程，做 `startup-timeout` / `max-lifetime-timeout` / `stdin-close` / `parent-disconnect` / `SIGINT` / `SIGTERM` 六类终止路径，`SIGTERM` 后 3 秒 `SIGKILL`，非 Windows 用 `process.kill(-pid)` 杀进程组。管理器侧另有 `assertTenantLimit`（每租户并发上限）、`touchClient`/`touchRuntime` 空闲计时、`snapshot`/`list`/`killByFilter`/`closeClient`/`failRuntimes`，并通过 `setAuditSink` 把起停事件交给 ① 的 `McpRuntimeAuditService`。**默认关闭**：未设 `XPERT_MCP_STDIO_RUNTIME_ENABLED` 时 `prepareServer` 抛 `MCP stdio runtime is disabled`（fail-closed）。

**停止与审计**：`MCPToolset.close()` 先 `detachMcpAppInstancesForClient(client)`，再 `forceCloseMCPClientTransports(client)`（反射 `_transportInstances` → 中止 `_abortController` → 关 `_eventSource`），调 `this.destroy?.()`（即 `mcpStdioRuntimeManager.closeClient`），最后 `client.close()` 并把 `client` / `consumer` / `destroy` 置空。

## 2. MCP 服务端协议面

`MCPService implements OnModuleInit, OnModuleDestroy`，构造时建 `new McpServer({ name, version, capabilities })`。`onModuleInit` 顺序为：`scanAndRegisterProviders()` → `new NestSSEAdapter({ messagesEndpoint, sseEndpoint, globalApiPrefix })` → `setupStdioTransport()`（仅 `options.enableStdio` 为真时连接 `StdioServerTransport`，失败直接 `throw`）。

`scanAndRegisterProviders` 遍历 `discoveryService.getProviders()`，对每个有 `instance` 的 provider 用 `metadataScanner.getAllFilteredMethodNames(prototype)` 取方法名，再用 `reflector.get(MetadataKey.MCP_RESOURCE / MCP_TOOL / MCP_PROMPT, instance[method])` 取值并分别注册：
- `registerResource`：用 `new ResourceTemplate(\`${name}://{id}\`, { list: undefined })`，返回值统一包成 `{ contents: [...] }`。
- `registerTool`：参数经 `convertParametersToZod` 转 Zod（仅支持 `string|number|boolean|array|object` 与「已是 Zod」两种情形，其余回落 `z.any()`），返回值包成 `{ content: [...] }`。
- `registerPrompt`：把 `params` 与动态返回值浅合并。
三处都 `logger.log('Registered MCP ...: name')` 且捕获异常后重抛。

**传输面**：`BaseMCPController` 是 `@Controller()` + `@Public()`，两个端点 `@Get('mcp/sse')` 与 `@Post('mcp/messages')`，都把 `req`/`res` 直接交给 `MCPService`。`NestSSEAdapter.createTransport(res)` 用 `${globalApiPrefix}/${messagesEndpoint}` 作为回传地址构造 `SSEServerTransport`，从 `(transport as any)._sessionId` 取会话 id 存入 `activeTransports`，并注册 `res.on('close')` 清理；`handleMessages` 从 `req.query.sessionId` 查找，未命中返回 404 `Session not found`，命中则 `transport.handlePostMessage(req, res, req.body)`。

**协议版本口径**：本目录**未声明 `MCP_PROTOCOL_VERSION`**；`name`/`version`/`capabilities` 全部来自宿主传入的 `MCP_OPTIONS`（`IMCPOptions`：`name`、`version`、`capabilities`、`enableStdio`、`messagesEndpoint`、`sseEndpoint`、`globalApiPrefix`）。这与发布侧固定 `MCP_PROTOCOL_VERSION = '2026-07-28'` 形成口径差。

章节来源：[mcp.service.ts](file://packages/server-ai/src/mcp/mcp.service.ts)（关键符号：MCPService.onModuleInit / scanAndRegisterProviders / registerResource / registerTool / registerPrompt / convertParametersToZod）、[sse-transport.ts](file://packages/server-ai/src/mcp/transport/sse-transport.ts)（关键符号：NestSSEAdapter.createTransport / handleSSE / handleMessages）、[base-mcp.controller.ts](file://packages/server-ai/src/mcp/controllers/base-mcp.controller.ts)（关键符号：BaseMCPController.sseHandler / messagesHandler）

## 3. 发布生命周期

**草稿**：`McpPublicationService.create` 先 `assertNameAndSlug` + `assertAuthMethods`（`oauth` 需 `assertMcpOAuthEnabled()`）+ `assertSlugAvailable`，然后以 `status: 'draft'`、`authMethods: input.authMethods?.length ? input.authMethods : ['api_key']`、`protocolVersion: MCP_PROTOCOL_VERSION`、`reviewStatus: 'current'`、`runtime: parseMcpRuntimeConfiguration(input.runtime)` 落库。`runtime` 由 zod `.strict()` 解析，当前只允许 `{ files: { type: 'user' } }`。

**能力快照**：管理端点 `PUT mcp-publications/:id/capabilities` 收 `McpCapabilityBindingInput[]`，`replaceCapabilities` 走 `manager.transaction` 整体替换绑定；绑定对象的 `descriptorHash` / `descriptorSnapshot` / `pluginVersion` 来自台账 `mcp_capability_catalog`（由 `McpCapabilityCatalogService` 的 `prepareToolsetCapabilities` + `replacePreparedToolsetCapabilities` 产出）。`GET .../available-capability-sources` 与 `GET .../available-capabilities?toolsetId=` 提供「按工具集懒加载可选能力」。台账刷新入口是 `POST mcp-capability-catalog/toolsets/:toolsetId/discover` → `discoverAndReplaceMcpToolset`。

**审核**：`reviewStatus ∈ {current, required}`、`reviewReason` 为文本拼接。触发 `required` 的唯一路径是读取期对账（`resolveRuntimeCapabilities`）：工具集不可用 → `"<publicName>: source toolset is unavailable"`；台账无对应能力 → `"<publicName>: source capability is unavailable"`；hash 不等且 `compareMcpCapabilityDescriptors` 判定 `breaking` → `"<publicName>: <reasons.join(', ')>"`。兼容变更则**就地更新**绑定（`descriptorHash` / `descriptorSnapshot` / `pluginVersion`）并 `publishCatalogChanged`。

**激活**：`enable` → `assertCanEnable`（三项断言：`reviewStatus !== 'required'`、至少一条 `enabled: true` 绑定、`authMethods` 含 `oauth` 时须有 `enabled: true` 的 OAuth policy）→ `setStatus(id, 'active')`；`disable` 走 `setStatus(id, 'disabled')`，并在 `disabled` 时额外 `publishAccessInvalidated`。`getManagementView(id, ['capabilities'])` 与 `list()`（`IMcpPublicationSummary`：`capabilityCount` / `apiKeyCount` / `oauthEnabled` / `publicationScope` / `organizationAccessEnabled` / `recentInvocationAt` / `recentErrorAt`）供管理面渲染；`test(id)` 返回四项 checks（`protocolVersion` / `capabilityCount` / `oauth` / `status` 等）与 `ready` 汇总。

## 4. 认证与授权

**API Key**：`API_KEY_PREFIX = 'xpert_mcp_'`、`STORED_PREFIX_LENGTH = 24`。`createForPublication` 生成 `secret = xpert_mcp_ + randomBytes(32).toString('base64url')`，落库 `keyPrefix = secret.slice(0, 24)`、`keyHash = sha256(secret)`（`char(64)`，`select:false`）、`encryptedSecret = revealable ? encryptSecret(secret, environment.secretsEncryptionKey) : null`、`scopes = normalizeScopes(...)`（默认 `['tools:list','tools:call']`，空串或 >191 抛错）。`authenticate` 用 `keyPrefix` 定位行（`addSelect('apiKey.keyHash')`），再以 `timingSafeEqual` 比对哈希，成功后 `update({ lastUsedAt })`。**`rotate` 是「先撤销旧行再新建」**，不是原地更新；`revoke` 只写 `revokedAt` / `revokedById`。`getOrCreateRevealableCredential` 是显式授权路径：要求当前用户 id、当前 organizationId 与目标一致，命中可复用（有密文、未过期、scopes 完全匹配）则 `decryptSecret` 返回，否则新建。

**OAuth policy**：`McpOAuthService.upsert` 规范化 `issuer`（`normalizeTrustedUrl` + 去尾斜杠）、校验 `audience` 长度 ≤500、`subjectMapping` 三个 claim 名过 `CLAIM_NAME_PATTERN`（默认 `sub`/`email`/`azp`）、`requiredScopes` 归一，`normalizeIntrospectionPolicy` 处理 `introspection.clientSecret` 的三态（省略 = 保留现值、`null` = 清空、新值 = 轮换），并用 `introspectionClientSecretConfigured` 布尔位对外表达「是否已配置」（不读密文）。`authenticate` 流程：`discover(policy.issuer)` 取 OIDC metadata（TTL + 最大字节 + 非公开网段阻断）→ `jose.createRemoteJWKSet(normalizeTrustedUrl(metadata.jwksUri))` 且 `customFetch: guardedOAuthFetch` → `jwtVerify(token, jwks, { issuer, audience, requiredClaims: [subjectClaim], clockTolerance: 30 })` → 若 `introspectionEnabled` 则 `introspectToken` 并要求 `introspection.subject === tokenSubject`（否则 401）→ scopes 取 introspection 优先、否则 `tokenScopes(payload)` → `requiredScopes.some(...)` 缺失即 401 → `resolveUser` 按 `subjectClaim`/`emailClaim` 解析平台用户。全部失败统一 401。

**入口分流**：`McpAuthenticationService.authenticate` 先 `bearerToken(authorization)`（严格 `Bearer <token>` 两段、无多余段），token 以 `xpert_mcp_` 开头走 API Key，否则 `assertMcpOAuthEnabled()` 后走 OAuth。`challenge` 在 OAuth 关闭或发布单未启用 `oauth` 时返回裸 `Bearer`，否则返回 OAuth 的 `resource_metadata` 挑战。

**组织级授权**：`McpPublicationAuthorizationService.assertCanRun` 断言 `tenantId` / `publicationId` / `organizationId` 三者一致（发布单 `organizationId` 非空时强制相等；为空时走 `access.assertEnabled`），再解析用户并要求该用户在本租户存在且 `organizations` 里含 `isActive` 的目标组织成员关系；`subjectType === 'service_account'` 直接返回 `null`（无用户身份）。`McpPublicationAccessService` 的 `enable` / `disable` 以唯一索引冲突重取做竞态兜底，两者都 `publishAccessInvalidated`。

## 5. 调用与审计

**入口编排**：`McpPublicationController` 是 `@Public() @Controller('mcp/p')` + `@All(':slug')`，全部交给 `McpPublicationRuntimeService.handle`。`handle` 的次序固定：① `findActiveBySlug`；② 生成/继承 trace（`traceparent`/`tracestate`/`baggage` 三键，header 与 `_meta` 双来源）与 `requestId`；③ `authentication.authenticate`，失败且为 `UnauthorizedException` 时写 `WWW-Authenticate` 挑战头；④ `publicationAuthorization.assertCanRun`；⑤ `rateLimit.assertWithinLimit`；⑥ `publications.resolveRuntimeCapabilities`；⑦ `canExposeCapability` + `compareRuntimeCapabilities` 过滤排序；⑧ 先试 `handleTaskSubscriptionRequest`（SSE 订阅）、再试 `handleTaskProtocolRequest`（tasks/*）；⑨ 都未命中才 `createMcpHandler(() => this.createServer(...), { legacy:'stateless', responseMode:'auto', bus })` + `toNodeHandler`，在 `runWithCapturedRequestContext`（注入 `user` 与 `tenant-id`/`organization-id`/`x-request-id` 头）内先给 `McpLegacySessions` 一次机会，未接管才走 `nodeHandler`。`finally` 中 `handler.close()`，并统一 `applicationMetrics.recordMcpRequest` 与一行 `event: 'mcp.request'` JSON 日志。

**审计边界**：`McpInvocationAuditService.start` 一次调用写一行（`status: 'started'`），`capabilityId` / `toolsetId` / `capabilityKey` / `publicName` 从能力绑定拷入，`clientName` 取 `clientName ?? principal.credentialPrefix`，`organizationId` 取 `principal.organizationId ?? publication.organizationId ?? null`。`succeeded` / `failed` 只改 `status` / `durationMs` / `errorCode`（`ForbiddenException` → `denied`）。**隐私边界**：`argumentSummary` 由 `summarizeArguments` 生成，对象只写 `{ keys: Object.keys(value).slice(0, 100), bytes }`，数组/标量只写 `{ type }`——**从不写入参数值**；`errorCode` 只取 `error.code`（≤100 字符）或 `error.name`、否则 `'UNKNOWN'`。该列 `select:false`，`search` 默认不返回。`GET mcp-publications/:id/audit` 支持 `take`（上限 500）/`skip`，并按「共享发布时叠加当前 organizationId 过滤」处理。

**限流与输入校验**：`McpRateLimitService` 用 Redis 定窗计数，key 为 `mcp:rate:${publicationId}:${subjectId}:${capabilityId|'server'}:${bucket}`，默认 120 次 / 60 秒，能力级 `policy.rateLimit` 优先；超限返回 429 且 `retryAfterSeconds`。`mcp-input-schema.ts` 用 Ajv 2020/2019/draft7 三引擎按 `$schema` 方言替换 SDK 默认校验器，失败时只输出 `path` / `code` / `message` / 可选 `allowedValues`（各字段截断），**不回显提交值**，`issueTotal` 保留总数、`truncated` 标记只报前 20 条。

## 6. 长任务

`McpTaskService.create` 的幂等与指纹：
- `idempotencyKey = sha256(publicationId \0 subjectType \0 subjectId \0 requestId \0 typeof rpcRequestId \0 String(rpcRequestId ?? '') \0 capability.publicName)`。
- `inputHash = hashJson(arguments)`；`arguments` 与 `requestPayload` 都过 `requireJsonValue` + `assertJsonSize(..., MAX_TASK_PAYLOAD_BYTES)`。
- 先 `findByIdempotency` 命中即 `assertIdempotentReplay`（比对主体与 `inputHash`，不一致抛 `-32602`）并返回既有任务；`saveTask` 抛唯一冲突时**再查一次**（并发兜底）后同样走重放校验。
- 入队前先 `managedQueue.getExecutionPoolHealth({ executionPool: 'default' })`，不可用即 `-32603`。入队失败则把任务置 `failed` + `statusMessage` + `error` 后重抛。
- `pollIntervalMs = DEFAULT_POLL_INTERVAL_MS`；`expiresAt = now + clampLifetime(maxLifetimeMs)`。

**五个 `select:false` 载荷列**：`inputRequests` / `inputResponses` / `requestPayload` / `resultRef` / `error`。`requestPayload` 是完整的 `McpTaskJobPayload`（`version` / `taskId` / `publicationId` / `runtime` / `capabilityId` / `tenantId` / `organizationId` / `toolsetId` / `capabilityKey` / 可选 `serverName` / `remoteName` / `remoteTaskMode` / `arguments` / `principal{type,id,userId?,clientId?}` / 可选 `traceId` / `appResourceUri` / `approvalGranted`），`parseTaskPayload` 在 worker 侧反序列化并逐项校验。`approvalGranted` 带逐字注释 `Server-obtained approval for this queued invocation; never supplied by tool arguments.`——**宿主裁决，不接受工具参数**。

**轮询 / 取消 / 过期**：`get()` 在 `expiresAt <= now` 且非终态时把任务改写为 `failed` + `MCP_TASK_EXPIRED`；`update()` 处理 `input_required → working` 的补充输入（`revision += 1`，`createTaskInput` 校验 required 字段齐全）；`cancel()` 调用 `managedQueue.cancel(jobId)` 并把 `#activeTaskControllers` 中登记的 AbortController 中止。`watchTaskCancellation` 用 `subscriptions.subscribeTasks(publicationId, ...)` 通知 + 4000 ms 轮询双通道刷新取消与状态，`abortActiveExecutions` 在关闭时清理。

**worker 侧二次授权**：`McpTaskProcessor` 是 `@PluginJobProcessor({ pluginName:'@xpert-ai/platform', queueName:'mcp-publication', jobName:'execute-tool', concurrency: 4 })`，只转调 `tasks.process(job.data)`。`McpTaskExecutionService.run` 在真正执行前重做全部校验：task 与 payload 的 `publicationId`/`tenantId`/`capabilityId`/`subjectType`/`subjectId`/`organizationId` 逐项相等；发布单必须仍为 `status:'active'`；`resolveRuntimeCapabilities` 后绑定必须仍 `enabled` 且 `toolsetId`/`capabilityKey` 一致；审批模式 `confirm` 要求 `approvalGranted === true`、`allow` 还须 `canAllowMcpToolDirectly(descriptor)`；`JSON.stringify(runtime)` 必须与 payload 里的一致（注释：`A queue retry must not silently select a different model or storage binding.`）；最后 `runWithCapturedRequestContext` 恢复已验证用户身份。

## 7. 邻域交叉

**`mcp-consumer` 为何被 `xpert-toolset.module` 注册**：`McpConsumerOAuthService` 需要持有 `McpConsumerOAuthCredential` / `McpConsumerOAuthSession` 两个实体仓库，而 `McpConsumerCapabilitiesService` 的构造依赖是 `ToolRuntimeService`——后者由 `xpert-toolset.module` 提供并导出。因此 `xpert-toolset.module.ts` 的 `forFeature` 收进这两个实体、`controllers` 收进 `McpConsumerOAuthController` + `McpConsumerCapabilitiesController`、`providers`/`exports` 收进两个服务。`mcp-consumer` 自身**不含 Nest 模块**（目录只有控制器、服务、连接与协议子目录），必须由宿主模块承载——`mcp-module-wiring.spec.ts` 正是断言 `McpConsumerCapabilitiesService` 的 `design:paramtypes` 等于 `[ToolRuntimeService]`。`McpConsumerOAuthController` 提供工具集 MCP OAuth 的授权回调链路，与发布侧的 `McpOAuthService` **不是同一套**：前者是「作为客户端去连别人的 OAuth 保护资源」，后者是「作为资源服务器验证别人的 token」。

**`mcp-app-runtime` 的角色**：目录内 25 文件，含 `McpAppAudit` / `McpAppHistory` 两个实体、`McpAppAuditService`、`McpAppHistoryStoreService` / `McpAppHistoryService`、`McpAppInstanceStoreService`、`McpAppToolApprovalService`、`middleware-mcp-apps.service.ts`。它由 `xpert-toolset.module` 注册并由 `McpAppsController`（`@Controller('mcp-apps')`）暴露。与客户端的交叉点是 `app-support.ts`（65 KB，`registerMcpAppInstance` / `restoreMcpAppInstance` / `createMcpAppInstanceToken` / `verifyMcpAppInstanceToken` / `installMcpToolAppMetadataBridge` / `registerMcpAppInstance` 后的持久化等待）与 `mcp-app-execution-context.ts` 的 `readMcpAppExecutionContext`。与发布侧的交叉点是 `McpAppBundleService`——它只读 `LOADED_PLUGINS` 取插件 bundle 根，`realpath` 后强制入口落在根内且 `size <= 2 MiB`，产出 `ui://xpert/<publicationId>/<pluginName>/<capabilityKey>` 形式的资源，`_meta.ui` 携带 title/refresh/description/csp/permissions。

**另外两处邻域**：`mcp-files.controller.ts` 与 `mcp-files.service.ts` 把「个人文件」做成能力——`authorize` 先鉴权再 `WeakMap` 绑定请求上下文（注释：`authenticate before buffering uploads; bind storage to the verified user, never request fields`），要求 `principal.subjectType === 'user'`、scope 含 `files:read`/`files:write`/`*`、且发布单 `runtime.files.type === 'user'`，单文件上限 256 MiB。`mcp-subscription.service.ts` 用 Redis 频道 `xpert:mcp:publication-events` 做跨副本广播（`publishCatalogChanged` / `publishTaskUpdated` / `publishAccessInvalidated`），Redis 缺失时降级为进程内。

## 8. 设计模式与热点路径

**模式清单**（均为代码可见事实）：
1. **适配器**：`NestSSEAdapter`（NestJS HTTP ↔ `SSEServerTransport`）、`LangChainMcpConnection`（`MultiServerMCPClient` ↔ `McpConsumer`）、`_BaseToolset` 子类 `MCPToolset`。

## 10. 技术债与未确认项

1. **`MCPModule` 无装配点**：全仓搜 `MCPModule` 仅命中 `mcp.module.ts` 自身；`BaseMCPController` 的 `mcp/sse` / `mcp/messages` 与协议侧 stdio 分支均未接线。是「未确认」而非「不存在」——可能由外部宿主按需 `register()`。`[推测：也可能已被发布侧完全取代而残留]`
2. **`createProMCPClient` 是桩**：直接返回 `{ client: null, destroy: null, logs: null }` 并 `void _runtimeContext`，因此 `environment.pro === true` 时 `MCPToolset.initTools` 会拿到 `null` client。`[推测：Pro 实现位于闭源分支或外部包]`
3. **MCP OAuth 属 Pro 能力**：`assertMcpOAuthEnabled` 在 `environment.mcpOAuthEnabled === false` 时抛 `MCP OAuth is available only in Xpert Pro.`；开源环境的下拉配置面（`oauth-policy` 三个端点与 metadata 端点）全部 403，`assertAuthMethods` 含 `oauth` 时也拒绝。
4. **`mcp_publication_capability.toolsetId` 与 `mcp_capability_catalog.toolsetId` 无 FK**：是刻意的可诊断性取舍（注释明确），代价是被删工具集的残绑定只能靠读取期对账暴露（`reviewStatus='required'`），无 DB 级联清理。
5. **变更分类逻辑在 ① 的包里**：`hashMcpCapabilityDescriptor` / `compareMcpCapabilityDescriptors` 位于 `src/tool-runtime/capability-descriptor.ts`，本子域只调用。发布链的 breaking 判定实际上由 ① 维护，跨子域改动风险高。
6. **`_meta` 桥是临时兼容层**：`meta-artifact-bridge.ts` 与 `app-support.ts` 的多处 monkey-patch 依赖 `@langchain/mcp-adapters` 内部结构（`_transportInstances` / `_abortController` / `_eventSource` / `_sessionId` 均以 `Reflect` 读取），升级适配器版本即可能失效。
7. **`revision` 不是并发控制**：`mcp_task.revision` 是普通 `int`（非 `@VersionColumn`），全域无乐观锁；并发保护实际来自唯一索引 + 单 worker（`concurrency: 4`）。
8. **协议版本口径不统一**：发布侧固定 `'2026-07-28'`，协议侧无显式声明；`mcp-legacy-sessions.ts` 的 `legacySessionSnapshot` 用 sha256 快照作会话有效性依据，进程内 TTL 30 分钟 / 上限 256，无跨副本共享。
9. **`mcp_runtime_instance` 的 180 天保留期只有查询侧窗口**：未见清理作业（`@Cron` / `@Interval` 在本目录 0 命中）。
10. **`mcp` 目录 0 spec**：协议侧完全无测试覆盖。`[推测：因未接线导致测试缺位]`

## 11. 设计维度

**维度一：信任边界的位置**——本子域把「信任」放在三个不同层次，且**全部以宿主而非调用方为真值来源**。① 认证层：`McpAuthenticationService` 只认 `Bearer <token>` 两段式，API Key 用 `timingSafeEqual` 比对 sha256，OAuth 用 `jwtVerify` + 可选 introspection 双通道。② 授权层：`McpPublicationAuthorizationService` 强制三元（tenant/publication/organization）一致 + 组织成员 `isActive`，`service_account` 显式放弃用户身份（返回 `null`）。③ 执行层：`McpTaskExecutionService.run` 与 `McpFilesService.authorize` 在延迟节点重做全套校验，并额外要求 `runtime` 配置与入队时逐字节相等。反面证据同样明确：`mcp_json_schema` 校验失败**不回显提交值**、`argumentSummary` **不写参数值**、`errorCode` 只取错误名——脱敏是逐点设计而非统一中间件。

**维度二：可变性的分级治理**——八张表按可变性分成四档，每档用不同机制兜底。**只追加**：`mcp_invocation_audit`（`requestId` 唯一）用 `RESTRICT` 阻断发布单硬删。**幂等追加**：`mcp_task` 用 `idempotencyKey` + `inputHash` 让「重放」与「新请求」可区分，并把并发兜底放在唯一冲突后的二次查询。**整体替换**：`mcp_capability_catalog` 与 `mcp_publication_capability` 用事务 delete + save 重建，靠唯一索引约束形状。**开闭而非增删**：`mcp_api_key.revokedAt` / `mcp_publication_access.disabledAt` 用时间戳表达撤销，行不消失。这套分级让「审计不可删」「绑定可重建」「密钥可追溯」三种语义各自成立，代价是 FK 语义必须逐表记忆（`RESTRICT` 仅一处、`CASCADE` 五处、无 FK 两处）。

## 12. 结论

本子域的实现重心落在发布侧：`McpPublicationRuntimeService.handle` 是唯一入口且编排次序固定（认证 → 授权 → 限流 → 能力对账 → 订阅/任务协议分流 → SDK handler），`McpPublicationService.resolveRuntimeCapabilities` 是唯一的能力对账面（既做 hash 对齐又把 breaking 变更升级为 `reviewStatus='required'`），`McpTaskService` + `McpTaskExecutionService` 构成「入队幂等 + worker 重授权」的双保险。协议侧 `src/mcp/**` 是完整但未接线的通用封装，客户端 `provider/mcp/**` 是 ① 与 ② 的接口面且承担最重的进程管理（stdio runner）。

三个实现层结论：① **信任只来自宿主**——审批、runtime 配置、文件作用域、组织准入四处都有逐字注释禁止调用方注入，且都在延迟节点重校验；② **脱敏是逐点的、不是统一的**——审计只存 keys/bytes，schema 报错只报路径，日志只打 `requestId`/`traceId`/`method`/`toolName`/`status`/`durationMs`；③ **快照与台账必须成对演进**——`descriptorSnapshot` + `descriptorHash` 是能力变更可分类的前提，任何只写一侧的改动都会让审核门槛失真。

需要长期盯的四个点：`MCPModule` 的装配真空、`createProMCPClient` 桩的分支可达性、`_meta` 桥对 `@langchain/mcp-adapters` 内部结构的反射依赖、以及 `mcp` 目录 0 spec 的测试空白。
