## 3. 需 PG / 子进程 / 网络的用例

### 3.1 PostgreSQL

**本子域 33 个 spec 全部不需要真实 PostgreSQL**：在 `mcp-publication/` 与 `provider/mcp/` 内搜索 `DATABASE_URL` / `POSTGRES` / `describe.skip` / `testcontainers` 均 **0 命中**。仓储全部以 mock 提供（如 `mcp-publication.service.spec.ts` 手写 `rawBuilder(...)` 与 `repository<T>({ find, createQueryBuilder })`；`mcp-task.service.spec.ts` 用内存数组 + `createTaskRepository(stored)` 模拟）。因此**唯一索引、`select:false`、`RESTRICT` 级联这三类语义只被元数据层断言覆盖**（`entities.spec.ts` 读 `getMetadataArgsStorage()`），不被真实 DB 行为覆盖。

**需要 PG 的分界**：本域唯一确认需要真实数据库的集成测试在邻域——`agent-plugin/maintenance/package-maintenance.integration.spec.ts` 以 `AGENT_PLUGIN_TEST_DATABASE_URL` 门控（缺失即 `describe.skip`），属 ③ 子专家范围。

`[推测：`mcp_publication_capability` / `mcp_task` 的唯一索引冲突兜底（`23505` 分支）在现有 spec 中通过 mock 抛错触发，真实 PG 下的行为无覆盖]`

### 3.2 子进程（stdio）

- `mcp-stdio-runtime.audit.spec.ts` **不 spawn 真实子进程**：它直接调 `manager.prepareServer(...)` 并断言审计事件与 fail-closed 行为，`XPERT_MCP_STDIO_RUNTIME_ENABLED` 用 `process.env` 开关后 `afterEach` 还原。
- **`mcp-stdio-runner.js` 本身无 spec**：`parseSpec` / `terminate` / `killChild`（含 `process.kill(-pid)` 进程组杀）仅在 `client-factory.spec.ts` 的文件系统 fixture 中被间接引用，**未被真实执行**。
- `client-factory.spec.ts` 用 `mkdtempSync` + `realpathSync` 造临时目录做路径边界测试，`afterEach` 清理 `tempRoots`——**纯文件系统，无网络、无子进程**。
- `app-support.spec.ts` 与 `meta-artifact-bridge.spec.ts` 全程 mock `@langchain/mcp-adapters`，不发起真实连接。

### 3.3 网络

**`mcp-oauth.service.spec.ts` 是本子域唯一接管网络的 spec**：`beforeAll` 保存 `global.fetch`，用 `jest.fn(async (input) => ...)` 覆写，构造 OIDC discovery metadata 与 JWKS 响应；`afterEach` 还原 `originalFetch`。覆盖点包括：
- 签名 token 验证 + subject 映射；
- 授权服务器报告 token 已撤销时 fail-closed；
- introspection 凭据加密且密文不外泄；
- 生产环境回环地址 issuer 在发起 discovery **之前**即拒绝；
- **不跟随 OAuth discovery 重定向**（用 `Response.redirect(..., 302)` 验证）。

`mcp-oauth-metadata.controller.spec.ts` 与 `mcp-publication-management.controller.spec.ts` 通过 `environment.mcpOAuthEnabled` 开关验证开源 403 分支，**不联网**。

`mcp-rate-limit.service.spec.ts` 与 `mcp-subscription.service.spec.ts` 使用 **mock Redis**（前者 mock `REDIS_CLIENT`；后者以 `@Optional()` 注入为 undefined 走降级）；`mcp-module-wiring.spec.ts` 只断言模块元数据里 `imports` 含 `RedisModule`，**不建立真实 Redis 连接**。

## 4. 测试缺口

按风险从高到低：

1. **协议侧 `src/mcp/**` 零覆盖（0 spec）**：`MCPService.scanAndRegisterProviders` 的装饰器反射注册、`NestSSEAdapter` 的 `activeTransports` 会话生命周期与 404 语义、`handleSSEConnection` 中「不手动 start」这一注释级约束、`convertParametersToZod` 的类型回落——全部无测试。**这是本子域最大的测试空白。**
2. **发布链无端到端集成测试**：`mcp-publication-runtime.protocol.spec.ts` 用 `Test.createTestingModule` + mock 掉 `McpPublicationService` / `McpAuthenticationService` / `ToolRuntimeService`，覆盖的是**协议编解码与编排次序**，不是「真实 DB + 真实工具集 + 真实 HTTP」的端到端。`handle` 里的 `runWithCapturedRequestContext`、`applicationTracing.withRemoteContext` 与 `McpLegacySessions` 三者的真实交互无覆盖。
3. **stdio 端到端缺失**：`mcp-stdio-runner.js` 从未被真实 spawn；`XPERT_MCP_STDIO_RUNTIME_ENABLED=true` 下的「子进程起 → touch 续期 → 空闲超时 → SIGTERM/SIGKILL」链路、`writeFileSync` 类 `initScripts` 的真实执行、`assertTenantLimit` 的并发上限均无覆盖。
4. **OAuth introspection 真实端点无覆盖**：`introspectToken` 的 HTTP 调用在 spec 中由 `global.fetch` mock 承载，`guardedOAuthFetch` 的「最大字节截断（`readBoundedResponseBody`）」「非公开网段阻断（`assertPublicResolution`）」「内容长度预检」等分支**只在 discovery 路径被间接验证，introspection 路径未见独立用例**。
5. **`descriptorHash` 变更分类的端到端无覆盖**：`compareMcpCapabilityDescriptors` 自身的 spec 在 ① 的 `tool-runtime/capability-descriptor.spec.ts`；本子域 `resolveRuntimeCapabilities` 中「兼容 → 就地更新 binding + `publishCatalogChanged`」与「breaking → `reviewStatus='required'` + `reviewReason`」的完整链路在 `mcp-publication.service.spec.ts` 中覆盖程度**未逐条核对**，`[推测：覆盖偏浅]`。
6. **FK `onDelete` 语义无行为测试**：`mcp_invocation_audit` 的 `RESTRICT`（发布单不可带审计硬删）、五处 `CASCADE`、两处「刻意无 FK」的残绑定场景——`entities.spec.ts` 只断言表名与列属性，**不看关系元数据**；真实 PG 下的删除行为无覆盖。
7. **`mcp-consumer` / `mcp-app-runtime` 的 spec 未逐条核对**：本批次只确认文件存在与 `mcp-module-wiring.spec.ts` 的结构断言。
8. **`mcp_inputSchema` 的方言分支**：`mcp-input-schema.spec.ts` 仅 2 条用例，draft-07 / 2019-09 / 2020-12 三分支与「不支持方言抛错」是否全覆盖**未逐条核对**。

## 5. 结论

本子域的测试呈**强不对称**：发布侧 24 个 spec / ≥138 条用例，覆盖了协议编解码、管理面、密钥、OAuth、审计、任务、文件与实体元数据，且在 `mcp-oauth.service.spec.ts` 中做到了唯一一处真实网络面接管（含「不跟随重定向」「回环地址拒绝」这类安全分支）；客户端侧 9 个 spec / 44 条用例，靠 mock 适配器覆盖三传输装配、MCP App 桥、任务状态与 fail-closed；而**协议侧 `src/mcp/**` 是 0 spec 的真空**。

三条可执行结论：
1. **默认无外部依赖，跑法一致**：33 个 spec 全部走 `node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts --runTestsByPath <spec>`，不需要 PG、不需要 Redis；网络与子进程分别只在 `mcp-oauth.service.spec.ts` 与 `mcp-stdio-runtime.audit.spec.ts` 有受控代偿。加 `-t` 可做用例级过滤。
2. **元数据层断言是当前唯一的「结构性回归网」**：`entities.spec.ts` 用 `getMetadataArgsStorage()` 锁定了 8 张表名与 `keyHash`/`encryptedSecret`/`argumentSummary`/`requestPayload`/`inputRequests`/`resultRef` 的 `select:false`，`mcp-module-wiring.spec.ts` 用 `MODULE_METADATA.IMPORTS` 锁定了 `RedisModule` 依赖与 `McpConsumerCapabilitiesService` 的构造签名。**任何改动这两处元数据的重构必须同步改这两个 spec**，否则「隐藏列被放开」这类事故不会被任何测试发现。
3. **优先补齐三块**：协议侧 `MCPService`/`NestSSEAdapter` 的单元测试（现为 0）、stdio runner 的真实子进程端到端（现为 0）、`descriptorHash` 变更分类在 `resolveRuntimeCapabilities` 上的完整行为用例（现覆盖偏浅 `[推测]`）。前两块补齐后，本子域才算从「发布侧单腿站立」变为双腿。
