## 3. 运行命令

`server-ai` 的 jest 配置：`preset: '../../jest.preset.js'`、`testEnvironment: 'node'`、TS 走 `ts-jest`（`tsconfig.spec.json`）、JS/MJS 走 `babel-jest`；`moduleNameMapper` 把 `@xpert-ai/server-core`、`@xpert-ai/contracts`、`@xpert-ai/plugin-sdk` 直指源码目录（**无需先构建依赖包**）；无全局 setup/setupFiles，fixture 各 spec 自带。

```bash
# 1) 单文件（本子域最常用）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/xpert-toolset/xpert-toolset.service.spec.ts

# 2) 多个文件一次跑（工具集主体）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/xpert-toolset/xpert-toolset.service.spec.ts \
                   packages/server-ai/src/xpert-toolset/mcp-runtime-audit.service.spec.ts \
                   packages/server-ai/src/xpert-toolset/commands/handlers/get-tools.handler.test.ts

# 3) 执行面（tool-runtime）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/tool-runtime/tool-runtime.service.spec.ts \
                   packages/server-ai/src/tool-runtime/toolset-scope.spec.ts \
                   packages/server-ai/src/tool-runtime/workspace-scope.spec.ts \
                   packages/server-ai/src/tool-runtime/capability-descriptor.spec.ts

# 4) 按用例名过滤（-t）——单条断言级复现
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/tool-runtime/toolset-scope.spec.ts -t 'mcp'

# 5) 按目录整批（① 三个目录）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --testPathPattern 'src/(xpert-toolset|xpert-tool|tool-runtime)/'

# 6) 需要真库时额外注入环境变量（默认 skip）
AGENT_PLUGIN_TEST_DATABASE_URL=postgres://… \
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/agent-plugin/maintenance/package-maintenance.integration.spec.ts
```

注意：`provider/mcp/**` 的 9 个 spec 属 ②，但同一目录下的 `mcp-stdio-runtime.audit.spec.ts` 会直接覆盖 ① 的审计 sink 行为，改 `McpRuntimeAuditService` 时应连带跑它；`mcp` 模块 0 spec，任何「跑 MCP 协议端点」的期望不落在本子域。

## 4. 需外部依赖的用例

| 依赖 | 影响的 spec | 判定 |
|---|---|---|
| **真实 PostgreSQL** | ① 范围**无**；最近的是 `agent-plugin/maintenance/package-maintenance.integration.spec.ts`（`AGENT_PLUGIN_TEST_DATABASE_URL` 未设即 `describe.skip`；该用例属 ③） | ① 的服务 spec 全用 fake repository / queryBuilder，无 PG 依赖 |
| **子进程 stdio（spawn）** | ① 范围**无**。`mcp-stdio-runtime.audit.spec.ts` 只到 `prepareServer`（不 spawn）、`attachClient` 用假 client；`provider/mcp/client-factory.spec.ts` 通过 `process.env.XPERT_MCP_STDIO_RUNTIME_ENABLED='true'` 走配置分支但连接仍是 mock | 实测在本子域 spec 中检索 `spawn|execFile|mcp-stdio-runner` **0 命中** ⇒ `runnerPid`/`childPid` 解析与僵尸回收**未被验证** |
| **网络（HTTP 出网）** | `utils/parser.spec.ts`（纯文本解析，不出网）、`get-odata-remote-metadata.handler.test.ts`（handler 级，HTTP 客户端被 mock） | ① 的 schema 解析与远端拉取在 spec 里都被隔离；无真实出网断言 |
| **Redis / Bull 队列** | ① 范围**无**。`ToolRuntimeService` 依赖 `MANAGED_QUEUE_SERVICE_TOKEN` 与 `McpSubscriptionService`，spec 中以 fake 注入 | `[推测]`：若新增队列行为断言，需引入 fake 而非真 Redis |
| **环境变量（非外部服务）** | `XPERT_MCP_STDIO_RUNTIME_ENABLED`（stdio 开关）、`NODE_ENV`（② 的 OAuth 用例） | 都在 spec 内自设并 `afterEach` 还原，**不是环境前置** |
| **文件系统** | `ListBuiltinToolsHandler`/`ToolProviderIconHandler`/`ListBuiltinToolProvidersHandler` 的 spec 会触达 `yaml`/`_assets` 读取路径 | 依赖仓库内静态资源文件存在（`packages/server-ai/src/xpert-toolset/provider/builtin/**`），无外部服务 |

结论：**① 子域的 26 个文件全部可在无任何外部服务的环境下执行**（除 upstream 未设变量即 skip 的 ③ 集成用例）。

## 5. 缺口

1. **无守卫级断言**：`ToolsetGuard`（5 分钟缓存的三条分支：命中、作者命中、`canAccess` 命中/拒绝）**没有 spec 文件**（`xpert-toolset/guards/*.spec.ts` 不存在）；`WorkspaceAuthoringGuard`、`McpRuntimeController.assertSuperAdmin` 同样无专用用例。这正好是 01-架构「关键不变量」里最需要回归的三条。
2. **`xpert-toolset.controller.ts` 无控制器 spec**：18 个端点（含 `@Sse` 流、`GetDefaultTenantQuery` 回落、`toolset:avatar:*` 缓存分支）无逐条用例，前端契约只能靠 `xpert-toolset.service.spec.ts` 间接保障。`by-workspace` 的 `'null'/'undefined'` 分支与 `ToolsetPublicDTO` 的字段裁剪无断言。
3. **执行面的边界语义覆盖不均**：`tool-runtime.service.spec.ts` 覆盖装配与归一，但「四条越界拒绝」中至少要对齐——`McpToolsetSnapshotApiOnly`（非 api 源传快照）、`McpToolsetSnapshot{Identity,Tenant,Workspace,Organization}Mismatch`、`McpToolsetWorkspaceMismatch`、`McpOrganizationPublicationWorkspaceToolset`；`toolset-scope.spec.ts` 已覆盖 `persistedToolsetWhere` 的组合，但 controller/handler 级未串联。
4. **`executeTool` 的 `MCPToolset && serverName && remoteName` 与 `remoteTaskMode` 分支（含 `callMcpTaskTool`）无 ① 侧用例**（相关逻辑在 ② 的 `mcp-toolset.task.spec.ts`）。

## 6. 结论

判定：**✅ 可跑（本报告不实跑，只给命令与判据）**。① 子域 26 个相关文件（17 `.spec.ts` + 9 `.test.ts`）全部不连外部服务：Repository/QueryBuilder/HTTP 客户端/队列/Redis 全为 mock 或 fake，`moduleNameMapper` 已把三个 workspace 包指向源码，因此不需要先构建依赖包；唯一需要真库的集成用例在 ③（`AGENT_PLUGIN_TEST_DATABASE_URL`，默认 `describe.skip`）。运行入口统一为 `--config packages/server-ai/jest.config.ts --runTestsByPath <spec>`，单个断言级复现用 `-t`。

覆盖结构上，本子域呈现**「执行面与纯函数覆盖好、边界与守卫覆盖差」**的形态：`tool-runtime` 的四个纯函数/装配 spec（`toolset-scope`/`workspace-scope`/`capability-descriptor`/`tool-runtime.service`）与 `utils/parser.spec.ts` 是质量最好的一批；而 `ToolsetGuard` 的缓存语义、`xpert-toolset.controller` 的 18 个端点、`afterLoad` 的 schema 覆盖行为、`closeLostActiveRecords` 的收敛、`spawn` 进程管理五处**完全没有断言**——恰好是 01-架构「关键不变量」清单里排前几位的项。新增改动若触碰这些点，应先补最小回归用例再改代码。
