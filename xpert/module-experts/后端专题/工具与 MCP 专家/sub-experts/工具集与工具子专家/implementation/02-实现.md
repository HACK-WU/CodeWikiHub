## 1. 工具集 CRUD 与类型 / provider 选择

HTTP 面是 `XpertToolsetController extends CrudController<XpertToolset>`：`GET /` 与 `GET by-workspace/:workspaceId` 都先 `service.afterLoad()` 再包 `ToolsetPublicDTO`；`GET tags` 返回 `defaultToolTags`；`GET providers` / `GET provider/:name` 走 `ListBuiltinToolProvidersQuery` 并包 `ToolProviderDTO`。写面继承 CRUD，`XpertToolsetService.update(id, entity)` 被**显式收窄**到 `updateToolset`（注释逐字：`Isolate TypeORM's recursive update type; business callers use the shallow method to keep ts-node inference bounded.`），实现是 `super.findOne(id)` + `assign` + `save`——即**浅更新、无 PATCH 语义校验**。

`create` 与 `save` 是仅有的两个写入口，都先 `assertValidTagAssociations(..., TagCategoryEnum.TOOLSET)`；`getAllByWorkspace(workspaceId, data, published, user)` 的分支很关键：`workspaceId` 为空/字符串 `'null'`/`'undefined'` → `{ workspaceId: IsNull(), createdById: user.id }`（私有工具集），否则先 `assertWorkspaceAuthoringAccess(workspaceId)` 再按 workspace 过滤；`published` 时追加 `publishAt: Not(IsNull())`。

`createBuiltinToolset(provider, entity)` 是「类型/provider 选择」的唯一入口：先 `ListBuiltinToolProvidersQuery([provider])`，缺失即 `ToolProviderNotFoundError`；再由 `EnvStateQuery`（有 workspaceId 时）与 `agentMiddlewareRuntime.createScopedApi({tenantId, organizationId})` 组装 `BuiltinToolset` 参数；然后 `validateCredentials(entity.credentials)`；最后**强制** `category = XpertToolsetCategoryEnum.BUILTIN`、`type = provider`，并用 provider 身份生成默认 `name`/`avatar`（`ToolProviderDTO` 拼 `…/api/xpert-toolset/builtin-provider/:name/icon`，带 `?org=`）。带 `entity.id` 时退化为 `updateToolset`。

类型口径：契约侧 `XpertToolsetCategoryEnum = builtin | api | mcp | workflow(@deprecated)`，实体列 `category` 是 `varchar(10)` 且额外允许 `'command'`；`schema`/`schemaType`（`openapi_json | openapi_yaml`）只服务 API 型工具集。

章节来源：[xpert-toolset.controller.ts](file://packages/server-ai/src/xpert-toolset/xpert-toolset.controller.ts)（关键符号：XpertToolsetController.getAllByWorkspace / getAllToolProviders / createBuiltinInstance）、[xpert-toolset.service.ts](file://packages/server-ai/src/xpert-toolset/xpert-toolset.service.ts)（关键符号：XpertToolsetService.updateToolset / getAllByWorkspace / createBuiltinToolset）、[dto/tool-provider.dto.ts](file://packages/server-ai/src/xpert-toolset/dto/tool-provider.dto.ts)（关键符号：ToolProviderDTO 构造的 icon URL）

## 2. provider 体系

`provider/index.ts` 只做导出聚合（`openapi` / `builtin` / `odata` / `mcp`），真正的分流发生在 `ToolRuntimeService.loadToolsets` 的 `switch (toolset.category)`：`BUILTIN` → `createBuiltinToolset(toolset.type, toolset, context)`；`API` → `type === 'openapi'` 走 `OpenAPIToolset`、`type === 'odata'` 走 `ODataToolset`、其余抛 `ToolProviderNotFoundError`；`MCP` → `new MCPToolset(...)`（②）；其它 category 抛错。

**builtin 的声明与注入**：`BUILTIN_TOOLSET_REPOSITORY` 是一个静态注册表（`baseUrl = 'packages/server-ai/src/xpert-toolset/provider/builtin/'` + 9 个提供者类：Planning、Tavily、SearchAPI、Email、Bing、DingTalk、Slack、Discord、Serper）。`createBuiltinToolset(provider, toolset, params)` 先按 `provider` 静态命中并 `new providerTypeClass(toolset, params)`；**未命中时回落 `CreateToolsetCommand`**（由平台插件注册的 `ToolsetRegistry` 策略实现）→ 仍未命中才抛 `ToolProviderNotFoundError`。工具声明侧由每个 provider 自己的类决定：以 `PlanningToolset` 为例，`static provider = 'planning'`，`initTools()` 按 `toolset.tools.filter(_ => _.enabled)` 的 `tool.name` 逐个 `switch` 出 `PlanningCreateTool`/`PlanningListTool`/`PlanningDeleteStepTool`/`PlanningUpdateStepTool`，并额外提供 `getVariables()` 声明 `plan_title`/`plan_steps` 两个 LangGraph 状态变量。⇒ **「有哪些工具」由库内 `xpert_tool` 行决定，「工具如何实现」由 provider 类决定**。

**openapi 的解析与测试**：`OpenAPIToolset extends BaseToolset<OpenAPITool>`，`providerType = API`，构造时把 `toolset.tools.filter(_ => isEnableTool(_, this.toolset))` 逐条生成**动态子类**（`static lc_name() => item.name`，即工具名进入 LangChain 的可辨识名），`getTool(name)` 线性查找到不存在即 `throw new Error('tool … not found')`（非 `ToolNotFoundError`）。解析链有三条：`POST provider/openapi/remote`（`GetOpenAPIRemoteSchemaQuery` 拉远端 schema）、`POST provider/openapi/schema`（`ParserOpenAPISchemaCommand` → `ApiBasedToolSchemaParser.autoParseToToolBundle`，返回 `{ schema_type, parameters_schema, credentials_schema, warning }`，其中 `credentials_schema` 固定三项：`auth_type`(none|api_key)、`api_key_header`(默认 `api_key`)、`api_key_value`）、`POST provider/openapi/test`（直接派 `TestOpenAPICommand`，不建工具集）。

**odata 的结构化生成**：`ODataToolset extends BaseToolset<ODataTool>`，构造时按 `toolset.tools?.filter(_ => _.enabled)`（注意此处用 `enabled` 而非 `isEnableTool`）建动态子类；`getODataService()` 用 `@sap_oss/odata-library` 的 `Service({ url: toolset.options.baseUrl, auth })`，`credentials.auth_type` 缺失即 `ToolProviderCredentialValidationError('Missing auth_type')`，仅支持 `ApiAuthType.BASIC`。`getToolsSchema()` 是**确定性生成器**：对每个 entitySet 生成四件工具 `Create_/Get_/Query_/Delete_ + name`，参数取自 `entityType.Key` 与 `Properties`（过滤 `Visible`），类型经 `mapODataTypeToOpenAPI`（`Edm.String→string`、`Edm.Decimal→number`、`Edm.DateTime→number`，**其余类型返回 undefined**）。配套端点 `POST provider/odata/remote`、`POST provider/odata/schema`。

**工具 schema 生成的两条路径**：(a) 库内 schema（`xpert_tool.schema.parameters`）经 `utils/parser.ts` 的 `ApiBasedToolSchemaParser`（`convertPropertyValueType` 做值类型转换）与 `ToolSchemaParser.parseZodToJsonSchema` 互转；(b) 运行时探测——内置 provider 由 `ListBuiltinToolsQuery` 从插件注册表（`provider.createTools()` → `parseZodToJsonSchema`）或从 `…/provider/builtin/<name>/tools/*.yaml` 读取（按 `_<name>.yaml` 前缀排除，`getPositionMap` 决定顺序，**结果按 provider 名缓存在内存 Map**）。

章节来源：[provider/builtin/index.ts](file://packages/server-ai/src/xpert-toolset/provider/builtin/index.ts)（关键符号：BUILTIN_TOOLSET_REPOSITORY / createBuiltinToolset）、[provider/builtin/planning/planning.ts](file://packages/server-ai/src/xpert-toolset/provider/builtin/planning/planning.ts)（关键符号：PlanningToolset.provider / initTools / getVariables）、[provider/openapi/openapi-toolset.ts](file://packages/server-ai/src/xpert-toolset/provider/openapi/openapi-toolset.ts)（关键符号：OpenAPIToolset 构造函数 / getTool）、[provider/odata/odata-toolset.ts](file://packages/server-ai/src/xpert-toolset/provider/odata/odata-toolset.ts)（关键符号：ODataToolset.getToolsSchema / getODataService / mapODataTypeToOpenAPI）、[commands/handlers/parser-openapi-schema.handler.ts](file://packages/server-ai/src/xpert-toolset/commands/handlers/parser-openapi-schema.handler.ts)（关键符号：ParserOpenAPISchemaHandler.execute / credentials_schema）

## 3. 工具发现链

**库内发现（HTTP 读路径）**：`GET :toolsetId/tools` → `service.findOne(toolsetId, { relations: ['tools'] })` → `afterLoad([toolset])` → 返回 `hydrated.tools`。`afterLoad` 做两件事：按 `category === BUILTIN` 从 `ListBuiltinToolProvidersQuery` 回填 provider tags；`hydrateBuiltinToolSchemas` 对每个内置 provider 执行一次 `ListBuiltinToolsQuery(provider)`，用最新工具定义覆盖 `label ??=`/`description ??=`/`schema =`。

**内置工具清单**：`ListBuiltinToolsHandler` 优先走插件注册表（`ToolsetRegistry.get(provider)` → `createTools()` → 映射为 `IBuiltinTool`，`schema` 由 `parseZodToJsonSchema` 生成），失败才回落 yaml 目录读取；两级都按 provider 缓存。查询对象支持 `names` 过滤（`tool.identity.name` 精确匹配）。

**装配式发现（运行时路径）**：`ToolsetGetToolsCommand(ids, environment?)` → `ToolsetGetToolsHandler`：从 `RequestContext` 取 `currentUserId`/`currentTenantId`/`getOrganizationId`，`principal` 有用户即 `{type:'user', id, userId}`，否则 `{type:'service_account', id:'xpert-runtime'}`，随后 `toolRuntime.loadToolsets({...})`。`ids` 为 `null`/`undefined`/`[]` 时经 `loadToolsets` 的空列表短路返回 `[]`。

**远端探测（MCP）**：`POST provider/mcp/tools` 标 `@Sse()`（注释逐字：`@Post @Sse There is a priority order.`），以 `Observable` + `RunnableLambda` 派 `MCPToolsBySchemaCommand`，事件分 `MESSAGE`（结果）与 `EVENT`（`ON_CHAT_EVENT` 进度），并用 `keepAlive(30000)` + `takeUntilClose(res)` 保活（② 的 `MCPToolsBySchemaHandler` 实现，本子域只负责路由与流）。

**provider 元数据发现**：`ListBuiltinToolProvidersHandler` 合并静态注册表（读 `<providerPath>/<name>.yaml`，按 name 缓存）与 `toolsetRegistry.list()`；插件提供者的 `identity.icon` 从 `{value|svg|image}` 里取首个非空字符串。图标字节由 `ToolProviderIconHandler` 产出：插件 `meta.icon` 支持 `IconDefinition`（`type==='svg'`）与历史形态（`{svg,color}`、`{image}`），静态 provider 读 `_assets/<icon 文件名>` 的 `readFileSync`，返回 `[Buffer, mimetype]`，由控制器 `res.end()` 直出。

章节来源：[commands/handlers/get-tools.handler.ts](file://packages/server-ai/src/xpert-toolset/commands/handlers/get-tools.handler.ts)（关键符号：ToolsetGetToolsHandler.execute / principal 分流）、[queries/handlers/list-builtin-tools.handler.ts](file://packages/server-ai/src/xpert-toolset/queries/handlers/list-builtin-tools.handler.ts)（关键符号：ListBuiltinToolsHandler.getBuiltinTools / getProviderServerPath）、[queries/handlers/list-builtin-providers.handler.ts](file://packages/server-ai/src/xpert-toolset/queries/handlers/list-builtin-providers.handler.ts)（关键符号：ListBuiltinToolProvidersHandler.getProviderSchema / getPluginIconValue）、[queries/handlers/get-provider-icon.handler.ts](file://packages/server-ai/src/xpert-toolset/queries/handlers/get-provider-icon.handler.ts)（关键符号：ToolProviderIconHandler.resolveIcon / normalizeSvgResource）、[xpert-toolset.controller.ts](file://packages/server-ai/src/xpert-toolset/xpert-toolset.controller.ts)（关键符号：XpertToolsetController.getMCPTools / getToolsetTools）

## 4. 工具执行面 tool-runtime

**谁调**：① 的 `ToolInvokeHandler`（HTTP 测试与 API）、① 的 `ToolsetGetToolsHandler`（Agent 装配）、② 的发布运行时（`executeMcpCapability` 族）。三种调用方共享入口，但只有 Agent 侧会长期持有 `_BaseToolset` 实例。

**如何寻址**：`loadToolsets(request)`：空 `toolsetIds` 短路返回 `[]`；`resolveToolsets` 先去重 id，再处理 `toolsetSnapshots`（**仅 `source === 'api'`**，逐个校验 id 属于请求集合、必须有 tenant+workspace、tenant/workspace/organization 必须一致，否则抛带 i18n key 的 `ToolProviderNotFoundError`），持久化部分用 `persistedToolsetWhere(request, workspaceId, persistedIds)` + `relations: ['tools']` 查库，最后**按请求顺序** `flatMap` 回填（查不到的静默丢弃）。随后逐工具集：`resolveToolRuntimeScope` 解析存储边界（`files`→`users`、`projectId`→`projects`、`workspaceDataScope==='user'`→`user-xperts`、否则 `xperts`）、`createScopedApi` 生成模型能力、按 category 建 runtime、再以 `WeakMap` 记住 `#runtimeToolsets` 与 `#runtimeHosts`（host 由 `createToolCredentialsApi(credentials)`、`subscriptions.eventsApiForToolset(...)` 与模型能力合成）。`attachDeclaredToolAdapters` 会给实现了 `getMcpCapabilityDefinitions()` 的工具集**动态追加**声明式工具（重名即抛 `ToolProviderNotFoundError`，并把 `toolset.tools` 一起替换）。

**executeTool 的语义**：先 `loadToolsets({...request, toolsetIds:[toolsetId]})`，取不到抛 `ToolNotFoundError('Toolset … was not found in the requested workspace')`；构造 `ToolExecutionContext`（含 `host`：`this.#runtimeHosts.get(toolset) ?? request.host ?? {}`）；`try` 内顺序为：`await toolset.initTools()` → 命中 **declared tool** 则 `executeDeclaredTool`（`inputSchema.parseAsync` → `definition.execute` → 若 `outputSchema` 与 `structuredContent` 同时在则再 parse）→ `MCPToolset && serverName && remoteName` 时按 `remoteTaskMode` 走 `callMcpTaskTool` 或 `callMcpTool`（**不** `initTools` 的普通工具路径）→ 否则 `toolset.getTool(name)`（不存在抛 `ToolNotFoundError`）并 `tool.invoke(arguments, { configurable: { ..., toolExecutionContext, tool_call_id: requestId } })`；`finally` 恒 `toolset.close()`（异常只 `logger.debug`）。**超时**不由本层提供，而是由宿主注入 `request.signal`（`AbortSignal`）与 provider 自身策略承担。

**结果与错误归一**：`normalizeToolResult` 把字符串 → `{content:[{type:'text',text}]}`；tool-result-like（有 `content`）→ 归一 `content`（text/image/audio/resource_link，未知项丢弃）+ `structuredContent` + `_meta`→`meta`（JSON 往返）+ `isError`；其它对象 → `{structuredContent: value}`。参数非对象时 `requireToolArguments` 抛 `MCP tool arguments must be an object.`。

**能力面（②侧入口但由①实现）**：`describeCapabilities` 只读 `McpCapabilityCatalog`（`toolsetId In`、`tenantId`、可选 `organizationId ?? IsNull()`、`enabled: true`），并把 `source.toolsetId` 覆写为**权威值**；`withCapabilityToolset` 统一支撑 `executeMcpResource`/`executeMcpPrompt`/`completeMcpCapability`——`MCPToolset` 直连，其它 provider 经 `requireCapabilityProvider(...).getMcpCapabilityDefinitions()` 查声明（缺失抛 `ToolProviderNotFoundError('… does not provide MCP capability handlers')`），`app` 类型直接抛能力缺失。

**用量记账**：`loadToolsets` 在 `getExecutionId ?? executionId` 存在时构造 `createExecutionModelUsageRecorder(…, usage => commandBus.execute(new XpertAgentExecutionRecordUsageCommand(executionId, usage)))`，并把 `reportUsage` 注入 `modelRuntime`（工具模型调用才计费）。

章节来源：[tool-runtime.service.ts](file://packages/server-ai/src/tool-runtime/tool-runtime.service.ts)（关键符号：ToolRuntimeService.loadToolsets / executeTool / withCapabilityToolset / normalizeToolResult / createExecutionRuntimeCapabilities）、[workspace-scope.ts](file://packages/server-ai/src/tool-runtime/workspace-scope.ts)（关键符号：resolveToolRuntimeScope）、[toolset-scope.ts](file://packages/server-ai/src/tool-runtime/toolset-scope.ts)（关键符号：persistedToolsetWhere）

## 5. xpert-tool 面

`XpertToolModule` 仅 `RouterModule.register([{ path: '/xpert-tool' }])` + `forFeature([XpertTool])` + `imports: [TenantModule, CqrsModule, XpertToolsetModule]`，providers 只有 `XpertToolService` 与 `CommandHandlers`。

- `POST test` → `XpertToolService.testTool(body)`：先按 `tool.toolsetId` 取库内工具集、按 `tool.id` 取库内工具，然后以 `{...toolDetail, ...omit(tool,'toolset'), toolset: toolset ?? tool.toolset}` 派 `ToolInvokeCommand`——即**入参可覆盖库内行**（测试语义）。
- `GET :id` → `getTool(id, { relations })`：强制并入 `relations: ['toolset']`；若工具集 `category === BUILTIN`，再用 `ListBuiltinToolsQuery(toolset.type, [tool.name])` 回填 `provider`（临时属性）、`label`、`description`、`schema`。
- `GET :id/faker` → `getParamsFaker(id)`：内置工具走 `ToolSchemaParser.parseZodToJsonSchema(tool.schema)` + `JSONSchemaFaker.generate`；**非内置**（API/MCP）走 `ToolsetGetToolsCommand([toolsetId], { workspaceId })` → `initTools()` → `getTool(name)` → 优先 `(tool as DynamicStructuredTool).lc_kwargs?.schema`，兜底 `parseZodToJsonSchema(toolInstance.schema)`，`finally` 中 `toolset.close()`（异常只 debug）。⇒ faker 是**唯一会为生成示例参数而建远端连接**的读端点。

`ToolInvokeHandler` 是执行面的最后一跳：从 `RequestContext` 取 tenant/org/user；**强制** `{...command.tool, enabled: true}`；要求 `toolset`、`tenantId`、`workspaceId` 三者齐备，否则 `BadRequestException('Tool invocation requires explicit tenant and workspace context.')`；按 `tool.schema.parameters` 的 `form`/`llm` 分组用 `ApiBasedToolSchemaParser.convertPropertyValueType` 转换入参；把工具集**脱库快照**化（`Object.assign(new XpertToolset(), toolset, { id: toolset.id ?? randomUUID(), tenantId, organizationId, workspaceId, tools: [tool] })`）后以 `source: 'api'`、`toolsetSnapshots: [snapshot]`、`executionId = requestId = randomUUID()` 调 `executeTool`；收集 `subscriber` 事件，有则返回 `{events, result}`；捕获 `error.name === 'ToolException'` 转 `ToolInvokeError`（注释逐字：`The MCP adapter identifies tool failures by name but does not export its error class.`）。

## 6. MCP apps 与运行时审计

**MCP apps HTTP 面（7 条端点）**：`McpAppsController('mcp-apps')` 全部透传到 `McpAppsService`——`GET :appInstanceId/history` 与 `POST :appInstanceId/resume` 用 `ZodValidationPipe(mcpAppHistoryQuerySchema)` 强制 `messageId`（失败消息 i18n key `server-ai:Error.McpAppHistoryQueryInvalid`）；`GET :appInstanceId/resource`、`POST :appInstanceId/rpc`、`POST :appInstanceId/approvals/:approvalId/{approve,reject}`、`DELETE :appInstanceId` 用 `McpAppReviveQuery` 携带复活凭证。服务内部是一整套**按实例鉴权 + 复活**逻辑：`assertAccessForInstance`/`assertTokenForInstance`/`assertReviveToken`/`assertReviveAccess`/`assertInstanceUser`/`assertMessageBootstrap`/`assertExpiredTokenForBootstrap`，`reviveInstance()` 会重建 toolset 客户端与执行上下文，`handleRpc()` 按 JSON-RPC 方法分派到 `tools/call`、`resources/read`、`ui/download` 等并使审批贯穿（`tools` 的 `requiresApproval`、`approval` 记录、失败回写 `rpcErrorCode`），`getResource()` 组装 CSP/permissions/prefersBorder 与 `toolInfo`。⇒ **App 实例的生命周期与审批全部在 ① 的服务层，实体与存储来自 `mcp-app-runtime`（②侧邻域）**。

**运行时审计服务**：`McpRuntimeAuditService implements OnApplicationBootstrap`，构造注入 `McpRuntimeInstanceEntity` 与 `PluginResourceInstallation` 两个 repository。写侧四个方法：`recordStarting`（写 `serverName`/`toolsetId`/`toolsetName`/`pluginManaged`/`pluginName`/`componentKey`/`pluginRuntimeId`/`xpertId`/`agentKey`/`executionId`/`conversationId`/`appInstanceId`/`origin`/`status`/`startedAt`/`idleExpiresAt`/`maxLifetimeExpiresAt`/`commandLabel`/`commandHash`/`policySnapshot`，并先用 `findResourceInstallation` 按 `pluginName`+`componentKey`+`runtimeId`+`workspaceId`+`xpertId` 反查安装台账补 `resourceInstallationId`）、`recordRunning`（`status`/`readyAt`/`startupDurationMs`/`runnerPid`/`childPid`/`idleExpiresAt`/`maxLifetimeExpiresAt`/`stderrTail`）、`recordClosed`（`status`/`closedAt`/`closeReason`/`durationMs`/pid/`stderrTail`）、`recordAppInstance`（条件 UPDATE 追加 `appInstanceId`）。启动期 `closeLostActiveRecords()` 按 `ACTIVE_RUNTIME_STATUSES` 批量收敛。读侧 `list(query, liveSnapshots)` 合并「库内历史行 + 内存活体快照」（`mergeLiveRecords` 用 live 值优先，`toLiveOnlyItem` 处理只在内存存在的实例），并配套 `listFilterOptions`/`distinctOptions`/`workspaceOptions`/`toolsetOptions`/`liveWorkspaceOptions` 生成筛选下拉；`toRuntimeManagerFilter(query)` 把审计查询参数翻译成 `mcpStdioRuntimeManager.list(filter)` 的过滤条件。保留期常量 `DEFAULT_RUNTIME_AUDIT_RETENTION_DAYS` 与 `defaultFromDate` 只作用于查询窗口。

**停机阀**：`McpRuntimeController('operations/mcp-runtimes')` 三个端点全部先 `assertSuperAdmin()`（`RequestContext.hasRole(RolesEnum.SUPER_ADMIN)`，否则 `ForbiddenException('Only SUPER_ADMIN users can manage MCP stdio runtimes')`）：`GET` 返回 `list(query, mcpStdioRuntimeManager.list(...))`；`POST :runtimeId/stop` → `closeRuntime(runtimeId, 'admin-stop')`；`POST kill` → `killByFilter(toRuntimeManagerFilter(body ?? {}), 'admin-kill')`。`runnerPid`/`childPid`/`stderrTail` 是**审计列**，进程本体的生成与回收在 ② 的 `mcp-stdio-runner`。

## 9. 热点路径

1. **`XpertToolsetService.afterLoad`**：每次列表/详情都要为每个内置 provider 各发一次 `ListBuiltinToolsQuery`（N 次查询 + 全量 schema 覆盖），是工具集列表页的固定放大开销。
2. **`ToolRuntimeService.loadToolsets`**：每次装配/执行都查库 + `resolveToolRuntimeScope` + `createScopedApi` + 按 category 建 runtime；MCP 类别还会建远端连接（启动成本由 ② 的 `startupTimeoutMs` 约束）。
3. **`hydrateBuiltinToolSchemas` 的 `Promise.all`**：并发发起但**没有并发上限**，provider 数与工具数同时大时是峰值来源。
4. **`ToolInvokeHandler`**：每次测试/API 调用都要造快照、查 `EnvStateQuery`、建工具集、`initTools()`、执行、`close()`——**无实例复用**。
5. **`XpertToolService.getParamsFaker`**：非内置工具必须真实建连（`initTools()`）才能取 schema 生成示例，属于「读端点触发远端副作用」。
6. **`McpRuntimeAuditService.list`**：一次请求内要跑库内分页 + 5 类筛选下拉（`listFilterOptions`/`workspaceOptions`/`toolsetOptions` + live 合并），表行数随时间线性增长（无清理作业）。
7. **`McpAppsService.handleRpc`**：每次 App RPC 都要鉴权（instance/token/revive 三重断言）、必要时复活 toolset 客户端、并在审批路径上写审计。

章节来源：[xpert-toolset.service.ts](file://packages/server-ai/src/xpert-toolset/xpert-toolset.service.ts)（关键符号：hydrateBuiltinToolSchemas / afterLoad）、[tool-runtime.service.ts](file://packages/server-ai/src/tool-runtime/tool-runtime.service.ts)（关键符号：ToolRuntimeService.loadToolsets 的 Promise.all）、[mcp-runtime-audit.service.ts](file://packages/server-ai/src/xpert-toolset/mcp-runtime-audit.service.ts)（关键符号：McpRuntimeAuditService.list / listFilterOptions）、[xpert-tool.service.ts](file://packages/server-ai/src/xpert-tool/xpert-tool.service.ts)（关键符号：XpertToolService.getParamsFaker）

## 11. 技术债与 hack

1. **凭据加密仍是注释**：`createBuiltinToolset` 内逐字保留 `// encrypt credentials` 与 `// credentials = tool_configuration.encrypt_tool_credentials(credentials)`；`credentials` 明文 json 落库，保护只到「不回显」。
2. **`ToolsetGuard` 无失效通道**：只缓存允许结果、缓存 5 分钟，全仓**未找到清除点**；被移出工作区/被转交的工具集在窗口内仍可读凭据。
3. **`XpertToolsetSubscriber` 空壳**：`afterLoad` 逻辑整段注释，能力迁到 `XpertToolsetService.afterLoad`；绕过服务层的仓储读不会自动回填（`[推测]`：这是为避开 TypeORM 生命周期里无法注入 `QueryBus` 的限制）。
4. **`XpertToolsetService` 的遗留命令表**：`registerCommand`/`executeCommand` + 私有 `commands: Map` 全标 `@deprecated` 且类上保留。
5. **`enabled` 与 `disabled` 双列并存**：`xpert_tool.enabled` 标 `@deprecated use disabled`，两列都可空；`isEnableTool` 做归一，但 `OpenAPIToolset` 用 `isEnableTool`、`ODataToolset` 与 `PlanningToolset.initTools` 直接筛 `_.enabled` ⇒ **同库数据在两类 provider 下可用性判定可能不一致**（后两处不读 `disabled`）。
6. **`ODataToolset.mapODataTypeToOpenAPI` 是穷举 switch 且无兜底**：未命中类型返回 `undefined`，进入 schema 后成为无类型参数。
7. **工具失败靠错误名识别**：`ToolInvokeHandler` 用 `error.name === 'ToolException'`（注释逐字：`The MCP adapter identifies tool failures by name but does not export its error class.`），上游改类名即静默降级为 500。
8. **`updateToolset` 是「读-改-写全量浅合并」**：`findOne` + `assign` + `save` 无并发控制（`xpert_toolset` 无 `@VersionColumn`），`[推测]` 并发编辑存在丢写。
9. **`mcp_runtime_instance` 无清理作业**：`DEFAULT_RUNTIME_AUDIT_RETENTION_DAYS` 只做查询窗口过滤，行数只增；且 ORM 侧 `record*` 均为 update，无 delete 路径。
10. **模块吞邻域资产**：`XpertToolsetModule` 的 forFeature 含 `mcp-publication`/`mcp-app-runtime`/`mcp-consumer`/`plugin-resource` 的表，controllers 含 `mcp-consumer` 两个控制器，`[推测]` 是为绕开循环依赖而集中 repository 提供方，代价是模块边界与子域边界不一致。
11. **`GET :id/faker` 的远端副作用**：非内置工具会真实建连（`initTools()`）只为取 schema，失败/超时直接映射到该读端点。
12. **`XpertToolController` 无自定义守卫**：`POST test`、`GET :id`、`GET :id/faker` 仅依赖全局 `@ApiBearerAuth`，工具集级/工作区级准入**不下沉**到该控制器（对比 `:id/credentials` 有 `ToolsetGuard`）。
13. **`xpert-toolset`/`xpert-tool` 无迁移文件**：表结构完全由实体驱动，`[推测]` 生产库列变更依赖 synchronize 或外部迁移工具。

## 12. 设计维度分析

**「声明式清单」vs「运行时探测」**：同一件事（工具有哪些、参数是什么）在本子域有三份事实源——库内 `xpert_tool` 行（`afterLoad` 会用 provider 最新定义**覆盖**它）、provider 类/插件注册表（`initTools()` 按名 switch 或 `createTools()`）、远端探测（`POST provider/mcp/tools`、`getToolsSchema()`）。`afterLoad` 的策略是「库内保留行的存在性与启用态，语义字段一律以前者为准」，好处是升级 provider 不必回填数据；代价是**库内 schema 与真实 schema 可以长期不一致**（只有在读路径被临时纠正），且 `getParamsFaker` 走的是另一条（真连远端）路径。

**「多租户作用域」在四条独立通道上收敛**：① 守卫通道（`ToolsetGuard` 用 `createdById` 或 `workspaceService.canAccess(workspaceId, userId)`）；② 查询通道（`getAllByWorkspace` 把「无 workspace」翻译成 `workspaceId IsNull + createdById`）；③ 执行通道（`persistedToolsetWhere` + `toolsetWorkspaceId` 的越界拒绝 + `snapshot` 四项一致）；④ 存储通道（`resolveToolRuntimeScope` 把 project/xpert/user 三种绑定映射到 `catalog`+`scopeId`，并拒绝「个人 MCP files 与 project/xpert 同时出现」）。四者互不调用，任一处放宽都不会被另一处兜住——这是本子域最需要守的一致性结构。

**「缓存」的三处不同语义**：`ToolsetGuard` 缓存的是**授权决定**（5 分钟，只缓存允许，无失效）；`GET :id/avatar` 缓存的是**展示数据**（5 分钟，`tenantId + id` 键，过期自然重取）；`ListBuiltinTools`/`ListBuiltinToolProviders`/`ListBuiltinCredentialsSchema` 缓存的是**进程内静态清单**（无 TTL，插件热加载后需重启）。`[推测]` 前两者用同一 `CACHE_MANAGER`，若未来要做「工具集变更即失效」，需要同时清两类键但只应清授权类。

## 13. 结论

实现上，本子域把「工具集」做成了**一个可插拔的运行时容器**：`category`+`type` 决定由谁构造实例（builtin 注册表 / openapi / odata / mcp），`xpert_tool` 行决定暴露哪些工具，`afterLoad` 在读路径把语义字段拉齐到 provider 最新定义，执行侧再由 `ToolRuntimeService` 统一收口（作用域、快照、能力、用量、关闭）。`xpert-tool` 是这层容器的**调试面板**（`test`/`faker`/详情回填），MCP apps 与运行时审计则是两条独立的运维面（实例级 RPC 与进程级停机阀），二者都不参与工具集建模。

需要重点防守四处：① `credentials` 明文落库 + 5 分钟授权缓存构成的撤权窗口；② `enabled`/`disabled` 双列在 provider 间判定不一致（`isEnableTool` vs 裸 `_.enabled`）；③ 执行面的四次越界拒绝（workspace/organization/snapshot/参数）是安全边界，新增调用方必须走 `ExecuteToolRequest` 显式字段；④ `XpertToolsetModule` 的集中装配与 `provider/index.ts` 的混合导出使子域边界在代码上不可见，改任一邻域资产都要回到本子域回归。新增能力应继续走「provider 实现 + 注册表/插件策略登记 + `afterLoad` 回填 + 只经 `ToolRuntimeService` 执行」的既有骨架，不要绕过服务层直接写 `xpert_toolset`/`xpert_tool`。
