## 1. 目标与原则

- **目标**：把后端业务域知识沉淀为可被 AI 与人直接使用的资产，让「改代码前先查资产」成为默认动作
- **双层结构**：**契约层**（`C0/C1/C2/C4/C5`，使用者视角、黑盒）+ **实现层**（`implementation/01~07`，白盒：架构/实现/数据流转/模型/接口/测试/运维）
- **子专家**：单专家 >100 非 spec 或含明显异构子域时拆一级子专家；子专家产出 `C0/C1` + 4 篇实现层
- **划分判据（定案用）**：组内**依赖边密度**优先——组内无跨簇耦合的模块不应塞进同一专家（否则该专家不是「业务域」而是「杂物箱」）
- **四类查询入口**：`expert-lookup`（资产）· `ki-search`（记忆 scope `xpert-memory`）· `relation-lookup`（强关联）· `index-lookup`（`.fe-index/xpert` 后端 + `.fe-index/xpert-cloud` 前端）
- **不建专家的范围**：共享设施与基础层（`common`/`config`/`contracts`/`desktop-protocol`/`nsjail-runner`）、已发布 SDK（`packages/plugin-sdk`、`packages/plugins/*`）

### 5.3 定案（2026-10-16）

**批次 5 = 6 个专家**（总数 13 → **14**），构成如下：

| 专家 | 模块 | 建议子专家 |
|---|---|---|
| 9 项目与任务协作专家 | `xpert-project` + `xpert-task` + `business-area` | ①项目本体与资源 ②任务与计划 |
| 10 工具与 MCP 专家 | `xpert-toolset` + `xpert-tool` + `agent-plugin` + `mcp` + `mcp-publication` | ①工具集与工具 ②MCP 协议与发布 ③Agent 插件 |
| 11 Agent 演进专家 | `agent-evolution` | ①变更与生命周期 ②评估与发布（19 表可分） |
| 12 运行时·沙箱·产物专家 | `sandbox` + `runtime-control` + `artifacts` + `workspace-file-access` + `health` | ①沙箱执行 ②运行时控制与健康 ③产物与文件访问 |
| 13 **文件理解与记忆专家** | `file-understanding` + `file-memory` + `storage-file` | ①文件理解 ②文件记忆与存储 |
| 14 **平台底座与集成专家** | `data-source` + `xpert-table` + `integration` + `view-extension` + `aimodel` + 字典四件 + `desktop-shell` + `mobile` + `initialization` | ①集成与扩展点 ②数据源与表格 ③基础字典与客户端壳 |

**为何从 13 变 14**：原「13」的确切组成不可恢复；按依赖证据，把原 ⑤（309 非 spec / 17 模块 / 零跨簇耦合）整体交给一个专家会产出「杂物箱式」资产——违反 §1 的划分判据。拆出「文件理解与记忆」（133 非 spec，且与 Assistant 域 15 条耦合、是对话/知识与工作台的共同底座）后，两块各自都可被写成有边界、可被 lookup 命中的业务域。
**若需严格守住 13**：唯一代价可接受的合并是把「Agent 演进」（仅 44）并入「运行时·沙箱·产物」，但二者语义无关，**不建议**。
