# C5 · 关键决策（Agent 执行链专家）

> 本域「明写证据」极厚：下列决策的措辞尽量逐条引用仓库内文档原文（不加行号）。凡属推断补足之处显式标 `[推测]`。「被否决方案」仅在源码/文档有明确对照时填写，否则写「无」。

## D1 · Invocation 是运行时账本，Task 保留业务决策

- **分类**：领域边界 / 架构分层
- **动机（避坑）**：现象——把「传输成功」当作任务完成，或让 runtime 再注册一个执行器去驱动 Task；后果——账本与业务决策耦合、重复执行、任务被误判完成。
- **决策**：Invocation 作为运行时账本；Project Task 保留业务决策；复用既有 Handoff 队列（持久化 outbox/inbox/consumer claim），**不注册第二个执行器**、不从传输成功推断完成。
- **背景约束**：native Task 保留自身会话/Redis 流传输；`AssistantTask` 仍是兼容门面，其底层执行器不得回调该门面递归。
- **被否决方案**：为 Agent runtime 另注册执行器；由传输成功推断 Task 完成；让底层执行器回调 `startTask` 门面（递归）。
- **重新评估触发条件**：Task 生命周期语义变更需跨域确认（`xpert-project` 侧）。
- **关联代码**：`file://packages/server-ai/src/handoff/runtime-messaging/README.md`、`file://packages/server-ai/src/xpert-agent-execution/runtime/assistant-task-runtime.service.ts`、`file://docs/plans/2026-09-22-unified-agent-invocation.md`（「AssistantTask remains a compatible facade; its underlying executor must not call back into that facade and recurse.」）
- **证据来源**：`file://packages/server-ai/src/handoff/runtime-messaging/README.md`——「Invocation remains the runtime ledger. Project Tasks retain business decisions. This host infrastructure uses the existing Handoff queues with persisted outbox, inbox and consumer claims; it does not register another executor or infer Task completion from transport success.」

## D2 · CAS 状态转移 + store 与 append-only 观察历史同事务

- **分类**：并发控制 / 事务一致性
- **动机（避坑）**：现象——并发写覆盖状态、事件与状态不一致；后果——观察历史出现空洞、审计不可信。
- **决策**：状态转移一律经 `revision` CAS（`replace(record, expectedRevision)`），并在**同一事务**内提交状态与 append-only 观察历史（`agent_invocation_event`，唯一 `(invocationId, revision)`）。
- **背景约束**：`revision` 是应用层乐观锁版本，不是 DB 自增/`@VersionColumn`；任何绕过 store 直写 `invocation` 列的代码都会静默破坏一致性（唯一约束只保护事件表）。
- **被否决方案**：以本地事件通知代替提交（源码注释：「The due-time update is already durable; a local notification must not undo a committed result.」——通知失败即降级到轮询）。
- **重新评估触发条件**：出现需要跨表强一致的新的状态载体时。
- **关联代码**：`file://packages/server-ai/src/agent-invocation/invocation-runtime.ts`、`file://packages/server-ai/src/agent-invocation/typeorm-invocation.store.ts`
- **证据来源**：`file://packages/server-ai/src/agent-invocation/README.md`——「`AgentInvocationRuntime`: authorization, idempotency, pinned strategies and compare-and-swap state transitions.」「`TypeOrmAgentInvocationStore`: state and append-only observation history in one transaction.」

## D3 · 中间件工具/工作流节点/后台任务是同一 runtime 的 caller

- **分类**：领域边界 / 统一调用面
- **动机（避坑）**：现象——各调用面各自持有另一 Agent 的图、进程、会话或协议；后果——授权与取消口径分裂、无法审计、行为不可收敛。
- **决策**：中间件工具、工作流 Agent 节点、后台任务**都是同一 `AgentInvocationRuntime` 的 caller**，不得各自拥有另一 Agent 的 graph/process/session/protocol。工作流调用走同一 runtime，但不要求 LLM 去调工具。
- **背景约束**：本地 sub-agent 与 Collaborator 仍是作者态概念，均解析为 Xpert target；外部 provider（Codex/Pi/Claude Code/OpenCode）由插件提供策略；标准 Agent Plugin 包只能引用已批准绑定，不能加载 server 代码。
- **被否决方案**：保留旧的 `getMiddlewareDelegations` 私有符号通道不迁移（仅在等价的中断与输出投影测试通过后才替换为普通可调用工具）。
- **重新评估触发条件**：当某调用面确实需要独立执行语义（例如新增非 CLI 域作业）时，先在 `runtime-task` 统一策略内扩展。
- **关联代码**：`file://packages/server-ai/src/shared/agent/middleware-runtime/middleware-runtime.service.ts`、`file://packages/server-ai/src/agent-invocation/invocation-factory.service.ts`
- **证据来源**：`file://docs/plans/2026-09-22-unified-agent-invocation.md`——「Introduce an AgentInvocationRuntime and plugin SDK execution strategies. Middleware tools, workflow Agent nodes and background tasks are callers of the same runtime. They do not own another Agent's graph, process, session or protocol.」

## D4 · 解析一次即 pin，恢复不得静默回退

- **分类**：可恢复性 / provider 生命周期
- **动机（避坑）**：现象——恢复时按 provider 名重新解析到另一个实现；后果——在途调用语义漂移，且升级/下线会悄悄改变历史行为。
- **决策**：解析 provider 一次并把 `providerSource` 快照与 `target.revision` 固定落库；后续 `inspect`/`cancel`/`respond` 一律走 `pinned()`（`registry.getPinned`），失效即 `ProviderChanged`（409），**不静默回退**。
- **背景约束**：binding 创建拒绝 `provider ∈ {xpert, xpert-task}`，`target.revision` 建时 `randomUUID()` 固定；换配置/版本必须新建绑定。
- **被否决方案**：找不到快照时降级到另一个实现或按 provider 名重新解析（明确否决）。
- **重新评估触发条件**：下线/升级某 runtime provider 时必须保证旧快照仍可解析，否则在途调用集体 409——这是**设计使然**，不应被「修掉」。
- **关联代码**：`file://packages/server-ai/src/agent-invocation/invocation-runtime.ts`、`file://packages/server-ai/src/agent-invocation/runtime-bindings.controller.ts`
- **证据来源**：`file://docs/plans/2026-09-22-unified-agent-invocation.md`——「Resolve a provider once and pin its source. Removal or upgrade must never silently fall back to a different implementation during recovery.」「A provider-version mismatch blocks continuation instead of selecting a fallback.」

## D5 · 先持久化再派发

- **分类**：可靠性 / 幂等
- **动机（避坑）**：现象——先派发后落库；后果——崩溃后产生孤儿执行、重复启动、无法对账。
- **决策**：先校验 caller/组织/workspace-project/target 与资源权限，再持久化 invocation 与不可变 target 快照，**然后**才派发；幂等键包含父执行与调用点/toolCallId；重复的父调用挂回原 invocation。
- **背景约束**：`start` 先 `insert` 保留 `queued`，CAS `begin` 成功（`startPendingUntil` = now + 120s 启动 fence）后才调 `strategy.start`；provider handle 与生命周期事件持久化。
- **被否决方案**：以周期性 schedule ID 单独作幂等键（文档明写「A recurring schedule ID alone does not identify a single run.」）；先派发再补录。
- **重新评估触发条件**：无此项。
- **关联代码**：`file://packages/server-ai/src/agent-invocation/invocation-runtime.ts`（`save(..., 'begin')` 置 `startPendingUntil`）
- **证据来源**：`file://docs/plans/2026-09-22-unified-agent-invocation.md`——「Validate caller, organization, workspace/project, target and current resource permissions.」「Persist an invocation and immutable target snapshot before dispatch. The idempotency key includes the parent execution and call site/toolCallId.」

## D6 · 停请求不是终止证明

- **分类**：终止判定 / 可观测性
- **动机（避坑）**：现象——发出取消或观察者断开即认为运行结束；后果——`unknown` 被隐藏、投影出错误终态、上层基于假终态做决策。
- **决策**：终止只由 `exited` 确认；`unknown` 必须保持可见；断开观察者不取消运行，取消需 provider 确认。
- **背景约束**：执行授权生命周期跟随 CLI 会话/托管调用，独立于浏览器/Desktop 登录与查看/控制连接；终态、取消、过期或权限失效仍需 host 对账。
- **被否决方案**：把 stop 请求或连接断开当作终止证明（明确否决）。
- **重新评估触发条件**：无此项。
- **关联代码**：`file://packages/server-ai/src/agent-invocation/README.md`（Host execution runner 节）、`file://packages/server-ai/src/handoff/runtime-messaging/README.md`（「ambiguous launch … must remain visible」同类原则）
- **证据来源**：`file://packages/server-ai/src/agent-invocation/README.md`——「A stop request is not proof of termination: only `exited` confirms the process stopped, and `unknown` must remain visible.」

## D7 · 终局化不得重放初始行；`completedAt` 只表真终态

- **分类**：账本写入规则 / 时间语义
- **动机（避坑）**：现象——用初次 `create` 的整行快照做终局化写回，或用 `updatedAt`/`elapsedTime` 反推结束时间；后果——覆盖更新的审计时间戳与用量计数、时间线出现伪造的结束时刻。
- **决策**：`create`/`update` 忽略调用方 `createdAt`/`updatedAt`；整行重放初值被禁止；`completedAt` **只**记录成功/失败/超时/中断的墙钟时间，恢复为 running/pending 时清空，重复终局化与元数据更新保留已记录终点；`elapsedTime` 不用于重建日历时间，`updatedAt` 不能替代结束时间。
- **背景约束**：运行时回调仍可持久化自己的 metadata 与 checkpoint 字段；`recordUsage` 必须在事务内执行。
- **被否决方案**：用 `updatedAt` 或 `elapsedTime` 回填历史 `completedAt`（文档明写不可靠、迁移明确不 backfill）；重放初始行。
- **重新评估触发条件**：无此项——迁移明确「历史行的真实结束时间无法可靠恢复，任务时间线留空为未知」。
- **关联代码**：`file://packages/server-ai/src/xpert-agent-execution/agent-execution.service.ts`、`file://packages/server-ai/src/xpert-agent-execution/migrations/20261008-execution-completed-at.sql`
- **证据来源**：`file://packages/server-ai/src/xpert-agent-execution/README.md`——「Finalization must not replay the initial database row, which can overwrite newer timestamps and usage counters.」「`completedAt` records the wall-clock time when an execution succeeds, fails, times out or is interrupted. Resuming to running/pending clears it; the next stop records a new timestamp.」

## D8 · `waitForTasks` 是有界观察，超时不挂父级

- **分类**：等待语义 / Agent 交互模型
- **动机（避坑）**：现象——让等待挂起父级或让长任务靠 LLM 轮询循环；后果——父图被无谓阻塞、token 成本随轮询线性上升、`pending` 被误读为完成。
- **决策**：`waitForTasks` 支撑 `task_status` 工具，与单任务 `awaitResult` 互补；观测窗口耗尽**正常返回 `pending`**，不挂起父级、不暗示任务完成；只有人工交互才挂起图。
- **背景约束**：图适配器提供通用 wait/resume 桥；后台调用返回任务引用；持久 provider 会话默认单写者；并行编码任务使用隔离工作区（除非共享策略显式允许）。
- **被否决方案**：让长任务依赖 LLM 轮询循环（文档明写「A long-running tool must not require an LLM polling loop.」）；把等待当作同步阻塞。
- **重新评估触发条件**：新增非 CLI 域作业时，先扩 `runtime-task` 统一策略。
- **关联代码**：`file://packages/server-ai/src/agent-invocation/invocation-factory.service.ts`、`file://packages/plugin-sdk/src/lib/agent/runtime/capability.ts`
- **证据来源**：`file://packages/server-ai/src/agent-invocation/README.md`——「`invocation-task-wait`: bounded observation for Agent-driven status polling; only human interactions suspend.」「An elapsed observation window returns `pending` normally; it does not suspend the parent or imply task completion.」

## D9 · 取消是协作式（与「对话与会话专家」共享证据）

- **分类**：取消协议 / 跨模块契约
- **动机（避坑）**：现象——把取消实现为强杀进程，或把 canceled 结果送进死信并重试；后果——同步 CPU-bound 代码无法被强杀而状态混乱、取消被重试反向抵消。
- **决策**：取消通过 `AbortSignal` 传递；队列态（`waiting`/`delayed`/`paused`）靠移除 Bull job 立即生效，`active` 态靠 abort 在途处理器；跨实例经 Redis pub/sub 传播；取消结果表示为 `dead(canceled:...)` 且**不进死信、不重试**。
- **背景约束**：`ai:execution:cancel` 与 `ai:handoff:cancel` 是两条彼此独立的频道，互不替代；会话取消先执行执行取消，再 best-effort 停 handoff，后者失败只记 warning；`redrive` 与对账不得越过用户 stop 屏障。
- **被否决方案**：强杀同步 CPU-bound 代码（文档明写不做）；取消结果进死信/重试（明确否决）；把队列查找改为 Redis 索引键（README「Design Tradeoffs」明写当前选择扫描：更简单可靠、按当前 job 量计成本）。
- **重新评估触发条件**：停止请求频率显著上升，使「扫描成本与 job 量成正比」成为瓶颈时（README 明写的取舍点）。
- **关联代码**：`file://packages/server-ai/src/shared/execution/execution-cancel.service.ts`、`file://packages/server-ai/src/handoff/handoff-cancel.service.ts`、`file://packages/server-ai/src/chat-conversation/commands/handlers/cancel-conversation.handler.ts`
- **证据来源**：`file://packages/server-ai/src/handoff/README.md`——「Cancellation is cooperative.」「The system signals cancellation through `AbortSignal`; it does not force-kill synchronous CPU-bound code.」「Cancellation is represented as `dead` with reason prefix `canceled:`.」「Canceled results do not go to dead-letter and are not retried.」

## D10 · 含糊启动不得自动重放

- **分类**：恢复 / 幂等
- **动机（避坑）**：现象——launch/进程状态不明时自动重试；后果——重复外部副作用、重复消耗配额，且无法区分「没起来」与「起来了但回执丢了」。
- **决策**：含糊启动必须保持 `unknown` 且**永不自动重放**；已提交的 pending dispatch 意图可重排，但重排必须携带原 call ID 与当前授权；只有**尚无任何 launch receipt** 时，已验证的 preflight 失败才可记为 failed。
- **背景约束**：持久化启动 fence 最长 120s，期内后台巡检不做中间态失效判定；`reserved` consumer 恢复同一 execution ID，`started` 后只检查该 execution；`consumer_outcome_unknown` 保持 blocked，`redrive` 只复核同一条已记录的 execution identity。
- **被否决方案**：传输重试或 redrive 重新启动 CLI / 分配替代 consumer（明确否决）；把含糊启动按时间推断为失败。
- **重新评估触发条件**：无此项（「Exactly-once remote side effects are not promised.」）。
- **关联代码**：`file://packages/server-ai/src/handoff/runtime-messaging/README.md`、`file://packages/server-ai/src/agent-invocation/README.md`
- **证据来源**：`file://packages/server-ai/src/agent-invocation/README.md`——「Checkpoint it before sending the initial task; ambiguous launch or process state must not trigger an automatic replay.」`runtime-messaging/README.md`——「Neither transport retries nor redrive relaunches the CLI or allocates a replacement consumer.」

## D11 · 中间件只暴露 scoped API，不得把全局 registry 传给插件

- **分类**：安全边界 / 能力注入
- **动机（避坑）**：现象——把全局 capability registry 或 runner factory 交给插件；后果——插件可跨租户解析能力、绕过 owner/workspace 校验。
- **决策**：invocation factory 为每次操作捕获不可变身份 scope，只向 runtime 策略暴露 scoped runner capability，**不暴露全局 capability registry 或 runner factory**；中间件侧由 `createScopedApi(scope)` 组合 actor token/artifacts/collaboration/connector/workspace files/model client，能力集合随 scope 变化，缺能力时显式失败。
- **背景约束**：runner factory 构造不执行任何启动或 I/O；正常调用与绑定授权仍先于策略派发；草稿态上下文（`getDraftXpertMiddlewareContext` / `createDraftXpertMiddlewareRuntime`）与发布态分离。
- **被否决方案**：把全局 registry / runner factory 直接交给插件（README 逐字否决）；在 feature 模块里重复 provider 化 runtime service（`middleware-runtime.provider-boundary.spec.ts` 断言消费模块必须 import runtime 模块而非自行 provide，且 file/actor-token/connector/知识文档视觉资产的 scoped factory 由其领域模块 own）。
- **重新评估触发条件**：新增宿主集成能力时，须走 scoped factory 注册，不得扩到共享门面。
- **关联代码**：`file://packages/server-ai/src/shared/agent/middleware-runtime/middleware-runtime.service.ts`、`file://packages/server-ai/src/shared/agent/middleware-runtime/middleware-runtime.provider-boundary.spec.ts`、`file://packages/server-ai/src/shared/agent/middleware-runtime/execution-scope.ts`
- **证据来源**：`file://packages/server-ai/src/agent-invocation/README.md`——「It does not expose the global capability registry or the runner factory.」`middleware-runtime.service.ts` 注释——「Stable facade that assembles invocation-scoped middleware capabilities. Domain behavior lives in focused runtime services so this class only owns capability composition and scope-specific host integrations.」「Do not capture the first caller identity on this shared facade or resolve factories before discovery.」
- **备注**：任务书所指 `provider-boundary.spec.ts`，实际文件名为 `middleware-runtime.provider-boundary.spec.ts`；其断言对象是**模块 provider 归属**（谁 provide / 谁 import），并未逐字断言「不把全局 registry 传给插件」——该结论的直接证据是 README 原文与 `createScopedApi` 实现，`[推测]` 部分仅限「spec 是该边界的目的性防线」这一解释。
