## 1. start 的授权与幂等

`scoped(access)` 先 `structuredClone(access.scope)` 并校验五元身份（`tenantId/organizationId/userId/parentExecutionId/callerAgentKey`），缺失即 `InvalidScope`（403），随后返回只含 `start/inspect/cancel/respond` 的 `AgentInvocationApi`。`start` 的顺序是：`structuredClone(request)` → `validateRequest` → `authorizeAgentInvocation(() => access.authorize(request.target))` → `access.signal?.throwIfAborted()` → `agentInvocationId(scope, callId)` → `store.read(id, scope)`。

授权失败被 `authorizeAgentInvocation` 包成 `AgentInvocationAuthorizationError`（明写「must stop the run, not become an ordinary retryable tool result」）；`factory.api()` 里的 `authorize` 回调用 `resolve(bindingId)` 或 `resolveGroupTarget` 取回允许目标，并逐字段比对 `revision/provider/reference` 与 `sameInvocationData(configuration)`，任一不等即 `CallConflict`（409）。

幂等与复用：`agentInvocationId` 把 `canonical({scope, callId})` 的 sha256 前 32 位整形为 UUID（`-5…-a…` 形态）；命中已有记录则 `assertScope`（不一致按 `NotFound` 处理）→ `canonical(record.invocation.request)` 全等（不等即 `CallConflict`）→ `pinned(record)`；终态直接返回，非终态仅 `queued` 或（`waiting` 且策略 `recovery === 'checkpoint'`）才继续。未命中则 `registry.get` + `registry.getSource` 建 `queued` 记录并 `insert`（`orIgnore().returning('id')`，并发插入失败递归重入）。

启动与收敛：CAS `save(record, {status:'running', interaction:undefined, error:undefined}, false, 'begin')` 赢家才调 `strategy.start`；策略返回后重读 `latest`，若 revision 更强且状态不同/终态则用 `latest.invocation.status` 收敛，否则写回 `observation`。异常路径：`AgentInvocationNotStartedError` 且无 handle → `failed`；`isSuspension` → `waiting`；否则 `unknown` + `DispatchUnknown` 并继续抛出。

## 2. CAS 与事件

`replace(record, expectedRevision)` 在单事务内执行 `UPDATE agent_invocation SET invocation=:invocation::jsonb, providerSource=:providerSource::jsonb, revision=:revision, nextObservationAt=now() WHERE id/tenantId/organizationId/ownerId 且 revision=:expectedRevision`；`affected !== 1` 直接返回 `false`（不抛错），调用方 `updateLatest` 重读重试最多 8 次，超限 `ConcurrentUpdate`。

`appendEvent` 只把 `status/handle/interaction/progress/result/error` 六个字段写进 `agent_invocation_event.observation`（不落未受限的 provider 调试流），唯一索引 `(invocationId, revision)` 让重复 revision 直接触发约束错误并回滚整个事务；同一事务还 `appendRuntimeDelivery(manager, invocation)`，并在状态属 `succeeded|failed|cancelled|waiting` 时 `UPDATE agent_invocation_wait SET nextCheckAt = now()`（匹配 `id = invocation.id` 或 `request->'taskIds' ? invocation.id`）。

提交后仅对上述四态发 `TaskObservationCommittedEvent`，且异常被吞为 `warn('Task observation notification deferred to polling')`——本地事件只是加速，不是恢复依据。CAS 语义上还有一处保护：`updateLatest` 中若 `latest.invocation.status === 'cancelling'` 而 observation 为 `running`，则保持 `cancelling`（迟到的 progress 不得撤销已接受的取消请求）。

## 3. Monitor 三态循环

`reconcile()` 由 `@Interval(5000)` 驱动、`busy`/`stopping` 门闩防重入：取 `state='waiting' AND nextCheckAt <= now()` 的 `take: 10` 行，同时把指标 `applicationMetrics.setInvocationWait({pending, oldestErrorSeconds})` 用一条 SQL（`state IN ('waiting','ready','blocked')`，`oldestErrorSeconds` 取 `lastError IS NOT NULL` 的最老 `createdAt`）刷新，最后 `Promise.allSettled(records.map(process))`。

`process(wait)` 处理 waiting 组：`claim(wait, 'waiting', ...)` 抢租约 → `withAccess` → 对 `request.taskIds ?? [wait.id]` 逐个 `api.inspect` → `taskWaitReason(states, mode ?? 'all')`；`attention` 时读 checkpoint 并比对 `invocationWaitInteraction`，若匹配到已存在的人工 interaction 且已过 `deadlineAt` 则置 `blocked` + `lastError='awaiting_user'`；`unknown` 超过 `HOST_TASK_WAIT_POLICY.unknownGraceMs` 则 `unavailable`，过 `deadlineAt` 则 `timeout`；最终回写 `state: ready|waiting`、`lastError: unknown ? 'outcome_unknown' : null`、`nextCheckAt = now + (outcome ? 0 : 15s)`。

`deliver(wait)` 处理 ready 组（由 `InvocationContinuationDispatcher` 的 `@Interval(1000)`、`take: 10`、`active.size < 4` 触发且**不被观察扫描 await**）：先重校验每个依赖的 `inspect`，再沿 `parentId` 上溯父执行（`visited` 去重、`size >= 64` 抛 `Invalid execution ancestry`），父执行仍 `RUNNING` 则推后 5 s；checkpoint 命中人工审批则 `blocked` + `awaiting_user`（「先到的完成事件不得重放后来的人工审批」）；`threadId` 不符、无 tuple、无 interruptId 或执行态非 `INTERRUPTED|ERROR` 一律 `stale`；否则发 `RunCreateStreamCommand`（`action: 'resume'`，`decision.payload[interruptId] = {waitId, completed:true}`，上下文带 `invocationId/waitLeaseToken/checkpointId/interruptId`），结束后按是否仍有 pending interrupt 落 `waiting|delivered`。

`claim(state, handler)` 用 CAS 抢租约：`leaseToken = randomUUID()`、`leaseUntil = now + 120s`、`nextCheckAt = now + 15s`，条件含 `state = :state` 且 `("leaseUntil" IS NULL OR "leaseUntil" < now())`；成功后每 30 s 心跳续租（失败只 `warn('Task wait lease renewal failed')`），失败路径回写 `state: 过 deadlineAt ? 'blocked' : state`、`lastError='continuation_pending'`、`nextCheckAt = now + 60s`，`finally` 里清空 `leaseToken/leaseUntil`。`withAccess` 从 `request.scope`（历史行回落到 `agent_invocation.invocation.scope`）解析 scope 并逐字段与 wait 行比对，再复检 `user.type === USER` 与 `isActive` 的 membership（组织也须 `isActive`），然后 `runWithCapturedRequestContext(captureRequestContext(...))` 重建 actor/tenant/org 后 `factory.createScopedApi(scope)`。

## 4. 等待与续跑

`agent_invocation_wait.state` 取值 `waiting | ready | delivered | stale | blocked`；登记走 `AgentInvocationWaitStore.register/registerTasks`（`id` 为 `[tenantId, organizationId, userId, parentExecutionId, callerAgentKey, callId]` 的 sha256 UUID 形态，`insert().orIgnore()` 后重读，`threadId`/`mode`/`taskIds` 不符即 `CallConflict`；`threadId` 取自 runnable config，缺失即 `InvalidScope`；`deadlineAt = now + HOST_TASK_WAIT_POLICY.maxWaitMs`）。`invocationTaskWaitSchema` 限制 `taskIds` 1–32 个且不重复、`timeoutMs` 0–60000、schema `.strict()`。

有界等待：`awaitInvocationTasks` 把 `timeoutMs` 夹到 `min(request.timeoutMs ?? policy.inlineWaitMs, policy.maxInlineWaitMs)`，循环 `observeTasks`（`pollIntervalMs` 轮询、到点返回 `pending`）；`pending` 且含 `unknown` 归一为 `unavailable`；仅 `attention` 且 `timeoutMs !== 0` 时才 `interrupt({type:'agent_invocation', invocationId, reason:'user_input', interaction})`，并在响应 `interactionId` 匹配时 `api.respond`。`AgentInvocationFactoryService.awaitResult` 与 `waitForTasks` 共用同一实现，并在返回前 `claimResults`（仅 `succeeded|failed|cancelled` 且带 `dispatch` 的任务经 `ClaimAgentRuntimeResultsCommand` 消费）。

续跑围栏：`AgentInvocationResumeFence`（`waitLeaseToken?`/`invocationId`/`checkpointNamespace`/`checkpointId`/`interruptId`）；`assertInvocationResume` 要求 `action === 'resume'`、`matchesInvocationResume(tuple, fence)`（checkpoint.id 相等、无人工 interaction、interruptId 相等），且当 fence 带 `waitLeaseToken` 时 `CheckTaskWaitClaimQuery` 必须命中（`state='ready'` 且 `leaseUntil > now`），否则 `BadRequestException`（i18n `AgentInvocationContinuationStale`）。`CancelTaskWaitsCommand` 用一条 SQL 把与取消执行关联的 wait 行置 `stale` + `lastError='parent_cancelled'` 并清租约。`parallel-delegation.ts` 以 `Send` 为每个子任务派生独立 checkpoint 命名空间（`childCallId = callId:index`，上限 `MAX_PARALLEL_DELEGATIONS = 32`），对 graph interrupt 与 `AgentInvocationAuthorizationError` 原样抛出，对 `DispatchUnknown` 转为单条失败结果而不重试。

## 5. activity 游标

`InvocationActivityService.recorder(invocation)` 暴露 `readCheckpoint`（读 `agent_invocation_activity_state` 的 `seq/sourceCursor`）与 `append`（解析 `executionActivityBatchSchema`）。`append` 在单事务内 `insert().orIgnore()` 建 state 行后以 `pessimistic_write` 取回，若 `state.closed` 或 `expectedSourceCursor` 与现存 `sourceCursor` 不符则**直接返回旧游标不做任何写入**；每个 item 先 `redactCredentials` 脱敏、解析 `executionActivityItemSchema`，工具项做「running 不得覆盖已终态」与 `previous.item.content` 合并且按 `hash` 去重。

容量与缺口：累计 `bytes > EXECUTION_ACTIVITY_MAX_BYTES`（默认 32 MiB，区间 1 MiB–128 MiB）或 `state.seq >= 20000` 时把 `capture_limit` 记入 `state.gaps` 并跳过该 item——**主动声明缺口而非静默截断**；单个工具输出超过 65536 字符时截断并把完整内容写入 volume（`outputRef.key = sha256`）；`expiresAt = now + EXECUTION_ACTIVITY_RETENTION_DAYS * 86400000`，`batch.complete` 时置 `closed = true`。

读取面：`page` 以 `state.seq` 为 committed waterline，先按 `itemId` 取 `MAX(seq) <= waterline` 再回捞，`take(limit + 1)` 给出 `hasMore`，并把 `state` 归一为 `not_recorded | expired | closed | recording`，终态未 closed 时补 `interrupted` gap；`output(invocation, key, offset)` 在 state 缺失、`expired`、已过 `expiresAt` 或无 volume 时一律 `NotFound`，按 65536 字节分段返回。`purgeExpired` 由 `@Interval(3600000)` 每次取 100 行删除 item、置 `expired = true`，失败只 `warn('Execution activity retention cleanup deferred')`。`agent_invocation_activity_item` 的唯一索引 `(invocationId, seq)` 兜底游标幂等。

## 6. 取消

两条 pub/sub 分工明确：`ExecutionCancelService`（`ai:execution:cancel`）做执行取消，`HandoffCancelService`（`ai:handoff:cancel`）做队列/进程取消，互相不替代。本域侧流程：`cancelExecutions(ids, reason?)` 先去重（`new Set(ids.filter(Boolean))`），`redis.publish` 失败**只 `warn('Failed to publish cancel event: ...')`**，随后无条件本地 `applyCancel`——对 `#controllers` 里登记的 `AbortController` 调 `abort(new ExecutionCancelledError(id, reason ?? 'Canceled by user'))` 并删除条目；`onModuleInit` 用 `redis.duplicate()` 订阅并把消息交给 `handleCancelMessage`（解析失败只 `warn('Invalid cancel payload: ...')`）以覆盖跨副本。

`ExecutionCancelledError.code = 'EXECUTION_CANCELLED_BY_USER'`。`executionAbortScope(executionId, cancellations, parents)` 为每次调用建独立 controller，把父信号（去重后）逐个订阅并级联（父已 abort 则立即 abort），`register` 后返回 `{controller, dispose}`；`unregister(executionId, controller)` 采用「同一实例才删」的对比删除，避免旧实例覆盖新登记。

`control(id, access, 'cancel')` 的入口约束：策略须声明 `capabilities.cancellation` 且有 `cancel` 否则 `Unsupported`（422）；先 `save(record, {status:'cancelling'})` 再调 `strategy.cancel(handle, context)`；终态记录直接返回不发起取消。取消只是请求，不构成终止证明，也不取消 Project Task。

## 7. 执行账本写入

`create`：`omit(entity, ['createdAt','updatedAt'])` 后由 `executionCompletedAt(undefined, entity.status)` 决定 `completedAt` 初值（终态才有值）。`update(id, entity)`：同样 omit 审计列，先 `super.findOne(id)` 取租户/组织，再在事务内 `findOne(..., { lock: { mode: 'pessimistic_write' } })` 重读，用 `executionCompletedAt(current, changes.status)` 重算后 `assign(current, changes, { completedAt })` 与 `manager.save(current)`（保留 ORM 生成的 `updatedAt`）。

`executionCompletedAt` 规则：`running|pending` → `null`（清空）；本次为停止态（`success|error|timeout|interrupted`）且上次非停止态 → `new Date()`；否则保留 `previous.completedAt ?? null`（历史停止态记录的结束时间不可由元数据写入建立）。`recordUsage(id, usage)` 在事务内 `increment(XpertAgentExecution, {id}, 'tokens', usage.tokens)`；仅当 `usage.type !== 'estimated'` 且带 `details` 时另写 `responseLatency`（毫秒转秒）、`currency`、`totalPrice`、`inputTokens/inputUnitPrice/inputPriceUnit`、`outputTokens/outputUnitPrice/outputPriceUnit`。

`interruptRunning(ids, threadId, error)` 是一次 `repository.update({id: In(ids), threadId, status: RUNNING}, {status: INTERRUPTED, error, completedAt: new Date()})`——只影响仍为运行态且线程匹配的行；源码注释声明「Only called with execution IDs already resolved through tenant-scoped access checks」。此外 `findAllByParentId` 与 `findAllByXpertAgent`（限 `parentId IS NULL`，可带 `createdById`）是只读查询面。

## 8. AssistantTaskRuntimeService 的任务入口

`AssistantTaskRuntimeStrategy`（`@AgentRuntimeStrategy('xpert-task')`）声明 `capabilities = {recovery:'session', interactions:false, cancellation:true, background:true}`，其 `start/inspect/cancel` 全部转交给由 `context.capabilities.require(AssistantTaskExecution)` 注入的执行体——即「legacy task transport is an executor, never a call back into startTask」，避免 facade 递归。`invokeAssistantTask` 组装 scope（`parentExecutionId = identity.executionId || task:<xpertId>:<taskId||callId>`）与 `AssistantTaskExecution`，再由 `api.start` 以 `bindingId = assistant-task:<xpertId>:<target.id>`、`provider = 'xpert-task'`、`revision = target.revision` 发起；`receipt.status` 经 `Receipt.parse` 归一（`interrupted → waiting`，`cancelled|cancelling → unknown`），无结果且无句柄可观察时抛 `DispatchUnknown`。

`AssistantTaskRuntimeService` 是任务 facade：`getModels`（经 `PublishedXpertAccessService` 与 `AssistantModelSelectionService`）、`getTaskStatus`、`assertExternalAssistantBinding`（重新解析已发布图以吸收必需连边变更）、`listCorrelatedExecutions`（只列 requester 拥有且绑定当前 `available` 的关联执行）、`cancelTask`（发 `CancelConversationCommand`，返回 `canceledExecutionIds`）、`startTask`（校验 `xpertId`/`prompt`，`target.requesterXpertId !== xpertId` 即 `InvalidScope`，再以私有 `dispatchTask` 作为 executor 调 `invokeAssistantTask`）。调用侧 `assistant-task-adapter` 的 `callId` 取 `clientMessageId || correlation.operationId || executionId || randomUUID()`，与明写约束「An explicit operation/client-message/execution ID provides Task idempotency; a recurring schedule ID alone does not identify a single run」一致。

## 10. 热点路径

1. **invocation 认领竞争**：`AgentInvocationMonitorService.reconcile`（5 s / take 10）与 `InvocationContinuationDispatcher.dispatch`（1 s / take 10 / active ≤ 4）共用 `claim` 的 CAS 抢租约，是执行链唯一持久恢复通道；本地事件与队列只是加速。
2. **CAS 冲突重读**：`updateLatest` 的读—改—CAS 环（≤8 次）与 `start` 的 `insert` 递归重入；长任务高频 progress、取消与交互并发时最容易出现 `ConcurrentUpdate` 与 `CallConflict`。
3. **activity 追尾**：`append` 的事务 + `pessimistic_write` 单行锁 + 逐 item 的 hash/字节计算与 volume 写；大输出（>65536）会额外产生 volume I/O 并按字节上限提前触发 `capture_limit`。
4. **父执行上溯**：`deliver` 每次沿 `parentId` 逐级查询（≤64 跳），父执行仍 `RUNNING` 时整组推后 5 s，深链 + 高频 ready 组会放大查询量。

## 12. 技术债与 hack

1. **三套租约并存易混**：`observationLeaseToken/observationLeaseUntil`、`agent_invocation_wait.leaseToken/leaseUntil`、`agent_runtime_delivery|inbox.leaseToken/leaseUntil` 语义与时长全不同、互不校验，混用会造成重复投递或提前接管。
2. **`agent_invocation_wait` 表名与语义错位**：实体注释明写「Durable dependency groups; table name preserves existing single-task checkpoints.」，且组语义迁移 DROP 了指向 `agent_invocation(id)` 的外键，按 FK 假设推断关联会得出错误结论。
3. **`RuntimeDeliveryController` 的注册地错位**：文件在 `handoff/runtime-messaging/`，controller 注册与方法逻辑却在「对话与会话专家」侧，排查路由极易走错域。
4. **跨副本取消静默失败**：`publish` 失败与订阅异常只 `warn`；Redis 不通即「本副本照停、其他副本静默丢取消」，端到端取消无法仅凭日志确认。
5. **`prompt` 类内容不入账本的设计对排障的影响**：`agent_invocation_event.observation` 只取 6 个字段、`agent_invocation_activity_item` 对字符串统一 `redactCredentials` 且工具输出超 65536 只留 `outputRef`——可审计，但排障需要经 `InvocationActivityService.output` 与 volume 才能复原完整输出。
6. **`grant`/replay 语义边界**：`listCorrelatedExecutions` 只列 `available` 绑定，历史终态调用不会被自动唤醒（只由新的已提交观察产生投递意图），遗留数据在升级后的可见性需人工确认。

## 13. 设计维度分析

### 13.1 「账本状态」与「观察历史」的分离度
`agent_invocation.invocation` 是可变的当前快照（含 `revision`），`agent_invocation_event` 是不可变历史（只留 6 字段）。分离的收益是恢复只需读当前行、审计只需读事件表，代价是两者一致性完全依赖「同事务 + CAS 赢家」这一约束——绕过 store 直写任一表都会静默破坏可审计性。

章节来源：[typeorm-invocation.store.ts](file://packages/server-ai/src/agent-invocation/typeorm-invocation.store.ts)（关键符号：TypeOrmAgentInvocationStore.replace/appendEvent）、[2026-09-22-unified-agent-invocation.md](file://docs/plans/2026-09-22-unified-agent-invocation.md)（关键符号：Only the runtime writes invocation status）

### 13.2 观察驱动 vs 事件驱动的取舍
`TaskObservationCommittedEvent` 只在提交后发本地通知且异常被吞，`reconcile` 固定 5 s 扫描，跨副本正确性因此不依赖事件可达性，代价是观察延迟上限 ≈ 5 s + `nextCheckAt`（wait 组 15 s）。这是一次明确的「以延迟换正确性」选择：README 明写「Polling is the durable recovery mechanism; local events and queue delivery are acceleration only.」

## 14. 结论

实现层由四条骨架支撑：① 幂等键 + CAS + 启动围栏把「一次调用」变成可重入的持久记录；② 同事务的事件表 + outbox 把「观察」变成可恢复审计与可靠投递；③ 租约 + 轮询 + 心跳把「等待/续跑」变成不依赖本地状态的可恢复过程；④ `XpertAgentExecutionService` 与 `executionCompletedAt` 把审计时间戳收口到唯一写入面。最易出错的四处是：三套租约混用、绕开 store/service 直写账本、跨副本取消的静默失败、以及把 `unknown`/`pending` 当成终态或完成证据。
