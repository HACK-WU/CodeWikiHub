## 1. 三套租约对照表

| 租约 | 载体列 | 时长 / 续租 | 扫描节拍与并发 | 适用对象 |
|---|---|---|---|---|
| 观察租约 | `agent_invocation.observationLeaseToken` / `observationLeaseUntil` | 60 s；每 20 s 续租，失败只 `warn('Runtime observation lease renewal deferred')` | `@Interval(5000)`，`nextObservationAt <= now()` 且请求含 `dispatch` 或 `activity`，`take(20)`，`scanning` 门闩 | 只**观察**已存在句柄，绝不启动；「Missing receipts are never launch instructions.」 |
| wait 租约 | `agent_invocation_wait.leaseToken` / `leaseUntil` | 120 s；每 30 s 续租，失败只 `warn('Task wait lease renewal failed')` | `reconcile` 5 s / `take(10)`（waiting 组）；`dispatch` 1 s / `take(10)` / `active ≤ 4`（ready 组）；claim 时把 `nextCheckAt` 推后 15 s | 老的 checkpoint 续跑路径（`process()`/`deliver()`），`CheckTaskWaitClaimQuery` 复核 |
| 投递 / 消费租约 | `agent_runtime_delivery.leaseToken` / `leaseUntil`、`agent_runtime_inbox.leaseToken` / `leaseUntil`（两表均有 `(state, nextAttemptAt)` 索引） | 由 `RuntimeMessageProcessor` / `RuntimeMessageInboxService` 管理 | 队列驱动 + `nextAttemptAt` 重排 | 传输收据与消费认领；语义归属「对话与会话专家」 |

排障第一步永远是确认「这条日志/这行数据属于哪一套租约」：三者时长、扫描条件、续租失败日志文本都不同，且互不校验。租约只是「多进程扫描不互相踩」的机制，**不是互斥保证**——真正的裁决仍是 CAS 落库。

## 2. polling 是唯一持久恢复机制与启动 fence

明写原文：「Leases permit independent host processes to scan safely. **Polling is the durable recovery mechanism**; local events and queue delivery are acceleration only.」因此：

- `TypeOrmAgentInvocationStore.replace` 提交后发的 `TaskObservationCommittedEvent` 只把**本进程**的下一轮扫描提前叫醒（`AgentInvocationMonitorService.handle()` 中 `void this.reconcile().catch(...)`），异常被吞为 `warn('Task observation reconciliation deferred')`；跨副本、跨进程重启的正确性只靠 `@Interval`。
- 因此**调低或关闭 `@Interval` 等于关闭恢复**：waiting 组、ready 组、观察组三条链都会停滞，且不会产生显式错误日志。
- 观察侧成功回写 `nextObservationAt` = 终态 `null` / `unknown` 60 s / 其余 5 s，失败写 `observationError='observation_unavailable'` 并推后 60 s；`null` 表示「不再观察」，不是「已完成」。

**启动 fence ≤120 s 的运维含义**：持久化围栏（`startPendingUntil = now + 120 s`；README：「A persisted startup fence lasts at most 120 seconds.」）期间，后台巡检不做中间态失效判定，不会把「启动中途的 launch receipt」判成 `unknown`；取消路径在此期间仍可用；围栏到期后巡检恢复，无 handle 的记录才收敛为 `unknown`。已验证的 preflight 失败只有在**尚无任何 launch receipt** 时才能记为 failed；含糊启动必须保持 `unknown` 且永不自动重放。运维判定上，把「fence 窗口内的静默」与「fence 之后的 `unknown`」分开看，是最容易被误报为故障的一处。

章节来源：[runtime-messaging/README.md](file://packages/server-ai/src/handoff/runtime-messaging/README.md)（关键符号：Leases、A persisted startup fence lasts at most 120 seconds）、[invocation-monitor.service.ts](file://packages/server-ai/src/agent-invocation/invocation-monitor.service.ts)（关键符号：AgentInvocationMonitorService.handle/reconcile）、[invocation-runtime.ts](file://packages/server-ai/src/agent-invocation/invocation-runtime.ts)（关键符号：AgentInvocationRuntime.save、startPendingUntil）

## 3. 取消的运维语义

取消走**两条彼此独立的 Redis pub/sub**，任意一条不通就有一条链路静默失效：

| 频道 | 发布方 | 语义 | 失败表现（源码实测） |
|---|---|---|---|
| `ai:execution:cancel` | `ExecutionCancelService.cancelExecutions(ids, reason?)` | abort 本地登记的 `AbortController`，`ExecutionCancelledError`（`code = 'EXECUTION_CANCELLED_BY_USER'`） | `redis.publish` 抛错只 `logger.warn('Failed to publish cancel event: ...')`，随后仍执行本地 `applyCancel`——**本副本照常停，其他副本静默丢取消** |
| `ai:handoff:cancel` | `HandoffCancelService`（属 handoff 侧） | 队列态删除与 active 态 abort | 与执行取消互不替代；Redis 不可用时该链路整体不可靠 |

排查「静默丢取消」的固定顺序：① 确认该执行所在副本是否订阅到了频道（订阅在 `onModuleInit` 建立，扩容期间新副本可能漏掉一次性消息）；② 看 `Invalid cancel payload` 与 `Failed to publish cancel event` 两类 `warn`；③ 用 Invocation 终态与 provider 的 `exited` 观察交叉验证——**发出了取消不等于进程已停**，`unknown` 必须保持可见。取消是协作式的（`AbortSignal` 传递），不能强杀同步 CPU-bound 代码；`executionAbortScope` 只保证父→子级联与 `dispose` 时对比删除登记。`ExecutionCancelModule` 为 `@Global` 模块，只提供 `ExecutionCancelService`。

章节来源：[execution-cancel.service.ts](file://packages/server-ai/src/shared/execution/execution-cancel.service.ts)（关键符号：ExecutionCancelService.cancelExecutions/applyCancel/onModuleInit/handleCancelMessage、EXECUTION_CANCEL_CHANNEL）、[execution-cancel.module.ts](file://packages/server-ai/src/shared/execution/execution-cancel.module.ts)（关键符号：ExecutionCancelModule）、[agent-invocation/README.md](file://packages/server-ai/src/agent-invocation/README.md)（关键符号：A stop request is not proof of termination）

## 4. 队列与后台任务清单

本子域**不自建队列**，挂在既有 handoff 队列上：

- **handoff 队列**：承载 runtime 投递（`RuntimeMessageTransportService`）与消费者恢复；`agent_runtime_delivery` / `agent_runtime_inbox` 承载 outbox/inbox 与 claim，`.redrive` 只重排被阻塞/失败的传输并保留 claim、phase 与 user-stop 屏障，不重放、不重分配消费者。
- **观察轮询（本域真正的后台任务）**：`AgentInvocationMonitorService.reconcile`（5 s / take 10）、`InvocationContinuationDispatcher.dispatch`（1 s / take 10 / active ≤4，`deliver` 不被观察扫描 await）、`RuntimeObservationMonitorService.reconcile`（5 s / take 20）、`InvocationActivityService.purgeExpired`（1 h / take 100）；前三者都用 `Promise.allSettled` 并行，单条失败不阻塞同批。
- **失败语义**：wait 路径 action 抛错写 `lastError='continuation_pending'`、`nextCheckAt +60 s`，过 `deadlineAt` 直接 `blocked`；观察路径抛错写 `observationError='observation_unavailable'`、`nextObservationAt +60 s`；activity 清理失败只 `warn('Execution activity retention cleanup deferred')`。
- **有界等待不占队列**：`waitForTasks` 超窗正常返回 `pending`，不挂起父级、不暗示任务完成；只有人工交互才挂起（`waiting` + `interaction`）。

## 7. 日志与观测点

| 观测点 | 载体 | 判读 |
|---|---|---|
| `observationError` | `agent_invocation.observationError`，失败写固定串 `'observation_unavailable'`，成功清 `null` | 非空即最近一轮巡检失败；配合 `nextObservationAt` 已推后 60 s 判断「正在退避」 |
| `agent_invocation_wait.lastError` | `'outcome_unknown'`（有依赖 unknown）/ `'awaiting_user'`（卡人工审批）/ `'continuation_pending'`（续跑 action 抛错，60 s 后重试；过 `deadlineAt` 转 `blocked`）/ `'parent_cancelled'`（被取消置 `stale`） | 四种串各指不同处置动作，不要混看 |
| `reconcile()` 指标 | `applicationMetrics.setInvocationWait({pending, oldestErrorSeconds})`，SQL 口径 `state IN ('waiting','ready','blocked')`；`oldestErrorSeconds` 取 `lastError IS NOT NULL` 的最老 `createdAt` | `pending` 长期不降 → 扫描能力不足或依赖卡死；`oldestErrorSeconds` 单调上升 → 有错误从未被清掉 |
| activity 状态 | `page()` 返回 `state`：`not_recorded / recording / closed / expired`，`gaps` 含 `capture_limit`、`interrupted` | `expired` 仍返回空 items；`gaps` 是已知缺失区间，不是错误日志 |
| execution `status` / `error` / `completedAt` | `xpert_agent_execution`；`interruptRunning(ids, threadId, error)` 只把 `RUNNING` 且 `threadId` 匹配的行改成 `INTERRUPTED` 并写 `completedAt` | 不误伤已终态行；历史行 `completedAt` 为 NULL 属预期 |
| Logger 关键字（全部 `warn`） | `'Task observation notification deferred to polling'`、`'Task observation reconciliation deferred'`、`'Task wait lease renewal failed'`、`'Task continuation delivery failed'`、`'Runtime observation scan deferred'`、`'Runtime observation lease renewal deferred'`、`'Failed to publish cancel event: ...'`、`'Invalid cancel payload: ...'`、`'Execution activity retention cleanup deferred'` | 全是降级信号、不阻塞主流程，因此**不能仅凭错误率判断健康**；要结合 `pending` 与 `oldestErrorSeconds` |
| 统一错误码 | `invocationError(code)` 固定映射：`InvalidScope` 403、`InvalidRequest` 400、`CallConflict` 409、`NotFound` 404、`Unsupported` 422、`ProviderUnavailable` 503、`ProviderChanged`/`DispatchUnknown`/`InteractionConflict`/`ConcurrentUpdate` 409、`MissingResult` 502 | 抓 `code` 比抓变动的 i18n 文案更稳 |

## 8. 多副本注意事项

- **CAS 冲突是常态，不是异常**：`replace(record, expectedRevision)` 失败即返回 `false`，由 `updateLatest` 重读重试（≤8 次）；滚动升级期间新旧副本同时写同一调用会出现大量「提交失败但无错误」，监控不应把它当故障；`agent_invocation_event` 唯一 `(invocationId, revision)` 保证事件级幂等。
- **租约续租失败只 warn，不中止本轮**：三套租约心跳都是 `setInterval(...).catch(warn)`。若某副本 GC 停顿超过租约，另一副本会合法接管同一行——两边都以为持有，**只有 CAS 落库能裁决**；绝不能把「租约未过期」当互斥保证。
- **多副本取消必须有 Redis**：`ai:execution:cancel` 是 pub/sub（非持久、非确认），副本扩容期间新副本若在订阅建立前收到取消会永久漏掉；约定是「先部署消费者，再依赖跨副本取消」。
- **门闩是进程内单例**：`AgentInvocationMonitorService.busy`、`InvocationContinuationDispatcher.scanning/active`、`RuntimeObservationMonitorService.scanning` 只阻止同进程重入；跨副本靠 `leaseUntil` + `take(N)` 分摊，因此吞吐**不随副本数线性上升**（每副本每轮仍是 take 10/20/4，且大量轮次因租约被占而空转）。
- **在途本地事件不跨副本**：`TaskObservationCommittedEvent` 只唤醒本进程的 `reconcile`；另一副本只能等自己的 `@Interval`——这是「polling 是唯一持久恢复机制」的直接推论。
- **fence 与租约的组合风险**：副本 A 处于启动围栏内不做失效判定，副本 B 若已过围栏并接管同批行，可能先把 `running` 判成 `unknown`；排障时要把「同一时间窗内的 `unknown`」与启动时刻对齐看。

## 9. 安全运维

- **owner-scoped 收据不等于结果与运行权限**：`GET /api/agent-invocations/:id/delivery` 的投影里**没有结果体**，且授权撤销后 owner 仍可读传输失败（明写「Owners with active organization membership can inspect transport failures even when a binding is revoked; this endpoint does not expose executor result bodies or grant runtime access.」）。审计时不要把「能看收据」当成「有数据面权限」。
- **pin 快照不可静默回退**：`agent_invocation.providerSource` 首次解析即落库，后续 `inspect/cancel/respond` 都走 `registry.getPinned`，找不到即 `ProviderChanged`（409）。运维含义：升级/下线某个 runtime provider 时必须保证旧快照仍可解析，否则在途调用会集体 409，**这是设计使然**，不该被「修掉」。
- **绑定创建期的硬闸**：`POST /api/agent-runtime-bindings` 走 `requireResourceAdmin()`，显式拒绝 `provider ∈ {xpert, xpert-task}`（`InvalidRequest`），`workspaceIds` 去重后必须全部命中当前 org scope（`countBy` 不符即 `InvalidScope`），`target.revision` 与 `id` 都在建时 `randomUUID()` 固定；`bindingSchema` 为 `.strict()`，未知字段直接 400。
- **管理面靠显式调用而非 Guard**：`AgentRuntimeBindingsController` 三个端点都调 `requireResourceAdmin()`，`AgentInvocationsController` 用 `findOwned()` 校验 `id + ownerId + tenantId + organizationId` 并与记录内 `scope` 四元组逐字段复核；两个 controller 都**没有 `@UseGuards`**——新增端点若忘记补判权，全局 AuthGuard 只保证「已登录」。native 目标（`xpert`/`xpert-task`）的 `cancel`/`respond` 一律 `Unsupported`（422），只保留只读 inspect。
- **执行器凭据边界**：host runner 的 receipt 只含 ID 与授权工作目录，不含模型凭据、不接受调用方自选命令；`AgentExecutionRunnerFactoryCapability` 只把 `AgentExecutionRunnerCapability` 暴露给 runtime 策略，不暴露全局能力注册表或 runner 工厂。
- **activity 数据面收敛**：`output(invocation, key, offset)` 在 state 缺失、`expired` 或已过 `expiresAt` 时一律 `NotFound`；超 `EXECUTION_ACTIVITY_MAX_BYTES` 或 `seq >= 20000` 时记 `gaps: ['capture_limit']`——主动声明缺口而不是静默截断；写入前对字符串统一 `redactCredentials`。
- **资源卡与下载**：`InvocationResultsProvider.resolveViewFile` 要求引用带 `versionId` 并经 `artifacts.resolveForManagementAccess` 解析 pinned 版本（不静默选后续版本）；资源卡本身不授予访问权。

## 10. 结论

本子域的运维本质是「用轮询 + CAS + 租约把不稳定交给可恢复的持久状态」：三套租约必须分清（观察 60 s / wait 120 s / 投递与消费各一套），恢复只认 `@Interval`（本地事件与队列只是加速）；启动 fence ≤120 s 解释了「刚启动时的静默」与「围栏后的 `unknown`」都是预期；取消是协作式的两条独立 pub/sub，任何一条不通都会静默丢取消，`unknown` 必须保持可见；迁移全部 additive + repeatable，`completedAt` **不 backfill**、历史行结束时间永久未知；多副本下 `busy`/`scanning` 只是进程内门闩，最终裁决永远是 CAS 落库。
