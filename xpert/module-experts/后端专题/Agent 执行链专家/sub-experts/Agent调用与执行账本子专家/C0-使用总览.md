# C0 · 使用总览（Agent 调用与执行账本子专家）

> 契约层 CR1。父级域契约见 `file://.module-experts/后端专题/Agent 执行链专家/C0-使用总览.md`；本文只覆盖子专家 ②。
> 路径以仓库根为基准的相对 `file://` 引用；不写行号；不复述实现层结构、规模与测试清单。

## 1. 定位

本子专家负责 **「一次 Agent 调用如何被授权、幂等发起、记账、观察与停止」**：Invocation 运行时账本、执行与用量账本、有界等待与续跑、协作式取消、后台任务入口与结果/资源卡视图。

- 目录：`file://packages/server-ai/src/agent-invocation/`、`file://packages/server-ai/src/xpert-agent-execution/`、`file://packages/server-ai/src/shared/execution/`
- 核心口径（明写）：**Invocation 是运行时账本，Project Task 保留业务决策**；中间件工具、工作流 Agent 节点、后台任务是**同一个 runtime 的 caller**，不各自拥有另一 Agent 的图、进程、会话或协议。
- **不做**：投递与队列（`handoff` 的队列 / outbox 写入器 / 实时通道）、会话与线程准入、具体 provider 实现（`xpert-plugins/xpertai/integrations/agent-runtimes` 的 Codex / Pi / Claude Code / OpenCode）。

## 2. 何时找这个子专家

- 查「一次执行为什么没跑起来 / 卡住 / 停在 waiting」。
- 查 Invocation 状态口径、幂等命中与 CAS 冲突（提交失败但无异常、`ConcurrentUpdate`）。
- 排查运行时绑定（org 级绑定、`provider` 白名单、workspace 授权、`enabled` 语义）。
- 排查「停不下来」「僵尸 run」「取消丢了」「续跑没发生」。
- 查执行与用量账本口径（审计时间戳、`completedAt`、用量与定价写入）。
- 接后台任务（`AssistantTaskRuntimeService`）或 `task_status` 型有界等待。
- 查 activity 游标 / 分段读与活动记录保留。
- 需要判断某件事属于「本域账本不变量」还是「跨域投递语义」。

## 3. 能力清单

| 能力 | 入口 | 一句话 |
|---|---|---|
| 调用唯一状态转移入口 | 服务 `AgentInvocationRuntime.scoped(access)` → `{ start, inspect, cancel, respond }` | 授权、幂等键、pin、CAS 全在这一个入口 |
| 幂等复用 | `AgentInvocationFactoryService.existingApi(id)` | 按记录还原**原始** scope 的 scoped API（仅项目作用域且非 captured） |

| 恢复与续跑后台通道 | `AgentInvocationMonitorService.process` / `deliver`（内部 `claim` 租约领取） | 轮询扫描 + 租约认领，本地事件只提前唤醒 |
| 等待与续跑 | `AgentInvocationWaitStore`、`invocation-task-wait.ts`、`task-wait-control.ts`、`InvocationContinuationDispatcher` | `agent_invocation_wait` 状态机 + 有界观察 |

| 绑定管理 | `GET/POST /api/agent-runtime-bindings`、`PUT :id` | admin-only；拒绝 `provider ∈ {xpert, xpert-task}` |
| 调用控制面 | `GET /api/agent-invocations/:id`、`POST :id/cancel`、`POST :id/respond` | owner 四元组校验；native 的 cancel/respond 一律 `Unsupported` |

## 4. 边界

1. **投递读据与重排（`delivery` / `redrive`）逻辑属「对话与会话专家」**：`RuntimeDeliveryController` 文件物理在 `handoff/runtime-messaging/`，controller 注册在 `AgentInvocationModule.controllers`，对外同一前缀；改动需两侧确认。
2. **队列物理与 outbox 写入器属对方**：`TypeOrmAgentInvocationStore.replace` 在同事务内调 `appendRuntimeDelivery` 写 `agent_runtime_delivery`，但传输 worker、`RuntimeMessageProcessor`、`RuntimeMessageInboxService`、`RuntimeObservationMonitorService` 的语义不在本域。
3. **Project Task 的业务决策与最终验收不在本域**；本域只负责「已决定工作的执行与调用账本」。
4. **模型客户端与计费属「模型访问与计费专家」**；本域只提供经 `AgentInvocationFactoryService` 捕获的 scoped 出口。
5. **`native-invocation-reader.ts` 物理在 `agent-invocation/` 但语义属本域的只读观察面**；`/api/xpert-agent/*` 属子专家 ①；中间件运行时 / Prompt 工作流 / 协作属子专家 ③。
6. WS / GraphQL / gRPC 面：**无此项**。

## 5. 已知问题与常见坑

1. **CAS 冲突是返回值不是异常**：`replace(record, expectedRevision)` 在 `affected !== 1` 时立即返回 `false`；调用方必须重读重算（`updateLatest` 上限 8 次，超限才收敛为 `ConcurrentUpdate` 409）。事件表唯一 `(invocationId, revision)` 冲突会回滚整个 `replace` 事务。
2. **停请求不是终止证明**：只有 `exited` 能确认进程停止，`unknown` **必须保持可见**；取消是协作式的（`AbortSignal`），不强杀 CPU-bound，也取消不了 Project Task。
3. **解析一次即 pin，恢复不得静默回退**：`providerSource` 首次解析落库，此后 `pinned(record)` 走 `registry.getPinned(provider, providerSource)`，找不到即 `ProviderChanged`（409），**不降级**到另一个实现。
4. **先持久化再派发**：`start` 先 `insert` 保留 `queued`，CAS `begin` 赢家才调 `strategy.start`；幂等键 `agentInvocationId(scope, callId)` 含 `scope.parentExecutionId` 与调用点 `callId`（toolCallId）。
5. **`waitForTasks` 是有界观察**：观察窗口耗尽正常返回 `pending`，**不挂起父级、不暗示完成**；只有人工交互才挂起父级；`unknown` 在 `pending` 中归一为 `unavailable`。
6. **终局化不得重放初始行**：整行重放初次快照会覆盖较新的 `updatedAt` 与用量计数；元数据写入不得移动已记录的结束时间。
7. **`completedAt` 规则**：只在真终态写、恢复 `running` 时清空；迁移**不 backfill** 历史行，`updatedAt` 不能替代结束时间。
8. **三套租约易混**：观察租约（`observationLeaseToken` / `observationLeaseUntil`）、wait 组续跑租约（`leaseToken` / `leaseUntil`）、`agent_runtime_delivery`/`inbox` 的传输与消费认领——语义与时长全不同、互不校验；「租约未过期」不等于互斥保证。
9. **polling 是唯一持久恢复机制**：本地事件与队列投递只是加速，调低或关闭定时扫描等于关闭恢复；**启动围栏内不做中间态失效判定**（`startPendingUntil = now + 120_000`，取消路径仍可用），围栏到期后无 handle 才收敛为 `unknown`。
10. **跨副本取消靠 Redis `ai:execution:cancel`**：发布失败与订阅失败**只告警**——本副本照常停、其他副本可能静默丢取消；无 Redis 时该链路整条不成立。
11. **含糊启动不得自动重放**：`start` 异常落 `unknown` 并抛 `DispatchUnknown`；「先到的完成事件不得重放后来的人工审批」。
12. **`agent_invocation_wait` 表名与语义错位**：实体 `AgentInvocationWaitEntity` 已是「有依赖组的等待记录」，组身份不再天然绑定某个 invocation；按外键假设推断关联会得出错误结论。**另**：`AgentInvocations` / `AgentRuntimeBindings` 两个 controller **无 `@UseGuards`**，鉴权是显式调用型（`findOwned()` 四元组 / `requireResourceAdmin()`）——新增端点若只依赖全局 `AuthGuard`，默认就是放行的。
