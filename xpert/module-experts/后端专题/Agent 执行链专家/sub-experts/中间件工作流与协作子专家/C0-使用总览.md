# C0 · 使用总览（中间件运行时 · Prompt 工作流 · 协作子专家）

> 契约层 CR1。父级域契约见 `file://.module-experts/后端专题/Agent 执行链专家/C0-使用总览.md`；本文只覆盖子专家 ③。
> 路径以仓库根为基准的相对 `file://` 引用；不写行号；不复述实现层结构、规模与测试清单。

## 1. 定位

三块代码共享同一个定位：**给 Agent 提供受控能力面，而不是承载业务逻辑**。

- **中间件运行时**（`file://packages/server-ai/src/shared/agent/middleware-runtime/`）：把一次调用内的能力装配为 `AgentMiddlewareRuntimeApi`（`createScopedApi` / `createModelClient` / `getModelProvider?` / `wrapWorkflowNodeExecution` / `emitMiddlewareEvent?` / `capabilities?`），并注入 `IAgentMiddlewareContext.runtime` 供中间件策略按需取用。`AgentMiddlewareRuntimeService` 自身不含领域行为——「domain behavior lives in focused runtime services so this class only owns capability composition」。
- **Prompt 工作流**（`file://packages/server-ai/src/prompt-workflow/`）：斜杠命令 → 提示词模板的**作者态存储**与**运行时解析**面。运行时只输出扁平化的 `RuntimePromptWorkflowCommandSource[]`，真正的展开由 `ResolvePromptWorkflowInvocationHandler` 完成，且仅当输入形如 `/name args` 时才介入。
- **协作**（`file://packages/server-ai/src/collaboration/`）：**不是 Agent 执行链的一部分**，只提供共享文档的 CRDT 能力面（`CollaborationApi`）与在线状态（presence）。平台持有权威 Yjs 状态；「Plugin providers own resource authorization and projection into business entities」。

## 2. 何时找这个子专家

- 接中间件插件，或排查「插件能拿到什么能力、不能拿到什么能力」。
- 排查草稿态 / 发布态 runtime 上下文串味。
- 改 Prompt 工作流模板（工作空间命令模板、命令档案快照、运行时斜杠命令解析）。
- 排查 `prompt_workflow` 同名冲突、归档 / 软删后的可见范围与「用量」口径。
- 查 / 接协作文档 WS（CRDT 更新、presence、会话凭据、ack 语义）。
- 排查「更新已 ack 但文档没变」「重连后丢包」「物化失败但更新不丢」。
- 判断某能力该由插件 provider 提供还是由平台提供。
- 需要确认模型 client 的构造、provider 解析与事件出口路径。

## 3. 能力清单

| 能力 | 入口 | 一句话 |
|---|---|---|
| scoped API 注入 | 服务 `AgentMiddlewareRuntimeService.createScopedApi(scope)` | 每次都新建；`scope` 含租户 / 组织 / 用户 / 工作区 / 项目 / 助手 |
| 模型 client | 服务 `createModelClient(copilotModel, options)` | 走 `AgentMiddlewareModelRuntimeService`，与 `expectedExecutionModel` 不符即拒绝 |
| provider 解析 | 服务 `getModelProvider(provider)` / `resolveSelectedConnectorRuntimeBindings(scope)` | 必须同时具备 provider 与租户；无候选即「未配置」 |
| 事件出口 | 服务 `emitMiddlewareEvent(event)` | 统一事件类型与时间字段后经聊天事件送出 |
| 工作流节点执行包裹 | 服务 `wrapWorkflowNodeExecution(run, params)` | 把节点执行包上执行账本语义（中断归 `interrupted`） |
| 运行时 scope 补齐 | `resolveAgentExecutionScope(scope)`（`execution-scope.ts`） | 从 LangChain runnable config 补齐 tenant/org/user 等身份 |
| Prompt 工作流作者态 | `GET/POST/PUT /api/prompt-workflow/*`（7 端点，全 `WorkspaceAuthoringGuard`） | workspace 内模板 CRUD / 归档 / 复制 / 用量 / 档案校验 |
| Prompt 工作流运行时解析 | `PromptWorkflowService.resolveRuntimeCommandProfile(...)`；CQRS `ResolvePromptWorkflowInvocationQuery` | 把斜杠命令展开成一次对话输入 |
| 协作文档与在线状态 | WS `/api/collaboration`；服务 `CollaborationService.createScopedApi(defaults)` → `CollaborationApi` | CRDT 文档 + presence；`update` 先落库后 ack |
| 物化重试 | `CollaborationService.retryMaterialization(documentId)` | 物化失败只降级为「失败 + 重试」，绝不回滚已提交更新 |

## 4. 边界

1. **本子专家不拥有 Agent 图与调用账本**：中间件策略注册表 `AgentMiddlewareRegistry` 由 `@xpert-ai/plugin-sdk` 提供；工作流 / 协作都不定义 Agent 图。
2. **协作 ≠ Agent 执行**：协作只提供文档能力面，业务实体投影由插件 provider 负责（服务注释明写）。
3. **模型 / 凭据的创建属「模型访问与计费专家」**：本子专家只提供 scoped 出口；计费与用量落地归属对方。
4. **`/api/xpert-agent/middlewares*` 三端点属子专家 ①**（草稿态可视面），本子专家只提供其底层运行时装配语义。
5. **`/api/prompt-workflow/*` 是作者态面**：运行时解析经 CQRS 查询与 `shared/agent/message.ts` 派发，不新增 HTTP 面。
6. **图编译与校验属子专家 ①**；Invocation 账本与执行账本属子专家 ②。
7. GraphQL / gRPC 面：**无此项**。

## 5. 已知问题与常见坑

1. **只暴露 `createScopedApi` 的受控 API，不得把全局 registry 传给插件**：`AgentMiddlewareRuntimeApi` 只含上表五个能力位 + `capabilities`；平台能力通过 `platformCapabilities.require(...)` 在服务内部取用后转发。该边界由 `file://packages/server-ai/src/shared/agent/middleware-runtime/middleware-runtime.provider-boundary.spec.ts` 以**模块元数据断言**固化：消费方必须 import runtime module、不得自行 provide runtime service；`SandboxModule` 不得导入 `AgentMiddlewareRuntimeModule`。
2. **草稿态与发布态上下文分离**：草稿 runtime 由子专家 ① 的 `createDraftXpertMiddlewareRuntime` 单独构造；运行时报文 scope 由 `resolveAgentExecutionScope` 从 runnable config 补齐，**不复用请求上下文**。
3. **Workspace 能力需要绑定数据所有者**：只有 `projectId` / `xpertId` 存在，或 `catalog === 'users' && scopeId === userId` 时才注册 workspace-files、tool-images、知识库视觉资产能力（`hasBoundRuntimeWorkspaceScope`）；缺能力时 `require(...)` **显式失败**，而不是回落到更宽的默认实现。
4. **`prompt_workflow` 唯一 `(workspaceId, name)`**：实体上 `@Index(['workspaceId', 'name'], { unique: true })`；同名并发创建 / 重命名直接撞唯一约束；软删（`archivedAt`）**不影响**唯一约束。
5. **`sourceTemplateId` 是 server-owned provenance**：实体 JSDoc 明写「never inferred from a matching name」；`initializeDefaultsInWorkspace` 的关联补写必须**同时**匹配 `sourceTemplateId`。
6. **`associatedXpertIds` 需与模板使用方同步**：默认初始化只在「有 `sourceTemplateId` 且有 `xpertId`、未归档、且该 xpert 不在现有列表」时才追加；清空该数组会把命令放大为全局可见。
7. **协作鉴权是 opaque `sessionId` / `clientKey`，不是 Nest Guard**：`resolveSession(sessionId, clientKey, documentId)` 校验 documentId 匹配与 TTL，并用 `timingSafeEqual` 比对 `clientKeyHash`；会话只访问单个文档房间（`collaboration:<documentId>`）；凭据泄漏即可被任意来源复用。
8. **WS `cors.origin='*'`**：`@WebSocketGateway({ namespace: '/api/collaboration', cors: { origin: '*' }, transports: ['websocket'] })`——非 websocket 传输不被接受，也不会因来源不同被拦。
9. **`update` 先落库后 ack**：网关注释「Persist a client update before acknowledging it; service broadcasts after commit」；服务端错误统一 `client.emit('error', { message })`，**不映射 HTTP 状态，也不发 `update-ack`**——客户端必须按 ack 语义重试。
10. **`collaboration.module` 是 `@Global`**；中间件运行时模块同样是 `@Global()` 并以 `XPERT_AGENT_MIDDLEWARE_RUNTIME_TOKEN` 暴露门面。全局模块让「谁在什么时候拿到了能力」更难在依赖图上看出来。
11. **`pruneUpdates` 有保留窗口**：`UPDATE_RETENTION_COUNT = 200`、`UPDATE_RETENTION_MS = 24h`，二者取更保守者裁剪 `collaboration_update`；**早于窗口的重放不再命中判重**。
12. **更新历史与权威状态分离**：`applyUpdate` 走「授权 → 判重 → 合并 → 落库 → 广播 → 物化」；物化失败由 `enqueueMaterialization` / `retryMaterialization` 兜底，已提交的更新不回滚。
