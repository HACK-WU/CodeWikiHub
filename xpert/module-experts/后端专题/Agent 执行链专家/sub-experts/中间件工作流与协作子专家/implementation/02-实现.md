## createScopedApi：注入清单与 capabilities 输出

`createScopedApi(scope = {})` 先复制 scope（`connectorBindingIds`/`connectorProviders` 做浅拷贝防止调用方数组被改写），随后构造五个能力 API 并汇总为 `DefaultRuntimeCapabilityRegistry`：

| 输出 | 来源 |
| --- | --- |
| `ActorTokenRuntimeCapability` | `platformCapabilities.require(ActorTokenRuntimeFactoryCapability).createScopedApi({ ...scope, act: { sub: 'xpert_agent' } })` |
| `FileRuntimeCapability` | `fileRuntime.createScopedApi(scope)` |
| `ConnectorRuntimeCapability` | `platformCapabilities.require(ConnectorRuntimeFactoryCapability).createScopedApi(scope)` |
| `ArtifactsRuntimeCapability` | `artifacts.createScopedApi({ ...scope, organizationId: scope.organizationId ?? RequestContext.getOrganizationId() })` |
| `CollaborationRuntimeCapability` | `collaboration.createScopedApi(scope)` |
| `AgentInvocationRuntimeCapability` | 仅当 `platformCapabilities.get(AgentRuntimeFactoryCapability)` 命中时注册 |
| `WorkspaceFilesRuntimeCapability` / `ToolImagesRuntimeCapability` / `KnowledgeDocumentVisualAssetsRuntimeCapability` | 仅当 `hasBoundRuntimeWorkspaceScope(scope)` 为真 |

另外固定注册 `['platform.middleware.mcp-apps', { version: 1 }]`，并以 `this.platformCapabilities` 作为父层完成继承。`ToolImagesRuntimeCapability` 的 `resolveScope` 延迟调用 `resolveAgentExecutionScope(scope)`，再用 `RequestContext.currentTenantId()/getOrganizationId()/currentUserId()` 兜底。

## ModelRuntimeService：provider 解析与事件出口

- **`createModelClient`**：解析 tenant/org/user/xpert（scope 优先，`RequestContext` 兜底）；`CopilotGetOneQuery(tenantId, copilotId, ['modelProvider'])`；若传入 `expectedExecutionModel` 则逐字段比对 copilotId / providerScopeId / providerName / providerOrganizationId，不符抛 `Error.ModelExecutionDenied`；限额走 `CopilotCheckLimitCommand`，但 `purpose === 'observe'` 时跳过（不改配额）；LLM 类型额外做 `ensureCopilotModelContextSize` 与 `resolveModelParameterOptions`；最后 `modelProvider.getModelInstance(...)`，在 `handleLLMTokens` 中回放 `usageCallback`、按需写 `applicationMetrics.recordLlmUsage`、再提交 `CopilotTokenRecordCommand`；捕获 `ExceedingLimitException` 时 abort 当前请求。
- **`getModelProvider(provider, scope)`**：必须同时具备 `provider` 与 `tenantId`，否则抛 `Error.ToolModelProviderContextRequired`；候选来自 `CopilotService.findAllEnabledCopilotsWithoutMembership`，过滤条件包含 providerName、可选 providerScopeId、`isValid !== false`、credentials 非空；排序为「组织匹配优先 → `MODEL_PROVIDER_ROLE_PRIORITY`（Primary/Secondary/Reasoning/Embedding）→ provider id 字典序」；无候选抛 `Error.ToolModelProviderNotConfigured`；返回连接对象含 `providerScopeId/copilotId/baseURL/authorization/resolveModelAccess/resolvePricingSnapshot/reportUsage`，`reportUsage` 最终落 `CopilotUsageService.recordModelUsage`。
- **`emitMiddlewareEvent`**：剥掉 `agentKey`/`type`，统一打上 `type: 'middleware_event'`，补 `created_date`，并在 `status` 存在且非 `running` 时补 `end_date`，经 `dispatchCustomEvent(ChatMessageEventTypeEnum.ON_CHAT_EVENT, ...)` 送出。

章节来源：[model-runtime.service.ts](file://packages/server-ai/src/shared/agent/middleware-runtime/model-runtime.service.ts)（关键符号：AgentMiddlewareModelRuntimeService.getModelProvider / emitMiddlewareEvent）

## wrapWorkflowNodeExecution：执行包裹语义

`AgentMiddlewareRuntimeService.wrapWorkflowNodeExecution` 直接委托 `AgentMiddlewareModelRuntimeService`，后者把 `commandBus`/`queryBus` 注入 `wrapAgentExecution(run, params)` 并立即调用返回的闭包。`wrapAgentExecution` 的语义为：写入 `RUNNING` 的 `XpertAgentExecutionUpsertCommand` → 推送 `ON_AGENT_START` → `try` 执行 `run(execution)` 取 `{ output, state }` → `catch` 时把 `isGraphInterrupt` 或 `ExecutionCancelledError` 记为 `INTERRUPTED`、其余记为 `ERROR`（GraphInterrupt 不写 error），并按需调用 `catchError` → `finally` 以 `elapsedTime` 与 `outputs: { output }` 二次 upsert，重新查询 `XpertAgentExecutionOneQuery`，推送 `ON_AGENT_END`。函数返回值是内部 `state`，`output` 只用于落库与事件。

## 中间件注册与顺序

## Prompt 工作流：作者态 CRUD 与默认初始化

- **`createInWorkspace`**：`normalizePromptWorkflowInput` → `resolvePromptWorkflowAssociations` → `this.create({ ...workflow, ...associations, workspaceId })`（基类 `XpertWorkspaceBaseService.create` 会再次断言写权限并补齐 workspace/tenant/organization 列）。
- **`initializeDefaultsInWorkspace`**：断言写权限 → 归一化 → 模板内同名直接 `BadRequestException('Template prompt workflow names must be unique')` → `repository.manager.transaction`，在事务内以 `lock: { mode: 'pessimistic_write' }` 读取同名既有行。若同时给出 `sourceTemplateId` 与 `xpertId`，对满足「同 sourceTemplateId、未归档、`associatedXpertIds` 非空且不含该 xpert」的行**追加** xpert id；随后只插入缺失名字，并写入 `sourceTemplateId`、`workspaceId/tenantId/organizationId`、`createdById/updatedById`。返回 `{ created, skipped }`。
- **按 key 变体**：`upsertInWorkspaceByKey` 先归一化 key（剥前导 `/`），不存在则 `create`、存在则 `update`，返回值带 `operation: 'created' | 'updated'`；`archiveInWorkspaceByKey` 返回 `operation: 'deleted'`。
- **`updateInWorkspace`**：`findOne(id)` 后校验 `workspaceId` 一致，否则 404；归一化后 `Object.assign` 显式清理语义——`label/description/category/argsHint/icon/runtimeCapabilities` 传 `undefined` 保留旧值、传空值则置 `null`。
- **`duplicateInWorkspace`** 用 `createCopyName`（`-copy`、`-copy-2`…最多 100 次，`slice(0, 64)`）派生名字，并复制快照、组织标签与 `associatedXpertIds`。
- **`getUsage`**：汇总 workspace 内未删除的 xpert，判定为 `latest && isPromptWorkflowApplicable` 或 `commandProfile`/`draft.team.commandProfile` 中存在 `source === 'workspace_prompt_workflow' && workflowId === id` 的条目。

## Prompt 工作流：校验、快照与运行时解析

- **`validateCommandProfile(workspaceId, profile)`**：先 `normalizeCommandProfile`；仅收集「启用、`source === 'workspace_prompt_workflow'`、无 `snapshot`」条目的 `workflowId`，有 id 但缺 workspaceId 直接 400；随后 `findActiveWorkflowMap` 要求全部命中未归档未删除的行，否则 400 列出缺失 id。`source === 'xpert'` 走 `normalizeLocalCommandEntry`（要求合法 name 与 template）；`source === 'skill'` 要求 `skillCommandName ?? name`。
- **`snapshotCommandProfile`**：在 validate 基础上为每条 workspace 条目写入 `snapshot = mergeWorkflowWithEntry(workflow, entry)`，把「引用」固化为「可离线回放的快照」。
- **`resolveRuntimeCommandProfile(xpert)`**：`hasProfile = profile.enabled === true`。无 profile 时回落到 `findDefaultWorkspaceCommandSources`（`archivedAt IsNull`、`deletedAt IsNull`、按 name 升序、过滤 `isPromptWorkflowApplicable`）。有 profile 时：`enabled === false` 的 workspace 条目构成禁用集；workspaceCommands 取「未归档、未禁用、applicable」；随后按 `sortCommandProfileEntries`（order 升序）逐条处理——`xpert` 条目归一化为快照并标记 `sourceType: 'xpert'`，`workspace_prompt_workflow` 条目以 `entry.snapshot ?? configured` 为源、先移除同 workflowId 旧项再 push 合并结果，`skill` 条目按 `priority === 'preferred'` 分流。最后 `resolveCapabilityScopes` 对两类命令统一做 `resolvePromptWorkflowCapabilities(runtimeCapabilities, xpertId)`。
- **CQRS 调用面**：`ResolvePromptWorkflowInvocationQuery`（`type = '[Prompt Workflow] Resolve invocation'`）由 handler 处理：若上游已把 `executionType === 'insert_text'` 的 prompt_workflow 展开则直接返回 null；否则先尝试中间件斜杠命令（由 `xpert.graph` 的中间件节点 + registry `meta.slashCommands` 推导，`/goal` 这类非必需命令还要求 `runtimeCapabilities.plugins.nodeKeys` 命中），再走 `resolveRuntimeCommandProfile`。展开时保留 `help/clear/plan/goal/skills/plugins/subagents/model/effort/status/mention` 为保留名，`renderPromptWorkflowTemplate` 支持 `{{args}}` 占位符替换，否则模板与参数以空行拼接。

## 协作：会话鉴权与 CRDT 物化

- **`createSessionWithScope`**：`requireDocument` → `authorize(..., access)` → `sessionId = randomBytes(32).base64url`、`clientKey = randomBytes(24).base64url`，仅保存 `clientKeyHash = sha256(clientKey)`；`actor` 由 `createUserActor(RequestContext.currentUser(), scope.userId, sessionId)` 生成；TTL 600s，写入本地 Map 与 Redis（key 为 sessionId 的 hash）。
- **`resolveSession(sessionId, clientKey, documentId)`**：三者缺一即 null；先清过期本地会话，再回落 Redis；校验 `session.documentId === documentId`、未过期，并用 `timingSafeEqual` 比对哈希。
- **`applyUpdateWithScope`**：解析 base64（上限 2 MiB）→ 事务内 `pessimistic_write` 锁文档；要求 `status === 'active'`（否则 404）；`authorize(..., 'write')`；`expectedSequence` 不符抛序列冲突 400；以 `sha256(update)` 判重（重复直接返回，不重复广播/物化）；`Y.applyUpdate` 后校验文档体积 ≤ 32 MiB，`sequenceNumber += 1`、`updateCount += 1`、`materializationStatus = 'pending'`，写 `collaboration_update` 与文档快照。提交后广播 `update`、执行 `materialize`、异步 `pruneUpdates`。
- **物化**：`materialize` 调用 provider 的 `materializeDocument`，成功则更新 `materializedSequence/materializationStatus='ready'/lastMaterializationError=null`；失败只标记 `failed` 并写错误信息（截断 2000 字符），绝不回滚已提交的 CRDT 更新，随后 `enqueueMaterialization` 投递 `{ queueName: 'collaboration', jobName: 'materialize', attempts: 3, backoffMs: exponential 1000 }`。`CollaborationMaterializationProcessor`（`@PluginJobProcessor`，concurrency 2）调用 `retryMaterialization` 重放。`getDocumentWithScope` 在 `materializedSequence < sequenceNumber` 时还会触发 `platform:read-repair`。
- **`pruneUpdates`**：删除同时满足「`sequenceNumber <= seq - 200`」且「`createdAt < now - 24h`」的历史行。
- **presence**：`persistPresence` 经 `sanitizePresence`（体积上限 16 KiB）后写 Redis（entry TTL 30s，index SET 再 expire 60s）并广播；`readPresence` 读取时顺带剔除 `updatedAt < now - 15s` 的陈旧项并广播 `presence-remove`。

## WS gateway 的消息处理与 ack 顺序

`CollaborationGateway` 声明 `namespace: '/api/collaboration'`、`cors: { origin: '*' }`、`transports: ['websocket']`。连接阶段从 `handshake.auth`（或 query）取 `sessionId/clientKey/documentId`，`resolveSession` 失败即 emit `error` 并 `disconnect(true)`；成功后加入房间 `collaboration:${documentId}`，依次 emit `sync`（完整状态或增量）与 `presence-snapshot`（含 `selfClientId`）。消息面：

| 消息 | 行为 | 回执 |
| --- | --- | --- |
| `update` | `applyUpdateForSession`（校验 write 权限） | 成功 `update-ack`，失败 `error` |
| `sync-request` | `getStateForSession(session, stateVectorBase64)` | `sync` |
| `presence` | `upsertPresenceForSession(session, client.id, sanitizePatch(data))` | 无（失败 `error`） |

`update` 的 ack 在服务端持久化完成之后发出；广播由 `CollaborationService.onBroadcast` 回调统一扇出到单文档房间。断开连接时按 clientId 移除 presence。

## 设计模式

- **Scoped API 门面**：`createScopedApi` 每次调用产出独立能力表；`CollaborationService.createScopedApi(defaults)` 先绑定身份再暴露 10 个方法，插件无法逐调用伪造 tenant/scope。
- **策略注册表**：`BaseStrategyRegistry` + 装饰器发现（`AgentMiddlewareRegistry`、`WorkflowNodeStrategy`）。
- **CQRS**：`ResolvePromptWorkflowInvocationQuery` 与 `XpertAgentExecution*` 命令/查询。
- **WS Gateway + Redis Pub/Sub**：`onBroadcast` 本地优先、Redis 跨节点，`receiveBroadcast` 丢弃同 `nodeId` 回环。
- **CRDT（Yjs）+ 事务内悲观锁 + 幂等哈希**：把并发写合并进单文档序列号。
- **软删/归档双轨**：`deletedAt`（软删）与 `archivedAt`（业务归档）并存于 prompt_workflow。

## 热点路径

1. **每次中间件执行的 scoped API 创建**：一次中间件装配会创建 actorToken/file/connector/artifacts/collaboration 五个 scoped API，可能再加 agentInvocation、workspaceFiles、toolImages、visualAssets 四个；`api` getter 每次都新建（注释明示不得缓存首个调用者身份）。
2. **协作高频 update 的写放大**：每次 update 至少 1 次文档锁读 + 1 次哈希查重 + 2 次写（update 行 + 文档整状态 base64 重写）+ 1 次广播 + 1 次 provider 物化；`pruneUpdates` 又是异步删除。文档状态随编辑线性增长，32 MiB 上限即天花板。
3. **运行时命令解析**：`resolveRuntimeCommandProfile` 每次都会拉取 workspace 全量未删除工作流再内存过滤（`/name` 命中时）。

## 技术债

1. **`collaboration.module.ts` 的 `@Global` 隐式耦合**：`@Global()` 使 `CollaborationService` 与 `CollaborationDocumentProviderRegistry` 可被任意模块注入，依赖关系不再由 import 图表达；同时 `CollaborationGateway` 未被 exports。
2. **`cors.origin = '*'`**：WS 命名空间对任意来源开放，安全性完全依赖 opaque 会话凭据本身（无 Origin 白名单、无 Nest Guard）。
3. **opaque token 的校验链完整性未确认**：`resolveSession` 只校验会话存在/未过期/文档匹配/clientKey 哈希，代码内**没有**再次校验租户、用户或 workspace 成员资格；若会话可被跨环境复用（如共享 Redis），缺少第二道校验的证据。
4. **`prompt-workflow` 关联同步易错**：`associatedXpertIds` 在 `initializeDefaultsInWorkspace` 中被静默追加，`resolvePromptWorkflowAssociations` 只校验**新增** id（既有历史 id 允许悬空），且 `isPromptWorkflowApplicable` 把「空数组」定义为全局可见——清空即放大可见范围。
5. **`pruneUpdates` 的保留窗口**：只保留最近 200 条且不超过 24h 的 update 行，`updateHash` 幂等窗口随之收窄——早于窗口的重放请求将不再命中判重而重新计入序列号。
6. **`prompt_workflow` 唯一约束不感知软删**：`@Index(['workspaceId', 'name'], { unique: true })` 与 `deletedAt` 并存，被软删的名字无法在原 workspace 复用（`createCopyName`/`findWorkspaceWorkflowByKey` 均按 `deletedAt IsNull` 过滤）。

## 设计维度

- **维度一：身份绑定时机**。运行时侧「一次调用一次装配」（`createScopedApi` 不缓存调用者），协作侧「一次会话一次绑定」（`createScopedApi(defaults)` 固化 scope，浏览器只持 opaque 凭据）——两者都把 scope 从「参数」提升为「构造前提」。
- **维度二：引用 vs 快照**。`TXpertCommandProfileEntry` 允许 `workflowId` 引用与 `snapshot` 内联并存，`snapshotCommandProfile` 主动固化，`resolveRuntimeCommandProfile` 以 `entry.snapshot ?? configured` 取值——发布态可离线回放，草稿态始终读最新。
- **维度三：失败语义**。模型侧失败直接抛出；协作物化失败降级为 `failed` + 队列重试，绝不否定已提交的 CRDT 更新；Prompt 工作流引用失效则在 validate 阶段 400 拦截。

## 结论

实现上三块共享同一套「宿主授予、插件消费」的结构：中间件运行时把领域能力收敛到一次 `createScopedApi`，Prompt 工作流用「作者态 CRUD + 快照/运行时解析」覆盖草稿与发布两种语义，协作把权威 CRDT 状态留在平台、把授权与投影交给插件 provider。主要风险集中在模块可见性（`@Global`）、WS 面暴露（`cors: '*'`）与保留窗口（`pruneUpdates`）三处。
