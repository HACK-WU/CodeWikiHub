## prompt_workflow 表 schema

`@Entity('prompt_workflow')`，`@Index(['workspaceId', 'name'], { unique: true })`。

| 列 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| `name` | `varchar(64)`，NOT NULL | 命令名；运行时按 `/^[a-z0-9][a-z0-9_-]{0,63}$/` 归一化 |
| `label` | `varchar(120)`，NULL | 展示名 |
| `description` | `varchar`，NULL | 描述 |
| `icon` | `json`，NULL | 字符串或图标对象 |
| `category` | `varchar(80)`，NULL | 分组 |
| `aliases` | `json`，NULL | 别名数组（参与斜杠命令匹配） |
| `argsHint` | `varchar(120)`，NULL | 参数提示 |
| `template` | `text`，NOT NULL | 提示词模板，支持 `{{args}}` |
| `scenarios` | `json`，NULL | 预设场景，由 `isPromptWorkflowScenarios` 约束 |
| `tags` | `json`，NULL | 自由标签字符串数组 |
| `organizationTags` | M2M → `Tag`，`eager: true` | 通过 `prompt_workflow_tag` 关联 |
| `sourceTemplateId` | `varchar`，NULL | **server-owned provenance**；JSDoc：「never inferred from a matching name」 |
| `associatedXpertIds` | `json`，NULL | 适用专家；空数组语义为「全 workspace 可用」 |
| `visibility` | `varchar(20)`，默认 `'private'` | 仅接受 `private` / `team` / `tenant`，非法值回落 `private` |
| `runtimeCapabilities` | `json`，NULL | 能力选择原始值，运行时经 `resolvePromptWorkflowCapabilities` 解析 |
| `archivedAt` | `timestamptz`，NULL | 业务归档时刻（与继承的 `deletedAt` 软删并存） |

注意：契约类型 `TPromptWorkflow` 含可选 `actionType`（`insert_text` / `insert_invocation` / `submit_prompt`），但**实体未声明 `actionType` 列**，该字段只出现在命令档案条目与快照中，不落 `prompt_workflow` 表。

## prompt_workflow_tag 关联表

`PromptWorkflow.organizationTags` 为 `@ManyToMany(() => Tag, { eager: true })`，并以 `@JoinTable({ name: 'prompt_workflow_tag' })` 指定连接表名。该表由 TypeORM 隐式维护（两列外键：prompt_workflow 侧与 Tag 侧），本子域无独立实体、无额外列。标签合法性由 `assertValidTagAssociations(..., target: 'prompt_workflow', relation: 'organizationTags')` 约束：新增标签必须属于当前 tenant（组织标签须匹配 org）、`isActive !== false`，且 `getTagTargets(tag)` 包含 `prompt_workflow`；已持久化的历史关联不做回溯校验。

## collaboration_document 表 schema

`@Entity('collaboration_document')`，索引：唯一 `(scopeKey, providerKey, resourceId)`、普通 `(tenantId, organizationId, providerKey, status)`。JSDoc：「Persistent authoritative CRDT snapshot and its plugin materialization checkpoint」。

| 列 | 类型 / 默认 | 说明 |
| --- | --- | --- |
| `scopeKey` | `varchar` | `sha256("{tenantId ?? '-'}:{organizationId ?? '-'}")` 派生的存储边界，刻意不含 workspace/project/xpert/user 公开标识 |
| `providerKey` | `varchar` | 插件 provider 键，上限 160 |
| `resourceId` | `varchar` | 业务资源 id，上限 256 |
| `engine` | `varchar`，默认 `'yjs'` | CRDT 引擎 |
| `schemaVersion` | `int`，默认 `1` | 插件文档 schema 版本 |
| `status` | `varchar`，默认 `'active'` | `active` / `archived`（`deleteDocument` 写 `'deleted'`） |
| `stateBase64` | `text` | 权威全量 Yjs 状态 |
| `stateVectorBase64` | `text` | 状态向量 |
| `sequenceNumber` | `int`，默认 `0` | 已接受更新的序列号，用于并发校验 |
| `updateCount` | `int`，默认 `0` | 累计接受的更新数 |
| `materializedSequence` | `int`，默认 `0` | 已成功投影到业务实体的序列号 |
| `materializationStatus` | `varchar`，默认 `'ready'` | `ready` / `pending`（接受更新后）/ `failed` |
| `lastMaterializationError` | `text`，NULL | 失败信息，写入前截断至 2000 字符 |
| `workspaceId` / `projectId` / `xpertId` / `userId` | `varchar`，NULL | 业务溯源列（不参与 `scopeKey`） |
| `metadata` | `json`，NULL | 初始化时由 provider 提供的元数据 |

## collaboration_update 表 schema

`@Entity('collaboration_update')`，索引：唯一 `(documentId, sequenceNumber)`、唯一 `(documentId, updateHash)`、普通 `(tenantId, organizationId, documentId)`。JSDoc：「Bounded immutable journal used for update idempotency and operational diagnostics」。

| 列 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| `document` | `ManyToOne(() => CollaborationDocument, { nullable: false, onDelete: 'CASCADE' })`，`@JoinColumn({ name: 'documentId' })` | 文档级联删除 |
| `documentId` | `uuid` | 归属文档 |
| `sequenceNumber` | `int` | 该更新被接受后的文档序列号（每个文档唯一） |
| `updateBase64` | `text` | 客户端提交的原始更新（未重编码） |
| `updateHash` | `varchar` | `sha256(update)`，幂等键（每文档唯一） |
| `origin` | `varchar`，NULL | 更新来源标记，上限 256；默认写入 `platform.collaboration` |
| `actorType` | `varchar`，NULL | `user` / `agent` / `system` |
| `presenceId` | `varchar`，NULL | 操作者 presence 标识 |
| `userId` | `varchar`，NULL | 平台用户 id（来自 scope） |

无独立「客户端标识」列：客户端身份由 `presenceId` 与 `origin` 承载；`clientKey` 仅用于会话鉴权，从不落库（只存其哈希于会话记录）。

## 基类与继承

- `CollaborationDocument` / `CollaborationUpdate extends TenantOrganizationBaseEntity`（**不是** `WorkspaceBaseEntity`）——协作文档不属于 workspace 实体域，workspaceId 只作为普通可空列存在。

## 迁移与 seed

**该模块无此项。** 本子域未提供任何迁移文件：`packages/server-ai/src` 下的迁移目录仅存在于 `agent-invocation`、`agent-plugin`、`assistant-binding`、`chat-conversation`、`chat-message`、`desktop-shell`、`graphrag`、`knowledgebase`、`mcp-app-runtime`、`model-execution`、`xpert-agent-execution`、`xpert-project`、`handoff/runtime-messaging`，均不含 `prompt_workflow` / `collaboration_document` / `collaboration_update` 的建表或 seed 逻辑。因此三张表的 schema 完全由实体定义推导（TypeORM 同步/外部迁移机制），`prompt_workflow_tag` 由 `@JoinTable` 隐式生成。默认工作流数据来自 `PromptWorkflowService.initializeDefaultsInWorkspace` 的运行时写入，而非 seed 脚本。

## 校验规则

- **名字与模板**：`normalizePromptWorkflowInput` 要求 name 命中 `^[a-z0-9][a-z0-9_-]{0,63}$`（否则 400「Prompt workflow command name is invalid」）、template 非空（否则 400「Prompt workflow template is required」）；`normalizeWorkflowKey` 额外剥离前导 `/`。
- **数组与图标**：`normalizeStringArray` 去重、去空、去非字符串；`mergeStringArrayOverride` 在覆盖为空时回落到原值；`normalizeIcon` 接受字符串或普通对象。
- **枚举回落**：`normalizeVisibility` 非法值回落 `private`；`normalizeCommandProfileEntry` 丢弃 `source` 不在 `xpert|workspace_prompt_workflow|skill` 的条目，`actionType` 只接受三种合法值，`enabled` 默认 `true`。
- **scenarios**：由契约层 `isPromptWorkflowScenarios` 校验——最多 20 条、`id`/`label`/`args` 必填且长度受限（100/120/20000）、id 不重复。
- **validateCommandProfile**：workspace 引用必须全部命中「未归档 + 未删除」集合，缺失即 400 并列出 id；有 workspace 引用却缺 workspaceId 时 400；`skill` 条目要求 `skillCommandName ?? name`。
- **关联校验**：`resolvePromptWorkflowAssociations` 用 zod 限制 id 为 UUID 数组、最多 500、去重；`associatedXpertIds` 仅校验**新增** id（必须为同 workspace、同 tenant、`latest: true` 的 Xpert），数量不符抛 `Error.PromptWorkflowAssociationsUnavailable`。
- **协作输入**：`requiredText` / `optionalText`（长度上限）/ `optionalBase64`（`/^[A-Za-z0-9+/=_-]+$/`，非法返回 null）/ `positiveInteger` / `clamp`；`sanitizePresence` 强制 `clientId`/`presenceId`/`displayName`/`color` 必填，坐标与缩放做范围裁剪。

章节来源：[prompt-workflow.service.ts](file://packages/server-ai/src/prompt-workflow/prompt-workflow.service.ts)（关键符号：PromptWorkflowService.normalizePromptWorkflowInput / validateCommandProfile）· [collaboration-input.ts](file://packages/server-ai/src/collaboration/collaboration-input.ts)（关键符号：requiredText / optionalBase64）

## 已知风险

1. **同名并发**：`(workspaceId, name)` 唯一索引与运行时的「先查后插」之间存在竞态；`initializeDefaultsInWorkspace` 用事务 + `pessimistic_write` 缓解，但 `createInWorkspace` / `upsertInWorkspaceByKey` 不持锁，并发创建仍会撞唯一索引并冒泡为未翻译的数据库错误。
2. **关联漂移**：`associatedXpertIds` 只校验新增、既有 id 允许悬空；且空数组 = 全 workspace 可见，一次误清空即扩大适用范围。
3. **软删/归档与引用**：`archivedAt` 与 `deletedAt` 语义重叠且查询条件不一致（`resolveRuntimeCommandProfile` 用 `deletedAt IsNull` + `archivedAt` 过滤；`findWorkspaceWorkflowByKey` 只过滤 `deletedAt`）；唯一索引不感知软删，名字无法复用。命令档案中的 `snapshot` 会让发布态在源工作流被归档/改写后仍按旧内容执行。
4. **协作 update 的保留与清理**：`pruneUpdates` 的窗口是「最近 200 条 **且** 24h 内」双条件，`collaboration_update` 是唯一的幂等依据，窗口之外的重放不再判重、会推进序列号并可能触发 `expectedSequence` 冲突。
5. **协作状态列无版本约束**：`stateBase64` / `stateVectorBase64` / `scopeKey` 无 CHECK 约束，体积上限（32 MiB / 2 MiB）只在服务层校验；`scopeKey` 只由 tenant+organization 派生，跨 workspace 的同 provider/resource 组合会落入同一条文档记录。

## 结论

数据模型把三类「受控能力」分别映射为一张工作流表（含唯一 key 与 server-owned provenance）、一张标签连接表，以及协作的文档表 + 更新日志表；三表实体均未提供迁移，schema 由实体推导。`collaboration_update` 既是幂等键又受有限保留窗口约束，是协作面最需要关注的数据模型薄弱点；`prompt_workflow` 的唯一索引与软删/归档双轨并存则是最易被忽略的写路径风险。
