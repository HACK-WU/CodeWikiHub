## 3. `copilotModel` 级联语义

`copilotModel` 是 `@OneToOne(() => CopilotModel, { nullable: true, cascade: ["insert", "update", "remove", "soft-remove", "recover"] })` + `@JoinColumn()`，**无 `onDelete` 声明**。语义要点：① 这是「拥有」型关系——保存 `XpertAgent` 时若 payload 带 `copilotModel`，TypeORM 会级联插入/更新模型行；移除或软删 Agent 时也会带上 `remove`/`soft-remove`/`recover`。② 与 `xpert` 关系的差异：`xpert` 是 `onDelete: 'CASCADE'` + `onUpdate: 'CASCADE'`（删团队即删 agent 定义行），`team` 是 `onDelete: 'CASCADE'`，二者都不带 cascade 数组，即不会因为保存 agent 而反向写 `Xpert` 行。③ 赋值面：`XpertAgentService.update` 直接 `assign(_entity, entity)` 后 `repository.save(_entity)`，因此任何把 `copilotModel` 一起提交的更新都会触发上述级联；本子域无字段白名单。

`effective-copilot-model.ts` 的 `resolveEffectiveCopilotModel` 是**只读**的选模策略，不参与持久化：运行时选模优先级为「同一团队 + 显式/偏好来源时用 `primaryCopilotModel` → 命中 `primaryAgentKey` 时用 `primaryCopilotModel` → 否则 `agent.copilotModel ?? assistantModel`」，其中 `assistantModel` 在 `primaryModelSource ∈ {explicit, preference}` 且 `xpertId === team.id` 时取 `options.primaryCopilotModel ?? team.copilotModel`，否则取 `team.copilotModel`。

另需注意 `copilotModelId` 的 `@RelationId((it: Xpert) => it.copilotModel)`：回调参数类型注解写成 `Xpert`（与 `xpert` 关系的写法一致），与 `teamId` 的 `@RelationId((it: XpertAgent) => it.team)` 不同。这属可疑的复制粘贴，实际列值需按运行库回归确认。

## 4. 四个 json 列与 `teamId` 的语义与风险

`knowledgebaseIds` / `toolsetIds` / `collaboratorNames` 三列为纯 json 数组，`leaderKey` 为纯字符串——**四者都没有 FK、没有 CHECK、没有连接表**，数据库层不提供任何引用完整性：

1. **删除不级联、不报错**：删知识库或工具集后，`knowledgebaseIds`/`toolsetIds` 中的 id 静默悬空；`collaborators.integration.spec.ts` 与 `graphrag/bounded-graph-reader.ts` 都在做「按 id 再查一次」的补偿，说明消费侧必须自行处理缺失。
2. **`leaderKey` 指向 key 而非 id**：团队内改名（或同团队出现重复 `key`，因 `key` 无唯一索引）都会让 leader 解析歧义；`leaderKey` 也不区分「leader 在哪个团队」，跨团队引用只能靠 `xpertId`/`teamId` 兜。
3. **`collaboratorNames` 与 `followers?` 不是同一件事**：落库面只有 `collaboratorNames`，`collaborators?`/`followers?` 是运行期装配出来的对象数组（`resolveCollaborators` 从 `agent.collaborators` 读取），二者不一致时以内存装配为准。
4. **`teamId` 的双重团队引用**：同一行既有 `xpert`（OneToOne，`onDelete: CASCADE`/`onUpdate: CASCADE`）又有 `team`（ManyToOne，`onDelete: CASCADE`），两列都指向 `Xpert` 且都可空；语义靠调用方约定（agent 所属团队 vs 该 agent 归属的团队容器），数据库不禁止两者指向不同团队，也不禁止指向同一个团队。
5. **`knowledgebaseIds` 的跨域读放大**：`graphrag/bounded-graph-reader.ts` 直接 `getRepository(XpertAgent).findOne(...)` 后读 `knowledgebaseIds`，即该 json 列已成外部契约，改语义需两侧确认。

## 5. 索引与唯一约束

**实体层零 `@Index` 声明**：`xpert_agent.entity.ts` 全文没有 `@Index`/`@Unique`，本子域也未提供任何手写 DDL。

**可能的隐式约束（待核实）**：`xpert` 与 `copilotModel` 均为 `@OneToOne` + `@JoinColumn()`，TypeORM 的 schema 构建器对 OneToOne 连接列通常生成 UNIQUE 约束（即 `xpertId` 唯一，保证一个团队一行 agent 定义）；`team` 与两个 `@RelationId` 列本身不产生唯一性。但仓库内**没有任何 `xpert_agent` 的迁移脚本可验证**（实测 `xpert-agent/` 目录 0 个 `.sql`，全仓 `.sql` 中仅 `xpert_agent_execution` 及其引用出现，从未出现 `CREATE TABLE ... xpert_agent`），因此该 UNIQUE 是否存在完全取决于部署时 `synchronize` 是否启用与当前库的同步历史，属**待核实项**。

**明确不存在的约束**：`key` 无唯一索引，也不存在 `(xpertId, key)` 复合唯一约束 → 同一团队可存在多个同 `key` 的 agent 行，`leaderKey`/`getSwarmPartners` 的按 key 解析因此存在歧义空间；`knowledgebaseIds`/`toolsetIds`/`collaboratorNames`/`leaderKey` 无任何 DB 约束。

## 7. 校验规则

- **实体/DTO 层（class-validator）**：`key` 有 `@IsString()` 且无 `@IsOptional()`（必填）；`name` 有 `@IsString()`，`title`/`description`/`prompt`/`avatar`/`leaderKey` 有 `@IsOptional()`；`promptTemplates`/`parameters`/`outputVariables`/`options` 为 `@IsJSON() + @IsOptional()`；`knowledgebaseIds`/`toolsetIds`/`collaboratorNames` 为 **`@IsJSON()` 且无 `@IsOptional()`** —— 与「列为 `nullable: true`」形成不对称。`avatar` 列是 `json` 却用 `@IsString()`，类型与校验不匹配。
- **是否存在全局校验管道（待核实/否）**：全仓实测 **0 处** `useGlobalPipes`，`apps/api/src/bootstrap/index.ts` 只有 `setGlobalPrefix`。因此上述 class-validator 装饰器目前不构成运行时闸门，实际入参约束来自 `CrudController` 继承实现与各 handler 的参数选择；断言「`knowledgebaseIds` 缺失会被 400」缺乏源码支持。
- **HTTP 边界**：`XpertAgentController` 无 `@UseGuards`（仅类级 `@ApiBearerAuth()` 注解）；`getMiddlewareTools`/`testMiddlewareTool` 把任意异常包成 `BadRequestException(getErrorMessage(err))`，`testNode` 包成 `HttpException(getErrorMessage(err), 500)`，均无 i18n key。
- **业务校验（validator 产出 `ChecklistItem`）**：`XpertAgentGraphValidator` → `AGENT_SUBGRAPH_BUILD_CYCLE`（`field: 'connections'`，`level: 'error'`）；`XpertAgentNodeValidator` → `AGENT_STRUCTURED_OUTPUT_FILE_UNDERSTANDING_CONFLICT`、`AGENT_FILE_UNDERSTANDING_EMBEDDING_UNAVAILABLE`（`field: 'options.fileUnderstanding.enabled'`，`level: 'warning'`）；`plugins/middleware/validator.ts` → `MIDDLEWARE_PROVIDER_NOT_FOUND`、`MIDDLEWARE_REQUIRED_FEATURE_DISABLED`、`MULTIPLE_SKILLS_MIDDLEWARE_CONNECTED`。
- **归一化环节**：`XpertAgentService.normalizeSchema` 把 zod（含 `_def`）经 `ToolSchemaParser.parseZodToJsonSchema` 转 JSON Schema，否则 `JSON.parse(JSON.stringify(...))`，异常一律返回 `null` —— 属「松散校验」，不抛错。
- **编译期不消费校验结果**：`CompileGraphHandler.execute` 不读 `ChecklistItem`，校验结论不阻断编译。

## 8. 已知风险与坑

1. **自引用式团队列**：`teamId` 与 `xpertId` 都指向 `Xpert` 且都可空、都 `onDelete: CASCADE`。批量删团队时同一行可能同时命中两条级联；两列指向不同团队时无 DB 约束阻止，语义只能靠调用方保证。
2. **级联删除面不对称**：删 `Xpert` → 经 `xpert`/`team` 两路 CASCADE 删 agent 行，并经 `copilotModel` 的 cascade 数组删模型行；而 `knowledgebaseIds`/`toolsetIds`/`collaboratorNames`/`leaderKey` 指向的目标被删时**不会有任何清理**。方向性刚好相反：本行是删除的「受方」，同时又是 json 引用的「施方」但不级联。
3. **json 列的无约束引用**：三个 json 数组的 id 只保证「是字符串数组」，不保证存在、不保证同租户/同组织、不保证去重；`toolsetIds` 与 `knowledgebaseIds` 的内容一旦跨租户抄写不会报错。
4. **`key` 无唯一索引**：`(xpertId, key)` 无唯一约束，`leaderKey` 与 `getSwarmPartners` 的 key 解析可能命中多行；`XpertAgentService.update` 又不校验 `key` 变更，一次 update 即可让 `leaderKey` 悬空。
5. **`update` 的整实体保存**：`assign + repository.save` 无字段白名单，payload 携带关系字段会触发 `copilotModel` 5 项 cascade；也无法防止 `xpertId`/`teamId` 被改写到其它团队。
6. **`copilotModelId` 的 `@RelationId` 回调类型写成 `Xpert`**：与 `teamId` 的写法不一致，属可疑复制粘贴；列为待核实项，需按运行库实际列值回归。
7. **表结构无迁移**：`xpert_agent` 完全依赖 `synchronize`；生产关闭同步即无建表来源，第 5 节的隐式 UNIQUE 也因此无法静态确认。
8. **`avatar` 列类型与校验不一致**：`json` 列 + `@IsString()`，一旦启用严格校验管道会与实际写入的 `TAvatar` 对象冲突。
9. **校验装饰器目前不生效**：全仓无 `useGlobalPipes`，因此「`knowledgebaseIds`/`toolsetIds`/`collaboratorNames` 因缺 `@IsOptional()` 会被拒」这一推论不成立；把实体注解当运行时契约是常见误判。
10. **跨域读放大**：`chat-conversation` 注册 `XpertAgent` 并注入仓储、`graphrag` 经 `getRepository(XpertAgent)` 直读 `knowledgebaseIds` —— 本域列改名或语义调整会同时影响两个相邻模块。

## 9. 结论

`xpert_agent` 是一张「组织级 + 三关系 + 四弱引用」的定义表：关系面（`xpert` OneToOne CASCADE、`team` ManyToOne CASCADE、`copilotModel` OneToOne 全量 cascade）承担生命周期，弱引用面（`leaderKey`、`collaboratorNames`、`knowledgebaseIds`、`toolsetIds`）承担图装配语义但没有任何 DB 保护。本表无实体索引、无迁移文件、无 seeder，唯一性只能寄望于 `@OneToOne` 的隐式 UNIQUE 且无法静态验证。最需要在下游代码里显式补偿的三件事是：删目标后清理 json 引用、`update` 时限制可写列、以及对 `key` 做团队内唯一性校验。
