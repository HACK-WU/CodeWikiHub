## 1. 核心流程实现位置

### 1.1 定义 CRUD 与 `update` 的边界

`XpertAgentController` 是空 `@Controller()`，`/xpert-agent` 前缀由 `RouterModule.register([{ path: '/xpert-agent', module: XpertAgentModule }])` 提供；它 `extends CrudController<XpertAgent>`，因此继承 `count`/`pagination`/`my`/`/:id`/`create`/`update`/`delete`/`softRemove`/`softRecover` 全套。显式端点只有 5 个：`chat`（SSE）、`xpert/:id/test/:key`（`WorkflowTestNodeCommand`，错误包成 `HttpException(getErrorMessage(err), 500)`）、`middlewares`、`middlewares/:provider/tools`、`middlewares/:provider/tools/:toolName/test`（后两者失败 → `BadRequestException(getErrorMessage(err))`，无 i18n key）。

`XpertAgentService` 只覆写了一个 CRUD 方法：`update(id, entity)` = `super.findOne(id)` → `assign(_entity, entity)` → `repository.save(_entity)`。**边界语义**：这是整实体保存，不做字段白名单（`key`、`xpertId`、`teamId` 均可在一次 `update` 中被改写），不校验 `key` 在团队内唯一（实体无唯一索引），且因 `copilotModel` 关系声明了 `cascade: ["insert","update","remove","soft-remove","recover"]`，随 `save` 一起提交的 `copilotModel` 会触发模型的插入/更新/删除。`create` 与删除路径仍走基类实现。

### 1.2 图编译链

`CompileGraphCommand`（`type = '[Xpert Agent] Compile graph'`）携带 `agentKeyOrName`、`xpert`、`options`（含 `leaderKey`/`rootExecutionId`/`thread_id`/`rootController`/`signal`/`execution`），返回 `{ graph, agent, xpertGraph }`。`CompileGraphHandler.execute` 的执行顺序固定为：① `GetXpertWorkflowQuery(xpert.id, agentKeyOrName, command.options?.isDraft)` 取 `{ agent, graph: xpertGraph }`；② `agent` 缺失即抛 `NotFoundException`（文案含 `draft is ...`）；③ `getSwarmPartners(xpertGraph, agent.key, partners)` 累积伙伴；④ `partners.length > 1` → `XpertAgentSwarmCommand`（透传 `signal: rootController.signal`），否则 → `XpertAgentSubgraphCommand`（额外补 `isStart: true`、`channel: channelName(agent.key)`、`partners: []`）；⑤ 解构 `swarmOrGraph.graph` 返回。

**校验项**（`@OnEvent(EventNameXpertValidate)` 订阅者，与编译无调用关系）：`XpertAgentGraphValidator.handle` 调 `validateAgentSubgraphBuildCycles` —— 以 `start:<agentKey>` / `normal:<agentKey>` 为状态建依赖图（`buildFollowerTargets` 收集 `type === 'agent'` 的 agent→agent 连边、`buildWorkflowStartTargets` 收集 workflow→agent 连边、`collectEntryBuildStates` 沿 `getCurrentGraph`/`findStartNodes` 展开入口），用 `findReachableCycles` 找环并按规范化旋转去重，产出 `ruleCode: AGENT_SUBGRAPH_BUILD_CYCLE`、`field: 'connections'`、`level: 'error'`。`XpertAgentNodeValidator.handle` 逐 agent 节点调 `check`：`options.structuredOutputMethod && options.fileUnderstanding.enabled !== false` → `AGENT_STRUCTURED_OUTPUT_FILE_UNDERSTANDING_CONFLICT`；`fileUnderstanding.enabled !== false && !embeddingCopilotAvailable` → `AGENT_FILE_UNDERSTANDING_EMBEDDING_UNAVAILABLE`（两者 `level: 'warning'`）；嵌入可用性经 `CopilotOneByRoleQuery(tenantId, organizationId, AiProviderRole.Embedding)` + `isEmbeddingCopilotAvailable` 判定，无 `queryBus` 或抛异常时保守返回 `true`/`false`。

### 1.4 多智能体

`XpertAgentSwarmHandler.execute`（`XpertAgentSwarmCommand`）逐 `partners` 成员构造子图：① 为成员生成 handoff 工具集 —— 只保留图中满足 `conn.type === 'agent' && conn.from === member && conn.to === p` 的伙伴，工具名用 partner key、描述经 `agentLabel(agent)` 拼接；② 以 `XpertAgentSubgraphCommand(member, xpert, { leaderKey: null, isStart: true, channel: null, partners, handoffTools, rootExecutionId, thread_id, subscriber })` 编出子树；③ 用 `RunnableLambda` 包一层执行壳：`XpertAgentExecutionUpsertCommand` 首写（`parentId = executionId`、`predecessor = configurable.agentKey`、`inputs: { input: state.input }`）→ `messageEvent(ON_AGENT_START, __execution)` → `graph.invoke`（向 `configurable` 注入 `agentKey: member`、`executionId`，向 `metadata` 注入 `parentExecutionId`）→ `finally` 中 `finalize()`：`graph.getState(config)` 取 `checkpoint_id`，再 upsert `checkpointId`/`elapsedTime`/`status`/`error`/`outputs`，经 `XpertAgentExecutionOneQuery` 重读后发 `ON_AGENT_END`；异常时若非 `isParentCommand`/`isCommand` 则记 `ERROR` 后原样抛出。④ 状态 schema 为 `Annotation.Root({ ...AgentStateAnnotation.spec, activeAgent: Annotation<string> })`，`createSwarm({ agents, defaultActiveAgent: agentKeyOrName, stateSchema })` 编译并挂 `CopilotCheckpointSaver` 与 `options.store`，最后 `installThreadPauseGuards(builder.nodes, options.shouldPause)`。

**静态协作**（`collaborators.middleware.ts`）：`resolveCollaborators` 以 `agent.collaborators` 为基础，若 `runtimeCapabilities` 是 allowlist 则用 `getRuntimeEnabledSubAgentConnections(graph, agent, { runtimeCapabilities })` 过滤出 `type === 'xpert'` 的目标 key 后裁剪；`isStart && !leaderKey` 时再并入 `runtimeResources.experts`（动态资源只给入口 agent，子 agent 不继承会话资源）；按 `expert.id` 去重保序。`createCollaboratorsMiddleware` 产出 `{ name: '__collaborators_middleware__', tools }`，专家数为 0 时 `tools` 为空数组。`collaboratorToolDeclaration(expert)` 生成声明式工具：工具名 = `expert.slug`，schema 为 `createParameters(expert.agentConfig?.parameters ?? expert.agent?.parameters)` + 必填 `input` 且 `.strict()`，执行体只抛 `Error(t('server-ai:Error.AgentInvocationInvalidScope'))` —— 直接调用即失败，真实执行必须走宿主图（注释：Built in automatically; users select experts, not a second middleware switch.）。

### 1.5 native 编译

三个文件的头注释即自证兼容定位：`native-agent.compiler.ts` 首行「Native compatibility compiler: preserves existing state projections and graph edges.」；`native-graph-adapter.ts`「Invariants: keep parent checkpoint configuration and native state projection intact. Only this adapter serializes graph state」；`agent-invocation-graph.service.ts`「Invariants: keep native checkpoint configuration and stable tool/node names. Authorization runs outside the child graph, including on checkpoint resume.」

`NativeAgentCompiler.compile(agent, config)`：派发 `XpertAgentSubgraphCommand`（`isStart: isTool`、`leaderKey` 取自 `options`）得 `{ graph, nextNodes, failNode }`；构造占位 `DynamicStructuredTool`（`name = agentUniqueName(agent)`，执行即抛 `InvalidScope`）；返回 `stateGraph = RunnableLambda.from(...).withConfig({ tags: [xpert.id] })`。该 lambda 的语义与 swarm 侧同构：首写执行（`id` 优先取 `config.configurable.agentInvocationId`、`metadata.invocationKind = 'sub_agent'`、`sourceToolCallId`）→ `ON_AGENT_START` → `graph.invoke`（tool 模式把 `call.args` 与 `STATE_VARIABLE_HUMAN` 合入子状态）→ 组装回写状态（tool 模式同时向 `channelName(leaderKey)` 与 `channelName(agent.key)` 投 `ToolMessage`；非 tool 模式投完整 `messages` 与 `output`）→ 按 `agent.options.memories` 写记忆变量 → `finally` 中 `finalize()`；`isGraphInterrupt(err)` 归 `INTERRUPTED`，否则 `ERROR`。

`AgentInvocationGraphService` 是 native 的装配层：`compileExperts(experts, context)` 先做工具名冲突检查（`AgentResourceToolConflict`），按专家名与 `PARALLEL_DELEGATION_TOOL` 二次检查；`XpertCollaborator.build` 产出子图后经 `wrap` 包一层；只有不在 `interruptBefore`/`interruptAfter`/`endNodes` 白名单中的子项才进入并行委派工具。`compileLocal(agent, config, scope)` 供 subgraph 内的 agent 节点直接调用。`wrap(...)` 用 `createHash('sha256')` 计算 `revision`（`publishAt` + `graph` + 可选 `draft` + `entry`），生成 `target = { bindingId: xpert:${id}:${entry}, provider: 'xpert', revision, reference: id, configuration: { entry } }`，`authorize` 中先按需 `resources.resolve` 再对非本团队目标做 `GetXpertWorkflowQuery` 复核。

`wrapNativeAgentInvocation(graph, runtime, context)`（`native-graph-adapter.ts`）是真正的执行壳：从 `config.configurable` 取 `parentExecutionId`（缺失即 `InvalidScope`），`callId` 优先取 `toolCall.id`、回退 `__pregel_task_id`、再回退 `checkpoint_ns`（注释：Graph task id is stable on checkpoint replay and distinct across loop iterations.），随后 `runtime.scoped({ scope, capabilities, signal, authorize, isSuspension: isGraphInterrupt }).start({ target, callId: ${bindingId}:${callId}, input: { prompt: '', parameters: { nativeInputDigest } } })`；`succeeded` 时用 `JsonPlusSerializer` 反序列化结果（校验 `type`/`value` 否则 `MissingResult`），`cancelled` 抛 `ExecutionCancelledError`，`failed`/`unknown` 抛 `DispatchUnknown`，其余状态先 `interrupt({ type: 'agent_invocation', ... })` 再抛 `ConcurrentUpdate`。

### 1.7 `chatAgent` 入口与 `resume({ decision })` 的 HITL 恢复路径

`XpertAgentService.chatAgent(params, options)`：先 `FindXpertQuery({ id: request.xpertId }, { relations: ['agent'], isDraft: true })` 取草稿团队，再 `commandBus.execute(XpertAgentChatCommand)`，参数拼装为 `state = request.state ?? { [STATE_VARIABLE_HUMAN]: {} }`、`agentKey = request.agentKey`，options 固定 `isDraft: true`、`store: null`、`from: 'debugger'`；`request.action === 'resume'` 时额外注入 `execution: { id: request.target.executionId, category: 'agent' }` 与 `resume: { decision: request.decision, ...(request.patch ? { patch: request.patch } : {}) }`，并把 `resume` 一路透传（`chatAgent` → `XpertAgentChatHandler` → `XpertAgentInvokeCommand` → invoke 图的输入构造）。

恢复语义落在 `invoke.handler`：`toInterruptCommand(options.resume)` 把 `{ decision, patch }` 转成 `TInterruptCommand` —— `decision.type === 'confirm'` 时 `command.resume = decision.payload ?? {}`，`reject` 且带 payload 时直接透传 payload；`patch.toolCalls`/`patch.update`/`patch.agentKey` 逐项搬运（`patch.agentKey` 决定恢复到哪个子 agent）。若 `shouldRejectResumeWithGraph(resume)`（即 `reject` 且 payload 为 `undefined`）则先 `graph.updateState` 注入运行时系统状态再走 `reject`，否则以 `new Command({ ...pick(payload, 'resume'), update: mergeCommandUpdateWithSystemState(...) })` 作为 `graphInput` 续跑。`chat.handler` 在流尾识别 `ON_INTERRUPT` 事件（记入 `operation`），`isInterruptedExecutionError(err)` 时把根执行落 `INTERRUPTED` 而非 `ERROR`；客户端断开（`unsubscribe`）落 `ERROR` + `error: 'Aborted!'`。

## 2. 设计模式及落点

| 模式 | 落点 |
|---|---|
| 命令 / 查询分离（CQRS） | `CompileGraphCommand`、`XpertAgentSwarmCommand`、`XpertAgentSubgraphCommand`、`XpertAgentChatCommand`、`XpertAgentInvokeCommand`、`WorkflowTestNodeCommand`、`CreateWorkflowNodeCommand`；查询 `GetXpertWorkflowQuery`、`XpertAgentExecutionOneQuery` |
| 策略注册表 | `WorkflowNodeRegistry`/`WorkflowTriggerRegistry`/`AgentMiddlewareRegistry` + 本地 `Strategies`/`Validators` 常量；`XpertAgentService.getMiddlewareStrategies` 用 `isUserAddableAgentMiddleware` 过滤并回填 `TAgentMiddlewareSource` |
| barrel 组织 | `xpert-agent/index.ts`（7 个再导出）、`commands/index.ts`、`commands/handlers/index.ts`、`queries/index.ts`、`workflow/index.ts`、`plugins/index.ts` |
| 事件驱动校验（观察者） | `@OnEvent(EventNameXpertValidate)` 的 `XpertAgentGraphValidator`、`XpertAgentNodeValidator`、`WorkflowMiddlewareNodeValidator` |
| 门面 + 作用域注入 | `XpertAgentService.createDraftXpertMiddlewareRuntime` 调 `AgentMiddlewareRuntimeService.createScopedApi`；`resolveXpertDataVolumeScope` 产出数据卷作用域 |
| 装饰器（包装器） | `XpertAgentSwarmHandler` 与 `NativeAgentCompiler` 各自用 `RunnableLambda` 把执行账本与流式投影包在子图外 |

## 3. 热点路径

1. **swarm 图生成的逐成员子图编译**：`XpertAgentSwarmHandler.execute` 对每个 partner 都要跑一次 `XpertAgentSubgraphCommand`（内含 toolset/MCP/middleware 装配），成员数线性放大；伙伴越多，图编译耗时与内存占用越集中，是定义面最贵的一次调用。
2. **native 编译的哈希与序列化**：`AgentInvocationGraphService.wrap` 每次都对 `publishAt` + 整图 + `entry` 做 `JSON.stringify` + `sha256`；`wrapNativeAgentInvocation` 每跳还要 `JsonPlusSerializer.dumpsTyped` 两次（输入摘要与输出体 base64）。长会话中每次委派都会走这条路径。
3. **草稿解析的重复查询**：`getDraftXpertMiddlewareContext` 在 `getMiddlewareTools`/`testMiddlewareTool` 各调一次，且 `chatAgent` 也独立发一次 `FindXpertQuery({ isDraft: true })`；编辑器高频点击工具清单时对 `xpert` 域形成读压力。
4. **`update` 的整实体保存**：`XpertAgentService.update` 走 `repository.save`，若 payload 携带 `copilotModel`/`team`/`xpert` 关系，则连带触发关联写入与级联，属定义面最容易产生意外写放大的点。

## 5. 技术债与 hack

1. **`xpert_agent` 的 json 引用非 FK**：`knowledgebaseIds`/`toolsetIds`/`collaboratorNames` 是 `@Column({ type: 'json' })`，`leaderKey` 只是字符串；实体无 `@ManyToMany`/`@JoinTable`，`knowledgebases?`/`toolsets?`/`collaborators?`/`followers?` 均为内存属性。删除知识库、工具集、协作者团队都不会级联清理，悬空引用只由业务侧消化。
2. **native 与 legacy 双图路径并存且投影重复**：`XpertAgentSwarmHandler` 与 `NativeAgentCompiler` 各自维护一份「`RunnableLambda` 执行壳 + 执行 upsert + `ON_AGENT_START`/`ON_AGENT_END`」，两者的 `metadata` 字段（`agentKey`/`parentExecutionId`/`invocationKind`）与状态推导分支并不完全一致；`native-agent.compiler.ts` 首行注释「preserves existing state projections and graph edges」即承认这是兼容层。
3. **barrel 的隐式导出面不一致**：`commands/index.ts` 导出 `chat.command`/`invoke.command`/`compile-graph.command`/`create-node-*`/`summarize-title`/`workflow-subgraph`/`connect-agent-knowledgebases`，**不导出** `subgraph.command` 与 `create-swarm.command`；外部因此只能深链 `xpert-agent/commands/subgraph.command`（`native-agent.compiler.ts` 正是这么做的）。同时 `agent.ts` 把 `FakeStreamingChatModel` 提升为 barrel 面的一部分。
4. **两个同名 `Validators` 靠别名消解**：`workflow/index.ts` 与 `plugins/index.ts` 各导出一个 `Validators`，`xpert-agent.module.ts` 用 `Validators as PluginValidators` 区隔；新增 validator 时容易漏注册到 `providers`。
5. **`chatAgent` 与执行链的耦合点未做防御**：`request.action === 'resume'` 分支直接读 `request.target.executionId` 与 `request.decision`，`target` 缺失会在取属性时抛运行期错误；同一入口还硬编码 `isDraft: true`、`store: null`、`from: 'debugger'`，使「调试入口」与「发布执行」共用一条命令却带不同隐式上下文。
6. **校验与编译解耦**：`CompileGraphHandler` 不消费任何 `ChecklistItem`，「编译前必须过 validator」不成立；校验结论只体现在草稿侧返回值。
7. **`update` 是整实体保存**：无字段白名单、无 `key` 唯一性校验、无关系字段剥离；`copilotModel` 的 5 项 cascade 会在同一次 `save` 中生效。
8. **`agent.ts` 的调试输出副作用**：`createMapStreamEvents` 在 debug 级别下用 `process.stdout.write('.')`/`'\n'` 直接写标准输出，属绕过 logger 的调试残留。

## 6. 设计维度分析

### 6.1 草稿态 vs 发布态：同一入口的两种身份

`chatAgent` 以 `isDraft: true` 读团队、`store: null` 关掉长期记忆、`from: 'debugger'` 标注来源；`getDraftXpertMiddlewareContext` 在取数前先做 `assertCanAuthorById` 授权，再以 `isDraft: true` 读特征（仅取 `id`/`features`/`workspaceId`/`workspaceDataScope` 四字段）；`createDraftXpertMiddlewareRuntime` 用 `resolveXpertDataVolumeScope` 把数据卷隔离到当前用户（`isolateByUser: xpertScope.catalog === 'user-xperts'`）。native 侧把这一维度压进 `revision`：仅 `isDraft` 时把 `draft` 纳入哈希，因此「编辑未发布草稿」不会让已暂停的已发布运行失效。设计取向是**用同一套图代码承载两种身份，靠上下文参数与哈希隔离**——代价是发布/草稿的行为差异没有编译期约束。

章节来源：[xpert-agent.service.ts](file://packages/server-ai/src/xpert-agent/xpert-agent.service.ts)（关键符号：`XpertAgentService.chatAgent`/`getDraftXpertMiddlewareContext`/`createDraftXpertMiddlewareRuntime`）、[agent-invocation-graph.service.ts](file://packages/server-ai/src/agent-invocation/agent-invocation-graph.service.ts)（关键符号：`AgentInvocationGraphService.wrap`）

### 6.2 legacy 图 vs native 图：两套投影、一个账本

legacy 侧（swarm/subgraph）用 `subscriber.next(messageEvent(...))` 直接向 SSE 流推事件，执行记录靠 `XpertAgentExecutionUpsertCommand` 两次写；native 侧把子图包成 `RunnableLambda` 后经 `runtime.start` 落 Invocation，结果体以 `JsonPlusSerializer` + base64 存取，`interrupt` 只作挂起信号。共同点是两者都最终写 `xpert_agent_execution` 并复用 `messageEvent`；差异是 native 侧多一层 `callId` 幂等与 `nativeInputDigest` 输入摘要。这种「一个账本、两套投影」的结构让新增执行语义必须同时改两处。

章节来源：[create-swarm.handler.ts](file://packages/server-ai/src/xpert-agent/commands/handlers/create-swarm.handler.ts)（关键符号：`XpertAgentSwarmHandler.execute`）、[native-agent.compiler.ts](file://packages/server-ai/src/agent-invocation/native-agent.compiler.ts)（关键符号：`NativeAgentCompiler.compile`）、[native-graph-adapter.ts](file://packages/server-ai/src/agent-invocation/native-graph-adapter.ts)（关键符号：`wrapNativeAgentInvocation`）

### 6.3 静态协作者 vs 动态 swarm：两种多智能体语义

swarm 是**图内**语义：`getSwarmPartners` 从连接推导成员，handoff 工具按 `type === 'agent'` 连边过滤，状态用 `activeAgent` 表示当前发言人，每次切换都由 `RunnableLambda` 写子执行。协作者是**图外**语义：`resolveCollaborators` 从 `agent.collaborators` + 图上的 `type === 'xpert'` 连边 + `runtimeResources.experts` 三源合并，产出的是普通中间件工具，调用即进入一次 native Invocation。前者共享同一份 `activeAgent` 状态与 checkpointer，后者以 `parentExecutionId` 串接、彼此 checkpointer 独立（`collaborators.integration.spec.ts` 里「resumes independent children of a single delegation call without mixing their checkpoints」正是在断言这条边界）。

## 7. 结论

实现层由三条链支撑：定义链（`XpertAgentController` → `XpertAgentService` → `xpert_agent`）承载 CRUD 与草稿态调试；编译链（`CompileGraphCommand` → swarm/subgraph，或 native 三件套）产出可执行图并把执行账本写入交给 `XpertAgentExecutionUpsertCommand`；投影链（`agent.ts` 的 `createMapStreamEvents`/`messageEvent`）把 LangGraph 事件翻译成前端 SSE 契约。校验是第四条但与编译解耦。最易出错的三处是：双图路径的投影漂移、三文件跨目录归属导致的影响面误判、以及 barrel 与 `Validators` 命名不一致带来的漏注册。
