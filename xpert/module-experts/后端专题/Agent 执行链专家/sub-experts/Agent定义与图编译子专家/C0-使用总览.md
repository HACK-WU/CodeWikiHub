# C0 · 使用总览（Agent 定义与图编译子专家）

> 契约层 CR1。父级域契约见 `file://.module-experts/后端专题/Agent 执行链专家/C0-使用总览.md`；本文只覆盖子专家 ①。
> 路径以仓库根为基准的相对 `file://` 引用；不写行号；不复述实现层文档的结构、规模与测试清单。

## 1. 定位

本子专家负责 **「Agent 长什么样（定义）+ 这段定义被编译成哪张可执行图」**：`xpert-agent/` 的定义面 CRUD、草稿校验、图命令链（`CompileGraphCommand` → swarm / subgraph）、native 兼容编译，以及中间件策略与工具在**草稿态**的可视面。

- 主目录：`file://packages/server-ai/src/xpert-agent/`
- 语义属本子专家、**文件物理在 `agent-invocation/`** 的 native 三件套：`file://packages/server-ai/src/agent-invocation/native-agent.compiler.ts`、`file://packages/server-ai/src/agent-invocation/agent-invocation-graph.service.ts`、`file://packages/server-ai/src/agent-invocation/native-graph-adapter.ts`
- **不做**：Invocation 运行时与执行账本（子专家 ②）；中间件运行时本体、Prompt 工作流、协作（子专家 ③）；`xpert` 团队定义本体（`xpert` 域，经 `FindXpertQuery` / `GetXpertWorkflowQuery` 只读）。

## 2. 何时找这个子专家

- 改 Agent 定义字段、`xpert_agent` 读写行为、CRUD 继承面的权限口径。
- 改多智能体编排：swarm / handoff / 静态协作者，或排查「为什么走了 swarm 而不是 subgraph」。
- 排查「图编译成功了但校验没过」「校验没跑」「子图成环」。
- 接中间件：在草稿态列出策略 / 列工具 / 试跑单个工具。
- 排查 Agent 直连对话（`POST /api/xpert-agent/chat`，SSE）与人工决策恢复 `action: 'resume'`。
- 排查工作流单节点调试端点 `POST /api/xpert-agent/xpert/:id/test/:key` 的报错形态。
- 判断某个改动该按「目录」找还是按「语义」找人（native 三件套是典型陷阱）。
- 改节点 / 插件 / 工作流校验器（错误码与级别）。

## 4. 边界（与两个兄弟子专家）

1. **账本与调用运行时 → 子专家 ②**：本子专家的定义面**不直接注入** `xpert_agent_execution` 仓储，所有执行写入经 CQRS `XpertAgentExecutionUpsertCommand`（swarm 子执行、native 子图、chat 根执行三条路径）。
2. **中间件运行时本体 / Prompt 工作流 / 协作 → 子专家 ③**：本子专家只做「草稿态取用」（`getDraftXpertMiddlewareContext` + `createDraftXpertMiddlewareRuntime`），不拥有 `AgentMiddlewareRuntimeService.createScopedApi` 的能力装配语义。
3. **反向依赖必须双侧确认**：`native-graph-adapter.ts` 调 `AgentInvocationRuntime.scoped` 与 `invocationError`，`AgentInvocationGraphService` 的 `wrap` 依赖 `ExecutionCancelService`——改这三件套需 ① + ② 双方确认。
4. **对照**：`RuntimeDeliveryController` 方向相反——物理在 `handoff/runtime-messaging/`，注册在 `AgentInvocationModule.controllers`，归 ② 的对外面。
5. **`xpert_agent` 表被跨域共享**：`chat-conversation` 在 `TypeOrmModule.forFeature` 中注册 `XpertAgent`；`graphrag/bounded-graph-reader.ts` 经 `DataSource.getRepository(XpertAgent)` 直读 `knowledgebaseIds`。
6. WS 面：**无此项**。

## 5. 已知问题与常见坑

1. **编译成功 ≠ 校验通过**：`CompileGraphHandler.execute` 只调 `GetXpertWorkflowQuery` 与两条子命令，**不读取** `ChecklistItem`；校验由 `@OnEvent(EventNameXpertValidate)` 的订阅者（`XpertAgentGraphValidator`、`XpertAgentNodeValidator`、`plugins`/`workflow` 下各 validator）独立产出。「编译前必须过 validator」在源码中**不成立**，闸门实际落在草稿保存侧。
2. **native 与 legacy 双图路径并存**：`CompileGraphHandler` 产出的是 legacy 图（swarm/subgraph handler）；native 分支由 `NativeAgentCompiler` + `AgentInvocationGraphService` 另起一条路径接入同一执行账本。排障时要先确认走的是哪条。
3. **`xpert_agent` 的 `knowledgebaseIds` / `toolsetIds` / `collaboratorNames` 是 `@Column({ type: 'json', nullable: true })`，没有 FK**：实体上无 `@ManyToMany`/`@JoinTable`，`knowledgebases?` / `toolsets?` / `collaborators?` 只是内存属性。删知识库 / 工具集 / 协作团队不会级联清理，也不会报错。
4. **native 三件套按目录归属会误划给子专家 ②**：`NativeAgentCompiler` 与 `AgentInvocationGraphService` 由 `XpertAgentModule.providers` 注册，并复用本域 `agent.ts` 的 `messageEvent`、`collaborators.middleware.ts` 的 `collaboratorToolDeclaration`。
5. **barrel 隐式导出面**：`plugins/index.ts` 的 `Strategies`/`Validators` 与 `workflow/index.ts` 的 `Validators` 直接被 `XpertAgentModule.providers` 展开注册；改 barrel 等于改 provider 集合，`DiscoveryModule` 型注册表会随之变化。
6. **草稿态与发布态上下文分离**：`chatAgent` 固定 `isDraft: true` + `store: null`（无长期记忆）；`getDraftXpertMiddlewareContext` 先 `assertCanAuthorById` 再 `FindXpertQuery({ id }, { isDraft: true })`；native 侧 `AgentInvocationGraphService.wrap` 的 `revision` 仅在 `isDraft` 时把 `target.draft` 纳入哈希。
7. **子图成环错误码 `AGENT_SUBGRAPH_BUILD_CYCLE`**：定义在 `file://packages/server-ai/src/xpert-agent/graph-validator.ts`，是**校验项规则码**，不是运行时异常；`XpertAgentNodeValidator` 的两条规则是 `AGENT_STRUCTURED_OUTPUT_FILE_UNDERSTANDING_CONFLICT` 与 `AGENT_FILE_UNDERSTANDING_EMBEDDING_UNAVAILABLE`（`level: 'warning'`）。
8. **三个 HTTP 面的错误包装不一致**：`testNode` 把任意错误包成 `HttpException(getErrorMessage(err), 500)`；中间件两个端点包成 `BadRequestException`（400）；`GET middlewares` 不包。抓 code 比抓文案稳。
9. **swarm 的 handoff 工具来自 `@langchain/langgraph-swarm` 的 `createHandoffTool`**，与 `chat/commands/handlers/handoff.ts` 导出的同名函数**不是同一个**；`chat-common-agent-builder.ts` 用的是本地那个。改动前先确认引用点。
10. **分派条件是伙伴数不是 leader**：`partners.length > 1` 才走 swarm；`XpertAgentSubgraphCommand` 的 `leaderKey` 承担三态语义（`isStart && !leaderKey` 主 agent / `isStart && leaderKey` 子 agent / `!isStart && leaderKey` 工作流内普通 agent）。
11. **单节点调试只接受 `{ state }`**：端点签名是 `@Body() body: { state: any }`，多余字段不进命令。
12. **入向 CQRS 不经模块 import**：`xpert/commands/handlers/chat.handler.ts`、`file-memory/adapters/xpert-dreamer-invoker.ts` 发 `XpertAgentChatCommand`；`shared/agent/xpert.ts`、`chat/commands/handlers/chat-common-agent-builder.ts`、`xpert/commands/handlers/export-diagram.handler.ts` 用 `CompileGraphCommand`。改命令签名要看这些调用方，而不是只看模块依赖图。
