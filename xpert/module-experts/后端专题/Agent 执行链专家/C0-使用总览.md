# C0 · 使用总览（Agent 执行链专家）

> 契约层 CR1。面向「要改动或要排查 Agent 执行链」的使用者：先看这里定位入口与边界，再按需跳 `C1-能力契约.md`。
> 实现细节（算法、私有方法、内部字段堆砌）不在本层出现。

## 0. 专家定位

本专家负责 **「一次 Agent 工作如何被定义、编译、发起、记账、观察与停止」**：Agent 定义面与图编译（`xpert-agent/`）、统一调用运行时与执行/用量账本（`agent-invocation/` + `xpert-agent-execution/` + `shared/execution/`）、以及中间件受控运行时、Prompt 工作流、协作文档这三块运行时外围（`shared/agent/middleware-runtime/` + `prompt-workflow/` + `collaboration/`）。

一句话口径：**中间件工具、工作流 Agent 节点、后台任务是同一个调用运行时的 caller，它们不各自拥有另一 Agent 的图、进程、会话或协议；本域只做「已决定工作的执行与调用账本」，不做投递、不做队列、不做会话准入。**

## 1. 何时找这个专家

- 改 Agent 图、多智能体编排（swarm / handoff / 静态协作者）、节点与中间件策略注册。
- 查「一次执行为什么没跑起来 / 卡住 / 停在 waiting」，或 `unknown` 为何必须保持可见。
- 查 Invocation 状态口径与 CAS 冲突（提交失败但无异常、`ConcurrentUpdate`）。
- 接中间件，或排查「插件能拿到什么能力、不能拿到什么能力」的边界。
- 改 Prompt 工作流（工作空间命令模板、命令档案快照、运行时斜杠命令解析）。
- 查 / 接协作文档 WS（CRDT 更新、presence、会话凭据、ack 语义）。
- 排查「停不下来」「僵尸 run」「取消丢了」「续跑没发生」。
- 查执行与用量账本口径（审计时间戳、`completedAt`、`tokens` / 定价写入、只读日志与检查点）。
- 排查运行时绑定（org 级绑定、`provider` 白名单、workspace 授权、`enabled` 语义）。

## 6. 边界

**本域不做的事（与相邻专家分工）**

1. **投递与队列属「对话与会话专家」**：handoff 的队列/outbox 写入器与实时通道属对方；`agent_runtime_delivery` / `agent_runtime_inbox` 的实体物理在 `handoff/runtime-messaging/`，本域只注册并消费「账本不变量」，不改投递语义。
2. **`/api/agent-invocations/:id/delivery` 与 `.../delivery/redrive` 的 HTTP 逻辑属「对话与会话专家」**：`RuntimeDeliveryController` 文件物理在 `handoff/`，controller 注册在本域 `AgentInvocationModule`，因此对外表现为同一前缀——改动需两侧确认。
3. **会话与线程准入属「对话与会话专家」**（`ChatExecutionAdmissionService`、线程暂停/恢复控制）。
4. **模型客户端创建属「模型访问与计费专家」**（模型查询与计费命令/用量服务）；本域只提供 `createModelClient` / `getModelProvider` 的 scoped 出口。
5. **`agent-evolution/` 不属本域**：仅经 CQRS `XpertAgentExecutionUpsertCommand` 单向耦合，本域不拥有提案—评估—发布治理。

**四个归属判定**

1. `shared/agent/middleware-runtime` **属本域**：独立 Nest 模块 `AgentMiddlewareRuntimeModule`，以 `XPERT_AGENT_MIDDLEWARE_RUNTIME_TOKEN` 暴露门面，被本域与 Chat/Xpert 依赖。
2. `execution-cancel` **不是顶层目录**，真实位置是 `shared/execution/`（`ExecutionCancelModule` / `ExecutionCancelService` / `ExecutionCancelledError` / `executionAbortScope`），**归本域**（执行链取消）。
3. `agent-evolution/` **不在本域**，只记录耦合点。
4. **native 编译三件套文件物理在 `agent-invocation/` 但语义属图编译（子专家 ①）**：排障时按「语义归属」找人，不要按目录找人。
5. 相邻澄清：`/api/xpert/chat` **不存在**；真实入口是 `/api/xpert-agent/chat`（Agent 直连，本域）与 `/api/xpert/:id/chat`（定义面调试入口，非本域）。

## 7. 已知问题与常见坑

1. **停请求不是终止证明**：只有 `exited` 能确认进程停止，`unknown` 必须保持可见；取消是协作式的（`AbortSignal`），不强杀 CPU-bound，也取消不了 Project Task。
2. **解析一次即 pin，恢复不得静默回退**：provider 来源在首次解析时固定，恢复走 pinned 查找；找不到即显式报错（409 `ProviderChanged`），**不是**悄悄降级到另一个实现。
3. **CAS 冲突要重读重试**：状态提交以 `revision` 做 CAS，`replace(record, expectedRevision)` **返回 boolean**——`false` 即冲突（非异常），调用方必须重读重算；重试超限才收敛为 `ConcurrentUpdate`。
4. **polling 是唯一持久恢复机制**：本地事件与队列投递只是加速，调低/关闭定时扫描等于关闭恢复；**启动 fence ≤120s 内不做中间态失效判定**（取消路径仍可用），含糊启动必须对账且永不自动重放。
5. **三套租约易混**：`observationLeaseToken/observationLeaseUntil`（观察已存在句柄，60s）、`wait.leaseToken/leaseUntil`（wait 组续跑投递，120s）、`agent_runtime_delivery`/`inbox` 的 lease（传输与消费认领）语义与时长全不同、互不校验；「租约未过期」不等于互斥保证。
6. **终局化不得重放初始行**：整行重放初次快照会覆盖 `updatedAt` 与用量计数；`completedAt` 只在真终态写、恢复 `running` 时清空，`updatedAt` 不能替代结束时间，元数据写入不得移动已记录的结束时间。
7. **跨副本取消靠 Redis `ai:execution:cancel`**：发布失败与订阅失败**只告警**——本副本照常停、其他副本**静默丢取消**；无 Redis 时跨实例链路整条不再成立。
8. **`AgentRuntimeBindings` / `AgentInvocations` 无 `@UseGuards`**：鉴权是显式调用型（`requireResourceAdmin()` / `findOwned()` 四元组）；结合「Guard 无元数据即放行」，新增端点若只依赖全局 `AuthGuard`，默认就是放行的。
9. **binding 拒绝 `provider ∈ {xpert, xpert-task}`**（内置运行时不经绑定暴露），`target.revision` 建时随机固定；改配置/版本要新建绑定，不能原地改。
10. **中间件只暴露 scoped API，不得把全局 capability registry 传给插件**：一次调用一次装配、缺能力即显式失败；草稿态上下文与发布态上下文分离，两者不共享全局注册表。
11. **`prompt_workflow` 唯一 `(workspaceId,name)`**：同名并发创建/重命名直接撞唯一约束；`associatedXpertIds` 需与模板使用方同步，归档/软删后的「用量」口径与实际可见范围易错（软删不影响唯一约束）。
12. **collaboration 是 WS 面**：`cors.origin='*'`、用不透明 `sessionId`/`clientKey` 鉴权（**不是** Nest Guard）、`update` **先落库后 ack**；客户端必须按 ack 语义重试，凭据泄漏即可被任意来源复用。
13. **`agent_invocation_wait` 表名与语义历史错位**：真实语义已是「有依赖组的等待记录」，且组身份不再天然绑定某个 invocation，按外键假设推断关联会得出错误结论。
14. **`waitForTasks` 是有界观察**：观察窗口耗尽正常返回 `pending`，**不挂起父级、不意味着任务完成**；只有人工交互才挂起；`pending` 中含 `unknown` 归一为 `unavailable`。
15. **绕过 service 直写账本会静默破坏审计**：审计时间戳、`completedAt` 规则、用量与定价写入都收口在执行账本服务内；只保护事件表唯一约束并不能救回被改坏的当前快照。
16. **用量与定价的入口守卫存在交叉条件（待核实）**：写入入口与定价写入的前置条件方向相反，需按真实用量类型回归确认定价是否落库。
