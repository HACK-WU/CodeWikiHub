## 1. 核心流程实现位置

### 1.1 图编译与校验
`XpertAgentController` 的 `POST xpert/:id/test/:key` 发 `WorkflowTestNodeCommand`；正式编译由 `CompileGraphCommand`（含 `leaderKey`/`rootExecutionId`/`thread_id`/`rootController`/`signal`）进入 `CompileGraphHandler`：取 `GetXpertWorkflowQuery` → `getSwarmPartners` → `XpertAgentSwarmCommand` 或 `XpertAgentSubgraphCommand`。校验侧 `XpertAgentGraphValidator.handle` 与 `XpertAgentNodeValidator.handle`/`check` 响应 `XpertDraftValidateEvent`；图构建与流式事件投影在 `agent.ts`（导出 `messageEvent`，并再导出 `FakeStreamingChatModel`）。

### 1.4 Invocation 生命周期

## 2. 设计模式及落点

| 模式 | 落点 |
|---|---|
| 乐观并发 / CAS | `agent_invocation.revision` + `TypeOrmAgentInvocationStore.replace` + `updateLatest` 重试环 + 事件唯一 `(invocationId, revision)` |
| Outbox / Inbox | `appendRuntimeDelivery`（同事务）、`agent_runtime_inbox` 消费与 `claim/phase`、`redrive` 只重排不重放 |
| 租约（lease） | `observationLeaseToken/observationLeaseUntil`、`agent_invocation_wait.leaseToken/leaseUntil`、`claim(state, handler)` + 心跳续租 |
| 幂等键 | `agentInvocationId(scope, callId)`（规范化 JSON + sha256）、`existingApi(id)` 复用、结果消费 scoped unique key |
| 策略注册表 | `AgentRuntimeRegistry`（含 `getSource`/`getPinned`）、`AgentMiddlewareRegistry`、`WorkflowNodeRegistry`/`WorkflowTriggerRegistry` |
| 命令/查询分离（CQRS） | `CompileGraphCommand`、`XpertAgentSwarmCommand`、`XpertAgentSubgraphCommand`、`XpertAgentExecutionUpsertCommand`、`WorkflowTestNodeCommand`、`ResolvePromptWorkflowInvocationQuery` |
| 门面 + 作用域注入 | `AgentMiddlewareRuntimeService` / `AgentInvocationFactoryService`（captured identity、只暴露 scoped capability） |
| WS 网关 | `CollaborationGateway`（room per document、服务端广播回调订阅/退订） |

## 3. 热点路径

1. **invocation 认领与观察**：`AgentInvocationMonitorService.reconcile`（`@Interval(5000)`，`busy` 门闩，`take: 10`，`where {state: 'waiting', nextCheckAt <= now}`）→ `process` → `claim` → `withAccess` → `api.inspect`，是执行链唯一持久恢复通道（README 明写 polling 才是持久恢复机制，本地事件/队列只是加速）。
2. **CAS 冲突重读**：`AgentInvocationRuntime.updateLatest` 最多 8 次读—改—CAS；`start` 的 `insert` 冲突递归重入；热点是长任务高频 progress 与取消/交互并发时的 `ConcurrentUpdate`。
3. **中间件 scoped API 创建**：`createScopedApi` 每次调用都重新组装 capability 注册表并复制 connector id 数组，属高频构造点；`api` getter 亦每次新建（不缓存首个调用者身份，属有意设计）。
4. **执行账本写入**：`XpertAgentExecutionService.update` 的 `pessimistic_write` 行锁在 swarms/子图并发终局化时形成串行点，`recordUsage` 的独立事务与之交错。

## 5. 技术债与 hack

1. **注册地 ≠ 物理位置**：`RuntimeDeliveryController` 与 `agent_runtime_delivery`/`agent_runtime_inbox` 实体物理在 handoff，注册/注册表在 `AgentInvocationModule`；`handoff` 侧无 RouterModule/controller，排查路由时极易走错域。
2. **跨副本取消订阅失败仅告警**：`ExecutionCancelService.onModuleInit` 失败只 `logger.warn`（Redis 通道不可用即静默丢取消），`cancelExecutions` 的 publish 失败亦只告警；真实 Redis 下的端到端取消仍属未确认验收项。
3. **显式调用型鉴权无装饰器**：`AgentInvocationsController` 与 `AgentRuntimeBindingsController` 无 `@UseGuards`，靠方法内 `findOwned()` 四元组与 `requireResourceAdmin()`；`PromptWorkflowController` 用 `WorkspaceAuthoringGuard`，两种口径并存，新增端点默认可被「忘记判权」。
4. **collaboration 的传输面**：`@WebSocketGateway({cors: {origin: '*'}})` + opaque `sessionId/clientKey` 鉴权（非 Nest Guard），且服务与模块 `@Global`，跨模块隐式耦合面大。
5. **prompt_workflow 并发与关联同步**：唯一 `(workspaceId, name)` 使同名创建/重命名竞争；`associatedXpertIds` 需与模板使用方同步，归档/删除后的 usage 口径易错。
6. **`FakeStreamingChatModel` 的测试边界**：它被 `xpert-agent/agent.ts` 再导出，除测试外还用于 `workflow/answer/node.ts` 的答案节点，属生产路径上的「伪模型」依赖，容易误判为纯测试替身。
7. **`agent-evolution` 仅经 CQRS 耦合**：本域通过 `XpertAgentExecutionUpsertCommand` 被演进治理域消费，无编译期接口约束，执行账本字段语义变更（如 `completedAt`）需跨域确认。
8. **执行账本绕过 service 直写的风险**：`recordUsage`/`pessimistic_write`/`completedAt` 规则都封装在 `XpertAgentExecutionService`；绕过它直写 repository 会破坏「终局化不得重放初始行」「审计时间戳不接受调用方值」两条明写约束。

## 6. 设计维度分析

### 6.1 幂等键 vs 乐观锁：两种「重复」的分工
幂等键 `agentInvocationId(scope, callId)` 解决「同一逻辑调用被多次发起」（跨进程、跨 turn、崩溃重启），把语义去重压缩成主键；CAS `revision` + 唯一 `(invocationId, revision)` 解决「同一记录被并发写入」。两者不可互换：只做哈希会让并发写覆盖，只做 CAS 会让重放产生第二条记录；因此 `start` 先幂等查/插，再 CAS 抢占启动权（`begin` fence 120s），并由事件表唯一索引在数据库层收口。

章节来源：[invocation-runtime.ts](file://packages/server-ai/src/agent-invocation/invocation-runtime.ts)（关键符号：agentInvocationId/save）、[invocation.entity.ts](file://packages/server-ai/src/agent-invocation/invocation.entity.ts)（关键符号：AgentInvocationEventEntity）

### 6.2 观察的一致性模型：polling 为真相，事件为加速
`TaskObservationCommittedEvent` 只在提交后发本地通知且异常被吞（「deferred to polling」）；`reconcile` 固定 5s 扫描 `(state,nextCheckAt)`，因此多副本下正确性不依赖事件可达性，租约只保证「多进程扫描不互相踩」。代价是观察延迟上限 ≈ 5s + `nextCheckAt` 间隔，且「启动 fence ≤120s 内不做中间态失效判定」把含糊启动的正确性交给对账而非状态推断。

章节来源：[invocation-monitor.service.ts](file://packages/server-ai/src/agent-invocation/invocation-monitor.service.ts)（关键符号：AgentInvocationMonitorService.reconcile/handle）、[runtime-messaging/README.md](file://packages/server-ai/src/handoff/runtime-messaging/README.md)（关键符号：Polling is the durable recovery mechanism）

### 6.3 受控 API 的作用域收窄 vs 组合成本
`createScopedApi` 以「每次都重新组合 + 只在有绑定工作区作用域时注册工作区能力」换取泄漏面最小化（不暴露全局 registry、不暴露 runner factory），并让 `capabilities.require(...)` 在缺能力时显式失败；代价是调用点构造成本与能力集合随 scope 变化（同一 API 类型在不同 scope 下能力不同），测试用 `provider-boundary.spec.ts` 固化该边界。该设计是「插件不得自持跨租户上下文」这一不变量的实现手段，而非性能优化点。

## 7. 结论

实现层由三条「事务性骨架」支撑：图编译的 CQRS 链（`CompileGraphCommand` → swarm/subgraph）产出可执行图；执行账本链（`chat.handler` → `XpertAgentExecutionUpsertHandler` → `XpertAgentExecutionService`）以 ORM 管理审计时间与 `completedAt`；Invocation 链（`AgentInvocationRuntime` → `TypeOrmAgentInvocationStore` → `AgentInvocationMonitorService`）以幂等键 + CAS + 租约 + 同事务事件表把观察变成可恢复的审计历史，取消则以 Redis 广播 + 本地 abort 协作式完成。最容易出错的三处是跨副本取消的静默失败、双鉴权口径（Guard vs 显式 `requireResourceAdmin`/`findOwned`）、以及绕过 `XpertAgentExecutionService` 直写账本；三者都不在编译期报错，只能靠 README 约束与测试守住。
