## 框架与运行方式

Jest 30 + ts-jest（`tsconfig.spec.json`）+ babel-jest 处理 `node_modules` 中的 ESM 包，`testEnvironment: 'node'`，preset `../../jest.preset.js`。`moduleNameMapper` **直连源码**，不依赖预构建产物：

- `^@xpert-ai/server-core$` → `<rootDir>/../server/src/index.ts`
- `^@xpert-ai/contracts$` → `<rootDir>/../contracts/src/index.ts`
- `^@xpert-ai/plugin-sdk$` → `<rootDir>/../plugin-sdk/src/index.ts`
- `^@xpert-ai/cli-model-profiles$`、`^@xpert-ai/shadcn-ui/brand-icons$` 同理

运行方式（Nx 目标 `test` → `@nx/jest:jest`，`jestConfig: packages/server-ai/jest.config.ts`）：

```bash
# 全量（仓库根）
pnpm nx test server-ai
# 单文件（实测可用命令）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/agent-invocation/invocation-runtime.spec.ts
# 图案过滤（README 记录的 e2e 用法）
pnpm nx test server-ai --testPathPattern=enqueue-agent-chat-message.handler.e2e.spec.ts
```

## 断言与 mock 风格

- **受控 adapter + 手写假体**。`invocations.controller.spec.ts` 用 `fixture(provider, reference)` 工厂一次性拼出 entity、`records.findOneBy` 假仓库、`queries.execute` 假 QueryBus、真 `DefaultRuntimeCapabilityRegistry().register(ProjectAccessRuntimeCapability, projects)`，再 `new NativeAgentInvocationReader(...)` 与 `new AgentInvocationsController(...)` 直接构造——不启 Nest 容器。断言偏向**调用顺序与调用次数**：`expect(f.factory.createCapturedApi).not.toHaveBeenCalled()`、`.toHaveBeenCalledWith(new GetXpertWorkflowQuery(reference))`、`f.queries.execute.mock.calls.some(...)`。
- **HTTP 边界用真 Nest 管道**。`runtime-delivery.controller.spec.ts` 走 `Test.createTestingModule(...).createNestApplication()` + `app.listen(0)` + `fetch`，因此验证的是真实 pipe / 状态码语义（`:id` 非法 → 400 且**未触达** access 层；body 带身份字段 → 400 且未更新；未授权 redrive → 403 且未改传输）。README 亦明写「Boundary tests exercise actual Nest HTTP pipes and inherited handler injection」。
- **错误码断言用对象匹配**。`expect(...).rejects.toMatchObject({ code: 'NotFound' })`、`{ code: 'Unsupported', status: 422 }`、`{ status: 403 }`——即 `AgentInvocationError` 的 `code` 与 HTTP status 双断言，权限失败必须保持 403 而**不得**被包成通用错误。
- **`FakeStreamingChatModel`**（`shared/agent/fake-streaming-chat-model.ts`，经 `xpert-agent/agent.ts` 再导出）承载图与流式用例的模型边界，避免真实模型调用；`agent.spec.ts`、`subgraph.handler.spec.ts` 等围绕它断言流式事件投影。
- **`provider-boundary.spec.ts` 用元数据反射立边界**。它不跑业务，而是读 `MODULE_METADATA.PROVIDERS` / `MODULE_METADATA.IMPORTS`（含 `forwardRef` 解包）断言：消费方模块**不得**再声明 `AgentMiddlewareRuntimeService`，而必须 import `AgentMiddlewareRuntimeModule`；`WorkspaceFilesRuntimeCapabilityService`、`FileRuntimeService`、`ActorTokenRuntimeService` 各有唯一 provider owner；`SandboxModule` 不得依赖 `AgentMiddlewareRuntimeModule`。这是一条「架构不可回退」的断言，而非行为断言。

## 需真实依赖的用例清单

**真实 PostgreSQL（`XPERT_EXECUTION_TEST_DATABASE_URL`，URL path 必须以 `/xpert_execution_test_` 开头，否则 `beforeAll` 直接抛 `Dedicated test database required`）——本域实测只有 2 个：**

1. [invocation-wait.integration.spec.ts](file://packages/server-ai/src/agent-invocation/invocation-wait.integration.spec.ts)：随机 schema + `EntitySchema` 建表，随后按 `migrations/` 目录逐个应用 `20260922-agent-invocation.sql`、`20261001-invocation-wait.sql`、`20261002-task-wait-groups.sql` 等。
2. [activity.integration.spec.ts](file://packages/server-ai/src/agent-invocation/activity/activity.integration.spec.ts)：真实 PG + 临时目录 `VolumeClient` 立 activity 账本的容量、截止与归档边界。

**需真实 Redis**：本域/相邻域的取消链依赖 Redis pub/sub（`ai:execution:cancel`）。`execution-abort-scope.spec.ts` 的跨节点用例用**手写假 redis 对象**（只实现 `duplicate/connect/subscribe/publish`）覆盖消息格式，仍未覆盖真实 Redis 投递。队列恢复链的真 Redis 覆盖在 `handoff/runtime-messaging/testing/queue-recovery.cases.ts` / `queue-recovery.worker.spec.ts`，由 `XPERT_EXECUTION_TEST_REDIS_URL`、`XPERT_EXECUTION_TEST_REDIS_CONTAINER`、`XPERT_RECOVERY_CHILD` 门控，否则 `it.skip`。

**可选端到端脚本（不作为 CI 项）**：`node tools/scripts/verify-runtime-recovery.mjs`，自建 `postgres:16-alpine` + `redis:7-alpine`（Redis 带 `--appendonly yes --appendfsync always`）容器，绑定临时 localhost 端口，只清理带 `ai.xpert.test=runtime-recovery` 标签的资源；不改动平台业务库或队列。

## 缺口与不可执行项

- **不需要数据库的「integration」容易被误读为需要 DB。** `collaborators.integration.spec.ts` 与 `knowledge-preview.integration.spec.ts` 实际是内存 fixture（无 `typeorm` / `DataSource` 引用），把它们排进「需 PG 清单」会误判 CI 依赖。
- **真实模型、真实 Redis 投递、部署平台、Computer CLI 均无验收。** README 原话：「Database tests use real PostgreSQL/TypeORM with isolated schemas and controlled adapters. … They do not constitute a live Redis, deployed platform, real model or Computer CLI acceptance test.」真实模型侧只有 `FakeStreamingChatModel`。
- **CAS 多副本竞争、租约到期的真实并发时序**：单进程 spec 只能覆盖布尔返回与重读分支，多副本交错无法在单测里复现；`queue-recovery.worker.spec.ts` 的父/子进程方案是唯一接近的近似。
- **`XpertAgentController` 的 HTTP 面（`/chat` SSE、`middlewares/*`）无 controller 级 spec**：搜遍 `xpert-agent/` 的 32 个 spec，没有对 `XpertAgentController` 的 SSE 头、`keepAlive` 心跳、`takeUntilClose` 断开语义或 `BadRequestException` 包装的断言。
- **WS 面覆盖偏薄**：`collaboration/` 仅 2 个 spec，`collaboration.gateway.spec.ts` 只断言初始 presence 快照里的 socket 标识；`cors.origin='*'`、opaque 会话鉴权失败分支、`update-ack` 先落库后 ack 的时序、单房间 fan-out 均无断言。
- **`native-invocation-reader.ts` 无独立 spec**：其校验被 `invocations.controller.spec.ts` 间接覆盖（workspace 重分配 → `InvalidScope`、撤权 → 403、project 复核 → 403），但 `xpert-task` 的 workspace 取值分支只覆盖了一例。
- **`queue-recovery.worker.spec.ts` 需要 Docker 或外部容器编排**，默认路径下整组 skip，容易在本地被当成「通过」。

## 可执行性结论

✅ **可跑。** 75 个 spec 中，绝大多数是零外部依赖的构造式单测，在 `pnpm nx test server-ai` 或单文件 `--runTestsByPath` 下可直接执行；`moduleNameMapper` 直连源码，无需先构建 `contracts` / `plugin-sdk` / `server`。AGENTS.md 记录 server-ai 测试可运行，本域未见已知失败条目。

前提与边界：① 两个 `*.integration.spec.ts` 必须提供 `XPERT_EXECUTION_TEST_DATABASE_URL` 且库名以 `/xpert_execution_test_` 开头，否则静默转 `describe.skip`；② 队列恢复真 Redis 组必须显式提供 `XPERT_EXECUTION_TEST_REDIS_URL` 等变量，否则 `it.skip`；③ 端到端恢复验收只能由 `tools/scripts/verify-runtime-recovery.mjs` 显式触发，需要本机 Docker；④ README 明写 DB 测试**不构成** live Redis、部署平台、真实模型或 Computer CLI 的验收——因此「75 个通过」只证明逻辑与事务边界，不证明多副本取消、真实模型行为与真实队列投递。
