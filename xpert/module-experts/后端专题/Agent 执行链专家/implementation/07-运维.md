## 运行时租约与恢复

同一套扫描骨架下**并存三套互不相同的租约**，排障时必须先分清是哪一套：

| 租约 | 载体列 | 时长 / 续租 | 扫描节拍 | 适用对象 |
|---|---|---|---|---|
| 观察租约 | `agent_invocation.observationLeaseToken` / `observationLeaseUntil` | 60 s；每 20 s 续租，续租失败只 `warn('Runtime observation lease renewal deferred')` | `@Interval(5000)`，每轮取 `take(20)`，条件 `nextObservationAt <= now()` 且请求含 `dispatch` 或 `activity` | 只**观察**已有 handle，绝不启动；“Missing receipts are never launch instructions” |
| wait 租约 | `agent_invocation_wait.leaseToken` / `leaseUntil` | 120 s；每 30 s 续租，失败 `warn('Task wait lease renewal failed')` | `@Interval(5000)`，`reconcile()` 取 `take(10)`；claim 时同步把 `nextCheckAt` 推后 15 s | 老的 checkpoint 续跑路径（`process()` 走 waiting 组，`deliver()` 走 ready 组） |
| 投递 / 消费租约 | `agent_runtime_delivery.leaseToken` `leaseUntil`、`agent_runtime_inbox.leaseToken` `leaseUntil` (两表均有 `(state, nextAttemptAt)` 索引) | 由 `RuntimeMessageProcessor` / `RuntimeMessageInboxService` 管理，本域只注册实体 | 队列驱动 + `nextAttemptAt` 重排 | 传输收据与消费认领；语义归属「对话与会话域」 |

**polling 是唯一持久恢复机制。** README 原话：「Leases permit independent host processes to scan safely. Polling is the durable recovery mechanism; local events and queue delivery are acceleration only.」`AgentInvocationMonitorService.handle()` 响应 `TaskObservationCommittedEvent` 时并不直接处理，而是 `void this.reconcile().catch(...)`——本地事件只是把下一轮扫描提前叫醒，真正的恢复靠 `@Interval`。因此**调低/关闭定时器等于关闭恢复**。

**启动 fence ≤ 120 s。** 持久化的启动围栏期内，后台巡检**不做中间态失效判定**：不把「启动中途的 launch receipt」判成 `unknown`；取消路径在此期间仍然可用；围栏到期后巡检恢复正常。已验证的 preflight 失败只有在**尚无任何 launch receipt** 时才能记为 failed，含糊启动必须保持 `unknown` 且永不自动重放。

`busy` / `scanning` / `stopping` 三个进程内门闩防止重入：`reconcile()` 未结束就跳过下一拍，`onModuleDestroy` 置 `stopping` 后不再取新任务。

## 取消运维语义

取消走**两条彼此独立的 Redis pub/sub**，任意一条不通就有一条链路静默失效：

| 频道 | 发布方 | 语义 | 失败表现（源码实测） |
|---|---|---|---|
| `ai:execution:cancel` | `ExecutionCancelService.cancelExecutions(ids, reason?)` | abort 本地注册的 `AbortController`，reason 为 `ExecutionCancelledError`（code `EXECUTION_CANCELLED_BY_USER`） | `redis.publish` 抛错只 `logger.warn('Failed to publish cancel event: ...')`，紧接着仍执行本地 `applyCancel`——**本副本照常停，其他副本静默丢取消** |
| `ai:handoff:cancel` | `HandoffCancelService.cancelMessages(messageIds, reason?)` | 让跨实例的 in-flight job abort，归一为 `dead(canceled:...)` | Redis 是 `@Optional()` 注入：**没有 Redis 时 `onModuleInit` 直接 return**，跨实例取消整条静默失效；publish 失败同样只 `warn('Failed to publish handoff cancel event: ...')` |

**「停请求不是终止证明」对运维判断的含义**（README 原话「A stop request is not proof of termination: only `exited` confirms the process stopped, and `unknown` must remain visible.」）：发出了取消不等于进程已停。运维判定必须以 `exited`（或 Invocation 的终态观察）为准；`unknown` **必须保持可见**，不能被「已经下过取消」推断为已终止。取消本身是**协作式**的——通过 `AbortSignal` 传递，不强杀同步 CPU-bound 代码；队列态（`waiting`/`delayed`/`paused`）靠**移除 Bull job** 立即生效，`active` 态的 abort 是 best-effort 且 race-sensitive：扫描与 abort 送达之间若 job 恰好跑完，它会**正常完成**。会话取消的顺序是「先执行执行取消，再 best-effort 停 handoff」，handoff 停失败只记 warning，不阻塞会话取消流程。

## 队列与后台任务

本域**不自建队列**，而是挂在既有 handoff 队列上：

- **handoff 队列**：`HandoffQueueService` 承载消息派发；`HandoffQueueGatewayService` 扫描 `waiting` / `delayed` / `paused` / `active` 四种状态来匹配 `message.id` 与 `payload.executionId`（**扫描而非 Redis 索引**，成本与当前 job 量成正比）；队列态删除、`active` 态 abort。
- **观察轮询**：`AgentInvocationMonitorService.reconcile()`（5 s，waiting 组 take 10）与 `RuntimeObservationMonitorService.reconcile()`（5 s，take 20）是本域真正的「后台任务」；两轮都用 `Promise.allSettled` 并行，单个失败不阻塞同批其他任务。
- **续跑派发**：`deliver()` 由独立 dispatcher 触发、**不被观察扫描 await**。它先重校验每个依赖的访问权（即使结果已落库），再沿 `parentId` 上溯（`visited` 去重且 `size >= 64` 即抛 `Invalid execution ancestry`），父执行仍 `RUNNING` 就推后 5 s。恢复前若检出人工审批 checkpoint 且与 `wait.id` 匹配，状态置 `blocked` + `lastError = 'awaiting_user'`——**「先到的完成事件不得重放后来的人工审批」**。
- **失败语义**：wait 路径的 action 抛错时写 `lastError = 'continuation_pending'`、`nextCheckAt` 推后 60 s，`deadlineAt` 已过则直接置 `blocked`；观察路径抛错写 `observationError = 'observation_unavailable'` 并把 `nextObservationAt` 推后 60 s（常态 5 s，`unknown` 态 60 s，终态置 `null` 停止观察）。
- **时间轴驱动的异步等待**：`waitForTasks` 超窗正常返回 `pending`，**不挂起父级、不暗示任务完成**；单任务 `awaitResult` 与之共享同一 scoped 消费键。

## 日志与观测点

| 观测点 | 载体 | 判读 |
|---|---|---|
| `observationError` | `agent_invocation.observationError`，失败时写固定串 `'observation_unavailable'`，成功时清 `null` | 非空即该调用最近一轮巡检失败；配合 `nextObservationAt` 已推后 60 s 判断「正在退避」 |
| `agent_invocation_wait.lastError` | 固定串 `'outcome_unknown'`（有依赖处于 unknown）/ `'awaiting_user'`（卡在人工审批）/ `'continuation_pending'`（上一轮续跑 action 抛错） | 三种串各自指向完全不同的处置动作，不要混看 |
| 观察轮询指标 | `applicationMetrics.setInvocationWait({ pending, oldestErrorSeconds })`，SQL 口径 `state IN ('waiting','ready','blocked')`；`oldestErrorSeconds` 取 `createdAt` 中 `lastError IS NOT NULL` 的最老一条 | `pending` 长时间不降 → 扫描能力不足或依赖卡死；`oldestErrorSeconds` 单调上升 → 有错误从未被清掉 |
| wait 状态迁移 | `waiting` → `ready`（出 outcome）/ `blocked`（审批超 deadline）/ `stale`（父执行缺失、threadId 不符或 checkpoint 无 interrupt）/ `delivered`（恢复完成且无新 pending） | `stale` 通常意味着 checkpoints 已被清理或线程被替换 |
| execution `status` / `error` | `xpert_agent_execution.status` / `error` / `completedAt`；`interruptRunning(ids, threadId, error)` 只把 `RUNNING` 行改成 `INTERRUPTED` 并写 `completedAt` | 只影响 `RUNNING` 且 `threadId` 匹配的行，不会误伤已终态行 |
| Logger 关键字 | `'Task observation reconciliation deferred'`、`'Runtime observation scan deferred'`、`'Runtime observation lease renewal deferred'`、`'Task wait lease renewal failed'`、`'Invalid cancel payload: ...'`、`'Failed to publish cancel event: ...'`、`'Failed to publish handoff cancel event: ...'`、`'Execution activity retention cleanup deferred'`、`'Collaboration Redis subscriber is unavailable: ...'` | 全是 `warn` 级降级信号，**不阻塞主流程**，因此不能仅凭错误率判断健康 |
| 统一错误码 | `invocationError(code)` → `code` + HTTP 状态对固定（见接口文档错误码表）；`runtimeMessageError(code)` → `Access` 403 / `Invalid` 400 / 其余 409 | 抓 `code` 比抓变动的 i18n 文案更稳 |

## 多副本注意事项

- **CAS 冲突是常态，不是异常。** `store.replace(record, expectedRevision)` 以 `where {id, tenantId, organizationId, ownerId, revision: expectedRevision}` 提交并返回 boolean；失败即重读再试，且 `agent_invocation_event` 上的唯一索引 `(invocationId, revision)` 保证事件级幂等。滚动升级期间新旧副本同时写同一调用会出现大量「提交失败但无错误」，监控不应把它当故障。
- **租约续租失败只 warn，不中止本轮。** 三套租约的心跳都是 `setInterval(...).catch(() => warn(...))`。若某副本 GC 停顿超过租约时长，另一副本会合法接管同一行——两边都以为持有，这时**只有 CAS 落库能裁决**；因此绝不能把「租约未过期」当作互斥保证。
- **多副本取消必须有 Redis。** `ai:execution:cancel` / `ai:handoff:cancel` 都是 pub/sub（非持久、非确认）：副本扩容期间新副本若在订阅建立前就收到取消，会永久漏掉这一次；`HandoffCancelService` 在无 Redis 注入时**完全跳过订阅**。滚动升级的既有约定是「先部署消费者」，本域同样适用——先让所有副本都订阅得上，再依赖跨副本取消。
- **`busy` 门闩是进程内单例，不做跨副本协调。** `AgentInvocationMonitorService.busy`、`RuntimeObservationMonitorService.scanning` 只阻止同一进程重入；跨副本靠 `leaseUntil` + `take(N)` 分摊。因此期望吞吐随副本数线性上升是错的——每副本每轮仍是 take 10/20，且大量轮次会因租约被占而空转。
- **fence 与租约的组合风险。** 副本 A 处于启动围栏内时不做中间态失效判定，副本 B 若已过围栏并接管同一批行，可能先把 `running` 判成 `unknown`。排障时要把「同一时间窗内的 `unknown`」与启动时刻对齐看。
- **在途本地事件不跨副本。** `TaskObservationCommittedEvent` 只在本进程把 `reconcile` 提前唤醒；另一个副本只能等自己的 `@Interval` 过去才看到——这也是「polling 是唯一持久恢复机制」的直接运维推论。

## 安全运维

- **owner-scoped 收据不等于结果与运行权限。** `GET /api/agent-invocations/:id/delivery` 在两个维度上刻意收窄：投影字段里**没有结果体**，且授权撤销后 owner 仍可读传输失败（README 原话：「Owners with active organization membership can inspect transport failures even when a binding is revoked; this endpoint does not expose executor result bodies or grant runtime access.」）。审计时不要把「能看收据」当成「有数据面权限」。
- **`providerSource` 快照不可静默回退。** `agent_invocation.providerSource` 在首次解析时落库，后续所有 `inspect` / `cancel` / `respond` 都走 `registry.getPinned(provider, providerSource)`；找不到即 `ProviderChanged`（409）而**不是**悄悄降级到另一个实现。运维含义：升级/下线某个 runtime provider 时必须保证旧快照仍可解析，否则在途调用会集体 409，且这是**设计使然**，不该被「修掉」。
- **绑定创建期的两道硬闸。** `POST /api/agent-runtime-bindings` 显式拒绝 `provider ∈ {xpert, xpert-task}`（`InvalidRequest` 400），并要求 `workspaceIds` 全部命中当前 org scope（数量不符即 `InvalidScope` 403）；`target.revision` 与 `id` 都在建时用 `randomUUID()` 固定。三道检查合起来防的是「借绑定绕开 org 边界」与「用外部 provider 覆盖原生路径」。
- **绑定管理面是 admin-only，靠显式调用而非 Guard。** 三个端点都调 `requireResourceAdmin()`（非 SUPER_ADMIN/ADMIN 抛 `ForbiddenException`，i18n `server-ai:Error.AgentResourceAdminRequired`），并直接把返回的 org scope 拼进 `where`。风险点：controller 上没有 `@UseGuards`，若未来新增端点忘记补 `requireResourceAdmin()`，全局 `AuthGuard` 只保证「已登录」——结合 AGENTS.md 记录的「Guard 无元数据即放行」，新端点会**默认放行**。`create` 中 `registry.get(...)` 的返回值被丢弃，未注册 provider 不会在那里失败，也是同类隐性放行面。
- **native 面刻意不提供 HTTP 控制。** `/api/agent-invocations/:id/cancel` 与 `/respond` 对 `xpert` / `xpert-task` 一律 `Unsupported`（422），native 的控制权保留在各自既有路由，避免出一条绕过图/任务自身授权链的旁路。
- **WS 的 `cors.origin='*'` 是明确风险点。** `CollaborationGateway` 声明 `cors: { origin: '*' }` 且 `transports: ['websocket']`，命名空间固定 `/api/collaboration`，鉴权完全依赖 opaque `sessionId` + `clientKey`（**无 Nest Guard**）。运维含义：① 浏览器侧任何来源都能发起握手，真正的边界只剩 `resolveSession` 的令牌校验，令牌一旦泄漏即可被任意来源复用；② 需要在网关/反向代理层补 origin 白名单与速率限制；③ `CollaborationModule` 标了 `@Global()`，误用会造成跨模块隐式耦合。
- **子进程/执行器凭据边界。** host runner 的 receipt 只含 ID 与授权工作目录，**不含模型凭据，也不接受调用方自选的任意命令**；`AgentExecutionRunnerFactoryCapability` 只把 `AgentExecutionRunnerCapability` 暴露给 runtime 策略，不暴露全局能力注册表或 runner 工厂。
- **activity 输出解密面收敛。** `output(invocation, key, offset)` 在 state 缺失、`expired` 为真或已过 `expiresAt` 时一律 `NotFound`；归档输出按 `EXECUTION_ACTIVITY_MAX_BYTES` 与 `state.seq >= 20000` 双上限截断，越限记入 `gaps: ['capture_limit']`——即数据面**主动声明缺口**而不是静默截断。
