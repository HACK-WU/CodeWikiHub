## Recipe 1 · 编译并校验一个 Agent 图（含多智能体 leader/followers）

- **业务目标**：把一个 Agent 定义（`xpert_agent` + 团队图）编译为可执行 `CompiledStateGraph`，并在发布前完成图/节点校验。
- **调用顺序**：`POST /api/xpert-agent/chat`（SSE，草稿态直连）→ `XpertAgentService.chatAgent` → `FindXpertQuery({ isDraft: true })` → `XpertAgentChatCommand` → `CompileGraphCommand` → `GetXpertWorkflowQuery` → `getSwarmPartners` 判定：伙伴数 > 1 走 `XpertAgentSwarmCommand`（leader/followers + handoff 工具），否则走 `XpertAgentSubgraphCommand`。校验**不在编译链内**，而是 `EventNameXpertValidate`（`XpertDraftValidateEvent`）的订阅者：`XpertAgentGraphValidator`、`XpertAgentNodeValidator` 及 plugins/workflow 下各 validator。
- **事务边界**：编译与校验均不写业务表；执行账本写入发生在后续执行链（见 Recipe 2）。校验与编译不同步串联，因此「编译成功」不等于「校验通过」。
- **预期结果**：返回 `CompiledStateGraph`；多成员时 swarm 为每个 partner 生成 handoff 工具，并注入 `installThreadPauseGuards` 暂停门闩。
- **错误处理**：agent 找不到抛 `NotFoundException`；子图成环报校验错误码 `AGENT_SUBGRAPH_BUILD_CYCLE`；`POST /api/xpert-agent/xpert/:id/test/:key` 单节点调试把任意错误包成 `HttpException(getErrorMessage(err), 500)`。
- **真实代码示例**（`file://packages/server-ai/src/xpert-agent/commands/handlers/compile-graph.handler.ts`）：

```ts
const { agent, graph: xpertGraph } = await this.queryBus.execute<GetXpertWorkflowQuery, { agent: IXpertAgent; graph: TXpertGraph }>(
  new GetXpertWorkflowQuery(xpert.id, agentKeyOrName, command.options?.isDraft)
)
const partners = []
getSwarmPartners(xpertGraph, agent.key, partners)
if (partners.length > 1) {
  swarmOrGraph = await this.commandBus.execute<XpertAgentSwarmCommand, { agent: IXpertAgent; graph: CompiledStateGraph<any, any, any> }>(
    new XpertAgentSwarmCommand(agentKeyOrName, xpert, { ...options, rootController, signal: rootController.signal, partners })
  )
} else {
  swarmOrGraph = await this.commandBus.execute<XpertAgentSubgraphCommand, { agent: IXpertAgent; graph: CompiledStateGraph<any, any, any> }>(
    new XpertAgentSubgraphCommand(agentKeyOrName, xpert, { ...options, isStart: true, channel: channelName(agent.key), partners: [] })
  )
}
```

## Recipe 2 · 触发一次 Agent 对话并流式消费（含 HITL `resume({ decision })`）

- **业务目标**：以 SSE 消费一次 Agent 执行；在人工审批点（interrupt）暂停，随后用同一 execution 续跑。
- **调用顺序**：`POST /api/xpert-agent/chat`（`@Sse()`，`keepAlive(30000)`，`takeUntilClose(res)`）→ `XpertAgentService.chatAgent`；中断后前端回传 `action: 'resume'` + `target.executionId` + `decision`（可选 `patch`）→ `XpertAgentChatCommand` 携带 `execution:{id, category:'agent'}` 与 `resume:{ decision, patch }`。
- **事务边界**：执行账本三处 upsert（开始/中间/结束）走 CQRS `XpertAgentExecutionUpsertCommand` → `XpertAgentExecutionService`；`create` 剔除调用方 `createdAt/updatedAt`，`update` 在事务内 `pessimistic_write` 重载后写入，`recordUsage` 亦在独立事务内。
- **预期结果**：SSE 事件流；`xpert_agent_execution.status` 落 `running/success/error/pending/timeout/interrupted`；graph interrupt 与 `ExecutionCancelledError` 归 `interrupted`。
- **错误处理**：`ExecutionCancelledError`、graph interrupt 归 `interrupted`；已有 `threadId` 的执行禁止改挂另一线程（`ForbiddenException`）；native 的 `/respond` 与 `/cancel` HTTP 面一律 `Unsupported`（422），交互只能走图内 resume。
- **真实代码示例**（`file://packages/server-ai/src/xpert-agent/xpert-agent.service.ts`）：

```ts
execution: request.action === 'resume' ? { id: request.target.executionId, category: 'agent' } : undefined,
resume: request.action === 'resume'
  ? { decision: request.decision, ...(request.patch ? { patch: request.patch } : {}) }
  : undefined,
from: 'debugger'
```

`decision` 的归一在 `file://packages/server-ai/src/xpert-agent/commands/handlers/invoke.handler.ts`：`type === 'confirm'` 取 `payload ?? {}` 作为 `resume`，`type === 'reject'` 且无 payload 时不允许带图恢复（`shouldRejectResumeWithGraph`）。

## Recipe 3 · 以 Invocation 方式起一次调用并有界等待（`waitForTasks` 超时返回 `pending`）

- **业务目标**：以运行时账本方式发起后台/外部调用，并在有界窗口内观察依赖任务；窗口耗尽时正常返回 `pending`，**不挂起父级**。
- **调用顺序**：`runtime.scoped(scope)` → `api.start(request)`（幂等键 `agentInvocationId(scope, callId)`）→ 需要等待时 `api.waitForTasks({ callId, taskIds, mode }, { signal })`（或单任务 `api.awaitResult(id, { timeoutMs })`）→ `claimResults` 认领结果。
- **事务边界**：等待组登记 `AgentInvocationWaitStore.registerTasks`（`id()` 哈希幂等、`state='waiting'`、`deadlineAt = now + HOST_TASK_WAIT_POLICY.maxWaitMs`）；状态提交 `replace` 成功时同事务把匹配 wait 行 `nextCheckAt` 置 `now()`。有界等待与异步续跑共享同一 scoped 结果消费键。
- **预期结果**：窗口耗尽返回含 `pending` 任务的结果对象（可由 Agent 再次等待）；只有人工交互会挂起图（`invocation-wait` / `invocation-task-wait`）。
- **错误处理**：未注入 `commands` → `Unsupported`（422）；`CancelTaskWaitsCommand` 令 wait 行 `stale` + `lastError='parent_cancelled'`；超 `deadlineAt` 置 `blocked`；`unknown` 超过宽限窗（`XPERT_TASK_UNKNOWN_GRACE_MS`，须 ≤ `XPERT_TASK_MAX_WAIT_MS`）判 `unavailable`。
- **真实代码示例**（`file://packages/plugin-sdk/src/lib/agent/runtime/capability.ts` 与 `file://packages/server-ai/src/agent-invocation/invocation-factory.service.ts`）：

```ts
/** Bounded observation; may return a running task. Only human interactions may suspend the graph. */
awaitResult?(invocationId: string, options?: { signal?: AbortSignal; timeoutMs?: number }): Promise<AgentInvocation>
/** Wait for dependencies within a bounded window. The Agent may wait again when the result is pending. */
waitForTasks?(request: TaskWaitRequest, options?: { signal?: AbortSignal }): Promise<TaskWaitResult<AgentInvocation>>
```

```ts
waitForTasks: async (request, options) => {
  const result = await awaitInvocationTasks(controls, request, options?.signal)
  await claimResults(request.callId, result.tasks)
  return result
}
```

## Recipe 4 · 取消一次执行（协作式：Redis + abort；终态归一；停请求不是终止证明）

- **业务目标**：请求停止一次运行中的执行，并保证「取消是请求、不是终止证明」。
- **调用顺序**：外部 provider 走 `POST /api/agent-invocations/:id/cancel`；native（`xpert` / `xpert-task`）该路由恒返回 `Unsupported`，保留各自既有路由（会话侧走 SDK cancel endpoint / `CancelConversationHandler`）。会话取消顺序：先 `cancelRuns(executionIds)` + `cancelExecutions(..., 'Canceled by user')`，再 best-effort `StopHandoffMessageCommand`（handoff 停失败只记 warning，不阻塞会话取消）。
- **事务边界**：无跨表事务。执行取消是「先 `publish('ai:execution:cancel')` 再本地 `applyCancel`」；handoff 取消对队列态直接移除 Bull job，对 `active` 态发 abort。
- **预期结果**：本地 `AbortController.abort(new ExecutionCancelledError(...))`；handoff 归一为 `dead(canceled:...)` 且**不进死信、不重试**；`interruptRunning(ids, threadId, error)` 只把仍为 `running` 的行改为 `interrupted` 并写 `completedAt`。
- **错误处理**：Redis publish 失败仅 `warn`（本副本照常停，其他副本静默丢取消）；队列扫描与 abort 送达之间 job 可能正常完成（best-effort、race-sensitive）；`unknown` 必须保持可见——只有 `exited` 确认进程已停。
- **真实代码示例**（`file://packages/server-ai/src/shared/execution/execution-cancel.service.ts`）：

```ts
async cancelExecutions(executionIds: string[], reason?: string) {
  const uniqueIds = Array.from(new Set(executionIds.filter(Boolean)))
  if (!uniqueIds.length) return
  try {
    await this.redis.publish(EXECUTION_CANCEL_CHANNEL, JSON.stringify({ executionIds: uniqueIds, reason }))
  } catch (error) {
    this.#logger.warn(`Failed to publish cancel event: ${error}`)
  }
  this.applyCancel(uniqueIds, reason)
}
```

## Recipe 5 · 处理 CAS 冲突（重读重试）

- **业务目标**：并发写同一 Invocation 时不丢事件、不误判终态。
- **调用顺序**：`store.read` → 计算 next → `store.replace(next, record.invocation.revision)`；返回 `false` 即重读再试（`updateLatest` 最多 8 次）；`start` 的 `insert` 冲突则递归重入。
- **事务边界**：`replace` 在**单事务**内 `update ... where { id, tenantId, organizationId, ownerId, revision: expectedRevision }` + `appendEvent`（唯一 `(invocationId, revision)`）；`affected !== 1` 立即返回 `false`。
- **预期结果**：成功即 `revision + 1`；`nextObservationAt` 刷新为 `now()`；终态（`succeeded|failed|cancelled|waiting`）提交后发本地 `TaskObservationCommittedEvent`。
- **错误处理**：8 次后抛 `ConcurrentUpdate`（409）；`requireClaim` 路径失败直接抛 `ConcurrentUpdate`；事件表唯一索引冲突会回滚整个 `replace` 事务。滚动升级期间出现大量「提交失败但无错误」属常态，不应计为故障。
- **真实代码示例**（`file://packages/server-ai/src/agent-invocation/invocation-runtime.ts`、`file://packages/server-ai/src/agent-invocation/typeorm-invocation.store.ts`）：

```ts
private async updateLatest(id, access, observation, finishStart = false) {
  for (let attempt = 0; attempt < 8; attempt++) {
    const latest = await this.store.read(id, access.scope)
    ...
    const saved = await this.save(latest, next, false, finishStart ? 'finish' : undefined)
    if (saved) return saved
  }
  throw invocationError('ConcurrentUpdate')
}
```

```ts
if (result.affected !== 1) return false
await this.appendEvent(manager, record)
return true
```

## Recipe 6 · 排查「僵尸 run / 卡住」

- **业务目标**：区分「正在跑」「含糊启动」「已被取消但未证明终止」「等待窗口未到」四类卡住。
- **调用顺序**：① 看 `agent_invocation.observationError`（非空即最近巡检失败）+ `nextObservationAt`（是否已退避到 60s）；② 看 `agent_invocation_wait.state / lastError / nextCheckAt / deadlineAt`；③ 看 `xpert_agent_execution.status / error / completedAt`；④ 确认观察扫描定时器**未被调低或关闭**（关闭定时器 = 关闭恢复）；⑤ 对启动围栏内的记录不要按时间推断失效。
- **事务边界**：观察租约 `observationLeaseToken/observationLeaseUntil`（60s，20s 续租）与 wait 租约 `leaseToken/leaseUntil`（120s，30s 续租）语义不同、互不校验；跨副本靠 `leaseUntil` + `take(N)` 分摊，`busy/scanning` 门闩只在进程内。
- **预期结果**：终态置 `nextObservationAt = null` 停止观察；`unknown` 60s；其余 5s；持久化启动 fence 最长 120s 内不做中间态失效判定。
- **错误处理**：`observation_unavailable`（巡检失败，退避 60s）、`continuation_pending`（续跑 action 抛错，退避 60s / 超 deadline 改 `blocked`）、`awaiting_user`（卡人工审批）、`outcome_unknown`、`parent_cancelled`；`stale` 通常意味 checkpoint 已被清理或线程被替换。租约未过期**不是**互斥保证，只有 CAS 落库能裁决。
- **真实代码示例**（`file://packages/server-ai/src/agent-invocation/typeorm-invocation.store.ts`）：

```ts
if (committed && ['succeeded', 'failed', 'cancelled', 'waiting'].includes(invocation.status)) {
  // The due-time update is already durable; a local notification must not undo a committed result.
  try { this.events?.publish(new TaskObservationCommittedEvent()) } catch {
    this.logger.warn('Task observation notification deferred to polling')
  }
}
```

## Recipe 7 · 配 Prompt 工作流并在运行时解析（作者态 → `resolveRuntimeCommandProfile`）

- **业务目标**：在工作空间内维护 slash 命令模板，发布时固化为命令档案，运行时按 xpert 解析为可执行命令面。
- **调用顺序**：作者态 `GET/POST/PUT/POST archive/POST duplicate /api/prompt-workflow/...`（全部 `@UseGuards(WorkspaceAuthoringGuard)`）→ `POST /workspace/:workspaceId/validate-profile` → 发布时 `snapshotCommandProfile(workspaceId, commandProfile)` 写入 `xpert.commandProfile` → 运行时 `resolveRuntimeCommandProfile(xpert)`（经 `ResolvePromptWorkflowInvocationQuery` 消费）→ 回填 user input。
- **事务边界**：`initializeDefaultsInWorkspace` 在事务内 `pessimistic_write` 锁同名工作流后只补插缺失项；唯一索引 `(workspaceId, name)` 兜底。
- **预期结果**：`{ profile, runtime }` 双口径返回，`runtime = { hasProfile, xpertCommands, workspaceCommands, preferredSkillEntries, skillEntries }`；快照固定 `version: 1`，运行时不依赖后续改名/归档。
- **错误处理**：workspaceId 非 UUID → 400（`server-ai:Error.WorkspaceIdInvalid`）；同名并发创建/重命名撞唯一约束；`workspace_prompt_workflow` 条目必须带存在的 `workspaceId`，`skill` 条目必须有 `skillCommandName|name`；命中 `insert_text` 且 `commandSource.kind === 'prompt_workflow'` 时返回 `null`（**不覆盖用户已编辑内容**）；`sourceTemplateId` 是 server-owned provenance，**不得按名字推断**。
- **真实代码示例**（`file://packages/server-ai/src/xpert/xpert.controller.ts`、`file://packages/server-ai/src/xpert/commands/handlers/publish.handler.ts`）：

```ts
const sourceProfile = xpert.draft?.team?.commandProfile ?? xpert.commandProfile
return { profile: sourceProfile ?? { version: 1, commands: [] },
```

## Recipe 8 · 接协作文档（`createSession` → WS update → 物化重试）

- **业务目标**：让外部/插件侧以 CRDT 会话接入一份协作文档并保证更新幂等与重连修复。
- **调用顺序**：`collaboration.createScopedApi(defaults).createSession({ documentId, access })` 取得 `{ sessionId, clientKey, documentId, namespace }` → WS 连接 `/api/collaboration`（`handshake.auth` 携带三者）→ 收 `sync` + `presence-snapshot` → 发 `update` → 收 `update-ack` → 丢包/重连发 `sync-request`（带 `stateVectorBase64`）取增量；物化失败时 `retryMaterialization(documentId)` / `enqueueMaterialization`。
- **事务边界**：`applyUpdateWithScope` 在事务内 `pessimistic_write` 锁文档、按 `(documentId, updateHash)` 去重、`sequenceNumber + 1`、编码快照（`stateBase64` / `stateVectorBase64`）并累加 `updateCount`；**提交后才 `update-ack`**，随后 `publishBroadcast`（Redis `xpert:collaboration:broadcast`）跨节点扇出。
- **预期结果**：唯一 `(documentId, sequenceNumber)` 与 `(documentId, updateHash)`；`materializationStatus` / `lastMaterializationError` 回写；保留量由 `UPDATE_RETENTION_COUNT = 200` / `UPDATE_RETENTION_MS = 24h` 控制。
- **错误处理**：`resolveSession` 返回 null 时 emit `error` 并 `disconnect(true)`；鉴权是 opaque `sessionId/clientKey`（**无 Nest Guard**），TTL 600s，`cors.origin='*'` 属明确风险点，需在网关补 origin 白名单与限速；客户端必须按 ack 语义重试。
- **真实代码示例**（`file://packages/server-ai/src/collaboration/collaboration.service.ts`）：

```ts
createScopedApi(defaults: CollaborationRuntimeDefaults = {}): CollaborationApi {

    applyUpdate: (input) => this.applyUpdateWithScope(input, this.resolveScope(defaults)),
    createSession: (input) => this.createSessionWithScope(input, this.resolveScope(defaults)),
    ...
  }
}
```

## Recipe 9 · 配 Agent runtime binding（`provider` 白名单、`target.revision` 固定、workspace 归属）

- **业务目标**：由组织管理员把插件提供的 runtime provider 绑定到本组织的若干 workspace，供 Agent 的 `AgentInvocation` 工具按 `{id, name, description, mode}` 调用（`mode: wait` 交给 host checkpoint 适配器，`mode: background` 返回 invocation ID）。
- **调用顺序**：`GET /api/agent-runtime-bindings` → `POST /api/agent-runtime-bindings { title, workspaceIds, provider, reference, configuration }` → `PUT /api/agent-runtime-bindings/:id { enabled }`；下发时挂插件的 `AgentInvocation` 中间件（每条目生成一个普通 prompt 工具，**不在图构建器里加 provider 分支**）。
- **事务边界**：插入走参数化 `insert().values({ ... :workspaces::jsonb, :target::jsonb })`；workspace 归属是应用层 `countBy` 校验（`workspaceIds` 是 json 列、无 FK），不是 DB 约束。
- **预期结果**：返回绑定实体，`target = { bindingId, provider, reference, revision: randomUUID(), configuration }`，`enabled = true`；**配置/版本替换必须新建绑定**（不允许原地换 revision）。
- **错误处理**：zod `.strict()` 未知字段 → 400；`provider ∈ { xpert, xpert-task }` → `InvalidRequest`（400）；`workspaceIds` 去重后归属数量不符 → `InvalidScope`（403）；非 SUPER_ADMIN/ADMIN → `ForbiddenException`（`server-ai:Error.AgentResourceAdminRequired`）；被禁即视为显式撤权。注意 `create` 中 `registry.get(...)` 的返回值被丢弃，未注册 provider 不会在那里失败。
- **真实代码示例**（`file://packages/server-ai/src/agent-invocation/runtime-bindings.controller.ts`）：

```ts
if (input.provider === 'xpert' || input.provider === 'xpert-task') throw invocationError('InvalidRequest')
this.registry.get(input.provider, scope.organizationId)
const workspaces = [...new Set(input.workspaceIds)]
const count = await this.bindings.manager.getRepository(XpertWorkspace).countBy({ ...scope, id: In(workspaces) })
if (count !== workspaces.length) throw invocationError('InvalidScope')
const id = randomUUID()
target: { bindingId: id, provider: input.provider, reference: input.reference, revision: randomUUID(), configuration: input.configuration }
```
