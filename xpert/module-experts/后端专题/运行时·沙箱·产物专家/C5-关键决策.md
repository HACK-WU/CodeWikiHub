## D1 NsJail 作为唯一隔离后端
- **分类**：技术选型
- **动机（避坑）**：现象——把用户可控命令放在 API 进程内（Local Shell）或普通容器里跑；后果——没有命名空间、只读 rootfs、`NO_NEW_PRIVS`、capability dropping、seccomp 与 cgroup 的资源/权限边界，可执行文件的构造面暴露给请求方。
- **决策**：隔离后端收口为策略注册表内的 nsjail 实现（`@SandboxProviderStrategy('nsjail')` ＋ `@SandboxWorkspaceMapperStrategy('nsjail')`），执行落到**唯一特权组件** Runner（独立容器、HTTP 协议），每个 execute/终端/托管服务各得独立 NsJail 进程边界。
- **约束**：Runner 侧 `privileged: true` ＋ `apparmor=unconfined` ＋ `cgroup: host` ＋ `/sys/fs/cgroup:rw`；**RPC 请求不能选择挂载、宿主 PID、NsJail 参数或可执行文件**；工作区路径必须解析在 `XPERT_NSJAIL_WORKSPACE_ROOT` 之下；cgroup v2 不可写时 Runner **fail fast** 而非静默降级；配好 `NSJAIL_RUNNER_URL`/`TOKEN` 后 Local Shell **fail-closed 关闭**；`LocalBrowserRuntimeProvider` 仅开发（注释逐字：source-checkout tooling, never a production fallback）。
- **被否决方案**：无（实现层未见对「docker / 进程内子进程作为隔离后端」的显式否决记录）；`[推测]` 未选容器直连的动因是把特权面收敛到单一组件、并让执行后端与 API 生命周期解耦。
- **重新评估触发条件**：需要远程/共享 Runner、要求把 `privileged` 收窄为能力/设备白名单、或要在 Docker Desktop 等非真实 Linux 宿主上跑生产时（文档明确 Docker Desktop 只做冒烟，不构成 native Linux 证据）。
- **关联代码**：`file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.provider.ts`、`file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.ts`、`file://.deploy/nsjail-runner/docker-compose.nsjail.yml`、`file://.deploy/nsjail-runner/Dockerfile`
- **证据来源**：实现层 [01-架构.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/01-架构.md)「关键不变量」1 与「依赖关系」执行后端归属段；[07-运维.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/07-运维.md)「二、NsJail 运行时的部署」与「三、nsjail 二进制、内核要求与权限模型」；[02-实现.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/02-实现.md)「设计维度分析」隔离强度段。

## D2 Runner 一分为二：元数据包 vs `.deploy` 实现
- **分类**：架构设计
- **动机（避坑）**：现象——把 Runner 当普通 workspace 包（`packages/nsjail-runner`）维护与发布；后果——镜像构建/部署步骤与代码位置失配，升级顺序无人约束，出现「API 比 Runner 新」的静默不兼容（协议能力位不足时 `create()` 直接失败）。
- **决策**：`packages/nsjail-runner/package.json` 只作**发布元数据**（`private: true`，description「Release metadata for the Xpert NsJail runner Docker image」），真实 runner（`runner.py` ＋ `network.py`/`net_proxy.py`/`seccomp.policy`）与 `Dockerfile` 留在 `.deploy/nsjail-runner/`；API 侧只保留协议校验与适配（provider / sandbox / runner client / types）。
- **约束**：协议常量 `NSJAIL_RUNNER_PROJECT_CONTENT_PROTOCOL_VERSION = 2`、`NSJAIL_RUNNER_APP_DATA_PROTOCOL_VERSION = 3` 是硬门槛（项目态校验 2、所有运行时校验 3）；升级顺序被文档钉死为「先镜像后 API」且 API 会拒绝更旧 Runner；镜像固定 `xpert-nsjail-runner:3.6` 且 `NSJAIL_COMMIT` 在 clone 后校验哈希（漂移即构建失败）；回滚要**成对**取消 `NSJAIL_RUNNER_URL`/`NSJAIL_RUNNER_TOKEN`，否则 provider 半可见。
- **被否决方案**：无（未见对「Runner 作为 workspace 包随 API 发布」的显式否决记录）。
- **重新评估触发条件**：Runner 需要独立版本线/多镜像并存，或协议门槛要支持向后兼容窗口（当前切换期需重启既有运行时）时。
- **关联代码**：`file://packages/nsjail-runner/package.json`、`file://.deploy/nsjail-runner/Dockerfile`、`file://packages/server-ai/src/sandbox/nsjail/nsjail.types.ts`、`file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.provider.ts`
- **证据来源**：[01-架构.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/01-架构.md)「依赖关系」执行后端归属段（README 逐字「The runner and Dockerfile remain in [.deploy/nsjail-runner]」）；[07-运维.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/07-运维.md)「二」「七、升级与回滚」。

## D3 `@Public()` 面的取舍与补偿控制
- **分类**：安全合规
- **动机（避坑）**：现象——同源 iframe 无法携带 `Authorization` 头、沙箱内页面也需要直取卷资源；若把「跳过 JWT」当成「公开」，私有数据就会随公共前缀一起暴露；若一律要求 JWT，预览与卷投递功能做不出来。
- **决策**：本域只开两类 `@Public()`——① **3 条 proxy 通配路由**（`@All` 匹配 `proxy`/`proxy/`/`proxy/*path`）一律挂 `SandboxPreviewAuthGuard`：cookie `xpert_sandbox_preview` 的 JWT（`aud='sandbox-preview'`、`sub='sandbox-preview-session'`）票面 `conversationId`/`serviceId` **必须与路径参数一致**；② `GET volume/*path` 匿名，但配四类路径黑名单 ＋ `assertPublicWorkspacePath` ＋ `openFileSnapshot` 后按实际卷内相对路径复检 `rejectProtectedPaths`。
- **约束**：`@Public()` **只跳过全局 JWT，不提供租户隔离**——volume 的 `tenant` 仅用于定位卷根；该面**无审计、无速率限制**；预览签名密钥取 `JWT_SECRET`，缺失时建会话直接 500（**不降级放行**）；proxy 转发前清洗请求头并丢弃 `set-cookie`/`service-worker-allowed`，平台凭证与预览 cookie 不得进入 provider 后端。
- **被否决方案**：无（未见对「给 volume 通配补身份校验」或「以 Authorization 取代 cookie」的显式否决记录）。
- **重新评估触发条件**：公共卷前缀出现业务数据、需要按租户限流/审计、或需要支持 WebSocket 升级（Vite HMR）时。
- **关联代码**：`file://packages/server-ai/src/sandbox/sandbox.controller.ts`、`file://packages/server-ai/src/sandbox/sandbox-preview-auth.guard.ts`、`file://packages/server-ai/src/sandbox/sandbox-preview-session.service.ts`、`file://packages/server/src/bootstrap/index.ts`
- **证据来源**：[01-架构.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/01-架构.md)「关键不变量」4~5；[02-实现.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/02-实现.md)「volume 通配路由」「预览 proxy」两节的风险与护栏清单；[05-接口.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/05-接口.md)「十三、鉴权与准入矩阵」。

## D4 WS 终端（而非仅 HTTP/SSE）与逐消息鉴权
- **分类**：接口契约
- **动机（避坑）**：现象——HTTP/SSE 只有单向流，PTY 的输入、窗口尺寸与键序表达不了；仓库现存的 `POST /terminal` 是 `@Post` ＋ `@Sse()` 的非标准组合，客户端必须按 POST＋SSE 解析；后果——要么做不出真实交互终端，要么把会话身份与终端状态混在一次性请求里。
- **决策**：交互终端走 socket.io 命名空间 `sandbox-terminal`（4 类客户端消息 / 5 类服务端事件），**每条消息重鉴权**（`SandboxTerminalAuthGuard`：`cs-x-` 前缀走 client-secret，否则 `WsJWTGuard`，再过 `assertWorkbenchPrincipal`）；`open` 额外查库确认会话存在并复核助手范围；WS 不经 HTTP 请求上下文中间件，故 `open` 用 `runWithCapturedRequestContext` 手工回填 actor 与 `organization-id`；SSE 端点保留为 `backend.streamExecute` 的一次性执行通道。
- **约束**：会话表只在进程内（`#sessions`/`#pendingOpens`），**无 TTL**，靠 `close`/进程退出/错误/断连四条路径销毁；同一 `requestId` 重复 open 会把旧请求标记 canceled、迟到会话立即关闭；无持久化 ⇒ 多副本下必须重连；终端槽位每 runtime 8 个且 fork 前原子预留；`sandbox_shell` 中间件默认超时 600 秒并统一受 `xpertFeatures.sandbox.enabled` 门控。
- **被否决方案**：无（未见对「只做 HTTP/SSE 终端」的显式否决记录）。
- **重新评估触发条件**：需要终端会话跨副本、可审计或可续接，或需要多终端分屏/配额治理时。
- **关联代码**：`file://packages/server-ai/src/sandbox/sandbox-terminal.gateway.ts`、`file://packages/server-ai/src/sandbox/sandbox-terminal-auth.guard.ts`、`file://packages/server-ai/src/sandbox/sandbox.controller.ts`、`file://packages/contracts/src/ai/sandbox-terminal.model.ts`
- **证据来源**：[01-架构.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/01-架构.md)「关键不变量」3；[02-实现.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/02-实现.md)「WS 终端网关」；[05-接口.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/05-接口.md)「七、WS 终端」。

## D5 配额与超时三层策略
- **分类**：性能取舍
- **动机（避坑）**：现象——Agent 循环 ＋ 重试会在没有并发闸门的情况下同时起大量 NsJail 边界；只做单层限流又会被某个租户/用户吃满全局配额；后果——宿主内存/CPU 被击穿，失败集中在最贵的时刻，且「谁在占用」无法归因。
- **决策**：三层闸门——① **作业层** Redis ZSET 租约三桶（`SANDBOX_JOB_GLOBAL_LIMIT=20` / `TENANT=4` / `USER=2`，匿名作业无 user 桶），Lua 原子同时占位，超限抛 `SandboxJobRuntimeError('SANDBOX_CAPACITY_UNAVAILABLE', retryable=true)`；② **注册表层**硬约束 `timeoutMs ≤ hardDeadlineMs`，作业行写 `hardDeadlineAt = now + definition.hardDeadlineMs`；③ **Runner 层**独立准入与 TTL（`MAX_RUNTIMES=100`、`MAX_EXECUTIONS_GLOBAL=32`/`PER_RUNTIME=4`、`MAX_TERMINALS_PER_RUNTIME=8`、`MAX_PROXIES_GLOBAL=64`、`PROXY_IDLE_TIMEOUT_SECONDS=60`、`MEMORY_BYTES=2147483648`、`SWAP_BYTES=0`、`PIDS=128`、`RLIMIT_AS_MB=4096`、空闲 2h/硬租约 24h）。
- **约束**：容量桶泄漏表现为**永不放行**；`waitForCapacity` 会让请求在拿到 lease 前长时间挂住；Runner 侧超限是**字面截断**（`MAX_SERVICE_LOG_BYTES`/`MAX_DOWNLOAD_BYTES`/`MAX_READY_TEXT_BYTES`）而非报错；`RUNTIME_IDLE_TTL_SECONDS=7200` 只回收运行时、**不回收卷内文件**；`readyPattern` 名不副实（按字节限量并字面匹配，正则元字符无特殊语义）。
- **被否决方案**：无（未见对「单层限流」或「无 TTL 长驻运行时」的显式否决记录）。
- **重新评估触发条件**：单机多租户密度提升、需要按组织配额或「预留＋抢占」语义，或需要把容量释放从 Lua 租约换成可观测的调度器时。
- **关联代码**：`file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job-capacity.service.ts`、`file://packages/server-ai/src/sandbox/sandbox-job/sandbox-runtime-definition.registry.ts`、`file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job.entity.ts`、`file://.deploy/nsjail-runner/docker-compose.nsjail.yml`

## D6 `runtime-control` 的门禁粒度
- **分类**：安全合规
- **动机（避坑）**：现象——6 个端点若一律加 `RoleGuard`＋`SUPER_ADMIN`，只读自检也进不去；若只靠类级 `TenantPermissionGuard`，普通登录者就能触发生产集群自重启；若门禁只写在装饰器上，任何绕过装饰器的服务调用都能触发自信号。
- **决策**：**读写分离 ＋ 双层门禁**——装饰器层：类级 `TenantPermissionGuard`，仅 `GET instances`、`POST instances/:instanceId/retire`、`POST restart` 叠加 `RoleGuard`＋`@Roles(SUPER_ADMIN)`；服务层：**全部 6 条**（含无 `RoleGuard` 的 3 条读端点 `restart-capability`、`restart/:restartId`、`plugin-convergence/:generation`）都过 `assertAuthorizedActor()` 三重断言（必须交互式会话、必须 SUPER_ADMIN、必须默认租户）。
- **约束**：`RUNTIME_PROCESS_SIGNALER` 的真实实现是 `process.kill(process.pid, signal)`（自信号，靠 PM2/容器监管者拉起替代副本）；重启协调依赖**副本间共享同一 Redis**；API Key 身份一律被拒（`interactive-auth-required`）；`retire` 必须带 `expectedBootId` 防误退；本地 nodemon 下「重启」等价于 watcher 重拉，drain 语义不成立。
- **被否决方案**：无（未见对「全端点统一 SUPER_ADMIN」或「只靠服务层断言」的显式否决记录）。**实测事实**：3 条只读端点确实没有装饰器级 `RoleGuard`，其保护完全来自服务层断言。
- **重新评估触发条件**：需要把只读状态开放给运维只读角色（RBAC 细分）、支持多默认租户/多区域，或要把 rollout 编排下沉到容器平台时。
- **关联代码**：`file://packages/server/src/runtime-control/runtime-control.controller.ts`、`file://packages/server/src/runtime-control/runtime-control.service.ts`、`file://packages/server/src/runtime-control/runtime-control.module.ts`
- **证据来源**：[01-架构.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/01-架构.md)「关键不变量」6；[05-接口.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/05-接口.md)「八、RuntimeControlController」表与「十三、鉴权与准入矩阵」；[07-运维.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/07-运维.md)「八、运行时控制面操作」。

## D7 健康探针的检查项选择
- **分类**：接口契约
- **动机（避坑）**：现象——把 liveness 与 readiness 合成一个端点，编排层会在 drain 或缓存抖动时误杀实例；而 DB 探针只做连接 ping 对 MikroORM 连接问题不敏感（`checkDbWithTerminus = false` 的注释正说明了踩过的坑）；后果——重启风暴或「探针健康但实例不可用」的假阳性。
- **决策**：两条 `@Public()` 探针语义分离——`GET /health/ready` 只读 `RuntimeLifecycleService.readiness()`（**不查任何外部依赖**，非 `ready` 即 503 ＋ `Cache-Control: no-store`）；`GET /health` 用 Terminus 聚合四项：DB（`userRepository.count()` 真实查询）、磁盘（`resolve(__dirname)`、`thresholdPercent: 99.999999`）、缓存 set/get 往返、Redis（仅 `REDIS_ENABLED === 'true'` 时加入）。
- **约束**：四个开关 `checkDb/checkStorage/checkCache/checkRedis` **硬编码 true**；`/health` 路径被 `RuntimeDrainMiddleware.isHealthRequest` 豁免，重启期间仍可探活（**探针可用 ≠ 接业务流量**）；DB 与磁盘异常被吞成 `{ status:'down', message }` 返回体而非抛错（`[推测]` 对聚合静默）；health 是本域测试最薄处（5 文件 / 0 spec）。
- **被否决方案**：无（注释只解释了**为何关闭** Terminus DB ping，未见对「合并两条探针」或「移除某项检查」的显式否决记录）。
- **重新评估触发条件**：需要基于探针做自动扩缩容/自动重启（要求把 `down` 变成真实失败）、或用户量增长使每次 `count()` 成本不可接受时。
- **关联代码**：`file://packages/server/src/health/health.controller.ts`、`file://packages/server/src/health/health.module.ts`、`file://.deploy/api/healthcheck.cjs`、`file://packages/server/src/runtime-control/runtime-drain.middleware.ts`
- **证据来源**：[01-架构.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/01-架构.md)「关键不变量」7；[02-实现.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/02-实现.md)「健康检查」与「技术债与 hack」8~9；[07-运维.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/07-运维.md)「九、健康探针的接入」。

## D8 产物登记的幂等设计
- **分类**：接口契约
- **动机（避坑）**：现象——Agent/插件重试会重复登记同一产物；若幂等只做在应用层「先查后写」，并发下会建出多个同源容器与重复版本；后果——分享链接指向哪个版本不确定、审计与统计口径失真、`currentVersionId` 语义被破坏。
- **决策**：**由数据库承担幂等**——`artifact` 用 4 条**部分唯一索引**（按 `organizationId`/`userId` 是否 NULL 切分同一业务约束）保证「同来源同作用域只有一个容器」，应用层 `findExistingArtifact` 命中即复用行并把 `status` 复位 `active`；`artifact_version` 用 `(tenantId, organizationId, artifactId, versionNumber)` 抗版本号并发、`(artifactId, idempotencyKey)` 抗重放，`ensureArtifactVersionWithDefaults` 强制 `idempotencyKey`、先查后写并返回 `created|reused`；`artifact_link` 用 `slug` 唯一 ＋ 部分唯一（`status='active'` 的 `shareKey`）保证 URL 稳定且同 key 同时只有一条有效分享。
- **约束**：`artifact_version` **版本不可变**（改内容只能新增版本，展示策略改在 link）；`workspaceFileRef` json 非空（字节在 Workspace Files，本域不存内容）；公开读取每次重算 `sha256`，不符即拒绝并记 `denied`——把「内容正确」的验证成本从写入期推到读取期；`artifact.kind` 默认 `'file'`、`status` 默认 `'active'`。
- **被否决方案**：无（未见对「仅应用层去重」或「允许同名重复容器」的显式否决记录）。
- **重新评估触发条件**：需要同一来源多容器（多环境/多版本并存）、要引入对象存储直传，或大产物读取的内存峰值（整文件读入 + sha256）不可接受时。
- **关联代码**：`file://packages/server-ai/src/artifacts/artifacts.service.ts`、`file://packages/server-ai/src/artifacts/entities/artifact.entity.ts`、`file://packages/server-ai/src/artifacts/entities/artifact-version.entity.ts`、`file://packages/server-ai/src/artifacts/entities/artifact-link.entity.ts`

## D9 工作区文件访问的路径约束
- **分类**：安全合规
- **动机（避坑）**：现象——若让客户端传路径、或把 `fileKey` 直接当磁盘路径使用，调用方可以构造越界路径、指向未授权文件，或从错误信息里反推主机布局；后果——卷内越权读取与主机路径外溢。
- **决策**：**两段式 ＋ 服务端解析**——`createSession`（`resolveViewFileAccessContext` ＋ `assertAssistantFileAccess`，写 cookie）与 `createGrant`（`requireAuthenticatedSession` → `resolveViewFileResource` → `assertContextMatchesSession`（租户/组织/用户/host/view/dataScope 必须与 session 完全一致）→ `assertPortableReference`）；读取时 `resolveAuthorizedFile` 先 `resolveWorkspaceVolumeScope(grant.reference, …)` 再 `volumeClient.resolve(...)`，`fileName` 只参与匹配、**不参与拼路径**。
- **约束**：grant 到期时间**跟 session 走**（不独立续期）；session/grant 全在 Cache，进程重启即全部失效；content 控制器是类级 `@Public()`，必须配合 `WorkspaceFileAccessGuard`，且额外做 `assertRequestOrigin`（同源 iframe 无 Origin/Referer 与附件下载有显式放行分支，其余 403）；失效会话/授权一律 404（避免探测存在性）。
- **被否决方案**：无（未见对「客户端传路径」或「长期 token 直读」的显式否决记录）。
- **重新评估触发条件**：需要长时下载/断点续传、跨域嵌入，或要把 grant 落库以支持多副本续接时。
- **关联代码**：`file://packages/server-ai/src/workspace-file-access/workspace-file-access.service.ts`、`file://packages/server-ai/src/workspace-file-access/workspace-file-access.guard.ts`、`file://packages/server-ai/src/workspace-file-access/workspace-file-content.controller.ts`
- **证据来源**：[02-实现.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/02-实现.md)「工作区文件访问授权」；[03-数据流转.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/03-数据流转.md)「链路八」路径约束条；[05-接口.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/05-接口.md)「十一、workspace-file-access」。

## D10 外部实体注册进本域 `forFeature`

## D11 托管服务台账：运行时快照而非历史
- **分类**：架构设计
- **动机（避坑）**：现象——把 dev server 的生命周期只留在内存，API 重启后前端列表变空、也无法处置残留进程；反过来若每次状态变化都追加历史行，台账会膨胀成事件流，且「当前端口/预览地址」要额外聚合才能得到。
- **决策**：`sandbox_managed_service` **一行一服务**（唯一 `(conversationId, name)`），`status`/`runtimeRef`/`startedAt`/`actualPort` 由 `NsjailSandbox.startService` 的 `onStateChange` **反复覆盖**（语义是「最后一次观测」），`ownerExecutionId`/`ownerAgentKey` 只做执行账本的字符串弱引用；列表端点**绝不创建沙箱**（重启后仍只读既有记录）。
- **约束**：状态枚举 `starting|running|stopping|stopped|failed|lost`，`transportMode ∈ none|http`，预览要求 `http` 且有 `previewUrl`；`proxyByConversationId` 转发前清洗请求头；运行时长驻进程被 Runner TTL（空闲 2h／硬租约 24h）回收后，记录会被标记 `stopped`/`lost`；行随会话删除（FK CASCADE），无归档列。
- **被否决方案**：无（未见对「内存态托管服务」或「事件式历史表」的显式否决记录）。
- **重新评估触发条件**：需要托管服务事件历史/审计、要让服务脱离会话（跨会话复用同一 dev server），或需要多副本共享服务台账时。
- **关联代码**：`file://packages/server-ai/src/sandbox/sandbox-managed-service.entity.ts`、`file://packages/server-ai/src/sandbox/sandbox-managed-service.service.ts`、`file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.ts`

## D12 短时授权：预览与文件会话不落表
- **分类**：安全合规
- **动机（避坑）**：现象——把预览与文件访问做成长期 token 或落库会话；后果——长期凭据放宽了泄漏面、撤权必须等过期、多副本还要处理会话一致性；而预览是 iframe 场景、文件访问是单次投递场景，都不需要长期凭据。
- **决策**：一律**短时 ＋ 不落表**——预览 cookie `xpert_sandbox_preview`（JWT `aud='sandbox-preview'`，TTL 1 小时，`path` 精确到具体 service 的 proxy）；工作区文件 cookie `xpert_workspace_file_access` ＋ Cache 中的 session/grant（TTL 1 小时，grant 随 session 到期）；产物分享会话 cookie `xpert_artifact_share_session`（TTL 15 分钟、`path=/artifacts/share`，服务端把 TTL 上限钉在 365 天）。
- **约束**：三者都由 `JWT_SECRET` 签名——缺失时预览建会话直接 **500**（不降级放行），轮换方式就是轮换 `JWT_SECRET`；进程重启即全部失效（多副本下需重连/重授权）；cookie 手工解析在 `sandbox-preview-auth.guard.ts`、`workspace-file-access.guard.ts` 与 terminal 守卫中各写一份（语义一致但实现分散，改协议易漏改）。
- **被否决方案**：无（未见对「持久化 token / 落库会话」的显式否决记录）。
- **重新评估触发条件**：需要多副本续接、需要可撤销的长期分享，或要把 `JWT_SECRET` 换成独立签名密钥/密钥轮换体系时。
- **关联代码**：`file://packages/server-ai/src/sandbox/sandbox-preview-session.service.ts`、`file://packages/server-ai/src/workspace-file-access/workspace-file-access.service.ts`、`file://packages/server-ai/src/artifacts/artifacts.service.ts`
- **证据来源**：[01-架构.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/01-架构.md)「关键不变量」5 与「结论」短时授权段；[05-接口.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/05-接口.md)「六、九、十一」三节的 cookie 口径；[07-运维.md](file://.module-experts/后端专题/运行时·沙箱·产物专家/implementation/07-运维.md)「十、产物与状态数据的运维」凭据段。
