## Recipe 1 起一个沙箱执行（配额、策略与结果回收）
- **业务目标**：让插件运行时/Agent 工具在隔离边界里跑一次命令或一个作业，并拿到可核对的结果与产物引用。
- **调用顺序**：先做上下文准入 `authorizeConversation`（会话存在、`conversation.tenantId` 等于当前租户、助手 `features.sandbox.enabled` 为真、provider 非空）→ `resolveConversationSandbox`（**会真正申请后端**）→ `SandboxAcquireBackendCommand` → `NsjailSandboxProvider.create`（`NSJAIL_RUNNER_URL`/`NSJAIL_RUNNER_TOKEN` 缺一即抛 `NsJailRunnerNotConfigured` → 要求 `workspaceBinding.volumeRoot` → Runner `/health`（5 秒缓存＋并发合流）→ 项目态校验协议 2、所有运行时校验协议 3 → 稳定 `runtimeId`（sha256 截 32 位）→ `POST /v1/runtimes`）。作业面走 `SandboxJobRuntimeCapabilityService.run`：`requireRunnableAction` → `findIdempotent(tenantId, idempotencyKey)` → `bindingSelector.require` → `prepareAttempt` → `capacity.acquire` → `execute`。
- **事务-时序边界**：幂等命中 `succeeded` 直接复用；命中 `waiting/starting/running` 走 `waitForAttachedJob`（心跳 30 秒、TTL 120 秒）；`cleanupPending` 时先 `requirePreviousAttemptCleanup`；输入快照落 `.platform/inputs`，单作业输入/输出各上限 350 MB；容量是 Redis Lua 同时占 global/tenant/user 三档。
- **预期结果**：`sandbox_job` 落证据行（`status`/`attempt`/`hardDeadlineAt`/`progress`/`outputs`/`runtimeArtifactKind|Reference|Digest`），随后 `destroySandbox` → `cleanupVolume` 回收运行时与卷。
- **错误处理**：任一容量桶满 → `SandboxJobRuntimeError('SANDBOX_CAPACITY_UNAVAILABLE', retryable=true)`；Runner 不可达或协议能力位不足 → `create()` 直接失败（协议 2/3 是硬门槛）；`408/429/5xx`、`TypeError`、`NsjailRunnerTimeoutError` 判可重试，其余为永久失败。
- **真实代码示例**：
```ts
// 作业链顺序（实现层逐步记录）：run → requireRunnableAction → findIdempotent
// → bindingSelector.require → prepareAttempt → capacity.acquire → execute → finally capacity.release
// 注册表硬约束：timeoutMs ≤ hardDeadlineMs；hardDeadlineAt = now + definition.hardDeadlineMs
```
章节来源：[sandbox-job-runtime-capability.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job-runtime-capability.service.ts)（关键符号：SandboxJobRuntimeCapabilityService.run / waitForAttachedJob / cleanupOrphans）、[nsjail-sandbox.provider.ts](file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.provider.ts)（关键符号：NsjailSandboxProvider.create / readRunnerConfig）、[sandbox-job-capacity.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job-capacity.service.ts)（关键符号：ACQUIRE_SCRIPT / acquire / SandboxJobRuntimeError）

## Recipe 2 取消与超时后的清理
- **业务目标**：把一次长跑或失联的执行停干净，并保证「上一次没清干净」不会静默叠加新尝试。
- **调用顺序**：应用内取消 `cancel()` → `runtime.terminate()` → 置 `status='cancelled'` ＋ `errorCode='SANDBOX_CANCELLED'` ＋ `finishedAt` → `destroySandbox` → `cleanupVolume`。超时不由取消实现，而由 `hardDeadlineAt` 表达；`cleanupOrphans` 在 `onModuleInit` 先跑一次、此后每 60 秒扫 `hardDeadlineAt < now` 与 `cleanupPending: true`，定时器 `unref()`。
- **事务-时序边界**：等待期靠 120 秒心跳续期；进程级重启不影响作业行——重启后同 `idempotencyKey` 的 `waiting/starting/running` 会被重新附着（跨进程重挂属该分支的自然结果 `[推测]`）。
- **预期结果**：作业行到达终态并留下 `cleanupPending`/`cleanedAt` 清理证据；`requirePreviousAttemptCleanup` 会在新尝试前拦住未清理的旧行。
- **错误处理**：清理失败**可追但不可自愈**（只留证据）；`sandbox.service.ts` 的 `@Cron cleanCron` 是空壳（只打一行 debug 日志，表达式与文案互相矛盾），真实回收只依赖 `cleanupOrphans` 与 Runner 侧 2h 空闲/24h 硬 TTL，**API 挂掉期间无补偿**；`sandbox_job.containerRef` 已 `@deprecated`，旧行可能新旧引用并存。
- **真实代码示例**：
```ts
// 取消分支：runtime.terminate() → status='cancelled' + errorCode='SANDBOX_CANCELLED' + finishedAt
//            → destroySandbox → cleanupVolume
// 兜底扫描：setInterval(cleanupOrphans, 60_000).unref()（onModuleInit 先执行一次）
```
章节来源：[sandbox-job-runtime-capability.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job-runtime-capability.service.ts)（关键符号：cancel / cleanupOrphans / requirePreviousAttemptCleanup）、[sandbox.service.ts](file://packages/server-ai/src/sandbox/sandbox.service.ts)（关键符号：SandboxService.cleanCron）、[sandbox-job.entity.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job.entity.ts)（关键符号：cleanupPending / cleanedAt / containerRef）

## Recipe 3 WS 终端会话（建连 → 鉴权 → 收发 → 断开清理）
- **业务目标**：在工作台里开一个真实 PTY，能交互输入、调整窗口尺寸、主动关闭。
- **调用顺序**：handshake（`handshake.auth.token`：`cs-x-` 前缀走 client-secret，否则 `WsJWTGuard`）→ 每条消息经 `SandboxTerminalAuthGuard` 重鉴权 → `assertWorkbenchPrincipal` → `open{conversationId, requestId, cols, rows}`（注册 pending open；WS 不经 HTTP 中间件，故用 `runWithCapturedRequestContext` 手工回填 actor 与 `organization-id`）→ `resolveConversationSandbox` → `terminalAdapter.open` → `opened{provider, sessionId, workingDirectory}` → `input`/`resize` → `output`/`exit`/`error`/`closed` → `close{sessionId|requestId}` 或断连。
- **事务-时序边界**：`open` 用 pending 对象实现取消——同一 `requestId` 重复 open 会把旧请求标记 canceled，迟到解析的会话立即关闭；会话表只在进程内 `Map<socketId, Map<sessionId, entry>>`，不落库、不跨副本；网关自身无空闲超时，存活由 Runner 进程边界决定；终端槽位每 runtime 8 个且 fork 前原子预留。
- **预期结果**：`opened` 携带 provider/sessionId/workingDirectory；关闭原因是六值之一（`client_closed`/`process_exited`/`socket_disconnected`/`error`/`open_failed`/`unsupported_provider`），错误码是 11 值枚举（含 `sandbox_disabled`/`unsupported_provider`/`session_not_found`）。
- **错误处理**：握手失败是 `WsException({status:403})`——**不要用 HTTP 状态码断言**；业务失败走 `error` ＋ `closed` 事件；`session_not_found`＝会话已被移除；关闭失败只 `logger.warn`，可能残留远端终端会话；`POST /api/sandbox/terminal`（`@Post` ＋ `@Sse`）是遗留的一次性流式执行通道，不是标准 `@Sse` 用法。
- **真实代码示例**：
```ts
// @WebSocketGateway({ namespace: 'sandbox-terminal', cors: { origin: '*' } })
// 4 类客户端消息：open / input / resize / close   （SandboxTerminalClientEvent）
// 5 类服务端事件：opened / output / exit / error / closed
// 每个 handler 都带 @UseGuards(SandboxTerminalAuthGuard)
```
章节来源：[sandbox-terminal.gateway.ts](file://packages/server-ai/src/sandbox/sandbox-terminal.gateway.ts)（关键符号：open / handleDisconnect / registerPendingOpen / normalizeError）、[sandbox-terminal-auth.guard.ts](file://packages/server-ai/src/sandbox/sandbox-terminal-auth.guard.ts)（关键符号：SandboxTerminalAuthGuard.canActivate / assertWorkbenchPrincipal）、[sandbox-terminal.model.ts](file://packages/contracts/src/ai/sandbox-terminal.model.ts)（关键符号：SandboxTerminalClientEvent / SandboxTerminalErrorCode / SandboxTerminalClosedReason）

## Recipe 4 预览 proxy（会话 → 3 条 @Public() 路由 → 过期）
- **业务目标**：把沙箱里跑的 dev server 通过同源路径交给浏览器 iframe，同时不让平台凭证进入沙箱后端。
- **调用顺序**：先起托管服务（`POST /api/sandbox/conversations/:cid/services/start`，需 `status==='running'`、`transportMode==='http'`、有 `previewUrl`）→ `POST …/services/:sid/preview-session`（写 cookie `xpert_sandbox_preview`，返回 `{expiresAt, previewUrl}`）→ 浏览器直连 3 条 `@All` 路由之一（`…/proxy`、`…/proxy/`、`…/proxy/*path`，由 `SandboxPreviewAuthGuard` 逐请求校验）→ `proxyByConversationId` 转发到目标端口。
- **事务-时序边界**：cookie `httpOnly`、`sameSite:'lax'`、TTL 1 小时、`path` 精确到 `…/services/<serviceId>/proxy`、`secure` 由请求协议或 `x-forwarded-proto` 推导；转发前**原地替换** `request.headers`/`headersDistinct`/`rawHeaders` 并劫持 `response.setHeader`（丢弃 `set-cookie`、`service-worker-allowed`，重写 `location`），`finally` 还原三者；Runner 侧上游空闲 60 秒关闭。
- **预期结果**：同源 iframe 内正常加载页面；`preview-session` 是唯一把 `organizationId` 设为必填 query 的托管服务端点；**线程面没有 proxy 路由**（预览代理只挂会话面）。
- **错误处理**：无 cookie → 401「Sandbox preview session is required.」；票面与路径不符/过期/签名错 → 401「Sandbox preview session is invalid.」；`JWT_SECRET` 未配 → 500 `provider_unavailable`（**不降级放行**）；服务不支持代理 → 400 `unsupported_provider`；`transportMode !== 'http'` → 400 `preview_unavailable`；**不支持 WebSocket 升级**（Vite HMR 属显式范围外能力）。
- **真实代码示例**：
```http
POST /api/sandbox/conversations/<cid>/services/<sid>/preview-session   # 种 cookie，返回 expiresAt/previewUrl
ALL  /api/sandbox/conversations/<cid>/services/<sid>/proxy             # @Public + SandboxPreviewAuthGuard
ALL  /api/sandbox/conversations/<cid>/services/<sid>/proxy/*path       # 同上（含第三条 proxy/）
```
章节来源：[sandbox-preview-session.service.ts](file://packages/server-ai/src/sandbox/sandbox-preview-session.service.ts)（关键符号：createSession / verifySession / buildCookiePath / SANDBOX_PREVIEW_COOKIE_NAME）、[sandbox-preview-auth.guard.ts](file://packages/server-ai/src/sandbox/sandbox-preview-auth.guard.ts)（关键符号：SandboxPreviewAuthGuard.canActivate）、[sandbox-managed-service.service.ts](file://packages/server-ai/src/sandbox/sandbox-managed-service.service.ts)（关键符号：proxyByConversationId）

## Recipe 5 volume 通配访问（用途、风险与校验）
- **业务目标**：为「不需要登录就该能看」的卷资源（已发布预览的静态资源、运行时作业产物）提供直取入口，同时把项目/用户隔离路径挡在外面。
- **调用顺序**：`GET /api/sandbox/volume/*path?tenant=&download=` → `normalizeSandboxVolumeRequestSubpath` → 第一次 `isProtectedVolumeSubpath` → tenant 解析（query → `RequestContext` → `GetDefaultTenantQuery` 默认租户）→ dev 环境 `normalizeSandboxPublicVolumeSubpath` 归一 → 第二次黑名单校验 → `serveVolumeFile`。
- **事务-时序边界**：黑名单四类（`project/*`、`user/*/xpert/*`、`xpert/*/user/*`、`runtime-jobs/*`）命中即 403；`openFileSnapshot` 打开后还要按**实际卷内相对路径**复检 `rejectProtectedPaths`（防符号链接别名绕过）；`assertPublicWorkspacePath` 为通用越界拒绝原语；目录/非普通文件 404。
- **预期结果**：普通文件 200（`Accept-Ranges: bytes`、`Content-Length`、`Content-Type` 推断；Range 命中 206、越界 416；`download=1|true|yes` 强制 `attachment`）。
- **错误处理**：403 `Error.ProtectedVolumeAuthenticationRequired`；400 `SandboxVolumeQueryParameterInvalid`/`VolumeScopeIdentifierInvalid`/`SandboxVolumeInvalidPath`；**风险如实记**——未登录者可读公共卷前缀，无审计、无速率限制，`tenant` 只用于定位卷根、不构成授权，安全性完全依赖「公共前缀不含敏感数据」这一部署假设。需要身份的读取走三条私有路由：`volume/project/:projectId/*path`（额外 `assertCanRead` 且拒绝跨租户 tenant，403 `Error.ProjectVolumeCrossTenant`）、`volume/user/:userId/xpert/:xpertId/*path`（当前用户必须等于 `:userId`，403 `Error.UserXpertVolumePrivate`）、`volume/xpert/:xpertId/user/:userId/*path`（旧布局兼容）。
- **真实代码示例**：
```http
GET /api/sandbox/volume/previews/index.html?tenant=<tenant>&download=1   # @Public，仅路径护栏
GET /api/sandbox/volume/project/<projectId>/app.js                       # 需登录 + assertCanRead
GET /api/sandbox/volume/user/<userId>/xpert/<xpertId>/out.png            # 需登录 + 身份等于 :userId
```
章节来源：[sandbox.controller.ts](file://packages/server-ai/src/sandbox/sandbox.controller.ts)（关键符号：getVolumeFile / serveVolumeFile / isProtectedVolumeSubpath / normalizeSandboxPublicVolumeSubpath）、[nsjail-sandbox.provider.ts](file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.provider.ts)（关键符号：NsjailWorkspacePathMapper.mapVolumeToWorkspace）

## Recipe 6 运行时重启（system/runtime 系列）
- **业务目标**：以「逐副本自信号 ＋ 排水」的方式滚动替换 API 副本，并让在途请求可预期地收敛。
- **调用顺序**：自检 `GET /api/system/runtime/restart-capability`（返回 `{allowed, mode:'rolling-self-signal', reason}`，`reason ∈ allowed|interactive-auth-required|super-admin-required|default-tenant-required`）→ `POST /api/system/runtime/restart`（**202**，body 必带 `confirmation === RUNTIME_RESTART_CONFIRMATION`，可选 `reason`/`allowDowntime`/`runtimeRequirements[]` ≤100 条）→ 轮询 `GET /restart/:restartId`；副本盘点 `GET /instances`、单副本下线 `POST /instances/:instanceId/retire`（必须带 `expectedBootId`）。
- **事务-时序边界**：协调器先抢 Redis 活动重启键 → 逐副本 `beginDrain`（单例，重复进入返回 false）→ drain 期间**非 `/health`** 请求 503 ＋ `Retry-After: 5` ＋ `Connection: close`（`RUNTIME_DRAINING`/`RUNTIME_NOT_READY`）→ 队列关停（`RuntimeQueueShutdownService` 用 `DiscoveryService` 动态发现 `Bull`/`WorkerHost` 并 pause/close）→ `process.kill(process.pid, signal)`；`beforeApplicationShutdown` 的 `waitForIdle(1_000)` 给 SSE 最后一次 flush 机会；一次只 drain 一个候选副本。
- **预期结果**：副本状态在 `ready`/`draining`/`unready` 间推进，替代副本由 PM2/容器监管者拉起并重新注册；`allowDowntime` 只在「最后一个健康副本」时必须；沙箱作业不因重启丢失（状态在 `sandbox_job`，重连后按 `idempotencyKey` 重新附着）。
- **错误处理**：`confirmation` 缺失/不符 → 400 `RUNTIME_RESTART_CONFIRMATION_REQUIRED`；已有进行中重启 → 409；非交互式会话（API Key 一律拒）/非 `SUPER_ADMIN`/非默认租户 → 403 三兄弟；协调不可用 → 503；未知 `restartId` → 404 `RUNTIME_RESTART_NOT_FOUND`；本地 nodemon 下「重启」等价于 watcher 重拉，**不要指望 drain 语义**。
- **真实代码示例**：
```http
GET  /api/system/runtime/restart-capability     # 发布前自检：allowed/reason
POST /api/system/runtime/restart                # 202；confirmation 常量必填；409 表示已有进行中重启
GET  /api/system/runtime/restart/<restartId>    # 目标/已完成/失败副本数
GET  /api/system/runtime/instances              # SUPER_ADMIN；副本清单
```

## Recipe 7 插件收敛排障（plugin-convergence）
- **业务目标**：确认「插件已发布代次」是否真的收敛到全部副本，并区分「持久化成功但 rollout 未起」与「某副本没回来」。
- **调用顺序**：触发路径不走 HTTP——`recordPluginRuntimeRequirements` 先**持久化代次**（Redis `PLUGIN_GENERATION_KEY`），再尽力启动 rollout；只读核对 `GET /api/system/runtime/plugin-convergence/:generation`（`ParseIntPipe` 解析代数，返回 `status`/`restartId`/目标与已完成副本数），配合 `GET /restart/:restartId` 与 `GET /instances` 定位到具体副本。
- **事务-时序边界**：排队变更在下一轮 rollout 执行；`runtime-rollout-policy.ts` 规定排队变更**不得**改写候补副本的准入清单——`replacementAdmission` 要求 `phase==='rolling'`、非 `preparing`、无 failed 目标且在副本重启超时内。代次端点只有类级 `TenantPermissionGuard`，无 `RoleGuard`（见 C5-D6）。
- **预期结果**：代次状态可读且能反查承载它的 `restartId`；日志若明说「durable but its rollout has not started yet」，说明代次已落盘、rollout 未起（属预期分支，不是故障）。
- **错误处理**：代数不存在/未落地 → 404 `PLUGIN_RUNTIME_CONVERGENCE_NOT_FOUND`；非数字 → 400；副本数长时间不动＝某副本未重新注册（PM2 未拉起）或 Redis 协调键被占。
- **真实代码示例**：
```http
GET /api/system/runtime/plugin-convergence/<generation>   # status + restartId + 目标/已完成副本数
GET /api/system/runtime/restart/<restartId>               # 交叉核对同一轮 rollout
```
章节来源：[runtime-control.controller.ts](file://packages/server/src/runtime-control/runtime-control.controller.ts)（关键符号：pluginConvergenceStatus）、[plugin-runtime-generation.store.ts](file://packages/server/src/runtime-control/plugin-runtime-generation.store.ts)（关键符号：PLUGIN_GENERATION_KEY）、[runtime-rollout-policy.ts](file://packages/server/src/runtime-control/runtime-rollout-policy.ts)（关键符号：replacementAdmission）

## Recipe 8 健康探针接入与排障
- **业务目标**：给编排层两条语义不同的探针——「本进程愿不愿接流量」与「依赖还活着吗」，并让滚动重启期间的探针不被排水误伤。
- **调用顺序**：readiness `GET /api/health/ready` → 直接读 `RuntimeLifecycleService.readiness()`（**不查任何外部依赖**）；巡检/告警 `GET /api/health` → Terminus 顺序聚合 DB（`userRepository.count()`）→ 磁盘（`resolve(__dirname)`、`thresholdPercent: 99.999999`）→ 缓存 set/get 往返 → Redis（仅 `REDIS_ENABLED === 'true'`）。
- **事务-时序边界**：四个开关 `checkDb/checkStorage/checkCache/checkRedis` **硬编码 true**；`/health` 路径被 `RuntimeDrainMiddleware.isHealthRequest` 豁免，因此排水期间仍可探活（**探针可用 ≠ 副本还接业务流量**）；每次调用生成 `HealthCheckExecutionTimer-<uuid>` 计时标签。
- **预期结果**：`/health/ready` 在 `ready` 时 200 且恒带 `Cache-Control: no-store`，非 ready 时 **503**；`/health` 返回四项 `up`/`down` 明细。容器自检参数可直接抄：`HEALTHCHECK --interval=30s --timeout=15s --start-period=60s --retries=3 CMD ["node","healthcheck.cjs"]`（`healthcheck.cjs` 并发请求两条端点，要求 `ready.status === 'ready'`、`health.status === 'ok'` 且 `details[*].status === 'up'`）。
- **错误处理**：DB 与磁盘异常是 `return { status:'down', message }`——**返回体不抛错**（`[推测]` 对聚合是静默的）；缓存/Redis 失败抛 `HealthCheckError`，会真正让聚合失败；K8s 建议 `readinessProbe` → `/health/ready`（drain 期自动摘流量），`/health` 更适合深度巡检（磁盘阈值接近 100%、DB 是真实查询）。
- **真实代码示例**：
```yaml

livenessProbe:  { httpGet: { path: /api/health/ready, port: 3000 } }   # 避免 DB/缓存抖动直接杀实例
```

## Recipe 9 产物登记与读取（授权边界）
- **业务目标**：把一次产出登记成可版本化、可分享、可审计的产物，并保证字节不落表（表里只有可移植引用）。
- **调用顺序**：登记 `POST /api/artifacts`（或插件侧 `ArtifactsRuntimeCapability` 经 `createScopedApi()`，如 `FileActivityStorage.archive`）→ `createArtifact` 先按「源身份 ＋ 作用域」`findExistingArtifact`（命中即复用同一行并把 `status` 复位 `active`）→ 版本 `POST /:artifactId/versions` 或幂等 `POST /:artifactId/versions/ensure`（`ensureArtifactVersionWithDefaults` 强制 `idempotencyKey`，先 `findOne({artifactId, idempotencyKey})`，命中返回 `reused`）→ 分享链接 `POST /:artifactId/links` 或 `links/signed-preview` → 公开读取 `GET /api/artifacts/share/:slug[/download|/descriptor]`。
- **事务-时序边界**：`artifact_version` **无更新语义**（改内容只能新增版本，展示策略改在 link）；每 artifact 至多一条 active share（部分唯一索引）；分享会话 cookie `xpert_artifact_share_session` TTL 15 分钟、`path=/artifacts/share`，服务端把 TTL 上限钉在 365 天；`listArtifacts` 的 `pageSize` 上限 100。
- **预期结果**：公开读取先过 `authorizeArtifactLink`（签名预览 query `xpert_artifact_preview` / 登录态 / 分享会话 cookie 三选一），再 `readWorkspaceArtifact(version.workspaceFileRef)` 取字节并**用 sha256 复核**；响应头固定 `nosniff`/`no-referrer`/`no-store` ＋ `X-Xpert-Artifact-Version`/`-SHA256`，`text/html` 另加 CSP（`strict`/`interactive` 两档）；descriptor 序列化会剔除 `workspaceFileRef`。
- **错误处理**：作用域不匹配与真不存在都是 404；`deleted`/`revoked`/`expired`/链接建立后内容变更/校验和与大小不符 → **410**；需登录但无会话 → 302 跳 `/artifacts/auth/<slug>`；401「Login is required to access this artifact link」、403「Download is not allowed for this artifact link」；`image/svg+xml` **永不内联**，不支持 MIME 落 `application/octet-stream` 强制下载；审计只写 `ipHash`，实体注释禁止落 token、平台凭证与文件内容。
- **真实代码示例**：
```http
POST /api/artifacts                                  # createArtifact（同源命中即复用行）
POST /api/artifacts/<artifactId>/versions/ensure      # idempotencyKey 必填，created | reused
POST /api/artifacts/<artifactId>/links                # 每 artifact 至多一条 active share
GET  /api/artifacts/share/<slug>?xpert_artifact_preview=<signed>   # @Public + sha256 复核
```

## Recipe 11 排障入口合集（沙箱 / 终端 / 预览 / 产物 / 健康）
- **业务目标**：把五类高频症状落到唯一判据与处置动作，避免按症状猜测。
- **调用顺序（排查链）**：
  1. **沙箱起不来**：先看成对变量 `NSJAIL_RUNNER_URL`/`NSJAIL_RUNNER_TOKEN`（provider 可见性由它们决定；未配则 Local Shell 可用但**无 Linux 挂载边界**）；再核对 Runner `/health` 的能力位（`projectContentReadOnly`/`appDataProtection`，不足说明 Runner 旧于协议 2/3）；「创建即失败」＝协议不满足或卷路径越界；「Runner 启动即退出」＝宿主无可写统一 cgroup v2（fail fast，仅探针可临时 `XPERT_NSJAIL_USE_CGROUP_V2=false`）。
  2. **终端连不上**：`error.code` = `unsupported_provider`（provider 无 terminal 适配器）/ `sandbox_disabled`（会话 xpert 特性 `sandbox` 未开）；403 `WsException`＝握手 token 或助手作用域不符；终端槽位（每 runtime 8）打满也开不了新会话。
  3. **预览 401/403**：cookie path 必须精确等于 `/api/sandbox/conversations/<c>/services/<s>/proxy`；HTTPS 终止未透传 `x-forwarded-proto` 会丢 `secure` cookie；票面与路径参数不一致直接拒——处置是重新 `POST …/preview-session` 并确认代理链透传该头；400 再分 `unsupported_provider` 与 `preview_unavailable`。
  4. **产物 404 还是 410**：404＝作用域不匹配或卷内引用缺失（本域只存引用，字节归 Workspace Files）；410＝`deleted`/`revoked`/`expired` 的**正常语义**——用 `artifact_access_log.event` 对齐是哪种，同一条链反复 `denied` 说明分享策略配置问题。
  5. **健康抖动**：`cache` down＝缓存往返失败（Redis 开启时 `cacheType=redis`）；`database` down 是真实 `count()` 失败而非 Terminus ping；drain 期间 `/ready` 主动 503 是**预期**；对照 `HealthCheckExecutionTimer-<uuid>` 计时日志与磁盘水位。
- **事务-时序边界**：`/health` 被排水中间件豁免，所以「重启期间探针仍可用」不等于「副本还能接业务流量」；滚动重启卡住先看 `restart/:restartId` 与 `plugin-convergence/:generation`（副本数长时间不动＝某副本未重新注册或 Redis 协调键被占）。
- **预期结果**：把 `volume/*path` 的公共前缀当**事实上的 CDN 语义**对待（匿名可读、无审计、无限流）；把 `RUNTIME_DRAINING` 的 503 与产物 410 当预期状态而非故障。
- **错误处理**：`sandbox_job.status` ＋ `hardDeadlineAt` 判堆积（容量桶满会持续抛 `SANDBOX_CAPACITY_UNAVAILABLE`，桶内泄漏表现为永不放行）；Runner 侧日志与 `XPERT_NSJAIL_REAPER_INTERVAL_SECONDS` 判运行时泄漏（空闲 2h／硬租约 24h，`MAX_RUNTIMES` 打满会让新 runtime 创建失败）；超限输出是**字面截断**（长度恰好等于上限即是它）。
- **真实代码示例**：
```http
GET  /api/health/ready                                   # ready 200 / 非 ready 503（no-store）
GET  /api/health                                         # database/storage/cache/redis 四项 up|down
GET  /api/system/runtime/restart/<restartId>             # 滚动重启进度
GET  /api/system/runtime/plugin-convergence/<generation>  # 插件代次收敛
GET  /api/artifacts/<idOrSlug>                            # 产物 404/410 判定入口
```
