## 1. 执行请求链

**准入 → 组装 → 创建 → 执行 → 回收**。`resolveConversationSandbox` = `authorizeConversation` + `resolveSandbox(ctx, true)`：准入先查 `ChatConversation`（带 `xpert` 关系），要求 `conversation.tenantId === tenantId`、助手 `features.sandbox.enabled` 为真、`features.sandbox.provider` 非空，群运行时另派 `ResolveGroupRuntimeAccessCommand`，项目会话要求 `xpertId` 且过 `assertCanUseXpert`，非项目/非群会话要求 `createdById === userId`。组装阶段（仅 `create=true`）会在助手模板含 `manifest.files` 且无项目/环境时派 `InitializeAssistantTemplateFilesCommand`；工作区由 `XpertWorkAreaResolver.resolve`（被动态带 `createDirectories: false`）给出 `volumeScope`/`workspaceBinding`/`workingDirectory`，`workFor` 由 `resolveSandboxWorkFor` 按「环境优先 → 项目 → 用户」派生。

**创建**：`SandboxAcquireBackendCommand` → `NsjailSandboxProvider.create`：读 `NSJAIL_RUNNER_URL`/`NSJAIL_RUNNER_TOKEN`（缺一抛 `NsJailRunnerNotConfigured`）→ 要求 `workspaceBinding.volumeRoot` → 取 Runner `/health`（5 秒缓存 + 同 configKey 并发合流，失败回落 `available: false`）→ 项目态校验协议 2（`projectContentReadOnly`）、所有运行时校验协议 3（`appDataProtection`）→ `runtimeId = sha256([tenantId, workFor.type, workFor.id, environmentId, workspacePath, workingDirectory, protectProjectContent]).slice(0,32)` → `POST /v1/runtimes` → 返回 `NsjailSandbox`（`id = nsjail-<runtimeId>`）。**稳定性含义**：同一 `(租户, workFor, 环境, 卷, 工作目录, 项目只读)` 重复创建收敛到同一 `runtimeId`。

**执行与回收**：`NsjailSandbox.execute`/`streamExecute` 都包在 `withRuntimeRecovery` 里；返回 `ExecuteResponse{exitCode, output, timedOut, truncated}`（流式先按 NDJSON 逐行回调再取 `result` 事件）。HTTP 侧唯一执行入口是 `POST terminal`（`@Post` + `@Sse`，30 秒 `keepAlive` 注释事件 + `takeUntilClose`），退出码非 0 走 **SSE 的 error 通道**而非 HTTP 状态码。

## 2. Runner 客户端与协议

`NsjailRunnerClient` 是**纯 HTTP 客户端**，无状态、每次请求带 `authorization: Bearer <token>`，并对手工构造的响应做字段级解析（缺字段即抛 `NsJailRunnerInvalid*`）。端点全集：`GET /health`、`POST /v1/runtimes`、`DELETE /v1/runtimes/:id`、`POST /v1/runtimes/:id/exec`、`POST .../exec/stream`、`POST .../files/upload`、`POST .../files/download`、`POST .../terminals`、`GET .../terminals/:id/events`（timeout 35s）、`POST .../input`、`POST .../resize`、`DELETE .../terminals/:id`、`POST .../services`（40s）、`GET .../services`、`GET .../services/:id/logs?tail=`、`DELETE .../services/:id`（10s）、`POST .../services/:id/proxy`（`redirect: 'manual'`、`timeoutMs: 0` 即不设超时）。

**超时对齐**：默认 10 秒；exec/stream 用 `resolveSandboxExecutionOptions(options)` 的 `timeoutMs` **加 10 秒宽限**（`RUNNER_GRACE_PERIOD_MS`）；health 用 2 秒。**错误分类三分**：`isNsjailRuntimeNotFoundError`（404 且 runnerMessage 为 `NsJail runtime not found`）→ 触发运行时重建；`isPermanentNsjailRunnerRequestError`（4xx 且非 408/429）→ 永久；`isRetryableNsjailRunnerRequestError`（408/429/5xx、`TypeError`、`NsjailRunnerTimeoutError`）→ 可重试。proxy 响应通过头 `x-xpert-nsjail-proxy-response = 1` 标记，命中时**任何状态码都不当错误**，直接回传上游响应体。

章节来源：[nsjail-runner.client.ts](file://packages/server-ai/src/sandbox/nsjail/nsjail-runner.client.ts)（关键符号：NsjailRunnerClient.execute / streamExecute / proxyService / isRetryableNsjailRunnerRequestError）、[nsjail.types.ts](file://packages/server-ai/src/sandbox/nsjail/nsjail.types.ts)（关键符号：NsjailExecutionRequest / NsjailServiceState / NsjailProxyRequest）

## 3. WS 终端

**4 类客户端消息**：`open{conversationId, projectId?, requestId, cols, rows}`、`input{sessionId, data}`、`resize{sessionId, cols, rows}`、`close{sessionId | requestId}`。**5 类服务端事件**：`opened{provider, requestId, sessionId, workingDirectory}`、`output{sessionId, data}`、`exit{sessionId, exitCode, signal}`、`error{code, message, requestId?/sessionId?}`、`closed{reason, requestId?/sessionId?}`（6 种 `reason`，11 种 `code`）。

**鉴权**：每个 handler 都挂 `@UseGuards(SandboxTerminalAuthGuard)`（逐消息重校验），`open` 另查库确认会话并复核助手作用域；失败一律 `WsException({status:403})`。**上下文回填**：WS 不经 HTTP 中间件，故 `open` 用 `runWithCapturedRequestContext` 把 `{user, headers:{'tenant-id','organization-id'}}` 手工塞进上下文再调 `resolveConversationSandbox`。**取消语义**：`registerPendingOpen(socketId, requestId)` 若发现同 `requestId` 旧对象则先置 `canceled`；解析完成、adapter 打开、pendingError 三处都检查 `canceled`，命中即关闭已建会话并静默返回。**心跳与断开清理**：网关自身**无空闲超时**，存活由 Runner 进程边界决定；`handleDisconnect` 先把该 socket 全部 pendingOpen 置 canceled，再按 `socket_disconnected` 逐个 `closeSession`（不发 `closed`）并删除 socket 表；`exit`/`error` 事件到达时会同时删表并清空空 socket。远端终端**轮询**在适配器侧：`NsjailTerminalSession.poll` 初始 100ms 指数退避到 5000ms 上限，永久错误转 `onError`。

章节来源：[sandbox-terminal.gateway.ts](file://packages/server-ai/src/sandbox/sandbox-terminal.gateway.ts)（关键符号：open / input / resize / close / handleDisconnect / registerPendingOpen）、[sandbox-terminal-auth.guard.ts](file://packages/server-ai/src/sandbox/sandbox-terminal-auth.guard.ts)（关键符号：SandboxTerminalAuthGuard.canActivate）、[sandbox-terminal.model.ts](file://packages/contracts/src/ai/sandbox-terminal.model.ts)（关键符号：SandboxTerminalClientEvent / SandboxTerminalClosedReason / SandboxTerminalErrorCode）、[nsjail-sandbox.ts](file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.ts)（关键符号：NsjailTerminalSession.poll）

## 4. 预览 proxy 3 路由与会话

**发牌**：`POST .../services/:serviceId/preview-session`（会话面与线程面各一条，`organizationId` 为必填 query）→ `SandboxPreviewSessionService.createSession(service, {secure})`：要求 `service.id`、`previewUrl` 非空且 `transportMode === 'http'`，否则抛 `PreviewUnavailable`（400）；签发 JWT 并写 cookie。**三条 `@Public()` 路由**：`@All('.../proxy')`、`@All('.../proxy/')`（均把 pathname 固定为 `/`）、`@All('.../proxy/*path')`（`/${paths.join('/')}`），三者都汇聚到同一个私有 `proxyManagedService`，并把 `originalUrl` 的 query 原样拼回 `requestPath`。

**准入**：`SandboxPreviewAuthGuard` 手工解析 `cookie` 头取 `xpert_sandbox_preview` → `verifySession`（`verify(token, JWT_SECRET, {audience})`）→ 要求票面 `conversationId`/`serviceId` 等于路由参数；无 cookie 401「Sandbox preview session is required.」，不匹配 401「invalid.」。**转发**：`proxyByConversationId` 先 `requireService` 再**每次请求** `resolveConversationSandbox`（会真正申请后端）与解析 `SandboxServiceProxyAdapter`；转发前原地替换 `headers`/`headersDistinct`/`rawHeaders` 清掉 8 类敏感头（`authorization`/`cookie`/`proxy-authorization`/`x-api-key`/`x-auth-token`/`x-client-secret`/`x-csrf-token`/`x-xsrf-token`），劫持 `response.setHeader` 丢弃 `set-cookie`/`service-worker-allowed` 并把 `location` 重写到 `/api/sandbox/conversations/<cid>/services/<sid>/proxy/`，`finally` 还原。适配器侧再有第二层头清洗（另剔 `connection`/`keep-alive`/`te`/`trailer`/`transfer-encoding`/`upgrade`/`accept-encoding`/`host`），并对 `text/html`、`text/css`、`javascript` 类响应做正文内的绝对路径重写（请求体与重写响应各 16 MB 上限）。**未支持项**：不代理 WebSocket 升级（Vite HMR 属显式范围外）。

章节来源：[sandbox-preview-session.service.ts](file://packages/server-ai/src/sandbox/sandbox-preview-session.service.ts)（关键符号：createSession / verifySession / buildCookiePath）、[sandbox-preview-auth.guard.ts](file://packages/server-ai/src/sandbox/sandbox-preview-auth.guard.ts)（关键符号：SandboxPreviewAuthGuard.canActivate）、[sandbox-managed-service.service.ts](file://packages/server-ai/src/sandbox/sandbox-managed-service.service.ts)（关键符号：proxyByConversationId / sanitizePreviewRequestHeaders）、[nsjail-sandbox.ts](file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.ts)（关键符号：proxyServiceRequest / rewritePreviewTextResponse）

## 5. volume 通配路由

`GET volume/*path` 标 `@Public()`，用途是给「不需要登录就该能看」的资源（已发布预览静态资源、运行时作业产物快照）一个直取入口。**校验链**（顺序即代码顺序）：`normalizeSandboxVolumeRequestSubpath(paths.join('/'))`（空即 400）→ 第一次 `isProtectedVolumeSubpath` → tenant 解析（query → `RequestContext.currentTenantId()` → `GetDefaultTenantQuery`）→ `assertValidVolumeScopeId` → `VolumeClient.getApiContainerSandboxVolumeRoot(tenant)` → dev 环境 `normalizeSandboxPublicVolumeSubpath` 归一 → **第二次** `isProtectedVolumeSubpath` → `serveVolumeFile(..., {rejectProtectedPaths: true})`。`serveVolumeFile` 再做 `assertPublicWorkspacePath(subpath)`、`openFileSnapshot` 后按 `openedFile.volumeRelativePath` 复检黑名单、非普通文件 404；响应支持 `Range`（206 / 416）、`download=1|true|yes` 强制 attachment、非纯文本自动挂 `Content-Disposition`。**已知风险**：匿名可读公共前缀、无审计、无限流、`tenant` 只定位卷根不构成授权。

章节来源：[sandbox.controller.ts](file://packages/server-ai/src/sandbox/sandbox.controller.ts)（关键符号：getVolumeFile / serveVolumeFile / isProtectedVolumeSubpath / normalizeSandboxVolumeRequestSubpath）

## 6. job 与容量

`SandboxJobRuntimeCapabilityService.run` 的顺序是稳定契约：`requireRunnableAction`（动作存在性、版本兼容、`scope.tenantId` 必须等于当前租户、`idempotencyKey`/`outputs`/输入文件校验；错误码 `SANDBOX_ACTION_INVALID|UNAVAILABLE`、`SANDBOX_PROFILE_UNAVAILABLE`、`SANDBOX_VERSION_MISMATCH`、`EXPORT_INPUT_INVALID`）→ `findIdempotent(tenantId, idempotencyKey)` → 命中 `succeeded` 直接 `toSucceeded`，命中活跃态走 `waitForAttachedJob`（500ms 轮询，`waiting` 时重置 deadline，超时抛 `EXPORT_TIMEOUT` retryable）→ `cleanupPending` 时 `requirePreviousAttemptCleanup` → `bindingSelector.require(definition, jobId, {readOnlyFileMounts})` → `prepareAttempt`（写 `waiting`、`attempt+1`、初始 `hardDeadlineAt = now + 120s`；唯一索引冲突则回查转附着）→ `waitForCapacity` → `execute` → `finally capacity.release`。

**三桶租约**：`SandboxJobCapacityService` 的 Lua 脚本逐桶 `ZREMRANGEBYSCORE` 清过期后 `ZCARD` 比限（`SANDBOX_JOB_GLOBAL_LIMIT` 20 / `TENANT_LIMIT` 4 / `USER_LIMIT` 2，匿名作业无 user 桶），全部满足才 `ZADD` + `PEXPIRE`；租约时长 = `definition.hardDeadlineMs + 60_000`。`waitForCapacity` 在桶满时每 30 秒把作业心跳回写为 `waiting` 并把 `hardDeadlineAt` 续期 120 秒，同时每 `capacityPollInterval()` 重试；发现作业被取消/丢失立刻抛 `SANDBOX_CANCELLED`/`SANDBOX_START_FAILED`。

**执行期**：`execute` 先 `volumeClient.resolve({catalog:'runtime-jobs', jobId}).ensureRoot()`，把卷内 `workspace/` 作为运行时卷根（`serverRoot` 与 `hostRoot` 同步推导），`createOptions` 标 `ephemeral: true`、`workFor: {type:'job', id: jobId}`，随后 `runtimeRef = runtime.id`、`cleanupPending = true`、`status = 'running'`；有效超时取 `min(normalizeTimeout(input.timeoutMs, definition.timeoutMs), definition.hardDeadlineMs)`。**定义与绑定**：`SandboxRuntimeDefinitionRegistry` 启动时加载 7 个 JSON 定义（`browser/playwright-1.61/v1`、`browser/ai-playwright-1.61/v1`、`browser/video-playwright-1.61/v1`、`document/libreoffice-v1`、`document/node-20/v1`、`document/java-17/v1`、`document/python-3.12/v1`），逐字段白名单校验、强制 `timeoutMs ≤ hardDeadlineMs`、`security` 必须为硬化四件套、`networkPolicy.mode ∈ none|internal-only`；`SandboxRuntimeBindingSelector.inspect` 按「profile 名 + provider 类型 + 能力满足 + 只读挂载需求 + 产物可接受」过滤候补，按 `priority → provider.type → binding.id` 排序后**逐个探测健康**，`require` 把失败归一为 `SANDBOX_RUNTIME_UNAVAILABLE`（retryable=false）与 `SANDBOX_START_FAILED`（retryable=true）；生产环境 `oci-image` 必须 `@sha256:` 摘要钉住。`SandboxRuntimeHealthService` 每 15 秒探测全部定义并把记录写入 Redis hash（`sandbox_runtime:{health}:<profile>`，TTL 90 秒，失败态只缓存 5 秒），`onModuleDestroy` 经 `runShutdownStep('sandbox-runtime.unregister')` 注销自己的 executorId 字段。

章节来源：[sandbox-job-runtime-capability.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job-runtime-capability.service.ts)（关键符号：run / waitForCapacity / execute / waitForAttachedJob / prepareAttempt）、[sandbox-job-capacity.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job-capacity.service.ts)（关键符号：ACQUIRE_SCRIPT / acquire）、[sandbox-runtime-definition.registry.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-runtime-definition.registry.ts)（关键符号：parseDefinition / requireManifestValue）、[sandbox-runtime-binding-selector.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-runtime-binding-selector.service.ts)（关键符号：inspect / require / isArtifactAllowed）、[sandbox-runtime-health.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-runtime-health.service.ts)（关键符号：refreshAll / publish / onModuleDestroy）

## 7. managed service

**台账**：`sandbox_managed_service` 一行一服务，`(conversationId, name)` 唯一，FK 到 `ChatConversation` 且 `onDelete: 'CASCADE'`。`startByConversationId` 先 `resolveConversationSandbox`（**会创建沙箱**）与 `resolveSandboxManagedServiceAdapter`；同名已存在且未带 `replaceExisting` → 409 `ServiceNameConflict`，带 `replaceExisting` 则先 `stopService` 再复用同一行；实体写入 `status='starting'`、`requestedPort`/`actualPort`、`transportMode = port ? 'http' : 'none'`、`metadata.launch`（env/readyPattern）与 `metadata.logs`（`<workingDirectory>/.xpert/managed-services/<serviceId>/{stdout,stderr}.log`）；适配器 `startService` 通过 `onStateChange` 回调把 `starting → running|failed` 落库（失败还写 `metadata.error` 并抛 `ServiceStartFailed` 400）。**被动发现**：列表/查询类走 `findExistingSandbox`，解析不到时把 `running|starting|stopping` 降级为 `lost` 且 `previewUrl = null`；适配器 `listServices` 在 Runner 报 runtime-not-found 时同样把活跃态标 `lost`（注释逐字「Passive discovery must not resurrect a runtime that has already stopped.」）。**`onModuleInit` 修复**：把库里残留的 `running`/`starting` 全量置 `lost` + `stoppedAt`。**previewUrl 派生**：仅 `running` + `transportMode==='http'` 才生成 `/api/sandbox/conversations/<cid>/services/<sid>/proxy[/<previewPath>]`，这是 proxy 与 `preview-session` 的共同前提。

## 9. 清理与泄漏防护

**运行时自愈**：`NsjailSandbox.withRuntimeRecovery` 捕获 `isNsjailRuntimeNotFoundError` → `recreateRuntime(generation)`（按 generation 去重并发重建，成功后 `runtimeGeneration += 1`）→ **重试一次**原操作；其它错误一律上抛，不吞。**孤儿扫描**（API 侧）：`cleanupOrphans` 每 60 秒扫两批——(a) 活跃态且 `hardDeadlineAt < now` → 置 `lost` + `SANDBOX_START_FAILED` + `finishedAt`，再 `destroySandbox`，成功才 `cleanupVolume`；(b) `cleanupPending = true` 且**终态** → 同样销毁与清卷。`destroySandbox` 无 `runtimeRef` 与 provider 时直接清 `cleanupPending` 并写 `cleanedAt`；有 ref 无 provider 时保持 pending 并告警；销毁失败同样保持 pending。**进程内状态**：`active: Map<jobId, {runtime, resolution}>` 供 `cancel()` 直接 `terminate()`。**Runner 侧兜底**（外部契约）：无 API 活动 2 小时销毁、连续活跃 24 小时硬租约、`reaper` 60 秒、`MAX_RUNTIMES` 打满后新 runtime 创建失败——**API 挂掉期间只能靠它收敛**。**WS/预览侧**：断连逐个关终端；预览 cookie 1 小时自然过期；托管服务靠 `onModuleInit` 的 `lost` 修复。

## 11. 热点路径

1. **`resolveConversationSandbox`**：卷路由、上传、SSE、托管服务 14 条、3 条 proxy、WS `open` 全部先走它；proxy **每次请求**都解析一次（会查会话 + 可能申请运行时），是「dev server 托管在沙箱内」场景的第一成本项。
2. **`waitForCapacity` 与 `waitForAttachedJob`**：桶满时请求在拿到 lease 前长时间挂住（30 秒心跳续期 + 轮询），附着等待按 `hardDeadlineMs` 上限；两者都是**长事务内的忙等**。
3. **终端轮询**：每个终端一条 `NsjailTerminalSession.poll` 循环（`pollTerminal` timeout 35 秒），长连接终端按终端数占用 API I/O。
4. **卷投递**：每次 `openFileSnapshot` + `fstat` + 可能的 Range 流；公共前缀无限流门。
5. **作业输入物化**：输入快照落 `.platform/inputs`（1 MB 缓冲复制），单作业输入/输出各 350 MB 上限，是内存与磁盘峰值来源。
6. **`SandboxRuntimeHealthService.refreshAll`**：每 15 秒遍历全部定义并逐候补 `getBindingHealth`，`pendingProbes` 去重、失败 5 秒短缓存。

## 13. 技术债与 hack

1. **`cleanCron` 是空壳**：`@Cron('0 0 * * * *')` 却只 `logger.debug('Called when the current second is 45')`，表达式与文案互相矛盾；真实回收只靠 `cleanupOrphans` 与 Runner TTL。证据：[sandbox.service.ts](file://packages/server-ai/src/sandbox/sandbox.service.ts)。
2. **`containerRef` 已废弃**：实体注释逐字 `@deprecated Read-only compatibility evidence. New attempts write runtimeRef.`，读侧（`destroySandbox`/`toSnapshot`）仍做双字段兼容。证据：[sandbox-job.entity.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job.entity.ts)。
3. **cookie 手工解析重复**：`SandboxPreviewAuthGuard`（`headers.cookie`）、终端（走 `handshake.auth.token`）各写一遍取值逻辑，且 `WorkspaceFileAccessGuard`（③）还有一份，语义一致但实现分散。
4. **`queries/index.ts` 为空**：控制器却注入 `queryBus` 并在卷通配里执行 `GetDefaultTenantQuery`，本子域查询 handler 未落地。
5. **`POST terminal` + `@Sse()` 组合**：同一路由挂 `@Post('terminal')`、`@Header('content-type','text/event-stream')` 与 `@Sse()`，属非标准用法，客户端必须按 POST + SSE 解析。
6. **`client.ts` 的遗留 `SandboxFileSystem`**：打 `${sandboxUrl}/file/`、`/shell/exec/`、`/python/exec/`、`/browser/`，其服务端对手方在本仓扫描范围内未找到，属悬空兼容层。
7. **`[推测]` 三桶计数泄漏不可自愈**：`acquire` 成功但进程在 `release` 前被杀时，租约只能等 ZSET 分数过期；由于 `PEXPIRE = expires - now + 60000`，桶本身会过期，因此**理论上自愈**，但「桶内残留到过期前持续拒绝」的行为未做运行时验证。
8. **`[推测]` 附着等待的跨进程语义**：`run()` 命中活跃态即附着，文档化路径是「同一 API 进程内的并发调用」；跨副本/进程重启后的重新附着未在专项用例中取证。
9. **`[推测]` 卷通配的符号链接防护完备性**：护栏是「打开后按实际相对路径复检」，但 `openFileSnapshot` 之外是否还有其它别名通道（如硬链接指向受保护 inode）未逐项验证。

## 14. 设计维度分析

**隔离强度 vs 开发便利**：生产侧把「不可信」压到唯一特权组件——Runner 侧独立进程边界（namespace + 只读 rootfs + `NO_NEW_PRIVS` + capability dropping + seccomp + cgroup v2），API 侧不暴露任何「自选挂载/宿主 PID/NsJail 参数/可执行文件」的入参；代价是协议版本成为升级瓶颈（协议 2/3 是硬门槛，Runner 降级会让 `create()` 全量失败）。开发侧（`LocalBrowserRuntimeProvider`）直接跑本机进程，模块用 `isDevelopmentSandboxRuntimeEnvironment()` 三元决定是否注入，注释强调「never a production fallback」——两种隔离度共享同一套 provider 抽象与同一批工具中间件。

**超时归属的三层分工**：① **作业层**用 `hardDeadlineAt` + 三桶租约表达「谁有权跑、最多跑多久」（权威在数据库与 Redis）；② **注册表层**用 `timeoutMs ≤ hardDeadlineMs` 把「软上限不得超过硬截止」变成**加载期校验**（配置错误启动即暴露，而非运行期）；③ **Runner 层**用 `MAX_EXECUTIONS_PER_RUNTIME`/`MAX_TERMINALS_PER_RUNTIME`/`MAX_SERVICES_PER_RUNTIME`/`MAX_PROXIES_PER_RUNTIME` 与 `MAX_RUNTIMES` 做最后一道准入，并对每个 jail 施加内存/swap/CPU/PID/rlimit 上限。三层各自 fail-closed，且**任一层超限都不表现为 HTTP 码**——作业侧是 `errorCode` 与状态，Runner 侧是请求被拒。

**授权面的四种粒度**：全局守卫兜底（除 `@Public()`）、方法级 `@Public()` + 自定义 cookie guard（3 条 proxy）、`@UseGuards` 逐消息（WS 终端）、**纯路径护栏**（volume 通配）。第四种是唯一「跳过 JWT 且不补身份」的形态，故只能靠「公共前缀不含敏感数据」的部署假设成立；审计「谁能读」时必须同时看全局守卫、方法装饰器、自定义 guard 与路由形态四处。

## 15. 结论

本子域的实现主线是「**把不确定的东西全部推到可枚举的状态与可复核的失败**」：执行层面用稳定 `runtimeId` + `withRuntimeRecovery` 换取「同一工作区重复命令不换身份、运行时被回收可自愈」；作业层面用唯一幂等键 + 三桶租约 + 硬截止 + 60 秒孤儿扫描换取「重试安全、并发可控、崩溃可收敛」；交互层面用「进程内会话表 + 逐消息重鉴权 + pending 取消」换取终端可用性与最小状态面；预览层面用「签名 cookie + 双层头清洗 + 正文路径重写」换取「iframe 直连但不泄平台凭证」；投递层面用「两次黑名单 + 打开后复检」换取匿名只读面的最小暴露。

改动前必须同时确认四件事：① 新入口是否经过 `resolveConversationSandbox`（否则绕过准入）；② 是否扩大了 volume 通配或 `@Public()` 面（这是本子域唯一无身份补位的路径）；③ 超时/取消是否仍落在 `hardDeadlineAt` + `cleanupPending` 这套证据链上（`requirePreviousAttemptCleanup` 会拦住后续尝试）；④ 是否新增了跨子域共享文件的第二职责（`sandbox.controller`/`sandbox-job.*`/`sandbox-*.model.ts`）。命令面的正确姿态是「控制器只发命令、服务只落证据、Runner 只做边界」。
