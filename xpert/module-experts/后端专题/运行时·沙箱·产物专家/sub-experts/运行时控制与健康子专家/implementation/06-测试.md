| # | spec | 顶层 describe | 一句话 |
|---|---|---|---|
| 1 | `runtime-control.controller.spec.ts` | `Runtime control HTTP boundary` | 反射断言类级保留 `TenantPermissionGuard` 且 `listInstances`/`retireInstance`/`restart` 带 `RoleGuard`，并起真实 Nest 应用（守卫被 override 为放行）在 HTTP 边界校验 `allowDowntime` 不被默认打开、非法 body 400、`expectedBootId` 与审计 `sourceIp` 正确透传 |
| 2 | `runtime-control.service.spec.ts` | `RuntimeControlService` | 用 mock 协调器 ＋ 打桩 `RequestContext`/`setDefaultTenantId` 验证：默认租户超管可重启、`allowDowntime` 不绕过授权（api-key/普通用户/异租户三态 × 重启与退役）、`restartCapability()` 的 `allowed`、状态缺失时 404、代次状态按 generation 读取 |
| 3 | `runtime-lifecycle.service.spec.ts` | `RuntimeLifecycleService` | 每次 boot 生成不同 `instanceId`；`trackRequest` 计数与 `waitForIdle` 在请求结束后立即返回；活跃请求不结束时按超时返回 false |
| 4 | `runtime-plugin-admission.spec.ts` | `RuntimePluginAdmission` | 准入闸门：候选失败时既有健康副本继续服务、回归旧 boot 被围栏到与期望代次一致、必须 listening ＋ 稳定 ≥3s 才落盘已知良好启动、租约丢失/校验窗口过期（含 Redis 挂起）即关就绪、延迟回复跨过租约不保留旧准入、仅在代次 failed 后允许验证过的回滚 |
| 5 | `runtime-restart-coordinator.service.spec.ts` | `RuntimeRestartCoordinatorService` | 编排状态机主用例集（本子域最大 spec）：延迟确认不得覆盖失败/换操作、未就绪注册被排除且 bootstrap 后追平、历史过期的晚到副本追平、退役后保留快照且失败需显式重试、一个不响应成员不拖垮可响应副本、catch-up 与完成结果之间的原子性、failed 代次历史过期后仍封锁、离线历史在 catch-up 中被忽略、卸载后期望清单被替换且正确卸载的新副本保持在线 |
| 6 | `runtime-rollout-regressions.spec.ts` | `Plugin rollout availability regressions` | 回归集：显式同意才允许单副本中断、上一次操作的中断同意不得传给排队中的自动变更、drain 期间健康对等副本消失则取消终止、当前代次候补在更新插件排队时仍被准入并最终完成两轮 rollout、候补缺一项未变插件或存在无关陈旧 boot 时不被准入、每代次保留不可变累积清单 |

| 10 | `runtime-queue-shutdown.service.spec.ts` | `RuntimeQueueShutdownService` | 用 `DiscoveryModule` 注入真实 `Bull` 替身：停等卡住的 job 后强制关闭 worker、空闲队列保持可写直到其它队列排空、公共宽限期结束前保持所有生产者打开、两种 Nest 队列类型都能发现且只排水一次并用本地强制关闭 |

## §4 缺口

1. **`health/**` 零测试（5 文件 / 0 spec）**：`HealthController.check` 的四项聚合、`checkDb`/`checkStorage`/`checkCache`/`checkRedis` 开关、DB 与磁盘异常被吞成 `status:'down'` 的语义、`/health/ready` 的 503 与 `Cache-Control: no-store` 全无自动化验证；两个指示器（`CacheHealthIndicator` 依赖 `CACHE_MANAGER`、`RedisHealthIndicator` 自建客户端且 `stopRedis` 无调用点）同样没有 spec。
2. **`RuntimeDrainMiddleware` 本体没有独立 spec**：它只在 `runtime-shutdown.spec.ts` 的真实进程夹具里被间接覆盖（`app.use(...)`），因此「503 body 的 `errorCode` 选择」「`Retry-After: 5`/`Connection: close` 头」「`/health` 正则的豁免边界（含误伤面）」都没有直接断言。
3. **纯函数策略模块没有单元 spec**：`runtime-rollout-policy.ts`（`replacementAdmission` 的三种返回条件）、`runtime-restart-deadlines.ts`（`operationDeadlineAt`/`operationStateTtlSeconds`/`restartStatus`）、`plugin-runtime-requirements.ts`（`absent`/`failure`/版本与 revision 不一致的分支）、`plugin-convergence-capacity.ts`（`awaiting_restart` 触发条件）目前只被高层的协调器/回归 spec 间接覆盖，边界分支（如 `absent` 状态命中失败记录）缺少直测。
4. **无多副本端到端**：`FakeRedis` 是进程内替身，无法证伪「各副本不共享同一 Redis」这类真实部署错误；也没有并发两个 `POST /restart` 的竞态用例（409 路径只在服务层 mock 层面出现）。
5. **无 6 端点的鉴权矩阵用例**：`runtime-control.controller.spec.ts` 把 `TenantPermissionGuard`/`RoleGuard` override 成放行，只断言装饰器元数据存在；**「3 条读端点缺 `RoleGuard` 且服务层无断言」这一实测事实没有测试钉住**（也没有用例证明普通登录者可读到状态）。
6. **`enableRuntimeShutdown` 的生产接线无测试**：`bootstrap/index.ts` 未调用它，因此没有 spec 能证明生产关停链真的会跑；夹具中的 `beforeClose` 与 `timeoutMs` 都是测试自造。
7. **无「探针可用 ≠ 接业务流量」的端到端断言**：drain 期间 `/health*` 放行与业务 503 的对照目前只靠代码阅读，`healthcheck.cjs` 也没有对应的自动化用例。
8. **`[推测]` 缺失的性能回归**：`GET /api/health` 每次 `userRepository.count()` 全表计数、协调器 1 秒轮询的 Redis 负载，都没有基准或压测用例。

## §5 结论

`runtime-control` 的测试密度在本专家域里偏高：10 个 spec 覆盖了「HTTP 边界 ＋ 服务层三重断言 ＋ 生命周期计数 ＋ 准入闸门 ＋ 编排状态机 ＋ 回归集 ＋ 关停三件套（prepare/step/queue）」，并且用**内存 `FakeRedis` ＋ 真实子进程夹具**两种非常规手段把「多副本共识」与「信号/SSE 时序」这两类最难测的东西拉进了自动化。代价是：真实 Redis、真实队列、真实 PostgreSQL 一律不进测试，正确性依赖「替身行为与真实实现同构」这一假设。

`health/**` 是明确的空洞：5 个生产文件、0 个 spec，却决定编排层是否重启实例；`RuntimeDrainMiddleware` 的 503 出口也只在真实进程夹具里被顺带走过。**最值得补的三条**：① `health.controller.spec.ts`——四项聚合的成功/降级/异常吞没三条路径 ＋ `readiness` 的 503/`no-store` 断言；② `runtime-drain.middleware.spec.ts`——`null` 分支的 `errorCode` 选择、响应头、`/health` 正则边界（含误伤路径）；③ `runtime-control.controller.spec.ts` 增加**未 override 守卫**的鉴权矩阵用例，把「3 条读端点只有租户门禁」写成可执行的期望而不是文档里的一句话。
