## §1 RuntimeControlService 的方法族

`RuntimeControlService` 是 6 端点的直接服务，字段只有 `mode = 'rolling-self-signal'` 与两个依赖（`RuntimeRestartCoordinatorService`、`InstanceRegistryService` 的 3 个方法的 `Pick`）。

| 方法（方法族） | 行为 | 失败面 |
|---|---|---|
| `listInstances()` | 断言 → `instances.getRegisteredInstanceDetails()` | 403 三兄弟 |
| `retireInstance(instanceId, dto, {sourceIp})` | 断言 → `instances.retireInstance(instanceId, expectedBootId)` → 结构化审计（`event:'runtime.instance.retirement'` ＋ actor/tenant/sourceIp） | 403；`expectedBootId` 不匹配时返回 `boot-changed` 而非抛错 |
| `restartCapability()` | **纯返回、不抛**：`currentApiKey()` → `interactive-auth-required`；无 `SUPER_ADMIN` → `super-admin-required`；`getDefaultTenantId()` 为空或租户不等 → `default-tenant-required`；否则 `allowed` | 无异常路径 |
| `requestRestart(input, audit)` | 断言 → 校验 `confirmation === RUNTIME_RESTART_CONFIRMATION` → `coordinator.requestRestart({source:'interactive', allowDowntime?, reason?.trim(), actorUserId, tenantId, sourceIp, runtimeRequirements})` | 400 `RUNTIME_RESTART_CONFIRMATION_REQUIRED`；409/503 由协调器抛出 |
| `restartStatus(restartId)` | `coordinator.getStatus()`，空则 404 | 404 `RUNTIME_RESTART_NOT_FOUND`；**未做身份断言** |
| `pluginConvergenceStatus(generation)` | `coordinator.getPluginConvergenceStatus()`，空则 404 | 404 `PLUGIN_RUNTIME_CONVERGENCE_NOT_FOUND`；**未做身份断言** |
| `recordPluginRuntimeChange(input)` / `recordPluginRuntimeRequirements(requirements, reason)` | 直接转发到协调器（**无身份断言**，供插件域内部调用） | 由协调器返回 `scheduled:false, generation:0` 或抛错 |
| `assertAuthorizedActor()`（private） | 读 `restartCapability().reason` 并把三种原因映射为 403 + 明确 `errorCode` | 见 §1 表上行 |

**实测门禁差异**：装饰器层 `GET instances`/`POST retire`/`POST restart` 带 `RoleGuard`＋`@Roles(SUPER_ADMIN)`；`restart-capability`/`restart/:restartId`/`plugin-convergence/:generation` **只有类级 `TenantPermissionGuard`**。服务层断言只在 `listInstances`/`retireInstance`/`requestRestart` 出现，读状态的两条方法既不抛错也不自检。

## §2 runtime-drain.middleware 的实现与生效路径

**实现**（40 行内）：构造函数注入 `RuntimeLifecycleService`。`use(request, response, next)` 的判定顺序是——① `isHealthRequest(request)` 为真直接 `next()`；② `const release = this.lifecycle.trackRequest()`，返回 `null` 则写 `Retry-After: 5`、`Connection: close`、`status(503).json({statusCode:503, errorCode, message})` 并 **`return`（不调 next）**；③ 成功则 `response.once('finish', release)` 与 `response.once('close', release)` 后 `next()`。`isHealthRequest` 取 `(request.originalUrl || request.url).split('?')[0]` 并用 `/\/health(?:\/|$)/` 正则——**它匹配任何以 `/health` 结尾或以 `/health/` 开头的路径段**，而不只是 `/api/health`。

**生效路径**：`RuntimeControlModule.configure(consumer)` 里 `consumer.apply(RuntimeDrainMiddleware).forRoutes('*')`，模块由 `server.module.ts` 导入，因此**全局生效**（测试夹具走 `app.use(drainMiddleware.use.bind(drainMiddleware))` 的等价形态）。`errorCode` 取值逻辑：`readiness().status === 'draining'` → `RUNTIME_DRAINING`；否则 `RUNTIME_NOT_READY`（即 `readinessGuard()` 为假导致的 `unready`）。`trackRequest()` 的 `null` 有两个来源：`drainState` 非空，或 `readinessGuard()` 为假——后者由 `RuntimePluginAdmission` 构造时 `lifecycle.setReadinessGuard(...)` 写入（插件启动监听位 ＋ 准入位 ＋ 5 秒校验窗口 ＋ 注册租约）。

**与 `trackRequest` 释放的协作**：释放闭包内部 `released` 标志保证 `finish`/`close` 双触发只减一次；计数归零时唤醒全部 `idleWaiters`。**SSE 类长连接会被算作在途请求**，这是「排空要等 `activeRequests === 0`，故需要 30 s 上限 + `forceCloseConnections`」的由来。

## §3 滚动重启的实现细节

**信号与进程模型（不是容器、不是集群 API）**：`runtime-control.module.ts` 顶部注释把前提钉死——生产 API 跑在 Docker 内的 PM2 下，模块一次只信号一个副本，由进程监管者拉起替代进程；本地开发必须走 nodemon 之类的 watcher。`RUNTIME_PROCESS_SIGNALER` 用 `useValue` 注入的实现体是 `signal: (signal) => process.kill(process.pid, signal)`——**自己给自己发 `SIGTERM`**，生命周期只有 `'SIGTERM'` 一个取值。

**编排状态机（协调器，1 秒轮询 ＋ Pub/Sub 唤醒）**：`requestRestart` 分支为「带 `runtimeRequirements` → 先发布代次再确保 rollout 起」与「普通请求 → 查 `ACTIVE_RESTART_KEY`，有则 409，无则 `startOperation`」。`startOperation` → `prepareOperation`（`randomUUID()` 作 restartId、快照 `getReadyInstances()` 逐副本 `initialize` 目标行、`EXPIRE` 目标表）→ 写元数据 → 抢锁（普通操作 `SET NX PX 15min`；`plugin-catch-up` 走 `claimCatchUp`，要求期望清单处于 `completed` 且代次一致）→ `activateOperation`（审计 `runtime.restart.requested`、逐代次写 `in_progress`、重算 `deadlineAt = ceil(副本数/1) × 300 s + 30 s`、`phase='rolling'`、`preparing=false`、延长活动锁、发布事件）。每个 tick 依次检查：`preparing` 超期 → failed；`phase==='collecting'` → `finalizeRegistration`（注册锁 ＋ 补齐参与者 ＋ 重新算期限）；本副本目标 `pending` 且 `expectedBootId` 未变 → 回填 `observedBootId`；**`PENDING_TARGET_TIMEOUT_MS = 45 s` 未确认** → `Replica X disappeared before restart` → 失败并终止操作；`restarting` 超 `REPLICA_RESTART_TIMEOUT_MS = 300 s` → `did not return after restart`；全 completed → finished；超 `deadlineAt` → failed。

**候选副本执行段**：`beginReplicaRestart` 要求 `admission.isStable()`（ready 且 ready 持续 ≥3 s）、抢唯一重启槽、复核「`allowDowntime` 或仍有别的健康副本」、`preparePluginStartupRetry()`、把目标写 `restarting`（Lua 比较写）→ `lifecycle.beginDrain({restartId, requestedAt})`（单例，返回 false 即回滚目标并释放槽）→ `setReady(false)` → `setTimeout(candidate → terminateAfterDrain, 750 ms)`（`unref`）。`terminateAfterDrain` 再 `waitForIdle(30_000)`，复核活动键未变/无失败目标/仍有健康对等副本，写审计 `runtime.restart.replica-signaling`，最后 `processSignaler.signal('SIGTERM')`；任一步失败即 `cancelDrain` ＋ `failTarget` ＋ `finishOperation('failed')`。

**恢复与交接**：新进程 bootId 变了 → 同 tick 内先查 `getPluginStartupFailure()`，再做 `evaluateRuntimeRequirements`（优先用操作冻结的 `admissionRequirements`），`waiting` 就等、`failed` 就失败、`satisfied` 且 `isStable()` 才 `completeTarget('replacement-ready')`（写 `acknowledgedBootId`、释放槽、审计、广播）。**同一操作内出现更新代次**时不另起操作，而是 `finishOperation` 里探测 `currentGeneration > metadata.pluginGeneration`，用 `plugin-follow-up` 造后继操作并以 `TRANSITION_ACTIVE_RESTART_SCRIPT` **原子交棒**（返回 `generation-changed` 则重试、`lost` 则退出）；失败则把 `pluginGeneration + 1..current` 全部标 failed，造成「失败代次必须显式新代次才解封」。`awaitPluginRestartApproval` 处理「只剩 1 个健康副本且需求未满足」：不自动重启，而是把代次写成 `awaiting_restart` 等运维显式 `allowDowntime`。

**关停预算（进程侧）**：`enableRuntimeShutdown(app, {beforeClose, timeoutMs, signals})` 覆盖 Nest 自带的 `enableShutdownHooks` 无界监听——它安装 `ShutdownSignal` 全集监听，`shutdown()` 幂等（`closing` promise）、装**一个** `RUNTIME_SHUTDOWN_TIMEOUT_MS = 30_000` 看门狗（`unref`）、超时用 `writeSync(2, …deadline-exceeded, pendingSteps…)` 再 `process.exit(1)`；`beforeClose` 返回非 `completed` 就直接 `finish(1)`（**绝不在未完成的 prepare 之下销毁依赖**）；`app.close(signal)` 之后再 `process.exit(status === 'completed' ? 0 : 1)`。`prepareApiShutdown` = `beginDrain({restartId:'process-shutdown'})` → `waitForIdle(10_000)` → `queues.close()`；`RuntimeQueueShutdownService.close()` 用 `DiscoveryService` 按实例身份去重发现 `Bull`（`pause(true)`/`close(true)`）与 `WorkerHost`（`worker.pause()`/`worker.close(true)`），`drainShutdownQueues` 对每个队列 `runShutdownStep(…, timeoutMs = 10_000)` 并在全部排水后加一道 barrier 再 close；`runShutdownStep` 默认 3 s 超时、返回 `completed|failed|timed_out`，`pendingShutdownSteps()` 为超时报告提供当时仍挂起的步骤名。

`[推测]` 生产里没有调用点：全仓 `packages/` 内 `enableRuntimeShutdown` 只出现在自身定义与 `runtime-shutdown.spec.ts` 经 `fixtures/shutdown-process.cjs` 的调用；`bootstrap/index.ts` 只做 `app.use(helmet())`、`setGlobalPrefix`、`app.listen`，`BootstrapModule.onApplicationShutdown` 只打日志。因此「SIGTERM → 排空 → 队列 close → exit」链的实际接线在仓库外。

## §4 插件收敛的实现

**发布（原子冻结清单）**：`PluginRuntimeGenerationStore.publish` 依 `PUBLISH_PLUGIN_GENERATION_SCRIPT`——`INCR` 代次键 → 把 `change` 写入 `:gen:change` → 写 `:gen:status`（`in_progress`）→ 逐条需求 `HSET` 进 `DESIRED_PLUGINS_KEY` → **把整份期望清单快照到 `:gen:requirements`**。快照是准入的关键：`mergeRuntimeRequirements` 以 `scopeKey\u0000pluginName` 为键去重，`createRestartMetadata` 把「交互式需求 ＋ 各排队代次需求」合并成 `runtimeRequirements`，并以 `readRequirements(generation)` 冻结 `admissionRequirements`——注释明写「Full desired manifest at this operation's generation, never a later queued generation」。

**状态与读写口径**：`writeState` 走 `WRITE_GENERATION_STATE_SCRIPT`，当传入 `restartId` 时要求活动锁属于它，且**拒绝对当前代次的 `failed` 状态做覆盖**（「A failed generation stays blocked until a new generation is explicitly published」）；`readDesired` 一次 `HGETALL` 得到原子快照，`generation`/`status` 与插件条目分离，历史过期后 fail-closed 取 `failed`；`readPending` 从当前代次向前回溯连续的 `in_progress` 段；`hasAttempted` 用 `REPLICA_ATTEMPTS_KEY`（由 `RuntimeRestartTargetStore.update` 的 Lua 顺带写入）保证每个副本每代次最多追平一次。

**准入（决定本副本是否 ready）**：`RuntimePluginAdmission.refresh(generations, rollout?)` 计算三种通过条件——`matches`（当前运行态满足期望清单）、`matchesRollout`（满足操作冻结清单，且 `desired.status==='in_progress'` 且 `desired.generation >= rollout.generation`）、`fail-open 分支`（`desired` 未完成时保持既有连接 `continuous`，或代次已 failed 且 `canRestorePluginStartup`）；然后 `ready = isPluginStartupListening() && admitted && isLeaseValid() && readiness().status !== 'draining'`，`setReady(ready, checkedUntil = now + 5 s)`；`isStable()` 要求 ready 持续 ≥3 s，稳定后才 `admitPluginStartup(state)` 把「已知良好启动」落盘。失败的候选不清空既有健康副本的准入（「keep existing healthy boots serving their previous version」），而新的/回归的 boot 会被围栏到与期望代次一致。

**收敛判定与失败面**：`evaluateRuntimeRequirements(requirements, state)` 的语义见 01-架构 §4④。失败传播到 HTTP 面只有两条：`GET /plugin-convergence/:generation` 读 `writeState` 的持久结果（`in_progress` 且承载操作 failed 时**上报 failed**），以及 `recordPluginRequirements` 在发布失败时返回 `scheduled:false, generation:0` 并打 error 日志、在 rollout 未起时打 warn「durable but its rollout has not started yet」。

## §5 健康控制器与探针实现

`HealthController`（`@Controller('health')`，前缀来自全局 `api`）构造注入 `HealthCheckService`、`TypeOrmHealthIndicator`、`DiskHealthIndicator`、两个自定义指示器、`RuntimeLifecycleService` 与 `@InjectRepository(User) userRepository`；四个开关是 `private readonly checkDb/checkStorage/checkCache/checkRedis = true`（**硬编码**），`checkDbWithTerminus = false`（注释：因 MikroORM 下 Terminus DB 检查出现过连接相关问题而默认关闭）。

| 端点 | 实现 | 语义 |
|---|---|---|
| `@Public() @Get('ready')` | `readiness()`：读 `runtimeLifecycle.readiness()`；非 `ready` 时 `response.status(503)`（`passthrough`），恒设 `Cache-Control: no-store` | **只反映本地就绪（drain / 准入 / 租约），不查任何外部依赖** |
| `@Public() @Get()` | `check()`：生成 `HealthCheckExecutionTimer-<uuid>` 并用 `console.time/timeEnd` 计时；按开关顺序 push 四个 `async () => …` 到 `checks`，最后 `health.check(checks)` | Terminus 聚合体（`info`/`error`/`details`），失败项进 `details` |

**逐项实现（按源码顺序）**：① `database`——`checkDbWithTerminus` 为真时先 `typeOrmHealthIndicator.pingCheck('database', { connection, timeout: 60000 })`（默认不走）；随后 `userRepository.count()` 真实查库并 `console.log` 计数；异常被 `catch` 成 `{database:{status:'down', message}}`；`finally` 里仅在 terminus 模式下 `queryRunner.release()`。② `storage`——`path.resolve(__dirname)` ＋ `disk.checkStorage('storage', { path, thresholdPercent: 99.999999 })`；异常同样被吞成 `{disk:{status:'down', message}}`。③ `cache`——`cacheHealthIndicator.isHealthy('cache')`：`cacheManager.set('health-check-'+uuid, 'health', 60_000)` 后 `get` 比对，成功 `getStatus`，失败抛 `HealthCheckError`（并附 `cacheType: REDIS_ENABLED==='true' ? ## §7 设计模式与热点路径

**设计模式**：① **端口/可替换依赖注入**——`RUNTIME_PROCESS_SIGNALER`（symbol token ＋ `useValue` 默认实现）让「自信号」在测试里可替换；② **策略层纯函数化**——`runtime-rollout-policy.ts` / `runtime-restart-deadlines.ts` / `plugin-runtime-requirements.ts` / `plugin-convergence-capacity.ts` 均为无状态函数，状态机只做编排；③ **存储封装（Repository 模式）**——`RuntimeRestartTargetStore` / `PluginRuntimeGenerationStore` 把键布局与 Lua 脚本包起来；④ **Lua 比较写（CAS）**——目标转移、锁释放/续期、活动操作交棒、代次状态写入全部条件化，避免过期轮询覆盖新状态；⑤ **双通道协调**——Pub/Sub 唤醒 ＋ 1 s 轮询兜底（`duplicate()` 不可用时纯轮询）；⑥ **围栏 + 准入开关**——`refresh()` 一个方法同时决定「接不接流量」与「是否落盘已知良好启动」；⑦ **哨兵值与逐步超时**——`runShutdownStep` 的 `completed|failed|timed_out` 三态避免 `Promise.race` 的未处理拒绝；⑧ **单例守卫**——`beginDrain` 只成功一次、`RuntimeQueueShutdownService.closing` 与协调器 `processing` 防重入。

**热点路径**：① 每个请求过 `RuntimeDrainMiddleware`（两次 `readiness()` 调用只发生在 503 分支，正常分支是「正则 + 计数 + 两个 once 监听」）；② 协调器 **1 秒一次 tick**（`COORDINATOR_POLL_MS`，`unref`），每 tick 至少 `get(ACTIVE_RESTART_KEY)` ＋ `readDesired()`（`HGETALL`）＋ 可能的 `readMetadata`/`read targets`；③ `GET /api/health` 每次 `userRepository.count()`（全表计数）＋ 缓存 set/get；④ 重启时每副本一次 `waitForIdle(30 s)` 的阻塞式等待；⑤ 队列排水按队列数并发但共用 10 s 宽限。

## §9 技术债与 hack

1. **只读端点无装饰器级 `RoleGuard`**（`restart-capability`/`restart/:restartId`/`plugin-convergence/:generation`），保护完全来自类级租户门禁；`restartStatus` 与 `pluginConvergenceStatus` 连服务层 `assertAuthorizedActor()` 都没有调用——**状态枚举面对任何通过租户权限的登录者开放**。
2. **`enableRuntimeShutdown` 无生产调用点**：`bootstrap/index.ts` 只 `app.listen`，`BootstrapModule.onApplicationShutdown` 只打日志；该 helper 与 `prepareApiShutdown`/`runShutdownStep` 目前只被 `runtime-shutdown.spec.ts` 经 `fixtures/shutdown-process.cjs` 驱动。`[推测]` 生产关停在仓库外的入口/编排里另行接线，否则排空与队列关停不会执行。
3. **`process.kill(process.pid, signal)`**：信号只对自己发，语义完全外挂于监管者；本地 nodemon 下「重启」只是 watcher 重拉（模块头注释明示）。
4. **`restartCapability()` 在中间件路径里被 `readiness()` 之外的调用混用**：`assertAuthorizedActor()` 每次都用「构造一个 capability 再读 reason 字符串」的方式做判定，三处 403 分支靠字符串比较（`'interactive-auth-required'` 等），改枚举即静默失效。
5. **`Retry-After` 固定 5 秒**，而实际 drain 上限是 30 s：客户端按 5 s 重试时可能连续撞 503。
6. **健康检查里 Redis 客户端持有一个常驻连接**（构造函数 `startRedis()` 不 await，`stopRedis()` 带 `TODO` 且无调用点），并且启动时会 `console.log` 完整 `REDIS_URL`（含用户名口令）。
7. **`GET /api/health` 的 DB 探活是 `userRepository.count()` 全表计数**，随用户量增长成本上升；且 DB/磁盘异常被吞成 `{status:'down'}` 返回体，Terminus 整体仍是 `ok`（`[推测]` 对聚合是静默的，`healthcheck.cjs` 靠 `details[*].status` 逐项兜住）。
8. **`/\/health(?:\/|$)/` 的豁免面比预期宽**：任何末段为 `health` 的路径都会被排空中间件放行，`[推测]` 若引入同名业务路由会被静默排除出排空保护。
9. **`awaitPluginRestartApproval` 的等待是「沉默的」**：代次被写成 `awaiting_restart` 后不重试、不通知（只有代次端点可查），需要运维主动用 `allowDowntime` 触发。
10. **`checkDbWithTerminus=false`** 使 Terminus 的 ping 通道（带 60 s 超时）常闭，DB 检查只剩计数查询，连接半死时的判定能力更弱。
11. **审计只走 `logger.warn(JSON.stringify(...))`**（`writeAuditLog`），不落表、不脱敏；`retireInstance` 的审计用 `logger.log`，两类事件级别不一致。

## §10 设计维度分析

**维度一：控制面「决策 / 执行」分离的彻底程度**。本域把「谁该动、什么时候动」放进 Redis 状态机（元数据、目标表、槽位、代次），把「怎么动」收敛为一次自信号；`allowDowntime`、`maxConcurrentRestarts=1`、最后一个健康副本需显式同意这三条把「可用性判断」从实现里抽成**显式输入**。代价是控制面无法自愈：协调器一旦失去 Redis 或活动锁，剩余副本只能持续 503（fail-closed）；收益是任何副本都能被杀而不丢编排进度（每个 tick 都从 Redis 重读，不依赖内存游标）。

**维度二：健康语义的「分层与豁免」**。两条探针分工明确——`/health/ready` 只谈本地就绪（drain、准入、租约），`/health` 谈外部依赖体检；排空中间件只豁免 `/health*`，因此 drain 期间「探针绿、业务红」是可观测的稳定状态。这套分层的代价是**判定权被分散在三处**：中间件（503 拦截）、控制器（readiness 端点）、指示器（依赖体检），而三者共享的 `readinessGuard()` 是运行期注入的闭包——**读者必须跳到 `RuntimePluginAdmission` 才能知道「什么时候不 ready」**。`[推测]` 若把准入位暴露成 readiness 的一个字段（现在只暴露 `status`/`instanceId`/`activeRequests`/`restartId`），排障成本会显著下降。

## §11 结论

实现层的三条主轴：**状态外置**（Redis 键 + Lua CAS，进程内只剩计数与锁）、**执行收口为一次自信号**（`process.kill(process.pid,'SIGTERM')`，替代副本由监管者拉起）、**健康与业务分离**（`/health*` 豁免排空、`/ready` 只读本地就绪）。插件收敛是同一条主轴的第二种用法：期望清单被原子冻结为「代次 + 快照」，准入闸门把「进程是否达标」变成可读的 ready 位，失败代次被显式封锁直到新代次发布，追平由 `plugin-catch-up` 逐副本、每代次一次地完成。

风险集中在四处：只读端点门禁偏弱、`enableRuntimeShutdown` 无生产接线、健康探针零测试且异常被吞、审计只落日志。这四点都不影响「滚动重启能跑通」这一主路径，但会同时抬高**排障成本**与**误用成本**。下一步值得做的最小改动：把 `restartStatus`/`pluginConvergenceStatus` 补上 `assertAuthorizedActor()`（或在装饰器层加只读角色），并把 `enableRuntimeShutdown(...)` 接到真实入口的 signal 安装处。
