## 定位

本子专家管的是 **API 进程副本自己的生命周期**——不是容器，也不是沙箱。① **运行时控制面**：`RuntimeControlController` 6 端点 → `RuntimeControlService`（三重断言与错误码映射）→ `RuntimeRestartCoordinatorService`（唯一编排状态机：Redis 锁 / 目标表 / 1 秒轮询 / Pub/Sub 唤醒 / Lua CAS 交棒）；列出与退役注册副本、重启能力自检、滚动重启编排与查询、插件运行时收敛查询，并对外暴露 `recordPluginRuntimeChange` / `recordPluginRuntimeRequirements` 供插件域登记目标清单。② **排空与关停面**：`RuntimeDrainMiddleware`（`forRoutes('*')` 全路由挂载）＋ `RuntimeLifecycleService`（在途请求计数、drain 单例、就绪状态）＋ `prepareApiShutdown` / `RuntimeQueueShutdownService`（HTTP 宽限期 → 队列 `pause(true)`/`close(true)`）＋ `enableRuntimeShutdown`（一信号一预算的进程级看门狗）。③ **健康面**：`HealthController` 两条 `@Public()` 探针（`GET /health/ready` 读本地就绪；`GET /health` 用 Terminus 聚合依赖体检）＋ `CacheHealthIndicator`/`RedisHealthIndicator`。

**一句话口径**：控制面把「谁该重启、什么时候重启、重启后是否达标」全部外化成 **Redis 键与目标表**，执行收口为**一次自信号** `process.kill(process.pid, 'SIGTERM')`（替代副本由 PM2/容器监管者拉起）；进程内只留三样状态（在途计数、准入位、重入锁），因此**任何进程重启都会丢失本地视图而保留集群视图**。健康是唯一的例外通道——`/health*` 被排空中间件豁免，故「重启中仍能探活、但不再接业务流量」这条编排契约成立。

章节来源：[runtime-control.service.ts](file://packages/server/src/runtime-control/runtime-control.service.ts)（关键符号：RuntimeControlService / assertAuthorizedActor / requestRestart）、[runtime-restart-coordinator.service.ts](file://packages/server/src/runtime-control/runtime-restart-coordinator.service.ts)（关键符号：startOperation / processActiveRestart / terminateAfterDrain）、[health.controller.ts](file://packages/server/src/health/health.controller.ts)（关键符号：readiness / check）

## 何时找这个子专家

- 要**改重启**：`POST /api/system/runtime/restart`（202，body 必须 `confirmation === RUNTIME_RESTART_CONFIRMATION`）、单活动操作幂等（`ACTIVE_RESTART_KEY` `SET NX PX 15min`，重复抛 409 `RUNTIME_RESTART_IN_PROGRESS`）、`allowDowntime`、候选副本 750ms 延迟与 `waitForIdle(30s)`、`RUNTIME_PROCESS_SIGNALER` 的可替换实现。
- 要**改排空行为**：`RuntimeDrainMiddleware.use` 的判定顺序（`isHealthRequest` 放行 → `trackRequest()` 返回 `null` 即 503 ＋ `Retry-After: 5` ＋ `Connection: close`）、`errorCode` 取值（`RUNTIME_DRAINING` vs `RUNTIME_NOT_READY`）、`finish`/`close` 双触发只释放一次。
- 要**改插件收敛**：`PluginRuntimeGenerationStore.publish` 的原子冻结清单、`writeState` 拒绝覆盖 failed 代次、`evaluateRuntimeRequirements` 的四种失败、`RuntimePluginAdmission.refresh` 的 ready 计算与 `isStable()` 的 3 秒持续、`awaitPluginRestartApproval` 的 `awaiting_restart`。
- 要**改能力探测**：`restartCapability()` 是**纯返回、不抛错**的三态（`interactive-auth-required` / `super-admin-required` / `default-tenant-required`），发布流水线用它做发布前自检；`assertAuthorizedActor()` 靠**字符串比较**这三个 reason。
- 要**改健康探针**：`GET /api/health` 的四项聚合（`database`/`storage`/`cache`/`redis`，四个开关**硬编码为 true**，`checkDbWithTerminus = false`）、`GET /api/health/ready` 的非 `ready` 即 503 ＋ `Cache-Control: no-store`、`.deploy/api/healthcheck.cjs` 的 5 秒 `AbortSignal.timeout` 与逐项 `details[*].status === 'up'`。
- 要**改多副本运维语义**：参与者是操作创建时冻结的 `getReadyInstances()` 快照（逐副本 `expectedBootId`），未就绪副本由 `reconcileLocalPlugins` 的 `plugin-catch-up` 追平（每副本每代次一次，`REPLICA_ATTEMPTS_KEY`）；串行滚动（`maxConcurrentRestarts = 1`）＋**最后一个健康副本必须显式 `allowDowntime`**。
- 要**改关停预算**：`prepareApiShutdown`（`beginDrain({restartId:'process-shutdown'})` → `waitForIdle(10_000)` → `queues.close()`）、`enableRuntimeShutdown` 的单看门狗 `RUNTIME_SHUTDOWN_TIMEOUT_MS = 30_000` 与 `runShutdownStep` 的 `completed|failed|timed_out` 三态。
- 要**排查「探针绿但业务 503」**：`readinessGuard()` 是运行时注入的闭包（`RuntimePluginAdmission.refresh` 决定），把「插件启动未监听 / 准入未通过 / 5 秒校验窗口过期 / 注册租约失效」变成中间件 503——排障需跳到 `RuntimePluginAdmission`，而不是只读 `runtime-lifecycle.service.ts`。

## 边界

**做什么**：API 副本的注册视图与退役、滚动自重启编排、排空与在途流量摘除、队列关停与进程关停预算、插件运行时代次发布与收敛准入、存活/就绪探针。

**不做什么**

- **不含 ① 沙箱执行**：NsJail Runner、沙箱运行时、终端、托管服务与预览、卷投递归 [子专家①](file://.module-experts/后端专题/运行时·沙箱·产物专家/sub-experts/沙箱执行子专家/C0-使用总览.md)；本子域**不接触沙箱运行时**，关停期只做「HTTP 宽限 10s → 队列 pause/close」。
- **不含 ③ 产物与文件访问**：`artifact*` 四表与 `workspace-file-access` 归 [子专家③](file://.module-experts/后端专题/运行时·沙箱·产物专家/sub-experts/产物与文件访问子专家/C0-使用总览.md)。
- **不重启容器、不调度 Pod**：容器编排在部署层（runner/镜像/编排清单不在本域），本域只对自己的进程发信号。
- **不拥有副本注册表本体**：`InstanceRegistryService` 属 `managed-connection`，本域只消费 `getReadyInstances`/`getRegisteredInstanceDetails`/`retireInstance`/`setReady`/`isLeaseValid`/`getPluginState`。
- **不拥有插件装载与启动重试语义**：`plugin/plugin-startup-state.ts` 归平台插件域；本域只消费 `isPluginStartupListening`/`admitPluginStartup`/`canRestorePluginStartup` 等。
- **不承担业务数据健康**：DB 探活只做 `userRepository.count()`，不校验表结构、索引或迁移状态。
- **不写任何本域表**：`health` 的唯一实体注册是从 core 内部引入的**外部实体** `User`（只读 `count()`）。

## 已知问题与常见坑

1. **6 端点的门禁是「双层 + 不对称」**：`GET /instances`、`POST /instances/:instanceId/retire`、`POST /restart` 三处方法级带 `@UseGuards(RoleGuard)` + `@Roles(SUPER_ADMIN)` 且服务层再走 `assertAuthorizedActor()`；而 `GET /restart-capability`、`GET /restart/:restartId`、`GET /plugin-convergence/:generation` **只有类级 `TenantPermissionGuard`**，其中 `restartStatus()` 与 `pluginConvergenceStatus()` **连服务层断言都没调用**。
   - 契约来源：[runtime-control.controller.ts](file://packages/server/src/runtime-control/runtime-control.controller.ts)（关键符号：@UseGuards(TenantPermissionGuard) / @Roles(RolesEnum.SUPER_ADMIN)）、[runtime-control.service.ts](file://packages/server/src/runtime-control/runtime-control.service.ts)（关键符号：restartStatus / pluginConvergenceStatus / assertAuthorizedActor）。
2. **`assertAuthorizedActor()` 的三重前置是「非 API Key（交互式）＋ SUPER_ADMIN ＋ 默认租户」，且判定靠字符串**：`restartCapability().reason ∈ {interactive-auth-required, super-admin-required, default-tenant-required}` → 403 `RUNTIME_RESTART_INTERACTIVE_AUTH_REQUIRED` / `…_SUPER_ADMIN_REQUIRED` / `…_DEFAULT_TENANT_REQUIRED`；**改枚举即静默失效**。
   - 契约来源：[runtime-control.service.ts](file://packages/server/src/runtime-control/runtime-control.service.ts)（关键符号：restartCapability / assertAuthorizedActor）。
3. **`runtime-drain.middleware` 的排空期请求行为与触发面比预期宽**：`forRoutes('*')` 全路由；`isHealthRequest` 用 `/\/health(?:\/|$)/` 匹配 `originalUrl` 去 query 后的路径，**任何末段为 `health` 的路径都会被豁免**；503 分支返回 `{statusCode:503, errorCode, message}` 且 **不调 `next()`**；`Retry-After` 固定 5 秒，而实际 drain 上限是 30 秒（客户端按 5 秒重试会连续撞 503）。
   - 契约来源：[runtime-drain.middleware.ts](file://packages/server/src/runtime-control/runtime-drain.middleware.ts)（关键符号：use / isHealthRequest）、[runtime-restart-coordinator.service.ts](file://packages/server/src/runtime-control/runtime-restart-coordinator.service.ts)（关键符号：DEFAULT_DRAIN_TIMEOUT_MS）。
4. **重启对在途执行的影响是「进程级」而非「沙箱级」**：候选副本先 `setReady(false)` → 等 750ms → `waitForIdle(30_000)` → 复核「活动键未变 + 无 failed 目标 + 仍有别的就绪副本（或 `allowDowntime`）」→ 才自信号 `SIGTERM`，失败即 `cancelDrain` ＋ `failTarget`。**在途沙箱作业不因 API 重启而中断**（作业运行在 NsJail 进程边界内），但**依赖本副本 SSE/HTTP 长连接的调用方会看到流被切断**（契约层以 `RUNTIME_STREAM_INTERRUPTED_EVENT = 'runtime-interrupted'` 显式命名）。
   - 契约来源：[runtime-restart-coordinator.service.ts](file://packages/server/src/runtime-control/runtime-restart-coordinator.service.ts)（关键符号：beginReplicaRestart / terminateAfterDrain / cancelDrain）、[runtime-restart-deadlines.ts](file://packages/server/src/runtime-control/runtime-restart-deadlines.ts)（关键符号：REPLICA_RESTART_TIMEOUT_MS）。
5. **插件收敛失败面是「沉默 + 封锁」**：`awaitPluginRestartApproval` 在「单副本且需求未满足且未获故障容忍」时保持 idle 并把代次写成 `awaiting_restart`（不重试、不通知）；`writeState` **拒绝对当前代次的 `failed` 覆盖**，`readDesired` 在历史过期后 fail-closed 取 `failed`；同一操作内出现更新代次时不另起操作，而是用 `TRANSITION_ACTIVE_RESTART_SCRIPT` **原子交棒**，交棒失败则把 `pluginGeneration + 1..current` 全部标 failed。
   - 契约来源：[plugin-convergence-capacity.ts](file://packages/server/src/runtime-control/plugin-convergence-capacity.ts)（关键符号：awaitPluginRestartApproval）、[plugin-runtime-generation.store.ts](file://packages/server/src/runtime-control/plugin-runtime-generation.store.ts)（关键符号：publish / writeState / readDesired / claimCatchUp）。
6. **健康检查的检查项、超时与失败语义不对称**：四项开关是 `private readonly checkDb/checkStorage/checkCache/checkRedis = true`（硬编码），`checkDbWithTerminus = false`（Terminus ping 常闭）；`database` 与 `storage` 的异常被 `catch` 吞成 `{status:'down', message}` 返回体（`[推测]` Terminus 聚合仍为 `ok`），只有 `cache`/`redis` 抛 `HealthCheckError` 才会聚合失败。**本域没有单点超时**，时限来自 `healthcheck.cjs` 的 5 秒；`redis` 指示器在构造函数里 `startRedis()`（不 await，且 `console.log` 含口令的 `REDIS_URL`），`stopRedis()` 带 `TODO` 且无调用点。
   - 契约来源：[health.controller.ts](file://packages/server/src/health/health.controller.ts)（关键符号：check / checkDbWithTerminus / checkStorage / checkCache）、[redis-health.indicator.ts](file://packages/server/src/health/indicators/redis-health.indicator.ts)（关键符号：startRedis / checkRedis / stopRedis）。
7. **多副本的硬前提是「共享同一 Redis + PM2 式监管者」**：所有副本共享 `ACTIVE_RESTART_KEY`，但**只有目标是自己（`expectedBootId === 本进程 bootId`）时才执行重启**；未就绪副本不被纳入快照、之后由 `plugin-catch-up` 追平；协调通信是「1 秒轮询 + Pub/Sub 唤醒」双通道（`duplicate()` 不可用则退化纯轮询）。**本地 nodemon 下的「重启」不等于 drain**（模块头注释明示）。
   - 契约来源：[runtime-restart-coordinator.service.ts](file://packages/server/src/runtime-control/runtime-restart-coordinator.service.ts)（关键符号：COORDINATOR_POLL_MS / ACTIVE_RESTART_KEY / reconcileLocalPlugins / startSubscriber）、[runtime-control.module.ts](file://packages/server/src/runtime-control/runtime-control.module.ts)（关键符号：模块头注释 / processSignaler）。
8. **`enableRuntimeShutdown` 在仓库内没有生产调用点**：`packages/` 内它只出现在自身定义与 `runtime-shutdown.spec.ts` 经 `fixtures/shutdown-process.cjs` 的调用；`bootstrap/index.ts` 只做 `helmet()` / `setGlobalPrefix` / `app.listen`，`BootstrapModule.onApplicationShutdown` 只打日志。因此「SIGTERM → 排空 → 队列 close → 显式 exit」这条预算链在仓库可见范围内未被接线，实际接线位置在仓库外 `[推测]`。
   - 契约来源：[runtime-shutdown.ts](file://packages/server/src/runtime-control/runtime-shutdown.ts)（关键符号：enableRuntimeShutdown / RUNTIME_SHUTDOWN_TIMEOUT_MS）、[bootstrap/index.ts](file://packages/server/src/bootstrap/index.ts)（关键符号：bootstrap / app.listen）。
