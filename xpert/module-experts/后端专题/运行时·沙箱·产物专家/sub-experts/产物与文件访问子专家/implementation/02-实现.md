## 产物登记链

**容器登记 `createArtifactWithDefaults`**：`normalizeSourceInput`（`pluginName`/`resourceType`/`resourceId` 必填）→ `resolveCreateScope`（input → 能力的 defaults → `RequestContext` 三级回退，`tenantId` 缺失即 400）→ `findExistingArtifact`（按 `tenantId+pluginName+resourceType+resourceId` 查，再在内存里比对可空的 `organizationId`/`userId`）→ 命中即**复用同一行**：`status='active'`、回写 `kind`/`checksum`/`title`/`description`/`metadata`；未命中 `create+save`，捕获唯一约束错误后再查一次（并发重试也幂等）。

**版本登记 `createArtifactVersionWithDefaults`**：`resolveScopedArtifact`（越域即 404；`deleted` 即 410）→ `normalizeArtifactVersionInput`（`workspaceFileRef` 必填、`source` 必须是 `platform.workspace.files`、路径归一化、`mimeType` 白名单）→ `readWorkspaceArtifact`（整文件读进内存）→ 用真实字节算 `sha256` 与 `size` 并与入参复核（不符 400）→ `versionNumber = max + 1` → 若 `setCurrent !== false` 回写 `artifact.currentVersionId` 并复位 `status='active'`。

**幂等登记 `ensureArtifactVersionWithDefaults`**：**强制** `idempotencyKey`；进入 `withLockedArtifact`（事务 + `pessimistic_write` 锁 `artifact` 行）后先查 `(artifactId, idempotencyKey)`：命中且 `sha256` 一致 → `{ outcome: 'reused' }`；命中但字节不同 → 400「already used for different content」；未命中才 insert，返回 `{ outcome: 'created' }`。

**实测生产方**：`FileActivityStorage.archive`（插件名 `platform.file-activity`，先 `files.uploadBuffer` 再 `ensureArtifactVersion`，`idempotencyKey = sha256`）· `ToolImageArtifacts.save`（`resourceId = <scopeHash>:<sha256>`，图片先 `sharp` 解码校验）· `knowledgebase-tools` 中间件 · 管理面 `POST /api/artifacts`。

章节来源：[artifacts.service.ts](file://packages/server-ai/src/artifacts/artifacts.service.ts)（关键符号：createArtifactWithDefaults / findExistingArtifact / normalizeArtifactVersionInput / ensureArtifactVersionWithDefaults / withLockedArtifact）、[file-activity-storage.service.ts](file://packages/server-ai/src/sandbox/middlewares/file-activity-storage.service.ts)（关键符号：FileActivityStorage.archive）、[tool-image-artifacts.ts](file://packages/server-ai/src/shared/runtime/tool-image-artifacts.ts)（关键符号：ToolImageArtifacts.save）

## 产物读取与下载

**管理面 `GET /api/artifacts/:artifactId/versions/:artifactVersionId/content`**：`resolveForManagementAccess` → `resolveScopedArtifact` → 非 `active` 即 410 → `resolveRequestedVersion`（`version` 模式按 id，否则 `currentVersionId`；非 `active` 即 404）→ `readWorkspaceArtifact` → `sha256` 复核（不符 410）→ 控制器逐项设头：`Content-Type`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cache-Control: private, no-store`、`X-Xpert-Artifact-Version`、`X-Xpert-Artifact-SHA256`、`Content-Disposition: inline`；`text/html` 追加 `interactive` 档 CSP。

**公开面（`@Public()` 3 条）**：`resolveAccessContextFromRequest`（先 Bearer JWT，再分享会话 cookie）→ `resolveForPublicAccess` → `authorizeArtifactLink`：`download` 但 `allowDownload === false` 记 `denied` 并 403；`assertPublicAccess` 判 `revoked` → 410、`expired` → 回写 `expired` 并 410、`canAccessLink` 不过则按有无身份记 401/403；随后 `resolveLinkVersion` → 读字节 → `sha256` 复核，不符则记 `denied` 并抛 410「Artifact changed after the link was created」→ `incrementCounters`（`repository.increment` 原子自增 `accessCount`/`downloadCount`）→ `recordAccessLog(event)`。`descriptor` 走 `resolveDescriptorForPublicAccess`，序列化时**剔除** `workspaceFileRef` 与嵌套 `artifact`/`version`。

**落盘方式**：产物是**全量 Buffer**（`VolumeSubtreeClient.readBuffer` → `res.send(buffer)`），**没有** Range / 206 / 断点续传 —— 与 `workspace-file-access` 的流式实现是两套（后者 `createReadStream` + `resolveHttpByteRange`）。

**分享会话**：`POST /api/artifacts/share-session/:slug`（需登录）→ 复用 `assertPublicAccess` 授权 → 校正 `publicUrl` 为 canonical → 签 15 分钟 JWT cookie（`httpOnly`、`sameSite: 'lax'`、`secure` 由 `req.secure`/`x-forwarded-proto` 推导、`path=/artifacts/share`）；`sendOrRedirect` 捕获 401 时 302 到 `/artifacts/auth/:slug`（`download` 追加 `?download=1`）。

章节来源：[artifacts.service.ts](file://packages/server-ai/src/artifacts/artifacts.service.ts)（关键符号：resolveForManagementAccess / resolveArtifactLink / authorizeArtifactLink / assertPublicAccess / canAccessLink / incrementCounters / createArtifactShareSession）、[artifacts.controller.ts](file://packages/server-ai/src/artifacts/artifacts.controller.ts)（关键符号：sendArtifactResponse / buildContentDisposition / buildHtmlCsp / sendOrRedirect）

## 工作区文件访问的路径解析与越界防护

**第一段 `createSession`**：`viewExtensionService.resolveViewFileAccessContext(hostType, hostId, viewKey, { runtimeScope })` → `assertAssistantFileAccess`（`hostType === 'agent'` 且无 `projectId` 时派发 `ResolveAssistantFileAccessCommand(hostId, 'read', 'runtime')`）→ 生成 `sessionId` 并把 `{tenantId, organizationId, userId, hostType, hostId, viewKey, dataScopeKey, runtimeScope, origin, expiresAt}` 写 Cache（TTL 1 小时）→ 签 JWT（`aud='workspace-view-file-access'`）写 cookie，`path = /api/workspace-files/content/<sessionId>`。

**第二段 `createGrant`**：`requireAuthenticatedSession`（Cache 命中 + `RequestContext` 的 `tenantId`/`organizationId`/`userId` 与 session **全等**，否则 404）→ 再一次 `assertAssistantFileAccess` → `resolveViewFileResource`（**服务端**把 View 业务资源解析成便携引用）→ `assertContextMatchesSession`（`bindingsMatch` 比对 8 个字段 + `runtimeScope`）→ `assertPortableReference` → grant 写 Cache，`expiresAt = session.expiresAt`（**随 session 到期，不独立续期**）→ 返回 `/api/workspace-files/content/<sid>/<gid>/<encodeURIComponent(fileName)>`。

**第三段读取**：`WorkspaceFileAccessGuard.canActivate` 从 cookie 取 `xpert_workspace_file_access`（缺失 401）→ `authorizeContent(sessionId, grantId, fileName, token)`：验 JWT（`aud` 双校验）+ `payload.sessionId === 路径 sessionId` + `sessionMatchesPayload` + 未过期；grant 必须存在、`publicFileName === 路径 fileName`、`bindingsMatch(session, grant)`、未过期，否则一律 404（避免探测）。

**路径解析与越界防护（逐条）**：

1. **客户端不传路径**：路由只有 `sessionId`/`grantId`/`fileName`；`fileName` 仅做**相等匹配**，`resolveAuthorizedFile` 用的是 `grant.reference.filePath`。
2. **引用白名单**：`assertPortableReference` 要求 `source === 'platform.workspace.files'`、`filePath` 非空、`tenantId` 存在且等于 `session.tenantId`（否则 400 `WorkspaceFileAccessInvalidReference`）。
3. **卷作用域解析**：`resolveWorkspaceVolumeScope(reference, { tenantId, userId: reference.userId ?? session.userId })`；catalog 决定卷（`projects` / `users` / `xperts` / `user-xperts` / `knowledges` / `skills`），`projects` 要求 `scopeId === projectId`、`xperts`/`user-xperts` 要求 `scopeId === xpertId`、`users` 要求 `scopeId === userId`，不满足返回 `null` → 404。
4. **相对路径归一化**：同一域内的 `normalizeWorkspaceRelativePath` / `normalizeWorkspaceFilePath` 用 `path.posix.normalize` 去掉前导 `/`、反斜杠转 `/`，并拒绝空、`.`、`..`、`../` 前缀与 `\0`。
5. **重放防护**：认证下载路径 `authorizeAuthenticatedContent` 会**重新** `resolveViewFileResource` 并比对 `filePath` 与 `volumeScope`（`isDeepStrictEqual`），fileKey 被改绑到别的文件/卷时旧 grant 立即 404。
6. **fileName 净化**：`normalizeFileName` = `basename(...)` + 去 `\u0000-\u001f\u007f` + 空白兜底 `'workspace-file'`；`buildWorkspaceFileContentDisposition` 把 quoted filename 限成 ASCII（非法字符替 `_`），真名走 RFC 5987 `filename*=UTF-8''…`。
7. **origin 校验**：`assertRequestOrigin` 只在 `origin === session.origin` 或等于 `environment.baseUrl` 的 origin 时放行；另有三条显式分支——`preview` 且 `Sec-Fetch-Site: same-origin|same-site` + `Mode: no-cors` + `Dest: image` 无 Origin 放行、`preview` 且无 Origin/Referer 但 `same-origin/cors/empty` 放行、`download` 无 Origin 放行；其余 403。放行时下发 `Access-Control-Allow-Origin` + `Allow-Credentials` + `Vary: Origin`。
8. **前端二次校验**：`viewFileContentRoute` 要求 grant URL 与配置的 API 同源、前缀为 `<api>/workspace-files/content/`、无凭据/查询串/片段、路径段恰为 3 段且不复号穿越（`.`/`..`/斜杠），否则直接抛错。

**流式投递**：`sendWorkspaceFileContent` 先 `stat` 校验 `isFile`（否则 404），`resolveHttpByteRange` → 不可满足走 416 + `Content-Range: bytes */size`，部分请求走 206 + `Content-Range`；`HEAD` 只发头；`createReadStream(pipe)`，流错误时未发送响应则 404、已发送则 `destroy`，响应 `close` 时销毁流；固定 `Accept-Ranges`/`Cache-Control: private, no-store`/`nosniff`/`no-referrer` 与 `Access-Control-Expose-Headers`。

章节来源：[workspace-file-access.service.ts](file://packages/server-ai/src/workspace-file-access/workspace-file-access.service.ts)（关键符号：createSession / createGrant / authorizeContent / resolveAuthorizedFile / authorizeAuthenticatedContent / assertRequestOrigin / buildCookiePath / assertPortableReference）、[workspace-file-content.response.ts](file://packages/server-ai/src/workspace-file-access/workspace-file-content.response.ts)（关键符号：sendWorkspaceFileContent / buildWorkspaceFileContentDisposition）、[workspace-file.ts](file://packages/server-ai/src/file-understanding/domain/workspace-file.ts)（关键符号：resolveWorkspaceVolumeScope / normalizeWorkspaceRelativePath）、[view-file-content-route.ts](file://apps/cloud/src/app/@core/services/view-file-content-route.ts)（关键符号：viewFileContentRoute）

## 4 张表的写入点

| 表 | 写入点（服务方法） | 写什么 |
|---|---|---|
| `artifact` | `createArtifactWithDefaults` | insert 或复用更新（`status/kind/checksum/title/description/metadata`） |
| `artifact` | `createArtifactVersionWithDefaults` / `ensureArtifactVersionWithDefaults`（`setCurrent !== false`） | `currentVersionId`、`status='active'` |
| `artifact` | `archiveArtifactWithDefaults` / `deleteArtifactWithDefaults` | `status='archived'` / `'deleted'`（**软删，行不删**） |
| `artifact_version` | `createArtifactVersionWithDefaults` / `ensureArtifactVersionWithDefaults` | 只 insert（`versionNumber`、`workspaceFileRef`、`mimeType`、`size`、`sha256`、`idempotencyKey`…），无 update 路径 |
| `artifact_link` | `createArtifactLinkRecord` | insert（`slug`、`publicUrl`、`accessMode`、`tokenHash`、`expiresAt`、`disposition`、`allowDownload`、`safeHtmlProfile`） |
| `artifact_link` | `ensureArtifactShareWithDefaults` | 命中同 `shareKey` 且策略等价则 `reused`；否则旧链 `revoked` + 新建（`created` / `replaced`） |
| `artifact_link` | `updateArtifactLinkAccessWithDefaults` | `applyAccessPatch`（`accessMode`/`customPrincipals`/`expiresAt`/`status='active'`/`revokedAt=null`/`tokenHash`）与 `applyPresentationPatch`，可改 `versionMode`/`artifactVersionId` |
| `artifact_link` | `revokeArtifactLinkWithDefaults` / `revokeArtifactShareWithDefaults` / `deleteArtifactWithDefaults` | `status='revoked'` + `revokedAt` |
| `artifact_link` | `assertPublicAccess` / `getArtifactShareWithDefaults` | 读到过期即回写 `status='expired'` |
| `artifact_link` | `createArtifactShareSession` / `incrementCounters` | canonical `publicUrl` 校正；`accessCount`/`downloadCount` 原子自增 |
| `artifact_access_log` | `recordAccessLog(link, …)` | link 维度：`access`/`download`/`denied`/`revoked`/`expired` + `statusCode`/`principalUserId`/`ipHash`/`userAgent` |
| `artifact_access_log` | `recordArtifactAccessLog(artifact, …)` | artifact 维度：`archived`/`deleted`，`linkId = null`、`slug = artifact:<id>` |

两处审计写入都用 `try/catch` 静默失败（注释：「审计不得让合法操作失败」），因此审计是**尽力而为**语义。

## 与沙箱作业、会话、前端的交互

**与沙箱作业（`sandbox_job`）**：**无直接交互**。`sandbox-job/**` 内的 `artifact` 全部是「运行时镜像/文件系统产物」（`runtimeArtifactKind` / `Reference` / `Digest`），与产品产物同名不同义；两者的共同点是都通过插件能力面暴露（`platform.artifacts` / `platform.sandbox.jobs`）。本子域对沙箱的唯一真实接触点是**反向调用**：`sandbox/middlewares/file-activity-storage.service.ts` 在 `present_files` 归档时调用 `ArtifactsRuntimeCapability` 的 `createArtifact` / `listArtifactVersions` / `ensureArtifactVersion`。

**与会话**：本子域不写会话表，也不持会话外键；`ToolImageArtifacts` 把 `conversationId` 落在 `artifact.metadata` 里（弱引用）；会话侧读产物由 `chat-conversation` 的 `read-conversation-artifact.handler` 完成（外部消费方）。

**与前端 / 宿主**：公开分享面是 host 级路由 `/artifacts/share/:slug`（`setGlobalPrefix` 显式排除 `api`），未登录时 302 到前端 `/artifacts/auth/:slug`；分享会话的握手 URL 由 `artifactShareSessionUrl` 用 `API_PREFIX` 拼；workspace-file 内容令牌由 `viewFileContentRoute` 在校验后映射成宿主自己的认证路由。

**与运行时 client-secret 面（相邻但复用本服务）**：`WorkspaceFileAccessRuntimeController`（`@Controller('workspace-files/view-sessions')`，`ApiKeyOrClientSecretAuthGuard` + `AssistantFileAccessGuard`，`@AssistantFileAccess('view-session-create'|'view-session')`）与 `GroupViewFilesController`（群工作台路径，额外 `assertAuthenticatedSessionScope` 校验 `hostType='agent'` + `hostId` + `runtimeScope`）都调用本子域的 `WorkspaceFileAccessService`；运行时控制器返回 grant 的 **pathname**，让客户端用自己的认证传输解析。

章节来源：[workspace-file-access-runtime.controller.ts](file://packages/server-ai/src/ai/workspace-file-access-runtime.controller.ts)（关键符号：WorkspaceFileAccessRuntimeController.createGrant 的 pathname 返回）、[assistant-file-access.guard.ts](file://packages/server-ai/src/ai/assistant-file-access.guard.ts)（关键符号：AssistantFileAccessGuard.canActivate / AssistantFileAccess）、[tool-image-artifacts.ts](file://packages/server-ai/src/shared/runtime/tool-image-artifacts.ts)（关键符号：ToolImageArtifacts.save 的 metadata.conversationId）

## 清理、失效与配额

- **无清理任务**：两个子目录内**没有** `@Cron` / `setInterval` / retention 逻辑，也没有 `migrations/*.sql`；`artifact_access_log` 只增不减（父级 07 同样记录「未找到 TTL/清理任务」）。
- **有效期常量**：分享会话 cookie `15 分钟`（`ARTIFACT_SHARE_SESSION_TTL_SECONDS`）· 签名预览默认 `15 分钟`（`DEFAULT_SIGNED_PREVIEW_TTL_SECONDS`）· 链接 TTL 上限 `365 天`（`MAX_TTL_SECONDS`，超过即 400）· 工作区文件会话 `1 小时`（`WORKSPACE_FILE_ACCESS_TTL_MS`，grant 到期随 session）。
- **失效语义**：产物是**逻辑状态机**（`deleted`/`archived` 只改状态并连带吊销 link），字节与行都留给运维处理；`expired` 是读取时判定 + 回写。
- **分页与上限**：`listArtifacts` 的 `pageSize` 上限 100（默认 20）；Grant 只做**签发**，没有速率限制与最大签发数限制。
- **配额**：本子域**没有配额实现**——唯一体量约束来自 `artifact_version.size`（bigint）与产物 MIME 白名单；`[推测]` 大产物与高频公开读取的容量/成本约束依赖卷侧与网关侧，而匿名 `public_link` 的实际屏障只有 12 字符 slug 熵（`ARTIFACT_LINK_SLUG_ALPHABET`，57 个字符）与 `expiresAt`。

章节来源：[artifacts.service.ts](file://packages/server-ai/src/artifacts/artifacts.service.ts)（关键符号：ARTIFACT_SHARE_SESSION_TTL_SECONDS / DEFAULT_SIGNED_PREVIEW_TTL_SECONDS / MAX_TTL_SECONDS / createArtifactLinkSlug / MAX_PAGE_SIZE）、[workspace-file-access.service.ts](file://packages/server-ai/src/workspace-file-access/workspace-file-access.service.ts)（关键符号：WORKSPACE_FILE_ACCESS_TTL_MS / hasExpired）

## 设计模式

| 模式 | 落点 |
|---|---|
| 能力提供者 + 作用域门面 | `@RuntimeCapabilityProvider(ArtifactsRuntimeCapability)` + `ArtifactsService.createScopedApi(defaults)`（16 个方法闭包绑定默认 scope） |
| CQRS 命令 | `ResolveAssistantFileAccessCommand`（经 `CommandBus` 执行，用于 Assistant 运行时读权限） |
| 守卫链 / 显式放行的最小面 | 全局 `AuthGuard` →（管理面）直接进服务；（内容面）类级 `@Public()` + `WorkspaceFileAccessGuard`；（运行时面）`ApiKeyOrClientSecretAuthGuard` + `AssistantFileAccessGuard` |
| 短时令牌 + 服务端会话记录 | JWT cookie（`aud`/`sub` 双校验）+ Cache 里的 session/grant 记录（双写才能用） |
| 幂等键 | `artifact_version(artifactId, idempotencyKey)`、`artifact_link.slug` 唯一、`artifact_link(artifactId, shareKey) WHERE status='active'` 部分唯一、`artifact` 四条部分唯一 |
| 乐观重试 + 悲观锁 | `isUniqueConstraintError` 后重查（容器登记）；`withLockedArtifact`（事务 + `pessimistic_write`）保护版本号与分享槽位 |

| 共享投递助手 | `sendWorkspaceFileContent` / `buildWorkspaceFileContentDisposition` 被 content 控制器、管理下载、运行时控制器三处复用 |

## 热点路径

1. **`readWorkspaceArtifact` 是产物面唯一的内容入口**：登记版本、公开预览、管理预览、认证共享内容全部走它，整文件读进内存并算 `sha256`——大产物即内存峰值，且没有缓存。
2. **公开分享面每次都验身份**：`resolveAccessContextFromRequest` 逐请求验 Bearer JWT 或分享 cookie，命中 cookie 时还要 `userService.getIfExists` 查库。
3. **内容读取面（cookie 路径）每请求两次 Cache 读 + 一次 re-resolve**（运行时路径还要再调 provider），并对文件做 `stat`。
4. **审计写入在关键路径上同步等待**：`recordAccessLog` 在返回字节前 `await`（虽然失败被吞），每次公开读取都会产生一行 `artifact_access_log`。
5. **`ensureArtifactVersion` 的锁竞争**：同一 artifact 的并发登记会在 `artifact` 行上串行化（事务 + 悲观锁），是插件批量归档（`present_files` 每文件一次）时的争用点。

## 技术债

1. **文档与源码的前缀漂移**：父级 C1/05 记公开分享为 `/api/artifacts/share/...`，实际被 `setGlobalPrefix` 的 `exclude` 摘成 `/artifacts/share/...`（已核实，需在文档层统一）。
2. **产物读取无流式**：全量 `Buffer` + `sha256` 复核，大文件既是内存峰值也无法断点续传；同子域的 workspace-file 面却有完整 Range 支持，两套策略并存。
3. **审计尽力而为**：`recordAccessLog` / `recordArtifactAccessLog` 的 `catch` 为空，审计缺失不会被上游感知，也没有补写机制。
4. **审计表无归档**：`artifact_access_log` 无 TTL/分片/清理任务，长期运行需外部作业（运维侧结论一致）。
5. **`artifact_version.status` 无迁移路径**：只在 insert 写 `'active'`，契约里的 `'deleted'` 在本域无写入点（`[已核实]` 服务层无 update）。
6. **`inferArtifactKind` 为死代码**：`artifacts.service.ts` 内定义并引用了 `PPTX_MIME_TYPE`，但全文件无调用点；`createArtifactWithDefaults` 直接 `kind: input.kind ?? 'file'`，导致「按 MIME 推断 kind」的策略未生效。
7. **双校验和字段语义重叠**：`artifact.checksum`（来源侧校验和）与 `artifact_version.sha256`（内容哈希）并行存在，只有后者参与读取复核。`[推测]`：`checksum` 目前仅作来源去重提示。
8. **会话/授权状态只在 Cache**：多副本必须在同一集中式缓存上；进程重启即全部失效（用户需重新走两段式授权）。
9. **`custom_principals` 支持面窄**：只匹配 `userId`、`user:<id>`、`organization:<id>` 三种字面量，没有组/角色语义。
10. **`assertRequestOrigin` 依赖 `Sec-Fetch-*`**：老浏览器不发送 Fetch Metadata 时预览分支会被拒（403），只能靠 session.origin 匹配。
11. **`createArtifactVersion` 的 `currentVersionId` 竞态**：非幂等分支不加锁（只有 `ensure`/`ensureShare` 走 `withLockedArtifact`），并发创建可能出现「后写的 current 不是最大版本号」`[推测]`。
12. **`artifact_access_log.ipHash` 无盐**：`hashString` 即裸 `sha256(value)`，IPv4 空间可暴力枚举 `[推测]`（隐私弱化，非功能性缺陷）。

## 设计维度分析

1. **信任边界维度**：本子域实际存在三张面孔——① **管理面**（全局 JWT + 服务层作用域查询，越域 404）；② **公开面**（`@Public()` + link 策略 + 签名 token/分享 cookie，匿名可达）；③ **运行时面**（Client Secret + Assistant 绑定）。同一份内容经三面投递，但授权判定分别落在 `resolveScopedArtifact` / `canAccessLink` / `AssistantFileAccessGuard` 三处，读代码时必须按面区分。
2. **一致性模型维度**：产物链是 **DB 强一致**（唯一索引 + 悲观锁 + 事务），文件访问链是 **Cache 弱一致**（会话/grant 可丢、可过期、重启即失效）。因此「旧 grant 不能指向新文件」这种正确性靠**重解析 + 值比对**兜底，而不是靠存储事务。
3. **定位方式维度**：产物用**不透明引用**（`workspaceFileRef` + slug）对外，工作区文件用**服务端解析的相对路径**对内；两条链都刻意让客户端拿不到宿主文件系统路径，代价是每次读取都要经卷作用域解析。
4. **失效模型维度**：链接失效是「状态位 + 读取时判定」，会话失效是「TTL + 进程内存/Cache 性」，字节回收完全不在本子域——本域因此没有删除语义上的强一致要求，但也失去了主动回收能力。

## 结论

1. 实现形态是「**薄控制器 + 厚服务 + 外置字节**」：所有授权、幂等、路径解析都在服务层，控制器只做参数透传与响应头；`artifacts.service.ts` 是单点大文件（近 2000 行）是主要维护成本。
2. **幂等实现分两档**：容器登记靠「先查 + 唯一约束重试」，版本与分享槽位靠「事务 + 悲观锁 + 先查后写」，二者语义不同但都只保证「同一来源/同一键不重复」。
3. **越界防护有 8 层**（不接受路径 → 引用白名单 → 卷作用域 → 相对路径归一化 → 重放比对 → 文件名净化 → origin 校验 → 前端二次校验），是本子域最完整的一块安全设计。
4. 主要缺口集中在**清理/配额/流式**三项（均默认交给外部或卷侧），以及审计的**尽力而为**语义；这些不是缺陷，但决定了本子域的运维成本边界。
