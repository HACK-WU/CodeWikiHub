## 索引与唯一约束口径

- `artifact` 的 4 条部分唯一索引 = 同一业务约束在「有/无 organization」×「有/无 user」四种空值切分下的表达：**PG 的部分唯一索引即应用层的并发防线**，服务层只做「先查后写 + 唯一冲突重查」的优化。
- `artifact_version` 两条唯一索引 = 两种幂等：`(artifactId, idempotencyKey)` 抗重放（`created`/`reused`），`(tenantId, organizationId, artifactId, versionNumber)` 抗版本号并发。
- `artifact_link` 的 `(slug)` 唯一 = URL 稳定性；`WHERE shareKey IS NOT NULL AND status='active'` 部分唯一 = 「稳定分享槽位」语义（`ensureArtifactShare` 才敢做「复用或替换」）。
- **无 `select: false` 列**：`artifact_link.tokenHash` 与 `artifact_access_log.ipHash` 在实体层没有默认屏蔽，安全性靠服务层不出参（`serializeLink` 不返回 `tokenHash`）。
- **没有指向本域之外的 FK**：`workspaceFileRef`、`userId`/`workspaceId`/`projectId`/`xpertId`、`artifact_access_log.artifactId` 都是字符串/JSON 弱引用；本域 4 表与外域之间只靠 `forFeature` 注册的实体和值比对协作。

| 规则类别 | 具体规则 | 依据 |
|---|---|---|

| 契约枚举 | `ArtifactKind = html\|markdown\|pdf\|pptx\|image\|file\|site\|presentation`；`ArtifactStatus = active\|archived\|deleted`；`ArtifactVersionStatus = active\|deleted`；`ArtifactLinkStatus = active\|revoked\|expired`；`ArtifactAccessMode` 六值；`ArtifactAccessEvent` 七值；`ArtifactLinkVersionMode = latest\|version`；`ArtifactLinkDisposition = inline\|attachment`；`ArtifactSafeHtmlProfile = strict\|interactive` | 契约 |

| 审计内容约束 | 只写摘要（`ipHash`、`userAgent`、`statusCode`、`error`），**禁止**落预览 token、平台凭据与文件内容 | 实体注释 |
| 版本不可变 | `artifact_version` 无更新语义（改内容只能新增版本）；展示策略改在 `artifact_link` | 实体注释与服务方法集 |

## 未确认项

1. **`artifact_version.status` 的迁移路径未确认**：契约含 `'deleted'`，但服务层没有任何把版本置为 `deleted` 的代码；是否存在外部 DDL/维护脚本未在本仓核实。
2. **`artifact.kind` 的取值落地范围未确认**：契约含 `site` / `presentation`，而服务端 `inferArtifactKind` 只映射 `html/markdown/pdf/pptx/image/file`，且该函数**无调用点**；`site`/`presentation` 由谁写入未核实 `[推测]`：可能由前端/插件直接传 `kind`。
3. **`artifact_access_log` 的读取方未确认**：本子域 24 条端点中无审计查询接口，仓库内除 `artifacts.module.ts`/`core/entities/index.ts`/service 外无引用；「管理端审计查询」是否存在（或由外部 BI 直连 DB）未核实。
4. **DDL 归属未确认**：`artifacts` 模块**无 `migrations/*.sql`**，4 张表依赖外部 schema-sync 作业/插件 DDL 流程生成，生产环境实际索引文本（尤其 4 条部分唯一索引）未在本仓核实。
5. **`artifact.checksum` 的语义未确认**：来源侧 `checksum` 与内容 `sha256` 并存，前者是否参与任何判定（除展示与 `createArtifact` 回写）未核实 `[推测]`：目前仅作为来源去重提示。
6. **`ipHash` 的不可逆性未确认**：实现是裸 `sha256(ip)` 无盐，是否在上游做二次保护未核实 `[推测]`：IPv4 空间可被枚举。
7. **配额相关列未确认**：4 张表内**没有任何配额/用量列**（`accessCount`/`downloadCount` 是计数而非配额），是否存在外部配额表或网关限流未核实。
8. **`workspace-file-access` 的缓存后端未确认**：`CACHE_MANAGER` 的实际 driver（内存 vs Redis）由外部配置决定，多副本一致性表现未在本仓核实。

## 结论

1. 本子域的数据模型是**「4 张表 + 0 张表」的对照结构**：产物侧 4 表承担身份、版本、策略与审计；文件访问侧完全不落表（Cache + cookie），因此它的「模型」其实是 JWT 载荷与两条 Cache 键（`workspace-file-access:session:<id>`、`…:grant:<session>:<grant>`）。
2. 唯一性全部压在索引上（4 + 2 + 2 条唯一/部分唯一），并在服务层以「先查后写 + 冲突重查 + 悲观锁」三层兜底；这也解释了为什么 4 张表没有业务唯一约束之外的复杂校验。
3. 表间只有一条链：`artifact → (version, link) → access_log`，级联删除 + 审计保留（SET NULL）的组合意味着「删产物 = 删版本与链接 + 留审计」。
4. 字节永远不在表里：`workspaceFileRef`（json 非空）是本域与外域唯一的内容通道，也是本子域与「文件理解与记忆专家」的契约面。
