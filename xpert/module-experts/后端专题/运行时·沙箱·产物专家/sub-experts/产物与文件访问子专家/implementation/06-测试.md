## 运行命令

两个子域同一配置（`packages/server-ai/jest.config.ts`，`moduleNameMapper` 直指 `@xpert-ai/*` 源码，无需先构建依赖包）：

```bash
# 1) 只跑本子域四个 spec（按路径）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --runTestsByPath packages/server-ai/src/artifacts/artifacts.service.spec.ts \
                   packages/server-ai/src/artifacts/artifacts.controller.spec.ts \
                   packages/server-ai/src/workspace-file-access/workspace-file-access.service.spec.ts \
                   packages/server-ai/src/workspace-file-access/workspace-file-content.controller.spec.ts

# 2) 按目录 + 用例名过滤（-t）
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --testPathPattern 'src/(artifacts|workspace-file-access)/' -t 'signed preview'
node node_modules/jest/bin/jest.js --config packages/server-ai/jest.config.ts \
  --testPathPattern 'src/workspace-file-access/' -t 'grant'

# 3) Nx 方式（项目名 server-ai）
corepack pnpm exec nx run server-ai:test --runInBand --skipNxCache
```

注意：**不能**用 `packages/server/jest.config.ts` 跑本子域（`runtime-control`/`health` 才属那个配置），跨配置会因 `moduleNameMapper` 不解析内部路径而失败。

## 断言与 mock 风格

- **谁直接用真对象、谁用替身**：`artifacts.controller.spec.ts` 直接 `new ArtifactsManagementController(service as never)` 注入 `jest.fn()` 替身服务，并自建 `responseFixture()`（`headers: Map` + `send/redirect/cookie/clearCookie` jest.fn）来断言**头与副作用**，不涉及真实 Express；service 侧断言调用参数（`toEqual({ artifactId, artifactVersionId })`）。
- **服务级替身面**：`artifacts.service.spec.ts` 以内存 Repository/DataSource 替身驱动 `withLockedArtifact` 分支；`workspace-file-access.service.spec.ts` 自建 `cacheManager` 替身 + 假的 `ViewExtensionService`/`VolumeClient`，断言的是**授权结论与 cookie/URL 形状**，而非文件系统。
- **以「不可信输入」为断言中心**：跨租户 provider 资源、跨 Project dataScope 复用、无 Origin/Referer 的预览、未确认的 `public_link`、键复用不同字节——用例几乎都在验证「**拒绝**」路径是否成立，这是本子域最有价值的测试资产。
- **响应头/纯函数断言**：CSP 两档（interactive 含 `script-src 'unsafe-inline'`、strict 无脚本）、`Content-Disposition` 的 ASCII fallback 与 RFC 5987 编码，都是逐项字符串断言 + `validateHeaderValue` 复核。
- **无 HTTP e2e**：本子域 4 个 spec 都没有起 Nest 应用、没有真实 `supertest`、没有 DB/Redis 集成用例。

## 缺口

1. **`WorkspaceFileAccessGuard.canActivate` 无独立 spec**：cookie 缺失抛 401、`readCookieValue` 的解码回退（`decodeURIComponent` 失败取原值）都没有直接用例；service 层 `authorizeContent` 有覆盖，但 guard 的「把授权挂到 `request.workspaceFileAccess`」这一步没有断言。
2. **`sendWorkspaceFileContent` 的流式分支零覆盖**：`206`/`416`、`Content-Range`、`HEAD` 只发头、`createReadStream` 出错时的 404/`destroy`、`Access-Control-Allow-*` 下发——全部没有 spec（父级 06 也把它列为「纯函数断言」的邻居）。当前唯一相关断言是 `Content-Disposition` 编码。
3. **`assertRequestOrigin` 的分支未逐条覆盖**：同源 iframe fetch 与「仍需有效 cookie/grant」有 2 条用例，但 `download` 无 Origin 分支、`session.origin` 匹配分支、`Vary: Origin` 头未断言。
4. **artifacts 的 410/失效语义未逐条断言**：`revoked`/`expired`/`deleted`/校验和不一致的响应码与 `artifact_access_log.event` 组合没有用例（父级 06 亦记「仅 service + controller 两 spec」）。
5. **审计写入零断言**：`recordAccessLog` / `recordArtifactAccessLog`（含 `try/catch` 静默失败）在 4 个 spec 中无验证点；`ipHash`、`userAgent`、`statusCode` 的落库形状无测试证据。
6. **前缀与装配无 spec**：`setGlobalPrefix` 的 `exclude(['artifacts/share', …])` 造成的「公开分享不在 `/api` 下」这条契约（本批已核实）没有测试固定；`RouterModule.register('/workspace-files')` 的路由形状同样无断言。
7. **MIME 策略文档化缺口**：`artifact-mime-policy.ts` 无独立 spec（SVG 拒登由 service spec 间接覆盖，`getArtifactArchiveMimeType` 的归档降级无断言）。
8. **无集成 / e2e**：没有真实 DB 的多租户越权回归、没有真实缓存的会话失效回归、没有 Range 流式的端到端验证。

## 结论

1. **可跑**：4 个 spec 均为纯单测（替身 Repository / Cache / Volume / View service），用 `packages/server-ai/jest.config.ts` 直接可执行，不依赖 PG/Redis/网络/卷；`nx run server-ai:test` 与直接 jest 等价。
2. **覆盖结构不对称**：**授权与幂等**（
`public_link` 确认、签名预览、跨租户/跨 Project 拒绝、键复用拒绝）覆盖得很好；**传输与响应**（Range、HEAD、审计落库、guard 交互、路由前缀）几乎空白。
3. **本子域最需要补的三类用例**：① `WorkspaceFileAccessGuard` + `sendWorkspaceFileContent` 的守卫/流式单测；② artifacts 的 410/失效 + 审计事件用例；③ 路由前缀（`exclude`）与 `RouterModule` 装配的形状断言——这三类都是「一旦被改动就是安全事故或文档漂移」的地方。
4. **本轮不实跑**：仅给出命令与判据；`it` 计数来自 `.spec.ts` 源码静态统计（实测 29 个），与父级 06 「artifacts 2 / workspace-file-access 2」的 spec 数口径一致。
