## 沙箱创建与执行链
**准入与后端获取**：HTTP 侧没有「执行任意命令」的通用端点（唯一例外是 `POST terminal` 的 SSE）。主链路是 `SandboxConversationContextService.resolveConversationSandbox` → `authorizeConversation`（会话必须存在、`conversation.tenantId` 必须等于当前租户、助手 `features.sandbox.enabled` 必须为真、`features.sandbox.provider` 必须非空、群会话另走 `ResolveGroupRuntimeAccessCommand`）→ `resolveSandbox(context, true)` 组装并派发 `SandboxAcquireBackendCommand`；`findExistingSandbox` 走同一解析但**不申请**后端。工作区形态由 `sandbox-work-for.ts` 与 `XpertWorkAreaResolver` 决定，项目态会自动打开 `protectProjectContent`。
**运行时创建**：`SandboxAcquireBackendHandler` 落到 `SandboxProviderRegistry`，生产实现是 `NsjailSandboxProvider.create`：先读 `NSJAIL_RUNNER_URL`/`NSJAIL_RUNNER_TOKEN`（缺一即抛 `NsJailRunnerNotConfigured`）→ 要求 `workspaceBinding.volumeRoot` → 取 Runner `/health`（5 秒缓存 + 并发合流）→ 项目态校验协议 2（`projectContentReadOnly`），**所有**运行时校验协议 3（`appDataProtection`）→ 计算稳定 `runtimeId`（sha256 截 32 位）→ `POST /v1/runtimes`。创建失败只有两种分类：配置/协议不满足（永久）与健康探测失败（Runner 不可用）。
**执行与流式**：`NsjailSandbox.execute` 与 `streamExecute` 都包在 `withRuntimeRecovery` 里（runtime 被判 not-found 时重建并递增 generation，不吞其它错误）；`NsjailRunnerClient` 把超时对齐为 `timeoutMs + RUNNER_GRACE_PERIOD_MS`，并把 `408/429/5xx`、`TypeError`、`NsjailRunnerTimeoutError` 判为可重试，其余为永久错误。
**作业链（更重的路径）**：`SandboxJobRuntimeCapabilityService.run` 的顺序是「解析可运行动作与定义 → `findIdempotent`（命中 `succeeded` 直接复用；命中 `waiting/starting/running` 则 `waitForAttachedJob` 附着，等待心跳 30 秒、TTL 120 秒，`lost` 则递归重跑）→ `cleanupPending` 时先 `requirePreviousAttemptCleanup` → `bindingSelector.require`（含只读文件挂载需求）→ `prepareAttempt`（输入快照到 `.platform/inputs`，输入/输出各自上限 350 MB）→ `capacity.acquire`（Redis Lua 同时占 global/tenant/user 三档配额，默认 20/4/2）→ `execute` → 校验输出并写 `runtimeArtifactKind|Reference|Digest`、`outputs`、`errorCode/errorMessage` → `finally capacity.release`」。
**超时 / 取消 / 清理**：`hardDeadlineAt` 来自定义的 `hardDeadlineMs`（注册表要求 `timeoutMs ≤ hardDeadlineMs`），等待期用 120 秒心跳续期；`cancel()` 置 `cancelled` + 尝试 `runtime.terminate()` + `destroySandbox` + `cleanupVolume`；`onModuleInit` 立刻跑一次并每 60 秒 `cleanupOrphans`（扫 `hardDeadlineAt < now` 与 `cleanupPending: true`），定时器 `unref()`。
章节来源：[sandbox-conversation-context.service.ts](file://packages/server-ai/src/sandbox/sandbox-conversation-context.service.ts)（关键符号：SandboxConversationContextService.authorizeConversation）、[nsjail-sandbox.provider.ts](file://packages/server-ai/src/sandbox/nsjail/nsjail-sandbox.provider.ts)（关键符号：NsjailSandboxProvider.create）、[sandbox-job-runtime-capability.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job-runtime-capability.service.ts)（关键符号：SandboxJobRuntimeCapabilityService.run）、[sandbox-job-capacity.service.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-job-capacity.service.ts)（关键符号：SandboxJobCapacityService.acquire）、[sandbox-runtime-definition.registry.ts](file://packages/server-ai/src/sandbox/sandbox-job/sandbox-runtime-definition.registry.ts)（关键符号：SandboxRuntimeDefinitionRegistry）

## WS 终端网关
`@WebSocketGateway({ namespace: 'sandbox-terminal', cors: { origin: '*' } })`，实现 `OnGatewayDisconnect`。**4 类客户端消息**（契约枚举 `SandboxTerminalClientEvent`）：`open`（`conversationId`+可选 `projectId`+`requestId`+cols/rows）、`input`（`sessionId`+data）、`resize`、`close`（按 `sessionId` **或** `requestId` 二选一）。**5 类服务端事件**（`SandboxTerminalServerEvent`）：`opened`（provider/sessionId/workingDirectory）、`output`、`exit`（exitCode/signal）、`error`、`closed`（六种 `reason`）。
**实现要点**：① 每个 handler 都挂 `@UseGuards(SandboxTerminalAuthGuard)`，即**每条消息重新鉴权**（`cs-x-` 前缀走 client-secret 分支，否则走 `WsJWTGuard`；都要过 `assertWorkbenchPrincipal`；`open` 额外查库确认会话存在并复核助手范围）；② WS 不经过 HTTP 请求上下文中间件，因此 `open` 用 `runWithCapturedRequestContext` 把认证主体与 `organization-id` 手工塞进上下文，再调 `resolveConversationSandbox`；③ `open` 用「pending open」对象实现取消：先注册、后解析，任何阶段发现 `canceled` 就关闭已建会话并静默返回；重复 `requestId` 会把旧对象标记取消；④ 会话表在进程内存（`#sessions`、`#pendingOpens`），`handleDisconnect` 逐个以 `SocketDisconnected` 关闭；⑤ 输出走 `client.emit(Output)` 直接透传，不缓冲；⑥ 错误统一经 `normalizeError` 归一化（识别 `code`/`message` 形态与 Nest `getResponse()`），失败关闭只 `logger.warn` 不抛。
**超时语义**：网关自身**没有空闲超时**；终端存活由 Runner 的进程边界（超时/销毁即终止）与「进程退出 → `onExit` → `exit`+`closed`」决定，客户端 `input` 之后若会话已被移除只回 `SessionNotFound`。
章节来源：[sandbox-terminal.gateway.ts](file://packages/server-ai/src/sandbox/sandbox-terminal.gateway.ts)（关键符号：SandboxTerminalGateway.open）、[sandbox-terminal-auth.guard.ts](file://packages/server-ai/src/sandbox/sandbox-terminal-auth.guard.ts)（关键符号：SandboxTerminalAuthGuard.canActivate）、[sandbox-terminal.model.ts](file://packages/contracts/src/ai/sandbox-terminal.model.ts)（关键符号：SandboxTerminalClientEvent）

## 预览 proxy
**发牌**：`POST conversations/:conversationId/services/:serviceId/preview-session` 调 `SandboxPreviewSessionService.createSession(service, { secure })`——要求服务 `status==='running'` 且 `transportMode==='http'` 且有 `previewUrl`，否则抛 `SandboxManagedServiceError(PreviewUnavailable, 400)`；成功后写 cookie `xpert_sandbox_preview`（`httpOnly`、`sameSite:'lax'`、`path` 精确到 `.../services/<serviceId>/proxy`、TTL 1 小时、`secure` 由 `request.secure` 或 `x-forwarded-proto` 推导）并返回 `expiresAt`/`previewUrl`。
**三条 `@Public()` 路由**：`@All('.../proxy')`、`@All('.../proxy/')`、`@All('.../proxy/*path')`，都被 `SandboxPreviewAuthGuard` 接管：无 cookie 401「Sandbox preview session is required.」；有 cookie 则 `verifySession`（`aud='sandbox-preview'`，`sub='sandbox-preview-session'`，`conversationId`/`serviceId` 必须与路由参数相等），任一不符 401。secret 缺失（`JWT_SECRET` 未配）直接 500，**不降级为放行**。
**转发**：`SandboxManagedServiceService.proxyByConversationId` 先查服务与会话上下文（会真正解析沙箱），再取 provider 的 `SandboxServiceProxyAdapter`；转发前**原地替换** `request.headers`/`headersDistinct`/`rawHeaders` 为清洗后的副本（注释：平台凭证与预览会话 cookie 不得进入任何 provider 后端），并劫持 `response.setHeader` 丢弃 `set-cookie`、`service-worker-allowed`，把 `location` 重写到 proxy 基路径；`finally` 还原三者。Runner 侧只进入该服务的网络命名空间，空闲上游响应默认 60 秒关闭，且**当前开源预览控制器不代理 WebSocket 升级**（Vite HMR 需后续工作）。

## volume 通配路由
**真实用途**：`GET volume/*path` 是**容器/沙箱卷的公开投递口**，供已发布预览、静态资源、运行时作业产物等「不需要登录就该能看」的资源直接取字节。它标 `@Public()`，即**不要求 JWT**，靠路径前缀与租户推导工作：`tenant` 可来自 query，否则取 `RequestContext.currentTenantId()`，再退回 `GetDefaultTenantQuery` 的默认租户，最后 `assertValidVolumeScopeId` 校验为单段标识；dev 环境先做 `normalizeSandboxPublicVolumeSubpath` 归一。
**护栏（如实记全部）**：① 请求路径先 `normalizeSandboxVolumeRequestSubpath`；② 进入前与归一后各做一次 `isProtectedVolumeSubpath`，命中 `project/*`、`user/*/xpert/*`、`xpert/*/user/*`、`runtime-jobs/*` 即 403；③ `serveVolumeFile` 内 `assertPublicWorkspacePath(subpath)`；④ 用 `openFileSnapshot` 打开后再按**实际卷内相对路径**复检 `rejectProtectedPaths`（防符号链接别名绕过）；⑤ 目录/非普通文件 404；⑥ 支持 `Range`（部分内容 206、越界 416）。
**风险（必须如实）**：**未登录者可读公共卷前缀**；没有审计记录（`artifact_access_log` 只管 artifact）；没有速率限制；`tenant` 参数存在但只用于定位卷根，不构成授权；安全性完全依赖「公共前缀不含敏感数据」这一运维假设。相邻的**私密**路由（`volume/project/:projectId/*path`、`volume/user/:userId/xpert/:xpertId/*path`、`volume/xpert/:xpertId/user/:userId/*path`）没有 `@Public()`，走全局 `AuthGuard`，且项目路由还会 `assertCanRead(projectId)` 并拒绝跨租户 `tenant` 参数。
章节来源：[sandbox.controller.ts](file://packages/server-ai/src/sandbox/sandbox.controller.ts)（关键符号：SandboxController.getVolumeFile）、[sandbox.controller.ts](file://packages/server-ai/src/sandbox/sandbox.controller.ts)（关键符号：SandboxController.serveVolumeFile）

## runtime-control 六端点
`@Controller('system/runtime')` + 类级 `@UseGuards(TenantPermissionGuard)`，**无 RouterModule**，前缀直接写在装饰器上。
1. `GET instances`：额外 `RoleGuard`+`@Roles(SUPER_ADMIN)`，服务层先 `assertAuthorizedActor()`，返回 `InstanceRegistryService.getRegisteredInstanceDetails()`（实例/副本注册表）。
2. `POST instances/:instanceId/retire`：同样 SUPER_ADMIN，body 走 `whitelist+forbidNonWhitelisted` 校验并携带 `expectedBootId`，成功后写一条结构化审计日志（`event: runtime.instance.retirement`，含 actorUserId/tenantId/sourceIp），返回 `IRuntimeInstanceRetirementResult`。
3. `GET restart-capability`：**无 RoleGuard**，纯读：先看 `RequestContext.currentApiKey()`（有 API Key 即 `interactive-auth-required`），再看是否 SUPER_ADMIN，再看是否默认租户，返回 `{allowed, mode: 'rolling-self-signal', reason}`。
4. `GET restart/:restartId`：读协调器状态，缺失 404 `RUNTIME_RESTART_NOT_FOUND`。
5. `GET plugin-convergence/:generation`：`ParseIntPipe` 解析代数，读插件收敛状态，缺失 404 `PLUGIN_RUNTIME_CONVERGENCE_NOT_FOUND`。
6. `POST restart`：`RoleGuard`+SUPER_ADMIN+`@HttpCode(202)`，body 必须带 `confirmation === RUNTIME_RESTART_CONFIRMATION`，否则 400 `RUNTIME_RESTART_CONFIRMATION_REQUIRED`；随后 `assertAuthorizedActor()` 三重断言（交互式会话 / SUPER_ADMIN / 默认租户），再交 `RuntimeRestartCoordinatorService.requestRestart({source:'interactive', allowDowntime?, reason?, runtimeRequirements?})`。
**影响面**：一次重启请求会经过「协调器收集目标 → 逐副本 `RuntimeLifecycleService.beginDrain`（drain 单例，重复进入返回 false）→ 排水期间 `RuntimeDrainMiddleware` 对非 `/health` 请求回 503 并带 `Retry-After: 5` → 关闭队列（`RuntimeQueueShutdownService` 用 `DiscoveryService` 发现 `Bull`/`WorkerHost` 并 pause/close）→ `process.kill(process.pid, signal)`」，由 PM2/容器监管者拉起新进程；`beforeApplicationShutdown` 会 `waitForIdle(1_000)` 给 SSE 最后一个写机会。`runtime-rollout-policy.ts` 额外规定排队变更不得改写候补副本的准入清单（`replacementAdmission` 要求 `phase==='rolling'`、非 `preparing`、无 failed 目标且在副本重启超时内）。

## 健康检查
`GET /health/ready`：直接 `RuntimeLifecycleService.readiness()`，非 `ready` 置 503，并总是 `Cache-Control: no-store`（避免编排层缓存就绪结论）；它**不查任何外部依赖**，语义纯粹是「本进程是否愿意接流量」。
`GET /health`：`@Public()`，每次生成一个 `HealthCheckExecutionTimer-<uuid>` 计时标签，按四个**硬编码为 true** 的开关依次塞入检查函数：DB → 磁盘 → 缓存 → Redis；最后由 `HealthCheckService.check(checks)` 聚合。
- **DB**：默认走 `userRepository.count()`（`checkDbWithTerminus = false`，注释说明 MikroORM 下 Terminus DB ping 有连接相关问题）；异常时 `return { database: { status: 'down', message } }`——**返回体不抛错**。
- **磁盘**：`disk.checkStorage('storage', { path: resolve(__dirname), thresholdPercent: 99.999999 })`；异常同样返回 `{ disk: { status: 'down' } }`。
- **缓存**：`CacheHealthIndicator` 写入随机键再读回比对，不一致抛 `HealthCheckError`（会在聚合里真正变成失败）。
- **Redis**：仅当 `REDIS_ENABLED === 'true'` 才加入检查，构造期异步建连，做一次 set/get 往返，失败抛 `HealthCheckError`（该 indicator 自带 TODO 说明关停时未 disconnect）。
**失败语义小结**：缓存/Redis 失败可让聚合失败；DB 与磁盘失败被吞成状态字段，**不会**让 `/health` 非 200（`[推测]`——依据代码路径与 Terminus 语义推断，未做运行时验证）；排水期间本路径被 `RuntimeDrainMiddleware.isHealthRequest` 正则豁免，因此重启期间 `/health` 仍可用。

## 工作区文件访问授权
**两段式授权**：`POST /workspace-files/view-sessions` → `createSession`：解析视图文件访问上下文（`resolveViewFileAccessContext`，hostType/hostId/viewKey + 可选 runtimeScope）→ `assertAssistantFileAccess` → 生成 `sessionId` 并把 session 记录写缓存（TTL 1 小时）→ 签发 JWT cookie `xpert_workspace_file_access`，cookie `path` 限定到该会话的内容前缀、`httpOnly`、`sameSite:'lax'`、`secure` 由请求推导。`POST view-sessions/:sessionId/grants` → `createGrant`：`requireAuthenticatedSession` → `resolveViewFileResource`（服务端解析出真实文件引用）→ `assertContextMatchesSession`（租户/组织/用户/host/view/dataScope 必须与 session 完全一致）→ `assertPortableReference`（必须是 Workspace Files 便携引用）→ grant 记录写缓存，到期时间**跟 session 走**（不独立续期），返回内容 URL/文件名/MIME/大小。
**读取**：`content` 控制器是类级 `@Public()`＋`@UseGuards(WorkspaceFileAccessGuard)`，只有 `GET`/`HEAD` 两条路由。guard 从 cookie 取 token → `authorizeContent(sessionId, grantId, fileName, token)`（校验 JWT 与缓存 session 一致、未过期、grant 存在且与请求文件名匹配）→ 把授权结果挂到 `request.workspaceFileAccess`。控制器随后做 `assertRequestOrigin(session, request, grant.purpose)`（按用途校验来源）、`resolveAuthorizedFile`（`resolveWorkspaceVolumeScope(grant.reference, …)` 复用 file-understanding 的解析 → `volumeClient.resolve(...)` → 再断言一次便携引用），最后 `sendWorkspaceFileContent` 设置 `Cache-Control: private, no-store` 与 `X-Content-Type-Options: nosniff` 并流式返回。**鉴权下载**另有 `GET view-sessions/:sessionId/grants/:grantId/content/:fileName`（走登录态 `authorizeAuthenticatedDownload`），`DELETE view-sessions/:sessionId` 撤销会话并清 cookie。
**约束**：路径由服务端从 grant 的 `reference` 解析，**客户端不能传路径**；fileName 参与匹配但不参与拼路径；session/grant 全在缓存，进程重启即失效。

## 热点路径
1. **`resolveConversationSandbox` 是全域最热的入口**：卷路由、文件上传、SSE 终端、托管服务 12 条、预览 proxy、WS 终端 `open` 全部先走它；`authorizeConversation` 要查会话（带 `xpert` 关系）、校验租户/用户/特性开关/provider，`resolveSandbox(true)` 还可能真的申请运行时——**预览 proxy 每次请求都解析一次沙箱上下文**，是「静态资源托管在沙箱内」场景下的第一成本项。
2. **作业执行事务段**：`run` 内「幂等查询 → 附着等待（最多按 `hardDeadlineMs` 等）→ 绑定选择 → 输入快照复制（1 MB 缓冲）→ Redis 容量租约」串行发生，容量不足会让请求**在拿到 lease 前**长时间挂住（`waitForCapacity`）。
3. **终端轮询**：`NsjailTerminalSession.poll` 在未退出前持续 `GET` 轮询 Runner，失败走指数退避到上限——长连接终端会按「每个终端一条轮询循环」占用 API 侧 I/O。
4. **卷投递**：`serveVolumeFile` 每个请求都要 `openFileSnapshot` + `fstat` + 可能的 Range 流式；公共卷被打满时没有限流门。
5. **`/health`**：每次调用都跑 DB `count()` + 磁盘 stat + 缓存 set/get 往返 +（可选）Redis 往返，并打印多行 `console.log`；编排层探针频率决定它的成本。
6. **公开 Artifact 读取**：`readWorkspaceArtifact` 会把整个文件读进内存并算 `sha256`（预览与下载都如此），大产物是内存峰值来源。

## 技术债与 hack
1. **定时清理是空壳**：`SandboxService.cleanCron` 用 `@Cron('0 0 * * * *')` 却只 `logger.debug('Called when the current second is 45')`——表达式与日志文案互相矛盾，实际清理靠 `cleanupOrphans` 与 Runner 侧 TTL。
2. **`sandbox_job.containerRef` 已废弃**：实体注释逐字 `/** @deprecated Read-only compatibility evidence. New attempts write runtimeRef. */`，新旧字段并存需要读侧双写兼容。
3. **遗留 HTTP 沙箱客户端无对手方**：`client.ts` 的 `SandboxFileSystem` 打 `/file/`、`/shell/exec/`、`/python/exec/`、`/browser/`，但本仓库扫描范围内**未找到对应服务端实现**，属悬空兼容层。
4. **`POST terminal` 与 `@Sse()` 组合**：同一路由同时挂 `@Post('terminal')`、`@Header('content-type','text/event-stream')` 与 `@Sse()`，是非标准用法，客户端必须按 POST + SSE 解析。
5. **cookie 手工解析重复三处**：`SandboxPreviewAuthGuard`、`WorkspaceFileAccessGuard`、`SandboxTerminalAuthGuard`（走 handshake）各写一遍取值逻辑，语义一致但实现分散。
6. **查询面未落地**：`queries/index.ts` 为空目录，控制器却注入 `queryBus` 并执行 `GetDefaultTenantQuery`——域内查询 handler 的缺失让「查询」这件事散落在服务方法里。
7. **模块前缀风格不一致**：sandbox / workspace-file-access 用 `RouterModule.register`，artifacts / health / runtime-control 把前缀写死在 `@Controller(...)`；统计路由时必须两处都看。
8. **`health` 零测试**：5 个文件、0 个 spec，却决定编排层是否重启 Pod；`checkDbWithTerminus` 默认关闭的注释说明历史上踩过 MikroORM + Terminus 的坑。
9. **`[推测]` DB/磁盘失败被吞**：两分支在异常时 `return { status: 'down' }` 而非抛错，按 Terminus 语义这些「down」很可能被当作正常结果合并；若成立，则 `/health` 对 DB 与磁盘实际不可用是**静默**的。未做运行时验证。
10. **`[推测]` 附件保护的远程调用**：`README.md` 明示「API rejects older Runners」「先升级镜像再升级 API」，意味着滚动升级期间旧 Runner + 新 API 会让**所有** `create()` 失败（协议 3 是硬门槛），回滚窗口很窄；具体失败面未做实测。
11. **`@Public()` 通配卷无审计与限流**：anonymous 读面无法从日志侧追溯，也没有速率限制（见 §4）。
12. **`LocalBrowserRuntimeProvider` 的存在方式**：模块用 `isDevelopmentSandboxRuntimeEnvironment()` 三元表达式决定 provider 列表，注释强调「never a production fallback」——但同一份代码在开发环境跑的正是本机进程（`local-runtime-process.ts` 的 `timeoutMs/maxOutputBytes/cwd/env` 选项），与生产隔离度差异极大。

## 设计维度分析
**隔离强度 vs 开发便利**：生产侧把「不可信」做到极致——独立特权 Runner、只读 rootfs、seccomp、cgroup、只读 Project Content 覆盖挂载、`.apps` 只读掩码，代价是**每个 execute/终端/托管服务各起一个 NsJail 进程边界**且需要真实的 cgroup v2 委托（否则 Runner 直接 fail fast，而非静默降级）。开发侧则反过来信任宿主：`Local Shell` 明示「trusted development execution」，本机浏览器运行时只探测本机 CLI。两边共享同一套 provider 抽象与同一批中间件工具，**同一段 Agent 代码在两种隔离度下都能跑**，这正是把 `NsjailSandboxProvider` 做成策略而非 if 分支的价值。
**授权面的三种粒度**：本域同时存在三种授权风格——全局守卫 + 类级声明（sandbox、artifacts）、类级守卫 + 方法级角色（runtime-control）、类级 `@Public()` + 自定义 cookie guard（workspace files content、预览 proxy）。第三种必须小心：`@Public()` 只是「跳过 JWT」，真正的准入在 guard 里；而 volume 通配是**唯一**只跳过 JWT、不再补任何身份的端点，因此它实质上是"公共资源 CDN 语义"。三者混用带来的后果是：审计「谁能读」时必须同时查全局守卫、类级装饰器、方法级 guard 与 route 形态。
**字节归属 vs 引用登记**：本域所有持久化都不存字节——`artifact_version.workspaceFileRef`、`sandbox_job.runtimeArtifactReference`、托管服务日志路径（`.xpert/managed-services/<id>/{stdout,stderr}.log`）全是引用或路径。好处是备份/迁移轻、跨卷复用；代价是**一致性必须靠校验补**：artifact 每次公开读取都重算 sha256，不符即拒绝并记 `denied`。这是一种明确的取舍：把「内容正确」的验证成本从写入期推到读取期。
**生命周期所有权分层**：`.deploy/nsjail-runner/README.md` 逐字界定了权属——「Xpert still owns provider selection, workspace binding, terminal routing, managed-service records, and preview authorization」，Runner 只做进程边界与资源限制，且「RPC 请求不能选择挂载、宿主 PID、NsJail 参数或可执行文件」。结果是：**任何扩展沙箱能力的改动都必须在 Nest 侧加协议字段**，无法从请求里透传，安全边界不被客户端可影响；反面是协议版本成为升级瓶颈（协议 2/3 是硬门槛）。

## 结论
实现上，本域把「执行」与「交付」都做成了**短时、可撤销、可审计**的链路：沙箱运行时用稳定 runtimeId + `withRuntimeRecovery` 换取「同一工作区重复命令不换身份」，作业用幂等键 + 容量租约 + 硬截止 + 孤儿清理换取「重试安全、并发可控、崩溃可收敛」，托管服务用台账 + proxy 头清洗换取「预览不泄平台凭证」，产物用四张表 + 便携引用 + sha256 复核换取「登记幂等、字节外置、读取可验证」，文件访问用「会话 + grant」两段式换取「客户端永远不传路径」。
需要重点防守四处：① volume 通配 `@Public()` 是全域唯一「跳过 JWT 且不补身份」的路由，公共卷前缀就是事实上的公开面；② 预览 proxy 每次请求都解析沙箱上下文、并依赖 cookie 路径前缀这一「弱隔离」，跨服务 cookie 混淆只能靠 `conversationId`/`serviceId` 比对兜住；③ `SandboxConversationContextService` 的申请语义（`resolve*`）与被动语义（`findExisting*`）必须继续分清，否则「看一眼列表就复活沙箱」；④ 健康探针的 DB/磁盘失败很可能被静默吞掉，而它是编排层唯一的判断依据。新增能力时的正确骨架是：走命令入口 → 在 Runner 侧加协议能力位并在 `create()` 前置校验 → 产物只登记引用 + digest → 对外投递一律走「短时签名 + 最小范围」。
