## D1 启动超时是致命错误，且失败日志不记录插件配置与异常文本

- **分类**：启动可靠性与可观测性边界。
- **动机（避坑）**：现象——某个插件生命周期 hook 在默认 30s 内未返回；后果——超时的 hook 仍可能已经改动进程状态（注册表、定时器、文件、连接），若进程照常进入就绪，就会以半初始化状态对外服务，且后续排查无法区分「加载完成」与「hook 卡住」。
- **决策**：所有生命周期 hook 由 `runPluginStartupStep(name, stage, action, timeoutMs = 30000)` 包裹，超时抛 `PluginStartupTimeoutError`（`code = 'PLUGIN_STARTUP_TIMEOUT'`）并使进程不得进入就绪；失败日志只输出 `event` / `pluginName` / `stage` / `durationMs` / `code`，**不输出插件配置与异常文本**。
- **背景约束**：插件配置可能承载凭据；异常文本同理。因此日志不是排障主通道，排障必须依赖 `code` + `stage`、`loadFailures` 上报与副本私有快照。
- **被否决方案**：无（源码未记录候选方案，只以注释形式固定不变量）。
- **重新评估触发条件**：需要在不降低安全性的前提下缩短排障时间（例如引入可脱敏的结构化错误码域）；或插件生态普遍出现接近 30s 的合法初始化。
- **关联代码**：[plugin-startup-step.ts](file://packages/server/src/plugin/plugin-startup-step.ts)、[plugin.module.ts](file://packages/server/src/plugin/plugin.module.ts)、[plugin-runtime-state.service.ts](file://packages/server/src/plugin/plugin-runtime-state.service.ts)。
- **证据来源**：`plugin-startup-step.ts` 顶部注释「Startup timeouts are fatal: a timed-out hook may still mutate the process, so it cannot serve traffic.」与失败分支注释「Do not log plugin configuration or arbitrary exception text which can contain credentials.」

## D2 启动快照副本本地私有、绝不改写期望 DB 配置；候选 boot 只尝试一次；DB migration 必须向后兼容

- **分类**：多副本一致性与回滚安全。
- **动机（避坑）**：现象——上一次重启因某插件候选配置失败；后果——若把「回滚」实现为改写期望配置，多副本会各自回滚到不同状态、人工修复必须反写 DB，且失败进程可能进入崩溃循环。
- **决策**：快照按副本（`XPERT_INSTANCE_ID` / `HOSTNAME` 派生）落在本地、权限收紧、内容用 `__xpert_plugin_encrypted__` 信封加密，且**永不写回期望的数据库配置**；未完成的候选 boot 只尝试一次，随后由 supervisor 恢复上次被接纳的配置；快照只恢复代码与配置，**DB migration 必须保持向后兼容**。
- **背景约束**：回滚后的旧代码会读新 schema，因此迁移不能依赖「只有新版代码理解」的列语义；恢复耗尽的进程以 keep-alive 阻塞而非崩溃退出，避免被 orchestrator 反复重启。
- **被否决方案**：把快照内容或回滚结果写回期望 DB 配置（被「never change the desired database configuration」直接否定）。
- **重新评估触发条件**：引入集中式配置中心并需要跨副本统一回滚；或决定允许破坏性迁移（此时必须先取消本不变量并给出回滚窗口）。
- **关联代码**：[plugin-startup-state.ts](file://packages/server/src/plugin/plugin-startup-state.ts)、[runtime-plugin-admission.ts](file://packages/server/src/runtime-control/runtime-plugin-admission.ts)、[plugin-startup-watchdog.ts](file://packages/server/src/plugin/plugin-startup-watchdog.ts)。
- **证据来源**：`plugin-startup-state.ts` 顶部三行不变量注释；`runtime-plugin-admission.ts` 中「New/returning boots are fenced until current, or explicitly restored after a failed candidate.」

## D3 注册链顺序不可颠倒：先合并 ORM metadata → 再 lazyLoad → 最后注册路由与策略

- **分类**：动态装配时序（框架级脆弱契约）。
- **动机（避坑）**：现象——先 `lazyLoader.load()` 再合并实体；后果——插件的 Repository 在活 `DataSource` 里没有元数据，任何查询立即 `EntityMetadataNotFoundError`；现象——路由注册顺序错；后果——插件 controller 挂到尾部 404 处理器之后，表现为「装成功但全 404」。
- **决策**：`PluginManagementService` 固定执行 ① `collectPluginOrmMetadata` + `validatePluginEntityTableNames` + `registerPluginOrmMetadataInDataSource`（声明 namespace 时表名前缀必须匹配 `plugin_<namespace>_`），② `snapshotModuleIds` / `snapshotHttpRouteStack` 后 `lazyLoader.load(...)`，③ `registerPluginControllerRoutes`（把新 Express 层移到 404/错误处理器之前）+ `registerInstalledPluginStrategies` + 手动 `onPluginBootstrap`。注册只刷新 metadata，**DDL 由加锁的 schema preflight 独占**（Redis 锁 `xpert:plugin:schema-sync`）。
- **背景约束**：宿主没有 `migrations/` 目录，宿主表走 synchronize 式建表；插件自带实体只能运行期合并 + preflight 建表；重名实体直接抛 `ConflictException`，禁止静默覆盖宿主表。
- **被否决方案**：无（源码以不变量注释固定顺序，未记录候选方案）。
- **重新评估触发条件**：Nest 的 `LazyModuleLoader` 或 Express 栈结构变更导致 `snapshotHttpRouteStack` / `moveNewExpressLayersAheadOfTailHandlers` 失效；或引入真正的按插件独立 DataSource 方案。
- **关联代码**：[plugin-management.service.ts](file://packages/server/src/plugin/plugin-management.service.ts)、[plugin-orm-metadata.ts](file://packages/server/src/plugin/plugin-orm-metadata.ts)、[plugin-http-routes.ts](file://packages/server/src/plugin/plugin-http-routes.ts)、[plugin-schema-sync.service.ts](file://packages/server/src/plugin/plugin-schema-sync.service.ts)。
- **证据来源**：`plugin-management.service.ts` 顶部三条 Invariants；`plugin-orm-metadata.ts` 顶部「Why this exists」注释（含 `EntityMetadataNotFoundError`）。

## D4 启动恢复与运行期安装必须收敛到同一 staging 路径语义

- **分类**：数据所有权与重启可复现性。
- **动机（避坑）**：现象——`source === 'code'` 的插件在重启后直接沿用磁盘上的旧拷贝；后果——工作区源已变而进程加载的是过期代码，且失败现场无法复现；同时 `packageDir` 是瞬态字段，落库前被剔除，DB 里根本不存在可用目录。
- **决策**：启动恢复与运行期安装必须收敛到**同一套**目录结构与 manifest 语义；带持久化 `workspacePath` 的本地 code 插件在加载前必须重新 stage（`stageWorkspacePlugin` / `stagePackageDirectoryPlugin`，realpath + 白名单 + 包名匹配 + 必须含 `dist/` / `src/index.ts` 或编译入口）；非 code 插件统一走组织插件 store 与 manifest，load-failure 追踪集中在一处。
- **背景约束**：`packageDir` 只允许服务端归档上传路径传入（`allowPackageDir`），HTTP 不可携带；重启时不得依赖磁盘残留。
- **被否决方案**：让重启沿用上一次 staging 的磁盘结果（注释明确否定：「so restarts do not depend on stale copies」）。
- **重新评估触发条件**：引入内容寻址的插件缓存（指纹可验证）从而允许跨重启复用同一份拷贝；或插件运行时不落在文件系统上。
- **关联代码**：[plugin.helper.ts](file://packages/server/src/plugin/plugin.helper.ts)、[organization-plugin.store.ts](file://packages/server/src/plugin/organization-plugin.store.ts)、[source-config.ts](file://packages/server/src/plugin/source-config.ts)、[plugin-instance.loader.ts](file://packages/server/src/plugin/plugin-instance.loader.ts)。
- **证据来源**：`plugin.helper.ts` 顶部 Invariants（「Startup restore and runtime install must converge on the same staged plugin path semantics.」）。

## D5 App 安装用唯一 `scopeKey` 作数据库并发锁

- **分类**：并发控制与幂等。
- **动机（避坑）**：现象——用户在多浏览器 / 多会话重复点「初始化」，或进程崩溃后重试；后果——重复创建 Workspace、Assistant、知识库，产生无法自动归并的孤儿资源。
- **决策**：`plugin_application_installation` 上 `(tenantId, pluginName, appName, scopeKey)` 唯一；`scopeKey` 取 organizationId。插入成功者即「认领者」，唯一索引冲突被捕获后回读现状并返回，不再创建资源；`configuring` / `failed` / `degraded` 行可被修复式接管，`initializing` 行 5 分钟后允许被第二个请求接管。
- **背景约束**：认领的容错依赖数据库唯一索引而非分布式锁；并发正确性完全建立在 PostgreSQL 唯一约束上。5 分钟接管窗口是启发式，长耗时初始化（多知识库 + 套件）可能被误判为「进程已崩」。
- **被否决方案**：无（源码未记录候选方案）。
- **重新评估触发条件**：出现真实的长耗时初始化被 5 分钟窗口误接管；或需要支持多组织并发安装同一 App 时的细粒度资源键。
- **关联代码**：[plugin-application-installation.entity.ts](file://packages/server-ai/src/plugin-resource/plugin-application-installation.entity.ts)、[plugin-application.service.ts](file://packages/server-ai/src/plugin-resource/plugin-application.service.ts)（`claimInstallation`）、[plugin-application-setup.service.ts](file://packages/server-ai/src/plugin-resource/application-setup/plugin-application-setup.service.ts)。
- **证据来源**：实体类 JSDoc「The unique scope key is the database concurrency lock that prevents duplicate resources when users retry or initialize from multiple browser sessions.」；`claimInstallation` JSDoc「an initializing row becomes reclaimable after five minutes so a crashed process cannot deadlock it.」

## D6 package scope 是授权边界，runtime policy 是独立能力，两者不可互相推导

- **分类**：授权模型正交性。
- **动机（避坑）**：现象——用「包声明的 level」去推断「能否热装」；后果——把授权结论当成能力结论：一个 tenant 级包被误当成必须重启（能力误判）或反之被热装（进程内状态与授权面不一致）。
- **决策**：`PluginLevel`（包归属与可见性）与 `runtimePolicy`（install / update / uninstall 各自 `hot` 或 `restart`）是两个正交维度：`requiresPluginRestart` 在插件声明了 policy 时**只用 policy**，未声明时才回退到历史契约（system / tenant 需重启、organization 热加载）。读取侧再由 `effectiveLoadedPlugins` 按「当前组织 → 本租户全局 → 系统全局」收敛可见插件集合。
- **背景约束**：`runtimePolicy` 必须三键齐全且取值合法，否则 `parsePluginRuntimePolicy` 直接抛 `PluginRuntimePolicyInvalid`；运行期若 policy 变化另有 `PluginRuntimePolicyChanged` 错误码。
- **被否决方案**：无（注释只声明「二者独立」，未记录候选方案）。
- **重新评估触发条件**：需要为已安装插件做在线策略迁移（把 restart 插件改成 hot）时的迁移语义定义；或出现同一包在不同 scope 需要不同 policy 的需求。
- **关联代码**：[plugin-runtime-policy.ts](file://packages/server/src/plugin/plugin-runtime-policy.ts)、[plugin-uninstall.service.ts](file://packages/server/src/plugin/uninstall/plugin-uninstall.service.ts)、[effective-loaded-plugins.ts](file://packages/server-ai/src/plugin-resource/effective-loaded-plugins.ts)。
- **证据来源**：`plugin-runtime-policy.ts` 首行注释「Package scope is an authorization boundary; runtime policy is a separate, explicit capability.」及 `requiresPluginRestart` 中的回退注释。

## D7 模板不得把插件导出的全部资源当副作用安装；recovery 标识不接受 HTTP 输入

- **分类**：输入信任边界与副作用控制。
- **动机（避坑）**：现象——把 `dependencies.plugins` 当成「安装该插件全部组件」的清单，或允许前端传入 `resumeXpertId` / `onImported`；后果——装一个模板就顺带装上整包 Skill/MCP/Hook/App（越权且不可回滚），或把服务端恢复流程的检查点暴露给任意调用方（可指向他人 Xpert、可绕过串行化重试）。
- **决策**：`dependencies.plugins` **只声明运行时前置条件**，函数体根本不读取它；portable 资源（`skills` / `mcpServers` / `hooks` / `apps`）必须来自模板上显式保存的选择器，跨插件依赖按 `pluginName` 分组解析以保持 portable namespace 与安装根正确。`PluginTemplateInstallCommand.bootstrap`（`resumeXpertId` + `onImported`）明确为「服务端拥有的恢复流程」，绝不接受 HTTP body，唯一带 `bootstrap` 的调用点是服务端 bootstrap 服务。
- **背景约束**：模板与资源的选择边界只由注释约束，契约层没有类型级强制；组件安装会改写当前 draft 的 Agent middleware 绑定，因此补跑路径必须在执行时才加载导入图。
- **被否决方案**：①「装模板 = 安装插件全部导出」，②「recovery 标识/回调由 HTTP 传入」——两者均被源码注释直接否定。
- **重新评估触发条件**：需要支持「模板显式声明整包安装」时必须新增独立选项并同时设计回滚；或需要把恢复流程开放给外部编排器时，必须先定义签名与幂等令牌。
- **关联代码**：[template-runtime-dependencies.ts](file://packages/server-ai/src/plugin-resource/commands/template-runtime-dependencies.ts)、[install-template.command.ts](file://packages/server-ai/src/plugin-resource/commands/install-template.command.ts)、[install-template.handler.ts](file://packages/server-ai/src/plugin-resource/commands/install-template.handler.ts)、[sync-template-dependencies.handler.ts](file://packages/server-ai/src/plugin-resource/commands/sync-template-dependencies.handler.ts)。
- **证据来源**：`template-runtime-dependencies.ts` 注释「dependencies.plugins declares runtime prerequisites only. Portable resources must be selected explicitly so a template never installs every Skill/MCP/Hook/App exported by a plugin as an accidental side effect.」；`install-template.command.ts` 类 JSDoc 与字段注释「Internal resumable bootstrap; never accepted from an HTTP body.」

## D8 setup 向导用 PG advisory lock 串行化，且进度不保留凭据

- **分类**：分布式锁与敏感数据最小化。
- **动机（避坑）**：现象——操作员刷新页面、换副本、或并排开两个浏览器重跑系统初始化；后果——重复安装插件、并发写坏进度、或产生两份「已完成」的假状态；若把凭据一并落库，则进度表成为密钥泄漏面。
- **决策**：用**专用** QueryRunner 连接执行 `SELECT pg_try_advisory_lock(hashtext('xpert:setup-plugins:<tenantId>'))`，拿不到锁直接返回当前 status（幂等）；锁在异步任务 finally 中释放、进程退出由 PG 自动释放。进度以确定性主键（`uuidv5('xpert:setup-plugins:<tenantId>')`）写入 `tenant_setting`，**只存状态不存凭据**；每项安装前后都落盘，单项失败只标 `failed` 并继续，因此可在同一把锁下续跑。
- **背景约束**：该向导实际强绑定 PostgreSQL（`hashtext` 与 advisory lock 不可用于 SQLite/MySQL）；30s 无回执或回执缺失一律降级为 `attention`，不做「乐观完成」。
- **被否决方案**：无（源码以 Invariants 注释固定该机制）。
- **重新评估触发条件**：需要支持非 PostgreSQL 部署形态；或需要多个租户并发初始化时的锁粒度调整（当前按 tenantId 一把锁）。
- **关联代码**：[setup-plugins.store.ts](file://packages/server/src/plugin/setup/setup-plugins.store.ts)、[setup-plugins.service.ts](file://packages/server/src/plugin/setup/setup-plugins.service.ts)、[setup-plugins.schema.ts](file://packages/server/src/plugin/setup/setup-plugins.schema.ts)。
- **证据来源**：`setup-plugins.store.ts` 顶部 Invariants「PostgreSQL owns the install lock across replicas and browser retries … Progress survives API restarts in tenant settings, without retaining credentials.」及 `pg_try_advisory_lock` 实现。

## D9 运行前置条件必须显式断言：SDK 兼容在安装/加载期断言，无登录用户时必须显式解析 scope

- **分类**：契约校验与作用域可证明性。
- **动机（避坑）**：现象——插件把 `@xpert-ai/plugin-sdk` 写进 `dependencies` 或声明跨 major 的 peer range；后果——宿主与插件各持一份 SDK 实例，运行期出现类型与注册表分叉且难以定位。现象——bootstrap 后台同步没有登录用户，查询按「当前用户为空」构造；后果——跨租户泄漏或误改他组织资源。
- **决策**：① SDK 契约**显式断言**：包名不匹配、`@xpert-ai/plugin-sdk` 出现在 `dependencies`、`artifactNamespace` 嵌套值与非嵌套值不一致等直接抛 `PluginSdkValidationError`；安装候选与已安装状态各有断言函数（`assertPluginSdkInstallCandidate` / `assertInstalledPluginSdkCompatibility`）阻断不兼容包；peer range 漂移则以 warning 形式暴露在 `PluginInstance.meta.sdkCompatibilityWarnings`。② 无登录用户的同步路径必须显式解析 scope：`tenantId` 缺失直接 400，`organizationId` 为空时强制 `organizationId IS NULL`，**绝不发出无 scope 的管理查询**。
- **背景约束**：SDK 兼容只对「安装候选」硬阻断，运行期 peer range 漂移仅告警，因此兼容性仍有赖插件自觉；scope 解析依赖 `RequestContext.getScope()` 中存在已恢复的作用域。
- **被否决方案**：无（源码以断言 + 注释固定；未记录候选方案）。
- **重新评估触发条件**：出现插件在宿主内多实例 SDK 的真实事故（届时应把 peer range 漂移也升级为阻断）；或需要支持真正的跨租户后台运维视角（需要新的显式 scope 凭证机制）。
- **关联代码**：[plugin-sdk-versioning.ts](file://packages/server/src/plugin/plugin-sdk-versioning.ts)、[plugin-resource-installation-scope.ts](file://packages/server-ai/src/plugin-resource/plugin-resource-installation-scope.ts)、[plugin-scope.guard.ts](file://packages/server/src/shared/guards/plugin-scope.guard.ts)。
- **证据来源**：`plugin-sdk-versioning.ts` 中的 `PluginSdkValidationError` 抛出点与 `warnPluginSdkCompatibility`；`plugin-resource-installation-scope.ts` 顶部「Why this exists」注释「Never issue an unscoped management query when the tenant is missing.」
