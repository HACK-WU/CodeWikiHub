## 核心流程实现位置
### 安装链：sources → 下载/解包 → stage → 合并 metadata → lazyLoad → 注册路由/策略 → 落 plugin_instance
入口 `POST /plugin`（`PluginController.installPlugin`）与 `POST /plugin/archive`（`installPluginArchive`，multer `limits.fileSize = 100 * 1024 * 1024`）。`PluginManagementService.installPlugin` 的固定顺序为：解析 scope（`resolvePluginScope`，含 tenant-global 与 system 特例）→ SDK 兼容与 level 判定（`assertPluginSdkInstallCandidate` / `assertPluginSdkCompatibility`）→ system/tenant 归属冲突检查 → 若 `requiresPluginRestart` 则只做 staging：`registerPluginsAsync({ stageOnly: true })` 内部按 source 分派 `stagePackageDirectoryPlugin` / `stageWorkspacePlugin` / `installOrganizationPlugins`（npm 安装并写 manifest），随后 `assertInstalledPluginSdkCompatibility`、artifact namespace 校验、`pluginSchemaSync.synchronize`（Redis 锁 + scope 化 DDL）、`pluginInstanceService.upsert({ pendingRestart: true })`、`runtimeControl.recordPluginRuntimeChange`。热路径继续：`registerPluginsAsync` → `loadPlugin` → `inspectConfig` → 逐模块执行三段式。

三段式（顺序不可颠倒，`plugin-management.service.ts` 顶部不变量）：① `collectPluginOrmMetadata([dynamicModule])` + `validatePluginEntityTableNames` + `registerPluginOrmMetadataInDataSource`（先合并实体/订阅者并 `buildMetadatas`）；② `snapshotModuleIds` / `snapshotHttpRouteStack` 后 `lazyLoader.load(() => dynamicModule)`；③ `registerPluginControllerRoutes`（把新 Express 层移到 404/错误处理器之前）+ `registerInstalledPluginStrategies`（往 `StrategyBus` 写策略与队列处理器）+ 手动调 `onPluginBootstrap`。收尾 `upsert({ pendingRestart: false })`、`runtimeState.report()`、`recordPluginRuntimeChange`。卸载/失败路径由 `uninstaller.uninstallByPackageNameWithGuard(..., 'refresh')` 保证先清旧实例。

章节来源：[plugin-management.service.ts](file://packages/server/src/plugin/plugin-management.service.ts)（关键符号：PluginManagementService.installPlugin）、[plugin.helper.ts](file://packages/server/src/plugin/plugin.helper.ts)（关键符号：registerPluginsAsync）

### 卸载与重启策略
`PluginController.uninstall` → `PluginManagementService.uninstallByNamesWithGuard` → `PluginUninstallService.uninstallByNamesWithGuard`：先做权限/level 判定（`canManageSystemPlugins` / `canManageTenantPlugins` / `canUninstallPlugin`）、解析 `scopeKey`、筛出 loaded 目标，再按 `requiresPluginRestart(policy, level, operation)` 分流 —— 未声明 policy 时 system/tenant 默认 restart、organization 走热卸载；随后清 `StrategyBus` 记录、`pluginInstanceService.uninstall/deactivate`、必要时 `runtimeControl.recordPluginRuntimeChange`。更新侧由 `canUpdatePlugin` / `supportsNpmRegistryUpdates` / `hasNewerVersion` 与 `POST /plugin/update`、`UpdatePluginCommand` 承载；`refreshCodePlugin` 专为 `source === 'code'` 插件重新 staging。

### Setup 向导（advisory lock + 进度存 tenant settings）
`SetupPluginsController` → `SetupPluginsService.catalog/status/start`。授权要求「默认租户内的 SuperAdmin 会话且非 API Key」；`SetupPluginsStore.acquire` 用独立连接执行 `SELECT pg_try_advisory_lock(hashtext($1))`，键为 `xpert:setup-plugins:<tenantId>`，拿不到锁则直接回退到 `status()`。进度以 uuid v5 派生 id 写入 `TenantSetting`（name `setupPluginInstallation`），**不保留任何凭据**；`run()` 顺序安装市场插件（`installPlugin(..., { deferActivation: true })`，单项失败只标 `failed` 并继续，每项先 `save` 再进入下一项，因此重启后可从同一锁下续跑），再执行 `ImportDefaultAgentPluginsCommand`，最后汇总 `runtimeRequirements` 置 `phase='restarting'` 并 `requestRestart`；`status()` 用 `pluginConvergenceStatus` / `restartStatus` 收敛状态，超过 30s 无回执则标 `attention`。

## 设计模式及落点
- **三段式动态装配**：`plugin-management.service.ts` 一处集中实现，`plugin-orm-metadata.ts` / `plugin-http-routes.ts` / `plugin-strategy-registration.ts` 三个机制文件分别负责一段，形成可测试的边界。
- **策略注册表**：`StrategyBus.upsert`（插件策略与队列处理器，含 `sourceId = scopeKey:plugin@version:Target`）、`SkillSourceProviderRegistry`（clawhub / github / zip / workspace-public）、`XpertToolProviderRegistry`（运行期工具提供者）、`PluginMarketplaceRegistry`。
- **CQRS**：跨域交互全部命令/查询化（`ImportDefaultAgentPluginsCommand`、`UpdatePluginCommand`、`ResolvePluginArtifactNamespaceQuery`、`PluginTemplateInstallCommand`、`PluginTemplateSyncDependenciesCommand`、`ListComponentStatesQuery`）。
- **Gate / Guard**：全局 `PluginScopeGuard` 按插件控制器上的 `ORGANIZATION_METADATA_KEY` 拒绝越 scope 请求；控制器层再叠 `RoleGuard + RolesEnum`；服务层用 `canManageSystemPlugins` / `canManageTenantPlugins` 做二级校验。
- **三种并发锁**：PG advisory lock（setup 向导）、数据库 unique `scopeKey`（App 安装幂等）、Redis 锁/租约（插件 schema 同步与市场共享缓存）。
- **缓存与负缓存**：`MarketplaceCache`（本地）+ `PluginMarketplaceSharedCache`（Redis，TTL + failureTtl + retention + 租约续期与发布）。

章节来源：[plugin-strategy-registration.ts](file://packages/server/src/plugin/plugin-strategy-registration.ts)（关键符号：registerInstalledPluginStrategies）、[plugin-marketplace-shared-cache.ts](file://packages/server/src/plugin/marketplace/plugin-marketplace-shared-cache.ts)（关键符号：PluginMarketplaceSharedCache.withLease）

## 热点路径
- **启动期逐插件 bootstrap**：`PluginModule.onModuleInit` 顺序 `for await` 每个插件模块并调 `runPluginStartupStep`（默认 30s 超时，超时抛 `PluginStartupTimeoutError` 并导致就绪失败）；事件循环被同步初始化阻塞时由 `createPluginStartupWatchdog` 的 worker 线程兜底。
- **市场抓取与 TTL 缓存**：来源目录默认 10 分钟新鲜期（`XPERT_PLUGIN_MARKETPLACE_CACHE_TTL_MS`）、共享索引结果保留两倍时长、公开目录 24 小时保留并在刷新时继续提供陈旧数据；npm README/下载量只在详情/后台索引用时抓取，不进列表热路径。
- **工作区技能文件读写**：`getWorkspaceSkillsRoot` 下的解包与删除、`archiver` 打包下载、bundle hash 比对决定是否重写文件，均为磁盘密集路径。
- **动态路由注册**：每次热装都要重新计算模块 id 快照、注册 `RoutesResolver` 并把新增 Express 层移动到尾部处理器之前，属于对框架内部结构的直接操作。

## 技术债与 hack
- **启动链硬编码**：`RootModule` / `WorkerRootModule` / `MigrationRootModule` 三处各自 `imports [..., PluginModule.init()]`，全局 `PluginScopeGuard` 又单独在 `bootstrap/index.ts` 注册；调整插件装配策略必须同步改多处，且缺少编译期约束。
- **动态装配顺序脆弱**：三段式任一环节提前（先 load 再合并 metadata）会得到 `EntityMetadataNotFoundError`；路由注册依赖对 Express 栈尾层的启发式识别（`snapshotHttpRouteStack` + `moveNewExpressLayersAheadOfTailHandlers`），框架内部结构变化即失效。
- **Hook `command` 是可执行代码边界**：`PluginHooksMiddleware` 通过 sandbox backend 执行插件提供的命令，权限收敛依赖 sandbox 配置而非类型系统。
- **上传/解包防护不对称**：插件归档有显式 `assertSafeArchiveEntries`（覆盖 zip 与 tar 的 `../`、绝对路径），multer 限额 100MB；而技能 zip 上传路径（`skill-package.controller.ts` 的 `FileInterceptor('file')` 无 `limits`）与其解包实现未见等价校验与大小上限，属待确认的风险面。
- **SDK 版本漂移只告警**：`plugin-sdk-versioning.ts` 对缺失 peer、非法 range、跨 major range 只产出 warning（`plugin-sdk-peer-range-incompatible` 等）而不阻断加载，运行期兼容性靠插件自觉。
- **`effective-loaded-plugins.ts` 的收敛语义隐晦**：以 `reverse()` + `seen` 实现「org > tenant-global > system」同名覆盖，只保留最后一条符合条件的记录，改动过滤顺序即改变可见插件集合，缺少断言保护。
- **文档与代码前缀不一致**：`AGENTS.md` 记录索引端点为 `/skill-repository/indexes`（`POST /sync/:repositoryId`），实际控制器是 `@Controller('skill-repository-indexes')`。
- **staging 指纹与文件系统耦合**：工作区插件仅在复制输入变化时 restage、运行依赖仅在 install fingerprint 匹配时复用，进程外的手工改动不会被感知。

## 设计维度分析
### 维度一：授权与作用域的正交表达
本实现把「这台机器能不能装」拆成三个互不推导的维度：`scopeKey`（租户/租户全局/组织/系统）、`level`（system / tenant / organization）、`runtimePolicy`（install / update / uninstall 各自 hot 或 restart）。读取侧由 `effectiveLoadedPlugins` 与 `resolveLoadedPluginResourceRoot` 统一按「当前组织 → 本租户全局 → 系统全局」优先级收敛；写入侧由 `canManageSystemPlugins` / `canManageTenantPlugins` 与 HTTP 全局 `PluginScopeGuard` 双重校验。无登录用户的后台路径则以 `applyPluginResourceOrganizationScope` 强制 tenant 必填并显式区分 `organizationId IS NULL`（tenant 级）与组织级行，避免跨作用域污染。

### 维度二：一致性与并发控制的分层
一致性被拆成三层并用不同机制承担：①**数据库唯一键**承担业务幂等（`plugin_instance` 的 `(scopeKey, pluginName)` 与 partial unique tenant 级 `pluginName`；`plugin_application_installation` 的 unique `scopeKey`，用于抵御多会话重试）；②**PG advisory lock** 承担长事务级互斥（setup 向导在同一锁下续跑，进程退出自动释放）；③**Redis 锁/租约 + 发布**承担跨副本的短临界区（插件 schema 同步、市场共享缓存的刷新与陈旧读）。状态机侧用 `pendingRestart` / `deferActivation` / `pluginConvergenceStatus` 把「已落库」与「已生效」显式分离，符合「每项先落库再收敛」的恢复语义。

## 结论
实现主干可以概括为四句：安装是「先 staging、再合并 metadata、再 load、最后注册」的幂等流水线；生效与否由 `runtimePolicy` 与 `deferActivation`/`pendingRestart` 显式决定；scope 是唯一可被证明的授权凭证，任何缺少 tenant 的查询都必须失败；资源与技能资产只通过固定矩阵与 `sharedSkillId` 约定落地。要改动这一层，最需要预先回答的问题是：这次变更属于哪一段装配、是否需要重启、以及 scope 是否可证明——三点任一含糊都会立刻表现为启动失败、重复资源或跨租户泄漏。
