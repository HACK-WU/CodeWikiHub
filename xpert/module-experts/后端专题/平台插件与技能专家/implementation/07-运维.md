## 部署与启动

启动链分三处协作：`beginPluginStartup(root)` 建快照状态与看门狗（默认 120s）→ `selectPluginStartup(groups)` 用指纹决定「本次尝试的候选配置」还是「回滚到上次已准入配置」→ 监听就绪后 `admitPluginStartup(state)` 提交并把 runtime 状态（含失败列表）写入快照；`runtime-control/runtime-plugin-admission.ts` 是调用点，超时/失败会关闭 readiness，重启协调器据此判定替换失败。

- 每个生命周期钩子由 `runPluginStartupStep(name, stage, action, timeoutMs = 30000)` 包裹：超时抛 `PluginStartupTimeoutError`（`code = 'PLUGIN_STARTUP_TIMEOUT'`），注释明确「超时的 hook 可能已改动进程，因此不能对外提供服务」——**启动超时是致命错误**。
- Nest 无法解析插件模块时错误直接上抛（`PluginModule.bootstrapPluginLifecycleMethods`）：保持 readiness 关闭，让重启协调器判定替换失败，而不是对外宣告已就绪。
- 恢复耗尽（`PluginStartupRecoveryRequiredError`）时 `holdFailedPluginStartup` 用 `setInterval` 保活而不是崩溃退出，避免 PM2 崩溃循环；运维需修复后手动重启。
- 关闭：`onModuleDestroy` 对每个插件跑 `runShutdownStep('plugin.<name>.destroy')`，单个插件卡死不会阻塞后续清理（全局进程截止时间仍生效）。
- 安装/升级期另有 schema preflight：Redis 锁 `xpert:plugin:schema-sync`（TTL 5 分钟），未拿到锁直接报「Another plugin schema migration is already in progress」。

## 缓存

- 市场目录三层缓存：`source-raw` / `source-enriched`（TTL = `MARKETPLACE_CACHE_TTL_MS`，retention 2×）、`public-catalog`（retention 86400000ms）；TTL 内直接返回 `lastCatalog`，过期则由 Redis 租约选出唯一刷新者，写回用 PG `xmin` 栅栏保证只有赢家生效。
- 冷启动路径：先返回 raw 索引，enrich（npm 下载量、bundle manifest）在后台异步补，失败只 warn 不阻断。
- 图标资源：`/plugin/marketplace/assets/icon` 响应头 `Cache-Control: private, max-age=86400, immutable` + `Vary: Authorization, tenant-id, organization-id, x-scope-level` + `X-Content-Type-Options: nosniff`，hash 以 64 位十六进制校验。
- 作用域收敛：`effectiveLoadedPlugins` 只保留当前组织、（非全局组织时）租户级与 system 级记录，并按归一化包名「后加载者胜」，保证缓存/列表不会跨作用域泄漏或重复。

## 日志与告警

- 启动日志为结构化 JSON：`plugin.startup.started` / `plugin.startup.completed`（含 `durationMs`）/ `plugin.startup.failed`（含 `code`、`durationMs`）。失败日志**刻意不记录插件配置与任意异常文本**，因为二者可能含凭据——排查时先用 `code` + `stage` 定位，不要期待日志里有配置内容。
- 恢复耗尽打印 `runtime.startup.recovery-required` 并附快照中的 failure。
- 加载失败集中登记在 `loadFailures`，通过 `PluginRuntimeStateService.report()` 上报到实例注册表；`PluginInstance.meta.sdkCompatibilityWarnings` 会作为告警随插件描述对外暴露（`ensureHostPluginSdkLink` / `warnPluginSdkCompatibility` 生成），安装候选阶段则由 `assertPluginSdkInstallCandidate` 直接拒绝不兼容包。
- 市场侧失败只 warn（`Marketplace refresh failed: ...`），技能索引 sync 失败转 `BadRequestException` 并照常更新 `lastSyncAt`。

## 多副本与锁

- setup 向导：`pg_try_advisory_lock(hashtext('xpert:setup-plugins:<tenantId>'))`，用**专用** QueryRunner 连接持有到安装结束，进程退出即释放；进度在 `tenant_setting`，因此刷新页面/换副本重试仍幂等。
- 技能公共仓库：`pg_advisory_xact_lock(hashtext(tenantId), hashtext('workspace-public'))`，**仅当连接类型是 postgres 时执行**（其他数据库直接跳过，靠 partial unique 兜底）。
- 插件 schema DDL：Redis 锁 `xpert:plugin:schema-sync`（TTL 5 分钟）串行化多副本迁移。
- 市场 DSL 刷新：Redis 租约 + PG `xmin::text` 条件更新（`lastCatalog`/`lastIndexStatus` 写入必须赢家且仅赢家）。
- App 安装：`plugin_application_installation` 唯一 `(tenantId, pluginName, appName, scopeKey)` 是数据库级并发锁（注释即写明「防止多浏览器重试产生重复资源」），插入冲突即判定已被认领。
- **非 PG 环境风险**：advisory lock、`xmin` 栅栏、`ON CONFLICT ... orIgnore` 等均依赖 PostgreSQL；SQLite/MySQL 部署下这些锁退化为「无锁 + 唯一索引兜底」，SetupPluginsStore 的 `hashtext` 调用也会失败，因此该向导实际强绑定 PG。

## 安全运维

- 归档上传：`POST /plugin/archive` 受 `FileInterceptor` 限制 100MB；`extractPluginArchive` 按魔数判定 zip/tgz/tar，`assertSafeArchiveEntries` 拒绝 `..`、绝对路径等越界条目，且要求包内**恰好一个** `package.json`；tar 分支通过系统 `tar` 可执行文件解包，需保证运行镜像内有 `tar` 且临时目录可写。
- 远端来源即代码：内置/git/github/平台注册表/npm 最终都会把第三方包加载进本进程（可注册 controller、ORM 实体、subscriber、hook）；安装前要做来源审查，`PLUGIN_WORKSPACE_ROOTS` 只约束本地 code 插件源路径白名单，不是沙箱。
- code 插件路径校验：`workspacePath` 必须绝对路径、必须存在且为目录、必须 realpath 落在白名单内、包名与请求一致，且含 `dist/`、`src/index.ts` 或编译入口；`packageDir` 不允许从 HTTP 传入（仅内部上传流程）。
- Hook 组件的 `command` 由插件声明、以 shell 形式执行，但**必须存在 sandbox backend**，否则直接判定失败并上报 `Sandbox backend is not available for plugin hook execution.`；执行结果（含 exitCode、output）都会 emit 到 middleware 事件，属可审计内容。
- 凭据：插件实例 `config` 与会话密钥相关逻辑集中在校验/解密路径，启动快照落盘使用 `__xpert_plugin_encrypted__` 信封加密（`serializePluginConfig`，密钥取 `environment.secretsEncryptionKey`），文件权限 0600、目录 0700；setup 进度**不存凭据**。
- 暴露面：市场控制器含 `@Public()` 的 `plugin/marketplace/public` 端点，其余插件/资源接口均带鉴权与角色守卫（`install-organization` / `install-xpert` 需 SuperAdmin 等）。
