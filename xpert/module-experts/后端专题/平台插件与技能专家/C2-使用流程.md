# C2 · 使用流程（平台插件与技能专家）

范围说明：本文只覆盖本父专家拥有的后端域（`packages/server/src/plugin`、`packages/server-ai/src/plugin-resource`、`skill-package`、`skill-repository`）。不含 `packages/plugin-sdk` 与 `packages/plugins/*`。
前置约定：HTTP 前缀叠加全局 `/api`；除 `/api/plugin/marketplace/public` 外均需登录态；`plugin-applications` 的写接口需 `SUPER_ADMIN | ADMIN | TRIAL`；技能文件读写需 `WorkspaceAuthoringGuard`（判定依据为工作区写权限）。

## R1 安装一个市场插件到指定作用域（含 level 与 restart/hot 判定）

- **业务目标**：把市场包落到 organization（就地热装）或 tenant / system（staging 后等重启）作用域，并拿到「是否需要重启」的明确结论。
- **调用顺序**：`POST /api/plugin`（或 `POST /api/plugin/archive` 上传 zip）→ `PluginController.installPlugin` / `installPluginArchive` → `PluginManagementService.installPlugin(body, options)`，内部固定顺序为：`resolvePluginScope` → `assertPluginSdkInstallCandidate` / `assertPluginSdkCompatibility` → system/tenant 归属冲突检查 → `requiresPluginRestart(policy, level, operation)` 分流 → 需要重启时 `registerPluginsAsync({ stageOnly: true })` + `pluginSchemaSync.synchronize` + `pluginInstanceService.upsert({ pendingRestart: true })` + `runtimeControl.recordPluginRuntimeChange`；可热装时继续 `registerPluginsAsync` 的三段式装配（metadata → `lazyLoader.load` → 路由/策略注册）后 `upsert({ pendingRestart: false })`。
- **事务边界**：没有跨步骤数据库事务。边界是「每项先落库再收敛」：`plugin_instance` 行写入即提交点，之后由 RuntimeControl 的 generation 或重启回执收敛；DDL 由加锁的 schema preflight（Redis 锁 `xpert:plugin:schema-sync`）单独承担。
- **预期结果**：返回 `PluginInstallResult`（`restartRequired: true` 或 `runtimeConvergence.generation`）；`plugin_instance.level` 已定，`pendingRestart` 表达「已落库、当前进程未加载」。
- **错误处理**：400 `server:Error.PluginPackageNameRequired`、`PluginSystemLevelInstallForbidden`、`PluginTenantLevelInstallForbidden`、`PluginProcessLevelConflict`、`PluginTenantLevelAlreadyOwned`、`PluginRuntimePolicyChanged`、`PluginInstallFailed`；setup 场景下 level 与期望不符报 `SetupPluginLevel`（提示刷新目录重试）。
- **真实代码示例**：

## R2 卸载 / 升级（降级）与「替换失败」收敛

- **业务目标**：摘除或替换一个已加载插件，并让多副本在重启后收敛到同一状态；替换失败时回到上次可用配置。
- **调用顺序**：卸载 `DELETE /api/plugin/uninstall`（body `{ names[], organizationId?, scopeKey? }`）→ `PluginUninstallService.uninstallByNamesWithGuard`：解析 `scopeKey` → `canManageGlobalPlugins` / `canManageSystemPlugins` / `canManageTenantPlugins` 与「禁止卸载 system」校验 → 分两路，需重启走 `pluginInstanceService.deactivate` + `strategyBus.remove(...)`，可热卸走 `pluginInstanceService.uninstall`（= deactivate + `removePlugins`）→ 两条路径最后都 `runtimeControl.recordPluginRuntimeRequirements([{ scopeKey, pluginName, state: 'absent' }])`。升级 `POST /api/plugin/update` → `UpdatePluginCommand`（仅 npm 源可升级，`hasNewerVersion` 为假时直接返回 `updated: false`）；降级须显式带 `version` 重新走 `POST /api/plugin` 安装路径。
- **事务边界**：重启路径**不改活模块图、不删 runtime 目录**（「保留已加载代码直到重启」）；收敛由重启/替换完成。热路径同一调用内同时删库与删目录。
- **预期结果**：`{ success: true, ... }` 携带 `runtimeConvergence.generation` 或 `restartRequired: true`；`pendingRestart` 与 RuntimeControl 语义一致。
- **错误处理**：400 `server:Error.PluginNamesRequired`（空数组）、`PluginSystemUninstallForbidden`；替换失败由 `RuntimePluginAdmission` 处理——候选 boot 只尝试一次，失败后（`desired.status === 'failed'`）通过 `canRestorePluginStartup(state)` 恢复上次被接纳配置，未就绪的 boot 一律被 fence。

## R3 配置市场来源（内置 / git·github / 平台注册表）并刷新

- **业务目标**：让市场列表稳定聚合内置公开源、第三方 git/github 目录与平台注册表条目。
- **调用顺序**：内置源无需登记，直接由 `BUILTIN_MARKETPLACE_URL`（`XPERT_PLUGIN_MARKETPLACE_URL` 可覆盖）提供；第三方源 `POST /api/plugin/marketplace/sources` → `PluginMarketplaceService.createSource`（`assertSuperAdmin` + `normalizeSourceInput` + 落 `plugin_marketplace_source` + 首次刷新），后续 `POST /sources/:id/refresh` / `POST /sources/refresh`；平台注册表 `POST /registry` → `PluginMarketplaceRegistry.createRegistryItem`，刷新时 `refreshSource(PLATFORM_REGISTRY_SOURCE_ID)` 委派 `registry.refreshPlatformRegistrySource()`；读取 `GET /api/plugin/marketplace`（`targetApp` / `sourceId` / `search` / `view=summary`）与公开的 `GET /public`。
- **事务边界**：写 `plugin_marketplace_source` / `plugin_marketplace_registry_item` 行；目录快照 `lastCatalog` 与 `lastIndexStatus` 的写回由 Redis 租约选出唯一刷新者、并以 PG `xmin` 栅栏保证只有赢家生效。
- **预期结果**：`lastIndexStatus ∈ idle | success | failed`、`lastIndexedAt`、`lastCatalog` 更新；`view=summary` 列表读路径不触发包 I/O，冷启动先返回 raw 索引、enrich 异步补。
- **错误处理**：来源保存成功但刷新失败 → 400 `Marketplace source was saved but could not be refreshed: ...`；marketplace 请求受 `XPERT_PLUGIN_MARKETPLACE_REQUEST_TIMEOUT_MS`（默认 10s）与代理配置约束；`git` 类型依赖运行镜像内 `git` 可执行文件。

## R4 从模板把 portable 资源装进工作区（`PluginTemplateInstallCommand`）

- **业务目标**：把模板里**显式声明**的 Skill / MCP Server / Hook / App 装进工作区 Xpert，并绑定到草稿的 Agent 上。
- **调用顺序**：`commandBus.execute(new PluginTemplateInstallCommand(templateId, workspaceId, language, basic?, publish?, locale?, capabilities, bootstrap?))` → `PluginTemplateInstallHandler.execute`：`assertCanAuthor(workspaceId)` → 读模板并 `yaml.parse(export_data)` + `normalizeDraft` → `capabilities.prepareInstallation` / `configureRealtimeVoice` → `XpertImportCommand`（恢复态先按 `resumeXpertId` 续跑，`bootstrap.onImported` 落检查点）→ `resolveTemplateRuntimeDependencyComponents` → `PluginResourceInstallerService.installComponentsForXpert` → 模板 toolset 依赖挂载 →（可选）发布 → 工作区初始化。补跑路径 `PluginTemplateSyncDependenciesCommand` 在执行时才 `getTeam(xpertId)` 取图。
- **事务边界**：无外层事务。组件逐条 `save(plugin_resource_installation)` 后一次性 `updateDraft`；非恢复态失败时 `rollbackTemplateXpert` 回收导入出的 Xpert。
- **预期结果**：`PluginResourceInstallResult`；组件行 `status ∈ ready | pending_auth | blocked`，`definitionHash` 标识版本，Skill/Hook 节点回写 draft。
- **错误处理**：选择器无匹配 → 404 `PLUGIN_RESOURCE_NO_MATCHING_COMPONENTS`；目标不支持该资源类型 → 400 `Selected plugin resources cannot be installed to ...`；**recovery 标识（`resumeXpertId` / `onImported`）绝不接受 HTTP 输入**，唯一带 `bootstrap` 的调用点是服务端恢复流程（`bosi-bootstrap.service.ts`）。

## R5 App 初始化（`prepare` → `initialize` → `bindToolset` → 状态查询，`scopeKey` 并发锁）

- **业务目标**：把一个受治理的插件 App 变成可用的「工作区 + Assistant + 知识库」组合，且重复点击不产生重复资源。
- **调用顺序**：`GET /api/plugin-applications/catalog | detail | status` 选型 → `POST prepare`（只分配配置用工作区，占位 `scopeKey = organizationId`、`status = configuring`）→ `POST bind-toolset`（在行锁内绑定具体 toolset）→ `POST initialize`（`operationId` 必填 → 已有 `ready` 先 `refreshHealth`，健康即直接返回 → `getPreflightForApplication` → 模型/套件校验 → `applicationToolsets.prepare` → `claimInstallation` → 事务外逐段创建 → 写 `resourceRefs` 与 `status = ready`）→ `GET status` 轮询。
- **事务边界**：认领靠数据库唯一索引（`(tenantId, pluginName, appName, scopeKey)`，插入冲突即视为已被认领，直接回读现状）；资源创建在事务外，靠 `compensate` + `previousResourceState` 精确补偿；`application-setup/` 的 prepare / bind / discard 在 `manager.transaction` 内用 `pessimistic_write` 锁行。
- **预期结果**：`plugin_application_installation` 一行 `ready`，`resourceRefs` 含 `workspace` / `assistant` / `knowledgebase:<key>`；`initializing` 行超过 5 分钟可被接管。
- **错误处理**：403 `role_required`；400 `scope_not_supported` / `organization_scope_required` / `application_preflight_failed` / `application_suite_runtime_unavailable` / `invalid_*_model`；409 `application_installation_conflict` / `application_assistant_name_conflict`；失败置 `failed` + `errorCode = 'initialization_failed'`；HTTP 层 `.strict()` schema 拒绝 `workspaceId` / `tenantId` / `organizationId` / `credentials` 注入。

## R7 上传技能包到工作区并分享 / 发布到公开仓库

- **业务目标**：把 zip 技能包装进工作区，再作为组织共享技能发布到 workspace-public 仓库并出现在市场。
- **调用顺序**：`POST /api/skill-package/workspace/:workspaceId/upload`（`WorkspaceAuthoringGuard`）→ `uploadSkillPackagesFromFile` → 写 `skill_package`（`visibility` 默认 `private`）→ 用 `PUT .../:id/file` / `POST .../:id/file/upload` 编辑 → `POST .../:id/share` → `shareSkillPackage`：`assertWorkspaceWritePermission` → 只接受 `skillIndexId` 为空的工作区自建技能 → 生成或复用 `sharedSkillId`（`shared-skill-<uuid>`）→ `ensureWorkspacePublicRepository` → 私有发布辅助 `publishSharedSkillPackage` 复制到组织共享目录并写索引行。仓库侧直传走 `POST /api/skill-repository/:id/upload`。
- **事务边界**：磁盘快照（组织共享目录）+ `skill_package.sharedPackagePath` + `skill_repository_index` 行，三者无数据库事务包裹；路径一律由 `getWorkspaceSkillsRoot(tenantId, workspaceId)` 派生，越界路径在 service 层以 `validateSkillRelativePath` 拒绝。
- **预期结果**：`sharedSkillId` 与 `sharedPackagePath` 落库，公开仓库出现同名索引行，可被 `installSkillPackage` 再次装回任意工作区。
- **错误处理**：非 UUID workspaceId → 400 `server-ai:Error.WorkspaceIdInvalid`；已安装包（`skillIndexId` 非空）→ 400 `Only workspace uploaded skills can be shared`；源目录缺失 → `Shared skill snapshot not found`（同 `sharedSkillId` 复用时不会自动重建）。
- **真实代码示例**：


## R8 排障：装完路由 404 / `EntityMetadataNotFoundError` / 启动期插件失败导致 readiness 不通过

- **业务目标**：在最短路径上把「插件装完但不可用」定位到具体一段装配或某个插件。
- **排查顺序（推荐）**：
  1. **先验装配顺序**：三段式（合并 ORM metadata → lazyLoad → 注册路由/策略）不可颠倒。出现 `EntityMetadataNotFoundError` 基本等于「先 load 后合并」，或缺 `registerPluginOrmMetadataInDataSource`。
  2. **再看路由 404**：确认 `registerPluginControllerRoutes` 是否执行（它把新增 Express 层移到尾部 404/错误处理器之前），并确认请求 scope 与插件 controller 的 scope 声明一致——scope 不匹配是 403 `Plugin endpoint is not available in the current tenant or organization scope`，而非 404；另查 `GET /api/plugin` 返回的 `loadStatus`，为 `PENDING_RESTART` 说明只是 staging 未加载。
  3. **再查 readiness**：结构化日志只有 `plugin.startup.started/completed/failed`，failed 记录含 `code` 与 `stage`（30s 超时即 `PLUGIN_STARTUP_TIMEOUT`），**刻意不含插件配置与异常文本**（可能含凭据）；接着看 `loadFailures` 上报的实例注册表与副本私有快照 `.runtime-plugin-state/<replica>.json`；若日志出现 `runtime.startup.recovery-required`，进程以 keep-alive 阻塞而非崩溃重启，需人工修复后手动重启。
  4. **最后收敛**：候选 boot 只尝试一次，确认是某插件导致后按 R2 卸载 / 让 supervisor 恢复上次被接纳配置。
- **事务边界**：无写操作；本 Recipe 只读日志、快照、`plugin_instance` 与注册表。
- **预期结果**：把问题定位到「装配顺序 / scope 声明 / 单插件 hook / 恢复耗尽」四类之一。
- **错误处理与已知坑**：不要用库里的 `sourceConfig` 判断磁盘状态（`packageDir` 是瞬态字段，落库前被 `omitTransientPluginSourceConfig` 删除，重启必须重新 stage）；改完 `source === 'code'` 的插件必须 `POST /api/plugin/refresh` 重新 staging；归档上传上限 100MB，解包拒绝 `..` 与绝对路径。
