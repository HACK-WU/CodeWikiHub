# C0 · 使用总览 — 插件安装与运行时子专家

| 项 | 值 |
| --- | --- |
| 覆盖范围 | `packages/server/src/plugin/**`（78 个源文件，含 `marketplace/`、`setup/`、`permissions/`、`uninstall/`、`commands|queries`）+ `apps/api` 启动链中插件相关段落 |
| 契约层定位 | 父专家「平台插件与技能专家」的子专家①：**插件本体的安装、加载与生效时机** |
| 不覆盖 | `packages/plugin-sdk`（宿主发布的 SDK 契约，是外部依赖）、`packages/plugins/*`（内置插件实现）、组件落点（见子专家②）、技能包与技能仓库（见子专家③） |
| 契约层约定 | 只承诺可观察行为语义与交互边界；不含算法细节、私有方法名与行号 |

## 定位与何时找

本子域回答一个问题：**「这台机器上装了哪些插件、还能不能装、装完什么时候生效」** —— 全部口径都锚在「重启才生效的东西」上：磁盘上的插件 staging 目录、`plugin_instance` 表、市场来源目录，以及本次进程启动时写下的那份候选配置快照。

**拥有**：表 `plugin_instance`、`plugin_marketplace_source`、`plugin_marketplace_registry_item`，以及复用 `tenant_setting` 承载的 setup 进度行；磁盘上的 staging 根与 `plugins.json` manifest、`plugins/.runtime-plugin-state/<replica>.json` 启动快照；安装 / 归档安装 / 卸载 / 升级 / 刷新编排、SDK 兼容断言、artifact namespace 归属判定、level 归属判定、schema preflight、三段式动态装配、市场来源与目录聚合、setup 向导四阶段状态机。

**何时找本子域**：
- 要安装 / 卸载 / 升级 / 刷新插件，或要判断「这次装完要不要重启」。
- 要新增或调整市场来源（内置 JSON 目录、GitHub、Git、平台注册表、npm），或维护平台注册表条目。
- 要接入 `/api/system/setup/plugins` 初始化向导，或排查向导卡在 `installing` / `restarting` / `attention`。
- 要解释启动期为什么某插件没被加载、候选 boot 为什么回滚、快照为什么被 block。
- 要只读地拿到「已加载插件的组件清单」（不做任何落点安装 —— 落点属于子专家②）。
- 要调整插件层级（system / tenant / organization）与作用域可见性规则。

**不找本子域的时机**：想让插件导出的 Skill / MCP / Hook / App 真正挂到工作区或智能体上；想读写技能包文件树；想改插件 SDK 的 API 形状。

## 能力清单

| # | 能力 | 入口 | 关键语义 |
| --- | --- | --- | --- |
| 1 | 安装（code / npm / archive） | `PluginManagementService.installPlugin`、`installArchivePlugin`，`POST /api/plugin`、`POST /api/plugin/archive` | `source` 六类：内置 JSON 目录、`github`、`git`、平台注册表、`npm`、本地上传归档；code 源必须给 `sourceConfig.workspacePath`；`packageDir` 仅服务端归档路径可用 |
| 2 | 卸载与升级 | `PluginUninstallService.uninstallByNamesWithGuard`、`UpdatePluginHandler`、`refreshCodePlugin` | 卸载先过 level 护栏再按 `requiresPluginRestart(..., 'uninstall')` 分流「只摘登记」或「清磁盘+内存」；升级按 npm registry 版本比较；code 插件走 refresh 重建运行时目录 |
| 3 | 实例与作用域可见性 | `PluginInstanceService.findVisibleInOrganization`、`upsert`；`resolvePluginScope` | scopeKey 三类取值：`system:global`、`tenant:<id>:global`、organizationId；可见性收敛顺序为「当前组织 > 本租户全局 > system 全局」 |
| 4 | 市场来源与注册表 | `PluginMarketplaceService`、`PluginMarketplaceRegistry`、`/api/plugin/marketplace/*` | 来源类型 `url|github|git`（读取时另有代码合成的 `platform`）；共享缓存以 Redis 租约为真相；平台注册表来源不落库 |
| 5 | setup 向导 | `SetupPluginsService.start|status|catalog`、`/api/system/setup/plugins` | 四阶段 `idle|installing|restarting|completed(+attention)`；PG advisory lock 跨副本互斥；逐项 `deferActivation` 安装后统一交还重启收敛 |
| 6 | 启动期 bootstrap 与快照恢复 | `preBootstrapPlugins`、`PluginStartupState.select|commit`、`PluginModule.onModuleInit` | 每个 boot 只尝试一次候选配置；失败则 block 并回滚到上次已准入配置；快照天然副本私有 |
| 7 | SDK 兼容断言 | `assertPluginSdkCompatibility`、`assertInstalledPluginSdkCompatibility`、`assertPluginSdkInstallCandidate` | 把 SDK 写进 `dependencies` 直接失败；跨 major / 缺 peer 只产出 warning 并上抛到描述符 |
| 8 | 运行时策略判定 | `parsePluginRuntimePolicy`、`requiresPluginRestart` | `package.json` 的 `xpert.plugin.runtimePolicy` 声明 install/update/uninstall 各自 `hot|restart`；未声明时 system/tenant 默认 restart、organization 默认 hot |
| 9 | 组件清单只读 | `readLoadedPluginBundleComponents`、`GET /api/plugin/:name/components` | 从插件 bundle manifest 收集组件并叠加运行期 Tool Provider 组件，供上层展示与落点选择 |
| 10 | 实例运行态上报 | `PluginRuntimeStateService.report`、`resolvePluginRuntimeRevision` | 输出 `loaded` / `loadFailures` 与 `runtimeRevision`，是 `deferActivation` 之后收敛判定的事实来源 |

## 边界

- **不管**组件在工作区 / 智能体 / 组织上的安装：Skill / MCP Server / Hook / App 的落点、运行体创建、MCP 凭据发布全部属于**插件资源与模板安装子专家**（`packages/server-ai/src/plugin-resource`）。本子域只提供「插件已加载 + 组件清单 + 加载根」。
- **不管**技能包与技能仓库：技能包文件树、技能索引、公开仓库与同步属于**技能包与技能仓库子专家**；本子域只在读取组件清单时把 Skill 组件当元数据暴露。
- **不含** plugin-sdk 本体：`@xpert-ai/plugin-sdk` 是宿主提供的唯一运行时实例，插件必须以 `peerDependencies` 声明；本子域只做兼容断言与 link 保障。
- **不含**内置插件本体与插件 DDL：装配阶段只刷新 TypeORM metadata，建表由加锁的 schema preflight 负责。
- **不含**跨子域编排：setup 向导只发 `ImportDefaultAgentPluginsCommand`，不实现其处理逻辑。

## 已知坑

1. **启动 hook 超时 / 失败即致命**：`runPluginStartupStep` 默认 30s，超时抛 `PluginStartupTimeoutError`（`code = 'PLUGIN_STARTUP_TIMEOUT'`），进程保持不可服务；失败日志刻意**只**输出 `{event, pluginName, stage, durationMs, code}`，**不记录插件配置与异常文本**（可能含凭据）。排查必须依赖快照与 `code`，不要指望日志里有堆栈。
2. **动态装配顺序不可颠倒**：必须先合并 ORM metadata（`collectPluginOrmMetadata` → `validatePluginEntityTableNames` → `registerPluginOrmMetadataInDataSource`），再 `lazyLoader.load()`，最后注册路由与策略。顺序颠倒会得到 `EntityMetadataNotFoundError`，或路由被 splice 到尾部 404 处理器之后（表现为 404）。
3. **`packageDir` 是瞬态字段**：落库前由 `omitTransientPluginSourceConfig` 删除；HTTP 传入必须被拒绝（只有归档上传路径带 `allowPackageDir`）。因此**不能靠库里 `sourceConfig` 判断磁盘状态**。
4. **`(scopeKey, pluginName)` 与 partial unique 语义不同**：唯一键 `(scopeKey, pluginName)` 兜业务幂等；partial unique `pluginName WHERE level='tenant'` 兜「tenant 级插件全平台只允许一个租户持有」。`(tenantId, organizationId, pluginName)` 在 `organizationId IS NULL` 时因 SQL NULL 语义**不互相冲突**。
5. **未声明 `PluginRuntimePolicy` 时的默认**：`requiresPluginRestart` 对 system / tenant 返回 `true`、organization 返回 `false`；同一次判定还要按 `existingRuntime ? 'update' : 'install'` 选 operation。声明为 hot 却实际需要重启时，热路径会抛 `server:Error.PluginRuntimePolicyChanged`。
6. **zip 上传约 100MB 且 zip-slip 防护只覆盖路径**：`FileInterceptor` 限额 100MB；`assertSafeArchiveEntries` 对 zip 条目名与 `tar -tf` 列表都拒绝 `..` / `../` 前缀与绝对路径，并要求归档内**恰好一个 `package.json`**；但**符号链接 / 硬链接等特殊条目未在代码中确认有显式拒绝**，解包仍可能把链接写入目标目录树内。
7. **hook `command` 是可执行代码边界**：`PluginHooksMiddleware` 从 bundle 读 hook 的 `command`，拼成 `XPERT_PLUGIN_ROOT=... XPERT_PLUGIN_DATA=... <command>` 交给 sandbox backend；无 backend 即失败。行为收敛依赖 sandbox 配置，**不是**类型系统。
8. **市场可从任意 GitHub / Git URL 拉取**：来源 URL、`ref`、`sparsePath` 全由使用者填写，远端即代码；`PLUGIN_WORKSPACE_ROOTS` 只约束本地 code 插件的源路径白名单，**不是**远端内容的沙箱。
9. **外部可执行文件依赖**：`fetchGitCatalog` 需要镜像里有 `git`（clone 到临时目录后按 `sparsePath` 找清单，`finally` 清理）；tar/tgz 解包需要 `tar`。二者失败只能从异常文本推断。
10. **setup 与 PG advisory lock 强依赖 PostgreSQL**：向导用**专用 QueryRunner** 执行 `SELECT pg_try_advisory_lock(hashtext('xpert:setup-plugins:<tenantId>'))`，拿不到锁即回退 `status()`（幂等）；锁随连接释放，非 PG 环境语义不成立。续跑靠「每步 `store.save` + 乐观并发校验」而不是内存状态。
11. **启动快照只读不写回**：快照是副本私有副本（文件名由实例标识 + hostname 派生），候选 boot 只尝试一次，随后由 supervisor 用上次已准入配置恢复；恢复耗尽时进程被保活而非退出，需要运维介入。
12. **全局 `PluginScopeGuard` 是隐式鉴权面**：它不在 `plugin/` 目录内，而是 `packages/server/src/shared/guards/` 的全局守卫，按控制器上的作用域元数据与请求上下文比对。**调整插件控制器的 scope 声明等价于调整全局鉴权面**。

## 一分钟判断

- 问「装完生效了吗」→ 看 `requiresPluginRestart` 的三元组（policy / level / operation），以及返回里的 `restartRequired` 还是 `runtimeConvergence.generation`。
- 问「为什么我这边看不到这个插件」→ 看 `scopeKey` 三类取值与 `effectiveInCurrentScope` / `scopeRelation`（`overrides-global` / `shadowed-by-organization`）。
- 问「为什么重启后没起来」→ 看 `plugins/.runtime-plugin-state/<replica>.json` 的 `attempted` / `blocked` / `good` 与失败登记。
- 问「能不能装」→ 先过 SDK 兼容闸门与 artifact namespace，再过 level 归属与角色护栏。
