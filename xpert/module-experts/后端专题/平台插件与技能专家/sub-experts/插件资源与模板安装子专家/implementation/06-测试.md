## 逐文件覆盖点
1. **`plugin-resource-installer.service.spec.ts`（8 例，顶部 13 处 `jest.mock`）**：静态 capability 描述文件引用不需要启动 MCP server；显式 capability 声明的解析与不完整 behavior 元数据的拒绝；选择器无匹配时返回稳定 `errorCode`；一个插件 Skill 展开到多个目标 Agent（`expandPluginRuntimeComponents` 基数还原）；占位 connector id 的 App 组件被 `blocked` 且 `config` 被包裹；`on_install` 的 App 组件为 `pending_auth`；普通 App 组件为 `ready`；manifest 组件若自称 runtime MCP provider 会被拒绝。该文件把 typeorm / server-core / skill-package / xpert / toolset / mcp-capability-catalog 全部 mock，直接 `new PluginResourceInstallerService(...)` 构造。
2. **`plugin-resource-components.spec.ts`（2 例）**：区分「已加载插件确实不存在」与「插件存在但没有 portable 资源 manifest」两种 `NotFoundException` 语义（`resolveLoadedPluginResourceRoot`）。
3. **`plugin-resource-installation-scope.spec.ts`（3 例）**：scope 缺失时**在任何查询之前**抛错；bootstrap 场景在无登录用户时保留已恢复的 tenant；带组织的安装行被限制在「恢复出的 tenant + organization」内（`applyPluginResourceOrganizationScope`）。
4. **`plugin-resource.controller.spec.ts`（1 例）**：仅用装饰器元数据断言 `installOrganization` 的 `ROLES_METADATA` 为 `[RolesEnum.SUPER_ADMIN]`、`GUARDS_METADATA` 为 `[RoleGuard]`。
5. **`plugin-application.service.spec.ts`（8 例）**：授权模型元数据投影（保留连接标识、剔除密钥）；catalog 返回可信配置 + 市场元数据 + 当前 scope 状态；不从名称或模板名反推 App 配置；不解析属于其他组织加载记录的 App 贡献；不可初始化的角色不枚举组织模型；组织角色默认值独立于 provider 目录顺序；省略模型 id 时使用服务端授权的组织默认值；已健康 `ready` 的安装不再要求模型。
6. **`plugin-application-suite.spec.ts`（3 例）**：套件图校验（嵌套角色引用、重复边、可达性与环）；嵌套已发布边的校验与未声明 coordinator 委派的拒绝；跨组 standalone 身份校验与总规模上界。
7. **`plugin-application-suite.service.spec.ts`（7 例）**：建资源前校验全部模板来源；并行发布独立 Assistant 且重试不产生重复；为仅有角色的安装补建缺失的 standalone Assistant；检测并修复被删除的 standalone Assistant 而不替换业务角色；发布失败后保留已拥有的部分资源并续跑；发布前先发布嵌套依赖并在修复时检查绑定；对「只有入口」的安装原位修复。
8. **`plugin-application-assets.spec.ts`（3 例）**：内联 portable manifest 声明的截图；不读取未声明的本地文件；远程截图 URL 保持原样。
9. **`plugin-mcp-server.service.spec.ts`（8 例）**：租户插件只停用当前组织的 grant；激活失败时补偿已准备的 Toolset / catalog / Publication；组织级插件停用其专属 Publication；凭据可重复获取且限定在请求组织；带 MCP Apps 的 Provider 凭据附加 Resource scope；卸载时停用租户 Publication 与所有历史组织 Publication；在 loader 移除运行记录前捕获插件 scope；所有模块初始化完成后对已启用 Provider 做一次对账。
10. **`application-setup/plugin-application-setup.service.spec.ts`（6 例）**：只准备一个私有工作区且下次访问复用；激活失败后保留配置并在安装锁内绑定；绝不覆盖进行中的初始化；丢弃时只删该 scope 的草稿工作区与其配置；工作区已被其他资源引用时拒绝删除；要求组织上下文并在复用工作区时复核 authoring 权限。
11. **`application-toolsets/plugin-application-toolsets.service.spec.ts`（15 例，两个 describe）**：依赖去重不受 Agent / 图身份影响；同一 provider 的具名实例保持独立；自动发现 coordinator / role / standalone Assistant 需求；只返回公开选项元数据并过滤同组织 authoring 权限；排除外部或只读工作区，仅保留用户自有的松散配置；复制异名来源时把凭据留在服务端并分配新 tool id；原位绑定已保存配置并保留 id；采纳已存在于准备阶段工作区的配置而不克隆；为第二个具名依赖复制共享本地来源且不改名第一个绑定；拒绝不可用实例 / 错配依赖 / 无启用工具配置的绑定；preflight 后重查权限并拒绝已撤销来源；复用已存在的托管实例并在修复被删除实例时保留 id；恢复软删托管实例且回滚时不删原数据；拒绝指向安装范围之外的托管资源引用；回滚只覆盖本次尝试并把托管 toolset 计入健康检查。
12. **`application-toolsets/application-initialize.http.spec.ts`（4 例，1 个 `it.each` 表）**：见下节。
13. **`commands/install-template.handler.spec.ts`（12 例）**：空白模板创建互不相同的 Xpert 且保留用户给定名称；在创建或发布 Assistant 之前先校验 capability 装配；按需发布；工作区无默认环境时仍可发布（不绑环境）；默认安装保持 draft；插件依赖安装完成后再初始化模板 prompt 工作流；把模板内置 toolset 依赖挂到导入的 draft；必需内置 toolset 缺失时回滚导入的 Xpert；使用显式选择的 LLM 模型而不强制 primary copilot 回退；补齐缺失 sandbox provider；替换不可用的 sandbox provider；保持可用的 sandbox provider 不变。
14. **`commands/install-template-recovery.handler.spec.ts`（5 例）**：在安装资源前先落检查点（`onImported`）；用原始模型与 dataScope 原位修复不完整 draft；透传 tenant 级查找失败且不创建替代对象；先校验工作区 author 权限再访问恢复目标；非可续跑的普通安装失败时仍然回滚。
15. **`commands/template-runtime-dependencies.spec.ts`（2 例）**：`dependencies.plugins` 被视为前置条件而非隐式 portable 选择器；只解析显式声明的 portable 资源。这两例正是「模板不顺带装整包组件」不变量的直接护栏。
16. **`queries/handlers/list-component-states.handler.spec.ts`（7 例）**：检查工作区安装态需要 authoring 权限；不选工作区即可读组织 TOOLSET 状态；运行时技能包被删除后不再标记为已安装；tenant-global 组织安装与具名组织互相隔离；按当前 `sharedSkillId` 标记插件技能已安装；仅资源定义变化时把已安装 provider 标为 stale；当前组织未获得 grant 前 tenant Provider 显示为禁用。

## HTTP 用例说明
`application-initialize.http.spec.ts` 是本子域唯一的真实 HTTP 用例：`Test.createTestingModule({ controllers: [PluginApplicationController], providers: [{ provide: PluginApplicationService, useValue: service }] })` + `.overrideGuard(RoleGuard).useValue({ canActivate: () => allowed })` + `createNestApplication({ logger: false })` + `listen(0, '127.0.0.1')`，用 `fetch` 打 `${origin}/plugin-applications/initialize`。测试内先 `init({ lng: 'en', resources: ... })` 提供 `server-ai:Error.ApplicationInitializeRequestInvalid` 词条。

- 断言面：成功路径 201 且 `service.initialize` 收到归一化后的 `{ pluginName, appName: 'example', operationId, toolsets }`（证明 `ZodValidationPipe` 的 trim 生效）；注入字段（`workspaceId` / `tenantId` / `organizationId` / `credentials`）、工具集重复 key、非 UUID 的 `toolsetId`、空 `operationId` 一律 400，且 `service.initialize` **未被调用**；角色不放行时 403 且未被调用。
- 未覆盖点：该文件**没有** `setGlobalPrefix('api')`，路径前缀就是控制器声明的 `plugin-applications`；也**没有**接入数据库、真实 guard 或真实 `PluginApplicationService`，因此它只验证「路由 + 管道 + 角色拦截」，不验证服务内部编排。
- 其余 3 个方法（`prepare` / `bind-toolset` / `discard-configuration`）在该文件里只作为 `service` 的 mock 存在，路由级行为未被请求命中，属于缺口（见下节）。

## 无测试与缺口
- **`discardConfiguration` 缺 HTTP / 服务级端点覆盖**：`application-setup` 的 `discard` 有服务级用例（6 例中的 3 例），但 `PluginApplicationController.discard` 的路由、schema（与 `prepare` 共用 `applicationSetupSchema`）与错误映射没有用例；`prepare` / `bind-toolset` 同样只测到服务层与 mock 层。
- **MCP 凭据路径覆盖有限**：`credential` 有 2 例（可重复获取、附 Resource scope），但 `connectionInfo` 的「Publication 未 active 即 404」分支、`resolvePublication` 的 slug 冲突分支、`retireLegacyOrganizationPublicationSafely` 的失败吞掉分支都无用例；`plugin-mcp-server-contract.ts` 无同名 spec（capability 与 transport 校验只由 installer spec 的两例间接覆盖）。
- **installer 的 HTTP 端点覆盖极低**：`plugin-resource.controller.spec.ts` 只有 1 例元数据断言，`install-workspace` / `install-xpert` / `get-state` 及 4 个 MCP 端点的入参归一化函数（`parseMcpPolicy`、`parseAuthPolicy`、`normalizeComponentSelectors`）没有直接用例。
- **无 spec 的源文件**：`plugin-resource-installation.entity.ts`、`plugin-application-installation.entity.ts`、`plugin-hooks.middleware.ts`、`plugin-application.controller.ts`、`plugin-application-suite.service.ts` 之外仍有 `effective-loaded-plugins.ts`、`plugin-resource-app-status.ts`（由 installer spec 间接覆盖）、`plugin-resource.module.ts`、`index.ts`、`application-setup/application-setup.schema.ts`、`queries/list-component-states.query.ts`、两个 `commands/*.command.ts` 均无同名 spec。
- **`PluginHooksMiddleware` 零覆盖**：Hook 是唯一会在 Agent 运行期执行插件命令的组件，却没有任何 spec；其沙箱边界与 `events` 过滤逻辑只能靠 review 保证。
- **并发语义未被真实验证**：`claimInstallation` 的 5 分钟 reclaim 与 unique `scopeKey` 冲突回读在 `plugin-application.service.spec.ts` 中由 mock repository 驱动，没有真实数据库用例；`application-setup` 的 `pessimistic_write` 与 `insert().orIgnore()` 同理。
- **跨模块回归点**：`PluginTemplateSyncDependenciesCommand` 的发送方测试位于本目录之外（`xpert/commands/handlers/sync-template.handler.spec.ts`），改动本子域的命令签名时必须一并回归该文件与 `initialization/bootstrap.service.spec.ts`、`bosi-bootstrap.service.spec.ts`（两者都 mock 了 `../plugin-resource`）。

## 可执行性结论
- **可跑**：16 个 spec 全部位于 `packages/server-ai` 包内，用 `packages/server-ai/jest.config.ts` 定向运行即可，无需外部服务；无 `.only` / 硬编码 `.skip`。
- **无真依赖用例**：与父专家范围里两个 `*.integration.spec.ts` 不同，本子域没有任何 PG / Redis / 文件系统强依赖用例（`plugin-resource-installer.service.spec.ts` 连 `node:fs/promises` 的调用都由 mock 插件根规避），因此 CI 无需额外环境变量；代价是数据库层语义（唯一索引、行锁、orIgnore 冲突）完全没有被真实执行验证。
- **改动后的最小回归集**：改安装/解析 → `plugin-resource-installer.service.spec.ts` + `plugin-resource-components.spec.ts` + `plugin-resource-installation-scope.spec.ts` + `commands/template-runtime-dependencies.spec.ts`；改 App 编排 → `plugin-application.service.spec.ts` + `application-setup/plugin-application-setup.service.spec.ts` + `application-toolsets/*`；改 MCP → `plugin-mcp-server.service.spec.ts`；改 HTTP 边界 → `application-initialize.http.spec.ts` + `plugin-resource.controller.spec.ts`。
- **剩余盲区**：真实并发认领、`discardConfiguration` 端点、`PluginHooksMiddleware` 运行期执行、MCP `connectionInfo` / legacy Publication 退役分支——这四处目前只能靠代码审查与手工验证，改动前建议先补用例。
