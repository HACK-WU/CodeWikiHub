## 模板安装链
**命令与恢复边界**：`PluginTemplateInstallCommand(templateId, workspaceId, language, basic?, publish, locale?, capabilities, bootstrap?)`，`bootstrap` 仅含 `resumeXpertId` 与 `onImported`，类注释写明「Recovery identifiers and callbacks must never come from HTTP input」；实际带 `bootstrap` 的调用点只有 `bosi-bootstrap.service.ts`（服务端恢复流程）。

**执行顺序**（`PluginTemplateInstallHandler.execute`）：`workspaceAccess.assertCanAuthor(workspaceId)` → 按 `capabilities` 计算实际 templateId → `xpertTemplateService.getTemplateDetail` → `yaml.parse(template.export_data)` → `normalizeDraft`（补 `workspaceId`、规范化 sandbox features、剥离 `prompt`/`workspaceDataScope` 等非 portable 字段）→ `capabilities.prepareInstallation` / `configureRealtimeVoice` → `XpertImportCommand`（恢复态下先 `findOneByIdWithinTenant(resumeXpertId)`，取回后校验 `workspaceId` 与模板来源一致，不匹配即抛错）→ `bootstrap.onImported({ id })` 落检查点 → 若恢复对象已发布则只补工作区初始化并返回 → 若恢复对象 draft 为空则用 `targetXpertId` 重放导入 → 组件与 toolset 依赖 → 可选发布 → 工作区初始化 → 返回 `PluginResourceInstallResult`。

**组件部分**：`resolveTemplateRuntimeDependencyComponents(installer, template.pluginName, template.dependencies)` 只遍历 `skills` / `mcpServers` / `hooks` / `apps` 四个显式数组；`dependencies.plugins` 被注释定格为「runtime prerequisites only」，函数体根本不读取它，因此不会出现「装模板 = 顺带安装插件全部组件」。跨插件依赖按 `pluginName` 分组，分别调用 `installer.resolveRuntimeComponents` 以保持正确的 portable namespace 与安装根目录，最后 `flat()`。随后 `installer.installComponentsForXpert(xpert, components)` 落表并改写 draft；模板 toolset 依赖由 `resolveTemplateToolsetDependencies` + `attachTemplateToolsetsToXpert` 单独挂到 Xpert。任一步失败且非恢复态时 `rollbackTemplateXpert` 回收导入出的 Xpert。

### 导入图加载时机
补跑路径 `PluginTemplateSyncDependenciesHandler.execute` 先解析依赖组件，**再**调用 `xpertService.getTeam(command.xpertId)` 取图并交给 `installComponentsForXpert`；源码注释给出原因：「component installation mutates the Agent-specific middleware bindings in that current draft」。也就是说导入图不能在命令构造或 handler 之外提前缓存，否则会拿到上一版 middleware 绑定而覆盖刚写入的 skills / hooks 节点。

## App 编排链
**读路径**：`getStatuses` / `getCatalog` / `getDetail` 都从 `loadedApplications()` 出发——只读 `effectiveLoadedPlugins()` 的 `instance.meta.targetAppMeta.*.marketplace.contents`，筛 `type === 'app' && appConfig`，按 `${pluginName}:${app.name}` 去重，经 `resolvePluginApplicationConfigAssets` 内联资源并把 `workspace.sharing` 强制为 `private`；`getStatusForApplication` 在缺少 tenant / organization 或 `scope !== ORGANIZATION` 时直接返回 `not_installed`，不做任何查询。

**写路径**：`initialize` 的顺序是不可交换的：`resolveApplication`（进程内可信注册表）→ `operationId` 必填 → `assertInitializationAccess` → 已 `ready` 则先 `refreshHealth`，仍然健康就直接返回（注释说明幂等重试不应依赖此后可能被禁用的模型）→ `getPreflightForApplication`（scope / role / 模型 / toolset 四类前置）→ 解析 embedding / vision 模型 → assistantSuite 校验 → `applicationToolsets.prepare`（客户端选择的再校验）→ `claimInstallation` → 认领失败即返回现状 → 事务外逐段创建：工作区（`settings.system.kind = 'plugin-app'`）→ `applicationToolsets.ensure` → 知识库（每建一个就落一次 `installation.knowledgebaseIds`）→ Assistant（suite 走 `assistantSuites.ensure`，否则执行 `PluginTemplateInstallCommand(..., publish: true)`）→ 写 `xpertId` / `status = ready` / `resourceRefs`（`workspace`、`assistant`、`knowledgebase:<key>`）→ `toStatus`。

**补偿**：catch 块在 `!suiteProvisioningStarted` 时回滚 toolset 变更、`compensate` 清理本次创建的工作区 / 知识库 / Xpert，并把 `workspaceId` / `knowledgebaseIds` / `xpertId` / `resourceRefs` 恢复为 `previousResourceState`；随后把状态置 `failed`、`errorCode = 'initialization_failed'`、`errorMessage = getErrorMessage(error)` 并重新抛出。

**setup 四步**：`prepare` 用 `insert().orIgnore()` 先占位（`scopeKey = organizationId`，`status = configuring`）再 `pessimistic_write` 锁行，只分配配置用工作区；`bindToolset` 在锁内 `assertCanAuthor` 后调 `toolsets.bind`；`discardConfiguration` 在锁内校验 `canDiscardApplicationConfiguration`、用 `pessimistic_write` 锁工作区、核对 `settings.system` 归属、扫描所有含 `workspaceId` 列的实体确认无其他资源后删除工作区与安装行。

## 组件安装与目标合法性校验
**解析**：`resolveRuntimeComponents(pluginName, selectors?, target?)` 先用 `resolveLoadedPluginResourceRoot` 定位已加载插件的 portable bundle 根（优先级：当前组织 scopeKey → 租户全局 → `SYSTEM_GLOBAL_SCOPE`），再合并两类组件——`readPluginResourceComponents` 从 manifest 收集的组件，与 `listRuntimeToolProviderComponents` 从 `XpertToolProviderRegistry` 收集的运行期 Provider 组件，后者按 `componentIdentity` 去重并覆盖同名 manifest 声明。

**选择**：有选择器时经 `selectPluginResourceComponents`，无匹配即抛 `NotFoundException`（`errorCode = NO_MATCHING_COMPONENTS`）；随后 `isPluginResourceInstallableForTarget(componentType, target)` 过滤，若显式选择器过滤后数量变少即抛 `BadRequestException`（拒绝静默降级）。有选择器时用 `expandPluginRuntimeComponents` 还原「一个组件挂到多个 Agent」的基数，每个展开项各自创建 Agent 级安装并独立改写该 Agent 的 middleware。

**落表**：`installRuntimeComponent` → `resolveRuntimeType`（`SKILL → skill_package`、`MCP_SERVER / TOOLSET → toolset`、`HOOK → hook_profile`、`APP → app_connector`，未知类型抛错）→ `ensureRuntime` 生成 `runtimeId`（Skill 走 `syncPluginSkillBundle` + `sharedSkillId = plugin:<plugin>:skill:<key>`；MCP 走 `ensureMcpToolset` 并 `replaceToolsetCapabilities`；Hook 为 `hook:<plugin>:<key>`；App 为 `app:<plugin>:<key>`）→ `resolveInstallationStatus` → `buildInstallationConfig` → `findInstallation` 去重后 upsert（`definitionHash`、`enabled = true`、`config` 经 `preserveManagedMcpConfig` 保留 Publication 相关字段）。

**draft 改写**：`installComponentsForXpert` 先取最新 team 并 `ensureDraft`，逐个组件按 `targetAgentKey ?? defaultAgentKey ?? getPrimaryAgentKey` 归属 Agent，安装后 `attachRuntimeComponent`（Skills → 中间件 `options.skills` 追加包 id；MCP → toolset 节点 + `applyMcpApprovalPolicy`；Hook → `pluginHooksMiddleware` 节点合并 hooks 数组；App → 返回 null 不挂节点），最后一次性 `xpertService.updateDraft`。

## MCP 组件启用与凭据
`PluginResourceController` 的 4 个 MCP 端点全部是 `SUPER_ADMIN` 且无请求体，服务侧 `resolveProviderOwnership` 依据加载记录与安装行判定 `PLUGIN_LEVEL`，再用 `runInProviderScope` 伪造一份带 `tenantId` / `organizationId` / `x-headers` 的 `RequestContext` 后执行。

- `enable`：`activateProvider` 负责 preflight（`componentKey` / `provider` / `sourceScopeKey`）→ 解析或创建 Publication（`resolvePublication`）→ 提交 capability 绑定 → 非组织级插件还要为当前组织开一次 access grant；失败时用 `rollbackActivation` 恢复上次有效 catalog 与 Publication 快照。
- `disable`：组织级插件关闭 Publication 并把 `installation.enabled = false`；租户/系统级插件只撤销当前组织的 grant，不关闭共享 Publication。
- `connectionInfo`：要求 Publication `active` 且对非组织级插件断言当前组织 grant 已启用。
- `credential`：在 `active` 前提下取连接信息、用 `managedMcpClientScopes` 计算 scope（含 MCP Apps 的 Resource scope），再 `apiKeys.getOrCreateRevealableCredential` 返回 `{ connectionInfo, apiKey, secret }`。

**契约侧**：`parsePluginMcpServerConfig` 要求 transport 可归一到 `stdio`（有 command）或 `http`（有 url），否则抛「invalid transport」；`capabilities` 可以是内联数组，也可以是相对 JSON 文件路径（由 `loadMcpCapabilities` 以 `realpath` + `relative` 校验必须落在插件根内）。capability 声明强校验：`descriptorVersion` 必须等于 `MCP_CAPABILITY_DESCRIPTOR_VERSION`，tool 需 `inputSchema` / `behavior` / annotations / `defaultApprovalMode`，resource 需 `uri`。审批策略由 `mergePluginMcpPolicies` 把 manifest policy 与安装选择器的 `policyOverrides` 合并，工具级只接受 `prompt` / `approve` / `deny`。

## 设计模式及落点
- **命令模式（CQRS）**：模板安装/续跑与依赖同步被封装成命令，发送方（App 初始化、bootstrap、Xpert 模板同步）只依赖命令定义，不依赖 handler 实现。
- **Gate**：三层拦阻——HTTP 的角色守卫、服务侧的 `assertInitializationAccess` / `assertCanAuthor` / `assertCanManage`、以及 `resolveProviderOwnership` 的作用域判定；`getPreflightForApplication` 还把「不可初始化的调用方不返回模型清单」写成显式分支。
- **并发锁**：`plugin_application_installation` 的 unique `scopeKey` + 条件式 `update`（`where status IN (...)` / `where updatedAt < now - 5min`）实现「认领成功者唯一」；`application-setup` 用 `pessimistic_write` 行锁保护配置事务；组件侧靠 `findInstallation` 查询去重。
- **检查点 + 补偿**：`bootstrap.onImported` 落 Xpert id 检查点、`installation.workspaceId` / `knowledgebaseIds` 逐段落库、失败时 `compensate` + `previousResourceState` 回滚，构成可重入的初始化。
- **纯函数提取**：`applicationToolsetDependencies`（依赖哈希去重与冲突拒绝）、`canDiscardApplicationConfiguration`、`buildBlockedAppConfig`、`resolvePluginAppResourceInstallationStatus` 都被抽成无副作用函数以便单测。

## 热点路径
- **`installComponentsForXpert` 的顺序 IO**：每个组件都串行执行「落表 → 建 toolset/技能包 → 改 draft」，同一模板挂多 Agent 时是 O(组件 × Agent) 的数据库与磁盘写入。
- **`ensureMcpToolset` 的重建语义**：已存在的托管 toolset 会先 `toolRepo.delete({ toolsetId })` 再 `updateToolset`，每次重装都重建工具行；`capabilityCatalog.replaceToolsetCapabilities` 在每次安装时重写能力目录。
- **`getStatuses` / `getCatalog` 的 N+1 健康检查**：对每个 App 都执行 `refreshHealth`，其中最多 3 类 `exists` 查询 + 套件与 toolset 健康检查，属读路径最重的一处。
- **`discard` 的全实体扫描**：为判断工作区是否被复用，遍历 `manager.connection.entityMetadatas` 并对每个含 `workspaceId` 列的实体发一次 `getExists`。
- **MCP 生命周期收敛**：`onModuleInit` 订阅 `StrategyBus.events$`，`REMOVE`（非 refresh 原因）与 Provider upsert 都通过 `queueMicrotask` 异步触发 `disableInstalledServersForScope` / `synchronizeEnabled`；`onApplicationBootstrap` 再对全部已注册 Provider 补一次收敛。

## 技术债与 hack
- **`scopeKey` 强依赖 PostgreSQL 唯一索引做锁**：并发正确性完全建立在 `(tenantId, pluginName, appName, scopeKey)` 的 unique 约束上，`claimInstallation` 里对插入异常直接 `catch {}` 后回读；换成非唯一索引或非 PG 时语义会静默退化，且错误被吞掉后只能靠回读结果判断。
- **5 分钟 reclaim 窗口是启发式**：`INITIALIZING` 行只要 `updatedAt` 早于 5 分钟就允许被第二个请求接管，长耗时初始化（多知识库 + 套件）可能被误判为「进程已崩」。
- **template 与 resource 边界靠手工维护**：`dependencies.plugins` 与 portable 资源数组的分离只由注释约束，契约里没有类型级强制；未来若有人「顺手」在解析函数里读 `plugins`，模板就会一次装上整包组件。
- **`application-setup/` 与 `application-toolsets/` 的 schema 与前端契约对齐未确认**：`prepare` 与 `discardConfiguration` 共用 `applicationSetupSchema`（只含 pluginName/appName），`bindToolset` 额外要求 `key` + `toolsetId` 且为 UUID；`prepare` 不接受任何 toolset 选择，实际绑定必须走 `bind-toolset`，这一点是否与前端调用序一致未在代码中找到约束。
- **`plugin_resource_installation` 没有唯一约束**：只有一条非唯一组合索引，重复安装依赖 `findInstallation` 查询去重，异常路径可能残留重复行或使 `runtimeNodeKey` 指向已失效节点。
- **draft 写入与安装落表不在同一事务**：`installComponentsForXpert` 先逐个 `save(installation)` 再 `updateDraft`，中途失败会留下「已落表但未挂到 draft」的行，只有模板安装链有 `rollbackTemplateXpert`，HTTP 直连入口没有等价回滚。
- **`attachRuntimeComponent` 对 App 返回 null**：APP 组件的 `runtimeNodeKey` 因此不会被刷新，只能靠 `status`（`pending_auth` / `blocked`）表达状态，与 Skill/Hook 的图绑定语义不一致。
- **capability 文件读取依赖文件系统布局**：`capabilitySource` 必须是插件根内的相对 JSON 路径，`realpath` 校验只在安装期执行一次，安装后移动插件目录不会被感知。

## 设计维度分析
### 维度一：信任边界的内外分离
本实现把「可信输入」压缩成两处确定性来源：App 定义只来自进程内已加载插件的 `meta`（`loadedApplications` 明确注释「no marketplace response or localized text participates in resolution」），runtime TOOLSET 只来自 `XpertToolProviderRegistry` 的注册项且必须 provider 名一致（`installRegisteredRuntimeToolProviderToOrganization` 的注释写明 manifest metadata 被刻意排除在信任边界外）。与之对称，HTTP 层用 `.strict()` Zod schema 把注入字段（tenantId / organizationId / workspaceId / credentials）直接判为 400，并在测试里逐条断言 `service.initialize` 未被调用——授权面因此只有 `RequestContext` 与注册表两个入口。

章节来源：[plugin-application.service.ts](file://packages/server-ai/src/plugin-resource/plugin-application.service.ts)（关键符号：PluginApplicationService.loadedApplications）、[application-toolsets/application-initialize.schema.ts](file://packages/server-ai/src/plugin-resource/application-toolsets/application-initialize.schema.ts)（关键符号：applicationInitializeSchema）

### 维度二：幂等性的三层实现
幂等被拆成三种机制：①**认领层**——unique `scopeKey` 决定「谁能开始」；②**检查点层**——`bootstrap.onImported` 先落 Xpert id、`installation.workspaceId` / `knowledgebaseIds` 每段落库，使中断后可原位续跑（源码注释「Repair missing resources without duplicating a healthy Assistant from the previous attempt」）；③**补偿层**——`previousResourceState` 只回滚本次尝试创建的资源，`suiteProvisioningStarted` 为真时连补偿都跳过（因为套件可能已经对外发布 caller）。三者共同把「重复点击」和「崩溃重启」都收敛到「最多一份资源」。

章节来源：[plugin-application.service.ts](file://packages/server-ai/src/plugin-resource/plugin-application.service.ts)（关键符号：PluginApplicationService.compensate）、[commands/install-template.handler.ts](file://packages/server-ai/src/plugin-resource/commands/install-template.handler.ts)（关键符号：PluginTemplateInstallHandler.execute）

## 结论
实现主干可以直接读成两句：**App 编排是带检查点的可重入事务，组件安装是带目标矩阵的幂等 upsert**。前者的正确性靠 unique `scopeKey` 认领 + 分段落库 + 精确补偿；后者的正确性靠「解析 → 目标校验 → 运行体创建 → 落表 → 改写 draft」的固定顺序，以及显式选择器与 `dependencies.plugins` 的隔离。改动时最需要预先确认的是：scope 是否可证明、这次安装属于哪个目标、以及写库与写 draft 之间是否需要补偿——三点任缺其一，都会立刻表现为重复安装、跨组织泄漏或 draft 绑定漂移。
