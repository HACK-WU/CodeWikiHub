# C0 · 使用总览 — 插件资源与模板安装子专家

| 项 | 值 |
| --- | --- |
| 覆盖范围 | `packages/server-ai/src/plugin-resource/**`（32 个源文件，含 `application-setup/`、`application-toolsets/`、`commands/`、`queries/`） |
| 契约层定位 | 父专家「平台插件与技能专家」的子专家②：**把已加载插件导出的组件装到 workspace / xpert / organization，并完成受治理 App 编排与插件 MCP 启用** |
| 不覆盖 | 插件下载 / 校验 / 解包 / 加载与重启判定（子专家①）、技能包与技能仓库（子专家③）、MCP 协议与 Publication 持久化（`../mcp-publication`）、模板 DSL 语义（`XpertTemplateService`） |
| 契约层约定 | 只承诺可观察行为语义与交互边界；不含私有方法名、行号与实现模式 |

## 定位与何时找

本子域是「**不重启也能生效的落点层**」：它把插件域产出的能力，按固定矩阵分发到三个落点，用 `definitionHash` 与 `runtimeNodeKey` 把「定义版本」与「图上的绑定」分开记录，用唯一 `scopeKey` 把并发收口到数据库。

**拥有**：表 `plugin_resource_installation`（组件安装态：`runtimeType` / `runtimeId` / `runtimeNodeKey` / `definitionHash` / `status` / `enabled`）与 `plugin_application_installation`（编排态 + `declaredScope`）；组件解析与目标校验、运行体创建（Skill 包 / Toolset / Hook Profile / App Connector）、draft 改写、模板安装与续跑、App 目录与初始化编排、插件 MCP Server 的提升与凭据签发、运行期 Hook 中间件。

**何时找本子域**：
- 要在工作区里装上插件导出的 Skill / MCP Server / App 组件，或在组织里装上 TOOLSET，或在智能体上挂 HOOK。
- 要启用 / 停用插件导出的 MCP Server，取回连接信息与一次性凭据。
- 要接入受治理 App：列目录、看状态、`initialize`、`prepare`、`bind-toolset`、`discard-configuration`。
- 要让模板导入出的 Xpert 带上模板显式声明的 skills / mcpServers / hooks / apps 依赖。
- 要排查「组件装了但没生效 / draft 绑定漂移 / 重复安装 / 跨组织可见」。

**不找本子域的时机**：想让插件「先装上 / 先能加载 / 先判断要不要重启」；想读写技能包文件树或技能索引；想替换 MCP 协议实现。

## 能力清单

| # | 能力 | 入口 | 关键语义 |
| --- | --- | --- | --- |
| 1 | 组件解析 | `PluginResourceInstallerService.resolveRuntimeComponents`、`resolveLoadedPluginResourceRoot` | 加载根按「当前组织 scopeKey → 租户全局 → `SYSTEM_GLOBAL_SCOPE`」解析；manifest 组件与运行期 Tool Provider 组件按 `componentType:componentKey` 去重，后者覆盖同名 manifest 声明 |
| 2 | 组件安装到 workspace | `installToWorkspace`，`POST /api/plugin/:name/resources/install-workspace` | 先 `assertCanAuthor(workspaceId)`；只接受 `SKILL` / `MCP_SERVER` / `APP`；返回 `{installations, pendingAuth}` |
| 3 | 组件安装到 organization | `installToOrganization`、`installRegisteredRuntimeToolProviderToOrganization`，`POST .../install-organization`（SUPER_ADMIN） | 只接受 `TOOLSET`；后一入口只承认运行期注册表中 provider 名一致的组件，manifest 元数据被排除在信任边界外 |
| 4 | 组件安装到 xpert（Agent） | `installToXpert`、`installComponentsForXpert`，`POST .../install-xpert` | 只接受 `HOOK`；落表后立即改写 draft 节点（Skills 中间件 / MCP toolset 节点 + 审批策略 / `pluginHooksMiddleware` 合并 hooks；APP 不挂节点） |
| 5 | App 编排 | `PluginApplicationService.getCatalog|getStatuses|getDetail`、`POST /api/plugin-applications/{initialize,prepare,bind-toolset,discard-configuration}` | App 定义只从进程内可信注册表解析；initialize 顺序为 preflight → 认领 → 逐段创建（工作区 → toolset → 知识库 → Assistant → 状态 `ready`） |
| 6 | 模板安装 | `PluginTemplateInstallCommand` / `PluginTemplateInstallHandler`、`PluginTemplateSyncDependenciesCommand` | 只遍历模板 `dependencies` 的 `skills` / `mcpServers` / `hooks` / `apps` 四个显式数组；`dependencies.plugins` 仅作运行时前置条件 |
| 7 | MCP 组件启用与凭据 | `PluginMcpServerService.enable|disable|connectionInfo|credential`，`POST/GET .../resources/mcp/:componentKey/*` | 组织级插件关闭 Publication 并置 `installation.enabled = false`；tenant/system 级只撤销当前组织 grant，不动共享 Publication；凭据一次性返回 |
| 8 | 作用域解析 | `applyPluginResourceOrganizationScope`、`effectiveLoadedPlugins` | 无登录用户的后台路径也必须显式解析 scope；tenant 缺失直接拒绝，`organizationId` 为空时强制 `IS NULL` |
| 9 | 组件状态聚合 | `ListPluginResourceComponentStatesQuery`、`GET .../resources/state` | 输出安装态 + `staleDefinition`（`definitionHash` 不一致）+ Publication 访问授权；按 `target` 参数区分三种视图 |
| 10 | 运行期 Hook 执行 | `PluginHooksMiddleware` | 从 draft 节点读 hooks 数组，按事件与工具匹配后交给 sandbox backend 执行命令 |

## 边界

- **不管**插件的下载、SDK 兼容校验、解包、加载、scope/level 登记与生效时机（是否重启）——全部属于**插件安装与运行时子专家**。本子域只消费「已加载插件记录 + 加载根 + 组件清单」。
- **不管**技能包与技能仓库：Skill 组件的运行体创建调用 `SkillPackageService.syncPluginSkillBundle`，文件树与索引归**技能包与技能仓库子专家**。
- **不实现** MCP 协议、Publication 与 API Key 的持久化（`../mcp-publication`）；**不解析**模板 DSL 语义（`XpertTemplateService`）；**不拥有** Agent 会话与知识库检索。
- **不接受** HTTP 传入的作用域与凭据：请求体只允许身份字段（`pluginName` / `appName` / `operationId` / `toolsetId` / 组件选择器），`tenantId` / `organizationId` / `workspaceId` / `credentials` 一律取 `RequestContext`。

## 已知坑

1. **唯一 `scopeKey` 就是数据库并发锁**：`plugin_application_installation` 的 unique `(tenantId, pluginName, appName, scopeKey)` 是「同一 App × 同一 scope 只允许一次编排」的闸门；插入冲突被解释为「别的请求已认领」而**不是错误**（`catch {}` 后回读）。`INITIALIZING` 行只要 `updatedAt` 早于 5 分钟就允许被第二个请求接管 —— 这是**启发式 reclaim 窗口**，长耗时初始化可能被误判为进程已崩。
2. **组件 → 目标合法性固定**：`organization` 仅 `TOOLSET`；`workspace` 为 `SKILL` / `MCP_SERVER` / `APP`；`xpert` 为 `HOOK`；**`ASSET` 在无目标时也被排除，永不安装**。显式选择器若与目标不匹配即 400，**绝不静默丢弃**。
3. **模板不得把插件导出的全部 Skill / MCP / Hook / App 当副作用装上**：`dependencies.plugins` 被注释定格为「runtime prerequisites only」，解析函数只遍历 portable 资源数组；该隔离**只由注释与测试约束**，契约里没有类型级强制 —— 谁「顺手」读了 `plugins`，模板就会一次装上整包组件。
4. **recovery 标识绝不接受 HTTP 输入**：`PluginTemplateInstallCommand.bootstrap`（`resumeXpertId` + `onImported`）标注「never accepted from an HTTP body」，实际调用方只有服务端 bootstrap 流程（如 `bosi-bootstrap.service.ts`）。
5. **无登录用户时必须显式解析 scope**：`applyPluginResourceOrganizationScope` 在 tenant 缺失时抛 400 `A tenant scope is required to manage plugin resources.`，**绝不发出无 scope 的查询**；`organizationId` 为空时强制 `organizationId IS NULL`，避免 tenant 级行与组织级行互相污染。
6. **`definitionHash` 只表达「定义是否陈旧」**：组件状态里的 `staleDefinition = 已安装 && effectiveInstallation.definitionHash !== component.definitionHash`；定义变更**不会自动重装**，只是标记陈旧，重装需再次触发安装。
7. **MCP transport 与审批策略强校验**：配置必须可归一到 `stdio`（有 command）或 `http`（有 url），否则抛 `MCP component '<key>' has invalid transport`；工具级审批只接受 `prompt` / `approve` / `deny`；`capabilities` 要么是内联数组，要么是**插件根内**的相对 JSON 路径（仅安装期 `realpath` 校验一次）。
8. **`discardConfiguration` 的语义是「只删自己需要的东西」**：在行锁内校验 `canDiscardApplicationConfiguration`，要求无 Xpert、无知识库、资源引用仅含 `workspace` / `toolset`，并**扫描全部带 `workspaceId` 列的实体**确认无其他资源，才删除配置工作区与安装行。
9. **draft 写入与安装落表不在同一事务**：`installComponentsForXpert` 先逐个 `save(installation)` 再一次性 `updateDraft`，中途失败会留下「已落表但未挂到 draft」的行；只有模板安装链有 `rollbackTemplateXpert`，HTTP 直连入口没有等价回滚。
10. **`plugin_resource_installation` 没有唯一约束**：只有一条非唯一组合索引，重复安装依赖 `findInstallation` 查询去重；异常路径可能残留重复行或使 `runtimeNodeKey` 指向已失效节点。
11. **信任边界只有两处**：App 定义只从进程内已加载插件（`loadedApplications` / `effectiveLoadedPlugins`）解析；runtime `TOOLSET` 只承认 `XpertToolProviderRegistry` 中注册且 provider 名一致的组件，**manifest 元数据不参与该判定**。
12. **APP 组件的 `runtimeNodeKey` 不刷新**：`attachRuntimeComponent` 对 App 返回 `null`，App 只能靠 `status`（`pending_auth` / `blocked` / `ready`）表达状态，与 Skill / Hook 的「图绑定」语义不一致；另需注意 capability 文件读取依赖安装期的文件系统布局，安装后移动插件目录不会被感知。

## 一分钟判断

- 问「这个组件能装到哪」→ 查目标矩阵（见坑 2）；不匹配就是 400，不是忽略。
- 问「为什么重复点了两次只装了一份」→ unique `scopeKey` 认领 + `findInstallation` 去重 + 检查点续跑三层幂等。
- 问「为什么我的模板导入出多余组件」→ 检查解析函数是否越界读了 `dependencies.plugins`（坑 3）。
- 问「为什么凭据突然拿不到」→ `connectionInfo` / `credential` 要求 Publication `active`，非组织级插件还要求当前组织 grant 已启用。
