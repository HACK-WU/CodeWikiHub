【决策记录｜取消是协作式，队列查找用扫描而非 Redis 索引】
- 分类：架构设计
- 动机：避免为「停止」强杀进程，或维护一份与队列状态可能不一致的索引
- 决策：取消通过 AbortSignal 传导（**不强杀同步 CPU 密集代码**）；队列查找逐个队列扫描 waiting/delayed/paused/active；waiting/delayed/paused 直接 removeJobs，active 走 HandoffCancelService.cancelMessages（本进程 AbortController.abort() + Redis pub/sub ai:handoff:cancel 跨实例）；结果统一归一为 dead(canceled:<reason>)，**不进死信、不重试**
- 背景约束：stop 是低频操作；active 取消天然对竞态敏感；取消分类必须跨 dispatcher、队列处理器、命令处理器三处一致（buildCanceledReason/isCanceledReason/isAbortLikeError）
- 被否决方案：**Redis 索引键**（README 原文：Queue lookup uses scanning instead of Redis index keys.）
- 重新评估触发条件：队列 job 量增长到扫描成本不可接受（README：Cost is proportional to current job volume.）；或取消成功率不达标且无法用 best-effort 竞态解释
- 关联代码：handoff/commands/handlers/stop-handoff-message.handler.ts、handoff-cancel.service.ts、dispatcher/handoff-queue-gateway.service.ts、cancel-reason.ts
- 证据来源：handoff/README.md（Cancellation is cooperative / Canceled results do not go to dead-letter and are not retried / Active cancel is best-effort and race-sensitive，明写）
