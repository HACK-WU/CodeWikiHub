【决策记录｜技术身份复用 COMMUNICATION 型用户】
- 分类：架构设计
- 动机：避坑：此前存在「按 apiKey 临时创建 communication user」与「把 request user 猜成某个 end user」两类做法 → 同一外部调用方可能产生多个技术用户，且请求代表的业务用户不可解释，审计与授权失真
- 决策：技术身份统一使用现有 UserType.COMMUNICATION 用户，不新增独立技术主体实体；技术身份用稳定标识绑定（xpert:<id> / integration:<id> / client:<code>）；本次请求代表的业务用户只能由 x-principal-user-id 头显式指定，且限定同租户
- 背景约束：user 表已同时容纳真人与技术用户，默认用户列表排除 COMMUNICATION；secret 策略要求会话型凭据的 acting user 必须是真人用户
- 被否决方案：新增 ApiConsumer 之类的技术主体实体；从 body/query 或上下文推断业务用户
- 重新评估触发条件：出现技术身份与真人身份需在数据库层面强隔离的需求（审计或合规要求「技术用户不得出现在用户管理/成员列表」）
- 关联代码：ApiKeyService.resolvePrincipal @ packages/server/src/api-key/api-key.service.ts；buildApiKeyPrincipal @ packages/server/src/api-key/api-key-principal.ts；API_PRINCIPAL_USER_ID_HEADER @ packages/contracts/src/api-key.model.ts
- 证据来源：docs/plans/PLAN_api_principal_identity.md（明写）；api-key.model.ts docstring（明写 resourceScope 不是权限授予）
