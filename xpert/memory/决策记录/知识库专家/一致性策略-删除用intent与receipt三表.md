【决策记录｜删除/发布用 intent + cleanup receipt + publication attempt 三表（可恢复删除）】\n- 分类：一致性策略 / 可运维性\n- 动机（避坑）：**现象** 硬删要跨三种存储（关系库行、向量表、Wiki 证据、图谱），历史实现都是「先删外部产物、再删行」。**后果** 中途崩溃后无法判断某产物是否已删，`indeterminate`（结果未知）只能靠告警与人工，且不可自动重试。[推测] 把「不确定」升格为可查询的一类状态而非隐式日志，是该契约设计的动机（源码未写明）\n- 决策：引入四表协议，状态集合显式包含 `indeterminate`：`deletion_intent.status ∈ prepared|written|promoted|compensated|indeterminate`（带租约 + 部分唯一 `(knowledgebaseId, sourceDocumentIdSnapshot) WHERE status <> 'completed'`）；`cleanup_receipt.status ∈ pending|succeeded|failed|indeterminate`（唯一 `(intentId, receiptKey)`）；`publication_attempt`（`producerKind` 覆盖 document|chunk|graph|wiki|embedding_rebuild，`artifacts` 每项带 `idempotencyKey`，带 `heartbeatAt`）；`publication_attempt_source`（唯一 `(attemptId, documentIdSnapshot)`）\n- 背景约束：跨存储无分布式事务；`hardDeletePendingAt` + `publicationEpoch` 构成 fail-closed 资格判断（读取侧统一过滤 `hardDeletePendingAt IS NULL`）\n- 被否决方案：无\n- 重新评估触发条件：编排服务落地（届时 `indeterminate` 有生产路径）；或存储层提供跨表原子删除\n- 关联代码/当前状态（关键落差）：四表已注册导出但**仓库内未找到任何写入/消费它们的服务**——当前硬删仍是 `deleteResolvedDocument → deleteDocumentArtifacts`（Wiki 撤回 → 向量删 → graph clear 失败仅告警）→ 物理删行 → `updateDocumentNumAfterDelete` 的顺序路径，**删除侧 `indeterminate` 无生产写入路径**；人工补偿入口仅在 Wiki/Graph 侧（`GET :knowledgebaseId/wiki/status` 的 `recoveryActions`）\n- 证据来源：deletion/entities.ts；document.module.ts；document.service.ts；knowledge-wiki.service.ts
