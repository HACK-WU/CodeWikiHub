【决策记录｜安全合规：凭据三层脱敏，但存储侧未加密】
- 分类：安全合规
- 动机（避坑）：**现象** 只靠 DTO 过滤（新增字段忘走 DTO 即泄漏）或只靠端点守卫（任何绕过端点的序列化、日志、导出都会带出凭据）；**后果** 凭据在回显面泄漏，且泄漏点随新功能扩散
- 决策：三层同时作用——① 实体 `@Exclude({ toPlainOnly: true })` 保证序列化即剔除；② `select: false` 保证默认查询**根本不取列**；③ 守卫保证端点级准入（`ToolsetGuard` 之于 `GET /:id/credentials`，`RoleGuard` + `@Roles(SUPER_ADMIN)` 之于发布管理面）；另配布尔位 `introspectionClientSecretConfigured`，让 UI 不读密文也能判断「是否已配置」
- 背景约束：`xpert_toolset.credentials` **库内是明文 json**（`createBuiltinToolset` 里 `// encrypt credentials` 与加密调用两行仍为注释）⇒ 这三层保护的是**回显**而不是**存储**；`mcp_api_key.keyHash`/`encryptedSecret` 与 `mcp_oauth_policy.introspectionClientSecretEncrypted` 才是「加密 + 隐藏」；`mcp_invocation_audit.argumentSummary`（只存 key 列表与字节数）与 `mcp_task` payload 类列同为 `select:false`
- 被否决方案：无（未见对「只用 DTO」或「不加隐藏列」的显式否决记录；三层各自对应一种已存在的泄漏路径）
- 重新评估触发条件：启用凭据加密、或新增任何凭据字段 / 导出面（CSV、事件、日志字段）时——须同步决定该字段落在三层中的哪几层，并复核 `ToolsetPublicDTO` 白名单
- 失败面：`introspectionClientSecretEncrypted` 只有 `select:false`、**无 `@Exclude`**，是整个密钥面唯一可被序列化带出的密文列
