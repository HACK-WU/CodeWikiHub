【决策记录｜架构设计-策略参数化登录方式】

- 分类：架构设计
- 动机：认证内核源自 Nebular auth 体系改造，需要「动作名 → 具体实现」可替换；若页面直连 HTTP，换登录方式就得改每一个页面
- 避坑（现象→后果）：只写策略类、忘记注册进 `XpAuthOptions.strategies` 时无编译期保护，调用在运行期同步抛 `TypeError("There is no Auth Strategy registered under '<name>' name")` —— 表现为整个登录动作崩溃
- 决策：认证动作全部经 `XpAuthService` 按 `strategyName` 分发到 `XpAuthStrategy` 子类，策略在 `XpAuthOptions.strategies` 表注册（`nbStrategiesFactory` 逐条 `injector.get(strategyClass)` + `setOptions`）；11 个公开方法统一形如 `(strategyName, data?)`，页面从 `forms.*.strategy`（当前全为 `'email'`）取名字，只处理「成功/失败 + 跳哪里」，返回面统一为 `XpAuthResult`
- 背景约束：现役策略只有 `AuthStrategy`（name=`email`）；`XpPasswordAuthStrategy` 存在但未注册，只被 spec 的 `/api/auth/custom/*` baseEndpoint 用例覆盖；`XpAuthResult` 是唯一返回面（isSuccess/getRedirect/getErrors/getMessages），页面不解析 HTTP
- 被否决方案：无
- 重新评估触发条件：出现「同一次提交需要横跨多策略」或页面需读策略内部状态的需求；或非 XHR 语义的认证方式（授权码整页跳转）大量增加、双轨需要收敛时
- 关联代码：`XpAuthService.authenticate/register/logout/requestPassword/resetPassword/refreshToken`、`XpAuthService.getStrategy`、`XpAuthStrategy`、`XpAuthOptions`/`defaultAuthOptions`、`auth.module.ts` 的 `nbStrategiesFactory`/`nbOptionsFactory`、`auth-result.ts`
