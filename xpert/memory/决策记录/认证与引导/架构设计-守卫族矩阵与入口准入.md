【决策记录｜架构设计-守卫族矩阵与入口准入】

- 分类：架构设计
- 动机：全站准入需要一处权威声明——「未登录 / 已登录 / 未初始化 / 无权限 / 有脏数据」五种状态的落点各不相同
- 避坑（现象→后果）：判据与落点若不成对，会出现「能进页面但接口 401」或白屏；`authGuard` 不清理本地令牌时，受保护页会反复被弹回且携带陈旧 token
- 决策：五入口并存、判据 + 落点成对——`authGuard`（`!!store.token`、只读本地 store 不发请求；失败先 `await authStrategy.logout()` 再 → `/auth/login?returnUrl=<原 URL>`）、auth 包 `NoAuthGuard`（`accept-invite` 且 query 含 `email`+`token` 无条件放行，其余已登录 → `/home`）、`onboardGuard`（有 tenant → `/home/`、探测 error → `/onboarding/unknown`、两者皆无放行）、`inviteGuard`（`route.data.expectedPermissions` 命中 `hasPermission` 且 `selectedOrganization.invitesAllowed`，否则 → `/`）、`dirtyCheckGuard`（`canDeactivate` + `ZardAlertDialogService.confirm` 确认框）
- 背景约束：`inviteGuard` 与 `@core/auth` 版 `NoAuthGuard` 全仓无路由引用（后者目标 `/pages/dashboard` 已不存在）；`xpert/routes.ts` 另有同名不同物、按 `XpertAPIService.getChatApp(name)` 判定的 `authGuard`，检索与评审极易误伤；onboarding 步骤 2 挂 `authGuard` 而 token 只由步骤 1a 的 `afterOnboard` 产生 ⇒ 三步不可跳步
- 被否决方案：无
- 重新评估触发条件：新增公共页或新守卫语义；清理未挂载守卫（inviteGuard、@core 版 NoAuthGuard）时须逐路由重核；路由侧白名单与请求侧 `ANONYMOUS_AUTH_PATHS`（6 条）必须同步维护
- 关联代码：`@core/auth/auth.guard.ts`、`auth/guards/no-auth.guard.ts`、`@core/auth/no-auth.guard.ts`、`@core/guards/onboard.guard.ts`、`@core/guards/invite.guard.ts`、`@core/guards/dirty-check.guard.ts`、`onboarding-routing.module.ts`、`features-routing.module.ts`
