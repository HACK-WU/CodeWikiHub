【决策记录｜三元权限面分离：创作 / 运行 / 文件】
- 分类：架构设计
- 动机：避坑——三套权限判定若共用一个入口，任何一处选错即构成越权；历史上 2026-10-09 的验收修的正是这类问题
- 决策：创作侧用 WorkspaceAuthoringGuard + XpertWorkspaceAccessService.assertCanAuthorById；运行侧用 PublishedXpertAccessService；文件侧用 AssistantFilesService.forRuntime/forAuthoring。三条面各自独立入口，互不代用
- 背景约束：AGENTS.md 明写 XpertWorkspace 是 Assistant/技能/连接器的创作资源容器，其 canRead/canRun/canWrite/canManage **不是** Assistant 文件权限；UserGroup 授权必须在无创作工作区成员资格时也能生效
- 被否决方案：用 XpertService.findOne()、XpertWorkspaceService.canAccess() 或工作区级 canRun 充当文件 ACL（AGENTS.md 显式禁止）
- 重新评估触发条件：出现「同一入口需同时判创作与运行」的需求单（当前无）
- 关联代码：workspace-access.service.ts（XpertWorkspaceAccessService.can）、published-xpert-access.service.ts、assistant-files.service.ts（forRuntime/forAuthoring）
- 证据来源：AGENTS.md（Authoring workspace versus Assistant file workspace）+ 子专家③ implementation/02-实现.md（明写）
