【决策记录｜多副本实例协调：能加锁的加锁，不能加锁的先记缺口】
- 分类：架构设计
- 动机：避坑——三个 API 实例同时从数据库加载 scheduled 任务、各自建 CronJob，同一任务被执行三次并产生三条 chat_conversation 记录；单实例假设在多副本下直接变成重复执行
- 决策：按「启动副作用是否跨实例互斥」分档。**已加锁**：XpertTriggerBootstrapRecoveryService 用 RedisLockService 按 job:trigger:v2:<xpertId>（10s）互斥，未抢到只记 skipped；BosiBootstrapService 写操作包在 pg_try_advisory_lock(hashtext('bosi-bootstrap')) 内，抢不到抛 ConflictException。**收敛 DDL**：DB_SCHEMA_SYNC_MODE=external 让 API 以 synchronize:false 启动，DDL 交独立 schema-sync 进程。**已知未覆盖**：AssistantBindingService.onModuleInit 的绑定回填无日志、无锁、无插入冲突忽略（PLAN_multi_instance_remediation.md 明确未覆盖）
- 背景约束：模板目录是共享文件系统（启动播种与导出写同一 externalRoot），多副本必须挂共享卷，否则导出模板只在写入副本可见
- 被否决方案：无（计划文档记录的是「当前不做的变更」）
- 重新评估触发条件：回填在多副本启动中出现唯一索引冲突/重复写（启动异常，或 assistant_binding 违反三条 partial unique）；或 bootstrap_recovery_summary 的 failed 计数持续 >0；或 XPERT_TEMPLATE_DIR 未落共享卷
- 关联代码：xpert/jobs/trigger-bootstrap-recovery.service.ts、assistant-binding.service.ts（onModuleInit/backfill*）、bosi/bosi-bootstrap.service.ts、packages/server/src/database/application-data-source.ts
- 证据来源：docs/plans/PLAN_multi_instance_remediation.md + implementation/07-运维.md（§5，明写）
