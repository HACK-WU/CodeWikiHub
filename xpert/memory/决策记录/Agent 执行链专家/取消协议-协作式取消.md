【决策记录｜取消是协作式（与「对话与会话专家」共享证据）】\n- 分类：取消协议 / 跨模块契约\n- 动机（避坑）：现象——把取消实现为强杀进程，或把 canceled 结果送进死信并重试；后果——同步 CPU-bound 代码无法被强杀而状态混乱、取消被重试反向抵消\n- 决策：取消通过 `AbortSignal` 传递；队列态（`waiting`/`delayed`/`paused`）靠移除 Bull job 立即生效，`active` 态靠 abort 在途处理器；跨实例经 Redis pub/sub 传播；取消结果表示为 `dead(canceled:...)` 且**不进死信、不重试**\n- 背景约束：`ai:execution:cancel` 与 `ai:handoff:cancel` 是**两条彼此独立**的频道，互不替代；会话取消先执行执行取消，再 best-effort 停 handoff，后者失败只记 warning；`redrive` 与对账不得越过用户 stop 屏障\n- 被否决方案：强杀同步 CPU-bound 代码（文档明写不做）；取消结果进死信/重试（明确否决）；把队列查找改为 Redis 索引键（README「Design Tradeoffs」明写当前选择扫描：更简单可靠、按当前 job 量计成本）\n- 重新评估触发条件：停止请求频率显著上升，使「扫描成本与 job 量成正比」成为瓶颈时\n- 关联代码：shared/execution/execution-cancel.service.ts；handoff/handoff-cancel.service.ts；chat-conversation/commands/handlers/cancel-conversation.handler.ts\n- 证据来源：handoff/README.md 逐字——「Cancellation is cooperative.」「The system signals cancellation through `AbortSignal`; it does not force-kill synchronous CPU-bound code.」「Cancellation is represented as `dead` with reason prefix `canceled:`.」「Canceled results do not go to dead-letter and are not retried.」
