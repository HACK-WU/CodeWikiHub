【决策记录｜性能取舍-召回注入预算（20KB/轮 · 60KB/会话 · 3s 超时）】
- 分类：性能取舍
- 动机（避坑）：**现象** 记忆消费挂在 `wrapModelCall` 上「每轮都可能」触发；**后果** 若不设体积与超时上限，召回记忆会挤占上下文预算（推理成本与首 token 延迟随记忆库增长而上升），召回模型调用与卷 IO 也会把每轮延迟拖到不可控
- 决策（分级召回）：`beforeAgent` 起**后台**召回 —— `listMemoryHeaders`（按卷根 mtime 缓存，命中即 0 IO）→ `selectSummaryDigestHeaders` 启发式取 **6 条 digest** → `FileMemoryRecallPlanner.selectRecallHeaders` 以**短名单 20** 交模型返回 `selectedIds`（默认超时 **1500ms**，超时/失败可 `fallback`；`fallbackOnFailure:false` 时直接返回空；`strategy ∈ model|fallback|disabled`）
- 决策（预算与注入）：`buildDetailBlock` 逐条 `getMemory`（**会写 `detail_read` 信号**）最多选 **5 条**；`wrapModelCall` 用 `[...buildMemoryContextMessages(recall), ...request.messages]` 前置注入 `[indexBlock, digestBlock, detailBlock]` 并附 `buildMemorySystemMessage`，受单轮 **20KB** / 单会话 **60KB** 预算约束（`MAX_DETAIL_BYTES_PER_TURN = 20 * 1024`、`MAX_DETAIL_BYTES_PER_SESSION = 60 * 1024`，可经 `options.recall.maxDetailBytesPerTurn/PerSession` 覆盖）、召回总超时 **3s**（`DEFAULT_RECALL_TIMEOUT_MS = 3000`）
- 背景约束（对账入口）：注入开销的对账字段是 `wrapModelCall` 日志 `recallStrategy`/`selected`/`detailBytes`/`surfacedSessionBytes`/`pending` —— 排障先看这几个字段，而不是猜记忆库大小
- 背景约束（另一套独立预算）：工具面召回独立计数 —— `memory_search` → `recordRecallHits`（写 `recall_hit`）、`memory_get` → `detail_read` ＋ `updateTopicUsage`；**无模型时 `memory_search` 返回 `[]`**；工具面与中间件注入共用同一记忆库但**不共享** 20KB/60KB 计数器
- 被否决方案：无（源码未记录替代方案的否决记录；预算常量与「可覆盖」选项本身就是取舍结果）
- 重评条件：记忆库条目量或单条正文显著增长、需要把「每轮注入」改为按需检索、或需要把 20KB/60KB 改成按模型上下文动态分配时；届时必须同时更新对账日志字段与 `DEFAULT_RECALL_MAX_SELECTED` 类选取上限
