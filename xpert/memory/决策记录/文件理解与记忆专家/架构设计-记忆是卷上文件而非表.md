【决策记录｜架构设计-记忆是卷上文件（markdown）而非表，且与理解链零耦合】
- 分类：数据归属
- 动机（避坑）：**现象** ① 长期记忆若落库，就要自带索引、清洗、审计、人工修正入口与迁移节奏，且与对话内容争抢同一套 DB 权限与发布窗口；若只做 session 摘要，则「跨会话事实」根本不存在。② 记忆若以「解析产物」为输入、或直接读 `file_asset`/`file_chunk`，记忆链就被解析状态机与向量可用性绑架；**后果** 一次解析失败或向量库不可用会连带记忆不可用，两个子域互相持有实体后依赖图出现环，任何一侧改表都要联动另一侧
- 决策（记忆形态）：记忆以**卷上 markdown/JSON** 承载 —— `.xpert/memory` ＋ 索引 `MEMORY.md` ＋ 四类目录 `user|feedback|project|reference`；frontmatter 承载 `id`/`scope`/`type`/`status`/`usage`/`confidence`/`source`；**记忆的读/写路径都不经 DB 事务、不落本域表**（换来人类可读、可 diff、可被 Agent 工具直接读写）
- 决策（三层解耦）：三条独立链并行 —— ① 字节句柄（`FileAsset` ＋ `storage_file`）；② 理解链（命令 → `FileParserRegistry` → `file_artifact` → `file_chunk`/`file_citation_anchor` → `file_embedding` 账本）；③ 记忆链（卷上 markdown，中间件消费）。记忆子域对理解子域**零代码依赖**，只共享卷基础设施与 `chat_conversation`/`chat_message`/`xpert` 三张只读表
- 背景约束：消费挂在 Agent 中间件（`beforeAgent` 起后台召回、`wrapModelCall` 前置注入、`afterAgent` writeback，并暴露 `memory_search`/`memory_get`/`memory_write`）；写入三入口（显式工具 / writeback / Dream 离线整理）；middleware 入口先 `assertFileMemorySandboxFeatureEnabled`（未启用直接抛错）；项目共享卷按 xpert 隔离为 `.xpert/memory/xperts/<xpertId>`；两者各自实现一个 `@AgentMiddlewareStrategy`（`FileUnderstandingMiddleware` / `XpertFileMemoryMiddleware`），代码上**互不 import**
- 被否决方案：无（源码未记录；实现层把「文件语义」描述为取舍结果而非否决记录）
- 重评条件：出现「用解析产物喂记忆」的产品需求（如把 PDF 摘要自动写成 memory）时，必须新增**显式跨域读接口**，而不是让记忆域直连 `file_asset`；需要跨助手共享记忆、检索级性能优化或记忆变更审计时，「卷上文件」的一致性（`MEMORY.md` 与 topic 文件）与并发写将成为约束
