【决策记录｜接口契约-项目选择与对话门面】

- 分类：接口契约
- 动机：对话域与项目域都需要「一次解析决定去哪、必要时先建项目」，需要一个跨域共享、无状态的解析契约
- 避坑（现象→后果）：若两侧各自拼 URL，新增项目类型就要在对话侧改路由分支（入口分裂）；`identity`/挂载参数在渲染中抖动会改变 ChatKit `runtimeKey`，直接导致会话重建
- 决策：把入口解析与「对话内建项目」收敛为项目域两枚无状态纯函数——`navigateProjectEntry(router, entry)` 按 `XpertProjectEntry` 闭合二分支导航（`kind:'project'` → `/project/:id`，缺 `projectId` 直接 `Promise.resolve(false)` 不导航；`kind:'assistant'` → `/chat/x/:slug[/p/:projectId]/c` 并携带 `queryParams {view: viewKey, viewSelection: selectionId}`）；`chatProjectCreateRequest`（识别 `project.create-entry`，`project.create` 的 name 去空白后必须非空、`projectType` 畸形则整体返回 `null`）与 `executeChatProjectCreate`（entry → `api.typeEntry(type,{xpertId})` 后导航；create → `api.create({name,xpertIds:[assistantId],projectType?})` 后回调 select）
- 背景约束：`XpertProjectTypeRef` 只认 `applicationKey` + `projectTypeKey` 两个非空字符串（契约注释：Resolved by the host and a trusted provider, never an arbitrary URL），默认 `GENERAL_PROJECT_TYPE = { applicationKey:'platform', projectTypeKey:'general' }`；项目选择的三段语义由对话域门面持有（`chatkitMountProjectId` 仅初始挂载、`chatkitProjectSelection` 初始草稿意图、`syncConversationProject(threadId)` 运行开始/结束后刷新持久项目且不新开会话），项目域只负责 projectId 绑定与入口解析（面板 identity `project-chat:${projectId}:${assistantId}`、composer projects 槽位 `locked:true`）
- 被否决方案：无
- 重新评估触发条件：出现第三种入口形态，或需要由任意 URL 承载项目类型时；`openCreate` 两段式（先 `typeEntry` 再决定跳转或建项目）被绕过即视为缺陷
