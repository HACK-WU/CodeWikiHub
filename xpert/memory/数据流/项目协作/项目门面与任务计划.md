【数据流｜项目门面与任务计划】

- 实体类型：项目/计划/任务/资产聚合投影（前端模型；服务端对应 `IXpertProject` 及其 36 表域，后端域未建专家）
- 结构（聚合信号）：`XpertProjectFacade` 的 `project`/`projects`/`projectsTotal`、`plans`/`tasks`、`conversations`、`assets`/`assetsTotal`/`assetCount`（仅无 parentId 根查询更新）、`activities`、`automations`/`scheduledTasks`、`projectInstruction`/`projectSkills`/`projectContentError`、`projectAccess`（capabilities `canRead/canEdit/canManage/canUse` + role）
- 结构（伴生态与派生）：四对 loading/error（loading/error、projectLoading/projectError、conversationsLoading/conversationsError、assetsLoading/assetsError）+ `hasProject`；计划树为「计划 → 冲刺/里程碑 → 任务」，任务关联 `{conversations, executions}`
- 生产方：`XpertProjectApiService`（GET /my、/types、/type-entry、/:id、/overview、/:id/access、/:id/plans*、/:id/tasks* 等）与 `@core XpertTaskService.getAll/schedule/pause/proposeRunAs/acceptRunAs`
- 主要消费方：项目列表页与工作区壳六页签（概览/计划/任务时间线/会话/资源/配置）、run-as 提案与接受区、项目内会话面板与既有会话对话框、`loadTaskRelations`/`reloadScheduledTasks` 的联动回填
- 业务用途：把「项目 → 计划 → 冲刺/里程碑 → 任务 → 会话/执行」一棵树收敛为可订阅信号，页面只读门面而不自造 loading 或直读 API 结果
- 关键约束：`loadProject` 先清空全部聚合子集再拉主记录，主记录到手即以 `#projectLoadSequence` 序号守卫并发派生并丢弃过期响应；overview 失败静默（壳层仍可用）；写路径一律「先打服务端、成功后局部回填」不乐观写；`projectAccess === null` fail-closed
- 详细流向：见 .module-experts/前端专题/项目协作专家/implementation/01-架构.md（关键不变量 1、门面与 API 层）与 C1-能力契约.md §1.1
