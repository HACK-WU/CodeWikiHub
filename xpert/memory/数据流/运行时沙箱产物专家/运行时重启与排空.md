【数据流｜运行时重启与排空】
- 实体类型：**无表**（`runtime-control` 22 非 spec / 10 spec / **0 张自建表**；health 5/0/0 表；workspace-file-access 8/2/0 表）——数据面全为进程内单例 ＋ 跨副本 Redis 键，**易失**
- 结构（进程内单例）：`RuntimeLifecycleService` 的 `readiness ∈ ready|draining|unready`、`trackRequest()` 在途请求计数、`beginDrain({restartId})`（单例，重复调用返回 false）、`cancelDrain(restartId)` 可回退；`RuntimeDrainMiddleware` 读同一状态决定放行或 503
- 结构（跨副本 Redis 键）：活动重启键（一次只 drain 一个候选副本）、重启目标表、插件代次键 `PLUGIN_GENERATION_KEY`；实例清单来自 `managed-connection` 的 `InstanceRegistryService`（`IRuntimeInstanceRegistration[]`，含 `bootId`）；同 Redis 上另有两族沙箱键 `sandbox_runtime:{health}:<profile>`（TTL = 心跳 TTL 的两倍）与 `sandbox_jobs:{capacity}:global|tenant:*|user:*`
- 生产方：`RuntimeControlService.requestRestart`（先 `assertAuthorizedActor()` 三重断言，`confirmation`/`allowDowntime`/`runtimeRequirements[]` 由 DTO 把关）→ `RuntimeRestartCoordinatorService` → `RuntimeLifecycleService.beginDrain` → `waitForIdle(1_000)` → `RuntimeQueueShutdownService` 暂停 Bull/WorkerHost → `RUNTIME_PROCESS_SIGNALER`（真实实现 `process.kill(process.pid, signal)`）
- 主要消费方：`RuntimeDrainMiddleware`（非 `/health` 请求 503 ＋ `Retry-After: 5`）、`HealthController.readiness`（`/health/ready` 200/503）、运维经 GET `/restart/:restartId` 与 `/plugin-convergence/:generation` 查状态、PM2/容器监管者按信号拉起替代副本、`SandboxRuntimeHealthService.onModuleDestroy`（注销 Redis 心跳）
- 用途：把「API 副本自身的滚动重启」做成可授权、可观测、可回退的一次操作，并让在途请求与队列在关停前收敛（为 SSE/流式响应留 flush 时间）
- 唯一可观测持久痕迹：Redis 键 ＋ 结构化日志（`runtime.instance.retirement`、`HealthCheckExecutionTimer-<uuid>`）＋ 实例注册表；**没有任何表可查**
- 边界：协调依赖副本间共享同一 Redis（不可用即 503 `Runtime restart coordination is unavailable`）；**最后一个健康副本需运维显式 `allowDowntime`**；本地 nodemon 的「重启」等价于 watcher 重拉，drain 语义不成立；`retire` 必须带 `expectedBootId` 防误退
- 与沙箱的关系：沙箱作业**不因重启丢失**（状态在 `sandbox_job`），重启后同 `idempotencyKey` 的 `waiting/starting/running` 作业会被 `waitForAttachedJob` 重新挂上（跨进程重挂属该分支的自然结果 `[推测]`）；WS 终端/预览会话在进程内存，重启后需浏览器侧重连
