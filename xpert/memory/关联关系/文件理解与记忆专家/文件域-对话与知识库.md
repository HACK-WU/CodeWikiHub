[强关联] 文件理解与记忆专家 与 对话与会话专家 + 知识库专家（`ConversationFileLink` 是唯一读边界，`storage_file` 是知识库唯一摄取源）
- 强度：必改 —— 改本域读边界（`ConversationFileLink` 语义或 `FileAsset.conversationId`）→ 会话侧附件面板/消息组装/重试重建输入必改；改会话或消息表结构 → 本域记忆取证（`XpertConversationHistoryReader`）与 link 幂等 upsert 必改；改 `storage_file` 行结构或删除路径 → 知识库摄取源自失效
- 原因：三者共用同一份「会话附件事实」，但边界严格单向 —— 本域只**持有 link 与句柄**，会话行的读写与「读边界给出方」在对话与会话域；知识库只把 `storage_file` 当**源文件句柄**（`GetOwnedStorageFileQuery`），**不共享** `file_asset` 解析结果（依赖面窄、无反向依赖）
- A 端（本域 · 授权边界）：`ConversationFileLink`（唯一索引 `(conversationId,fileAssetId)`，注释逐字「The link is the read-permission boundary for file tools」）@ file://packages/server-ai/src/file-understanding/entities/conversation-file-link.entity.ts；`FileAssetAccessService.{resolve,assertConversationAccess,assertCanLinkToConversation}` @ file://packages/server-ai/src/file-understanding/file-asset-access.service.ts
- A 端（本域 · 工具与会话消费面）：8 个 `parsed_file_*` 工具的 `listVisibleFiles`/`resolveFileIds`（有可信 `projectId` 走 `ListProjectFilesQuery`，否则走 `ListConversationFilesQuery`，不可见 id 直接拒）@ file://packages/server-ai/src/file-understanding/tools/file-understanding.tools.ts；`XpertConversationHistoryReader`（只读 `chat_conversation`/`chat_message`）@ file://packages/server-ai/src/file-memory/adapters/
- B 端（对话与会话专家）：`ChatConversation`/`ChatMessage`（含 `chat_message` 与 `FileAsset` 的 `fileAssets` 关联与物理联接表、`@Tree('closure-table')` 与两个唯一索引）；`AttachFileToConversationCommand` 的投递方；会话侧附件面板与消息组装（`shared/agent/message.ts` 经 `ResolveAuthorizedFileAssetQuery`/`ReadFileAssetSourceQuery`/`GetFilePreviewQuery`，并保留老客户端 `GetOwnedStorageFileQuery` 兜底）
- B 端（知识库专家）：`knowledge-document/document.service.ts` 三处只用 `GetOwnedStorageFileQuery(document.storageFileId)` 取源句柄；**知识库侧是否会对 `storage_file` 行做二次写（补 `url`/`thumb`）未确认** @ .module-experts/后端专题/知识库专家/
- 改哪一侧会连带改另一侧：① 无 link 就没有会话级可见性 ⇒ 会话侧新增「引用某文件」必须投递 `AttachFileToConversationCommand` 而非直接调工具；② 本域 `attach` 是**先授权再看 link** ⇒ 会话/项目侧任何「先查 link」的快捷路径都会破坏该不变量；③ 附件重试重建输入依赖消息侧 `fileAssets` 联接表 ＋ StorageFile 兜底通道，改其一必改其二
- 边界面：会话/消息与附件面板归对话与会话专家；文档摄取、切片与向量归知识库专家；本域只提供句柄、解析状态、分块检索与读边界（**旧 `ConvFileDeleteCommand` 已由 `DeleteFileAssetCommand` 取代**）
