[强关联] 文件理解与记忆专家 与 项目与任务协作专家 + 运行时·沙箱·产物专家（`workspacePath` 投影与 `purgeProjectFile` 是仅有的两个跨域写口）
- 强度：必改 —— 改本域工作区投影（`workspacePath` / `FileWorkspaceProjectionService.projectFileAsset`）→ 沙箱侧文件消费与卷投递必改；改项目侧永久删除编排（`ProjectPurgeService.purge`）或项目卷布局 → 本域 `purgeProjectFile` 的一致性校验必改；改沙箱 backend/卷作用域 → 本域记忆读写（经 sandbox backend）与产物读回必改
- 原因：项目卷与项目资产索引归项目与任务协作专家，本域通过 `XpertProjectAccessService` 复用项目准入（`assertCanEdit`/`assertCanPurge`）并在项目永久删除时被 `ProjectPurgeService` 调用；沙箱与产物登记归运行时·沙箱·产物专家 —— 本域**交付 `workspacePath` 与 `FileRuntimeCapability`，不落沙箱产物**；记忆读写经 sandbox backend 执行，但 **backend 本身不归本域**
- A 端（本域 · 投影与回收）：`FileWorkspaceProjectionService.projectFileAsset`（best-effort write-through，投影失败不影响 attach 结果）@ file://packages/server-ai/src/file-understanding/file-workspace-projection.service.ts；`FileAssetDeletionService.purgeProjectFile`（注释逐字「Dedicated project lifecycle entry; never trusts the supplied project ID as authority.」）@ file://packages/server-ai/src/file-understanding/file-asset-deletion.service.ts；`resolveFileAssetWorkspaceVolumeScope` @ file://packages/server-ai/src/file-understanding/domain/workspace-file.ts
- A 端（本域 · 运行时与记忆面）：`FileRuntimeService.resolveFile/createScopedApi({conversationId})`（注释要求 Never persist a conversation identity on the shared provider instance.）@ file://packages/server-ai/src/file-understanding/runtime/file-runtime.service.ts；`XpertSandboxMemoryStore`（记忆落卷经 sandbox backend，入口先 `assertFileMemorySandboxFeatureEnabled`）@ file://packages/server-ai/src/file-memory/sandbox-memory.store.ts
- B 端（项目与任务协作专家）：`XpertProject`（`xpert_project` 本域只读注册、**写操作 0**）、`XpertProjectAccessService.assertCanEdit/assertCanPurge`、`ProjectPurgeService.purge`（先做「处理中不许删」忙判：存在 `uploaded/scanning/parsing/processing/queued` 即 400 `ProjectPurgeBusy`，逐资产清理后删项目卷根）；项目侧 `project-file.entity.ts` 已标注弃用（改走 FileAsset 工作区投影）
- B 端（运行时·沙箱·产物专家）：`ArtifactsService.createArtifact/ensureArtifactVersion`（产物四表只存 `workspaceFileRef` 便携引用，**字节归本域卷**）、`SandboxController.serveVolumeFile/uploadFile`（`mode:'mounted_workspace'`）、`WorkspaceFileAccessService`（**从本域导入** `resolveWorkspaceVolumeScope`）、`FileActivityStorage.archive`（沙箱中间件先 `WorkspaceFiles.uploadBuffer` 再登记）
- 改哪一侧会连带改另一侧：① 项目删除是**双域协作** —— 项目侧忙判 ＋ 本域逐资产硬删七步（向量→锚点→向量账本→chunk→artifact→link→`file_asset` 行→页图对象→派生目录）；任一侧改判定就产生「DB 已删、对象还在」的孤儿；② 本域 `workspacePath` 是沙箱侧**只读消费**的 POSIX 相对路径 ⇒ 改投影格式会打断沙箱/运行时的文件预览；③ 沙箱侧 `artifact_version.workspaceFileRef` 由 Workspace Files 上传结果组装 ⇒ 本域改上传返回体必须同步产物的引用校验（读取期 `sha256` 复核不符即 410/409）
- 边界面：项目卷、项目资产索引与项目生命周期归项目与任务协作专家；沙箱执行、产物登记与分享归运行时·沙箱·产物专家；本域只提供句柄、投影与回收执行（**不做沙箱内文件写入** —— `FileWorkspaceProjectionService` 只把对象存储文件**投影**为工作区路径）
