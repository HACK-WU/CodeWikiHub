只读 Token 的 `readOnly` 从「只约束 MCP 通道」扩到 `/mcp` + `/api` 写接口 + `/open/v1` 三通道一致（#96，2026-11-25 落地；同日补 Q2 模型消耗口径）。

- 旧判断（被推翻）: docs 明写「只读只约束 MCP 通道，`/api/*` 与 chat 通道仍可写」，实现上也确实不读 `principal.readOnly`；前端 UserTokenSection 却承诺「Token 权限不会超过账号权限 / 只读 Token 仅能检索与读取知识库」——两者矛盾。
- 写维度决定: 中央闸门按「token + readOnly + WRITE_CAPABILITIES」拒绝（403 `TOKEN_READONLY`，与 `/mcp` 同码）；chat 通道按能力集收窄工具面（`withoutWriteCapabilities`）。**不改 role**：token 无 userId，降级 viewer 会让 chat 会话归属校验直接 403。
- 模型维度决定（Q2）: 发起 AI 追问同样拒绝（403 `TOKEN_MODEL_FORBIDDEN`，与 `/mcp` 对 `ki_ask` 同口径）。标记挂在**路由**（`route-permissions.ts` 的 `modelConsuming`）而不是能力上 —— `knowledge.ask` 同时覆盖「发起/停止/读记录」，按能力判会连停止与读记录一起拦；停止追问与读历史记录仍放行。
- 硬约束: 只读判定必须排在 capability 判定**之后**，否则 viewer 会话错误码从 `USER_READONLY` 变 `TOKEN_READONLY`。
- 边界: 读接口、检索、历史追问、停止追问放行；chat 内的 `ki_ask` 仍可用（chat 本身已消耗模型，viewer 会话同样可用）。
- 备选（未采纳）: 让 token 能力 = 所有者角色能力 ∩ `TOKEN_CAPABILITIES`——需跨 user-store 取 owner 角色，并推翻 `TOKEN_CAPABILITIES` 的既有决策与断言。
- 对外代价: 外部脚本用只读 Token 直调 `/api` 写接口或发起追问会由 200 变 403（breaking），需 release note。
- 遗留: `POST /api/vector/status/refresh` 登记为 `knowledge.read` 但含刷新动作（既有口径，未核）。
