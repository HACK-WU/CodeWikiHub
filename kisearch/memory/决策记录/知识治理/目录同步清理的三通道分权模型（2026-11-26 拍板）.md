目录导入的「同步清理」按通道分权：页面可算可删、本机 CLI 可算可删、远端 token 通道只算不删。
- 拍板（2026-11-26 用户）：① token 通道不提供删除权限，open-api 不开删除端点；② 范围含同机 `ki import`。
- 三通道：页面 = `pruneStale` 开关 + `POST /api/import/prune`（权限 `datasource.delete`，前端二次确认）；本机 = `ki import --prune` 只打印、`--prune --yes` 走 `executeBatchDelete`；`ki-client upload-dir --prune` = 调只读端点拿候选并打印，再提示去页面或服务端主机删除。
- 硬约束一：`ki-client` 增量只传 sha256 变化的文件，服务端收到的文件集 ≠ 本次目录全量 ⇒ 客户端必须显式交出全量 `.md` 相对路径（图片是 assets，混入会稀释闸门分母）；不能用「服务端收到了哪些」当全量。
- 硬约束二：open-api 的只读判定按 HTTP 方法（GET 放行 / POST 返 403 `OPEN_API_TOKEN_READONLY`），候选查询若走 POST 就只有可写 token 能用；因 `--prune` 依附上传命令（上传本就需可写 token），语义自洽，不算缺陷。
- 删除面：`executeBatchDelete` 默认硬删 wiki 镜像 `.md`（不进回收站）；数据源 prune 显式 `wikiDelete:false` 回避，导入清理沿用「删镜像」（与页面一致），需在确认清单里显式披露。
- 实施前置核查（2026-11-26 代码直读）：`daemon-dispatch.ts:161` 把 import 的 params 原样展开（CLI 传的 `pruneStale`/`pickMode` 会透传；`lib/import.ts` 注释「CLI 与 daemon RPC 都不传」是现状描述而非限制）；`ki-client/src/http.ts:174` 已有 `postJson`，客户端无需新增 HTTP 原语；open-api 侧**无任何 JSON body 解析**（`readJsonBody` 0 命中），这是本次唯一需新建的基础设施（含大小上限与 413）。
- 候选口径唯一：必须复用 `planImportPrune`（双闸门 0.8 / 0.8、500 上限、候选指纹），禁止客户端另算一套，否则 CLI 会删得比页面狠。
