分析链路与查找链路的 ki_group_list / ki_tag_list 统一改为「逐成员收集 + 分层降级」，修复视图或多库 scope 下只查首个成员库的静默丢失（事件 #112）。
- 判据: 聚合语义工具（树 / 标签，要全貌）必须逐成员收集；定位语义工具（ki_get_module_info，要一篇）才允许命中即止。同一条捷径被两类工具共用，就是 #110 / #112 的共同根因
- 落点: analysis-runner.ts 与 recall/tool-runner.ts 均接 group-list-view.queryGroupByScope / tag-list-view.tagListByScope
- 统一入口新增三个可选参数: resolved（调用方已解析的 physical，避免入口内部 loadConfig 绕过 config 快照）、maxFullMembers（前 N 个成员完整树、其余按 depth=1 只给顶层 Group）、runOne / listOne（执行器接管，保住 OperationCoordinator 互斥与快照）
- 降级口径: 分析 / 查找链路传 maxFullMembers=1；降级桶带 degraded:true + note「需细看请把 scope 传成该库名」，不许静默降级
- scopeUsed 口径: 视图 / 多库时记视图名（原先记首个命中库名，调用方看不出漏了成员）；ki_get_module_info 的 read.scope 仍记真实库 —— 那是「从哪篇读到」，两者不可统一
- 三端补齐（2026-11-27 二轮）: 统一入口原判据只看 isViewRequest，逗号多库（scope:"a,b"）虽被 resolveScopeTargets 标了 multiRequested，却因 views 为空落到 single 分支只取首个库。判据改为 isViewRequest || multiRequested；view 字段回显原始入参（不再空串）。单库 / 视图入参形状零变化；逗号多库入参从「静默单库」改为分桶 / 合并，属对外响应形状变化（用户已拍板）。CLI 命令层对逗号仍在 validateScope 处 fail-loud 报错，不静默丢失，未改
- 被否方案: 「只查第一个 + 整体标注」——模型不知道漏了什么，只能靠回传成员清单逐库补查，N-1 次往返未必更省 token，且多轮更易丢线索
- 验收: 真机 kisearch-docs 视图 group 由单库 457 字变两桶 394+348（xperts 降级 depth=1）、tag count=165 且 scopes 覆盖两库；真机逗号多库 scope=kisearch-memory,kisearch-xperts 两桶均有内容、tag count=165 覆盖两库。测试 recall-tool 22/22、analysis-scope-switch 11/11、chat-tool-view 11/11（后者新增 2 例锁死逗号多库）、mcp-tool-view 9/9、group-cli 5/5、query-group 41/41；tsc 0
