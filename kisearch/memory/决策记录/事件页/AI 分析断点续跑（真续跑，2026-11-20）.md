AI 分析被中断（服务重启 / 进程被杀）后可以「继续分析」，从断点接着跑而不是从头重来。用户 2026-11-20 明确选择真续跑（而不是「带线索重跑」）。

- 断点文件：`.events/{eventId}.analysis.resume.json`（与 `.analysis.json` 分离，因为生命周期不同：断点只在跑着/中断时有意义，收尾即删）。内容：完整 `messages`（system + 首条 user + 历次 assistant/tool，含工具响应正文）、round/turns/tokens/elapsedMs、steps、filesRead、startedAt/updatedAt。
- 写点：**每轮工具结果都进 messages 之后**写一次（原子写：tmp + rename），写失败吞掉不打断分析。
- 清理：终态（ready/partial/failed/cancelled）写盘成功后 `clearResume`；新增一次分析（非续跑）开始时也清旧断点。7 天 TTL，读时过期即删。
- 体积：`RESUME_MAX_BYTES = 8MB`，超限裁掉最旧轮次（保留 system + 首条 user + 最近 24 条消息、最近 120 条 steps）。
- 续跑入口：`POST /events/:id/analyze {resume:true}`；**复用原 runId**（前端认同一个运行），`steps` 接着追加而不是重置，`round` 从断点轮次继续，`stats.ms` 用累计 `elapsedMs`（不含停机时间）。
- 校验：断点 runId 必须与当前草稿 runId 一致，否则视为脏断点，删掉并报 `ANALYSIS_RESUME_UNAVAILABLE`（1621 / HTTP 409）。
- 前端：详情 `analysis.resumeAvailable`（后端 stat 一次，不解析正文）；中断态底栏出「重新分析」+「继续分析」，后者走 resume。
- 真机验证（#62）：跑 55s（12 步）→ `kill -9` → 重启，得到 `failed / ANALYSIS_INTERRUPTED / steps=14 / resumeAvailable=true` → 续跑启动后 `steps=14` 且 runId 不变，随后 16→25 继续增长。
- 边界：首轮就挂（还没工具轮）没有断点；断点不跨设备；恢复的是上下文快照，源码此后若变，结论仍可能按旧代码得出（TTL 7 天是折中）。
