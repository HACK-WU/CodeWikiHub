2026-11-23 用真实上游实测 OpenAI 多模态消息形状的可接受度，结论直接决定图片该从哪条消息进入上下文。
- 环境：deepseek-v4.1-flash-1017（配置取自 ~/.ki/config.yaml）
- 支持：`content` 传 `[{type:'text'},{type:'image_url',image_url:{url:'data:image/png;base64,…'}}]` 返回 200，模型准确读出图内三段色带
- 关键：`role:'tool'` 消息**可直接承载** `image_url` part，且模型确实读取（回答中主动说明「颜色名来自结果中附带的图片」）⇒ MCP 工具结果带图**不必**挪进 user 消息，不触碰 tool-loop 的「末条恒为本轮 user」不变量
- 成本口径：`image_tokens` 只随**像素尺寸**增长，与文件体积无关 —— 240×120→202、512²→184、1024²→652（6KB 与 71KB 噪声图同值）、1568²→994；单条 2 张线性累加 404；耗时 1.4~2.9s
- 推论：压缩画质/体积不省 token，只有降分辨率才省；图片不可按字符计入 `maxToolResponseChars`（base64 会撞穿 10000）
- 边界：未验证真实界面截图的**中文小字**识别、4MB 级请求体上游上限、其他厂商模型（故 `llm.supportsImages` 仍须手填、不自动探测）
- 复现：`CodeWikiHub/kisearch/requirements/2026-11-23-AI对话图片输入/demo/verify/probe-image-multimodal*.mjs`（脚本自生成 PNG、零依赖，apiKey 从 ~/.ki/config.yaml 读取），同目录 `verify-report.md` 为完整探测明细
- 需求：REQ-20261123-006（用户上传图）；MCP/文档附图读取为事件 #78
