知识治理的读接口（分类/事件/回收站/计数/诊断/参考文档搜索）没有接视图展开：视图名被原样当物理 scope 去读，`readAllGroupCaches` / `readAllEvents` / `listTrash` / `readGovernance` 全部返回空，页面与侧栏显示 0 且不报错。
- 机制：`resolveScopeTargets` 是视图唯一展开点，但 `governance-http.ts` 的 `scopeFromQuery` / `scopeFromBody` 只做 `assertScope` 名字比对后原样返回；同时 `listTypes` 对不存在的库返回内置类型，所以页面看起来「正常但空」。
- 已支持视图的对照：`/api/doc/list`、`/api/doc/get`、`/api/tags` 与 MCP `ki_search` / `ki_group_list` / `ki_tag_list` / `ki_get_module_info` / `ki_recall`。
- 写侧基本安全：事件创建/流转/分类改档/事件类型都走 `withScopeWriteLock`，其内 `assertNotScopeView`（在取锁与建目录之前）会抛 `VIEW_NOT_WRITABLE`。
- **两处漏网（实证）**：`POST/DELETE /governance/lifecycle/presets` 与 `PUT /governance/trash/settings` 直接 `writeGovernance(scope)`，不经写锁；`writeJson -> walWrite` 首行 `mkdirSync(dirname)` 会在 `dataDir/<视图名>/` 建出目录与 governance.json，违反「视图名不得进入 getKbDir」的铁律。
- 改造要点：治理读路径入口改用 `resolveScopeTargets` + 逐库 try/catch 合并（参 `mcp-tools/group-list.ts` 分桶）；文档条目必须带 `scope`（身份三元组），事件 shortId 是库内计数、合并后必冲突；鉴权不能只比名字，要换 `isScopeAccessAllowed`（视图 ∧ 全部成员），否则视图成为越权通道。
- 位置：`src/lib/governance-http.ts`、`src/lib/scope-policy.ts`、`src/lib/scope-write-lock.ts`、`web/src/lib/viewBuckets.ts`（前端跨库复合键范式）。
