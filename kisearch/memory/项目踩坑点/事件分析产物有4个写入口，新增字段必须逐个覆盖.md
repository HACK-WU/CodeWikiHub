事件分析的 `{eventId}.analysis.json` 有 **4 个写入口**，新增字段（例：数据链路 `dataFlow`）必须逐个覆盖，漏一个就是「数据丢失」或「语义撕裂」。

- **AI 分析**：`analysis-runner` 解析模型 JSON + 建草稿 → 新分析自然带；重跑会重建草稿，字段随之消失（符合预期）。
- **外部上传（MCP `ki_event_edit action=analysis`）**：`analysis-store.saveExternalAnalysis` + `analysis-edit.validateExternalImport` + `mcp-tools/event-edit.ts` **三张表**（`ALLOWED_FIELDS.analysis` / `KNOWN_FIELDS` / zod schema）。白名单是严格的：漏登记则调用方传了直接报错；不传则不报错但**整篇重建草稿时字段消失**（整篇覆盖语义，无局部更新）。
- **追问补丁**：`analysis-ask-patch` 只解析 `conclusion` / `chain` / `reason`，`diffProposal` 也只比较这两块 → 采纳后是「新结论 + 旧链路」并存，语义撕裂，风险最高（用户会照旧链路排查）。
- **人工校正 `PATCH /analysis`**：按 H12「结论不可人工编辑」，新字段**不应**加入，否则破例；`saveDraftEdits` 是字段可省的整块提交，未提交字段会被保留（所以补丁链路才不会丢）。
- **重置 `DELETE /analysis`**：整块清空，天然覆盖。
- 另有两处必同步：① 契约双份 `src/lib/governance-contract.ts` + `web/src/api/governanceContract.ts`（逐字比对测试）；② 前端三处渲染（`EventAnalysisCard` 结论卡 / 编辑态只读结论块 / `AiAnalyzePanel` 最终结论）。
- 位置: `src/lib/events/analysis-store.ts`、`src/lib/mcp-tools/event-edit.ts`、`src/lib/events/analysis-ask-patch.ts`
