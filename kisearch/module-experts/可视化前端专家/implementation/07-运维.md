## 简介

本文覆盖 ki-web 的构建、部署、配置与排障。前端无独立运行时进程——生产形态下它是 `ki mcp --http --web` 托管的静态目录，运维动作收敛为「构建 + 重启后端」。

章节来源：[vite.config.ts](file://web/vite.config.ts)（关键符号：文件头注释「独立 Vite 工程」）

## 构建与依赖管理

| 动作 | 命令 | 说明 |
|---|---|---|
| 安装 | `cd web && npm install` | 独立 package-lock（web/package-lock.json），与根工程互不干扰 |
| 开发 | `npm run dev` | 5173 端口（strictPort，被占即失败不换端口） |
| 类型检查 | `npm run typecheck` | `tsc --noEmit` |
| 构建 | `npm run build` | 先 `tsc --noEmit` 再 `vite build`（类型错误阻断构建，fail-loud） |
| 预览构建产物 | `npm run preview` | vite 本地预览 dist（接口需另配，一般不用） |

- 产物：`web/dist/`（`build.target: 'es2022'`，无 sourcemap）；已提交构建产物的独立部署不可取——**dist 由构建生成，随源码演进**
- 构建依赖：Node ≥ 18（对齐根工程）；Vite 5 + @vitejs/plugin-react
- `@` 别名仅构建期（vite resolve.alias）；`web/tsconfig.json` 需保持 paths 映射一致

章节来源：[package.json](file://web/package.json)（关键符号：`scripts`）；[vite.config.ts](file://web/vite.config.ts)（关键符号：`build`、`resolve.alias`、`server.strictPort`）

## 部署形态与启动矩阵

| 场景 | 启动命令 | 访问 | 静态来源 |
|---|---|---|---|
| 生产（推荐） | `ki mcp --http --web`（可加 `-d` daemon、`--web` 状态会随 restart 延续） | `http://127.0.0.1:7423/` | `web/dist`（serveStatic + SPA fallback） |
| 开发联调 | `ki mcp --http` + `cd web && npm run dev` | `http://127.0.0.1:5173/` | Vite dev server（HMR），`/api` `/mcp` `/healthz` 代理 7423 |
| 纯 MCP（无 UI） | `ki mcp --http` | — | 不托管静态（`webDir` 缺省禁用） |

- SPA fallback：非 `/api`、`/mcp`、`/healthz` 的 GET 404 时回退 `index.html`；带路径穿越防护（normalize 后必须仍在 webDir 内）
- 前端进程不存在——**无需为前端做守护**；`ki mcp --http -d` 即覆盖 UI 可用性
- 重启语义：`ki mcp restart` 延续上次 `--web` 状态（lock 文件记录）；显式关闭用 `restart --no-web`

章节来源：[mcp-http.ts](file://src/lib/mcp-http.ts)（关键符号：`serveStatic`、`webDir`）；[vite.config.ts](file://web/vite.config.ts)（关键符号：`server.proxy`）

## 配置项

前端**无独立配置文件**；行为受以下项影响：

| 配置点 | 位置 | 影响 |
|---|---|---|
| MCP HTTP host/port | `~/.ki/config.yaml`（`mcp.http.*`）或 CLI 覆盖 | 端口非 7423 时：生产自动跟随；**dev 模式需手改 vite.config proxy 目标** |
| 版本横幅 | `AppShell.tsx` 硬编码「ki v0.1.0 · MCP 7423」 | 纯展示文案，改版本/端口需手改 |
| `--web` 开关 | CLI `ki mcp --web/--no-web` | 是否托管 UI |
| localStorage | 浏览器侧 `ki-web:scope`、`ki-theme` | 用户偏好，清除即重置 |

章节来源：[AppShell.tsx](file://web/src/layouts/AppShell.tsx)（关键符号：footer 版本行）；[scopeContext.tsx](file://web/src/lib/scopeContext.tsx)（关键符号：`STORAGE_KEY`）

## 日志与排障

- **前端无日志上报**：不向后端发送遥测；排障靠浏览器 DevTools（Console/Network）
- **后端侧**：`ki mcp --http` 的 stderr 日志含请求级来源标注（`[kisearch][mcp:<tool>]` / `api:<endpoint>`），可直接看到前端触发的调用
- **典型故障速查**：

| 症状 | 排查 |
|---|---|
| 白屏 + Console 报 `/mcp` 连接失败 | 后端未启动或 dev 代理目标端口不对 |
| 横幅「MCP HTTP 未就绪」但接口部分可用 | `/api/health` 失败——看后端 stderr 健康检查项 |
| 构建失败 | `npm run build` 先跑 tsc，看类型错误（改动了 api 层类型最常见） |
| 页面路由 404 刷白 | 确认经 `--web` 访问（有 SPA fallback）；直接文件协议打开 dist 不行 |
| 搜索一直失败 | 后端向量库锁/引擎状态，看 `[kisearch][mcp:ki_search]` 日志 |

章节来源：[mcp-http.ts](file://src/lib/mcp-http.ts)（关键符号：`serveStatic` 路径穿越防护）

## 升级与兼容注意

- **前端不校验后端版本**：无 version 握手，前后端版本错配时靠接口报错暴露（后端长驻进程自身有 version-guard 升级提醒，但不覆盖前端）
- **升级流程**：`git pull` → `cd web && npm install && npm run build` → `ki mcp restart`（延续 --web）；跳过 build 直接 restart 会继续用旧 dist
- **mermaid/marked 大依赖**：升级注意 mermaid chunk 体积与 `securityLevel: 'loose'` 设置（当前有意为之，允许图表内 HTML）

章节来源：[mcp-server.ts](file://src/mcp-server.ts)（关键符号：`runRestartCommand`、`--web` 延续逻辑）；[MarkdownPreview.tsx](file://web/src/components/MarkdownPreview.tsx)（关键符号：`mermaid.initialize`）

## 结论

ki-web 的运维面极小：一条构建命令 + 后端 `--web` 开关即完成部署；无独立进程、无配置文件、无日志系统。唯一需要记住的运维约束是**「改前端必须重新 build 才对生产生效」**与 **dev 模式代理端口和后端端口要一致**。
