> 本契约覆盖本专家的公开能力。契约来源标注函数签名（非行号）。

## 0. 入口对照（CLI ⇄ MCP ⇄ 纯函数）

## 1. 评分引擎（`src/lib/scoring.ts`）

### 1.1 `Relation`（数据模型）

- **用途**：关系条目。relations-cache 与各管理命令共用，导入链路（知识索引导入专家）同构。
- **字段**：`id: string`、`text: string`、`score: number`、`useCount: number`、`lastUsedTime: number | null`、`isImported: boolean`；可选 `memoryId?: string`（内容向量主 docId）、`memoryIds?: string[]`（全部内容向量 docId，多 tag 各一）、`sourcePath?: string`、`tags?: string[]`（文档级自定义标签）。
- **约束**：`useCount` 封顶 `MAX_USE_COUNT = 10`；`lastUsedTime` 为 `null` 表示从未被读取过。

### 1.2 `calculateScore(useCount, lastUsedTime, now, halfLifeHours?)`

- **用途**：计算关系的使用密度评分。
- **参数**：
  - `useCount: number` — 使用次数。传 `0` 时直接返回 `0`。
  - `lastUsedTime: number | null` — 上次使用时间戳（毫秒）。传 `null` 时按"刚使用"处理（无衰减），等价于 `score = useCount`。
  - `now: number` — 当前时间戳（毫秒）。
  - `halfLifeHours: number`（默认 `24`）— 半衰期（小时）。值越大衰减越慢。
- **返回**：`number`。
- **异常**：无。
- **约束**：纯函数，不修改入参。

```ts
import { calculateScore } from './lib/scoring.js';
// 5 次使用、12 小时前用过、半衰期 24h → 5 / (1 + 12/24) ≈ 3.33
const score = calculateScore(5, Date.now() - 12 * 3600_000, Date.now(), 24);
// 从未使用过 → 0
const zero = calculateScore(0, null, Date.now());
```

### 1.3 `recordUse(relation, now)`

- **用途**：记录一次使用（带防刷）。
- **参数**：
  - `relation: Relation`。
  - `now: number` — 当前时间戳（毫秒）。
- **返回**：`Relation`（**新对象，不修改入参**）。
- **行为语义**：
  - 距上次使用不足 `MIN_RECORD_INTERVAL_MINUTES = 5` 分钟 → 原样返回入参（不计数、不更新时间）。
  - 否则 `useCount` 加 1 后按 `MAX_USE_COUNT = 10` 封顶，并更新 `lastUsedTime = now`。
  - `lastUsedTime` 为 `null` 时不受防刷限制，直接计数。
- **约束**：返回新对象；判定用 `relation.lastUsedTime`，不是返回值的 score（score 需调用方另行 `calculateScore` 重算）。

```ts
import { recordUse, calculateScore } from './lib/scoring.js';
const now = Date.now();
const updated = recordUse(rel, now);               // 防刷内可能等于 rel
updated.score = calculateScore(updated.useCount, updated.lastUsedTime, now, 24);
```

### 1.4 `hybridPartition(items, now, config)`

- **用途**：对 Relation 数组做冷热分区（含新兴热区识别）。
- **参数**：
  - `items: Relation[]`。
  - `now: number`。
  - `config: PartitionConfig`（见 1.7）。
- **返回**：`{ hot: Relation[]; warm: Relation[]; cold: Relation[] }`。
- **行为语义**：先用 `calculateScore(item.useCount, item.lastUsedTime, now, config.halfLifeHours)` 重算每个条目的 score；`config.recentHours` 内有 `lastUsedTime` 的条目视为"新兴"，新兴项按 `lastUsedTime` 降序优先占热区席位（最多 `config.reservedEmerging` 个），其余按 score 降序填充。

### 1.5 `partitionByScore<T>(items, accessors, config)`

- **用途**：泛型冷热分区，供 Relation 与 Group 路径等不同 item 类型复用。
- **参数**：
  - `items: T[]`。
  - `accessors: { getId; getScore; isEmerging; getEmergingSortScore? }` — `getId(item) => string`、`getScore(item) => number`、`isEmerging(item) => boolean`；`getEmergingSortScore` 省略时回退用 `getScore`。
  - `config: PartitionConfig`。
- **返回**：`PartitionResult<T>` = `{ hot: T[]; warm: T[]; cold: T[]; emergingSet: Set<string> }`。
- **行为语义**：热区席位 `max(minHotCount, ceil(n * hotPercent))`；温区 `ceil(n * warmPercent)`，其余进冷区。上限截断（`maxHotCount` / `maxWarmCount` / `maxColdCount`）时**优先保留新兴席位**，再补历史高分。
- **约束**：纯函数；`getId` 重复会导致条目被去重丢弃。

```ts
import { partitionByScore } from './lib/scoring.js';
import { DEFAULT_PARTITION_CONFIG } from './lib/constants.js';
const { hot, warm, cold, emergingSet } = partitionByScore(
  paths,
  { getId: (p) => p, getScore: (p) => scoreMap.get(p) ?? 0, isEmerging: (p) => recent.has(p) },
  DEFAULT_PARTITION_CONFIG
);
```

### 1.6 `boundaryDecay(hotItems, warmItems, newScore, decayStep?)`

- **用途**：新内容挤入热区时，对热区/温区边界做衰减。
- **参数**：`hotItems: Relation[]`（按 score 降序）、`warmItems: Relation[]`（按 score 降序）、`newScore: number`、`decayStep: number`（默认 `5`）。
- **返回**：`{ hotItems; warmItems; triggered: boolean; originMax?: number }`。
- **行为语义**：仅当 `hotItems` 非空**且** `newScore` 严格大于热区最低分时触发（`triggered: true`）；否则原样浅拷贝返回 `triggered: false`。触发时整体下调边界分数，热区仅 1 项时走单元素退化（只按 `decayStep` 衰减，不拉低到温区水平）。
- **约束**：纯函数，返回新对象数组（浅拷贝元素）。

```ts
import { boundaryDecay } from './lib/scoring.js';
const r = boundaryDecay(hot, warm, newScore);
if (r.triggered) console.log('边界已衰减，原温区最高分', r.originMax);
```

### 1.7 `PartitionConfig` / `DEFAULT_PARTITION_CONFIG`

- **契约来源**：`src/lib/constants.ts`。
- **当前默认值**：`hotPercent: 0.3`、`warmPercent: 0.5`、`reservedEmerging: 10`、`recentHours: 48`、`minHotCount: 1`、`decayStep: 5`、`halfLifeHours: 24`、`maxHotCount: 10`、`maxWarmCount: 50`、`maxColdCount: null`、`maxKeywordCount: 50`。
- **行为语义**：`maxColdCount: null` 表示冷区不截断；`recentHours` 同时决定新兴识别窗口与 `emerging` 分区口径。
- **约束**：配置从 `relations-cache.json` 的 `partition_config` 读取，缺失时回退 `DEFAULT_PARTITION_CONFIG`。

## 2. Group 路径解析（`src/lib/group-resolve.ts`）

### 2.1 `resolveGroupPath(userInput, groupIndex, groupsData, scope?)`

- **用途**：把用户输入的 Group 路径解析为索引树中真实存在的路径。
- **参数**：
  - `userInput: string` — 用户输入的 Group 路径。
  - `groupIndex: GroupIndex` — `group-index.json` 数据。
  - `groupsData: Record<string, unknown>` — relations-cache 的 `groups`（有 Relation 数据的 Group 在此有键）。
  - `scope?: string` — **传入才启用向量兜底**；不传则跳过语义模糊匹配。
- **返回**：`Promise<ResolveResult>`，字段为 `{ resolvedPath: string; hint: string; matched: boolean; candidates?: string[]; fuzzyMatched?: boolean; fuzzyScore?: number }`。
- **行为语义**（四级降级）：
  1. `groupsData` 键精确命中 → `matched: true`，`hint` 为空串。
  2. `group-index` 树中路径完整存在 → `matched: true`（路径存在但无 Relation 数据也算成功）。
  3. 顶层 Group 下整段补全：唯一命中 → 自动补全（`hint` 为补全提示）；多个命中 → `matched: false` + `candidates` 列表。
  4. 向量兜底（需传 `scope`）：`searchPath(userInput, 'ki-path', scope)` 命中且候选路径真实存在 → `matched: true` + `fuzzyMatched: true`；否则回退到部分匹配提示（含最近前缀与其子节点）或"未匹配到任何 Group"+可用顶层 Group 列表。
- **异常**：不抛异常；失败以 `matched: false` + `hint` 表达。
- **约束**：路径分隔符只支持 `/`（**不再支持 `.`**）；已无 rootName 概念，`userInput` 即完整相对路径。

```ts
import { resolveGroupPath } from './lib/group-resolve.js';
const r = await resolveGroupPath('docs/api', groupIndex, cache.groups, scope);
if (r.matched) use(r.resolvedPath);
else console.error(r.hint, r.candidates);
```

### 2.2 `pathExistsInTree(groups, groupPath)`

- **用途**：判断路径在 group-index 树中是否完整存在。**返回** `boolean`。空路径返回 `false`。

### 2.3 `findLongestExistingPrefix(groups, groupPath)`

- **用途**：找路径在树中的最长存在前缀。**返回** `string | null`（首段就不存在返回 `null`）。

### 2.4 `getDirectChildren(groups, groupPath)`

- **用途**：取节点下直接子节点名列表。**返回** `string[]`（路径不存在返回 `[]`）。`groupPath` 传空串等价于取顶层节点。

## 3. Wiki 写回与历史补齐（`src/lib/wiki-sync.ts`）

### 3.1 `isUnsafeRelationName(relation)`

- **用途**：relation 名合法性判定。
- **返回**：`boolean` — 含 `/`、`\` 或 `..` 时为 `true`（非法）。
- **约束**：入口校验与各 wiki 文件定位点复用同一判定，避免漂移。

### 3.2 `writeBackToWiki(scope, group, relation, moduleInfo)`

- **用途**：把关系内容写回外部 Wiki 文件。
- **返回**：`WikiWritebackResult` = `{ synced: boolean; file?: string; reason?: string }`。
- **行为语义**：
  - `wikiSync.enabled` 显式为 `false` → `{ synced: false, reason: 'wikiSync.enabled=false 已禁用 wiki 写回' }`（未配置 wikiSync 时视为启用）。
  - 目标目录优先级：group-index 的 `source.dir` > 配置的 `wikiSync.sourceDir`；都没有 → `{ synced: false, reason: '无可用 wiki 写回目录…' }`。
  - 目标目录不存在或为空且 `wikiSync.autoBackfill` 未显式关闭 → **先自动全量补齐历史关系**再写本次条目（stderr 输出补齐提示）。
  - 写回路径 `{目标目录}/{group}/{relation}.md`，`group` 为空串时落在目标目录根。
- **异常**：**不抛异常**，所有失败以 `reason` 返回。
- **约束**：`relation` 含非法路径字符时拒绝；目录递归创建。

```ts
import { writeBackToWiki } from './lib/wiki-sync.js';
const r = writeBackToWiki(scope, 'wiki/docs', '告警收敛机制', '## 概述…');
if (r.synced) console.log('已写回', r.file);
else console.warn('跳过写回：', r.reason);
```

### 3.3 `backfillWiki(scope, opts?)`

- **用途**：历史补齐——把 KB 中已有 Relations 全量写回 Wiki（典型场景：先导入数据、后才开启 wikiSync）。
- **参数**：`scope: string`；`opts?: { force?: boolean }`。
- **返回**：`WikiBackfillResult` = `{ ok; action: 'wiki-backfill'; scope; error?; targetDir?; stats: { total; written; skipped; empty; existed }; skipped: Array<{groupPath; relation; reason}> }`。
- **行为语义**：
  - `force` 缺省（`false`）→ **幂等：已存在的文件跳过**，不刷新 `exportedAt`（避免 git 管理的 wiki 目录产生全量脏 diff）；`force: true` → 全量覆盖写。
  - 遍历 relations-cache 的 `groups`（平铺完整路径键），从 local KB 取每条 relation 内容逐条写回。
  - 失败前置（fail-loud，`ok: false` + `error`）：`wikiSync.enabled === false`、无可用目标目录、`relations-cache` 不存在或解析失败。
- **约束**：local KB 无内容的条目计入 `stats.empty` 而非失败；含非法路径字符的脏数据跳过。

```ts
import { backfillWiki } from './lib/wiki-sync.js';
const r = backfillWiki(scope);                 // 只补缺
// { ok: true, stats: { total: 42, written: 7, skipped: 0, empty: 3, existed: 32 }, … }
const full = backfillWiki(scope, { force: true }); // 全量覆盖
```

### 3.4 CLI：`ki wiki-backfill <scope> [--force]`

- **用途**：上述 `backfillWiki` 的命令行入口。位置参数 `<scope>` 必填，其余仅接受 `--force`（未知参数报错并打印帮助）。
- **返回**：JSON（`WikiBackfillResult`）；失败时 `{ ok: false, error, code, help }` 且退出码 1。

```bash
ki wiki-backfill my-proj              # 幂等补齐
ki wiki-backfill my-proj --force      # 全量覆盖写
```

## 4. 路径语义搜索（`src/lib/path-search.ts`）

### 4.1 `searchPath(query, tag, scope, threshold?)`

- **用途**：Group 路径 / Relation 名称的向量语义模糊匹配（精确匹配失败时的兜底）。
- **参数**：
  - `query: string` — 查询文本。
  - `tag: 'ki-path' | 'ki-relation'` — `ki-path` 搜 Group 路径，`ki-relation` 搜 Relation 名称。
  - `scope: string`。
  - `threshold: number`（默认 `0`）— RRF 融合分阈值。默认 `0` 表示接受 top-1，**质量由调用方对候选做存在性二次校验保证**。
- **返回**：`Promise<PathSearchResult | null>`，`PathSearchResult` = `{ matched: boolean; rawText: string; extractedPath: string; score: number }`。
- **行为语义**：检索无结果时返回 `{ matched: false, rawText: '', extractedPath: '', score: 0 }`；有结果但分数低于阈值时返回 `{ matched: false, rawText, extractedPath: '', score }`（保留原文与分数）。
- **异常**：**不抛异常**——网络/服务不可用等一律 stderr 提示后返回 `null`（静默降级）。`query` 为空/空白直接返回 `null`。
- **约束**：只取 top-1；融合分量级远小于 1，**不可沿用余弦阈值 0.75**。

```ts
import { searchPath } from './lib/path-search.js';
const r = await searchPath('告警收敛', 'ki-relation', scope);
if (r?.matched) console.log(r.extractedPath, r.score);
```

## 5. 关系回写（`src/sync-relation.ts`）

### 5.1 `executeSyncRelation(params)`

- **用途**：单条关系写入（cache + local KB + 向量 + Wiki 四层）。
- **参数** `SyncRelationParams`：
  - `scope?: string` — 缺省走 scope 护栏解析（default 模式回退 `default`，strict 模式必须显式且已注册）。
  - `group: string`、`relation: string`、`moduleInfo: string` — 均必填且不可为空白。
  - `vector?: boolean`（默认 `true`）— `false` 为非向量化模式：**仅写 KB 层，不产生 memoryId，内容无法被 `ki search` 召回**。
  - `tags?: string` — 逗号分隔的自定义内容标签，叠加在默认 `ki-search` 之上。
- **返回**：`SyncRelationResult` = `{ ok: true; scope; relation; evicted: string | null; hint?; vectorPending?; vectorStored?; vectorReason?; wikiSynced?; wikiFile?; wikiReason? } | { ok: false; error }`。
- **行为语义**：
  - 同一 `group` 下已存在同名 relation → 视为"更新"：记一次使用（受 5 分钟防刷限制）、覆盖 local KB 内容。
  - 新增且该 Group 关系数已达 `maxHotCount` → 淘汰 score 最低的一条，`evicted` 为被淘汰的 relation 文本。
  - `vectorStored: true` 表示至少一条内容向量写入成功；部分失败时 `vectorStored` 仍为 `true` 但附带 `vectorReason`（旧向量被保留，不"删旧丢新"）。
  - `hint` 透出 Group 路径解析提示（自动补全 / 未匹配）。
- **异常**：不抛异常，一律转为 `{ ok: false, error }`。
- **约束**：`relation` 含 `/`、`\`、`..` 在写入任何数据前直接拒绝；`moduleInfo` 超 1000 字符 CLI 侧仅告警不切分。

```ts
import { executeSyncRelation } from './sync-relation.js';
const r = await executeSyncRelation({
  scope: 'my-proj',
  group: 'wiki/docs',
  relation: '告警收敛机制',
  moduleInfo: '## 概述\n告警收敛通过聚合相似告警降低噪声。',
  tags: '告警,收敛',
});
if (r.ok) console.log(r.vectorStored, r.wikiSynced, r.evicted);
```

```bash
ki sync-relation --scope my-proj --group "wiki/docs" \
  --relation "告警收敛机制" --module-info "## 概述…" --tags "告警,收敛"
ki sync-relation --scope my-proj --group "wiki/docs" --relation "草稿" --module-info "…" --no-vector
```

### 5.2 `executeBulkSyncRelation(params)`

- **用途**：批量关系写入。**一次 embedding + 一次 worker upsert** 取代 N 次独立调用（解决 MCP 并发写入慢）。
- **参数**：`{ scope?: string; items: BulkSyncItem[]; vector?: boolean }`；`BulkSyncItem` = `{ group; relation; module_info; tags? }`。
- **返回**：`BulkSyncRelationResult` = `{ ok: true; scope; total; succeeded; failed; skipped; results: BulkSyncResultItem[]; vectorStored: boolean; hints?: string[] } | { ok: false; error }`。
- **行为语义**：
  - 单条 `BulkSyncResultItem` 含 `{ group; relation; evicted; vectorStored?; vectorReason?; wikiSynced?; wikiFile?; wikiReason?; contentTags?; skipped?; skipReason? }`。
  - 逐条校验失败（缺参数 / 空内容 / relation 非法字符）→ `skipped: true` + `skipReason`，**不中断整批**。
  - 同批出现相同 `(group, relation)` → 后一条覆盖前一条；前一条标记 `vectorStored: false` + `vectorReason`（内容向量由后续条目覆盖写入），且不计入"失败"。
  - 顶层 `vectorStored` 为 `true` 的条件：排除 skipped 与去重覆盖条目后，**所有条目都完全成功**（无 `vectorReason`）。任一部分失败即为 `false`。
  - `contentTags` 向量化时为 `['ki-search', ...自定义 tags]`；非向量化时为 `[]`。
- **异常**：不抛异常。向量服务不可用时不阻塞 KB 层，逐条标记 `vectorStored: false` + `vectorReason`。
- **约束**：`items` 空数组直接返回 `{ ok: false, error: 'items 不能为空' }`。

```ts
import { executeBulkSyncRelation } from './sync-relation.js';
const r = await executeBulkSyncRelation({
  scope: 'my-proj',
  items: [
    { group: 'wiki/docs', relation: '告警收敛机制', module_info: '## 概述…', tags: '告警' },
    { group: 'wiki/docs', relation: '降噪策略', module_info: '## 概述…' },
  ],
});
if (r.ok) console.log(`${r.succeeded}/${r.total} 成功，向量全写入=${r.vectorStored}`);
```

### 5.3 `parseContentTags(tags?)`

- **用途**：逗号分隔标签串解析（小写化、去重、过滤保留字 `ki-search` / `ki-relation` / `ki-path`）。
- **返回**：`string[]`。**契约来源**：定义于 `src/lib/constants.ts`，`sync-relation.ts` 保留 re-export 供既有调用方引用。

## 6. Group 查询（`src/query-group.ts`）

### 6.1 `executeQueryGroup(params)`

- **用途**：查询 Group 树 / Relations，输出**格式化文本**（词云 + 冷热分区 + 统计）。
- **参数** `QueryGroupParams`：`scope: string`、`groupsParam?: string`（逗号分隔路径列表）、`hotCount: number`、`depth: number`、`modes: string[]`、`autoFallback?: boolean`（默认 `true`）。
- **返回**：`QueryGroupResult` = `{ ok: true; scope: string; output: string } | { ok: false; error: string }`。
- **行为语义**：
  - **返回的是已渲染好的纯文本 `output`**，不是结构化对象——需要结构化数据时须改用 `relations-cache.json` 直读或 `get-module-info`。
  - `--mode` 逗号分隔，有效值 `hot | warm | cold | emerging | full`；空值或非法值 → `{ ok: false, error }`。
  - 传 `groupsParam` → 逐个解析路径后展示该 Group 的 Relations（按分区截断到 `hotCount`）；`full` 模式额外递归展示子 Group（各分区上限 50 条，超出提示缩小范围）。
  - 不传 `groupsParam` → 按分区展示热门索引 Top `hotCount`，`full` 模式追加完整索引树（受 `depth` 限制）与统计信息。
  - `autoFallback: true` 时，路径未命中会追加一次通用语义搜索结果（tag `ki-path`，top 5）作为兜底提示。
- **异常**：不抛异常。
- **约束**：`depth` 有效区间 1–10（CLI 侧越界会告警并回退/截断为 4 或 10）；`hotCount` 非正整数回退为 5。

```ts
import { executeQueryGroup } from './query-group.js';
const r = await executeQueryGroup({ scope: 'my-proj', hotCount: 10, depth: 4, modes: ['hot', 'emerging'] });
if (r.ok) console.log(r.output);
```

```bash
ki query-group --scope my-proj --mode hot,emerging --hot-count 10
ki query-group --scope my-proj --groups "wiki/docs" --mode full
```

## 7. Group 树管理（`src/manage-index.ts`）

### 7.1 `executeManageCreate(params)`

- **用途**：在 Group 树中创建节点。
- **参数** `ManageCreateParams`：`scope: string`、`name: string`（不能含 `/`）、`parent?: string`。
- **返回**：`{ ok: true; scope; path; hint? } | { ok: false; error }`。
- **行为语义**：`parent` 路径不存在时尝试 `resolveGroupPath` 补全（**不传 scope 参数，不启用向量兜底**）；补全成功按补全后路径创建并透出 `hint`。同名节点已存在 → 拒绝。
- **约束**：`scope` 为空直接返回错误。

```ts
import { executeManageCreate } from './manage-index.js';
const r = await executeManageCreate({ scope: 'my-proj', name: '网络治理', parent: 'BK-Monitor-Wiki' });
```

### 7.2 `executeListScopes()`

- **用途**：列出全部 scope（磁盘已初始化 ∪ 配置已注册，取并集）。
- **返回**：`{ ok: true; scopes: Array<{ scope; topGroups: string[]; registered: boolean; initialized: boolean }>; total: number }`。
- **行为语义**：`registered` = 是否在 `config.scopes` 注册；`initialized` = 磁盘上是否有 `relations-cache.json`。已注册但未初始化的 scope 也会列出。
- **约束**：同步函数，无入参。

```ts
import { executeListScopes } from './manage-index.js';
const { scopes, total } = executeListScopes();
```

### 7.3 `executeManageDeleteEmpty(params)`

- **用途**：删除**空节点**（无子节点、无 relation、无本地 KB 内容）。MCP 侧唯一开放的删除能力。
- **参数** `ManageDeleteEmptyParams`：`scope: string`、`name: string`、`parent?: string`。
- **返回**：`{ ok: true; scope; path; hint? } | { ok: false; error; children?: string[]; hint? }`。
- **行为语义**：
  - 有子节点 → 拒绝并回 `children` 列表 + 引导 CLI 级联命令。
  - 本节点及子路径下存在 relation → 拒绝并提示 relation 条数。
  - local KB 仍有条目 → 拒绝（只剩 `version`/`updatedAt` 元字段的空壳不阻断，会顺带清理）。
  - 删除后顺带清理 relations-cache 中无 relation 的空壳 key 与 local KB 空文件。
- **约束**：**非破坏性**——不触发级联删除；级联请用 CLI `ki manage-index --action delete --force` 或 `ki delete-relation -g <group>`。

```ts
import { executeManageDeleteEmpty } from './manage-index.js';
const r = await executeManageDeleteEmpty({ scope: 'my-proj', name: '网络治理', parent: 'BK-Monitor-Wiki' });
if (!r.ok) console.error(r.error, r.children);
```

### 7.4 CLI 级联删除：`ki manage-index --action delete --name <n> [--parent <p>] --force`

- **行为语义**：非空节点需 `--force`；删除树节点后 **级联清理** relations-cache 前缀匹配的键、local KB `index.json`、向量（`memoryId` 聚合一次 `vectorDelete`），**不清理 wiki 文件**。
- **返回**：`{ ok: true; scope?; path; hint?; cascade: { cacheGroupsRemoved; localKbFilesRemoved; memDeleted; memSkipped; errors? } }`。
- **约束**：`--force` 是删除非空节点的唯一开关（MCP 无对应能力）。

```bash
ki manage-index --scope my-proj --action delete --name "网络治理" --parent "BK-Monitor-Wiki" --force
```

## 8. 模块信息查询（`src/get-module-info.ts`）

### 8.1 `executeGetModuleInfo(params)`

- **用途**：读取指定 Group/Relation 的本地 KB 原文，并顺带记一次使用（更新评分）。
- **参数** `GetModuleInfoParams`：`scope: string`、`group: string`、`relation: string`（`id` 或 `text` 均可）。
- **返回**：`GetModuleInfoResult` = `{ ok: true; scope; content: string; hint? } | { ok: false; error; hint? }`。
- **行为语义**：
  - Group 走 `resolveGroupPath`（**传 scope，启用向量兜底**）；未命中 → 失败 + 提示可用路径。
  - Relation 先按 `id` 或 `text` 精确匹配；未命中再走 `searchPath(relation, 'ki-relation', scope)` 语义兜底，命中则透出"近似匹配"提示并采用该条目。
  - 读取成功会执行 `recordUse` + `calculateScore` 并回写 relations-cache（**有副作用：会改评分**）。
- **异常**：不抛异常。
- **约束**：路径存在但 relations-cache 无数据、或 local KB 缺失/无该条目，均返回失败并给出修复指引。

```ts
import { executeGetModuleInfo } from './get-module-info.js';
const r = await executeGetModuleInfo({ scope: 'my-proj', group: 'wiki/docs', relation: '告警收敛机制' });
if (r.ok) console.log(r.content);
```

```bash
ki get-module-info --scope my-proj --group "wiki/docs" --relation "告警收敛机制"
```

## 9. 关系与目录删除（`src/delete-relation.ts`）

### 9.1 `executeDeleteRelation(params)`

- **用途**：删除单条 Relation 及其四层关联数据。
- **参数** `DeleteRelationParams`：`scope?: string`、`group: string`、`relation: string`。
- **返回**：`{ ok: true; scope; result: DeleteResult } | { ok: false; error }`；`DeleteResult` = `{ relation; group; deleted; cacheRemoved; kbRemoved; wikiRemoved; memRemoved; memMethod: 'memoryId' | 'search' | 'skip' | 'none'; memMemoryId?; reason? }`。
- **行为语义**：
  - 删除顺序：relations-cache → local KB → wiki 文件（**移入回收站，非物理删除**）→ 向量。
  - `deleted` 等价于 `cacheRemoved`；cache 已清但 wiki/向量残留的情况仍会继续清理后两层。
  - 向量删除优先按 `memoryIds`（多 tag 内容向量全部清理），退化为 `memoryId`，两者都无则走 `vectorSearch` 严格匹配兜底（relation 名称须作为标题前缀出现）；`memMethod` 标明实际采用的路径。
  - 向量服务不可用 → `memMethod: 'skip'`，其余各层照常删除。
- **约束**：不删除 group-index 的树节点（Group 可能含其他 Relation）。

```ts
import { executeDeleteRelation } from './delete-relation.js';
const r = await executeDeleteRelation({ scope: 'my-proj', group: 'wiki/docs', relation: '旧接口说明' });
if (r.ok) console.log(r.result.memMethod, r.result.wikiRemoved);
```

### 9.2 `executeDeleteGroup(params)`

- **用途**：**目录级删除**——删除整个 Group（含全部子 Group）的数据与树节点。
- **参数** `DeleteGroupParams`：`scope?: string`、`group: string`。
- **返回**：`{ ok: true; scope; result: DeleteGroupResult } | { ok: false; error }`；`DeleteGroupResult` = `{ group; deleted; relationCount; wikiMoved; nodeRemoved; vectorRemoved; reason? }`。
- **行为语义**：
  - 级联范围 = relations-cache 中 `key === group` 或 `key.startsWith(group + '/')` 的**平铺完整路径键**（含全部子 Group）。
  - 清理顺序：向量（聚合全部 `memoryIds` 一次删除）→ relations-cache → local KB（递归删 `kb/<scope>/<group>/` 子树）→ wiki 目录移入回收站 → group-index 树节点（叶子节点连带清理变空的父节点）。
  - `vectorRemoved: false` 表示存在残留孤儿向量（**显式反馈，避免"删除后仍能搜到"的静默不一致**）；`NOT_FOUND` 视为已清理不误报；无向量可删时为 `true`。
- **异常**：不抛异常。
- **约束**：解析出的 group 路径为空串时**拒绝执行**（防递归删到整个 scope 数据目录）。

```ts
import { executeDeleteGroup } from './delete-relation.js';
const r = await executeDeleteGroup({ scope: 'my-proj', group: 'wiki/docs' });
if (r.ok && !r.result.vectorRemoved) console.warn('向量有残留：', r.result.reason);
```

```bash
ki delete-relation --scope my-proj --group "wiki/docs"          # 目录级（省略 --relation）
ki delete-relation --scope my-proj --group "wiki/docs" --relation "旧接口说明"   # 文档级
```

### 9.3 `executeBatchDelete(scope, items)`

- **用途**：批量删除（串行逐条调用 `executeDeleteRelation`）。
- **参数**：`scope: string | undefined`、`items: Array<{ group; relation }>`。
- **返回**：`{ ok: true; scope?; results: DeleteResult[]; total; failed }`。
- **约束**：**无目录级批量**——`items` 每项都必须带 `relation`。

## 10. 已知约束汇总

- **relation 名禁用 `/`、`\`、`..`**（直接作为 wiki 文件名）；非法时在写入任何数据前拒绝，避免"cache/向量已写、wiki 静默跳过"的半成品。
- **`recordUse` 5 分钟防刷 + `useCount` 上限 10**；`recordUse` 返回新对象，score 需另行重算。
- **向量兜底阈值默认 0**，质量依赖调用方存在性二次校验；向量服务不可用时 `searchPath` 返回 `null`（静默降级）。
- **MCP 删除能力受限**：`ki_manage_index_delete` 仅限空节点；级联删除只能走 CLI（`manage-index --force` 或 `delete-relation -g <group>`）。
- **删除不物理删文件**：wiki 文件与目录统一移入 `{sourceDir}/.ki/trash/`（保留 group 完整结构，重名追加时间戳）。
- **非向量化模式（`vector: false` / `--no-vector`）不产生 memoryId**，内容无法被 `ki search` 召回。
- **`wiki-backfill` 缺省幂等**（跳过已存在文件），`--force` 才覆盖写；`wikiSync.enabled: false` 会同时禁用单条写回与补齐。
- **Group 路径分隔符仅 `/`**；rootName 概念已移除，group 即完整相对路径。
