# C2-使用流程：关系与索引管理专家

> 每条流程含：业务目标 / 调用顺序 / 事务边界 / 预期结果 / 真实代码示例。
> CLI 示例可直接执行；TS 示例为使用方代码，API 签名真实。

## 流程 1：关系写入（单条，四层联动）

**业务目标**：AI 识别到一个关系后写入 kisearch，并可选写回外部 Wiki。

**调用顺序**：
1. `executeSyncRelation({ scope, group, relation, moduleInfo, tags? })`

**事务边界**：四层写入（relations-cache + local KB + 向量 + Wiki）。向量与 Wiki 失败均不阻断——分别以 `vectorStored` / `vectorReason`、`wikiSynced` / `wikiReason` 透出。relation 非法字符在写入任何数据前拒绝（不产生半成品）。

**预期结果**：`{ ok, scope, relation, evicted, vectorStored, contentTags, wikiSynced, wikiFile? }`；Group 路径自动补全时附 `hint`。

**错误处理**：参数缺失/空白 → `{ ok: false, error }`；relation 含非法字符 → 拒绝；relations-cache 不存在 → 拒绝（需先初始化 scope）。

```bash
ki sync-relation --scope my-proj --group "wiki/docs" \
  --relation "告警收敛机制" --module-info "## 概述\n告警收敛通过聚合相似告警降低噪声。" \
  --tags "告警,收敛"
```

```ts
import { executeSyncRelation } from './sync-relation.js';
const r = await executeSyncRelation({
  scope: 'my-proj',
  group: 'wiki/docs',
  relation: '告警收敛机制',
  moduleInfo: '## 概述\n告警收敛通过聚合相似告警降低噪声。',
  tags: '告警,收敛',
});
if (!r.ok) throw new Error(r.error);
if (r.vectorStored === false) console.warn('向量未写入：', r.vectorReason);
```

## 流程 2：批量关系写入（推荐用于多条目）

**业务目标**：一次写入多条关系，避免 N 次 embedding 往返。

**调用顺序**：
1. `executeBulkSyncRelation({ scope, items, vector? })`

**事务边界**：先在内存中逐条改 cache 并收集向量 entries，再一次批量写入向量，最后一次落盘 cache + 各自 wiki 写回。单条失败只标记 `skipped`，不中断整批。

**预期结果**：`{ ok, total, succeeded, failed, skipped, results, vectorStored, hints? }`。

**错误处理**：`items` 空数组 → `{ ok: false, error: 'items 不能为空' }`；同批重复 `(group, relation)` 后一条覆盖前一条（前一条 `vectorStored: false` + `vectorReason`，不计失败）。

```bash
# batch.json 支持 {"items":[...]} 或裸数组 [...]
ki sync-relation --scope my-proj --input ./batch.json
```

```ts
import { executeBulkSyncRelation } from './sync-relation.js';
const r = await executeBulkSyncRelation({
  scope: 'my-proj',
  items: [
    { group: 'wiki/docs', relation: '告警收敛机制', module_info: '## 概述…', tags: '告警' },
    { group: 'wiki/docs', relation: '降噪策略',     module_info: '## 概述…' },
  ],
});
if (r.ok) console.log(`${r.succeeded}/${r.total}，向量全写入=${r.vectorStored}`);
```

## 流程 3：关系查询与删除

**业务目标**：查看某 Group 的关系分区，再删除过时关系。

**调用顺序**：
1. `executeQueryGroup({ scope, groupsParam, modes, hotCount, depth })`（看分区）
2. `executeDeleteRelation({ scope, group, relation })`（删单条）

**事务边界**：query 只读（不写盘）；delete 四层联动，wiki 文件**移入回收站**而非物理删除。向量删除优先 `memoryIds` → `memoryId` → `vectorSearch` 严格匹配兜底。

**预期结果**：query 返回纯文本 `output`；delete 返回 `DeleteResult`（`cacheRemoved` / `kbRemoved` / `wikiRemoved` / `memRemoved` / `memMethod`）。

```bash
ki query-group --scope my-proj --groups "wiki/docs" --mode hot,warm --hot-count 10
ki delete-relation --scope my-proj --group "wiki/docs" --relation "旧接口说明"
```

```ts
import { executeDeleteRelation } from './delete-relation.js';
const r = await executeDeleteRelation({ scope: 'my-proj', group: 'wiki/docs', relation: '旧接口说明' });
if (r.ok && !r.result.memRemoved) console.warn('向量未清理：', r.result.reason);
```

## 流程 4：Group 树管理（创建 → 级联删除）

**业务目标**：建立 Group 层级；清理时连数据一起删。

**调用顺序**：
1. `executeManageCreate({ scope, name, parent })` 建节点
2. 清理时二选一：
   - 树节点级联：`ki manage-index --action delete --name <n> --parent <p> --force`
   - Group 数据级联：`ki delete-relation -g <group>`（省略 `--relation`，走 `executeDeleteGroup`）
3. 只需删空节点时：`executeManageDeleteEmpty({ scope, name, parent })`（MCP 可用）

**事务边界**：
- `manage-index --force`：删树节点 + 级联清 cache/local KB/向量，**不动 wiki 文件**。
- `delete-relation -g <group>`：清向量 + cache + local KB 子树 + wiki 目录移入回收站 + 树节点（**更彻底，推荐**）。
- `executeManageDeleteEmpty`：非破坏性，仅限空节点。

**预期结果**：前者返回 `cascade` 计数；后者返回 `DeleteGroupResult`（`relationCount` / `wikiMoved` / `nodeRemoved` / `vectorRemoved`）。

```bash
ki manage-index --scope my-proj --action create --name "网络治理" --parent "BK-Monitor-Wiki"
ki delete-relation --scope my-proj --group "BK-Monitor-Wiki/网络治理"
```

## 流程 5：模块信息读取

**业务目标**：读取某个 Group/Relation 的本地 KB 原文。

**调用顺序**：
1. `executeGetModuleInfo({ scope, group, relation })`

**事务边界**：**非纯读**——成功读取会执行 `recordUse` + `calculateScore` 并回写 relations-cache（有评分副作用，受 5 分钟防刷限制）。

**预期结果**：`{ ok, scope, content }`；Group 或 Relation 走语义兜底命中时附 `hint`。

```bash
ki get-module-info --scope my-proj --group "wiki/docs" --relation "告警收敛机制"
```

## 流程 6：Wiki 双向同步配置与历史补齐

**业务目标**：让关系写入自动落盘到外部 Wiki，并补齐开启前的历史关系。

**调用顺序**：
1. 配置写回目录（二选一）：
   - 导入写入 source 块：`ki scan-kb import --source <dir> --scope <s>`（source.dir 自动生效）
   - 配置文件：`~/.ki/config.yaml` 的 `scopes.<scope>.wikiSync: { enabled: true, sourceDir }`
2. 首次开启后补齐历史：`ki wiki-backfill <scope>`
3. 后续新增关系由 `sync-relation` 自动写回（目录为空时会触发 autoBackfill）

**事务边界**：写回失败不抛异常、不阻断关系写入（返回 `reason`）；backfill 缺省幂等（跳过已存在文件）。

**预期结果**：`{ ok, targetDir, stats: { total, written, skipped, empty, existed } }`。

**配置校验**（`ki doctor`）：`wikiSync` 仅接受 `enabled`（boolean）/ `sourceDir`（string）/ `autoBackfill`（boolean），未知字段 fail-loud；scope 级 `sourceDir` 已废弃（被忽略，仅告警）。

```yaml
# ~/.ki/config.yaml
scopes:
  my-proj:
    wikiSync:
      enabled: true
      sourceDir: /repo/src/docs
      autoBackfill: true   # 目标目录为空时自动补齐历史（缺省 true）
```

```bash
ki wiki-backfill my-proj            # 只补缺（推荐，不产生 git 脏 diff）
ki wiki-backfill my-proj --force    # 全量覆盖写
```
