# C2-使用流程：存储与配置基础专家

## 流程 1：备份 → 还原（数据保护）

**业务目标**：对 scope 数据做快照备份，灾难后从快照还原。

**调用顺序**：
1. `ki backup <scope>`（或调用 `lib/backup.ts` 的 `autoBackup` 在导入后自动备份）
2. 需要还原时：`ki restore <scope>`（列可用备份）→ `ki restore <scope> --from-snapshot --yes`

**事务边界**：`--from-snapshot` 为破坏性覆盖（覆盖整个 scope 数据目录），需显式 `--yes` 确认；还原时会自动先打一份安全网快照到受管 `backupDir`，并输出「将被覆盖的数据规模」总览。

**预期结果**：`backup` 输出快照文件路径；`restore --from-snapshot` 还原后 scope 数据与快照一致；加 `--rebuild-vector` 时再经 `rebuildScopeVectors` 重建向量（可配 `--group` 只重建子树）。

**错误处理**：tar 不可用 / 目录不可写 / 磁盘空间不足时输出明确错误（PreflightError / 自带提示）；备份失败不阻断导入（仅 stderr 警告）；未加 `--yes` 时以 `CONFIRMATION_REQUIRED` 退出码 1 退出（不交互等待）。

**真实代码示例**：
```bash
# 1. 备份
ki backup my-proj

# 2. 列出可用备份
ki restore my-proj --list

# 3. 从最新快照还原（破坏性，需确认）+ 还原后重建向量
ki restore my-proj --from-snapshot --rebuild-vector --yes

# 3'. 只重建某个 Group 子树的向量（不清空其他向量）
ki restore my-proj --rebuild-vector --group 监控/告警中心 --yes
```

## 流程 2：配置初始化 → 诊断（首次使用）

**业务目标**：初始化配置并验证环境可用（含字段级校验）。

**调用顺序**：
1. `ki config init` 生成 `~/.ki/config.yaml`（同时创建 dataDir / backupDir / vectorDir）
2. 手工编辑配置（填 `embedding.apiKey`，按需调 dataDir / scopes）
3. `ki doctor` 验证配置字段 / 目录可写 / apiKey / embedding 连通性与维度 / zvec collection

**事务边界**：均为只读（init 写配置文件一次，doctor 全程只读）。

**预期结果**：doctor 输出 `✅/⚠️/❌` 报告；有 ❌ 时退出码 1（可作 CI gate）。`ki mcp` 启动预检复用同一逻辑，存在 ❌ 拒绝启动。

**错误处理**：字段名拼错 / 类型错 / 取值非法在配置加载阶段即 fail-loud（`CONFIG_FIELD_INVALID`，逐项列出字段路径，拼写类附相近字段建议）；废弃字段与空值仅走「配置字段」告警项，不阻断；embedding 密钥缺失 / 维度不匹配会明确报失败项；`apiKey` 缺失不做隐式回退。

**真实代码示例**：
```bash
ki config init
ki doctor
```

```yaml
# ~/.ki/config.yaml（合法写法示例）
dataDir: $HOME/.ki/kb
backupDir: $HOME/.ki/backup
vectorDir: $HOME/.ki/vector
embedding:
  provider: siliconflow
  baseURL: https://api.siliconflow.cn/v1
  model: Qwen/Qwen3-Embedding-8B
  dimension: 4096
  apiKey: ${SILICONFLOW_API_KEY}
scopeMode: default
scopes:
  default: {}          # 留空必须写 {}，裸写 `default:` 会被解析为 null 而忽略
```

## 流程 3：导出 KB 为 Wiki（数据交付）

**业务目标**：将 scope 的结构化知识导出为 Markdown 目录。

**调用顺序**：
1. `ki export <scope> --output <dir>`（可选 `--group <path>` 只导出子树，`--yes` 跳过覆盖确认）

**事务边界**：只读数据源（group-index + relations-cache + local KB），写目标目录前做可写性预检。

**预期结果**：目标目录生成按 Group 路径组织的 Markdown 文件，带 YAML frontmatter（`groupPath/relation/exportedAt`）；`--group` 时该子树提为顶层目录。

**错误处理**：目标目录不可写抛 `DIR_NOT_WRITABLE`；relations-cache.json 不存在时提示先执行 import。

**真实代码示例**：
```bash
# 全量导出
ki export my-proj --output ./wiki-out

# 只导出某个 Group 子树
ki export my-proj --output ./wiki-out --group 监控/告警中心
```

## 流程 4：scope 生命周期管理（清理 / 摘除）

**业务目标**：查看各 scope 存在于哪些层（KB / 向量 / 配置注册），并安全清理不再需要的 scope。

**调用顺序**：
1. `ki scope list` 查看三层并集与每层存在情况
2. `ki scope clear <name> --yes` 清空数据保留 scope，或 `ki scope delete <name> --yes` 彻底摘除（清向量 + 删 KB 目录 + 移除配置条目）

**事务边界**：`clear` / `delete` 均为破坏性操作，强制 `--yes`；需向量服务可用。`default` scope 不可 delete。

**预期结果**：`list` 返回 `{count, scopes:[{scope, kb, vector, registered, wikiCount}]}`；`delete` 返回 `{deletedVectors, kbRemoved, configRemoved}`；`clear` 返回 `{tags, deletedVectors, kbCleared}`。

**错误处理**：未加 `--yes` 时返回 `requireConfirm:true` + `willDelete` 预览（不交互等待）；**向量服务不可用时 delete/clear 直接拒绝**（"拒绝删除以免两层不一致"，不降级为只删 KB）；`list` 则降级为仅 KB 层（`vectorAvailable:false` + `vectorReason`），不阻塞。

**真实代码示例**：
```bash
ki scope list
ki scope clear my-proj --yes              # 清空 KB 内容，保留目录与配置
ki scope clear my-proj --tags ki-path --yes # 只清向量层 ki-path 标签，不动 KB
ki scope delete old-proj --yes            # 彻底摘除
```
