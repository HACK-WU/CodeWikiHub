# C2-使用流程：知识索引导入专家

## 流程 1：目录导入（首次或全量更新）

**业务目标**：将外部 Markdown Wiki 目录导入 kisearch（自动切分 + 向量化）。

**调用顺序**：
1. `ki scan-kb import --source <dir> --scope <scope> [--group <path>]`
2. 完成后自动备份（autoBackup，失败不阻断）

**事务边界**：导入持 `.import.lock`（同 scope 并发拒绝）；vector 模式下 scope 已有向量先全量清空再重建；成功后清锁与中断标记。

**预期结果**：stdout 输出 `ImportResult`（`stats {total(chunks), vectorized, errors, skipped}`）；relations-cache / local KB / group-index.source 落盘。

**错误处理**：源目录不存在 / 无白名单文件 / 并发导入冲突均 fail-loud（`ok:false` + exit 1）。

**真实代码示例**：
```bash
ki scan-kb import --source /path/to/wiki --scope my-proj --group wiki
```

## 流程 2：增量更新（幂等重导）

**业务目标**：知识库文件变更后更新索引——**直接重跑 import 即可**（无独立增量模式）。

**调用顺序**：
1. 修改源目录中的文件（增/改）
2. 重跑 `ki scan-kb import --source <同一目录> --scope <scope> [--group <同一 group>]`

**事务边界**：同 sourcePath 覆盖更新、新文件导入、同名不同源（sourcePath 不同）跳过；向量层由覆盖前置清理统一重建。

**预期结果**：变更文件的内容与向量更新；未变更文件幂等重导（结果一致）。

**错误处理**：无（幂等）；仅真冲突（不同文件同名 relation）时跳过并在 skipped 反馈。

**真实代码示例**：
```bash
# 首次
ki scan-kb import --source /path/to/wiki --scope my-proj
# 文件变更后：原样重跑（幂等 = 增量）
ki scan-kb import --source /path/to/wiki --scope my-proj
```

## 流程 3：单文件导入

**业务目标**：只导入一个 Markdown 文档到指定 Group。

**调用顺序**：
1. `ki scan-kb import --source <file.md> --scope <scope> --group <path>`

**事务边界**：同流程 1；后缀必须命中白名单（默认 `.md`），未命中报错拒绝。

**预期结果**：文件落 `--group` 指定 Group（缺省落 scope name 根）；`--tags` 可同时打标。

**真实代码示例**：
```bash
ki scan-kb import --source ./meeting-notes.md --scope my-proj --group wiki/会议纪要 --tags "meeting"
```

## 流程 4：HTTP 导入（前端/程序化接入）

**业务目标**：通过 HTTP API 上传并导入文档（Web 导入页链路）。

**调用顺序**：
1. `POST /api/import/upload`：`{scope, files: [{name, content: base64}]}` → 得 `uploadId`
2. `POST /api/import/run`：`{scope, uploadId, group?}` → `202 {jobId}`（异步）
3. 轮询 `GET /api/import/status?jobId=<id>` 直到 `job.state === 'done' | 'failed'`

**事务边界**：run 为异步 job；group 缺省与 CLI 推断语义一致；服务重启后 job 丢失（404，重传即可）。

**预期结果**：`job.result` 为 `ImportResult`（同 CLI 返回结构）。

**真实代码示例**：
```bash
# 1) 上传（content 为 base64）
curl -X POST http://127.0.0.1:7423/api/import/upload \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"scope":"my-proj","files":[{"name":"a.md","content":"IyB0aXRsZQ=="}]}'
# → {"ok":true,"uploadId":"<id>",...}

# 2) 触发导入
curl -X POST http://127.0.0.1:7423/api/import/run \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"scope":"my-proj","uploadId":"<id>","group":"wiki"}'
# → 202 {"ok":true,"jobId":"<jobId>"}

# 3) 轮询
curl "http://127.0.0.1:7423/api/import/status?jobId=<jobId>" -H 'Authorization: Bearer <token>'
# → {"ok":true,"job":{"state":"done","result":{...ImportResult}}}
```

## 流程 5：导入中断后的恢复

**业务目标**：导入被中断（Ctrl-C / kill）后恢复一致状态。

**调用顺序**：
1. 任意向量命令（search / import 等）会自动提示「检测到未完成的导入」
2. 按提示执行 `ki restore <scope> --rebuild-vector`（从已落盘 KB 重建向量）
3. 或直接重新成功执行 import（成功后自动清中断标记）

**事务边界**：中断时 SIGINT/SIGTERM 已同步清导入锁（保留标记）；SIGKILL 残留锁由下次导入 pid 探活自动清理。

**预期结果**：中断标记清除，向量与 KB 恢复一致。

**真实代码示例**：
```bash
ki restore my-proj --rebuild-vector --yes
```

## 流程 6：还原后重建向量

**业务目标**：restore 还原 KB 后重建向量层（向量不随快照还原）；或对子树/标签做局部重建。

**调用顺序**：
1. `ki restore <scope> --from-snapshot --yes`（还原 KB 文件层，内部自动触发全量重建）
2. 局部场景：`ki restore <scope> --rebuild-vector --group <path>`（子树过滤）/ `--tags <tags>`（合并打标）

**事务边界**：全量重建先清空旧向量（幂等可重跑）；局部重建（--group/--tags）不清空 scope。

**预期结果**：三类+tag 向量重建，content docId 回写 relations-cache。

**真实代码示例**：
```bash
ki restore my-proj --from-snapshot --yes                  # 全量
ki restore my-proj --rebuild-vector --group wiki --tags v2 # 局部子树 + 打标
```
