# C2-使用流程：检索与向量客户端专家

> 每条流程含：业务目标 / 调用顺序 / 事务边界 / 预期结果 / 真实代码示例。
> CLI 示例可直接执行；TS 示例为使用方代码，API 签名真实。
> 上次全量核对：2026-08-28（git commit `9841255`）

## 流程 1：语义检索（默认搜全部）

**业务目标**：用自然语言查询知识库，拿到带原文定位的命中结果。

**调用顺序**：
1. `ensureVectorAvailable(scope)`（可选，显式调用可提前拿到不可用原因）
2. `executeSearch({ scope, query, limit?, tags?, includeOriginal? })`

**事务边界**：纯读（不写任何层）。`getRelationMap` 会构建并缓存内存映射（首次 O(N) 读 `relations-cache.json`）。

**预期结果**：`{ ok: true, scope, results: SearchHit[] }`；向量不可用时 `{ ok: false, error, degraded: true }`。

**内部行为**：枚举该 scope 全部 tag → 单次多 tag OR 查询（1 次 embedding）→ 按 tag 分组各取前 `limit` 条 → `TAG_PRIORITY` 排序 → memoryId 反查附加 `group`/`relation` → 多 tag 去重（同 `(group, relation)` 保留 score 最高）。

```bash
ki search "告警收敛机制" --scope myproj --limit 5
ki search "告警收敛" --scope myproj --tags "ki-search,告警"   # 限定 tag，单次查询
```

```ts
import { executeSearch } from './search.js';
const r = await executeSearch({ scope: 'myproj', query: '告警收敛机制', limit: 5 });
if (!r.ok) { console.error(r.error); process.exit(1); }
for (const h of r.results) console.log(h.score, h.tag, h.group, h.relation);
```

## 流程 2：检索 + 原文召回（REQ-09）

**业务目标**：拿到命中结果的文件级原文（未清洗 Markdown），用于直接引用。

**调用顺序**：
1. `executeSearch({ ..., includeOriginal: true })`

**事务边界**：读向量层 + 读 local KB（`kb/{scope}/{group}/index.json`）。**不写**任何层。

**预期结果**：每条命中带 `originalRetrieved`；成功时 `original` 为文件级原文；失败时 `original` 为向量文档 content 兜底并附 `originalHint`。同一文件多 chunk 命中时，后续条删除 `original` 并标 `deduplicated: true`。

**错误处理**：`originalRetrieved: false` 不是失败——看 `originalHint` 决定是补写（`sync-relation`）还是重建（`ki restore <scope> --rebuild-vector`）。

```bash
ki search "告警收敛机制" --scope myproj --original
```

```ts
import { executeSearch } from './search.js';
const r = await executeSearch({ scope: 'myproj', query: '告警收敛机制', includeOriginal: true });
if (r.ok) {
  for (const h of r.results) {
    if (h.originalRetrieved && !h.deduplicated) console.log(h.original);
    else if (!h.originalRetrieved) console.warn(h.originalHint);
  }
}
```

## 流程 3：单条 / 批量向量写入

**业务目标**：把文本写入向量层（幂等 upsert）。

**调用顺序**：
1. `executeStore({ scope, text, tags? })` 或 `executeBulkStore({ scope, inputFile })`

**事务边界**：**只写向量层**——不写 relations-cache / local KB / group-index。此类数据没有原文定位字段，检索时 `group`/`relation` 缺失、原文召回降级为向量文档。

**预期结果**：`{ ok, scope, docId }` 或 `{ ok, scope, total, succeeded, failed, results }`。

**错误处理**：`text` 超 50_000 字符报错；批量输入非 JSON 数组或某项缺 `text` → 整体报错；逐条写入失败只上报不中断。

```bash
ki store "登录流程说明" --scope myproj --tags ki-search
ki bulk_store --scope myproj --input ./vecs.json
```

```ts
import { vectorStore, vectorBulkStore } from './lib/vector-client.js';
const { docId } = await vectorStore({ scope: 'myproj', text: '登录流程说明', tags: 'ki-search' });
const r = await vectorBulkStore({ scope: 'myproj', entries: [{ text: 'a' }, { text: 'b', tags: 'ki-relation' }] });
```

> **勿用 `ki bulk_store` 写知识记忆**——写记忆请用 `ki sync-relation --input`（会同时写四层），否则产生孤儿向量。

## 流程 4：按 docId 管理向量文档

**业务目标**：查看 / 删除向量层文档（管理面）。

**调用顺序**：
1. `executeTagList({ scope })`（先看有哪些 tag）
2. `executeDocList({ scope, tags?, limit?, full? })`（查看候选，content 默认截断 200 字）
3. `executeDocDelete({ scope, ids, yes })`（**先不带 `--yes` 预览**，确认后再带）

**事务边界**：`executeDocDelete` **只删向量层**，不联动 KB。删前自动 `vectorFetchDocs` 取回做 scope 护栏核对。

**预期结果**：
- 无 `--yes` → `{ ok: false, requireConfirm: true, willDelete, notFound, scopeMismatch }`（不删任何东西）
- 带 `--yes` → `{ ok: true, requested, deleted, errors }`

**错误处理**：跨 scope 的 docid 进 `scopeMismatch` 跳过（不报错）；不存在的 id 进 `notFound`。

```bash
ki tag list --scope myproj
ki doc list --scope myproj --tags ki-search --limit 20 --full
ki doc delete <docid> --scope myproj             # 预览，拒绝执行
ki doc delete <docid> --scope myproj --yes       # 确认删除
```

## 流程 5：清空 / 重建某 scope 的向量

**业务目标**：覆盖导入或数据损坏后重建向量。

**调用顺序**：
1. `vectorCountScope({ scope, tags? })`（确认规模）
2. `vectorDeleteScope({ scope, tags? }, onProgress?)`（分批清空）
3. 由知识索引导入链路 `batchVectorize` 重新写入，或 `ki restore <scope> --rebuild-vector`

**事务边界**：纯向量层删除，分批循环（每批 ≤ 10_000），带无进展保护（`res.ok === 0` 时退出防死循环）。

```ts
import { vectorCountScope, vectorDeleteScope } from './lib/vector-client.js';
console.log('当前文档数', await vectorCountScope({ scope: 'myproj' }));
const { deleted } = await vectorDeleteScope({ scope: 'myproj' }, (n) => process.stderr.write(`已清 ${n}\r`));
```

## 流程 6：常驻进程的引擎生命周期（MCP / HTTP 服务）

**业务目标**：让常驻服务与其他 MCP 实例 / CLI 短命令**错开共享**同一个向量库（单进程独占锁）。

**调用顺序**：
1. 服务启动时 `enableIdleClose(idleMs)`（如 3000）
2. 每个向量操作经 `vector*` / `execute*`（内部统一走 `withEngine`，自带在途保护与自愈重试）
3. 服务关闭时 `closeEngine()`

**事务边界**：空闲超时自动释放锁；下次调用惰性 reopen（约 0.7s）。**在途操作（`_inFlightOps > 0`，含 embedding 网络阶段）不会被打断**。

**预期结果**：多实例错开抢锁，撞锁时 `probeWithRetry` 等 2s×3 后仍锁才失败，stderr 输出带来源标注的等待日志。

```ts
import { enableIdleClose, closeEngine, runWithVectorSource } from './lib/vector-client.js';
enableIdleClose(3000);                       // 常驻层：空闲 3s 释放锁
process.on('SIGTERM', async () => { await closeEngine(); process.exit(0); });
// HTTP 入口标注来源，便于定位撞锁端点
runWithVectorSource('/api/search', () => executeSearch({ scope, query }));
```

## 流程 7：排查"搜不到 / 搜不准"

**调用顺序**（诊断链）：
1. `ensureVectorAvailable(scope)` → 是否 `LOCKED` / `CORRUPTED` / `PROBE_ERROR`
2. `executeTagList({ scope })` → 该 scope 下实际有哪些 tag、`truncated` 是否为真
3. `vectorCountScope({ scope })` → 文档数是否为 0
4. `ki doc list --scope <s> --full` → 内容是否写入、tag 是否符合预期
5. 若内容在但召回差 → 降低或去掉 `threshold`（RRF 融合分量级远小于 1，勿用 0.75）
6. 若 `group`/`relation` 缺失 → 数据来源是否为 `ki store`（不写 KB）
7. 若刚升级过 → 检查是否命中 docId scheme 变更（需 re-import / `rebuild-vector`）
