## 1. 执行摘要

1. **需求本质是"把 web AI 对话页的问答能力降维成一次工具调用"**，而不是"再接一个 LLM"。现有 14 个 MCP 工具全是知识库原子操作（检索 / 读写 / 枚举），**没有任何"让 ki 自己回答"的入口**（🟢 `src/lib/mcp-server-factory.ts:37-69`）。
2. **"每次全新对话"是新增语义，不是简化**。现有对话三个生成入口全部强依赖会话文件 `ConversationFile` 与 SSE 流，**代码中不存在无会话 / 一次性问答入口**（🟢 `src/lib/chat/chat-routes.ts:405-420`、`retrieval/tool-loop.ts:82`）。实现上等于新开一条极简链路，绕开会话层。
3. **最贴近的现成模板是压缩摘要**：`summarizeForCompaction()` 正是"无会话、一次性、纯文本返回"的写法（🟢 `src/lib/chat/compaction.ts:67-106`），但它**不带检索**——要不要带检索是本需求第一号待拍板项。
4. **三个必须过的闸门**（不做即缺陷）：① 隐私确认 `kbDisclosureAck`（内部检索 = 知识库内容外发）；② 递归自调（内层工具面若含 `ki_ask` 会无限套娃，且 `maxToolRounds = Infinity` 无防线，🟢 `chat-contract.ts:475`）；③ 只读 Token（会消耗 LLM 额度，登记进只读白名单等于扩大既有安全缺口，🟢 `docs/mcp-http.md:99`）。
5. **最大风险不在技术，在价值**：外部 AI 客户端已能调 `ki_search` 自行检索。若 `ki_ask` 用的是弱模型（截图为 deepseek-flash），可能出现"外部 AI 强推理 + ki 弱合成"叠加后**质量不如外部 AI 自己检索**。此项需一次实测对比才能定 Kano，当前标 **Kano 待定**。

## 3.4 直观视图

### 调用链（目标形态）

```
外部 AI 客户端（CodeBuddy / Claude Code / Cursor）
  │  MCP tools/call  ki_ask{ scope, question }
  ▼
ki MCP server（/mcp 或 stdio→daemon）
  ├─ ① 鉴权：scope 越权 · 只读 Token · 能力点
  ├─ ② 就绪闸门：LLM 已配置 · kbDisclosureAck 已确认
  ▼
一次性问答链路（★新建：不建会话 / 不落盘）
  ├─ 组装：复用 prompt-config 的 system 块 + 单条 user（无历史回放）
  ├─ 内层工具面：只读检索子集（显式排除 ki_ask 自身，防递归）
  ├─ streamChat() 流式生成 → 聚合为整段（MCP 无流式返回）
  └─ 返回：answer + sources[]（+ usage / rounds）
```

### 与现有 web 对话的差异

```
                    web AI 对话（现状）          ki_ask（本需求）
会话落盘            ConversationFile             无
历史             轮次回放 + 证据回放（前 5 轮）   无（每次全新）
传输             SSE 逐字流                    一次性聚合
提示词            首轮快照固化                  每次按当前配置（无快照）
工具面            读写全量（可配）              只读检索子集
```

### 三个候选形态

```
A 纯问答（不检索）
  └─ 1 次 LLM · 3~15s · 成本最低
  └─ 但答案只来自模型参数，与 ki 知识库无关 → 与"就像页面这样"背离

B 无状态 RAG（推荐）
  └─ 内部多轮检索 + 合成 · 10~90s · 成本 = 一次会话
  └─ 答案带来源，可追溯；与页面口径一致 ★

C 检索打包（不调 LLM）
  └─ 2~5s · 零额外 LLM 成本 · 无递归无额度风险
  └─ 返回 top-N 片段给外部 AI 自己合成 → 但它就不是"和 AI 对话"了
```

2. 验证通过后转 **`design-craft`** 出技术设计：重点覆盖 6 处工具登记点、内层工具面白名单、超时档位、能力点、协调器 kind 归属。
3. 若 D1 拍板为 C（检索打包）或 A（纯问答），本报告 §3.1 的 R3 / R4 / R6 需相应调整后重新定稿。

# 9. v2 修订（2026-11-13）：可选续接 + 10 分钟 TTL

> 需求方原话：「每次返回一个会话 ID，如果要接着上次对话，传入会话 ID 就可以了，否则就是新的对话。对话历史有效期十分钟，最后一次对话 10 分以后自动删除。」

## 9.1 结论

**方案可行，推荐采纳**，但建议**分两期落地**（见 9.5）。

比纯无状态更好，因为它一次解决三个原方案解决不了的问题：

- **N1「被当多轮用却无记忆」** → 变成可选能力，追问有明确契约；
- **D6「AI 无法澄清」** → 可先返回「需澄清」再由调用方带 `context_id` 追问；
- **省 token**：追问传 20 字符 ID，而不是把数 KB 上文原样回传。

同时 TTL 只有 10 分钟，把「有状态」的风险压到很小（无跨天脏数据、无长期越权面）。

## 9.2 技术可行性（🟢 代码直读，四个关键发现）

| 发现 | 证据 | 意义 |
|---|---|---|
| **会话列表只认 `c-` 前缀** | `chat-store.ts:127` `CONV_FILE_RE = /^c-[A-Za-z0-9-]+\.json$/`；`:184,454` 均按它过滤 | 短会话用 `ka-` 前缀落**同目录**即天然不进 web 会话列表 —— 不需要新目录、不需要改列表逻辑 |
| 会话锁现成可复用 | `chat-store.ts:70-82` `withConvLock(id)`（链尾回收 key） | 同 ID 并发天然串行，无需新锁 |
| **每次写盘自动打 `updatedAt`** | `writeJson` 统一打戳（`chat-store.ts` 既有约定，见项目踩坑记忆） | **滑动 TTL 零新字段**：直接读 `updatedAt` 判定 |
| 定时清扫有成熟范式 | `mcp-http.ts:670` `sweepTimer` + `timer.unref?.()`；`scope-usage.ts:106-109` | GC 照抄即可，且不阻进程退出 |
| 落盘天然按 scope 分目录 | `chat-store.ts:117-119` `convPath` = `{chatDir}/{scope}/{id}.json` | 跨 scope 传 ID **天然找不到**（路径不匹配），越权面很小 |

**两处必须补的代价**：

1. `assertValidId`（`chat-store.ts:130-134`）强制 `^c-` 前缀 → 新前缀需**单独实现**防路径穿越校验，不能直接喂给现有读函数。
2. `clearConversations`（`:454`）只删 `c-*` → 短会话**不会被「清空会话」联动清理**，只能靠 TTL GC 兜底（要写进验收）。

## 9.3 需求修订

**R1 改写**：`ki_ask` 默认开启**新问答上下文**；传入 `context_id` 则续接该上下文。每次返回新的 `context_id` + 过期时刻。

**新增条目**：

| ID | 优先级 | 需求 | 验收标准 | Kano |
|---|---|---|---|---|
| **R13** | P1 | 可选续接：`context_id` 轮询 + 每次返回（含首轮） | 传 ID 追问能引用前一轮内容；不传则与前一轮完全无关 | 期望 |
| **R14** | P1 | 滑动 TTL 10 分钟（最后一次交互起算）+ 自动清理 | 造过期数据 → 文件被删；10 分钟内反复交互不被删 | 必备 |
| **R15** | P0 | **过期语义显式化**：`context_id` 已过期 / 不存在 → **明确报错**（含「重新提问将开启新上下文」提示），不得静默当新会话 | 用过期 ID 调用得到专用错误码；答案不得基于空历史生成 | 必备 |
| **R16** | P0 | 归属校验：ID 绑定 scope + 调用方身份，跨身份续接拒绝 | 换 Token / 换 scope 用同一 ID → 拒绝 | 必备 |
| **R17** | P1 | 上下文预算：轮次或字符超限时**明确报错**（提示新开），不静默截断 | 造超限会话 → 得到可读错误 | 期望 |

**R11 参数化追加**：`context_id`（可选）、`ttl`（可选，须有上限）。

## 9.4 新增负向需求

| # | 场景 | 期望行为 |
|---|---|---|
| **N9** | 拿过期 / 不存在 / 别人的 `context_id` 续接 | 专用错误码 + 可操作提示；**绝不静默降级为新会话**（降级会让外部 AI 误以为上下文还在，答非所问） |
| **N10** | 同一 `context_id` 并发两次调用 | 或串行排队（有超时）或明确 409；不得两个请求同时改写同一份历史 |
| **N11** | ID 泄露 | 高熵随机（≥128bit）+ 绑定 scope/身份；不可猜、不可跨库复用 |
| **N12** | 10 分钟内无限轮次 → 上下文膨胀 | 轮次/字符上限 + 明确报错，不静默截断历史 |
| **N13** | 系统时间跳变（NTP 校时 / 休眠唤醒） | TTL 判定口径要写清（建议 wall-clock 且容忍单向偏差），避免「刚建就过期」或「永不过期」 |
| **N14** | 进程重启（daemon 重载） | 明确：落盘则 10 分钟内仍可续接；若改内存态必须写清「重启即失效」 |
| **N15** | 客户端长期缓存 ID | 过期错误文案必须能驱动它自我纠正（重问一次） |

## 9.5 分期建议（推荐）

```
第一期（无状态）                   第二期（可选续接）
R1~R7 主链路跑通                   R13~R17 + N9~N15
先验证 D4 客户端超时 / D5 耗时     不影响第一期契约（纯新增可选参数）
/D10 答案质量
  └─ 若第一期就证明「价值不成立」，第二期根本不用做
```

**理由**：续接是**增值功能而非前提**。若客户端超时或答案质量不过关，第一期结论会直接否决整个需求，先做续接等于白做。反之第一期通过后，第二期是纯增量、可独立验证。

## 9.7 影响面增补

| 受影响方 | 类型 | 程度 | 建议处理 |
|---|---|---|---|
| 数据生命周期 | 数据 | 降级 | **10 分钟自动删除 → 排查窗口极短**，故 R9 审计日志升级为 **P0**（必须独立于短会话保留） |
| 「清空会话」功能 | 数据 | 降级 | 不联动删除 `ka-*`（见 9.2），靠 GC 兜底，需在文档写明 |
| 磁盘临时文件 | 性能 | 无感 | 10 分钟窗口内多客户端并发会产生临时文件，GC 周期需与写入量一同评估 |
| 隐私 | 合规 | **改善** | 临时内容自动消失，比长期留痕更安全（正向） |
| 客户端行为 | 外部契约 | 降级 | 外部 AI 若「拿到 ID 就总是传」会把无关问题串成一轮对话 → 文案必须写「仅在追问时传」 |
