## 0. 全局理解声明

- **业务目标**：把「每次手动敲一长串 `ki import` 参数」变成「登记一次 + 一条短命令同步」，并能在页面看到数据源与上次同步结果。
- **系统位置**：
  ```
  本地文档目录（用户维护）
    └─▶ 数据源登记（datasource.json）
          └─▶ ki datasource sync ─▶ handleDirectImport（既有管线）─▶ 库/向量/FTS
                └─▶ 可选 planImportPrune + executeBatchDelete（既有能力）
                      └─▶ 下游消费：wiki 写回(sync_relation) / 页面只读展示 / 任务台账
  ```
- **整体成功判据（后续场景逐个回扣）**：
  1. 登记一次后同步无需再输路径与参数
  2. 同步结果可判定（成功/部分失败/失败/缺失 四态清晰）
  3. **绝不因同步删除把库清空或误删**（系统无回收站，删除不可逆）
  4. 页面只读但不误导（看得见、知道下一步怎么敲）
  5. 与既有 `ki import` / Web 上传导入 / Web prune 三条通道不冲突

## 3. 场景推演详情（节选关键场景）

### S3 日常同步（少量增删改）—— ❌ P3

```
{ki datasource sync --scope monitot}
  ├─ 读 datasource.json ✅
  ├─ 读 group-index 快照（prune 需要库内 sourcePath 集合）✅
  ├─ collectMarkdownFiles 全量扫描（128 篇）✅
  ├─ 导入 128 篇：125 成功 / 3 失败（embedding 超时）✅ 失败可重试
  └─ 算候选 = 库中 sourcePath − 本次扫描 rel
        ├─ 若 scannedRels 取「全量扫描」→ 3 篇失败文件仍在集合内 → 不进候选 ✅
        └─ 若 scannedRels 取「成功导入清单」→ 3 篇失败文件被判"本地已删" → 删除 ❌ ← P3
```

**需求质量验证**

| 维度 | 验证问题 | 结果 | 说明 |
|---|---|---|---|
| 场景完整性 | 失败文件在下一轮同步的命运是否定义？ | ❌ | 需求 §8 只写"扫描 0 文件"，**未锁定"候选必须基于全量扫描"**。既有实现（`import.ts:765-771` 注释）恰好踩过这个坑，但新 CLI 路径可能自行拼装 `scannedRels` |

### S4 大规模删除（git 切分支）—— ⚠️ P2 / P5 / P10

```
{sync --scope default}（源目录从 128 篇变成 60 篇，因为切到另一分支）
  ├─ 覆盖率判定：库中 128 篇的 sourcePath 有 58 篇仍出现在本次 60 篇 → 重合率 0.45 < 0.8
  └─ GATE_COORD → 不产候选 ✅（闸门救命）
       └─ 但页面只显示 failed，用户不知道该改哪里 ⚠️

{sync --scope default --yes}（用户看到 12 篇待删，隔了 10 分钟再执行）
  ├─ 这 10 分钟里源目录又变了（另一个分支被 check out）
  └─ 实际删除 21 篇，与用户确认的 12 篇不一致 ❌ ← P2（无回收站，不可逆）
```

### S7 页面查看 —— ⚠️ P7 / P18 / P21

```
{打开「数据源」页}
  ├─ 列表 2 行（跨 scope）✅
  ├─ 当前正在跑 sync（CLI 起的任务）→ 页面显示 "6 天前同步" + "⚠ 部分失败" ❌ ← P7
  │    用户以为同步没在跑，等不及又敲一遍 → 撞 scope 写锁
  ├─ 顶栏切到 monitot → 页面仍显示 2 行（全站其他页都跟随 scope）⚠️ ← P18
  └─ 远程 token 客户端看到 /Users/me/docs/api 全路径 ⚠️ ← P21
```

### S9 修改配置：改 `--group` —— ❌ P12

```
{ki datasource add --scope monitot --source ~/docs/api --group wiki/新的}
  └─ 下次同步
       ├─ 导入时 resolveImportConflict：**按 sourcePath 全局匹配**（import-conflict.ts:95）
       │     → 命中旧记录（在 wiki/API接口文档 下）→ action=overwrite，relation 取旧 text
       └─ 结果：文档到底留在旧 group 还是落到新 group？
            · 若覆盖旧记录 → 改 group 静默不生效（用户看着配置改了，落点没变）
            · 若按新 group 写 → 旧 group 残留孤儿记录
            需求未定义预期行为 ❌ ← P12（需运行验证实际分支）
```

### S10 取消登记 remove —— ❌ P1

```
{ki datasource remove --scope monitot --yes}
  ├─ 删 datasource.json ✅
  ├─ group-index.json.source.dir 仍指向 ~/docs/api（既有写入未清）⚠️
  └─ 下次演进（R15 迁移逻辑）读取 source.dir → 自动登记回来 ❌ ← P1
       remove 变成"删了又活"，用户无法取消登记
```

### S13 升级迁移 —— ❌ P4

```
{升级后首次打开数据源页}
  └─ R15 从 group-index.json.source 自动登记
       ├─ source 块只有 dir / chunkSize / chunkOverlap（scope.ts:135-141）
       ├─ 原导入参数 --group wiki 无法还原 → group = null（按顶层目录自动）
       └─ 页面显示"落点：自动"，而文档实际在 wiki/ 下 ❌ ← P4
            用户按页面理解去排查，得到错误结论
```

## 5. 推演结论

- **推演覆盖**：5 个角色（含 1 个环境角色）/ 13 个有效场景（S8 取消）
- **问题发现（v4 时点）**：🔴 4 / 🟡 12 / 🟢 5 = 21 项（P5、P13 已关闭）
- **v5 修订后**：🔴 **0** / 🟡 13 / 🟢 5 —— 4 项阻断已全部修复并增量重推通过

| 条件 | 结论 |
|---|---|
| 存在 ≥1 个 🔴 阻断 | **❌ 不通过** |

**必须修复后才能进入 design-craft 的 4 项**

1. **P1** R15 ↔ R10 冲突：迁移与取消登记互斥（否则 remove 功能不成立）
2. **P2** `--yes` 语义：必须收敛为"同一次调用内确认"，否则删除对象与用户确认不一致
3. **P3** 删除候选口径：写死"全量扫描 rel 集合"，否则失败文件会被误删
4. **P4** R15 迁移：`group` 不可还原，须改为提示式或强制 dry-run

**整体回扣全局目标**：4 个 🔴 中 3 个（P1/P2/P3）直接威胁「成功判据 3：绝不误删」，1 个（P4）威胁「判据 2：结果可判定」。即使其余 18 个 🟡/🟢 全不修，功能主线可用；但这 4 项不修，**功能的破坏性会超过它的价值**。

### 下一步建议

1. 修订需求文档（修 P1~P4 + 合并 P5/P6/P13/P17 的措辞），修订后做**增量推演**（只重推 S3/S4/S9/S10/S13 五个场景）。
2. 修完再进 `design-craft`；设计阶段需回答 P12（改 group 的实际行为）—— 建议用 `demo-verify` 或最小实测确认 `resolveImportConflict` 命中旧 sourcePath 后的 group 归属。
3. 本推演为**文档推理**，P12 / P2 的实际后果需运行验证，不作已证结论。

### 8.2 增量推演新发现

```
{ki datasource sync --scope monitot --yes}
  ├─ 扫描 128 篇 → 导入 125 成功 / 3 失败
  └─ 算候选 5 篇（占比 4%，未触发 20% 护栏）→ 直接删除 ✅
        └─ 用户在执行前**看不到这 5 篇是谁** ⚠️ ← P24
             （P2 修复后，"先看清单再确认"的跨调用路径被关闭）
```

| # | 类型 | 角色 | 场景 | 问题 | 影响 | 建议 | 严重度 |
|---|---|---|---|---|---|---|---|
| P24 | 场景完整性 | 1 | S4 | `--yes` 同调用授权后，删除前无法预览；`--dry-run` 的候选与真正执行时可能微差 | 预期：确认前知道删哪几篇 → 实际：只知道"删了 5 篇"（执行后明细见 `lastSync`） | ① 执行后输出必须列出被删的 5 条（group + relation）；② 文档与 `--help` 建议"首次或目录刚变动过时先 `--dry-run`" | 🟡 |
