## 二、替代方案

| 主题 | 备选 | 取舍 |
|---|---|---|
| 调度器与 coordinator | 非排队 `trySubmit` | 能保留 queue/指标，但要改 coordinator 契约；当前 scope 锁 + 预检已能防并发，优先低成本 |
| 定时配置存储 | 独立 `schedule.json` | 彻底避开与同步 `lastSync` 的写冲突（保存不再 409），代价是多一个文件与清理逻辑；若用户频繁在同步中改计划，值得重新评估 |
| 跳过留痕 | 新增 `skipped` 任务状态 | 满足"每次都进"，但改任务页/顶栏/状态机；先确认用户语义 |
| 顶栏即时性 | 空闲轮询 5s / SSE | 5s 成本可控；SSE 能真正"那一刻"，但要新增推送通道 |
| 多标签页冲突 | `baseUpdatedAt` 乐观锁 | 成本低，能防止静默覆盖；适合本项目已有跨标签页问题的背景 |

## 三、认可点

- **scope → clone 锁序**与 `syncDataSource` 内部一致，避免了"先 clone 后 scope"与手动同步的死锁；先锁后建任务，避免锁冲突留下假失败任务。
- **CLONE_BUSY 预锁 + 竞态兜底**把"共享仓库忙"从失败态中摘出，符合 N5。
- **按需定时器**（0 计划无 timer）直接落实用户 D10，避免空转。
- **启动补跑只补一次** + `lastAutoFor` 去重，能覆盖停机、休眠、时钟回拨的重复触发。
- **仅一次完成自动关闭**避免了"已完成仍显示开启"的误导。
- **详情只读、待删除不动**与用户确认一致。

## 四、补充场景

**正向**
1. 开启周期 30 分钟 → 到点执行 → 任务页 `source=scheduler` → 下次时间推进 → 详情只读展示。
2. 指定时间「每天 09:00」从未来某天开始 → 当天 09:00 执行；停机 3 天后启动 → 只补跑一次。
3. 连续 3 次失败 → 页面 `定时⚠` + "仍会尝试" → 第 4 个周期继续。

**负向**
4. 两个 scope 共享托管 clone，定时同时到期 → 全局并发 1 + clone 预锁 → 一个执行、另一个 skip（无失败任务）。
5. 定时运行中用户在页面改计划 → 409；同步结束后可保存。
6. 恢复旧快照 → 计划回到旧值（需 refresh + 用户知情）。
7. 两个标签页同时改计划 → 后写覆盖（Q4，需版本校验或接受）。

**运维**
8. `KI_DISABLE_DATASOURCE_SCHEDULER=1` → 保存成功但不执行；healthz 显示 disabled。
9. 调度锁残留 → PID 已死回收；无法解析 → 不抢占并告警。
10. 1 分钟 × 20 源 → 实际执行受同步耗时限制，大量 overdue/skip；需在页面/文档提示。
