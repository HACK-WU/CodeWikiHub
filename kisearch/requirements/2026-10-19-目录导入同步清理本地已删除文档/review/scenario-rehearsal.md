# 场景推演：目录导入同步清理本地已删除文档（需求文档模式）

> 推演时间：2026-10-19
> 推演对象：需求文档模式（用户明确要求「推演这个需求」）
> 输入文档：`requirement.md`（设计文档已存在，仅用于对照「需求 → 设计」是否漂移，不展开设计点推演）

## 1. 全局理解声明

| 项 | 内容 |
|---|---|
| 业务目标 | 目录导入后，把「库里还留着、但这次上传的目录里已经没有」的文档清掉，避免知识库与本地文档脱节 |
| 系统位置 | 浏览器读目录 → `/import/upload` 暂存 → `/import/run` 幂等导入 → [本次新增] 候选清单 → 用户确认 → 批量删除 |
| 整体成功判据 | ① 只删「本地真的没有」的，本地还在的一篇都不能误删；② 用户看到的就是将要删的；③ 误删可发现、可恢复；④ 不影响既有导入链路 |

| 2 | CLI 用户 | 用户 | 已登录 | `ki import` / `ki delete-relation` 手工清理 | 需求 §6 |

## 4. 场景推演详情

### S1 整目录重传（Happy Path）

```text
{用户选目录 wiki-2026/，勾选『导入后提示清理』}
  ▼
{导入 128 篇，5 篇内容未变} ✅
  ▼
{计算候选：库 130 篇 − 本次 128 篇 = 2 篇} ✅
  ├─{闸门 A：128/128 = 100%} ✅
  ├─{闸门 B：2/130 = 1.5%} ✅
  └─{token 生成、结果卡渲染} ✅
  ▼
{用户确认 → 删除 2 篇 → 回收站} ✅
```

**结论：通过**。删除对象 = 清单对象，数据守恒成立。

### S2 选错目录 / 层级变化

```text
{上次传 wiki-2026/，这次误传 wiki-2026/部署/}
  ▼
{本次 rel 全部变成 a.md（少一层），库里是 部署/a.md}
  ├─{闸门 A：交集 0 → 0%} ❌ → 自动关闭 ✅
  └─{结果卡提示「可能选错目录层级」} ✅
```

**结论：通过**。保护措施有效，符合全局判据 ①。

### S3 上传不完整（核心阻断项）

```text
{用户选目录 128 篇，其中 3 篇因网络中断/单文件超限被 /api/import/upload 拒绝}
  ▼
{暂存目录只有 125 篇 → 服务端扫描 125 篇}
  ▼
{导入成功 125 篇（导入本身不报错，errors 在 session 里）} ⚠️
  ▼
{候选 = 库 130 − 本次 125 = 5 篇}
  ├─ 其中 2 篇确实本地已删 ✅
  └─ 另 3 篇本地仍在硬盘上，只是没传上去 ❌ ← 问题
  ▼
{闸门 A = 125/128 = 97.7% ✅、闸门 B = 5/130 = 3.8% ✅ → 全部放行}
  ▼
{用户看到「本次目录里没有」→ 全选删除 → 本地还在的 3 篇文档被删} ❌
```

- **数据守恒**：本次 rel 集合发生**静默减少**（上传失败的文件被无声地从"本次有"里剔除），候选计算无法区分"本地没有"与"没传上来" ⇒ 破坏守恒。
- **效果等价性**：预期「只删本地没有的」→ 实际「连没传上来的也删」⇒ 影响重大且不可逆（需重传恢复）。
- 需求 N1 只挡住「选择文件」模式，**没有挡住「目录模式但上传不完整」**。
- 保护闸门挡不住：3/128 的缺失对闸门 A/B 几乎无感（保护措施防"整体选错"，不防"少量缺失"）。

### S4 未选 Group + 只传子集

```text
{未选 Group → 作用域 = 全 scope；本次只传了 部署/}
  ▼
{架构/ 组全部进候选，但标记为「未触及 group」} ✅
  ▼
{默认不勾选，用户需展开手动勾} ✅
```

**结论：通过**（需求 R4.6 与设计一致）。

### S5 删除中途中断 / 重复点击

```text
{用户点「删除所选 50 篇」→ 第 20 篇时断网/关页面}
  ▼
{服务端已删 20 篇，前端无回执} ❌ 无定义
  ▼
{用户回来再点删除 → token 已变 → 409} ⚠️ 用户看到"失败"
```

需求 N7 只定义「逐条回显失败」，未定义"前端拿不到回执"的中间态；N6 定义了 token 失效 → 409，但未定义"重复点击"的期望语义。

### S6 隔天回来再点删除

```text
{导入完成 25 小时后点删除}
  ▼
{uploadId 对应暂存目录已被清理（空闲 24h）} ❌ 需求无定义
  ▼
{按需求字面实现 → 无法重算 → 只能报错}
```

需求全文未提「候选清单的有效期」与过期兜底。

### S7 文件移动目录

```text
{本地 a.md 移到 sub/a.md，其他不变}
  ▼
{旧文档 a.md 进候选 → 删；新文档 sub/a.md 新建} ✅ 语义正确
  ⚠️ 需求 N8 只写了"改名（a.md → b.md）"，未覆盖"移动目录"
```

## 5. 问题汇总

| # | 类型 | 角色 | 场景 | 问题描述 | 功能影响（预期 → 实际） | 建议 | 严重度 |
|---|---|---|---|---|------|------|:---:|
| 1 | 遗漏场景 | 上传用户 | S3 | **上传不完整时未把失败文件视为"本次有"**；需求仅挡了 `pickMode=files` | 预期：只删本地真的没有的 → 实际：把"没传上来"的文件也判为已删除并删掉，本地文件仍在但知识库文档丢失 | 补需求条目：上传失败批次/文件时禁止清理，或把失败 rel 作为 `preserveRels` 与扫描集合并集 | 🔴 |
| 2 | 需求缺口 | 上传用户 | S6 | 候选清单**没有有效期定义**，暂存目录 24h 后清理 | 预期：随时可回来点删除 → 实际：过期后无法重算，删除直接失败 | 补"候选有效期 24h"与过期提示 | 🟡 |
| 3 | 边界未定义 | 上传用户 | S5 | 删除中途中断/重复点击的期望终态未定义 | 预期：能看到删到哪、能续删 → 实际：无回执，重复点击报 token 失效 | 补：中断后以库为准重算；重复点击表现为"无剩余候选" | 🟡 |
| 4 | 需求一致性 | 上传用户 | S1 | 闸门 B 分母：需求写「库中文档总数」，设计改为「可判定文档数（有 sourcePath）」 | 预期：同一比例含义一致 → 实际：无 sourcePath 文档多时需求口径**稀释比例**、放宽保护 | 需求 §3.4 同步为 `judicable` | 🟡 |
| 5 | 术语一致性 | 实现者 | 全部 | 需求 R2 用 `pruneCandidates`，设计定名 `ImportResult.prune` | 预期：字段名唯一 → 实际：实现者按需求找不到字段 | 需求统一为 `prune` | 🟡 |
| 6 | 需求缺口 | 实现者 | 全部 | 需求 R3 只写"服务端重算 + token"，**未定义重算所需文件集合从哪来** | 预期：服务端拿到与 run 同源的扫描集合 → 实际：若由前端拼清单，token 恒失配、删除永远 409 | 需求 §3.3 补：服务端通过 `uploadId` 重扫同一暂存目录 | 🟡 |
| 7 | 角色对齐 | 共用 scope 使用者 | S8 | 「同一 scope 被多人/多来源写入」的角色未定义，仅作为"已接受风险" | 预期：A 的操作不影响 B → 实际：A 上传 A 目录即可删掉 B 来源的同组文档 | 补角色说明与使用边界（默认单机单用户） | 🟡 |
| 8 | 边界覆盖 | 上传用户 | S7 | N8 只覆盖"改名"，未覆盖"移动目录" | 预期：改名/移动都按「删旧建新」且提示 → 实际：移动目录未说明，用户可能误判为 bug | N8 扩写为"改名/移动" | 🟡 |
| 9 | 验收模糊 | 测试者 | 全部 | R6 只写"明确错误码/文案"未给具体错误码；R9 未列必须出现的字段 | 预期：验收可逐条判定 → 实际：不同实现者判定不同 | 补 R6 错误码名、R9 必现字段清单 | 🟢 |

## 6. 推演结论

### 整体评估

- 推演覆盖：4 个角色（含 1 个缺失角色）/ 8 个场景
- 问题发现：🔴 1 / 🟡 7 / 🟢 2
- **全局回扣**：S1/S2/S4 回扣成功；**S3 破坏全局判据 ①「本地还在的一篇都不能误删」** ⇒ 按全局视角记 🔴，不因闸门通过而放行。

### 评审结论

| 条件 | 结论 |
|---|---|
| 存在 ≥1 个 🔴 阻断 | **❌ 不通过** |

### 一句话判断

需求整体符合实际、主链路成立，双闸门方向正确；但有一个必须补的前提——**「本次上传完整」是"本地没有"判定的隐含假设，而需求从未显式要求验证它**。该假设一旦破了（网络抖动、单文件超限、浏览器读文件失败），功能会从"同步删除"变成"删掉本地还在的文档"，且所有闸门都拦不住（少量缺失对比例几乎无感）。

## 7. 补丁效果验证

### S3 上传不完整

```text
{128 篇中 3 篇上传失败}
  ▼
{分支 A：前端传 preserveRels=[3 个 rel]}
  ├─{有效集合 = 扫描 125 ∪ 3 = 128} ✅
  └─{候选 = 库 130 − 128 = 2} ✅
  ▼
{分支 B：拿不到失败清单 → UPLOAD_INCOMPLETE，不产候选} ✅
  ▼
❌ 残余：前端「只收集到部分失败清单」时仍会传 preserveRels
   → 漏掉的那几篇被判候选 → 误删本地仍在的文档
```

**判定：主路径堵住，残留 1 处（`preserveRels` 完整性前提未定义）。**

### S5 删除中断 / 重复点击

```text
{点删除 50 篇 → 第 20 篇时断网}
  ▼
{服务端连接断开但 handler 继续执行 → 50 篇删完} ✅
  ▼
{用户回来点删除 → 重算候选 = 0，token 不同 → 409} ❌ 补丁未堵住
```

**判定：未堵住。** ① 候选已空仍返回 409，前端无法区分「已删完」与「库被改」；② N12 要求「以库为准重算」，但无任何接口能重算并返回新 token。

### S6 候选过期

```text
{实测 JOB_TTL_MS = 1 小时；服务重启即清空 jobs Map}
  ▼
{导入完 >1h 回来 → /api/import/status 无 job → 结果卡连同候选消失} ❌
```

**判定：未堵住。** 需求写的 24h 与代码现状（1h）不符；另 `scannedRels` 降级通道与 S03 冲突（Web 端不实现），实际无效。
