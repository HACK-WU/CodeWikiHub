# 需求分析：目录导入同步清理「库中存在、本次目录已没有」的文档

- **来源**：用户 2026-10-19 原话「上传导入那里，想新增一个功能，当上传的是目录时，可以在知识库中同步删除本地被删除的文件，或者说是知识库同步删除本地没有的文档。」（附上传导入页截图）
- **分析口径**：product-manager（M1 需求定义 · 一次成型档）+ 3 轮用户决策修订
- **证据声明**：`🟢` 最高等级 = **代码直读**（未运行实测）；界面为描述生成的 ASCII 草图，非实测画面，不构成证据降级（判定类型为"符合性"，代码直读即为一手证据）
- **已拍板结论**：Q1 不做来源识别、不关心顶级目录名；Q2 功能默认关闭；Q3 不做删除前备份；Q4 单次上限 500；Q5 作用域见 §3.2；保护措施采用「双 80% 闸门」（见 §3.4）

## 2. 现状链路

```
浏览器选目录/文件（showDirectoryPicker / webkitdirectory / 拖拽）
  └─▶ base64 分片 POST /api/import/upload ─▶ ~/.ki/import-uploads/<uploadId>/
        └─▶ POST /api/import/preflight（只读：内容重复检测）
              └─▶ POST /api/import/run ─▶ handleDirectImport(sourceDir = 暂存目录)
                    └─▶ 幂等追加写 relations-cache / local KB / 向量 / FTS
```

- 每篇文档在 `relations-cache.json` 的 `hot_relations[].sourcePath` 记录「相对源目录的 posix 路径」，**这是唯一可靠的逐文件来源坐标**。
- `sourcePath` 可能为空（历史 `sync-relation` 手工写入，`src/lib/relation-map.ts:33`）。
- `--group` 缺省时，落点 = 文件的相对目录（顶层子目录名即根节点），**一次目录导入会散到多个 group**（`src/lib/import.ts:286-293`）。

## 3. 需求定义

### 3.1 功能定位

在「上传导入」页新增一个**可选、默认关闭**的能力：目录导入完成后，把「库中存在、本次上传的目录里没有」的文档列成候选清单，由用户确认后批量删除。

**不做**：来源标识、顶级目录名记录、导入前预检拦截、自动删除。理由（用户 Q1）：顶级目录名本就不保存，每次导入实时算差集即可；增量比对的数据基础已具备，反向差集成本相同。

### 3.2 作用域口径（定稿）

| 导入时的 Group 选择 | 清理作用域 |
|---|---|
| 选了 Group `G` | `G` 及其所有子 Group（`G/*`）——因为选 G 后文件落点是 `G/<相对子目录>` |
| 未选 Group | **整个 scope**：所有 Group + scope 根节点上的顶层文件 |

### 3.3 判定口径（防实现漂移）

| 项 | 定义 |
|---|---|
| 本次 `rel` 集合 | 本次**目录扫描**到的全部文档相对路径（`collectMarkdownFiles`）。**不是**实际写入/更新的文件——增量跳过重算（`unchanged`）的文件必须算"有" |
| 库中坐标集合 | 作用域内所有 `relation.sourcePath`，**排除空值** |
| 候选 | 库中坐标 − 本次 `rel`（按 `(group, relation)` 定位） |
| 无法判定区 | `sourcePath` 为空的文档：**永不进候选**，单列「N 篇无法判定来源，不参与清理」 |
| 计算时机 | 仅当开关开启时计算；**先算闸门、再算候选**（闸门不过则不枚举明细） |
| 空值 | 库中坐标集合为空 → 无候选 → 不产候选；本次 `rel` 为空（0 文件）→ 不产候选并 fail-loud |
| **前提：上传完整** | 「本次目录里没有」只有在**本次上传完整**时才等价于「本地没有」。上传阶段失败的文件（网络中断 / 单文件超限 / 浏览器读失败）**不在暂存目录**，会被误判为"本地已删" ⇒ 必须按 R11 处理，否则整个功能的核心目标不成立 |
| 重算数据来源 | `/api/import/prune` 由服务端通过 `uploadId` 重新扫描同一暂存目录得到 `rel` 集合（与 run 完全同源）；**不得由前端拼接文件清单**（前端清单不含被服务端拒绝的文件，会导致候选集漂移、token 恒失配） |

### 3.4 保护措施：双 80% 闸门（用户提案的落地形态）

用户提案为「上传目录结构与库中目录结构 ≥80% 吻合，否则自动关闭」。经场景推演，**单一结构指标有盲区与误伤**，故量尺下沉到逐文件路径，并补一道反向闸门：

```
闸门 A（坐标一致性）
  A = |本次 rel ∩ 库中 sourcePath| / min(|本次 rel|, |库中 sourcePath|)
  要求 A ≥ 0.8
  含义：这次上传的路径，库里得"认识"

闸门 B（删除规模）
  B = 候选数 / 作用域内可判定文档数（sourcePath 非空，即 judicable）
  要求 B ≤ 0.8
  含义：这次要删的不能超过库中「可判定文档」的八成

任一不通过 → 自动关闭清理能力（不静默，必须说明原因 + 给 CLI 出口）
```

> **分母为什么不用"库中文档总数"**：`sourcePath` 为空的文档占比较高时，用总数会**稀释比例**（同样删 40 篇，100 篇的库算 40%、50 篇可判定的库算 80%），放宽保护。分母取 `judicable` 才与"实际能被清理的范围"同尺度。

**为什么两道都要**：

| 单闸门 | 漏洞 |
|---|---|
| 只有 A | 只上传 3 个文件时，3 个都能在库里找到 → A=100% 放行，但候选 = 其余全部 → 灾难 |
| 只有 B | 选错目录但 group 名撞车、且新目录文档更少 → B 可能仅 30% 放行 → 整组误删 |

**场景判定表（验收即按此表逐条验证）**：

| # | 场景 | A | B | 期望结果 |
|---|---|---|---|---|
| 1 | 正常：130 篇删 2 篇后再上传 | 100% ✓ | 1.5% ✓ | 放行 |
| 2 | 这次多选/少选一层目录 | 0% ✗ | 100% ✗ | 关闭 |
| 3 | 选错目录，但 group 名撞车 | 0% ✗ | 100% ✗ | 关闭 |
| 4 | 用户删掉整个 `架构/` 目录（想清理） | 100% ✓ | 15% ✓ | 放行（不误伤） |
| 5 | 首次对已有 1000 篇的库开启 | 0% ✗ | 100% ✗ | 关闭 |
| 6 | 只上传了 3 个文件 | 100% ✓ | 99% ✗ | 关闭 |
| 7 | 大批量整理（130 篇删 110） | 100% ✓ | 85% ✗ | 关闭，引导 CLI |

**附加**：候选占比 > 20% 时**前端强制二次确认**（须输入「删除」二字），**不关闭**功能。理由：用户若把目录分多次上传（同 group 内先传 x 再传 y），闸门 A 可 100%、闸门 B 在 50% 处放行，此时只能靠人眼把关。

**阈值**：`0.8` 常量化，文案引用同一常量（不得写死两处）；配置化（`import.pruneMatchThreshold`）放 P2。

## 5. 负向需求

| # | 场景 | 期望行为 |
|---|---|---|
| N1 | 只选了几个文件（非目录） | 不计算、不产候选；服务端收到 `pruneStale=true` 直接拒绝 |
| N2 | 空目录 / 扫描到 0 篇 | 不产候选，明确提示"本次未扫描到文档，已跳过清理" |
| N3 | 上传层级与上次不同 | 双闸门关闭 + 结果卡提示"可能选错目录层级" |
| N4 | 选错目录但 group 名相同 | 闸门 A 关闭（路径不重合） |
| N5 | 导入失败 / 被取消 | 不产候选、删除数为 0（导入未成立，不做清理） |
| N6 | 用户在候选清单停留期间库发生变化 | `pruneToken` 失效 → 409，要求刷新清单后重试 |
| N7 | 删除过程中部分失败 | 逐条回显失败原因，不阻塞导入结果；接口整体返回 `ok: true` + `failed[]` |
| N8 | 文件改名或移动目录（`a.md` → `b.md`，或 `a.md` → `sub/a.md`） | 旧文档进候选、新文档新建；文案需说明"改名/移动 = 删除旧 + 新建，评分与使用次数不迁移" |
| N9 | 候选文档存在未结束的关系编辑草稿 | 沿用既有删除卫兵：拒绝该项并给出原因（`delete-relation` 已有此拦截） |
| N10 | 同一 group 内小比例混装（其他来源文档占 17%） | 双闸门放行 → 会删掉那 17%。**已明确接受**，兜底功能默认关闭 + 未触及 group 默认不勾 + 清单逐条可见 |
| N11 | **上传阶段有文件失败**（网络中断 / 单文件超限 / 浏览器读失败） | 见 R11：不产候选，或把这些 `rel` 并入 `preserveRels` 排除。**绝不能把它们判为"本地已删"**（否则会删掉本地仍在的文档） |
| N12 | 删除中途中断（断网 / 关页面） | 已删除部分不可回滚；重新进入后先用 **`dryRun` 重算候选**再继续删；前端需提示"部分可能已删除，请刷新核对" |
| N13 | 候选清单过期 | **实际有效期 = min(job TTL 1h, 暂存 24h) = 1 小时**（`JOB_TTL_MS`），服务重启立即失效；过期后需重新导入一次。暂存被清理时删除接口返回 `PRUNE_SOURCE_UNAVAILABLE` |
| N14 | 重复点击删除 / 并发两个删除请求 | 重算后候选已空 → **200 `allDone`（不报错）**；候选非空但 token 不同 → 409。前端对 `allDone` 显示"已无剩余候选" |

| ② | 交互 | 未触及 group 分组 | 单列、默认不勾（R4.6） |
| ③ | 文案 | 恢复说明 | 原文进 `.ki/trash`；向量/FTS 不可撤销 |
| ④ | 交互 | 删除按钮 | 文案带数量；>500 时改为提示分批/CLI |

---

## 8. 已接受的风险

**同 group 内小比例混装**：group `wiki` 有 100 篇来自 A 目录、20 篇来自 B 目录；这次只上传 A → 候选 20/120 = 17%，闸门 A = 100% → 双闸门均放行 → B 的 20 篇会被删除。

这是「不做来源识别」（Q1）的固有代价，无法靠闸门解决。兜底：功能默认关闭 + 未触及 group 默认不勾 + 清单逐条可见 + 二次确认。

**多人共用同一 scope**：scope 不做用户隔离，任何能访问该 scope 的使用者都能执行清理。本需求默认前提是**单机单用户**；多人共用时，"别人导入的文档"与"自己目录里没有的文件"在系统视角下不可区分，属 N10 的子情形，界面需在候选区标注作用域（`scopeGroups` / `untouchedGroups`）供使用者自行判断。
