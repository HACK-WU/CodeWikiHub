# 需求分析：本地文档变更自动同步（同步源）

- **来源**：用户 2026-10-19 原话「当前可以在知识导入那里上传文档。但是每当后面本地文档发生了变更，更新，并入新增，修改。（删除暂时忽略）后，还需要再次手动上传更新，感觉很麻烦。有什么办法可以解决一下么？」
- **分析口径**：product-manager（M1 需求定义 · 一次成型档），1 个确认点（3 问）
- **证据声明**：`🟢` 最高等级 = **代码直读**（未运行实测）；界面为描述生成的 ASCII 草图，属"符合性"判定，代码直读即为一手证据
- **已拍板结论**：
  - **Q1 部署形态**：本地文档与 ki daemon **同一台机器** → 采用「服务端直读目录」，不做浏览器目录句柄
  - **Q2 同步形态**：**后台全自动**（关掉浏览器也要同步）
  - **Q3 成本边界**：**允许消耗 embedding**，但必须「变更预筛 + 失败退避熔断」

---

## 1. 结论速览

| # | 结论 | 证据 |
|---|------|------|
| 1 | **痛点的根因不是"上传麻烦"，而是系统没有"源"的概念**：Web 上传落 `~/.ki/import-uploads/<uploadId>/`，24h TTL 清理，`source.dir` 记的就是这个临时目录 | 🟢 `src/lib/mcp-http-api.ts:100-107`、`:1478`、`src/lib/import.ts:1739` |
| 2 | **变更判定只在服务端做**（收到文件之后才判），浏览器端拿不到任何水位线 ⇒ 每次只能整目录重传 | 🟢 `src/lib/import.ts:504-549`（`isContentUnchanged`） |
| 3 | **全仓没有任何 watch / cron / 调度器**，唯一 `fs.watch` 是版本升级提示，与导入无关 | 🟢 `src/lib/version-guard.ts:41-45` |
| 4 | **CLI 侧已经是幂等增量**：重复执行 `ki import --source <目录> --group <g>` 即同步变更（未变文件自动跳过），且与 Web「选择目录」的 `sourcePath` 口径已对齐 | 🟢 `docs/import.md:44-54`、`web/src/pages/ImportPage.tsx:104-118` |
| 5 | **预筛能力已经存在**：`handleDirectImport` 支持 `onlyRelPaths`（只处理名单内文件，名单外完全不读、不切分、不向量化） | 🟢 `src/lib/import.ts:225-231`、`:807-846` |
| 6 | **daemon 是天然宿主**：常驻、回环免鉴权、任务台账可持久化、索引整理队列已有 | 🟢 `src/lib/mcp-http.ts:50-58`、`src/lib/task-registry.ts:148-157` |
| 7 | ⚠️ **`source.dir` 不能被复用为同步源路径**：`sync_relation` 的 wiki 写回**优先级 1** 就是它，复用会把 KB 内容写进用户的原始文档目录 | 🟢 `src/lib/wiki-sync.ts:45-57` |

## 2. 现状链路与痛点

### 2.1 AS-IS

```
本地文档（用户电脑）
  └─ 浏览器：拖拽 / 选择目录 / 选择文件            ← 每次手动，且需重新定位目录
       └─ POST /api/import/upload（base64 分批）
            └─ ~/.ki/import-uploads/<uploadId>/    ← 临时暂存，24h TTL 清理
                 └─ POST /api/import/run → handleDirectImport
                      ├─ 同 sourcePath + 内容未变 → 跳过重算
                      ├─ 同 sourcePath + 内容已变 → 覆盖更新（重切分 + embedding）
                      └─ 新文件 → 导入
```

### 2.2 三个痛点

| # | 痛点 | 本质 | 证据 |
|---|------|------|------|
| P1 | 每次都要重新选目录 | **源身份未被持久化**（存的是临时暂存目录） | `src/lib/mcp-http-api.ts:1478` + `src/lib/import.ts:1739` |
| P2 | 得自己记得"文档改过了" | 无 stale 提示、无同步状态 | `web/src` 下零 `sourceDir` 引用 |
| P3 | 整目录重传 | 变更判定只在服务端 | `src/lib/import.ts:504-549` |

## 4. 需求定义

| ID | 需求 | 说明 | Kano | 价值 | 成本 |
|---|---|---|---|---|---|
| **R1** | 同步源登记 | 网页登记「服务器本地目录 + scope + group + 导入参数」，持久化 | 期望 | 高 | 中 |
| **R2** | 立即同步 | 点一下直接扫源目录走幂等导入，**不经浏览器上传**；返回 变更/跳过/失败 计数 | 期望 | 高 | 低 |
| **R3** | 同步状态可见 | 卡片显示上次/下次同步时间与结果；失败给**可执行**指引（路径不存在/无权限/配额）；进任务台账 | **必备** | 高 | 低 |
| **R4** | 定时自动同步 | 间隔可配（默认 30 min，最小 5 min），daemon 内调度，重启后补跑 | 期望 | 高 | 中 |
| **R5** | 变更预筛水位线 | 按 `mtime+size` 比对，只把变更文件经 `onlyRelPaths` 交给导入 | 期望 | 高 | 低 |
| **R6** | 实时监听 | `fs.watch` 递归 / chokidar + 防抖 + 稳定窗口 | 兴奋 | 中 | 中 |
| **R7** | 浏览器目录记忆 | IndexedDB 存 DirectoryHandle，只上传变更文件 | 无差异（已确认同机，本期不做） | 低 | 中 |
| **R8** | Stale 提示 | 顶部/导入页显示"N 个源有更新未同步" | 兴奋 | 中 | 低 |

**本期范围**：R1 + R2 + R3 + R4 + R5；R6/R8 视实施情况追加；**R7 不做**。

## 5. 负向需求

1. **源不可达**（路径改名 / 网盘未挂载 / 无权限）→ fail-loud 标红，**严禁**把"扫不到文件"当"文件都删了"去清库。
2. **写入中半截文件**（编辑器保存瞬间）→ 稳定窗口：`mtime` 静默 ≥2s 且 size 稳定才读。
3. **一次保存多次事件**（自动保存 / 格式化）→ 去抖合并，同文件一轮只处理一次。
4. **变更风暴**（`git checkout` 数百文件）→ 复用 `--max-batch-files/bytes/chunks` 上限 + 进度可取消。
5. **与手动导入并发** → 走既有 scope 写锁排队，UI 明示占用方，不静默失败。
6. **Embedding 故障 / 配额耗尽** → 指数退避 + 连续失败熔断并通知，不反复重试烧配额。
7. **冲突策略误配** → 自动同步**强制 `incremental`**，禁止 `suffix`（否则每轮生成 `_1` 副本）。
8. **源目录被当成 wiki 写回目标** → 见 §3 第 1 行，字段隔离 + 登记时检测冲突并拒绝。
9. **源内文件被删除**（本期不处理）→ 库内不删，仅在源卡片提示"源中已不存在 N 篇"；与 REQ-20261019-001 的清理能力对接。

## 6. 界面预期（描述生成 ASCII 草图）

```
┌────────────────────────────────────────────────────────┐
│ ① 同步源                                    Scope: ai-docs│
│ ┌────────────────────────────────────────────────────┐ │
│ │ [dir] /Users/me/wiki   → group: wiki   ② 待更新 3 篇│ │
│ │ 上次同步 10-19 14:32 成功（3 变更 / 0 失败）        │ │
│ │ 触发：( )手动 (o)每 30 分钟 ( )实时监听 [ 立即同步 ]│ │
│ └────────────────────────────────────────────────────┘ │
│ [ + 新增同步源 ]                                        │
├────────────────────────────────────────────────────────┤
│ ③ 一次性导入（原入口，保留）                            │
│ ┌────────────────────────────────────────────────────┐ │
│ │ 拖拽 Markdown 文件或目录到此处，或点击选择          │ │
│ │ [ 选择文件 ]  [ 选择目录 ]                          │ │
│ └────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────┘
```

| 编号 | 类型 | 目标 | 说明 |
|---|---|---|---|
| ① | 交互 | 同步源区块 | 置顶于一次性导入之上；无源时整块收起只留 `[+ 新增同步源]` |
| ② | 状态 | 待更新计数 | 由 R5 水位线与源目录比对得出；无变化显示"已是最新" |
| ③ | 交互 | 一次性导入区 | 原逻辑零改动，避免破坏既有上传用户 |

## 7. 优先级

| 优先级 | 条目 | Kano | 价值 | 成本 | 理由 |
|---|---|---|---|---|---|
| **P0** | R1+R2+R3（源登记 + 立即同步 + 状态可见） | 期望/必备 | 高 | 中 | **所有自动化的地基**，单独即消灭 P1/P3 |
| **P1** | R4+R5（定时 + 预筛） | 期望 | 高 | 中 | 用户要的"自动"，须先有 R1 才有落点 |
| **P2** | R6（实时监听） | 兴奋 | 中 | 中 | 定时已够用 |
| **P2** | R8（stale 提示） | 兴奋 | 中 | 低 | 可与 R3 合并 |

**顺序判断**：先做"源"再做"自动"。直接上 watcher 会因为没有源身份无处挂载，最后仍要回头补 R1。
