## 1. 需求速览

| # | 结论 | 证据 |
|---|------|------|
| 1 | 污染的根因不是「没有删除入口」，而是**文档从写入那刻起就没有任何「我多旧、我还该不该在」的信息** | `src/lib/scoring.ts:23-55` `Relation` 无 `createdAt` / `lifecycle` / `expiresAt` 🟢 |
| 2 | 污染已可量化：`kisearch-memory` 现 24 group / **168 篇**；元数据可统计的 120 条里 **50 条（42%）`useCount=0` 从未被读取**，36 条（30%）超 30 天未用 | 本地实测 🟢 |
| 3 | 纯 TTL 自动删是**错的模型**：「性能优化完成 / bug 解决」是业务事件，不是时间函数。正解是「到期进回收站 + 人工复核」，不是「到期物理删」 | 设计判断 🟡 |
| 4 | 两个维度**正交**：分类决定「何时消失」，阶段决定「何时可被检索」。一份排查中的 bug 记录被检索命中，比一份旧报告被命中危害更大（会被当成结论） | 设计判断 🟡 |

| 6 | 回收站必须**删除即摘索引**（语义 / 全文 / 关系 / 路径四类），否则「删了还在被召回」，污染一点没减少 | `src/delete-relation.ts:182-287` 🟢 |
| 7 | 缺省分类 = **wiki**（宁污染，不误删）：判错两个方向代价不对称 | `archive.md:213`、`archive.md:34` 历史误删教训 🟢 |
| 8 | 工程量大：动 `Relation` schema + 4 条写入链路 + 2 条删除链路 + export/restore + 检索 + 新前端三页 | 见 §12 🟡 |

## 2. 背景

### 2.1 污染是怎么形成的

```
文档写入（4 条入口：ki_sync_relation / ki_bulk_sync_relation / open-api upload / ki import）
  │
  ├─ 不记 createdAt ─────────────┐
  ├─ 无 lifecycle 标记 ──────────┤
  └─ 无 expiresAt / eventId ─────┘
                                  ▼
                        谁也不知道「该清谁、什么时候清」
                                  │
        ┌─────────────────────────┼─────────────────────────┐
        ▼                         ▼                         ▼
  检索无时效衰减            列表无时间可看            无批量清理入口
  （旧报告当现状召回）      （人工也判断不了）        （清 30 篇点 30 次）
        │                         │                         │
        └─────────────────────────┼─────────────────────────┘
                                  ▼
                     删除不可逆（无回收站）⇒ 不敢自动清
                                  ▼
                        永久累积 = 污染（现状）
```

### 2.2 典型场景（必须覆盖的两个）

| 场景 | 期望 | 为什么纯时间 TTL 不行 |
|---|---|---|
| 性能分析报告 | 优化完成后删除 | 优化可能拖 3 个月，30 天 TTL 会删掉还没做完的分析 |
| bug 排查报告 | bug 解决后删除 | bug 可能长期未解决，但排查记录已过时 |

共性：**价值终点由业务事件决定**。所以模型里必须有「事件」这个实体，事件收口才触发清理。

### 2.3 反向约束（决定了方案不能怎么设计）

| 约束 | 依据 |
|---|---|
| **数据源同步的文档绝不能套 TTL** | 它们由 import-prune 按源文件判定；强行加时效会被下次同步导回来（`doc-move` 的 409 `DATASOURCE_BLOCKED` 前例）🟢 |
| **不能用 tags 做生命周期标记** | `relation.tags` 每个 tag 会写一条内容向量进检索池，用它打「临时」标**反而增加污染** 🟢 |
| **不能把回收站放在 `{sourceDir}/.ki/trash/`** | 历史 `archive.md:213`：会搬走用户 wiki 仓库的子目录，已作为 bug 移除 🟢 |
| **恢复必然要重建索引** | 删除即摘索引的代价，几秒到几十秒，必须明示 🟡 |

## 3. 整体模型

```
文档（Relation）
├─ lifecycle    : wiki | temp | event            ← 决定「何时消失」
├─ expiresAt    : 仅 temp（到期 → 回收站）
├─ eventId      : 仅 event → 指向事件实例
│                  └─ 事件当前阶段 → visibility（full | fts-only | hidden）
│                       └─ 四类索引按档位摘除 / 写入
└─ refs         : 参考文档引用（反向，不改文档本身任何属性）

事件（Event）
├─ id / title / typeId / stageIndex / closedAt
└─ 阶段链由 EventType 定义（有序，末位为终态）

事件类型（EventType）
├─ name / builtin
├─ stages[]      : { name, visibility, disabled }   ← 可见性三档
└─ terminalAction: keep | trash                     ← 类型级，不随阶段拖动漂移

回收站（TrashItem）
└─ 索引已摘 · 原文 + wiki 源文件留 7 天 · 恢复需重建索引
```

**关键：`temp` 到期与 `event` 收口，走的是同一条「→ 回收站」的落点。** 这是为什么回收站必须第一个做。

## 4. 模块一：文档分类

### 4.1 分类语义

| 分类 | 徽标色 | 消失条件 | 说明 |
|---|---|---|---|
| **wiki** | 绿（`--ki-color-primary`） | 永不 | 缺省值 |
| **临时** | 琥珀（`--ki-color-warning`） | `expiresAt` 到期 → 回收站 | 有效期 7/30/90 天 + 自定义（1~365） |
| **事件** | 蓝（`--ki-color-info`） | 事件收口 → 按终态动作（保留 / 移入回收站） | 需绑定 `eventId` |

### 4.2 缺省走安全侧

**新建文档若不指定分类，一律 wiki。**

| 判错方向 | 后果 | 可接受度 |
|---|---|---|
| 临时标成 wiki | 污染继续（可下次再清） | 可接受 |
| wiki 标成临时 | 有用知识被删（虽可恢复但要重建索引，7 天后彻底没了） | **不可接受** |

### 4.3 倒计时语气分层

`剩 ≤2 天` 红 · `3~5 天` 琥珀 · `≥6 天` 中性。初版把 8 天也标琥珀，视觉噪音过大，已收敛。

### 4.4 数据源文档豁免

`sourcePath` 非空（由数据源同步）/ `isImported` 的文档 → **强制 wiki**，前端灰化 + 标注「由数据源同步」，不允许改分类。

## 5. 模块二：事件与阶段

### 5.1 为什么需要事件

分类只能表达「何时消失」，表达不了「**还在进行中，所以不该被当成结论**」。事件提供两件事：

1. 一个「未收口 / 已收口」的状态机 —— 决定文档何时可删
2. 一条**阶段链** —— 决定文档在哪个阶段可被检索到

### 5.2 三档可见性（不是布尔）

| 档位 | dense | FTS | 检索效果 | 实现现状 |
|---|---|---|---|---|
| `full`（语义+全文） | ✅ | ✅ | 语义与全文都能查 | 现成默认路径 🟢 |
| `fts-only`（仅全文） | ❌ | ✅ | 语义查不到、全文能查到 | **现成能力**（`vector:false`）🟢 |
| `hidden`（不可检索） | ❌ | ❌ | 谁都查不到，但浏览页可见 | **需新增**（FTS 也要摘） |

内置三类型示例：

```
bug 排查    排查中(hidden) → 已定位(fts-only) → 修复中(fts-only) → 已关闭(full) 保留
性能优化    分析中(hidden) → 优化中(fts-only) → 已验证(fts-only) → 已完成(full) 移入回收站
需求实现    实施中(hidden) → 联调中(fts-only) → 已上线(full) 保留
```

### 5.3 hidden 档必须摘四类索引

```
内容 dense（memoryIds）   → ki_search 语义命中
FTS（ftsIds）             → ki_search 全文命中
ki-relation（关系名向量）  → 关系 / 标题相似召回
ki-path（路径向量）        → 路径模糊兜底
```

**漏任何一类都会被兜底召回。** 这是最容易做漏的地方（先例：`2026-10-21-删除关系残留路径向量`）。

### 5.4 阶段定义的两条约束

| 约束 | 理由 |
|---|---|
| **编辑已存在类型时，阶段只能追加不能删** | 已有事件停在该阶段后，删定义会留下悬空状态；要废弃请用「停用」（新事件不可进入，老事件可停留，并提供「迁移到 X」引导） |
| **新建类型时（草稿态）可以删** | 还没有任何事件依赖 |

### 5.5 终态位置动态，但动作固定在类型级

阶段可拖动排序 ⇒ 「哪个阶段是终态」由**最后一枚**决定（demo 用 CSS `:last-child` 实现，拖动后无需 JS 维护标记）。

**但「终态做什么」不能跟着位置漂移**：如果 `action` 存在阶段对象上，拖动把原终态挪到中间、再追加一个新终态（默认 keep），原本的「移入回收站」会静默丢失。所以 `terminalAction` 是**事件类型级字段**（见 §9.3）。

### 5.6 复用类型阶段 = 复制，不是引用

复用后是独立副本，源类型后续调整不影响新类型。

**如果做成引用**（改 A 所有复用过它的类型一起变），就是隐性联动：用户在界面上完全看不出这层依赖，且无从追溯。项目已有同类教训（数据源 `sourcePath` 联动、跨组共享 docId）。

### 5.7 未收口事件的兜底期限（防「永不清理」）

事件驱动清理依赖「事件会被收口」，但**没有机制保证事件一定会收口** —— 一个被遗忘的未收口事件，会让它挂的文档永远不清理，等于把「永久累积」换了个地方。

所以事件类文档**必须带兜底期限**：

| 项 | 值 |
|---|---|
| 字段 | `EventTypeRecord.fallbackDays`（默认 90，可设为 null 关闭） |
| 触发 | 事件创建满 `fallbackDays` 仍未收口 |
| 行为 | 关联文档**进回收站**，`reason = 'event-expired'`；事件列表该条标红「已超兜底期限」 |
| 不做什么 | **不自动收口事件**（收口是业务判断，机器不能替人拍板），只处理文档 |

> 兜底期限 < 事件真实生命周期是常态（bug 可能拖半年），所以兜底触发时给的是**回收站 + 7 天窗口**，而不是直接物理删。人在 7 天内可以把文档捞回来并绑定到新事件。

### 5.8 事件删除的前置条件

**事件未到终态不允许删除。** 事件是文档的分类宿主，没走完就删，关联文档会失去宿主。

删除时必须选择关联文档去向：**改为 wiki 保留**（默认）/ **移入回收站**。

**两种去向都必须清理引用，否则 `eventId` 会指向已不存在的事件（悬空引用）**：

| 去向 | `lifecycle` | `eventId` | `expiresAt` | `TrashItem.reason` |
|---|---|---|---|---|
| 改为 wiki 保留 | `wiki` | **清空** | 清空 | — |
| 移入回收站 | `temp` | **清空** | `now + 7d`（回收站期限） | `event-closed` |
| 兜底到期（§5.7） | `temp` | **清空** | `now + 7d` | `event-expired` |

「终态动作为 keep」的事件收口时，文档同样要把 `lifecycle` 从 `event` 改为 `wiki` —— **`event` 是「挂在事件上」的临时状态，事件没了它就不该存在。**

## 6. 模块三：回收站

### 6.1 核心定义

```
删除时
  ├─ 索引层（relations 分片 / dense 向量 / FTS / 路径向量 / 关系向量）→ 立刻清掉
  └─ 内容层（local KB 原文 + wiki 源文件 + 元数据）→ 移入回收站，留 7 天
恢复时
  └─ 从回收站取回原文 → 重新走 sync 链路（重建向量 + FTS）→ 数秒
到期时
  └─ 物理清除（惰性：daemon 启动扫一次 + 每次删除/写入操作时顺带扫）
```

**反过来做（索引保留、只标记已删）会让 `ki_search` 继续召回已删文档 —— 污染完全没解决，只是换了个地方展示。**

### 6.2 目录位置

`~/.ki/trash/{scope}/{group}/`（数据目录），**不放在 `{sourceDir}/` 下**。

wiki 源文件进回收站用 **copy 而非 move**，原文件仍按现语义 unlink —— 避免「用户仓库里凭空出现 `.ki`」（`archive.md:213` 前例）。

### 6.3 设置项

| 项 | 选项 | 默认 |
|---|---|---|
| 保留天数 | 3 / 7 / 14 / 30 | 7 |
| 到期处理 | 自动清除 / 仅提醒不自动删 | 自动清除 |

不可配：「删除即摘索引」（这是污染是否消失的前提，不提供关闭开关）。

### 6.4 恢复后的期限重算（否则会「恢复完立刻又到期」）

`temp` 文档进回收站时 `expiresAt` 已过（它就是因为过期才进来的）。如果恢复时沿用它，**下一次惰性清理立刻又把它送回去** —— 用户会看到「恢复了，刷新一下又没了」。

**规则**：

| 场景 | 恢复后的 `expiresAt` |
|---|---|
| 原 `expiresAt` 已过 | `now + 原期限长度`（不是原值），并在 UI 提示「已按原期限续期 N 天」 |
| 原 `expiresAt` 未过（手动删除的） | 原值不变 |
| 恢复时用户主动改分类为 wiki | 清空 `expiresAt` |

**同一文档连续恢复 ≥3 次**时提示「这份文档反复过期，建议改为 wiki 或调长有效期」—— 这是「有效期猜不准」的信号（H5）。

### 6.5 「沉淀为 wiki」的位置

放在**回收站里**由人主动触发，而不是删除前拦截。

理由：删除时用户只想清干净，不想做知识整理；放在回收站天然有 7 天窗口，真没用的到期自动清，有价值的再提炼。AI 提炼结果**先落草稿**，人工确认后才入库。

> 同时要直说：**这个功能的真实价值低于它的想象价值**。如果一份文档真有沉淀价值，写入时就该标 wiki，而不是等删了再抢救。它应该是「补救机制」，投入要克制。

## 7. 模块四：参考文档

### 7.1 与关联文档的本质区别（关键）

```
关联文档 = 事件的「产物」  → 可见性由事件阶段决定 → 事件收口跟着处理
参考文档 = 文档的「引用」  → 可见性取文档自身     → 与事件生命周期无关
```

**如果参考文档也被阶段控制，就会污染原文档**：一篇 `项目架构/配置` 下的 wiki 因为被某事件引用，就在事件「排查中」期间从语义检索里消失，而它自己的分类明明是永久 wiki。

所以：**加入 = 建一条引用关系，不写文档任何属性；移除 = 解除引用，不删文档。**

### 7.2 两个来源

| 来源 | 交互 | 关键约束 |
|---|---|---|
| **AI 检索** | 基于事件描述 + 关联文档摘要 → 检索知识库 → 候选列表（含相关性分数 + **为什么相关**）→ 勾选确认 | 自动排除「已关联」与「已加入」；默认只勾 ≥0.6；低分项留给人判断 |
| **手动添加** | 按名称 / 路径搜索全库 → 勾选加入 | 同样排除已关联 / 已加入 |

### 7.3 AI 过程必须可见

点击「AI 查找」后不能直接出结果 —— 要有**可折叠的执行日志**（非对话形态）：

```
⊙ 检索完成 · 找到 3 篇候选          5 步 · 4 次调用 · 3.1s  ▾
──────────────────────────────────────────────────────────────
✓ 理解事件：#3 登录页白屏 · bug 排查 · 当前「已定位」
  ┃ skill  event-context                              180ms
✓ 在 kisearch-memory 语义检索 168 篇… 命中 12 篇
  ┃ MCP  ki_search                                    640ms
✓ 排除 3 篇已关联、2 篇已加入 → 剩 7 篇
✓ 按相关度排序，取前 3 篇
  ┃ skill  relevance-rank                            90ms
```

三条硬要求：
1. **每一步必须带真实数字**（命中 12 篇、排除 5 篇），否则就是假动画，用户会连带怀疑结果
2. **每步可单独展开**看详情（实际 query / grep pattern / 排除名单）
3. 结果出来后**过程自动折叠**，可点回看

## 8. 前端信息架构

### 8.1 侧栏分组

`AppShell.tsx:66-80` 现为扁平 10 项，再加 3 项会稀释主路径 ⇒ 拆为两组：

```
工作空间   总览 / 知识库浏览 / 语义搜索 / AI 对话 / 上传导入
           知识写入 / 数据源 / 后台任务 / 知识视图 / 资源
知识治理   文档分类 / 事件 / 回收站
```

### 8.2 浏览页零改动（仅加一个只读徽标）

尊重「浏览页就是浏览所有文档」的定位。但有一个真实缺口：分类信息完全不可见，用户会在文档消失时才发现。

**补救**：阅读器页头加一个**不加高度**的分类徽标（复用 `ki-badge`），不改列表、不加筛选、不改布局。

### 8.3 三页形态

| 页面 | 形态 | demo 区块 |
|---|---|---|
| 文档分类 | 表格 + 分类分段筛选 + 多选批量改分类 + 按剩余天数排序 | P1 |
| 事件 | 左列表（搜索 + 限高滚动）+ 右详情（阶段流水线 / 关联文档 / 参考文档 / MCP 示例）| P2 |
| 事件类型 | 同上页内 tab：阶段表（可见性三档 + 终态动作标记）+ 新建类型（回车添加 + 拖动排序 + 复用）| P2 |
| 回收站 | 表格 + 删除原因筛选 + 行内恢复 / 沉淀为 wiki + 批量 + 设置弹窗 | P3 |

## 9. 数据模型

### 9.1 Relation 扩展

```ts
interface Relation {
  // …现有字段不动…
  lifecycle?: 'wiki' | 'temp' | 'event';   // 缺省 wiki
  expiresAt?: number;                       // 仅 temp；毫秒时间戳
  eventId?: string;                         // 仅 event
}
```

**必须同步进**：`relations` 分片 schema、`export` / `restore` 兼容类型、`rebuild-vector`（重建时按阶段档位走，不能一律 full）。

### 9.2 事件

```ts
interface EventRecord {
  id: string;              // "#3" 或 uuid
  scope: string;
  title: string;
  typeId: string;
  stageIndex: number;
  closedAt: number | null;
  createdAt: number;
  updatedAt: number;
}
```

关联文档由 `Relation.eventId` 反向聚合，**不在事件上存文档列表**（避免双向一致性）。

**流转历史单独存**（删除事件的弹窗承诺了「阶段流转记录一并消失」，必须有承载）：

```ts
interface EventStageLog {
  eventId: string;
  fromStage: number | null;   // null = 创建
  toStage: number;
  at: number;
  by: 'user' | 'ai';
}
```

存放位置：`<kbDir>/.events/<eventId>.log.jsonl`（按事件分文件，追加写，随事件删除一并清理）。

### 9.3 事件类型

```ts
interface EventTypeRecord {
  id: string;
  scope: string;
  name: string;
  builtin: boolean;        // 内置不可删
  stages: Array<{
    name: string;
    visibility: 'full' | 'fts-only' | 'hidden';
    disabled?: boolean;          // 停用，不可进入新事件
  }>;
  /** 未收口兜底天数（默认 90；null = 关闭兜底）—— 见 §5.7 */
  fallbackDays: number | null;
  /**
   * 终态动作：**类型级字段，不挂在阶段上**。
   * 若挂在 stages[last].action：拖动把原终态挪到中间、再追加新终态（默认 keep）时，
   * 原本的 trash 会静默丢失 —— 这是「终态位置动态」必然带来的坑。
   */
  terminalAction: 'keep' | 'trash';
}
```

**Q5 定案（含行为说明）**：浏览页实际有两条搜索通道 —— `getDocList({ q })` 走**元数据扫描**（文档名 / 路径），`kiSearch()` 走 **FTS**（正文）。`hidden` 档摘掉 FTS 后：

| 浏览页操作 | `hidden` 文档的表现 |
|---|---|
| 左侧文档树 | 正常可见（只要还在库里） |
| 按**文档名 / 路径**搜 | 正常命中（走元数据，不受影响） |
| 按**正文内容**搜 | **搜不到**（FTS 已摘） |
| 打开阅读 | 正常（原文在 local KB） |

这不是 bug，正是「不参与检索」的应有表现。但**必须在 UI 上说清**：`hidden` 档的文档在阅读器页头显示「当前不可被检索」，避免用户以为搜索坏了。

## 17. 关键假设

| ID | 假设 | 错了会怎样 | 验证方法 |
|---|---|---|---|
| H1 | AI 写入时会真的传分类 | 全落 wiki 缺省，等于没做 | 灰度 2 周统计临时类占比 |
