# 需求：AI 分析工具面开放写入（可写 MCP 对分析开放）

**来源**：用户需求（2026-11-23）+ 两张截图（现状「AI 分析 → 知识库只读」4 项；对照「AI 对话 → 写入 6 / 删除 2，危险 · 默认关」）。
**模式**：product-manager M1 需求定义 + M4 界面呈现（组合输出一张清单）。
**证据声明**：最高 `🟢 代码直读`（工具面 / 校验 / 执行装配 / 只读库门禁全部指到 `file:line`）+ 用户上传截图（现状界面属实）；**预期界面为设计推演 `🟡`，未实测运行**。
**拍板**：2026-11-23 用户确认 PM 报告全部建议（含界面预期图与 H1~H7 取舍），据此定稿 v1。

## 1. 执行摘要

1. **诉求可实现，机制基本齐备**：写工具 8 个在对话侧已有完整实现（`src/lib/chat/mcp-tool-registry.ts:541-870`，走 OperationCoordinator 排队 + 超时 + 配置快照），只读库门禁已覆盖全部写 op（`src/lib/scope-policy.ts:70-101`）。`🟢`
2. **必须同批修的默认值陷阱**：`defaultAnalysisTools()` 把 `ANALYSIS_TOOL_NAMES` **全部置 true**（`prompt-config.ts:228-232`），normalize 以它为基线（`:1613`），前端与两个 runner 又把「缺键」当开启（`PromptConfigLayer.tsx:1098`、`analysis-runner.ts:1163`、`analysis-ask-runner.ts:254`）。直接把写工具加进白名单 ⇒ **存量配置升级后静默开启写权限**。`🟢`
3. **本质差异是「谁在场」**：对话是用户在场、可即时纠正；分析是 `void executeAnalysisBackground(...)` 后台跑完才看结果，只有「停止」一个闸（`analysis-runner.ts:1093`），写已落盘不可撤销。`🟢`
4. **追问会连带获得写工具**：分析与追问共用同一份 `analysisCfg.tools`（`analysis-ask-runner.ts:253-255`），无法只给其中一个；该口径与既有草案 REQ-20261123-002 的 REQ-06「工具开关直接共用 `analysis`」一致。`🟢`
5. **本期范围已收窄**（用户拍板）：写入组**4 个**纳入；`ki_bulk_store`（任意本地文件路径）、`ki_edit_relation`（异步轮询 + 局部改易坏文档）、删除组 2 个**不纳入**。

- **可行性 / 复杂度**：9 条结论中 **7 可实施 / 2 有条件**；整体复杂度 **高**（主导：结构面 —— 跨 chat 配置域 + events 执行域 + web 设置页 + 追问 runner）。
