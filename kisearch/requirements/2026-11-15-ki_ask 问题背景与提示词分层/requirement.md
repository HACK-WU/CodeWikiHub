# 需求分析：`ki_ask` 支持问题背景 + 提示词分层

- **来源**：2026-11-15 需求方提出「`ki_ask` 能返回答案，但 AI 不知道问题背景，希望能上传简要背景/上下文」，并追问「`ki_ask` 用的提示词与页面上配置的基础提示词是否共用」。
- **前置需求**：[REQ-20261113-001 MCP 无状态 AI 问答工具](../2026-11-13-mcp-stateless-ask/requirement.md)（一期工具面 + 二期 `context_id` 续接已落地）。
- **模式**：M1 需求定义（一次成型档）。
- **证据声明**：最高等级 **`🟢` 代码直读**（含 `file:line`）+ 一条命令实测（内置基础提示词字符数 = **1117**，与页面截图「1117 字 · 默认」逐字一致）；**未运行**真实 `ki_ask` 链路（需上游 key），故「提示词文案效果 / 答案质量 / 轮次收益」类结论只到 `🟡`，全部进 §11 关键假设。
- **v2 修订（2026-11-15）**：需求方拍板 —— `background` 上限由建议值 8000 **下调为 2000 字符**（「背景只需简短描述当前遇到的问题」）；其余 4 项采纳建议。§5 R3、§10、§12 以 v2 为准，需求状态 → **已确认**。

## 1. 背景与问题

### 1.1 需求方原话拆成两个问题

| # | 问题 | 性质 |
|---|------|------|
| Q1 | `ki_ask` 只能问问题，AI 不知道背景 ⇒ 希望支持上传简要背景/上下文 | 新需求（本文件主体） |
| Q2 | `ki_ask` 用的提示词，和页面上配置的基础提示词是否共用 | 现状核查（结论见 §2，直接决定 Q1 的方案取舍） |

### 1.2 为什么「现在也能用」不等于「够用」

现状两条替代路径都存在，但都不满足语义：

| 替代方案 | 现状可行性 | 为什么不满足 |
|---|---|---|
| 把背景塞进 `question` | 可用，但 `question` 只允许 **4000 字符**，超限 fail-loud，且失败文案明确劝退长材料（`🟢 src/lib/mcp-tools/ask.ts:116-123`） | 背景被当成「问题内容」参与检索 query 构造，污染检索意图；问题与前提混在一段文本里，答案口径也不稳 |
| 先建 `context_id` 说背景、再问问题 | 可用，但需 **多一次工具往返** | ① 背景占掉 20 条消息预算的 2 条；② 受 **10 分钟滑动 TTL** 约束，回头再问背景就过期；③ 每次问答只有 **6 轮**检索预算，先花一轮说背景是净损失 |

**产品判断**：背景是「稳定前提」（项目 / 版本 / 环境 / 约束 / 已试过的方案），不是「历史对话」。它应当**随问题一次性带上**，既不进会话历史，也不占检索轮次；且因是「简短前提」，上限必须显著低于 `question`，否则会退化成「贴材料」入口。

## 2. 现状核查：提示词确实共用（Q2 结论）

`ki_ask` 没有自己的 system 提示词，复用页面「AI 对话 → 基础提示词」那一份。

```text
ki_ask(question)
  ▼ ask.ts:196            runAsk({ scope, question, contextId, capabilities })
  ▼ ask-runner.ts:358     runToolLoop({ conv: 内存骨架, convSystemPrompt: '' })
  ▼ ask-runner.ts:243     buildMemoryConv() —— 无 injected 字段（无会话快照）
  ▼ tool-loop.ts:284      injectionBlocks = conv.injected?.blocks ?? runtime.systemBlocks
  │                       ⇒ 恒走 systemBlocks（每次实时读盘）
  ▼ tool-loop.ts:172      resolveRuntime() → readPromptConfig(loadConfig()).config
  ▼ prompt-config.ts:748  promptSnapshotBlocks(cfg) = [
        ├─ skill 目录（renderSkillCatalog）
        ├─ 页面「基础提示词」prompt.content   ◀── 截图里这 1117 字
        └─ HARD_RULES_BLOCK（硬性反幻觉规则）
      ]
```

### 2.1 共用清单

| 共用项 | 证据 | 差异 |
|---|---|---|
| 基础提示词 `prompt.content` | `🟢 prompt-config.ts:754` | **无**。图中「1117 字 · 默认」= `DEFAULT_CHAT_PROMPT` 实测 **1117** 字符 ⇒ 当前磁盘上是内置默认值，未被改过 |
| skill 目录 + 启用状态 | `🟢 prompt-config.ts:753`、`:760` | 无 |
| 硬性规则 `HARD_RULES_BLOCK` | `🟢 prompt-config.ts:755` | 无 |
| 工具开关 `tools` | `🟢 mcp-tool-registry.ts:880-882` ∩ `tool-loop.ts:665` | `ki_ask` 再叠加只读上界 `knowledge.read`（`🟢 ask.ts:41`）⇒ **页面上关掉 `ki_search`，`ki_ask` 内层也检索不到** |
| 思考级别 / 工具返回上限 / 检索条数 | `🟢 tool-loop.ts:184`、`:199`、`:200` | 无 |
| 会话级 `systemPrompt` | `🟢 ask-runner.ts:362` 传 `''` | **不共用**（页面可为单会话自定义提示词，`ki_ask` 不注入） |
| 生效时机 | 页面走会话快照（新建会话才生效）；`ki_ask` 无快照 | 方向相反：`ki_ask` **每次调用吃最新配置** |

### 2.2 共用带来的两处真实缺口

1. **提示词是「面向页面会话」写的，却被借给无界面通道**（`🟢` 事实 / `🟡` 影响）：
   - 「界面会展示来源入口，编号由系统生成，不自行伪造」（`🟢 retrieval-skill.ts:121`）—— `ki_ask` 返回 JSON，没有界面；
   - 「本会话上下文」「用户引用」（`🟢 retrieval-skill.ts:132/138`）—— 调用方是外部 AI 客户端，不是坐在页面前的人；
   - 影响：措辞失真，模型可能产出「见右侧来源面板」这类无效指引。等级 `🟡`（需实测一次调用观察）。
2. **skill 加载要花掉一次检索轮次**（`🟢` 事实）：`tool-loop.ts:671` 无条件暴露 `use_skill`，而基础提示词第 135 行要求「用 `use_skill("builtin-retrieval")` 加载 skill」⇒ 6 轮预算先扣 1 轮搬规则；且 `ki_ask` 的 `conv` 从不写 `loadedSkillIds`（`🟢 ask-runner.ts:243-267`），跨轮不重放（`🟢 tool-loop.ts:301`），续接时消费的 skill 正文丢失。

> 这正是「AI 不知道背景」的同源病根：**问题不是缺一个参数，而是「页面会话的规则被复用到无界面、无人类、单次请求的通道上」**。因此本需求把「背景入参」和「提示词分层」放在一起。

## 6. 负向需求

1. **参数为空**：`background=""` / 全空白 → 等同未传，不报错（不制造无意义失败）。
2. **超长**：超上限 fail-loud，沿用 `question` 的口径（`🟢 ask-contract.ts:27-35`）；错误文案必须点明「背景是交代前提，不是贴材料」，把调用方导向 `ki_search`。
3. **误用为长文载体**：背景塞整段日志/代码 → 文案指向 `ki_search` 取片段后自行归纳（与第 2 条同一出口）。
4. **指令注入**：背景里写「忽略以上规则 / 你是另一个模型」→ 作为待分析内容；复用基础提示词已有条款语义（`🟢 retrieval-skill.ts:144`）。
5. **状态异常**：`context_id` 过期但仍重传 `background` → 沿用 `ASK_CONTEXT_EXPIRED` 明确报错，**不静默新开**会话。
6. **矛盾输入**：背景说 A、历史说 B → 以本轮背景为准并显式说明冲突（R5）。
7. **隐私**：背景正文**不进日志、不落盘**（已拍板口径，§10-1）。

## 8. 直观视图：背景进入哪一层

```text
本轮上游 messages（ki_ask）
├─ system#1  skill 目录            ┐
├─ system#2  页面「基础提示词」1117字 ├─ 共用页面配置（不改）
├─ system#3  硬性规则              ┘
├─ [R9] system#4  MCP 场景适配块   ◀── 新增（方案 B，不改共用正文）
├─ 历史（仅 context_id 续接时）
└─ user       ← background 附录段 + question   ◀── R2 注入位置
```

**R2 的依据不是偏好**：`🟢 tool-loop.ts:232-238` 记录了引用块曾被放进 system 组，导致「thinking 里反复说最后一条 user 是空的、答非所问」的实测踩坑，最终改为附在本轮 user 消息末尾。背景与引用同属「本轮附带材料」，走同一条路。

## 10. 拍板结论（2026-11-15，需求方确认）

| # | 事项 | 结论 | 落地要点 |
|---|---|---|---|
| 1 | `background` 是否落盘 | **不落盘**（一次性语义） | 只对本轮生效；续接需重传；不占 20 条消息预算 |
| 2 | 参数命名 | **`background`** | `context` 已被 `context_id` 占词，禁止混用 |
| 3 | 提示词分层 | **方案 B**：共用块不变 + `ki_ask` 追加 MCP 适配块 | 页面会话 `messages` 字节不变（回归用例守） |
| 4 | `background` 上限 | **2000 字符**（原建议 8000 经需求方判定过宽） | 语义 = 简短前提（项目 / 版本 / 环境 / 已试方案）；2000 ≈ 1000 汉字，足以容纳 20~30 行报错摘要；长材料走 `ki_search` |
| 5 | 页面关只读工具会削弱 `ki_ask` | **保持现状**，文档与工具描述写明 | 不绕过 `prompt-config` 的 `tools` 开关（配置即事实） |

**v2 变更摘要**：`background` 上限 8000 → **2000**（需求方：「背景只需要简短描述当前遇到的问题就可以了」）；其余 4 项采纳建议值；状态 草案 → 已确认。

## 11. 关键假设

| ID | 假设 | 错了会怎样 | 验证方法 |
|---|---|---|---|
| A1 | 调用方（外部 AI）会读 `TOOL_DESCRIPTION` 并按需传 `background` | 描述再准也没人传，需求价值归零 | 真实 MCP 调用日志中 `background` 出现率 |
| A2 | 背景主要价值是「帮模型构造更准的检索 query」，而非仅「答得更贴题」 | 若只是后者，收益低于预期 | 抽 10 条同题对比「带 / 不带背景」的检索 query 与来源命中 |
| A3 | 6 轮预算足以容纳「1 轮加载 skill + 检索作答」 | 背景变长后 `truncated` 上升 | `ask-log` 的 `rounds` / `truncated` 分布统计 |
| A4 | 页面提示词的页面专属措辞会对 `ki_ask` 产生可见偏差 | R9 可降级为 P2（保留为可选项） | 单次真实调用观察答案是否出现「见界面/来源面板」类无效指引 |
| A5 | 2000 字符足以承载真实背景（不掉到「必须塞 `question`」） | 需求方仍被逼用 `question` 装长背景，R3 形同虚设 | 真实调用日志中 `backgroundChars` 分布；若 ≥1800 占比高则复核上限 |

## 12. 验收方式（实施后按此判定）

1. **契约层**：`background` 缺省时，构造的上游 `messages` 与改造前**字节一致**（回归用例）。
2. **注入层**：传背景时背景只出现在最后一条 `user` 内，system 组不变（R2）。
3. **边界层**：2000 / 2001 字符、空串、全空白、与 `context_id` 组合 8 种路径各有断言（R3/R4）。
4. **负向层**：注入型背景不改变系统行为；`context_id` 过期仍明确报错（§6）。
5. **场景层**：真实 MCP 客户端调用 3 例——① 单次带背景问；② 带背景问 + `context_id` 追问；③ 不传背景（验证向后兼容）。
