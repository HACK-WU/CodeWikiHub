# 需求：任务详情导入信息完备

## 1. 背景

后台任务页（`/tasks`）右侧 DETAIL 面板是用户回看导入结果的唯一入口，但当前只渲染 8 个字段（来源 / 知识库 / 阶段 / 索引 / 进度 / 起止时间 / 已提交条目 / 任务 ID）。

用户实测反馈：**「导入的总文件数、scope、成功多少、失败多少、同名策略、疑似重复、Group、tag、是否开启向量，这些信息全都没有展示」**。

经代码核对与场景推演（见 `review/scenario-rehearsal.md` 推演结论），问题不是前端漏渲染，而是**任务台账契约的采集缺口**：

1. 三端（web job / CLI 直连 / daemon RPC）创建任务时只写 `{ operation, scope }`，导入参数与结果统计**从未落台账**；
2. 结果统计只存在于内存 `Job.result`（TTL 1h / 上限 50 条 / 重启即丢），而任务详情读的是 `.ki-tasks/<id>.json`；
3. 详情里的「进度 · 写入 100%（1/1）」是**最后一个阶段事件**的快照（`persist` 的 1/1 步），既不是文件数也不是完成率，完成态下是零信息且会误导。

## 2. 目标与非目标

**目标**：让用户在一个详情面板内回答四个问题——「导入了什么 / 成没成 / 哪里不对劲 / 下一步怎么办」，且结论在 1h 内可回看、三端一致、不依赖进程存活。

**非目标**：
- 不做长期审计（任务保留期仍为 1h，见待确认 ①）；
- 不重做任务中心信息架构（左列表 + 右详情结构不变）；
- 不改变导入核心逻辑（`handleDirectImport` 的统计口径不动，只做透传）。

## 3. 需求清单

### 3.1 R1 结果摘要（文件级，必备）

详情必须展示文件维度的结果，而不是阶段进度：

| 字段 | 语义 | 口径来源 |
|---|---|---|
| 扫描 | 白名单后、剔除疑似重复前的文件数 | `stats.files.scanned` |
| 成功 | 文件级完成（含增量未变） | `stats.files.completed` |
| **其中内容未变** | 增量导入下内容未变、未重算的文件数（`completed` 的子集） | `stats.files.unchanged` |
| 未完成 | 未提交元数据的文件数 | `stats.files.incomplete` |
| 跳过 | 未进入最终处理的文件数（合计） | `stats.files.skipped` |
| 跳过原因 | 同名冲突 / 疑似重复 / 超限或 hook 失败（三者分开） | `conflicts`、`duplicatesSkipped`、差值 |
| 向量条目 | 写入 dense 层的条目数 | `stats.vectorized` |
| 全文索引条目 | FTS 条目数（失败时 dense 正常但搜不到） | `stats.fullTextIndexed` |
| 附件 | 复制的本地图片数 | `stats.assets` |

**R1.1**：`unchanged` 必须与 `completed` 分开展示。默认策略即增量导入，若把未重算的文件计入「成功」而不说明，用户会把"改了文档没生效"误判为 Bug。

**R1.2**：`跳过 2` 必须能看出成因。三种成因的后续动作完全不同：库中已有（不用管）/ 疑似重复（可建副本）/ 文件过大（需切分）。

### 3.2 R2 参数快照（必备）

详情必须展示本次任务的执行参数（而非当前配置）：

| 字段 | 说明 |
|---|---|
| 知识库（scope） | 已有，保留 |
| 来源形态 | 浏览器上传（暂存目录，会被 TTL 清理）/ 外部目录（CLI 指定）——决定能否事后重试 |
| Group | **可多值**（源目录子结构会派生多个 Group）；无显式 group 时标注「按源目录自动派生」 |
| 标签 | 本次导入写入的文档级 tag；未设置显示「未设置」 |
| 向量 | 是否写入 dense 层（`--no-vector` 时为「仅全文索引」） |
| 同名策略 | 增量导入 / 自动添加后缀（+ 后缀模板）/ 覆盖已有 / 跳过同名 |
| 疑似重复 | 是否启用了「跳过重复」 |

**R2.1**：参数快照复用既有 `ImportRetryParams` 语义（group / chunkSize / chunkOverlap / vector / tags / conflictMode / conflictSuffix），**不新造口径**。

### 3.3 R3 失败可判别原因（必备）

- 台账必须保存**可判别错误码**（如 `ALL_FILES_DUPLICATES` / `IMPORT_BUDGET_EXCEEDED` / `VECTORIZATION_STOPPED` / `INCOMPLETE_LIST_*`），不能只留经 `safeErrorSummary` 压缩后的泛化文案；
- 未命中白名单的错误，现有兜底文案「请查看发起端的命令输出或服务日志」**对网页用户无效**（网页用户没有"发起端命令输出"），必须给出可在页面内执行的下一步。

### 3.4 R4 疑似重复明细（期望）

- 计数（`stats.files.duplicatesSkipped`）+ 明细（本次被跳过的文件 → 库中已有的文档）；
- 明细**必须有硬上限**且 UI 明示「仅显示前 N 条 / 共 M 条」，避免台账文件超限导致任务消失（见 N1）。

### 3.5 R5 同名冲突明细（期望）

`suffix` 策略下用户最需要知道「我的文件被改名成什么」：展示 `原 relation → 新 relation`（`conflicts` 明细），与 R4「疑似重复」是两个不同概念，不得合并成一个数。

### 3.6 R6 任务血缘（期望）

重试会创建**新任务**。详情必须能显示「重试自 xxx」，列表/详情能区分原始任务与重试任务——否则三条同名「上传导入」用户无法判断谁是谁。

### 3.7 R7 时间口径（期望）

必须区分：创建时刻、开始执行时刻（排队结束）、结束时刻，并派生「排队时长」与「执行时长」。现状只显示起止时间，长任务排队 5 分钟后用户看到「耗时 2s」会困惑。

### 3.8 R8 索引与模型（期望）

- 保留现有 `indexReadiness`（dense 就绪判据）；
- 补充 embedding 模型名与维度，并**明确标注为「当前配置」**——它不是任务执行时的配置快照（配置可能已改），不得让用户误读为"当次导入用的模型"。

### 3.9 R9 导航（建议）

scope 可点击跳转到 Browse 页该知识库。

### 3.10 R10 列表行摘要（建议）

任务列表行可显示关键结果（如「成功 10 · 跳过 2」），提升扫读效率。

## 4. 负向需求

| # | 场景 | 期望行为 |
|---|---|---|
| N1 | 台账文件超过 32KB 上限 | `readRecordFile` 超限返回 `null` ⇒ 任务从列表与详情**彻底消失**。明细必须有硬上限，且"超限后果"要有单测锁死 |
| N2 | 旧任务记录没有新字段 | 显示「—」或「未记录」，**不得**渲染 `undefined` / `0` / `NaN` |
| N3 | 台账写入失败（磁盘满 / 权限） | 不得静默：任务详情应能表达"这份数据可能不完整" |
| N4 | 明细含绝对路径 | 只允许相对路径入库（复用 `sanitizeRelPath` 口径），绝对路径一律拒绝或脱敏为 `[path]` |
| N5 | 任务已过期（>1h） | 明确提示「记录已清理」，不得显示成「任务失败」 |
| N6 | 字段缺失 vs 值为 0 | 必须可区分：`unchanged` 缺失 ≠「0 篇未变」 |
| N7 | 运行中轮询（3s） | 新字段写入不得让详情读到半截 JSON（沿用原子写） |
| N8 | group / tag 含特殊字符 | 正常转义渲染，不得破坏布局或注入 |
| N9 | 全部文件为疑似重复（`ALL_FILES_DUPLICATES`） | 必须显示为「未写入任何文件」+ 给出「仍然导入」路径，**不得**渲染成红态失败 |

## 5. 影响评估

| 受影响功能/方 | 影响类型 | 影响程度 | 证据 | 建议处理 |
|---|---|---|---|---|
| 任务列表行文案 | 展示 | 降级 | `TasksPage.tsx:449-455` 与详情共用进度文案 | 与详情同口径 |
| `TaskRecord` 落盘契约 | 数据 | 无感 | `task-registry.ts:164-178` 只校验必填字段 | 新增字段一律可选 |
| 前端类型副本 | 数据 | 无感 | `web/src/api/tasksApi.ts:28-46` 手写复制 | 同步补 |
| 三端写入点 | 数据 | 无感 | `mcp-http-api.ts:258` / `import.ts:166` / `daemon-rpc.ts:380` | 三处都写 |
| restore / rebuild 任务 | 展示 | 无感 | 复用同一 `TaskRecord` | 按 operation 分支渲染 |
| 任务文件写放大 | 性能 | 无感 | 32KB 上限 + 每 5s 整文件重写 | 明细硬上限 + 单测 |
| 既有测试 | 数据 | 无感 | `test/task-registry.test.ts` 只断言 state/error | 新增字段不破坏 |

**未发现关联方（需确认）**：无（任务台账仅被 `/api/tasks`、`/api/tasks/:id` 与前端任务页消费；`scopeImportRunning` / `activeImportCount` 只看 state/scope，不受影响）。

## 6. 验收标准

| # | 验收项 | 判定方法 |
|---|---|---|
| AC1 | 完成态详情不再显示阶段进度（`persist 1/1`），改显示文件级结果 | 导入 1 篇后详情显示「扫描 1 / 成功 1」而非「写入 100%（1/1）」 |
| AC2 | 增量导入显示「其中内容未变 N 篇」 | 同目录导两次，第二次未变数 = 文件数 |
| AC3 | 跳过数可拆出疑似重复 / 同名冲突 / 超限三类 | 造 3 类各 1 篇，三类分别计数 |
| AC4 | 参数快照三端一致 | web / CLI / daemon 各跑一次，字段一致（来源形态按入口不同） |
| AC5 | 失败任务显示可判别原因 + 页面内可执行动作 | 断网触发失败，详情给「重试 / 检查 embedding 配置」而非"查看服务日志" |
| AC6 | 疑似重复明细有硬上限，超限时台账仍可读 | 造 200 篇重复，台账文件 < 32KB 且任务可见 |
| AC7 | 重试任务显示血缘 | 点「重试未完成」后新任务详情显示「重试自 REQ 原任务」 |
| AC8 | 旧任务记录（无新字段）不出现 `undefined/0` | 手写一份旧格式 json，详情显示「—」 |
| AC9 | 排队与执行时长分开 | mock coordinator 排队 5s，详情显示「排队 5s · 执行 2s」 |

## 7. 关键假设与待确认

| # | 事项 | 影响 | 状态 |
|---|---|---|---|
| ① | 任务保留期仍为 1h，不做长期审计 | 「明天回看」仍做不到 | **需拍板** |
| ② | 疑似重复明细上限（建议 20 条） | 大库排查时可能不够 | **需拍板** |
| ③ | 用户所说「scope 名称」是否其实指 Group | 决定 R2 的字段优先级 | **需确认** |
| ④ | CLI / daemon 任务的参数快照是否一并做 | 决定"任务中心是否可信" | **需拍板** |
