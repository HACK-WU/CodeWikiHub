# 场景推演：任务详情「导入信息完备」

> 推演对象：需求文档模式（无 DESIGN.md 时的首轮推演，输入为 PM 分析报告 + 用户 8 项诉求）
> 证据性质：**推演结论（代码直读 + 逐场景语义走查，未实际执行）**

## 1. 全局理解

| 项 | 内容 |
|---|---|
| 业务目标 | 在一处回答「这次导入干了什么、成没成、哪里不对、下一步怎么办」 |
| 系统位置 | 导入/重试/还原 job → 任务台账 `.ki-tasks/*.json` → 用户决策 |
| 整体成功判据 | ① 8 项诉求全覆盖 ② 数据可回溯 ③ 三端一致 ④ 不破坏契约（1h TTL / 32KB / 5s 心跳整写）⑤ 文案不误导 |

## 2. 推演覆盖

- 角色：普通网页用户 / CLI 用户 / 排障者 / 环境角色（TTL、心跳、coordinator 队列、embedding 服务）

- 启用 profile：新增功能类 + 事务状态机类 + 批处理类

## 4. 对首轮 PM 报告的三条纠正

1. **漏掉 `/api/import/status?jobId=` 兜底路径**：web 任务 `id === jobId`，可补查完整 `result`；但内存 1h / ≤50 条 / 重启 404 / CLI-daemon 无 job ⇒ 只能当过渡，不能当终态（已在 S-02 D2-1 记录为被否决方案）。
2. **Group 不是单值**：`result.groups` 是数组。
3. **32KB 上限后果比原判断更严重**：`readRecordFile` 超限返回 `null` ⇒ 任务从列表与详情**彻底消失**（不是加载慢），明细上限必须硬编码 + 单测锁死（S-01 §3.3）。
