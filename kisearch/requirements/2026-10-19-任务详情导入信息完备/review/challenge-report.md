# 🎯 设计文档质疑报告

> 对象：REQ-20261019-004 全套设计（design-review 已通过修复后）
> 姿态：假设"已评审通过"仍有问题；以场景推演替代复现

## 📋 设计上下文确认

- **核心目标**：任务详情能回答「导入了什么 / 成没成 / 哪里不对 / 下一步怎么办」
- **衡量标准**：AC1–AC9；全局判据 ①8 项覆盖 ②可回溯 ③三端一致 ④不破坏契约 ⑤文案不误导
- **排除范围**：长期审计、任务中心信息架构重做、导入核心统计口径改动
- **隐含假设**：
  1. 失败任务的 `error` 对象携带 `stats.files`（**未验证**）
  2. `runImportJob` 的 params 写入发生在任务可见之前（**与实现不符**）
  3. `retryOf` 指向的任务在展示时仍存在（**1h TTL 后不成立**）

## ⚔️ 反对意见

### 意见 1：失败 / 取消路径拿不到文件级统计，设计假设未经验证

- **反对理由**：S-02 §3.3(1) 写「失败时 `stats.files` 可能存在于 `failure.stats`」。实测代码：`IMPORT_CANCELLED` 的 error 只有 `message`（含「已完成 N/M 个文件」）；`ALL_FILES_DUPLICATES` 只有 `code`；`VECTORIZATION_STOPPED` 的 `stats` 是 **chunk 级**（`total/succeeded/failed/notProcessed/partialCommitted`），**无 `files`**。且 `makeVectorizationStopError` 全仓无调用点（死代码），该码的实际产生路径不受该函数约束。
- **功能影响**：预期「失败任务也能看到成功多少、未完成多少」→ 实际只有一句错误文案 + 错误码，`result.files` 为空，详情结果段全 `—`。**用户最需要数字的场景恰恰没有数字。**
- **严重程度**：🔴 致命
- **替代方案**：① 不虚构数据——明确「文件级明细不可用（任务在元数据提交前中断）」，把 `error` 文案里的「已完成 N/M 个文件」作为唯一权威数字展示；② 中期再让 `checkCancelled` / 停止分支把 `files` 摘要挂到 error 上（改动在导入核心，需独立需求）。
- **验证方法**：断网触发一次失败导入，检查 `.ki-tasks/<id>.json` 是否含 `result.files`。

### 意见 2：排队期间参数快照为空（写入时机在 coordinator 回调内）

- **反对理由**：S-02 §3.2 声明「args 就绪即写」。但 web 路径的 `update({ state:'running', startedAt, params })` 位于 `coordinator.submit(...)` 的**执行回调**内，排队时不执行。用户点开「排队中」任务的详情会看到参数全 `—`，TasksPage 的 `queued` 态恰恰是最想确认「我这次用了什么策略」的时刻。
- **功能影响**：预期「排队中也能看到本次参数」→ 实际参数段全空。
- **严重程度**：🟡 重要
- **替代方案**：把 `update({ params })` 前移到 `coordinator.submit()` **之前**（args 此时已组装完成），`state/startedAt` 仍留在回调内。
- **验证方法**：mock 一个长排队（同 scope 先起一个导入），检查 queued 任务 JSON 的 `params`。

### 意见 3：`retryOf` 是死链——1h 后原任务已被清理

- **反对理由**：台账 TTL 1h（`TASK_TTL_MS`），S-03 却把 `retryOf` 渲染成任务标识；用户点击/查找时原任务很可能不存在。
- **功能影响**：预期「追溯原始任务」→ 实际显示一个查不到的 ID，且无任何提示。
- **严重程度**：🟡 重要
- **替代方案**：只显示短 ID（前 8 位）+ `title` 提示「原任务保留 1 小时，可能已清理」；不渲染为可点击链接。若将来延长 TTL 再考虑跳转。
- **验证方法**：建两个任务后手动删除前者 JSON，检查详情文案。

### 意见 4：否决 job 兜底，导致升级后首批任务体验倒退

- **反对理由**：D2-1 否决 `/api/import/status` 兜底。但**升级前创建的任务**没有 `params/result`，而它们对应的 goroutine job 往往还在内存里（1h 内）。用户升级后立刻回看刚跑完的导入，看到的是全 `—`，比升级前更差。
- **功能影响**：预期「升级后信息更全」→ 实际「升级后 1 小时内反而看不到任何结果」。
- **严重程度**：🟡 重要（可接受但需拍板）
- **替代方案**：过渡期（一个 TTL）在 `getTask` 之外可选查 job，命中则合并显示；或接受该倒退并在详情给出「旧记录，无结果摘要」提示（S-03 §5 已含后者）。
- **裁决**：**维持 D2-1**（两套真相的长期成本 > 一次性体验倒退），但必须在 S-03 明示「旧记录」原因，避免用户以为功能坏了。

### 意见 5：全局回扣——"下一步怎么办"仍缺落点

- **反对理由**：任务中心与导入页各持一半信息：任务中心有状态无明细；导入页有明细但依赖浏览器内存 state，刷新即失。当 `errorCode` 缺失时，S-03 让用户「打开导入页查看本次批次」，但导入页无法定位到历史批次。
- **功能影响**：预期「知道下一步点哪里」→ 实际被引导到一个查不到本次结果的页面。
- **严重程度**：🟡 重要（全局性问题）
- **替代方案**：动作区只给**确定可达**的入口——「重试未完成」（走清单，服务端权威）、「重新导入」（去导入页新建）；**不承诺**「在导入页查看本次结果」。已在 S-03 修正为不写该措辞。
- **验证方法**：完成一次导入 → 刷新浏览器 → 检查导入页是否还能看到上次结果。

### 意见 6：`sourceKind` 存在两份 uploads 路径常量

- **反对理由**：`task-snapshot.ts` 默认 `~/.ki/import-uploads`，`mcp-http-api.getUploadsRoot()` 另有一份。任一处调整即静默漂移，`sourceKind` 判定失效（会把 upload 误判为 external）。
- **功能影响**：预期「来源形态准确」→ 实际可能误判，进而误导「能否事后重试」。
- **严重程度**：🟢 建议
- **替代方案**：web 端显式传 `getUploadsRoot()`；CLI/daemon 用默认值（本身无暂存目录概念）。

### 意见 7：`errorCode` 白名单会静默丢弃非大写下划线码

- **反对理由**：`ERROR_CODE_RE = /^[A-Z][A-Z0-9_]{1,63}$/`。当前所有码均符合，但未来若出现 camelCase 或含 `-` 的码会被静默丢弃，UI 退化为「未知错误」，且无日志。
- **严重程度**：🟢 建议
- **替代方案**：不匹配时不写入 `errorCode`，但 `logWarn` 一次（fail-loud）。

## ✅ 认可点

1. **32KB 护栏放在 `writeRecord` 唯一入口**——避免第三处漏改，且用"任务会消失"这一真实后果作为设计依据（`readRecordFile` 返回 null），不是抽象风险。
2. **`errorCode` 并入 `result.errorCode`**——失败时即使没有结果摘要也落一个只含码的对象，避免"错误码在别处"的两套读法。
3. **抽取逻辑收敛到 `task-snapshot.ts` 单一实现**，并写明历史上 `kindForOperation` 漏标的教训——有据可依，不是教条。
4. **`unchanged` 从 `completed` 中拆出**——直接消除「改了文档没生效」的误判，这是本次最实质的用户价值之一。

## ➕ 补充场景与情况

- **同时多点重试**：两个浏览器窗口都点「重试未完成」→ 服务端 409 闸门已挡；但**任务 B 已创建后**由 409 返回，台账里会留下一个失败任务吗？（当前 `createJob` 在闸门之后，不会）
- **任务被 TTL 清理后详情仍打开**：`getTask` 返回 404，S-03 已改文案「记录已清理」，但轮询 `refetchInterval` 在 `unknown` 时 15s 继续请求，会持续 404 → 应停止轮询。
- **暗色主题下明细折叠**：`<details>` 的默认 marker 颜色在某些浏览器跟随 UA，需实测 `--ki-color-*` 下的可见性。

### 行动建议

**必须处理**
1. 失败/取消路径**不得虚构 `files`**：S-02 改为「失败时 result.files 允许缺失，由 `error` 文案承载 N/M」；S-03 结果段显示「文件级明细不可用（任务在提交前中断）」并保留 `error` 原文。—— 对应「失败任务无数字」的功能影响。

**建议处理**
2. web 路径 params 写入前移到 `coordinator.submit()` 之前（一起修 S-02 时点说明）。
3. `retryOf` 只显示短 ID + 过期提示，不渲染链接。
4. S-03 明示「旧记录，无结果摘要」的**原因**（升级前任务），避免被读成功能故障。
5. 详情 404 时停止轮询（`refetchInterval` 返回 false）。

**可选处理**
6. web 端显式传 `getUploadsRoot()`。
7. `errorCode` 白名单不匹配时 `logWarn`。
