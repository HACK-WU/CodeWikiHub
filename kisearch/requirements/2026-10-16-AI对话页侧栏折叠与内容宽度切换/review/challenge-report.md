# 二次质疑报告：对话页左栏折叠与内容宽度切换

**变更类型**：新增功能（feat）→ 采用「需求验证 / 边界验证 / 冲突验证 / 体验质量」四路 + 通用加压项（数据守恒、全局回扣、搭车变更）
**质疑总数**：12 条 → **成立 4** / 不成立 8；**阻断级 0**

## 一、成立的质疑

### Q1 🟡 中｜「铺满」在 ≤1440 分辨率下几乎无收益
- **质疑**：功能价值依赖超大屏。实测（1920）消息列 880 → 1384（+504）；而 1440 下 `main` 列仅 952 ⇒ 铺满后 928（**+48px**）。用户在 1440 笔记本上看不出差别。
- **证据**：`temp/probe-chatpage-layout.cjs` 与走查 C 段实测。
- **处置**：不阻断（功能本身正确、默认居中不改变现状）。**必须在交付说明中告知收益门槛**，避免用户"点了没变化"→ 误判功能失效。已写入 code-review §6。
- **可选增强**（未做，交用户决定）：≤1440 区间把「铺满」定义为**同时收窄左右 padding 至 12px + 放开 880**（收益约 96px），或干脆在该区间一并隐藏控件。

### Q2 🟡 中｜`--ki-chatpage-prose-max: 1100px` 未经用户确认
- **质疑**：用户在确认点只批了「方案 C（容器铺满 + 正文限宽 + 代码/表格铺满）」的**思路**，未确认具体上限值。1100px 是 AI 自行取值 ⇒ 用户看到「铺满后段落仍不到底」时可能认为实现有误。
- **证据**：`ki.css` G 段 `:root` 注释自述「约 68 个中文字」。
- **处置**：不阻断。**须显式告知该值可调**（改一个 CSS 变量）。已写入 code-review §6。

### Q3 🟡 中｜走查盲区：超宽表格从未被覆盖
- **质疑**：E 段溢出断言只查 `.ki-chat-msg__body > *`（即 `.ki-markdown` 自身），而 B 段注入的探针元素在进入 E 段前已被移除 ⇒ **宽表格（shrink-to-fit、列多时必然宽于容器）从未被真实测过**。
- **证据**：首轮 E 段脚本（无表格注入）。
- **处置**：**已修**。补 `E5`：注入 24 列宽表格 → 断言页面级不横向滚动（容器级滚动仅作记录，属既有行为、非本次引入）。复验 35/35 全绿。

### Q4 🟡 中｜折叠态左栏仍保留在 DOM 中
- **质疑**：折叠用 `0` 列 + `min-width:0` + `overflow:hidden` + `visibility:hidden`，会话列表（最多 50 条 ×2 组）仍在渲染树内 —— 是否有成本/可访问性代价？
- **证据**：`ki.css` G 段 `@media (min-width: 1024px)` 规则。
- **处置**：**不构成缺陷**。① `visibility:hidden` 元素**对辅助技术同样隐藏**，不会让屏幕阅读器读到不可见的会话列表；② 渲染成本极低（列表本就常驻）；③ **不能用 `display:none`** —— 它会让 `.ki-chatpage__main` 落到第一列 `0px` 上使对话区塌陷（走查实测 `contentW: 0`）。已在 CSS 注释中记录该围栏。
- **残留**：如未来列表规模显著增长，可考虑折叠时 `content-visibility: hidden`（本次不做）。
