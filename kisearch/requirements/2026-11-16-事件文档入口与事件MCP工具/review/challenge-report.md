## 一、反对意见（按风险）

### 🔴 R1 解绑后 `ki-path` 永不重建（新增路径稳定触发既有缺陷）

- **证据**：`planTransition`（`src/lib/visibility-index.ts:165-183`）对 `hidden → full` 只返回 `write: ['dense','fts','relation']`；`ki-path` 仅有一条摘除分支（`:351-359`，`to==='hidden'` 且组内全不可见）。仓库内无任何 `ki-path` 重建调用点。
- **后果**：某组里唯一的事件文档被解绑回 `wiki` 后，该组 path 向量永久缺失，按组路径的语义检索再也搜不到这个组；页面显示一切正常。事件流转 `hidden → full` 同样中招，但本批把「随时解绑」变成常规路径，命中率大幅上升。
- **替代方案**：`planTransition` 增加 `hidden → non-hidden` 时 `write` 含 `'path'`（组级写入幂等）；同时修解绑与流转两条路径，而不是只补解绑。
- **处置**：已写入 S-01 §3.1.2 + 决策 D19；因属"顺带修复既有缺陷"，升级为待确认项 Q3。

### 🟡 R2 摘除失败对用户不可见（"以为藏起来了，其实没藏"）

- **证据**：`applyVisibility`（`:287-345`）摘除失败时 `failed.push(kind)` + 写 `.visibility-failures.json`，返回值里 `failed` 字段**只有诊断页消费**；S-01 原设计只把 `pending` 透出。
- **后果**：向量引擎不可用/维度不匹配时，绑定到 `hidden` 阶段"成功"，文档仍可被 `ki_search` 召回，界面显示「不可检索」徽标 —— 语义与展示相反。
- **替代方案**：接口与 MCP 返回 `visibilityFailed[]`（per-item），页面在成员区顶部给警示条；AI 侧同样透出，避免向用户保证"已隐藏"。
- **处置**：已写入 S-01 §5.1 / §7 / §3.5 与 S-03 §3.2。

### 🟡 R3 绑定/解绑后事件 `updatedAt` 不变（列表不冒泡）

- **证据**：`listEvents` 按 `updatedAt` 倒序（`event-service.ts:129`）；原设计只改文档分片，未写事件文件。
- **后果**：用户刚挂完文档，事件列表位置不变，"最近动过的事件"这个隐含信息失真；多窗口场景下另一窗口看不到变化。
- **替代方案**：绑定/解绑成功后 `writeEvent({...event, updatedAt: now})`；**不动 `revision`**（`revision` 是描述编辑的乐观锁，改动会让页面正在编辑的描述变 `REVISION_CONFLICT`）。
- **处置**：已写入 S-01 §3.1。

### 🟡 R4 `event-service.ts` 体积继续膨胀

- **证据**：该文件已 ~700 行，同时承担事件状态机、终态动作、成员聚合、可见性登记；本批再增约 200 行成员绑定逻辑。
- **后果**：职责混杂使测试无法按职责切分，后续并行实现时冲突面变大（G5 风险放大）。
- **替代方案**：新增 `src/lib/events/members.ts` 承载 `MEMBER_LIMIT` / `bindMembers` / `bindMembersLocked` / `unbindMember`；`event-service.ts` 只保留 `createEvent` 改调 locked 版。
- **处置**：已写入 S-01 §8 影响范围与决策 D18。

### 🟢 R5 `consumePending` 串行 Map 需清理

- **证据**：S-01 §3.3 只写"用 in-flight Map 串行"，未写释放。
- **替代方案**：Promise `.finally(() => map.delete(scope))`，否则长期运行进程会按 scope 积累已完成 Promise（每个 scope 一条，量不大但属泄漏）。
- **处置**：实现注意项，文字已隐含在"复用 Promise"里，不单独改文档。

## 二、认可点（复核通过，不需修改）

| # | 结论 | 复核依据 |
|---|---|---|
| 1 | 冲突校验必须落服务层 | MCP 直连服务层，HTTP 层拦截会留绕过路径（`governance-http.ts` 与 `mcp-tools/*` 双入口已核实） |

## 四、全局回扣质疑

| 回扣维度 | 结论 |
|---|---|
| **目标回扣** | 业务目标一句话：让事件在页面与 AI 两侧都能被完整管理（建/删/挂/摘）。设计覆盖了三个入口缺口与 MCP 工具化，且明确不做 AI 候选参考文档，目标对齐。**但**「解绑后仍能被检索」与「挂到不可检索阶段后仍能被检索」都会直接击穿事件阶段的产品语义——R1/R2 不修则目标只达成"能挂"，没达成"挂了真的生效"。已作为必做项写入。 |
| **位置回扣** | 调用链：`页面/MCP → governance-http/mcp-tools → events(members/event-service) → relation-lifecycle → visibility-index/queue → 向量+FTS`。改动集中在成员与档位两层，未触碰导入/检索读取链；共享面（`governance-contract` 双份、`tool-permissions`、测试清单）已在父文档 G1/G2 声明。 |
| **判据回扣** | 既有整体判据复核：① 事件流转仍只由 `transitionEvent` 写状态（本批不动）② 收口/删除的终态动作不变（`applyTerminalAction` 未改）③ 只读 Token 工具面仍隔离（新工具进写块）④ 文档分类锁（`isImported`）在绑定路径上新增校验，比原来更严。四条均成立。 |
