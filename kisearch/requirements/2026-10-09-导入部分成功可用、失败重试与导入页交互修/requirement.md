# 导入部分成功可用、失败重试与导入页交互修复

> 模式：PM 需求分析（M1 需求定义 + M2 导入页两点体验）。
> **证据声明**：最高证据等级 🟢 **代码直读**（未运行实测、未构造故障注入）；体验与视觉类判定（切页后"该不该清空"、免回车后的顺滑度）为 🟡 或进待确认清单。
> 前置：仓库已登记 REQ-20260928-001《上传导入跨页面任务与暂存清理》、REQ-20260929-001《批量向量化故障止损与全局状态提示》，但**两者的需求目录均已缺失**（`req doctor` 既有漂移），内容不可读——本需求与它们的关系需按标题口径人工确认（见 §5 待确认）。

## 0. 用户诉求

| # | 原话（要点） | 类型判定 |
|---|-------------|---------|
| **R1** | 导入中 embedding 突然不可用 → 导入失败，但**已向量化成功的部分文档也一起不可用**（前端浏览不了、`ki search` 查不到）。期望：已成功的部分正常导入且可用 | 现状与产品期望相反（回滚把已成功的工作**删除**）→ 需求 + 缺陷 |
| **R2** | 失败时前端给「重试导入」按钮，**只重试失败的部分** | 新功能（断点续传/增量重试） |
| **R3** | 上传导入 tab 切走再切回，上传导入中的**数据没有清空** | 体验缺陷（边界待拍板：任务该留、暂存该清） |
| **R4** | 新建 scope **必须强制回车才生效** | 体验缺陷 + 实现与自身注释不一致 |

## 1. 现状与根因（🟢 代码直读）

### 1.1 R1 根因链：系统性向量故障 = **全批回滚 + 物理删除已完成的工作**

| 步骤 | 位置 | 行为 |
|------|------|------|
| ① 原文先落地 | `src/lib/import.ts:834-847` | 扫描结束时 flush 组级原文缓冲，`kb/<scope>/<group>/index.json` 已写入（**早于向量化**） |
| ② 向量化 | `src/lib/import.ts:865-883` | embedding 系统性不可用 → `vectorizeResult.stopReason`（`classifyVectorizationStop`） |
| ③ 全批标记失败 | `src/lib/import.ts:905-917` | `for (const rec of fileRecords) failedRecords.add(rec)` —— **整批**（对比 `:918-923` 逐文件失败只标该文件） |
| ④ 回滚 | `src/lib/import.ts:1007-1019` | 对每个失败记录：`restoreLocalKb`（`:1593-1604`，新文件 `previousText === undefined` → `removeFromLocalKb` **删掉刚写的 KB 原文**）+ `deleteVectorIds` 删除本批新写入的向量 |
| ⑤ 抛错 | `src/lib/import.ts:1038-1049` | `throw makeVectorizationStopError(...)`（`code: VECTORIZATION_STOPPED`） |
| ⑥ 元数据永不落盘 | `src/lib/import.ts:1361 / 1421-1425 / 1430` | Phase 3（Group 树）、Phase 4（relations 元数据）、Phase 5（source）**均未执行** |

**后果**：已成功向量化的文档 → 向量被删、KB 原文被删、relations 元数据从未写入 →
- `/api/doc/list`：只遍历 `readAllGroupCaches` 的 `hot_relations`（`src/lib/mcp-http-api.ts:321-363`）→ **看不到任何新文档**；
- `ki query-group`：`loadCacheShape` 无分片 → 「(暂无 Relations)」；
- `ki search`：向量已删 → **无命中**。

→ 用户描述完全成立，且**比描述更彻底**：不是"隐藏了"，是**被删除**（KB 原文与向量都不可恢复，只能重跑，而重跑要重新付 embedding 成本）。

### 1.2 两个容易混淆的相邻场景（改造时必须区分）

| 场景 | 当前行为 | 是否"能搜到但看不到" |
|------|---------|---------------------|
| **取消**（`checkCancelled`，`import.ts:884/924`） | 向量与本地 KB **保留**、元数据不写 | ✅ 正是这种"半可用"状态 |
| **逐文件失败**（`:918-923`） | 只标该文件失败，其余继续，任务 `finish('partial')`（`mcp-http-api.ts:1308-1311`） | 部分成功语义**已存在** |
| **系统性停止**（本次 R1） | **整批**失败 + 回滚删除 | ❌ 已成功部分被抹掉 |

**结论**：R1 的本质不是"从零加能力"，而是**把已有的「部分成功」语义从"单文件失败"扩展到"系统性停止"**，并让已提交部分留下可用的元数据。

### 1.3 R2 现状：失败后没有"只重试未完成部分"的入口

- 失败只在导入页错误卡显示错误原文（`web/src/pages/ImportPage.tsx:1540-1554`）；**导入阶段没有重试按钮**（只有上传阶段有 `retryUpload`，`:1030-1039`，复用同一 `uploadPlanRef` 续传 —— 可照抄的模式）。
- 失败态**不展示任何统计**（结果摘要只在 `phase==='done' && !error` 渲染，`:1578-1584`），用户不知道"成了多少、剩多少"。
- 重跑会新建 `uploadId` 并 `continueUpload(0)` **整批重传**（`:1000-1023`）。
- 后端 `/api/import/run` 立即返回 `202 + jobId`（`mcp-http-api.ts:1248`）；`/api/import/status` 失败时 **`result` 为空**，只有字符串错误（内含「成功 x，失败 y，未处理 z，补偿未完成 w」，`import.ts:1610-1613`）→ **没有结构化的"未完成清单"**，前端即便加按钮也无法据此重试子集（这是 R2 的硬依赖）。
- 任务库侧已有 `partialCommitted` + `recoveryHint`（`mcp-http-api.ts:1316-1322`；展示于 `web/src/pages/TasksPage.tsx:103,107`）。

### 1.4 R3 现状：「隐藏不卸载」的副作用（**任务该留、暂存该清，边界未定**）

- `web/src/layouts/AppShell.tsx:347-349`：`<div style={{ display: importVisible ? 'contents' : 'none' }}><ImportPage /></div>` → 路由切走时**组件常驻不卸载**，`web/src/routes.tsx` 的 `/import` 只是占位 route。
- 全部状态在组件内：`ImportPage.tsx:348-462`（`selections`/`uploadStats`/`error`/`progressText`…）+ ref `:459-462`（`uploadPlanRef`）。
- **没有任何清空逻辑**：成功/失败只重置 `scopeConfirmed`（`:615/:626`）→ 切回后旧批次的选择、上传统计、错误卡都还在。
- 挂载一次的恢复 `useEffect(..., [])`（`:479-574`）依赖 localStorage 凭据（`:881/:998/:1021`）→ 那是"刷新/重进页面续传"的**既有设计**，与 tab 切换无关。
- ⚪ 服务端暂存：`~/.ki/import-uploads/<uploadId>/`（`mcp-http-api.ts:76-78`）在 `src/` 与 `web/src/` 全仓**只有 3 处引用（路径定义与注释），无任何删除/清理调用** → 暂存目录只增不减。是否属本次范围见 §5。

### 1.5 R4 现状：文档说"回车或点确认"，实现只有回车

- `web/src/components/ScopePathSelect.tsx:4` 头部注释：「输入名称回车**（或点确认）**创建」；placeholder（`:149`）与 hint（`:222`）也只提回车。
- 实际 `confirmNewScope` **只有一个调用点**：`:164-168` 的 `Enter` 分支。界面上**没有确认按钮**，输入框也**没有 `onBlur`**。
- 输入只写父级草稿：`:155-159` → `ImportPage.tsx:356 setScopeDraft`。
- 未确认就点「开始导入」→ 被拦截 + 红字提示「「x」还没确认，请按回车确认新建的 Scope」（`ImportPage.tsx:1074-1095`）→ 用户感知为"必须强制回车"。
- 「选择已有」模式是**输入即筛选、点选生效**（`:161-162` / `:111-117`）→ 同一组件内两种模式交互模型不一致。

## 2. 现状 → 预期（R1）

```text
【现状】embedding 中途不可用
  扫描 → 原文写入 KB ✅ → 向量化：成功 30 篇 / 挂掉
        → 整批标记失败 → 回滚：删 30 篇向量 + 删 30 篇 KB 原文 → 抛错
        → 元数据(Phase4) 从未写 → 浏览/查询/检索 全空，成果不可恢复
【预期】
  扫描 → 原文写入 KB ✅ → 向量化：成功 30 篇 / 挂掉
        → ✅ 提交已完成部分：元数据 + 原文 + 向量 全部保留（可浏览、可检索、可编辑）
        → ✅ 未完成部分单独记账（哪几篇/哪个 chunk、为什么失败）
        → 任务终态标注「部分成功（30/50）」，前端给出「重试未完成 20 篇」入口
        → 重试只跑 20 篇；已成功 30 篇不重传、不重算 embedding、不被 `_1` 冲突改名
```

## 4. 负向需求（本需求真实相关）

| # | 场景 | 期望行为 |
|---|------|---------|
| N1 | **部分 chunk 成功、部分 chunk 失败**（同一文件 10 个 chunk 只成 3 个） | 不得产生"半截文档"；文件级判定：要么整篇可用（全部 chunk 成功）并标注，要么整篇进未完成清单。**判定口径需拍板** |
| N2 | 重试时 embedding 仍不可用 | 立即失败退出、不产生重复副本、未完成清单不变（幂等），并用一句话说明"上次也是这个原因" |
| N3 | 重试时源文件已被删除/改名 | 该条目进"无法重试"清单并说明原因，不阻塞其余条目 |
| N4 | 同一批重试两次 / 并发点两次 | 第二次被拒（或幂等 no-op），不产生 `_1` 副本、不重复计费 embedding |
| N5 | 部分成功后又"取消" | 已提交部分保持可用；取消只影响未完成部分 |
| N6 | 部分成功后立刻切 tab / 刷新 / 关页面 | 任务若在途则继续；重试入口在重进后仍可找到（任务中心持久化） |
| N7 | 磁盘/配额不足导致提交部分元数据失败 | 不静默：明确报"已成功 X 篇、提交失败 Y 篇"，并提供处置路径 |
| N8 | 部分成功后用户直接编辑/删除成功部分 | 与崩溃重跑/重试并发时不得互相覆盖（按 relation 粒度幂等） |

## 6. 关键假设

| ID | 假设 | 错了会怎样 | 验证方法 |
|----|------|-----------|---------|
| A1 | R1 的期望是"保留已成功部分"，而不是"整批失败也要给出可浏览的中间态但数据仍不可信" | 若用户要的是后者，R1 从"提交语义"降级为"展示语义"，工作量与风险大幅不同 | 一句确认（本报告唯一确认点） |
| A2 | 系统性停止（`VECTORIZATION_STOPPED`）是 R1 的主场景；`IMPORT_CANCELLED` 的"能搜不能看"属另一个待修不一致 | 若把两者混为一谈，会漏掉取消路径的元数据补齐 | 复现两条路径各一次（取消 / 拔掉 embedding 端点）比对现象 |
| A3 | R2 的"失败的部分"= 本次导入的未完成文件集合（不是历史所有失败） | 若用户期望跨批次累计，需要持久化台账 | 用户确认 |
| A4 | R3 的"数据"指**上传选择与统计**，不含在途任务进度 | 若指"任务也要清空"，则与跨页面任务设计冲突，需先改需求 | 用户确认 |
| A5 | R4 当前拦截是由"未确认草稿"导致（不是别的校验） | 修错地方 | 已由 `ImportPage.tsx:1074-1095` 代码直读确认为 🟢 |
