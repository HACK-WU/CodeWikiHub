## 1. 核心规则与其推论

### 1.1 可见性判定

```ts
function isViewVisible(config: KiConfig, authScopes: string[] | null, view: string): boolean {
  if (authScopes === null) return true;                       // 本机免鉴权
  if (!isScopeAuthorized(authScopes, view)) return false;     // ① 视图授权
  const members = getViewMembers(config, view);
  // ② 全部成员授权（全有或全无，不做部分可见）
  return members.every((m) => isScopeAuthorized(authScopes, m));
}
```

| 场景 | 结果 |
|---|---|
| token = `['all']` | 全部视图可见 |
| token = `['team','a','b']`，`team=[a,b]` | ✅ 可见 |
| token = `['team','a']`，`team=[a,b]` | ❌ **不可见**（缺 b） |
| token = `['a','b']`，未授权 `team` | ❌ 不可见（缺视图授权） |
| token = `['team']`，`team=[a,b]` | ❌ 不可见（缺成员授权） |

**成员不存在时的口径（补充，见 Q8）**：`getViewMembers` 返回的是配置里的字面量，成员可能尚未导入（003 D4 前向声明允许）。`isScopeAuthorized` 只判"名字在不在授权集合里"，与该 scope 是否存在无关 —— 所以公式**无需特判**：成员缺失时只有显式被授权该名字（或 `all`）的 token 可见。副作用是「含缺失成员的视图」对普通 token 基本不可见，这正是 003 D4「前向声明」在 004 下的自然结果。

### 1.2 推论一：**视图不携带任何额外权限**（本需求最有价值的性质）

要用视图读到 `b` 的内容，token **必须本来就有 `b` 的授权**（D3 ②）。

因此：

> **视图是纯便利层**——它只改变"用几个名字去检索"，不改变"能读到什么"。

这条性质取代了 `REQ-20261104-003` S-04 §3.4 的安全论证。原论证是：

```
视图仅 CLI 可改 → 改视图需要管理员权限 → 动态跟随安全
```

它依赖"页面不开编辑"这个**脆弱前提**（用户本来就计划推翻）。新论证是：

```
视图可见需要全部成员授权 → 视图永远不能成为越权通道 → 与创建入口在哪里无关
```

**结论：新规则让设计更健壮，不是加负担。** 原 §3.4 整节可以删除。

### 1.3 推论二：**给视图加成员会收缩受众**（必须显式提示的运维后果）

`team=[a,b]` 可见于 token `T1=['team','a','b']`。管理员把 `c` 加进 `team` 后：

- `T1` 缺 `c` 授权 → **整个 `team` 视图对 T1 消失**（不是少一个库，是整个视图没了）
- 表现为 Agent 突然检索失败 / Web 顶栏里视图不见了

这是"全有或全无"的必然代价，**必须在变更前给出影响面**：

```
$ ki view add team c
⚠ 该视图当前被 3 个 Token 授权，其中 2 个缺少新成员「c」的授权：
  - Token d4e5f6（团队 Agent）：变更后将无法看到该视图
  - Token g7h8i9（外部客户）：变更后将无法看到该视图
继续？[y/N]
```

页面编辑同理：提交前弹出同样的清单。（⚠ 此交互**尚未落到 §4 布局与 demo**——见 §7 Q3。若不采纳二次确认，本句改为"提交前以实时影响面面板为准"，两处口径须一致。）

### 1.4 视图名规则（D5：支持英文与中文）

**关键约束不在"能不能存"，而在"这个名字会被当成 `--scope` 的值传出去"**（003 D1：`--scope` 同时接受 scope 名与视图名）。

| 项 | 规则 | 理由 |
|---|---|---|
| 长度 | 1–40 个字符（按 Unicode 码点） | demo `maxlength=40`；保证 `--scope` 一行内可读 |
| 允许 | CJK 汉字、拉丁字母、数字、`-`、`_`、全角标点（如「·」） | 对齐项目里 **group 名**的做法——拒绝危险字符，而非白名单 ASCII（`src/lib/import-path.ts:85` 只拒绝对路径 / 反斜杠 / `..`） |
| 禁止 | 半角逗号 `,`、全角逗号「，」、空白（含首尾）、`/`、`\`、`..`、控制字符与换行 | `,` 是 `--scope a,b` 的分隔符；`/` `\` `..` 是路径语义；全角逗号一并禁，避免"看起来是分隔符但不是" |
| 保留名 | `all` / `default` / `__global__` / `__root__` | 003 R-03，`src/lib/scope-view.ts:38` |
| 唯一性 | 与 scope 名、其他视图名互斥，**大小写不敏感** | 003 R-03 共用命名空间；不敏感可避免 `--scope Team` / `team` 二义 |
| scope 侧 | **不变**，仍 `^[a-zA-Z0-9_-]+$` | 会落磁盘目录、进 shell 参数，不放宽 |
| 非 ASCII 名 | 一定是视图名 | 靠 scope 的 ASCII 约束天然区分，不需要额外标记位 |

**解析顺序（硬要求）**：`--scope <name>` **先查视图**（名字或 ID），命中即按视图展开；未命中才走 `validateScope`。顺序反过来，中文名会在 `isViewName` 之前先被 `INVALID_SCOPE` 拒掉（`src/lib/scope.ts:42`）。

**落点差异（两处不能一起放宽）**：

- `VIEW_NAME_PATTERN`（`src/lib/scope-view.ts:29`）→ 放宽到 §1.4 规则；
- `SCOPE_PATTERN`（`src/lib/scope.ts:13`）→ **不动**；
- `mcp-token.ts:96` 那份是**授权参数**的名字校验，放宽成"任意非 ASCII"会让任意中文串写进 `token.scopes`。必须改成"**已知视图名或视图 ID**"的存在性判定，而不是改正则。

### 1.5 稳定标识：ID、改名与存量迁移（D7）

003 排除改名的理由是三个断点（token 白名单 / localStorage / 深链）。**ID 方案把前两个断点永久消除**，深链的代价降级为"改名后旧链接失效"。

```jsonc
// v1（003 已上线）：按名字做键
{ "team": { "members": ["a", "b"] } }

// v2（**实现采用**：仍按名字做键，id 存在值里）
{ "团队研发": { "id": "v_09ccd52b", "members": ["a","b"],
                 "createdBy": "mCWCPcwK", "createdAt": "2026-11-05T01:58:59.186Z",
                 "updatedBy": "mCWCPcwK", "updatedAt": "2026-11-05T02:01:12.000Z",
                 "revision": 3 } }

> **方案修正（实施时定，2026-11-05）**：原设计写的是「按 ID 做键、名字只是值」，实际改成
> **按名字做键 + 值里存 `id`**。理由：
> - 按名字做键时 `readViews()` 签名不变，8 处读路径（`scope.ts`、`view.ts`、`scope-policy.ts`、
>   4 个 MCP 工具、`group.ts`）**零改动**，回归面小一个数量级；
> - 按 ID 做键要额外维护「名字 → ID」索引，`--scope <名字>` 的解析还得先查索引；
> - 改名只是一次原子写（删旧键 + 插新键，值里的 `id` 不动），不需要跨文件事务。
>
> **D7 的诉求（改名不影响 token 授权 / 前端选中态）由 `id` 不变满足，与"键是什么"无关。**
```

**迁移（幂等，加载时执行一次，写回须持 views 锁）**：

1. 旧条目无 `id` → 派生 `v_` + 名字稳定 hash 前 8 位；`name` = 原键。派生后**固化写回**，之后不再重算（否则名字改了 hash 就变）。
2. `viewGrants` / `scopes` 中出现**已知视图名** → 替换为对应 ID 并回写 `mcp-tokens.json`（该文件有锁、0600）。
3. 迁移失败（`views` 文件损坏 / token 文件不可写）→ **fail-loud 拒绝写操作**，不静默跳过（沿用 003 `VIEWS_CORRUPT` 口径）。
4. **旧视图没有 `createdAt`**（003 只存 `members`）→ **保持缺失，不伪造迁移时刻**。列表显示 `—`，`title` 说明「该视图早于创建时间记录」。编一个假时间比留空更糟——用户会把它当事实。

**改名后各位置的锚点**：

| 位置 | 用 ID 还是名字 | 说明 |
|---|---|---|
| token 授权（`viewGrants` / `scopes`） | **ID** | 改名不影响授权，无需重新签发 |
| 前端 localStorage 选中态 | **ID** | 同上 |
| 深链 `?scope=<name>` | 名字（可读），解析失败再当 ID 试 | 改名后旧链接失效 → 提示「视图可能已改名」，不静默回退 |
| CLI `--scope` | 名字为主，**ID 也接受** | 对外契约不变（003 D1） |
| 日志 / 错误文案 / `views[].view` | 名字 | 给人看 |
| chat 会话 / 导出目录 | 不涉及 | 003 已排除视图参与这两条路径 |

### 1.6 写权限矩阵（D6）

| 操作者 | 列出 / 查看 | 编辑成员 / 改名 / 删除 |
|---|---|---|
| 本机 CLI（无登录态） | 全部 | **全部**（D8：`createdBy` 记默认管理员，等价管理员） |
| 管理员（`role === 'admin'`） | 全部 | **全部** |
| 其他登录用户 | **全部**（D1 团队共享，只是不能改） | **仅自己创建的** |

- 判定：`canEditView(view, actor) = actor.isAdmin || view.createdBy === actor.id`
- `createdBy` / `updatedBy` 存 **userId**（如 `u_8f3a2c91`），**不存显示名** —— 显示名可改、账号可删
- 创建者账号被删除 → 该视图**无主**，仅管理员可改（不会死锁）
- 越权 → `403 VIEW_NOT_OWNER`，文案「仅创建者或管理员可修改该视图」
- 后端返回 `canEdit`，**前端不得自己比 id**（两处口径必然漂移）
- R-05 的"被授权该视图"判定同样按 **ID** 比对（`viewGrants` 存 ID 后，按名字比会全部落空）

> 表现是「提示行没靠到底、下面漏出半行字」（用户 2026-11-05 指出）。两层结构从根上避免这个问题。
>
> 行高：候选行 **27px**（`padding: 5px 9px` + 12px/1.4 行高、`min-height: 27px`）、**行间距 0**（靠 padding 分隔）。
> ⚠ 不要再加 padding 或 gap：项高到 32px 时文字上下各留 7px，整列看起来"一条一条隔很远"（用户 2026-11-05 两轮反馈的同一个问题）。

### 4.4 关键布局决策

| 决策 | 理由 |
|---|---|
| 候选面板走**常规流**，不用绝对定位浮层 | 浮层会盖住下方的「影响面提示」与「保存」按钮；而影响面提示正是选成员时要持续盯着的信息 |
| **影响面随选择实时重算** | 本页唯一的决策辅助：改成员前就能看到"会打挂哪些 Token" |
| 视图行常驻影响面摘要 | 藏进编辑页就没人看，改视图的风险无人预知 |
| 校验在**用户触碰后**才标红 | 刚打开表单就满屏红字过于粗暴；未动过时用中性色说明 |
| 成员 chip 分两类标记：**状态**（互斥）`缺失`（红，KB 与向量层都没有）/ `空`（**信息蓝**，库在但 0 篇）；**属性**（可叠加）`只读`（黄）/ `只全文` / `定时` | 状态互斥、属性可叠加，例：`团队研发 · 只全文 · 定时`。三者含义完全不同：`iso-scan-…`（库在、0 篇）与 `grp-dbg2`（库没了）若长得一样，用户分不清"还没导入"还是"库不可用"。**空库必须有可见底色**（`color-mix(info 14%, surface)` + 蓝字）；最初做成透明+虚线，在白卡片上几乎看不见（用户 2026-11-05：「你这空用白色，太不明显了吧」）。也不能用红/黄——那是"缺失"与"只读"的语义 |
| `只全文` = `kb && !vector`；`定时` = 数据源 `schedule.enabled`；**`定时（上次失败）`** = `schedule.lastAutoState === 'failed'` | 前者说明"语义检索不覆盖该库，关键词检索仍可用"；定时两态必须分开——只显示「定时」会让一直跑挂的源看起来仍是最新的，用户不会去查。⚠ **空库不标「只全文」**（0 篇时谈不上检索方式），**缺失不标任何属性**（库都不可用）。**判定用 `lastAutoState` 而不是 `lastSync.state`**：前者是定时跑出来的结果，后者可能是手动同步，手动失败不代表定时链路有问题。**视觉**：失败态用**警示色虚线边框 + 不填底色**——填充是「缺失」（红底）与「空」（蓝底）的表达方式，填了会抢语义；虚线一眼区分"这条链路有问题"与"这个库有问题"。且只在 chip 无主状态色时叠加 |
| **`维度不一致`**（v17 增量，方案 A）：成员 chip 追加 `· 维度不一致`，danger 色实线不填底；配色优先级 `缺失 > 维度不一致 > 空 > 只读`；hover 写「语义检索会直接跳过该库」+ `ki restore <scope> --rebuild-vector --yes`；视图行另给「N 个库的维度状态未确认」 | 维度不匹配的成员在默认 hybrid 检索里被 `onScopeError → return []` **整库跳过**（`src/lib/vector-client.ts:1077-1079`），其余库照常出结果；`src/search.ts:303-304` 注释明确「视图把跨时期导入的一批库聚在一起，其中残留旧维度是常态」。检索结果页只有**事后**的「已跳过或受限 N 项」（`SearchPage.tsx:724-728`），视图页补的是**事前**预告。**数据源只用 `.vector-status` 快照**（纯 fs 零锁，不 `withEngine`）：`getVectorDimensionStatus` 要 `ZVecOpen` 拿锁，撞锁约 15s/scope，不能进列表请求路径（项目既有决策 `mcp-server.ts:955-958`「不做 O(scope) 逐集合维度诊断」）。故口径是「**已确认清单**」：`persisted === undefined` / 快照损坏 / scope 不匹配 / 未刷新一律 `unknown`，不标、也不当成一致，必须由行内「未确认」兜底。**★ 集合维度不看 5 分钟 TTL**（`readPersistedVectorDimension`）：它是结构性事实，只有重建 / 重导才会变，而这些路径都会刷新快照；二次质疑实测本机 178 份快照全部过期（含真实 `persisted=4096 / configured=1024`），若沿用 `readVectorDimensionSnapshot` 的 TTL 判定会让标记**一个都不出现**。配置维度仍活读比较，改配置后结论跟着变；顶栏 banner / 总览面板的 TTL 语义不受影响。代价是集合被外部手段重建却没刷新快照时可能误报，按 fail-loud 取舍并在 hover 写明「依据上次维度检查，若已重建请重新检查」。**复检补两条护栏**：① `refreshVectorDimensionSnapshot` 的失败分支必须**保留上次 `persisted`**（否则一次锁冲突 / embedding 超时写「无 persisted」快照覆盖旧值，已确认的 mismatch 会静默消失；`state` 仍 unknown，顶栏/总览语义不变）；② `persisted` 只收**正整数**，防损坏/伪造值被当成 mismatch。**★ 三态必须逐个上屏**：用户反馈「只给行级『N 个未确认』看不出是哪个 scope」——后端本就能区分 `ok` / `unknown`，是前端把两者都渲染成无标记。故 `unknown` 也要在**每个成员 chip** 上追加 `· 维度未确认`（`ok` 保持无标记，避免全屏噪音），配最低优先级的中性虚线色（仅无主状态色、无定时失败虚线时叠加）；行级提示由纯数字改为列出前 3 个 scope 名 + `title` 全量名单，编辑表单已选 chip 同步。⚠ 与 `· 只全文` 区分：后者「语义不覆盖但关键词可用」（设计如此），前者「整库 0 命中」（异常、需重建） |
| 入口做成**侧边栏独立页**而非个人中心区块 | 视图是跨 scope 的读侧聚合，属于"工作空间"一级导航而非账号设置；放个人中心等于把全局能力藏进设置页 |
| 页面自身**不画标题栏** | 顶栏（折叠按钮 + 页面标题 + scope 选择器 + 服务徽标）由 `AppShell` 统一渲染，自画会与全局动作重复并错位 |
| 无权限时按钮**禁用**而非隐藏 | 隐藏会让人以为视图不见了/坏了；禁用 + `title` 能同时表达"它存在"与"你没权限" |
| 图标用 **`layers`（三层叠片）**，不用 `folder` | 视图是"多个库叠成一个入口"，不是目录；文件夹会暗示点开是目录树，与实际行为不符 |

**★ 面板收起的点击时序（本次走查发现，已修；其它页面同样适用）**

候选面板改走常规流（§4.4 的决策）后，收起会**改变布局高度**。于是两个坑必须同时避开：

- **不能在 `pointerdown` / `mousedown` 当场收起** —— 按钮会在 `mouseup` 之前移位，`click` 丢失，表现为「点保存没反应，要再点一次」；
- **不能在 `click` 里用 `picker.contains(e.target)` 判断** —— 点候选项 / chip 会整块重建 `innerHTML`，`click` 冒泡到 document 时 `target` 已脱离文档，`contains` 恒为 false，表现为「刚选中一项，列表就自己关了」。

demo 的解法：`pointerdown`（早于重建）只记录 `inside` 标志，到 `click`（最后一个事件）阶段再决定收起。任何"常规流下拉 + 下方有按钮"的组合都要注意这个时序。

```
