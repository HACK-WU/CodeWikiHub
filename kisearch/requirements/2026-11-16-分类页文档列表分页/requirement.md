# 需求：分类页文档列表分页

> 归属：知识治理（REQ-20261113-004）S-07 分类页增强。页面 `/governance/lifecycle`（侧栏「知识治理 → 分类」）。

## 1. 问题

分类页表格**一次渲染全部分档文档**，无任何翻页入口：

- 前端固定 `limit: 200`（`web/src/pages/LifecyclePage.tsx`），后端返回的 `total` 被直接丢弃 ⇒ 144 篇的库一次铺 144 行；超过 200 篇的部分**静默消失且无提示**。
- 后端 `/api/governance/docs` 早已支持 `limit`(1~200) / `offset` 并返回过滤后全量 `total`，前端 API 客户端也透传 `offset`，**能力现成、只是没用**。
- 实测规模：kisearch 162 / kisearch-memory 144 / kisearch-xperts 82 / default 16 篇，最大者已达后端上限的 81%。

## 2. 关键约束：筛选 / 计数 / 排序都在前端

分类页有三处依赖「已取回的全量列表」，且都在客户端计算：

| 依赖 | 位置 | 若改服务端分页会怎样 |
|---|---|---|
| 分类筛选（全部 / 事件 / 临时 / wiki） | `visible` useMemo | 只能筛当前页 ⇒ 显示「事件 0」但翻页后冒出事件文档 |
| 各档计数 | `counts` useMemo | 只统计当前页 ⇒ 与服务端 badge 口径打架 |
| 按剩余天数排序 | `visible` useMemo | 只在当前页内排序 ⇒ 全局最紧急的不在第一页 |

⇒ **采用客户端分页**（筛选 → 排序 → 切页），后端不改。

## 3. 已拍板决策（2026-11-16 用户确认）

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| Q1 | 每页条数 | 默认 **20**，可选 20 / 50 / 100 | 表格行高约 34px，10 行/页太碎（144 篇要翻 15 页）；数据源/任务页默认 10 是卡片行高不同 |
| Q2 | 「全选」语义 | **当前页** | 与表头 checkbox 紧邻，表格惯例一致；跨页全选靠「筛选结果」已经在语义上覆盖 |
| Q3 | 跨页已选 | **保留**，批量条显示跨页总数 | 已有 `Set` 天然跨页；清空会让分批挑选失效 |
| Q4 | >200 篇兜底 | **显式提示**（不改上限） | 成本最低、符合 fail-loud；真需要时再走服务端分页 |
| Q5 | 范围 | **只做分类页** | 事件页 / 回收站页行模型不同，混改风险高 |
| Q6 | 方案 | **客户端分页**（A） | 见 §2 |

## 5. 负向需求

| 类别 | 场景 | 处置 |
|---|---|---|
| 误操作 | 跨页已选 8 篇，当前页只看到 3 篇就点批量改 | 批量条显式标「含其他页 M 篇」 |
| 误操作 | 改每页条数后停在旧页码 | 改条数一律回第 1 页 |
| 参数错误 | 非法 limit / offset | 后端已 clamp（1~200 / ≥0），前端只出白名单选项 |
| 中途放弃 | 改分类弹窗打开时翻页 | 弹窗目标固定在 `editing` 快照，翻页不影响 |
| 状态异常 | 筛选后结果变少、旧页码超界 | 页码收敛 + `currentPage` 收敛帧保护 |
| 状态异常 | 已选文档被别处删除 / 移组 | 批量提交由后端 `failed[]` 汇总提示（现状已覆盖） |
| 权限 | 只读账号 | 翻页 / 勾选 / 改每页条数可用；批量与「改」保持禁用（现状） |
| 数据异常 | 切换 scope | 页码与已选一并重置 |

**实施期新增决策（用户确认范围的细化，未改变已拍板项）**

- **切换分类筛选时清空已选**：筛选是换视角（wiki / 临时 / 事件互斥），保留上一视角的勾选会变成「已选 N 篇，当前页 0 篇」的闷改入口；搜索本来就因重新请求而清空，排序只改顺序故不清空。跨页分批挑选（翻页）**不受影响**，符合 Q3。
