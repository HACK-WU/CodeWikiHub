# 🎯 设计文档质疑报告：重复导入可跳过疑似重复文档

> 对象：`design/DESIGN.md` + S-01/S-02/S-03（design-review 第 2 轮"有条件通过"后）
> 时间：2026-10-19
> 方法：设计文档模式（阶段 0~7），以场景推演替代复现；交叉核对真实代码

---

## 📋 设计上下文确认

- **核心目标**：预检命中"内容一致但来源不同"时，允许"跳过这些、其余照常导入"，且跳过项零写入、无不可逆意外副本。
- **衡量标准**：AC1~AC16（其中 AC15 要求"全部重复被拦截时用户仍可继续"）。
- **覆盖范围**：Web 导入页 → `/api/import/run` → `handleDirectImport` → 结果回传。
- **排除范围**：CLI / MCP 参数、逐篇勾选、判据调整、跳过决策持久化。
- **隐含假设**：
  1. 轮询能拿到 `job.errorCode`（已在 design-review 补）；
  2. **被拦截后 `uploadPlanRef` 仍在**（❓ 本次质疑推翻）；
  3. 判定成本可忽略（❓ 未实测）。

## ⚔️ 反对意见

### 意见 1：前端终态清理会清掉 plan 与凭据，"被拦截后仍可继续"依旧不可达

- **反对理由**：`ALL_FILES_DUPLICATES` 走的是 job `failed` 分支，而 `ImportResult.partial` 只按 `failedRecords.size > 0` 判定（`import.ts:1870`）——跳过场景根本没进循环，`partial=false`。前端终态清理对 `partial=false` 的处理是**清空 `uploadPlanRef` 并删除本地凭据**（`ImportPage.tsx:566-568`）。因此 S-03 用 `preflightSnapshotRef` 恢复了面板，但面板上的「仍然导入」调 `confirmDuplicateImport` 时 `uploadPlanRef.current` 已为 `null`，命中兜底分支（`ImportPage.tsx:1191-1197`）→ 用户只能重新上传整批。
- **功能影响**：预期「跳过重复文档」→ 全部重复 → 提示后点「仍然导入」即可建副本 → 实际：提示后点「仍然导入」无响应/被提示"需重新选择文件"，用户被迫重传整批（大目录需数分钟）。**AC15 仍不成立**。
- **严重程度**：🔴 致命（design-review 只修了"面板数据"，没修"plan 与凭据的生命周期"）
- **替代方案**：终态清理判据加入错码白名单——`job.errorCode === 'ALL_FILES_DUPLICATES'` 时按"待处置结果"处理（保留 `uploadPlanRef`、保留凭据、`phase` 回 `awaiting-confirm`），与 `partial` 同款路径。
- **验证方法**：构造全重复批次 → 点跳过 → 断言 `uploadPlanRef.current !== null`、localStorage 凭据仍在、点「仍然导入」后成功起 job。

### 意见 2：AC3 与 D4 的适用场景不匹配

- **反对理由**：S-01 D4 声称"job 终态 + 参数不同 → 新建 job"，但该分支只有在**用户还能发起第 2 次请求**时才可达。跳过**成功**时（有文件被导入），前端正常收尾会清 plan/凭据、面板消失，用户无法"同 uploadId 再点仍然导入"；`/api/import/run` 的幂等复用分支仍会返回旧 jobId。故 D4 实际只服务"被拦截后改选"这一个场景。
- **功能影响**：预期按 AC3 验证"跳过后可补导副本" → 实际该路径不存在，验收会失败或被迫改成"重新上传"。
- **严重程度**：🟡 重要（需求/设计表述不一致，非功能缺陷）
- **替代方案**：AC3 改写为两条——① 被拦截后可改选「仍然导入」（同 uploadId）；② **跳过后补导副本需重新上传**（本期接受，文案明示）。
- **验证方法**：跳过成功批次结束后，`uploadPlanRef.current === null` 即证明。

### 意见 3：性能数字是"假精确"，且缺降级路径

- **反对理由**：DESIGN §4 风险 7 写"万篇库约数十~数百 ms"，但该判定要 ① 遍历全部 Group 的 local KB 并逐篇 sha256（万篇 × ~20KB ≈ 200MB 读盘 + 哈希），② 再读本批文件（预检已读过一次）。量级更可能是**秒级**，尤其冷缓存或机械盘。设计既未给实测，也未给"超阈值降级"。
- **功能影响**：预期点「跳过重复文档」后 1 秒内开始导入 → 实际可能出现数秒无反馈的"启动导入…"（大库），用户以为卡死；极端情况下前端已有 30s 级等待。
- **严重程度**：🟡 重要
- **替代方案**：① 把数字标注为 `[需实测]`，实施前用隔离实例量一次（万篇量级构造）；② 增加降级：判定期间 `progressText` 显示"正在比对库内文档…"；③ 若实测 >5s，考虑"库内文档数超阈值（如 5 万）时退化为仅按 relation 名判定"或加一次性索引缓存。
- **验证方法**：`temp/probe-duplicate-hits-cost.ts` 构造 1 万篇 local KB，量 `collectDuplicateHits` 耗时。

### 意见 4：任务中心会留下一条 `failed` 任务，与页面"可纠正提示"口径冲突

- **反对理由**：`runImportJob` 的 catch 对 `ALL_FILES_DUPLICATES` 走 `job.state='failed'` + `taskReporter.finish('failed', ...)`（`mcp-http-api.ts:1916-1926`）。S-03 只规定**页面**不显示红态，但任务中心/任务列表读的是任务台账，仍会显示"导入失败"。
- **功能影响**：预期用户看到"全部重复，请改用仍然导入" → 实际任务中心同时记录一条失败任务，用户下次翻任务列表会以为系统出错。
- **严重程度**：🟡 重要
- **替代方案**：台账 `error` 文案改为引导性文案（"本批全部为疑似重复，未写入任何文件"），并在任务详情标注"未写入 / 可重试"；或为该错码单独映射一个非失败态（需评估任务状态枚举的兼容成本）。
- **验证方法**：触发全重复拦截后查任务中心条目状态与文案。

## ✅ 认可点

- S-02 补的**恒等式证明表**直接堵住了"`skipped` 重复加一次 dup"的实现陷阱，这是设计文档里少见的强约束。
- B1"只在 `skipDuplicates` 为真时替换 `budgetFiles`"的写法保住了 AC8，没有顺手改掉 `onlyRelPaths` 的既有预算口径。
- 抽 `duplicate-index.ts` 破环的选择正确：`import-preflight.ts` 已 import `import.ts`，反向引用必然成环。
- 三态复用分流（相同/运行中不同/终态不同）比"一律 409"和"一律新建"都更贴用户实际路径。

### 已核验**不成立**的质疑（避免后续重复讨论）

| 质疑 | 结论 | 依据 |
|---|---|---|
| `partial` 会因跳过变成"部分成功" | ❌ 不成立 | `partial = failedRecords.size > 0`（`import.ts:1870`），跳过不进 `failedRecords` |
| 跳过项会进 `incomplete` 清单 | ❌ 不成立 | `incomplete` 由 `failedRecords` 派生；跳过在循环前剔除 |
| 两个标签页并发会起两个 job | ❌ 不成立 | Node 单线程 + `rejectIfImportBusy` 同步判据，请求处理段无 await 交错 |
| 方案偏离"取消部分重复"的原始诉求 | ❌ 不成立（已知取舍） | 用户 Q1 明确只做"跳过全部重复" |

## ➕ 补充场景与情况

1. **被拦截后用户离开页面再回来**：plan 已清、凭据已清，面板不会恢复——需确认这是可接受行为（建议文案提示"重新上传后可改选仍然导入"）。
2. **同一条目在预检命中但 run 时库已被别的会话删除**：本次会正常导入（不跳过）。结果区显示的跳过数会小于面板，属设计已声明（以 run 为准），但**用户可能质疑数字对不上**，建议结果区加一句"以本次实际判定为准"。
3. **`existingSourcePath` 为空的历史文档**（手工 sync-relation 写入）：会被判为重复。若这类文档恰好与新导入内容一致，跳过是正确行为，但明细里"来源未记录"可能让用户困惑——沿用预检既有展示口径。

## 📊 风险评估与建议

### 🎯 裁决结论

**⚠️ 修改 🔴 意见 1 + 🟡 意见 2/3 后进入开发**；意见 4 建议同步处理（成本低）。

### 识别的风险

- **风险 1**：被拦截后无法改选，用户被迫重传整批 — 可能性**高**（全重复是常见场景：重复导入同一目录） — 功能影响：预期一键改选 → 实际重传数分钟
- **风险 2**：大库跳过判定无反馈 — 可能性**中** — 功能影响：预期秒级启动 → 实际数秒"卡住"，可能触发用户重复点击
- **风险 3**：任务中心留失败记录 — 可能性**高** — 功能影响：预期"可纠正提示" → 实际台账多一条"导入失败"

### 风险等级

- **总体风险**：🔴 高风险（1 条致命）
- **风险分布**：🔴 1 / 🟡 3 / 🟢 0

### 行动建议

#### 必须处理
1. 终态清理判据加入 `ALL_FILES_DUPLICATES`，保留 `uploadPlanRef` 与凭据、`phase` 回 `awaiting-confirm` — 否则 AC15 不成立，用户被迫重传（意见 1）

#### 建议处理
1. 改写需求 AC3 与 S-01 D4 的适用场景表述（意见 2）— 否则验收会验一个不存在的路径
2. 性能数字标 `[需实测]` + 判定期进度文案 + 超阈值降级预案（意见 3）— 避免大库"卡住"观感
3. `ALL_FILES_DUPLICATES` 的任务台账文案改为引导性表述（意见 4）— 避免任务中心与页面口径冲突

#### 可选处理
1. 结果区补一句"跳过数以本次实际判定为准" — 降低"数字对不上"的疑问
