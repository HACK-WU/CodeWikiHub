# 场景推演结果：AI 对话思考级别可配置

> 推演时间：2026-10-16 · 推演对象：**设计文档模式**（输入：`design/DESIGN.md` + `requirement.md`）
> 证据性质：**推演结论（基于文档推理，未实际执行）** —— 需要执行性证据的部分见文末"下一步建议"

## 1. 全局理解声明 + 角色清单

### 1.1 全局理解声明

| 理解项 | 内容 |
|--------|------|
| **业务目标** | 让 AI 对话的思考档位**可控且不绑定厂商**：运维定义清单与默认档、用户按清单选择、都不配则行为与现状**逐字节一致** |
| **系统位置** | 上游＝运维的 `config.yaml` + 用户的配置面板；本功能＝档位装配与下发；下游＝上游模型 API 与既有 `reasoning` 展示链路 |
| **整体成功判据** | ① 未配置时请求体不变；② 面板显示与实际下发一致（含"脱离清单"可见）；③ 非法值不到达上游（**唯一例外**＝用户拍板的"照发既有值"）；④ 用户在任何状态下都**不被卡死**（能保存、能恢复默认） |

### 1.2 角色清单

| # | 角色 | 类型 | 权限层级 | 职责 | 来源 |
|---|------|------|---------|------|------|
| 1 | 运维 / 部署者 | 用户 | 文件系统（可改 `config.yaml`） | 定义清单与默认档 | DESIGN §2 |
| 2 | 对话使用者 | 用户 | 已登录（可写全局对话配置） | 选择档位、保存、发起提问 | DESIGN §4.5 |
| 3 | 上游模型 API | 外部系统 | — | 按档位返回 `reasoning_content`（或对未知字段 400） | DESIGN §8.3 |
| 4 | 配置文件（`config.yaml` / `prompt-config.json`） | 环境角色 | — | 会被手工改坏、会被并发覆盖 | DESIGN §9 |

## 3. 场景推演详情

### S1 首次配置 → 选择 max → 提问

```text
{运维写 reasoningEfforts:[low,high,max] + reasoningEffort:high} ✅ 校验通过
  ▼
{用户开面板} ✅ GET 返回 options/default/effort/overridden
  ▼
{选 max → 保存} ✅ PUT 通过（max ∈ 清单）→ 原子落盘
  ▼
{提问} ✅ resolveRuntime → body.reasoning_effort = "max"
  ▼
{上游返回 reasoning 流} ✅
  └─ ⚠️ 面板"跟随模型默认"哨兵与清单元素可能撞名 ← ❌ 问题 1
```

### S2 运维改小清单 → 用户保存其它字段

```text
{运维把清单改成 [low]（默认档仍是 high）}
  ├─ {ki 命令} ❌ 跨字段校验失败 → 全部命令不可用 ← ❌ 问题 2
  └─ {运维同步改/删默认档后}
        ▼
     {用户只改 skill → 保存} ✅ 既有值 max 放行（决策 6/7 生效，不死锁）
        ▼
     {面板} ✅ 显示"当前值不在可选清单内" + 恢复默认可用
        ▼
     {提问} ✅ 仍按 max 发送（符合用户拍板的"照发"）
```

### S3 上游 400（换模型/网关）

```text
{提问 → body 带 reasoning_effort} ▼ {上游 400}
  ├─ 错误文案仅含 "reasoning_effort" ✅ → mapUpstreamError 追加指引（§4.7）
  └─ ⚠️ 错误文案同时含 "tools"/"function" 字样 → looksLikeToolsUnsupported 误判为"工具不支持"
        → 走降级路径（去掉 tools）→ 仍带档位 → 再 400 → 文案指向错误方向 ← ❌ 问题 3
```

### S4 手工改坏 `prompt-config.json`

```text
{json 里 reasoningEffort = ""（非法）} ▼ {打开面板}
  ✅ 只忽略该字段 + issue 透出；提示词/skill/工具开关照常显示（决策 7 生效）
  ✅ 用户保存后磁盘上的非法值被清除（自愈）
```

### S5 全未配置（回归基线）· S6 旧 daemon + 新前端 · S7 运行中改坏配置 · S8 并发保存

| 场景 | 推演结果 |
|------|---------|
| S5 全未配置 | ✅ `resolveRuntime` 得 `undefined` → **键不出现**（有测试锁）；面板禁用并指引 |
| S6 旧 daemon + 新前端 | ✅ 新字段缺失 → 按"未配置"渲染 + "可能未重启"提示；PUT 的未知键被旧 normalize 忽略（不 400） |
| S7 运行中改坏 `config.yaml` | ✅ last-known-good + `/healthz` 暴露，已有对话不受影响（§11 已写） |
| S8 两标签页并发保存 | ✅ 沿用既有"整体替换 + 后写覆盖"（N9 已声明）；⚠️ 旧草稿保存会回滚对方刚存的档位 —— **既有语义，非本设计引入**（🟢 可选增强：保存前提示"配置已在别处变更"） |

**数据走向验证（新增字段双向贯通）**：`llm.reasoningEfforts`（运维→schema→GET→面板）与 `prompt-config.reasoningEffort`（面板→PUT→磁盘→读取→请求体）**两向贯通、无死字段**；异常归宿明确（PUT 400 不落盘 / 上游 400 可见 / 读取非法仅忽略该字段）。

## 4. 问题汇总

| # | 类型 | 角色 | 场景 | 问题描述 | 功能影响（预期 → 实际） | 建议 | 严重度 |
|---|------|------|------|---------|------------------------|------|:------:|
| 1 | 流程缺陷 | 使用者 | S1 | **哨兵值与清单元素可能撞名**：本地点"跟随模型默认"用的是字符串 `'default'`；若运维把 `default` 作为**真实档位**写进清单，`buildEffortOptions` 的"同值去重"会让用户选中它时变成"不下发"，而用户以为在发 `default` | 预期"选择即发送该值" → 实际"选了 default 却不发送"，且**完全不可观测**（上游不报错） | 哨兵改为**不可能与真实档位撞名的内部值**（如 `__follow_default__`），或改变量语义：清单元素一律原样透传，哨兵只做 UI 层映射 | 🟡 |
| 2 | 流程缺陷 | 运维 | S2 | **"默认档 ∉ 清单"的 fail-loud 粒度过粗**：运维只想缩小清单时，若忘记同步改默认档，会导致 `ki` **全部命令不可用**（含排障入口），设计 §11 未点明这一后果，错误文案也未给"同步改默认档 / 删除默认档"的出路 | 预期"一处配置错误只影响该功能" → 实际"整个 CLI 不可用，运维需自己猜出根因" | ① §11 明确该后果；② 跨字段校验的错误文案直接给两条出路（同步修改 / 删除 `llm.reasoningEffort`）；③ 保持 fail-loud 不变（符合 R5 与用户哲学） | 🟡 |
| 3 | 遗漏场景 | 使用者 | S3 | **400 文案可能被误判为"工具不支持"**：`looksLikeToolsUnsupported` 只看 body 是否含 tool/function 关键词；某些网关的 400 会把 `reasoning_effort` 与 `tools` 一并列出（如 `unknown parameters: tools, reasoning_effort`），触发既有降级分支 → 去掉 tools 重试仍带档位 → 再失败，错误指向错误方向 | 预期"用户按提示清掉档位即恢复" → 实际"用户看到『上游不支持 function calling』，按提示操作无效" | §4.7 补一句：该错误识别需先排除档位相关关键词（或降级前先剔除 `reasoning_effort` 重试一次）；§13 补对应用例 | 🟡（置信度中） |

统计：🔴 阻断 **0** 个 / 🟡 警告 **3** 个 / 🟢 建议 **1** 个（S8 的可选增强）
