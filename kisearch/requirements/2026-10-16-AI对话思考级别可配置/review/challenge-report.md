## ⚔️ 反对意见

### 意见1：多轮工具调用下延迟与成本成倍放大，报告只交了"单轮"数据

- **反对理由**：工具轮次上限已取消（`DEFAULT_MAX_TOOL_ROUNDS = Number.POSITIVE_INFINITY`，`llm-client.ts:67`），一次提问会以 `while(true)` 反复发起上游请求（`tool-loop.ts:585`），**每一轮都携带同一档位**。报告 §2.3 的延迟表（`max` 档正文首字 12.9–16.8s、总时长 13.6–17.8s）是**单轮**数据；§3.0 影响面也没有"成本/计费"这一行。
- **功能影响**：预期「选 `max` 得到更深的思考」→ 实际「多轮检索场景下单次提问的总等待被 ×轮次（3 轮即 40–50s 量级），上游计费同步上升」，用户完全无从预期。
- **严重程度**：🟡 重要
- **替代方案**：① 面板文案写明"思考更深 = 更慢更贵，多轮检索会叠加"；② 验收项补一条"多轮工具调用场景实测一次总时长与 usage"。
- **验证方法**：用真实上游发起一次会产生 2–3 轮工具调用的提问，记录总时长与 `usage.completion_tokens_details.reasoning_tokens`。

### 意见2：D4「压缩摘要不继承」语义未定死（三种可能，报告只写了否定）

- **反对理由**：报告 D4 推荐"不继承"，但**没有说明压缩时到底发什么** —— ① 完全不传该字段（= 现状）② 传 `config.yaml` 的部署默认档 ③ 继承用户覆盖值。`compaction.ts:85-96` 有独立参数块（读 `cfg.llm`，**不读**对话配置），所以三种都能实现。
- **功能影响**：预期「压缩不受用户档位影响」→ 实际「实现者顺手把部署默认档带上，用户即使没配也变慢；或漏改导致意外继承」——行为二义，测试也无法写断言。
- **严重程度**：🟡 重要
- **替代方案**：D4 写明 **"不继承 = 该请求完全不携带该字段"**（保持现状，最小惊讶）；若将来要为压缩单独定档，另开需求。
- **验证方法**：实现后断言压缩请求体不含 `reasoning_effort`。

### 意见3：新增配置项的「贯通链路」未逐跳交代（三值来源不清）

- **反对理由**：本需求新增 1–3 个配置元素（可选清单、部署默认档、用户覆盖值）。报告给了装配点（`resolveRuntime`）与面板落点，但没有逐跳链路：**谁生产、落哪里、谁读、从哪个接口下发、面板三态（未配置 / 默认 / 自定义）各读哪个字段**。现有下发通道有两条（`GET /api/chat/config` 侧 `contextCharsDefault`、`GET /api/chat/prompt-config` 侧 `limits` + `defaults`），`PromptConfigLayer` 用的是后者（`chat-routes.ts:578-613`）。
- **功能影响**：预期「面板严格按 `config.yaml` 清单显示」→ 实际「清单走 A 接口、默认值走 B 接口，前端任一处拼接出错就静默渲染成空下拉/错误默认态」，且旧版 daemon 组合下的降级提示也会缺依据。
- **严重程度**：🟡 重要
- **替代方案**：设计文档必须给出「字段贯通表」：字段 → 生产方 → 存储 → 读取点 → 下发接口 → 消费方（面板/请求体），并明确"清单未配置"在接口里的表达（`undefined` vs `[]`，两者语义不同）。
- **验证方法**：实现后逐跳核对；旧 daemon + 新前端组合手测。

### 意见4：前端与服务端**双白名单拷贝**会静默清掉用户档位（项目已踩过两次）

- **反对理由**：
  - 前端 `PromptConfigLayer.tsx:61-72` 的 `cloneConfig` 是**白名单式拷贝**，其注释已记录该坑：「漏掉它会让草稿静默丢掉用户覆盖值（表现为『改了 skill 保存一下，上下文上限就被清回默认了』）」；
  - 服务端 `normalizePromptConfig`（`prompt-config.ts:302-467`）同为白名单，**未识别键静默忽略**，而 `savePromptConfig` 用归一化结果**整体覆写**文件 → 新字段若未加入归一化，保存一次别的配置即被抹掉。
- **功能影响**：预期「档位改完保存生效」→ 实际「漏改任一处，用户保存 skill 时档位被静默清除；或档位保存后无声消失」，无任何报错。
- **严重程度**：🟡 重要（不致命但极难发现；项目在 `contextChars` 与工具预算上已各踩一次）
- **替代方案**：设计阶段把这两处列为**必改点**，并在验收里加端到端回归：「改档位 → 改 skill → 保存 → 两者都在」。
- **验证方法**：新增回归用例 + 手测一次。

### 意见5：统计措辞过强，且未标注样本污染（并发取样 / 撞顶）

- **反对理由**：报告用**"无显著差异"**（统计术语）描述 n=8 的中位数比较，未做任何检验；第四轮样本中 `baseline` 有 1 次、`max` 有 2 次撞到 `max_tokens=4096` 上限（**均值被低估，`max` 的真实差异只会更大**，但表格未标注"撞顶"含义）；第五轮 9 个请求**并发**下发，延迟值含上游排队干扰，不能当纯时延基准。
- **功能影响**：预期「证据可信、结论可复用」→ 实际「设计/文案可能把『默认 ≈ high』当成已验证事实写进产品说明，或以单次观测做验收」。
- **严重程度**：🟡 重要
- **替代方案**：① 措辞降级为"中位数接近（差约 5.6%），n=8 不足以称统计无差异"；② 表格加"4096 = 撞顶"标注；③ 延迟表注明"并发取样，仅反映相对趋势"。
- **验证方法**：串行重测，或把样本量提到每档 ≥20 次再做中位数比较。

### 意见6：N3（覆盖值不在清单内）只写"需定死"，未给推荐策略

- **反对理由**：这是**用户可见行为**（运维事后改清单），报告把它整体推给设计阶段，但设计阶段若无人拍板，最可能的默认实现就是"静默回退"或"照发"。
- **功能影响**：预期「配置变动可控可解释」→ 实际「上游对任意值都返回 200（本次实测），静默回退与静默照发**都不会有任何报错**」——用户看到的现象与配置不符却查不出原因。
- **严重程度**：🟡 重要
- **替代方案**：推荐「**请求仍按用户已存值下发**（不静默篡改用户选择）+ 面板明示『当前值不在可选清单内』+ 一键恢复默认」；若选"回退部署默认"，也必须**可见提示**。
- **验证方法**：改清单后打开面板 + 发一次提问，检查请求体与 UI 文案。

## ✅ 认可点

1. **实测先行**：把"上游不校验取值"（`medium`/`ultra` 均 200）作为白名单设计的硬依据，避免了"靠上游报错发现拼错"的错误假设 —— 这是本报告最有价值的一条。
2. **风险前置排除**：首字超时不会被高档位误伤（首块 0.3–0.4s 实测）；思考内容不入 `messages`（N12）⇒ 与 `contextChars` 无耦合，报告未把两件事混为一谈。
3. **成本评估务实**：与 `contextChars` 三级链同构、装配点仅一处、无数据迁移，且明确指出压缩摘要路径的存在（而非遗漏）。
4. **负向需求覆盖到位**：空清单 / 单档 / 类型错 / 撤销确认 / 并发覆盖 / 未保存离开等边界均已列出。
5. **不做内置取值表**的取舍明确（换来"换上游即失效"的反面代价也写清了）。

## ➕ 补充场景与情况

1. **用户自助维护清单的期望**：需求 2 说"可选项必须在 `config.yaml` 配置"，但**界面里没有维护清单的入口**（面板只选值）。需在文案里说明"档位集合由运维配置文件定义"，否则用户会找"添加档位"按钮。
2. **档位与思考展示的联动**：上游不返回 `reasoning_content` 时按普通流处理（`llm-client.ts:9`）⇒ 低档或该上游不返回时，用户看不到思考块，**不要**在文案里承诺"一定能看到思考过程"。
3. **成本可见性（可选增强）**：面板已有 usage 显示（含 `reasoningTokens`），可在思考块标注"思考 N tokens"，让档位效果对用户可感（与 R6 诚实性文案互补）。
4. **多标签页/多用户语义**：档位与其他对话配置同为全局（`PromptConfigLayer` footer 声明"作用域：全局"），沿用即可 —— 报告已按此口径，无异议。
