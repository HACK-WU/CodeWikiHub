## 0. 关键结论（先读这一段）

### 0.1 不是从零做：文档内**高亮内核已存在**，缺的是「用户入口 + 上一个 + 快捷键」

- 已实现（🟢 代码直读 + 真机实测）：`applyDocumentHighlights` / `clearDocumentHighlights` / `focusDocumentHighlight`（`ModuleDrawer.tsx:86-148`）、命中计数与索引（`highlightCount/highlightIndex`）、`<mark class="ki-doc-highlight">` 样式（`ki.css:1893-1903`）、命中导航条（`ModuleDrawer.tsx:839-859`）。
- 实测 C（语义检索抽屉打开文档）：高亮条渲染为 **`1/200`**、页内 `<mark>` **196 个**、当前命中 `activeMarks=1` ⇒ 链路是活的。
- 缺的三件：**① 没有输入框**（实测 `[data-ki-drawer-find]` 不存在）；② 只有「下一个命中」，**没有「上一个」**；③ 无法主动开启 —— 高亮只能由外部 prop `highlightQuery` 一次性触发（打开文档时）。

### 0.2 现状最扎眼：Ctrl+F 在三种形态下**行为分裂**，其中一处与代码注释意图相悖

| 形态 | 判定选择器命中情况 | Ctrl+F 实测行为 | 说明 |
|---|---|---|---|
| **A 浏览页内联阅读**（截图 1） | 元素带 `.ki-drawer--inline` | `prevented=true`，焦点被抢到**「搜索全库文档」框** | 搜索范围是**全库**，且结果会替换主区把文档顶掉 → 用户想搜当前文档却搜了全库 |
| **B 浏览页全屏** | 元素**同时带** `.ki-drawer--inline` **和** `.ki-drawer--fullscreen` | `prevented=true`，焦点同样被抢到「搜索全库文档」框 | **与注释意图相悖**：`AppShell.tsx:322/327` 明写「覆盖层抽屉打开时保留浏览器默认查找」，全屏已是覆盖层，却因 class 叠加被 `:not(.ki-drawer--inline)` 判成 inline ⇒ 判定失效。🟢 三重证据：实测 + 代码 + **git 历史（判据与 `.ki-drawer--inline.ki-drawer--fullscreen` 组合同属提交 `ab1e3ec` 2026-10-02，属同一次改动内未同步更新，排除"注释过期/后来改主意"）** |
| **C 语义检索抽屉**（截图 2） | 纯 `.ki-drawer`（无 inline） | `prevented=false`，焦点留在 `BODY` → 走**浏览器原生查找** | 能用但是「搜整页」：会命中大纲/按钮/工具条等 UI 文本，无命中计数、无上/下一个、移动端不可用 |

> 一句话：**三处入口，三种体验，没有一处是「搜当前文档」**。

### 0.3 一处即全覆盖 —— 三形态是同一个组件

`ModuleDrawer.tsx` 是唯一文档查看器：浏览页内联与抽屉（`BrowsePage.tsx:932-966`）、语义检索抽屉（`SearchPage.tsx:760-795`）、全屏（受控 `fullscreen`）、AI 引用预览（`ChatPanel.tsx:1953-1965`）全部走它 ⇒ **文档内搜索只需实现一次，自动覆盖截图 1 / 截图 2 全部形态**（🟢 代码实证 + 实测三形态 `drawerCount=1`）。

## 1. 目标与范围

- **目标**：在文档查看器内提供「搜索当前文档关键词 → 立刻看到命中位置与数量 → 快速前后跳转」的能力，行为心智对齐浏览器 Ctrl+F，但**只搜当前文档正文**。
- **范围**：`ModuleDrawer` 及其四个入口（浏览页内联 / 浏览页抽屉 / 全屏 / 检索与引用预览）+ 全局 Ctrl+F 判定（`AppShell.tsx:320-337`）。
- **不在范围**：跨文档/全库搜索（已有「搜索全库文档」与语义检索页），以及 `highlightQuery` 链路自身的功能扩展。

### 2.1 Ctrl+F 判定优先级链（三档）【v2 新增】

> 质疑意见 1：原报告只问"是否一并修缺陷"，未定义修好之后 Ctrl+F 怎么分发，实施时容易出现"内联搜本文、全屏又跳全库"的二次分裂。

| 档 | 条件 | 行为 |
|---|---|---|
| **①** | 文档查看器可见（`.ki-drawer` 存在，**含内联 / 全屏 / 抽屉三种形态**） | `preventDefault` → 打开并聚焦**文档内搜索**框 |
| **②** | 无文档查看器，但页面存在 `[data-ki-search-input]`（浏览页 / 检索页） | 保持现状：聚焦应用内**全库/语义**搜索框 |
| **③** | 两者都没有 | 不拦截，保留**浏览器原生查找** |

> 与既有代码的差异：现判据 `:not(.ki-drawer--inline)` 把三种形态割成两派（内联→②、抽屉→③、内联全屏被误判→②）。本链把"查看器可见"统一为 ①，浏览器原生查找退到 ③，并作为 R12 的兜底路径。

**实施中发现并修复的两个缺陷**（均由本需求的测试暴露）：

1. **一次 Esc 同时关掉查找框与文档** —— input 的 `onKeyDown` 里处理 Esc 时，React 对 discrete 事件同步 flush 状态更新并重挂 window 监听器（新闭包 `findOpen` 已是 false），事件随后冒泡到 window 时走了「关抽屉」分支。修法：Esc 只由 window 上的单一入口处理（`handleFindKeyDown` 仅保留 Enter / Shift+Enter）。
2. **计数 200 但 DOM 只有 196**（§4 影响面表登记的既有偏差）—— 根因：Markdown 的**异步渲染**（mermaid / 代码块）会替换子树，把手动插入的 `mark` 一并丢掉。修法：应用后 400ms / 1200ms 各复扫一次，确认少了就重新应用（幂等），仍少则把计数收敛到 DOM 实数。
