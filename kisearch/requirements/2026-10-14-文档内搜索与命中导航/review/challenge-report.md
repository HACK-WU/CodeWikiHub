# 🎯 需求报告质疑报告：文档内搜索与命中导航

- **质疑对象**：`requirement.md`（REQ-20261014-002，M1 需求报告）
- **对象类型**：报告文档（复用设计文档质疑策略，聚焦点 = 结论是否站得住 / 影响面是否遗漏 / 风险定级是否合理）
- **质疑方式**：代码直读复核 + 真机实测复核 + `git log -S` 历史核实 + 场景推演
- **触发**：auto-review Step 6（本次写入含多文件 + 需求文档，按"跨模块影响"判定需二次质疑）

## 📋 上下文确认

- **核心目标**：让用户在**当前文档内**快速定位关键词（对齐浏览器 Ctrl+F 的心智），覆盖内联阅读 / 全屏 / 检索抽屉三种形态。
- **测量口径**：命中即时可见、计数正确、可前后跳转、Ctrl+F 能唤出。
- **范围**：`ModuleDrawer` + `AppShell` 的 Ctrl+F 判定；不含全库/语义检索本身的改造。
- **关键约束**：复用既有高亮内核；不改动后端；既有 `highlightQuery` 链路（AI 引用片段定位）不得回归。

## ⚔️ 反对意见

### 意见 1：把 B 态判为"缺陷"的证据链不完整；且修复后的**快捷键判定优先级链**未定义

- **反对理由**：报告用「注释写的是 A、代码做的是 B」判定 B（内联全屏）为既有缺陷。但注释与代码不一致存在另一种可能——**注释过期**（产品后来改主意，全屏也让 Ctrl+F 聚焦全库搜索）。原报告未给出排除证据，属"用一个未经排除的假设支撑一个结论"。
  - **补证（本次已做）**：`git log -S "ki-drawer--inline"` 与 `git log -S "ki-drawer--inline.ki-drawer--fullscreen"` 均指向**同一提交 `ab1e3ec`（2026-10-02）** ⇒ 「内联全屏」组合态与 Ctrl+F 判据是同一次改动引入的，判据未随新组合态同步更新，**不存在跨期决策冲突** ⇒ 缺陷判定成立（🟢）。
  - **仍然缺的**：报告 Q7 只问"是否一并修"，**没有定义修好之后 Ctrl+F 该怎么分发**（文档查看器可见 / 不可见 / 无应用内搜索框三档），实施者可能各改一处、行为再次分裂。
- **功能影响**：预期「一键在本文档内查找」→ 实际 若优先级链未定，实施后可能出现「内联态搜本文、全屏态又跳全库」的二次分裂。
- **严重程度**：🔴 致命（决定需求能否达成）。
- **替代方案**：在需求文档中新增一节「Ctrl+F 判定优先级链（3 档）」：① 文档查看器可见 → 文档内搜索；② 无查看器但页面有 `[data-ki-search-input]` → 聚焦应用内搜索框（保持现状）；③ 两者都无 → 保留浏览器原生查找。
- **验证方法**：实施后按三档逐一实测（内联 / 全屏 / 抽屉 / 非文档页）。

### 意见 2：R8「性能与规模保护」的验收标准不可验证

- **反对理由**："10 万字符文档输入单字不卡死"不是可判定标准；也未给现状基线（🟢：`applyDocumentHighlights` 每输入一次全量重算 + DOM 重建，且**无命中上限**）。
- **功能影响**：预期「长文档也能搜」→ 实际 输入单字可能产生数千个 `<mark>`，每次按键重排导致输入明显迟滞，且用户得不到任何解释。
- **严重程度**：🔴 致命（体验类核心风险，且无判定标准就无法验收）。
- **替代方案**：改为可测量三条——① 查询长度上限（建议 ≤200 字符，超出截断并提示）；② 高命中场景（10 万字符 / 5000 命中）单次重算 ≤300ms，且输入过程可交互；③ 命中数超上限（建议 2000）时截断并在计数处标注「仅显示前 N 个」。
- **验证方法**：构造 10 万字符文档 + 高频字，用 `performance.now()` 量测 `applyDocumentHighlights` 单次耗时与输入响应。

### 意见 3：R11（两个搜索的区分）定级与环境不符

- **反对理由**：实测 A/B 表明用户痛点**恰恰**是"在文档可见时被抢到全库搜索"。把区分放 P2，可能造成"功能做了但用户仍被误抢/仍分不清"。
- **功能影响**：预期「截图 1 那个场景按 Ctrl+F 搜本文」→ 实际 若 R5 与 R11 分档落地，内联阅读态仍可能聚焦全库框，用户会认为需求没做。
- **严重程度**：🟡 重要。
- **替代方案**：R11 提为 P1，或与 R5 合并为一条（"Ctrl+F 按优先级链分发 + 两框文案/位置区分"）。
- **验证方法**：实施后在内联态按 Ctrl+F，断言焦点落在文档内搜索框且文案可区分。

### 意见 4：搜索态与既有「锚点定位」的关系未定义

- **反对理由**：`ModuleDrawer` 内已存在**三套定位**：深链接锚点（`anchorWarning`）、外部 `highlightQuery`、（新）手工搜索。报告只定义了后两者关系（R7 / Q6），漏了锚点这一路。
- **功能影响**：预期「搜索滚动干净可预期」→ 实际 由 `?anchor=` 深链接打开的文档，搜索跳转与锚点定位可能互相抢滚动位置（`focusDocumentHighlight` 会 `scrollTo`）。
- **严重程度**：🟡 重要。
- **替代方案**：明确"手工搜索期间锚点定位不再触发；清空搜索后不回跳锚点"。
- **验证方法**：用 `?anchor=` 深链接打开文档后立即搜索，观察滚动是否抖动/回跳。

### 意见 5：影响面表漏了两处既有消费方/约定

- **反对理由**：`SearchPage.tsx:242` 同样在 `openDocument` 时沿用 `highlightQuery`（与已登记的 `BrowsePage.tsx:567` 同类）；`SourcesList.tsx:6` 的「不新建高亮机制」约定也未列入"不得破坏的约定"。本次全量 grep `highlightQuery` 共 20 处命中，报告影响面表未覆盖这两处。
- **功能影响**：预期「改造机制后三条链路都不回归」→ 实际 漏改 `SearchPage` 的沿用点 ⇒ 语义检索内「上一级/下一级」跳转会丢高亮。
- **严重程度**：🟡 重要。
- **替代方案**：影响面表补这 2 行，并把「`highlightQuery` 是既有唯一高亮入口（不新建机制）」写成显式约束。
- **验证方法**：改造后跑「检索 → 打开文档 → 上一级/下一级」链路，断言高亮仍在。

### 意见 6：计数与实际可导航命中数不一致，被当成"顺带核查"而不是需求条目

- **反对理由**：实测 C 出现 `高亮条 1/200` 但页内 `<mark>` 仅 **196** 个。这属于**用户可见的观测偏差**（导航到第 197 个可能无高亮可跳）。报告把它挂在影响面表并写"实施时一并核查"——但新搜索复用同一内核，用户会看到同样的偏差 ⇒ 它不是"顺带"，而是 R4（反馈正确性）的验收子项。
- **功能影响**：预期「1/200 表示有 200 个命中且都能逐个跳转」→ 实际 后几个命中可能跳不动或计数虚高。
- **严重程度**：🟡 重要（计数正确性属必备质量）。
- **替代方案**：把"计数 === 实际渲染并可导航的 mark 数"写入 R4 验收标准；根因定位可交 `debug`（本次不修）。
- **验证方法**：对同一文档复算（逐文本节点匹配计数 vs DOM mark 计数），定位差异来源（排除容器 / 嵌套 / 重复 apply）。

### 意见 7：缺少「整体成功判据」—— 实施后无回归锚点（全局回扣）

- **反对理由**：报告给了 12 条需求与影响面表，但**没有一句话说明"这个需求做完后，哪些整体行为必须保持不变"**。缺整体判据 ⇒ 实施者只能按需求条目自证，跨链路回归无锚点。
- **功能影响**：预期「新功能不伤旧链路」→ 实际 高风险链路（AI 引用片段定位、全库/语义检索、浏览器原生查找退路）无明确回归清单，容易在"顺手改 AppShell"时被破坏。
- **严重程度**：🟡 重要（按 challenger 规则，给不出全局图景本身即成立质疑）。
- **替代方案**：补一节「整体成功判据（必须保持不变）」，建议 5 条：① AI 引用片段打开文档仍自动定位并高亮；② 全库检索命中 / 语义全文命中打开文档仍自动高亮；③ 非文档页 Ctrl+F 仍聚焦应用内搜索框；④ 全屏切换后滚动位置恢复仍正常；⑤ 浏览器原生查找仍可作为兜底（保留路径）。
- **验证方法**：实施后逐条回归（可在同一端到端脚本内断言）。

## ➕ 补充场景与情况

| 场景 | 说明 |
|---|---|
| **中文输入法组合输入（IME composition）** | 用拼音输入时 `compositionstart → compositionupdate → compositionend` 期间会连续触发 `input`。若按普通输入做防抖重算，用户还没选词就在搜索、命中数抖动。需明确"组合输入期间不重算，`compositionend` 后再搜"（报告与负向需求均未覆盖，中文用户必踩） |
| **搜索框存在时的 Tab 焦点链** | 新增控件会改变 `ModuleDrawer` 内 Tab 顺序（当前头部工具条已有 4-7 个按钮），需明确焦点落点 |
| **命中的滚动容器是自定义滚动区** | `focusDocumentHighlight` 的 `scrollTo` 作用于 `.ki-drawer__body`；全屏切换会重建该节点 ⇒ 搜索态必须以组件 state 存活（报告 R3 已提，建议在实施时用"全屏往返后当前命中不丢"作为回归断言） |
| **检索态打开文档的高亮来自 `resultQuery`** | 全文检索时搜索框内容可能与打开文档后的文档内搜索词不一致（一个是检索词、一个是当前查找词），需明确"打开时预填检索词"还是"独立不关联"（Q6 的细化） |

## 📊 风险评估与建议

### 🎯 裁决结论

**⚠️ 修改 🔴/🟡 意见后进入设计**（意见 1、2 为 🔴，必须处理；意见 3-7 为 🟡，建议处理）。

### 识别的风险

| 风险 | 可能性 | 功能影响 |
|---|---|---|
| 快捷键分发无优先级链 | 高 | 实施后行为再次分裂：内联搜本文、全屏跳全库 |
| 性能无判定标准 | 中高 | 长文档大量命中时输入迟滞，且无上限提示，验收无从判定 |
| `highlightQuery` 链路漏改 | 中 | AI 引用 / 检索内跳转丢高亮（既有能力退化） |
| 计数偏差未纳入验收 | 中 | 用户按计数跳转时"跳不动"，产生"功能不可靠"的观感 |
| 缺整体成功判据 | 中 | 跨链路回归无锚点，改快捷键时可能连带破坏既有搜索入口 |

### 风险等级

- **总体风险**：🟡 中风险（需求方向成立、证据充分，风险集中在**判定口径缺失**而非方向错误）
- **风险分布**：🔴 2 个、🟡 5 个、🟢 0 个

2. **把 R8 验收改为可测量三条**（长度上限 / 重算耗时 / 命中截断提示） —— 否则无法验收，且用户会遇到无解释的迟滞（意见 2）。
