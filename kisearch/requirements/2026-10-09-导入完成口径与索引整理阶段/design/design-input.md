## 1. Q6（R9 路线）：三条路线的取舍与建议

### 1.1 红线（设计不可越）

**N10**：占槽强制释放**不得**让"半写状态"暴露给读 —— 读与元数据写之间的互斥（S-01 的提交窗口）不可放松。宁可让该请求自己失败并给降级结果。

### 1.2 三条路线

| 路线 | 机制 | 优点 | 代价/风险 | 依赖 |
|---|---|---|---|---|
| **a** 占槽上限 | 队列内任务设最大占用时长，超限**强制释放** + 降级返回 | 改动封闭；直接解决"挂死" | 通用上限与 N10 冲突：强制释放仍在跑的**写**会让读与其并发；释放 **read** 同样造成"读与新写并发" ⇒ **只能对"可安全放弃的任务"生效**（白名单） | 无 |
| **b** `engine-read` kind | 新增细粒度 kind："只读引擎"任务与元数据读互不阻塞、仍与写互斥 | 覆盖"未来新增的挂住读"；语义清晰 | 队列语义变更（三态 → 四态）；**需先实测引擎并发能力**（同进程并发打开/读同一 collection 的行为） | 引擎并发能力验证 |
| **c** 引擎"忙"信号 + read 旁路 | 依赖引擎提供 busy 信号再决定让路 | 最彻底 | 外部依赖，当前 zvec 无该 API | 引擎能力确认 |

### 1.3 已签发建议（需求文档 Q6 行，AI 建议待用户最终确认）

**先 a 后 b**；c 待引擎能力确认。**R8（已落地）就是路线 a 的"白名单"形态** —— 只读辅助请求（`refresh` / `tags`）在 handler 内部超时后自行返回降级结果，队列槽随即放行。因此：

> **R9 的剩余价值 = ① 把"可安全放弃"从白名单扩展成体系（覆盖未来新增的挂住任务类型）；② 需要时引入 b 的队列语义。**

### 1.4 设计须回答

1. 路线 a 的"白名单"边界如何定义与落地（哪些 operation 可放弃、判定放哪层、新增任务如何登记）？
2. 路线 b 是否需要：若 a 的白名单 + 强制超时已成体系，b 的增量价值与成本？**引擎并发读安全性必须实测后再定**。
3. 占槽超限事件的**可观测性**（日志 / 任务中心可见？）。

## 2. Q7（`indexCompleteness` 语义）：已核定结论

- **结论**：`stats.indexCompleteness` **≠ "索引实体是否存在"**。现网 **23/23** 个 scope 都有 dense 索引实体（5MB~114MB）；有新鲜快照的 **11 个样本信号全部为 0**、为 1 的样本 **0 个** ⇒ 应读作「**已被显式整理并激活（`optimize()` 路径）**」的标记。
- **对判据的影响**：R4/R6/A3 一律采用 **A11 交叉口径**（*索引实体文件存在* **+** *重开校验*）；`indexCompleteness` 降为**辅助信号**，不得单独用作"未建"判据（否则会把"索引其实已建"误判为"未建" → 重复整理、浪费 CPU）。
- **证据**：`review/exp-3-index-completeness-semantics.md`（全程只读：文件扫描 + 直读快照 JSON）。
- **设计须回答**：`indexing` 阶段的**完成判据**怎么写（实体 + 重开校验的具体检查点与成本）；信号是否仍需"整理后置 1"，还是仅作提示位。

## 3. 待设计需求逐条输入

> 约束 = 必须满足的红线；证据 = 已实测的支撑数据；开放项 = 设计前需回执或测试确认。

### R1 两级完成口径（P0）

- **约束**：任务终态区分「**可用**」（文档可浏览/可检索）与「**已优化**」（索引整理完成）；CLI / HTTP / 任务中心 / 导入页**四端口径一致**；**不新增状态枚举**（复用 `phase`）。
- **证据**：现场一/二；`src/lib/task-registry.ts` 已有 `phase` 字段。
- **依赖**：R2（阶段名）、R4（`optimize` 触发点）。
- **开放项**：REQ-20261009-001 的 `partial` 与「可用/已优化」**叠加**时如何呈现（现有负向/验收未覆盖）。

### R2 阶段化展示（P0）

- **约束**：`扫描/切分 → 向量化(x/y) → 提交元数据 → 索引整理中 → 已优化`；**不得伪造百分比**（N5）；同一时刻三端显示同一阶段。
- **证据**：S-01 的 `runMetadataCommit` 窗口提供"提交元数据"阶段的天然边界；任务台账已有 `phase`。
- **依赖**：R4（"索引整理中"需要真实状态源，不能只靠 UI 推测）。
- **开放项**：`indexing` 阶段的进度显示口径（实体扫描？时长不定？—— 与 Q7 结论联动）。

### R4 接入 `optimize`（P0）

- **约束**：**异步** `await optimize({ concurrency: N })`，**不用** `optimizeSync()`（实验 1：阻塞 worker、多核暴涨）；**不推迟「可用」**；失败/超时降级「可用」+ 可重试，**不得判失败、不得丢数据**（N4/N8）。
- **证据**：实验 1（8000 向量：`optimizeSync` 16.8~21.5 CPU 秒 ≈ 4.3 核；`concurrency:1` ≈ 1.0 核；`concurrency:4` ≈ 2.4 核）；现场二（`dense.index.3.proxima` 119MB 引擎自行落盘、信号仍 0）；Q2 已拍板（异步 + 限核）、Q4 已拍板（全局串行 ≤1）。
- **依赖**：R6（判据）、R1/R2（展示）、N3（取消后继续完成）。
- **开放项**：进程重启导致的"整理中断"如何恢复（N4 延伸）；`optimize` 单次成本上界——是否需要按批分片 optimize（现场二单核 ~10 分钟）。

### R6 索引就绪可观测（P0，部分落地）

- **现状**：S-02 已接出 `ki doctor` 文案 / 维度快照 / `/api/vector/status`（`indexCompleteness` 透传链：native stats → worker → `engine.info()` → `vectorCollectionDiagnostics` → `getVectorDimensionStatus`）。
- **约束**：接**任务 / 任务中心 / 诊断接口**三处（当前只有诊断接口）；A11——信号与实体必须给出可验证的对应关系。
- **依赖**：Q7 结论（§2）。
- **开放项**：任务侧的暴露形态（任务结果字段？阶段进度？）；存量 scope 的"待整理"清单如何产出（一次性只读扫描的成本与粒度）。

### R7 跳过未变重写（P1，收益最大）

- **约束**：判定 = **id 一致 + 维度/模型一致性校验**；命中 **N7** 任一情况（维度/模型变更、上次写入未确认成功、tag/group 等影响 id 的字段变化、FTS 与 dense 双写不一致）**必须重写**；**不得以"跳过"掩盖写入失败**。
- **证据**：实验 2（同 id 覆盖写 24.76 CPU 秒/150s ≈ 删旧插新 23.65/24.11；**单轮写入尾巴 ≈0** ⇒ 触发条件是"对已存在数据再写一遍"）；引擎单次写入上限 1024 篇（当前每批 200）。
- **依赖**：R4/R2（"跳过"计数在展示侧的呈现）。
- **开放项**：`skipped` 计数是否进任务台账（A7 要求"如实反映"）；跳过对 `indexCompleteness`/索引实体的影响（跳过后是否仍需 optimize）。

### R5 整理期提示（P1，随 R2）

- **约束**：整理期同 scope 检索**返回正常（可慢）**+ 明确提示；不得阻塞其他 scope。
- **证据**：现场二——`optimize` 独占 worker（`info()` 212ms ≈ `optimize` 233ms）；CPU 100% 期间**其他 scope 读 2ms**。

### R10 陈旧 scope 写锁（P2）——已决策不做

- `scope-write-lock.ts:28-42` 已有正确的惰性 stale 回收（`process.kill(pid,0)` 存活判定 + inode/dev 二次校验），残留文件无实际危害。**设计不需覆盖**。
