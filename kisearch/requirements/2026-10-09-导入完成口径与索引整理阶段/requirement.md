## 0. 用户诉求

1. **完成口径要诚实**：真正的「导入完成」应在 zvec 的向量/索引写入完成之后才算（用户原话：*"真正的导入完成应该是等 zvec 的数据也全部写入完成后，才算是导入完成"*）；并且要能看到**不同的阶段**。
2. （由现场一排障延伸）导入后该 scope 页面打不开、CPU 长时间 100% 的现象需要**可解释、可控**，而不是"数分钟后自愈"。
3. （现场二追问，2026-10-10）**"收尾阶段究竟在干嘛？就不能导入的时候让 zvec 边干活，非要等结束后再干么？"** —— 用户观察：*"导入过程中 node CPU 使用率并不高，但一旦导入成功后立即升高到 100%"*。要求解释这条尾巴的本质，并给出可行的方向。

### 1.4 实验结论摘要（细节见 `review/exp-*.md`）

**实验 1（`optimize()` 的代价）**
- 不调 `optimize()` → 索引永远不建：写入后 `indexCompleteness.dense` 恒 0，**静置 180s 零后台活动**，重开后仍 0（"引擎会自己整理"被证伪）。
  - ⚠️ **2026-10-10 部分修正**：现场二出现 `dense.index.3.proxima`（119MB）**由引擎自行构建并落盘**（无 `optimize()` 调用方），但 `indexCompleteness.dense` **仍为 0** ⇒ 见 H1 修正。
- 调它 → 总 CPU **不随并发度变化**（8000 向量：`optimizeSync()` 16.8~21.5 CPU 秒 ≈ 4.3 核；`concurrency:1` ≈ 1.0 核；`concurrency:4` ≈ 2.4 核）⇒ **并发度只改"几核、多久"**。
- `stats.indexCompleteness`（0→1，重开后仍可读）曾是"索引就绪"信号 —— 现被现场二反例削弱（H1）。

**实验 2（CPU 尾巴的触发条件）**
- **触发条件 = "对已存在的数据再写一遍"**：单轮写入尾巴 ≈0；删旧插新 23.65/24.11 CPU 秒·150s；**同 id 覆盖写（完全不删）24.76** ⇒ 与删除无关；每批 200 vs 1000 无差别。
- **不能关掉**：`ZVecInitOptions` 无 compaction/flush 参数。
- **能"少触发"**：向量 id 是内容哈希，**重导入时内容未变的片段 id 一致，本可跳过重写**（现状整批重写）→ R7。
- 引擎单次写入上限 **1024 篇**（当前每批 200）。

**现场二的补充结论（回答"收尾在干嘛 / 能否边导边干"，🟢 实测）** 🆕
- 收尾干的是：**为 15546 篇向量构建并落盘 dense 索引 + FTS/scalar 落盘**（单核 100% 纯计算 ~10 分钟，产物见 1.2 表）。
- 为什么导入期 CPU 低：写入走内存缓冲 + append/日志（顺序写）；重活（flush/compaction/索引构建）由引擎在**写入压力消退后**集中做（LSM 常规调度）。
- **"边导边干"引擎侧做不到**：无 compaction/flush 旋钮；唯一显式入口 `optimize()` 是**同步、独占 worker**（实测 233ms 的 optimize 期间 `info()` 延迟 212ms），插进导入只会把导入自身拖成"假死"。
- **CPU 100% 本身不是页面卡死的原因**：同进程 `k8s` 同接口全程 2ms ⇒ 致卡的是 **⑤/⑥（队列槽被挂住的辅助请求占死）**。

## 2. 现状 → 预期

| 时刻 | 现状 | 预期 |
|---|---|---|
| T1 元数据提交 | 文档已入库但被队列挡住 → "完成却看不到" | 立即可浏览/可编辑（**读接口不被引擎收尾阻塞**） |
| T2 向量可搜 | 同 scope 查询排队 | 可检索（整理期允许变慢，但要有提示） |
| T3 索引就绪 | 无提示、自愈；且**实际从未就绪** | 任务显式阶段「索引整理中 → 已优化」，终态两级 |
| T4 引擎收尾期（非 optimize，引擎自行整理） 🆕 | 一个挂住的辅助请求可让整个 scope **不可读** >10 分钟 | 读**始终**可用；辅助请求超时降级；**任何任务不得无限期占槽** |

```
扫描/切分 → 向量化(x/y) → 提交元数据 → 索引整理中 → 已优化
                                        └─ 整理期：可浏览/可检索（检索可能变慢）
```

## 4. 负向需求

| # | 场景 | 必须给用户的结果 |
|---|---|---|
| N1 | 整理中用户编辑/删除该 scope 文档 | 不产生数据损坏；行为有定义（排队/阻塞/允许）并实测；不得静默丢失编辑 |
| N2 | 整理中重复导入同 scope | 串行化（同 scope 队列覆盖或把整理纳入队列），不得叠加并发整理 |
| N3 | 导入被取消（Ctrl+C / 取消按钮） | 明确"取消后索引整理是否继续"并给文案；不得留下"半整理"且无提示 |
| N4 | `optimize` 失败/超时/进程重启 | 数据仍「可用」；任务不判失败；给出可重试整理的入口与说明 |
| N5 | 无进度百分比 | 禁止伪造进度；用 `indexCompleteness`（口径见 H1 修正）或"时长不定"表述 |
| N6 | 多 scope 同时整理 | 有并发上限，避免 CPU 打满（现场已观测单核 100% 持续 ~11 分钟） |
| N7 | **跳过未变重写的边界**（R7） | 以下情况**必须重写**而非跳过：embedding 维度/模型已变更（与持久化维度不符）、上次写入未确认成功、tag/group 等影响 id 的字段变化、FTS 与 dense 双写不一致。**不得**以"跳过"掩盖写入失败 |
| N8 | 引擎不可用/无 `optimize` 能力 | 导入仍可完成（降级为「可用」），不得阻塞整个导入 |
| **N9** 🆕 | 辅助请求（R8）超时降级 | 降级**不得被误判为"引擎故障"**：不得触发重建/清库引导、不得让导入任务因此判失败；文案需区分"未知/陈旧"与"故障" |
| **N10** 🆕 | 队列槽上限强制释放（R9）后 | **不得让"半写状态"暴露给读** —— 宁可让该请求自己失败并给降级结果，也不得放松读与元数据写之间的互斥（与 S-01 选项 b 的红线一致） |
| **N11** 🆕 | 陈旧锁回收（R10） | 不得误删活锁：判活以 **pid 存活 + 心跳时间** 为准，跨进程安全；回收动作留日志 |
