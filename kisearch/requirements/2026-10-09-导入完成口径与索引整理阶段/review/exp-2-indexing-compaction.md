# 实验 2：复现「导入后单核 100% CPU 尾巴」并锁定触发条件

> 关联需求：**REQ-20261009-003**（父需求 REQ-20260930-002）
> 目标：定位生产现场那 ~11 分钟 / ≈660 单核秒到底是什么（实验 1 已证伪「是 dense 索引构建」：15000 向量的索引构建只需 ≈20 单核秒）
> 一句话结论：**同型尾巴复现成功**（单核 `rocksdb:*` 后台线程 compact `fts.*.rocksdb`）；**触发条件是「对已存在的数据再写一遍」**，与文本体量、批量大小、是否显式删除无关；**公开 API 无 compaction/flush 旋钮，只能「少触发」+「不被它挡住」**
> 状态：实验 2 完成（2026-10-09）；样本覆盖 4 种写入形态 + 2 次复跑

## 2. 结果

### 2.1 复现：与生产现场同型的三件套

| 指标 | 生产现场（debug-report） | 实验复现（I 臂） |
|---|---|---|
| 忙线程 | `rocksdb+` | **`rocksdb:high`** |
| CPU | 单核 100% 连续 ~11 分钟 | 峰值 **115~120%**（单核跑满），间歇性突发 |
| 变更文件 | `fts.2.rocksdb/000045.sst`、`MANIFEST-000020`、`scalar.4.ipc` | **`0/fts.2.rocksdb/000022.sst`、`0/fts.2.rocksdb/MANIFEST-000005`** |

⇒ 机制一致：**FTS 存储（RocksDB）后台 compaction，单线程吃满一核**。

### 2.2 触发条件（15000 篇 × 2KB，逐因素隔离）

| 臂 | 写入形态 | 尾巴 CPU（窗口） | 峰值 | 忙线程 | 判定 |
|---|---|---|---|---|---|
| **H** | 单轮写入（只有一遍） | ≈0（9.97 / 240s ≈ 全为探针） | 15.3% | 0 | **不触发** |
| **I** | 删旧 15000 + 插新 15000 | **23.65**、**24.11**（150s，两次复跑）；38.11（240s） | 119.5% / 119.9% / 119.6% | 1 | ✅ **触发且可复现** |
| **L** | **覆盖写同一批 id（完全不删）** | **24.76**（150s） | 115.6% | 1 | ✅ **同样触发** ⇒ 删除不是关键 |
| **K** | 同 I，但每批 1000（引擎单批上限 1024） | 39.18（240s） vs I 38.11 | 116.6% | 1 | ❌ 批量大小无差别 |
| **J** | 先打底 1 万再做删改（库 25k 篇 / 386MB） | ≈0（11.06 / 240s） | 15.3% | 0 | ⚠️ **未复现** |

**读法**：
- 写一遍不触发；**再写一遍就触发**（无论"删旧插新"还是"同 id 覆盖写"）。
- 触发与文本体量（H 有 2KB 大文本但不触发）、批量大小（200 vs 1000 无差别）、显式删除（L 不删也触发）**均无关**。
- 触发带**阈值/时序性**：J 臂库更大却没触发 ⇒ 绝对时长/是否触发**不可外推**，只能定性。

### 2.3 生产 11 分钟 vs 实验 ~24 CPU 秒 / 150s 的差异（如实标注）

| 项 | 生产 | 实验 |
|---|---|---|
| 库规模 | 28491 篇（探针实测），历史段更多 | 15000 篇（I/K/L）；25000 篇（J） |
| 尾巴形态 | 连续单核 100% ~11 分钟 | 间歇突发，平均 ~0.16 CPU 秒/秒（单核的 16%） |
| 绝对工作量 | ≈660 单核秒 | 24~39 CPU 秒 / 窗口 |

⇒ **机制已确认，绝对时长不可外推**；生产更长与库规模、历史段、触发时机有关，需要真实库上的观测才能定量。

### 2.4 平台约束（顺带发现）

- 引擎**单次写入上限 1024 篇**：`Too many docs: 2000 exceeds max write batch size of 1024`（我们当前每批 200，有提升空间，但对 compaction 无影响）。
- 空集合的 `indexCompleteness` 缺省为 1（无数据可索引）——所以现网读到 0 才意味着 **"有数据但没建索引"**。

## 3. 结论（可行动）

1. **这条尾巴关不掉**：`ZVecInitOptions` 全量 12 项里与整理相关的只有 `optimizeThreads` / `queryThreads`，**没有 compaction / flush 参数**；而这条 compaction 本来就只占 1 条线程（限到 1 也还是 1）。
2. **能"少触发"**：只要避免"对已存在数据再写一遍"，就不会触发（H 臂实证）。我们代码里有明确落点：
   - 向量 id 是**内容哈希**（`src/lib/fts-client.ts:82-87`：`sha256(scope ␀ group ␀ relation ␀ tag ␀ text)`）；
   - ⇒ **重导入时内容未变的片段 id 完全一致，本可跳过重写（也跳过重新 embedding）**，而现在仍会整批重写；
   - 这既省 embedding 成本，又直接消除触发条件。
   - 需设计确认的边界：embedding 维度/模型变更、上次写入失败但 id 已存在、tag/group 变化导致 id 变化、FTS 与 dense 双写一致性。
3. **能"不被它挡住"**：产线用户可见伤害来自 `doc-list` 被同 scope 引擎队列阻塞（25s 超时 vs 恢复后 22ms），与 CPU 峰值本身无必然关系 ⇒ **读解耦 + 阶段可见**是最确定的收益。
4. 与实验 1 的合并判断：**"接入 optimize" 与 "减少重写" 是两件独立的事**——前者修"索引从来没建"（现网全库 `indexCompleteness.dense=0`），后者修"重导入触发 compaction"。
