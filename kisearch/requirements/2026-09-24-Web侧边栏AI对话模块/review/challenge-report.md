## 📋 上下文确认

- **对象目标**：验证「侧边栏 AI 对话模块」的技术可行性与体验风险，并据此调整需求
- **覆盖范围**：chat 集成 / SSE 链路 / reasoning 模型行为 / 三栏布局 / 会话落盘

## ⚔️ 反对意见

### 意见 1：延迟结论建立在单次采样上，方差未经评估（已用新证据证实）

- **反对理由**：验证报告中"首答 1209ms / 4729ms / 5308ms / 11991ms"全部是**每模型单次调用**的结果，却被写成可用于设计的定量依据。质疑后补测 `qwen3.8-flash` **同题 3 次**：

  | 采样 | 首字 | 首答 | 思考 token |
  |---|---:|---:|---:|
  | 1 | 871ms | 2187ms | 61 |
  | 2 | 894ms | 2004ms | 46 |
  | 3 | 647ms | 1139ms | 25 |

  首答**波动接近 2 倍**（1139~2187ms）、思考 token **波动 2.4 倍**（25~61）。原报告中"qwen3.8-flash 首答 1209ms"属抽样侥幸，不代表稳态；反之"11991ms 最坏值"也可能是单次异常。
- **功能影响**：预期「用实测数据锁定默认模型与 P0 优先级」→ 实际「若按单点数据做取舍，可能为某个抽样较快的模型定型，上线后延迟与成本落在分布的另一端」
- **严重程度**：🟡 重要（结论方向未错——7 个模型全部有 reasoning 行为——但定量细节不可作为承诺指标）
- **替代方案**：所有延迟/成本数字标注「单次采样，n=1」并附 3 次采样分布；需要精确指标时用 n≥5 取中位数
- **验证方法**：重跑上表（命令：`node /tmp/probe-models.mjs <模型> <模型> <模型>`）

### 意见 2：会话写入是「读-改-写」，WAL 只保护写，存在消息静默丢失竞态

- **反对理由**：`src/lib/wal.ts:1-12` 明确实现了**跨进程文件锁**（`O_CREAT|O_EXCL`，超时 10s、陈旧 30s），并发写同一文件的 Last-Write-Wins 已被防护——这一点原报告未发现、质疑方的初始假设（多标签页会丢数据）**被推翻**。但 `walWrite` 只保证**单次写入原子**，不保护 **读-改-写序列**：需求中的发消息路径是「读会话 JSON → 追加 user 消息 → 写盘 → … → 追加 assistant 消息 → 写盘」。两个并发请求（两个标签页、或同一会话被快速重复提交）可各自读到同一版本、各追加自己的消息、再串行落盘，**后写覆盖先写 → 某条消息静默消失**。
- **功能影响**：预期「历史会话完整可追溯」→ 实际「并发场景下消息静默丢失，用户只看到自己的部分提问消失，且无任何提示」
- **严重程度**：🟡 重要（数据丢失类，但触发需并发；单用户单标签页不触发）
- **替代方案**：① daemon 侧按会话 ID 串行化写入（内存队列 / mutex，最简）；② 写前校验版本（乐观锁：比较 `updatedAt` 或自增 `seq`，冲突则重试）；③ 消息追加改为独立分片文件（代价大，不推荐）
- **验证方法**：对同一会话并发发两条消息，检查落盘消息数是否为 4（user/assistant × 2）；当前原型预期会失败

### 意见 3：R11 把「必须展示思考内容」写进 P0，属未经拍板的范围扩张

- **反对理由**：验证数据支持的是「长思考期间必须有**可见状态**」（否则 12s 空窗被误判卡死），而**展示 reasoning 正文**是另一件事——它带来 UI 复杂度、内容可读性（实测思考可达 2635 字）、以及是否落盘的存储代价（T5）。requirement.md 把两者合并为一条 P0（R11）并附"可展开/收起"验收标准，等于替用户决定了范围。
- **功能影响**：预期「按用户确认的 5 项需求实施」→ 实际「实施方按 R11 做了思维链 UI，可能偏离用户"只要能对话"的原始期望」
- **严重程度**：🟡 重要
- **替代方案**：拆分 **R11a 生成状态指示（P0，只要求"有反馈"）** 与 **R11b reasoning 内容展示与呈现方式（P1，与 T5 落盘决策绑定，需用户拍板）**
- **验证方法**：把拆分后的两条交用户确认，观察其是否仍要 reasoning 正文

### 意见 4：原型未触及 daemon 框架层，结论不可直接外推为「生产可行」

- **反对理由**：原型是独立进程（原生 `http`），而生产路径是 `浏览器 → mcp-http.ts → runWithConfigSnapshot / runWithVectorSource → handler → 上游`（`src/lib/mcp-http.ts:595-599`）。原型**没有**覆盖：① 鉴权与 `Bearer` token→scope 校验（`mcp-http-api.ts:273-296`）；② 新增只读接口的越权白名单登记（`:300-310`）；③ `runWithConfigSnapshot` 在 SSE 长连接期间的配置快照行为；④ 长响应下 daemon 的关闭/重启语义。报告虽写"原型非生产代码"，但 §11 的 ✅ 结论未同步标注这一缺口。
- **功能影响**：预期「R-02 通过 ⇒ 生产链路可行」→ 实际「框架层若对长连接有额外约束（快照释放时机、关闭流程），实现期才发现需返工」
- **严重程度**：🟡 重要
- **替代方案**：设计阶段在真实 daemon 上加一个最小 SSE 端点（一次 `curl -N` 即验），把"框架层可用"作为设计前置门；不改变原型的验证结论，但明确其边界
- **验证方法**：在 daemon 内实现 `/api/chat/ping-stream`（纯文本流），`curl -N` 观察是否被框架层缓冲或提前关闭

### 意见 5：布局结论缺真实页面基线，"342px"是构造值而非产品实测

- **反对理由**：342px 来自我构造的三栏 demo（232 + 300 + 360 均为硬编码近似值）。真实 `/browse` 在 1280px 下的主内容区宽度**未测**（当时 daemon 未运行，7423 无响应）。若现状基线本就很窄，则"加面板导致不可用"的归因需要修正为"现状已接近临界，面板加速恶化"。
- **功能影响**：预期「据实测定窄屏降级阈值」→ 实际「阈值可能建立在错误的基线上，降级触发点偏早或偏晚」
- **严重程度**：🟡 重要
- **替代方案**：启动 daemon 后补测真实 `/browse` 在 1280/1440/1600 三档下的主内容区宽度，写入设计文档作为阈值依据
- **验证方法**：`ki mcp restart --web` 后用浏览器读取 `.ki-content-inner` 宽度

### 意见 6：reasoning 回传污染风险未在任何文档中声明

- **反对理由**：落盘会话含 `reasoning`（验证已证实）。L1 记忆的实现方式是"把历史 messages 回传"，若实现时把落盘的 assistant 消息（含 reasoning 字段）一并拼进 `messages`，会污染上下文——实测单次思考可达 2635 字，远大于答案本身，将同时放大 token 成本与延迟，并可能让模型"复述自己的思考"。
- **功能影响**：预期「多轮对话省 token」→ 实际「长会话 token 爆炸，成本与延迟随轮次远超预期」
- **严重程度**：🟡 重要（实现期高概率踩中）
- **替代方案**：在设计文档中明确硬约束——**reasoning 永不回传**，仅用于展示与复盘；回传的 assistant 内容只用 `content`
- **验证方法**：实现后检查上游请求体，确认 `messages` 中无 `reasoning` 字段

### 意见 7："新进程读盘 ≈ daemon 重启"表述过强

- **反对理由**：验证只证明了"另一个进程能读取同一目录的 JSON"，未覆盖 daemon 的 RPC 层、配置重载、锁竞争与启动自检。原报告写"等价 daemon 重启后可读"，把较弱的事实放大成较强的结论。
- **功能影响**：预期「R5 验收标准已被验证」→ 实际「daemon 重启后的会话可见性仍未验证」
- **严重程度**：🟢 建议
- **替代方案**：改为"读盘路径等价（文件无内存态依赖），daemon 重启流程未验证"
- **验证方法**：daemon 重启后 GET 会话列表

### 意见 8："候选模型全部是 reasoning"与"成本差约 20 倍"均为过度概括

- **反对理由**：① "全部"仅覆盖当时所测 4 个模型；质疑补测 `qwen3.7-max`/`auto`/`deepseek-v4-pro` 后为 **7/7 均为 reasoning**（仍有 8 个模型未测，含多模态，见下方补测数据），可支持"绝大多数可用文本模型为 reasoning"但不能支持"全部"。② "成本差约 20 倍"实际是 **completion token 量差**（48 vs 944），未计入各模型单价差异，成本差可能显著不同。
- **功能影响**：预期「据此锁定默认模型与成本预期」→ 实际「若单价差距抵消 token 差，默认模型选择与成本预期都会偏」
- **严重程度**：🟢 建议
- **替代方案**：表述限定为"抽测 7/7 为 reasoning"与"completion token 量差约 20 倍（未计单价）"
- **验证方法**：查询该平台各模型价目表后重算

## ✅ 认可点

1. **验证方式有效**：用真实模型 + 真实浏览器实测，而非静态推演；关键结论可复核（命令、截图、落盘文件均留存）
2. **发现决定性事实**：reasoning 模型的首答延迟与思考 token 占比，是本需求最大的隐藏风险；若按普通 chat 模型设计 UI（非流式、无状态指示），实现期必然返工
3. **正确区分了"方案不可行"与"原型有缺陷"**：demo 首次验证中 curl 截断导致的"assistant 未落盘"被正确识别为中止语义验证，未误判为方案缺陷
4. **D4 独立目录决策有额外收益**：同时解除了"快照恢复覆盖会话"与"删除 Group 误伤会话"两个耦合点，验证报告与需求文档一致记录了该推理
5. **WAL 复用决策正确**：`src/lib/wal.ts` 已实现跨进程锁，会话落盘复用既有原语无需新建并发保护（仅需补 RMW 层，见意见 2）

## ➕ 补充场景与情况

| 场景 | 说明 | 建议归属 |
|---|---|---|
| 反向代理/网关缓冲 | 生产若经 nginx 等转发，SSE 可能被缓冲导致"一次性吐出"；本机直连无此问题 | 设计阶段：响应头 `X-Accel-Buffering: no` + 部署说明 |
| 多标签页并发 | 同一会话在两个标签页同时发送 → 意见 2 的竞态 | 设计阶段：会话级串行化 |
| 模型不可用/限流 | 上游 429/5xx 下会话与 UI 的表现未验证（负向 N4 仅列条目） | 实现期补齐 |
| 长会话 token 累积 | L1 全量历史 + reasoning 不回传的前提下，累积仍随轮次上升 | 已有 L2 待办，建议加"用量可见" |
| 思考内容的呈现 | 实测思考可达 2635 字，全量展示会淹没答案 | R11b 交互设计需定"折叠/摘要/仅状态" |
| 语言与合规 | 思考内容语言可能与用户输入不一致、可能包含敏感推理路径 | 产品确认是否允许展示 |

## 📊 风险评估与建议

### 🎯 裁决结论

**⚠️ 修改 🟡 意见后进入开发**（方向无需重做：验证结论的核心判断——流式 P0、状态指示必需、布局需降级——均成立且被更强证据支持；需修正的是表述严谨性、两条遗漏约束与一项范围扩张）

### 识别的风险

- **风险 1**：并发写入导致消息静默丢失 — 可能性：中 — 功能影响：预期「历史完整可追溯」→ 实际「消息无提示消失」（意见 2）
- **风险 2**：reasoning 误回传导致 token 与延迟爆炸 — 可能性：中高（实现期易踩） — 功能影响：预期「多轮省 token」→ 实际「随轮次显著放大」（意见 6）
- **风险 3**：框架层未验证导致实现期返工 — 可能性：低中 — 功能影响：预期「R-02 通过即生产可行」→ 实际「长连接在 daemon 中的行为未知」（意见 4）
- **风险 4**：定量指标不可承诺 — 可能性：高 — 功能影响：预期「按实测锁阈值」→ 实际「阈值建立在单点抽样上」（意见 1、5、8）
- **风险 5**：范围扩张偏离用户预期 — 可能性：中 — 功能影响：预期「按已确认 5 项实施」→ 实际「多出未拍板的思维链 UI」（意见 3）

### 风险等级

- **总体风险**：🟡 中风险（无 🔴：不存在会破坏既有功能或数据安全的方案级缺陷）
- **风险分布**：高风险 0 个，中风险 5 个（意见 1-6 归并），低风险 2 个（意见 7、8）

### 行动建议

#### 必须处理

1. **在需求/设计文档中声明「reasoning 永不回传」硬约束** — 对应意见 6 的功能影响（token 与延迟随轮次放大）
2. **为会话写入补 RMW 保护设计**（会话级串行化或乐观锁）— 对应意见 2 的功能影响（消息静默丢失）
3. **拆分 R11**：R11a 状态指示保持 P0；R11b reasoning 内容展示降为 P1 并绑定 T5 由用户拍板 — 对应意见 3 的功能影响（范围偏离用户确认）

#### 建议处理

1. **修正验证报告中全部定量表述**：延迟标注单次采样 + 附 3 次采样分布；"成本差 20 倍"改为"completion token 量差约 20 倍（未计单价）"；"全部模型"改为"抽测 7/7"
2. **补测真实页面布局基线**（daemon 启动后测 1280/1440/1600 三档）后再定降级阈值
3. **把"框架层 SSE 可用"列为设计前置门**（真实 daemon 上一个最小流式端点验证）

#### 可选处理

1. "新进程读盘 ≈ daemon 重启"表述收紧
2. 补充反向代理缓冲与模型限流两个场景到设计文档

## 全局回扣

| 回扣 | 结论 |
|---|---|
| **目标回扣** | 本需求的**技术目标**（对话面板能跑）已被验证；但**产品目标**（让用户愿意在知识库页面里对话）未被验证——D1 决定不接知识库时，面板与通用 LLM 客户端无差异，用户是否留在这里对话属未验证假设，建议列入下一增量评估 |
| **位置回扣** | 调用链：`浏览器 → demo server → 上游 API` vs 生产 `浏览器 → mcp-http.ts(鉴权/快照/协调器) → handler → 上游 API`；差异集中在框架层（意见 4），不影响方案方向，但影响"验证完成度"的表述 |
| **判据回扣** | 整体成功判据「既有 5 个页面功能不被破坏」：目前仅完成"布局会被挤压"的事实确认，**改造后既有页面仍可用**尚未验证 → 已列为 R3 硬性验收，须在实现后回归 5 个页面 |
