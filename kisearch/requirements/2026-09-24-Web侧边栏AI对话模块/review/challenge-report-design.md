# 🎯 设计文档质疑报告（二次质疑 · auto-review 接力）

> 质疑对象：`design/DESIGN.md` + S01~S05（design-review 通过后的对抗式再审）
> 质疑模式：设计文档模式（design.md 策略）+ auto-review Step 7 过滤
> 前置：专家资产查询因 ki daemon 不可用跳过；本报告同时承担 auto-review 的 Step 6/7 产出

## 📋 设计上下文确认

- **目标**：Web 任意页面右侧常驻面板完成对话闭环（多轮 / 历史 / 归档 / 提示词），模型由用户配置
- **覆盖**：`config.llm` 与后端代理（S-01）、会话存储与写入一致性（S-02）、前端面板与流式（S-03）、会话管理与提示词（S-04）、思考折叠展示（S-05）
- **隐含假设**：单用户单机低并发；可能启用 token 鉴权（`authScopes`）；上游实现差异需容错；会话归属跟随 scope

## ⚔️ 反对意见

### 意见 1：`/api/chat/conversations/:id` 不含 scope，存在越权与查找歧义（🟡，已修复）

- **反对理由**：会话按 scope 分目录存储，但所有按 id 操作的接口路径都不含 scope。服务端要么跨全部 scope 扫描（知道 id 即可读他 scope 会话 → 越权），要么依赖调用方另行传 scope（契约未定义 → 实现歧义）。
- **功能影响**：预期「会话按 scope 隔离，越权被拦截」→ 实际「跨 scope 探测或误读，鉴权形同虚设」
- **严重程度**：🟡 重要（安全 + 契约完整性）
- **替代方案**：查找范围限定在 token 授权 scope 内 + 命中后复核会话 `scope`；越权统一返回 403（不用 404，避免状态码探测）
- **验证方法**：用仅授权 `scopeA` 的 token 请求 `scopeB` 下的会话 id，应得 403；遍历范围内无此 id 得 404
- **处理**：✅ 已写入 S-02 §3.4（含 id 全局唯一性约定）

### 意见 2：中止时答案为空的消息语义缺失（🟡）

- **反对理由**：reasoning 模型实测可能在思考阶段消耗 99% 的 completion 预算（思考 1070 / 答案 10 token），用户点「停止」时**很可能 `content` 为空**。S-02 的 `aborted:true` 与 S-05 的中止说明都假定"已有部分内容"，未定义空内容的情形：落盘一条空消息？还是完全不落盘？
- **功能影响**：预期「中止保留已生成部分」→ 实际「会话里留下一条空助手消息，刷新后像数据丢失，或列表预览显示空白」
- **严重程度**：🟡 重要
- **替代方案**：`aborted && content === ''` → **不写入 assistant 消息**（仅前端本地提示"已中止，本次无输出"），避免污染会话与预览；`content` 非空才落盘
- **验证方法**：在思考阶段（首字后、首答前）点停止，检查会话文件中无空 assistant 消息

### 意见 3：需求 T2（会话 scope 归属）未随设计决策回写（🟡）

- **反对理由**：设计已按"会话跟随 scope"落地（父文档决策点 + S-02 路径 + S-04 联动），但 `requirement.md` §8 中 T2 仍为「待定（建议跟随）」。文档状态不同步会让评审者误以为该决策仍开放，实现期也可能被当作可变项。
- **功能影响**：预期「需求与设计状态一致」→ 实际「审阅者按待定项重新讨论已落地决策，返工风险」
- **严重程度**：🟡 重要（一致性）
- **替代方案**：需求 §8 T2 状态改为「✅ 已确认（2026-09-24，随设计决策 D9）」，并在 §0 决策表补 D9
- **验证方法**：`req list --id REQ-20260924-001` 与文档交叉核对

### 意见 4：`config doctor` 对 `llm` 缺失的处置未定义（🟡）

- **反对理由**：S-01 影响范围提到「`config doctor` 输出需补 llm 段状态」，但未定义该检查是 fail 还是 warn。既有 `config doctor` 承载启动自检语义（`src/mcp-server.ts:694-714` 的 embedding 预检"失败仅 warn"），若 llm 缺失被判 fail，会让**未使用对话功能的用户升级后自检变红**。
- **功能影响**：预期「新增配置项有自检」→ 实际「不用对话的用户被误报故障」
- **严重程度**：🟡 重要
- **替代方案**：明确 llm 缺失在 doctor 中为 **warn**（与 embedding 预检同级），仅在调用对话接口时 fail-loud
- **验证方法**：无 llm 段的配置执行 `ki config doctor`，应只出现 warn

### 意见 5：`ConversationFile.version` 与全局 `CURRENT_DATA_VERSION` 的语义重叠（🟢）

- **反对理由**：设计固定写 `version: 1`，而 `writeJson` 会自动注入 `CURRENT_DATA_VERSION`（`src/lib/store.ts:59-62`）。将来全局版本升到 2 时，会话文件会被写成 2，与"固定 1"的设计描述冲突。
- **功能影响**：预期「版本语义明确」→ 实际「实现者可能硬编码 1，或误判旧文件兼容性」
- **严重程度**：🟢 建议
- **替代方案**：明确"`version` 跟随全局 `CURRENT_DATA_VERSION`，业务不硬编码"
- **验证方法**：代码审查时确认写入路径未硬编码

### 意见 6：`meta.ttfbMs` 的服务端口径与用户感知口径未区分（🟢）

- **反对理由**：S-03 界面展示「首字 469ms」来自**服务端测量**（请求上游 → 首个 chunk），不含网络与渲染时间；用户实际感受从点击算起。两者混用会让性能优化判断失准。
- **功能影响**：预期「用量数据反映真实体验」→ 实际「指标偏乐观，掩盖前端渲染延迟」
- **严重程度**：🟢 建议
- **替代方案**：前端另记 `userPerceivedFirstByteMs`（点击 → 首个渲染帧）并区分展示，或明确标注为"服务端首字"
- **验证方法**：对比同一请求的前后端计时差

### 意见 7：归档会话仍可继续对话，会让归档视图持续上浮（🟢）

- **反对理由**：S-02/S-04 都允许在已归档会话继续对话并按 `updatedAt` 排序，导致归档区被"活跃但归档"的会话占据顶部，与"归档=我不看了"的心智冲突。
- **功能影响**：预期「归档用于收敛列表」→ 实际「归档列表被顶起，用户仍需再归档一次」
- **严重程度**：🟢 建议
- **替代方案**：发消息时自动取消归档（`archived→false` 并提示），或在归档列表按 `archivedAt` 而非 `updatedAt` 排序
- **验证方法**：归档一个会话 → 继续对话 → 检查其所在视图与排序

### 意见 8：上游错误原文（≤200 字）直接回传浏览器（🟢）

- **反对理由**：S-01 异常表把上游错误体截断原文回传前端"便于排查"。虽为本地单用户场景，但上游错误体可能包含凭据片段、内部主机名或请求 id。
- **功能影响**：预期「错误可排查」→ 实际「上游内部信息可能被写入浏览器控制台/截图外流」
- **严重程度**：🟢 建议
- **替代方案**：错误体仅写入 daemon 日志，前端只给规范化文案 + 一个"复制诊断信息"按钮（按需拉取）
- **验证方法**：构造上游 500，检查响应体中无原始错误体

### 意见 9：未约定并发生成上限（🟢）

- **反对理由**：多标签页 × 多会话可同时发起多个 12s 量级的长流，设计未约定上限（上游常有并发限制，且 Windows/Linux 下每个流占用 socket 与内存）。
- **功能影响**：预期「面板始终可用」→ 实际「并发超限时上游 429、或本地资源紧张导致全部变慢」
- **严重程度**：🟢 建议
- **替代方案**：daemon 侧对"进行中的生成"计数（建议上限 3~5），超限返回 429 `CHAT_BUSY` 并提示稍后重试
- **验证方法**：并发发起 10 个请求，观察是否被限流且有明确提示

### 意见 10：`configPath` 绝对路径回传前端（🟢）

- **反对理由**：`GET /api/chat/config` 返回配置文件绝对路径供 fail-loud 文案使用；本机单用户可接受，但若将来经反向代理暴露到局域网/公网即成为路径泄露。
- **功能影响**：预期「配置指引清晰」→ 实际「暴露服务器目录结构」
- **严重程度**：🟢 建议
- **替代方案**：返回相对路径或仅返回文件名（`~/.ki/config.yaml` 形式），文案改为"请在配置文件的 llm 段填写……"
- **验证方法**：检查响应体中无绝对路径

## ✅ 认可点

1. **写入一致性问题被正确识别并给出双重保障**（daemon 内 mutex + `seq` 审计），且明确划出了"生成期间不持锁"的性能边界
2. **reasoning 隔离做到了结构性保证**：`ChatMessage` 不含该字段，从数据模型层面消除误回传可能，比"记得别传"更可靠
3. **设计明确保留了被否决方案与否决理由**（单一大 JSON / SQLite / zvec / EventSource / sessionStorage），后续评估可直接复用
4. **降级策略修正为按主内容区实测宽度判定**（而非统一视口阈值），避免了非 Browse 页过早降级
5. **前置门被显式列出**（框架层长流、真实布局基线、并发不丢验证），未把"未验证"包装成"已完成"

## ➕ 补充场景

| 场景 | 说明 | 建议归属 |
|---|---|---|
| 上游返回空 `choices` 但流未结束 | 部分实现会先发 usage-only chunk | S-01 容错：无 choices 时跳过，不计入解析失败 |
| 会话文件被手工编辑（字段缺失） | 用户可能直接改 JSON | S-02：读取时做字段兜底（缺失取默认值），不抛错 |
| 系统时间回拨导致 `updatedAt` 乱序 | 列表排序异常 | 低频，接受；排序键含 id 可保证稳定 |
| 长会话（500 条）详情响应体较大（数 MB） | 面板加载慢 | 超出本期范围；已列"提示新建会话" |
