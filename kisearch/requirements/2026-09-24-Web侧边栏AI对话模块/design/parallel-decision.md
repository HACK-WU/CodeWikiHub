# 并行交付判定 + 模块划分 + 骨架交付清单

> 依据：`design-craft` 阶段 5.5（判定标准 SSOT 在 `delivery-slicing` 快速通道五条）
> 输入：`requirement.md` v7 + `design/S01~S07`（含 v2 修订）+ `api/`（14 接口）
> **本文件是「走并行 / 走串行」的决策书，也是骨架生成（`design-to-code`）的输入**

---

## 1. 并行交付判定

### 1.1 五条判据逐条核对

| # | 判据 | 实测 | 结论 |
|---|------|------|:---:|
| 1 | 可并行砖头 **≥ 3 片** | 真实契约边界只有 **2 条**（后端链 / 前端链，中间靠 SSE 协议解耦）→ **2 片** | ❌ |
| 2 | 骨架成本 + 公共前置 **< 50%** | 见 §1.2 估算：**≈ 55%**（协议 + 类型 + 配置全是前后端共享面） | ❌ |
| 3 | 契约稳定 + **风险点已验证** | 契约刚随 D13 修订（未沉淀）；**前置门① 未清**（daemon 框架层 + 工具往返未验） | ❌ |
| 4 | 主干可编译 + 可提供独立工作副本 | `tsc --noEmit` 退出码 **0** ✅；git worktree 可用 ✅ | ✅ |
| 5 | 用户要求分窗口并行 | 用户要求"走完整链"，未强制并行 | ⚠️ |

**判定：不满足全部五条 → 按判据应走单窗口串行。**

### 1.2 为什么可并行砖头只有 2 片（这是本需求的结构性事实）

```text
后端（一条串行链，无法内部并行）：
  llm-client(tools 支持) → retrieval(工具/投影/循环) → chat-store(sources) → mcp-http-api(路由)
  └─ 后一个依赖前一个的【实现】，不是只依赖接口 → 同批不可拆

前端（一条串行链）：
  AppShell(常驻 store + 开关) → ChatPanel(事件消费) → 来源引用 UI / 工具步骤展示
  └─ 同样逐层依赖

两端之间：靠 SSE 事件协议 + config 字段解耦 → ← 唯一可切的地方
```

### 1.3 真实账目（并行 vs 串行）

| 方案 | 骨架 | 并行段 | 集成 | **总计** | 用户人工动作 |
|------|:---:|:---:|:---:|:---:|:---:|
| **串行** | 共用（但可更薄） | A 2d + B 2d = **4d** | 0.5d | **≈ 5.5d** | ~2 次 |
| **并行（2 片）** | 更厚（协议冻结 + 契约测试 + mock） | **max(2d, 2d) = 2d** | 1.5d | **≈ 5d** | **~9 次**（2×(建副本+粘 handoff+配环境+收片) + 拼接） |

**净收益 ≈ 0.5 天，代价是用户多 7 次人工动作。**

> 按链路自己的调度成本口径（`≈ 4N + M + 1`，N=2 → 9 次），**这个账不划算**。
> 收益被两件事吃掉：① 只有 2 片（并行度低）；② 骨架必须做厚（协议 + 契约测试 + mock），而串行路线下骨架可以更薄。

## 2. 5.5.1 模块划分（无论走哪条路都需要）

### 2.1 砖头清单

| 砖头 | 类型 | 独占写（**已核对互斥**） | 只读 / 禁碰 | 依赖 | 承接需求 |
|------|------|------------------------|------------|------|---------|
| **SR-01 后端检索与生成链** | 新增型 + 挂载型 | `src/lib/retrieval/**`（新增）<br/>`src/lib/llm-client.ts`（新增）<br/>`src/lib/chat-store.ts`（新增）<br/>`src/lib/retrieval-*` 前缀配置 | 只读：`src/search.ts`（**复用不改**）<br/>禁碰：`web/**` | — | S01 v2 / S02 v2 / S07 / API-01, 08, 11~14 |
| **SR-02 前端对话面板** | 新增型 + 挂载型 | `web/src/**` | 只读：`src/**`（只读契约）<br/>禁碰：`src/**` 写入 | SR-01 的**接口**（SSE 协议 + config 字段） | S03 v2 / S05 v2 / API-01, 08, 11~14 |

**互斥校验**：`src/lib/**` ∩ `web/src/**` = **∅** ✅ 可同批。

> 前后端天然目录隔离，是**最容易并行的一类场景**——这也是本需求仍值得讨论"是否放行"的原因（判据在边界上）。

### 2.2 依赖 DAG

```text
SR-01 ──(接口级：SSE 事件协议 + ChatConfigOk 字段)──> SR-02
```

**依赖性质判定（决定是否形成批次）**：

| 依赖 | 性质 | 处理 |
|------|------|------|
| SR-02 需要 SR-01 的 **事件协议 / 字段形状** | **接口级** | → **骨架（类型 + 桩）**，不形成批次 ✅ |
| SR-02 需要 SR-01 的**真实 SSE 流**才能端到端验证 | 实现级 | → 靠 **mock**（冻结点提供 mock SSE 流），拼接期换真实 |

**结论：若走并行，1 批即可**（两片同批），无需分批。

## 4. 路线选择（**待用户拍板**）

| 方案 | 内容 | 验证到的机制 | 代价 |
|------|------|-------------|------|
| **A 尊重判定：走串行** | `plan-track` + 薄骨架（第 1/2/5 项，砍掉 mock 与数据走向预演）+ 单窗口实现 | ✅ 验证「判据真的会拦住不该并行的需求」<br/>❌ 验证不到切片 / 砖头包 / 拼接 | 与用户"走完整链"的预期不符 |
| **B 放行并行（边界情况）** | 走 §2 的 2 片 + §3 完整 11 项骨架 → 切片 → 子 agent 并行 → 拼接 | ✅ 验证链路**全部机制**（骨架 11 项 / 目录互斥 / 零上下文自包含 / 6 拒收门 / 语义验收）<br/>✅ 得到真实数据（并行到底省不省） | 已知总账不划算（净收益 0.5d，用户动作 +7 次）；**但这是拿真实需求换链路验证数据** |

**AI 建议：选 B，但要如实记账。**

理由：本需求是**判据的边界情况**（2 片、目录天然互斥），不是"明显不该并行"（那种情况下放行毫无价值）。放行能得到链路全部环节的真实数据，且 §1.3 的账目本身就是**链路最有价值的产出之一**——它第一次把"并行到底省不省"算成了具体数字。

**若选 B，必须显式记录**："本次为边界放行，判据 1/2/3 均未通过；放行目的是验证交付链机制，不作为该需求的最优实施建议。"

**若选 A**：`design/parallel-decision.md`（本文件）§1 即为最终结论，转入 `plan-track` 串行，§3 骨架清单按 §4-A 裁剪。
