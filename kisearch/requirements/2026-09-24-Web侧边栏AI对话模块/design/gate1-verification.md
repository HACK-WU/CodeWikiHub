## 2. 三条实现级发现（**S07 原设计未写死，必须补**）

### 2.1 一次响应可能返回**多个** `tool_calls` —— 每个都必须有对应的 `tool` 消息

实测：第一轮返回 **2 个** `kb_search` 调用。首版脚本只执行了第 1 个，**模型随即反复请求**。

> **协议要求一一对应**：`assistant` 消息里的 N 个 `tool_calls`，必须跟 N 条 `tool` 消息（各自的 `tool_call_id`）。
> 漏一个 → 模型认为"工具没答完" → 继续请求，**表现为循环不收敛**（易被误判为"模型太笨"）。

### 2.2 单次往返**不够**，必须有循环（S07 §3.4 的循环设计必要）

实测的完整往返序列：

```text
round 1  2 个 tool_calls（hybrid / fulltext 各一）
round 2  又 1 个 tool_calls（换 query 再试）
round 3  仍要调工具 → 【拿掉 tools 后强制作答】→ finish_reason=stop，终答 155 字
```

模型在**明知已有检索结果**的情况下仍连续 3 轮请求工具。

### 2.3 ★「强制作答」的**实现方式**：达轮次上限后**拿掉 `tools` 再调一次**

原设计只写了"强制作答"（S07 §3.4 硬约束 3），未规定怎么做。本次验证确定：

| 做法 | 结果 |
|------|------|
| ✅ **拿掉 `tools` 参数再调一次** | 模型只能作答 → `finish_reason=stop`，正常收敛 |
| ❌ 直接截断（不发请求，用已有内容收尾） | 会得到**空终答**（模型还没来得及产出 content）—— 实测 round 3 之前每轮 `content` 均为 0 字 |

> **这一点必须写进实现**：轮次上限到达时**不是停止**，而是**换一种方式再问一次**。

## 3. 对 T11（工具轮次上限）的评估

**结论：3 轮「刚好够用，但没有余量」。**

| 观察 | 含义 |
|------|------|
| 本次最简场景（单轮提问 + 1 个 mock 工具）就用了**满 3 轮** | 真实场景（知识库更大、问题更复杂）**很可能超 3 轮** |
| 且第 3 轮是**强制**收敛 | 若有第 4 轮需求，当前设计会**强行截断** → 可能答不完整 |

**建议（不阻塞实现，交用户/实现期定）**：

- **保持默认 3**，但**必须实现 §2.3 的强制作答**（否则会空终答）
- 前端在 `done` 事件带 `warning:'tool-rounds-exhausted'` 时**提供「继续检索」按钮**（用户手动放行 1–2 轮）—— 比单纯提高默认上限更省成本
- 若实测发现真实场景频繁触顶 → 再评估是否把默认提到 4–5

## 4. ⚠️ 未覆盖清单（**诚实边界，不得省略**）

| 未覆盖项 | 为什么 | 何时补 |
|---------|--------|--------|
| **真实 daemon 的鉴权**（Bearer → scope 集合） | 本脚本是独立进程，无鉴权层 | 实现期第一步（在真实 daemon 挂载后） |
| **配置快照**（`runWithConfigSnapshot`） | 同上 | 同上 |
| **越权白名单登记**（带 scope 的 GET） | 同上 | 同上 |
| **长连接关闭语义**（客户端断开 / daemon 退出时的清理） | 同上 | 同上 |
| 检索质量（用本地 mock，不碰真实 zvec） | 本门只验"能不能通"，不验"检得好不好" | 拼接期语义验收 |
| 多轮工具循环下的**总时长**（300s 预算是否够） | 本次 3 轮总耗时 <15s；真实检索更慢 | 实现期实测 |

> **放行判断**：⑤ 项未覆盖中，前 4 项在既有代码里**已有 13 条路由的先例**（框架层机制成熟、非新风险）；
> 真正**无先例**的两项（SSE 长流、工具循环）**已通过**。
> 故判定：**前置门主体通过，可进入切片**；框架层验证并入实现期第一步（在真实 daemon 挂载后立即补跑）。

## 5. 复现方式

```bash
# 凭据通过环境变量传入（不落盘）
LLM_API_KEY=xxx LLM_BASE_URL=xxx LLM_MODEL=xxx node .delivery/verify-gate.mjs
# 或写入 .delivery/llm.env（已 gitignore）
```

**两次运行的数据方差**（同一提示词）：

| 指标 | 第 1 次 | 第 2 次 | 倍差 |
|------|:---:|:---:|:---:|
| 总时长 | 29292 ms | 48557 ms | 1.66× |
| TTFB | 679 ms | 1205 ms | 1.77× |
| reasoning 字数 | 1476 | 4767 | 3.23× |
| reasoning / completion | 60% | 84% | — |

> **方差印证**：与 `demo/verify-report.md` §2/§3 的"单次采样波动近 2 倍"一致。
> **推论**：超时预算（整体 300s）**不可按单次最优值设计**，必须按最坏档留余量。
> **另一推论**：reasoning 占 completion 的 60%–84% → **D7/N12（reasoning 不落盘、不回传）的收益远大于预估**（若误回传，token 成本与延迟同时放大 4–5 倍）。
