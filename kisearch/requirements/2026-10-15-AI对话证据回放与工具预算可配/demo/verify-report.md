- **判定手法**：请求携带 `ki_search` 工具定义（与设计一致的 schema：`maximum=50`、无 default），**只发第一次响应**——看模型**是否发起 tool_call**

- **运行**：`env -u NODE_OPTIONS -u BASH_ENV node demo/probe.mjs`

## 2. 逐风险点结论

### 【R-01 上游对长 user 消息的接受度】✅ 通过

- **依据**：21294 字符的 user 消息 → **HTTP 200**，正常返回，TTFB 1343ms，无 400 / 无长度告警
- **备注**：单次探测；最坏组合（引用块 6000 + 证据块 20000 ≈ 26K）未覆盖，真实回放时按 S-02 §9 复验

### 【R-02 回放的成本与延迟】⚠️ 有条件通过

- **依据**：20K 字符证据 → promptTokens **10183**（基线 549 的 **×18.5**）；TTFB **1343ms**（基线 957ms，**+40%**）⇒ **超出 S-02 §9 的"≤ 基线 +30%"判据**
- **调整项**：`replayMaxChars` 由 **20000 下调至 10000**（按实测线性外推，TTFB 增量可回落至 +20% 内）；同步更新 S-02 §3.4 预算推导与 §9 判据
- **补充**：中文 token 效率高于预期（20K 字符 ≈ 9.6K token ≈ 2 字符/token），成本侧可接受

### 【R-03 S-03 判据是否让模型不再重复检索】✅ 通过（**强证据**）

- **依据（对照实验）**：同一问题、同一份证据，**仅措辞不同** ——
  - T2（旧口径）→ **发起 `ki_search`** ⇒ **复现了用户报告的"引用已在上下文仍重复检索"**
  - T3（新口径）→ **不调用工具，直接基于证据作答**
- **意义**：S-03 的三处文案改动被证明**直接有效**，且成本极低（无需实现 S-02）—— 交付顺序"**S-03 先行**"获得执行性证据支撑

### 【R-04 模型是否误判证据块为"用户新输入"】⚠️ 有条件通过

- **依据**：T3 回答直接进入知识内容（`## 一、kubectl rollout restart 做了什么`），**未出现**"你给的资料里…"或反问"你指的是哪一段" ⇒ 未观察到误判
- **调整项/观察点 1**：**T4（长证据）下模型仍选择检索** ⇒ 证据块过长时 S-03 判据的作用被削弱。**部分归因于夹具质量**（T4 证据是同一段文字重复 ~57 次，语义高度冗余，模型可能判定"证据不可用"而重新检索）—— **不得据此断定"长证据必然失效"**，需在真实回放下复验
- **观察点 2（正向）**：T4 中模型**自主传 `limit=10`**（> 默认 5）⇒ 实证 D5「放开 limit 上限让 AI 自主控制」的设计价值——模型确实会按问题复杂度调大条数

### 【整体决策】⚠️ 更新设计后进入开发

调整项（已执行，见 §3）：S-02 回放预算 20000 → 10000；TTFT 判据按新预算重述；新增"长证据下模型行为"观察点。

## 4. 局限声明（诚实标注）

1. **单次探测**：每用例 1 次调用，未做多次取稳定性（模型行为有随机性；T2/T3 的对照差异较大，结论方向可靠，但比例数字不宜外推）
2. **T4 夹具失真**：长证据为同一段落重复拼接，语义冗余，**不能代表真实回放**（真实证据是不同文档片段）
3. **未执行工具**：只验证"是否发起调用"，未验证"拿到检索结果后的行为"
4. **未覆盖**：26K 最坏组合、多轮累积回放、`regenerate`/`edit` 路径、压缩后场景 —— 属实施后的 e2e 范围
