# 🎯 设计文档质疑报告（challenger · 设计模式）

- **质疑对象**：`design/DESIGN.md` + `S01/S02/S03_*_DESIGN.md`（design-review 通过后）
- **前置**：design-review 1🔴+5🟡+3🟢 已修复并通过增量再审
- **用户裁决**：**1 + 2**（按意见修订设计 + 报告落盘）

## 📋 设计上下文确认

- **核心目标**：让 AI 在持续对话中拿到完整证据（历史工具返回 + 引用），并把两个工具预算（返回字符上限 / 检索条数）交给用户与 AI 控制
- **范围**：S-01 工具预算可配 · S-02 历史证据回放 · S-03 提示词证据复用；排除协议消息重建、`config.yaml` 层、回放可视化
- **关键约束**：单机单用户；上游 OpenAI 兼容（长消息容忍度未知）；旧会话零迁移；不破 N17
- **隐含假设**：① 上游接受较长 user 消息；② `progress[].response` 可用于回放；③ 回放成本上升用户可接受

## ⚔️ 反对意见

### 意见 1：预算注入点与执行路径不符 —— `searchHitsPerCall` 会静默不生效 🔴

- **反对理由**：S-01 §3.3 把默认值注入放在 `enabledChatToolEntries` 返回的包装 `run` 上；但 `tool-loop` 执行工具走 `getChatTool(call.name)`（`src/lib/chat/retrieval/tool-loop.ts:676`）——**注册表原始 entry**，而 `runtime.toolEntries` 仅用于 `toolDefs`（`:524`，喂 schema）。包装的 `run` 永不被调用。
- **功能影响**：预期"把检索条数默认值调成 8 → AI 不传 limit 时按 8 检索" → 实际"**仍是 5 且无提示**"（静默失败）
- **严重程度**：🔴 致命
- **替代方案**：(a) 注入点移到 **tool-loop 执行前**（`entry.parse` 后、`entry.run` 前）：`parsed = applyBudgetDefault(entry.name, parsed, runtime.budget.hitsPerCall)`（推荐）；(b) 执行查找改走 `runtime.toolEntries.find(...)`（顺带修"被关闭工具仍可执行"的既有隐患，改动面更大）
- **验证方法**：配置 `searchHitsPerCall = 8` → 断言 `executeSearch` 收到的 limit = 8

### 意见 2：证据块构造无异常降级 🟡

- **功能影响**：预期"回放失败最多是没有证据" → 实际"**整个回答生成失败**"（脏数据让会话不可用）
- **替代方案**：构造包 `try/catch`，失败视作无证据 + 生成继续

### 意见 3：历史证据与本轮引用块未去重 🟡

- **反对理由**：S-02 §3.1 只排除"本轮 refs 不参与收集"，未把收集结果与本轮 refs 比对；前端 pendingRefs 多轮携带 ⇒ 同一片段常在两处出现
- **功能影响**：同一片段重复占位（最多白耗条级预算），可能误导模型对证据量的判断
- **替代方案**：收集后按 `(group, doc, text)` 与本轮 refs 比对，命中即剔除

### 意见 4：交付顺序值得重排 —— 先用 S-03 验证收益，再定 S-02 规模 🟡

- **反对理由**：S-03（成本最低）与 S-02（成本最高、带来持续成本）解决同一症状的两个成因；设计把 S-02 定为主体并给出固定预算，但无"先测 S-03 再定预算"的路径
- **功能影响**：可能为已被提示词部分解决的问题付出每轮 +2 万字符的持续成本
- **替代方案**：顺序改为 **S-03 → 实测 → S-01 → S-02**（据实测确认回放预算与范围，可缩为最近 2 轮或仅回放 `ki_get_module_info` 整篇原文）

### 意见 5：缺成本/延迟量化验证项 🟡

- **反对理由**：全局风险只写"成本与延迟线性上升"，验证标准里无可测指标；`replayMaxChars = 20000` 无推导依据
- **功能影响**：预算可能过大（每轮多付 2 万字符）或过小（证据半截不可用），上线后无从判断
- **替代方案**：补三项实测（prompt tokens 增量、TTFT 不超过基线 +30%、预算推导过程）

### 意见 6：上游拒绝长 user 消息时无兜底 🟢

- 建议登记为待定问题（去掉证据块重试一次的兜底成本不低，与 `degraded` 事件语义需一起评估）

### 意见 7：单轮 user 消息总量未量化 🟢

- 本轮 user = 问题 + 引用块（≤6000）+ 证据块（≤20000）⇒ 最坏 26K+ 字符；补估算说明

## ✅ 认可点

- **"证据已落盘 ⇒ 零迁移"**：把 S-02 从"新增存储"降为"读取 + 渲染"，是全设计最有价值的降本决策
- **压缩联动靠"只遍历 `conv.messages`"天然满足**：无额外状态，不易回退
- **S-01"schema 静态 + 运行时注入"路线正确**（仅注入点选错）；保留 `maxHitsPerCall` 常量名同时服务页面投影，避免投影口径漂移
- 决策点表每条都有被否决方案 + 可观测触发条件

## ➕ 补充场景

- 证据块内"当时已截断"的半截 JSON 与本轮完整返回可能并存 → 建议验证标准加"含截断证据的追问仍能正确作答"

## 🔍 质疑详情

### 质疑 #1：**失败步骤的响应被当作证据回放** ✅ 成立（已当场修复）

- 🏷️ 类型：数据守恒 — 内容（证据质量）
- 📍 涉及：`replay.ts::collectReplayItems` 的工具步骤收集条件
- ❓ 质疑点：`progress` 的**失败步骤同样带 `response`**（`tool-loop.ts:707 / :739 / :774` 三条错误路径都 `serializeToolResponse({error:...})` 且落盘），而原收集条件只过滤 `phase` / `kind` / 空 text ⇒ **历史错误会被当证据回放**
- 🔍 验证方法：断言含 `error` 字段的步骤不产出 `ReplayItem`
- ⚠️ 风险：证据块混入 `{"error":"未知工具 ghost_tool"}` / `{"error":"检索超时"}` ⇒ 模型可能**误判某工具不可用**，或重复复述历史错误
- 📊 置信度：**高**（错误路径代码可直接确认）
- 💡 建议：收集时跳过 `p.error` 非空的步骤
- **处置**：✅ **已修复** —— `replay.ts` 增 `if (typeof p.error === 'string' && p.error.length > 0) continue;` + 回归用例（覆盖"未知工具"与"执行失败"两种形态）；复跑 `evidence-replay` **20/20**、后端全量 **315/315**

### 质疑 #2：`toolResponseChars` 配置生效缺端到端断言 💤 可延后

- 🏷️ 类型：测试覆盖
- 📍 涉及：`test/chat/tool-budget-injection.test.ts`（只断言"未配置 → 内置 10000"）
- ❓ 质疑点：单元级已覆盖 `serializeToolResponse(v, limit)`，但"配置 20000 → `tool_end.response.limit=20000`"的端到端链路未断言
- 📊 置信度：中
- **过滤结论**：💤 **可延后** —— 该链路两个环节（配置读取 → `runtime.budget`、`runtime.budget` → 序列化）已分别被单测覆盖；常规编码不会做错

### 质疑 #3：长证据下"证据复用判据"可能被削弱 🟢 已知（设计已登记）

- 🏷️ 类型：边界条件 — 极端输入

- 📊 置信度：中 —— 该夹具为同段文字重复拼接（语义冗余），**不能代表真实回放**
- **过滤结论**：非代码层面 → **保留**；已在设计 S-02 §10 Q6 登记为观察点（修复动作 = 重启后真实回放复验）
