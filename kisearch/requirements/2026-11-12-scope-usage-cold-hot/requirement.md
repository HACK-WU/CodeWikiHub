## 1. 结论先行

1. **「参考 group 冷热」只能参考形态，不能参考数据。**
   group 冷热分 = `useCount / (1 + 距上次使用小时 / 24)`（`src/lib/scoring.ts:84-101`），而 `useCount` 全仓只有 3 个加 1 点：`ki_get_module_info` 读原文（`src/get-module-info.ts:393-401`、`:666-671`）与「同名重复写入」（`src/sync-relation.ts:207-220`）。**检索（`ki_search`）完全不加热度**（`src/search.ts` 对 `useCount/lastUsedTime/recordUse` 均 0 命中），且 `MAX_USE_COUNT = 10` + 5 分钟防刷（`src/lib/constants.ts:20-21`）⇒ 饱和的相对排序，做不了调用量。→ 已按 D1 改为新建统计。
2. **scope 级调用量目前是零。** 全仓 `hitCount|callCount|stats.json|usage.json|records.json` 0 命中，HTTP 层无请求计数。最接近的三样都覆盖不了：任务台账（7 天 TTL、只记长任务）、chat 会话文件（只含 Web 对话）、文档计数缓存（不落盘）。
3. **采集成本低，已有一个天然收口。** `operation-coordinator.submit()`（`src/lib/operation-coordinator.ts:220`）贯穿 MCP HTTP / Web REST / Web 对话（进程内直调）/ daemon RPC（CLI 实际走这条，`bin/ki.mjs:220`），`kindForMcpToolNames()`（`:131`）已判 read/write，`scopes[]` 已是本次触及的 scope 列表。
4. **可参考的 group 遗产**：`partitionByScore()`（`src/lib/scoring.ts:182-271`，泛型 + accessor 注入、含溢出回流与守恒不变量）、参数语言 `hotPercent/warmPercent/reservedEmerging/halfLifeHours`（`src/lib/constants.ts:38-49`）、`recentHours = 48` 的新兴判据（`src/query-group.ts:281-289`）。**不要参考**其「治理」语义：group 的 `maxHotCount` 只是展示口径，逐出已被移除（`src/sync-relation.ts:232-236`），且无任何调度消费冷热分区。
5. **默认排序与「找冷库清理」存在方向冲突（新发现）**：按 D6 降序，「未使用 / 冷」的 100+ 个测试残留会全部沉到 162 行末尾——恰恰是想清理的那批。→ 见 §4-R7 与 §5-负向 9。
6. **配套缺口**：Web 端没有任何 scope 处置入口（`web/src` 搜 `scope-delete|deleteScope` 0 命中，仅 CLI/daemon 有，`src/lib/daemon-dispatch.ts:79/84`）。冷热列点出「该清理谁」却无处处理。

## 4. 需求清单

### R1 冷热状态列（P0 · Kano 期望）

- 位于「层状态」右侧，取值 `热 / 温 / 冷 / 无调用`，色点 + 文字（沿用 `.ki-badge` 体系，不新造视觉语言）。
- **零调用档的文案必须是「无调用」而非「未使用」**：判据是「**本窗口内** 0 次」，中文「未使用」指向「从没人用」，而 162 行里 100+ 行会命中该档 —— 是诱发批量误删的最短路径（评审意见 3）。
- 判据：基于新埋调用量，形态复用 `partitionByScore()`（热/温/冷 + 新兴并入热，参数走 `DEFAULT_PARTITION_CONFIG`），窗口 **近 7 天**，并在卡片头显示窗口标签 `[近 7 天 ▾]`（第一版静态标签，不做切换）。
- 验收：① 造高频 / 中频 / 零调用三个 scope，分别显示 热 / 温 / 未使用；② 改 `partition_config` 后分区随之变化（阈值不写死）；③ 单测覆盖与 `partitionByScore` 相同的守恒不变量。

### R2 查询调用量列（P0 · Kano 期望）

- 独立一列，右对齐、等宽字体（`.ki-num`），千分位（`1,284`）；零值渲染 `0`，无统计期渲染 `—`。
- 口径：**仅检索类调用**（`ki_search` / `ki_group_list` / `ki_get_module_info` 等）。管理类读（浏览页的 `/api/doc/list`、`tag-list`、`export`）**不计**——否则「在页面翻过」会被记成「被检索」，冷热直接失真（设计评审意见 2 修正）。同一请求对同一 scope 最多 +1（batch 内多工具同 scope 不重复计，write 优先）。
- 验收：一次 `ki_search` 后该 scope 查询 +1、写入不变；`scope:"a,b"` 时 a、b 各 +1；在浏览页连续切 group 20 次，查询列**不变**。

### R3 写入调用量列（P0 · Kano 期望）

- 同 R2 的展示规格；口径 = 写类调用（store / sync_relation / import / datasource-sync / restore / edit / delete 等）。
- **运维动作不计**：`vector-optimize`、`datasource-add-remote` 这类不改数据的 engine-only 操作排除（评审意见 6）。
- 验收：一次 `ki_sync_relation` 后写入 +1、查询不变；只做过 `vector-optimize` 的 scope 写入列保持 0。

### R4 四列排序（P0 · Kano 必备）

- 冷热 / 查询 / 写入 / 文档数 四列表头可点击切换升序、降序。
- **默认排序（D6）**：`冷热降序（热 3 > 温 2 > 冷 1 > 未使用 0）→ 文档数降序 → scope 名升序`。第三健必须存在，否则同热度同文档数的相邻行在多次渲染间可能换位（抖动）。
- 表头用箭头指示当前排序键；默认态 `冷热 ↓` + `文档数 ↓`。
- 空值（`—`）排序位置：无论升降序一律排在有效值之后（不得因 `—` 混入头部）。
- 验收：点「查询」→ 降序 → 再点升序；刷新后回到默认排序；无统计值的行始终在末尾。

### R5 统计缺失与降级（P0 · Kano 必备）

- 统计文件不存在 / 损坏 / 读超时 → 相关列显示 `—`，`ki_scope_list` 仍正常返回，列表不报错、不空、不降级为骨架屏。
- 首次上线历史为空：统一 `—` + tooltip「自 YYYY-MM-DD 起统计」，**不得显示 0**（0 会被读成「确实没人用」）。
- 验收：删除统计文件 → 列表正常、三个数值列全 `—`、控制台无未捕获异常。

### R6 第二张表同步加列（P1 · Kano 期望 · 已确认 D8）

同页「显示注册 scope」表（`DashboardPage.tsx:549-601`，现为 Scope / 层状态 / Wiki 回写 三列）同步加「冷热 / 查询 / 写入」三列，与主表同口径同窗口。

- 验收：两张表对同一 scope 显示的冷热与调用量完全一致；该表在窄屏下的隐藏规则一并定义（届时为 6 列）。

### R7 排序方式带来的可用性补丁（P1 · Kano 期望 · 已确认 D11）

D6 让「未使用 / 冷」沉底，与「找出该清理的」目的相反；且默认不再是字母序，找特定库要靠滚动。两条补丁**与排序同批交付**：

- **冷热升序切换**（R4 已含双向）：点「冷热」一次即把「未使用」翻到最前；
- **Scope 搜索框**：卡头左侧输入框，前端过滤 `list`，零后端改动、零新增请求。

验收：① 输入 `bkmontest` 即时过滤为 4 行，清空即恢复；② 搜索结果沿用当前排序；③ 搜索与排序可叠加（先筛后排）。

### R8 Web 端 scope 处置入口（不进本期 · 建议独立需求）

冷热度真正的下一步是「冷库怎么处理」（删除 / 清空 / 归档）。Web 端目前无入口，建议单独立需求。

## 5. 负向需求

1. **统计写入失败不得影响主链路**：磁盘满 / 权限错时检索与写入必须照常成功，计数 best-effort 并只告警一次。
2. **统计文件损坏**：解析失败按「无数据」处理并就地重建，不抛错、不阻断 `ki_scope_list`。
3. **历史空窗**：显示 `—` 而非 `0`，并给出统计起始日。
4. **高频循环调用**：AI Agent 可能秒级循环检索，计数须为**按天滚动窗口桶**（固定长度整数数组），不存逐条日志。
5. **多 scope / 视图**：同一请求内同一 scope 只 +1；视图按 D3 摊到成员库，**不得视图名与成员库都记导致翻倍**。
6. **窗口不一致**：列表展示的查询/写入与冷热判定必须同窗口同数据源，否则出现「0 调用但显示热」的自相矛盾。
7. **无 scope 参数的工具**：`ki_scope_list` / `ki_view_list`（`src/lib/mcp-tools/tool-access.ts:46-49`）不计入任何 scope。
8. **冷热与文档数矛盾**：143 篇文档显示「冷」是正常结果（文档多≠用得多），须给 tooltip 解释。
9. **默认排序把冷库全部沉底**：162 行里 100+ 是「未使用」，用户想清理时必须先切升序或搜索——R7 必须与 R4 同批交付，不得后补。
10. **6 列挤压**：`bulk-verify-1786619558409` 这类长名（25 字符）在 1065px 下会顶破布局，必须截断 + title 全名，否则层状态列被挤出卡片（`.ki-card` 是 `overflow:hidden`，页面级 `scrollWidth` 仍为 0，肉眼才发现）。
11. **切换窗口后冷热不同步**（D10）：把窗口从 7 天切到 30 天后，若只重算数字而不重算冷热，会出现「近 30 天 0 次调用却显示热」——两项必须同一次重算、同一份数据。
12. **失败调用计入后数字虚高**（D7）：写入列含失败流量，用户若拿它做容量规划会高估成功量——tooltip 必须写明「含失败调用」，且不提供成功/失败拆分（避免范围膨胀）。
13. **失败调用的 scope 名未经校验就入统计**：埋点取 `args.scope` 原始字面量（不走 `resolveScope`）且失败也计入（D7），拼错的名字会建出 key → 90 天内无界膨胀。`recordScopeUsage` 必须做字符集/长度校验并设 key 数硬上限。
14. **「在页面翻过」被记成「被检索」**：管理类读（`/api/doc/list`、`tag-list`）若计入查询，冷热会被管理员自己的浏览行为刷热——查询口径必须只含检索类。
