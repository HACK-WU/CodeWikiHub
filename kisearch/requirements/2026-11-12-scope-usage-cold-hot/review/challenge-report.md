## ⚔️ 反对意见

### 意见 1：`initScopeUsage` 的落点会污染单测，并与「只有 daemon 写」自相矛盾

- **反对理由**：S-01 §9 写「`initScopeUsage(config)` 在 MCP HTTP server 启动后调用（`src/lib/mcp-http.ts`）」，同时声明「CLI 直连不初始化 ⇒ 不写」。但 `createMcpHttpServer()` 是导出函数，**测试与嵌入式调用也会创建它**（`src/lib/mcp-http.ts:614`）。任何跑 HTTP 层单测的用例都会触发 `initScopeUsage` → 拉起 30s 定时器 → 在 `dataDir` 下真实创建 `.ki-usage/scope-usage.json`。测试互相污染、CI 留下残留文件，且与「只有 daemon 是写者」的硬声明直接冲突。
- **功能影响**：预期「统计文件只由生产 daemon 写入」→ 实际「每次跑测试套件都可能在测试机/开发机生成并累积统计文件」，且定时器 `unref` 后仍可能跨用例写盘。
- **严重程度**：🔴 致命（不是展示错误，而是打破了设计自己立的「单写者」前提，后续所有并发假设失效）
- **替代方案**：`initScopeUsage` 上移到 **daemon 进程的唯一启动点** —— `src/mcp-server.ts:1321` 的 `startDaemonRpcServer()` **之前**（已核实同一进程先起 RPC 再起 HTTP）。`createMcpHttpServer` 内部不 init。
- **验证方法**：读 `src/mcp-server.ts:1319-1330`，确认 RPC 与 HTTP 同进程、且 HTTP 启动无条件；再 grep `createMcpHttpServer` 的测试调用点。

### 意见 2：「查询」口径把 Web 浏览行为也算进去，冷热会被自己点出来

- **反对理由**：S-01 用 `kindForOperation` 的 `read` 判定作为「查询」，而 `READ_OPERATIONS` 覆盖的是**所有读操作**，包括浏览页高频调用的 `/api/doc/list`、`/api/tags`、`/api/datasource/list`。管理员在浏览页点开一个 scope、反复切 group，就能把该 scope 的「查询」刷到很高，而它**没有任何 AI 检索**。冷热是按调用量算的，于是「热」会指向一个只是被自己翻过的库。
- **功能影响**：预期「热 = 这个库被频繁检索/使用」→ 实际「热 = 有人（可能就是你自己）在页面上翻过它」，基于冷热做的清理判断会走反。
- **严重程度**：🟡 重要
- **替代方案**：二选一 —— ① 查询口径收窄为「检索类」（`ki_search` / `ki_group_list` / `ki_get_module_info`），管理类读（doc-list / tag-list / datasource-list）不计；② 拆成「检索」与「浏览」两列（列宽代价大）。推荐 ①，并把口径写进列头 tooltip。
- **验证方法**：在浏览页反复切 group 20 次，对比该 scope 的查询列涨幅与 `ki_search` 一次调用的涨幅。

### 意见 3：`unused` 这个词会诱导误删，且跨窗口时自相矛盾

- **反对理由**：`unused` 的判据是「**窗口内** `read + write === 0`」。一个每月用一次的重要库，切到「近 7 天」显示「未使用」，切到「近 30 天」显示「热」。而列表上的文案是「未使用」——中文语义指向「从没人用」。截图里 162 个库有 100+ 个会显示「未使用」，用户极可能据此判定「都是垃圾」并批量清理。
- **功能影响**：预期「未使用 = 确实没人用」→ 实际「未使用 = 近 7 天没人用」，误删低频但重要的库（如季度对账用的知识库）。
- **严重程度**：🟡 重要（有真实破坏性动作的风险，但需用户主动执行删除，且 Web 端当前没有删除入口 —— 危险度因 R8 未做而降低）
- **替代方案**：文案改为「窗口内 0 次」或直接显示 `0` 而不给档位标签；「从未使用」（全局 `lastUsedAt` 缺失）单独用「无记录」表达。两者不可混用同一个词。
- **验证方法**：造一个「只在 20 天前被调用过」的 scope，分别在 7/30 天窗口下看它显示什么。

### 意见 4：失败调用的 scope 名未经校验就入统计，可被用来无限膨胀统计文件

- **反对理由**：S-01 明确「失败也计入」且埋点取的是 **`args.scope` 原始字面量**（与 `mcp-http.ts:959` 的 `queueScopes` 同源，注释写明「不经过 `resolveScope`」）。这意味着一个拼错的、或不存在的 scope 名也会在 `finally` 里 `recordScopeUsage` 建出 key。90 天保留期内，只要请求的 scope 名不断变化，`scopes` 对象就无界增长；单测里 `recordScopeUsage` 若被直接调用更是如此。
- **功能影响**：预期「统计文件规模 ≈ scope 数 × 90 天」→ 实际「规模 ≈ 期间出现过的所有不同 scope 字面量」，flush 序列化体积与 `ki_scope_list` 读放大都随之上涨。
- **严重程度**：🟡 重要
- **替代方案**：`recordScopeUsage` 入口做一次轻量校验（字符集 `[A-Za-z0-9_-]`、长度上限、以及视图名白名单判定），非法直接丢弃不计；另加一个硬上限（如 key > 2000 时拒绝新建并告警一次）。
- **验证方法**：连发 1000 次 `ki_search`，每次 `scope` 用随机串，观察统计文件 key 数量。

### 意见 5：`usageTargets` 伪代码缺去重，与正文「同批同 scope 只记一次」矛盾

- **反对理由**：S-01 §3.2 正文写「同一批内同一 scope 出现多次 → 去重后只记一次（需求负向 5）」，但紧随其后的伪代码是直接 `usageTargets.push(...)`，没有去重。实现者照抄伪代码就会双计。
- **功能影响**：预期「一次 batch 对同一 scope 记 1」→ 实际「记 N」，批量客户端（如一次 prompt 里并发多个检索）会让数字翻倍。
- **严重程度**：🟡 重要（文档内部矛盾，属实现陷阱）
- **替代方案**：伪代码改为先 `Map<scope, kind>` 聚合（同 scope 多工具时 `write` 优先），再转为数组。
- **验证方法**：构造一个 batch 含两个都是 `ki_search`、`scope` 相同的消息，断言计数 +1。

### 意见 6：`engine-only` 归入「写入」，会让运维操作污染写入数

- **反对理由**：`kindForOperation` 对 `import / datasource-sync / vector-optimize / datasource-add-remote` 返回 `engine-only`，S-01 把它映射为 `write`。其中 `vector-optimize`（向量优化）、`datasource-add-remote`（登记远程源）**不写入 scope 数据**，只是运维动作。
- **功能影响**：预期「写入 = 往这个库里写内容」→ 实际「写入 = 写内容 + 优化索引 + 改数据源配置」，用户按写入数判断「这个库在被持续维护」会得到假象。
- **严重程度**：🟡 重要（口径失真，不致命）
- **替代方案**：`engine-only` 中只把真正产生数据的（`import` / `datasource-sync` / `restore`）计入 `write`，其余运维操作不计；或统一归入「写入」但 tooltip 注明「含运维操作」。
- **验证方法**：对一个只做过 `vector-optimize` 的 scope，看写入列是否为 0。

### 意见 7：全局 `since` 无法表达「这个库从哪天开始才有数据」，分母不可比

- **反对理由**：S-02 把 `since` 定义为全局最早的日桶日期。但某 scope 可能 3 天前才第一次被调用 —— 它的 `d30.read = 5` 实际只覆盖 3 天，与一个真正统计满 30 天的库（`d30.read = 5`）在表格里长得一模一样。用户据此比较「谁用得多」会得出错误结论。
- **功能影响**：预期「同一列的数字可比」→ 实际「新库的数字天然偏小，看起来更冷」，新接入的知识库会被判成「冷」。
- **严重程度**：🟡 重要
- **替代方案**：`ScopeUsageWindow` 增 `coveredDays`（该 scope 在该窗口内实际有数据的天数，或改用每 scope 的 `firstSeen`）；前端在 `coveredDays < windowDays` 时给数字加角标或降透明度。
- **验证方法**：造一个 3 天前才开始有调用的 scope，对比它与满 30 天库的展示。

### 意见 8：视图摊分按「当前完整成员」展开，与请求当时的授权范围不一致

- **反对理由**：S-02 §3.2 聚合时用 `resolveScopeTargets(config, name)` 展开视图成员。埋点阶段记的是视图名字面量，而**请求当时该 Token 可能只被授权了部分成员**（`rejectScopeViolationRequest` 对视图做「全有或全无」判定，但 `strict` 白名单会 `skipped` 部分成员）。聚合时按当前配置完整展开 ⇒ 调用被摊到用户当时无权访问的成员上。
- **功能影响**：预期「计数落在真实被读的库上」→ 实际「计数落在视图定义的全部成员上（即使当时未授权）」，造成授权库计数偏低、未授权库（用户看不到行）计数偏高。不构成信息泄露（列表已按 RBAC 裁剪），但数字不准。
- **严重程度**：🟡 重要
- **替代方案**：接受该偏差并在文档声明（成本最低）；或埋点阶段记录 `views` 与 `members` 快照（成本高，且会让埋点不再 O(1)）。
- **验证方法**：Token 只授权视图的部分成员，调用一次后看两边的计数分布。

## ✅ 认可点

1. **三档窗口一次返回**而非传入 `windowDays` —— 正确识别了 `queryKey` 全局共享（`web/src/lib/hooks.ts:83-90`，AppShell 选择器同源）会导致的双重请求，这不是显然的选择。
2. **异步累加 + 定时 flush** —— 引用了真实历史事故（`/api/doc/list` 25s 挂死、`queue.queues` 积压）作为约束依据，而不是泛泛的「考虑性能」。
3. **先剔除 `unused` 再做相对分档** —— 若照搬 group 的 `hotPercent=0.3` 对 162 个全量分，会产出 49 个「热」其中 40+ 个是 0 调用。剔除后分档是必须的，不是可选优化。
4. **`.ki-scope-table` 独立命名空间** —— 发现 `ki.css:1281` 是全局选择器、会隐藏所有 `.ki-table` 的第 3/4 列，这个坑不查代码看不出来。
5. **`reservedEmerging: 0`** —— 主动识别出「沿用 group 参数会让新库挤掉老库」并记录偏离理由。

## ➕ 补充场景与情况

| # | 场景 | 现状 |
|---|---|---|
| 1 | daemon 未启动时 CLI 直连执行 `ki search` | 不计数（设计已声明），但用户会以为「我明明用过」——建议在文档/列头 tooltip 写明统计只覆盖 daemon |
| 2 | 统计文件被手动删除 | flush 会重建，历史丢失；`since` 会变成删除后首日 → 与「自 X 起统计」说法冲突，需接受或写明 |
| 3 | 跨时区部署（daemon 在 UTC、用户在东八区） | 日桶按服务器本地时区切分，「近 7 天」边界与用户感知差 8 小时 |
| 4 | 同一 scope 同时被直接调用与视图摊分 | 累加正确，但用户无法区分「直接用的」与「经视图用的」 |
| 5 | 总览页两个表都在 30s 内刷新 | 同一 `staleTime`，无额外请求；但 flush 30s + 缓存 30s ⇒ 最长 60s 滞后，需在 tooltip 用 `updatedAt` 说明 |

## 📊 风险评估与建议

### 🎯 裁决结论

**⚠️ 修改 1 条 🔴 + 7 条 🟡 后进入开发**（不构成重做：核心架构 —— coordinator 埋点、单文件聚合、三档同源、异步 flush —— 均成立）

### 识别的风险

- **风险 1**：测试污染与单写者假设失效 —— 可能性 高 —— 功能影响：预期统计文件只由生产 daemon 写 → 实际每次跑 HTTP 测试都创建/累积统计文件，并发假设全部失真
- **风险 2**：冷热被 Web 浏览行为污染 —— 可能性 高 —— 功能影响：预期「热 = 被频繁检索」→ 实际「热 = 有人在页面翻过」，清理判断走反
- **风险 3**：「未使用」诱导误删低频重要库 —— 可能性 中 —— 功能影响：预期「没人用」→ 实际「近 7 天没用」，季度对账类库被清
- **风险 4**：统计文件无界膨胀 —— 可能性 低（需构造请求）—— 功能影响：预期「规模 ≈ scope × 90 天」→ 实际随不同 scope 字面量数增长
- **风险 5~8**：口径与一致性缺陷 —— 可能性 中 —— 功能影响：数字双计 / 运维计入写入 / 新库分母不可比 / 视图计数偏移

### 风险等级

- **总体风险**：🟡 中风险
- **风险分布**：高 1 个，中 7 个，低 0 个

### 行动建议

#### 必须处理

1. `initScopeUsage` 移到 `src/mcp-server.ts:1321` 之前 —— 对应风险 1，否则「单写者」前提不成立，后续并发与文件锁设计全部失去依据。

#### 建议处理

1. 查询口径收窄为检索类，管理类读不计（意见 2）—— 否则「热」可能只是你自己翻页翻出来的
2. `unused` 文案改为「窗口内 0 次」，「从未使用」单独表达（意见 3）—— 避免 100+ 行同款「未使用」诱发批量误删
3. `recordScopeUsage` 入口做 scope 名字符集/长度校验 + key 数硬上限（意见 4）
4. `usageTargets` 伪代码改 `Map` 去重（意见 5）—— 文档与代码矛盾会让实现者照抄错的那份
5. `engine-only` 中仅 `import / datasource-sync / restore` 计 write（意见 6）
6. `ScopeUsageWindow` 增 `coveredDays` 或每 scope `firstSeen`（意见 7）
7. 视图摊分偏差写入文档声明（意见 8）—— 成本最低的处置

#### 可选处理

1. 列头 tooltip 补「仅统计经 daemon 的调用」「按调用次数计，非条目数」「数据滞后 ≤60s」
