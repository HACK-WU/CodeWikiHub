## 📋 需求确认（简）

- **功能目标**：让用户看得见上下文占用（字符口径 / 1000K）、在阈值前被提醒并被给出路、可手动压缩以继续对话。
- **来源**：用户口头 + 截图（🟢 明确），已落需求文档 v3（R1–R8 + N1–N14）。
- **隐性需求**（质疑者补充）：① 压缩后**立刻**看到效果；② 压缩/撤销必须可回退；③ 压缩**不得**违反既有隐私门禁（外发未确认）；
  ④ 摘要失败时用户要有**替代出路**而不是死循环重试。

## 🔍 成立质疑（已修复）

### 🔴 质疑 #1（安全 / 隐私）压缩会外发对话，但未走"外发未确认"门禁 —— **成立，已修**

- 🏷️ 类型：安全风险 + 冲突验证（与 T12 既有门禁冲突）
- 📍 涉及：`chat-routes.ts::handleConversationCompact`
- ❓ 质疑点：生成路径（API-08/11/12）统一经 `requireGenerationReady`，`status.ackRequired === true` 时 **403 DISCLOSURE_REQUIRED**
  拦截"把知识库内容发给外部模型"。而**摘要式压缩同样会把早期对话发给外部模型**，实现里却只检查了 `enabled` 与"会话是否生成中"，
  **绕过了用户尚未确认的隐私门禁** —— 用户在"未确认外发"状态下点一次压缩，对话内容就外发了。
- 🔍 验证方法：`kbDisclosureAck: false` + 调用 `POST …/compact {mode:'auto'}`，观察是否发起上游请求。
- ⚠️ 若成立的风险：**未授权的数据外发**（P0 级隐私事故面），且由于压缩是用户主动动作，用户会以为是本机操作。
- ✅ **修复**：显式 `mode:'summary'` + `ackRequired` → **403 DISCLOSURE_REQUIRED**（与生成一致）；
  `mode:'auto'` + `ackRequired` → **降级为截断式**（内容不出本机）并在响应 `warning` 里明示原因。
- 📌 验证证据：`temp/verify-context-usage.cjs` 场景 **D1/D2/D3 全过**（隔离实例 + 改写 yaml 热生效，未重启）。

### 🟡 质疑 #2（体验 / 异常出路）摘要失败后用户没有替代出路 —— **成立，已修**

- 🏷️ 类型：负向体验 — 恢复路径
- 📍 涉及：`ChatPanel` 压缩反馈区
- ❓ 质疑点：摘要式压缩失败（上游 500 / 摘要为空）时，会话保持不变（fail-loud，正确），但 UI 只给一行错误文本，
  **用户唯一能做的就是再点一次同一个注定失败的动作**；而后端其实支持 `mode:'truncate'`，前端从不发送它。
  "fail-loud + 给出路"是项目既定原则，此处只有 loud 没有出路。
- ✅ **修复**：错误反馈旁新增「改用截断式压缩」按钮（明示"不生成摘要、原对话仍会备份、可撤销"）。
- 📌 验证证据：代码 + 端到端 B3 同路径（成功态）已覆盖；按钮仅在 `err && !compaction` 时出现。

### 🟡 质疑 #3（正确性 / 数字失真）压缩后 chip 仍显示压缩前的旧值 —— **成立，实施中已发现并修**

- 🏷️ 类型：边界/状态一致性 — 数据陈旧
- 📍 涉及：`compaction.contextChars` + `ChatPanel` 取值优先级
- ❓ 质疑点：压缩移除的只是消息，**保留下来的那条 assistant 消息上仍写着压缩前的 `contextChars`**（它是"那次请求时"的规模）。
  面板直接沿用它 ⇒ 用户刚压完却看到占比不降（实测 4.3K → 4.3K，142% 不动）——**数字说谎比没数字更糟**。
- ✅ **修复**：压缩记录新增 `contextChars`（后端 `projectNextContextChars` 按**与 `context` 事件同一函数**重算：
  system 组 + 保留消息 + 摘要块）；前端仅在"压缩时间晚于上一条回答"时采用它，下一轮问答后自动切回实测值。
- 📌 验证证据：端到端 **B3e/B3f**（chip 下降且与 `compaction.contextChars` 一致）+ 单测"投影回调落盘"。

### 🟢 质疑 #4（输入边界）`keepRecent=0` 会把会话压空 —— **成立，已加守卫**

- ❓ 质疑点：`planCompaction(messages, 0)` ⇒ `keep=[]` ⇒ **会话消息全空**；API 接受请求体里的 `keepRecent`，
  虽非 UI 路径，但"压缩"语义是"保留最近 + 压掉更早"，压空属语义跑偏（备份虽在，用户会以为对话丢了）。
- ✅ **修复**：`keepRecent < 1` 显式拒绝并给人话原因 + 单测。
