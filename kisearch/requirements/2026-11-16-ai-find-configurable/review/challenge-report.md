# 质疑报告 · AI 查找可配置化（设计文档模式）

- 需求：REQ-20261116-005
- 质疑对象：`design/DESIGN.md` + `S01`~`S04`
- 质疑时间：2026-11-16
- 前置：`design/design-review.md`（第 1 轮，⚠️ 有条件通过）

## 一、反对意见

### O-1 跨库引用的「文档可见性」被漏掉（🔴 高）

**反对**：设计只定义了「可见性按源库解析」（S-02 §3.2），但没定义**不可检索（`hidden`）的跨库文档能否被加入参考文档**。

**推理链**：B 库的文档可能被 B 库的另一个事件绑定，该事件处于不可检索阶段 → `resolveVisibilityOfRelation('B', rel).mode = 'hidden'`。此时：

1. 候选行显示「不可检索」，但勾选框仍可点（`FindRefModal` 现有逻辑只按 score 默认勾选）；
2. 加入后 `refs.json` 记录成功；
3. AI 对话检索时该文档召回不到 → 用户看到「已加入的参考文档从来没被引用过」。

单库时代这个问题也存在，但用户至少能在同一页面看到那个事件；跨库后源库事件对用户不可见，问题被放大成「幽灵引用」。

**替代方案**：
- 加入时对 `hidden` 文档给**强提示**（不是静默允许）：候选行显示「源库事件 #N 使其不可检索」，勾选时二次确认；
- 或直接禁止加入（后端 409 `REF_DOC_NOT_SEARCHABLE`），并在候选列表保留展示但禁用勾选。

**验证方法**：在 B 库造一个绑定在不可检索阶段的文档，从 A 库事件查找它并尝试加入，看是否被静默接受。

---

### O-2 「全局一份 extraScopes」对多库事件是错配（🟡 中，需求已拍板但缺扩展点）

**反对**：需求阶段定的是「全局一份额外放开列表」（Q5）。但事件本身分散在不同库——给 A 库事件配的「可查 B 库」，同样会作用于 C 库事件；而 C 库用户可能不希望跨到 B 库。

**为什么现在就要管**：S-01 的 `FindRangeConfig` 只有 `extraScopes: string[]`。将来要差异化就得改结构 + 迁移配置。多写一个可选字段的成本，远低于事后加。

**替代方案**（不改当前行为）：
```ts
interface FindRangeConfig {
  extraScopes: string[];                          // 全局默认（当前行为）
  byScope?: Record<string, string[]>;             // 预留：按事件库覆盖，缺省走 extraScopes
}
```
设计里声明「本期不实现 `byScope`，仅预留字段并在校验中忽略」或明确「不预留、届时改结构」——两者都行，但不能不说。

---

### O-3 深度通道的 `score` 来源不可靠，会让「模型高置信候选」默认不勾（🟡 中）

**反对**：S-03 §3.5 说通过校验的候选「补 `score` = 该库内 `ki_search` 最后一次命中分，无命中则 0」。问题有三：

1. 模型可能**完全没调用** `ki_search`（直接凭 `ki_group_list` 猜），此时全部 score=0；
2. 「最后一次命中分」要从被截断的工具返回里解析，脆弱；
3. score=0 → `weak=true` → **默认不勾选**（`FindRefModal.tsx:75` 按 `score >= 0.6` 默认勾）。结果是模型筛过的候选，用户要逐条手动勾。

**替代方案**：深度通道的默认勾选改为「模型输出顺序的前 K 条 + 通过校验」；score 只作展示与排序辅助，不参与默认勾选判定。或在 `RefCandidate` 里加 `origin: 'fast' | 'deep'`，前端按 origin 用不同默认勾选策略。

---

### O-4 双层超时没有对齐（🟡 中）

**反对**：S-03 服务端 `timeoutMs` 缺省 45s、上限 60s；S-04 前端 deep 缺省 60s。当用户把 `timeoutMs` 配成 60s 时，**前端先超时掐断**，服务端仍在跑并计费，用户看到"查找超时"但后台还在烧 token。

**替代方案**：前端超时 = 服务端 `timeoutMs` + 10s（从 `GET /api/chat/config` 的 `find.timeoutMs` 动态取），而不是前端写死 60s。

---

### O-5 快速通道多库时 `total` 的语义变了，文案没跟上（🟡 中）

**反对**：`total` 现状是「库内文档总数」，用于 `empty-scope` 判定与过程面板展示（"共 N 篇"）。多库求和后含义变成「参与检索的文档总数」，但用户看到的是"这个库里有多少篇"的历史语义。

**替代方案**：多库时文案改为「共 N 篇（M 个库）」，并保留 `matchedByScope` 式的分库计数（`executeSearch` 已有该字段可借鉴）。

---

### O-6 「源库不存在」与「文档被删」都标 `stale`，用户无法判断下一步（🟡 中）

**反对**：S-02 说引用读取按源库解析，源库不存在时 `readAllGroupCaches` 返回空 → 全部引用标 `stale`。但 `stale` 现状语义是「文档已不存在」，用户会去源库找文档，而实际是整个库没了。

**替代方案**：`stale` 增加 `reason: 'doc-deleted' | 'scope-missing'`，前端文案区分（"文档已删除" vs "该库已不存在或无权限"）。

---

### O-7 一期上线时，5 块配置对默认路径仍然无效（🟡 中，体验风险）

**反对**：一期只交付 S-01 + S-02（无深度通道）。此时 AI 设置里已经出现「基础提示词 / Skill / 工具 / 预算 / 思考级别」5 块，而**用户点「AI 查找」默认走快速通道，这些配置依然不生效**——正是本次需求要消灭的「改了没反应」。

S-04 §3.6 文案表只改了措辞，没定义「一期深度未上线时」的呈现。若一期就挂 5 块可编辑配置，等于把老问题换个位置。

**替代方案**：一期给这 5 块加统一的**未生效横幅**（复用现有「未接入」的视觉语言，但文案改为"深度查找上线后生效"），或 S-03 与 S-01 同批上线。这是**分期方案的硬约束，必须与需求侧对齐**。

---

### O-8 跨库引用对既有生命周期路径的影响未核查（🟡 中）

**反对**：父文档 §4.4 风险表列了去重 key、AbortSignal、老配置等，但**没有核查事件侧路径**：事件关闭 / 进回收站 / 删除事件 / 恢复事件，这些路径对 `refs.json` 的处理是否受 `sourceScope` 影响？设计未取证。

**替代方案**：S-02 影响范围补 `src/lib/events/event-service.ts`、回收站相关路径的核查项，确认「事件侧操作只动本库 refs 文件，不触碰被引文档」这一既有判据在跨库后仍成立。

---

### O-9 `resolveFindTargets` 的读放大（🟢 低）

每请求读 `views.json` + 列 scopes。`scope-access.ts:49` 已有 mtime 缓存，复用即可；设计应显式声明「不自建缓存」，避免实现时各写一套。

## 二、认可点

| # | 认可点 | 理由 |
|---|---|---|
| 1 | 保留确定性快速通道 | 现有五步 <1s、可断言、零成本，直接换掉是纯损失 |
| 2 | `targets` 后端解析、前端不可传 | 从根上关掉越权入口，比"前端校验"可靠 |
| 3 | 引用去重 key 含 `sourceScope` | 这是正确性缺陷（跨库同名静默跳过），设计抓到了 |
| 4 | 深度通道工具作用域由 runner 注入 | 把权限边界留在服务端，而不是交给模型 |
| 5 | 同步 + abort 而非异步草稿 | 查找产物一次性消费，草稿机制确实是过度设计 |
| 6 | 候选三重校验（范围/存在性/未已用） | 防幻觉写脏 `refs.json` 的唯一有效手段 |

## 三、补充场景（设计未覆盖）

| # | 场景 | 期望 |
|---|---|---|
| S1 | 事件在 A 库，B 库文档被 B 库另一事件绑定且该事件不可检索 | 见 O-1 |
| S2 | 引用加入后，源库被删除 / 被移出配置 | 见 O-6 |
| S3 | 用户在查找进行中切换顶部 scope（事件页 scope 变化） | 弹窗应 abort 并提示，而不是把 A 库结果渲染在 C 库事件上 |
| S4 | 深度查找过程中配置被另一管理员修改（工具被关） | 本次查找按启动时快照执行，下一次生效；设计未声明 |
| S5 | `extraScopes` 含视图，且视图在查找期间成员变更 | 本次按启动时展开结果执行，响应 `targets` 如实回显 |

## 四、风险评估汇总

| 风险 | 等级 | 是否阻断实施 | 依据 |
|---|---|---|---|
| O-1 可见性未定义 | 🔴 高 | **是（一期）** | 会产生「加了却检索不到的幽灵引用」，且用户无法自查 |
| O-7 一期配置空转 | 🟡 中 | 是（体验） | 直接把本次需求要解决的问题换个位置 |
| O-2 / O-3 / O-4 / O-5 / O-6 / O-8 | 🟡 中 | 否（可在设计中补一段） | 均为一句话可补的缺口 |
| O-9 | 🟢 低 | 否 | 复用既有缓存即可 |

## 五、质疑结论

**设计主体成立**（方案选择、数据模型、权限模型、双通道取舍均站得住），但存在 **1 项高风险的语义缺口（O-1）** 与 **1 项分期方案的自洽性问题（O-7）**，建议在实施前补进设计。
