# 🎯 设计文档质疑报告：删除落回收站（REQ-20261123-005）

质疑对象：`design/DESIGN.md` + `S01~S05`（design-review 第 2 轮已通过）
质疑时间：2026-11-23
质疑姿态：假设"已通过评审"的设计仍有问题，逐条找代码证据

---

## 📋 设计上下文确认

- **核心目标**：删除可逆 —— 文档级（已实现，缺曝光）+ 组级（新实现）都能从回收站恢复
- **衡量标准**：删组后能在回收站看到组条目并整组恢复；MCP 空组删除同样可恢复；清库不产生回收站条目
- **覆盖范围**：回收站存储/服务、组删除执行层、治理 HTTP、契约 DTO、Web 删除弹窗与回收站页
- **排除范围**：scope 级入站、回收站清空按钮、wiki 源文件回滚、MCP 回收站工具
- **隐含假设（及失效后果）**：
  1. 组内文档的元数据（relations 分片）与正文（KB index.json）**一致** → 失效则快照漏篇（见反对意见 1）
  2. 附件目录是"每篇独立"的 → **该假设是错的**（见反对意见 2）
  3. 回收站条目到期清理的用户感知与文档条目一致 → 失效则用户不知情地丢失整组（见反对意见 4）

---

## ⚔️ 反对意见

### 意见 1：快照以 relations 分片为准会漏篇，且删完就永久没了

- **反对理由**：设计 §S03 方案 3 写「N 篇元数据 ← `loadRelations`」，而 `loadRelations`（`src/lib/group-delete.ts:283-291`）只读 relations 分片的 `hot_relations`；正文则是「按 group 读 index.json，取 relations 列表里的键」。也就是说**快照的篇目集合完全由分片决定**。但真正删数据的是 `fs.rmSync(kbGroupDir, {recursive})`（`group-delete.ts:700`）——它删的是**磁盘上所有文件**，包括「KB index.json 里有正文、分片里没有对应 relation」的文档。这类不一致在本项目有真实来源：`planGroupDelete` 本身就把两者分开统计（`willDelete.relations` 与 `willDelete.kbFiles` 是两个字段，`:55-64`），说明二者数量可以不等。
- **功能影响**：预期「删组后整组 8 篇都能恢复」→ 实际「分片里只有 7 篇，第 8 篇的正文随 rmSync 永久消失，且回收站里连条目都没有，用户根本不知道丢了东西」。
- **严重程度**：🔴 致命（不可逆数据丢失，且静默）
- **替代方案**：快照数据源改为 **KB 键 ∪ 分片键的并集**：① 两边都有 → 完整快照；② 分片有 KB 无 → 记 `doc.json`、无 `content.md`（残壳，与 S03 现有处理一致）；③ **KB 有分片无 → 以 KB 键补一条，`relationSnapshot` 缺失，恢复时重建最小元数据**（`text` + 默认分类），并在 `warnings` 里明说「N 篇缺少元数据，恢复后为最小记录」。`GroupSnapshotDoc` 增加 `source: 'both' | 'shard-only' | 'kb-only'` 以便恢复侧区分。
- **验证方法**：造一条"分片删掉、KB 保留"的不一致数据 → 删组 → 检查组快照 `docs/` 篇数是否等于 KB 键数 + 分片独有数。

### 意见 2：附件是"组级共享目录"，逐篇复制会 N 倍膨胀

- **反对理由**：设计 §S02 的目录布局把 `assets/` 放在 `docs/NNNN/` 下（每篇一份）。但 `getAssetsDir(scope, groupPath)` 返回的是 `{kbDir}/{group}/assets`（`src/lib/scope.ts:128-131`）——**整个 group 共用一份附件目录，不存在"某篇文档的附件"这个概念**。若某组 8 篇文档、assets 100 MB，逐篇复制会写出 800 MB，远超被删数据本身。而且现有单篇 `moveToTrash` 已经有这个毛病（`trash-service.ts:88` 每次复制整个 group assets），组快照会把它放大 N 倍。
- **功能影响**：预期「回收站保留该组一份完整副本」→ 实际「磁盘占用是原组的 N 倍，7 天保留期内可能撑爆数据盘，进而让后续删除因 ENOSPC 失败（而 fail-closed 会让用户删不掉任何东西）」。
- **严重程度**：🔴 致命（容量爆炸 → 反向导致删除功能不可用）
- **替代方案**：组级附件**只存一份**：`__group__…/assets/<序号>/` + `assets.json` 清单 `[{group, dir}]`（子组各自有 assets，故按 group 各存一份，不按文档）。恢复时一次性 `cpSync` 回各 group 的 `getAssetsDir`。`docs/NNNN/` 只留 `doc.json` + `content.md`。
- **验证方法**：构造单组 3 篇 + 一个 20 MB 附件 → 删组 → 断言组快照目录总大小 ≈ 原组大小（≤ 1.2 倍），而非 3 倍。

### 意见 3：到期清理会静默删掉整组，用户没有任何区分提示

- **反对理由**：`purgeExpired`（`src/lib/trash-service.ts:331-357`）对每个到期条目调 `removeTrashItem` 并 push 一个 brief `{group, name, dirName}`，不区分 `kind`。组条目到期时，用户看到的是"清理了 部署运维"，实际删掉的是 N 篇文档 + 全部附件。而 `expireAction='notify'` 模式下页面标红也只显示一行。
- **功能影响**：预期「到期前能看到"这个组里有 8 篇即将被清掉"」→ 实际「只看到一个组名，用户以为只是删了个空分组」。
- **严重程度**：🟡 重要（不可逆且信息不足，但不是设计缺陷型丢失）
- **替代方案**：`PurgeOutcome` 的 brief 增加 `kind` 与 `docCount`；`/governance/trash/sweep` 与设置弹窗的"将清理 N 条"文案补上"其中 M 个分组、共 K 篇"。
- **验证方法**：构造一个已到期的组条目 → `POST /trash/sweep {dryRun:true}` → 检查返回是否含 `kind` 与 `docCount`。

### 意见 4：恢复 event 类文档会带回悬空的 eventId

- **反对理由**：组内文档可能属于 `lifecycle='event'`（`relation.eventId`）。S04 说"期限重算复用 `recomputeLifecycle`，按各篇原分类"，而该函数对 event 分支的处理是**保留绑定**（`trash-service.ts:203-206`），并在注释里承认"事件是否仍存在由读侧校验，悬空引用由 diagnostics 暴露"。组删除→期间事件被删→恢复组，会一次性制造 N 条悬空引用。
- **功能影响**：预期「恢复的文档都能正常显示归属」→ 实际「恢复后这批文档挂着不存在的事件，页面归属信息异常，且只在 diagnostics 里能看到」。
- **严重程度**：🟡 重要
- **替代方案**：恢复组时对 event 类文档逐篇校验事件是否存在：不存在则降级为 `wiki`（并在 `hint` 里说明"K 篇的原事件已删除，已按长期保留恢复"）。这是对现状单篇行为的**有意改进**，需在 S04 决策点里显式声明（现状不校验，属已知缺口）。
- **验证方法**：造 event 文档 → 删组 → 删事件 → 恢复组 → 断言该篇 `lifecycle='wiki'` 且 hint 有说明。

### 意见 5：`dirSizeBytes` 在写锁内同步递归统计

- **反对理由**：组快照的 `sizeBytes` 由 `dirSizeBytes` 递归统计（`trash-store.ts:120-141`），在 `withScopeWriteLock` 内同步执行。组快照文件数是单篇的几十上百倍，大组会明显拉长写锁持有时间——而写锁期间所有该 scope 的写操作（导入、编辑、其他删除）都在排队。
- **功能影响**：预期「删除一个 200 篇的组耗时 < 3 s」→ 实际「拷贝 + 统计同步完成后才释放锁，期间 Web 端所有写操作转圈」。
- **严重程度**：🟡 重要
- **替代方案**：写入时 `sizeBytes` 先填 `0` 并标 `sizePending: true`，由列表读取时惰性补算并回写（读路径已经会读 meta，回写成本低）；或按 `docs` 文件数估算。**至少**应在 S03 待定项里给出"大组实测"的验收点。
- **验证方法**：构造 200 篇的组 → 删组 → 测量写锁持有时长与 Web 端并发写请求的排队时长。

### 意见 6：MCP "删空组"语义变化后，回收站会堆积无价值的空组条目

- **反对理由**：空组入站（已拍板 A）后，每次 `ki_group_delete_empty` 都会在 `.trash/` 留下一条 `kind='group'`、`docCount=0` 的条目，占用回收站列表与角标。AI 在自动化流程里频繁建删临时分组时，回收站会被空组条目刷满，把真正有价值的文档条目挤到后面（列表按 `deletedAt` 倒序，最新在最前）。
- **功能影响**：预期「回收站是"待处理的可恢复项"」→ 实际「回收站被无价值的空组条目占满，用户找真正的可恢复文档要翻页」。
- **严重程度**：🟢 建议
- **替代方案**：空组条目（`docCount === 0`）**不写入回收站**，但返回体里给出 `trash: null` + `hint: "空组无可恢复内容，已直接删除"`。或保留但默认折叠（列表加"隐藏空组"开关）。前者更简单，但违背"所有删除都可恢复"的一致语义——需你判断。
- **验证方法**：连续 `ki_group_create` + `ki_group_delete_empty` 10 次 → 检查回收站条目数。

## ✅ 认可点

- 「不可回滚区」的划分（窗口 1 成功前后区别对待快照回滚）是本设计最有价值的一处判断：它把 `executeLocal` 三段失败路径（`:688-690` / `:705-707` / `:726-728`）逐一对应到了正确的处置，避免了"回滚掉唯一副本"。
- 拒绝复用 `moveToTrash` 并给出 fail-closed 证据（`trash-service.ts:73-79`），挡掉了"空组接进去 100% 失败"的想当然实现。
- 先写 `meta.json` 骨架再写 `docs/` 的顺序，保证任何中途失败都留下"可见可删"的条目，而不是不可见磁盘垃圾。

## ➕ 补充场景与情况

| 场景 | 说明 |
|---|---|
| **组内文档名以 `__group__` 开头** | 文档条目 dirName 与组条目前缀撞名。现有 `resolveDirName` 会加时间戳，但语义上应禁止 relation 名以 `__group__` 开头（或组条目改用不可碰撞的命名，如 `.group-<stamp>`） |
| **同一 group 连续删两次** | 第二次删的是重建后的空组，产生第二条 `__group__` 条目。恢复两条都点到时会撞 → 需在 S04 冲突判定里覆盖（当前写的是"目标组非空拒绝"，两条都恢复第二条会被拒 ✓ 可接受，但用户会看到 409 却不知为何） |
| **组恢复过程中用户刷新页面** | 恢复是同步长事务（N 篇），HTTP 可能超时。S04 未定义超时阈值与前端等待策略 —— 建议 S04 待定项补"大组恢复的前端等待/重试" |
| **`ki backup` 快照会包含 `.trash`** | `trash-store.ts:10` 头注释确认回收站在 kbDir 内、会被 backup 覆盖 ✓ 好事，但组快照会显著放大备份体积，S02 风险节应提及 |
| **多窗口并发删同一组** | 写锁串行化，第二次 `planGroupDelete` 会 `GROUP_NOT_FOUND` ✓ 安全 |

## 📊 风险评估与建议

### 🎯 裁决结论

**⚠️ 修改 🔴 / 🟡 意见后进入开发**（整体方向成立，但意见 1、2 必须在实施前修掉）

### 识别的风险

- **风险 1**：快照漏篇 —— 分片与 KB 不一致时，正文随 `rmSync` 永久消失且无回收站条目 · 可能性 **中**（`planGroupDelete` 分两个字段统计即证明项目见过这类不一致）· 功能影响：**用户丢了文档却完全不知情**
- **风险 2**：附件 N 倍膨胀 —— 组级共享 assets 被逐篇复制 · 可能性 **高**（设计就是这么写的）· 功能影响：**磁盘写满后 fail-closed 让删除功能整体不可用**
- **风险 3**：到期清理无区分提示 · 可能性 **高** · 功能影响：**用户以为清了个空组，实际丢了 8 篇**
- **风险 4**：event 悬空引用 · 可能性 **中** · 功能影响：**恢复后归属信息异常，只在 diagnostics 可见**
- **风险 5**：写锁内递归统计拖慢并发写 · 可能性 **中** · 功能影响：**大组删除期间 Web 写操作排队**
- **风险 6**：空组条目堆积 · 可能性 **中** · 功能影响：**回收站信噪比下降**

### 风险等级

- **总体风险**：🔴 高风险（存在 2 条不可逆数据丢失路径）
- **风险分布**：🔴 2 个，🟡 3 个，🟢 1 个

### 行动建议

#### 必须处理（🔴）

1. 快照数据源改为 KB ∪ 分片的并集，`GroupSnapshotDoc` 加 `source` 字段 —— 否则**第 8 篇文档的正文会随组删除永久消失**
2. 附件改为组级单份存储（`assets/<序号>/` + `assets.json`）—— 否则**100 MB 附件组会写出 800 MB，写满盘后删除功能整体失效**

#### 建议处理（🟡）

3. `PurgeOutcome` 与 sweep 文案补 `kind` / `docCount` —— 否则**用户以为清的是空组**
4. 恢复组时校验 event 是否存在，不存在降级为 wiki —— 否则**一次恢复制造 N 条悬空引用**
5. `sizeBytes` 惰性计算或给出大组实测验收点 —— 否则**大组删除期间全站写操作排队**
6. 补 `__group__` 命名冲突与"两条组条目都恢复"的冲突提示

#### 可选处理（🟢）

7. 空组条目是否写入回收站，重新确认（与"所有删除都可恢复"的语义权衡）
8. S04 补大组恢复的前端等待/超时策略
